# BuckyOS Agent浏览器 PRD方向

## 一、产品定位

Agent 浏览器是 BuckyOS 中由 Personal Agent 主用、Owner 可直接使用的浏览器。浏览器运行在 Personal Server 上。只有手机的用户，也能从 BuckyOS 打开这个浏览器，自己看网页，或把当前的事交给 Agent 继续办。

BuckyOS 对网页交互的长期判断是，过去由人直接看的内容，可以先由 Personal Agent 阅读，再按这个人的关注点呈现。用户随时可以看原始页面。需要办事时，用户在对话里说清目标，Agent 操作网站，页面用来呈现内容和进度。

## 二、为什么现在做

Desktop 版已经可以通过 Computer Use 临时借用 Owner 的宿主浏览器。例如，Owner 已经登录 Gmail，Agent 就能借用现有会话读取邮件，省去针对这次任务单独走 Gmail API 授权的流程。这说明通用浏览器能给 Agent 提供跨网站的操作能力。BuckyOS 的标准环境是运行在 Linux 主机上的容器。面向普通用户的 Kiosk 可能装在一台类似 NAS 的无显示器盒子上，用户平时只有手机，Agent 此时没有桌面浏览器可借。

| 需求来源 | 要解决的问题 |
| --- | --- |
| Kiosk 与手机用户 | Personal Agent 在无桌面环境中也能访问和操作网页。Owner 可以从手机打开同一个浏览器，在需要时参与。 |
| BuckyOS 应用开发 | BuckyOS 作为 WebOS，应用往往需要在浏览器里验证。开发者委派前端任务后，Agent 能打开实际页面、检查效果并完成调试。 |
| AI Workspace 导出 PDF | 用户从手机发起画布导出时，由 Personal Server 完成页面排版和渲染，生成 PDF。 |

浏览器的版本和占用空间曾让单个需求有理由继续等待。现在网页代办、前端调试和 PDF 导出都需要浏览器能力，讨论的判断是推进这件事。前端调试和 PDF 导出可以由各自的工作入口触发，普通用户通过 BuckyOS 里的「Agent 浏览器」App 进入下面三种模式。

## 三、三种浏览模式

| 模式 | 用户看到什么 | 谁在操作 |
| --- | --- | --- |
| 原始页面模式 | Personal Server 上打开的原始网页，保留网站原有布局和交互。 | 用户可以直接操作，并在需要时交给 Agent。 |
| 重排模式 | Agent 根据用户为这个网站设定的偏好重新呈现的页面。 | 用户直接阅读、打开普通链接。依赖原网页的动作可由 Agent 代办，或切回原始页面继续。 |
| 对话模式 | 与当前网页关联的聊天和办理进度。 | 用户交代目标、补充信息。Agent 接手期间，网页供用户只读观察。 |

### 原始页面模式

用户在 BuckyOS 打开「Agent 浏览器」，即可使用某个 Agent 在 Personal Server 上运行的浏览器。网页资源由服务器加载。手机网络较弱时，原始页面可以用较低帧率呈现，优先让用户看清页面并完成操作。体验取决于手机到 Personal Server 的连接，以及 Personal Server 到网站的网络条件。

用户在这个浏览器里工作时，Agent 能利用当前页面和操作进度协助。比如用户已经找到办事入口，可以把后续步骤直接交给 Agent，从当前页面接着做。

### 重排模式

> 2026-11-25：重排的形态在二期改成了“个人重排站”（长期阅读的网站由 Agent 接入、定时更新、在首页连读），单个网页的重排只保留“只整理这一页”。见 [二期需求](<BuckyOS Agent浏览器 二期需求.md>)。下面两段是一期的方向，其中“按网站的偏好沿用设定”“在原网页上执行按钮再带回重排页”不再提供。

重排从阅读做起。有些旧网站在手机上难以打开或阅读。用户可以告诉 Agent「这个网站我只看更新日期、标题和正文，按手机单栏显示」。Agent 先打开原网页，再按这项偏好呈现。经常浏览的网站可以沿用设定，用户也可以带着当前页面进入对话，告诉 Agent 哪些内容需要保留、怎样排更顺手。

重排后的页面可以直接在手机上显示。弱网时，用户可用较少的传输量阅读内容。当用户点击依赖原网页交互的按钮时，Agent 可以在原网页上执行，并把更新后的结果带回重排页。用户也可以切回原始页面，沿用当前浏览进度。

### 对话模式

对话和网页共用一个 Work Session。用户可以围绕正在看的网页讨论重排，也可以直接说「我要办这项业务」，由 Agent 寻找入口、理解步骤并操作网页。

Agent 操作期间，用户可以查看网页进度，网页处于只读状态。Agent 尽量使用已经掌握的信息预填。遇到缺少的内容，就通过类似 Ask User 的交互在聊天框里提问，或只展示需要用户补填的几项。用户在对话里回答，Agent 把信息填到网页上，继续办理。

## 四、围绕一件事保持上下文

Work Session 按事情组织。一项任务可以经过多个页面或多个网站。Agent 在同一个 Session 里理解用户的目标、当前页面和已完成的步骤。用户可以在不同任务之间切换，回来接着办。网页显示方式改变，或者操作从用户交给 Agent，都应延续当前的页面和任务进度。

以一个入口难找的政务事项为例：

1. 用户从手机打开政务网站，发现菜单和流程在手机上难以操作，于是在对话里说清要办理的事项。
2. Agent 查找入口并操作网页。即使中途需要进入另一个网站，用户仍在同一个 Work Session 里查看进展。
3. Agent 先填入已有信息，办理遇到缺项时在对话里向用户询问。用户补充后，Agent 继续办理，并在对话中说明结果或当前卡在哪一步。

## 五、后续需要确定的产品选择

- **默认入口。** 第一次打开 Agent 浏览器时，默认从原始页面进入，还是先给用户一个可以直接交代任务的对话入口。
- **首批场景。** 选哪些老旧网站检验重排是否让手机阅读更方便，选哪些复杂流程检验 Agent 能否沿着用户目标把事情推进下去。
- **协作控制。** 如何让用户一眼看懂当前由谁操作、Agent 正在等什么，以及用户如何接手。
