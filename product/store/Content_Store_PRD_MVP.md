# Content Store PRD（MVP / 内容浏览与购买一体化）

基于语音记录与实际客户交流整理，用于指导产品、设计与 Figma 等 AI 设计工具出图

## 文档信息

- **文档版本**：V1.2
- **产品阶段**：MVP（桌面端优先）
- **文档目的**：在同一个 App 中跑通内容浏览、关联发现、收藏、购买/获取、安装与打开使用；仅看已有内容时提供传统 Library 体验
- **信息来源**：用户语音记录整理、实际客户交流反馈
- **本次调整**：在统一浏览与购买的基础上，明确 Store 主要收录公开的工业内容，Library 获取渠道不限，但不包括用户自己生产的传统个人内容；个人库收录与商店购买权益、实际可用状态分开。真实支付仍不在本期范围内

## 1. 产品定义与目标

客户希望在浏览自己的内容时，也能自然地发现、购买相关内容，不必在内容商店与 Library 两个 App 之间切换。只展示已有内容是传统 Library 的能力；本产品还要把已有内容与可获取内容放在同一浏览体系中，让用户看清内容之间的关联。

Content Store 因此定位为集内容浏览、购买/获取、管理与使用入口于一体的内容 App。浏览对象包括商店可获取内容、用户已有内容，以及用户收藏或手动添加的内容引用。Library 是同一内容视图的“已有内容”筛选，不再作为独立 App 或与商店割裂的一级页面。

MVP 在桌面端跑通“浏览已有或可获取内容 → 查看详情与关联内容 → 按需收藏、购买/获取 → 安装或直接打开 → 继续浏览”的完整闭环。购买后的内容仍是原来的内容对象，只更新用户权益与可用状态，不生成一份独立的 Library 副本。

当前版本只要求桌面端可用，界面可以偏工具化、结构化，不追求品牌化与最终视觉精修。未来会快速转向移动优先设计，因此本版需要在信息架构与交互上保留可扩展性。

- MVP 首要目标：跑通统一浏览、关联发现、获取与使用的流程，安装是其中一个环节。
- 当前只做桌面端主流程；移动端是下一阶段，不在本次设计交付范围。
- 产品保持开放：商店收录内容与用户自行添加的内容可在同一入口浏览；安装引导能力继续作为 SDK / 协议能力供第三方商店调用。
- 内容详情在桌面端使用浮层/模态层承载，未来移动端再切换到业内常见的独立详情页逻辑。
- 本期“浏览”包含查找、查看详情与关联、打开可用内容。应用、Agent 等复用各自的使用入口；媒体、书籍等未来可接入预览、播放或阅读能力，本期不新建通用播放器/阅读器。

### 1.1 Store 与 Library 的内容来源

| 维度 | Store | Library |
| --- | --- | --- |
| 内容定位 | 大部分是面向公众发布、发行的工业内容，通常有标准化的名称、作者/发行方、版本或商品信息 | 用户已有的内容产品集合，获取渠道不限；不包括用户自己生产的传统个人内容 |
| 典型来源 | 开发者、创作者或发行方公开发布的应用、Agent、模型等内容，后续扩展到游戏、书籍、媒体等 | Store 购买/获取、其他渠道购买、用户自行下载或导入的内容等 |
| 收录依据 | 是否进入公开分发目录 | 是否已由用户获取或将实际内容纳入个人库；不要求 Store 收录、商品标识或商店购买记录 |
| 信息完整度 | 通常具备较完整的公开元信息与获取条件 | 可以只有文件名、类型和来源，缺少发行方、价格或版本不影响入库 |

- 这里的“公开的工业内容”指面向公众发行的内容产品，不限于工业行业题材；“公开”描述其发布与可发现性，不代表免费。
- Store 与 Library 可以重叠，但 Library 不是 Store 已购商品的子集。用户自行下载、导入的内容即使在 Store 中不存在，也属于 Library。
- “来源不限”指获取渠道不限，不代表收录所有个人文件。本产品不包括用户自己生产的传统个人内容，例如个人照片、生活视频、私人录音；自行下载/导入也遵循这一内容边界。
- 边界按内容用途与形态区分，不按文件格式区分。例如，作为作品发行的视频、音频属于后续媒体内容范围，用户自己拍摄的生活视频、私人录音不属于本产品范围。
- 统一浏览展示 Store 目录与当前用户 Library 内容的并集。内容入库不等于发布到 Store，也不自动对其他用户可见。
- “已有内容”表示已纳入个人库，不要求当前一定可打开或安装；文件暂不可访问、类型尚不支持等情况通过可用状态表达，内容记录仍保留。
- 收藏或只添加商品 metadata 链接仅建立兴趣/引用记录，与将实际文件或内容导入 Library 分开。

## 2. 设计原则（供 UI / Figma AI 使用）

- 先把流程跑通：优先保证信息层级清晰、CTA 明确、状态变化可见。
- 桌面优先：建议以 1440px 宽度作为主画板基线设计，兼容 1280px。
- 中性工具风：简洁、理性、留白充足，适配未来嵌入第三方场景的开放生态感。
- 以内容为中心：已有内容与可获取内容共用分类、搜索、卡片和详情，通过筛选与状态区分。
- 连续浏览：收藏、获取与安装后保留当前分类、搜索、滚动位置和关联浏览路径，不强制切换到另一内容页。
- 关联可解释：展示“依赖”“可搭配使用”“同系列”等具体关系，并标明关联对象是否已有；不只给出无理由的“猜你喜欢”。
- 状态统一：同一个内容在列表、详情、关联卡片与安装队列中的个人库收录、商店权益、收藏、安装和运行状态必须实时同步。
- 模块化：同一套卡片骨架适配多种内容类型，不同类型仅在元信息区与操作区差异化。
- 可扩展：内容分类、详情模块、关系类型和安装引导选项都必须支持未来扩容。

> 建议设计语言：浅色底、深色文字、轻边框、少量强调色。不要在 MVP 阶段做重品牌化、强插画、复杂动效。

## 3. 范围与非范围

### 3.1 本期范围（In Scope）

- 单一内容浏览入口，提供“全部内容 / 已有内容 / 已收藏”范围筛选；“已有内容”即 Library 视图。
- 左侧分类 + 右侧内容卡片的双栏浏览结构。
- Header 内统一搜索，覆盖可获取内容与用户内容；可叠加范围和分类筛选。
- 用户自行下载/导入且符合第 1.1 节内容边界的库内内容参与统一展示与搜索，不要求存在 Store 商品或购买记录。
- 内容详情浮层（桌面端）。
- 详情中的关联内容模块，支持已有与未拥有内容之间的连续浏览。
- 收藏动作，与购买/获取权益分开。
- 价格/免费、个人库收录与商店权益展示、购买或获取确认，以及明确标注的模拟购买流程。
- 根据权益和可用状态提供获取、安装、查看进度或打开入口。
- 安装引导 Popup Window。
- 当前浏览页内的获取结果反馈与全局安装队列/进度展示。
- 内容浏览页右上角通过 package meta URL 手动添加内容。
- 多内容类型的统一展示骨架与基础状态体系。

按页面入口分（沿用原路径，仅说明产品入口，不定义新安装协议）

- 统一内容浏览页 /store_index，范围、分类、搜索为同一页面的视图条件。
- 内容详情入口 /content?content_id=xxx，App 内点击卡片以同一详情浮层承载。
- app 安装引导 /app_install?method=install_app&url=...&params...，复用公共安装能力。


### 3.2 明确不做（Out of Scope）

- 完整支付流程与真实购买结算。
- 移动端最终交互形态与适配。
- AI 自动翻译简介。
- 评分、评论、排行榜、个性化推荐算法、AI 自动构建内容知识图谱与复杂关系图编辑。
- 复杂社交能力（分享、关注开发者、社区讨论）。
- 完整的卸载、升级、回滚、批量安装管理。
- 丰富媒体资产展示（截图轮播、视频预览等），MVP 可不做。
- 统一媒体播放器、电子书阅读器，以及将各内容的完整使用界面搬进 Content Store。
- 用户自己生产的传统个人内容管理，如个人照片、生活视频、私人录音等；这是产品内容边界，不因后续增加媒体类型而自动纳入。

## 4. 信息架构（Information Architecture）

MVP 只有一个内容浏览主页面，不再使用“商店 / 我的内容”两个一级 Tab。用户通过同一页面中的范围筛选切换关注对象，分类、搜索、详情和安装队列保持一致。

| 层级 | 名称 | 说明 |
| --- | --- | --- |
| 主入口 | 内容浏览 | 汇总可获取内容、已有内容、收藏和手动添加引用，同一内容合并展示 |
| 范围筛选 | 全部内容（默认） | 同时浏览已有与未拥有的内容，明确显示权益与可用状态 |
| 范围筛选 | 已有内容（Library） | 仅展示已纳入个人库的内容，来源不限；包括已购买但未安装、用户自行下载/导入等内容 |
| 范围筛选 | 已收藏 | 展示用户标记为感兴趣的内容，可包含已有和未拥有内容 |
| 左侧二级分类 | 内容分类导航 | 从上到下排列，点击后切换右侧内容区域 |
| 右侧主区域 | 内容卡片区 | 按当前分类展示 Item Card 列表/网格 |
| 详情内导航 | 关联内容 | 按关系展示内容，可从已有内容继续发现未拥有内容，或反向查看 |
| 全局辅助 | 搜索 / 安装队列 / 添加内容 | 在所有浏览范围下可用，不要求先进入 Library |

范围筛选与内容类型是两个独立维度。例如，“已有内容 + Models”是用户已有模型；切换到“全部内容”后保留 Models 分类和搜索词，以便继续发现可获取模型。

> 本文统一使用“已有内容”表示 Library 范围。实际内容下载后纳入个人库或导入个人库即可成为已有内容；仅收藏或添加商品 metadata 引用不会自动入库。个人库收录不等于通过 Store 购买。

## 5. 内容分类体系

录音中对内容分类存在递进补充，综合后建议在 MVP 中采用“统一骨架 + 可扩展分类”的方案。为保证设计可落地，本文将分类拆为当前必须支持的类型与保留扩展槽位。

| 一级内容类型 | 二级说明 | MVP 处理建议 | 备注 |
| --- | --- | --- | --- |
| 应用 | 移植类应用（容器化迁移的传统应用） | 必须支持 | 示例：WordPress、n8n、Home Assistant |
| 应用 | 原生应用（基于平台原生 SDK 开发） | 必须支持 | 属于重点鼓励生态方向 |
| Agent | 可安装的 Agent / Sub-Agent | 建议支持 | 主 Agent 与 Sub-Agent 关系后续可细化，MVP 先完成安装入口 |
| Skills | Agent 能力扩展 | 预留类目 | 如开发资源不足，可先作为 Agent 下子类展示 |
| Models | 本地模型 | 建议支持并做前置条件提示 | 仅在本地 AI 能力满足时可安装 |

- Agent 类内容依赖系统至少配置一个可用的大语言模型 Provider。
- Models 类内容依赖本地 AI 能力与足够算力（如 GPU）。
- 即使系统当前能力不足，也建议允许用户浏览相关内容，但在详情页与安装按钮处明确前置条件。
- 关联展示可使用上述类型的元信息；实际安装/打开仅对已接入相应能力的类型启用，预留类型明确显示“暂不支持安装/使用”。MVP 至少以应用类型跑通获取、安装与打开流程。

## 6. 未来扩展方向（本期只预留，不设计细节）

- Media / Videos：作为作品或内容产品发行的视频、音频、图片、文件等数字媒体内容，仍遵循第 1.1 节对传统个人内容的排除边界。
- Games：游戏内容。
- Books：电子书或其他阅读内容。
- 更广义目标：成为覆盖多种数字内容类型的统一浏览、购买与使用入口。

> 未来新增大类沿用统一分类和范围筛选；同系列书籍、作品与扩展内容等关系沿用关联模块，不另建互相隔离的 Store 与 Library。

## 7. 用户任务流

### 7.1 主流程 A：浏览、获取并使用内容

1. 进入内容浏览页，默认范围为“全部内容”。
2. 选择分类或搜索，同时看到符合条件的已有内容与可获取内容。
3. 点击内容卡片，打开详情浮层，查看简介、价格/权益、使用条件与关联内容。
4. 按第 16 节选择主操作：可购买的付费内容显示“购买 + 价格”，免费内容显示“获取”；已有内容按可用状态显示“安装”或“打开”。
5. 点击购买/获取后，在当前 App 内完成权益检查与确认；MVP 购买演示规则见第 11 节，用户可取消并返回原详情。
6. 获取成功后原卡片与详情立即更新权益，内容自动进入“已有内容”范围；用户可选择立即安装或稍后再用。
7. 需要安装时打开安装引导 Popup，完成概览、配置和最终确认。
8. 安装请求被接受后关闭 Popup，原浏览上下文保持不变，全局队列和对应卡片显示进度。
9. 安装完成后显示“打开”等可用操作；有直接使用入口且无需安装的内容可直接打开。
10. 用户可继续浏览当前列表、查看关联内容，或主动切换“已有内容”筛选。

### 7.2 主流程 B：先收藏，后续再获取或使用

1. 用户在任一浏览范围中进入内容详情。
2. 点击“收藏”。
3. 内容进入“已收藏”筛选，权益和安装状态不变。
4. 用户后续在“已收藏”中再次打开同一详情，根据当前状态购买/获取、安装或打开。

### 7.3 主流程 C：手动添加商店外内容

1. 用户在任一浏览范围中点击右上角“＋ 添加内容”。
2. 在弹窗中输入 package meta URL。
3. 系统解析成功后，新增内容引用或与已有内容合并，标明“手动添加”来源。
4. 仅有 metadata 不代表已拥有或可安装；获取/可用资格明确后再提供对应操作。
5. 成功反馈提供“查看内容”；若当前筛选不包含该内容，保留筛选并提示其已添加，用户仍可直接打开详情。

### 7.4 主流程 D：从已有内容发现并获取关联内容

1. 用户选择“已有内容”，找到一个已安装的 Agent 并打开详情。
2. 在详情的“关联内容”中主动选择“查看全部关联内容（含未拥有）”，查看声明可配套使用的 Skill、依赖的 Model 等，以及各自的“已有”“免费”或价格标记和必要条件。
3. 用户点击一个未拥有的 Skill，在同一详情容器内进入该内容，保留“返回上一内容”的路径。
4. 用户查看配套关系与条件后，按需获取 Skill；安装能力已接入时可继续安装，未接入则明确提示。系统不因关联关系自动购买或安装其他内容。
5. 用户返回原 Agent，看到关联 Skill 的最新状态；关闭详情后仍回到原 Library 筛选与滚动位置。

### 7.5 主流程 E：只浏览和使用已有内容

1. 用户切换“已有内容”，列表与搜索结果显示其个人库内容，包括 Store 获取和自行下载/导入的内容。
2. 已购买但未安装的内容可安装，已可用内容可打开；无需先进入另一商店页面。
3. 关联模块默认展示已有的关联内容，提供“查看全部关联内容（含未拥有）”的显式展开入口，用户主动展开后才显示可获取内容。

自行下载/导入的内容不需要先匹配 Store 商品或补充商店购买记录；按实际能力提供打开/安装入口。暂不可用的内容仍显示在 Library 中，并说明具体原因。

## 8. 全局框架与页面结构

### 8.1 全局 Header

- 左侧：品牌 / 产品名（可极简）。
- 中部或右侧：统一搜索框，默认文案“搜索内容”。
- 右侧辅助操作：安装队列入口与“＋ 添加内容”。
- 内容区顶部：范围筛选“全部内容 / 已有内容 / 已收藏”，与搜索条件同时可见。
- 选择范围后搜索文案可变为“搜索已有内容”“搜索已收藏内容”，范围切换保留关键词。

### 8.2 左侧分类栏

- 纵向排列，从上到下展示分类。
- 建议包含：全部、应用、Agent、Skills、Models；如应用下需细分，可展开显示“移植类应用 / 原生应用”。
- 选中态明确，支持 hover。

### 8.3 右侧内容区

- 使用卡片网格为主，支持不同内容类型复用统一卡片骨架。
- 桌面端建议 3~4 列响应式卡片布局。
- 当内容较少时，优先保证卡片宽度与信息可读性，不必强行铺满。
- “全部内容”混合展示符合条件的已有与未拥有内容，不再拆成两套商店/Library 列表。
- 获取、安装等操作完成后保留当前列表位置，用卡片状态和轻量反馈提示变化。

## 9. 统一内容浏览页（Content Browser）

浏览页帮助用户在同一内容集合中查找已有内容、发现可获取内容，并进入统一详情。MVP 不需要复杂推荐首页；分类、状态和可解释的内容关联是主要发现方式。

| 模块 | 必备内容 | 交互要求 |
| --- | --- | --- |
| Header | 统一搜索、队列入口、添加内容 | 所有浏览范围共用 |
| 范围筛选 | 全部内容 / 已有内容 / 已收藏 | 与分类和关键词组合，不切换 App 或详情体系 |
| 左侧分类 | 全部 / 应用 / Agent / Skills / Models | 点击分类刷新右侧内容 |
| 内容卡片 | 图标、名称、类型标签、发行方、短描述、价格/权益与可用状态 | 点击卡片打开同一详情浮层 |
| 安装反馈 | 全局队列摘要与任务面板 | 安装开始后可见，浏览其他分类或范围时仍可访问 |
| 空状态 | 暂无内容 / 无搜索结果 | 提供返回上一级分类或清空搜索的引导 |

- 卡片不强制放购买或安装按钮，可统一进入详情后操作；已有且可用的内容建议提供快捷“打开”。
- 价格、个人库收录、商店权益、收藏和安装状态分别表达；不能把“未安装”当作“未购买”，也不能把“已收藏”当作“已拥有”。
- 商店未收录但用户已有、收藏或手动添加的内容仍可进入统一集合；缺少商店信息时展示可用元信息与来源。
- 自行下载/导入内容可仅凭个人库记录展示；没有商品价格、发行方等字段时无需补齐商店信息，也不默认展示购买按钮。
- 同一内容按稳定内容标识合并，保留来源信息；仅名称相同不视为同一内容。
- 库内内容没有 Store 商品标识时保留独立的个人库标识。若能确认其与公开内容对应，可关联商品信息，但保留用户文件及来源，不因同名直接覆盖。

## 10. 内容详情浮层（Desktop Modal / Overlay）

桌面端点击任何内容卡片后，默认以浮层而不是独立页面展示详情。这样可以更快跑通流程，也便于未来替换为移动端独立详情页。

| 区域 | 内容要求 | 说明 |
| --- | --- | --- |
| 顶部信息区 | 图标、名称、内容类型、发行方/开发商 | 信息一眼可识别 |
| 价格与权益区 | 免费 / 价格与币种 / 已有 / 权益待确认 | Store 商品按获取条件展示；库内内容显示“已有”及来源，无对应商品时价格与商店权益不适用 |
| 主 CTA | 购买 / 获取 / 安装 / 查看进度 / 打开 | 按权益和可用状态选择，规则见第 16 节 |
| 次 CTA | 收藏 / 取消收藏 | 仅记录兴趣，不改变权益和安装状态 |
| 简介模块 | 多语言描述 + fallback 逻辑 | 优先显示系统当前语言；无则 fallback 到默认语言 |
| 开发商/发行商模块 | 名称、简介、可信标识（可选） | MVP 不需要复杂品牌页 |
| 版本记录模块 | 历史版本 / 发布时间 / 更新说明 | 以列表或时间线形式展示 |
| 状态模块 | 个人库收录、商店权益、收藏、安装与运行状态 | 与列表、关联卡片和队列同步 |
| 关联内容模块 | 关系名称、关联卡片、关系说明、价格/权益及使用条件 | 支持已有与未拥有内容之间连续浏览 |

- MVP 不做自动翻译；只做语言匹配与 fallback。
- 不同内容类型可在详情中插入差异化模块，但外层骨架保持一致。
- 若前置条件不满足（如未配置 LLM Provider、GPU 不足），仍可展示详情，但安装按钮需置灰或点击后提示前置条件。

### 10.1 关联内容（MVP 必做）

| 关系类型 | 示例 | 展示要求 |
| --- | --- | --- |
| 依赖 / 被依赖 | Agent 依赖某 Model，某 Skill 需要指定 Agent | 明确方向、是否必需和当前满足情况 |
| 配套 / 扩展 | 应用的扩展包、Agent 可使用的 Skill | 仅按明确声明展示适用对象、版本等已知条件 |
| 同系列 / 同集合 | 一组工具、后续的同系列书籍或媒体 | 使用来源中明确的系列/集合信息 |
| 同作者 / 同发行方 / 同主题 | 同一发行方的其他内容、相同主题标签 | 展示具体关联理由；同主题不代表兼容或依赖 |

- 本期使用内容元信息中的显式关系、人工维护的关联，以及作者/系列/标签等可核实的匹配，不要求推荐算法或图谱可视化。
- 每个关联项至少表达目标内容、关系类型、简短理由和当前价格/权益、可用状态；关联模块复用同一套内容卡片与详情。
- 在“全部内容 / 已收藏”范围打开详情时，关联模块可同时展示已有与未拥有内容；在“已有内容”范围按第 7.5 节默认仅显示已有关系项。
- 关联模块不受原列表分类、关键词和来源筛选限制，例如 Agent 详情仍可展示关联 Model；仅继承是否只看已有的选择，并在本次关联浏览与返回过程中保留该选择。
- 点击关联卡片在当前详情容器内切换内容，提供返回上一内容入口，不层层叠加模态窗；关闭后恢复原列表上下文。
- 一个内容可同时存在多种关系，目标卡片不重复堆叠，关系可合并为多个标签。互相引用不触发无限展开。
- 无关系数据时隐藏模块或显示“暂无关联内容”；目标无法访问时标明不可用，不伪造价格、购买或安装入口。
- 关联关系也可连接用户自行下载/导入的库内内容与 Store 中的公开内容；缺少商品元信息不影响库内内容独立展示，不强制匹配或编造关系。

## 11. 购买 / 获取与权益检查（MVP 演示边界）

购买/获取发生在统一详情流程内。业务上先明确用户能否使用内容，再决定是否需要安装；已有权益的内容不重复进入购买确认。

### 11.1 确认与结果

- 未拥有、价格明确且购买能力可用的付费内容，主 CTA 显示“购买 + 价格”；确认层展示内容名称、价格、币种及已知使用条件。MVP 演示与未接入支付时的表现见第 11.2 节。
- 免费内容显示“获取”；获取成功产生已有权益，收藏不承担获取功能。
- 用户明确确认后才提交获取操作；取消、失败或权益未知时不标记已拥有、不自动安装。
- 检查中显示“正在检查获取资格……”，避免重复提交；结果不能一律当作通过。
- 获取成功后留在原详情，更新所有相关位置的状态，提供“安装/打开”及“稍后使用”选择；不自动切换范围或购买关联内容。
- 已有内容的安装仍需检查安装前置条件；已有权益不等于当前设备可安装或可运行。

### 11.2 本期支付处理

- 真实扣款、订单结算、退款和订阅计费不在本期范围。MVP 验收购买路径时使用明确标记的演示内容与模拟权益。
- 演示购买的价格与按钮旁、确认层和结果均标注“演示，不会扣款”；最终按钮为“模拟购买”，成功后的权益标记为“已有（演示）”。模拟权益仅用于演示数据，不得作为真实付费内容的访问授权。
- 可用约 1.5~2 秒的占位过程展示检查状态，但演示数据必须能覆盖成功、取消和失败分支，不能靠等待完成就默认获得权益。
- 对真实付费内容，如支付能力未接入，则显示“暂不支持购买”，允许查看详情与收藏，不绕过购买直接安装。
- 价格或权益未知时明确显示“价格待确认 / 权益待确认”，不推断为免费或已拥有；检查失败保留原内容状态并提供重试入口。

## 12. 安装引导 Popup Window（SDK 能力）

安装引导是可被 Content Store 和第三方商店共同调用的独立 Popup Window。它需要尽量简洁、通用，并能适配不同 UI 体系，作为开放安装协议 / SDK 的统一安装引导界面。

> Popup 在用户最终确认、安装请求被接受后关闭，不需要在 Popup 内展示长时间下载进度。进度由内容 App 的全局安装队列承接，保留原浏览范围、搜索和详情上下文。独立窗口承载公共安装能力，不要求用户切换到另一个 Store 或 Library App。

### 12.1 设计目标

- 轻量、简洁、中性，适配不同宿主产品。
- 清晰表达当前要安装的内容对象。
- 清晰展示必要配置项与开发者推荐配置。
- 安装请求被接受后关闭窗口，在宿主内查看进度；提交失败时留在引导中说明原因。
- Content Store 复用公共安装引导，应用安装检查与执行边界遵循现有 [App Service PRD](../app_service/BuckyOS_App_Service_PRD.md)，本次不增加另一套安装管理功能。

### 12.2 推荐步骤

| 步骤 | 名称 | 内容 | 主要按钮 |
| --- | --- | --- | --- |
| Step 1 | 安装概览 | 展示应用/内容的名称、图标、简介、来源、关键提示 | 下一步 |
| Step 2 | 配置选项 | 展示必要选项、开发者推荐选项、全部可配置项（重点是目录挂载、权限、公开/登录访问等） | 上一步 / 下一步 |
| Step 3 | 确认并开始安装 | 展示最终摘要，用户确认后开始安装 | 返回 / 开始安装 |

### 12.3 配置项设计要求

- MVP 重点围绕目录挂载、访问权限、是否公开访问、是否需要登录等配置。
- 配置分为：必填项、推荐项、可选高级项。
- 开发者可给出推荐配置，界面上需要明显标识“推荐”。
- 即使未来配置项扩展，界面结构也应支持长列表与分组。

## 13. 已有内容视图（Library）与全局安装队列

“已有内容”是第 9 节统一内容浏览页的范围筛选，满足只查看自己已有内容的传统 Library 需求。Library 获取渠道不限，包含 Store 或其他渠道获取、用户自行下载/导入的内容产品；不包括用户自己生产的个人照片、生活视频、私人录音等传统个人内容。已购买但未安装、已导入但暂不可打开等内容都保留在库中；仅收藏或只添加商品 metadata 引用不等于实际内容入库。

| 模块 | 内容要求 | 交互要求 |
| --- | --- | --- |
| 范围与搜索 | 已有内容 + 当前分类 + 关键词 | 只返回已有内容；可显式切换“全部内容”扩大搜索 |
| 内容卡片区 | 已有未安装、安装中、已安装、可用内容 | 优先表达安装/打开等下一步动作 |
| 详情与关联 | 复用统一详情，关联默认仅看已有 | 用户主动展开后可发现未拥有的关联内容 |
| 全局安装队列 | 正在执行、成功与失败的安装任务 | 所有范围可访问，点击任务进入同一内容详情 |
| 添加内容 | 实际内容入库与 metadata 引用分开 | 用户下载/导入形成的个人库记录直接纳入已有内容，不以 Store 权益检查为前提 |

- 安装开始后在当前页显示轻量反馈与队列摘要；用户可展开任务面板或继续浏览，不强制跳转。
- 切换分类、范围或打开关联详情不隐藏全局任务入口；同一个内容在队列、卡片、详情中的进度必须一致。
- 安装成功后权益保持不变，CTA 根据实际可用情况更新；安装失败也不丢失已获取权益。
- “已有内容”为空时提供“浏览全部内容”和“添加内容”入口，由用户主动选择，不自动混入未拥有内容。
- 缺少商店购买记录、商品元信息或当前无法打开，不影响库内内容在 Library 中展示与搜索；实际可用性单独标注。

## 14. 通过 URL 添加内容弹窗

MVP 需要保留一条商店外手动安装入口，以支持用户添加商店里暂时没有收录的内容。本节定义 package meta URL 添加流程；Library 的来源不限于此入口，用户自行下载/导入符合第 1.1 节范围的实际内容后，形成的个人库记录同样需要展示与检索。

| 元素 | 说明 |
| --- | --- |
| 入口位置 | 内容浏览页 Header 的“＋ 添加内容”按钮，所有范围均可见 |
| 弹窗标题 | 添加内容 / 从 URL 添加 |
| 输入项 | package meta URL（单行输入） |
| 辅助说明 | 提示用户填写可解析的 package metadata 地址 |
| 主按钮 | 添加 |
| 成功结果 | 在统一内容集合新增引用或合并已有对象，标明手动添加来源，并提供查看详情入口 |
| 失败结果 | 提示 URL 无效或解析失败，保留输入便于修改 |

- 此 metadata 添加弹窗只需暴露 URL 输入；实际文件下载/导入的交互不在本节展开，不能把本节的 URL 解析规则当作所有 Library 内容的入库要求。
- 若解析出的稳定内容标识已存在，提示“该内容已存在”并提供查看入口，不重复创建卡片；名称相同不能直接合并。
- 添加 metadata 只建立内容引用，不自动收藏、获取付费权益或判定可安装。用户后续获取或导入实际内容时建立个人库记录；自行下载/导入内容无需先经 Store 确认权益。
- 手动添加的内容可通过来源标记筛选找回；即使无商店收录记录，也应保留在统一浏览集合中。

## 15. 内容卡片设计规范

### 15.1 统一内容卡片（Content Card）

- 基础字段：图标、名称、类型标签；Store 商品还应展示发行方/开发商与短描述。库内内容可使用文件名、类型图标和来源，缺少商品元信息时不阻止展示。
- 必须区分：价格/免费、个人库收录、商店权益，以及收藏、安装状态；信息未知时如实标注，不适用的商品信息无需展示。
- 推荐字段：前置条件标签（需要 AI Provider / 需要本地算力）、来源标记。
- 交互：点击整张卡片进入详情浮层。

### 15.2 已有内容下的展示重点

- 复用同一卡片，突出可用状态与“安装/打开”等动作，不另建 Library 专属内容对象。
- 安装中时必须展示：进度条 + 当前阶段文案。
- 已安装后建议展示：版本号、最近状态、运行状态。
- 不同类型可在底部信息区差异化，例如 Agent 显示 Provider 状态，Model 显示大小/算力要求。

### 15.3 关联卡片

- 复用统一卡片的紧凑形态，额外显示关系名称与理由。
- “已有”及来源、可获取内容的价格/免费标记必须在关联模块内直接可见，不要求逐个打开才能判断。
- 关系本身不改变权益；“配套扩展”不表示自动包含在主内容的购买中。

### 15.4 统一卡片骨架

- 顶部：图标 + 名称 + 类型标签。
- 中部：摘要描述 / 类型关键信息。
- 底部：价格/权益区与状态区（收藏、安装进度、运行状态或前置条件）。
- MVP 优先保持骨架统一，避免为每个类型设计完全不同的卡片。

## 16. 状态体系（Global State Model）

个人库收录、商店权益、收藏和安装不是互斥的单一状态。用户可以同时“已入库 + 已收藏 + Store 已获取 + 未安装”，也可以“自行导入已入库 + 未收藏 + 商店权益不适用 + 可打开”。“已有”标签依据个人库记录展示，不限于商店购买权益。

### 16.1 独立状态维度

| 维度 | 状态示例 | 说明 |
| --- | --- | --- |
| 个人库收录 | 未入库 / 已入库 | 决定是否进入“已有内容”；获取或下载/导入产品范围内的实际内容都可建立个人库记录 |
| 获取条件 | 免费 / 付费及价格币种 / 暂不支持获取 / 价格未知 / 不适用 | Store 商品的获取条件；无对应商品的库内内容不要求价格信息 |
| 商店权益 | 未获取 / 已获取 / 待确认 / 不适用 | 决定从 Store 获取或使用其商品资源的权益；不作为自行下载/导入内容进入 Library 的前提 |
| 收藏 | 未收藏 / 已收藏 | 仅记录兴趣，与权益独立 |
| 获取过程 | 检查中 / 待确认 / 处理中 / 成功 / 失败 | 临时流程；取消或失败不产生新权益 |
| 安装 | 无需安装 / 未安装 / 配置中 / 安装中 / 已安装 / 安装失败 | 与权益独立，安装失败不等于失去内容 |
| 使用 | 可打开 / 运行中 / 不可用 / 待确认 | 由对应内容能力决定，安装成功不自动等于运行中 |
| 来源 | Store 获取 / 其他渠道获取 / 自行下载 / 导入 / metadata 引用等 | 获取渠道不限，同一内容可有多个来源；来源记录与商店购买权益分开 |

### 16.2 主 CTA 规则

| 条件 | 主 CTA / 反馈 |
| --- | --- |
| 获取或安装处理中 | 正在处理 / 查看进度，禁止重复提交 |
| 从 Store 获取/使用商品资源所需权益未知，或购买所需价格未知 | 检查权益 / 价格待确认；不阻止个人库记录展示，也不阻止使用用户另行导入的可用内容 |
| 未拥有，付费且购买能力可用 | 购买 + 价格；MVP 演示内容按第 11.2 节标注模拟购买 |
| 未拥有，真实付费且支付未接入 | 暂不支持购买；仍可收藏 |
| 未拥有，明确免费且可获取 | 获取 |
| 已有，需要安装且条件满足 | 安装 |
| 已有，但安装/使用条件不足 | 展示具体原因及可行修复入口，不能直接执行 |
| 已有且有可用入口（已安装或无需安装） | 打开 / 使用等类型对应动作 |
| 已安装但无直接打开能力 | 查看状态，不伪造打开入口 |
| 安装失败 | 查看失败原因；支持时提供重试入口 |

已有内容按实际安装/使用条件提供操作，无需等待 Store 价格或购买记录。用户自行下载/导入的内容可以显示“已有”，但不因此标记为“Store 已购买”；如另行获取 Store 商品资源，再按对应获取规则处理。

> 内容按稳定标识关联，个人库记录、商店权益、收藏与安装状态按当前用户及使用环境读取。列表、详情、关联卡片和任务队列使用同一状态来源；模拟权益始终保留演示标记。

## 17. 搜索、筛选与排序

- 统一搜索覆盖商店可获取内容与用户已有、收藏、手动添加内容，检索字段包含名称、短描述、开发商/发行方、标签和类型。
- 范围筛选决定结果集合：“全部内容”返回公开 Store 目录与当前用户内容的并集；“已有内容”按个人库记录筛选，包含自行下载/导入内容；“已收藏”按收藏标记筛选。
- 范围、分类、关键词和来源等已选条件需可见；切换范围保留分类与关键词，并支持清空条件。
- 同一内容在搜索结果中只出现一次，展示当前权益与可用状态；商店未收录的用户内容也能被搜到。
- “已有内容”无匹配结果时可提示“在全部内容中搜索”，由用户点击扩大范围，不自动混入购买结果。
- MVP 以搜索与左侧分类为主，不强制加入复杂排序器。
- 若需要排序，建议仅保留“默认 / 最近更新 / 最近添加”三种简单模式。

## 19. 前置条件与能力约束

- Agent 内容至少要求系统存在一个可用的大语言模型 Provider。
- Models 内容要求系统具备本地 AI 能力，且在需要时满足本地算力条件。
- 前置条件不足时，建议策略为“可浏览详情、不可直接安装”，并明确展示阻塞原因。
- 前置条件提示可以出现在卡片标签、详情提示条、安装按钮禁用说明中。
- 已知安装条件不足时，应在购买/获取确认前说明；用户可明确选择先获取、稍后使用，但不能把获取成功表示为当前环境可用。
- 关系中有必需依赖时展示依赖是否已有、可用及需要单独获取的情况；缺失必要条件时阻止直接安装。可选配套内容不应被当成安装阻塞项。
- 对未知兼容性显示“兼容性待确认”，不因同作者、同标签或出现在关联模块中就承诺可配套使用。

## 21. 关键交互与边界情况

- 重复收藏：已收藏内容显示“取消收藏”；取消收藏不移除已有权益或安装，不删除手动添加的引用。
- 重复添加 URL：按稳定内容标识合并，提示已存在并可查看；同名不同内容不合并。
- 重复购买/获取：处理中禁止重复提交，提交前再次检查权益；已拥有则更新为安装/打开等动作，不再创建获取操作。
- 获取取消或失败：保持原权益、收藏状态和浏览位置；可重试，不自动进入安装。
- 获取成功但稍后安装：内容立即属于“已有内容”，不能等安装完成才出现。
- 前置条件不足：安装按钮置灰或点击后说明原因，不应静默失败。
- 安装中再次打开详情：应看到安装状态与进度，而不是重新显示默认“安装”。
- 安装成功后：当前列表与所有关联卡片同步显示实际可用状态，不强制跳转。
- 关联对象不可用或无关系数据：说明情况或隐藏空模块，不生成虚假推荐；循环关系允许返回但不自动递归展开。
- Library 范围：默认列表、搜索和关联内容仅看已有；用户显式展开全部关联后可查看并获取未拥有内容，返回列表仍保留原筛选。
- 商店内容下架：用户已有内容的记录仍保留；能否继续使用依据实际权益与可用性，缺失信息显示待确认。
- 商店数据加载失败：已有内容数据可用时仍支持 Library 浏览与打开，提示可获取内容暂不可用，不清空用户内容。
- 自行下载/导入内容没有 Store 商品或购买记录：正常入库、展示与搜索，按实际能力打开；文件暂不可访问时保留记录并标明原因。
- 搜索无结果：应提供清空搜索的恢复操作。
- 分类为空：显示空状态而不是空白页。

### 21.1 MVP 验收场景

1. 同一关键词下存在已有与未拥有内容：“全部内容”同时命中且不重复；切换“已有内容”后仅剩已有项，关键词与分类保留。
2. 收藏未拥有内容：只进入“已收藏”，不进入 Library；模拟购买成功后显示“已有（演示）”，无需安装即可在演示 Library 中找到，取消收藏不影响该权益。
3. 从已有 Agent 查看关联 Skill：Library 默认只显示已有关系项；主动展开全部关联后，能看到未拥有 Skill 的关系理由与价格，获取后各处状态同步，返回路径不丢失。
4. 从当前搜索结果安装内容：安装请求被接受后 Popup 关闭，队列可见，列表筛选与位置不变；切换范围仍可查看任务。
5. 获取取消/失败、真实支付未接入：不新增权益、不开始安装；安装失败则保留原已有权益。
6. 添加未收录内容 URL：能从统一搜索和手动添加来源中找回；重复添加不生成副本，仅有 metadata 时不标记已拥有。
7. 已有内容具有可用入口时可直接打开，无需另开 Store 或 Library 查找；无打开能力时只展示实际可用操作。
8. 一项用户自行下载/导入的应用包没有 Store 商品、价格或购买记录：仍出现在 Library 与统一搜索中；暂不可打开时保留记录，入库不会将它发布到公共 Store。
9. 用户目录中同时存在自行下载的应用包与用户自己拍摄的照片、生活视频、私人录音：Library 可收录前者，后者不因导入或目录扫描而进入本产品的内容浏览与搜索范围。

## 22. 指标建议（用于验证 MVP 是否跑通）

- 浏览到详情转化率。
- 关联内容曝光到点击率，以及从已有内容出发的关联获取率。
- 购买/获取确认完成率与失败率；模拟购买单独统计，不作为真实成交指标。
- 详情到安装引导打开率。
- 安装引导完成率。
- 安装成功率。
- 首次安装完成耗时。
- URL 手动添加成功率。
- 已有内容查找后成功打开率、从查找到打开的耗时。
- 从浏览到获取并首次使用的任务完成率；验证过程中记录是否需要切换到独立 Store/Library App，以及返回原内容时是否丢失上下文。

## 24. 设计补位假设（为出图而做的明确化）

- 主浏览页使用“全部内容 / 已有内容 / 已收藏”范围筛选，不设独立商店与 Library 一级页。
- Store 大部分是公开发行的工业内容；Library 获取渠道不限，自行下载/导入的内容产品也算，不要求商店购买记录或当前可用；用户自己生产的传统个人内容不在产品范围内。
- “已有内容”列表、搜索与关联默认只看已有；扩大搜索或展开未拥有的关联内容都由用户主动触发。
- Skills 在 MVP 中预留为类目；如资源紧张，可先并入 Agent 分类。
- 卡片与详情展示必要价格/权益信息；真实支付未接入时按第 11 节演示，不把资格检查占位当作购买成功。
- 下载/安装长流程由全局队列展示，获取和安装后均保留当前浏览上下文。
- 关联内容是本期核心能力，使用显式元信息、人工关联与可核实匹配；不要求复杂算法或关系图。
- 桌面端优先采用统一卡片骨架，避免不同内容类型造成过度碎片化。

**共 6 个设计对象**：统一内容浏览页（含 Library 筛选）、统一详情浮层（含关联浏览）、购买/获取确认与状态层、安装引导 Popup、全局安装队列、通过 URL 添加内容弹窗。具体画面以第 23.2 节为准。
