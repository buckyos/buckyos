# BuckyOS Desktop · Node Updater 设计

Node Updater 是随 BuckyOS Desktop 安装包交付的独立 Rust 程序。在线和离线安装包均采用**方案 B：先迁移数据，再覆盖程序文件**。安装程序停服后运行目标版本的 Node Updater。只有迁移成功，安装程序才替换程序文件并启动新版 BuckyOS。迁移失败时，旧版二进制仍在，回滚只涉及已经变更的数据。

## 一、已确定的设计

### 1. 为什么桌面版需要独立的升级入口

BuckyOS 已经有基于 Repo 的分布式升级机制。在运行中的系统里，每个节点的 Node Daemon 根据 Consistent Config 中保存的标签、所管理的 PIKG 版本和实际运行版本判断是否需要升级。这套机制支持在指定节点升级指定的 PIKG 或二进制文件。

桌面场景还有两个问题。其一，传统部署由运维人员编排升级，在 System Config 里设置目标。普通桌面用户需要由安装程序代办整个升级过程。其二，Node Daemon 能升级它管理的服务，自身的二进制也需要一个外部程序替换。

0.7 / Beta 2.2 主要面向单节点或单一拓扑交付。从用户角度，可以把整套 BuckyOS 当作 PC 上的一项系统服务。现有桌面安装包已经能停止服务、覆盖程序文件、重新启动服务。利用这个停机窗口，安装程序可以一并替换 Node Daemon，并在启动前取得 Node Updater 的迁移结果。

完整的分布式升级按规划在 0.8.0 / Beta 3 处理，涉及多节点编排、镜像、ext tools 和 export 的升级，以及允许部分升级、强制升级和升级期间持续提供服务的条件。

### 2. 安装程序与 Node Updater 的职责

在线和离线安装包遵循同一条规则。安装程序可以替换随包发布的程序文件和程序自带的配置。遇到持久化的系统配置，按**存在即跳过**处理。即使新安装包带有更新的默认值，也要把已有配置交给 Node Updater 处理。

| 对象 | 安装程序 | Node Updater |
| --- | --- | --- |
| 程序文件、Node Daemon 二进制、随程序发布的配置 | 按安装包内容部署或替换 | 数据迁移范围之外 |
| 持久化的系统配置 | 配置缺失时执行 seed config，已有配置跳过 | 读取已有配置的 schema，按需迁移 |
| 服务数据和用户的应用数据（AppData） | 覆盖安装时保留 | 按模块检查 schema，处理需要转换的部分 |
| 用户自己的文件，如 home 中的文档 | 保留原文件 | 迁移和备份范围之外 |

安装程序调用**目标安装包自带的 Node Updater**，并根据其结果决定是否继续。Node Updater 读取已安装的 BuckyOS 发布版本，以自身所属的发布版本为目标。它支持向上迁移已有数据。数据格式高于自身读取能力时，返回失败。

#### 覆盖安装执行顺序（方案 B）

1. 安装程序从目标安装包单独解压 `node_updater`。如目标版本启用了最低 SDK 限制，先完成第 7 节的应用兼容性检查和必要的用户确认。
2. 安装程序停止 BuckyOS，包括 Node Daemon，再运行刚解压的 `node_updater`。
3. Node Updater 备份并迁移需要处理的数据，返回第 6 节定义的结果。收到失败结果，安装程序即中止覆盖安装。只有数据已恢复到旧版可读状态时，才可以重新启动旧版。
4. 收到成功结果后，安装程序替换程序文件，包括 Node Daemon。部署完成后启动新版 BuckyOS。如果覆盖程序文件时出错，安装程序保持停服，提示用户重新运行同一版本的安装包。已迁移的数据保留，重跑时仍从安装包解压并执行 `node_updater`。各模块均已达到目标 schema 时，`node_updater` 直接返回成功，安装程序重新覆盖程序文件，完成后再启动服务。

此前讨论的方案 A 顺序为停服、覆盖程序、迁移数据、启动新版。该顺序下，迁移失败时还需要恢复旧程序文件。方案 B 将这次覆盖放在迁移成功之后，省去了这一步回滚。

### 3. 按依赖关系和持久化 schema 执行迁移

Node Updater 提供统一入口，模块开发者声明数据之间的依赖。对于直接管理的数据区，先处理底层数据，再处理依赖它的上层数据。对于托管在系统服务里的应用状态，底层先提供旧数据，上层模块根据业务含义生成修改动作，最后由拥有该数据的系统服务迁移组件统一提交。每一步都要能从持久化数据区取得实际的源 schema 版本，再与目标模块使用的 schema 比较。BuckyOS 发布版本用于识别起点和目标，同一发布跨度内，各模块可以有不同的迁移需求。

- **schema 相同就跳过。** 例如，新旧 BuckyOS 中 Message Center 的数据都是 schema 7，本次覆盖安装可以直接保留该数据区。
- **需要转换时，由模块提供确定的转换逻辑。** 例如，新 schema 增加必填字段，迁移程序要根据业务含义为旧记录补值。数据结构有变化时，迁移程序读出旧结构，写成目标结构。
- **模块已兼容的格式可以继续保留。** 例如，消息服务能读取不同客户端版本的 Message Object，并允许按收到时的格式持久化。已有消息可以继续由服务读取，升级时无需逐条重写。

**每个模块的数据迁移都以一次原子提交（apply）完成。** 模块先准备转换结果，最后将新数据和对应的目标 schema 标记一起提交。提交前中断，数据区仍是旧数据和旧标记，重跑时可以重新迁移。提交后即使进程来不及报告成功，重跑也会读到目标 schema，跳过该模块的转换和写入。即使程序文件只覆盖了一部分，这个判断也以数据区中实际提交的标记为准。

#### 各模块的 data reader

每个模块将自己的 data reader 实现为 Rust 库，在同一个库内维护当前格式和该模块支持的旧 schema 的读取代码。Node Updater 在构建时直接链接各模块的 reader，复用模块的 Rust 库写入当前格式。模块负责人维护业务数据的读取与转换，Node Updater 负责调度并汇总结果。

所有模块的 reader 集中登记在同一个注册文件里。每项登记要能定位模块、reader 库和相关源文件，供后续 schema 审计使用。

#### System Config 中的应用配置如何离线迁移

System Config 是类似 etcd 的键值存储，多个应用的配置和系统内核配置共用这项服务。覆盖安装期间 BuckyOS 已停机，System Config 的在线接口不可用。Node Updater 在停机窗口内按以下顺序处理这份共享状态。

1. **导出旧配置。** Node Updater 通过 System Config 的迁移组件直接读取旧版持久化数据，导出同一份配置快照（dump）。各模块从快照中读取自己管理的 key 及其对应的 JSON 值。
2. **由各模块生成修改动作。** 每个模块根据自己配置的源 schema 和目标 schema，返回需要执行的操作列表（OP list）。例如，某个应用要为配置增加必填字段，就根据旧 JSON 算出新值，并返回对该 key 的更新操作。操作沿用 System Config 已有的事务语义。生成列表期间，各模块看到的都是升级前的值。
3. **由 System Config 一次提交。** 等所有相关模块都生成操作列表后，System Config 迁移组件将它们与自身所需的内核配置变更合并，在离线存储上执行一次原子更新。应用配置、内核配置及其对应的 schema 标记在同一事务中生效。若有模块无法生成操作，或事务提交失败，System Config 保留旧状态，Node Updater 向安装程序报告失败。

其他由系统服务托管的应用状态也遵循这个分工。服务提供旧数据，依赖该服务的模块生成业务变更，再由该服务的迁移组件将变更合并并写回。原子提交的边界是该服务管理的数据区。

### 4. 备份、迁移和失败恢复

1. **先处理系统配置。** 这部分数据通常较小，可以在转换前备份。若转换失败，由 Node Updater 使用备份恢复。系统配置阶段成功后，再进入应用数据阶段。
2. **再处理服务和应用数据。** 当前各模块的 AppData 都是体量较小的结构化数据。对本次需要变更的数据区，先备份、再转换。如果后续模块迁移失败，恢复本次已改动的数据，包括先前已迁移的依赖配置，使旧程序可以读回同一版本的数据。用户个人文件保留原样。

上述数据回滚适用于迁移阶段失败。迁移已成功、随后覆盖程序文件出错时，按第 2 节重跑同一版本的安装包，继续完成目标版本的部署。

### 5. 模块负责人和发版流程

模块在创建持久化状态时，必须把实际采用的 schema 版本写入数据区。格式发生变化时，模块负责人要同步维护版本标记。如果新格式仍被标成旧 schema，Node Updater 可能选错转换逻辑，甚至损坏数据。

每次正式发布前，各模块负责人核对本模块的持久化 schema。发生变化时，确认模块能否自行读取历史数据。需要离线迁移时，由熟悉业务的模块负责人提供对应的转换。发布记录应列出每个正式发布的 BuckyOS 版本及各模块随该版本交付的 schema，内部测试期间出现、从未正式发布的格式不计入历史兼容范围。

后续可在 Git commit hook 中使用 reader 注册文件匹配本次提交涉及的文件。命中时，触发“此次变更是否需要升级 schema”的审计，由模块负责人确认是否调整版本标记和补充迁移代码。

### 6. 返回值与历史兼容

当前没有需要兼容的历史发布版本。本期先定义 `node_updater` 返回给安装程序的结果，后续首次出现已发布的旧 schema 时，再补充相应的历史读取和转换逻辑。下表给出结果语义和建议的状态名。

| 迁移结果 | 返回信息 | 安装程序的动作 |
| --- | --- | --- |
| 成功（`success`） | 数据已达到目标格式。所有模块均可跳过时，也返回成功。 | 继续覆盖程序文件。 |
| schema 不受支持（`unsupported_schema`） | 返回模块、数据区的实际 schema、目标 schema，以及原因（过旧或过新）。将来启用最低支持范围后，过旧时还要返回仍可读取该数据的最新过渡安装包版本。 | 中止覆盖，显示不兼容原因。有过渡版本时，向用户指出应先使用哪个 BuckyOS 安装包。 |
| 迁移失败（`migration_failed`） | 返回失败步骤和原因。模块内出错时附上模块名。 | 中止覆盖，报告失败。 |

两类失败结果都应说明数据恢复状态，区分“未改动”“已回滚”和“恢复未完成”。数据未改动或已回滚，且原程序能读取时，可以重新启动旧版。恢复未完成时保持停机。

随着正式版本发布，reader 按实际发布过的 schema 积累兼容能力。即使按周发布 BuckyOS，只要某个模块的 schema 沿用多个版本，该模块就可以共用已有处理逻辑。

长期设计允许按组件设置最低支持的 schema。启用下限后，遇到过旧的数据时，Node Updater 应返回失败，指出受影响的组件及其 schema，并给出**仍能读取该 schema、可用于下一步升级的最新 BuckyOS 安装包版本**。各代安装包支持的范围需要相互衔接。

例如，某组件当前使用 schema 70，能直接从 schema 50 升级。用户的数据仍是 schema 10。如果某个历史安装包能读取 10 并写成 50，用户就先运行该安装包，再运行当前安装包，完成 **10 → 50 → 70**。这里的数字是组件的 schema 版本，返回给用户的过渡版本应是可识别的 BuckyOS 发布版本。

### 7. SDK 兼容性与已安装应用

BuckyOS 发布新版 SDK 时，默认向下兼容。例如，基于 SDK 100 开发的应用，在系统升级到 SDK 120 后仍能加载和运行。只有某次发布确实要停用旧 API 时，才由发布工具为该版本明确指定允许加载应用的最低 SDK 版本。

若目标发布版本启用了该限制，安装程序在运行停机迁移之前检查已安装应用。若有应用使用的 SDK 低于下限，升级检查返回受影响的应用清单，安装程序向用户说明哪些应用升级后将无法加载，以及原因。用户确认后才继续，用户取消则结束本次升级。升级完成后，新系统在加载应用时执行同一条最低版本规则。

## 二、重试验收用例

| 中断位置 | 重跑同一版本安装包时的预期结果 |
| --- | --- |
| 模块 A 已提交，模块 B 在 apply 前中断 | A 的转换和写入次数保持一次。B 读到旧数据和旧 schema，重新迁移后，新数据和目标 schema 同时可见。 |
| 模块 apply 已完成，进程在返回结果前中断 | 重跑通过持久化的目标 schema 识别该模块已完成，跳过写入。再次运行后数据内容与首次提交结果一致。 |
| 所有模块已迁移成功，安装程序在覆盖部分程序文件后报错 | 第一次安装保持停服并提示重跑。第二次运行时所有模块均跳过，`node_updater` 返回成功。安装程序重新覆盖程序文件。验证服务仅在部署完成后启动，运行的是目标版本。 |
