# BuckyOS Desktop · Node Updater 设计

**Node Updater 只适用于 BuckyOS Desktop（单机版）。** 单机版没有 etcd。System Config 使用本机的 sled 键值库，所有 RDB 实例均使用本机 SQLite 数据库。

Node Updater 以独立 Rust 程序随 Desktop 安装包交付。在线和离线安装包均采用**方案 B：先迁移数据，再覆盖程序文件**。停服后，目标版本的 Node Updater 在临时工作目录准备并校验各模块的迁移结果。全部通过后才统一提交到正式数据区（apply）。安装程序在提交成功后替换程序文件并启动新版 BuckyOS。

## 一、已确定的设计

### 1. 为什么桌面版需要独立的升级入口

BuckyOS 已经有基于 Repo 的分布式升级机制。在运行中的系统里，每个节点的 Node Daemon 根据 Consistent Config 中保存的标签、所管理的 PIKG 版本和实际运行版本判断是否需要升级。这套机制支持在指定节点升级指定的 PIKG 或二进制文件。

桌面场景还有两个问题。其一，传统部署由运维人员编排升级，在 System Config 里设置目标。普通桌面用户需要由安装程序代办整个升级过程。其二，Node Daemon 能升级它管理的服务，自身的二进制也需要一个外部程序替换。

0.7 / Beta 2.2 的 Desktop 安装包在本机部署整套 BuckyOS。从用户角度，可以把它当作 PC 上的一项系统服务。现有桌面安装包已经能停止服务、覆盖程序文件、重新启动服务。利用这个停机窗口，安装程序可以一并替换 Node Daemon，并在启动前取得 Node Updater 的迁移结果。

多节点部署的分布式升级另有规划，0.8.0 / Beta 3 处理多节点编排、镜像、ext tools 和 export 的升级，以及允许部分升级、强制升级和升级期间持续提供服务的条件。

### 2. 安装程序与 Node Updater 的职责

在线和离线安装包遵循同一条规则。安装程序可以替换随包发布的程序文件和程序自带的配置。遇到持久化的系统配置，按**存在即跳过**处理。即使新安装包带有更新的默认值，也要把已有配置交给 Node Updater 处理。

| 对象 | 安装程序 | Node Updater |
| --- | --- | --- |
| 程序文件、Node Daemon 二进制、随程序发布的配置 | 按安装包内容部署或替换 | 数据迁移范围之外 |
| 持久化的系统配置 | 配置缺失时执行 seed config，已有配置跳过 | 读取已有配置的 schema，按需迁移 |
| 服务数据和用户的应用数据（AppData） | 覆盖安装时保留 | 按模块检查 schema，处理需要转换的部分 |
| 用户自己的文件，如 home 中的文档 | 保留原文件 | 迁移和备份范围之外 |

安装程序调用**目标安装包自带的 Node Updater**，并根据其结果决定是否继续。Node Updater 读取已安装的 BuckyOS 发布版本，以自身所属的发布版本为目标。它支持向上迁移已有数据。数据格式高于自身读取能力时，返回失败。

**在线安装脚本默认可交互，只有显式传入 `--silent` 才进入静默模式。** 普通安装遇到需确认的事项时由用户选择继续或取消。静默安装将该模式传给预检、安装 hook 和 `node_updater`，即使从终端启动也全程无需应答。定时任务须显式传入 `--silent`。

#### 覆盖安装执行顺序（方案 B）

1. 安装程序从目标安装包单独解压 `node_updater`。如目标版本启用了最低 SDK 限制，先完成第 7 节的应用兼容性检查。静默安装在任何环节遇到需要用户确认的情况，都记录原因并以非零状态结束本次安装。停服前退出时，旧服务继续运行。
2. 安装程序停止 BuckyOS，包括 Node Daemon，再运行刚解压的 `node_updater`。
3. Node Updater 按第 3、4 节准备结果并执行最终 apply。返回失败时，安装程序中止覆盖，并根据第 6 节的数据状态决定能否恢复旧服务。
4. 收到成功结果后，安装程序替换程序文件，包括 Node Daemon。部署完成后启动新版 BuckyOS。如果覆盖程序文件时出错，保留已提交的数据并保持停服。交互安装提示重跑同一构建，静默安装记录该构建供下次续装。重跑仍从原包解压并执行 `node_updater`，验证目标 schema 已生效后跳过重复迁移，完成程序覆盖再启动服务。

此前讨论的方案 A 顺序为停服、覆盖程序、迁移数据、启动新版。该顺序下，迁移失败时还需要恢复旧程序文件。方案 B 将这次覆盖放在迁移成功之后，省去了这一步回滚。

### 3. 按依赖关系和持久化 schema 执行迁移

Node Updater 提供统一入口，模块开发者声明数据之间的依赖。对于直接管理的数据区，先准备底层数据的转换结果，再处理依赖它的上层数据。对于托管在系统服务里的应用状态，底层先提供旧数据，上层模块根据业务含义生成修改动作，由拥有该数据的系统服务迁移组件合并。每一步都要能从持久化数据区取得实际的源 schema 版本，再与目标模块使用的 schema 比较。BuckyOS 发布版本用于识别起点和目标，同一发布跨度内，各模块可以有不同的迁移需求。

- **schema 相同就跳过。** 例如，新旧 BuckyOS 中 Message Center 的数据都是 schema 7，本次覆盖安装可以直接保留该数据区。
- **需要转换时，由模块提供确定的转换逻辑。** 例如，新 schema 增加必填字段，迁移程序要根据业务含义为旧记录补值。数据结构有变化时，迁移程序读出旧结构，写成目标结构。
- **模块已兼容的格式可以继续保留。** 例如，消息服务能读取不同客户端版本的 Message Object，并允许按收到时的格式持久化。已有消息可以继续由服务读取，升级时无需逐条重写。

**所有模块共用一次最终 apply。** 准备阶段只读正式数据，各模块在本次升级的临时工作目录生成新数据或待执行的变更清单，以及对应的目标 schema 标记。依赖模块需要使用前一步的新数据时，从工作目录读取。只有所有模块都通过校验且已无待确认项，Node Updater 才将结果应用到正式数据区。每个数据区的新数据与 schema 标记一起生效。

#### 各模块的 data reader

每个模块将自己的 data reader 实现为 Rust 库，在同一个库内维护当前格式和该模块支持的旧 schema 的读取代码。Node Updater 在构建时直接链接各模块的 reader，复用模块的 Rust 库写入当前格式。模块负责人维护业务数据的读取与转换，Node Updater 负责调度并汇总结果。

所有模块的 reader 集中登记在同一个注册文件里。每项登记要能定位模块、reader 库和相关源文件，供后续 schema 审计使用。

#### System Config 中的应用配置如何离线迁移

Desktop 的 System Config 将应用配置和系统内核配置保存在本机 `$BUCKYOS_ROOT/local/system_config` 的 sled 键值库中。覆盖安装停服后，Node Updater 按以下顺序从该目录读取并迁移配置。

1. **导出旧配置。** Node Updater 通过 System Config 的迁移组件直接读取旧版持久化数据，导出同一份配置快照（dump）。各模块从快照中读取自己管理的 key 及其对应的 JSON 值。
2. **由各模块生成修改动作。** 每个模块根据自己配置的源 schema 和目标 schema，返回需要执行的操作列表（OP list）。例如，某个应用要为配置增加必填字段，就根据旧 JSON 算出新值，并返回对该 key 的更新操作。操作沿用 System Config 已有的事务语义。生成列表期间，各模块看到的都是升级前的值。
3. **暂存合并后的配置变更。** System Config 迁移组件将各模块的操作与内核配置变更、目标 schema 标记合并，在临时工作目录的数据库副本上用一个事务写入并校验。只有全部数据区准备成功，最终 apply 才将这份已验证的配置库切换为正式数据。

其他由系统服务托管的应用状态也遵循这个分工。服务提供旧数据，依赖该服务的模块生成业务变更，由服务迁移组件合并后交给最终 apply。

### 4. 备份、迁移和失败恢复

1. **准备失败。** 先准备系统配置，再准备服务和应用数据。任何转换、校验失败，或静默运行时发现需要用户决定，均丢弃本次暂存结果。此时所有正式数据和 schema 标记仍是原值。
2. **最终 apply 失败或中断。** 首次写入正式数据前，为本次涉及的数据区保留可恢复的旧数据，并持久记录目标构建、参与的数据区及提交进度。跨库或跨文件系统提交期间保持停服。某一数据区写入失败时，恢复本次已经写入的部分并校验旧数据。断电重跑时先核对持久记录和各数据区的实际状态，恢复期间保留所需备份与暂存结果。只有所有目标数据和标记均已落盘，才记录 apply 完成并返回成功。用户个人文件始终在迁移范围之外。

数据回滚用于最终 apply 已开始写入但未能完成的情况。整批数据已提交、随后覆盖程序文件出错时，按第 2 节重跑同一版本的安装包，继续完成目标版本的部署。

### 5. 模块负责人和发版流程

模块在创建持久化状态时，必须把实际采用的 schema 版本写入数据区。格式发生变化时，模块负责人要同步维护版本标记。如果新格式仍被标成旧 schema，Node Updater 可能选错转换逻辑，甚至损坏数据。

每次正式发布前，各模块负责人核对本模块的持久化 schema。发生变化时，确认模块能否自行读取历史数据。需要离线迁移时，由熟悉业务的模块负责人提供对应的转换。发布记录应列出每个正式发布的 BuckyOS 版本及各模块随该版本交付的 schema，内部测试期间出现、从未正式发布的格式不计入历史兼容范围。

后续可在 Git commit hook 中使用 reader 注册文件匹配本次提交涉及的文件。命中时，触发“此次变更是否需要升级 schema”的审计，由模块负责人确认是否调整版本标记和补充迁移代码。

### 6. 返回值与历史兼容

当前没有需要兼容的历史发布版本。本期先定义 `node_updater` 返回给安装程序的结果，后续首次出现已发布的旧 schema 时，再补充相应的历史读取和转换逻辑。下表给出结果语义和建议的状态名。

| 迁移结果 | 返回信息 | 安装程序的动作 |
| --- | --- | --- |
| 成功（`success`） | 最终 apply 已完成，或确认所有模块本来就满足目标格式。 | 继续覆盖程序文件。 |
| schema 不受支持（`unsupported_schema`） | 返回模块、数据区的实际 schema、目标 schema，以及原因（过旧或过新）。将来启用最低支持范围后，过旧时还要返回仍可读取该数据的最新过渡安装包版本。 | 中止覆盖，显示不兼容原因。有过渡版本时，向用户指出应先使用哪个 BuckyOS 安装包。 |
| 迁移失败（`migration_failed`） | 返回失败步骤和原因。模块内出错时附上模块名。 | 中止覆盖，报告失败。 |

两类失败结果都应说明失败阶段和正式数据状态。准备阶段遇到需要确认的情况时，静默运行返回 `migration_failed` 并给出原因。准备失败返回“未改动”，最终 apply 出错按实际状态报告“未改动”“已回滚”或“恢复未完成”。已停服时，只有正式数据未改动或已回滚且旧版可读，才可以重新启动旧版。恢复未完成或无法确认提交状态时保持停服。

随着正式版本发布，reader 按实际发布过的 schema 积累兼容能力。即使按周发布 BuckyOS，只要某个模块的 schema 沿用多个版本，该模块就可以共用已有处理逻辑。

长期设计允许按组件设置最低支持的 schema。启用下限后，遇到过旧的数据时，Node Updater 应返回失败，指出受影响的组件及其 schema，并给出**仍能读取该 schema、可用于下一步升级的最新 BuckyOS 安装包版本**。各代安装包支持的范围需要相互衔接。

例如，某组件当前使用 schema 70，能直接从 schema 50 升级。用户的数据仍是 schema 10。如果某个历史安装包能读取 10 并写成 50，用户就先运行该安装包，再运行当前安装包，完成 **10 → 50 → 70**。这里的数字是组件的 schema 版本，返回给用户的过渡版本应是可识别的 BuckyOS 发布版本。

### 7. SDK 兼容性与已安装应用

BuckyOS 发布新版 SDK 时，默认向下兼容。例如，基于 SDK 100 开发的应用，在系统升级到 SDK 120 后仍能加载和运行。只有某次发布确实要停用旧 API 时，才由发布工具为该版本明确指定允许加载应用的最低 SDK 版本。

若目标发布版本启用了该限制，安装程序在停服前检查已安装应用。若有应用使用的 SDK 低于下限，交互安装列出升级后将无法加载的应用和原因，由用户确认或取消。静默安装将同一清单写入日志并退出，旧服务继续运行。升级完成后，新系统在加载应用时执行同一条最低版本规则。

## 二、重试验收用例

| 故障位置 | 本次安装与重跑同一构建的预期结果 |
| --- | --- |
| A 已暂存，B 转换失败或在静默模式下需要用户确认 | 本次安装返回失败，删除暂存结果。A、B 正式数据及 schema 均与迁移前一致，程序文件完整。重跑需重新检查并准备。 |
| 最终 apply 在两个数据区之间中断 | 服务保持停止。重跑先核对提交进度，验证恢复后只有完整旧状态或完整目标状态可供服务使用。 |
| 最终 apply 已完成，进程在返回结果前中断 | 重跑根据持久记录和正式数据的目标 schema 确认提交完成，跳过重复写入。 |
| 所有模块已迁移成功，安装程序在覆盖部分程序文件后报错 | 第一次安装保持停服。第二次运行原构建时所有模块均跳过，`node_updater` 返回成功。安装程序重新覆盖程序文件。验证服务仅在部署完成后启动，运行的是目标版本。 |
