# AI Center Token Quota 与资源可见性 PRD

- 产品名称：AI Center / AICC
- 文档类型：PRD（产品需求文档）
- 状态：需求草案，定义下一阶段能力，不代表已实现
- 日期：2026-10-21
- 适用范围：Zone 内经 AICC 发起的 AI 调用；桌面端与移动端
- 关联文档：[AI Center PRD](AI_Center_PRD.md)、[AICC 用量统计需求](../../doc/aicc/aicc_usage_log_db_requirements.md)

## 1. 背景与目标

AICC 已具备用量记录与多维统计基础。下一阶段需要让管理员和普通用户在“看见消耗”的基础上，对未来消耗设置可执行的 Token Quota，避免某个用户或 App 持续占用 AI 资源。

本期必须满足：

1. 管理员可以为每个用户、每个 App 设置 token 上限，并按 Provider 或 Model 细分。
2. 支持周期额度与总量额度：周期额度每 4 小时、每 24 小时、每 72 小时或每周重置；总量额度持续扣减，用完后不自动恢复，只能由管理员手工充值增加额度。
3. 普通用户可以给自己的每个 App 设置周期 token 上限，使用相同的资源维度和周期选项；不能自行给管理员分配的总量额度充值。
4. 管理员限制与用户自设限制同时生效；调用前执行校验，调用后使用实际用量结算。
5. 从用量统计直接进入额度配置，并能解释“哪个限制生效、还剩多少、何时恢复”。
6. AIWorkspace 许愿格默认使用 workspace owner 的 AICC，也可配置为使用当前用户的 AICC；统计、额度和调用权限随选定归属一致生效。
7. 管理员可以按用户组配置 Provider 与 Model 可见性；用户只能看到获准 Provider 的实际模型清单中，同时获准的 Model。

本文补充主 PRD 中的“配额 / 限额控制”及按用户组开放 AI 资源的能力。额度属于 AICC 的调用策略，不等于 Provider 余额、Credit、费用预算，也不是每分钟请求数或 token 速率限制。资源可见性决定能看到和使用哪些资源，额度决定获准资源能使用多少，两者独立配置并同时校验。

## 2. 核心产品决策

以下是本草案采用的第一版默认口径，供产品、设计和实现共同使用：

| 项目 | 第一版定义 |
| --- | --- |
| 限制单位 | 归一化的总 token，输入与输出都计入 |
| 资源范围 | 全部 token 模型、某个 Provider 实例、某个精确 Model |
| 额度类型 | 周期额度与总量额度，可独立使用或同时生效 |
| 周期形式 | 周期额度采用固定窗口；每个窗口重新获得完整额度，不结转剩余额度 |
| 总量形式 | 初始发放加管理员手工充值，持续累计扣减，无自动重置和到期时间 |
| 额度规则关系 | 所有当前启用且命中的额度规则同时成立，不按角色或精细程度覆盖 |
| 资源可见性 | 按系统用户组授权 Provider + Model；与 Provider 实际模型清单取交集，未获允许的资源不返回给用户 |
| 默认行为 | 未配置规则表示该范围没有 AICC token 限制；仍受授权、路由及上游限制约束 |
| 数值含义 | 周期上限与总量初始额度为非负整数，充值增量为正整数；周期上限 `0` 表示禁止使用，总量余额 `0` 表示暂无额度；“不限额”通过不配置或停用规则表达 |
| 执行位置 | AICC 服务端统一执行，覆盖 UI、SDK、CLI、Agent 与直接 API 调用 |
| 控制方式 | 调用前预占，结束后结算；不能仅依赖异步报表做事后拦截 |

## 3. 角色、对象与权限

### 3.1 额度对象

| 规则来源 | 配置对象 | 消耗范围 | 可管理者 |
| --- | --- | --- | --- |
| 管理员 | 用户 | 归属该用户的所有 App 及直接调用的合计用量，包含获准代其发起的调用 | Zone 管理员 |
| 管理员 | App | 该 App 在本 Zone 所有用户下产生的合计用量 | Zone 管理员 |
| 管理员 | 用户 + App | 指定用户在指定 App 下产生的用量 | Zone 管理员 |
| 用户自设 | 本人 + App | 本人在指定 App 下产生的用量 | 本人 |

管理员的三类对象均支持周期额度和总量额度，以及相同的 Provider / Model 细分。第一版用户自设规则保持为周期限制；总量账户由管理员创建、管理及充值，用户可以查看影响本人的余额与消耗。

“App 总额度”与“某用户的 App 额度”是不同对象，界面必须明确标注“所有用户共享”或具体用户。用户总额度不是为每个 App 分别发一份额度。

App 使用可信调用身份中的 AppId 归集；同一 App 的多实例、多个 Session 共享对应额度。Agent 调用通过其可信 App 绑定归集，不能用 Agent 展示名或 Session ID 新建独立额度。普通用户只能选择归属于本人或本人获准使用的 App。

现有 `caller_app_id` 可能是 `app:filebrowser.buckyos.ai@alice` 这样的实例身份，也可能是 `system:control-panel`。服务端必须按可信身份模型解析 AppId、实例归属与用户，保留原始身份用于追溯：跨用户 App 总额按 AppId 聚合，个人 App 额度按“额度归属用户 + AppId”聚合，不能直接把原字段当作不含用户的 AppId。普通调用的额度归属用户就是认证用户；获准代用户执行的调用必须另行解析归属，不能直接以操作人或后台服务账号代替。

系统服务身份单独标识，普通系统调用计入对应用户总额度，第一版不作为普通 App 自限的配置对象。系统服务代业务 App 执行时，应保留可信的业务 App 归属；例如许愿格调用仍归入 AIWorkspace App，不能因后台执行而绕过 App 限制。

### 3.2 权限要求

- 管理员可以查看和管理所有管理员规则，以及查看其生效用量；管理员自身的推理调用也适用命中的规则，不隐式豁免。
- 普通用户可以新增、修改、停用、删除自己的 App 周期自限规则，查看影响本人的管理员限制；不能修改管理员规则或其他用户的规则，不能充值、直接改写总量余额或重建管理员的总量账户。
- 管理员需要收紧某个用户 App 时，应建立管理员规则，不借用用户身份修改个人规则。
- 用户可以提高或删除自己的限制，但实际调用始终受管理员限制约束。自设数值高于管理员限制时允许保存，界面解释管理员限制仍然有效。
- 普通用户可查看共享 App 额度对自己的影响、周期重置时间或总量充值状态；不暴露其他用户明细、调用内容或 Provider 凭据。
- 用户、租户、App 归属来自服务端验证后的身份及授权关系，不能相信请求正文中自填的 ID。App 发起的调用若缺少可验证的 App 归属，应拒绝，不能退化为“无 App”来绕过额度。合法直接调用仍计入用户总额度。

### 3.3 AIWorkspace 许愿格的 AICC 归属

workspace 提供“许愿格使用谁的 AICC”配置，由 workspace owner 或获授该配置管理权限的用户修改；默认值为“workspace owner”。同一 workspace 内的许愿格按该配置确定每次运行的 AICC 身份。

| 模式 | AICC 使用与额度归属 | 操作人 |
| --- | --- | --- |
| workspace owner（默认） | 使用该 workspace owner 获准使用的 AICC 资源，消耗计入 owner | 可以是 owner，也可以是获准运行许愿格的协作者 |
| 当前用户 | 使用触发本次许愿格运行的已认证用户的 AICC 资源，消耗计入该用户 | 本次运行的触发者，不是后来查看页面或结果的用户 |

“使用某用户的 AICC”同时决定调用授权、可使用的 Provider / Model、适用的路由配置及额度归属，不能只修改统计中的用户名。两种模式的业务 App 均为 AIWorkspace，调用同时受该额度归属用户的总额、管理员为其设置的 AIWorkspace 额度、其个人 AIWorkspace 自限，以及 AIWorkspace 共享 App 总额等命中规则约束。多个 workspace 或许愿格不会因此各获一份新的 App 额度。

例如 Bob 在 Alice 拥有的 workspace 中运行许愿格：默认使用 Alice 的 AICC，计入 Alice 的用户额度与 Alice 的 AIWorkspace App 额度；配置为“当前用户”后，Bob 新发起的运行使用 Bob 的 AICC，并计入 Bob 的相应额度。同一次消耗不同时计入 Alice 与 Bob 的用户额度。

执行与权限要求：

- 服务端同时校验操作人运行该许愿格的权限，以及按 workspace 配置使用所选用户 AICC 的授权关系。owner 模式通过受控的代执行授权实现，不向协作者暴露 owner 的凭据，也不允许调用者自填 owner 身份。
- AICC 归属不改变 workspace 的数据权限：读取来源、写入文档和应用候选结果仍按实际操作人的原有权限校验，不能因为使用 owner 的 AICC 就取得 owner 的文档权限。
- 在接受一次许愿格运行时确定并保存归属模式、额度归属用户、操作人及可信 AIWorkspace App 身份。该次运行产生的多次 AICC 调用、异步执行、重试、fallback 和结算沿用同一归属；每次实际上游调用仍按其预占时间确定周期窗口，并扣减命中的总量账户。
- “一次运行”指服务端接受的独立业务 run。分析、执行、反馈后重跑和修程序如建立新 run，应各自重新确定归属；当前用户模式下，下一 run 使用其实际触发者的 AICC。分析、执行、多轮工具调用及 `llm.map` 产生的 AICC 调用都纳入相应运行；仅重跑程序时的 `llm.map` 缓存未命中也按此计量，纯本地执行或本地结果缓存命中且未发起 AICC 调用不新增消耗。
- 模式修改或 workspace owner 变更只影响之后接受的新运行，不迁移历史消耗或在途运行的归属。后续调用仍须通过授权检查；原授权失效时停止继续调用，不能转扣其他用户。
- 当前用户模式必须能确定已认证的运行触发者；自动或后台触发若没有合法保存的执行用户及授权，则提示无法确定 AICC 使用者。owner 模式可以在 owner 未在线时通过有效的代执行授权运行。
- 所选用户额度不足、AICC 不可用或授权失效时明确报错，不能自动改用 owner、操作人或后台服务账号的额度。用户显式切换配置后重新发起，按一次新运行处理。
- 许愿格运行入口和运行详情展示“使用 workspace owner 的 AICC”或“使用当前用户的 AICC”及本次实际归属用户；额度错误说明受限用户和规则。Usage / Trace 同时保留额度归属用户与操作人，以及 workspace、许愿格和运行标识，便于区分“谁发起”与“额度算给谁”，展示范围遵循已有权限。

### 3.4 按用户组管理 Provider / Model 可见性

管理员可以针对不同系统用户组配置可见且可使用的 Provider 实例，并在每个获准 Provider 的 model list 内选择允许的精确 Model。组定义与成员关系复用 [用户类型与系统用户组](../users_and_agents/UserType.md) 中的 `group:<id>`，由 Users & Agents 管理；个人联系人分组、App 自报角色不能作为这里的用户组。

**最终模型列表必须同时满足三个条件：Provider 获准、Model 确实在该 Provider 的实际模型清单中、该精确 Model 获准。**

```text
某组的允许项 = 该组允许的 Provider 下，该组明确允许的精确 Model
用户的允许项 = 用户所属各系统用户组的允许项之并集
用户在 Provider P 下可见的模型 = P 的实际模型清单 ∩ 用户在 P 下的允许项
```

Provider 与 Model 使用 §4.1 的实例和精确模型身份。同名模型在不同 Provider、不同 variant 下分别授权。模型清单使用 AICC 从该 Provider 获取并规范化的 inventory，不能用全局 Model Driver 目录或其他 Provider 的清单补出资源。列表可见性适用于 token 与非 token 模型；非 token 操作不受本期 token 额度计量，不代表不受资源访问限制。

配置与组合规则：

- Provider 未获允许时，该 Provider 及其全部模型均不可见；允许某个 Model 不能越过 Provider 的限制。
- 允许 Provider 不等于允许其全部 Model。管理员必须选择模型；“全选当前模型”只保存当时的选择，之后发现的新模型、新版本或 variant 默认不可见，需再次明确开放。
- 每个组内先形成完整的 Provider + Model 允许项，再按用户所属组取并集，不能把不同组中不完整的 Provider 与 Model 配置拼成一份授权。
- 本期采用允许清单：组内未勾选表示该组不授予，不否决其他组已授予的同一资源。管理员需移除用户全部相关授权来源才能彻底撤销访问，预览必须列出各项授权来源。
- 未加入任何已配置组、未命中允许项或组已删除时，不返回对应资源。无规则不等于开放全部；初始化时由管理员为需要使用 AI 的用户组建立明确允许清单。
- 允许项只限定资源范围，不替代原有服务授权、App 授权及 Provider 凭据权限。管理员可在管理视图查看完整 inventory 以配置规则；其普通推理调用仍需通过资源与额度校验。
- Provider 允许但没有任何实际且获准的模型时，可展示该获准 Provider 的“暂无可用模型”空状态，不展示被过滤模型的名称、数量或其他元数据。Provider 资源本身的健康状态与访问权限分别展示。

例如 `group:customer` 允许 `cloud-main` 下的 `model-a@cloud-main`，而该 Provider 实际返回 model-a、model-b，另一个 Provider 返回 model-c，则该组用户只看到 cloud-main 及 model-a。为 model-b 配置 token 额度不会使其自动可见；model-a 不再出现在该 Provider inventory 时，也不能仅靠允许清单继续出现在可选列表中。

服务端与界面要求：

- Providers、Models、模型列表 API、搜索、选择器、Playground、额度配置及路由预览均使用同一过滤结果。普通用户不能先获取完整列表，再依靠前端隐藏；分页、计数和缓存也基于过滤后的集合。
- 用户直接提交不可见 Provider / 精确 Model，或者通过逻辑模型、别名、fallback 请求它们时，AICC 必须在上游调用前阻止。逻辑路由仅从获准资源中选候选；无候选时提示“没有获准的可用模型”，与额度不足区分，不泄露隐藏候选。
- 可见性与额度独立：已可见但额度耗尽的模型仍可显示受限状态；不可见资源不能因剩余额度、个人配置或已保存的旧模型 ID 而重新可见。
- 规则、组成员或 inventory 变化后，后续列表查询和新出站调用必须使用有效策略；撤权不能因旧会话缓存、已打开的选择器或某次运行尚未结束而继续放行。已发出的上游调用按原归属完成结算，后续重试和多轮调用重新检查权限。
- 组与策略由服务端可信身份解析，不能接受客户端自报组；缓存需区分授权用户和策略版本。无法可靠确定权限时返回权限状态不可用，不能返回完整目录或默认放行。
- 普通用户的 Usage、Trace、错误和历史额度规则也不能成为枚举隐藏资源的入口；撤权后保留历史消耗，资源身份按当前可见性隐藏或显示“已无访问权限”。管理员授权范围内的审计保留完整记录。

与许愿格归属的关系：owner 模式的执行候选按 owner 所在组授权，当前用户模式按本次触发用户所在组授权，不能合并两人的权限扩大候选。owner 的代执行授权仅用于获准的许愿格运行，不开放给协作者的个人 AICC 目录。向协作者展示具体 Provider / Model 条目时，还须满足该查看者的可见性；模型选择器只展示其可见且运行归属用户获准的项。owner 已配置的模型即使对协作者隐藏，仍可在合法代执行授权下运行，但只显示“workspace 已配置模型”，不暴露资源身份。运行归属保持固定，后续出站调用仍检查该归属用户当前有效的组策略。

## 4. 资源范围与规则叠加

### 4.1 Per Provider / Per Model

| 资源选择 | 计入范围 | 示例 |
| --- | --- | --- |
| 全部 token 模型 | 对象在全部 Provider、全部可计量 token 的模型上产生的消耗 | Alice 每周总计 2,000,000 tokens |
| 某个 Provider | 指定 Provider Instance 下全部 token 模型的合计消耗 | Alice 在 `cloud-main` 每 24 小时 200,000 tokens |
| 某个 Model | 指定 Provider Instance 下某个精确模型的消耗 | Alice 在 `model-a@cloud-main` 每 4 小时 50,000 tokens |

Provider 使用配置实例身份 `provider_instance_name`，不按厂商品牌、协议类型或 API Key 文本聚合。两个相同厂商的实例是两个额度范围；同实例内轮换凭据不刷新额度。

Model 采用 AICC 精确模型标识 `provider_model_id[:variant]@provider_instance_name`。同名模型在不同 Provider 实例下分别计量；不同 variant 分别计量。第一版不提供跨实例的模型家族额度或逻辑路径额度，界面必须展示所属实例及 variant，不能只显示模型简称。

逻辑模型调用按最终实际执行的精确模型计入额度；路由别名变更不改变已有消耗归属。新增模型自动受已配置的“全部模型”和对应 Provider 额度约束，精确模型规则不会自动迁移到新版本。资源下线后保留规则和历史，标记“资源不可用”，不得静默绑定到其他模型。

### 4.2 多条规则同时生效

一条请求可能同时命中用户总额、共享 App 总额、管理员指定的用户 App 额度、用户自限，以及各自的 Provider / Model 规则。所有当前启用且命中的规则都必须有足够可用额度；已停用或删除规则保留的总量账户仅参与记账，不参与阻断。

- 同一对象可以同时配置 4 小时、每周及总量规则，分别控制短时消耗、周消耗与累计可用额度。
- 周期规则按“来源 + 对象 + 资源 + 周期”唯一；总量账户按“Zone + 管理员规则来源 + 对象 + 资源”唯一，不区分哪位管理员创建。重复配置进入已有规则或账户，不叠加发放额度。
- 一次实际消耗分别扣减每条命中规则，原始 Usage 仍只记录一次；不能把各规则扣减之和当作总消耗。
- 不同对象、资源或周期的上限不能直接取最小值作为“统一上限”。只对某次调用的全部适用规则比较各自的剩余额度。
- App 的个人额度不预先占走用户总额度。各 App 共享用户剩余总额度，未使用的个人额度不能保证可用量。

示例：Alice 的 `cloud-main` 每 24 小时上限 200,000，写作 App 在全 Zone 同 Provider 每周上限 500,000，Alice 为自己的写作 App 设置每 4 小时 30,000，管理员另设 `model-a@cloud-main` 每 4 小时 50,000。Alice 在写作 App 调用该模型时，四条规则同时校验；任何一条不足都会影响本次调用。

也可以给 Alice 在 `cloud-main` 分配累计 1,000,000 tokens，同时限制每 4 小时 50,000 tokens。每 4 小时只恢复周期额度；总量用完后仍须管理员充值。充值后如果 4 小时额度已耗尽，仍需等待该周期重置或管理员调整周期上限。

## 5. 额度类型与恢复方式

### 5.1 周期额度的固定窗口定义

第一版采用统一 UTC 时间基准，避免不同客户端时区及夏令时改变额度。界面以用户本地时间展示当前周期起止、下次重置的绝对时间和倒计时，并明确标注时区。

| 周期选项 | 窗口边界 |
| --- | --- |
| 每 4 小时 | UTC 每日 00:00、04:00、08:00、12:00、16:00、20:00 |
| 每 24 小时 | UTC 每日 00:00 |
| 每 72 小时 | 以 `1970-01-05 00:00 UTC` 为固定基准，每 72 小时一个窗口 |
| 每周 | UTC 每周一 00:00，连续 7 天 |

窗口采用左闭右开区间 `[开始时间, 结束时间)`，边界上的新调用属于新窗口。周期不是“最近 N 小时”的滚动统计，也不从首次调用开始计时。

### 5.2 周期重置及跨周期请求

- 到达边界后自动进入新窗口，未用额度不累积，旧窗口记录保留。
- 同一规则的上限和周期配置持续有效，无需每期重新设置。
- 以实际 Provider 调用预占成功的时间确定所属窗口，保存该归属；调用跨过边界完成，仍结算到原窗口，不能扣到新窗口。
- 新窗口正常提供额度；旧窗口仍在执行的请求只能使用原预占，不得跨窗口追加旧调用的预算。
- 多条规则独立重置。一个窗口恢复额度，不代表其他命中规则已经恢复。
- 重启服务、切换节点、刷新页面、重新登录、轮换 Key 都不能触发额度重置。

### 5.3 总量额度与管理员充值

总量额度是一份持续使用的 token 余额，没有小时、天或周的重置，也没有自动续额。管理员首次建立账户时分配初始额度，之后每次实际调用扣减余额；用完后阻止新调用，等待管理员手工充值。

- 初始发放和后续充值均绑定明确的用户 / App / 用户 App 对象与 Provider / Model 范围，不生成可在不同账户之间任意通用的点数。
- 首次生效时保存账户的累计起点。准入发生在该时刻之前的历史调用和在途调用不追溯扣减；之后所有适用调用纳入该账户。生效与调用准入必须有确定的先后顺序。
- 初始额度可为零，此时显示“等待管理员充值”。每次充值输入正整数增量 token，增加累计发放量；不能将“充值 100,000”解释为把余额设置成 100,000。
- 充值不清零累计消耗，不释放在途预占，不重置周期额度，也不改变资源可见性。一次调用命中多个总量账户时分别扣减，充值仅影响被指定的账户。
- 充值必须形成持久记录，包含充值单号、账户、增量、管理员、时间和备注。相同充值单号重试只入账一次；同号但参数不同应拒绝。不同充值单号的并发充值应累加，不能覆盖。
- 充值、预占与结算按账户一致地执行；成功响应表示已持久生效。余额未知时不能靠重复充值请求猜测结果，应按充值单号查询原结果。
- 每个总量账户的累计起点与账本保持稳定。停用或删除规则只撤销该规则的阻断，期间的适用消耗和在途占用仍记录，账户余额不足不阻断调用；重新启用时已有消耗与占用必须计入。同对象和资源重建时恢复原账本，不再次自动发放初始额度。管理员若要追加额度，必须明确执行充值。
- 未使用的预占释放、暂估用量的真实结算或错误用量冲正可以恢复本来未消耗的余额，这不属于额外充值；已确认的实际消耗不会随时间返还。
- 即使展示的可用余额已经是零，实际超额导致的账面欠额也必须保留。后续充值先补足欠额，再产生可用额度，不能直接在显示的零上相加。

例如累计发放 100,000、已结算 60,000、预占 10,000，则可用 30,000；管理员再充值 50,000 后，累计发放变为 150,000，可用变为 80,000，已结算和预占均保持不变。

这里的“充值”是管理员发放 AICC token 额度，不涉及支付、货币、Provider 充值或 SN Credit；充值余额也不代表上游账号一定有可用余额。

## 6. Token 口径与用量基础

### 6.1 计量规则

额度使用 AICC 归一化的 `total_tokens`，与 Usage 的 token 定义保持一致。缺少总数但具备完整、可靠的输入和输出值时，由归一化层计算；不能把缺失字段当作零。

- 输入、输出、缓存读写、推理 token 的包含关系由 Provider 归一化层统一处理。已包含在 input / output / total 内的细项不能再次相加；未包含的可计量消耗应在归一化时补齐。
- 缓存命中也会消耗 token 额度，不按价格折扣折算。免费、本地、订阅模型只要支持 token 计量，都适用相同规则。
- 图片张数、音视频时长、金额和 Credit 不换算为 token。本期只覆盖能够形成可靠 token 用量与调用预算的操作；不支持的操作明确标记“未纳入 Token Quota”，不显示“已受额度保护”。
- 如果应支持 token 计量的调用异常缺少 usage，应进入待核对状态，不能伪装为非 token 操作绕过限制。
- 在上游调用前拒绝的请求不消耗额度。失败、取消、超时但已发生的上游 token 消耗仍计入，不能按最终业务结果是否成功决定是否扣减。

### 6.2 统计与额度的关系

复用已有 Usage 的用户、App、Provider、精确模型与 token 事实，在此基础上增加预占、结算、周期窗口或总量账户归属。用量报表可以异步刷新，但实时放行不得依赖有延迟的图表聚合值。

额度详情至少区分：已结算 token、执行中预占 token、待核对 token、可用 token。待核对 token 仍包含在占用中，不额外重复计算。

```text
周期可用 token = max(0, 周期上限 - 本期已结算 token - 本期未结算预占 token)
总量累计发放 = 初始发放 + 全部已成功入账的管理员充值
总量可用 token = max(0, 总量累计发放 - 自累计起点的已结算 token - 未结算预占 token)
```

新记录需要保留调用准入时间及最终用量事件的关联，支持按周期窗口或总量账户对账。普通 Usage 若按完成时间展示，跨窗口调用可能产生时间分布差异；“查看本期消耗”必须采用该周期规则的额度归属口径，能够说明差异。总量详情展示自累计起点的消耗与充值流水，不套用报表当前选择的时间范围计算余额。

新建或重新启用周期规则时，本期已有消耗及仍在执行的适用调用必须计入，不能从零开始。已有记录没有准入时间时，以原 Usage 事件时间作为历史归属，并在首次生效预览中说明；数据不完整时不能将未知用量按零放行。总量账户的初次生效与恢复遵循 §5.3，不能套用“当前周期”重新起算。

新建、重新启用周期规则或切换周期时，在途调用按原始准入时间投影到目标规则窗口，并关联后续结算；只有归属当前窗口的调用占用当前额度。上一窗口尚未结束的调用不能再次占用当前窗口。总量账户的在途占用一直保留到结算，不随周期边界或充值发生转移。

## 7. 调用执行与超限行为

### 7.1 调用前检查

1. 验证调用身份及必要的代执行授权，确定额度归属用户和可信业务 App，再匹配对象规则；AIWorkspace 许愿格遵循 §3.3 的运行归属。
2. 根据该 AICC 授权用户的组策略和 Provider 实际模型清单过滤候选，校验资源访问权限；得到获准 Provider / Model 后，补齐额度规则，计算所有适用周期窗口及总量账户的可用量。
3. 使用输入 token 的可靠上界与最大输出预算，为本次上游调用预占。输出预算应包含可消耗额度的隐藏推理等 token；调用未提供上限时使用服务端确定的有限默认上限。
4. 对全部当前启用且命中的周期窗口和总量账户原子检查并预占；只要一条不足，本次预占整体失败，不留下部分占用。已停用或删除规则的总量账户仍记录本次占用及后续消耗，但其余额不参与准入校验。
5. 预占成功后才发起上游调用。多个实例并发争抢同一剩余额度时，不能都读到余额后分别放行。

本期定义为强制限制新调用及其预算，不承诺在上游违反预算或计量异常时物理消耗绝不超额。正常情况下预占必须覆盖实际最大消耗；不具备可靠预算边界的操作不得宣称支持硬上限。

请求预算大于剩余额度时，应返回额度不足及允许的预算范围，不静默缩减用户指定的输出上限。应用可以据此主动降低预算后重新调用。

### 7.2 执行、重试与结算

- 非流式、流式和长任务使用相同校验。流式调用受预占的输出预算限制，不能先无限生成再在完成时发现超限。
- 成功完成后以实际 token 替换预占，多占部分释放；失败或取消后结算已产生的消耗，释放确认未使用的部分。
- 仅客户端断连不证明上游已停止，不能立即释放全部预占。超时且 usage 未知时保留待核对占用，并尝试恢复结算。
- 待核对占用必须在服务端公布的核对期限内转为真实结算或“按预占上限暂估结算”；不能永久悬挂或无依据清零。后续取得真实用量时幂等冲正，保留估算依据和变更记录。
- 每次真正发生的上游重试、fallback 都重新检查并记录其消耗；已发生的失败尝试不能被最终成功结果覆盖。内部多次调用也逐次计入。
- 相同调用的重放、重复回调和服务重启恢复不能重复预占或重复扣减；对调用与实际执行尝试分别建立唯一关联。
- 如实际用量异常超过预占，记录完整真实消耗及异常原因，剩余显示为零并阻止后续适用调用；不能截断统计数据来制造“未超限”。

### 7.3 路由与拒绝结果

额度不足的候选不可执行。只有原路由策略允许 fallback 时，才可尝试其他候选，并对新候选重新检查全部适用规则。用户总额或 App 总额耗尽时，换模型、换 Provider 不能绕过总额；仅某个精确模型耗尽时，其他获准模型可以继续使用。精确模型请求仍遵循原有的模型锁定语义。

全部候选因额度不足不可用时，返回可被应用识别的“Token 额度不足”，与 Provider 余额不足、上游限流、授权失败、模型不可用区分。产品契约至少包含：

- 阻断的规则、来源和对象，以及相关 Provider / Model。
- 额度类型、周期上限或总量累计发放、已用、预占和剩余；周期规则另有当前窗口，总量账户另有累计起点。
- 受影响调用的下次可能恢复时间；总量规则无自动恢复时间，`reset_at` 为 `null`。多个阻断规则同时存在时，不能只展示周期倒计时并承诺可用。
- 用户可采取的动作：周期额度等待重置或调整本人自限，总量额度联系管理员充值，或降低本次请求预算。

周期上限为零，或本次预算超过某条适用规则完整周期的上限时，应明确返回“无自动恢复时间”，提示修改规则或降低预算，不能承诺下一次重置后恢复。总量余额不足时提示“总量额度不足，需管理员充值”，不能要求等待小时、日或周重置；充值后仍须满足所有其他限制。

普通用户看到共享 App 规则时只获得必要的汇总与阻断信息。App / Agent 应停止对同一额度错误进行无间隔重试；额度恢复只恢复调用资格，不自动重放已经失败或取消的任务。

若已配置限制但额度状态无法可靠读取或预占无法持久化，应暂停受影响的新调用并返回“额度状态暂不可用”，不能视为无限额。报表暂时不可用不应影响可独立可靠执行的额度检查。

## 8. 配置变更与生效

| 操作 | 产品行为 |
| --- | --- |
| 新建周期规则 | 预览当前窗口已有消耗、在途占用与剩余；保存时重新计算并原子生效 |
| 提高周期上限 | 保存后对新调用立即生效，保持本期消耗；其他规则仍可能阻断 |
| 降低周期上限 | 保存后立即生效；低于已用加预占时可保存，但提示新调用将被阻断，已预占调用继续原预算 |
| 修改重置周期 | 显示待生效周期及时间，在当前旧周期结束时切换；新周期按其固定窗口计入已发生的适用消耗，不重新发放一份空额度 |
| 新建总量规则 | 管理员指定初始发放量，预览累计起点与作用范围；若已有同范围账户则恢复原账本，不再次发放 |
| 总量充值 | 管理员按正整数增量追加，幂等持久入账后生效；保持历史消耗、在途占用及其他规则 |
| 停用 / 删除 | 只撤销该条限制，其他规则继续生效；历史用量、预占结算和审计不删除 |
| 重新启用 / 重建 | 周期规则按当前窗口汇总；总量规则恢复原账户累计发放、全部适用消耗与预占，不因更换规则 ID 获得新额度 |

对象和资源范围作为规则身份，不直接编辑；更换对象或资源通过新建规则和停用旧规则完成，保存前展示受影响范围。修改周期的待生效变更可在生效前撤销。

周期与总量类型不支持原地切换，避免切换类型重置账目。管理员可分别建立两种规则，并明确停用不再需要的规则；停用管理员约束属于策略变更，不是充值。总量余额不提供直接覆盖编辑，增加额度只能走充值；初始发放及充值流水不能通过编辑规则改写。

修改周期的目标若已有相同来源、对象和资源的有效规则，应拒绝修改并引导编辑已有规则。保存时检查有效及待生效规则的冲突，实际切换时再次校验；发生冲突则保留旧周期规则并提示，不能自动覆盖、合并或解除原限制。

规则变更成功响应后，新准入请求必须看到生效版本。管理员与用户同时修改各自规则时仍保留双层约束；同一规则的过期编辑应提示冲突，避免静默覆盖。

所有配置变更和充值保留操作者、对象、变更前后值、生效时间。审计记录不包含提示词、输出内容或密钥。第一版不提供“清空用量”或额度转赠；增加周期额度使用提高上限，追加总量额度使用管理员手工充值。

用户组可见性策略独立版本化，保存前预览新增、移除的 Provider / Model 及受影响用户；保存成功后新查询和新出站调用使用生效策略。撤销可见性不清空额度历史，重新开放也不重置本期用量。

## 9. 信息架构与交互需求

### 9.1 入口

在 AI Center 增加“额度 / Quota”入口，与 Usage 并列。Usage 中的用户、App、Provider、Model 统计行提供“设置额度”，携带明确的统计对象与资源范围进入表单；统计时间范围不自动等同于额度重置周期。

普通用户默认进入“我的 App 额度”；管理员可切换“用户额度”“App 额度”和“指定用户的 App 额度”，并明确区分管理操作与自己的个人设置。

管理员另有“用户组资源可见性”入口：选择系统用户组，勾选允许的 Provider，再从其实际模型清单勾选 Model；可按具体用户预览最终列表和授权来源。组及成员管理跳转 Users & Agents。普通用户的 Provider / Model 选择器只显示过滤后的列表，不提供修改组策略的入口。

### 9.2 列表与详情

规则列表展示对象、资源范围、规则来源、额度类型、已用、预占、剩余、状态及可执行操作。周期额度另展示上限、周期、下次重置；总量额度另展示累计发放、“不自动重置”及管理员可见的“充值”操作。支持按类型 / 用户 / App / Provider / Model / 来源 / 状态筛选和搜索。移动端以卡片保留同样的信息与操作。

详情显示所有适用约束及“当前阻断原因”，不能只展示用户自设的那一条。用户可进入对应周期或总量累计范围的 Usage 明细，管理员可查看配置变更与充值流水；普通用户可查看本人账户的发放、消耗与余额，共享账户只展示必要汇总。

| 状态 | 展示与行为 |
| --- | --- |
| 未设置 | 明确说明当前范围没有自设额度，并展示已有管理员约束 |
| 正常 | 周期额度展示已用 / 上限、预占及下次重置；总量展示累计发放、累计消耗、预占及可用余额 |
| 接近上限 | 已结算加预占达到周期上限或总量累计发放的 80%，显示预警；不额外拦截，分母为零时直接展示耗尽 |
| 额度耗尽 | 周期额度标出阻断来源与恢复时间，上限为零时显示“已禁止使用”；总量额度显示“已用完，需管理员充值”，不显示重置倒计时 |
| 本次预算不足 | 可用量大于零但不足以满足本次请求，说明可降低请求预算 |
| 待核对 / 状态不可用 | 展示原因及数据更新时间，不能显示为“无限额” |
| 已停用 / 待生效 / 资源不可用 | 分别展示当前是否执行、预计生效时间或资源状态 |

额度页的余额变化应在请求结算或规则变更后及时更新；配置保存返回权威生效状态。首页及 Usage 提供接近上限与耗尽提示，第一版不要求邮件或推送通知。

### 9.3 设置额度流程

1. 选择对象；普通用户的用户身份固定为本人。
2. 选择“全部 token 模型 / 某个 Provider / 某个 Model”；模型选择显示完整身份，普通用户只能选择当前可见资源。“全部 token 模型”约束其获准资源的消耗，不授予额外访问权。
3. 管理员选择“周期额度 / 总量额度”；普通用户自设规则使用周期额度。
4. 周期额度输入 token 上限并选择 4 小时、24 小时、72 小时或每周，展示当前窗口和下一次重置时间；总量额度输入初始发放量并展示累计起点及“不自动重置”。数值支持 K / M 辅助输入，保存前展示精确整数。
5. 预览已用、预占、保存后剩余，以及其他同时生效的限制；已有总量账户只恢复原账本，额外发放进入充值流程。
6. 保存并回到详情；失败时保留输入，明确说明权限、冲突或状态不可用原因。

### 9.4 管理员手工充值流程

1. 在总量账户详情选择“充值”，明确展示目标用户 / App、Provider / Model、当前余额和预占。
2. 输入追加的 token 数量及可选备注，预览充值后累计发放和预计可用额度，并提示其他仍可能阻断的规则。
3. 提交前生成并保存本次充值的唯一单号或幂等键，提交后返回对应入账结果；防止重复点击、超时重试造成重复发放。失败时可按原单号查询或重试，不能自动另建一笔充值。
4. 刷新权威余额与流水；普通用户只看到余额更新，不获得充值权限。已失败的 AI 任务不会因充值自动重放。

## 10. 数据与服务能力要求

本节描述产品需要的信息，不冻结数据库表或公共 RPC 的最终命名。

| 对象 | 必要信息 |
| --- | --- |
| 额度规则 | 稳定 ID、Zone、来源、创建者、对象及可信身份、资源选择、周期 / 总量类型、周期规则的 token 上限及周期或总量账户引用、启停状态、版本、生效时间及待生效变更 |
| 用户组资源策略 | 稳定 ID、Zone、系统用户组引用、允许的 Provider 实例及各自精确 Model 清单、版本、生效时间和变更审计；成员关系引用统一身份系统 |
| 周期状态 | 规则与版本、窗口起止、上限、已结算、预占、可用、下次重置、数据更新时间 |
| 总量账户 | 独立于规则生命周期的稳定账户 ID、对象与资源、累计起点、累计发放、累计已结算、预占、账面余额及可用余额、版本；无周期终点，`reset_at = null` |
| 发放 / 充值记录 | 唯一单号、账户、初始发放或追加充值、token 增量、管理员、时间、备注、入账状态及幂等结果；累计发放可由记录对账 |
| 调用占用与结算 | 调用及尝试标识、额度归属用户、操作人、可信业务 App、实际 Provider / Model、准入时间、资源授权来源及策略版本、命中额度规则及周期窗口或总量账户、预算、实际用量或估算状态、Usage / Trace 关联；许愿格另存归属模式、workspace、许愿格与运行标识 |
| 变更审计 | 操作者、操作时间、目标规则、前后值、版本和生效时间 |

服务端需要支持权限过滤后的规则查询与管理、配置生效预览、某用户 App 的全部适用限制查询、实时额度状态查询、管理员充值及单号查询、调用预占与幂等结算。额度页展示与实际拒绝必须使用一致的规则语义。总量账本和充值记录持久保存，Usage 明细的清理不能导致余额重算为零消耗或再次发放。

资源可见性需要提供管理员组策略管理与有效权限预览、面向用户过滤后的 Provider / Model 查询，以及运行时资源授权校验；查询和执行复用同一套策略求值。当前路由偏好中的 Provider 过滤不能单独代替管理员的组授权或模型清单过滤。

AIWorkspace 到 AICC 的调用链需要传递并验证代执行授权与运行归属。AICC 的用户用量聚合及 tenant 隔离必须与额度归属一致，操作人单独记录；不能仅在前端更换展示名，或将客户端提交的归属用户直接作为可信身份。

当前实现可复用但不能直接等同于本期能力的基础：

- [Usage 共享类型](../../src/kernel/buckyos-api/src/aicc_usage_log.rs) 已包含用户、App、Provider、模型和 token 字段；现有事件时间与成功调用记录需要补足本期的准入归属、失败消耗及执行尝试语义。
- [现有 Usage 查询授权](../../src/frame/aicc/src/service/management.rs) 限制在调用者自己的 tenant 内；管理员跨用户查询及 App 总额管理需要明确增加管理授权，不能只靠前端传入其他用户的筛选参数。
- [现有 quota 服务](../../src/frame/aicc/src/service/quota.rs) 主要基于请求单位、费用和显式起止时间；本期需要补充 token、精确模型、周期规则、总量账户与充值、权限管理及实时预占，不能将未知额度状态直接沿用为放行依据。
- [AICC 运行时持久数据设计](../../doc/aicc/aicc_runtime_durable_data_schema.md) 可作为调用恢复与审计的衔接入口。规则、周期窗口或总量账户归属、充值记录、未结算占用及幂等关系必须可恢复，不随临时任务清理或服务重启丢失。

## 11. 验收标准

| 编号 | 场景 | 预期结果 |
| --- | --- | --- |
| Q01 | 管理员配置用户 Provider 额度 | 该用户所有 App 的对应 Provider 消耗共同累计，其他用户不占此额度 |
| Q02 | 管理员配置 App 额度及用户 App 额度 | 前者汇总所有用户，后者只影响指定组合；多实例和 Session 不产生额外额度 |
| Q03 | 普通用户管理自限 | 可以管理本人 App；伪造用户 / App ID、修改管理员规则或读取他人明细均被拒绝 |
| Q04 | 同时命中 Provider、Model、管理员和个人规则 | 全部校验并分别扣减；某条耗尽时不能被更宽松规则覆盖，原始统计不重复 |
| Q05 | 同一对象配置 4 小时与每周额度 | 分别累计和重置；4 小时重置后仍受耗尽的周额度限制 |
| Q06 | 测试全部四种周期及边界时间 | 按固定 UTC 窗口计算；本地时间和夏令时仅改变显示，不改变 4 / 24 / 72 小时或周长度 |
| Q07 | 两个并发请求分别需要 8,000，当前仅剩 10,000 | 最多一个获得预占；多条规则中的失败不会留下部分预占 |
| Q08 | 跨窗口流式 / 长任务、取消及断连 | 结算到原窗口；确认未用部分释放，未知用量保留并在期限内完成真实或暂估结算 |
| Q09 | 请求重放、重复完成回调、重启及跨实例恢复 | 同一次实际执行只扣一次，额度和预占不因重启重置 |
| Q10 | 失败重试、fallback 与逻辑模型切换 | 每次上游实际消耗按执行模型计入；新候选重新校验，用户 / App 总额不可绕过 |
| Q11 | 缓存、推理 token、缺失 usage 和非 token 操作 | 与归一化口径一致且不重复累计；未知用量不按零处理；未覆盖操作明确展示 |
| Q12 | 本周期已使用 60,000 后新设周期额度或降额为 50,000 | 新调用立即受阻，历史保留；提升至足够额度后可恢复，但仍受其他规则约束 |
| Q13 | 修改周期、目标周期冲突、周期规则停用后启用或删除重建 | 不隐式清零；周期切换按新窗口重算，在途按原始准入时间归属；冲突不覆盖规则或解除旧限制 |
| Q14 | 同名模型位于两个实例、Key 轮换及模型下线 | 精确模型额度分别归属；Key 轮换不刷新；下线规则保留且不迁移绑定 |
| Q15 | 额度状态读取失败或实际用量异常超预算 | 受限调用不静默放行；完整记录真实消耗、阻断状态与异常原因 |
| Q16 | 从 Usage 设置额度并触发拒绝 | 预填对象正确，预览与执行一致；明确规则来源与恢复操作；零上限或预算超过整期额度时不承诺重置后可用 |
| Q17 | Bob 在 Alice 的 workspace 中运行许愿格，未修改 AICC 配置 | 默认使用 Alice 的 AICC，计入 Alice 与 AIWorkspace 对应额度；操作人记录为 Bob，不重复扣 Bob 的用户额度 |
| Q18 | workspace 配置为使用当前用户 AICC，Bob 和 Carol 分别发起运行 | 各自使用本人获准使用的 AICC 资源，分别计入本人额度；AIWorkspace 共享 App 总额继续累计 |
| Q19 | 许愿格执行中修改归属模式或转移 workspace owner | 在途运行及其重试、fallback 保留原归属，新运行使用新配置；授权失效时停止，不迁移已产生消耗 |
| Q20 | 伪造 owner、缺少当前执行用户，或所选用户额度耗尽 | 未授权调用被拒绝，归属缺失和额度错误明确展示，不自动转扣其他用户；后台服务执行仍受 AIWorkspace App 限制 |
| Q21 | owner 模式访问文档，以及不同用户依次触发分析、执行和程序重跑 | 文档权限仍按操作人校验；每个新 run 重新确定 AICC 归属；`llm.map` 实际调用计入对应运行，未调用 AICC 的本地执行不新增消耗 |
| Q22 | 两个用户组获得不同 Provider 与 Model 授权 | 各组用户仅看到允许 Provider 实际模型清单中获准的精确 Model；同名跨实例及不同 variant 不混用 |
| Q23 | 用户属于多个组、没有匹配规则，或所属组被删除 | 完整授权项按组取并集，未勾选不覆盖其他组授权；未命中时无资源，不把“无额度限制”当作访问许可 |
| Q24 | Provider 新增 / 移除模型，或仅给隐藏模型配置额度 | 新模型不自动开放，已不在 inventory 的模型不列为可选；额度配置不授予可见性 |
| Q25 | 直接提交隐藏模型、逻辑路由 / fallback 命中隐藏模型，或使用缓存列表 | 服务端在出站前校验并阻止越权；查询、搜索、分页和错误不泄露隐藏资源 |
| Q26 | 管理员撤权或用户移组时存在在途任务 | 新列表和后续出站调用按有效授权执行；已发生消耗正常结算；重新开放不清零额度，历史视图不泄露已隐藏资源 |
| Q27 | owner 与协作者分属不同资源授权组 | 许愿格执行按所选 AICC 用户授权，不合并两人权限；协作者目录和模型详情仍按其可见权限过滤，隐藏的 owner 预设模型仅在合法代执行上下文使用 |
| Q28 | 总量初始发放 100,000，实际消耗全部额度后跨日、跨周或重启 | 余额仍为零，新调用被拒绝，提示管理员充值，无自动重置时间 |
| Q29 | 已用 60,000、预占 10,000、累计发放 100,000 时充值 50,000 | 累计发放变为 150,000，可用变为 80,000；历史、预占、周期额度和可见性不变 |
| Q30 | 重复充值请求、同号不同参数、两笔充值与结算并发 | 同一充值只入账一次，同号不同参数拒绝，独立充值累加；无重复发放、丢失更新或重复扣减 |
| Q31 | 普通用户尝试充值、编辑余额或重建总量账户 | 拒绝越权；用户调整自己的周期自限也不能改变管理员分配的总量余额 |
| Q32 | 同时命中周期与总量规则，分别触发其中一条耗尽 | 周期重置不补总量，充值不刷新周期；任何一条不足都不放行，无部分预占残留 |
| Q33 | 首次建立总量账户时有历史及在途调用；之后停用、删除并重建 | 首次累计起点前准入的调用不追扣，之后的适用消耗累计；停用期间继续记账，重建恢复原余额、占用与起点，不重领初始额度 |
| Q34 | 总量累计发放 100,000、实际消耗异常达到 110,000 后充值 5,000，再充值 20,000 | 欠额不被显示的零抹去；两次充值后可用量分别为 0 和 15,000，消耗与充值记录完整 |
| Q35 | 充值成功后响应丢失或服务重启，及 Usage 明细被清理 | 按原充值单号恢复同一结果；账本、占用及余额不丢失，不因明细清理重新获得额度 |

## 12. 本期边界

第一版交付管理员和用户两条完整路径，包括用户组资源可见性、周期与总量额度配置、管理员手工充值、查询、展示、调用前授权与额度约束、结算和恢复，不能只交付一个保存设置的页面。用户组本期用于资源可见性，不新增组共享 token 额度池。

以下能力留到后续：滚动窗口、自定义周期和时区、额度转赠与周期余额结转、批量模板、有有效期的临时额度包、费用预算、RPM / TPM、Agent / Session 独立额度、跨 Provider 实例的厂商或模型家族额度、非 token 计量单位的限额，以及外部通知渠道。总量账户的管理员手工充值属于本期；支付、自助购买、自动充值及资金退款不在本期范围内。

AICC 只能控制经自身发起的调用，直接使用外部 Provider 凭据绕过 AICC 的消耗不在本产品额度内。界面需明确额度的控制范围。
