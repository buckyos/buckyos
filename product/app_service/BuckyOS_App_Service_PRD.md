## 1. 文档目的

本文档用于定义 **BuckyOS App Service** 的产品定位、信息架构、核心交互、安装流程、状态模型与诊断逻辑，作为设计、研发与后续评审的基础版本。

App Service 不是一个“内容生态商店”，而是一个更偏系统层、工程化、保底型的应用服务管理组件。它用于在生态尚未成熟、应用分发形态尚不统一的阶段，承担应用安装、运行观测、基础控制与故障解释的职责。

## 2. 背景与问题定义

### 2.1 已有能力：Library

系统中已经有一个更偏生态型的能力（暂称 **Library**），其目标是承载：

- 内容分发
- 内容购买
- 内容使用
- 通过 Agent / Spider 等机制向生态补充内容与标准化资产

从长期设计目标看，Library 是一个用户完成付费内容网络核心行为的统一入口。

### 2.2 当前现实问题

尽管 Library 的目标完整，但在当前阶段存在以下现实约束：

#### 2.2.1 生态冷启动问题

早期生态内容有限，Library 很可能“空空如也”，无法作为用户进入系统后的主要可用入口。

#### 2.2.2 开发资源与迭代节奏限制

当前版本在该方向上的开发投入有限，而 Library 又依赖若干基础服务，因此其稳定性、完整性与覆盖面不足以承担“系统保底入口”的职责。

#### 2.2.3 内容分发形态不统一

并不是所有应用、内容或服务都适合进入商店式流程，例如：

- 开发中的组件
- 内部测试应用
- 临时分发服务
- 工程师之间直接交付的包
- 仅供开发与联调使用的运行对象

### 2.3 由此引出的产品机会

系统仍需要一个更“冰冷”、更直接、更偏工程化的组件，来承担以下职责：

- 观测系统中的应用层服务运行情况
- 提供更直接的安装入口
- 支持开发 → 安装 → 运行 → 测试 的闭环
- 在生态能力不足时作为系统保底方案

## 3. 产品定位

### 3.1 一句话定义

**App Service 是 BuckyOS 中面向应用层服务的系统级管理组件，用于提供应用安装、运行态观测、基础控制和故障解释能力。**

### 3.2 与 Library 的关系

| 维度 | Library | App Service |
|---|---|---|
| 定位 | 生态/内容网络入口 | 系统级应用服务管理入口 |
| 阶段角色 | 中长期生态核心 | 当前版本保底能力 |
| 主要目标 | 分发、购买、消费、生态增长 | 安装、运行、调试、观测、诊断 |
| 内容来源 | 标准化生态内容 | URL / 本地对象 / 文件等任意来源 |
| 风格 | 运营/生态导向 | 工程/控制台导向 |
| 目标用户 | 普通用户 + 生态参与者 | 开发者、进阶用户、系统使用者 |

### 3.3 设计原则

1. **去生态化**：不承担内容发现、推荐、运营等职责。
2. **工程化优先**：界面风格更接近 `ps` / `docker ps` / 控制台，而非商店。
3. **保底能力优先**：即使 Library 不可用，App Service 也应可独立完成基础安装与运行观测。
4. **直达能力**：用户能快速看到系统在运行什么，快速进入详情并执行控制。
5. **可解释性**：即便不提供所有修复入口，也必须告诉用户为什么应用无法运行。

## 4. 产品目标与非目标

### 4.1 产品目标

本版本 App Service 的目标包括：

1. 展示全部已安装应用及其运行状态。
2. 提供统一的应用详情页，用于查看状态、配置、版本与运行信息。
3. 提供标准控制操作：启动、停止。
4. 提供手工添加入口，支持 URL、App DID / App Meta 文本、`.pikg` 文件三类来源。
5. 将不同来源智能解析并归一化后，拉起统一的系统 App Installer 对话框。
6. 提供可由 App Service、链接、分享、商店等入口复用的标准安装引导流程。
7. 根据 App Document 展示应用信息、安装选项、权限、来源与风险，并要求管理员确认。
8. 将下载和安装过程视为带 `task_id` 的系统任务，提供可恢复、可解释的进度与结果反馈。
9. 在应用异常时提供人类可理解的原因解释，尤其是与 Docker 运行链路相关的问题。

### 4.2 非目标（当前版本不重点承载）

1. 不做商店式内容浏览与推荐。
2. 不要求提供完整的 Docker 管理入口。
3. 不承担内核配置能力。
4. 不要求覆盖复杂的应用发布/分发市场能力。
5. 不以日志分析平台为目标（日志能力可后续评估）。

## 5. 目标用户

### 5.1 普通用户

主要诉求：

- 看到当前运行中的应用
- 知道应用是否正常工作
- 在必要时对应用执行开始/停止操作
- 在应用出问题时获得可理解的原因说明

### 5.2 开发者 / 早期集成者

主要诉求：

- 快速安装开发中的应用
- 通过 URL / 本地对象 / 文件直接接入应用
- 完成开发 → 安装 → 测试的闭环
- 快速判断失败是出在镜像、引擎、配置还是安装资源

### 5.3 系统维护者 / 进阶用户

主要诉求：

- 从统一入口看到应用层、系统服务层、内核层的运行结构
- 判断故障是应用自身问题还是基础运行环境问题

## 7. 信息架构

### 7.1 首页信息层级

首页的核心目标是：**展示全部已安装应用及其运行状态，同时呈现系统服务与内核的当前运行情况**。

系统对象按三层结构展示：

1. **应用层（App Services）**
2. **系统服务层（System Services）**
3. **内核层（Kernel）**

### 7.2 排序与视觉权重

- 默认首先展示 **应用层**
- 其次展示 **系统服务层**
- 最后展示 **内核层**

这样做的原因是：

- 对普通用户来说，“应用”是最自然的认知层。
- 系统完整结构仍然存在，但不会在视觉上过于突兀。
- 内核层维持更“冰冷”的表达方式，减少对普通用户的干扰。

### 7.3 展示形式建议

| 层级 | 展示形式 | 说明 |
|---|---|---|
| 应用层 | 卡片列表 | 有图标、名称、状态、简介 |
| 系统服务层 | 简化列表或次级卡片 | 关注服务名称与状态 |
| 内核层 | 极简文本/列表 | 强调只读与低干预 |

## 8. 首页设计

### 8.1 页面目标

首页是一个运行态总览页。应用层展示全部已安装应用，包括已停止或异常的应用；系统服务层和内核层重点展示当前运行情况。

其设计逻辑接近：

- `ps`
- `top`
- `docker ps`

但对普通用户更友好，优先可视化应用层对象。

### 8.2 页面元素

#### 8.2.1 顶部区域

- 页面标题：App Service
- 安装入口：“+” 按钮

#### 8.2.2 主体区域

按三层分组展示运行对象：

```text
Apps
System Services
Kernel
```

### 8.3 App Card（应用卡片）

应用层对象以卡片展示，建议包含：

- 应用图标
- 应用名称
- 简短描述（如有）
- 当前状态

### 8.4 应用状态（首页可见）

至少支持以下状态表达：

- Running / 运行中
- Starting / 启动中
- Stopped / 已停止
- Error / 异常
- Installing / 安装中

### 8.5 首页核心交互

点击任意应用卡片，直接进入该应用详情页。

设计意图：

- 快速到达详情
- 减少层级
- 让首页真正成为“系统运行态入口”

## 10. Docker 运行依赖模型

由于很多应用基于 Docker，App Service 需要能够解释以下依赖关系：

```text
App
  ↓
Container
  ↓
Image
  ↓
Docker Engine
```

### 10.1 需要暴露给用户的关键状态

#### 10.1.1 Docker Engine 是否工作

如果 Docker Engine 未运行，则应用不工作是合理结果。用户需要在 App Service 中看到这一解释。

#### 10.1.2 应用所需 Image 是否存在

存在“应用已安装，但镜像未拉取成功”的情况。此时应用无法启动，系统应明确指出是 **image missing**，而不是仅笼统显示失败。

#### 10.1.3 Container 是否已创建/已运行

如果镜像存在但容器启动失败，系统也应给出相应诊断。

### 10.2 运行态依赖状态建议展示方式

在详情页中建议统一展示：

- Docker Engine: Running / Not Running
- Image: Present / Missing
- Container: Running / Stopped / Error

### 10.3 设计要求

App Service 不一定需要为 Docker 问题提供完整修复入口，但必须具备：

- **观测能力**
- **原因解释能力**

## 11. 诊断与错误表达

### 11.1 目标

系统在应用不可运行时，不应只展示技术性失败状态，而应尽可能输出用户可理解的原因。

### 11.2 最低支持错误类型

- Docker 引擎未运行
- Docker 镜像不存在 / 拉取失败
- 容器启动失败
- 安装文档无法解析
- 安装资源下载失败

### 11.3 表达形式

推荐以“原因描述”为主，而不是直接暴露大量底层日志。

示例：

- Docker 引擎未运行，应用无法启动
- 应用镜像尚未下载完成，因此当前无法运行
- 容器启动失败，请检查安装配置或运行依赖

> 注：更详细日志是否在后续版本提供，当前记为 TBD。

## 12. 安装入口

### 12.1 App Service 手工添加入口

在 App Service 首页提供右上角 **“+” 按钮**，进入手工添加流程。该入口负责接收和解析用户提供的安装来源。

### 12.2 其他拉起入口

系统公共 App Installer 对话框应支持由多个入口拉起，例如：

- App Service 手工添加
- 安装链接
- App 分享
- Library / 商店
- 其他已经获得 App Document、Installer 标准输入或 `task_id` 的系统组件

当前版本不要求同时实现所有入口，但公共对话框不能依赖 App Service 首页上下文。

### 12.3 两阶段边界

安装流程拆分为两个阶段：

1. **Stage 1：添加与解析来源**。由 App Service 的手工添加页面负责，将 URL、App DID / App Meta 文本或选中的 `.pikg` 文件转换为 Installer 的标准输入。
2. **Stage 2：标准安装引导**。由系统公共 App Installer 对话框负责校验、确认、下载、安装和结果反馈。

已经具备 Installer 标准输入或现有 `task_id` 的入口，可以跳过 Stage 1，直接拉起 Stage 2。

## 13. 安装来源

App Service 手工添加流程需要支持三类输入来源，并通过统一解析器完成智能识别。来源解析不能改变后续标准安装引导的交互。

本章产品语境中的 **App Meta** 对应安装协议中的 **App Document / APPDOC**。PRD 使用“App Meta”描述用户可以粘贴或由 URL 指向的分发内容，进入 Installer 后统一使用 App Document、App Document Object ID 和 `(App DID, "app")` 的正式协议语义。

### 13.1 URL 智能解析

对 Stage 1 而言，一个合法的安装 URL 只允许指向以下两类内容之一：

1. **App Meta URL**：响应内容是 App Meta JWT 或 JSON，即 App Document 候选内容。
2. **PIKG URL**：响应内容是 `.pikg` 文件。

URL 智能解析的含义是判断 URL 属于上述哪一类，并转换为相应的 Installer 输入；它不表示对普通网页进行抓取、搜索或推测安装信息。

- 识别为 App Meta URL 时，系统读取候选文档，提取 App DID，并按 13.2 的安全规则继续处理。
- 识别为 PIKG URL 时，系统将 URL 作为获取 `.pikg` 的位置，后续由 Installer Acquisition 下载到受控 Staging Area。
- 无法识别为上述任一类型时，该 URL 不是合法安装来源，不得进入 Stage 2。

适用场景：

- 开发者直接分享安装链接
- 内部分发
- 非商店化交付

解析失败时应区分 URL 无效、资源不可达、内容既不是 App Meta 也不是 `.pikg`、内容损坏或版本不兼容等原因，并保留用户原始输入。

### 13.2 粘贴 App DID / App Meta

Stage 1 提供一个文本输入区域，允许用户直接粘贴：

1. **App DID**：最简单的输入，直接作为 `identifier` 提交，并执行 `(App DID, "app")` 可信解析。
2. **签名 App Meta JWT**：推荐方式，对应协议中的 `APPDOC.wt` 文本。系统解析 JWT，提取 App DID、文档内容、签名和签发者信息，并将其作为带签名的 App Document 候选。
3. **App Meta JSON**：对应协议中的 `APPDOC.json` 内容。允许粘贴完整 JSON，但它是未签名候选内容，不能仅凭 JSON 自身证明真实性。

界面应优先引导用户复制和粘贴 JWT；文本识别成功后，在进入 Stage 2 前展示识别结果：“App DID”“签名 App Meta JWT”或“未签名 App Meta JSON”。

对于粘贴的 JWT 或 JSON，系统必须：

- 从候选内容中提取 App DID，并校验文档结构、`id` 和 `doc_type`。
- 将候选文档导入受控候选区，计算 App Document Object ID；该操作只保存待验证内容，不代表发布、信任或安装成功。
- 对提取出的 App DID 执行 `(App DID, "app")` 权威解析，并比较候选文档与权威结果的 Object ID、发布状态和 owner 证据。
- 对 JWT 验证签名及 owner 约束；签名有效只能证明相应 owner 授权构造了该内容，不能替代 App DID 的权威发布状态。
- 对未签名 JSON 明确显示安全警告。在普通安装策略下，无法与可信解析结果一致时不得继续安装；仅明确的本地开发或系统内部策略可以带警告继续。

任何候选内容都不能通过自行声明的 DID、owner 或来源为自身建立信任。

典型来源包括：

- 本机已存在资源
- 通过 MessageHub 等渠道收到的对象引用
- 其他方式同步到本地但尚未安装的对象

### 13.3 选择 `.pikg` 文件

Stage 1 不直接实现文件浏览，而是拉起独立的系统文件选择对话框。用户可以从两个位置选择 `.pikg`：

1. **本地设备**：通过文件选择对话框上传本地 `.pikg`。
2. **Personal Server**：选择已经保存在用户 Personal Server 文件系统中的 `.pikg`。

文件选择对话框应只允许确认 `.pikg` 文件，并向 Stage 1 返回轻量文件引用，不直接把文件二进制交给主页面。客户端或服务端随后将所选文件导入受控 Staging Area，得到 `staging_handle`，再交给 Installer 读取包内 App Document 与安装资源。

无论文件来自本地设备还是 Personal Server，公共安装接口都只能接收受控 `staging_handle`，不得接收任意服务端文件路径。本地上传与 Personal Server 选择在进入 Installer 后使用完全相同的校验和安装流程。

### 13.4 归一化结果

不同来源最终应归一化为 Installer 已定义的两类标准输入之一：

- **标识符入口**：`identifier`，可选携带 `referrer` 和初始 `options`；用于 App DID、名称、Object ID、URL 或分享对象。
- **本地包入口**：`staging_handle` 和可选初始 `options`；用于已经从本地设备或 Personal Server 导入 Staging Area 的 `.pikg`。

粘贴的 App Meta JWT / JSON 应先作为候选文档导入，得到 App Document Object ID，再以 Object ID 作为 `identifier` 提交。原始来源、输入类型、Referrer、候选文档和获取过程中的证据必须随安装任务保留，用于后续来源与信任解释。

## 14. 安装向导流程

安装采用“两阶段、一个公共对话框”的流程。

### 14.1 Stage 1：手工添加与来源解析

Stage 1 只存在于需要用户手工提供来源的入口。用户选择：

- 输入 URL；智能识别为 App Meta URL 或 PIKG URL
- 粘贴 App DID、App Meta JWT 或 App Meta JSON
- 选择 `.pikg`；可从本地设备上传，或从 Personal Server 选择已有文件

文本输入由 Stage 1 直接识别；`.pikg` 选择通过独立系统文件选择对话框完成。系统将输入转换为 `identifier` 或受控 `staging_handle`，提交标准安装请求并获得 `task_id`，随后拉起系统公共 App Installer 对话框。

在提交前，Stage 1 至少应展示识别出的来源类型；对于未签名 App Meta JSON，还应先展示“真实性尚未验证”的安全提示。其他入口也可以直接提交标准安装请求或使用已有 `task_id` 拉起公共对话框。

因此，本阶段的UI由1个万能Text Input (可以支持拖拽直接上传) + 2个按钮（上传pipkg ,选择pikg) + 1个下一步按钮组成
下一步按钮只有在确认解析到了“可以下一步”的合法input内容时，才会可用。

> 本章的 Step 是面向用户的 UI 阶段，不等同于安装协议中的 Resolve、Inspect、Acquire、Verify、Prepare、Deploy、Activate Stage。

### 14.2 Stage 2 / Step 1：Verify 与展示 App 信息

公共对话框通过 `task_id` 跟踪任务。第一步主要对应协议层 Resolve 与 Inspect 的结果，并展示进入安装确认所需的信息：

- App Document 是否有效，App DID 与发布状态是否可确认
- 当前 App Document Object ID、应用版本与发布版本
- 原始输入类型、来源、Referrer 与可用的信任证据
- App Meta 是签名 JWT、未签名 JSON，还是由 App DID 权威解析获得
- 当前目标平台是否支持
- 内容与信任是否离线就绪
- 缺失内容、预计下载量与可用 Source

校验通过后展示：

- 图标、名称、版本、描述
- App DID、App Document Object ID
- 原始来源与来源类型
- 发布者、签名或信任信息（如有）
- 无法验证或存在风险的项目

如果任务正在等待信任解析，UI 应展示 `TRUST_RESOLUTION_REQUIRED`，而不是把它归类为内容下载。如果身份已撤销或目标不受支持，UI 应禁止继续安装并明确说明原因。

### 14.3 Stage 2 / Step 2：安装选项与管理员确认

公共对话框根据 App Document 动态生成安装选项，展示默认值、必填项和可修改项，并基于 Inspect 结果生成稳定的 `InstallPlan`。至少需要覆盖：

- 目标 Node
- 安装组件
- 安装参数与自定义 Settings
- 所需权限
- 目录访问范围
- 网络或其他能力声明
- 系统资源访问要求
- 依赖与安装后的技术影响

用户修改目标或参数后，系统必须重新计算 `InstallPlan`、内容就绪状态和安装就绪状态。用户确认最终 Plan 与权限后，需要输入管理员密码完成管理员授权，并在同一个 `task_id` 上提交确认。该授权表达的是系统级安装操作的 sudo 语义，不要求 UI 暴露底层命令。

### 14.4 Stage 2 / Step 3：下载（如有必要）

管理员确认后，如果 `InstallPlan` 仍有缺失内容，原安装任务进入 Acquire 阶段。公共对话框展示当前资源、可用 Source、预计下载量和进度；内容获取完成后进入协议层 Verify。

如果所需资源已经存在，下载阶段可以自动跳过，但任务状态中仍应记录该阶段无需执行。

### 14.5 Stage 2 / Step 4：执行安装

内容获取与 Verify 完成后，系统在同一个 `task_id` 下继续执行 Prepare、Deploy 和 Activate，包括：

- 写入安装记录
- 注册应用服务
- 准备运行环境
- 根据安装选项应用配置
- 启动并执行健康检查

公共对话框持续展示任务阶段和核心进度，详细任务信息可同时在系统任务管理器中查看。

### 14.6 Stage 2 / Step 5：安装成功

安装成功后，公共对话框展示：

- 安装成功状态
- 已安装版本和目标节点等核心结果
- 自动启动状态
- 进入应用详情页或关闭对话框的操作

安装完成后默认自动启动应用。安装成功与运行成功是两个独立状态，自动启动失败不能覆盖已经完成的安装结果。

### 14.7 公共失败页

Verify、下载或执行安装任一阶段失败时，公共对话框进入失败页。失败页必须展示人类可理解的错误分类、失败阶段和下一步动作，不以底层错误码作为唯一反馈。

## 15. 安装任务与状态流转

### 15.1 `task_id` 是安装事务的统一标识

Stage 1 提交标准安装请求时，系统立即创建可恢复的安装事务并返回 `task_id`。Resolve、Inspect、等待确认、Acquire、Verify、Prepare、Deploy 和 Activate 都属于同一个任务；公共对话框和任务管理器通过同一个 `task_id` 查询状态。

### 15.2 在 App Service 中的表现

安装开始后：

- App Service 中出现应用“安装中”状态
- 系统任务管理器中出现对应安装任务
- 公共 App Installer 对话框展示当前阶段、进度摘要与错误信息

用户关闭并重新打开公共对话框时，应能通过 `task_id` 恢复同一安装任务的状态，而不是创建重复任务。更详细的执行信息可前往任务管理器查看。

### 15.3 状态流转

协议层状态及其默认产品表达如下：

| 协议 Stage / Task Status | 默认产品表达 |
|---|---|
| Resolve / Inspect | 正在校验应用 |
| `WaitingForApproval` | 等待安装确认 |
| Acquire | 正在获取内容 |
| Verify | 正在验证内容 |
| Prepare / Deploy | 正在安装 |
| Activate | 正在启动并检查应用 |
| Completed + `Installed` | 安装成功 |

任务可能进入需要单独解释的状态：

```text
WAITING_FOR_TRUST_RESOLUTION
IDENTITY_REVOKED
CONTENT_DOWNLOAD_REQUIRED
DEPLOYED_BUT_ACTIVATION_FAILED
```

### 15.4 安装结果反馈

安装成功后，首页中对应应用卡片从“安装中”切换为“启动中”或“运行中”。如果自动启动失败，应显示“已安装但启动失败”，并保留安装成功结果。

### 15.5 最低任务进度信息

通过 `task_id` 至少能够获得：

- 当前阶段
- 当前状态
- 进度摘要；无法计算百分比时可以只展示阶段状态
- 成功结果或失败分类
- 面向用户的错误说明

## 16. 安装失败处理

### 16.1 Stage 1 来源解析与 Stage 2 Verify 失败

例如：

- URL 无效
- URL 内容既不是 App Meta 也不是 `.pikg`
- App DID 无法解析
- App Meta JWT 格式或签名无效
- App Meta JSON 缺少合法 App DID，或与权威解析结果不一致
- 本地文件不是有效的 `.pikg`
- Personal Server 文件不存在、无访问权限或已发生变化
- `.pikg` 文件损坏或版本不兼容
- App Document 非法
- 来源或签名无法验证

处理方式：

- 在 Stage 1 或 Verify 页面直接提示
- 保留原始来源，允许用户返回修改
- 不进入管理员确认和执行安装阶段

### 16.2 下载与执行阶段失败

例如：

- 下载失败
- Docker Pull 失败
- 权限确认后执行中断
- 运行环境准备失败

处理方式：

- 公共失败页显示失败阶段、错误分类与下一步动作
- App Service 中显示安装失败或不可运行状态
- 支持重试；必要时允许返回修改来源或安装选项
- 支持复制脱敏后的错误信息
- 任务管理器中可通过 `task_id` 查看更详细失败信息

## 17. 交互原则总结

1. **首页纯粹**：用户一进来先看到应用及其运行状态。
2. **详情直达**：点卡片即可进入详情页，无额外层级。
3. **来源归一**：App Meta URL、PIKG URL、App DID、App Meta JWT / JSON 和选中的 `.pikg` 最终进入同一标准安装流程。
4. **对话框公共化**：App Installer 不依赖具体拉起入口，所有入口复用同一套确认与执行 UI。
5. **解释优先**：安装前解释来源、权限和风险，失败后解释原因与下一步动作。
6. **任务可追踪**：下载和安装由 `task_id` 驱动，不使用无法恢复的黑盒 Loading。
7. **职责分离**：App Service 提供手工入口与核心状态，公共对话框提供安装引导，任务管理器提供详细执行信息。
8. **工程风格**：这个组件不是商店，而是控制面板。

## 19. 功能需求清单（Functional Requirements）

### FR-01 首页运行态展示

系统应展示全部应用及系统运行对象，并按“应用 / 系统服务 / 内核”三层分组。

### FR-02 应用优先展示

系统应将应用层对象置于默认首屏位置，并以更友好的卡片形式呈现。

### FR-03 详情直达

点击应用卡片后，系统应直接进入该应用详情页。

### FR-04 详情页状态展示

系统应在详情页展示应用状态、安装配置、自定义设置、版本与运行环境信息。

### FR-05 标准控制操作

系统应支持对应用层服务执行启动与停止操作。

### FR-06 手工添加入口

系统应在 App Service 首页提供“+”入口，用于输入 URL、粘贴 App DID / App Meta 文本或选择 `.pikg` 文件。

### FR-07 URL 智能解析

系统应将合法安装 URL 明确识别为 App Meta URL 或 PIKG URL；其他内容类型不得进入标准安装引导。

### FR-08 App DID / App Meta 文本识别

文本输入应识别 App DID、签名 App Meta JWT 和未签名 App Meta JSON。JWT / JSON 应作为候选文档导入并取得 App Document Object ID，不能因解析成功而自动获得可信状态。

### FR-09 PIKG 文件选择

系统应通过独立文件选择对话框支持上传本地 `.pikg`，或选择 Personal Server 中已有的 `.pikg`，并将两者统一转换为受控 `staging_handle`。

### FR-10 安装来源归一化

系统应将三类安装来源归一化为 Installer 的 `identifier` 或 `staging_handle` 标准输入，并保留原始输入类型、来源和候选文档证据。

### FR-11 公共 App Installer 对话框

系统应提供不依赖具体入口的公共安装对话框，App Service 和其他系统入口能够复用同一流程。

### FR-12 Verify

系统应在安装前展示 Resolve、Inspect 和内容就绪分析的结果，包括 App 身份、输入类型、来源、信任证据、资源就绪状态和系统兼容性。

### FR-13 App Document 驱动的安装选项

系统应根据 App Document 生成安装选项与稳定的 `InstallPlan`，并展示权限、资源需求和安装后的技术影响。

### FR-14 管理员鉴权

系统应在开始下载或安装前要求输入管理员密码。

### FR-15 安装任务化

系统应在收到标准安装请求时创建统一任务并返回 `task_id`，公共对话框、App Service 与任务管理器应基于同一任务状态展示 Resolve 到 Activate 的全过程。

### FR-16 下载与安装进度

公共对话框应展示当前阶段与进度摘要；没有下载需求时应自动跳过下载阶段。

### FR-17 结果闭环

公共对话框应提供明确的安装成功页和失败页。失败页应支持重试，并在必要时返回修改来源或安装选项。

### FR-18 异常原因解释

系统应在应用无法正常运行时，向用户呈现可理解的原因描述。

### FR-19 Docker 依赖状态可见

系统应显示 Docker Engine、Image 与 Container 的关键状态。

## 20. 非功能要求（Non-functional Requirements）

### 20.1 可理解性

错误状态应尽量以自然语言表达，降低普通用户理解门槛。

### 20.2 即时反馈

应用控制操作与安装状态变化应有明确反馈。

### 20.3 一致性

所有拉起入口应使用同一公共安装流程、状态命名与字段含义，避免同一安装请求在不同入口中出现不同结果。

### 20.4 可恢复性

公共对话框关闭或页面刷新后，应能通过 `task_id` 恢复仍在执行或已经结束的安装任务状态，避免重复安装。

### 20.5 安全与可解释性

管理员密码不得进入安装任务日志或错误详情。来源、信任、权限和风险信息无法获得时，应明确显示“未知”，不能默认视为可信。

解析成功不等于验证成功：

- App Meta JWT 必须显示签名验证、owner 约束和权威发布状态的独立结果。
- App Meta JSON 必须标记为未签名候选内容，不能仅依赖文档内部声明的 DID 或 owner 建立信任。
- 文件选择对话框只返回文件引用；主页面不得获得 Personal Server 任意路径访问能力。

### 20.6 可扩展性

后续应能平滑扩展：

- 更新
- 卸载
- 日志
- 更详细运行指标
- 与 Library 的联动

## 21. 依赖与前置条件

App Service 的部分能力依赖：

1. App Document 格式及安装选项、权限、来源、签名等字段定义
2. URL 内容类型识别，以及 App Meta JWT / JSON 候选文档导入和 Object ID 计算能力
3. 可访问本地设备与 Personal Server 的系统文件选择对话框，以及轻量文件引用到受控 `staging_handle` 的转换能力
4. 公共 App Installer 对话框的拉起协议，以及 `identifier`、`staging_handle`、`task_id` 三类上下文
5. 支持 `task_id` 和阶段化进度的系统任务管理器
6. 管理员鉴权机制
7. Docker 运行环境与状态查询接口
8. 应用/服务运行状态查询接口

## 22. 风险与注意事项

### 22.1 状态定义需统一

“待校验 / 待确认 / 下载中 / 安装中 / 已安装 / 启动中 / 运行中 / 失败”等状态需要在产品、前端、后端之间统一定义，并区分“安装成功”与“启动成功”。

### 22.2 App Document 安装选项字段需定稿

核心 App Document schema 已由安装协议定义；安装选项、默认值、权限与技术影响的 UI 映射仍需定稿。公共对话框原型可以先使用占位模型，但进入实现前必须完成字段和默认值语义对齐。

### 22.3 粘贴 App Meta 的信任边界

JWT 带有签名不等于已由 App DID 当前发布，JSON 能被解析也不等于内容真实。产品文案和按钮状态必须区分“格式有效”“签名有效”“owner 有效”和“权威发布状态有效”。

### 22.4 URL 类型识别边界

URL 只允许解析为 App Meta 或 `.pikg`。如果识别规则依赖扩展名、Content-Type 或内容探测，必须限制下载大小、重定向和错误回退，避免把任意网页或不受控大文件交给解析器。

### 22.5 文件选择与访问边界

本地上传和 Personal Server 文件选择必须经过独立文件选择对话框。调用方只获得选中的轻量文件引用，不能借安装流程扩大到任意文件或路径访问权限。

### 22.6 多入口上下文需统一

不同入口可能携带 `identifier`、本地包 `staging_handle` 或已有 `task_id`。若拉起协议没有统一这三类上下文，公共对话框会产生入口相关的分支逻辑。

### 22.7 信任表达需保守

来源可识别不等于可信。签名、发布者或分享者信息缺失时，应明确表达未知状态，避免给出未经依据的信任结论。

### 22.8 Docker 异常原因需收敛

底层错误很多，但产品层需要收敛为少数可解释类别，否则用户会被技术细节淹没。

### 22.9 普通用户与开发者视角需平衡

如果表达过于底层，会影响普通用户理解；如果过于抽象，则开发者无法有效调试。需在信息默认层级上做好平衡。

## 23. 已确认事项与待定事项

### 23.1 已确认事项

1. 首页展示全部应用，包括已安装但未运行的应用。
2. 应用详情页中的 Settings 允许编辑。
3. 不提供 Restart 按钮，用户通过 Stop + Start 完成重启。
4. 安装完成后默认自动启动。
5. 安装失败后提供重试入口。
6. 应用详情页提供日志入口或跳转。
7. 系统服务层与内核层先展示系统可获得的 `service_info` 和 `service_spec` 简要信息。
8. 手工添加支持 URL、App DID / App Meta 文本和 `.pikg` 文件选择。
9. 来源解析与标准安装引导分离，标准安装引导使用系统公共 App Installer 对话框。
10. 合法安装 URL 只指向 App Meta 或 `.pikg`，不对普通网页做智能抓取。
11. App Meta 文本支持 App DID、签名 JWT 和未签名 JSON，并优先推荐 JWT。
12. `.pikg` 可以从本地设备上传，也可以从 Personal Server 已保存文件中选择。

### 23.2 待定事项

1. App Document 中安装选项、默认值、权限与技术影响的 UI 映射。
2. App Meta URL 与 PIKG URL 的识别顺序、Content-Type、重定向、大小限制和错误分类。
3. 粘贴 JWT / JSON 的大小限制、候选文档导入接口及 App Document Object ID 回传方式。
4. 文件选择对话框返回的轻量文件引用格式，以及本地上传 / Personal Server 文件到 `staging_handle` 的转换协议。
5. 多入口拉起公共 App Installer 时，`identifier`、`staging_handle` 或 `task_id` 的传递方式与鉴权边界。
6. Installer 状态、Readiness、结构化错误到用户文案和操作按钮的映射。

## 25. 附：产品总结

BuckyOS App Service 在当前版本中承担的是一个非常明确的角色：

> **它不是生态，不是商店，而是系统应用层服务的控制台。**

它需要在 Library 尚未成熟的阶段，为系统提供最基础、最可靠、最直接的应用接入与运行管理能力；同时，App Service 的手工添加入口与其他系统入口统一复用公共 App Installer 对话框，形成一致、可追踪、可恢复的安装体验。
