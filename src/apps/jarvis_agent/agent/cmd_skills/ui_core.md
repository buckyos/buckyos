---
name: ui_core
description: Commands of a conversation (UI session) — media understanding, work sessions and goals it started, memory, notifications, skills, subscriptions, tasks.
requires: an OpenDAN UI session (agent-session, llm_understand_media on PATH)
baseline: standard
---
Run these through `shell`; the session they act for comes from the environment (on a node runtime: from `.opendan/session.json` in the session's working directory).
The owner chooses read-write (default) or read-only access when creating the Agent. User-data writes follow that choice; `$OPENDAN_AGENT_ROOT` always stays writable, including sessions, memory, workspaces and skills. For a read-only refusal, keep drafts and generated files in your session or AgentRoot and report the refused destination.
AgentRoot is the owner's `home/agents/<agent_id>/` (`<agent_id>` is the full domain name); keep Agent data there, separate from the owner's ordinary files.
The final chat reply follows the current behavior's `[reply]` schema (`behaviors/chat_route.toml` for Jarvis): only `reply` is shown, `topic` updates the conversation, and `artifacts` become attachments. If validation still fails after one correction, the host closes the Turn as failed and shows its failure notice; inspect the run/worklog for the original output rather than sending the JSON or correction prompt to the user.
- `llm_understand_media <file | object id | url> [--goal "<what to find out>"]`: understand an image, a document (PDF …), audio or video — an attachment of a message (its id exactly as the attachment line gives it), a file, a link — through a model that can perceive it; the result is text. Use it before you answer about media; plain text files and text objects you read with `read`.
- `read` also takes system URLs (`obj://…`, `cyfs:///…`, a Zone's `https://…`; `## Objects` names the ones this session starts from): it describes the object — what it is, its properties, actions (with their risk) and events — and `read uri=<url> property=<name>` reads one declared property. It reads as you (this Agent): a refusal means your identity may not see it.
- `agent_tool xcall <obj://…> <action> [key=value …]`: call an action the object's description declares; the Provider authorizes it with your identity and the result names the action's risk. Ask the user before an action whose risk is not `read_only`.
- `agent-session read-session <sid> --report`: the full report of a work session (the background context shows one line of it).
- `agent-session sessions --children --active`: a readable list of the work sessions this conversation started and their state; add `--json` for structured session summaries.
- `agent-session workspace list` / `agent-session runtime list`: readable lists of registered workspaces and runtimes; add `--json` for complete records, or use `workspace get <id>` / `runtime get <id>` for one record.
- `agent-session recall <tag>...` / `agent-session ctl perceive "<sentence>"`: memory (see Memory).
- `agent-session notify show <id>` / `notify answer <id> (--option <v> | --text "<t>")` / `notify ack <id>`: notifications shown to the user (see the constraints).
- `agent-session goal list` / `goal show <id>` / `goal post <id> --msg "<text>"`: the agent's goals.
- `agent-session skill list` / `skill install <x.pikg | dir>` / `skill remove <name>`: the agent's skills — command manuals a work session can be given when it is created, and methods for goals. A manual marked `needs: extended environment` (or a platform) only works in a session on a runtime that declares it (`agent-session runtime list`). Install or remove one when the user asks; sessions already running keep the manuals they started with.
- `agent-session copy --from <session|workspace|runtime_id>:<path> --to <...>:<path> [--replace]`: one file between this session's runtime (where commands run) and its workspace or another runtime, verified and committed whole (`copy status|cancel <id>`).
- `agent-session ctl subscribe <spec>` / `ctl unsubscribe <id>`: follow an object or a session — `semi:object:<obj:// url>[#<event>]` shows its changes in the background context, `active:object:<obj:// url>[#<event>]` starts a turn on each change (the events are those its `read` lists; without `#<event>`, all of them), `semi:session:<sid>` follows a session's state. Only this Zone's `obj://` objects have events; another Zone's https objects are refused. A background line names its source as `<kind>:<id>`.
- `agent-session task wait <task_id> --wait-ms <ms>` / `task state <task_id>` / `task cancel <task_id>`: a shell command that continued as a task (give that shell call a larger wait_ms than the wait).
