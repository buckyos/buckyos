---
name: ui_core
description: Commands of a conversation (UI session) — media understanding, work sessions and goals it started, memory, notifications, skills, subscriptions, tasks.
requires: an OpenDAN UI session (agent-session, llm_understand_media on PATH)
baseline: standard
---
Run these through `shell`; the session they act for comes from the environment. A conversation always runs on your private runtime (your own environment, `extended`, every `agent-session` command and your skills' commands at hand); it knows one other runtime, the owner's default runtime (`<runtime>` in your context: id, OS, whether it is available, desktop access) — the owner's own machine. Anything to be done on the owner's machine — a screenshot, opening a file there, running a program there — is a work session created by `try_analyze_user_intent`, not something this conversation does; the conversation only reads there: a path the user types (`/Users/…`, `C:\…`, `/home/…`) is a path on the owner's default runtime, read with `read` or `agent-session copy --from <owner default runtime id>:<path> --to session:<file>` (when that runtime is unavailable or the path is not there, try your private runtime next, and say which machine you read from), and a quick look (a directory listing, one short command) goes through `agent-session run --runtime <owner default runtime id> --cwd <dir> -- <command>`. Other runtimes are not your business: work that needs them is a work session (a plan sees the whole table).
The owner chooses read-write (default) or read-only access when creating the Agent. User-data writes follow that choice; `$OPENDAN_AGENT_ROOT` always stays writable, including sessions, memory, workspaces and skills. For a read-only refusal, keep drafts and generated files in your session or AgentRoot and report the refused destination.
AgentRoot is the owner's `home/agents/<agent_id>/` (`<agent_id>` is the full domain name); keep Agent data there, separate from the owner's ordinary files.
The final chat reply follows the current behavior's `[reply]` schema (`behaviors/chat_route.toml` for Jarvis): only `reply` is shown, `topic` updates the conversation, and `artifacts` become attachments. If validation still fails after one correction, the host closes the Turn as failed and shows its failure notice; inspect the run/worklog for the original output rather than sending the JSON or correction prompt to the user.
- `llm_understand_media <file | object id | url> [--goal "<what to find out>"]`: understand an image, a document (PDF, docx, pptx, odt …), audio or video — an attachment of a message (its id exactly as the attachment line gives it), a file, a link — through a model that can perceive it; the result is text. Media the model cannot take as-is is converted by the system media pipeline first and the command waits for it: a long document can take minutes, and like any long shell command it continues as a task whose result comes back to you, so do not start it again. A long document is read as a catalog: the model sees the pages that fit and match the goal, and the end of the result says which it did not see; name a page in the goal ("page 120") to read it. Run it as a plain command, without `&&` or pipes, so that only the text result reaches you. Use it before you answer about media; plain text files and text objects you read with `read`.
- `read` also takes system URLs (`obj://…`, `cyfs:///…`, a Zone's `https://…`; `## Objects` names the ones this session starts from): it describes the object — what it is, its properties, actions (with their risk) and events — and `read uri=<url> property=<name>` reads one declared property. It reads as you (this Agent): a refusal means your identity may not see it.
- `agent_tool xcall <obj://…> <action> [key=value …]`: call an action the object's description declares; the Provider authorizes it with your identity and the result names the action's risk. Ask the user before an action whose risk is not `read_only`.
- `agent-session read-session <sid> --report`: the full report of a work session (its `finished` event shows one line of it).
- `agent-session sessions --children --active`: a readable list of the work sessions this conversation started and their state; add `--json` for structured session summaries.
- `agent-session post <plan sid> --msg "<the user's words and what the plan needs to understand them>"`: forward the user's change, addition or answer about running work to its plan session (one created with `--class plan_simple`); the plan decides what changes. Never post to the work sessions a plan runs.
- `agent-session workspace list`: readable list of registered workspaces (`--json` for complete records, `workspace get <id>` for one). `agent-session runtime list` exists but is not for choosing where work runs: the conversation's two runtimes are in `<runtime>`, and intent analysis places work.
- `agent-session recall <tag>...` / `agent-session ctl perceive "<sentence>"`: memory (see Memory).
- `agent-session notify show <id>` / `notify answer <id> (--option <v> | --text "<t>")` / `notify ack <id>`: notifications shown to the user (see the constraints).
- `agent-session goal list` / `goal show <id>` / `goal post <id> --msg "<text>"`: the agent's goals.
- `agent-session skill list` / `skill install <x.pikg | dir>` / `skill remove <name>`: the agent's skills — command manuals a work session can be given when it is created, and methods for goals. A manual marked `needs: extended environment` (or a platform) only works in a session on a runtime that declares it (`agent-session runtime list`). Install or remove one when the user asks; sessions already running keep the manuals they started with.
- `agent-session copy --from <session|workspace|runtime_id>:<path> --to <...>:<path> [--replace]`: one file between your private runtime (where commands run) and its workspace or another runtime, verified and committed whole (`copy status|cancel <id>`).
- `agent-session run --runtime <runtime_id|workspace> [--cwd <absolute dir on it>] [--timeout <secs>] -- <command>`: one command on another runtime of this agent, in that machine's own shell and PATH; output and exit code come back as they are (124: timed out). For a quick look only — a listing, a short read; anything that takes work or changes things on the owner's machine is a work session.
- `agent-session ctl subscribe <spec>` / `ctl unsubscribe <id>`: follow an object or a session — `semi:object:<obj:// url>[#<event>]` shows its changes in the background context, `active:object:<obj:// url>[#<event>]` starts a turn on each change (the events are those its `read` lists; without `#<event>`, all of them), `semi:session:<sid>` follows a session's state. A session of yours has `changed` and `finished` events (`obj://<agent_id>/sessions/<sid>#finished`). Only this Zone's `obj://` objects have events; another Zone's https objects are refused. A background line names its source as `<kind>:<id>`.
- `agent-session task state <task_id>` / `task cancel <task_id>`: a shell command that continued as a task. Its end comes back to you as input on its own, with its full result; there is nothing to wait for.
