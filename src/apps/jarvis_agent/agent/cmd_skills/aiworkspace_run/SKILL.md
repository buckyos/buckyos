---
name: aiworkspace_run
description: Execute a wish run of an AI Workspace that the user who owns you handed to you (a Goal naming a run and its claim token) — claim it, analyze the task, or write and trial-run the wish's macro, or run the stored macro; hand it in with what your model used, keep the lease alive — take a stage's outcome back (`run-rollback`), start an analysis run yourself when you worked out a wish's task in a conversation (such as one from the workspace's Agent panel, whose messages carry an `[aiworkspace context]` block), start a wish's stages or refresh a sourced table through the workspace's objects (`agent_tool xcall`, after asking the user), and read a workspace's tables and documents.
requires: the buckyos command (agent container: /opt/buckyos/bin/agent-tools/buckyos; host: $BUCKYOS_ROOT/bin/buckyos) signed in as this Agent (it runs macros with its own Deno); a hosted run the user who owns you started for you (you act in the workspace as yourself, judged as that user unless the workspace configured you), or update on the wish (an analyze or code run you start yourself; running the stored macro takes run or any write right on the wish)
baseline: standard
commands: jq
---
#### When to use
- A Goal gives you an AI Workspace run: a workspace id, a run id and a claim token (`ct_…`). The user who owns you chose "Use my Agent" for a task on the canvas (a "wish") and started it: a hosted run, executed by you, its model calls billed to that user (`run-get` → `context.executor` names you, `context.trigger` the user). Nobody else hands you runs; there is no workspace setting for it. The service fixed the task's inputs and output contract; you do the work and hand it in. When the stage ends the service checks it and writes its outcome into the workspace itself, at once (one Commit), and adds a record to the wish's history — failures are recorded too. Nobody confirms it first; the way back is the record's rollback. You never write workspace data yourself.
- Reading a workspace without a run (`info`, `read`, `query`) is for looking things up; it needs the owner to have granted you access.

#### Before you start
- `buckyos aiws --help`, `buckyos aiws run-claim --help`: the verbs and their options. Source: `cli/modules/aiws.ts` in buckyos-websdk (the only implementation).
- `buckyos aiws run-get --workspace <ws> --run <run>` shows the run's state, stage (`analyze`, `code`, `run`), execution context and a brief. A run that is `cancelled` is over; a run that is `interrupted` can be claimed again (a new attempt).
- The three stages: `analyze` settles the task contract (inputs, output contract, checks); `code` writes the wish's **macro** — one program that produces every result — and trial-runs it; when it ends only the macro is stored (the trial's results are not written: how many it made, which checks passed and its log go into the run's record); `run` runs the stored macro again on current data, with no model in the loop, and writes the results. How to write a macro: the macro guide, `src/frame/aiworkspace/aiws/README.md` (embedded in `stage.system` of a `code` run).
- Keep the lease alive while you work: `run-heartbeat` at least every minute (the claim answers `lease_ms`); a lapsed lease ends your attempt (`RUN_REVOKED`).

#### Shortest path (a code run)
```bash
WS=ws_…; RUN=run_…; TOKEN=ct_…
buckyos aiws run-claim --workspace $WS --run $RUN --claim-token $TOKEN > claim.json      # attempt, run_token, lease, stage (keep it outside work/)
jq -r .stage.user claim.json > task.md                                                   # the task: context map, task description, inputs, output contract, checks
jq -r .stage.system claim.json > rules.md                                                # the stage's rules and the macro guide
buckyos aiws run-files --workspace $WS --run $RUN --attempt 1 --dir work                 # context/, request.json, catalog/, lib/ (program host, stage budget), program/main.js if one exists
# write work/program/main.js: `export default async function main(aiws) { aiws.declare({ … }); … }` — see the macro guide in rules.md
buckyos aiws run-program --workspace $WS --run $RUN --attempt 1 --dir work               # runs it as every executor does and hands it in: previews, checks, manifest, problems
buckyos aiws run-tool --workspace $WS --run $RUN --attempt 1 --name check_results
buckyos aiws run-tool --workspace $WS --run $RUN --attempt 1 --name finish --args '{"summary":"…","assumptions":[],"warnings":[]}'
buckyos aiws run-report --workspace $WS --run $RUN --attempt 1 --finished --model <model> --input-tokens <n> --output-tokens <n> --calls <turns>
```
Report what your own model loop used in this stage with `run-report` (with `--finished` or `--error` alike): `--model` the model that answered your last turn, `--input-tokens` / `--output-tokens` summed over your turns, `--calls` the number of turns; leave out what you cannot tell. They go into the wish's history record as given. A `run` run calls no model of yours: leave them out (the macro's own AI calls are counted by the program host).
`run-program` (and `run-exec`, which only runs and prints the outcome, for debugging) starts the macro with the tool's own Deno, reading only `work/`, writing only `work/output/`, reaching only the Zone, with no environment and no token — `claim.json` outside `work/` stays out of its reach; never run a macro with `deno run -A`. Its `aiws.sql`, `aiws.ai.complete`, `aiws.llm.map`, `aiws.ai.image`, `aiws.ai.video` and `aiws.zone.fetch` are answered by the tool: SQL by the service on the run's snapshot, AI with your own AI resources (budgeted, cached by content; a generated picture or clip is imported into the workspace and the macro gets its object id), Zone resources with your session — `aiws.zone.fetch` only reads (GET / HEAD) and only what the macro lists in `aiws.declare({ …, zone: ["/kapi/<service>/…", …] })`; anything else answers `ZONE_READ_ONLY` / `ZONE_NOT_DECLARED`.

A `run` run comes with `stage.source` and `stage.manifest` (the stored macro): `run-files` writes it to `work/program/main.js`; `run-program`, then `run-report --finished`. Do not change the macro in a `run` run: a different one is refused; a run that fails (`PROGRAM_FAILED`, `MACRO_CODE_CHANGED`) is over — the wish needs a `code` run. The service judges the checks by their level: an `error` check that fails ends the run (`CHECKS_FAILED`) and nothing is written; a `warning` check that fails is written and heads the record's warnings. Results a person edited since the last run are overwritten, and rows or fields the macro no longer makes are removed; the record's warnings say which.

An `analyze` run has no macro: read `stage.user`, inspect data with `run-tool --name ws_profile|ws_read|ws_find|ws_query` (`ws_query` takes one SQL SELECT: `{ "sql": "SELECT \"月份\", sum(\"销售额\") FROM \"@T1\" GROUP BY 1" }` — a table by its handle, path or id, columns are field names, `"<field>#raw"` the stored values; `ws_read` of a table view Block gives its rows and its SQL; to join large tables put the smaller one in `WITH d AS MATERIALIZED (SELECT …)` and join to `d`), then `run-tool --name submit_analysis --args-file analysis.json` (the `wish.analysis.v3` object described in `stage.system`; contract results have no `approach`) until it is accepted, and `run-report --finished`. Give every acceptance check a `level` (a program check without one is refused): `error` when a failure means the results cannot be trusted or delivered, `warning` when they are usable but the user should be told — no model is there when the macro runs, so this decides. Bind only inputs that exist: when one the task needs cannot be found, say so (`status: needs_input` with `blockers`) — the run then fails with `NEEDS_INPUT` naming what is missing and writes nothing else; the user binds the input in the wish's properties and analyzes again. Data that is not in the workspace at all and has to come from outside: when the run was started by the workspace owner (`run-get` → `context.trigger`), build a data source for it (`aiworkspace_sync`), bind it as the input and go on; otherwise do not build one — submit `status: needs_input` with a blocker `{ code: "external_data", message, wanted: { meaning, origin?, freshness?, fields? } }` (the run fails `NEEDS_EXTERNAL_DATA`, the card offers the starter to ask the owner).

#### Starting a run yourself
When you worked out a wish's task with the user in a conversation, hand it over as an analysis: `buckyos aiws run-start --workspace $WS --wish <wish id> --stage analyze` answers a run and its `claim_token` (you are its executor; your AI resources pay; you need update on the wish — every stage writes the wish, so `run` alone starts nothing: `MACRO_CANNOT_WRITE`), then claim it and `run-tool --name submit_analysis` + `run-report --finished` as above (or `run-report --analysis-file analysis.json`). The service writes the analysis into the wish when it ends; coding works from it whoever analyzed.

#### Asked from the AI Workspace panel
The workspace's "Talk to your Agent" panel sends the user's message with a block after it, saying where they are and what they selected (only the lines that apply; a later message without one is about the same place):
```text
[aiworkspace context]
workspace: <title> obj://aiworkspace/<ws>
page: <the page the user is on>
canvas: <title> (surface) obj://aiworkspace/<ws>/entities/<id> <path>
guide: <name> step <n> obj://aiworkspace/<ws>/entities/<id>
view: data mode
open: <name> (<type>) obj://aiworkspace/<ws>/entities/<id> <path>
selected: <name> (<view> block) obj://aiworkspace/<ws>/entities/<block id> <path>; shows <name> (<type>) obj://aiworkspace/<ws>/entities/<data id>
```
Read what you need yourself (`buckyos obj read <url>`, `buckyos aiws read <id or path> --workspace <ws>`); the conversation is not the workspace's record. A selected wish is the `shows … (buckyos.wish)` id. Asked to analyze it, work the task out with the user, then hand it in as under "Starting a run yourself" (`run-start --wish <that id> --stage analyze`, claim, `submit_analysis`, `run-report --finished`) and tell the user the analysis is in the wish: they code and run it from the wish's card, or ask you to. A data source request sent from the panel's "Request a data source…" (what data, from where, how fresh, the wish and the workspace as `obj://` references) asks you, for the workspace owner, to set up that source; a collaborator's request reaches the owner, never you directly — work it when the owner hands it to you.

#### Actions on workspace objects
A workspace entity's description lists the actions it declares, each with its `risk`: `read uri=obj://aiworkspace/<ws>/entities/<id>` (shell: `agent_tool read <url>`; `buckyos obj read <url>` prints them under `declared.actions`). A wish declares `analyze`, `code` and `run` (`risk: write`: `proc.start` of `wish.xllm@1` with that stage), an entity a Source writes (`meta.data.write: refresh`, not a session feed) declares `refresh` (`risk: idempotent_write`: `proc.start` of `source.refresh@1`), other entities declare none. The root `obj://aiworkspace` has the Block-controls catalogue (`read uri=obj://aiworkspace property=controls`; one control's self-description: `buckyos aiws controls describe <kind>`).
- An action is its kRPC method called as you: refused or started exactly as `run-start` / `proc.start` would be. A reader sees the actions too; `meta.capabilities` is what you may do, and each action's description quotes how its method is authorized. The input is the method's `params` minus what the url names: for a stage `execution`, `request` (`today`, `timezone`), `location`; for both an `idempotency_key` (the schema is the Profile's `input`; source: `src/frame/aiworkspace/server/src/obj_provider.rs`).
- Before calling an action whose risk is not `read_only`, ask the user, saying what it writes (the description says it: an analysis, a macro, results that overwrite edits, a refreshed copy). Nothing in the system asks for you.
- `agent_tool xcall obj://aiworkspace/<ws>/entities/<wish id> analyze --params '{"execution":{"mode":"local"},"idempotency_key":"<key>"}'` answers the run: its `run_id`, and for a `local` run the `claim_token` — you execute it as above; `hosted` is for an account handing a run to one of its own Agents (an Agent calling it gets `EXECUTION_CONTEXT_MISSING`), so use `local`. `idempotency_key` goes inside `--params` (the `--idempotency-key` flag does not reach the service): the same key and input answer the same run, without one every call starts a new run. `refresh` takes only the key. Follow either with `buckyos aiws run-get --workspace <ws> --run <run_id>`.

#### Inputs and outputs
- Outside a run, a workspace entity is the object `obj://aiworkspace/<ws>/entities/<entity_id>` (a Reference's `mode=fixed`, `selector` and `version` go into its query): `read` describes it and `read … property=<name>` reads one property, with your own access to the workspace; its actions are in “Actions on workspace objects”.
- `stage.user` is the whole task: the workspace map with handles (`@T1`, `@B2`), the inputs by name, the output contract (result names, types, keys, views), the acceptance checks and fixed parameters (`today`, `timezone`). `stage.system` is the stage's rules; follow them (programs first, numbers in text only from facts, checks reported truthfully).
- The macro declares what it reads (`aiws.declare`), reads inputs with `aiws.input(name)` or `aiws.sql`, has the model write text from its facts with `aiws.ai.complete`, judges items with `aiws.llm.map`, generates pictures and clips with `aiws.ai.image` / `aiws.ai.video` (written with `aiws.result.file(name, media)`), and writes its results with `aiws.result.*`, `aiws.facts`, `aiws.check` (the macro guide is at the end of `stage.system`). Every result comes from the macro; there is no way to hand a result in directly.
- A mind map (or another Block-control, `catalog/controls.json`) is one result: `aiws.result.control("plan", { kind: "mindmap", children: "- Launch\n  - Market\n  - Product\n" })` — a Markdown outline (or `[{ text, children }]`); the service lays it out, never give coordinates. To grow an existing branch, take the node as an input (it reads as a Markdown outline of its subtree) and add `under: "<that input's name>"`: the new nodes hang under it.
- A composite control of the workspace (`WORKSPACE.md` lists them under “Composite controls of this Workspace” with their slots) is a `control` result too: `aiws.result.control("board", { def: "<author_did>#<name>", config: { title: "Week 44" }, slots: { cards: ["result:summary", "input:card"], header: [{ view: "richtext", markdown: "# Week 44" }] } })`. `result:<name>` moves that result's Block into the slot, `input:<name>` copies an input Block (or shows input data in a new Block), an inline item is a new text; `under: { input, slot }` adds them to a composite you read instead of making a new one. A definition that is not in the workspace is refused in the run: it has to be imported first (`aiworkspace_template_dev`).
- An HTML result (`aiws.result.html`) is a control of the workspace plus a Block: its `bindings` map names to `result:<name>` or `input:<name>`, and the page reads them with `aiws.input("<name>")`. Its html, css and js are fixed when the macro is coded: pass data through `bindings`, never by writing values into the code (a run whose code differs fails with `MACRO_CODE_CHANGED`). Controls a user built or imported (`data/extensions`) are bound the same way, through the Cell's `bindings`; their self-description is the definition's `agent` text (`buckyos aiws read <def> --workspace <ws>`).
- Outside a run you place controls with `doc.commit` (one `commit` call per Commit whatever its size — the client sends a large one in parts; at most 32 MiB / 50 000 operations). A composite control (a definition with `def_kind: composite`; its `composition.slots` say what each slot takes) is a container whose content are ordinary Blocks, each with the `slot` it fills; leave their positions to the composite (`"auto"`), except under a `fixed` layout, which keeps numbers:
  ```json
  [{ "op": "entity.create", "entity_id": "board-1", "type_id": "buckyos.container", "parent_id": "<surface>", "order_key": "m",
     "placement": { "x": 40, "y": 40, "w": "auto", "h": "auto" },
     "payload": { "kind": "composite", "def_ref": { "entity_id": "<composite def>" }, "config": { "title": "Today", "gap": 8 } } },
   { "op": "entity.create", "entity_id": "card-1", "type_id": "buckyos.cell", "parent_id": "board-1", "order_key": "a",
     "placement": { "x": "auto", "y": "auto", "w": 240, "h": 120 },
     "payload": { "view": { "type": "html" }, "def_ref": { "entity_id": "<card def>" }, "slot": "cards", "bindings": { "task": { "entity_id": "<record>" } } } }]
  ```
  `def_ref` of an instance never changes; moving a Block in or out is `tree.move { …, slot: "<name>" | null }`.
- Writing a Block's `config` / `bindings` / `on` outside a run: `entity.set_props` changes only the properties you name (`expect` per property from `key_revs["p:<key>.<name>"]`); handlers in `on` run when a person clicks in run mode with that person's rights — a view-mode collaborator needs `update` on what the handler writes.
- To copy Blocks — a composite instance with its cards, a group, a single Block — use one `tree.clone { source_id, parent_id, placement?, slot?, id_seed }` instead of re-creating them: the copies share definitions and shared data, own data (a note's text) is cloned, inner connectors follow. Pick a fresh `id_seed` (≤ 64 bytes); the accepted Commit lists `cloned: [{ op_index, new_ids: { <old id>: <new id> } }]`, and the ids are `c` + the first 26 hex digits of `sha256("<id_seed>\n<old id>")`, so you know them before the answer comes.
- Every `run-tool` / `run-program` answer is `{ status: "ok" | "error", text }`: `error` is what you must correct (a wrong handle, a result not in the contract, an undeclared field, a check not run), not a failure of the run. `finish` is refused until a trial run succeeded with a manifest and the contract is met. Read the checks of each trial and fix the macro until every `error` check passes: a `code` run that ends with one failing fails (`CHECKS_FAILED`) and stores no macro.
- `run-report --finished` makes the service check and write the stage's outcome (see “Check the result”). Give up with `run-report --error "<reason>"` only when the task cannot be done with the data there is (say what is missing): the failure is recorded, nothing else is written.

#### When it fails
- `RUN_REVOKED`: the run was cancelled, or another attempt took it over, or your lease lapsed — stop; claim again only when `run-get` says `interrupted`.
- `failed` after `run-report --finished` although your part was accepted: the service could not write the outcome — the wish or its results changed while the run went on, the plan has a hard problem (an output place gone, a result that cannot change its type, over a Commit's limits), or the run's identity no longer holds (`DELEGATION_STALE`). Only the failure record was written; the run is over, the user starts it again.
- `CHECKS_FAILED`: an `error` check failed — in a `code` run fix the macro before `finish`; in a `run` run nothing was written and the wish needs a `code` run (or a new analysis when the check itself is wrong). `NEEDS_INPUT`: the analysis found an input missing; nothing was written. `NEEDS_EXTERNAL_DATA`: the task needs data from outside the workspace (`record.error.missing_inputs[].wanted`); for the owner, `aiworkspace_sync`.
- `access_denied` on `run-claim`: the claim token is not this run's, or the run was handed to another Agent (`run-get` → `context.executor`).
- `MACRO_CANNOT_WRITE` (starting `code` / `run`): the run would be written as whoever starts it — a hosted run as you, judged as the user who owns you unless the workspace configured you — (bounded by the wish's `intersection` group), and that identity cannot update the wish or write where its results go — ask someone with update there to run it; `DEPENDENCY_UNAVAILABLE` "input … is not readable": that identity cannot read an input.
- `NEEDS_CODING` (starting a `run`): the macro no longer fits its inputs (a declared field deleted or of another type); the wish needs a `code` run. `NEEDS_ANALYSIS`: the request or the inputs changed; analyze first.
- `AI_NOT_DECLARED` / `AI_BUDGET_EXCEEDED` from a macro's AI call: declare it (`aiws.declare({ ai: { complete: { max_calls, max_tokens } } })`) or call less; `AI_QUOTA_*`: your AI resources refused — report the run's failure, do not retry in a loop.
- `subprocess is not allowed`: run macros with `run-exec` / `run-program` (the tool starts its own Deno), not by hand.

#### Check the result
`buckyos aiws run-get --workspace $WS --run $RUN`: `state` goes `validating`, `applying`, then `succeeded` with `applied` (`status: accepted` and the `commit`) and `record` (what the run added to the wish's history: outcome, warnings first, checks with their level, usage, what it read and wrote); `failed` carries the service's reason (`error.code`, `sub_code`, `detail`) and its failure `record`. `cancelled` and `interrupted` runs write no record.

#### Taking a stage back
`buckyos aiws run-rollback --workspace $WS --run <run>` takes back what one run wrote: results it updated return to what they were before it (a person's edits it overwrote included) and results it created go with their Blocks; a macro or an analysis returns to the one of the stage's previous record (none: it is removed). Only the run whose record is current for its stage can be rolled back (`NOT_CURRENT_RECORD` otherwise); then the previous one is current. It needs update on the wish, and it is the way back for a run no window can undo, such as one you executed. When what the run wrote was changed since, nothing is written: the answer is `status: needs_confirm` with what would be lost (`lost`; `hidden_lost` counts what you cannot read) — tell whoever asked, and run it again with `--confirm` only when they agree. Accepted, it answers the `commit` and the `rollback` record; the rolled-back record is kept and marked. Roll back only when asked to.
