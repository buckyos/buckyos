#### When to use
- You are asked to set up a workspace for someone: tables with fields and rows, a document, a canvas with Blocks bound to them, a wish block that computes results.
- You need to move content between workspaces or Zones: export a share package, import it elsewhere, or link one workspace's published table into another so it follows updates.
- You already hold a run of a wish block to execute: that is `aiworkspace_run`, not this manual.

#### Before you start
- `buckyos aiws --help`: the finding and reading verbs (`ls`, `find`, `grep`, `stat`, `cat`, `resolve`, `read`, `sql`, `info`), the write verbs (`table add|set|rm|field-add|option-add`, `text append|replace|rm`, `mv`, `rename`, `set-prop`), the Block-control verbs (`controls list|describe`, `import`, `export`) and the run verbs; `buckyos aiws <verb> --help` gives each one's exact options. Everything else is one kRPC method of the service (`/kapi/aiworkspace`), called through the websdk: `getAiWorkspaceClient()` in `buckyos-websdk/src/aiworkspace_client.ts` (`info`, `outline`, `read`, `readMeta`, `readBody`, `listEntities`, `findEntities`, `textQuery`, `sql`, `resolve`, `prepare`, `commit`, `run*`, and `call(method, params)` for the rest); the write helpers are `buckyos-websdk/src/aiws_write.ts`.
- **Find, read, query, write, read back.** Every entity has a name and a path (`/data/销售`, `/surfaces/看板/text-3`; `~<entity_id>/…` starts at an entity): `buckyos aiws ls /data --workspace <ws>`, `find <text>` (names and titles), `grep <text>` (the text of everything: a select by its label), `stat <path>` (what it is, its versions, the operations its type takes), `cat <path>` (its plain text: a table as CSV, a document as Markdown, a canvas as its Blocks). Query tables with SQL: `buckyos aiws sql 'SELECT "客户", sum("金额") FROM "/data/销售" GROUP BY 1' --workspace <ws>` — columns are field names (shown values: a select's label), `"<field>#raw"` the stored values (option ids, exact decimals), `_id` the record id; a table view Block's SQL is in `stat <block>` (`shows.view_sql`). To join large tables, put the smaller one in `WITH d AS MATERIALIZED (SELECT … FROM "/data/部门")` and join to `d` (a plain join of two large tables runs past the 2-second budget). Write with the verbs (`table add /data/销售 --values '{"客户":"甲","状态":"已完成"}'` takes field names and option labels; `table set` needs the record's id) or with `aiws_write.ts` + `commitOps`, then read back with `cat` / `sql`. Paths change when a title changes: keep entity ids for anything you store.
- The protocol is in `src/frame/aiworkspace/README.md` (Protocol: the method table with its stability level, the operation catalogue `schemas/operations.json`, selectors, error codes). Methods marked `stable` are the ones to build on.
- A write is a Commit: `doc.commit { protocol_version: "1.2", workspace_id, epoch, idempotency_key, session_id, operations: [...] }` (`"1.0"` / `"1.1"` are still accepted). `epoch` comes from `ws.get_info`; keep your `idempotency_key` — resending the same key never writes twice (`doc.get_submission` tells you what happened). A Commit of any size is one `aiws.commit(...)` call: the client sends one larger than a request (8 MiB) in parts and the service writes it as a single Commit — all of it or nothing, one undo step. Limits: 32 MiB and 50 000 operations per Commit (`LIMIT_EXCEEDED` beyond; split the work into several Commits yourself then). Do not cut a write into batches to stay small.

#### Shortest path (a workspace with a table and a canvas)
```ts
// a Deno script using the websdk; run it with: deno run -A build.ts
import { buckyos } from "buckyos"            // or the local dist/node.mjs
const aiws = buckyos.getAiWorkspaceClient()
const ws = (await aiws.call("ws.create", { title: "季度经营" })).workspace_id
const { epoch } = await aiws.info(ws)
await aiws.commit(ws, { protocol_version: "1.1", workspace_id: ws, epoch, idempotency_key: "build/1", session_id: "s1", operations: [
  { op: "entity.create", entity_id: "sales", type_id: "buckyos.table-source", parent_id: "data", order_key: "a", name: "销售",
    payload: { fields: [{ field_id: "month", name: "月份", type: "date" }, { field_id: "amount", name: "金额", type: "decimal", scale: 2 }] } },
  { op: "table.insert_records", source_id: "sales", records: [{ record_id: "r1", values: { month: "2026-07-01", amount: "10.50" } }] },
  { op: "entity.create", entity_id: "sf-content", type_id: "buckyos.container", parent_id: "canvas-content", order_key: "a", payload: { kind: "folder", system: "surface_content", surface_id: "sf", title: "看板" } },
  { op: "entity.create", entity_id: "sf", type_id: "buckyos.container", parent_id: "surfaces", order_key: "a", name: "看板", payload: { kind: "surface", layout: { mode: "free" }, title: "看板", content_folder_id: "sf-content" } },
  { op: "entity.create", entity_id: "blk-sales", type_id: "buckyos.cell", parent_id: "sf", order_key: "a", placement: { x: 40, y: 40, w: 520, h: 300 }, payload: { view: { type: "table" }, source_ref: { entity_id: "sales" }, title: "销售" } },
] })
```
Check with `buckyos aiws cat /data/销售 --workspace <ws>` (the name of an entity created without one follows its title, or is a counter such as `table-1`; this example names it), `buckyos aiws ls /surfaces/看板 --workspace <ws>` and `buckyos aiws info --workspace <ws>`. Data created under `canvas-content` belongs to its canvas (D05: it goes when its last Block goes); data under `data` is shared.

#### Inputs and outputs
- **Entity types**: `buckyos.table-source` (fields + records), `buckyos.richtext` (`content: { type: "doc", content: [blocks] }`, Markdown converts with the core's `markdown.rs`), `buckyos.record`, `buckyos.asset-ref` (upload first: `buckyos bucket put obj://bucket/<bucket>/<key> <file>` into a bucket your session may write, then `asset.import_object { workspace_id, obj_id }` with the printed `obj_id` — an account may instead pass `bucket_id` + `key` of its own `user/aiworkspace/<user>/assets`; the answer's `object_id` goes into the payload; optional `poster` — the `object_id` of another uploaded PNG/JPEG/WebP/GIF picturing a video, sound or PDF — plus `image { width, height }`, `duration_ms`, `page_count`), `buckyos.dir`, `buckyos.wish`, `buckyos.cell` (a Block: `view.type` from the Renderer catalogue, `source_ref` to the data it shows; a pen stroke is a Cell with `view: { type: "ink", version: 1 }` and its points in `config` — write it exactly as the backend README section "Ink" says, the Desktop's `src/frame/desktop/src/app/aiworkspace/ink/model.ts` `encodeStroke` is the reference encoder).
- **Block-controls (mind maps)**: a container whose `kind` is a control id lays out the Blocks it holds — do not compute their coordinates. `buckyos aiws controls list` names the controls (what each is, when to use it); `buckyos aiws controls describe mindmap` prints the full description to follow (config, child rules, `doc.commit` examples, formats, don'ts). The shortest way to a mind map is an outline file: `buckyos aiws import plan.md --workspace <ws> --parent <surface id> --at 100,80` (a nested Markdown list, or `.opml`); `buckyos aiws export <control id> --workspace <ws> [--format opml] [--out plan.md]` reads one back. With `doc.commit`, nodes are `buckyos.cell` with `view: { type: "mindnode" }`, the text in `title`, `parent_id` = the parent node, placement `{ "x": "auto", "y": "auto", "w": "auto", "h": "auto" }` (a non-text node gives numeric `w` / `h`).
- **Data controls (to-dos, calendar)**: a container with `kind: "todo"` or `"calendar"` shows the records of standard tables bound in `bindings` (`items`; `events` and `todo` are lists `[{ entity_id }, …]`) — its items are records, so add, complete, move or reschedule them with `table.*` operations, never Blocks; it takes numeric `w` / `h` like a Block. Place one with `buckyos aiws place todo|calendar --workspace <ws> --surface <canvas> [--bind "name=id[,id];…"]`: it settles the tables the way a person's insertion does (none → created on the canvas, one → bound, several → it fails with `NEEDS_UI` naming the binding to give). `buckyos aiws controls describe todo` (or `calendar`) prints the manual and its public contract (`control.contract`: properties, bindings, templates, gestures and what each writes). The user's own schedule is the workspace named `schedule` (`ws.ensure { name }` returns it, creating it once): use `buckyos aiws todo list|add|done|undone|update|move|rm` and `buckyos aiws cal list|add|update|rm|skip|postpone` (`--help` on each) rather than operations, and give the links they print.
- **Table files** (CSV / TSV / xlsx / SQLite the user gives you): do not infer types or write `table.insert_records` by hand. `import_table <file> --workspace <ws> --dry-run` prints the plan the Desktop's import wizard would make (header, field names and types — number, decimal, percentages as ratios, date, datetime, `currency` with its code, single select — row count, sample records, what changed on the way); read it, then run it again without `--dry-run` (`--parent <folder id>` for a data folder, `--sheet` / `--all-sheets`, `--table` for SQLite, `--header yes|no`, `--date-order dm`, `--timezone <iana>`, `--locale zh`). `import_table --help` lists the options; the importer's source is `src/frame/aiworkspace/import-table/` (vendored beside the command as `vendor/frame/aiworkspace/import-table/`).
- **Office documents** (.docx / .pptx the user gives you): do not retype them as operations. `import_office <file> --workspace <ws> --dry-run` prints what the Desktop's import dialog would make — a .docx as a new flow page (rich text Blocks with headings 1–3, lists, tables, links; pictures as their own Blocks; the original file last), a .pptx as a new free canvas with one page per slide (text, pictures, shapes; tables as grids of rectangles) and a presentation path — with the report of what was simplified; read it, then run it again without `--dry-run` (`--include-hidden`, `--keep-deleted`, `--no-original`, `--no-path`, `--title`). Here nothing is drawn by LibreOffice: charts, SmartArt without its saved drawing, EMF / WMF pictures and formulas stay boxes (pptx) or are left out (docx). When the report lists those, or the file is .doc / .ppt / .odt / .odp, tell the user to import it on the Desktop (Insert → Import Office document…, or drop the file), where the content server's LibreOffice turns them into pictures or imports the whole file as it looks. `import_office --help` lists the options; the converter's source is `src/frame/aiworkspace/import-office/` (vendored beside the command with import-drawio / import-pdf / import-table).
- **Field types**: `text | number | decimal (scale) | currency (currency: ISO 4217 code, scale, default 2) | date | datetime | boolean | select | multi_select (options, max_items?) | object_ref | json` (`json`: a JSON object ≤ 16 KiB, depth ≤ 8; filters only `is_empty` / `is_not_empty`). A table with `schema_id: "buckyos.todo@1"` or `"buckyos.calendar@1"` is a standard table the service checks at the end of each Commit (fields, statuses, start ≤ end, the RRULE subset): `src/frame/aiworkspace/schemas/standard-tables.md`. A currency value is `{ "amount": "12.50", "currency": "CNY" }` (or a bare amount in the field's default currency); never `"¥12.50"`. A `text` field with `submitter: true` (one per table, e.g. a vote) is filled by the service with whoever inserts the record — never write it; each principal has one record there (`SUBMITTER_EXISTS` names it in `data.record_id`: edit that one), and with `append` alone you may change or delete only your own.
- **Reading**: `doc.list { at }`, `doc.find { name?, type? }` and `doc.read { entity_id | path, as?: "meta" | "body", selector? }` (README “Finding, reading and querying”); `doc.query` takes `text` (a literal in names, titles and bodies) or `sql` (one SELECT over the tables — the top N of a vote: `SELECT j.value, count(*) FROM "<votes>" v, json_each(v."<picks>#raw") j GROUP BY 1 ORDER BY 2 DESC LIMIT 3`); a URL table's rows are `doc.source_query`. `doc.resolve { reference | path }` turns a path into the reference object `{ workspace_id, entity_id, mode: live | fixed, version? }` — keep references, not names or paths (D10).
- **Export / import**: `doc.export { mode: "share" | "personal_backup", self_contained? }` puts the package into the workspace owner's `exports` bucket (kept 7 days) and answers `download: { bucket_id, key, token }`; fetch `GET https://<zonehost>/bucket/v1/<bucket_id>/<key>?token=<token>` (or `buckyos bucket get obj://bucket/<bucket_id>/<key> <file>` where your session may read that bucket). `share` is content only (no collaboration history); `personal_backup` carries it. Import: upload the package (`buckyos bucket put`), then `ws.import { obj_id, semantics: "new" | "restore", replace? }` — an account may pass `bucket_id` + `key` of its own `user/aiworkspace/<user>/exports` instead, and that upload is consumed (or `ws.fork` for a copy inside this Zone).
- **Across workspaces** (D26): the publisher runs `ws.publish { entity_id }` (manage) and gets a link `https://aiws-<id>.<zonehost>/<workspace>/<name>` (`<id>` is the workspace id without `ws_`; or `/kapi/aiworkspace/pub/<ws>/<name>`); the consumer creates an entity with `payload.source = { kind: "workspace", workspace_id, entity_id, mode: "live" }` (another Zone: add `zone` and `url`) and refreshes it: `proc.start { program: "source.refresh@1", params: { entity_id }, idempotency_key }` → `proc.get` until `succeeded`. Any CSV / JSON / Markdown URL works the same with `source: { kind: "url", url }` (`refresh: { interval_s }` schedules it). A sourced entity is read-only (`SOURCE_READ_ONLY`): refresh, do not edit.
- **Wish blocks**: create a `buckyos.wish` (`prompt`, `executor: "xllm"`, `output: { container_id, surface_id, name }`), then `proc.start { program: "wish.xllm@1", params: { wish_id, stage: "analyze" | "code" | "run", execution: { mode: "local" | "hosted" } } }` — analyze gives the task contract, code writes and trial-runs the wish's macro (applying stores it with its results), run runs the stored macro again on current data; `proc.get` reports the candidate and a preview; `proc.apply { run_id, plan_digest, session_id }` writes it. Whoever starts a `local` run executes it (the answer carries its `claim_token`); in `hosted` mode the owner's Agent executes. Executing a run is `aiworkspace_run`; a template ships a wish with its macro (`program`), so a fresh copy can `run` without coding again while its inputs keep the declared fields.
- **Sharing with people**: `ws.grant { subject, capabilities: ["read", ...], scope_entity_id? }` (manage); `ws.list_grants`; entries for visitors are `ws.create_entry` / `ws.list_entries`.

#### Controls: develop, build, export, reuse
A control is a Block definition whose source is a folder (sub-folders allowed) in a home directory or on your disk, built into one workspace and then reused: a render control (`declarative` items or `html`; instances are Cells) or a composite (a panel that lays out real Blocks in named slots; instances are containers). Full contract: `src/frame/aiworkspace/README.md` “Extension controls”, “Composite controls” and “Extension controls P2 / P3” (`schemas/component.schema.json`, `schemas/composition.schema.json`, `schemas/migration.schema.json`, `schemas/template.schema.json`).
```bash
buckyos pikg init /tmp/kpi --owner did:bns:$ME --kind aiws-controls --source ./aiws   # a sample control: /tmp/kpi/aiws/controls/kpi/{component.json,declarative.json,AGENT.md}
#   add --composite for a composite skeleton: component.json (kind composite) + composition.json + AGENT.md
DIR=/tmp/kpi/aiws/controls/kpi                       # a local folder (files go inline; past 4 MiB the largest go to your exports bucket by reference), or a Zone path such as "/home/$ME/AI Workspace/Demo/controls/kpi"
buckyos aiws build "$DIR" --workspace $WS            # → def_entity_id, version; instances update; .aiws-build.json in $DIR keeps the base
buckyos aiws build "$DIR" --workspace $WS --dry-run  # diagnostics only
buckyos aiws pull <def_entity_id> --workspace $WS --out "$DIR" [--local]   # the workspace version (also synthesizes source for wish-made HTML controls)
buckyos aiws ext-export <def>,<def2> --workspace $WS --out ./pack --name kpi-pack --version 0.1.0 --install   # bundle (+ what they build on) → .pikg → your library
buckyos aiws library list                            # pkg_id, controls (ident = <author_did>#<name>, deps)
buckyos aiws ext-import <pkg_id>#<ident> --workspace $OTHER_WS     # one commit into data/extensions; its deps come along
buckyos aiws ext-upgrade <def_entity_id> --workspace $OTHER_WS [--migration m.json] [--dry-run] [--force]   # to the library's version of its package
buckyos aiws template export --workspace $WS --surfaces <surface>,… --id team-board --title "Team board" --param team_name:string:Team --reset <table> --out ./tpl --name team-kit --version 0.1.0 --install
buckyos aiws template list                           # <pkg_id>#<template id>, params
buckyos aiws template create <pkg_id>#<template id> --title "Red team" --param team_name=Red   # → a new workspace_id (each creation is independent)
```
- `component.json` (`manifest_version: 5`; 1–4 still read): `ident { author_did, name }` (name `[a-z0-9][a-z0-9._-]{0,63}`), `kind` (`declarative` | `html` | `composite`), `title`, `entry` (declarative: a JSON file; html: `{ html, css?, js? }`; composite: `composition.json`), optional `accepts`, `allow_no_source` (not on a composite), `default_size`, `config_schema` (only type / enum / default / required / title / description / minimum / maximum / minLength / maxLength / properties / items), `bindings { <name>: { accepts?, required?, many?, schema_id?, title? } }` (`many`: the instance binds a list; `schema_id`: only tables of that business schema, e.g. `buckyos.todo@1`), `catalog`, `agent` (a Markdown file), `assets`, `deps: ["<author_did>#<name>"]` (controls this one builds on: they must already be in the workspace, or come in the same import). File names may be relative paths (`icons/check.svg`); no part starts with `.`. Version 3: `events { <name>: { title?, params?: { <p>: { type: string|number|boolean|object|entity } } } }` (an HTML control with `host_api: 3` raises one with `await aiws.emit("<name>", params)`, a declarative one with the item `{ kind: "button", label, emit: "<name>" }`; a composite re-raises a child's in `composition.json` `events { <name>: { from: { slot, event } } }`), and `layout.algorithm: "grid"` (`columns`, `gap`) for a composite. Version 4: `actions: [{ id, title, modes?: ["edit","view"], needs?: [capabilities], run: handler | [handlers] }]` — offered on the instance's toolbar (in view mode too, before an HTML control runs); `run` is an event handler or `{ kind: "config", props }` (the instance's own properties, `{{now}}` is the service's clock) or `{ kind: "forward" }` (the running HTML receives `aiws.on("action:<id>", fn)`); `host_api: 4` adds `aiws.onConfig(cb)`, `aiws.serverNow()`, `aiws.userState.get/set` (the person's own) and `aiws.mediaUrl(binding, member?)` (a streamable address); `composition.json` adds `projections` (Blocks drawn from bound data: `source` records / members of a folder / counts of a list field / the viewer, a `template` of label / shape / asset nodes, `layout` list or grid), `media { slot, anchor }` (the slot's video plays from `config.<anchor> = { pos_ms, at_ms, playing }`), a slot's `visible { from: "first_open", for_ms }` (each viewer sees it for a while; presentation, not access) and events `from { projection, role }` with a default handler `on`. Version 5 (a composite): `on_bind` — steps run when it is placed or re-bound, from parent to child: `{ binding, pick: "one"|"many"|"all", title?, allow_new? }`, `{ binding, from_parent: "<parent binding>" }`, `{ binding, create: { standard: "buckyos.todo@1" } | { table: { name, fields, title_field_id? } } | { dir: { name } }, when?: "missing"|"always" }` (bindings no step settles follow the default: a required one created if it can be, the only one bound, several asked; a `many` one gets them all) — and `on_init_control` (child to parent, last): `{ require: "children" }`, `{ then: { action: "<declared action>" } }`. An HTML control (`host_api: 5`) may decide instead in its own script: `on_bind: "script"` (and `on_init_control: "script"`); before placing, the host runs `behavior.js` once more without a page (no `document` / `window`; `aiws.context.role === "bind"`), so begin the script's `(function () { … })()` wrapper with `if (aiws.context.role === 'bind') { aiws.on('bind', async (ctx) => ({ bindings: { <name>: id | [ids] | ref }, create: [{ ref, kind: "dir", name }] }) /* null cancels */); aiws.on('init_control', async (ctx) => true /* or a reason */); return }` — `ctx` has `reason`, `no_ui`, `given`, `parent`, `decls`, `find(query)`, `read(id)`, `canCreate(name)`, `defaults(names?)` and `dialogs.pickOne / pickMany / confirm` (`query.ids` narrows what a dialog lists). Place an instance with `buckyos aiws place <def id | author_did#name> --workspace <ws> --surface <canvas> [--bind …]` (it runs those steps without dialogs; run the `then` actions it lists yourself; an HTML control's script is not run there — give its bindings with `--bind`, a required one missing fails with `NEEDS_UI`). Worked examples: `doc/workspace/control-examples/` (TV screen, time-limited, photo vote — its `on_bind` creates the votes table, listen together — its script offers only folders holding audio).
- Declarative items read the main source with `bind: "sum:amount" | "count" | "<field>" | "props.<key>"`, a named binding with `bind: "<binding>.count"` etc.; HTML reads `aiws.input("<binding>")` and `aiws.context.config`; a file listed in `assets` is `await aiws.asset("<name>")` (a blob URL; check `typeof aiws.asset === "function"` first).
- A render instance is a `buckyos.cell` with `view: { type: "declarative" | "html" }`, `def_ref: { entity_id: <def> }`, `bindings: { <name>: { entity_id } }` (a list of them for a `many` binding), `config` (overrides only), `on` (handlers of its events). Change one property at a time with `{ op: "entity.set_props", entity_id, key: "config" | "bindings" | "on", props: { <name>: value | null }, expect: { <name>: <rev of key_revs["p:<key>.<name>"], 0 if absent> } }` — someone else's change of another property is kept; add the precondition `{ target: { entity_id: <def> }, expect: { rev: <def content_rev> } }` so a rebuilt definition refuses a stale write.
- Handlers (`on: { <event>: handler | [handlers] }`): `{ kind: "write", target: "<binding>", what: "recordSet" | "upsert" | "setMarkdown" | "toggle" (one value in a list field of the caller's own record of a submitter table: `{ field, value, max? }`) | "addOptions" (`{ field, from: <folder binding>, accept? }`: an option per file), args }`, `{ kind: "wish", wish_id }`, `{ kind: "open", target? }`, `{ kind: "notify", text }`; strings may say `{{event.<param>}}` / `{{config.<key>}}`. They run when a person clicks in run mode (their rights; one Commit per click); reloading never runs them again.
- A composite's `composition.json` says three things — `layout` (`stack` column/row with `spacing`, or `fixed`), `slots` (`{ <name>: { accepts: ["cell:<ident>", "<view type>", "container"], min, max, placement } }`) and `chrome` (`background`, `radius`, `border`, `title { text }`, `empty`); strings may say `{{config.<key>}}` for a property of `config_schema`. Its instance is a container, its content ordinary Blocks with `slot` (see `aiworkspace_run` for the `doc.commit` shape; copy one with `tree.clone`). Write `composition.json` by hand or start from `pikg init --composite`; `hello-controls/controls/hello-board/` in `doc/workspace/` is a worked example.
- Rebuilding needs the base you last built or pulled (kept in `.aiws-build.json`): `REVISION_CONFLICT` / `BUILD_BASE_STALE` or `BUILD_BASE_REQUIRED` means pull, merge, build (or `--force`). `BUILD_FAILED` lists `data.diagnostics` (`file`, `line`, `col`, `message`, `code`, `instances`, `dependents`); nothing was committed. `code: DEP_MISSING`: build or import the control named in `deps` (or a slot's `cell:<ident>`) first. Removing a binding, making one required, narrowing `accepts`, adding a required property, removing a composite slot or an event (or a param) fails for the instances it touches (`instances` names them) and while dependent controls use it (`dependents`); pass a migration (`--migration m.json`: `{ "<ident>": { config|bindings|events: { rename, drop, fill }, slots: { rename, move } } }`) to rewrite the instances in the same commit.
- Upgrades: `ext-upgrade` rebuilds a definition from its package's version in your library (with the package's definitions it builds on); `action: unchanged` when nothing is newer; `INVALID_OPERATION` / `EXT_LOCAL_CHANGES` (`data.files`) when it was built here after the import — `--force` replaces those changes. `ext-import` of an identity already here from another version is `EXT_IDENT_EXISTS` (`data.library_version`): upgrade instead.
- Templates: `template export` snapshots the chosen Surfaces with what they show, the controls they use and `--data` entities (never presentation paths, sessions, personal content); `{{params.<k>}}` in titles, Block / container `config`, record properties and table texts is replaced at creation, `--reset` tables start empty. Installing a template creates no workspace; `template create` (`ext.create_from_template`) makes a new one owned by you every time.
- `build` of a Zone folder reads it over the file service with your session (`--watch` rebuilds on every save there); of a local folder it reads your disk. Either way the files go to the service (≤ 4 MiB inline per build, larger files are uploaded and sent by reference automatically; files the file service holds as objects always go by reference).
- A `.pikg` without the CLI: the service packs one with `ext.pack { workspace_id, entity_ids, package: { name, version, title? } }` into your `exports` bucket (what the Desktop's “生成 .pikg” uses; unsigned: the service holds no author key); install it with `ext.install { pikg: { bucket_id, key } }`.

#### When it fails
- `rejected` with `errors[]`: read `code` / `sub_code` (`ID_CONFLICT`, `NAME_CONFLICT`, `SOURCE_READ_ONLY`, `LOCK_REQUIRED`, `QUOTA_EXCEEDED`…), never the text. A conflict answers the current revision in `conflicts[]`: read again, resend with the new `expect`.
- `PERMISSION_DENIED`: `ws.get_info.capabilities` lists what you may do; the owner grants more with `ws.grant`.
- `epoch` mismatch after an import or restore: call `ws.get_info` again.
- An unknown result (the request timed out): `doc.get_submission { epoch, idempotency_key }` — `accepted` means it is in; otherwise resend the same key.

#### Check the result
`buckyos aiws info --workspace <ws>` (head sequence, capabilities, usage), `buckyos aiws stat|cat <path> --workspace <ws>`, `buckyos aiws read <entity> --workspace <ws>` (the native content), `buckyos aiws sql "SELECT count(*) FROM \"<table path>\"" --workspace <ws>`. The workspace's page for people is on its own origin: `https://aiws-<id>.<zonehost>/<workspace>` (`<id>` is the workspace id without `ws_`; `ws.get_info.public_base` gives the origin), a Surface is `…/<workspace>/<surface>?id=<surface id>` — give users these links, never `/workspace/<ws>` on the Zone host (that is only the signed-in user's list).
