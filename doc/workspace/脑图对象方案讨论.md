## 1. 结论

**脑图不是“便签 + 连接线 + 分组”的拼装物，而是一棵带布局语义的树。** 现有架构能承接它，但缺的不是再注册一个 Block，而是一个内核原语加两条限制（2026-10-25 用户归结）：

**原语：placement 的分量可以是 `auto`。** `x`、`y`、`w`、`h` 各自可以是数值，也可以是 `auto`；`auto` 的值在读取/显示时由父容器的布局公式算出，不存储。用户手工拖动或缩放过某个分量，它就被写成数值，被 pin 住；“重置布局”就是把数值改回 `auto`。

**限制一：能填 `auto` 的对象必须在一个 layout block 下面。** 布局由父容器拥有（同 CSS）。公式的作用域是该容器的子树，重算有边界；容器自己的 `w`/`h` 可以是 `auto`（包住子节点），但它在自由画布上的 `x`/`y` 是数值，变化不会越过容器向外传播。自由画布上的普通对象不能自己声明 `auto`。



**限制二：公式只读自身数据，不从别的 UI Block 推导。** 一个容器的公式只能读自己的 config、直接子节点在树里的结构（`order_key`、折叠）和每个子节点已解析的尺寸；一个节点的尺寸只能来自自己的内容（文字、绑定的数据）。不能按 id 引用兄弟或任何其他 Block。依赖只沿树向下，没有图、没有环、没有失效传播。连接线是现有代码里唯一的跨 Block 派生几何（两端绑定别的 Block），它需要的第二遍布局、手势 Override 与 ShapeBook 异步读正是这条限制要避免的复杂度；连接线保持为唯一例外，在所有 `auto` 解析完之后的第二遍里算。

这个原语把几个原本分开的缺口收成一个：脑图节点的 `x`/`y` 是 `auto`（公式是树布局）；节点文字自适应是 `w`/`h` 为 `auto`（公式是文字测量），同时解决自由画布上便签/文本高度随内容增长的老问题；流式页看起来相近（`layout.mode = flow` 的子节点不存 placement，`layoutSurface` 用 `autoY` 顺序堆叠），但它的块宽来自页宽（自顶向下）、块高来自内容（自底向上），两个方向各占一个轴。按 §5.7“不混用”的严格读法它是混用，按“每轴单向”的读法不是；v1 不裁决这一点，流式页保持特例，不迁到这个原语上。组织结构图是同一个 `tree` 算法换方向；泳道、网格不在本方案范围。

这个原语有一个必须守住的边界：**它不是布局引擎**（§5.7）。核心是**单向**：方向（自顶向下或自底向上）由 layout 容器声明，容器内永不混用；此外具名算法不可组合、control 可以嵌套但每个容器只按自己的方向算自己的直接子节点（R24，§5.7），任意排版的需求走 HTML Block 扩展。

在它之上，脑图还需要两样东西：**容器级渲染器与布局器**（现在只有 Cell 有 Renderer，group 没有自己的外观和布局算法）和**隐式边**（脑图的边由父子关系推导、样式随分支继承，与现有“独立实体、删目标则冻结”的连接线语义相反）。

定案的模型（R1–R4，2026-10-27）：

- **mindmap 是按 Block-control 机制实现的第一个内置 control**，容器 kind 即 control id `mindmap`（R2）；树的每个节点是一个 `buckyos.cell`，`parent_id` 就是脑图父子，`order_key` 就是兄弟顺序。这是 Miro 的模型（每个节点是 item，带 `parent`），也最大化复用现有树原语。
- **节点 placement 为 `auto`**，由容器的树布局公式算出；用户拖到空处的节点被 pin 住（§5.5）。
- **边隐式**：由 mindmap 容器的渲染器绘制，样式是容器与节点的属性；不生成 connector 实体。
- **Agent 不算坐标**：Agent 和许愿格只提交逻辑树（Markdown 大纲是首选交换格式），placement 写 `auto`。这是对 AI 原生定位最重要的一条。

两条 2026-10-27 的归零结论收口了这个模型：

- **结构是 UI 的，内容绑数据**（§4.3）。节点可以是文字、视频、表格视图或任意 Block，“节点”只是 BlockTree 里带父子语义的位置；数据树表达不了这个，所以树结构只在 BlockTree，数据源模式不显示它（R21）。节点里的视频仍是引用 AssetRef 的 Cell，那条 AssetRef 和画布上任何视频一样落在画布内容区、受 D05 管；数据源模式看见的是“这个视频资产”，不知道它在脑图第几层。
- **脑图是第一个 Block-control**（§6.2）。参照迅雷 Bolt 界面引擎的 control：一个 control 由一组普通 UIObject 组合而成，对外是一个对象，对内子对象照常可取、可改、可加减。对到本方案：mindmap 容器是 control，节点是普通 Cell；容器定义给出属性 schema、子节点规则、布局算法、动作与键盘接管；子 Cell 的 `slot` 是容器内的命名空间（R22）。Bolt 的子对象不持久化而本方案的子 Cell 是文档实体，因此多出“内容子节点 / 模板子节点”的区分（R23），脑图只有前者。control 可以嵌套（R24）：一个节点可以是另一个 control 的实例。

## 2. Miro 脑图的对照基线

| 方面 | Miro 的做法 | 对本方案的含义 |
| --- | --- | --- |
| 对象模型 | 脑图节点是专用 item（REST API `mind_map_node`），带 `parent` 字段，文本在 `nodeView` | 父子关系是数据，不是连接线 |
| 边 | 隐式，由父子关系和布局推导；曲线/直角和分支颜色是节点或分支属性 | 不能照搬现有连接线对象 |
| 布局 | 自动：根向一侧或两侧展开；增删节点邻居让位；子树整体跟随；拖动节点到另一分支即重挂 | 需要布局引擎和派生坐标 |
| 交互 | Tab 加子、Enter 加兄弟、方向键在树上导航、Delete 删子树、折叠/展开分支、双击改文字 | 需要一套树导向的键盘与手势 |
| 节点尺寸 | 随文字自适应，超过最大宽度换行 | 需要文字测量进入布局 |
| 节点内容 | 文本为主，可附图片、链接；节点可转成便签或形状 | 节点应能承载现有 Block 内容 |
| AI 与导入 | 从提示词生成脑图、扩展分支；从文本/大纲导入；导出为文本 | 许愿格需要“树”这种结果 |
| 折叠状态 | 画板共享（所有人看到同一折叠状态） | 折叠应进文档而非个人状态 |

## 4. 对象模型

### 4.1 三条路线

| 路线 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| (a) 拼装 | 节点 = shape，边 = connector，子树 = group | 零内核改动 | 父子关系只能从连接线反推，语义模糊；每条边一个实体；删节点冻结线而不是删子树；无法自动布局；Miro 不是这样做的 |
| (b1) 单 Cell 持整棵树 | 一个 `buckyos.cell view.type=mindmap`，树在 `config` 里 | 流式页、发布页、导出简单；像 richtext 一样一个实体 | `MAX_CONFIG_BYTES = 64 KiB` 装不下大树；整棵树一个版本格，多人编辑互相冲突；节点级批注、锁、连接线绑定、许愿格引用全部失去 |
| (b2) 容器 + 节点 Cell | 新容器 kind `mindmap`，每个节点一个 Cell，`parent_id` 即父子，`order_key` 即兄弟序 | Miro 的模型；树原语、并发合并、批注、锁、连接线绑定全部复用；Agent 可逐节点提交 | 需要新 kind、容器级 Renderer、派生 placement（§5、§6） |

**推荐 (b2)。** 它把“树”这个结构交给已经稳定的 BlockTree，而不是在 config 里再发明一套。

### 4.2 (b2) 的数据契约草案

```jsonc
// 容器：树的根
{ "op": "entity.create", "entity_id": "mm1", "type_id": "buckyos.container", "parent_id": "sf",
  "order_key": "a", "placement": { "x": 100, "y": 100, "w": "auto", "h": "auto" },   // 外框包住子节点
  "payload": { "kind": "mindmap", "layout": { "mode": "tree" }, "title": "产品规划",
    "config": { "direction": "both", "edge": "curve", "spacing": { "sibling": 12, "level": 48 } } } }

// 节点：普通 Cell，parent_id 是父节点（根节点的父是容器）
{ "op": "entity.create", "entity_id": "n1", "type_id": "buckyos.cell", "parent_id": "mm1",
  "order_key": "a", "placement": { "x": "auto", "y": "auto", "w": "auto", "h": "auto" },   // 由容器公式算出；拖到空处后 x/y 变数值
  "payload": { "view": { "type": "mindnode" }, "title": "核心目标",
    "config": { "text": "核心目标", "branch_color": "#4f8df7", "side": "auto" } } }   // 折叠不在文档里，是 user_state（R8）
```

要点：

- 节点的 `parent_id` 可以是另一个节点：现有 BlockTree 只允许 Cell 作为叶子，group 作为容器。这是本方案对树原语的**唯一结构性扩展**：Cell 可以有子 Cell（只在 `mindmap` 容器内）。替代方案是每个节点一个 group 加一个 backing Cell，实体数翻倍，不推荐；而且节点内容是任意 Block（§4.3）时，节点必须就是那个 Cell 本身，壳方案让视频节点的 group 没有自己的尺寸来源，所以 R3 不是可选项而是必需。
- 子 Cell 可带容器内唯一的 `slot`（R22，Bolt `GetControlObject` 的命名空间，§6.2），路径 `bkg.text` 逐级解析。脑图节点同质，不用；schema 预留给 Button 这类组合 control。
- 文字节点的文字放在 `title`（≤ 256 字，outline 已投影），布局公式只凭 outline 就能算（§5.4）。节点可以是任意 Block（R10）：节点 Cell 的 `view.type` 不限，媒体/表格节点照常用 `source_ref` 绑数据实体（§4.3）；只有文字节点的 `w`/`h` 能是 `auto`，其他节点的 `w`/`h` 必须是数值，由 `check_placement` 按 `view.type` 校验（R17）。
- `direction`：`right` / `left` / `both`（根两侧）/ `down`（组织结构图）。四个首版都支持（R13）：同一个 `tree` 算法换参数。
- 边样式在容器上，分支颜色在一级子节点上并向下继承，节点可覆盖。
- 对 `mindmap` 容器内的节点，`locked`、批注、`presentation` 属性照常可用。

### 4.3 结构是 UI 的，内容绑数据（2026-10-27 用户归零）

曾经的问题是：脑图要不要成为一个数据实体，让数据源模式看见它的结构？答案是不要，理由比“数据树不显示 Block”更根本：**一个节点可以是文字、视频、表格视图或任意 UI Block**。数据树里没有任何一种实体能表达“这个位置上放着一个视频 Block”，硬要表达就得发明一个“节点”数据类型去包别的东西，等于把 BlockTree 复制一份进数据树。所以结构和内容是两层：

| 层 | 落点 | 数据源模式 |
| --- | --- | --- |
| 树结构（父子、兄弟序、折叠、pin） | BlockTree：mindmap 容器 + 节点 Cell | 不显示（R21）。与形状、框一致：第二期 §6.1“数据树不显示 BlockTree 中的 Block”，`DataTree.tsx` 已过滤 `buckyos.cell` |
| 文字节点内容 | Cell 自己的 `title` / `config.text`，同 `shapeBlock.tsx` 的 `saveText` | 不产生数据实体 |
| 媒体/表格等节点内容 | 节点 Cell 的 `source_ref` 指向 AssetRef / TableSource 等数据实体，落画布内容区，D05 owns/bind 规则照常 | 显示该数据实体本身，不知道它在脑图里 |

数据侧仍有出口，不靠数据树：§8 的 Markdown 大纲双向转换是结构的数据投影（“转成大纲插入文档”产出 richtext 数据实体）；许愿格 `mindmap` 结果直接以 Block 落到画布，依赖记录指向容器或节点 Cell 的 entity_id（Cell 能否作为 `input` 引用的目标，实施前核对 `REF_KINDS`）。

推论（已随 R1/R3/R10/R17 定案）：(b2)；Cell 可有子 Cell 是必需；首版节点内容就是任意 Block，不收窄到文字加图片；只有文字节点的尺寸能从 `title` 算出，其他节点的 `w`/`h` 必须是数值，这条写进 `check_placement`，不是约定。

## 5. `auto` placement 原语与布局公式

### 5.1 原语定义

`placement` 的 `x`、`y`、`w`、`h` 各自可以是有限数值或字符串 `"auto"`（`rotation` 不参与）。

- 数值：用户数据，现有语义不变（第二期 D1 自动合并）。
- `auto`：不存储值；读取/显示时由**父容器**的布局公式算出。公式由容器的 `kind`（或 `layout.mode`）决定，在注册表里按容器注册（§6.2）。
- 用户手工拖动或缩放某个分量，就把它写成数值（pin）；写回 `auto` 就是“重置布局”。两种写都是普通 placement 写，撤销、并发规则不变。
- core 的 `check_placement` 只校验形状：分量是数值或 `auto`；`auto` 只允许出现在 layout 容器的直接子节点上（见 5.2），和连接线“只能建在自由画布上”同类的树局部规则。core 不进布局。

流式页（`layout.mode = flow`）的子节点不存 placement、`layoutSurface` 用 `autoY` 顺序堆叠，看起来相近，但块宽来自页宽、块高来自内容，两个轴方向不同（§5.7）；v1 流式页保持特例，不迁到这个原语上。

更保守的替代（R19）：不引入 `auto` 字面量，沿用“没有 placement 就是自动，有就是 pin 住”。schema 零改动，但 pin 只能整体 pin，pin 住的节点文字改长后尺寸不再跟随。

### 5.2 限制一：只在 layout block 下面

能填 `auto` 的对象必须是一个 layout 容器（首版只有 `mindmap`）的直接子节点。原因是性能和可预测性：

- 公式的作用域是该容器的**直接子节点**，重算范围有边界；嵌套的 control（R24）自底向上逐层算，内层先得出自己的外框，对外层只是一个已解析尺寸的子节点，代价 O(子树)。
- 容器自己的 `w`/`h` 可以是 `auto`（外框包住子节点），但它在自由画布上的 `x`/`y` 是数值，所以子树变化不会越过容器往外传播；用户缩放脑图外框没有意义，禁用。
- 自由画布上的普通对象不能自己声明 `auto`，不存在“谁来算它”的问题。

### 5.3 限制二：公式只读自身数据

一个容器的公式只能读三样东西：

1. 自己的 `config`（方向、间距、边样式）。
2. 直接子节点在树里的结构：`order_key`、折叠状态。
3. 每个直接子节点已解析的尺寸（数值，或该子节点自己的尺寸公式算出的 `auto` 值）。

一个节点的尺寸只能来自自己的内容（标题文字、绑定的数据）。公式**不能按 id 引用兄弟或任何其他 UI Block**。于是依赖只沿树向下，没有依赖图、没有环、没有失效传播。

连接线是现有代码里唯一的跨 Block 派生几何（两端绑定别的 Block）。它为此需要的第二遍布局、手势期间的 `Override`、ShapeBook 异步读 payload，正是这条限制要避免的复杂度。结论：连接线保持为唯一例外，在所有 `auto` 解析完之后的第二遍里算（`resolveConnectors` 现状即如此）；脑图的隐式边由容器画自己的子节点，不属于跨 Block。

### 5.4 性能：公式只凭 outline 就能算

- outline 已投影 `title`、`order_key`、`parent_id`、`struct_rev`、`placement`。文字节点的文字就是 `title`（单行，≤ 256 字），折叠状态来自本人的 `user_state`（§7.3），布局器拿 outline 加本地折叠集合就能同步算完，千节点不用先发一千次 `doc.read`。非文字节点的尺寸是数值，也在 outline 里。
- 文字测量按（文字、字体、最大宽度）缓存；容器结果按子树 `struct_rev`、折叠集合与 pin 集合缓存，没变就不重算。
- 布局算法是纯函数（输入：子节点结构、尺寸、config；输出：placement 表），放共享 TS 模块（同 `import-drawio/` 的做法，Deno 与浏览器同用），Agent、导出、发布页都用同一份；需要千节点在一帧内。
- 公式**不版本化**（R18，用户定）：布局公式是特殊的，`auto` 的值不存储，没有需要保真的持久结果；算法改进后老文档跟着变，pin 住的数值分量不受影响。相应地共享模块要有布局快照测试防止无意的回归。
- 文字测量依赖字体，各端可能略有差异。这是唯一不纯的输入：首版接受（Miro 也是各端自己排），必要时再打包一套度量字体。

### 5.5 树内 pin 住的节点

用户把一个节点拖到空处，它的 `x`/`y` 变成数值。两种语义：

| 语义 | 做法 | 代价 |
| --- | --- | --- |
| 自由主题（XMind）（推荐） | pin 住的节点及其子树脱离自动排布：子树仍相对它按公式排，兄弟的布局不为它留位，边仍画 | 公式简单、可预测 |
| 约束式 | pin 住的节点是固定障碍，兄弟绕开它排 | 变成约束布局，难做难测 |

随之而来的交互区分：拖动节点落到另一个节点上是重挂（仍 `auto`），落到空处才是 pin（§7.2）。Miro 的脑图节点不能自由摆放，所以这里比 Miro 多一个自由度，要在 UI 上说清（pin 住的节点有标记，右键“回到自动布局”）。

### 5.6 算法

分层树布局（Reingold–Tilford 一类）即可，输入折叠状态（折叠子树按一个节点算）与 pin 集合（跳过），输出每个 `auto` 节点相对容器的坐标。`both` 方向把一级子节点按 `side` 分配到两侧（`auto` 时按顺序交替或按子树大小平衡）。拖动重挂时要实时预览（§7.2），以“假设重挂到这里”为输入重算。

### 5.7 边界：这不是布局引擎

“`auto` 分量 + 父容器公式”往下走的自然方向是 stack、grid、换行、对齐、内边距、min/max、flex 伸缩，也就是重做一遍 CSS。CSS 的难点在尺寸双向协商（父要包住子、子要父的可用宽度，于是两遍算固有尺寸）和行内文字流。本方案用四条规则把它挡在外面：

| 规则 | 含义 | 排除掉的东西 |
| --- | --- | --- |
| **单向**：方向是 layout 算法的属性，一个容器内只有一个方向，永不混用 | 自底向上的 layout（v1 唯一的 `tree`）：公式只给子节点 `x`/`y`，子节点 `w`/`h` 只来自自身内容（标题按常量最大宽度测量），容器尺寸 = 子节点外框并集；自顶向下的 layout（v1 没有）：容器尺寸是数值，子节点从容器取尺寸，容器不读子节点。两种都是单遍 | 同一容器内父依赖子又让子依赖父（stretch + 包住子节点、百分比 + 内容高度、flex 伸缩），也就是需要两遍布局的一切 |
| 公式是代码里注册的具名算法 | v1 只有 `tree`（方向参数覆盖脑图与组织结构图）；每多一个算法是一次产品决策 | 用户可写的布局表达式、通用 layout 属性集、布局组合 |
| control 可嵌套，但**每个容器只算自己的直接子节点、只按自己的方向** | 允许嵌套（R24，用户定）：Bolt 的 control 随便嵌（ListView 里套滚动条 control），嵌得起是因为父只读子的已存尺寸、单遍算完。本方案同理：内层 control 先按自己的算法得出外框（自底向上）或从父取尺寸（自顶向下，v1 无），对外层只是一个尺寸已解析的子节点；父不读孙，子不读父。被父赋了尺寸的内层 control 把该分量视为数值（pin），自己只排内部。pin / 重挂 / 键盘接管按最近的容器 | Figma 式“子撑父、父拉子”的双向嵌套 |
| 任意排版走 HTML Block 扩展 | 同源 iframe 的 `window.aiws` HTML Block 已经存在，是放 HTML 布局的地方 | 内核再长一个布局器 |

按这四条，v1 实际实现的是：一个自底向上的树容器给叶子子节点排位置，叶子尺寸是标题文字的固有尺寸，拖到空处就 pin。`auto` 做成每分量可选只是 schema 为 pin 预留的形状，不是算法层面的通用性。

关于“单向”的一个判据，留给以后：CSS 的块流是宽度自顶向下、高度自底向上，每个轴各一个方向，这是 CSS 里简单的部分；真正难的是**同一个轴上**双向协商（shrink-to-fit、百分比高度、flex 伸缩）。如果以后要把流式页或 stack 这类 layout 纳入本原语，“不混用”应按轴判，而不是按容器判。v1 不做这个决定。

**参考：迅雷 Bolt 界面引擎的位置表达式（2026-10-25，依据用户提供的原设计文档；用户能找到的只有这一份，其余凭记忆补充）。** Bolt 的 `left/top/width/height` 各是一个表达式（整数、四则运算、引用值），引用对象可以是祖先（直到 root）、同一父节点下的兄弟和自己，**不允许引用子节点**；可引用的属性是 `left/top/right/bottom/width/height`。引用拿到的是**已存储的直接值**，不会触发被引用方重算；求值是固定顺序的单遍：父先于子，兄弟按既有顺序，对象内按 `left → top → width → height`，已算过的引用新值，没算到的（自己、后面的兄弟、后面的属性）引用旧值。显式 `SetObjPos` 用数值替换表达式。公开示例里实际只见 `father.width` / `father.height`；列表、网格等自动布局在 Lua 里显式写坐标，文字排版封在 `TextObject` / `RichEditObject` 内。设计文档末尾把“是否允许引用兄弟节点、兄弟变化要不要递归通知”列为开放问题。

与本方案的关系：

- **单向是原则，方向是 layout 的属性。** 用户 2026-10-25 补充：Bolt 的核心思路是单向，而自顶向下还是自底向上由一个特殊的 layout 决定，不会混用。位置表达式那一层是自顶向下的（禁止向下引用，父尺寸永远不依赖子，一遍算完）；需要自底向上（内容决定尺寸）的地方由专门的 layout 对象承担，两者不在同一容器里混。本方案照搬这条原则：方向由 layout 容器声明，容器内不混用；v1 只有自底向上的 `tree`。CSS 难在同一处两个方向都要。
- **读存储值，不触发重算。** Bolt 的引用是已存值加固定求值顺序，容忍短暂过期，是有序单遍数据流而不是约束求解。本方案 R7“公式只读子节点已解析的尺寸”同理。
- **兄弟依赖内化进容器。** Bolt 的开放问题（兄弟引用的变化传播）在本方案里不存在：兄弟间距不是对象对对象的引用，而是容器的 `tree` 算法一次算完全部子节点；重算单位是容器，对象之间没有通知链。
- **pin 即 `SetObjPos`。** Bolt 显式设置位置就是用数值替换表达式；本方案的 pin 是把 `auto` 写成数值。
- **本方案更紧一档。** Bolt 有表达式语言；本方案的 placement 分量只有数值和 `auto` 两种取值，没有表达式、引用和求值顺序。Bolt 意义上的“排版需求”（相对父对象对齐、留边）在自由画布的绝对坐标下不存在，“自动布局”交给具名算法。

## 6. 边与容器级渲染

### 6.1 隐式边

脑图的边不生成 connector 实体：

- 边由 mindmap 容器的 Renderer 按父子关系绘制；路由（曲线/直角/直线）在容器 `config.edge`，颜色随分支继承，粗细可按层级衰减。
- 删节点连子树和边一起删（现有 `entity.delete` 的 `subtree` 已经做到），不是冻结。
- 隐式边不能用现有连接线工具加标签或改锚点。Miro 也不能，可接受。需要“关系线”时用普通连接线绑定两个节点（§3.1），它们走连接线自己的规则。

### 6.2 容器定义：Block-control（Bolt control 对照）

现状：`BlockRegistry` 只解析 Cell 的 `view.type`；group 的外观靠第一个子 Block 当 backing（`layout.ts` `backingId`）；自定义 Block 只有 `declarative`（解释器自带六种小控件）和 `html` 两种 `block-def`，都不能由标准 Block 组合而成，HTML Block 的 `createBlock` 只能在自己旁边建兄弟 Block。

2026-10-27 用户提出以迅雷 Bolt 界面引擎的 **control** 为参照：一个 control 由一组普通 UIObject 组合得到，对外是一个对象，其子对象都可以当普通对象对待。依据用户提供的 Thunder.Button 原始定义（Button.xml / Button.xml.lua）与公开资料（boltstack FAQ、BOLT_CONTROLS 的 ListView），control 由五部分组成，逐项对到本方案：

| Bolt | 含义 | 本方案 | 现状 |
| --- | --- | --- | --- |
| `attr_def` | 对外属性，带类型与默认值（`Text`、`Enable`、`NormalBkgID`…） | 容器 `config` + `config_schema` | `block-def` 有 `config_schema`，容器没有 |
| `objtemplate/children` | 一棵普通 UIObject 树，每个子对象有 control 内的 id（`button.bkg`、`button.text`、`focusrectangle`） | 容器下的子 Cell，都是普通 Block；`slot` 是容器内角色名 | R3、R22 |
| 子对象位置 `father.width`（本方案称 `parent`）、`SetObjPos` | 父先子后单遍；显式 `SetObjPos` 用数值替换表达式 | 子节点 placement `auto` + 父公式；pin 即写数值 | R5/R6 已定 |
| `method_def` + `eventlist` + `event_def` | 对外方法（`SetText`、`SetEnable`）；原始事件先到 control（`OnLButtonDown`、`OnKeyDown`），`RouteToFather` 冒泡，`FireExtEvent` 对外抛 | 容器 `actions` / `toolbar`；选中节点时 Tab/Enter/方向键由容器接管（§7.1） | 无容器级 actions |
| `GetControlObject(id)` | 只在当前 control 的**直接子对象**里按 id 找；深层逐级取；嵌套 control 各有自己的 id 空间 | 容器按 `slot` 找子 Cell，作用域是直接子节点 | 无 `slot` |

术语：`father.width` 是 Bolt 的原词，只在引用 Bolt 时照抄；本方案自己的名字统一用 **`parent`**（`parent.width` / `parent.height`，与 `parent_id` 一致），凡本方案出现对父容器尺寸的引用都按此写（用户 2026-10-27）。

**直接采纳的三条。**

1. **子对象是普通对象。** Button.xml.lua 对 `button.text` / `button.bkg` 直接 `SetObjPos`、`SetTextureID`，对 `masktexture`、tip 用 `AddChild` / `RemoveChild` 动态加减；ListView 把滚动条 control 当子对象加进 `listview.bkg`。对脑图：节点 Cell 直接复用选择、批注、锁、连接线绑定、原地改字，容器不转发任何东西。这是 (b2) 的论据，也是 Bolt 整套控件库验证过的做法。
2. **ControlObject 是命名空间隔离**（用户 2026-10-27 归结）。`button.bkg`、`focusrectangle` 这类 id 只需在 control 内唯一；`GetControlObject` 只到直接子对象，嵌套的 control 是另一个命名空间；用户记得 Bolt 也支持 `controlid.bkg.texture` 这样的路径名，类似 HTML 的按路径选择。两者一致：路径就是逐级的命名空间查找。对本方案（R22）：子 Cell 加容器内唯一的 `slot`，容器定义按 slot 找“文字那个子对象”，不按 entity_id；slot 的作用域就是直接子节点，与 §5.2 “`auto` 只在直接子节点”是同一条边界；**路径寻址** `bkg.text` 从容器出发逐段解析，每段在上一段的直接子节点里找，嵌套 control 的内部 slot 由它自己的命名空间解析。脑图节点同质不需要 slot，Button 类组合 control 需要；schema 预留，outline 投影。
3. **事件先到 control 再路由。** 对本方案：mindmap 容器接管选中节点时的键盘（§7.1）与拖动落点判定（§7.2），对外暴露的是容器 actions；v1 不需要用户可写的事件脚本，`event_def` 没有对应物。

**不能照搬的两处。**

- **布局是 Lua 命令式。** Button 的 `OnInitControl` / `SetSpaceMagrin` 用 `SetObjPos(margin, 0, "father.width-"..margin, "father.height")` 拼表达式字串排子对象。本方案的布局是注册的具名纯函数（§5.7 第二条）；内置 control 的布局用代码，用户定义的组合 control 若要进来，子节点位置首版只允许固定相对坐标（`algorithm: 'fixed'`，Bolt `SetObjPos` 数值那一档），不开表达式；若以后放开，对父尺寸的引用写 `parent.width` / `parent.height`，不沿用 Bolt 的 `father`。这是 §6.2 与 §5.7 的接缝，不在本方案裁决。
- **子对象不持久化。** Bolt 的 `objtemplate` 每次实例化重建，改模板所有实例一起变；运行态（`NowState`、`BtnDown`、`defaultani`）放 `GetAttribute()` 表里。本方案的子 Cell 是文档实体，改定义不会追到已有实例。因此区分两类子节点（R23，用户定）：**内容子节点**是文档实体、用户数据，脑图节点属于此；**模板子节点**不落实体，由容器 Renderer 按定义绘制（Button 的 bkg / focusrect / masktexture 这类“皮”），运行态放组件 state 或 `user_state`。脑图只有内容子节点；模板子节点的 `Chrome` 接口随第一个需要它的 control 落地。

**容器定义（`ContainerDefinition`）草案**，按五块补齐：

```ts
interface ContainerDefinition {
  kind: string; version: number; title: string          // control id 即容器 kind；`mindmap` 是第一个内置 control（R2）
  configSchema?: Json                                   // attr_def：direction / edge / spacing
  children: {                                           // objtemplate 的约束
    accepts: string[] | 'any'                           //   允许的子 Cell view.type；脑图 'any'（§4.3）
    containers: boolean                                 //   能否放 control 实例作子节点；脑图 true（R24）
    slots?: { id: string; accepts: string[]; required?: boolean }[]   // R22；脑图无
  }
  layout: {
    direction: 'bottom_up' | 'top_down'                 // §5.7 单向，v1 只有 bottom_up
    algorithm: 'tree' | 'fixed'                         // 具名算法，不版本化（R18）
    run(children: LaidChild[], config: Json, measure: Measure): Placements   // 只填 auto 分量（§5.3）
  }
  Chrome?: ComponentType<ContainerContext>              // 隐式边、外框、模板子节点（R23）
  create(args: CreateArgs): Operation[]                 // objtemplate 实例化：容器 + 初始内容子节点
  actions?: BlockAction[]; toolbar?; hover?             // method_def
  agent: AgentManual                                    // 给 Agent 的自述（R11，§8.1）
  keys?: (context: ContainerContext) => KeyHandler      // eventlist：选中子节点时接管键盘
}
```

接入点不变：

- `layoutSurface` 遇到 layout 容器时调用它的 `layout.run` 解析子节点的 `auto` 分量（数值分量照用），并把外框算到容器的 `Laid.rect`；连接线仍在其后的第二遍解析。
- 命中、裁剪、LOD、层叠仍按 Laid 走，不变。
- 边绘制走 SVG（与连接线 `paint.ts` 同一层），千节点规模下考虑合并为一条 path。
- 现有 `BlockDefinition.create` 已经是“一次插入返回一组操作”的形状，只是只建一个 Cell；容器的 `create` 建容器加初始内容子节点。

### 6.3 流式页

mindmap 容器在流式页作为一个自包含 Block 整体渲染（固定高度、内部可平移缩放，或按外框等比缩放）。这需要流式页能渲染一个“有自己外观的 group”，现在 `FlowSurface.tsx` 对 group 只有名字和删除。

## 7. 交互

### 7.1 键盘

| 键 | 动作 |
| --- | --- |
| Tab | 在选中节点下加子节点并进入编辑 |
| Enter | 加兄弟节点并进入编辑（编辑中 Enter 结束编辑，Shift+Enter 换行，同 shape） |
| ← → ↑ ↓ | 在树上导航：父 / 子 / 兄弟（`both` 方向下左右按侧翻转） |
| Delete | 删子树（现有 `deleteSelection` 已带 `descendants`） |
| Ctrl+/ 或点击折叠柄 | 折叠 / 展开 |
| Ctrl+D | 复制子树（`entity.clone` 子树，D05 同画布克隆） |

与现有画布快捷键的冲突：自由画布的方向键是微移（`CanvasView.tsx` 的 `step`），在 mindmap 容器内选中节点时改为树导航。

### 7.2 手势

- 拖动节点：拖的是子树；松手前实时预览新位置（布局器以“假设重挂到这里”为输入重算）；落到另一个节点上是重挂（placement 仍 `auto`），落点判定按“最近的候选父节点与插入位置”，不是 `groupAt` 的矩形包含；落到容器内空处是 pin（`x`/`y` 写数值，§5.5）。拖出容器外松手：**拒绝**（R9，用户定），节点回到原位；把节点挪到画布或另一棵脑图用复制粘贴（`entity.clone` 子树，D05 同画布克隆、跨画布引用），~~反向也不做“拖入即挂接”，画布对象进脑图同样走粘贴。~~ **2026-10-28 用户改为：画布上的 Block（连接线、笔迹除外）拖到节点上即挂入**，判定与预览同节点重挂（子节点，或靠边时插在旁边），placement 写 `x`/`y` `"auto"`、尺寸保留；拖出仍拒绝（R9 不变）。节点工具栏另有“插入”，打开插入目录，所选对象直接建为该节点的子节点（嵌套 control 全 `"auto"`，其他 Block 用目录默认尺寸）。
- 拖动容器：整棵树一起走（group 已如此）。
- 缩放容器外框：无意义，禁用（外框 `w`/`h` 是 `auto`）。
- 框选：按节点框选，`topLevel` 规则保证选中祖先时不重复选子项。
- 手机端：首版只查看与折叠，不编辑（`touch.ts` 现状）。

### 7.3 折叠状态

**折叠是 `user_state`**（R8，用户定），不是文档。每个人折自己的，布局各算各的；折叠不写提交、不进撤销栈、不进导出包。

- 存法：`user_state` 键 `mindmap:collapsed:<container>` → 已折叠节点 id 集合（第二期 §4.4 的服务端 + IndexedDB 双存，离线可用）；节点删除后集合里的残留 id 忽略。
- 布局输入：折叠集合与 outline 一起进布局器（§5.4）；折叠子树按一个节点算，缓存键含折叠集合。
- 没有本人状态的视图（发布页预渲染、导出、Agent 读取、放映）看到的是**全部展开**的形态；放映时的分步展开用第三期 step 的 `hide` 列表，不另加属性。
- 代价已接受：协作者看到的形态不同；Agent 不知道用户折了什么。

## 8. AI 生成与 Agent

- **Agent 不算坐标**：Agent 和许愿格提交逻辑树即可，节点 placement 写 `auto`（§5.1）。Agent 需要坐标时（例如再导出到 draw.io）运行共享布局模块。
- **交换格式**：Markdown 大纲（嵌套列表）是首选。`markdown.rs` 已能把 Markdown 转成 `bullet_list` 嵌套，再由一个纯函数把嵌套列表转成 mindmap 的 `entity.create` 序列；反向把脑图导出成 Markdown 给模型“扩展这一分支”。Markdown 保留节点文字的行内格式（粗体、链接）。
- **脑图 ↔ 富文本**：流式页里的嵌套列表可一键“转成脑图”，脑图可“转成大纲”插入文档，两者用同一个转换函数。

### 8.1 Agent 接口来自 Block-control 的通用机制（R11，用户定方向）

不为脑图单独设计 Agent 接口。用户的要求是“从 block-control 的通用机制来考虑设计，设计良好的 block-control 自带提示词”。落法：

- **每个 control 定义自带 `agent` 段**（`ContainerDefinition.agent`，§6.2）：一段给模型读的 Markdown 自述，包含它是什么、`config_schema` 各项的含义、子节点规则、怎样用 `doc.commit` 建一个实例与子节点（带 1–2 个最小操作序列范例）、支持的交换格式与转换入口、不能做什么（脑图：不要写坐标；非文字节点要给尺寸）。这就是 Bolt 里 `attr_def` + `method_def` 的那份“接口说明”，只是读者换成模型。
- **渐进式披露**（同 [[feedback-agent-tool-progressive-disclosure]] 与 cmd_skills 的做法）：手册 `aiworkspace_template_dev.md` 只列 control 目录（id、一句话、何时用），Agent 需要时再取某个 control 的 `agent` 全文。入口两个：`aiws controls list` / `aiws controls describe <kind>`（CLI 直接从共享模块读注册表，不经服务），以及 Desktop 侧 `ws.get_info` 返回 control 目录供许愿格构造 context。文本放在定义里，不是单独维护的手册文件，加 control 就带上说明。
- **许愿格结果**是通用的“control 实例”（`output.kind = control`，带 `kind` 与子节点操作），不是 `mindmap` 专用结果种类；“扩展这一分支”是以某节点 Cell 为输入的 wish。
- **导入/导出动词**挂在 control 上：`agent` 段声明它支持的格式（脑图：Markdown 大纲、OPML），`aiws` CLI 的 `import/export` 按 control 分派，而不是加 `mindmap import` 这样的专用动词。
- 顺序：`agent` 段与目录入口随 M1 的注册表落地 → 许愿格通用 control 结果（M3）→ CLI（M3）。
