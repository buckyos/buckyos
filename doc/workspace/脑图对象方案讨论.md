## 1. 结论

**脑图不是“便签 + 连接线 + 分组”的拼装物，而是一棵带布局语义的树。** 现有架构能承接它，但缺的不是再注册一个 Block，而是一个内核原语加两条限制（2026-10-25 用户归结）：

**原语：placement 的分量可以是 `auto`。** `x`、`y`、`w`、`h` 各自可以是数值，也可以是 `auto`；`auto` 的值在读取/显示时由父容器的布局公式算出，不存储。用户手工拖动或缩放过某个分量，它就被写成数值，被 pin 住；“重置布局”就是把数值改回 `auto`。

**限制一：能填 `auto` 的对象必须在一个 layout block 下面。** 布局由父容器拥有（同 CSS）。公式的作用域是该容器的子树，重算有边界；容器自己的 `w`/`h` 可以是 `auto`（包住子节点），但它在自由画布上的 `x`/`y` 是数值，变化不会越过容器向外传播。自由画布上的普通对象不能自己声明 `auto`。

**限制二：公式只读自身数据，不从别的 UI Block 推导。** 一个容器的公式只能读自己的 config、直接子节点在树里的结构（`order_key`、折叠）和每个子节点已解析的尺寸；一个节点的尺寸只能来自自己的内容（文字、绑定的数据）。不能按 id 引用兄弟或任何其他 Block。依赖只沿树向下，没有图、没有环、没有失效传播。连接线是现有代码里唯一的跨 Block 派生几何（两端绑定别的 Block），它需要的第二遍布局、手势 Override 与 ShapeBook 异步读正是这条限制要避免的复杂度；连接线保持为唯一例外，在所有 `auto` 解析完之后的第二遍里算。

这个原语把几个原本分开的缺口收成一个：脑图节点的 `x`/`y` 是 `auto`（公式是树布局）；节点文字自适应是 `w`/`h` 为 `auto`（公式是文字测量），同时解决自由画布上便签/文本高度随内容增长的老问题；流式页看起来相近（`layout.mode = flow` 的子节点不存 placement，`layoutSurface` 用 `autoY` 顺序堆叠），但它的块宽来自页宽（自顶向下）、块高来自内容（自底向上），两个方向各占一个轴。按 §5.7“不混用”的严格读法它是混用，按“每轴单向”的读法不是；v1 不裁决这一点，流式页保持特例，不迁到这个原语上。组织结构图是同一个 `tree` 算法换方向；泳道、网格不在本方案范围。

这个原语有一个必须守住的边界：**它不是布局引擎**（§5.7）。核心是**单向**：方向（自顶向下或自底向上）由 layout 容器声明，容器内永不混用；此外具名算法不可组合、layout 容器不嵌套，任意排版的需求走 HTML Block 扩展。

在它之上，脑图还需要两样东西：**容器级渲染器与布局器**（现在只有 Cell 有 Renderer，group 没有自己的外观和布局算法）和**隐式边**（脑图的边由父子关系推导、样式随分支继承，与现有“独立实体、删目标则冻结”的连接线语义相反）。

推荐的模型（§10 R1–R4 待定）：

- **新容器 kind `mindmap`**（或 group 的新 `layout.mode`），树的每个节点是一个 `buckyos.cell`，`parent_id` 就是脑图父子，`order_key` 就是兄弟顺序。这是 Miro 的模型（每个节点是 item，带 `parent`），也最大化复用现有树原语。
- **节点 placement 为 `auto`**，由容器的树布局公式算出；用户拖到空处的节点被 pin 住（§5.5）。
- **边隐式**：由 mindmap 容器的渲染器绘制，样式是容器与节点的属性；不生成 connector 实体。
- **Agent 不算坐标**：Agent 和许愿格只提交逻辑树（Markdown 大纲是首选交换格式），placement 写 `auto`。这是对 AI 原生定位最重要的一条。

## 2. Miro 脑图的对照基线

| 方面 | Miro 的做法 | 对本方案的含义 |
| --- | --- | --- |
| 对象模型 | 脑图节点是专用 item（REST API `mind_map_node`），带 `parent` 字段，文本在 `nodeView` | 父子关系是数据，不是连接线 |

## 4. 对象模型

### 4.1 三条路线

| 路线 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| (a) 拼装 | 节点 = shape，边 = connector，子树 = group | 零内核改动 | 父子关系只能从连接线反推，语义模糊；每条边一个实体；删节点冻结线而不是删子树；无法自动布局；Miro 不是这样做的 |
| (b1) 单 Cell 持整棵树 | 一个 `buckyos.cell view.type=mindmap`，树在 `config` 里 | 流式页、发布页、导出简单；像 richtext 一样一个实体 | `MAX_CONFIG_BYTES = 64 KiB` 装不下大树；整棵树一个版本格，多人编辑互相冲突；节点级批注、锁、连接线绑定、许愿格引用全部失去 |
| (b2) 容器 + 节点 Cell | 新容器 kind `mindmap`，每个节点一个 Cell，`parent_id` 即父子，`order_key` 即兄弟序 | Miro 的模型；树原语、并发合并、批注、锁、连接线绑定全部复用；Agent 可逐节点提交 | 需要新 kind、容器级 Renderer、派生 placement（§5、§6） |

**推荐 (b2)。** 它把“树”这个结构交给已经稳定的 BlockTree，而不是在 config 里再发明一套。

### 4.2 (b2) 的数据契约草案

```jsonc
// 容器：树的根
{ "op": "entity.create", "entity_id": "mm1", "type_id": "buckyos.container", "parent_id": "sf",
  "order_key": "a", "placement": { "x": 100, "y": 100, "w": "auto", "h": "auto" },   // 外框包住子节点
  "payload": { "kind": "mindmap", "layout": { "mode": "tree" }, "title": "产品规划",
    "config": { "direction": "both", "edge": "curve", "spacing": { "sibling": 12, "level": 48 } } } }

// 节点：普通 Cell，parent_id 是父节点（根节点的父是容器）
{ "op": "entity.create", "entity_id": "n1", "type_id": "buckyos.cell", "parent_id": "mm1",
  "order_key": "a", "placement": { "x": "auto", "y": "auto", "w": "auto", "h": "auto" },   // 由容器公式算出；拖到空处后 x/y 变数值
  "payload": { "view": { "type": "mindnode" }, "title": "核心目标",
    "config": { "text": "核心目标", "collapsed": false, "branch_color": "#4f8df7", "side": "auto" } } }
```

要点：

- 节点的 `parent_id` 可以是另一个节点：现有 BlockTree 只允许 Cell 作为叶子，group 作为容器。这是本方案对树原语的**唯一结构性扩展**：Cell 可以有子 Cell（只在 `mindmap` 容器内）。替代方案是每个节点一个 group 加一个 backing Cell，实体数翻倍，不推荐。
- 节点内容首版是单行文字，就放在 `title`（≤ 256 字，outline 已投影），布局公式只凭 outline 就能算（§5.4）。多行或富内容节点、承载其他 Block 内容（图片、表格视图）是后续项，且这类节点的尺寸首版要求是数值（pin 住）。
- `direction`：`right` / `left` / `both`（根两侧）/ `down`（组织结构图）。首版至少 `right` 与 `both`。
- 边样式在容器上，分支颜色在一级子节点上并向下继承，节点可覆盖。
- 对 `mindmap` 容器内的节点，`locked`、批注、`presentation` 属性照常可用。

## 5. `auto` placement 原语与布局公式

### 5.1 原语定义

`placement` 的 `x`、`y`、`w`、`h` 各自可以是有限数值或字符串 `"auto"`（`rotation` 不参与）。

- 数值：用户数据，现有语义不变（第二期 D1 自动合并）。
- `auto`：不存储值；读取/显示时由**父容器**的布局公式算出。公式由容器的 `kind`（或 `layout.mode`）决定，在注册表里按容器注册（§6.2）。
- 用户手工拖动或缩放某个分量，就把它写成数值（pin）；写回 `auto` 就是“重置布局”。两种写都是普通 placement 写，撤销、并发规则不变。
- core 的 `check_placement` 只校验形状：分量是数值或 `auto`；`auto` 只允许出现在 layout 容器的直接子节点上（见 5.2），和连接线“只能建在自由画布上”同类的树局部规则。core 不进布局。

流式页（`layout.mode = flow`）的子节点不存 placement、`layoutSurface` 用 `autoY` 顺序堆叠，看起来相近，但块宽来自页宽、块高来自内容，两个轴方向不同（§5.7）；v1 流式页保持特例，不迁到这个原语上。

更保守的替代（R19）：不引入 `auto` 字面量，沿用“没有 placement 就是自动，有就是 pin 住”。schema 零改动，但 pin 只能整体 pin，pin 住的节点文字改长后尺寸不再跟随。

### 5.2 限制一：只在 layout block 下面

能填 `auto` 的对象必须是一个 layout 容器（首版只有 `mindmap`）的直接子节点。原因是性能和可预测性：

- 公式的作用域是该容器的子树，重算范围有边界；嵌套的 layout 容器自底向上算一遍，代价 O(子树)。
- 容器自己的 `w`/`h` 可以是 `auto`（外框包住子节点），但它在自由画布上的 `x`/`y` 是数值，所以子树变化不会越过容器往外传播；用户缩放脑图外框没有意义，禁用。
- 自由画布上的普通对象不能自己声明 `auto`，不存在“谁来算它”的问题。

### 5.3 限制二：公式只读自身数据

一个容器的公式只能读三样东西：

1. 自己的 `config`（方向、间距、边样式）。
2. 直接子节点在树里的结构：`order_key`、折叠状态。
3. 每个直接子节点已解析的尺寸（数值，或该子节点自己的尺寸公式算出的 `auto` 值）。

一个节点的尺寸只能来自自己的内容（标题文字、绑定的数据）。公式**不能按 id 引用兄弟或任何其他 UI Block**。于是依赖只沿树向下，没有依赖图、没有环、没有失效传播。

连接线是现有代码里唯一的跨 Block 派生几何（两端绑定别的 Block）。它为此需要的第二遍布局、手势期间的 `Override`、ShapeBook 异步读 payload，正是这条限制要避免的复杂度。结论：连接线保持为唯一例外，在所有 `auto` 解析完之后的第二遍里算（`resolveConnectors` 现状即如此）；脑图的隐式边由容器画自己的子节点，不属于跨 Block。

### 5.4 性能：公式只凭 outline 就能算

- outline 已投影 `title`、`order_key`、`parent_id`、`struct_rev`、`placement`。首版脑图节点的文字就是 `title`（单行，≤ 256 字），折叠状态也投影进 outline（§7.3），布局器拿 outline 就能同步算完，千节点不用先发一千次 `doc.read`。
- 文字测量按（文字、字体、最大宽度）缓存；容器结果按子树 `struct_rev` 与折叠状态缓存，没变就不重算。
- 布局算法是纯函数（输入：子节点结构、尺寸、config；输出：placement 表），放共享 TS 模块（同 `import-drawio/` 的做法，Deno 与浏览器同用），Agent、导出、发布页都用同一份；需要千节点在一帧内。
- 公式带版本（容器 `layout.version`）：算法变了老文档仍按旧公式算。
- 文字测量依赖字体，各端可能略有差异。这是唯一不纯的输入：首版接受（Miro 也是各端自己排），必要时再打包一套度量字体。

### 5.5 树内 pin 住的节点

用户把一个节点拖到空处，它的 `x`/`y` 变成数值。两种语义：

| 语义 | 做法 | 代价 |
| --- | --- | --- |
| 自由主题（XMind）（推荐） | pin 住的节点及其子树脱离自动排布：子树仍相对它按公式排，兄弟的布局不为它留位，边仍画 | 公式简单、可预测 |
| 约束式 | pin 住的节点是固定障碍，兄弟绕开它排 | 变成约束布局，难做难测 |

随之而来的交互区分：拖动节点落到另一个节点上是重挂（仍 `auto`），落到空处才是 pin（§7.2）。Miro 的脑图节点不能自由摆放，所以这里比 Miro 多一个自由度，要在 UI 上说清（pin 住的节点有标记，右键“回到自动布局”）。

### 5.6 算法

分层树布局（Reingold–Tilford 一类）即可，输入折叠状态（折叠子树按一个节点算）与 pin 集合（跳过），输出每个 `auto` 节点相对容器的坐标。`both` 方向把一级子节点按 `side` 分配到两侧（`auto` 时按顺序交替或按子树大小平衡）。拖动重挂时要实时预览（§7.2），以“假设重挂到这里”为输入重算。

### 5.7 边界：这不是布局引擎

“`auto` 分量 + 父容器公式”往下走的自然方向是 stack、grid、换行、对齐、内边距、min/max、flex 伸缩，也就是重做一遍 CSS。CSS 的难点在尺寸双向协商（父要包住子、子要父的可用宽度，于是两遍算固有尺寸）和行内文字流。本方案用四条规则把它挡在外面：

| 规则 | 含义 | 排除掉的东西 |
| --- | --- | --- |
| **单向**：方向是 layout 算法的属性，一个容器内只有一个方向，永不混用 | 自底向上的 layout（v1 唯一的 `tree`）：公式只给子节点 `x`/`y`，子节点 `w`/`h` 只来自自身内容（标题按常量最大宽度测量），容器尺寸 = 子节点外框并集；自顶向下的 layout（v1 没有）：容器尺寸是数值，子节点从容器取尺寸，容器不读子节点。两种都是单遍 | 同一容器内父依赖子又让子依赖父（stretch + 包住子节点、百分比 + 内容高度、flex 伸缩），也就是需要两遍布局的一切 |
| 公式是代码里注册的具名算法 | v1 只有 `tree`（方向参数覆盖脑图与组织结构图）；每多一个算法是一次产品决策 | 用户可写的布局表达式、通用 layout 属性集、布局组合 |
| layout 容器不嵌套 | v1 脑图的子节点都是叶子 Cell；脑图不能放进另一个 layout 容器。放进泳道、分组这类“有皮的 group”可以，它们不是 layout 容器 | Figma 式嵌套 auto-layout |
| 任意排版走 HTML Block 扩展 | 同源 iframe 的 `window.aiws` HTML Block 已经存在，是放 HTML 布局的地方 | 内核再长一个布局器 |

按这四条，v1 实际实现的是：一个自底向上的树容器给叶子子节点排位置，叶子尺寸是标题文字的固有尺寸，拖到空处就 pin。`auto` 做成每分量可选只是 schema 为 pin 预留的形状，不是算法层面的通用性。

关于“单向”的一个判据，留给以后：CSS 的块流是宽度自顶向下、高度自底向上，每个轴各一个方向，这是 CSS 里简单的部分；真正难的是**同一个轴上**双向协商（shrink-to-fit、百分比高度、flex 伸缩）。如果以后要把流式页或 stack 这类 layout 纳入本原语，“不混用”应按轴判，而不是按容器判。v1 不做这个决定。

**参考：迅雷 Bolt 界面引擎的位置表达式（2026-10-25，依据用户提供的原设计文档；用户能找到的只有这一份，其余凭记忆补充）。** Bolt 的 `left/top/width/height` 各是一个表达式（整数、四则运算、引用值），引用对象可以是祖先（直到 root）、同一父节点下的兄弟和自己，**不允许引用子节点**；可引用的属性是 `left/top/right/bottom/width/height`。引用拿到的是**已存储的直接值**，不会触发被引用方重算；求值是固定顺序的单遍：父先于子，兄弟按既有顺序，对象内按 `left → top → width → height`，已算过的引用新值，没算到的（自己、后面的兄弟、后面的属性）引用旧值。显式 `SetObjPos` 用数值替换表达式。公开示例里实际只见 `father.width` / `father.height`；列表、网格等自动布局在 Lua 里显式写坐标，文字排版封在 `TextObject` / `RichEditObject` 内。设计文档末尾把“是否允许引用兄弟节点、兄弟变化要不要递归通知”列为开放问题。

与本方案的关系：

- **单向是原则，方向是 layout 的属性。** 用户 2026-10-25 补充：Bolt 的核心思路是单向，而自顶向下还是自底向上由一个特殊的 layout 决定，不会混用。位置表达式那一层是自顶向下的（禁止向下引用，父尺寸永远不依赖子，一遍算完）；需要自底向上（内容决定尺寸）的地方由专门的 layout 对象承担，两者不在同一容器里混。本方案照搬这条原则：方向由 layout 容器声明，容器内不混用；v1 只有自底向上的 `tree`。CSS 难在同一处两个方向都要。
- **读存储值，不触发重算。** Bolt 的引用是已存值加固定求值顺序，容忍短暂过期，是有序单遍数据流而不是约束求解。本方案 R7“公式只读子节点已解析的尺寸”同理。
- **兄弟依赖内化进容器。** Bolt 的开放问题（兄弟引用的变化传播）在本方案里不存在：兄弟间距不是对象对对象的引用，而是容器的 `tree` 算法一次算完全部子节点；重算单位是容器，对象之间没有通知链。
- **pin 即 `SetObjPos`。** Bolt 显式设置位置就是用数值替换表达式；本方案的 pin 是把 `auto` 写成数值。
- **本方案更紧一档。** Bolt 有表达式语言；本方案的 placement 分量只有数值和 `auto` 两种取值，没有表达式、引用和求值顺序。Bolt 意义上的“排版需求”（相对父对象对齐、留边）在自由画布的绝对坐标下不存在，“自动布局”交给具名算法。

## 6. 边与容器级渲染

### 6.1 隐式边

脑图的边不生成 connector 实体：

- 边由 mindmap 容器的 Renderer 按父子关系绘制；路由（曲线/直角/直线）在容器 `config.edge`，颜色随分支继承，粗细可按层级衰减。
- 删节点连子树和边一起删（现有 `entity.delete` 的 `subtree` 已经做到），不是冻结。
- 隐式边不能用现有连接线工具加标签或改锚点。Miro 也不能，可接受。需要“关系线”时用普通连接线绑定两个节点（§3.1），它们走连接线自己的规则。

### 6.2 容器级 Renderer 与布局器

现状：`BlockRegistry` 只解析 Cell 的 `view.type`；group 的外观靠第一个子 Block 当 backing（`layout.ts` `backingId`）。需要：

- 注册表增加**容器定义**（`ContainerDefinition`）：按容器 `kind`（或 `layout.mode`）解析，提供 `layout(children, config, measure) → placements`（只填子节点的 `auto` 分量，§5.3）、`Edges`（画边的 Renderer）、`toolbar`、`hover`。
- `layoutSurface` 遇到 layout 容器时调用它的布局器解析子节点的 `auto` 分量（数值分量照用），并把外框算到容器的 `Laid.rect`；连接线仍在其后的第二遍解析。
- 命中、裁剪、LOD、层叠仍按 Laid 走，不变。
- 边绘制走 SVG（与连接线 `paint.ts` 同一层），千节点规模下考虑合并为一条 path。

### 6.3 流式页

mindmap 容器在流式页作为一个自包含 Block 整体渲染（固定高度、内部可平移缩放，或按外框等比缩放）。这需要流式页能渲染一个“有自己外观的 group”，现在 `FlowSurface.tsx` 对 group 只有名字和删除。

## 7. 交互

### 7.1 键盘

| 键 | 动作 |
| --- | --- |
| Tab | 在选中节点下加子节点并进入编辑 |
| Enter | 加兄弟节点并进入编辑（编辑中 Enter 结束编辑，Shift+Enter 换行，同 shape） |
| ← → ↑ ↓ | 在树上导航：父 / 子 / 兄弟（`both` 方向下左右按侧翻转） |
| Delete | 删子树（现有 `deleteSelection` 已带 `descendants`） |
| Ctrl+/ 或点击折叠柄 | 折叠 / 展开 |
| Ctrl+D | 复制子树（`entity.clone` 子树，D05 同画布克隆） |

与现有画布快捷键的冲突：自由画布的方向键是微移（`CanvasView.tsx` 的 `step`），在 mindmap 容器内选中节点时改为树导航。

### 7.2 手势

- 拖动节点：拖的是子树；松手前实时预览新位置（布局器以“假设重挂到这里”为输入重算）；落到另一个节点上是重挂（placement 仍 `auto`），落点判定按“最近的候选父节点与插入位置”，不是 `groupAt` 的矩形包含；落到容器内空处是 pin（`x`/`y` 写数值，§5.5）。拖出容器外松手：节点脱离脑图变成普通对象（或拒绝，R9 待定）。
- 拖动容器：整棵树一起走（group 已如此）。
- 缩放容器外框：无意义，禁用（外框 `w`/`h` 是 `auto`）。
- 框选：按节点框选，`topLevel` 规则保证选中祖先时不重复选子项。
- 手机端：首版只查看与折叠，不编辑（`touch.ts` 现状）。

### 7.3 折叠状态

放文档（节点 `config.collapsed`，所有人共享，Miro 的做法）还是放 `user_state`（各人自己）？

- 放文档：布局结果对所有人一致，导出和发布页看到同一形态；折叠是协作动作，会写提交。
- 放个人状态：每人折叠不同，布局各算各的；导出、发布页、Agent 看到的形态与用户不一致。

推荐放文档。放映时的分步展开可以用第三期 step 的 `hide` 列表或新增“展开到第 N 层”的 step 属性，后续项。

## 8. AI 生成与 Agent

- **Agent 不算坐标**：Agent 和许愿格提交逻辑树即可，节点 placement 写 `auto`（§5.1）。Agent 需要坐标时（例如再导出到 draw.io）运行共享布局模块。
- **交换格式**：Markdown 大纲（嵌套列表）是首选。`markdown.rs` 已能把 Markdown 转成 `bullet_list` 嵌套，再由一个纯函数把嵌套列表转成 mindmap 的 `entity.create` 序列；反向把脑图导出成 Markdown 给模型“扩展这一分支”。Markdown 保留节点文字的行内格式（粗体、链接）。
- **许愿格**：结果种类增加 `mindmap`（或更一般的 `outline`），`output_mode` 下落到画布时生成容器与节点；“扩展分支”是以某节点为输入的 wish。
- **手册**：`aiworkspace_template_dev.md` 加“从 Markdown 大纲建脑图”范例；`aiws` CLI 是否加 `mindmap import/export` 动词待定（R11）。
- **脑图 ↔ 富文本**：流式页里的嵌套列表可一键“转成脑图”，脑图可“转成大纲”插入文档，两者用同一个转换函数。
