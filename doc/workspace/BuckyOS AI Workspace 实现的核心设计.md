## 1. 总体目标与设计边界

### 1.1 一句话定义

**AI Workspace 是一个以文档为交付与迁移单元、以命名数据源为内容基础、以可扩展 Cell 为操作和展现入口、以 Command 为变更入口，同时支持本地工作、多人协作与 AI 辅助的生产力内核。**

它不只是一个无限画布界面，也不只是给表格增加一个 AI 对话框。目标是让普通到中度专业的生产力软件，能够通过数据 Schema、Cell、属性面板、Renderer、工作模式和受控命令扩展，在同一内核上构建。

### 1.2 必须保持的设计原则

| 维度 | 设计原则 |
| --- | --- |
| 文档形态 | 逻辑上是一个可保存、复制、导出和导入的 Workspace 文件；运行时可以展开为目录。不能只有依赖后台服务才能解释的业务状态。 |
| 本地能力 | 对已经内置或同步到本地的数据，应能离线继续工作。外部系统不可用，不应使整个 Workspace 不可用。 |
| 数据纯净性 | 可共享的数据本体尽量不混入选区、编辑焦点、个人标注等上下文。稳定的数据内核优先。 |
| 数据统一性 | 表格、单体对象、对象集合、文件与目录均能进入统一的命名对象与数据源体系，但不强求使用同一种存储引擎。 |
| 引用与展现分离 | 数据源可以被多个 Cell、多个 Workspace 引用；同一数据可以有多种展现方式。 |
| 用户状态隔离 | 同一份共享数据，不意味着共享所有人的 UI 状态、输入中间态和本地操作历史。 |
| 可追踪修改 | 对文档与数据产生有效修改的操作，经统一 Command 机制执行，支持历史、撤销、重做与协作提交。 |
| AI 可控性 | AI 使用同一套权限和命令入口；心流建议在被接受前不修改正式文档。 |
| 发布边界 | 工作中间态和下游可依赖的已确认结果分开。保存草稿不等于对外发布。 |
| 扩展边界 | 行业扩展可以增加类型与能力，但不能绕过内核的权限、版本、历史和数据引用机制。 |
| 业务选择 | 同时支持“模板＋独立实例”与“共享数据源＋受限录入”，不强迫所有流程退化成一张共享表。 |

### 1.3 目标范围

重点覆盖对象、图层、片段、表格、文件和素材的组织、组合、标注、计算与展示。例如文档与笔记、流程图、轻中度设计工具、材料申报、报名审核、分析报告、AIGC 素材工作流和演示。

不以在同一个初始内核中重做像素级图像处理、复杂专业视频后期等专家工具的全部能力为目标。可以引用这些工具产生的资产，也可以通过扩展调用相关能力，但不能为了覆盖极少数重度场景使基础文档模型无限膨胀。

## 2. 核心分层：数据、上下文与工作记录

### 2.1 保留讨论中的三类数据

| 类别 | 内容 | 所有权与共享方式 |
| --- | --- | --- |
| 数据源与数据本体 | 业务表格、命名对象、对象集合、文件、目录及其结构定义 | 按数据源授权共享；不依赖某个用户的当前界面 |
| 边界数据 / UI 状态数据 | 标注、展现配置、选区、编辑状态、视角等 | 根据用途属于 Workspace、用户或 Session；并非全部公开或全部临时 |
| 工作记录数据 | 操作命令、局部撤销历史、有效提交、发布与审核记录 | 本地细粒度历史与共享变更日志分开管理 |

三类数据是语义分层，不等于三个必须独立部署的后台服务。

### 2.2 进一步区分“共享业务数据”和“Workspace 文档定义”

单元格自身也有需要持久化的数据。不能把“数据与 UI 分离”误解成“Cell 完全不是数据”，也不能因此把所有 Cell 属性都写进它所引用的业务数据源。

建议区分四个存储域：

| 存储域 | 示例 | 保存位置建议 |
| --- | --- | --- |
| 业务数据本体 | 学生成绩、角色设定图、报名材料 | 内置数据源或外部对象 / 文件系统 |
| Workspace 文档定义 | 数据源引用、Cell 定义、默认布局、Renderer 绑定、保存的 Viewport、模板定义 | Workspace 文档包 |
| 附加上下文 | 成绩疑问标注、评论线程、用户偏好、Session 选区 | 可共享附加层，或用户 / Session 私有存储 |
| 历史与运行记录 | 本地 Command、共享 Commit、AI 任务记录 | 按可见性与保留策略分别存放 |

其中，Cell 的默认位置、模板字段、保存的演示路径，是文档内容；用户此刻滚到哪里、选中了哪一行，是个人或 Session 状态。两者都与 UI 有关，但不应具有相同的生命周期。

**分层目标是避免污染可独立复用的数据源，而不是禁止 Workspace 保存展示与交互定义。**

### 2.3 总体关系

```text
Workspace 文档
  ├─ 数据源定义 ── Schema 引用 ── 数据本体 / 外部资源引用
  ├─ Cell 定义 ─── 数据绑定 ──── Renderer / 属性面板
  ├─ 共享附加层 ── 标注 / 评论 / 可复用的编辑状态
  ├─ 保存的 Viewport / 演示路径
  └─ 模板与实例关系

用户 / Session
  ├─ 私有 UI 状态、草稿、细粒度 Command History
  ├─ 当前实时 Viewport / 在线状态
  └─ 经筛选与验证的 Shared Commit
                       ↓
              Workspace 的共享版本
                       ↓
              显式发布的结果 / 输出通道

人类 UI、AI Agent、行业扩展
                  ↓
       同一套权限检查与 Command 执行入口
```

### 2.4 主要实体

| 实体 | 责任 |
| --- | --- |
| `WorkspaceManifest` | 文档身份、格式版本、文档索引、版本头与派生关系 |
| `DataSourceDescriptor` | 声明数据在哪里、是什么结构、如何读取 / 同步、有哪些能力 |
| `SchemaRef` | 引用可复用且有版本的数据结构定义 |
| `CellDefinition` | 描述一个 Cell 的类型、数据绑定、默认展现与文档内关系 |
| `Overlay` | 保存独立于业务数据的标注、评论或可共享编辑状态 |
| `UserState` / `SessionState` | 保存个人偏好与本次操作上下文 |
| `LocalCommand` | 支撑当前 Session 的细粒度编辑、撤销与重做 |
| `SharedCommit` | 表达可以对其他协作者生效的、经过校验的变更 |
| `ViewportState` / `SavedViewport` | 分别表达实时视角与可持久化演示视角 |
| `TemplateSpec` / `InstanceLineage` | 表达初始化要求、实例来源与模板版本 |
| `Publication` | 表达某个对外输出通道当前指向的已确认结果 |
| `AIProposal` / `AIExecutionRecord` | 分别表达尚未接受的建议与已执行任务的记录 |

这些实体可以共享同一个本地数据库或同一组文件；实体边界不等于进程边界。

## 3. 文档文件、运行目录与导出模型

### 3.1 文件化，而不是否定在线服务

**设计原则：Workspace 应当能够作为一个文档被理解、打开和迁移。** 在线身份、实时同步、任务调度、索引发现等可以由服务提供，但不能把文档内容、数据源关系、Cell 定义和展现结果只保存成某个后台系统无法离线解释的内部状态。

建议采用“逻辑单文件＋运行目录”的形式。单文件可以是容器包，扩展名可暂拟为 `.bcanvas`；具体扩展名和封装算法尚未确定。JSON 用于描述结构，不要求把全部数据序列化进一个巨大 JSON。

### 3.2 建议的运行目录

```text
workspace/
  manifest.json
  document/
    sources.json
    cells.json
    overlays.json
    viewports.json
    presentation-paths.json
    workspace-mode.json
    template.json                  # 非模板可省略
  schemas/
    ...                            # 自定义 Schema 或所需的版本副本
  data/
    <source-id>/object.json
    <source-id>/table.sqlite
    <source-id>/collection.sqlite
  snapshots/
    <source-id>/<revision>/...      # 外部源的本地同步快照
  renderers/
    <renderer-id>/manifest.json
    <renderer-id>/...               # 包括 AI 生成的 Renderer 资源
  assets/
    refs.json                      # 外部资产引用
    embedded/...                   # 按导出策略选择内嵌的资产
  history/
    shared/...                     # 经授权可导出的共享历史
  publications/
    channels.json
```

用户私有的选区、输入草稿、本地 Command、身份凭据和 Session 信息，建议放在独立的本地状态区，而不是默认放进可分享的文档包。允许额外提供“个人完整备份”，但必须与普通分享导出区分。

### 3.3 Manifest 示例

以下标识符均为示例用的不透明 ID，不预设 BuckyOS 实际的 DID、Object ID 或 URL 编码。

```json
{
  "format": "buckyos.ai-workspace",
  "format_version": "0.1-draft",
  "workspace_id": "ws:character-concept",
  "title": "角色设定工作区",
  "head_commit_id": "commit:42",
  "document": {
    "sources": "document/sources.json",
    "cells": "document/cells.json",
    "overlays": "document/overlays.json",
    "viewports": "document/viewports.json",
    "presentation_paths": "document/presentation-paths.json",
    "workspace_mode": "document/workspace-mode.json"
  },
  "schema_refs": [
    {
      "schema_id": "schema:character-profile",
      "version": "1"
    }
  ],
  "lineage": null,
  "required_extensions": []
}
```

`head_commit_id` 表示此文档快照对应的提交。它不是远端授权凭证，也不表示打开文件后自动拥有原在线工作区的写权限。

### 3.4 两类主要导出

| 导出类型 | 内容 | 离线含义 |
| --- | --- | --- |
| 引用型导出 | 文档定义、内置数据、允许带出的同步快照、Renderer 与外部引用 | 可使用包内数据；外部实时内容仍受网络和权限限制 |
| 自包含导出 | 在可授权、可获取的范围内，将引用资产复制进包或附带完整快照 | 对已纳入内容提供离线可读能力；不能承诺包含无权导出或未成功获取的资源 |

导出前应列出缺失资源、未解析引用、依赖的扩展和仍需联网的能力。**“一个文件”不自动等于“任何外部依赖都已被打包”。**

默认不导出其他用户的私有历史、访问令牌、外部连接凭据、邀请链接凭据或 AI 提供方密钥。可以保存权限配置模板，但在线授权和凭据需要在目标环境重新建立。

### 3.5 一致性与复制语义

导出应针对一个明确的文档版本创建一致快照。SQLite 等存储需要通过一致性备份或等效机制取得快照，不能直接把正在变化的数据库、日志与文档文件任意拼装。

“备份并恢复同一个 Workspace”与“创建一个新 Workspace”是不同操作。前者保留身份用于受控恢复；后者必须产生新的 `workspace_id`，记录来源，并隔离后续修改。普通文件复制后重新导入时，应明确选择恢复还是派生，不能无提示地让两个可独立编辑的副本争用同一个在线身份。

## 4. 数据源：来源、数据形态与访问模式

### 4.1 三个正交维度

不要将“内部 / 外部”“表格 / 对象”“只读 / 可写”揉成一套互斥类型。

| 维度 | 分类 | 说明 |
| --- | --- | --- |
| 数据所在位置 | 内置、外部引用 | 是否由当前文档包直接持有数据 |
| 数据形态 | Table、单体 Named Object、对象容器、文件 / 目录对象 | 描述数据是什么 |
| 访问与更新方式 | 本地读写、直接访问、同步后本地使用；另附读写能力 | 描述如何取得和修改数据 |

同一个类型可采用不同访问方式。例如成绩表可以内置，也可以引用另一个 Workspace 的发布结果；图片可以引用外部文件，也可以随文档内嵌。

### 4.2 内置数据源

内置源直接由当前 Workspace 管理，适合作为大多数轻中量结构化数据的默认形态。小对象可以保存为 JSON，表格可保存于 SQLite，对象容器可以使用具有索引能力的存储。

“以内部数据为主”是默认工作方式，不应变成容量上限或强制嵌入所有文件的规则。

### 4.3 外部源：直接访问模式

直接访问模式按需访问 URL 或对象定位器，读取外部当前内容。无法连接外部系统时，应显示不可用状态，不能悄悄把旧数据当作实时结果。

实现可以采用传输层缓存，但必须保持清晰的实时读取语义；若允许回退到历史快照，必须有显式策略与界面标记，不能与同步模式混淆。

### 4.4 外部源：手动同步模式

这是讨论中更常用的模式。导入时首先尝试取得一份本地快照，之后正常读取本地版本；只有用户显式同步，才去访问外部位置并更新快照。

该模式的关键语义是：

- 成功同步之后，离线仍可使用最后一次成功取得的版本。
- 同步失败不破坏已有快照，不把已有数据清空。
- 从未成功同步的源没有可用数据，应显示“尚未取得数据”，而不是假装存在本地版本。
- 必须能查看来源、已同步版本、同步时间和最后一次同步结果。

默认将外部同步快照视为**本地只读数据**。用户可由它派生出新的内置可写源；若确实需要向外部写回，则通过独立的写回能力、权限和提交机制实现，不能把“刷新快照”与“双向同步”当成同一功能。

### 4.5 外部源示例

```json
{
  "source_id": "src:confirmed-character-art",
  "name": "已确认角色设定图",
  "data_kind": "file_collection",
  "schema_ref": {
    "schema_id": "schema:character-art-collection",
    "version": "1"
  },
  "origin": {
    "kind": "external",
    "locator": {
      "kind": "workspace_output",
      "workspace_id": "ws:character-concept",
      "output_name": "confirmed-character-art"
    },
    "binding": {
      "kind": "published_channel",
      "channel": "confirmed"
    }
  },
  "access": {
    "read_mode": "manual_sync",
    "requested_capabilities": ["read", "refresh"]
  },
  "snapshot": {
    "source_revision": "revision:art-7",
    "local_ref": "snapshots/src-confirmed-character-art/revision-art-7/index.json"
  }
}
```

`requested_capabilities` 只是文档声明的能力需求。实际允许的能力必须由权威权限层与外部适配器共同确定，不能由修改 JSON 自行获得。

### 4.6 数据源可以写，但不是所有引用都能写

“数据源”不是只读概念。可写的内置表格、目标目录、生成结果集合，都可以接受用户或 AI 的写操作。

建议使用细分能力，例如 `read`、`append`、`update`、`delete`、`refresh`、`publish`。只允许报名者追加一行，与允许他读完整张报名表，是两种不同授权。

写入能否执行，要同时满足 Workspace 权限、源本身权限、外部适配器能力以及当前用户 / Agent 的授权。一个可写源在另一个 Workspace 中可以仅作为只读引用出现。

### 4.7 引用版本策略

建议把“引用什么版本”与“何时向远端读取”分开描述。

| 版本绑定 | 语义 |
| --- | --- |
| `fixed_revision` | 固定到指定版本，适合审计、复现和正式交付 |
| `published_channel` | 指向某个已确认输出通道；只有发布才改变其目标 |
| `live_head` | 指向源的当前共享版本，不包括未提交的私人草稿 |

手动同步源会将解析得到的版本固定成当前本地快照，直到下次同步。外部的已确认版本即使已经更新，也不应在离线或未同步时伪装成本地已更新。

## 5. 数据本体与 Schema

### 5.1 三类结构化数据形态

**Table 是 Named Object 体系内的特化类型，不是与其完全无关的另一套对象系统。** 从使用与优化角度，仍应显式区分三类。

| 形态 | 逻辑结构 | 建议存储 |
| --- | --- | --- |
| Table | 字段定义稳定的二维表；字段有名称、类型与描述 | SQLite 等关系型存储 |
| 单体 Named Object | 一个 Message、一份矢量图、一组配置或一个复杂业务对象 | JSON / 对象存储 |
| 对象容器 | 同构或异构的 Named Object 集合，可带索引与分页 | 带索引的集合存储；可从 SQLite 实现起步 |

理论上可以用命名对象容器统一表示上述形态，但不应以牺牲高效表格查询和存储为代价，强迫所有实现都走同一种通用对象引擎。

### 5.2 Schema 与数据分离

数据源引用 Schema，而不是每份数据都复制一整套结构定义。内核应提供常用 Schema，行业扩展和 AI 生成任务可以提出新的 Schema。

建议规则：同一个已发布的 `schema_id + version` 对应不可变的定义；结构改变产生新版本。AI 的识别和推断可以帮助用户建立 Schema，但运行中的校验不能依赖“AI 大概知道是什么”。

同构集合声明统一成员 Schema；异构集合允许成员分别声明类型，并可由容器声明允许的类型集合或约束。异构不等于没有结构信息。

### 5.3 稳定身份优先于位置

表格的行号、当前排序和显示列序号都是不稳定的。建议至少提供：

| 对象 | 稳定身份 |
| --- | --- |
| 数据源 | `source_id` |
| 表格记录 | `record_id` |
| 字段 | `field_id` |
| 集合成员 | `object_id` |
| 图形内部对象 | 在所属文档对象内稳定的 `object_id` |
| 文件 / 目录项 | 文件对象标识及必要的版本；名称只是可变显示信息 |

评论、标色、命令、AI 建议与共享链接，应尽量通过稳定身份定位。例如成绩疑问应锚定到“成绩源＋学生记录 ID＋科目字段 ID”，而不是“当前表格的第七行第三列”。

命名是用户操作入口，ID 是系统引用依据。数据源改名、Cell 移动或表格排序不应使引用失效。

### 5.4 推荐的对象引用结构

```json
{
  "workspace_id": "ws:course-grades",
  "source_id": "src:grades",
  "revision": "revision:18",
  "selector": {
    "kind": "table_field",
    "record_id": "student:20260017",
    "field_id": "field:mathematics"
  }
}
```

`revision` 是否固定由使用场景决定。正式审核与发布证据应绑定版本；普通实时表格视图可以跟随共享版本。对文本范围、图形对象、文件内页码等，可由对应 Schema 扩展选择器类型。

### 5.5 Schema 演进与数据迁移

重命名字段可以保留 `field_id`；删除字段或改变字段含义不能假装只是展示名称变化。迁移应当可验证，并记录数据版本变化。

迁移后失效的标注、旧 Viewport 锚点和历史引用，需要显示“目标已删除 / 结构已改变”，不能自动移到某个位置相近但语义不同的对象。

对未知 Schema，应保留原始数据，并提供通用对象属性查看器；不能因为缺少某个扩展而丢失其数据。

## 6. Cell、Renderer 与内容展现内核

### 6.1 Cell 的责任

Cell 是 Workspace 中可以被定位、选择、组织、展现和操作的内容单元。它通常引用一个数据源或一个命名对象，也可以声明多个输入绑定。多个 Cell 可以展示同一个源，不要求一份数据只能对应一个 Cell。

Cell 自身需要保存类型、绑定关系和文档级属性。许愿格的提示词与输入依赖就是其持久化内容，可由专用 Named Object 表达。不能把它们仅放在临时组件内存中。

建议区分：

- **Cell 文档定义**：类型、数据绑定、默认 Renderer、文档内位置、父子关系、可持久化配置。
- **Cell 运行状态**：本次加载进度、选中状态、光标、尚未提交的表单输入。
- **Cell 依赖数据**：被它读取、计算、展示或修改的源与对象。

上述三者应有关联，但不相互混装。也不要求为了每个 Cell 都额外创建一个用户可见的数据源；内核可以管理技术性的 Cell 内容对象。

### 6.2 推荐 Cell 结构

```json
{
  "cell_id": "cell:grades-chart",
  "cell_type": "data_view",
  "title": "成绩分布",
  "bindings": {
    "input": {
      "source_id": "src:grades"
    }
  },
  "renderer_ref": {
    "renderer_id": "renderer:grade-distribution",
    "version": "1"
  },
  "renderer_config": {
    "score_field_id": "field:mathematics"
  },
  "layout": {
    "parent_cell_id": null,
    "x": 120,
    "y": 80,
    "width": 640,
    "height": 360
  }
}
```

这是自由画布的一种建议布局结构，不要求流式文档、图层编辑和移动端全部使用相同的坐标布局。布局模式可扩展，但应保持稳定的 Cell 身份与引用。

### 6.3 每种数据都应有可解释的展现路径

Renderer 根据 Schema、媒体类型和上下文声明可处理的内容。对已支持的数据类型，系统应至少有一种展现方法；找不到专用 Renderer 时，回退到对象属性、原始结构或文件元数据视图。

对无法解码的媒体，通用回退能显示元数据与资源入口，并不等于能够播放或预览其内容。应明确区分“数据可保留”与“内容可完整展现”。

同一个 Table 可以显示成表格、统计卡片、图表或定制交互页面。Renderer 配置保存在 Cell 或可共享的展现附加层，不写入 Table 的业务字段。

### 6.4 与系统 Preview 能力的关系

讨论中已经提出，Cell 展现与 Preview 扩展具有共同基础。建议由系统级内容展现内核统一管理 Schema / 媒体类型识别、Renderer 发现、资源访问和生命周期。

Workspace 负责布局、编辑上下文、命令与权限；Preview 场景可以只提供只读上下文。两者复用展现能力，但不能假设一个只读预览组件天然就具有可编辑能力。

### 6.5 粗粒度与细粒度可以共存

| 粒度 | 示例 | 内核可见范围 |
| --- | --- | --- |
| 粗粒度 Cell | 整个流程图作为一个矢量文档 Cell | 内核认识该文档及其扩展提供的内部对象接口 |
| 细粒度 Cell | 每个方块、箭头、文本对象都是 Cell | 内核直接管理这些对象的布局、关系与操作 |
| 混合粒度 | 图形文档作为父 Cell，关键子对象具有稳定引用 | 统一定位父文档，按需深入内部对象 |

不能简单认为只有细粒度 Cell 才能被 AI 理解。粗粒度 Cell 也可以通过 Schema、对象树、选择器和命令接口暴露内部语义。反之，将每个图形都拆成 Cell，也不自动保证其关系与业务含义可理解。

内核应支持可寻址的嵌套对象与可选的 Cell 父子关系，不强迫一个表格里的每个普通数据格都变成独立 Canvas Cell。否则会让布局、权限和协作成本随数据量失控。

### 6.6 扩展不能绕过的数据通道

Renderer 可以负责渲染与交互，但不能私自获得任意源的读写能力。推荐所有数据读取通过受控绑定，所有有效写操作通过 Command Bridge。

Cell 属性面板、图形编辑器、表格编辑器与 AI 生成的 UI，都遵守这一约束。这样 UI 的形态可以变化，而撤销、权限、历史与协作仍然保持一致。

## 7. 边界数据、附加层与个人状态

### 7.1 不是所有 UI 相关数据都一样

建议给边界数据同时标记**所有者、作用范围、可见性、持久化方式**，而不是只设置一个笼统的 `is_ui_state`。

| 类型 | 示例 | 推荐归属 |
| --- | --- | --- |
| Session 临时状态 | 选区、焦点、正在拖动的对象、未提交输入 | 当前用户的当前 Session |
| 用户持久偏好 | 某用户偏好的表格列宽、折叠状态、显示方式 | 用户在该 Workspace 下的个人状态 |
| Workspace 共享展现 | 默认布局、默认列配置、保存的演示视角 | Workspace 文档定义 |
| 可独立共享附加层 | 单元格标色、疑问标注、评论和便签 | 有独立权限的 Overlay |

同一用户多设备、多标签页可以拥有不同 Session；“同一个用户”不等于“只有一份实时选区”。

### 7.2 成绩表标注示例

教师在某个画布中把成绩标成浅黄色，以提示“此分数待核对”，不应因此给共享成绩 Schema 添加一个 `background_color` 字段。

建议建立一个 Overlay，记录目标对象引用、颜色和说明。另一个画布可以只引用成绩源，也可以显式引用该 Overlay。只有选择共享附加层时，才看到相同标注。

如果“待核对”后来成为审核流程必须使用的业务状态，则应将它建模为明确的业务记录或审核对象，而不是永远依赖颜色判断。**是否进入业务数据，取决于业务语义，不取决于界面上是否有颜色。**

### 7.3 Overlay 示例

```json
{
  "overlay_id": "overlay:grade-review",
  "workspace_id": "ws:grade-review",
  "visibility": "workspace_shared",
  "entries": [
    {
      "entry_id": "annotation:17",
      "kind": "highlight",
      "target": {
        "workspace_id": "ws:course-grades",
        "source_id": "src:grades",
        "selector": {
          "kind": "table_field",
          "record_id": "student:20260017",
          "field_id": "field:mathematics"
        }
      },
      "style": {
        "background_color": "#FFF2CC"
      },
      "note": "请核对原始登记记录"
    }
  ]
}
```

源与 Overlay 都需要授权。获得某个成绩源的访问权，不自动意味着可以读取所有教师围绕它建立的私有审核标注。

### 7.4 只读画布、评论与便签

只读表示不能修改核心业务数据，不表示完全没有交互。公共画布可单独开放评论、便签、回复和个人视图状态。

评论线程是可持久化的附加数据，不应只存在于临时 UI 内存中。它可以采用命名对象集合存储，但在逻辑上属于评论 / 协作附加层，不混入所评论的数据源。

评论建议包含线程 ID、目标引用、作者、正文、回复关系、可见性和必要的审核状态。评论目标失效时应保留可解释的历史锚点，不能把评论移动到别人的记录上。

这里的“副本层”主要表示逻辑上的附加层或个人工作状态，**不要求为了每个 Guest 复制整份业务数据。**

### 7.5 匿名但相对持久的 Guest 身份

公共链接可以允许未登录访问者参与指定交互。建议区分三个概念：

1. 本地保存的匿名身份凭据，用于在同一设备上保持连续性。
2. 当前浏览产生的 Session，用于实时状态和操作上下文。
3. 公共链接或授权服务授予的能力，用于决定能否评论、回复或提交。

再次访问时可以恢复相同的匿名参与身份与个人状态，但不必复用永不过期的技术 Session。清除本地存储、换设备、凭据到期或使用隐私浏览，都可能中断这种连续性；匿名身份本身不等于可验证的现实身份。

建议默认将匿名身份限定在必要的 Workspace 或组织作用域，避免无必要的跨公共画布追踪。允许匿名写入的入口需要最基本的频率限制、内容治理与撤销 / 屏蔽能力。

## 8. Command、Session 与协作提交

### 8.1 一个修改入口，两种主要历史

**设计原则：人、AI 和扩展对数据与文档产生的有效修改，都进入统一 Command 执行机制。** 但不要求每次鼠标移动和光标闪烁都进入持久化历史。

建议分为：

| 层次 | 内容 | 用途 |
| --- | --- | --- |
| 本地 Session Command History | 细粒度编辑、输入中间态、局部撤销 / 重做 | 保持用户自己的操作连续性 |
| Shared Commit History | 经权限、Schema 和版本检查后对共享状态生效的变更 | 协作同步、正式变更追踪 |
| Publication / Audit 记录 | 发布、审核、权限变更等重要事件 | 下游依赖、业务追溯和安全审计 |

第三类可以建立在共享提交之上，不必成为另一套独立编辑引擎。

### 8.2 本地编辑不等于立即对外提交

用户 B 对一个单元格连续修改四次，这四次可以全部存在于 B 的本地历史，支持撤销与重做。其他用户 A 默认只应看到允许共享的有效结果。

在私有草稿模式下，不能先把四次输入广播给 A，再通过 UI 隐藏前三次。过滤必须发生在进入共享数据通道之前，否则无法满足中间态隐私要求。

同样，B 的细粒度历史不能因为导出共享日志、保存调试快照或将完整 Session 发给某个 AI 任务，而无意泄露。

### 8.3 三个容易混淆的动作

| 动作 | 语义 |
| --- | --- |
| 保存草稿 | 持久化自己的未提交输入与本地历史，不自动让其他人可见 |
| 提交共享变更 | 将一个有效变更集提交到 Workspace 的共享版本 |
| 发布结果 | 将某个已确认版本暴露给指定的下游输出通道 |

UI 可以把第二步命名为“保存”，但系统内部必须保留这三个概念。自动保存不得悄悄等同于对所有协作者发布。

### 8.4 与“默认实时同步”的兼容

建议采用以下基线：

**已经提交的共享变更实时分发；尚未提交的个人中间态是否同步，由 Cell / 数据类型 / 工作模式的策略决定。**

例如拖动公共画布中的已共享对象，可以启用即时提交或合并后的连续提交；敏感表单、长文本草稿和正式申报，适合显式提交。用户的选区与实时 Viewport 走单独的 Presence 通道，不因参与协作就被写入共享业务数据。

不能以“实时协作”为名，统一广播所有 Session 的所有命令；也不能为了私有草稿，把本应实时分发的已提交变化全部延迟到整个文档关闭。

### 8.5 命令与提交的建议字段

`LocalCommand` 至少应能表达操作目标、操作参数、本地顺序、所属 Session，以及本地撤销所需的信息。具体格式可以由命令类型实现。

共享提交需要一个更稳定的外部协议，例如：

```json
{
  "commit_id": "commit:grades-19",
  "workspace_id": "ws:course-grades",
  "author": {
    "principal_id": "user:teacher-b",
    "actor_kind": "human"
  },
  "session_id": "session:b-desktop-1",
  "base_revisions": {
    "src:grades": "revision:18"
  },
  "idempotency_key": "submission:grades-change-19",
  "operations": [
    {
      "operation": "set_field",
      "target": {
        "source_id": "src:grades",
        "record_id": "student:20260017",
        "field_id": "field:mathematics"
      },
      "expected_value": 85,
      "value": 88
    }
  ],
  "message": "更正数学成绩"
}
```

作者和权限不能只相信客户端字段。共享提交中的作者身份、接收时间和有效授权，需要由可信执行边界验证并记录。对导入的历史，可保存原始作者声明，但未验证的声明不能冒充当前环境的已认证操作。

### 8.6 提交流程

```text
UI / Agent / 扩展产生操作
    → 在当前用户允许访问的工作状态上形成 LocalCommand
    → 建立或更新本地草稿
    → 按策略形成候选变更集
    → 检查用户、目标数据源与具体操作权限
    → 检查 Schema、业务约束与基准版本
    → 原子提交到权威共享状态
    → 同步数据变更与对应历史
    → 通知 Cell、索引与订阅者刷新
```

对于一次批量补全学生名单，应支持命令组 / 事务，让用户能够把“一次接受 AI 补全”当作一个可理解的撤销动作，而不是被迫撤销几十条插入。

### 8.7 撤销与重做

未共享的本地操作，可以直接使用本地逆操作或快照回退。

已共享的操作不应通过删除公共历史来撤销。建议生成新的补偿提交，并验证它仍然适用。例如 A 把分数从 80 改成 85，随后 B 改成 90，A 再撤销时，不能不加判断地把当前值覆盖回 80。

共享撤销默认针对用户自己的操作或有授权的变更；撤销整批 AI 操作也需要检查这批对象是否已被其他人继续修改。存在冲突时，展示可撤销部分、冲突部分与处理选项，而不是静默覆盖。

外部文件删除、远程发布等不一定具有可用的逆操作。命令应声明可撤销性；不可逆或跨系统补偿动作需显式提示，不能承诺所有操作都能无损 Undo。

### 8.8 冲突：设计目标与现实边界

口述中提出“尽量让冲突留在 UI 层，核心数据不冲突”，应作为减小共享面和优化数据模型的目标，**不能作为实现中忽略数据冲突的前提**。

A 与 B 同时修改同一个共享成绩字段，确实会产生核心数据竞争。UI 状态隔离、私有草稿和提交过滤能减少冲突，却不能消除这种情况。

建议初始实现采用明确、可解释的乐观并发控制：

| 情况 | 建议策略 |
| --- | --- |
| 不同用户的选区、焦点 | 各自保存，不合并成一个全局值 |
| 不同记录或独立属性的修改 | 在约束允许时自动合并 |
| 同一字段基于同一旧值的竞争修改 | 显式报告冲突，交由用户或业务策略选择 |
| 删除对象与修改该对象同时发生 | 报告目标冲突，保留可恢复的待处理操作 |
| 唯一性、名额、余额等跨记录约束 | 在权威执行边界检查，不能只依赖字段级合并 |
| 富文本 / 特定图形的高频协作 | 可由类型扩展引入专用合并算法，但要接入统一提交协议 |

是否对特定数据类型引入 CRDT 等机制，属于实现选型。不能认为一个通用算法会自动解决所有业务约束和共享撤销问题。

### 8.9 离线与重新连接

离线期间继续记录本地 Command 和基准版本；需要共享的操作进入待提交队列。重连后先获取共享变化，再验证 / 合并待提交操作。

重复发送通过幂等键避免重复生效。删除、权限变化或外部源失效，应形成明确的失败状态。不能把离线产生的本地权利当成重连后仍有效的授权。

### 8.10 数据、日志与外部资产的一致性

本地结构化数据与其有效提交记录，应通过同一事务或等效的提交日志机制保持一致。不能出现“数据修改成功，但历史不存在”或“历史宣称成功，但数据未生效”。

多人在线时，不能把多个用户同时写入的 SQLite 文件直接当作普通文件做双向同步。建议由命令 / 提交层协调共享修改，再由存储适配器落盘。

对于外部文件和远程系统，不能假设存在跨系统原子事务。建议先暂存资产并取得可验证引用，再提交文档引用或发布指针；失败时保留可识别的待处理状态，清理未引用暂存产物。跨多个独立 Workspace 的修改同样不默认具有原子性。

## 9. 权限、数据可见性与信任边界

### 9.1 权限不是 UI 效果

画布可以配置权限，并据此改变可见 UI，但授权判断必须在数据访问与命令执行边界生效。

**隐藏一个 Cell、关闭属性面板、设置只读组件、只显示一个表单，都不能单独构成数据安全边界。** 没有权限的数据，不应已经被完整发送给访问者后再靠前端隐藏。

建议以操作能力为中心授权，并将文档访问、业务数据读写、附加层操作、发布、审核、跟随视角分别检查。

### 9.2 权限分层

| 层级 | 示例 |
| --- | --- |
| Workspace | 能否打开、管理、派生、导出 |
| 数据源 | 能否读、追加、修改、删除或刷新 |
| 记录 / 对象 / 字段 | 能否访问某个报名记录、学生成绩或受限材料 |
| Overlay | 能否查看教师标注、发表评论、回复或审核评论 |
| 业务操作 | 能否提交审核、确认报名、发布角色设定图 |
| Presence / Viewport | 能否广播自己的位置、跟随他人或在管理场景查看其视角 |
| AI 与外部服务 | 可把哪些数据发给哪个执行环境；任务可做哪些操作 |

实际有效能力是这些约束与外部源授权共同作用后的结果。Cell 不能因为存在一个“修改”按钮而提升权限。

### 9.3 跨 Workspace 引用不传递隐含授权

能够打开画布 B，不自动意味着可以打开它引用的画布 A 的全部数据。B 应当只暴露按授权可提供的源、快照或发布结果。

引用 Overlay、Renderer 资源和外部文件也遵守相同原则。资源名称、对象 ID、内容哈希或一个可解析路径，都不等于访问授权。

### 9.4 公共展示的投影视图

公共链接建议返回按访问者能力构造的文档投影：允许的 Cell、必要的数据切片、可用交互与公开附加层。

对共享报名表场景，普通报名者可以拥有“提交一条报名”的能力，但没有“读取报名集合”的能力。接口应直接支持这种差异，不应要求客户端先下载完整表格再新增一行。

### 9.5 AI 与扩展的信任边界

AI 获取的上下文只应来自当前授权范围。数据源中的文字、外部文件或评论都是待处理内容，不能自行提升权限、改变系统规则或要求工具越过授权边界。

AI 任务应带有发起人、委托能力范围与执行身份。生成计划需要经过确定性的权限、Schema 与业务校验；“模型认为允许”不构成授权。

## 10. AI 生成：许愿格、数据计算与定制 UI

### 10.1 两种基本产出，不是两套独立系统

AI 生成的主要结果可以分解为：

| 结果 | 语义 |
| --- | --- |
| 数据计算 / 生成 | 根据已有源或素材，得到新的数据、文件或对象集合 |
| 展现选择 / 生成 | 为已有或刚生成的数据选择 Renderer，或创造场景专用 Renderer |

一个任务可以同时包含两种结果。例如先从成绩表计算分布数据，再生成一个专用图表 Cell。若只是换一种方式展现原表，不应为了实现图表而无意义地复制原始数据源。

### 10.2 许愿格也是一个有 Schema 的内容对象

“UI Generate / 许愿格”不是独立于文档体系的神秘入口。它应有明确的数据定义，至少包括提示词、已确认的数据依赖、目标或输出位置及必要的执行配置。

其默认 Renderer 提供提示词编辑、依赖列表、生成按钮和结果状态。具有相应写入 / 执行权限的用户才能发起生成。

建议将任务运行进度与持久化的许愿内容分开：提示词和依赖属于文档；临时 Token 流、加载状态属于运行态；已完成任务可保存简化执行记录与产物来源。

### 10.3 先解析数据依赖，再生成

用户自然语言中会描述“用哪些数据做什么”。系统第一步应识别候选数据源，并在提示词下方明确列出。

推荐流程：

```text
输入 / 修改提示词
    → 查找当前授权范围内可用的数据源与名称
    → AI 识别候选依赖
    → 展示已识别源、歧义、缺失项与版本状态
    → 用户调整提示词并重新识别
    → 确认依赖绑定
    → 执行生成
```

用户通过调整提示词纠正依赖，是讨论中已明确的交互。可以进一步提供显式选择数据源的辅助 UI，但这是实现增强，不应变成隐藏的自动替换。

未解决的同名源、无权限源和缺失源，不得被 AI 静默猜测。数据选错会使后续计算与展现失去意义，因此依赖确认应成为执行前的独立步骤。

### 10.4 用户可感知源与技术性对象

数据源注册表可以包含用户命名的业务数据、AI 生成结果，以及内核管理的技术性对象。默认的数据选择器应优先展现用户有感知的业务源与产物，不把所有内部存储节点都暴露成同等重要的“数据”。

内部引用仍必须可追踪。隐藏技术细节不等于依赖关系可以不可解释。

### 10.5 统一的 AI 执行入口

Agent 可以由系统按任务特点选择通用能力或定制工具，但操作 Workspace 的 Skills 应以统一命令能力为基础。

建议提供的能力类别包括：发现和读取授权数据、创建数据源、变换数据、创建 Cell、绑定 Renderer、创建 Renderer 资源、添加标注、生成候选变更集，以及请求提交或发布。

“Agent 像人一样操作”指两者遵守相同的语义、权限与历史规则，不要求 Agent 模拟鼠标点击。结构化命令比屏幕坐标更适合确定性执行。

### 10.6 推荐执行协议

```text
冻结本次输入引用与版本
    → 建立最小必要上下文
    → Agent 生成计划 / 产物
    → 在暂存区生成数据、文件或 Renderer
    → 校验 Schema、资源权限、Renderer 能力与业务约束
    → 形成可审阅的变更集
    → 根据用户已授予的执行策略确认 / 应用
    → 通过统一 Command 提交
    → 保存输入版本、产物与本次有效变更的关联
```

对已由用户明确发起、范围清楚的“生成新图表”，可以在预先授权范围内自动应用结果；覆盖重要数据、对外发布或调用高影响外部操作，不能仅因为用户点击过一次“生成”就获得无限授权。

生成失败不应留下看似成功的半份正式结果。保留的中间产物应有明确的临时状态和清理策略。

### 10.7 Code Agent 可以生成一次性 Renderer

内核可以内置常用表格、图表和对象视图，但不追求穷举所有图表分类与配置项。Code Agent 可以为当前数据和任务生成仅在当前 Workspace 使用的 Renderer，HTML 资源包是一个可验证的候选实现。

例如用户要查看某个班级中特定分数段、某类异常记录及其说明，可以生成专门对应这些业务概念的视图和控制参数，而不是要求用户先把需求翻译成某种通用图表参数。

这些参数应有可描述的配置结构，并归入 Renderer 配置 / Cell 属性。生成 UI 的业务参数与原始业务数据仍保持分离。

### 10.8 生成 UI 的执行边界

生成代码应视为不可信扩展，而不是系统内核代码。建议采用隔离执行环境，例如独立沙箱框架中的 HTML 组件，并配套受控消息桥。

最小安全约束包括：默认没有任意网络访问、宿主 DOM、宿主存储或系统凭据权限；只读取声明且获授权的数据绑定；写入必须经 Command Bridge；资源请求经过授权代理；限制执行资源与持续占用；导入未知 Renderer 不自动授予其额外能力。

不能仅凭“放进 iframe”就认为安全隔离已经完成。沙箱标志、来源隔离、内容安全策略、消息来源验证和数据桥能力，都需要在实现时一起验证。

生成的 Renderer 及其所需本地资源应能随文档导出。在扩展缺失或被禁用时，仍能保留数据，并回退到可解释的通用视图。

### 10.9 生成结果的可追溯性

建议记录输入源及版本、提示词版本、执行工具 / 配置标识、生成产物、提交与执行状态。涉及敏感草稿或完整模型上下文时，应单独控制记录范围与可见性，不默认将完整会话公开。

只保存提示词、不保存实际使用的数据版本，无法解释后来为什么得到不同结果。因此正式生成或发布应尽量保留可定位的输入版本。

## 11. 心流模式与 Workspace 工作环境

### 11.1 从主动召唤到低干扰陪伴

**设计原则：心流 Agent 是可选功能，不默认强制启用。** 用户继续用语音、手写、键盘或直接操作进行原始记录；Agent 在合适时机给出建议，不要求用户先把输入改写成提示词。

可以观察的上下文包括当前选区、正在编辑的对象、用户自己的操作记录、输入内容与停顿。观察范围取决于用户选择的工作模式和已授予的数据权限。

### 11.2 建议区与正式文档隔离

```text
用户继续编辑
    → 心流 Agent 获取允许的上下文
    → 形成候选建议
    → 显示在独立建议区
    → 用户忽略：不改变正式文档
    → 用户接受：校验建议仍适用，转成 Command 执行
```

建议既可以是可阅读的信息，也可以是可执行的补全计划。两者不应使用同一种“默认立即改写”机制。

例如用户停顿在“去年某品类销售额”处，建议区可显示从授权资料中找到的数值及来源，用户可自行输入；在表格中输入两名学生后，Agent 可建议补全名单，用户接受后再进行批量插入。

### 11.3 建议应绑定上下文版本

一个补全建议生成后，用户可能已经修改了表格。接受建议时应重新验证目标、数据版本和权限，防止把旧上下文中的补全计划写入已变化的内容。

建议至少应具有目标、生成时的基准版本、说明、必要来源和可执行操作。用户接受后产生新的有效命令；“建议已经显示”不等于用户已经授权修改。

### 11.4 UI 与主动程度

移动端可以验证“约三分之二编辑区＋三分之一建议区”的布局，轻提示可使用低对比度文字；这些是体验方向，不是写死的数据格式。

主动程度可按 Workspace 模式配置，例如仅在停顿时检索、只提供相关资料、允许结构化补全建议，或更积极地提出下一步操作。应有频率、资源和上下文范围约束，避免每一次按键都触发昂贵或干扰性执行。

关闭心流模式应停止后续观察与任务触发，并处理正在运行的任务，不让用户关闭界面后仍持续发送草稿上下文。

### 11.5 私有草稿的 AI 处理边界

心流需要读到用户自己的未提交输入，但这不代表这些输入可以被其他协作者、其他用户的 Agent 或任何云端模型读取。

建议在启用时明确执行环境与数据范围：只在本地处理、允许指定远程能力处理，或不允许处理某类敏感源。该策略与协作同步策略独立；未共享给协作者的数据，同样可能因为调用外部 AI 而离开设备，必须单独控制。

### 11.6 Workspace Mode

Workspace 不只是装内容，也可以声明工作模式：布局、辅助工具、属性面板、默认输入方式、心流开关、演示模式等。

建议将这些声明保存为可移植配置，由系统 UI 宿主按能力与用户偏好应用。它不是任意改变全局系统设置的脚本；离开 Workspace 时应能恢复原环境，不应因打开外部画布而无提示地启用监测或关闭其他安全设置。

## 12. Viewport：实时跟随与演示路径

### 12.1 定义

Viewport 表示用户此刻在 Canvas 中看到的区域、缩放、聚焦对象和可选展示过滤。它可以表达当前关注视角，但不是对用户真实“思考内容”的判断。

Viewport 是核心协作能力，同时具有实时与持久化两种形态。

| 形态 | 归属 | 用途 |
| --- | --- | --- |
| 实时 `ViewportState` | 用户 / Session 的 Presence 状态 | 跟随讲解、共同浏览、授权管理查看 |
| 保存的 `SavedViewport` | Workspace 文档 | 固定视角、演示片段、讲解路径 |

### 12.2 Follow 模式

用户 A 浏览画布或讲解已有内容，其他协作者与有权限的 Guest 可以主动跟随其 Viewport。A 不需要持续编辑，移动视角并配合语音会议即可组织讲解。

跟随应同步视角所需的最小状态，而不是共享 A 的全部 Session。私有输入、未提交命令、个人标注和其他不属于广播范围的状态，不能因为 Follow 自动公开。

跟随者的屏幕尺寸可能不同，建议通过目标内容边界、锚定 Cell 或关注区域计算合适视图，不仅机械复制发送端的像素尺寸。退出 Follow 后应能回到自己的浏览状态。

### 12.3 保存视角与 Slide Show

用户可以保存当前视角，并指定只显示选中的 Cell，临时隐藏其他内容。若保存一组有顺序的 Viewport，就可以形成演示路径，也可支持跳转到任意保存的视角。

保存视角不复制底层内容。Cell 更新可以在动态演示中反映出来；需要稳定复现时，应把演示绑定到某个文档版本或发布快照。

示例：

```json
{
  "viewport_id": "viewport:overview",
  "title": "总体方案",
  "camera": {
    "focus_bounds": {
      "x": 100,
      "y": 50,
      "width": 1200,
      "height": 675
    },
    "fit": "contain"
  },
  "focus_cell_ids": ["cell:overview", "cell:key-data"],
  "visibility": {
    "mode": "include_only",
    "cell_ids": ["cell:overview", "cell:key-data"]
  },
  "document_binding": {
    "kind": "live_head"
  }
}
```

`visibility` 是演示过滤，不是访问控制。一个有完整文档读取权限的人，不能仅因为演示隐藏了某些 Cell 就被认为无权访问它们。公共演示仍须在数据层提供相应投影。

### 12.4 管理查看与介入

讨论中提出，管理员可以切到某个成员的当前 Viewport 查看工作状态。建议将其建模为独立授权能力，而不是“管理员可以任意读取所有私人 Session”。

管理查看应有明确的适用场景、可见范围、参与者可感知的状态和必要审计。切到对方视角查看，不等于远程接管对方输入，也不自动包含未共享草稿。

所谓“强制介入”需要在实现中进一步区分：查看视角、要求成员进入共同演示、改变共享对象，分别是不同权限；不能用一个笼统开关把它们混在一起。

### 12.5 实时状态不应使历史膨胀

Viewport 移动、缩放和 Presence 更新可以节流、覆盖和过期，不需要默认把每个位置都永久记入 Command History。保存视角、编辑演示路径则是持久化文档操作，需要进入有效历史。

## 13. 文件、AIGC 资产与跨画布发布

### 13.1 文件和目录也是数据源

结构化数据之外，文件、图片、视频、目录、网络目录都应通过 Named Object 与数据源描述体系被引用。文件和目录对象可以包含结构化元数据，但其媒体正文不必被转成 JSON。

大文件、目录和 AIGC 产物通常更适合保存于外部文件系统或对象系统。小型资产也可以内嵌；不能把“非结构化”绝对等同于“必须外部”。

### 13.2 用户看到业务名称，底层保存稳定引用

用户可以通过“画布名称 / 数据源名称”找到资产，不必手工寻找复杂目录或用文件名猜测版本。系统可以自动分配名称，但名称必须能展示、修改和消歧。

底层引用仍使用稳定的 Workspace ID、Source ID、对象身份和版本。画布改名或源改名不应导致下游断链。

### 13.3 当前工作源与已确认输出源

角色设定与建模示例应直接成为原型验证场景：

```text
角色设定 Workspace
  当前角色设定源
    ├─ 日常生成
    ├─ 多次修改
    └─ 候选结果
          ↓ 用户明确提交 / 发布
  已确认角色设定输出通道 → 某个确定的资产版本
          ↓ 下游按授权引用 / 同步
建模 Workspace
  只依赖“已确认角色设定”，不读取对方的全部草稿
```

已确认输出不必通过复制整份文件实现。可以建立一个有版本的发布记录，让输出通道指向确定的资产或集合快照。

### 13.4 发布应固定一组一致结果

如果一次确认涉及多张设定图、说明与材质参考，应发布一个包含完整对象引用的集合版本，避免下游读取到“半组新图＋半组旧图”。

发布流程建议为：完成产物写入与校验 → 建立不可变集合快照 → 检查发布权限 → 更新输出通道指针 → 通知订阅者。

下游采用手动同步时，只会知道或看到有新版本可用，不应擅自替换它正在使用的本地版本。下游采用直接读取发布通道时，才按策略读取新的已确认版本。

### 13.5 内容共享与去重

讨论希望复制画布后，已有媒体引用不产生重复占用。建议将大资产视为可共享的不可变对象，新画布只保存引用，修改产生新版本。

**能否实现物理层去重，需要与 BuckyOS 的真实对象 / 文件系统能力核实。** 若底层提供内容寻址或等效去重，相同内容可以复用同一物理对象；若没有，仅在文档里写了一个对象 ID 并不能保证磁盘已经去重。

不在本文中把口述中的底层名称推断为某个具体数据库或文件系统实现。后续必须对接真实的对象标识、版本、权限、写入与回收接口。

### 13.6 去重的边界

引用同一个既有资产，通常不需要重复复制其正文；但每次生成内容不同的图片、视频、临时产物仍然需要存储。打包为多个独立的自包含导出文件，也可能重复携带相同资产。

因此目标应是“避免无意义的重复拷贝”，不是承诺任意 AIGC 工作流都不增加存储量。

### 13.7 回收与保留

删除某个 Cell 或某个 Workspace，不应直接删除其他画布仍引用的媒体对象。建议通过可达引用或等效机制管理回收，并覆盖：当前文档、历史保留版本、已确认发布、模板实例和正在执行的 AI 任务。

临时文件可以配置清理策略，但已经发布、被其他 Workspace 引用或被用户标记保留的结果，不能被当作本地临时产物误删。

## 14. 模板、实例、Fork 与跨实例汇总

### 14.1 任何 Workspace 都可以成为模板来源

**设计原则：从现有画布保留核心内容与结构、清除不应继承的编辑状态，创建新的画布，本质上就是一次 Fork。** 模板不必是一套独立于普通文档的格式。

同时允许显式保存为模板，定义初始化参数、必填项、材料要求和实例化完成条件。未完成这些条件的实例可以保存为草稿，但不能进入后续要求“已完成初始化”的流程。

建议区分普通 Fork 与业务模板实例：二者都保留来源关系，但只有经模板实例化入口创建并完成相应注册的实例，才自动进入该业务的汇总范围。复制一个文件，不应凭空变成一份已提交报名。

### 14.2 Fork 时保留什么、重置什么

| 内容 | 建议默认行为 |
| --- | --- |
| Workspace ID | 生成新身份，保存来源 Workspace 与来源版本 |
| Cell、布局、Renderer、保存的 Viewport | 保留，并重映射内部身份与引用 |
| 内置可变业务数据 | 创建独立可写分支 / 副本；后续修改不能意外写回模板 |
| 不可变文件资产 | 保留共享引用；修改形成新版本 |
| 外部数据源 | 保留来源与读取策略，重新校验可访问性；不复制凭据或隐含授权 |
| 模板说明、初始化规则 | 保留 |
| 用户选区、焦点、输入中间态、Session | 清除 |
| 私人 Command History、私人标注 | 默认不继承 |
| 共享标注和评论 | 按模板用途显式选择；不默认把业务审核历史当作新实例内容 |
| 审核、确认、发布等业务状态 | 按实例化规则重置，不能继承“已通过”结论 |
| 在线成员授权、匿名链接、外部密钥 | 不直接复制；按目标环境重新建立 |

这里清除的是个性化与过程性编辑状态，不是把布局、属性面板配置和演示路径全部删除。否则模板将失去可复用的工作环境。

### 14.3 来源关系必须有稳定身份与版本

建议在实例 Manifest 中保存：

```json
{
  "lineage": {
    "kind": "template_instance",
    "template_workspace_id": "ws:application-template",
    "template_revision": "commit:template-5",
    "parent_workspace_id": "ws:application-template",
    "created_at": "2026-09-22T09:00:00+08:00",
    "instance_purpose": "application"
  }
}
```

这里的时间仅为格式示例。真实记录应由可信创建流程确定，并明确采用创建、提交还是确认时间作为后续查询口径。

实例固定到创建时的模板版本。模板后续更新不应静默改变已经提交或已确认实例的结构。需要迁移时，执行显式迁移并记录结果。

### 14.4 TemplateSpec 的职责

模板规则建议包括：初始化字段及默认值、必填参数、允许的材料类型、数据校验、初始业务状态、可执行的业务动作，以及供汇总使用的输出定义。

其中，“允许创建实例”“允许填表”“允许确认结果”不是同一种权限。模板内可以保存角色与流程配置，但具体主体绑定仍需要权威授权层执行。

AI 可以帮助检查材料完整性和内容是否符合要求。用户自己的 AI 能力与 Workspace 提供的统一 AI 能力均可支持这种工作方式，但调用身份、数据传输范围和资源承担主体需要明确，不能把一个共享密钥直接放进模板文件。

### 14.5 路线 A：独立实例承载复杂报名

每次报名创建独立 Workspace Instance。报名者在实例中填写结构化数据、上传材料、进行 AI 自查；审核员在授权范围内审核，并通过正式操作改变状态。

推荐的基础状态关系为：

```text
草稿 / 初始化未完成
    → 待确认（提交一个明确版本）
    → 已确认（审核通过该版本）
    ↘ 退回修改 → 新草稿 → 重新提交
```

业务状态属于可校验的业务记录，不是某个 Cell 的临时显示文字。谁能确认、确认哪一版、确认依据是什么，需要能够追溯。

这种模式适合材料较多、填写过程较长、对象结构不统一或需要独立工作环境的场景。它以单个 Workspace 为主要访问控制边界，但仍需要正确的权限默认值；不能因为创建了独立实例，就宣称天然不会泄露数据。

### 14.6 已确认状态必须绑定被确认的版本

仅记录 `status = confirmed` 不够。假设审核员确认后，报名者又修改材料，汇总不能直接读取其最新工作内容并继续当作已审核。

建议保存 `confirmed_revision`，并让汇总读取该版本。确认后的新编辑形成新的草稿或触发重新审核；旧的已确认版本是否继续有效，由业务规则明确。

相应地，撤回、取消确认和重新确认，都应通过授权操作表达，不能靠修改一个 UI 标签完成。

### 14.7 跨实例发现与查询

系统必须能在**明确的业务注册范围和授权范围内**，按模板与时间区间获取实例，并按业务状态筛选。

建议支持以下查询字段：

| 条件 | 作用 |
| --- | --- |
| `template_workspace_id` | 查找源于某模板的实例 |
| `template_revision` | 限定模板版本，或明确跨版本汇总 |
| `time_field` 与时间区间 | 明确按创建、提交或确认时间筛选 |
| `business_state` | 例如只取当前有效的已确认实例 |
| 业务作用域 | 某组织、项目、批次或已注册活动 |

查询结果至少包含实例 ID、模板版本、可访问位置、业务状态、确认版本和必要的覆盖范围信息。需要汇总的字段可由模板声明一个标准输出，而不要求汇总器理解每一个 Cell 的界面结构。

### 14.8 实例注册表与文件化并不冲突

建议采用可重建的实例注册 / 索引机制。局部单机范围可以索引已知文件；组织范围可以由在线服务接收实例创建、提交和状态变化事件。

文档仍然持有自己的来源与业务记录，注册表负责发现与检索，不成为唯一持有文档语义的后台系统。普通私人 Fork 也不应在用户不知情的情况下被加入某个全局业务目录。

不能只靠“当前设备扫到的文件”声称已找到某模板的所有实例。离线、权限不足或索引未同步时，结果必须说明仅覆盖当前已发现且可访问的实例。

索引记录可能滞后。生成正式汇总前，应校验对应实例的有效确认状态与确认版本，或在一个明确版本集合上生成汇总快照。

### 14.9 汇总结果本身也是数据源

```text
模板与时间条件
    → 查询已注册实例
    → 权限与状态校验
    → 固定本次使用的确认版本集合
    → 提取模板声明的输出
    → 校验 / 归一化 Schema
    → 生成汇总 Table 或对象集合
    → 用普通 Cell 展现和分析
```

汇总数据应保留输入实例 ID 与版本关联，以及查询时间口径、覆盖范围和失败项。这样后续才能解释某条记录来自哪里，以及为什么与上次汇总不同。

跨模板版本汇总需要显式字段映射或迁移规则。重复报名是否允许、以哪次确认结果为准，属于业务约束，不能仅靠按姓名去重。

### 14.10 路线 B：共享数据源＋受限表单录入

对于相对简单的业务，一个 Workspace 内保存报名集合，再提供受限的表单 Cell。报名者填写后，经校验追加一条记录即可，不需要创建独立 Workspace 再汇总。

这里“一个画布包含所有报名数据”描述的是逻辑数据归属，**不意味着访问者的客户端必须收到所有报名数据**。

安全实现应只向报名者提供表单定义、必要公开数据及其被允许查看的记录；提交端点在权威边界执行字段白名单、业务校验、追加授权和幂等控制。

报名者对其他 Cell 没有编辑权，也可能没有读取权。二者不能混淆。

### 14.11 两条路线的取舍

| 维度 | 模板＋独立实例 | 共享数据源＋受限录入 |
| --- | --- | --- |
| 工作单元 | 一次报名 / 一个任务是一份 Workspace | 一次报名是一条或一组记录 |
| 复杂材料与长流程 | 容易保留独立内容和过程 | 需要在共享模型里增加结构与规则 |
| 数据汇总 | 需要发现实例、选择版本与聚合 | 数据天然集中，查询较直接 |
| 主要权限边界 | Workspace，再叠加源与对象权限 | 数据源、记录与字段级权限 |
| 风险重点 | 实例分享配置、错误注册、错误确认、汇总覆盖 | 误开放整表读取、越权修改、前端隐藏代替授权 |
| 适用选择 | 需要独立工作环境、材料多、流程长 | 数据结构较稳定、录入过程较短 |

两种方式都应成为内核支持的组合模式。前者不是绝对安全，后者也不是必然不安全；区别在于安全边界与实现复杂度分布不同。机构可以据业务选择，而不是被迫只用“共享 Excel＋表单界面”的一种路线。

## 15. 行业软件扩展模型

### 15.1 用扩展构建工具，而不是另造内核

扩展一个领域生产力软件，至少可以提供：

| 扩展点 | 作用 |
| --- | --- |
| Schema | 定义领域对象、集合与业务结构 |
| Cell 类型 | 定义该领域的内容单元及其绑定要求 |
| Renderer / 编辑器 | 提供对象展现与交互 |
| 属性面板 | 让对象参数可编辑，参数语义由领域决定 |
| Command / 校验器 | 表达可追踪、可授权的领域修改 |
| Workspace Mode | 配置布局、辅助工具、操作环境和心流策略 |
| AI Skills | 让 Agent 使用该领域的读取、计算、生成与编辑能力 |

扩展可以只使用其中一部分。例如一个自定义统计视图可能只需要 Renderer 与配置 Schema；一个轻量设计环境则需要对象模型、编辑器、图层关系和一组命令。

### 15.2 内核不变，编辑体验可变

流式文档、二维画布、图层编辑、时间线式组合可以具有不同的 UI，但仍共享对象身份、数据源引用、命令历史、权限、发布和文件格式。

时间线、图层和几何关系可以由领域 Schema 表达，不要求立即加入内核所有数据类型。内核必须提供足以让扩展解释、寻址与操作这些对象的机制。

### 15.3 对扩展的最低契约

扩展需要声明可处理的 Schema / 版本、所需能力、读取与写入目标、命令及其校验方式、可撤销性和缺失时的回退方式。

不能只注册一个任意 UI，然后把真实数据写进内核不可见的私有目录。扩展持有的数据必须进入正式数据源或明确的扩展资源区，并随文档保存、迁移与权限管理。

同样，不能在保存时只留下渲染后的图片，丢掉可编辑的对象结构，除非用户明确执行的是扁平化导出。

### 15.4 检验扩展能力的三个代表场景

建议用以下三个不同粒度场景检验内核，而不是只做一个通用表格 Demo：

1. 流式记录与表格分析：验证数据绑定、个人状态、心流提示和生成图表。
2. 流程图 / 轻量图层设计：验证嵌套对象、关系、属性面板、命令与 Viewport。
3. AIGC 资产组合与发布：验证文件 / 目录源、当前与已确认版本、跨画布引用和模板流程。

通过这些场景，再判断是否需要把某个能力提升到内核。不要为了假想的所有行业需求，先向核心 Schema 添加大量专用字段。

## 16. 建议的内核模块与调用契约

### 16.1 逻辑模块

以下均是逻辑职责，可以先在一个本地进程内实现。

| 模块 | 核心职责 |
| --- | --- |
| Document Store | 打开、保存、导出、版本快照与 Fork |
| Schema Registry | Schema 注册、固定版本、校验与迁移 |
| Source Registry / Resolver | 数据源目录、命名解析、引用解析与能力查询 |
| Storage / Asset Adapters | Table、对象、集合、文件、目录与外部快照的实际读写 |
| Command Engine | 校验、事务、撤销、重做、共享提交与版本冲突 |
| Session / Overlay Manager | 私有状态、个人历史、标注与评论层 |
| Permission Gate | 权威访问控制与操作能力裁剪 |
| Renderer Host | Renderer 注册、隔离执行、属性面板与命令桥 |
| Collaboration Adapter | 已提交变更同步、Presence 与离线队列 |
| Viewport Manager | 实时视角、跟随、保存视角和演示路径 |
| Template / Instance Index | 实例化、来源记录、作用域内注册、发现与查询 |
| AI Orchestrator | 依赖解析、任务执行、候选变更与心流建议 |

先把这些职责做成清晰接口，不要求一开始拆成多个网络服务。在线版可以复用相同内核，替换身份、存储、索引和协作适配器。

### 16.2 最小调用语义

以下为语言无关的接口约定，而非已确定的 SDK 签名：

```text
list_sources(workspace, access_context)
  → 当前主体允许发现的数据源与可用能力

resolve(reference, access_context)
  → 已授权句柄、实际解析版本、可用性与来源信息

read(handle, selector_or_query, revision, page_cursor)
  → 授权范围内的数据、实际版本、下一页信息

prepare(command_group, base_revisions, access_context)
  → 候选变更、校验结果、冲突或能力不足信息

commit(prepared_change, idempotency_key, access_context)
  → 原子生效的共享提交与新版本，或明确失败

refresh(source, access_context)
  → 新本地快照或同步失败；失败时保留旧快照

publish(output_channel, immutable_result_ref, access_context)
  → 新发布版本与记录

query_instances(template, time_range, state, scope, access_context)
  → 授权实例、版本信息、覆盖范围与分页
```

`prepare` 不是绕过检查的授权凭证。`commit` 时仍需验证当前权限和版本，防止准备后目标已变化。读取分页应绑定稳定查询版本或说明一致性策略，避免遍历集合时重复或漏读。

数据源枚举也需要权限控制：不能仅因为用户无权读取正文，就把敏感源的名称与描述全部暴露给其 UI 或 AI。

### 16.3 Source Adapter 最低责任

每个适配器应报告可读写能力、版本语义、是否支持本地快照、是否可分页 / 索引、写入原子性范围，以及是否具备可用的撤销 / 版本保留能力。

不能为了统一接口而把不支持的能力伪装成成功。例如某个外部目录只支持读取，就不应该宣称提供通用事务写回。

SQL 可以作为表格查询能力，但不能成为绕过记录 / 字段级权限的后门。查询与变更都必须受授权约束，不能让任意扩展通过直接打开底层数据库逃避控制。

### 16.4 错误应可解释

建议至少区分：无访问权限、引用未找到、源尚未同步、当前离线、版本冲突、Schema 不兼容、目标已删除、扩展缺失、外部写入失败、发布失败和查询覆盖不完整。

UI、Agent 和自动化流程都应消费这些明确状态，而不是只有一个无法判断是否可重试的“失败”。

### 16.5 格式演进与导入边界

文档格式需要明确主版本与兼容策略。未知扩展字段应尽量保留；必要扩展缺失时可以限制编辑，但不能丢弃其数据。

迁移应在可回退的快照上执行，并记录格式与 Schema 变化。导入包要检查资源路径、包内引用、内容完整性与资源规模；不能允许资源路径越出工作目录，或在打开文档时自动执行未授权代码。

### 16.6 不同版本号的含义

| 标识 | 含义 |
| --- | --- |
| `workspace_id` | 稳定的文档身份 |
| `head_commit_id` | 当前 Workspace 文档对应的共享提交 |
| `source_revision` | 某数据源内容的版本 |
| 对象 / 资产版本 | 某个对象或文件正文的版本 |
| `schema_id + version` | 一份不可变结构定义的身份 |
| `renderer_id + version` | 一份可定位的展现实现 |
| `session_id` | 一次用户操作上下文，不是文档版本 |

这些标识不要求具有同一个全局递增序列。示例中的 `revision` 是上下文对应的版本引用，接入实际协议时需要明确其目标类型。不能把文件修改时间当作所有数据与业务确认的统一版本。

### 16.7 依赖图与派生更新

内核应能追踪：Cell 绑定哪些源，生成结果来自哪些输入版本，输出通道指向哪个结果，哪些 Workspace 引用了它。

输入更新后，普通数据视图可以刷新；已经生成的派生数据则需要明确的重算策略。**不能因为某个依赖变了，就默认再次调用 AI、产生费用并覆盖原结果。** 建议默认标记“输入已有新版本”，由用户重新执行；允许在显式配置后采用自动重算策略。

对象互相引用与计算依赖循环也应区分。解析对象图需要有访问范围和深度控制；自动重算链中的循环必须识别并处理，不能无限触发。

对于来自多个独立外部系统的输入，“各自固定版本”不等于“取得了同一时刻的全局原子快照”。应记录各自解析版本；需要严格组合一致性时，通过上游的集合发布或明确的业务协调实现。

## 17. 核心场景与验收标准

本节是后续原型与测试的验收约定，不表示这些功能已经实现或测试通过。

### 17.1 六条端到端路径

| 场景 | 应贯通的完整路径 |
| --- | --- |
| 成绩表与独立标注 | 创建成绩源 → 两个画布引用 → 各自标注 → 显式共享某个 Overlay → 排序后标注仍指向正确学生与科目 |
| 许愿格生成统计视图 | 输入提示词 → 显示并确认源 → 固定输入版本 → 计算或直接引用 → 生成 Renderer → 校验后创建 Cell → 可撤销 |
| 心流补全 | 用户输入两行 → Agent 形成候选名单 → 建议区展示 → 接受时校验版本 → 批量命令生效 → 一次撤销 |
| 角色设定到建模 | 工作中生成多次结果 → 显式确认集合 → 发布输出通道 → 建模画布同步该版本 → 上游草稿变化不影响下游 |
| 公共讲解与评论 | Guest 打开投影视图 → 跟随讲解者 Viewport → 在公开对象上评论 / 回复 → 退出跟随 → 恢复个人视角 |
| 报名与审核 | 模板创建实例或使用受限表单 → 校验 / 自查 → 正式提交 → 授权确认 → 按确认版本汇总或读取集中记录 |

### 17.2 必须验证的行为

| 编号 | 验证操作 | 通过标准 |
| --- | --- | --- |
| D01 | 创建含内置表、对象和 Cell 的 Workspace，导出后重新导入 | 数据、Schema 引用、布局与 Renderer 绑定可恢复；不依赖原编辑进程 |
| D02 | 同步一个外部源后断网打开 | 能读到最后成功快照，显示其版本；同步失败不清空数据 |
| D03 | 首次导入外部源即失败 | 显示尚未取得数据，不伪造空表或已同步状态 |
| D04 | 直接访问源在离线时读取 | 返回清晰的不可用结果；不悄悄用旧快照冒充实时内容 |
| D05 | 对同一数据源创建多个 Cell，并修改其中一个的展现配置 | 业务数据不受污染，其他 Cell 不被无意改动 |
| D06 | 给表格记录添加标注后执行排序、过滤和列重排 | 标注仍锚定原记录与字段，不随显示坐标漂移 |
| D07 | 两个画布各自标注，再显式共享一个 Overlay | 默认独立；授权共享后才可复用；私有附加层不泄露 |
| D08 | B 在私有草稿中改同一值四次，再提交一次 | B 可本地撤销重做；A 的客户端与共享日志不收到 B 的私有中间输入 |
| D09 | A、B 同时修改同一个业务字段 | 冲突可识别、可解释；没有无提示的数据覆盖 |
| D10 | A 修改后 B 再修改，A 尝试共享撤销 | 不覆盖 B 的更新；需要补偿校验或显式冲突处理 |
| D11 | 离线提交在重连时被重复发送 | 幂等处理，只生效一次；权限变化后不能越权应用 |
| D12 | Guest 只获评论能力 | 能评论 / 回复，但无法修改源；重复访问在凭据仍有效时可恢复匿名参与身份 |
| D13 | 无权用户通过隐藏 Cell 的 ID 或源查询接口请求数据 | 数据边界拒绝访问，不依赖 UI 隐藏 |
| D14 | 许愿格提示词涉及同名或无权限源 | 显示歧义 / 缺失，不静默猜测和执行 |
| D15 | 心流建议显示后不接受 | 正式数据、Cell 和共享历史均不因建议而改变 |
| D16 | 建议生成后用户修改目标，再点击接受 | 重新校验版本，不盲目套用过期操作 |
| D17 | AI 生成 Renderer 尝试读取未绑定源、访问凭据或直接写文件 | 沙箱与权限桥阻止越权；允许的写操作仍经 Command |
| D18 | 生成结果需要新增多个对象，执行中途失败 | 不留下冒充成功结果的半成品；正式事务与暂存产物状态可解释 |
| D19 | 上游反复修改角色设定草稿，下游引用已确认输出 | 下游版本不变；仅在新发布且满足读取 / 同步策略后更新 |
| D20 | 复制引用同一大资产的多个画布 | 文档层复用引用；物理去重须用实际存储统计另行验证，不能只检查 ID 相同 |
| D21 | 删除一个引用者并触发资产清理 | 仍被其他画布、发布或保留历史引用的资产不被删除 |
| D22 | 普通用户与 Guest 跟随讲解者，再切换保存的演示视角 | 视角正确变化；未共享草稿、私有标注和无权数据不随 Follow 暴露 |
| D23 | 从模板创建两个实例并分别编辑 | 内置可变数据相互独立；模板不被写回；私有历史与原访问凭据不继承 |
| D24 | 实例确认后又产生新草稿，再进行汇总 | 汇总读取明确的有效确认版本，不把新草稿当作已审核内容 |
| D25 | 按模板和日期查询，但设备只发现部分实例或索引未同步 | 结果说明作用域与覆盖限制，不宣称完整汇总 |
| D26 | 使用共享报名表入口提交，再尝试读取其他人的记录 | 追加可成功；越权读取 / 修改被数据层拒绝；重复提交不重复插入 |
| D27 | 在一份文档中组合粗粒度矢量 Cell 与细粒度对象 Cell | 两者均可保存、定位、授权和进入操作历史，不要求重做内核 |
| D28 | 缺少某个自定义 Renderer 时打开文档 | 原数据不丢失，可显示回退视图与扩展缺失状态 |
| D29 | 分享导出一个经历多人编辑、AI 调用和匿名评论的 Workspace | 按导出策略保留允许分享的内容，不带出私有历史、密钥或会话凭据 |
| D30 | 修改已发布模板的结构，再打开旧实例 | 旧实例仍能按创建时版本解释；迁移必须显式进行 |

<a id="section-18"></a>

## 18. 建议的实现顺序

实现顺序应围绕可验证的纵向闭环，而不是先搭一个大型后台或先写大量界面。以下是建议分层，不是时间承诺。

### 18.1 第一阶段：本地文档与数据闭环

实现文档包、运行目录、Schema 引用、三类结构化源及文件引用；至少提供通用对象、表格和一种媒体 / 文件视图。建立稳定 ID、Cell 绑定、个人状态与统一 Command，完成本地撤销、保存、导出、导入和 Fork。

同时实现外部手动同步快照，验证断网可用。此阶段就应证明：文件化不是界面上的“另存为”按钮，而是文档在没有原后台环境时仍能解释。

对应优先验收：D01—D07、D23、D28、D29。

### 18.2 第二阶段：权限、提交与多人边界

建立 LocalCommand 与 SharedCommit 分离、幂等提交、版本冲突、共享撤销和离线待提交队列。实现最小权限投影、Guest 评论、Overlay 共享和实时 Viewport Follow。

初始可以采用简单且可解释的版本冲突处理，不必为所有对象同时实现复杂的实时协同算法，但不能静默覆盖数据。

对应优先验收：D08—D13、D22、D26。

### 18.3 第三阶段：AI 生成与心流闭环

先完成受控 Renderer Host 与命令桥，再接入许愿格和 AI Skills。验证依赖识别、可追踪生成、场景专用 Renderer、候选变更校验与批量撤销。

心流从低干扰资料提示和一种结构化补全开始，重点验证不接受不修改、旧建议不误写、私有输入不会越界共享。

对应优先验收：D14—D18。

### 18.4 第四阶段：跨画布业务与领域扩展

实现当前 / 已确认发布通道、资产引用和回收约束、模板实例注册、按时间与状态查询、确认版本汇总，以及保存 Viewport 与演示路径。

通过独立实例报名和受限表单报名两条路径验证同一内核，再用图形对象编辑验证粗细粒度 Cell 的扩展能力。

对应优先验收：D19—D27、D30，以及各阶段尚未覆盖的完整回归。

### 18.5 不宜先做的事情

在数据身份、文档版本、命令权限和提交边界尚未确定时，不宜先追求复杂的自动协同算法、完整 Office 兼容、海量内置图表、任意系统 UI 接管或全行业编辑器覆盖。

这些能力可以逐步增加，但不能用演示效果掩盖底层数据不能独立保存、无法追踪修改或权限只在前端生效的问题。

## 19. 待决项与需要验证的假设

以下待决项主要涉及具体协议与实现选型，不应动摇前述分层、文件化与权限原则。

| 待决项 | 本文采用的基线 | 决策 / 验证方式 |
| --- | --- | --- |
| 容器格式与扩展名 | 单文档包＋展开目录；`.bcanvas` 只是暂名 | 比较随机读取、快照导出、增量保存、损坏恢复与工具链复杂度 |
| BuckyOS 对象身份与寻址 | 使用不透明对象身份和独立版本；示例不绑定真实协议 | 核实实际 Named Object、目录、权限和资源解析接口 |
| 物理去重与回收 | 文档层引用复用；底层去重能力未预设 | 对同一资产多画布引用、删除、历史保留和重新导入进行实际存储测试 |
| 各类数据的实时提交粒度 | 已提交变化实时分发；私人草稿不广播 | 用表格、文本和图形编辑分别验证即时、合并与显式提交策略 |
| 协同与共享撤销算法 | 乐观并发与明确冲突处理作为起点 | 用同字段竞争、删除 / 修改、跨记录约束和撤销链验证类型级策略 |
| 私人历史的持久化与保留 | 与共享包隔离，按用户策略保留 | 确定崩溃恢复、隐私删除、磁盘占用与个人备份之间的取舍 |
| 对象容器存储引擎 | 统一逻辑接口，可先复用现有本地存储能力 | 根据对象数量、查询、分页和发布方式测量，避免过早增加多套引擎 |
| 粗细粒度 Cell 的统一接口 | 允许嵌套对象引用和可选父子 Cell | 用流程图整体编辑、单对象操作与大表格展现验证边界 |
| 生成 Renderer 的载体 | HTML 沙箱是候选；统一数据桥与命令桥是要求 | 验证隔离、离线资源、性能、导出与异常恢复 |
| 全组织实例发现 | 有作用域的注册索引，明确覆盖范围 | 确定实例注册入口、权限过滤、状态同步和索引重建协议 |
| 管理员 Viewport 介入 | 作为独立权限，不等于读所有草稿或接管输入 | 明确产品中“查看、请求聚焦、共同演示、编辑”各操作的界限 |
| 发布与多源一致性 | 发布不可变结果集合，再更新通道 | 核实底层是否有条件更新与版本保存能力，并测试失败补偿 |
| AI 执行能力与资源主体 | 用户自有或 Workspace 提供均可 | 明确执行身份、上下文范围、外部传输授权与资源额度 |

尤其需要防止三种未经验证的推断：

**分离 UI 状态不等于核心数据不会冲突；文件引用不等于底层已经实现去重；独立 Canvas 不等于权限可以不用设计。**

## 20. 核心设计结论

本系统的最小稳定内核，不应由某一套固定编辑界面定义，而应由以下关系定义：

```text
可迁移的 Workspace 文档
    + 可命名、可授权、可版本化的数据源
    + 与数据分离的 Cell / Renderer / 附加层
    + 按用户与 Session 隔离的工作状态
    + 可追踪、可验证的 Command 与共享提交
    + 可复用的 Viewport、模板与发布关系
    + 使用相同权限和命令通道的 AI 与行业扩展
```

对于使用者，它可以表现为笔记、表格、图表、流程图、演示、报名材料、轻量设计或 AIGC 工作空间；对于内核，这些场景应尽量是同一套数据与操作模型的不同组合。

最终需要守住的边界是：

**共享数据，不强制共享所有编辑过程；共享结果，不强制暴露全部工作中间态；扩展 UI，不绕过数据与权限；增强 AI 主动性，不夺走用户对正式修改与发布的控制。**

做到这一点，AI Canvas / Workspace 才能成为可以持续扩展的生产力基础，而不是另一个把数据、界面、历史、AI 和业务流程混装在一起的单体应用。
