## 1. 本期定位与继承关系

[第三期规划](<BuckyOS AI Workspace 第三期规划.md>)完成 Frame、Viewport、混合路线、使用引导、当场演示、运行数据隔离和统一状态入口。[内核架构改进](<BuckyOS AiWorkspace 内核架构改进.md>)随后冻结了固定版本（D03）、历史保留与回收（D06）、执行授权（D16）、演示基线（D17）、程序隔离（D21）和按路径发布（D26）。本期将本地 Run 扩展为服务端管理的 Presentation Session，对齐[演示模式 PRD](<BuckyOS AI Workspace 演示模式PRD.md>)的房间、多人交互、保存及回放目标。

本期继续遵循：

- Frame 主要承载演示页面；Viewport 只定义某张 Surface 上的视觉中心和 zoom。
- `frame1 → frame2 → viewport1 → viewport2 → frame3` 使用同一套步骤和播放器。转场沿用第三期的写意方案（fly／fade／cut，第三期 §9）：到达后的取景必须精确，中间过程不是契约，不版本化。
- 每条路径有舞台逻辑尺寸；各端按“完整放入”适配同一个取景矩形，只有补边不同（第三期 §5.3）。
- 普通复杂画布使用引导不必创建房间。画布市场上架／交易仍是独立产品范围，不因公开演示而建设支付系统。
- 一份作品可以开展多场演示，作品版本、各场运行数据和记录相互可追溯。
- 原生音频只做一路主讲语音广播和录音，课件媒体的声音靠观众端同步播放而不转发（§7.3）；多人交流可以配合外部会议，不建设多人音视频会议或持续录屏平台。
- 内核 §十“固定版本演示”的五条约束：取得一致版本并闭合依赖；交互写入演示自己的空间；事件引用固定基线；演示快照的授权独立定义；固定内容不冻结 ACL。

“公开演示”表示具有可分享的房间入口，不等于默认全网匿名可读。观看、互动、保存、评阅、导出及管理权限分别控制。

**部署与连接前提（已定，2026-10-30）。** 老师基于已有 Workspace 创建公开课；公开课 URL 与来源 Workspace URL 使用同一 Host，以 Session 路径标识不同场次。本场运行副本即使使用新的 Workspace ID，也不改变公开课的 Host。

所有人的浏览器都连接 Workspace 所在的 Host，按权限推送／拉取命令、状态、事件与资源，构成中心拓扑；老师浏览器不承担面向学生的服务器或转发节点。老师不必是 Host Owner，Presenter 和 Audience 都是服务端授权的参与者，区别在可执行操作与可读取数据。

```text
老师浏览器（Presenter） ⇄ Workspace Host ⇄ 学生浏览器（Audience）
                              ⇅
                         公共屏／其他终端
```

长轮询、WebSocket 和语音传输协议是浏览器与 Host 之间的传输实现选择；状态由哪端计算是业务职责选择，均不改变上述拓扑。Host 背后的网关与服务部署、HTML 扩展的隔离子域也不改变公开课入口与来源 Workspace 同 Host 的约束。

**内核与扩展的分工（已定，2026-10-30，Q07／Q08／Q09）。** 本期只在内核增加与“一场演示”直接相关的通用能力：Session 生命周期与凭据、本场 Workspace、`session` feed、参与者作用域实体、对实体名额的原子认领、事件记录与回放。课堂互动的具体玩法（题目标识与答案复用、抢答／点名细则、超时与撤销、选择题的呈现与统计）不写进内核，而是在标准数据模型（§5.3 的 feed 与 §5.2 的 task／response／result 实体）之上用 Workspace 扩展机制实现（Block-control／组合控件／HTML 扩展，见[扩展实现思路](<BuckyOS AI Workspace 扩展实现思路.md>)）。系统随附一套“课堂互动”扩展作为默认实现，其规则可以被替换；本文 §5.2／§5.4 所述细则是这套默认扩展的行为，不是内核契约。一场演示的全部数据都以标准 Workspace 数据模型暴露，扩展读写的只是普通实体。

## 3. 房间与生命周期

### 3.1 Session 最小信息

| 信息 | 用途 |
| --- | --- |
| `session_id`、稳定链接 | 与来源 Workspace 同 Host，以独立 Session 路径标识本场；本场运行副本不另换公开课 Host |
| 来源 Workspace、路线及课件版本 | `{ workspace_id, epoch, seq, snapshot_id, content_root }`，固定本场开始时的内容及编排；`{ epoch, seq }` 即克隆点，`content_root` 由克隆时 `doc.checkpoint` 的物化流程产出，供归档 pin 与回放装载 |
| 运行数据上下文 | 本场 Workspace（`purpose=session`，原 Workspace 的整体克隆，见下文），不覆盖原作品 |
| Owner、Presenter 授权、参与身份 | 管理和现场控制分开，支持 Presenter 与 Owner 不同 |
| 访问／互动／保存策略 | 解释谁能加入、输入、公开结果、归档及管理；含是否允许 guest 互动（Q03）与本场容量／延迟目标（Q13） |
| 当前权威状态与事件 head | 当前步骤、转场、任务、已发布结果、恢复位置 |
| 记录与资源状态 | 正常记录、缺口、音频状态、待保存及归档 manifest |
| 课后数据入口 | 答案、评阅、讨论、评价与作品历次演示索引 |

**本场副本＝整体克隆（已定，Q02）。** 本场 Workspace 由原 Workspace 整库克隆得到：沿用 `clone_for_show` 的 `VACUUM INTO` 路径，`purpose=session`，长期保留，不被 `drop_stale_clones` 清扫，不计入放映克隆上限。选整体克隆而不是从去备注 `content_root` 载入，是因为 Workspace 的状态（run 记录、Source 绑定、扩展定义、ink、媒体资产引用等）已经越来越多，逐项“载入”容易漏；克隆天然完整。克隆带来的两个暴露问题在克隆完成后、房间开放前由服务端一次处理：

- 协作历史：把本场 Workspace 的历史下界 `base_seq` 设到克隆点并丢弃更早的 ops，`doc.get_changes`／`list_versions` 对任何凭据都从克隆点起算；原作品的协作过程不进入本场。
- 备注：执行一次“备注剥离”Commit，把 Frame `presentation.notes`／Viewport `notes` 移入本场 Workspace 中 Presenter 作用域的 `session/notes` 实体（按 step ID 索引），公共实体不再含备注；提示器从该实体读备注，不再回原 Workspace。公共投影因此不依赖字段级权限（§4）。

内容寻址对象按 bucket 引用计数共享，整库克隆复制的是实体与 ops 表，不复制媒体与快照对象。`ws.fork` 不用于本场副本：它要求 Export 能力且只从 content_root 载入。

### 3.2 生命周期

```text
准备 → 演示中 → 已结束／待保存 → 保存中 → 已归档
```

访问受限和删除是独立管理状态；不能把关闭新观众、结束直播、关闭评论和删除归档做成同一个操作。

- 创建房间生成唯一 Session 和稳定链接；再次授课创建另一场，不覆盖旧场。
- 准备阶段限制观众能看到的内容，不能提前发送老师备注、答案或准备中的草稿。
- 记录在演示开始时启动并持续暂存，“结束后保存”是决定保留和完成归档，不是从最终画面反推历史。
- 结束停止现场任务，但房间暂存仍按政策保留；结束者没有保存权限时等待 Owner 或已授权者处理。
- 保存成功后原链接进入本场回放与讨论；版本改动、重新授课不改变旧链接指向。
- 结束后未保存的场次暂存 N 天（已定，Q10：Workspace 服务级配置，与 OOD 存储空间相关，默认 7 天），到期删除本场 Workspace、事件与媒体，链接显示“未保存，已过期”，房间元数据保留；不能将未保存场次宣传为长期可用。

## 4. 角色、设备与权限

本文 Owner 指 Workspace／房间资源的管理角色，Host Owner 指主机管理身份，二者不混用。授课只要求获得创建本场及 Presenter 所需权限，不要求拥有 Host；各端都以各自的身份或受限凭据访问同一个 Host，由服务端执行权限检查。

| 角色／终端 | 可用能力 | 数据投影 |
| --- | --- | --- |
| Owner | 授权、保存、访问管理、导出和删除 | 按管理职责读取 |
| Presenter | 翻页、指针、现场操作、发题、选人、查看答案、发布结果 | 公共状态＋获授权的私有提示器数据 |
| Audience | 观看、跟随／自由浏览、获准反馈、本人作答与结果 | 公共状态＋本人的任务／响应 |
| Public Display | 展示当前公共状态 | 仅公共内容；不因账号也是 Presenter 而切入私有视图 |

Public Display 是终端用途，权限来自身份和受限访问上下文。终端用途必须在刷新、重连时保持；一个设备改成公共显示，不改变同账号平板的用途。

既有权限按实体／子树授予，没有字段／表格行级权限，也没有下级 deny；个人 scope 只对 owner 一人可见。不能把老师备注和所有人的答案放进一个对观众可读的对象，再在客户端隐藏；不能给观众原 Workspace 的全量 read 后依赖播放裁剪保护数据。参见 [access.rs](../../src/frame/aiworkspace/core/src/access.rs)。

第三期提示器的大屏模式目前靠“同一浏览器能读该工作区”渲染背景画面，等于把登录会话给了公共屏；本期公共屏必须换成本场签发的受限凭据。

**凭据与邀请链接（已定，Q14）。** 房间建好后 Owner／Presenter 可创建邀请链接；链接的权限由本场定义，与 Workspace 的分享权限相互独立，不复用 `ws.share` 的授权。观众链接签 `at_` 令牌（可观看、可按房间策略互动、绑定参与身份），大屏链接签 `dt_` 令牌（只读公共投影、无身份），提示器沿用 `pt_`。终端用途由令牌种类决定，刷新与重连保持；签发与清扫沿用 `pt_` 的机制。

建议采用服务端公共投影＋分作用域的数据访问：

- 公共房间不把原 Workspace 的读取权交给观众：观众凭 `at_`／`dt_` 只读本场 Workspace；本场 Workspace 的备注已在克隆后剥离到 Presenter 作用域实体、协作历史已裁到克隆点（§3.1），所以观众读到的实体本身不含备注。Presenter 的备注从本场的 `session/notes` 实体读。
- 答案按任务和参与者独立保存，只有本人及获授权的主讲／评阅者读取。个人 scope 只允许单一 owner 可见，不够用；已定（Q07）在 `access.rs` 新增一种参与者 scope：response 实体＝参与者所有 + 显式授权列表。task／response／result 都是本场 Workspace 内的标准实体，读取、变化流、导出走同一套权限过滤。
- 老师发布答案时，生成本次明确发布的内容版本／公共结果实体，不因给原始答案授权而将其全部历史、草稿和评语暴露出来。
- 读取、变化流、事件、快照、附件下载和导出都经过相同的权限过滤，避免只保护实时 UI。
- 公共端使用受限凭据／访问上下文，不能把 Owner 会话传给观众。D21 已裁决程序隔离走独立域名 + Worker/postMessage，但 T4-8 只完成子域路由；已定（Q06）v1 公共端与回放只渲染内置 Block 与 Block-control 控件，HTML 扩展只发布受控的状态／静态快照，live HTML 扩展等 T4-8 完成后再开放，不卡 M1。因此课堂互动默认扩展的观众端控件用 Block-control 实现，不依赖 live HTML 扩展。

**观众互动身份（已定，Q03）。** Zone 用户与 SSO 认证的 External 始终可互动；是否允许 `guest:` 互动是创建房间时的开关，默认关闭（guest 只能观看）。开关打开时 guest 可反馈、作答，但其身份是浏览器自声明令牌、可伪造，所以“每人仅答一次”对 guest 不可靠：guest 的响应在 feed 与结果中带身份等级标记，不参与名册匹配与点名池；需要可靠归属的课堂应保持开关关闭。Session Only Member 仍排在 SSO 之后，不在本期。

## 5. 跨设备同步与现场互动

### 5.1 同步与控制

本场共享状态统一经 Workspace Host 接收、确认、保存与分发；控制端提交命令或采样，观众从同一 Host 读取有权限的快照与事件。业务命令具有幂等键和作用域版本，重复发送不重复翻题、占位、提交或结束。舞台可以即时显示本地操作，但服务端未确认的内容不能视为已同步或已保存。

第三期已经采用服务端中继：舞台计算状态并分配 `seq`，服务端接受较新的状态保存在内存，提示器经服务端发命令、读状态。本期增加持久确认、事件序列与恢复能力。业务状态的计算分工已定（Q01，C）：步骤、黑屏、名额认领、结果发布由服务端执行业务规则后确认；指针、自由相机、笔迹由来源端采样，服务端校验权限、编号、记录并分发。服务端确认收到端上计算的状态，与服务端执行业务规则后确认结果，是两种处理职责，均使用同一中心拓扑。

指针、自由相机和笔迹由来源端采样，也必须经 Host 校验权限、分配事件序号与时间、记录和分发；个人浏览按个人作用域处理，不修改主讲状态。采样是否经过业务状态机不意味着省去浏览器与 Host 之间的传输。

加入和重连先获取有权限的当前快照，再补事件；不能要求新观众从开场逐条执行到当前。控制端断开不终止所有观众的房间，恢复后按服务端状态继续。

观众可停止跟随并自由浏览可见内容，然后回到主讲视角。个人浏览不修改主讲相机。每一步解析为同一个世界矩形（Frame 的矩形，或 Viewport 的中心与 zoom 按路径舞台尺寸得到的矩形），各端按“完整放入”适配到自己的舞台，只有补边不同（第三期 §5.3）。

**控制端（已定，Q05）。** v1 只做单演讲者：一场只有一个 Presenter 身份，同时只有一个活动控制端；同一 Presenter 的另一终端（例如平板换电脑）可显式接管，原控制端收到降级通知后只能观察；多 Presenter 并发或按作用域分权不在本期。

**传输（已定，Q04）。** 网关已支持 wss 透传，M1 直接用 WebSocket（`tokio-tungstenite` 已在依赖中）承载按 Session 的命令、事件与采样通道；加入／重连的“先快照再补事件”仍是协议层要求，与传输无关。现有 `show.watch` 用一个服务级 `watch` 通道唤醒所有放映的所有观察者的做法不再扩展；长轮询只保留给 WebSocket 建立失败时的降级读取。

### 5.2 反馈、弹幕和任务

| 功能 | 要求 |
| --- | --- |
| 位置反馈 | 使用 Surface／对象相对内容坐标，带类型和时间；不把屏幕像素贴到其他页 |
| 弹幕 | 主讲者配置区域、方向和可用策略；接收端可进入纯净模式 |
| 点名 | 明确任务、对象和参与者，授权后才获得输入能力；支持手选与随机抽取，抽取由课堂互动扩展在 Presenter 端执行并把种子与结果写入 task（§5.4） |
| 限额抢答 | 名额由内核的原子认领原语确认；重试幂等、不可超额；断线不自动重复分配（细则见下文默认扩展规则） |
| 作答 | 选择、文本、手写复用 Block 输入契约；每人独立响应。文本与手写（ink）Block 已有，**选择题 Block 不存在**，本期作为课堂互动扩展的 Block-control 控件新增，不进内核 |
| 结果发布 | 默认只供老师和本人查看；老师选择内容及发布范围 |
| 评阅 | 支持记录判断、评语及需要时的分数；发布由权限控制，不默认加入 AI 批改 |

任务至少包含稳定题目标识／版本、task ID、所属 Session、Block 引用、授权方式、人数上限、提交及修改策略、状态。响应至少包含 task、参与者、内容版本、提交时间与确认状态。核心目前没有 task／response 实体类型，也没有原子限额确认。内核本期只增加三件事：task／response／result 三种实体类型（Q07）；对实体名额的原子认领原语 `session.claim { entity_id, slot_key, participant }`，服务端在单事务内确认或拒绝，是限额抢答唯一需要内核参与的部分；以及 feed 刷新（§5.3）。它们之上的规则由课堂互动扩展实现。

“每场独立作答”和“同一题目每人仅答一次并复用”分别配置。题目标识、答案复用、资格撤销与迟到提交的规则（已定，Q08／Q09）由课堂互动扩展实现，内核不定制。默认扩展的规则：题目＝`{ source_workspace_id, entity_id, content_rev }`，content_rev 变即新题，同场重发＝新 task，跨场复用按前两项且 content_rev 相同、响应带原场次来源；名额超时不自动回收，老师可撤销并补选；断线不回收；迟到提交拒绝并记事件；撤销后已提交内容保留但标记无效。复用时保留原始场次来源，不能假装是本场新提交。

### 5.3 本场数据作为标准数据源：Block 的“演播时可用”

本期的互动能力不靠给每种 Block 开专用的 Session API，而是把本场运行数据按内核已有的 Source 模型（D12、D24）暴露成普通数据实体，让任何按绑定读数据的 Block（内置 Block、Block-control、HTML 扩展、许愿格）不改代码就能在演播时使用。

**模型。** 新增 Source 种类 `session`：`source{ kind: "session", feed: <feed 名>, mode: "live" }`。带这种 Source 的实体是本场 Workspace 里的普通 Table／Record，与 `url`／`workspace` Source 一样对 Block 和人只读（`SOURCE_READ_ONLY`），内容只由刷新写入，commit origin 仍为 `source`。区别在刷新来源：不是 `source.refresh@1` 的抓取任务，而是 Session 服务在状态变化时直接写入的 Commit，不经 HTTP、不占流量额度。

**feed 目录（v1 建议）。**

| feed | 形状 | 内容 | 默认读者 |
| --- | --- | --- | --- |
| `participants` | Table | 已加入本场的参与者：显示名、principal、角色、在线状态、最近心跳、加入时间 | Presenter／管理者；可按 Block 公开为去 principal 的投影 |
| `stage` | Record | 当前步骤、取景矩形、黑屏、跟随人数 | 公共 |
| `tasks` | Table | 本场任务：题目引用与版本、状态、授权方式、名额、已答人数 | 公共（不含选人名单以外的私有字段） |
| `my_responses` | Table（参与者作用域） | 本人的响应与确认状态 | 本人 |
| `responses` | Table（主讲作用域） | 全部响应 | Presenter／评阅者 |
| `results` | Table | 老师已发布的公共结果 | 公共 |
| `reactions` | Table | 位置反馈与弹幕的近期聚合 | 公共 |

feed 实体按作用域拆成不同实体而不是在一张表里按行过滤，因为权限模型没有行级授权（§4）；`my_responses` 对每个参与者是各自的隔离实体（Q07）。

**变化传播与记录。** feed 的每次刷新是一次普通 Commit，所以 Block 通过现有的 `doc.wait_changes` 与绑定 `watch(name)` 即可实时看到，不需要新的推送通道；同一 Commit 经 §6.3 的 outbox 进入时间线，回放时按 seq 读取 feed 实体，Block 就是在“只渲染历史状态”，不需要为回放另写实现。feed 目录与刷新粒度已定（Q19）：v1 固定为上表七个 feed，扩展只能绑定、不能自定义，目录随 PROTOCOL 版本演进；`stage`／`tasks`／`results`／`my_responses` 每次变化即一次 Commit，`participants`／`reactions`／`responses` 节流为每秒至多一次并合并期间变化，节流在事件中记为精度说明，丢弃的中间值按 §6.2 处理。

**课件设计期（已定，Q20）。** 课件作者在原 Workspace 里就能放置绑定 `session` feed 的 Block：原 Workspace 的 `data` 下有系统文件夹 `session`（同 `shows` 的做法），插入绑定 feed 的 Block 时自动创建对应的样例实体（固定 schema，空表或少量示例行，作者可改示例内容但不能改字段）；样例实体随克隆进入本场，Session 开始时服务按目录激活它们、清空示例并开始写入。Block 的绑定不变，从样例数据切换到真实数据。

**许愿格（已定，Q21）。** `session` 文件夹对许愿格可见（许愿格快照层目前只排除 `shows`）：feed 实体与普通 Table 一样可作为许愿格输入，Agent 驱动的 Block（如“根据作答分布生成讲评”）因此也演播时可用；`my_responses`／`responses` 的作用域照常生效。

**输入方向不走 Source。** Source 是单向的：参与者的作答、反馈、弹幕通过各自的输入契约（task／response 的 Commit，§5.2）提交，由服务确认后再反映到 feed。Block 读 feed、写契约，两端都是内核已有的机制。

**“演播时可用”的判定。** 一个 Block 在演播中可用，当它的全部绑定都解析到 `session` feed 或固定基线中的实体，且它的写入只发往任务输入契约。放映开始前的记录能力检查（§6.1）据此判断并提示哪些 Block 在本场只能静态显示。

### 5.4 典型场景：课堂出席与随机点名作答

这是本期互动能力的基准场景，也是 §5.3 的第一个用例：在线观众 Block 只是一个绑定 `participants` feed 的普通 Block。M1–M2 的任务、身份与记录设计都要能走通它。

**场景。** 老师在课件里放一个“在线观众”Block。上课时它实时列出已加入本场的人；学校场景下老师还预存了一张学员名册，Block 切到“对照名册”就直接列出谁没在线。讲到一道题时，老师按“随机点名”，系统从在线且在名册中、尚未答过的同学里选一人；被选中的同学的终端弹出这道题的作答界面（例如选择题），提交后老师看到答案，再决定是否公布。

**出席（presence）。** 服务端按本场维护参与者的在线状态：加入、心跳、离开、重连都更新它并产生事件（归入“运行与诊断”轨道的出席子类，默认 Presenter 与管理者可见），同时刷新 `participants` feed。出席是本场的数据，不是课件的数据：课件基线里只有 Block 配置和样例 feed 实体。在线判定与可见范围已定（Q18）：在线＝WebSocket 连接存活且最近 30 s 内有应用层心跳，连接断开即离线；出席事件默认只对 Presenter／管理者可见。

**在线观众 Block。** 随课堂互动扩展提供（Block-control 组合控件；表达能力不够时降为内置 Block，但接口仍只是绑定），两个绑定：`participants` feed 和一张名册 Table（原课件中的普通表格，随克隆进入本场，可选）。两种视图：“在线列表”和“对照名册”；对照名册输出三组：在线且在册、在册未在线（缺席）、在线不在册。默认只对 Presenter 可见；老师可以把它设为公开（例如投到大屏显示出席人数），公开投影只含显示名与在线状态，不含名册其他列与 principal（Q18）。因为它只是普通绑定，用 Block-control 或 HTML 扩展写一个不同样式的出席 Block，不需要本期提供任何新 API。

**名册与身份（已定，Q17）。** 名册一律按 DID 匹配：名册是普通 Table，约定 `principal` 列保存学生的 DID／Zone 用户名，与出席记录按这一列匹配；不做按行邀请链接，也不做按姓名自动匹配。名册有两种来源：课件作者在原 Workspace 里维护一张名册表（用 AI Workspace 的外部数据导入机制，即表格导入模块，随克隆进入本场）；或老师在房间创建后用同一导入机制把名册导入本场 Workspace。名册行与本场参与者的匹配结果写入本场（不改原课件），作为点名池和缺席统计的依据。

**随机点名。** 由课堂互动扩展在 Presenter 端执行（Q08／Q09：内核不定制）：扩展读 `participants` feed 与名册求出 `pool`（默认“在线 ∩ 在册”）与 `exclude`（默认“本任务已作答者”），用自带种子抽取，然后提交一次 task Commit，把种子、pool 版本、结果与被选者的输入授权（即其 response 实体的显式授权列表，Q07）一并写入；Commit 经 outbox 进入时间线，回放时直接读结果，不重新抽取。被选中者的终端通过绑定 `tasks`／`my_responses` feed 的 Block 看到自己被选中并弹出作答 UI；其他观众只看到“已点名某某”的公共字段（是否公开姓名由老师设置）。被选中者离线或超时，老师可撤销并重新点名（默认扩展规则见 §5.2）。

**作答与发布。** 选择题控件在参与者端以“作答模式”呈现，提交为该参与者的独立响应（Q07）；老师端的统计 Block 绑定 `responses` feed 实时看到，公布答案后 `results` feed 刷新，观众端绑定它的 Block 同步显示。

## 6. 全过程记录：覆盖范围和一致性

### 6.1 记录范围

默认记录所有受支持、可观察的演示行为，包括主讲和观众的行为；按作用域保存，而非全部放进公共录像。

| 轨道 | 包含内容 | 默认读者 |
| --- | --- | --- |
| 公共讲解 | Frame／Viewport 切换、相机动画、手动浏览、公共指针／板书、显隐、媒体状态、公开 Block 变化、临时内容、发题和结果发布 | 获准观看本场者 |
| 公开互动 | 位置反馈、弹幕及其位置／生命周期 | 获准观看者；纯净播放可以隐藏效果，原记录仍在 |
| 主讲私有 | 与任务有关的选人、授权、私有评阅及管理状态变化 | 获授权的主讲／管理者 |
| 参与者个人 | 本人的作答编辑／提交、个人浏览及相关状态 | 本人及被授权的管理者；不广播到公共回放 |
| 运行与诊断 | 命令结果、失败、连接中断、媒体缺口、资源与归档状态；参与者出席（加入／心跳超时／离开／重连，§5.4） | 对应管理权限；不混进公开内容 |

“所有行为”以系统支持的语义和实际呈现状态为边界：既记录离散动作，也记录影响过程的连续状态。记录文本编辑或笔迹时，应保存能还原该阶段的内容变化，不能只存“发生过输入”；个人敏感输入不进入公共轨道。板书与指针采样契约已定（Q15）：板书按 ink v1 段上行（每笔 ≤8 段，段内点带 t）；指针按 10 Hz 采样、静止不发；丢样时事件记缺口。第三方会议内部行为和任意扩展无法观察的内部状态，不在没有采集能力时宣称已被记录。

不逐项记录无关系统按键、浏览器 UI 或用户密码；影响演示结果的输入通过对应组件的状态契约保存。扩展、外部动态数据和媒体在开始前做记录能力检查；缺失能力必须显式降级，归档标明范围。

### 6.2 事件和时间

事件最小公共头：`event_id`、`session_id`、服务端 `seq`、演示相对时间、实际接收时间、actor／参与身份、作用域、类型、关联命令 ID 和 schema 版本。时间线使用统一的单调相对时间；时间校准已定（Q16）：演示相对时间以服务端接收为准，客户端连接时测 RTT 得到单调时钟偏移，采样事件带客户端单调时间、由服务端换算；不用各设备系统时钟排序。

步骤切换事件记录目标步骤、实际采用的转场类型（fly／fade／cut）和当时解析出的取景矩形；转场是写意的，不记录中间帧，也不版本化动画算法（第三期 §9）。自由浏览的相机、指针和笔迹按采样记录，必须能重建过程中间状态；丢弃样本时记录精度或缺口，不能无提示只存最后一个点。

事件引用当时已确认的状态和不可变输出。AI、代码、数据查询记录实际结果／资源版本；随机和定时驱动的 Block 需要保存足够的状态或采用快照。点击“运行”本身不足以还原结果。

### 6.3 持久化与恢复

- 本场数据 Commit 与时间线事件建立可恢复关联。建议在提交事务中写出待发布事件，再由记录器消费；采用其他方案时也需覆盖“数据已写、事件未写”的故障窗口。现有 Commit 走 `commit_inner` 单事务，可在同一事务追加 outbox 行。
- 只有成功确认的业务结果进入成功状态事件；失败及未知结果分别记录，重试按命令身份去重。
- 事件、关键快照、媒体分片和资源清单持续落盘，服务重启能恢复已确认范围并报告缺口。现有放映全部在内存（`Shows`、`ShowLocks`），服务重启即结束；本期 Session 必须落盘。
- 快照需要绑定事件 seq、文档提交位置、运行状态及资源版本，保证跳转时读取的是同一时刻。
- 暂存失败时立即显示记录异常；有权限者可选择继续演示并接受不完整记录，不能继续显示“完整记录中”。

## 7. 结构化回放与音频

### 7.1 重建路径

```text
本场固定课件基线
    + 不晚于目标时间的状态快照
    + 快照之后至目标时间的有权限事件
    + 当时的输出、笔迹、媒体及扩展快照
    → 目标时间的画面与交互结果
```

复用第三期的目标解析和舞台取景换算。播放、暂停、变速、按时间定位为必需；按 Frame／Viewport 步骤或题目定位作为导航入口。定位到转场中间时直接显示目标取景，或用当前实现重新做一次写意过渡，不要求复现原中间帧；定位到一笔尚未完成时显示相应笔段，不能只恢复落笔后的最终图形。

回放读取历史版本，不读取当前课件、当前动态 URL 数据或当前 AI 输出冒充历史。现有 `doc.list_versions / restore_version` 是单实体的 `content_rev`，不是“某 seq 时刻整树读取”；回放需要按本场 Workspace 的 seq 读取或按关键快照 `content_root` 装载（`materialize::load_ops` 已能从 content_root 载入）。renderer 契约版本需要保留；实现不支持历史版本时使用归档快照或明确缺失提示。

### 7.2 无副作用呈现

Replay 宿主只应用已保存状态，禁止重新运行 AI、执行产生副作用的代码、提交答案或发送业务请求。不能仅把 live 界面的按钮禁用后继续挂载会自动执行的扩展。现有 RenderHost 的 `show` 模式仍挂载 `presentation.live` 的 Block，回放需要新的只渲染模式。

复用组件必须有只渲染历史状态的实现；没有这种实现的 HTML Block 使用归档的静态快照／受控媒体替代。回放中的课后评论是新的房间数据，不修改历史事件。未来“再练一次”必须创建新任务上下文。

公共、主讲私有、个人回放分别生成授权投影。权限撤销后停止后续读取，不因事件在历史上曾可见就绕过当前访问控制；已公开的内容版本与之后的私有编辑也必须分清。

### 7.3 音频

讲课的声音有两路来源，本期分别处理，不混成一路再转发：

| 路 | 来源 | 到达观众的方式 | 进入归档的方式 |
| --- | --- | --- | --- |
| 语音路 | 老师的 mic | WebRTC 采集→OOD 转发→观众端播放（§7.3.1） | OOD 侧录制 Opus，按演示时间轴分段（§7.3.3） |
| 课件媒体路 | Workspace 里正在播放的媒体 Block（视频、音频资产） | **不转发声音**：媒体资产已在本场基线中，老师的播放／暂停／定位作为媒体状态事件广播，观众端本地同步播放同一资产（§7.3.2） | 只记媒体状态事件；回放时按事件重新播放归档中的资产 |
| 捕获路（v1 不做，Q23） | 不在基线中的声音（外部 URL、扩展内部音频、老师共享的其他标签页） | 不转发：演播中静音，记录能力检查（§6.1）在开始前提示“该媒体不在课件中，观众听不到”；主要场景靠“媒体先上传进课件”覆盖。`getDisplayMedia` 混音方案因 Safari 不支持且会把同步播放退化为转发，不做 | 不进入归档 |

两路都以 §6.2 的演示相对时间为轴，回放时语音录音和媒体事件按同一时轴对齐；两者的容差目标见 §7.3.5。设备切换、中断、静音、丢包和观众端缓冲都形成明确区间；播放位置或速率变化时内容与两路音频一起调整。

#### 7.3.1 语音路：WebRTC 采集与广播

**采集。** 老师端 `getUserMedia({ audio: { echoCancellation, noiseSuppression, autoGainControl } })` 得到 mic 轨道，经 `RTCPeerConnection` 以 Opus 发送（建议 32–48 kbps，`maxaveragebitrate`，DTX 开启）。老师端的课件媒体在本机播放，回声消除处理扬声器回授；设备切换（蓝牙耳机插拔）用 `replaceTrack` 换轨不重建连接，并产生设备切换事件。

**传输实现（已定，Q11／Q22）。** 语音沿用同一中心拓扑：老师向 Workspace Host 上行一路语音，Host 负责录制并向观众分发。服务端在 OOD 上承载语音能力。v1 只做 WebRTC，不做 HTTP 分片兜底：启用公开课功能的用户把语音当核心功能，WebRTC 因此是该功能对 Host 的强制要求；媒体端点不可达时房间明确报错“语音不可用，请检查 Host 部署”，不静默降级。曾比较的两种实现：

| 实现 | 老师上行 | Host／OOD 负担 | 录制 | 容量与延迟 |
| --- | --- | --- | --- | --- |
| A）服务端 WebRTC 音频转发（SFU） | 1 路 | 转发 N 路 RTP（Opus 不转码，每路 ≈40 kbps） | 服务端直接落盘 | 受服务端带宽限制：50 人约需 2 Mbps 出站带宽，需实测 |
| B）MediaRecorder 分片经 HTTP 上传／拉取（不采用） | 1 路 | 存储与分发分片 | 分片即录制 | 受服务端带宽与请求处理能力限制；延迟受分片长度、轮询与缓冲影响，需实测 |

采用 A：OOD 内置一个只做音频的 SFU（Rust 的 `webrtc` 或 `str0m` crate，M0 选型并确认引入新依赖），老师一路上行，观众各一路下行；OOD 同时把收到的 Opus 包按时间轴写入录制。B 不实现；若 M0 实测 SFU 在目标 OOD 上不可行，回到本文重新裁决，不悄悄降级。由 Host 分发和归档，不采用老师浏览器向观众转发的方案。

**信令与连接。** SDP／ICE 信令走同一 Host 的 Session WebSocket 通道（§5.1），连接凭据由本场令牌派生（Q14）；老师与观众分别连接服务端的媒体端点。HTTPS 入口可达不等于该媒体端点可达；媒体端点的暴露是开启公开课功能的部署前提（Q22）：node_daemon／网关在启用该功能时默认开放媒体端口（UDP 优先、TCP 备用），M0 在真实 Zone 验证可达性；cyfs-gateway／SN 侧的媒体中继作为网关独立需求评估，用于 Host 无法直接暴露端口的部署。不另建浏览器间通道。观众端只收不发，不需要 mic 权限；浏览器自动播放策略要求用户手势，观众的“加入房间”按钮同时解锁语音路与媒体路的播放。

**公共大屏。** 课堂里老师就在现场，大屏默认只播课件媒体路、不播语音路；远程大屏可以都播。这是终端用途的设置，随 `dt_` 令牌保存（Q14）。

**延迟目标。** WebRTC 实现下语音端到端目标 ≤500 ms；与步骤切换事件的相对顺序由观众端按时轴对齐，不要求语音与翻页严格同步。

#### 7.3.2 课件媒体路：事件驱动的同步播放

媒体 Block 的播放状态进入媒体状态契约：`{ entity_id, action: play | pause | seek | rate | ended, media_pos_ms, t_rel_ms, rate }`。老师端每次操作产生一条事件（走 Q01 的离散状态路径，经服务端确认），并在播放中每隔若干秒发一条 `sync` 锚点（同样形状，不改变状态，只校正）。

观众端收到后按校准时钟（Q16）计算目标位置：`target = media_pos_ms + (now_rel − t_rel_ms) × rate`，然后：

- 偏差大于硬阈值（建议 400 ms）时 `seek`；
- 偏差在软阈值内（建议 80–400 ms）时用 `playbackRate` 微调（±5% 以内）追平，不跳帧；
- 偏差小于软阈值不动作；
- 缓冲不足时静音追赶或暂停等待，并上报缓冲事件（个人轨道）；
- 加入或重连时先按 `stage` feed 中的媒体状态定位，再跟随后续事件。

老师端的 `seek`／`rate` 操作带本机当时的媒体位置，所以观众端不依赖自己的播放进度推算。媒体资产须在本场基线中（已上传的视频／音频），观众端用本场受限凭据按 Range 取流；现有资产服务 32 MiB 上限且无 Range（§11），本期需要 Range 支持，上限按 §7.3.5 定。

**控制权（已定，Q24）。** 演播中只有 Presenter 能播放／暂停／定位课件媒体；观众端的媒体控件在跟随时禁用，自由浏览时可用但只影响本机、不发事件，回到跟随时按 `stage` 重新定位。

媒体路的回放：归档不含媒体路的音频，而是按事件在归档资产上重新播放；资产缺失时按 §8 显示不完整。

同步精度的边界：浏览器 `seek` 到关键帧的粒度、各端解码延迟和网络抖动决定媒体路做不到帧级同步；本期的目标是“同一句台词同一时刻听到”（§7.3.5 的媒体路容差），不是帧对齐。

#### 7.3.3 录制、分段与时间映射

SFU 收到的 Opus 包带 RTP 时间戳，OOD 把它映射到演示相对时间后按固定长度（建议 10 s）封装为 Ogg Opus 分段资产，写入本场 Workspace 并记事件 `{ segment_id, t_rel_start, t_rel_end, lost_ms }`；丢包用 PLC 不填充、只记缺口。归档 manifest 的音频索引即这些分段的列表；回放按时间定位到分段内偏移。

暂存失败（磁盘满、写入错误）时立即在老师端提示“语音未在录制”，并按 §6.3 的规则由有权限者决定是否继续。

#### 7.3.4 现状

仓库中没有任何 WebRTC 代码（Rust 侧与前端都没有），网关没有 UDP 中继或 TURN，媒体 Block 没有播放状态契约（`AssetMedia` 只在激活时自动播放），资产服务无 Range。现有可复用的只有 Message Hub 的 `VoiceRecorder`（整段 MediaRecorder 录成一个文件，上限 5 分钟）和 Web Audio 的电平计。

外部会议可承载多人交流，但不假设 Workspace 自动获得其录音。只有本场实际启用且可用的主讲音源进入归档。传输、编码、OOD 带宽和存储容量在详细设计中测量选型，不在本规划中承诺未经验证的规模。

#### 7.3.5 容量与指标目标

已定（Q13）：下表是 M0 的起测目标，实测后修订。实现要自适应：媒体路阈值按测得的抖动调整，语音码率按带宽调整，采样节流按观众数调整；老师在开始演示时可在房间配置里设置本场目标（预期观众数、是否启用语音、媒体资产上限），房间据此选择参数并在超出时提示。

| 指标 | 起测目标 |
| --- | --- |
| 单 OOD 并发观众 | 50 |
| 状态延迟（命令确认到观众端呈现） | ≤2 s |
| 语音端到端 | ≤500 ms |
| 媒体路各端偏差 | ≤200 ms（硬阈值 400 ms 触发 seek） |
| 回放音画对齐 | ≤200 ms |
| 回放定位耗时 | ≤3 s |
| 单个媒体资产上限 | 2 GiB |

## 8. 保存、资源保留与长期房间

归档 manifest 至少固定课件基线、事件范围及版本、快照索引、历史输出／资产、音频分片与时间映射、缺失清单和访问策略引用。

保存成功表示声明保留的内容已可靠保存、原链接可读取；部分音频、资源或扩展状态缺失时，只能显示不完整归档。资源保留必须覆盖本场使用的历史图片、媒体、程序结果和 renderer 快照，不能因原作品更新或删除而错误清理。D06 的 30 天历史保留与服务级 GC 会回收只被历史引用的资源；已定（Q12）：`retentions` 账本新增 `session` 种类，归档时 pin 基线、快照与媒体的对象闭包，不受 30 天历史回收；删除房间时释放；本场 Workspace 的配额计到 Owner。

房间结束后继续支持：

- 时间点感受：保存回放时间和实际发表时间，便于在同一讲解时刻呈现。
- 普通评论：属于本场整体，不强制绑定播放时间。
- 课程评分／建议：独立于学生作答成绩，归属本场。
- 答案和后续评阅：保留原始提交，课后新增评语记录实际时间，不插回历史冒充现场操作。
- 原作品中的历次演示入口：可追溯不同版本、不同场次的记录与反馈。

Owner 可限制观看、关闭新评论或删除房间；这些操作分别生效。删除时清理本场专有资源引用，共享对象由引用保留规则管理，不能误删其他场次或原作品资源。
