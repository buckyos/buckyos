## 1. 本期定位与继承关系

[第三期规划](<BuckyOS AI Workspace 第三期规划.md>)完成 Frame、Viewport、混合路线、使用引导、当场演示、运行数据隔离和统一状态入口。[内核架构改进](<BuckyOS AiWorkspace 内核架构改进.md>)随后冻结了固定版本（D03）、历史保留与回收（D06）、执行授权（D16）、演示基线（D17）、程序隔离（D21）和按路径发布（D26）。本期将本地 Run 扩展为服务端管理的 Presentation Session，对齐[演示模式 PRD](<BuckyOS AI Workspace 演示模式PRD.md>)的房间、多人交互、保存及回放目标。

本期继续遵循：

- Frame 主要承载演示页面；Viewport 只定义某张 Surface 上的视觉中心和 zoom。
- `frame1 → frame2 → viewport1 → viewport2 → frame3` 使用同一套步骤和播放器。转场沿用第三期的写意方案（fly／fade／cut，第三期 §9）：到达后的取景必须精确，中间过程不是契约，不版本化。
- 每条路径有舞台逻辑尺寸；各端按“完整放入”适配同一个取景矩形，只有补边不同（第三期 §5.3）。
- 普通复杂画布使用引导不必创建房间。画布市场上架／交易仍是独立产品范围，不因公开演示而建设支付系统。
- 一份作品可以开展多场演示，作品版本、各场运行数据和记录相互可追溯。
- 原生音频只做一路主讲广播和录音，多人交流可以配合外部会议，不建设多人音视频会议或持续录屏平台。
- 内核 §十“固定版本演示”的五条约束：取得一致版本并闭合依赖；交互写入演示自己的空间；事件引用固定基线；演示快照的授权独立定义；固定内容不冻结 ACL。

“公开演示”表示具有可分享的房间入口，不等于默认全网匿名可读。观看、互动、保存、评阅、导出及管理权限分别控制。

## 3. 房间与生命周期

### 3.1 Session 最小信息

| 信息 | 用途 |
| --- | --- |
| `session_id`、稳定链接 | 标识本场，不使用原 Workspace 链接冒充 |
| 来源 Workspace、路线及课件版本 | `{ workspace_id, epoch, seq, snapshot_id, content_root }`，固定本场开始时的内容及编排；`content_root` 由 `doc.checkpoint` 的物化流程产出 |
| 运行数据上下文 | 本场 Workspace（`purpose=session`，从课件基线载入）或等价隔离空间，不覆盖原作品 |
| Owner、Presenter 授权、参与身份 | 管理和现场控制分开，支持 Presenter 与 Owner 不同 |
| 访问／互动／保存策略 | 解释谁能加入、输入、公开结果、归档及管理 |
| 当前权威状态与事件 head | 当前步骤、转场、任务、已发布结果、恢复位置 |
| 记录与资源状态 | 正常记录、缺口、音频状态、待保存及归档 manifest |
| 课后数据入口 | 答案、评阅、讨论、评价与作品历次演示索引 |

课件基线与运行副本的具体形态见 §12 Q02。无论选哪种，都要复用内容寻址对象，避免全量物理复制；现有 `clone_for_show` 与 `ws.fork` 都不直接够用：前者随服务重启被 `drop_stale_clones` 删除，后者要求 Export 能力并复制协作历史。

### 3.2 生命周期

```text
准备 → 演示中 → 已结束／待保存 → 保存中 → 已归档
```

访问受限和删除是独立管理状态；不能把关闭新观众、结束直播、关闭评论和删除归档做成同一个操作。

- 创建房间生成唯一 Session 和稳定链接；再次授课创建另一场，不覆盖旧场。
- 准备阶段限制观众能看到的内容，不能提前发送老师备注、答案或准备中的草稿。
- 记录在演示开始时启动并持续暂存，“结束后保存”是决定保留和完成归档，不是从最终画面反推历史。
- 结束停止现场任务，但房间暂存仍按政策保留；结束者没有保存权限时等待 Owner 或已授权者处理。
- 保存成功后原链接进入本场回放与讨论；版本改动、重新授课不改变旧链接指向。
- 暂存保留期限、容量和不保存后的房间表现见 §12 Q10；不能将未保存场次宣传为长期可用。

## 4. 角色、设备与权限

| 角色／终端 | 可用能力 | 数据投影 |
| --- | --- | --- |
| Owner | 授权、保存、访问管理、导出和删除 | 按管理职责读取 |
| Presenter | 翻页、指针、现场操作、发题、选人、查看答案、发布结果 | 公共状态＋获授权的私有提示器数据 |
| Audience | 观看、跟随／自由浏览、获准反馈、本人作答与结果 | 公共状态＋本人的任务／响应 |
| Public Display | 展示当前公共状态 | 仅公共内容；不因账号也是 Presenter 而切入私有视图 |

Public Display 是终端用途，权限来自身份和受限访问上下文。终端用途必须在刷新、重连时保持；一个设备改成公共显示，不改变同账号平板的用途。

既有权限按实体／子树授予，没有字段／表格行级权限，也没有下级 deny；个人 scope 只对 owner 一人可见。不能把老师备注和所有人的答案放进一个对观众可读的对象，再在客户端隐藏；不能给观众原 Workspace 的全量 read 后依赖播放裁剪保护数据。参见 [access.rs](../../src/frame/aiworkspace/core/src/access.rs)。

第三期提示器的大屏模式目前靠“同一浏览器能读该工作区”渲染背景画面，等于把登录会话给了公共屏；本期公共屏必须换成本场签发的受限凭据（§12 Q14）。

建议采用服务端公共投影＋分作用域的数据访问：

- 公共房间不把原 Workspace 的读取权交给观众：观众端读取本场 Workspace，其课件基线用 `materialize_notes(notes=false)` 生成，天然不含备注；Presenter 的备注仍以其本人权限从原 Workspace 读（沿用 `show.notes` 的做法）。
- 答案按任务和参与者独立保存，只有本人及获授权的主讲／评阅者读取。个人 scope 只允许单一 owner 可见，不够用；需要“参与者所有 + 显式授权列表”的隔离实体（§12 Q07）。
- 老师发布答案时，生成本次明确发布的内容版本／公共结果实体，不因给原始答案授权而将其全部历史、草稿和评语暴露出来。
- 读取、变化流、事件、快照、附件下载和导出都经过相同的权限过滤，避免只保护实时 UI。
- 公共端使用受限凭据／访问上下文，不能把 Owner 会话传给观众。D21 已裁决程序隔离走独立域名 + Worker/postMessage，但 T4-8 只完成子域路由；在它完成前，公共端与回放中的 HTML 扩展只发布受控的状态／静态快照（§12 Q06）。

匿名观看、稳定访客互动及身份恢复见 §12 Q03。“每人仅答一次”的可靠性必须与身份强度相符：现有 `guest:` 主体是浏览器自声明令牌，可伪造，只够归属批注，不够归属答案。

## 5. 跨设备同步与现场互动

### 5.1 同步与控制

服务端维护本场权威状态；控制端提交命令，成功确认后形成单调事件序列。命令具有幂等键和作用域版本，重复发送不重复翻题、占位、提交或结束。

这与第三期相反：第三期的权威在舞台，`seq` 由舞台编号，服务端只中继。本期的权威归属与连续采样的处理见 §12 Q01。

加入和重连先获取有权限的当前快照，再补事件；不能要求新观众从开场逐条执行到当前。控制端断开不终止所有观众的房间，恢复后按服务端状态继续。

观众可停止跟随并自由浏览可见内容，然后回到主讲视角。个人浏览不修改主讲相机。每一步解析为同一个世界矩形（Frame 的矩形，或 Viewport 的中心与 zoom 按路径舞台尺寸得到的矩形），各端按“完整放入”适配到自己的舞台，只有补边不同（第三期 §5.3）。

一个活动主控制端加显式接管（§12 Q05）。传输先复用现有长轮询，但现有 `show.watch` 用一个服务级 `watch` 通道唤醒所有放映的所有观察者，观众一多就放大；M1 至少改成按 Session 的通道并支持快照＋事件分页，是否增加 WebSocket 按 M2 实测决定（§12 Q04）。

### 5.2 反馈、弹幕和任务

| 功能 | 要求 |
| --- | --- |
| 位置反馈 | 使用 Surface／对象相对内容坐标，带类型和时间；不把屏幕像素贴到其他页 |
| 弹幕 | 主讲者配置区域、方向和可用策略；接收端可进入纯净模式 |
| 点名 | 明确任务、对象和参与者，授权后才获得输入能力；支持手选与服务端随机抽取（§5.4） |
| 限额抢答 | 服务端原子确认名额；重试幂等、不可超额；断线不自动重复分配 |
| 作答 | 选择、文本、手写复用 Block 输入契约；每人独立响应。文本与手写（ink）Block 已有，**选择题 Block 不存在**，本期新增 |
| 结果发布 | 默认只供老师和本人查看；老师选择内容及发布范围 |
| 评阅 | 支持记录判断、评语及需要时的分数；发布由权限控制，不默认加入 AI 批改 |

任务至少包含稳定题目标识／版本、task ID、所属 Session、Block 引用、授权方式、人数上限、提交及修改策略、状态。响应至少包含 task、参与者、内容版本、提交时间与确认状态。核心目前没有 task／response 实体类型，也没有原子限额确认。

“每场独立作答”和“同一题目每人仅答一次并复用”分别配置。题目改版是否仍为同题、同场重发是否新任务、资格撤销和迟到提交的规则见 §12 Q08、Q09；复用时保留原始场次来源，不能假装是本场新提交。

### 5.3 本场数据作为标准数据源：Block 的“演播时可用”

本期的互动能力不靠给每种 Block 开专用的 Session API，而是把本场运行数据按内核已有的 Source 模型（D12、D24）暴露成普通数据实体，让任何按绑定读数据的 Block（内置 Block、Block-control、HTML 扩展、许愿格）不改代码就能在演播时使用。

**模型。** 新增 Source 种类 `session`：`source{ kind: "session", feed: <feed 名>, mode: "live" }`。带这种 Source 的实体是本场 Workspace 里的普通 Table／Record，与 `url`／`workspace` Source 一样对 Block 和人只读（`SOURCE_READ_ONLY`），内容只由刷新写入，commit origin 仍为 `source`。区别在刷新来源：不是 `source.refresh@1` 的抓取任务，而是 Session 服务在状态变化时直接写入的 Commit，不经 HTTP、不占流量额度。

**feed 目录（v1 建议）。**

| feed | 形状 | 内容 | 默认读者 |
| --- | --- | --- | --- |
| `participants` | Table | 已加入本场的参与者：显示名、principal、角色、在线状态、最近心跳、加入时间 | Presenter／管理者；可按 Block 公开为去 principal 的投影 |
| `stage` | Record | 当前步骤、取景矩形、黑屏、跟随人数 | 公共 |
| `tasks` | Table | 本场任务：题目引用与版本、状态、授权方式、名额、已答人数 | 公共（不含选人名单以外的私有字段） |
| `my_responses` | Table（参与者作用域） | 本人的响应与确认状态 | 本人 |
| `responses` | Table（主讲作用域） | 全部响应 | Presenter／评阅者 |
| `results` | Table | 老师已发布的公共结果 | 公共 |
| `reactions` | Table | 位置反馈与弹幕的近期聚合 | 公共 |

feed 实体按作用域拆成不同实体而不是在一张表里按行过滤，因为权限模型没有行级授权（§4）；`my_responses` 对每个参与者是各自的隔离实体（§12 Q07）。

**变化传播与记录。** feed 的每次刷新是一次普通 Commit，所以 Block 通过现有的 `doc.wait_changes` 与绑定 `watch(name)` 即可实时看到，不需要新的推送通道；同一 Commit 经 §6.3 的 outbox 进入时间线，回放时按 seq 读取 feed 实体，Block 就是在“只渲染历史状态”，不需要为回放另写实现。高频 feed 按 §12 Q19 节流，节流丢弃的中间值按 §6.2 记为精度说明。

**课件设计期。** 课件作者在原 Workspace 里就能放置绑定 `session` feed 的 Block：原 Workspace 中的 feed 实体是同名的样例实体（空表或示例数据，§12 Q20），随基线进入本场；Session 开始时服务按目录激活它们并开始写入。Block 的绑定不变，从样例数据切换到真实数据。

**输入方向不走 Source。** Source 是单向的：参与者的作答、反馈、弹幕通过各自的输入契约（task／response 的 Commit，§5.2）提交，由服务确认后再反映到 feed。Block 读 feed、写契约，两端都是内核已有的机制。

**“演播时可用”的判定。** 一个 Block 在演播中可用，当它的全部绑定都解析到 `session` feed 或固定基线中的实体，且它的写入只发往任务输入契约。放映开始前的记录能力检查（§6.1）据此判断并提示哪些 Block 在本场只能静态显示。

### 5.4 典型场景：课堂出席与随机点名作答

这是本期互动能力的基准场景，也是 §5.3 的第一个用例：在线观众 Block 只是一个绑定 `participants` feed 的普通 Block。M1–M2 的任务、身份与记录设计都要能走通它。

**场景。** 老师在课件里放一个“在线观众”Block。上课时它实时列出已加入本场的人；学校场景下老师还预存了一张学员名册，Block 切到“对照名册”就直接列出谁没在线。讲到一道题时，老师按“随机点名”，系统从在线且在名册中、尚未答过的同学里选一人；被选中的同学的终端弹出这道题的作答界面（例如选择题），提交后老师看到答案，再决定是否公布。

**出席（presence）。** 服务端按本场维护参与者的在线状态：加入、心跳、离开、重连都更新它并产生事件（归入“运行与诊断”轨道的出席子类，默认 Presenter 与管理者可见），同时刷新 `participants` feed。出席是本场的数据，不是课件的数据：课件基线里只有 Block 配置和样例 feed 实体。在线判定与可见范围见 §12 Q18。

**在线观众 Block。** 内置 Block，两个绑定：`participants` feed 和一张名册 Table（原课件中的普通表格，随基线进入本场，可选）。两种视图：“在线列表”和“对照名册”；对照名册输出三组：在线且在册、在册未在线（缺席）、在线不在册。默认只对 Presenter 可见；老师可以把它设为公开（例如投到大屏显示出席人数），公开时按 Block 级权限投影，不泄露名册中的其他列。因为它只是普通绑定，用 Block-control 或 HTML 扩展写一个不同样式的出席 Block，不需要本期提供任何新 API。

**名册与身份。** 名册是普通 Table，约定一列保存参与者的稳定身份（principal／DID），与出席记录按这一列匹配；只按姓名匹配不可靠，不作为判定依据。身份如何填进名册见 §12 Q17。名册行与本场参与者的匹配结果写入本场（不改原课件），作为点名池和缺席统计的依据。

**随机点名。** Presenter 发出命令 `task.pick { task_id, strategy: "random", pool, exclude }`：`pool` 默认为“在线 ∩ 在册”，`exclude` 默认为“本任务已作答者”；服务端执行选择并把随机种子与结果写入事件，回放能复现同一结果而不重新抽取。被选中者获得该任务的输入授权，其终端收到定向事件后弹出作答 UI；其他观众只看到“已点名某某”的公共事件（是否公开姓名由老师设置）。被选中者离线或超时，老师可撤销并重新点名，规则同 §12 Q09。

**作答与发布。** 选择题 Block 在参与者端以“作答模式”呈现，提交为该参与者的独立响应（§12 Q07）；老师端的统计 Block 绑定 `responses` feed 实时看到，公布答案后 `results` feed 刷新，观众端绑定它的 Block 同步显示。

## 6. 全过程记录：覆盖范围和一致性

### 6.1 记录范围

默认记录所有受支持、可观察的演示行为，包括主讲和观众的行为；按作用域保存，而非全部放进公共录像。

| 轨道 | 包含内容 | 默认读者 |
| --- | --- | --- |
| 公共讲解 | Frame／Viewport 切换、相机动画、手动浏览、公共指针／板书、显隐、媒体状态、公开 Block 变化、临时内容、发题和结果发布 | 获准观看本场者 |
| 公开互动 | 位置反馈、弹幕及其位置／生命周期 | 获准观看者；纯净播放可以隐藏效果，原记录仍在 |
| 主讲私有 | 与任务有关的选人、授权、私有评阅及管理状态变化 | 获授权的主讲／管理者 |
| 参与者个人 | 本人的作答编辑／提交、个人浏览及相关状态 | 本人及被授权的管理者；不广播到公共回放 |
| 运行与诊断 | 命令结果、失败、连接中断、媒体缺口、资源与归档状态；参与者出席（加入／心跳超时／离开／重连，§5.4） | 对应管理权限；不混进公开内容 |

“所有行为”以系统支持的语义和实际呈现状态为边界：既记录离散动作，也记录影响过程的连续状态。记录文本编辑或笔迹时，应保存能还原该阶段的内容变化，不能只存“发生过输入”；个人敏感输入不进入公共轨道。板书的采样单位是 ink v1 的段（§12 Q15）。第三方会议内部行为和任意扩展无法观察的内部状态，不在没有采集能力时宣称已被记录。

不逐项记录无关系统按键、浏览器 UI 或用户密码；影响演示结果的输入通过对应组件的状态契约保存。扩展、外部动态数据和媒体在开始前做记录能力检查；缺失能力必须显式降级，归档标明范围。

### 6.2 事件和时间

事件最小公共头：`event_id`、`session_id`、服务端 `seq`、演示相对时间、实际接收时间、actor／参与身份、作用域、类型、关联命令 ID 和 schema 版本。时间线使用统一的单调相对时间；设备采样时间经过校准，不能靠各设备系统时钟直接排序（§12 Q16）。

步骤切换事件记录目标步骤、实际采用的转场类型（fly／fade／cut）和当时解析出的取景矩形；转场是写意的，不记录中间帧，也不版本化动画算法（第三期 §9、§12）。自由浏览的相机、指针和笔迹按采样记录，必须能重建过程中间状态；丢弃样本时记录精度或缺口，不能无提示只存最后一个点。

事件引用当时已确认的状态和不可变输出。AI、代码、数据查询记录实际结果／资源版本；随机和定时驱动的 Block 需要保存足够的状态或采用快照。点击“运行”本身不足以还原结果。

### 6.3 持久化与恢复

- 本场数据 Commit 与时间线事件建立可恢复关联。建议在提交事务中写出待发布事件，再由记录器消费；采用其他方案时也需覆盖“数据已写、事件未写”的故障窗口。现有 Commit 走 `commit_inner` 单事务，可在同一事务追加 outbox 行。
- 只有成功确认的业务结果进入成功状态事件；失败及未知结果分别记录，重试按命令身份去重。
- 事件、关键快照、媒体分片和资源清单持续落盘，服务重启能恢复已确认范围并报告缺口。现有放映全部在内存（`Shows`、`ShowLocks`），服务重启即结束；本期 Session 必须落盘。
- 快照需要绑定事件 seq、文档提交位置、运行状态及资源版本，保证跳转时读取的是同一时刻。
- 暂存失败时立即显示记录异常；有权限者可选择继续演示并接受不完整记录，不能继续显示“完整记录中”。

## 7. 结构化回放与音频

### 7.1 重建路径

```text
本场固定课件基线
    + 不晚于目标时间的状态快照
    + 快照之后至目标时间的有权限事件
    + 当时的输出、笔迹、媒体及扩展快照
    → 目标时间的画面与交互结果
```

复用第三期的目标解析和舞台取景换算。播放、暂停、变速、按时间定位为必需；按 Frame／Viewport 步骤或题目定位作为导航入口。定位到转场中间时直接显示目标取景，或用当前实现重新做一次写意过渡，不要求复现原中间帧；定位到一笔尚未完成时显示相应笔段，不能只恢复落笔后的最终图形。

回放读取历史版本，不读取当前课件、当前动态 URL 数据或当前 AI 输出冒充历史。现有 `doc.list_versions / restore_version` 是单实体的 `content_rev`，不是“某 seq 时刻整树读取”；回放需要按本场 Workspace 的 seq 读取或按关键快照 `content_root` 装载（`materialize::load_ops` 已能从 content_root 载入）。renderer 契约版本需要保留；实现不支持历史版本时使用归档快照或明确缺失提示。

### 7.2 无副作用呈现

Replay 宿主只应用已保存状态，禁止重新运行 AI、执行产生副作用的代码、提交答案或发送业务请求。不能仅把 live 界面的按钮禁用后继续挂载会自动执行的扩展。现有 RenderHost 的 `show` 模式仍挂载 `presentation.live` 的 Block，回放需要新的只渲染模式。

复用组件必须有只渲染历史状态的实现；没有这种实现的 HTML Block 使用归档的静态快照／受控媒体替代。回放中的课后评论是新的房间数据，不修改历史事件。未来“再练一次”必须创建新任务上下文。

公共、主讲私有、个人回放分别生成授权投影。权限撤销后停止后续读取，不因事件在历史上曾可见就绕过当前访问控制；已公开的内容版本与之后的私有编辑也必须分清。

### 7.3 音频

内置支持一路 Presenter → Audience 音频，并将实际录得的分片映射到演示时间轴。设备切换、中断、静音和丢片形成明确区间；播放位置或速率变化时内容与音频一起调整。

现有可复用的只有 Message Hub 的 `VoiceRecorder`：整段 MediaRecorder 录成一个文件，上限 5 分钟，无分片上传、无分发、无时间轴映射；AI Workspace 资产上限 32 MiB 且不支持 Range。本期音频方案见 §12 Q11。

外部会议可承载多人交流，但不假设 Workspace 自动获得其录音。只有本场实际启用且可用的主讲音源进入归档。传输、编码、OOD 带宽和存储容量在详细设计中测量选型，不在本规划中承诺未经验证的规模。

## 8. 保存、资源保留与长期房间

归档 manifest 至少固定课件基线、事件范围及版本、快照索引、历史输出／资产、音频分片与时间映射、缺失清单和访问策略引用。

保存成功表示声明保留的内容已可靠保存、原链接可读取；部分音频、资源或扩展状态缺失时，只能显示不完整归档。资源保留必须覆盖本场使用的历史图片、媒体、程序结果和 renderer 快照，不能因原作品更新或删除而错误清理。D06 的 30 天历史保留与服务级 GC 会回收只被历史引用的资源，归档需要在 `retentions` 账本增加 `session` 种类并 pin 其对象闭包（§12 Q12）。

房间结束后继续支持：

- 时间点感受：保存回放时间和实际发表时间，便于在同一讲解时刻呈现。
- 普通评论：属于本场整体，不强制绑定播放时间。
- 课程评分／建议：独立于学生作答成绩，归属本场。
- 答案和后续评阅：保留原始提交，课后新增评语记录实际时间，不插回历史冒充现场操作。
- 原作品中的历次演示入口：可追溯不同版本、不同场次的记录与反馈。

Owner 可限制观看、关闭新评论或删除房间；这些操作分别生效。删除时清理本场专有资源引用，共享对象由引用保留规则管理，不能误删其他场次或原作品资源。

| P4-04 | 超过名额的观众同时抢答并重试，题目同时结束 | 名额不超额、不重复；迟到和撤销结果明确，答案不丢、不互相覆盖 |

| P4-07 | 直接定位到动画／笔画／媒体播放的中间 | 状态与可用音频对齐，不要求从开头逐项观看 |
| P4-08 | 原课件升级，外部数据变化，原资产失效 | 优先使用已归档历史资源；缺失如实显示，不以当前资源替代 |
| P4-09 | 服务在 Commit 后、事件发布前崩溃 | 恢复后无重复业务结果，事件可补齐或准确报告缺口 |
| P4-10 | 主讲者断线、音频中断、暂存／保存空间不足 | 其他终端按策略继续；缺口明确；不宣称完整保存成功 |
| P4-11 | Presenter 无保存权限而结束，Owner 后续保存 | 权限分离；原链接进入正确归档，不擅自发起新场 |
| P4-12 | 回放时评论、评分、追加评阅，再撤销访问或删除房间 | 课后内容与原时间线分开；后续读取受当前权限控制，其他场次不受误删影响 |
| P4-13 | 服务重启（M1 起） | 演示中的 Session 恢复到已确认状态；观众端重连后继续；放映锁与本场 Workspace 都在 |
| P4-14 | 课堂出席与随机点名（§5.4）：30 人名册、20 人在线、老师连续点名三次，其中一人被点后断线 | 在线观众 Block 的在线／缺席／不在册三组正确且随加入离开实时更新；名册其他列不出现在公共投影；三次点名不重复、不选离线者，被点者终端弹出作答 UI，断线者可被撤销并重选；回放中点名结果与现场一致、不重新抽取 |

验证应覆盖真实 OOD／Zone、服务重启、弱网、不同尺寸设备和真实媒体；仅通过单机浏览器测试不能宣称公开演示已完成。

| 随机点名 | 无选人命令；任务授权不存在 | `task.pick` 服务端抽取、种子入事件、定向事件推送被选者、输入授权 |

## 12. 冻结前需要决定的设计问题

每项给出选项与建议；状态为“待定”的项裁决后回写本表，再据此推导实施 TODO。建议只是建议，用户可改。

| 编号 | 问题 | 选项 | 建议 | 状态 |
| --- | --- | --- | --- | --- |
| Q01 | 权威模型：谁决定本场状态 | A）服务端权威：命令进服务端状态机，产生状态与事件，舞台只渲染；B）舞台权威，服务端只排序记录（第三期延续）；C）分层：离散状态（步骤、黑屏、任务、发布）服务端权威；连续采样（指针、自由相机、笔迹）由来源端上行，服务端只分配 seq 与时间 | C。离散状态必须服务端权威才能做幂等、接管和重启恢复；连续采样走状态机只增加延迟 | 待定 |
| Q02 | 课件基线与本场副本形态 | A）基线＝去备注 `content_root`（`doc.checkpoint` 流程），本场＝从它载入的新 Workspace（`purpose=session`），Presenter 备注从原 Workspace 以本人权限读；B）长期克隆（整库 `VACUUM INTO`，含协作历史与备注），靠投影去备注；C）同一 Workspace 内按 Session 分区 | A。观众永远接触不到备注与协作历史；复用 fork 的载入路径；克隆的协作历史外泄问题（内核 review 已指出）自然消失。代价：本场 Workspace 没有原作品的 run 记录（本期不需要） | 待定 |
| Q03 | 观众互动的身份范围 | A）v1 只允许 Zone 用户与 SSO 认证的 External 互动，匿名／`guest:` 只能观看；访客互动等 Session Only Member；B）允许 `guest:` 互动，接受“每人一次”可被伪造；C）本期一并做访客身份 | A。P4-04／P4-05 的可靠性只在 A 下成立；用户已定 SOM 排在 SSO 之后 | 待定 |
