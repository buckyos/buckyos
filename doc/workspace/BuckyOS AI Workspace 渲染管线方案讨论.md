# BuckyOS AI Workspace 渲染管线方案讨论

> 状态：v0.2，2026-11-14，讨论稿。没有裁决，没有实施，也没有做过原型。本轮主要追加 §12–15：核心问题、风险、业界实践和待验证事项，不作路线结论。§1–11 保留初稿提议及其背景，其中的工作量和收益不是实施承诺。
>
> 起因：[打印（导出 PDF）TODO](../../notepads/aiws-print-pdf-export-todo.md) 评估渲染路线时，owner 的判断是：这带来渲染管线的重大变化。方向是尽量不让 Block 直接依赖下面是 HTML，而是用我们自己的、类似 canvas / DOM 的结构来组织渲染；不写 render 的 Block-control 反而改动较小；这是内核级别的改动，要专门讨论。
>
> 基线：初稿为 buckyos `7682af2da` 加当时的工作树改动；本轮补充核对为 `3b75db8f1` 加当前工作树改动。§2 保留初稿的实现记录，补充证据见 §13。表中的路径相对 `src/frame/aiworkspace/` 或 `src/frame/desktop/src/app/aiworkspace/`。

## 1. 初始提议（v0.1，未裁决）

以下保留初稿对节点树路线的提议，待 owner 裁决（§9）。本轮首先讨论的问题是：**要不要做自己的渲染抽象？** 这包括抽象的层次、布局结果由谁负责，以及哪些能力复用现成引擎；尚未选择 Z，也未冻结节点词汇。补充讨论见 §12–15。

**把 Block 的呈现契约从“输出 HTML”改为“输出一棵宿主定义的节点树”。HTML 变成屏幕上的一种输出方式，以及老 Block 和扩展 Block 的兼容路径。**

- **节点树。** 排版之前的结构：盒子、文字、图片、路径、分组。另有少数由宿主实现的复合节点（富文本正文、表格），和一个装 HTML 的节点。
- **后端。** 同一棵节点树交给不同的后端输出：屏幕（DOM）、PDF、静态 SVG。屏幕上的文字仍由浏览器排版。
- **三种写法。** 声明（模板，不写代码）、节点（代码返回节点树）、HTML（原样保留）。组合控件、投影和声明式 Block 属于第一种，定义文件不用改。
- **编辑器不动。** 富文本、表格等编辑器仍是 HTML，只在激活时挂载。
- **分阶段迁移。** 新旧两条路并存一段时间。先接上不写 render 的那一批和图形类 Block，再做富文本和表格。
- **起点是现成的。** 投影模板的节点（`label`、`shape`、`asset`）、组合控件的布局算法、脑图不依赖 DOM 的排版，已经是这个方向的雏形。

不改管线也有两种走法（§3）。三种走法的差别主要在：一个 Block 要写几份渲染，以及没有浏览器的地方能不能输出。

## 2. 现状

### 2.1 一个 Block 现在怎么画出来

1. `BlockDefinition` 给出几个 React 组件：必有的 `Static`，可选的 `Simplified`、`View`、`Editor`、`Inspector`（[registry.ts](../../src/frame/desktop/src/app/aiworkspace/ui/blocks/registry.ts)）。它们的输出都是 DOM。
2. `BlockHost` 按模式和状态选一个组件挂载，执行模式策略和挂载额度（编辑器 6 个，HTML 运行时 4 个），并把失败限制在这个 Block 里（[BlockHost.tsx](../../src/frame/desktop/src/app/aiworkspace/ui/blocks/BlockHost.tsx)、`ui/blocks/budget.ts`）。
3. 自由画布由 `RenderHost` 承载：一个世界层，摄像机是它上面的一个 CSS transform；每个 Block 一个绝对定位的帧；屏幕上很小的 Block 由宿主画占位；选中框和手柄画在一个 SVG 覆盖层里；命中靠空间索引做几何计算（[RenderHost.tsx](../../src/frame/desktop/src/app/aiworkspace/ui/canvas/render/RenderHost.tsx)）。
4. 流模式由 `FlowSurface` 承载，按兄弟顺序排成一列 DOM。放映用同一个 `RenderHost`，模式是 `show`。
5. 样式是一份约 1500 行的 `aiworkspace.css`，加上主题的 CSS 变量。

### 2.2 各类 Block 对 HTML 的依赖

| 类别 | 成员 | 现在怎么画 |
| --- | --- | --- |
| 内置内容 Block | table、richtext、record、asset、note | React 组件直接写 DOM 和 CSS |
| 纯 UI Block | frame、shape、label、connector、ink | React。图形部分是 SVG，路径由纯函数算出（`shapePaths`） |
| 控件 | 脑图、待办、日历、组合控件 | 布局是纯函数，Desktop 和 Deno 共用（`controls/`）。控件外观和子节点的绘制是 React |
| 投影子节点 | 控件按数据项实例化出来的节点 | 模板节点由宿主绘制，每个节点一个 span 或一个 svg（`ui/controls/data/ProjectedView.tsx`） |
| 扩展定义 | `composite`、`declarative`、`html` 三种 `kind` | `composite` 只有声明，由宿主执行，不运行代码。`declarative` 声明一组 items，由宿主解释。`html` 运行在同源 iframe 里，经 `window.aiws` 与宿主通信 |
| 其他内置 | 许愿格、目录、课堂控件、图表样例 | React |
| 编辑器 | 富文本（ProseMirror）、表格编辑等 | DOM |

### 2.3 已经不依赖 HTML 的部分

| 部分 | 情况 | 位置 |
| --- | --- | --- |
| 投影模板 | 一棵小树，节点只有 `label`、`shape`、`asset` 三种，带 `box`（位置）、`config`、`when`（条件显示）、`role`（按下的含义）、`edit`（就地编辑写哪个字段）。Desktop 和 Deno 共用 | `controls/projection.ts` |
| 组合布局 | `stack`、`grid`、`fixed` 三种算法都是纯函数 | `controls/composite.ts` |
| 脑图 | 文字测量经 `TextMetrics` 抽象：浏览器里用 canvas 测，Deno 里用近似值。断行、布局是纯函数。另有静态 SVG 输出 `controlSvg`，流模式里的脑图和许愿格预览在用 | `controls/measure.ts`、`controls/solve.ts`、`controls/svg.ts` |
| 画布宿主 | 命中、选中框、连接线路由都是宿主的几何计算，不问 DOM | `ui/canvas/render/` |
| 图形 | 轮廓由 `shapePaths` 算成路径 | `import-drawio/shapes.ts` |

最接近“我们自己的类似 DOM 的结构”的现成东西是投影模板：它已经是一套由宿主定义、由宿主绘制、两个运行环境共用的节点。

### 2.4 谁需要 HTML 以外的输出

| 需要 | 现在怎么解决 |
| --- | --- |
| 打印和 PDF | 没有 |
| 静态图（预览、缩略图） | 只有脑图有 SVG 输出。HTML 扩展 Block 靠实例上保存的一张快照图片 |
| 没有浏览器的环境（Agent、CLI、Zone 里的服务） | 只能拿到纯文本 `body`。脑图的布局可以算，文字宽度用近似值 |
| 大量 Block 或缩得很小时的轻量绘制 | `Simplified` 组件和宿主画的占位 |

脑图为了这些需要，已经单独做了一条不依赖 DOM 的路。打印会让每一种 Block 都面对同样的问题。

## 3. 三种走法

下表保留 X / Y / Z 的比较框架。共享节点描述、共享排版实现和共享绘制后端是不同程度的复用；不能仅由“节点树”推出打印质量或跨环境能力，进一步的风险见 §13。

| | X：不改管线 | Y：加第二份渲染 | Z：改成节点树 |
| --- | --- | --- | --- |
| 做法 | HTML 仍是唯一契约。打印等需求全部交给真正的浏览器引擎（无头浏览器或客户端壳的 WebView） | 屏幕管线不动。需要的 Block 另写一份打印渲染，其余 Block 走兼容路径。脑图现在就是这样 | Block 输出节点树，屏幕、PDF、SVG 都是它的后端。HTML 留作兼容路径 |
| 屏幕管线的改动 | 没有 | 没有 | 大。已迁移的 Block 在屏幕上也改走节点树 |
| 一个 Block 写几份渲染 | 通常一份；可能另有打印样式和呈现 | 新增输出实现，可复用其中的数据和几何逻辑 | 作者可能共用一份描述；宿主仍维护各后端和复合节点实现 |
| 打印质量 | 取决于引擎及打印样式，分页和打印专属内容仍需处理 | 取决于各 Block 的输出实现 | 待验证，取决于排版、分页、字体和兼容路径 |
| 屏幕和打印一致 | 同一引擎有利于一致，但页面宽度、打印样式和资源仍有差异 | 需要维护两种输出的一致性 | 共享描述不保证两个后端得到相同几何结果 |
| 没有浏览器的环境 | 引擎在哪里就能在哪里用 | 不依赖浏览器的输出实现能用 | 取决于排版、取数及资源链路；借浏览器排版的节点仍需要浏览器 |
| 扩展开发者 | 只写 HTML | 只写 HTML 也能打印，想提高质量再写第二份 | 三种写法（§4.8）。只写 HTML 仍然可以 |
| 新依赖 | 浏览器引擎，另行讨论 | 写 PDF 的库、字体文件，视内容可能需要排版库 | PDF、字体及可能的布局、文本排版库；不能预设与 Y 完全相同 |
| 主要风险 | 完全依赖引擎的讨论结果和它的体积 | 两份渲染长期不一致；每加一个输出目标再加一份 | 工作量大；两个后端排版要一致；双轨期长 |

说明：

- X 和 Z 不冲突。浏览器引擎有了以后，在 Z 里它是兼容路径的最好实现（把只有 HTML 的 Block 输出成一段 PDF）。
- Y 是我在打印 TODO 里最初的建议。它不动屏幕，起步最轻。它的问题是把“第二份渲染”固定成长期负担，每个 Block 的外观要在两处维护。
- Z 来自起初的方向性讨论。下面几节展开其设计假设，不代表已经决定采用。

## 4. 节点树的设计问题

本节保留初稿方案。排版前描述与排版后绘制结果可以同时存在；两者是否需要成为 BuckyOS 的公共契约，仍待讨论（§12）。

### 4.1 层次：排版之前，还是排版之后

“类似 canvas”和“类似 DOM”对应两个层次。

| | 排版之后：绘制清单（类似 canvas） | 排版之前：节点树（类似 DOM） |
| --- | --- | --- |
| 内容 | 已经定好位置的文字、路径、图片 | 盒子、文字段落、图片、路径，带尺寸约束和布局方式 |
| 谁排版 | Block 自己，或它调用的公共库 | 后端 |
| 宽度变化时 | Block 重新输出 | 后端重排 |
| 屏幕上的文字 | 可按已排版结果输出 DOM 或其他绘制结果；交互取决于源文映射和宿主接入，不能由“已排版”推断一定丢失 | 可输出 DOM 并交浏览器排版；选区、编辑和读屏仍需语义及生命周期支持 |
| 后端的难度 | 低，照着画 | 高，要实现布局和文字排版 |

建议：**Block 的契约是排版之前的节点树。绘制清单只作为 PDF、SVG 这些后端内部的中间结果。**

初稿的出发点是静态表现与 DOM 编辑器的衔接。但“必须由浏览器排版”不是已成立的约束；共享已排版结果并保留 DOM 文字也是需要比较的边界，现有脑图已按测量后的行输出 DOM（§13.2）。

### 4.2 节点词汇

从投影模板已有的三种节点出发，补到够用。

| 节点 | 作用 | 来源 |
| --- | --- | --- |
| 盒子 | 背景、边框、圆角、内边距，装子节点 | 新增 |
| 文字 | 一行或多行，带字号、粗细、颜色、对齐、换行或截断 | 现在的 `label` |
| 图片 | 资产或封面图 | 现在的 `asset` |
| 路径 | 图形轮廓、连接线、笔迹 | 现在的 `shape` |
| 分组 | 子节点按 `stack`、`grid`、`fixed` 排列 | 组合控件已有的三种算法 |
| 子 Block | 容器里的一个真实 Block，由宿主去取它的节点树 | slot |
| 复合节点 | 富文本正文、表格（§4.5） | 新增 |
| HTML | 一段只有屏幕后端能直接输出的 HTML（§4.7） | 现在的 HTML 扩展 Block |

每个节点可以带：条件显示、按下时的角色、就地编辑写入的字段、链接。这些投影模板里已经有。

词汇要小，语义要写死。它每多一项，就多一处两个后端必须一致的地方。

### 4.3 文字和字体

- **屏幕。** 浏览器排版，用设备上的字体。
- **其他后端。** 要自己断行，或者借浏览器排好再读结果（§4.9）。字体必须有文件可读，才能嵌进 PDF。
- **字体缺失。** owner 已定：打印时发现工作区用到的字体没有安装，提示用户打印可能失真，并引导去安装字体。字体的安装位置和默认字体在打印 TODO 里列为待确认。
- **一致性。** 屏幕和打印用的字体不同，或者断行算法不同，定宽文字框里的换行位置就可能不同。流模式不受影响，因为纸的宽度本来就不同。自由画布受影响。现在不同设备的屏幕之间已经有这个差别。

### 4.4 布局

- 自由画布上的 Block 有明确的盒子，布局只发生在 Block 内部。
- 组合控件的布局已经由宿主的纯函数完成，不依赖 DOM。
- Block 内部的布局用同一组算法（`stack`、`grid`、`fixed`），加上文字的固有尺寸。
- 屏幕后端把这组算法映射到 CSS；其他后端直接执行纯函数。两边的结果要一致，这是词汇必须小的另一个原因。
- 不引入通用的 CSS 布局。需要 CSS 自由度的 Block 留在 HTML 路径上。

### 4.5 富文本和表格：复合节点

这两个不适合拆成盒子和文字。

- **富文本。** 屏幕上静态表现和 ProseMirror 编辑器必须一模一样，否则进入编辑时文字会跳。所以它在节点树里是一个整体：节点带着文档内容，屏幕后端输出与编辑器相同的 DOM 和样式，PDF 后端按段落排版并报告每行的断点。
- **表格。** 屏幕上是虚拟滚动，每次取 200 行，还有单击即编辑。打印要的是全部行、按行分页和重复表头。两个后端要的东西差别很大，同样作为一个整体交给后端。
- 复合节点由宿主实现，每个后端一份。它们数量要少，新增一个就是给每个后端加一份实现。

### 4.6 交互和编辑器

- **按下、悬停。** 节点带角色，屏幕后端把 DOM 事件转成角色和动作。投影模板已经是这样。
- **编辑器。** 保持现状：HTML 组件，由 `BlockHost` 在激活时挂载。不纳入节点树。
- **画布级的交互。** 选中、拖动、手柄、连接线端点已经在宿主的覆盖层里，不受影响。
- **批注锚点、文字选中、浏览器查找、读屏。** 屏幕后端输出的是真正的 DOM 文字，这些能力保留。
- **动画和过渡。** 只属于屏幕后端，不进节点树。

### 4.7 HTML 的位置

- HTML 扩展 Block 不迁移。它在节点树里是一个 HTML 节点，屏幕上照旧运行在 iframe 里。
- 其他后端遇到 HTML 节点走兼容路径，办法可以换：
  1. 用实例上保存的快照图片，没有就输出占位。现在就能做。
  2. 有了浏览器引擎以后，让引擎把这一个 Block 输出成一段 PDF 或一张图。保真度最高，Block 不用改。
- 还没迁移的内置 Block 也按 HTML 节点处理。这样迁移可以一个一个来。
- owner 的底线是：只会输出 HTML 的 Block 也必须能打印。在浏览器引擎定下来之前，这条靠快照和占位只能算勉强满足。要完整满足，需要引擎，或者一个从 DOM 读位置的程序。后者支持的样式没有明确边界，建议不走。

### 4.8 作者接口

三种写法：

| 写法 | 谁用 | 改动 |
| --- | --- | --- |
| 声明 | 组合控件（`composition.json`）、投影模板、声明式 Block | 定义文件不用改。改的是宿主内部：把模板节点交给新的后端 |
| 节点 | 内置 Block，以及愿意写的扩展 | 从直接写 DOM 改为返回节点树 |
| HTML | HTML 扩展 Block、编辑器、暂未迁移的内置 Block | 不用改 |

“节点”这种写法有两种形态：

- **纯数据。** `render(输入)` 返回节点。输入里的数据由宿主先取好。它可以序列化、可以缓存、在任何环境都能跑。代价是现在的组件用 hooks 自己取数据（`useLoad`、`useVersion`），要改成先声明需要什么数据。
- **React 原语组件。** 内置 Block 仍然写 React，但只能用 `Box`、`Text`、`Image`、`Path` 这些原语。屏幕上它们直接输出 DOM。迁移小。代价是内核契约绑在 React 上，其他后端要带着 React 和数据层跑一遍。

建议：内核契约按纯数据定义，写进内核文档。Desktop 提供原语组件作为一种写法，它在屏幕上直接出 DOM，在其他后端收集成节点数据。声明式写法本身就是纯数据。取数据方式的改造放在第二步。

### 4.9 后端

| 后端 | 做什么 | 说明 |
| --- | --- | --- |
| 屏幕 | 节点映射成 DOM 和 CSS | 输出应与现在的 DOM 基本相同。投影节点现在的绘制（`LabelArt`、`ShapeArt`）可以直接复用 |
| PDF | 排版，分页，写文件 | 打印用 |
| 静态 SVG | 排版，输出字符串 | 预览、缩略图。取代 `controls/svg.ts` 这个只服务脑图的特例 |

PDF 和 SVG 后端的排版有两种做法：

- **自己排版。** 布局用已有的纯函数，文字用字体文件的度量断行。在浏览器和 Deno 里都能跑。富文本的段落排版是其中最大的一块。
- **借浏览器排版。** 在浏览器里用屏幕后端渲染一遍，再读出位置。因为节点词汇是封闭的，要读的 DOM 结构也是封闭的，这段程序有明确边界。只能在浏览器里用。

建议：简单节点（盒子、文字、图片、路径、分组）自己排版；复合节点先借浏览器排版，以后需要在没有浏览器的地方输出时再补自己的排版。

### 4.10 样式和主题

- 节点的样式是一个小集合：颜色、字号、粗细、对齐、边框、圆角、内边距、透明度。
- 颜色可以是主题记号（`accent`、`muted`、`danger` 等）。投影模板已经这样做，后端各自解析：屏幕映射到 CSS 变量，PDF 取浅色或深色主题的具体值。
- 阴影、渐变、滤镜先不进词汇。

## 5. 对各类 Block 的影响

下表是初稿估计。“小”“无”尚未覆盖复杂 SVG、PDF 导入文字、子 Block 挂载、流模式编辑生命周期和异步取数等条件，不能直接作为排期依据（§13）。

| 类别 | 改动 | 大小 |
| --- | --- | --- |
| 组合控件、投影子节点 | 定义文件不改。宿主内部把模板节点接到节点树 | 小。这就是“不写 render 的反而改动较小” |
| 声明式 Block | 定义不改。解释器从输出 React 改为输出节点 | 小 |
| 图形、Frame、连接线、笔迹、label、图片 | 改为返回路径、文字、图片节点 | 小 |
| 脑图 | 布局已经不依赖 DOM。节点的绘制改为节点树，`controlSvg` 并入 SVG 后端 | 小 |
| 表格 | 静态表现改为复合节点。编辑器不动 | 中到大 |
| 富文本 | 静态表现改为复合节点。编辑器不动。两者的外观一致要有测试守住 | 大 |
| 待办、日历 | 记录的投影部分已经是模板。月历格、工具条等外观是 React，要改写或留在 HTML | 中到大 |
| record、note、许愿格、目录、课堂控件、图表样例 | 逐个改写，或明确留在 HTML | 各自中等 |
| HTML 扩展 Block | 不改 | 无 |
| 所有编辑器 | 不改 | 无 |
| 画布宿主的覆盖层、命中、连接线路由 | 不改 | 无 |

## 6. 初步迁移设想（依赖路线裁决）

以下是选定节点树路线后的初稿设想，不是已确认的实施顺序。尤其是导出输入的固定基线与就绪协议，可能在首次输出 PDF 前就需要完成；阶段 2、3 的能力描述均为待验证目标（§13、§15）。

新旧并存：`BlockDefinition` 保留 `Static`，新增一个返回节点树的入口。有新入口的 Block，屏幕的静态表现、打印、静态 SVG 都走节点树；没有的，屏幕照旧，其他后端走兼容路径。

| 阶段 | 内容 | 做完以后 |
| --- | --- | --- |
| 0 | 定节点词汇、样式集合、布局语义，写进内核文档。定屏幕不变的验证办法（截图或 DOM 对比） | 有了契约 |
| 1 | 屏幕后端。把投影子节点、组合控件、声明式 Block 接到节点树。屏幕输出不变 | 不写 render 的那一批全部走新管线，用户看不出变化 |
| 2 | 图形、Frame、连接线、笔迹、label、图片、脑图改为返回节点。PDF 后端和 SVG 后端的简单节点部分 | 自由画布可以打印；脑图的 SVG 特例可以删除 |
| 3 | 富文本和表格的复合节点，先借浏览器排版 | 流模式可以打印 |
| 4 | 其余内置 Block 逐个决定：迁移，或留在 HTML | 双轨期结束，或有明确的长期名单 |
| 5 | 取数据方式的改造；复合节点自己排版 | 没有浏览器的地方也能输出 |

阶段 1 是整个改动的试金石：它不带来任何新功能，只验证“屏幕走节点树，行为不变”这件事做不做得到，代价有多大。建议先只做阶段 0 和 1 的一小部分作为原型，再决定后面。

## 7. 风险

| 风险 | 说明 | 应对 |
| --- | --- | --- |
| 两个后端排版不一致 | 屏幕靠浏览器，PDF 靠自己的排版，同一棵树可能排出不同的尺寸 | 词汇小，语义写死；对照测试；复合节点先借浏览器排版 |
| 静态表现和编辑器不一致 | 进入编辑时文字跳动 | 富文本和表格用复合节点，屏幕后端输出与编辑器相同的 DOM |
| 表现力下降 | 节点的样式集合比 CSS 小得多，现有外观的一部分做不出来 | 迁移前逐个 Block 核对；做不出来的留在 HTML |
| 屏幕性能回退 | 多了一层 | 屏幕后端的 DOM 量不多于现在；投影节点现在的轻量绘制保留；阶段 1 要量 |
| 双轨期长 | 两条路都要维护，测试矩阵变大 | 阶段 4 给出明确名单和期限 |
| 工作量大而收益靠后 | 阶段 1 没有新功能 | 阶段 2 就让打印可用，尽早兑现 |
| 扩展开发者的学习成本 | 三种写法 | HTML 一直可用；文档先讲声明和 HTML，节点写法作为进阶 |
| 复合节点变多 | 每个都要每个后端实现一遍 | 只收富文本和表格，新增要裁决 |

## 12. 核心问题：要不要做自己的渲染抽象？

本轮把讨论的起点前移：在决定节点树的八种节点、React 写法或迁移顺序之前，需要讨论 **BuckyOS 是否要定义并长期维护自己的渲染抽象，以及这个抽象覆盖到哪一层。** 本文不作这一裁决。

画像素的抽象太低，Block 作者要自行处理几乎全部呈现问题。`drawText(string, x, y)` 看起来简单，却隐含了字体匹配、字形整形、文字方向、断行和定位；如果再要求选中、复制、编辑与无障碍，接口还要提供文字与几何之间的对应关系。在浏览器产品中，交给 HTML / CSS 可以复用现成的这些能力，同时也把呈现契约和运行条件绑定到浏览器。

非浏览器环境已有 Pango、Qt、SkParagraph 等文本布局实践（§14）。这里未解决的选型问题，是它们怎样与 BuckyOS 的自由画布、流式文档、DOM 编辑器、打印和扩展模型衔接，而不是从零发明一种能够显示富文本的办法。

### 12.1 “自己的抽象”与“自己的实现”分开讨论

| 可以讨论的范围 | BuckyOS 需要长期负责什么 | 仍然依赖什么 |
| --- | --- | --- |
| 不新增跨后端呈现契约，保留 HTML，利用浏览器输出 | HTML Block 的生命周期、打印呈现和资源准备 | 浏览器的布局、字体及输出能力 |
| 只在导出内部定义中间结构，屏幕接口不变 | 导出结构、各 Block 的转换及输出行为 | 屏幕与导出之间的对应关系；各自使用的引擎 |
| 定义公共呈现协议，布局和绘制接现成引擎 | 节点语义、资源接口、引擎适配、能力差异、版本演进 | 引擎的功能边界、许可、平台和部署条件 |
| 进一步统一布局结果，并自行实现部分布局或文字处理 | 上述内容，以及测量、重排、缓存失效和一致性规则 | 未实现部分的库、字体和平台能力 |

这些范围可以组合，和 X / Y / Z 不是简单的一一对应。采用开源引擎不等于没有自有协议；定义自有协议也不等于必须自己实现字形整形、光栅化或 PDF 编码。需要比较的成本包括抽象本身的维护，而不只是第一版后端的代码量。

### 12.2 最小原语取决于服务对象

| 层次 | 可能的表达 | 能保留什么 | 单独不能解决什么 |
| --- | --- | --- | --- |
| 像素 | 位图及像素操作 | 最终外观 | 文字语义、无损缩放、重排、编辑 |
| 绘制结果 | 路径、图片、字形段、裁剪、变换、图层 | 已确定的几何和绘制顺序 | 如何从文档得到这些结果、分页及编辑状态 |
| 段落布局输入 | 文字、样式范围、内联对象、语言、宽度约束 | 原文及段落排版意图 | 最终字体、字形和行位置，需要排版系统求解 |
| 文档或呈现结构 | 盒子、段落、列表、表格、图片、Block 引用 | 内容关系及布局意图 | 每种节点的测量、分页和输出实现 |

`GlyphRun` 在本文中指使用具体字体的一段字形及其位置；它不是原始字符串。`Paragraph` 则是需要排版的段落输入。字形与原文字范围的映射可以伴随排版结果保留，用于命中、选区或文字提取，但这些映射本身还不是完整编辑器或无障碍实现。

业界存在“语义输入 → 排版结果 → 绘制后端”的分层（§14），因此排版前节点树和排版后绘制清单不必二选一。需要继续讨论的是：哪些层作为 Block 作者接口，哪些只在宿主内部存在，哪些直接采用第三方接口；BuckyOS 是否有足够的跨后端需求承担其中任一层的公共契约。

### 12.3 谁决定最终布局，仍然开放

- **浏览器决定。** 屏幕及导出都利用浏览器布局，需要验证服务端部署、手机入口、打印样式、完成信号和输出质量。
- **共享排版系统决定。** 不同输出消费已确定的布局，需要验证如何承载 DOM 编辑、文字选择、输入法、查找和无障碍。
- **各后端分别决定。** 共用内容和样式语义，保留各自排版，需要定义哪些差异允许存在，哪些会构成内容错误。

三种边界都有代价。是否需要逐行相同、允许怎样的字体替代、是否要求没有浏览器也能输出，以及何时需要这些能力，都是决定抽象范围的输入；不能由“一个 Block 只写一份”替代这些判断。

## 13. 方案风险补充

以下是设计假设及潜在回归，尚无新管线原型证明它们已经解决。代码链接用于说明当前约束，不把现有实现特征当成本方案已经引入的故障。

### 13.1 三条路线各自承担的风险

| 路线 | 主要风险 | 需要什么证据 |
| --- | --- | --- |
| X：保留 HTML，使用浏览器输出 | 引擎的部署体积和更新成本；长文档的内存及执行时间；屏幕 DOM 不等于打印 DOM；动态脚本、虚拟滚动和资源加载影响完整性 | 实际运行环境中的全量输出、分页、资源就绪、只读执行及性能记录 |
| Y：增加输出实现 | 外观和语义逐步分叉；新增输出目标可能再加适配；屏幕回归测试不能覆盖导出；兼容内容质量不一 | 明确复用的数据、几何与样式范围；同一内容的多输出对照及维护成本 |
| Z：公共节点或场景协议 | 宿主承担布局、字体、交互语义和版本治理；不同后端能力难以完全对齐；迁移与长期兼容并存；“一份描述”仍可能对应多份实现 | 契约边界、代表性内容覆盖、后端差异规则及端到端原型 |

### 13.2 共享节点不等于共享布局

§4.4 设想屏幕映射 CSS、其他后端执行纯函数。当前 [composite.ts](../../src/frame/aiworkspace/controls/composite.ts)主要按已知或测得的矩形摆放子节点；这与通用的约束布局并非同一范围。长文字进入受限宽度的 grid、嵌套盒子或自适应容器时，宽度分配和文字测量互相影响，两边可能得到不同高度，进而发生重叠、裁断或分页差异。

另一方面，现有脑图 [nodeBlock.tsx](../../src/frame/desktop/src/app/aiworkspace/ui/controls/mindmap/nodeBlock.tsx)已经按测量后的行输出 DOM。预先断行与保留 DOM 文字并不互斥；是否保留查找、选区和编辑体验，需要具体测试，不能按抽象层次直接判定。

待验证：盒子尺寸由哪个系统决定，文本测量怎样参与布局，尺寸变化如何更新命中及连线几何；相同字体和宽度下允许多大的几何误差、是否允许断行不同。

### 13.3 “简单文字”也需要完整的处理边界

当前 [measure.ts](../../src/frame/aiworkspace/controls/measure.ts)包含近似字宽、正则分词和逐 code point 拆分。这是现有脑图的实现背景，不能直接证明它足够支持新的通用文字节点。字体齐全时，组合字符、emoji、连字、中文标点禁则和双向文字仍可能导致错误。

字体名称也不足以确定字形：具体字体文件、字重、可变字体参数、回退链和加载状态都会影响结果。屏幕能够使用某个系统字体，不代表导出端已经取得同一字体的数据。字体缺失提示不能代替文字正确性保证。[HarfBuzz 对字形整形的说明](https://harfbuzz.github.io/what-is-harfbuzz.html)、[CSS Text 的断行与字形处理规则](https://www.w3.org/TR/css-text-3/)提供了问题范围。

待验证：支持的文字和字体范围、字体供应方式、缺字策略，以及字体变化后的缓存失效。流模式可以按纸宽重新排版，但依然需要正确断行、完整内容和合法分页；§4.3 的“不受影响”仅能理解为不要求复刻屏幕换行。

### 13.4 读 DOM 位置到可选可搜 PDF，中间仍有缺口

§4.9 假设节点词汇封闭，因此可从 DOM 读位置。布局矩形并不是完整的字形绘制数据；例如 [Range.getClientRects](https://www.w3.org/TR/cssom-view-1/#dom-range-getclientrects)提供矩形，不能直接替代字体、字形及原文映射。截图能记录外观，但不会自动得到可选可搜的文字；重新让 PDF 库排文字则需要再次验证一致性。

当前富文本的结构也不完全封闭：[schema](../../src/frame/aiworkspace/schemas/richtext.basic.v1.json)允许 `object_embed` 指向其他 Block，[StaticRichText](../../src/frame/desktop/src/app/aiworkspace/richtext/RichTextEditor.tsx)再通过 portal 挂载它们，内部可能包含未迁移或 HTML 内容。

待验证：测量结果究竟包含哪些信息、如何转换为 PDF、嵌入对象何时就绪及怎样提供尺寸；或是否改由浏览器直接生成输出片段，以及片段怎样参与最终页面。将富文本称为复合节点，本身不能限定这些工作。

### 13.5 行断点不足以独立承担分页

§4.5 的“报告每行断点”还没有说明跨页后的片段如何继续绘制。列表、引用、表格、嵌入对象都有额外约束：表头重复占用下一页空间，边框与内边距可能需要按片段处理，超高的不可拆分内容需要明确策略。

待验证：测量、合法断点、片段绘制及续页之间的契约；嵌套容器能否拆页；整块高度与断点是否足够，还是需要“给定宽度和剩余页高，返回当前片段及续页状态”的接口。[CSS Fragmentation](https://www.w3.org/TR/css-break-3/)展示了这一类问题，但不意味着本项目需要实现全部 CSS 分页语义。

### 13.6 纯数据输出与 React 原语不能代替数据就绪协议

阶段 2 涉及的绑定 label 已通过 [useBoundValue](../../src/frame/desktop/src/app/aiworkspace/ui/blocks/labelBlock.tsx)异步读取 record 或 table；[useLoad](../../src/frame/desktop/src/app/aiworkspace/state/hooks.ts)在 Effect 中加载。仅遍历 React 原语或执行一次服务端渲染，不能保证获得最终数据；React 的 Effect 不在服务端渲染时运行，见 [官方说明](https://react.dev/reference/react/useEffect#caveats)。

可能的失败包括空文字、尚未加载的图片、只打印部分表格行，以及导出期间异步读取进入新的数据版本。即使先固定了工作区结构，也要确认后续读取、字体和资源都使用相应基线。

待验证：依赖收集、只读快照、全量枚举、资源标识、完成信号、失败及取消。全部 hooks 的改造是否后置可以讨论，但首次导出如何取得完整且一致的输入，不能等阶段 5 才回答。

### 13.7 已有内容可能超过“最小节点词汇”的表现力

[ShapeArt](../../src/frame/desktop/src/app/aiworkspace/ui/blocks/shapeBlock.tsx)既画基础路径，也接受清洗后的 SVG body；[SVG 处理](../../src/frame/aiworkspace/import-drawio/svg.ts)涉及的能力超过少量路径和纯色。shape 还可以包含 PDF 导入的定坐标文字 span、独立样式和 `textLength`。把这些内容重新作为普通段落排版，可能破坏已有外观。

待验证：用“现有内容特性 → 新节点能力”逐项对照，而不只按 Block 类型判断迁移完成；复杂 SVG、预排版文字和不支持的效果走哪条路径，结果是否可搜索、是否仍可编辑。仅有矩形和短 label 的成功样例，不能支持“图形迁移小”的整体判断。

### 13.8 子 Block、编辑与交互不一定能保持宿主完全不变

当前 [RenderHost](../../src/frame/desktop/src/app/aiworkspace/ui/canvas/render/RenderHost.tsx)将真实 Block 扁平挂载为独立 frame，并维护稳定 DOM 顺序、全局层级、LOD 和离屏状态。如果新节点树中的子 Block 直接递归变成嵌套 DOM，就可能改变挂载所有权、裁剪和层级；若布局结果没有同步到几何索引，画面还会与手柄、命中及连线端点分离。

“输出 DOM 文字”也不能自动保留键盘、焦点、链接、禁用状态和读屏语义。当前 [declarative.tsx](../../src/frame/desktop/src/app/aiworkspace/ui/extensions/declarative.tsx)使用的原生按钮和列表，需要对应的语义接口。编辑器生命周期也分模式：[FlowSurface](../../src/frame/desktop/src/app/aiworkspace/ui/canvas/FlowSurface.tsx)在编辑模式直接激活非 HTML Block 的编辑器，所以初稿“所有编辑器只在激活时挂载”不能泛化为统一的按需挂载策略。

待验证：子 Block 是引用既有 frame 还是接管其生命周期，节点与源实体的稳定身份、事件边界、编辑焦点、输入法及选区怎样保持。截图和 DOM 数量均不足以单独验收这些行为。

### 13.9 HTML 兼容既有内容新鲜度，也有执行边界

当前 [bridge.ts](../../src/frame/desktop/src/app/aiworkspace/ui/extensions/bridge.ts)保存的快照只有资源信息，没有对应的输入或定义版本。数据更新后导出旧快照，属于内容正确性问题；位图快照与“文字可选可搜”的要求也需要明确例外。占位表示内容未输出，不能直接作为完整兼容的证明。

若接入浏览器重新执行动态 HTML，还需处理新的导出上下文：[htmlRuntime.ts](../../src/frame/desktop/src/app/aiworkspace/ui/extensions/htmlRuntime.ts)会执行扩展脚本，现有 bridge 包含读取、提交和上传等能力。直接复用并不能证明满足打印的固定基线、无写入要求。这是导出入口需要定义的契约，不是把现有同源 iframe 模型判定为本次新增漏洞。

待验证：快照版本或过期标记、动态脚本策略、资源访问边界、只读会话、渲染完成信号、超时和取消；输出结果如何区分当前内容、历史快照及占位。

### 13.10 性能与维护成本不能只按 DOM 数量估计

节点树增加的成本可能出现在树构造、序列化、文字测量、字体缓存、重新排版和失效传播中。导出长表格时还涉及全量取数、隐藏 DOM 或布局结果的内存。屏幕 DOM 数量不变，并不意味着拖动和编辑性能不变。

待验证：增量更新粒度、缓存键、资源释放、取消延迟、代表性工作区的帧时间、导出耗时和峰值内存。多后端的测试矩阵、第三方接口变化和长期 HTML 路径也会成为持续成本，不能仅计入一次迁移工作量。

## 14. 业界在渲染抽象上的实践

以下资料于本轮讨论核对，重点记录项目实际划分的职责。它们提供设计经验，不构成 BuckyOS 已选定某个库或公共协议的依据。设计提案、现有实现和本文引申分别说明；引入依赖及其许可、体积和平台适配仍需另行评估。

### 14.1 Skia / SkParagraph：文字处理与绘制分开

Skia 的 [Text API Overview](https://skia.org/docs/dev/design/text_overview/)专门讨论了文字的特殊性：它可以使用普通绘制操作，但从字符得到字形，需要独立且复杂的处理。该设计提案希望处理结果可以用于 DOM、WebGPU 或 WASM renderer，不绑定 Canvas；这不是浏览器已经普遍实现的标准接口。

实际的 [SkParagraph Paragraph 接口](https://github.com/google/skia/blob/main/modules/skparagraph/include/Paragraph.h)提供按宽度布局、绘制、行指标、范围矩形、命中及字形访问；[Builder](https://github.com/google/skia/blob/main/modules/skparagraph/include/ParagraphBuilder.h)接受文字、样式和内联占位对象。这里可观察的边界是“段落对象”与“字形绘制”，而不只是 `drawText`。

对本讨论的启发：段落可以是独立的可测量、可查询对象，文字排版不必由每个 Block 实现。仍需验证：文档分页、DOM 编辑器衔接和多后端效果覆盖。[CanvasKit](https://skia.org/docs/user/modules/canvaskit/)提供浏览器 WASM 接口；Skia 的[原生 PDF 后端](https://skia.org/docs/user/sample/pdf/)不能据此被推断为标准 CanvasKit 包已直接开放的同等能力。

### 14.2 Parley / Vello：把排版结果交给绘制系统

[Parley](https://github.com/linebender/parley)负责富文本布局；其 [Layout 输出](https://github.com/linebender/parley/blob/main/parley/src/layout/line.rs)包含定位后的字形段和内联盒子，并提供文字选择及编辑辅助。[Vello](https://github.com/linebender/vello)负责二维绘制。这提供了研究“文字服务输出什么、renderer 消费什么”的具体接口。

对本讨论的启发：绘制系统可以接收已经确定的字形及位置，不必再次解释字符串；布局系统则保留原文、行与几何的关系。仍需验证：字体供应、与 BuckyOS 文档的映射、分页、输入法及无障碍接入。有选择和命中接口，不等于有完整编辑器。

该项目栈仍在演进，不能仅凭早期设计文章判断当前依赖或后端状态；是否适合成为长期公共契约，需要按拟采用版本另做评估。

### 14.3 Typst：文档语义和固定位置的输出结构并存

Typst 的[库架构](https://docs.rs/typst/latest/typst/)区分带样式的内容与排版后的页面结果。[FrameItem](https://github.com/typst/typst/blob/main/crates/typst-library/src/layout/frame.rs)包含分组、已经完成字形整形的文字、图形、图片、链接和标签；分页文档的结果再由输出模块处理。

对本讨论的启发：作者结构与绘制结构可以同时存在，降低到绘制层时仍可保留链接等信息。仍需验证：这样的结构是否适合自由画布和交互编辑，怎样与现有 DOM、ProseMirror 及 Block 数据模型衔接。完整排版编译器的成功，不等于其内部结构可直接成为 Workspace 的公共接口。

### 14.4 Piet：统一 API 与统一实现的取舍

[Piet](https://github.com/linebender/piet)定义跨平台二维 API，并对接平台的绘图系统；其 [TextLayout](https://docs.rs/piet/latest/piet/trait.TextLayout.html)是可绘制、可查询行信息及命中的文字对象。仓库目前注明处于维护模式，没有计划中的主要 API 扩展。

对本讨论的启发：可以统一调用契约而继续复用平台能力，不一定随应用携带整套 renderer。对应的代价是平台间语义和度量差异仍需治理；Piet 的文字尺寸文档也明确列出了尚未严格统一的行为。统一接口本身不能作为输出完全一致的证明。

### 14.5 Pango / Qt：非浏览器的段落及文档实践

[PangoLayout](https://docs.gtk.org/Pango/class.Layout.html)接受字符串和属性，负责段落换行、对齐、省略等，并提供文字位置与几何位置的转换；其[处理管线](https://docs.gtk.org/Pango/pango_rendering.html)区分文字分段、字形整形、断行和绘制。

Qt 的 [QTextDocument](https://doc.qt.io/qt-6/qtextdocument.html)持有富文本文档，[QAbstractTextDocumentLayout](https://doc.qt.io/qt-6/qabstracttextdocumentlayout.html)提供绘制、命中、页数及内联对象等接口，标准布局支持列表、表格和内联图片。

这两类实践说明非浏览器环境有现成的段落和文档能力可研究。它们的粒度不同，也都不是现有浏览器 DOM 的直接替代品；需要分别评估接入成本、文档模型差异和具体运行环境。

### 14.6 React-pdf / Textkit：少量作者原语背后的完整管线

[React-pdf 的管线说明](https://react-pdf.org/blog/rendering-process)将内部数据树、样式及资源准备、布局、分页与 PDF 绘制分阶段处理。[Textkit](https://github.com/diegomura/react-pdf/blob/master/packages/textkit/README.md)处理带样式文本及字形、位置、索引映射；盒子布局与文本排版也有各自的职责。

对本讨论的启发：React 可以是一种作者写法，少量组件背后仍需要独立的数据、字体、布局和分页系统。这个案例可用于估算节点路线的实际范围，但不能证明一份 React 描述天然同时满足屏幕、编辑和 PDF 的要求。

### 14.7 Taffy / Yoga：只共享盒子布局也是一种边界

[Taffy](https://github.com/DioxusLabs/taffy)提供 Block、Flexbox、Grid 布局；[Yoga](https://www.yogalayout.dev/docs/advanced/external-layout-systems)提供 Flexbox 及外部测量接口。文本测量由外部系统在约束下完成，而不是由这些盒子布局库包办。

对本讨论的启发：可以只复用盒子几何，不同时决定段落、文档和绘制协议。仍需验证：外部文字测量怎样响应宽度约束，内容变化如何触发重排，以及这类算法与现有组合控件布局是否相容。它们不直接解决字体、分页或编辑问题。

## 15. 保持开放的问题与可验证事项

下面列出后续讨论需要的输入，不给出推荐路线，也不把验证清单当成已经批准的实施计划。

### 15.1 需要分别回答的问题

| 问题 | 需要澄清的边界 |
| --- | --- |
| 是否需要自有渲染抽象？ | 哪些实际需求无法由现有 HTML 路径或局部输出适配以可接受成本完成？收益是否足以覆盖协议的长期维护？ |
| 抽象服务谁？ | Block 作者、内部导出器、扩展作者是否需要同一接口？能否先仅在内部使用而不冻结公开协议？ |
| 是否需要两种表示？ | 排版输入与排版结果分别保留什么，哪些字段由 BuckyOS 定义，哪些采用第三方接口？ |
| 谁决定最终几何？ | 浏览器、共享排版系统，还是各后端分别排版？哪些差异允许存在？ |
| 复用到哪一层？ | 只复用字形整形、段落、盒子布局，还是完整文档排版？自定义协议如何承受所接引擎的变更？ |
| 哪些能力必须脱离浏览器？ | Agent、CLI、服务端、手机分别需要生成什么输出，时间要求是什么？ |
| 文字需要保留哪些语义？ | 原文字范围、选区、查找、复制、链接、输入法及无障碍分别由哪层负责？ |
| 数据和资源怎样固定？ | 基线、字体、图片、异步读取及导出完成信号如何贯通？ |
| HTML 兼容到什么程度？ | 当前内容、历史快照、占位能否分别接受？动态执行与只读导出的边界是什么？ |
| 如何处理超出词汇的已有内容？ | 复杂 SVG、预排版文字、嵌入 Block 的保真、可搜索和可编辑要求如何取舍？ |
| 何时可以扩大迁移？ | 需要哪些正确性、交互、性能和维护成本证据；哪些失败应触发缩小抽象范围或改换路线？ |

### 15.2 能暴露关键风险的验证内容

| 场景 | 需要观察什么 |
| --- | --- |
| 固定字体、固定宽度的复杂 label | 中文标点、混合字重、emoji、组合字符、双向文字的字形、断行、截断与文字提取 |
| 异步绑定 label 和图片，导出期间继续编辑 | 内容是否完整、是否来自同一基线、资源未就绪时怎样失败或降级 |
| 含列表、引用、链接及嵌入 Block 的跨页富文本 | 分页、续页装饰、嵌入对象边界、文字顺序、链接区域及内容完整性 |
| 超过当前单次取数窗口的表格 | 全量行、重复表头、多行单元格、超高行；不同纸宽下的重排 |
| 真实导入的 SVG 和 PDF 内容 | 复杂效果、预排版文字、缩放后外观和文字可搜索性 |
| 嵌套组合控件与跨容器连线 | 子 Block 挂载、编辑置顶、命中、拖入拖出、离屏重入和编辑焦点 |
| 键盘、触摸、中文输入法与读屏 | 激活、选区、按钮禁用、焦点恢复及编辑模式切换；不能只比较截图 |
| 动态 HTML 与保存的旧快照 | 输出新鲜度、只读执行、完成信号、超时、取消及降级标记 |
| 大量 Block 和长文档 | 帧时间、增量更新范围、导出耗时、峰值内存和取消后的资源释放 |

验证前还需约定容许的几何误差、断行差异、降级规则和性能预算，记录字体、引擎及测试环境。投影节点和短 label 的原型可以提供局部证据，但不足以独立回答“要不要做自己的渲染抽象”；这些材料用于后续裁决，本轮不选择方案。
