# BuckyOS AiWorkspace 核心架构设计冻结思路

> 文档性质：架构设计冻结思路整理稿。  
> 依据：2026 年 10 月 21 日关于 BuckyOS AI Workspace 的连续口述讨论。  
> 本文中的“冻结方向”指本轮讨论希望固定的架构原则；“现有能力”仅指口述明确说明已经具备的能力；“计划与预留”不代表已经实现。具体协议、算法及权限细则尚待确定的部分，集中列入文末待决事项。

## 一、冻结目标：稳定数据内核，明确计算与扩展边界

### 1.1 从可视化工具走向数据服务化的 API Runtime

AI Workspace 的画布和对象树，在组织应用的方式上，可以类比 Delphi、VB 时代的可视化开发工具：用户通过组件、属性和交互逻辑构建自己的工作环境。

根本变化在于，Workspace 不只有前端界面，还拥有可以提供数据服务的后端。画布背后的对象体系因此逐步成为一种新的 API Runtime：数据可以被命名、读取、修改、引用，也可以通过 Workspace 的服务接口供其他应用使用。

这种能力使功能扩展变得很快，也使内核边界成为必须提前冻结的问题。如果每一种新功能都向内核加入新的类型、操作、计算逻辑和权限例外，内核最终可能同时面临性能失控、兼容性破坏和安全边界弱化。

本轮冻结的重点不是列出所有功能，而是确定：**什么必须由稳定的数据内核承担，什么可以由已有数据结构组合表达，什么必须放在独立的计算与扩展环境中执行。**

### 1.2 整体架构主线

Workspace 的核心应当围绕一组可预测的状态与操作建立：以封闭的数据类型表达状态，以命名数据源提供访问，以版本和 Command 表达修改，以事务 Apply 和确定性合并处理协作。

Block 承担界面和交互；客户端脚本、公式、后台任务和 AI 能力承担不同形式的计算。其中，复杂任务使用独立的用户计算资源，不能因为挂接到 Workspace，就自然进入 Workspace 数据内核的计算空间。

由此形成以下职责划分：

| 层次或对象 | 主要职责 | 本轮关注的边界 |
| --- | --- | --- |
| 数据内核 | 数据类型、存储、读取、版本、Command、事务 Apply、确定性合并 | 语义有限、行为明确、可独立复现 |
| 数据源与 Source | 命名访问、外部引用、同步、本地可用版本 | 外部变化不直接穿透到核心 UI 依赖 |
| 画布与 Block | 数据投影、交互、界面组织 | 与共享数据源分离 |
| 用户 UI State | 保存某个用户在某个 Block 上的界面状态 | 跨设备持久化，不混入多人共享数据 |
| 计算扩展 | 客户端脚本、公式、批处理、函数对象、AI 任务 | 执行位置、权限身份、资源归属明确 |
| Presentation | 固定版本上的演示、同步事件与回放 | 独立于原 Workspace 的持续编辑 |

## 二、基础对象模型与命名

### 2.1 Workspace 的命名数据空间

在数据源模式中，Workspace 呈现一组可以通过名字访问的数据。名字可以采用类似 `A.B.C` 的分层形式，使数据构成一个命名对象空间。

这里的关键是“每个数据可以被准确引用”，而不是在本轮冻结名字的完整语法。路径转义、数组寻址、跨 Workspace 名称和 URL 之间的映射，仍需要后续协议定义。

数据源的基本视图为：

| 属性 | 含义 |
| --- | --- |
| Name | 数据名或变量名 |
| Type | 数据类型 |
| Value | 当前值 |
| Source | 来源及其引用、同步、缓存策略 |

这是用户和架构层面的概念结构，不代表已经确定最终序列化字段。

### 2.2 数据类型、来源与求值方式应分别理解

“它是什么类型”“它从哪里来”“它的值如何产生”是不同的问题。

一个表格可以是 Workspace 内部维护的表格，也可以是外部查询结果的只读副本；一个已经定义返回类型的属性，可以直接保存值，也可以保存用于求值的公式。因此，外部引用和公式不能简单地与 Number、Rich Text、Table 等数据类型混成同一层次的类型清单。

本轮的方向是保留这些不同维度，但不提前确定 `Source`、公式定义和缓存结果最终如何编码。

### 2.3 Named Object 与版本身份

Workspace 的类型体系需要与底层 NDN 的 Named Object 模型对齐。对象能够获得 `Object ID / Content ID`，通过 ID 确定一个具体内容版本。

这里需要区分三种概念：

| 概念 | 作用 |
| --- | --- |
| 数据源名称 | 在 Workspace 中找到某项数据 |
| Object ID / Content ID | 确定对象的具体内容版本 |
| URL | 表达资源位置或服务化访问入口 |

这三者应能够衔接，但不是同一个概念。一个稳定的数据源名字或访问入口可以继续指向更新后的状态，而某个内容版本的 ID 用于确定该版本本身。具体映射方式尚未冻结。

## 三、数据类型系统：封闭、有限、行为完全定义

### 3.1 类型系统是最严格的长期兼容性边界

数据源层应参考 JSON 的经验，用一组有限的、内置的通用原子类型和容器类型，覆盖用户定义状态的主要需要。

应用可以组合这些类型，定义自己的数据结构，但内核不应随着应用种类不断增加专用原生类型。类型一旦确定，原则上保持不变；即使只是新增一种类型，也应是最谨慎的内核演进之一。

原因不只是序列化兼容性。每个类型还携带操作集合、一致性规则、冲突处理规则和自动合并行为。修改类型语义，可能使旧数据、旧客户端和旧命令流不再具有相同含义。

**冻结方向：每一种内核类型及其操作都必须有明确的行为边界，避免未定义行为（UB）。**

### 3.2 结构化类型

#### 基础原子类型与普通文本

数字、普通字符串等基础类型沿用通用数据表达思路，本轮没有逐项列举完整清单。

普通文本可以考虑设置单值长度上限；纯文本协作可以参考已有的文本合并思路，但具体限制和算法不在本轮确定。

#### 富文本 Rich Text

富文本是独立的结构化类型，不应仅被视为普通字符串。其他位置引用时，可以转换为标准字符串表达，但其内部仍需保存格式和结构。

富文本可能很长，也可能由多人共同编辑。内部按段落组织、对不同段落的操作进行自动合并，是本轮讨论的方向；格式相关的冲突需要专门处理，不能直接把纯文本的合并语义套用过去。

本轮明确的是富文本的独立地位及协作需求，不是已经确定某一种富文本协议。

#### 表格 Table

表格对象比数组具有更丰富的语义。它以二维行列结构为基础，需要专门考虑行、列和单元格上的协作操作。

讨论中区分了两种表格形态：

| 形态 | 数据约束 | 关注点 |
| --- | --- | --- |
| 标准表格 | 有明确 Schema；同一列的数据遵循统一类型 | 行列操作、记录修改、类型约束 |
| 自由表格 | 类似电子表格；不同 Cell 可以具有不同类型 | 单元格操作、坐标引用，以及未来的单元格公式 |

是否以同一个内核类型的不同配置表达两种表格，还是分别定义，以及自由表格的具体支持范围，尚未形成最终协议。

#### 简单命名对象／JSON 对象

扩展中常用的一种数据是完整的 JSON 对象。其默认编辑语义不是内部字段的自动合并，而是锁定编辑、整体更新。

当用户 A 锁定对象进行编辑时，其他用户只读；完成后以新对象整体替换。不能因为对象内容使用 JSON 编码，就推定内核允许任意路径上的并发局部修改。

同时，讨论中存在 Big JSON 的扩展提议：对于特别大的 JSON，使用 JSON Patch 做隔离的局部更新。该提议尚未冻结，不能与当前默认的整体更新语义混用。

#### KV 与数组容器

基本容器包括 KV 容器和数组容器。对象数组还涉及元素类型约束：各项都可以是“对象”，但对象内部 Schema 未必相同。

数组是否必须同类型、对象数组如何容纳不同 Schema、元素如何定位及合并，仍需进一步明确。

尤其需要区分：**作为一个整体更新单元的 JSON 对象，与具有明确子项操作语义的 KV／数组容器，不能仅因外观都像 JSON 就视为同一种协作对象。**

### 3.3 非结构化类型：统一以 URL 表达

图片、音乐、文件等非结构化内容，无论原来位于本地磁盘、Workspace 内部还是外部网络，都应使用统一的 URL 表达资源引用。

插入到 Workspace 中的资源可以成为内部资源；也允许描述外部资源，例如表格中的一项引用某个 HTTP 音乐资源。是否同步到本地、何时同步以及是否允许直接外链，由数据源和引用策略进一步约束。

从访问形态看，非结构化资源主要分为两类：

| 形态 | 含义 | 更新方式 |
| --- | --- | --- |
| Stream | 打开后得到一段流内容，例如图片、音频、文件 | 外部编辑完成后，以新版本原子更新 |
| Folder | 一组文件、流或 URL 的组合 | 完整准备新资源集合，再整体切换引用 |

非结构化单体不在数据内核中进行内容级协作合并。例如，图片在其他软件中改好后，Workspace 接收一个整体的新版本。

### 3.4 Folder 的组合与原子切换语义

Folder 不只是操作系统目录的外观，还可以表达一组需要一起使用的资源。例如，一个应用顺次播放一组 URL，Folder 可以承担该资源集合的定义。

当几个文件必须配套更新时，应先在新位置准备完整版本，再把引用从旧 Folder URL 切换到新 Folder URL。这样，访问者不会看到第一个文件已更新、其余配套文件仍未更新的中间状态。

Folder 是否直接定义为数组、是否具有顺序、如何表达成员和版本，尚未冻结。保留 Folder 概念的一个原因，是它符合使用者对文件和目录的传统理解。

### 3.5 Folder 作为输入输出契约

Workspace 可以约定特殊文件夹的含义。例如，“产物文件夹”提供这个 Workspace 的最终产物，其他应用按约定访问该入口即可取得结果。

因此，Folder 不仅可以组织资源，也可以成为 Workspace 与其他应用之间的输入输出契约。稳定入口与具体产物版本的关系，还需要与 URL 和 Named Object 规则共同确定。

## 四、Source：外部引用、同步与本地可用性

### 4.1 内部值与外部只读引用

`Source` 为空时，数据由当前 Workspace 内部维护。

当 Source 指向外部引用时，Workspace 通过同步获得一个内部可用值，Block 再通过当前 Workspace 的数据源名字访问它。最常见的场景是两个 Workspace 之间引用数据。

基本路径是：

```text
外部数据／外部 Workspace
          ↓ 同步
当前 Workspace 的只读数据源及本地版本
          ↓ 引用
当前 Workspace 的 Block
```

原则上不鼓励 Block 绕过数据源，直接读取和渲染其他 Workspace 的业务数据。外部访问、数据同步和界面渲染应有清晰边界。外部内容转为内部可访问资源，也服务于前端跨域访问处理和数据独立性：UI 尽量依赖 Workspace 已持有的数据，而不是依赖源站持续可用。

### 4.2 自动同步与手动同步

自动同步可以由系统较频繁地主动刷新实现，不依赖所有外部服务都提供通知机制。手动同步则由用户在数据源界面明确触发，也可以只刷新某一个属性。

对于使用数据源的 Block，两者都是只读数据。Block 不必承担同步时机管理，也不必因为自动或手动策略不同而改变使用方式。

同步成功后切换到新值；已有数据源同步失败时，继续保留最近一次成功获取的值。

当一个 Workspace 同时存在多个外部属性时，仍有一个重要待决项：一次自动刷新，是各项分别成功后更新，还是全部完成后统一提交？口述提出了这一问题，但没有确定跨数据源刷新事务。

### 4.3 查询式 Source

Source 不必只能指向一个完整的命名对象，也可以是带查询参数的 URL。

例如，源数据集有数百万或数千万条记录，而当前表格只需要查询结果中的前 100 条。此时应将这部分结果同步到 Workspace，而不是先复制全部原始数据，再在本地使用其中很少一部分。

这类查询式数据源通常适合显式、手动的同步方式，但本轮没有把手动同步设为唯一规则。

### 4.4 首次创建必须获得一个可用版本

对于纳入数据源管理、作为 Workspace 内部依赖的外部内容，首次创建成功应意味着：至少已有一个可用版本被获取，并进入 Workspace 的存储空间。

下载或同步尚未完成时，数据源处于创建过程；只有成功后才成为其他 Block 可以引用的有效数据源。失败则不能把一个不可用的源当作创建成功。口述中也提到，首次导入可能使整个 Workspace 呈现下载状态；具体状态展示层级尚未确定。

这个原则同时适用于结构化数据和作为数据源管理的非结构化资源。它将外部源的后续可用性与 Workspace 当前版本的可用性分开，避免源站失效直接破坏已经建立的核心数据依赖。

### 4.5 Source 同时包含缓存与存储策略语义

Source 不只是一个地址，也表达外部内容怎样进入 Workspace、何时刷新，以及是否必须持有本地版本。

口述中提到类似 `storage` 的策略表达，用于强调某些资源必须先完成下载和保存，才能被当作有效依赖。这里确定的是策略需求，并没有冻结 `storage` 的字段、枚举或协议形式。

这也意味着 Workspace 会消耗真实容量：除了结构化数据，还包括可能占用很大空间的非结构化资源。

### 4.6 外部 UI 资源的例外

“核心依赖进入数据源”不等于禁止所有外部 URL。

例如，一个 Block 的装饰图标，通过 `img src` 引用外部 HTTP 图片，可以考虑遵循浏览器已有策略。核心业务数据和影响工作流成立的资源，则尽量通过内部数据源管理。

动态业务依赖与装饰性资源的具体边界，仍需明确，不能把外链例外扩大为绕过数据源的普遍路径。

### 4.7 Workspace 自身的服务化 URL

每个 Workspace 有独立的目录 URL。内部数据应能通过标准的转换规则获得对应的访问地址，使 Workspace 的数据源和资源真正成为可以引用的服务。

名称、目录 URL、属性访问和对象版本之间的转换逻辑需要统一，但本轮不预设路径格式。

## 五、Command、事务 Apply 与确定性合并

### 5.1 客户端提交的是操作，而不是任意后端代码

客户端通过命令描述对 Workspace 数据的修改。口述中的命令要素包括 Command Name、目标数据源名称和操作类型等；一次提交可以包含一个 Command 列表。

这些是操作模型的概念要素，不是已经冻结的请求字段。真正需要固定的是：命令对应已定义的数据类型操作，而不是让客户端向数据内核提交任意业务代码。

### 5.2 一次提交具有事务语义

当用户一次提交一组修改时，后端应以事务方式完成这一组修改。Apply 成功意味着整组修改已经生效，而不是只有其中一部分被写入。

后端确认成功后，后续读取最新状态应能观察到新结果。客户端本地快照如何追上新版本属于同步实现问题，不能把本地缓存读取与后端已提交状态混为一谈。

### 5.3 版本推进与并发提交

用户 A 和用户 B 可以同时基于 V1 生成各自的命令队列。服务器确定处理顺序后，例如先应用 A，再处理 B，B 的操作需要根据先前变化进行必要的转换或 Rebase，尽可能自动合并。

示意如下：

```text
共同初始状态 V1
  ├─ A 基于 V1 生成命令队列 A
  └─ B 基于 V1 生成命令队列 B

确定应用顺序：A → B
  → Apply A
  → 按既定规则处理 B 与已提交变化的关系
  → 得到确定的最终状态
```

最终编号是 V2 还是 V3，取决于具体版本计数规则，不是本轮要固定的内容。数据源版本、对象版本和 Workspace 整体版本的关系，也需要后续明确。

### 5.4 确定性是合并算法的核心契约

本轮要求的确定性可以表述为：

> 给定相同的初始数据状态、基于该状态产生的命令队列，以及相同的标准应用顺序，合并过程必须得到相同的最终状态。

算法应稳定、公开，并且能够在没有服务器参与的本地环境中复现。服务器负责接收与排序，不应成为算法结果不可解释的来源。

这一要求没有预先选定具体并发合并算法，也没有要求不同应用顺序必然得到相同结果。当前冻结的是“给定顺序后的确定性”，以及每类操作都具有明确语义。

### 5.5 自动合并并不等于所有数据都做细粒度合并

富文本、表格和容器可以具有专门的协作规则；简单 JSON 或复杂模型则可以采用锁定、整体替换。

不同类型采用不同的协作粒度并不破坏统一 Command 模型。需要避免的是：某类对象声称支持合并，却在冲突条件下留下未定义行为。

## 六、资源核算与服务限额

### 6.1 以内核职责为基础计算资源成本

数据内核主要提供读取、存储、修改 Apply 和合并 Apply。按照本轮讨论，其资源开销可以归为三类：

| 资源 | 核算对象 | 讨论中的特点 |
| --- | --- | --- |
| 存储 | 结构化数据、非结构化资源及相关状态 | 可能持续增长 |
| 流量 | 每个 Workspace 的上行与下行 | 可以按 Workspace 计量 |
| 计算 | 命令应用及并发合并等工作 | 在上述有限职责下，预期相对较轻 |

“计算相对轻”是对受控数据内核的定位，不是对后端公式、任意脚本或大规模 AI 计算的性能承诺。

### 6.2 不依赖每个 Workspace 一个 Docker 容器

Workspace 应能通过自身数据操作和资源计量判断是否触及 Limit，而不必为每个 Workspace 创建 Docker 容器后，才有办法管理用量。

这与后文中的独立后台计算容器不同：数据内核不依赖这类容器来提供基本服务，复杂扩展任务则可以使用用户自己的容器空间。

### 6.3 存储触限后的只读状态

本轮明确提出的规则是：**Workspace 达到存储容量上限后，整个 Workspace 进入只读状态。**

流量和计算资源触限时如何处理、哪些操作能够释放空间、释放后怎样恢复，以及配额检查与事务提交如何衔接，尚未确定。不能把这些未定义细节写成已有实现。

## 七、计算体系：执行位置与求值方式分别定义

### 7.1 计算能力不应被归成一个无限扩张的后端执行器

讨论先后涉及客户端脚本、公式、后台批处理、函数对象和 AI 计算。它们并不都处在同一个分类维度：

- 客户端与后端描述计算在哪里执行、使用谁的资源。
- 脚本、公式和函数对象描述计算如何表达、何时求值。
- AI 计算描述任务借助什么能力完成，也可以落在不同执行环境中。

因此，函数对象可以服务于公式或批处理，许愿格也可以选择前端或 Agent 执行模型。不能为了统一名称，将它们全部变成数据内核中的一种任意脚本能力。

| 能力 | 本轮说明的状态 | 架构定位 |
| --- | --- | --- |
| 客户端脚本 | 已实现 | 数据内核之外的客户端计算 |
| 前端／后端公式 | 谨慎考虑，模型需要预留 | 有明确返回类型的求值机制 |
| 后台批处理与离线分析 | 尚未定义完整机制 | Owner 独立计算空间中的任务 |
| Function Instance／函数对象 | 已有基础研究与设计，计划落地 | 可组合、可缓存、可发布的按需求值能力 |
| 标准许愿格 | 已有实现 | 带 AI 的客户端计算流程 |
| Agent 型许愿格 | 计划增加 | 指定用户资源空间中的 Agent 任务 |

### 7.2 客户端计算：现有、低内核负担的基本路径

客户端只要具有对应权限，就可以读取 Workspace 数据，在本地运行计算脚本，再将结果提交回 Workspace。

```text
Get 数据 → 客户端计算 → Set／Command 提交结果
```

这里的 `Set` 是修改命令的概括，不代表绕过事务和类型操作规则。

服务器不需要知道客户端用了什么算法、进行了多少次本地运算。它主要看到读写权限、操作频率、流量和数据修改，因此表现为数据 I/O，而不是业务计算。

计算尽可能前端化，是当前实现的重要方向。这种工作方式也接近电子表格用户的使用习惯：数据在客户端被处理，结果再被保存。

### 7.3 公式：类型不变，值由求值产生

公式需求的核心，是属性已经有明确的数据类型，但保存的不是一个现成值，而是产生这个值的计算表达式。

公式可以引用其他数据源；被引用的数据源又可能是公式，于是形成依赖链。自由表格中的每一个 Cell 还可能独立保存公式，并通过单元格坐标相互引用。

是否允许公式引用公式、允许多少层依赖、如何处理依赖传播，是需要单独定义的能力。

#### 前端公式

如果公式只引用已有的普通值，客户端可以读取这些值后完成求值。即使支持更复杂的依赖，也可以考虑在客户端完成，但需要定义完整的规则和成本边界。

逻辑上的 Get 不等于每次都发起 RPC。版本机制与快照同步可以把大量服务端状态带到本地，让客户端基于本地状态求值。

#### 后端公式

后端公式对读取者保持透明：客户端读取数据源，服务端完成所需计算，默认返回公式结果；只有显式要求查看公式时，才返回公式定义。

这种方式使其他应用仍以普通数据源接口使用结果，也给集中优化留下空间，但会增加服务端计算成本，并引入求值语言和依赖管理问题。

| 方面 | 前端公式 | 后端公式 |
| --- | --- | --- |
| 求值位置 | 客户端 | 服务端求值机制 |
| 普通读取结果 | 由客户端完成求值后使用 | 数据源读取直接返回求值结果 |
| 优化空间 | 本地快照、客户端计算 | 服务端的依赖与计算优化 |
| 主要边界 | 客户端能力、依赖同步 | 计算成本、语言限制、执行隔离 |

“后端公式”描述求值发生在后端，并不意味着已经决定把任意公式解释器直接嵌入数据内核。其执行组件和资源边界仍需定义。

#### 公式语言与循环依赖

使用通用语言会带来较大的执行与控制成本；自定义语言更容易限定能力，但优化机制需要自行建设。前端公式和后端公式不必强制使用同一种写法。

对于循环引用，口述提出了利用版本的候选思路：读取上一版本的值，使同一次求值不在当前版本中无限递归。该思路尚未冻结，初始值、版本推进和跨版本依赖的具体规则仍需确定。

**冻结方向是为公式保留位置，并明确前后端公式的区别；不是在本轮完成公式引擎的所有定义。**

### 7.4 后端批处理与离线分析

某些 Workspace 需要处理大量数据，或者数据规模可以存储，但计算过程特别复杂。这类需求更接近离线分析和批量处理，而不是日常的交互式数据修改。

本轮讨论允许为这类需求预留后端脚本或算子接口。Workspace Owner 在拥有相应权限时，可以配置批量任务、定时任务或触发任务，必要时使用分布式计算。

其执行路径仍然是：

```text
Workspace 数据
    ↓ Get
Owner 自有计算／容器空间中的任务
    ↓ 运算完成
Set／Command 写回 Workspace 数据区
```

复杂任务使用 Owner 自己的计算资源，而不是借用 Workspace 数据内核的计算空间。数据内核继续提供读取、提交和发布能力，不因此变成完整的分析执行平台。

需要进一步定义的包括：任务可以使用哪些编程语言、运行时能看到什么、可以访问哪些数据、如何触发、是否必须使用容器，以及如何管理任务生命周期。

当前应冻结扩展入口及资源归属，不提前承诺已经具备完整的 OLAP 引擎。

### 7.5 基于函数对象的链式计算与惰性求值

BuckyOS 还计划提供基于命名对象和算子的计算能力。口述使用了 `Function Instance`、`Chunk Object`、`Lambda Object`、`Lambda Function Object` 等名称；这些名称之间的最终关系尚未统一。

其共同方向是，以更接近函数式编程的方式组合整个计算过程，支持确定性计算、结果缓存、惰性求值和按需的局部求值。

如果用户没有读取某个数据源，就不必执行对应计算；真正读取时，也尽量只求出本次需要的部分。确定性的结果可以复用缓存，减少重复计算。

这套能力可以开放给 Workspace 的公式系统，也可以被后台批处理使用。它与执行位置是不同维度，不能直接等同为“必须在 Workspace 服务器中运行”。

#### 从发布结果走向发布计算定义

传统情况下，发布的是已经形成的数据对象，其他应用通过 Object ID 引用它。

函数对象机制允许同时发布数据和计算算子或计算定义。引用方不必在拿到引用时立即求值，也可能在自己的计算环境中完成求值。

由此，跨对象发布不再局限于静态结果，还可以发布一个可复用、按需执行的计算方法。

对 Workspace 用户而言，它可以体现为公式中新的计算能力，而不必暴露全部底层分布式机制。具体对象格式、缓存规则、调度及权限接口尚待后续设计。

## 八、AI 计算：许愿格的分析、执行与权限边界

### 8.1 现有许愿格的基本工作模型

许愿格（Prompt Cell）将用户的自然语言愿望转换成数据操作。它首先进行分析，再由用户触发实际执行。

分析阶段是只读的：结合 Workspace 上下文、模型能力和系统提示词，把粗糙需求变成更准确的任务描述。这里最重要的工作，是把用户的自然语言映射为准确的数据源名称。

例如，用户说“上面的销售数据”或“那段说明”，系统需要识别对应的命名数据源，检查是否存在；存在多种解释时，应提示用户澄清，而不是在执行中任意选择。

分析阶段需要确定输入数据源、输出目标和计算规则，并列出使用的数据源。输入确定后，即可在画布上绘制从数据源指向许愿格的依赖箭头。

此时尚未执行任务，也不应因为分析过程已经运行了 LLM，就把业务数据修改视为已发生。

### 8.2 分析可以包含探索 Workspace 上下文的循环

最初描述的是一次只读推理；对于较大的 Workspace 上下文，分析也可能需要 Agent Loop 才能找到相关数据。

因此，“标准模型”不应被限定为只能调用一次模型。它的边界在于分析与执行结果明确、权限受控、最终过程可以在客户端运行，而不是机械地限制模型调用次数。

这里对 Workspace 内部上下文的分析，不等于已经授权它自由探索外部世界。

### 8.3 两类执行内容

| 执行内容 | 典型任务 | 结果处理 |
| --- | --- | --- |
| LLM 语义计算 | 总结长文本、生成需要语言理解的内容 | 将结果写入分析阶段确定的目标 |
| AI 生成脚本 | 数据转换、统计和其他可以脚本完成的任务 | 用户查看并触发后，在客户端 Get → 计算 → Set |

AI 生成的脚本仍是普通客户端脚本。用户无需手写宏脚本，服务端也无需为每一种 AI 生成逻辑提供专用功能。

这正是当前能够谨慎推进公式系统的原因之一：一部分原本需要用户编写公式或代码的任务，可以由 AI 生成客户端计算流程完成。

### 8.4 Jarvis 操作 Workspace 与许愿格内部执行不同

另一条路径是由 Jarvis 通过标准操作接口模拟用户使用 Workspace。口述将该接口称为 HML，具体名称待核。

Jarvis 的 Agent 能力是完整的：它可以按照用户权限寻找资源、插入照片、操作 Workspace，甚至调用许愿格。

原始许愿格的设计则更受限，主要使用已有数据源，进行计算或触发已有 Source 的同步，而不自主寻找外部来源、创建新的输入数据源。

例如，用户要求“抓取当前纳斯达克涨幅最高的 100 只股票”。如果没有现成的、能够通过 URL 返回这些数据的服务，原有受限模型难以完成；具备外部探索能力的 Agent 则可以寻找来源并组织结果。

这一例子用于说明能力边界，并非本轮需要实际执行的行情查询。

### 8.5 关于“新建数据源”的待决边界

口述中同时包含两项表述：许愿格计算完成后可以形成新的结果对象；原始许愿格原则上不应自主新增数据源。

二者不能在文档中被直接合并成“完全禁止创建”或“可以自由创建”。后续需要区分：

| 行为 | 需要明确的问题 |
| --- | --- |
| 分析阶段声明输出目标 | 是否允许声明一个尚不存在的结果对象？ |
| 用户确认后的结果写回 | 输出对象由确认阶段创建，还是可由执行流程按声明创建？ |
| 探索外部来源并导入 | 是否仅限 Agent 模型？需要什么单独授权？ |
| 刷新已有 Source | 与创建新来源使用怎样不同的权限？ |

现阶段保留这一边界问题，不将原始模型解释成已经具备自主数据接入能力。

### 8.6 标准模型／前端模型

标准模型在当前登录用户的网页中运行。浏览器脚本根据许愿格属性构造提示词，通过 AICC 获取 AI 能力，再把结果通过普通 Set／Command 提交回 Workspace。

从 Workspace 后端看，它没有参与 AI 执行过程。许愿格本身可以只是多几个配置字段的 JSON 对象，执行表现为一个带 AI 的宏。

这一模型依赖当前用户的 AICC 权限。即使用户拥有许愿格的执行权限，如果不能访问 AICC，仍然无法完成对应的 AI 调用。

还必须区分三种授权：

| 授权 | 控制的问题 |
| --- | --- |
| 许愿格执行权限 | 是否可以触发这一预定义任务 |
| AICC 访问权限 | 是否可以调用相应 AI 能力及使用额度 |
| Workspace 数据修改权限 | 是否允许提交对应结果或操作 |

“允许执行预定义任务，但不允许自由编辑数据”是一种可能的产品边界。执行权限如何授权特定写入，而不等于任意编辑权，本轮尚未解决，不能简单把三种权限合并为一个开关。

### 8.7 Agent 执行模型

计划增加的第二种执行模型，是在选定用户的后台资源空间中运行 Agent。

以 Workspace Owner 提供环境为例：Owner 创建一个执行容器，容器归属于 Owner；为这一用途配置专用 App ID，再为其设置用量配额、使用范围及允许的 Workspace 操作。

有权限点击执行的协作者，触发的是这个已经配置好的环境。Agent 在容器内使用被委托的能力完成探索和计算，最后把结果提交回 Workspace。

这里需要明确区分三种角色：

| 角色 | 含义 |
| --- | --- |
| 触发者 | 点击许愿格执行的用户 |
| 执行环境所有者 | 提供容器、计算空间及相关授权的用户 |
| 执行身份／应用身份 | 实际执行操作时使用的、受配置约束的身份 |

触发者与环境所有者不一定相同。因此，这是一种权限委托，而不只是“换个位置运行同一个脚本”。

**权限上限原则：容器对 Workspace 的操作权限不得超过容器 Owner 本人拥有的权限。** 专用 App ID 还可以进一步收窄范围和额度；它不意味着任务自动获得 Owner 的全部权限。

许愿格编辑权限、执行权限和容器操作范围如何继承或关联，需要进一步定义。尤其不能让配置可被修改的任务，在未经约束的情况下继承另一身份的全部能力。

### 8.8 信任范围与应用化 Workspace

Owner 提供 Agent 环境具有风险。按本轮讨论，这种模式可能适合几个彼此信任的协作者，而不适合不加区分地开放给所有 Guest。

但标准模型也有另一侧限制：Guest 可能没有 AICC 权限。因此，面向不特定访问者的应用化 Workspace，仍需解决 AI 能力由谁提供、谁承担资源、谁授权执行的问题。

讨论中的候选路径包括 Guest 手动配置模型 Endpoint，以及联合登录用户使用自己所属 Zone 的 AICC。例如，Workspace 位于 Zone A，来自 Zone B 的用户使用 Zone B 的 AI 能力。

这些是待设计的能力来源，不代表已经冻结跨 Zone 凭据传递或代理协议。

### 8.9 Agent 与 XL Agent

口述还提出 Agent 模型可以进一步区分为 Agent 与 XL Agent 执行模型。二者名称、能力差异和接口尚未展开。

本轮保留该扩展分类，不自行赋予 XL Agent 含义。

## 九、统一后端任务入口：Workspace 管启动，用户空间管执行

### 9.1 后台批处理与 Agent 任务可以复用一套架构

后台批处理和 Agent 型许愿格虽然业务不同，但都需要在 Workspace 数据内核之外运行计算。

因此，可以考虑复用同一套技术架构：Workspace 保存必要状态和执行配置，Owner 配置相应能力后，由 Workspace 触发 Loader，在该用户的资源空间中启动任务。

```text
用户触发／定时／其他约定触发
              ↓
Workspace：状态与执行配置管理、Loader 启动入口
              ↓
指定用户的资源空间：进程／容器／Agent／批处理任务
              ↓
通过正常权限和 Command 接口读写 Workspace
```

任务是否共用进程、如何调度、怎样选择执行环境，仍属于后续实现问题。“复用一套架构”不等于所有任务必须共享同一个容器。

### 9.2 职责分配

| Workspace 一侧 | 用户计算空间一侧 |
| --- | --- |
| 保存执行配置及相关状态 | 提供实际执行环境 |
| 按权限和配置触发任务 | 运行脚本、算子或 Agent |
| 提供正常数据访问与提交接口 | 实施资源隔离、配额和运行控制 |
| 接收结果形成新的数据状态 | 在授权范围内获取数据并提交结果 |

Workspace 从这一角度承担 Loader 的角色，但不需要自己成为完整的容器资源管理平台。

### 9.3 与后端公式的关系仍需明确

后台批处理和 Agent 任务的资源归属已经有清晰方向；后端公式则可能处于读取路径中，需要另外决定如何接入受控求值组件。

因此，不能用“所有计算都外置”抹去后端公式的需求，也不能用“支持后端公式”作为任意扩展代码进入内核的理由。两者之间的接口和限制属于冻结前需要解决的关键问题。

## 十、Block、共享数据与用户私有 UI State

### 10.1 Block 是 UI，Data Source 是服务化数据

对象树中不只有数据源，还有大量 UI 对象。本轮统一将插入画布的独立界面组件称为 Block。

最常见的 Block 是数据源的投影：它负责展示、编辑或操作某项数据。例如，Rich Text 数据源绑定一个 Editor Block。

新建一段独立的可编辑内容时，插入 Editor 通常伴随创建相应数据源；但已有数据源也可以被其他 Block 继续引用。

一个 Workspace 可以有多个画布。画布一中的 Editor 和画布二中的展示 Block 可以指向同一份富文本，后者可以设置为只读，仅展示状态。

### 10.2 复制粘贴遵循 Block 的数据语义

复制 UI 不一定等于复制数据。本轮提出的预期如下：

| 原 Block 的性质 | 复制粘贴后的预期 |
| --- | --- |
| 对已有数据源的投影 | 新建一个投影 Block，继续引用原数据源 |
| 独立可编辑内容的 Block | 新建 Block，并同时创建一份新的数据源 |

这应按具体 Block 类型定义，不能只用“复制对象树节点”掩盖共享引用和独立副本之间的区别。

某个可编辑 Block 同时承担共享投影时如何处理、是否需要让用户选择复制方式，尚未展开。本轮不将该表视为覆盖所有情况的通用协议。

### 10.3 Block 可以声明 UI State

有些界面状态既不是共享业务数据，也不应只留在当前浏览器内存中。

典型场景是一个用于向表格新增记录的表单 Block：用户点击按钮打开表单，填写到一半关闭网页，在另一台电脑打开后，应能够继续填写。只有插入成功，才清空这份草稿状态。

为此，Block 可以声明自己的 UI State，通常一个简单 JSON 结构即可表达。具体采用 KV 还是其他结构，可以继续讨论。

渲染关系可以概括为：

```text
Block 配置 + 绑定的数据源 + 当前用户的 UI State → 界面呈现
```

### 10.4 UI State 按 User + Block 保存

同一用户对于同一个 Block，应只有一份逻辑上的 UI State，而不是每个 Session 各自一份互不相关的状态。

它需要跨设备和跨 Session 恢复，但不参与不同用户之间的共享数据协作。这里的“不参与协作同步”不等于只能存在本地，也不等于不保存。

同一用户同时打开多个 Session 并修改 UI State 时的冲突策略，尚未定义；不能把跨设备恢复直接等同为已经具备多人数据内核那样的合并语义。

### 10.5 Block 可以主要承担操作，而不是持续投影

用于新建记录的 Block 可以只保存表单 UI State，完成后向指定表格提交一条插入命令。它不必始终展示某个完整数据源，也不必把未提交表单草稿提前写进共享业务数据。

这使 Block 能承载更友好的工作流，而数据内核继续处理明确的结果操作。

## 十一、界面模式与独立 Presentation 数据域

### 11.1 两个基础模式

Workspace 有两个基础工作模式：数据源模式和画布／编辑模式。

| 模式 | 用户看到的内容 | 主要作用 |
| --- | --- | --- |
| 数据源模式 | 数据名、类型、值、Source，以及引用它的 Block | 直接查看和管理核心数据 |
| 画布／编辑模式 | 每个画布中的 Block Tree | 组织 UI、使用工作流和编辑内容 |

数据源模式的界面可以相对固定、朴素，重点是纯粹和清晰；画布模式是用户日常主要使用的界面，每张画布对应一棵 Block Tree。

Presentation 是建立在画布之上的演示模式，而不是把所有演示状态并回基础数据编辑模型。

### 11.2 一次演示绑定 Workspace 的确定版本

创建演示时，应选定 Workspace 当时的一个确定版本。之后其他人继续编辑原 Workspace，不应影响正在进行的演示。

可以完整复制一份，也可以利用 Named Object 的版本能力建立引用或 Fork。方向上倾向复用版本化对象，避免无必要地复制全部内容；具体实现仍未确定。

从内容基础看，演示依赖的是一个固定版本，而不是随时变化的 Workspace 当前状态。

### 11.3 演示状态独立保存

演示过程还会产生自己的数据，包括临时状态，以及可能需要长期保留的事件记录。

例如，主持人在第几秒翻到哪一页、做了什么标注，可以构成一段动作序列。进入同一演示房间的观众看到这些动作，之后也可以据此回放。

此类数据描述的是“这场演示发生了什么”，而不是“原 Workspace 的数据被怎样编辑”。因此必须有独立的数据格式和状态域。

### 11.4 四类状态不能混合

| 状态域 | 保存什么 | 作用范围 |
| --- | --- | --- |
| Data Source | 共享、可服务化的业务数据 | Workspace 数据模型 |
| Block Tree | 画布中的组件与配置 | 相应画布 |
| UI State | 用户未提交输入等界面状态 | User + Block |
| Presentation State | 某场演示的临时状态和事件序列 | 该次演示及其房间 |

**冻结方向：演示基于固定版本运行，其翻页、标注和回放数据不污染 Workspace 核心数据格式。**

演示持久化及回放目前不能视为全部已经实现，具体存储与事件协议仍需补充。

## 十二、扩展性验证：3D 建模与场景协作

### 12.1 验证问题

假设有人提出一个符合 Workspace 产品设计方向的可信需求：在画布中实现完整的 3D 建模和场景编辑工具。

Block 可以实现复杂渲染与交互。真正要验证的不是前端能否画出 3D，而是这类应用的数据状态、修改和协作，能否建立在有限的数据内核之上。

### 12.2 Mesh 模型与 Scene 场景分开处理

| 对象 | 示例内容 | 讨论中的协作选择 |
| --- | --- | --- |
| Mesh 模型 | 顶点、网格等复杂单体结构 | 可视为大 JSON／简单对象；锁定编辑、整体更新 |
| Scene 场景 | 多个模型实例、摄像机、场景元素及时间相关设置 | 有意拆成可并行编辑的数据结构 |

例如，一个用户锁定某个模型修改网格，其他用户只能只读；但在场景中，一个用户调整摄像机 A，另一个用户在街道上增加几棵树，可以希望尽量并行完成。

“模型难以协作、场景需要协作”是一个产品与数据建模选择，不是所有复杂对象天然都应该支持同样的合并粒度。

### 12.3 不把业务类型自动升级为内核类型

应用把某个结构称为 Mesh，不代表必须在数据内核里新增一个原生 Mesh 类型。它可以尝试使用已有 JSON、原子属性和容器表达。

Scene 的可协作性也应先通过已有类型及操作来构建。这里的目标是验证“能否做到”，而不是在没有具体数据结构和操作定义的情况下，宣布现有内核已经足够。

### 12.4 需要完成的验证

| 验证点 | 需要回答的问题 |
| --- | --- |
| 类型表达 | Mesh 和 Scene 能否由现有类型组合表达，而不增加内核专用类型？ |
| 协作粒度 | 哪些修改锁定整体对象，哪些修改可以独立提交？ |
| 操作模型 | 调整摄像机、增删模型实例等操作，能否落到已定义的 Command？ |
| 并发行为 | 两位用户基于同一版本修改时，合并结果是否可确定、可在本地复现？ |
| 扩展归属 | 需要新增的是 Block 和业务数据结构，还是内核语义？ |

如果必须改变内核，需进一步辨别是缺少通用基础能力，还是扩展层建模方式不合适。该案例目前是架构检验任务，尚无已完成的验证结果。

## 十三、本轮建议形成的冻结清单

以下清单汇总原则，不替代详细接口规范。

| 编号 | 冻结方向 | 保留的自由度 |
| --- | --- | --- |
| F01 | Workspace 以可服务化、版本化的数据内核为基础 | UI 与应用场景可持续扩展 |
| F02 | 内核类型有限、封闭，类型和操作无未定义行为 | 应用可组合类型并定义自身 Schema |
| F03 | 类型语义原则上长期不变，新增类型也需谨慎 | 不排除经过兼容性论证的演进 |
| F04 | 一组 Command 以事务方式 Apply | 请求格式和精确事务协议待定 |
| F05 | 给定状态、命令和顺序，合并结果确定且可本地复现 | 具体合并算法待定 |
| F06 | 非结构化资源统一使用 URL 表达 | Stream／Folder 的协议和映射待定 |
| F07 | 核心外部依赖先进入本地数据源，首次成功须有可用版本 | 同步策略及装饰性外链例外待定 |
| F08 | Workspace 可以独立计量存储、流量和内核计算 | 配额值、计费与细粒度限流不在本轮确定 |
| F09 | 存储触限后 Workspace 转入只读 | 回收、恢复和事务交界规则待定 |
| F10 | 现有计算优先复用客户端 Get → 计算 → Set | 计算脚本及界面可以持续扩展 |
| F11 | 为公式和函数对象保留清晰位置 | 不提前冻结语言、求值器和具体协议 |
| F12 | 批处理及 Agent 重计算使用独立用户资源空间 | 可复用后台执行架构 |
| F13 | 触发者、执行身份、资源所有者分别明确 | 委托及跨 Zone 使用规则待定 |
| F14 | 容器对 Workspace 的权限不超过其 Owner | 专用 App ID 可进一步限额、限权 |
| F15 | Block 与 Data Source 分离，UI State 按 User + Block 保存 | Block 的界面与业务交互可扩展 |
| F16 | 演示绑定确定版本，演示事件独立于 Workspace 数据 | 快照／Fork 及回放协议待定 |

## 结语

本轮架构冻结的中心，是让 Workspace 的扩展能力建立在稳定的数据契约上，而不是通过不断扩张内核来换取功能。

数据内核负责有限类型、明确操作、事务提交和可预测协作；Block、公式、脚本、Agent 与后台任务围绕这些能力扩展。计算在哪里发生、以谁的身份运行、消耗谁的资源，必须独立说清楚。共享数据、用户私有界面状态和演示状态，也应分别保存和演进。

**应当冻结的是这些边界与契约；应当保留的是在边界之上的组合、计算和应用创新空间。**
