# BuckyOS AI Workspace 第二期规划

> 状态：第二期实施规划 v0.2，已按 2026-10-06 的 review 裁决修订，待实现与验收。
>
> 实现基线：2026-10-06 工作区源码，第一期已在提交 `6a01de0a` 中合入。本文的“已有”表示源码中已有相应能力，不表示本次重新执行了第一期验收。
>
> 核心目标：**完成并验证 Workspace UI 框架的架构设计，以自由画布为重点，使数据、画布 UI、Block、布局和交互能够独立扩展，并在架构阶段确定无限画布的渲染与性能方案。**

## 1. 本期交付与范围

第一期建立了文档内核、统一命令、内置数据对象和浏览器离线副本。第二期在这些能力上形成正式的 UI 框架：用户既能在数据树中集中管理数据，也能在多张画布上组织同一份数据；开发者或 AI 增加一种展现时，不需要重新实现工作区、保存、权限和撤销。

系统具有三个顶层 UI 模式：

| 顶层模式 | 用户目的 | 第二期范围 |
| --- | --- | --- |
| 数据源模式 | 管理数据树中的原始数据、生成结果、引用关系和权限 | 在现有界面与编辑器上改进，完成左中右分栏、数据树及来源状态 |
| 画布模式 | 将数据和工具组织成可编辑的视觉工作空间 | 本期重点：多 Surface、自由布局、渲染宿主、Block 宿主、就近操作、扩展契约、许愿格 |
| 播放模式 | 点击“开始演示”后，按演示编排呈现内容 | 本期不实现；只明确其与文档、画布及运行状态的边界 |

画布模式包含**编辑模式、查看模式、播放编辑**三个子模式。本期建立真实的子模式状态与分派机制：编辑模式完成主要编辑能力；查看模式完成阅读交互与批注；播放编辑只在 UI 上提供入口和“尚未实现”的占位，不注册编排专用的 Renderer、动作或 Inspector，也不定义演示数据。“播放编辑”是编排演示，“播放模式”是执行演示，二者不能合并。

本期完成的判据是：

- 同一数据能在数据源模式中编辑，在不同 Surface 上以不同 Block 展现；数据树与各 Surface 的 BlockTree 分开管理。
- 编辑与查看子模式实际驱动各自的渲染、交互与工具策略；播放编辑占位可进入，且不写文档。
- 数据变化、引用失效、权限、离线和撤销在两种界面中保持同一语义；新增 Block 类型只需注册扩展。
- 许愿格以两遍执行产生结果，并能显示上游变化。
- 画布在约定规模下满足 M0 冻结的性能门槛。
- 最后用旧 ai-canvas 的两个 demo 验证这些边界。

明确延后：

- 顶层“开始演示”播放入口、播放编辑子模式的编排功能、演示路径编辑、时间轴、镜头切换、讲解者跟随及演示导出。
- 各子模式的高级专用功能，以及每种 Block 完整定制的各模式渲染器；本期必须具备统一分派、默认实现与回退机制。
- 连接线等需要端点引用或非矩形几何的画布专用 Block。
- Notion 式排版容器与新建画布模板；在自由画布核心完成后另行排期。
- 完整公式引擎、自动重算调度、跨 Workspace 发布与全局反向引用发现。
- 真实执行器（xllm、agent-work-session）接入、真实模型和视频生成服务；本期只冻结许愿格执行器契约，用 Mock 许愿格验证。
- AI 生成扩展代码的开放管线与扩展市场；本期的 HTML 扩展 Block 只用于 Mock 许愿格和验证样本（§10.4）。
- 全设备交互、多用户光标、不依附于数据的画布坐标评论钉；现有权限、并发和离线语义仍须保留。

本文收敛本期边界；较早的[核心设计](<BuckyOS AI Workspace 实现的核心设计.md>)中包含演示的长期闭环，不直接作为第二期必须完成的范围。

## 4. 统一模型：数据树、Surface 与 Block

### 4.1 两棵树

```text
root（Workspace）
├─ data（数据树根，系统节点）
│  ├─ 销售表、调研资料/ …          第一层：用户直接管理的数据与文件夹
│  └─ 画布内容区（系统文件夹，数据源模式默认折叠）
│     ├─ <Surface A 的内容>         便签、文本、图片、许愿格、生成结果 …
│     └─ <Surface B 的内容>
└─ surfaces（Surface 集合，系统节点）
   ├─ Surface A（layout: free）
   │  └─ BlockTree：Block、UI 分组
   └─ Surface B（layout: flow）
      └─ BlockTree
```

| 概念 | 落点 | 约束 |
| --- | --- | --- |
| 数据树 | `data` 下的文件夹与数据实体 | 持有业务内容和标注，与画布坐标无关；树位置决定管理归属与权限继承 |
| 数据实体 | 已有 TableSource、RichText、Record、AssetRef、Annotation；新增许愿格（§7）与 Block 定义（§10.3） | 只出现在数据树中 |
| Surface | `buckyos.container`，kind `surface`，`layout.mode: free \| flow` | 一张画布一个 Surface；一份 Workspace 可包含多张；ID 稳定唯一，不再依赖 `page-main` |
| BlockTree | Surface 下的 Block 与 UI 分组 | 只表达展现与排布，不持有业务内容 |
| 数据 Block | `buckyos.cell`＋数据引用＋Renderer 配置 | 多个 Block 可以引用同一数据；每个 Block 的布局和展现配置独立 |
| 纯 UI Block | 声明为无源的 Cell：框、形状、分隔等 | 不为它们伪造数据；本期不含连接线 |
| UI 分组 | BlockTree 中 kind `group` 的 Container | 表达成员关系与局部坐标空间，不等于数据分组 |
| 画布内容区 | `data` 下的系统文件夹，每个 Surface 一个子文件夹 | 与 Surface 同时创建、同时删除（§4.3） |
| 依赖记录 | 结果实体上的生成依赖（§7.3） | 与视觉分组、树父子关系、临时任务状态分开 |

产品中使用 Block 一词，现有协议中的展现单元仍称 Cell。富文本内部的 `block_id` 是文本锚点身份，不是画布 Block 身份。视觉框只是布置内容；需要成员关系时才使用 UI 分组；生成结果的集合由许愿格的输出目标和依赖记录指明（§7），不能依赖“恰好位于同一矩形内”。

两棵树仍在同一张实体表和 `tree_edges` 中，命令、权限路径并集、引用索引、撤销、离线副本与导出都沿用同一内核；变化的只是结构规则（§4.5）。

### 4.2 画布上创建的内容默认是数据

用户在画布上创建的文本、便签、图片、表格、许愿格，以及许愿格产生的结果，默认都由一个数据实体和一个展示它的 Block 组成。二者在同一次 Commit 中创建，形成一个撤销单位：

- 数据实体放在当前 Surface 的画布内容区子文件夹中。第一层数据源不受打扰，数据源模式仍能搜索、筛选和管理这些内容。
- 便签是标注数据（`buckyos.annotation`，kind `note`）。贴在某个数据上时以该数据为 `target`；自由放置的便签没有 `target`，需要内核放宽当前的必填约束。
- 只有框、形状等特殊格式是纯 UI Block，直接属于 BlockTree，不进入数据树。
- 从数据树拖入或“添加到画布”的已有数据只创建 Block，不复制数据。

“画布内容默认是数据还是纯 UI”是架构选择。本期选择前者：便签和文本可以被批注、引用、作为许愿格输入并出现在关系查询中，编辑与协同只需一套实现。代价是每个内容 Block 对应两个实体，需要画布内容区把它们与第一层数据源分开。

### 4.3 结构、引用与删除

- **Block 跨 Surface 移动**：`tree.move` 改变 Cell 的父节点和摆放，Cell ID、数据 ID、标注及依赖记录保持不变。数据留在原画布内容区，数据源模式提供显式的“移动到…”整理操作。
- **在另一张 Surface 展示同一数据**：创建新的 Cell，复用数据引用；“复制数据”是另一个明确操作。
- **删除 Block**：
  - 引用第一层或其他位置数据的 Block：只删除 Cell。
  - 引用画布内容区数据，且该数据没有其他 Block 或阻止删除的引用：Cell 与数据在同一次 Commit 中删除（删除便签就是删除便签）。
  - 画布内容区数据仍被其他 Block 引用：只删除 Cell，并提示数据仍在使用。
- **删除 Surface**：在一次 Commit 中删除 BlockTree 及其画布内容区子文件夹。其中有数据仍被其他 Surface 的 Block 或其他数据阻止删除时，预检列出可见引用，并提供“移到数据树后再删除”。不能把视觉删除解释成无条件级联删除数据。
- **删除数据**：先展示已授权的引用影响，遵守内核引用约束。预检只返回调用者可读的引用方；不可读部分只说明“存在无权查看的引用”，不返回其 ID、名称或数量。现有 `entity.delete` 直接返回全部引用方 `entity_id`，M1 修复。
- **权限**：移动对象可能改变继承权限，跨父节点移动按目标父节点重新校验。拥有 Surface 的结构权限不等于拥有数据的修改权限。
- 纯 UI Block 不进入数据树，可在 Surface 对象列表中定位。“不出现在数据树”不是安全边界。

### 4.4 三类状态

| 状态归属 | 内容 | 保存与传播 |
| --- | --- | --- |
| 共享文档 | 数据内容、Block 绑定、Renderer 标识与配置、两棵树的结构、`placement`、许愿格与依赖记录、Block 定义 | 经 Command 提交、撤销、同步、导出 |
| 用户工作状态 | 当前顶层模式、画布子模式、活动 Surface、每个 Surface 的视口、面板开关和宽度、临时筛选；数据源模式中无 Block 时的表格视图配置（排序、筛选、列宽） | 服务端按用户与 Workspace 保存，浏览器 IndexedDB 同时保存；不产生 Commit，不进变化流、导出包或撤销栈 |
| 当前交互状态 | 悬停、选区、拖拽预览、激活的编辑器、临时媒体预览 | 当前会话维护，不广播、不进入共享包或撤销栈 |

用户工作状态的保存规则：

- 服务端存放在 Workspace 的 `local.sqlite`，按主体分行。它与 grants、runs 同属部署数据，不进入 `doc.sqlite`。新增 Session 读写接口。
- 在线时写服务端，同时更新本地缓存；离线时只写 IndexedDB，恢复连接后上送。冲突按条目由后写者生效；视口等高频值节流上送。
- 打开 Workspace 时先用本地缓存立即恢复，再以服务端结果校正。Fork 与导入不带工作状态。
- Surface 被删除或失去读取权限后，相关条目被忽略并清理。

本期不保存演示运行状态。未来播放过程中相机、显隐、动画对文档的覆盖应属于播放会话，不能写回基础布局。

### 4.5 内核结构变化

| 位置 | 当前 | 第二期 |
| --- | --- | --- |
| root 的子节点 | 只能是 `page` | 只有 `data`、`surfaces` 两个系统节点，随 Workspace 创建，不可删除、移动或改名 |
| Container kind | `page` / `group` | `folder`（数据树）、`surface`、`group`（BlockTree）；取消 `page` |
| 数据树 | — | `data` / `folder` 下只能是 `folder` 或数据实体；TableSource 下的 RichText 正文规则不变；画布内容区是系统 `folder` |
| BlockTree | page/group 下混放 Cell、数据源和批注 | `surface` / `group` 下只能是 Cell 或 `group`；数据实体不能进入 BlockTree，Cell 不能进入数据树 |
| `placement` | `{ x, y, w, h, z? }` | `{ x, y, w, h }`，层叠顺序用 `order_key` |
| 批注 | `target` 必填，父节点为 page/group | 父节点在数据树；自由便签可以没有 `target` |
| Cell | `view.type` 四选一，`source_ref` 必填 | 按 D6 校验；声明无源的类型可以省略绑定 |

Surface 与其画布内容区子文件夹的对应方式（命名规则或互相引用）以及系统节点的固定 ID 在 M0 冻结。本期允许 breaking change：第一期示例数据（`api/sample.ts`、`fixtures/project-workspace.commits.json`）、内核 fixtures、e2e 夹具和导出包格式版本一起更新；导入旧包时返回明确的版本错误，不做迁移。

## 5. UI 框架分工

```text
WorkspaceShell：模式入口、保存/同步状态、统一撤销、通知、用户工作状态
├─ DataSourceView：数据树、数据详情、引用与依赖、权限、属性
└─ CanvasView：Surface 导航、选择、手势、就近工具
   ├─ CanvasModeController：编辑 / 查看 / 播放编辑（占位），统一交互与工具策略
   ├─ RenderHost：相机、空间索引、分层、LOD、挂载预算（§9）
   └─ LayoutHost → BlockHost → 按模式分派 Renderer / Editor

共用服务：SourceAdapterRegistry / BlockRegistry / 属性与动作描述
          ReferenceService / FreshnessService / WishService / 权限与写锁 / AnchorRegistry
                          ↓
               WorkspaceStore + WorkspaceSession
                    ↙                 ↘
         OnlineWorkspaceSession    ReplicaWorkspaceSession
                    ↓                 ↓
              Rust 服务内核       Worker / WASM 同一内核
```

图中各 View、Host、Registry 和服务是本期拟新增的前端职责，不是已有 RPC 名称。Surface 一词专指持久化的画布实体（§4.1），前端视图不再称 Surface。

关键约束：

1. Shell 管顶层模式与全局状态，CanvasModeController 管画布子模式及切换策略，View 管工作方式，RenderHost 管相机与可见性，LayoutHost 管排布，BlockHost 管生命周期、交互外框和错误，Renderer 管内容展现。不能把所有职责继续堆在 `WorkspaceView.tsx`。
2. Renderer 和属性编辑器只获得受限的读取、动作及提交桥，不直接调用底层 client、操作数据库或维护私有保存流程。
3. 文档变更通过 `WorkspaceStore.submit()`、许愿格应用入口及现有 `proc` 应用入口，统一记录保存状态、撤销和冲突。权限变更属于部署管理操作，经 Session 转发已有 `ws.*`，不伪装成可离线撤销的文档 Commit。
4. 顶层模式和画布子模式的切换均不销毁 Workspace 会话、撤销协调器和待提交队列。正在编辑的内容按原策略提交或保留为可恢复输入，不能因组件卸载而丢失；具体子模式切换行为见 §10.2。
5. 原有“未保存／已保存到本设备／已提交／需要处理”、写锁与权限提示在两种 View 中都可见；详细记录按需展开，不长期占据画布。
6. Renderer 缺失、数据不可读或单个视图异常时，由 BlockHost 提供局部回退，不使整个工作区无法打开和保存。

## 6. 数据源模式

### 6.1 左中右分栏

```text
┌─────────────────── 顶栏：工作区 / 模式 / 保存与同步 ───────────────────┐
│ 左侧                      │ 中间：当前选择的详情       │ 右侧：属性    │
│ 上：数据树                 │ 内容 / 引用与依赖          │ 类型与 Schema │
│ 第一层数据与文件夹         │ 原始值、表格或专用编辑器    │ 版本、依赖    │
│ 画布内容区（默认折叠）     │ 我引用谁 / 谁引用我        │ 权限、写锁    │
│ 下：权限管理              │ 选择权限项后显示授权详情   │ 可编辑配置    │
│ 预设权限组、画布权限       │                            │               │
└───────────────────────────┴────────────────────────────┴───────────────┘
```

左侧上半区是数据树：第一层显示用户直接管理的数据与文件夹；画布内容区默认折叠，按 Surface 分组，可展开、搜索和筛选；可按类型以及原始/生成结果筛选。数据树不显示 BlockTree 中的 Block，纯 UI Block 只在画布中管理。在数据源模式中新建或导入的数据，默认放在数据树第一层或当前选中的文件夹。

选中数据后，中间展示数据自身的内容：表的记录与字段、富文本、Record 属性、资产信息及预览、便签与批注；可展开受权限过滤的原始结构。编辑数据不必先创建 Block；没有 Block 时，表格的排序、筛选和列宽保存在用户工作状态中。复用现有表格与富文本能力时，应把“数据编辑”从“Cell 外框与视图配置”中拆开。

右侧展示当前对象的类型、稳定身份、版本、依赖、权限与写锁等属性；提供的编辑项必须有对应命令。原始值编辑、视图选项修改和 Schema 修改要清楚区分。单击引用可打开对应数据。选择“在画布中定位”后切换到相应 Surface 并聚焦 Block；若同一数据在多处展示，先列出可访问的位置。

### 6.2 引用与依赖

数据详情要同时回答：**它包含什么、它引用了谁、谁在使用它、结果是否仍对应当前输入。** 本期以 Workspace 内部引用为主。

| 关系 | 示例 | UI 语义 |
| --- | --- | --- |
| 展现绑定 | 销售表 → 表格 Block、图表 Block | 显示同一数据，数据变化后更新展现，不称为 AI 结果过期 |
| 普通引用 | Record 的对象引用、富文本嵌入、标注锚点、使用 Block 定义 | 可定位目标，按 live/fixed 语义解释 |
| 生成依赖 | 数据 1、数据 2 → 许愿格 → 数据 3 | 记录实际读取的版本；输入变化后提示需要刷新（§7.5） |

规则：

- 现有 `refs` 是正反向查询的基础，但不能自动推断完整的生成依赖；依赖以许愿格的输入引用和结果的依赖记录为准（§7）。
- 许愿格输入和结果依赖纳入 `refs` 索引，但不阻止删除（与标注锚点同类）；被依赖的数据删除后显示“引用不可用”。
- 表格范围使用稳定的 record/field ID 或声明的动态查询条件，不把显示行号当成依赖。动态查询还需记录决定成员集合的条件、成员版本及相关字段的类型版本。
- 关系与依赖查询通过新增的 Session 读取接口提供，由 core 实现，在线与离线读取同一投影。权限过滤在服务/副本的读取边界完成，不返回无权对象的名称、内容或全局引用数量。
- 反向引用只声明“当前 Workspace 中我有权查看的引用”，不承诺发现外部的所有使用者。关系页不能为了画图而把大表完整下载到浏览器。

### 6.3 左下权限管理

现有模型是主体在 Workspace 或实体子树上的能力授权；有效能力沿结构路径取并集，没有 deny 和字段级授权。`ws.list_grants` 目前要求 Workspace 的 `manage` 权限。

分享以整个 Workspace 为单位：把 Workspace 分享给某人，就是授予其 Workspace 级能力（至少 `read`）。子树授权只用于在此基础上增加能力，不作为分享入口。

“预设组”先落实为**预设权限组合与对应授权主体的分组展示**，使用现有 grant 协议，不伪造后台尚不存在的动态用户组成员关系：

| 预设权限组 | 默认能力 |
| --- | --- |
| 阅读者 | `read` |
| 评论者 | `read`、`comment` |
| 编辑者 | `read`、`append`、`update`、`delete`、`structure`、`comment` |
| 管理者 | 现有全部能力，包含 `export`、`manage` |
| 自定义 | 展示实际 capability 集合；例如仅追加，或单独授予导出 |

**画布权限**：由于没有 deny，按画布设计权限表示“在 Workspace 级能力之上，对某个 Surface 额外授予能力”，例如所有人都是阅读者、某几个人是画布 A 的编辑者。画布上创建的内容数据位于数据树的画布内容区（§4.2），因此一条画布权限同时写两行授权：Surface 子树和对应的画布内容区子文件夹。界面上作为一行“画布：A”展示和撤回。

**主体选择**：`ws.grant` 的 `subject` 是经认证的主体标识，后台不校验主体是否存在。界面需要 Zone 用户与 Agent 的列表来源；候选是 system-config 的 `users/`（`buckyos-api` 的 `get_user_list`）。普通用户能否读取、Agent 主体如何列出，在 M0 确认。`*` 的含义是任意已认证主体，不能标成匿名公开访问。

其余规则：

- 界面必须能查看预设组合、实际授权主体、授权作用域和继承来源。有 `manage` 的用户可以授予、调整或撤回；没有该能力的用户只显示自己的有效能力，不读取完整授权名单。
- 授权行的更新会替换该主体在该作用域的能力集合；界面应明确显示保存后的集合。撤回子树直接授权后，祖先或 Workspace 授权可能仍使权限有效，不能提示“已禁止访问”。角色名称只是预设解释，以后台返回的实际能力为准。
- 权限管理操作在线执行，不排入离线文档队列；重新进入权限页面或执行管理操作后重新读取授权，不能假定它会产生普通文档变化事件。断网时缓存的权限标为“最近已知状态”，重连后的提交按当前后台权限校验。
- 分享/导出不复制部署授权。真正的成员组、组织同步和组级授权另行设计。

## 7. 许愿格、生成结果与新鲜度

### 7.1 许愿格保存什么

许愿格是数据树中的实体（新类型，暂称 `buckyos.wish`，类型标识与 Schema 在 M0 冻结），保存运行一次 AIGC/AI 推理所需的信息：

| 内容 | 含义 |
| --- | --- |
| 原始提示词 | 用户的自然语言输入 |
| context 提示词 | 第一遍分析得到的完整提示，把用户的原始意图翻译为能准确引用指定数据的形式 |
| 输入引用 | context 提示词引用的数据：实体、选择器（稳定 record/field ID 或声明的查询条件）、版本策略（跟随当前 / 固定版本） |
| 执行器 | `mock`、`xllm`、`agent-work-session`；本期只实现 `mock` |
| 输出目标 | 数据树中的名称路径（形如 `$container/$blockname`）及结果类型 |
| 输出方式 | 覆盖到固定名称，或每次新建 |
| 执行配置 | 执行器参数、模型能力声明等，由执行器定义 |

许愿格在画布上由一个 Block 展示。它的输入引用纳入 `refs` 索引，但不阻止删除。

### 7.2 两遍执行

1. **分析**：执行器读取原始提示词和可见上下文，生成 context 提示词与输入引用。宿主检查引用的数据都存在、可读且范围有效，把结果展示给用户，并写回许愿格（一次 Commit）。输入缺失或无效时不能进入执行。
2. **执行**：按 context 提示词和输入引用执行，开始时固定实际读取的版本（读集合），产生候选操作。
3. **应用**：用户确认后，结果内容、需要新增的结果 Block 以及依赖记录在一次 Commit 中生效，以读集合作为前置条件。执行期间输入发生变化时应用冲突，不能先把状态标为“最新”；失败、取消或冲突时保留旧结果及旧依赖记录。

分析与执行是两次独立运行，可以分别重试。只修改原始提示词时，context 提示词标为“需要重新分析”。

计算归属：本期只有显式执行。收到变化事件的客户端不会自动执行；多人同时刷新同一许愿格时，应用阶段的前置条件保证只有一个结果被接受，另一方得到冲突并可查看已接受的结果。这是对[分层架构](<BuckyOS AI Workspace 分层架构.md>)中“多人场景的计算归属”的本期回答，需回写该文档。

### 7.3 结果写入与依赖记录

- **覆盖方式**：结果写入输出目标的固定名称，可以是单个实体或一个容器（`$container/$blockname`）。结构不变的刷新保留实体身份，引用它的 Block 和下游许愿格不变；之前的结果通过版本历史查看和回滚（§7.4）。
- **新建方式**：每次运行按命名规范新建一组实体，并在画布上生成对应的一组 Block，便于用户比较和选择；不移动、不覆盖旧结果。
- **结构变化**：结果结构变化（例如镜头数改变）时，能按名称对应的保留身份，多出的新建；本次没有生成的旧结果不自动删除，而是在许愿格上列为“上次存在、本次未生成”，由用户处理。不自动重定向下游引用，原型中的自动重定向行为不保留。
- **依赖记录**：每个结果实体记录来源许愿格、运行标识、执行器、读集合中各输入的版本格，以及生成时自身的内容版本。依赖记录是实体级的通用元数据，随 Commit 保存，不放进各类型的 payload，具体字段在 M0 冻结。表格单元格级的 `meta.derived` 保留，但改为指向许愿格与运行，不再自行保存整对象版本。
- **读集合**：直接复用执行时生成的前置条件。`store/src/proc.rs` 已按 `table_field_values`、`table_members`、`table_field_type` 等版本格生成前置条件；复用后，“是否过期”和“应用是否冲突”使用同一套版本语义。

### 7.4 版本历史与回滚

覆盖方式依赖“查看并回滚到之前的结果”。现有 `entity_versions` 只在 checkpoint/物化时登记实体版本，撤销依赖补偿提交，尚没有按实体列出和恢复历史版本的接口。M0 需确定：

- 应用许愿格结果时为结果实体登记可寻址的版本（物化该实体并写入 `entity_versions`），还是从提交历史重建。
- 新增“列出实体版本”读取与“恢复到某版本”命令。恢复是一次新的普通 Commit，可以撤销，并把依赖记录一起恢复为该版本对应的记录。
- 版本对象的保留期限，以及 Fork、导出时是否携带。

### 7.5 新鲜度与人工修改

新鲜度是基于依赖记录与当前可读取版本计算的状态，不是靠“最后更新时间”猜测。许愿格 Block、结果 Block 与数据源模式显示同一状态：

| 状态 | 判断与提示 |
| --- | --- |
| 当前有效 | 所有需要跟随当前数据的输入、许愿格配置与记录的基准一致 |
| 需要刷新 | 相关输入已变化；提示“此结果生成后，数据 1 / 数据 2 已改变”，列出可访问的变化来源 |
| 上游需要刷新 | 直接输入的值尚未变化，但该输入本身已过期；显示间接依赖，不能把整条链标为最新 |
| 引用不可用 | 目标删除、选择范围失效等；可访问时给出具体原因和修复入口 |
| 无法确认 | 离线缺少必要状态、数据没有可靠版本、权限或扩展不足；不伪装成有效或空数据 |

规则：

1. 执行开始时固定本次实际读取的基准；输入引用仍可声明跟随当前数据。不能因为执行使用了快照，就把本应跟随当前数据的依赖改成永久固定引用。
2. 用户明确指定的 `fixed_revision` 不因数据出现新版本而过期；可以显示存在新版，但固定快照缺失时仍须提示不可用。
3. 优先比较读集合的版本格；只有声明依赖整个对象时才比较整个内容版本。画布移动、缩放、选中以及无关字段变化不能使结果过期。
4. 变化流用于增量失效；重新打开、重连及导入后，还要从持久的依赖记录重新核对，不能要求浏览器一直在线才能发现变化。版本比较必须保留 epoch/快照语义，换代或导入后不能直接比较旧部署的裸 `seq`。
5. 沿依赖链传播“上游需要刷新”，但不自动执行。许愿格的输入形成环时，在分析或应用阶段拒绝；普通引用可以成环，遍历必须终止。
6. 新鲜度、执行状态、保存状态和“人工已修改”是四个维度。运行中、失败或人工修改都不能抹去输入过期的提示。
7. 刷新前识别已被人工修改的输出：结果实体的当前内容版本不等于依赖记录中的生成版本，且变化不来自该许愿格的后续运行；表格沿用单元格级 `manual_override`。为用户提供保留、显式替换或以新建方式生成三种选择；应用时再次校验输入与输出基准。
8. 新鲜度计算与依赖遍历在 core 中实现，服务端与 WASM 副本共享，经 Session 读取接口提供；前端 FreshnessService 只订阅和展示，不自行推导。

最小验证案例：用数据 1 和数据 2 经许愿格生成数据 3，修改数据 1 后，数据树、数据 3 详情、许愿格 Block 及所有引用数据 3 的 Block 显示一致的提示；移动 Block 不产生新的过期；刷新失败保留旧值；重新打开后提示仍可重建。

### 7.6 执行器与 Mock 许愿格

- **执行器契约**：
  - `analyze(原始提示词, 可见上下文) → context 提示词 + 输入引用`
  - `execute(context 提示词, 读集合快照) → 候选操作 + 告警`

  执行器不直接写文档；候选由宿主经 WorkspaceStore 提交，或经 `proc.apply` 应用。契约在 M0 冻结。
- **Mock 许愿格**：本期只实现 Mock 执行器。它是假的许愿格：交互与真许愿格一致，分析与执行的结果按固定规则从输入构造，结果标明“模拟”；支持确定性的失败注入，用于验证失败时保留旧结果。
- **实现方式**：Mock 许愿格以 HTML 扩展 Block 实现（§10.4），通过宿主的 JS API 读取输入并提交候选。原型 `canvas/agent/aigc.ts`、`agent/mock.ts` 的生成算法可以打包进该扩展复用；生成的 SVG 等图片经资产上传接口保存为 AssetRef，不再以 data URL 作为唯一存储。
- **运行记录**：Mock 在浏览器中执行，运行记录不进 `runs` 表；依赖记录中的运行标识由宿主生成，执行器标为 `mock`。
- **真实执行器**：xllm、agent-work-session 运行在服务端或 Agent 侧，后续经 `proc.*` 接入（服务端运行并产生候选，`proc.apply` 应用）。第一期的 `mock.task-summary@1` 保留为内核回归用例，不作为 demo 的执行器。

## 8. 画布模式：内容优先的自由画布

### 8.1 工作空间与多 Surface

交互方向参考 Miro 的内容优先布局：尽量把面积留给内容，工具跟随任务出现。

- 顶部保留工作区、顶层模式、画布子模式和精简状态入口。编辑与查看子模式本期完整可用；播放编辑显示入口，进入后显示“尚未实现”的占位说明。Surface 导航使用可收起的列表或切换器，提供新建、重命名、排序、切换及删除预检。
- 工具按子模式分派：编辑模式提供选择/插入工具，查看模式提供阅读与批注；缩放导航共用。数据树、属性、批注、许愿格详情均按需打开。
- 悬停提供轻量轮廓和动作提示；选中后在 Block 附近显示上下文工具；复杂配置才打开侧面属性区。不得给每个 Block 常驻一排完整按钮。
- 空白处提供插入入口：插入便签、文本、表格、图片或许愿格时，同时创建数据与 Block（§4.2）；插入框、形状时创建纯 UI Block。选中项提供编辑内容、查看依赖、增加视图和删除等动作。
- 从数据树拖入或选择“添加到画布”时，创建引用该数据的 Block；存在多个可用 Renderer 时允许选择展现。
- 每个 Surface 独立恢复个人视口（用户工作状态）。

flow 布局的 Surface 在编辑子模式下按现有流式编辑器工作，查看子模式下只读阅读，播放编辑同样是占位。保留流式编辑器不等于本期已经交付 Notion 模板体验。

### 8.2 坐标、手势与提交

共享布局使用 `TreeEdge.placement = { x, y, w, h }`。子节点坐标相对所属容器（Surface 或 UI 分组）；屏幕坐标与画布坐标由统一的视口控制器转换。缩放只改变用户视口，不改 Block 的共享尺寸。层叠顺序就是同一父节点下的 `order_key`：它是分数索引，置顶、置底只需修改一个 key，不必重排；`order_key` 相同时按 `child_id` 稳定排序。

编辑模式的最小交互：平移、缩放、适应全部/选区、单选、多选、框选、拖动、尺寸调整、层级调整、分组/解组和跨 Surface 移动。分组及跨父容器移动需要换算坐标，保持预期的视觉位置。受权限或写锁限制时，相应动作应可解释地不可用。查看模式与编辑模式共用视口和选择基础设施，按 §10.2 的模式策略开放操作。

拖动和尺寸调整期间只更新本地预览，完成时合并为一次 `tree.place` / `tree.move` 命令组；Esc 取消且不提交。一次手势形成一个撤销单位，不能每次 pointermove 都发 Commit。

并发按 D1 处理：

- 交互式布局操作不带 `expect`，后台按接受顺序逐个生效，后到者的位置为最终位置。
- 收到他人对布局的变化时，本地若没有进行中的手势则直接更新；若正在拖动同一 Block，手势结束后照常提交本地意图。
- 位置被他人覆盖的一方会看到“位置已被他人修改”的提示，并可一键重新应用自己的最后位置（一次新提交）。
- 撤销使用带 `expect` 的逆操作；若之后又被他人移动，按第一期规则报告冲突。
- 离线排队的布局操作在重连后按同一规则重新规划。
- 无关的数据内容修改不能引发布局冲突。

输入路由要区分画布操作与内容编辑：文本选择、输入法组合输入、表格滚动、输入框快捷键不能同时触发画布拖动或删除。键盘可以选中并激活 Block、打开动作菜单，Esc 逐层退出编辑、菜单和选择；核心动作不能只依赖鼠标悬停。

### 8.3 静态 Block 与激活编辑器

编辑模式中，Block 首先以静态内容展现，用于选中、移动和排布。“静态”表示不自动播放媒体、不自动运行许愿格或 HTML 扩展、不直接执行业务按钮，但仍应随已提交的数据变化更新显示。查看模式可以提供类型声明的阅读交互；播放编辑占位期间，Block 以静态内容显示。

在编辑模式中，用户双击或使用明确的“编辑内容”动作后，BlockHost 才挂载或激活对应 Editor；一次只让当前编辑目标接管输入，结束编辑后回到静态 Renderer。数据源模式可以直接呈现同一 Editor，不必通过画布手势激活；查看模式不沿用双击修改数据内容的行为。

许愿格的“分析”“执行”和媒体的“预览”都是显式动作：前者进入受控的许愿格流程（§7.2），后者打开可关闭的局部预览。局部视频预览不等于播放模式，也不引入演示编排。

### 8.4 浮动工具与标注

浮动工具位于屏幕坐标层，根据 Block 变换后的边界定位，并处理视口边缘避让。标注沿用 `AnchorRegistry` 的目标/范围/原文语义；缩放、排序、拖动及切换 Surface 不改变逻辑锚点。查看模式允许有 `comment` 能力的用户新增和回复批注（D13）。

## 9. 渲染架构与性能

用 Web 技术实现的无限画布，在对象数量、缩放跨度和嵌入的富交互内容增多时容易出现性能问题。这是架构问题，不能留到实现末期再优化。本节确定本期的渲染路线、必须遵守的规则和 M0 探针。

### 9.1 业界经验

| 产品 | 公开资料中的做法 | 对本期的启示 |
| --- | --- | --- |
| tldraw | 形状以 DOM/SVG 渲染；空间索引追踪可见形状，屏幕外的设为 `display: none` 而不卸载，选中和正在编辑的形状不裁剪；用信号做细粒度订阅，批量更新；按缩放降低细节（图片按 2 的幂档位选分辨率，低缩放下去掉阴影、虚线）；形状很多且相机移动时使用稳定的缩放值，避免反复重算 | 千级对象的 DOM 路线可行，前提是裁剪、细粒度订阅与 LOD |
| Excalidraw | Canvas 2D；静态层与交互层分开：静态层缓存、只在元素变化时重绘，选框、手柄、协作者光标、吸附线画在交互层 | 内容层与交互覆盖层分离 |
| React Flow | DOM 节点、整体视口变换；可选“只渲染可见元素”，但挂载/卸载与每帧裁剪计算本身有开销，维护者提醒需要实测 | 裁剪要有滞后边距，避免平移时的挂载风暴，用数据决定参数 |
| Miro 代码块 | 画布上用静态语法高亮渲染代码，只在编辑模式启动代码编辑器，否则大量代码块会有明显的性能问题；把模式切换作为重点性能测试项 | 与本期的“静态 Block＋激活编辑器”一致；模式切换要进探针 |
| Figma | C++ 编译为 WebAssembly，自绘 WebGL（现已支持 WebGPU）；高层渲染代码与底层图形 API 之间有接口层 | 极限规模需要自绘；渲染后端应可替换 |
| Google Docs | 2021 年从 DOM 渲染改为 Canvas 渲染，理由是性能与跨平台一致 | 必要时低细节层可以改为 Canvas 绘制 |

参考资料：[tldraw Performance](https://tldraw.dev/sdk-features/performance)、[tldraw Culling](https://tldraw.dev/sdk-features/culling)、[Excalidraw 渲染系统](https://deepwiki.com/excalidraw/excalidraw/5-rendering-and-export)、[Excalidraw issue #10063](https://github.com/excalidraw/excalidraw/issues/10063)、[React Flow API](https://reactflow.dev/api-reference/react-flow)、[xyflow PR #5830](https://github.com/xyflow/xyflow/pull/5830)、[Miro Code Block Widget](https://medium.com/miro-engineering/the-miro-code-block-widget-an-approach-backed-by-research-684ad5d2a1cd)、[Figma: Building a professional design tool on the web](https://www.figma.com/blog/building-a-professional-design-tool-on-the-web/)、[Figma Rendering: Powered by WebGPU](https://www.figma.com/blog/figma-rendering-powered-by-webgpu/)、[Google Docs Switches to Canvas Rendering](https://thenewstack.io/google-docs-switches-to-canvas-rendering-sidelining-the-dom/)。

### 9.2 本期渲染路线

本期采用以 DOM 为主的分层渲染（D14）：

| 层 | 内容 | 实现 |
| --- | --- | --- |
| 内容层 | Block 的静态 Renderer 输出 | DOM/SVG，放在同一个世界层容器内；平移缩放只改世界层的一个 CSS 变换，不逐个重新定位 Block，也不触发 React 渲染 |
| 低细节层 | Block 在屏幕上很小时的占位：外框、标题、缩略图 | 由 RenderHost 统一绘制，不要求每个 Renderer 实现；必要时改为 Canvas 2D（§9.4） |
| 覆盖层 | 悬停轮廓、选框、尺寸手柄、对齐线、框选矩形、就近工具 | 屏幕坐标的 SVG/Canvas，由选择与相机状态驱动，不重渲染 Block |
| 编辑层 | 当前激活的富文本、表格编辑器或 HTML 扩展 Block | 一次只挂载当前编辑目标的真实交互 DOM |

### 9.3 必须遵守的规则

1. **相机不进 React 状态树**：平移、缩放期间不重渲染 Block；手势停止后，按稳定的缩放值更新 LOD 和裁剪（节流）。
2. **空间索引**：维护 Block 世界坐标包围盒的空间索引，用于可见性裁剪、命中测试、框选与对齐吸附。命中测试按几何计算，不依赖每个 Block 的 DOM 事件。引入 R 树等第三方库需先确认；也可以自实现网格索引。
3. **裁剪分三级并带滞后**：
   - 可见区及外扩边距内挂载静态内容；
   - 更远处保持挂载但设为 `display: none`；
   - 超出内存预算或长时间不可见才卸载。

   选中、正在编辑、有未保存输入的 Block 永不裁剪；用滞后边距避免平移时反复挂载和卸载。
4. **细粒度订阅**：每个 Block 只订阅自己的结构条目（父节点、`order_key`、`placement`）和所引用数据的版本，一个 Block 的变化不重渲染其他 Block。结构变化按事件增量应用，不再整份重拉 `doc.outline`；变化事件是否携带边数据，还是按条目补读，在 M0 确定。
5. **手势不经过状态树和网络**：pointermove 合并为每帧处理一次；拖动时直接变换被选中 Block 的元素（或拖动代理层），不写 React 状态、不发网络请求，结束时一次提交。
6. **按可见区加载数据**：Block 进入可见区的外扩范围后才读取数据。打开 Surface 时，用批量读取获取 Block 配置和可见 Block 的数据，不为每个 Block 单独往返；大表只读当前页。
7. **LOD 由声明驱动**：BlockDefinition 至少声明静态渲染，可选声明简化渲染；低于阈值时由 RenderHost 显示占位。图片按屏幕尺寸选择分辨率档位（缩略图派生，2 的幂档位）；视频只显示封面帧，画布上不常驻解码器。
8. **昂贵元素有并发上限**：同时挂载的编辑器、HTML 扩展 Block 和视频解码器各有上限。HTML 扩展 Block 默认显示静态快照，激活时才挂载。
9. **避免布局抖动**：渲染循环中不交替读写布局；Block 尺寸以共享的 `placement` 为准，不靠测量 DOM 得出；ResizeObserver 只用于激活的编辑器。
10. **文字清晰度**：缩放过程中允许合成层直接缩放（`will-change`），停止后重新栅格化，保证静止时文字清晰。
11. **重计算移出主线程**：图表聚合、查询、依赖遍历放在 Worker（离线副本已有 Worker）或后台完成。

### 9.4 渲染后端可替换

Renderer 契约不暴露世界层和相机的实现：Renderer 只拿到数据快照、尺寸与显示上下文，输出静态视图；相机、裁剪、LOD 占位、覆盖层都由 RenderHost 负责。若 M0 探针证明 DOM 内容层在目标规模下达不到门槛，可以把低细节层和覆盖层换成 Canvas 2D，而不改 BlockDefinition 和 Renderer。全面自绘（WebGL/WebGPU、WASM 渲染引擎）不在本期范围。

### 9.5 M0 渲染探针

探针在真实的 RenderHost 骨架上测量，不在旧原型上测：

- **规模**：单个 Surface 分别放 1,000 和 5,000 个轻量 Block（文本、便签、框、图片缩略图），另含 20 个表格/图表 Block，以及 1 个引用 10,000 行表格的 Block；另有 3 个 Surface 共 1,000 个 Block 的多画布 fixture。
- **操作**：冷打开、切换 Surface、连续平移、跨 LOD 阈值缩放、框选 500 个后拖动、激活与退出富文本编辑器、切换画布子模式、远端客户端每秒 10 次布局变化。
- **指标**：首个可操作视图时间、帧耗时 P50/P95、长任务（超过 50 ms）次数、DOM 节点数、挂载的编辑器与 HTML 扩展 Block 数、JS 堆与解码图片内存、网络请求数。
- **环境**：以约定的桌面 Chromium 环境作为首个基准，记录硬件、浏览器、构建方式和数据规模。

建议的首轮门槛（1,000 Block 规模）：首个可操作视图在 2 秒内；平移缩放帧耗时 P95 不超过 16.7 ms；多选拖动 P95 不超过 32 ms；交互期间不出现 200 ms 以上的连续主线程阻塞。5,000 规模先记录数据，作为是否启用 §9.4 退路的依据。M0 探针后冻结正式门槛，不能把这些建议值写成现有性能结论。

无论设备速度如何，都必须证明：工作量受可见区和已激活编辑器约束；不会为每个 Block 挂载编辑器；不会为展示一个表格而下载整表；手势期间不产生连续的网络写入；离屏卸载不丢失输入。

## 10. Block 与数据扩展契约

### 10.1 两个扩展点

数据扩展决定“数据如何读取、编辑、校验和寻址”；Block 扩展决定“数据如何呈现、有哪些配置与动作”。二者通过绑定契约组合，不能为每一种图表再复制一种数据存储。

| 注册项 | 必须声明的职责 |
| --- | --- |
| SourceAdapter | 对应的数据类型/Schema 版本、详情与原始数据投影、编辑器、属性描述、支持的稳定选择器与依赖读取范围 |
| BlockDefinition | 稳定类型与版本、允许的数据类型与绑定数量、是否允许无源、配置 Schema、默认尺寸、支持的 View、编辑与查看子模式的 Renderer/Editor/动作映射、静态与简化渲染（§9.3 第 7 条）、成本声明（是否需要编辑器或运行 HTML）、回退规则 |
| Renderer | 根据数据快照、显示上下文和交互状态产生视图；不自行保存、不在渲染时执行许愿格 |
| Editor | 在用户激活后编辑数据或视图配置，返回受校验的操作，复用版本、权限、写锁和撤销 |
| Action / Inspector | 声明动作、属性、适用子模式及可用条件；由宿主统一放入就近工具、菜单和属性区 |
| LayoutAdapter | 解释容器布局与子项尺寸/位置；本期实现 free，保留已有 flow，后续接排版容器 |

**校验边界（D6）**：

- 后台只校验 Cell 的数据引用目标存在且是已知数据类型、Renderer 标识与版本格式合法、配置大小受限。后台不判断某个 Renderer 是否支持该数据类型；由前端注册表判断，不支持时由 BlockHost 回退为通用只读视图。新增 Renderer 不需要修改或发布后台。
- 内置表格视图对字段 ID 等引用的校验保留在后台，因为它们关系到数据一致性。
- 前端 SourceAdapter 不代替 Rust 的类型校验。新增持久数据类型时，服务端和 WASM 必须共享对应的确定性适配器；仅新增展现时，应优先复用已有的 Record、TableSource 等类型。

### 10.2 模式与交互状态是正交维度

本期建立独立的 `CanvasMode` 状态，取值为 `edit`、`view`、`presentation_edit`。它与顶层 UI 模式、对象权限和选中状态分开。宿主向 Renderer 提供 `view`、`canvasMode`、`selected`、`hovered`、`editorActive`、有效权限、只读原因和数据可用状态，实际驱动渲染与交互分派。

| 画布子模式 | 未选中 | 悬停 | 选中 | 本期 |
| --- | --- | --- | --- | --- |
| 编辑 | 静态内容 | 轻量轮廓、动作提示 | 选框、尺寸手柄、就近工具；显式激活 Editor | 完成主要的内容与布局编辑路径 |
| 查看 | 类型定义的阅读/交互表现 | 阅读动作提示 | 阅读焦点、选区及适用动作，不显示布局手柄 | 完成阅读交互与批注；除批注外不开放文档写入 |
| 播放编辑 | 静态内容 | 无 | 无 | 只有入口与“尚未实现”的占位；不选中、不写文档、不注册专用实现 |

选中对象也可以被悬停，所以二者采用独立标志，默认以选中外框优先，不重复绘制工具条。类型可以按模式定制内容表现；选择边界、焦点与可访问性由 Host 保持一致。注册表按编辑、查看子模式选择 Renderer、Editor、动作和 Inspector；未提供专用实现时使用声明的共用实现或静态回退，不继承其他模式的写入行为，也不默认运行代码。`presentation_edit` 保留在枚举和分派表中，以后实现时只增加注册，不修改 Host。

模式策略同时约束手势、双击、快捷键、工具栏和动作执行入口，不能只隐藏按钮。查看模式保留平移、缩放、文本选择、链接、临时筛选、显式媒体预览和批注。动作是否可执行，取决于模式策略、类型声明、对象权限、写锁与当前可用状态的共同约束；切换到编辑模式不会增加用户权限。

切换子模式时保留活动 Surface、视口和仍有效的选择；取消尚未完成的拖拽预览，释放旧模式的输入接管，按原保存策略结束编辑或保留可恢复输入。切换本身不创建文档 Commit，既有的待提交操作继续按原流程处理。模式名称和当前只读原因要分别呈现。

验收必须从真实画布入口切换三个子模式。编辑与查看要覆盖未选中、悬停、选中及选中后悬停四种状态；至少一个验证用 Block 提供可区分的编辑/查看展现，以及模式专用的动作或 Inspector，并覆盖缺少专用实现时的回退；播放编辑验证为可进入、只读的占位。仅声明枚举或在测试宿主中模拟参数，不算完成。

### 10.3 持久化与 Block 定义实体

- Cell 记录实际使用的 Renderer 标识、版本、配置及所需资源引用；打开者缺少该版本时，不能静默改用效果不同的“最新版本”。格式或协议有变化时必须显式升级版本，并给出迁移或拒绝策略；本期不建设通用兼容层。
- 非内置的 Block 定义作为文档实体保存（新类型，暂称 `buckyos.block_def`），位于数据树中，随导出、Fork 与离线副本携带。Cell 通过引用使用定义，该引用阻止删除。
- 定义分为两种：
  - **声明式**：字段绑定、布局原语、属性与动作描述；动作只能映射到已有命令或许愿格执行。
  - **HTML**：由 HTML 扩展宿主挂载运行（§10.4）。
- 内置 Renderer 是代码注册的实现，可以复用 React。声明式定义只由解释器解释，不执行其中的代码；HTML 定义按 §10.4 运行。
- 未知 Renderer、未知数据类型和不支持的 Schema 版本分别报告；原始内容仍可保留、导出，并通过通用只读视图检查。

### 10.4 HTML 扩展 Block

BuckyOS 是 OOD 体系：Owner 完全拥有自己的域名和 Zone，本来就可以在自己的站点上放任何代码。这与 Google Docs 等第三方托管的服务根本不同。因此 HTML 扩展 Block 不按“运行不可信代码”设计沙盒（D16）：

- **信任与风险**：Owner 是信任根，HTML Block 的风险由 Owner 自己管理。对 Workspace 的读者来说，安全边界等同于访问 Owner 的网站。大部分 HTML Block 由 Owner 用 Code Agent 构造。
- **运行方式**：与 Desktop 同源运行，可以联网和加载第三方库，不设 CSP 限制，不做能力交集。挂载在 iframe 中还是直接挂载由实现选择；选 iframe 是为了样式隔离、崩溃隔离和挂载管理，不是安全边界。
- **编程接口**：宿主提供稳定、版本化的 JS API：
  - 读取绑定数据的快照与有限的上下文；
  - 提交候选操作，由宿主经 WorkspaceStore 提交，复用权限、写锁、撤销与保存状态；
  - 上传资产；
  - 报告静态快照。

  这套 API 给 Code Agent 一个明确的生成目标，并让写入进入统一的撤销与保存流程。它不是安全边界：代码绕过它直接调用 kRPC，技术上不受阻止，但这样的写入不进入撤销栈和保存状态。
- **生命周期（性能）**：编辑与查看模式默认显示静态快照（扩展上次运行后报告并保存为资产；没有时显示占位），用户显式激活或执行动作时才挂载；同时挂载的数量受 §9.3 的上限约束。
- **错误与超时**：抛错、崩溃或无响应时局部回退，不影响其他 Block。
- **本期范围**：只用于 Mock 许愿格和一个验证样本；不建设 AI 生成扩展代码的管线和扩展市场。

非 Owner 引入的 HTML 定义在 Owner 打开时会以 Owner 的会话运行。本期优先能力，不加限制，作为已知风险记录（§15 R1）。

### 10.5 扩展样本

无限扩展是架构目标，本期用以下三个样本证明机制：

1. 为同一 TableSource 注册一种新的指标或图表 Block（代码注册），不修改 Shell、选择工具、保存流程和撤销机制。
2. 用一份人工准备、模拟 AI 产出的声明式 Block 定义实体，绑定已有的 Record/TableSource，提供属性与动作描述；经相同的注册、校验和回退路径加载，不为它写专用的画布逻辑。
3. Mock 许愿格：一个 HTML 扩展 Block，走完分析、执行、应用全流程。

这些样本验证扩展契约，不等于已支持任意 AI 生成代码的开放执行。

## 11. 两个 ai-canvas demo 的迁移验证

先完成画布框架和许愿格，再迁移场景。入口位于 `canvas/fixtures/sample-canvas.ts` 和 `canvas/fixtures/aigc-workflow.ts`；其现有演示路径本期不迁移。

### 11.1 季度经营分析

销售表迁移为数据树第一层的 TableSource；说明与摘要为 RichText，指标为 Record，图表为引用数据的 Block；许愿格为 Mock 许愿格，结果写入该 Surface 画布内容区中的命名结构，生成指标、区域对比、异常明细与摘要。

验收路径：

1. 创建示例 Workspace，在数据源模式中检查并修改销售数据。
2. 在两张 Surface 中创建共享该数据的不同 Block，确认视图配置互不影响。
3. 从许愿格显式运行 Mock：分析得到 context 提示词并检查输入，执行后预检，把结果、Block 和依赖记录一次应用；结果标明“模拟”。
4. 改动相关输入后，两种模式均显示结果需要刷新；修改布局不触发重算，也不误判过期。
5. 人工修改摘要后刷新，验证保留/替换/新建、版本冲突、一次撤销、失败时保留旧结果，以及回滚到上一版本的结果。
6. 保存、重新打开、导出再导入，恢复数据、绑定、布局与可解释的依赖状态。

本期以固定 fixture 作为主验收输入；CSV/XLSX 导入可以在复用原解析器并接入正式命令后补充，不把完整的 Excel 兼容作为画布架构验收的前置条件。

### 11.2 AI 短片工作流

迁移“剧本＋角色表＋风格 → 角色设定图 → 故事板/分镜表 → 成片预览”的多阶段链路。剧本、角色表、风格是数据；三个阶段是三个 Mock 许愿格，上一阶段的输出容器是下一阶段的输入引用。图片和预览帧通过正式的 AssetRef 与资产上传路径保存，不能继续把旧 CanvasDocument 中的大块 data URL 作为唯一存储。

验收重点：

- 许愿格、视觉框、图片、表格、文本、媒体预览组合为普通 Block，使用同一套选择、移动和属性机制。
- 从任一结果都能查看上下游依赖，并定位相关的 Surface。
- 角色设定图以新建方式运行两次，画布上出现两组可比较的结果；故事板以覆盖方式运行，并可回滚。
- 修改角色表或剧本后，显示直接过期与间接的上游过期；按顺序显式刷新，不因多个客户端收到变化而重复运行。
- 结果结构稳定时保留引用身份；结构变化、人工修改和取消/失败均按正式内核规则处理。
- 使用确定性 Mock 和原有的逐帧预览说明架构，不宣称生成了真实模型视频；默认画布保持静态，用户显式打开预览。

迁移后的两个 demo 必须通过 WorkspaceSession、正式命令、许愿格应用入口和资产接口运行，不保留 `APPLY_AGENT_PATCH` 这第二套写入链。
