# BuckyOS AI Workspace 第二期规划

> 状态：第二期实施规划，待实现与验收。
>
> 实现基线：2026-10-06 工作区中的源码，包含当前尚未提交的第一期改动。本文的“已有”表示源码中已有相应能力，不表示本次重新执行了第一期验收。
>
> 核心目标：**完成并验证 Workspace UI 框架的架构设计，以自由画布为重点，使数据源、Block、布局和交互能够独立扩展。**

## 1. 本期交付与范围

第一期建立了文档内核、统一命令、内置数据对象和浏览器离线副本。第二期在这些能力上形成正式的 UI 框架：用户既能集中管理数据，也能在多张画布上组织同一份数据；开发者或 AI 增加一种展现时，不需要重新实现工作区、保存、权限和撤销。

系统具有三个顶层 UI 模式：

| 顶层模式 | 用户目的 | 第二期范围 |
| --- | --- | --- |
| 数据源模式 | 管理原始数据、加工结果、引用关系和权限 | 在现有界面与编辑器上改进，完成左中右分栏及来源状态 |
| 画布模式 | 将数据和工具组织成可编辑的视觉工作空间 | 本期重点：多画布、自由布局、Block 宿主、就近操作、扩展契约 |
| 播放模式 | 点击“开始演示”后，按演示编排呈现内容 | 本期不实现；只明确其与文档、画布及运行状态的边界 |

画布模式未来还包含**编辑模式、查看模式、播放编辑**三个子模式。本期不提供这三个子模式的切换和完整行为，只交付默认的画布编辑体验，并在渲染契约中预留模式维度。“播放编辑”是编排演示，“播放模式”是执行演示，二者不能合并。

本期完成的判据是：同一数据源能在数据源模式中编辑，在不同画布上以不同 Block 展现；数据变化、引用失效、权限、离线和撤销在两种界面中保持同一语义；新增 Block 类型只需注册扩展；最后用旧 ai-canvas 的两个 demo 验证这些边界。

明确延后：

- 播放入口、演示路径编辑、时间轴、镜头切换、讲解者跟随及演示导出。
- 三个画布子模式的产品实现，以及每种类型完整的三套渲染器。
- Notion 式排版容器与新建画布模板；在自由画布核心完成后另行排期。
- 完整公式引擎、自动重算调度、跨 Workspace 发布与全局反向引用发现。
- 任意 AI 生成 JavaScript 的开放执行、扩展市场、真实模型和视频生成服务。
- 全设备交互、多用户光标等新协作体验；现有权限、并发和离线语义仍须保留。

本文收敛本期边界；较早的[核心设计](<BuckyOS AI Workspace 实现的核心设计.md>)中包含演示的长期闭环，不直接作为第二期必须完成的范围。

## 3. 统一模型：数据源、画布与 Block

### 3.1 概念与身份

| 概念 | 本期落点 | 约束 |
| --- | --- | --- |
| 数据源 | 已有 TableSource、RichText、Record、AssetRef 及其扩展 | 持有业务内容，与画布坐标无关 |
| 画布 | `buckyos.container`，`kind: page`，`layout.mode: free` | 一份 Workspace 可包含多张；沿用已有 page 身份，不另建平行 Canvas 文档 |
| 数据 Block | `buckyos.cell`＋数据引用＋Renderer 配置 | 多个 Cell 可以引用同一个源；每个 Cell 的布局和展现配置独立 |
| 画布专用 Block | 无数据源的装饰 Cell，或具有明确作用的 Container | 如背景框、形状、连接线；不为它们伪造业务数据源 |
| 布局容器 | 当前 Container 的布局策略扩展点 | 自由布局先实现；流式阅读能力保留，Notion 式排版后续实现 |
| 来源关系 | 描述生成结果、输入版本和加工配置的文档数据 | 与视觉分组、树父子关系、临时任务状态分开 |

产品中使用 Block 一词，现有协议中的数据视图仍称 Cell。富文本内部的 `block_id` 是文本锚点身份，不是画布 Block 身份。视觉框只是布置内容；需要成员关系时才使用 Container；生成结果集合另由来源记录指明，不能依赖“恰好位于同一矩形内”。

当前内核只允许 root 下放 page，数据源通常归属于某个 page/group。本期沿用该结构：数据源树是整个 Workspace 的**管理投影**，不因切换模式而重挂对象，也不强行新增根级“数据仓库”。源可以留在原属页，由其他页的 Cell 引用。

### 3.2 结构、引用与删除

- Block 跨画布移动：改变 Cell 的父节点和布局，保持 Cell ID、源 ID、标注及来源关系。
- 在另一张画布展示同一数据：创建新的 Cell，复用 `source_ref`；“复制数据”是另一个明确操作。
- 从画布移除一个数据 Block：只删除 Cell，不自动删除源。删除源前展示已授权的引用影响，遵守内核引用约束。
- 删除画布：按实际子树预检；若其源仍被其他画布引用，应先移动保留对象或处理引用，不能把视觉删除解释成无条件级联删除数据。
- 移动对象可能改变继承权限。跨页移动必须按目标父节点重新校验权限；拥有画布结构权限不等于拥有源的修改权限。
- 画布专用 Block 不进入默认数据源列表，但可在画布对象列表和引用详情中定位。“不展示在数据源列表”不是安全边界。

### 3.3 三类状态

| 状态归属 | 内容 | 保存与传播 |
| --- | --- | --- |
| 共享文档 | 源内容、Cell 绑定、Renderer 标识与配置、树结构、`placement`、来源记录 | 经 Command 提交、撤销、同步、导出 |
| 用户工作状态 | 当前 UI 模式、活动画布、每张画布视口、面板开关和宽度、临时筛选 | 按用户与 Workspace 保存；切换界面不生成文档 Commit |
| 当前交互状态 | 悬停、选区、拖拽预览、激活的编辑器、临时媒体预览 | 当前会话维护，不广播、不进入共享包或撤销栈 |

本期不保存演示运行状态。未来播放过程中相机、显隐、动画对文档的覆盖应属于播放会话，不能写回基础布局。

## 4. UI 框架分工

```text
WorkspaceShell：模式入口、保存/同步状态、统一撤销、通知
├─ DataSourceSurface：数据树、源详情、权限分组、属性
└─ CanvasSurface：画布导航、视口、选择、手势、就近工具
   └─ LayoutHost → BlockHost → Renderer / 按需激活的 Editor

共用服务：SourceAdapterRegistry / BlockRegistry / 属性与动作描述
          ReferenceService / FreshnessService / 权限与写锁 / AnchorRegistry
                          ↓
               WorkspaceStore + WorkspaceSession
                    ↙                 ↘
         OnlineWorkspaceSession    ReplicaWorkspaceSession
                    ↓                 ↓
              Rust 服务内核       Worker / WASM 同一内核
```

图中 Surface、Host、Registry 和关系服务是本期拟新增的前端职责，不是已有 RPC 名称。

关键约束：

1. Shell 管模式与全局状态，Surface 管工作方式，LayoutHost 管排布，BlockHost 管生命周期、交互外框和错误，Renderer 管内容展现。不能把所有职责继续堆在 `WorkspaceView.tsx`。
2. Renderer 和属性编辑器只获得受限的读取、动作及提交桥，不直接调用底层 client、操作数据库或维护私有保存流程。
3. 文档变更通过 `WorkspaceStore.submit()` 及现有加工应用入口；统一记录保存状态、撤销和冲突。权限变更属于部署管理操作，经 Session 转发已有 `ws.*`，不伪装成可离线撤销的文档 Commit。
4. 模式切换不销毁 Workspace 会话、撤销协调器和待提交队列。正在编辑的内容按原策略提交或保留为可恢复输入，不能因组件卸载而丢失。
5. 原有“未保存／已保存到本设备／已提交／需要处理”、写锁与权限提示在两种 Surface 中都可见；详细记录按需展开，不长期占据画布。
6. Renderer 缺失、源不可读或单个视图异常时，由 BlockHost 提供局部回退，不使整个工作区无法打开和保存。

## 5. 数据源模式

### 5.1 左中右分栏

```text
┌─────────────────── 顶栏：工作区 / 模式 / 保存与同步 ───────────────────┐
│ 左侧                      │ 中间：当前选择的详情       │ 右侧：属性    │
│ 上：Workspace 数据源树     │ 内容 / 引用与来源          │ 类型与 Schema │
│ 原始数据、派生数据、素材   │ 原始值、表格或专用编辑器    │ 版本、来源    │
│                           │ 我引用谁 / 谁引用我        │ 权限、写锁    │
│ 下：权限管理              │ 选择权限项后显示授权详情   │ 可编辑配置    │
│ 预设权限组、实际授权       │                            │               │
└───────────────────────────┴────────────────────────────┴───────────────┘
```

左侧上半区覆盖所有可读取的数据源，按所属页/组组织，可按类型与原始/派生来源筛选。不能继续把所有 Cell、Container 和源混成没有区分的对象列表。没有被画布引用的数据源也应可管理。

选中源后，中间展示源自身的内容：表的记录与字段、富文本、Record 属性、资产信息及预览；可展开受权限过滤的原始结构。源详情不必先创建一个 Cell 才能编辑。复用现有表格与富文本能力时，应把“数据编辑”从“Cell 外框与视图配置”中拆开。

右侧展示当前对象的类型、稳定身份、版本、来源、权限与写锁等属性；提供的编辑项必须有对应命令。原始值编辑、视图选项修改和 Schema 修改要清楚区分。单击引用可打开对应源；选择“在画布中定位”后切换到相应画布并聚焦 Cell。若同源有多个 Cell，应先列出可访问的位置。

### 5.2 引用与加工依赖

数据源详情要同时回答：**它包含什么、它引用了谁、谁在使用它、结果是否仍对应当前输入。** 本期以 Workspace 内部引用为主。

| 关系 | 示例 | UI 语义 |
| --- | --- | --- |
| 展现绑定 | 销售表 → 表格 Cell、图表 Cell | 显示同一数据，源变化后更新展现，不称为 AI 结果过期 |
| 普通引用 | Record 的对象引用、富文本嵌入、标注锚点 | 可定位目标，按 live/fixed 语义解释 |
| 加工依赖 | 数据 1、数据 2 → 计算/AI → 数据 3 | 记录实际采用的输入版本；非实时结果在相关输入变化后提示需要刷新 |

现有 `refs` 可以作为正反向查询的基础，但不能自动推断出完整加工血缘。`runs.inputs_json` 属于本部署的运行记录，表格 `meta.derived` 也不能覆盖全部结果类型。第二期需补齐以下文档契约：

- 每次被正式接受的加工结果关联一份来源描述，记录输入引用及选择范围、读取版本、程序/配置版本、输出目标和生成基准；多个输入、多个输出均可表达。
- 来源描述作为独立、可版本化的文档对象保存，通过内核类型适配器校验，并将引用纳入索引。具体类型标识和 Schema 在 M0 冻结；不能只存在浏览器内存或 `runs` 表。
- 表格范围使用稳定的 record/field ID 或声明的动态查询条件；不把显示行号当成依赖。动态查询还需记录决定成员集合的条件、成员版本及相关字段类型版本。
- 新生成内容、结果成员关系和来源描述在同一次文档提交中生效。刷新失败、取消或校验冲突时保留旧结果及其旧来源；不能先把状态改成“最新”。
- 关系查询通过新增的 Session 读取接口提供，在线与离线读取遵循同一投影。权限过滤在服务/副本读取边界完成，不返回无权对象的名称、内容或全局引用数量。
- 反向引用只声明“当前 Workspace 中我有权查看的引用”；不承诺发现外部所有使用者。关系页不能为画图而把大表完整下载到浏览器。

### 5.3 新鲜度与人工修改

新鲜度是基于来源记录与当前可读取版本计算的状态，不是依靠一个“最后更新时间”猜测：

| 状态 | 判断与提示 |
| --- | --- |
| 当前有效 | 所有需要跟随当前数据的输入、加工配置与记录的基准一致 |
| 需要刷新 | 相关输入已变化；提示“此结果生成后，数据 1 / 数据 2 已改变”，列出可访问的变化来源 |
| 上游需要刷新 | 直接输入的值尚未变化，但该输入本身已过期；显示间接依赖，不能把整条链标为最新 |
| 引用不可用 | 目标删除、选择范围失效等；可访问时给出具体原因和修复入口 |
| 无法确认 | 离线缺少必要状态、源无可靠版本、权限或扩展不足；不伪装成有效或空数据 |

规则：

1. 加工开始时固定本次实际读取的基准；逻辑绑定仍可声明跟随当前源。不能因执行使用了快照，就把本应跟随当前数据的依赖改成永久固定引用。
2. 用户明确指定的 `fixed_revision` 不因源的最新版本改变而过期；可显示存在新版，但固定快照缺失仍须提示不可用。
3. 优先比较真实读集合的版本格。只有声明依赖整个对象时才比较整个内容版本；画布移动、缩放、选中、无关字段变化不应无条件使结果过期。
4. 变化流用于增量失效；重新打开、重连及导入后还要从持久来源记录重新核对，不能要求浏览器一直在线才能发现变化。版本比较必须保留 epoch/快照语义，换代次或导入后不可直接比较旧部署的裸 `seq`。
5. 对依赖链传播“上游需要刷新”，不自动执行计算。加工依赖环应在配置或应用时拒绝；普通引用可以成环，遍历必须终止。
6. 新鲜度、任务执行状态、保存状态和“人工已修改”是四个维度。运行中、失败或人工修改都不能抹去输入过期提示。
7. 刷新前识别已被人工修改的输出，提供保留、显式替换或生成副本。应用时再次校验输入与输出基准；副本使用新 ID，不能把旧结果的下游引用静默切走。
8. 本期对结构不变的刷新保留输出身份；结果结构发生变化时明确处理失效引用。不能照搬原型中自动重定向全部下游的行为。

最小验证案例：用数据 1 和数据 2 生成数据 3，修改数据 1 后，数据源树、数据 3 详情及所有引用数据 3 的画布 Block 显示一致提示；移动其 Block 不产生新过期；刷新失败保留旧值；重新打开后提示仍可重建。

### 5.4 左下权限管理

现有模型是主体在 Workspace 或实体子树上的能力授权；有效能力沿结构路径取并集，没有 deny 和字段级授权。`ws.list_grants` 目前要求 Workspace 的 `manage` 权限。

本期“预设组”先落实为**预设权限组合与对应授权主体的分组展示**，使用现有 grant 协议，不伪造后台尚不存在的动态用户组成员关系：

| 预设权限组 | 默认能力 |
| --- | --- |
| 阅读者 | `read` |
| 评论者 | `read`、`comment` |
| 编辑者 | `read`、`append`、`update`、`delete`、`structure`、`comment` |
| 管理者 | 现有全部能力，包含 `export`、`manage` |
| 自定义 | 展示实际 capability 集合；例如仅追加，或单独授予导出 |

界面必须能查看预设组合、实际授权主体、授权作用域和继承来源。有 `manage` 的用户可选择主体与作用域授予、调整或撤回权限；没有该能力的用户显示自己的有效能力，不读取完整授权名单。`*` 的含义是任意已认证主体，不能标成匿名公开访问。

授权行更新是替换该主体在该作用域的能力集合；UI 应明确显示本次保存后的集合。撤回子树直接授权后，祖先或 Workspace 授权可能仍使权限有效，不能提示“已禁止访问”。角色名称只是预设解释，以后台返回的实际能力为准。

权限管理操作在线执行，不排入离线文档队列；权限页面重新进入或执行管理操作后重新读取授权，不能假定它会产生普通文档变化事件。断网时缓存权限标为最近已知状态，重连提交按当前后台权限校验。分享/导出不复制部署授权。真正的成员组、组织同步和组级授权另行设计。

## 6. 画布模式：内容优先的自由画布

### 6.1 工作空间与多画布

交互方向参考 Miro 的内容优先布局：尽量把面积留给内容，工具跟随任务出现。

- 顶部保留工作区、模式和精简状态入口；画布导航使用可收起的列表或切换器，提供新建、重命名、排序、切换及删除预检。
- 默认只显示选择/插入工具和缩放导航；数据源、属性、批注、加工详情均按需打开。
- 悬停提供轻量轮廓和动作提示；选中后在 Block 附近显示上下文工具；复杂配置才打开侧面属性区。
- 空白处提供插入入口，选中项提供编辑源、查看来源、增加视图和删除视图等动作。不得给每个 Block 常驻一排完整按钮。
- 从数据源树拖入或选择“添加到画布”时，创建引用该源的 Cell；存在多个可用 Renderer 时允许选择展现。
- 每张画布独立恢复个人视口；新增画布使用稳定、唯一 ID，不再依赖固定的 `page-main`。

已有 `flow` 页继续可打开和编辑，不自动重排为自由布局。新建自由画布和未来“Notion 文档”均复用 page 模型；旧流式编辑器的保留不等于本期已经交付 Notion 模板体验。

### 6.2 坐标、手势与提交

共享布局沿用 `TreeEdge.placement = { x, y, w, h, z? }`。子节点坐标相对所属容器；屏幕坐标与画布坐标由统一的视口控制器转换。缩放只改变用户视口，不改 Block 的共享尺寸。层叠使用明确的 z 值，相同值按稳定顺序消除歧义。

本期最小交互：平移、缩放、适应全部/选区、单选、多选、框选、拖动、尺寸调整、层级调整、分组/解组和跨画布移动。分组及跨父容器移动需换算坐标，保持预期视觉位置；有权限或写锁限制时动作应可解释地不可用。

拖动和尺寸调整期间只更新本地预览，完成时合并为一次 `tree.place` 命令组；Esc 取消不提交。一次手势形成一个撤销单位，不能每次 pointermove 都发 Commit。两个用户并发修改同一布局时，以开始手势时的 `struct_rev` 作为本期默认前置条件，冲突后保留可重新应用的本地意图；无关源内容修改不应引发布局冲突。

输入路由要区分画布操作与内容编辑：文本选择、输入法组合输入、表格滚动、输入框快捷键不能同时触发画布拖动或删除。键盘可选中并激活 Block、打开动作菜单，Esc 逐层退出编辑/菜单/选择；核心动作不能只依赖鼠标悬停。

### 6.3 “静态 Block”与激活编辑器

默认编辑体验中，Block 首先以静态内容展现，用于选中、移动和排布。“静态”表示不自动播放媒体、不自动运行脚本/许愿格、不直接执行业务按钮，仍应随已提交数据变化更新显示。

用户双击或使用明确的“编辑内容”动作后，BlockHost 才挂载或激活对应 Editor；一次只让当前编辑目标接管输入。结束编辑回到静态 Renderer。数据源模式可以直接呈现同一 Editor，不必通过画布手势激活。

许愿格的“运行”和媒体的“预览”属于显式动作：前者进入受控加工流程，后者打开可关闭的局部预览。局部视频预览不等于播放模式，也不引入演示编排。

### 6.4 性能与生命周期 

BlockHost 负责可见性裁剪、缩放下的简化展示、订阅释放和资源回收。视口外的 Block 不常驻富文本编辑器、整表数据或视频解码器；大表继续使用现有分页与虚拟化。选中、正在输入、存在未保存内容的 Block 不能因裁剪而丢失编辑状态。

浮动工具位于屏幕坐标层，根据 Block 的变换后边界定位，并处理视口边缘避让。标注沿用 `AnchorRegistry` 的目标/范围/原文语义；缩放、排序、拖动及切换画布不改变逻辑锚点。

## 7. Block 与数据源扩展契约

### 7.1 两个扩展点

数据源扩展决定“数据如何读取、编辑、校验和寻址”；Block 扩展决定“数据如何呈现、有哪些配置与动作”。二者通过绑定契约组合，不能为每一种图表再复制一种数据存储。

| 注册项 | 必须声明的职责 |
| --- | --- |
| SourceAdapter | 对应数据类型/Schema 版本、详情与原始数据投影、编辑器、属性描述、支持的稳定选择器与依赖读取范围 |
| BlockDefinition | 稳定类型与版本、允许的源类型/绑定数量、是否允许无源、配置 Schema、默认尺寸、支持的 Surface 与渲染模式 |
| Renderer | 根据数据快照、显示上下文和交互状态产生视图；不自行保存、不在渲染时执行加工 |
| Editor | 在用户激活后编辑源或视图配置，返回受校验的操作，复用版本、权限、写锁和撤销 |
| Action / Inspector | 声明动作、属性及可用条件；由宿主统一放入就近工具、菜单和属性区 |
| LayoutAdapter | 解释容器布局与子项尺寸/位置；本期实现 free，保留已有 flow，后续接排版容器 |

前端 SourceAdapter 不代替 Rust 的类型校验。新增持久数据类型时，服务端和 WASM 必须共享对应确定性适配器；仅新增展现时应优先复用已有 Record、TableSource 等类型。

### 7.2 模式与交互状态是正交维度

宿主未来向 Renderer 提供 `surface`、`canvasMode`、`selected`、`hovered`、`editorActive`、有效权限、只读原因和数据可用状态。本期只实现默认画布编辑路径，但接口不能把“已选中”误当成“可编辑”或把“查看模式”误当成“没有权限”。

| 画布子模式 | 未选中 | 悬停 | 选中 | 本期 |
| --- | --- | --- | --- | --- |
| 编辑 | 静态内容 | 轻量轮廓、动作提示 | 选框、尺寸手柄、就近工具；显式激活 Editor | 实现默认路径，不提供子模式切换 |
| 查看 | 类型定义的阅读/交互表现 | 阅读动作提示 | 类型定义的焦点或选择表现 | 仅预留契约 |
| 播放编辑 | 内容与编排信息的展现 | 编排动作提示 | 编排属性与相关控制 | 仅预留契约 |

选中对象也可以被悬停，所以二者采用独立标志，默认以选中外框优先，不重复绘制工具条。类型可按模式定制内容表现；选择边界、焦点与可访问性由 Host 保持一致。扩展未提供某种 Renderer 时回退到静态展现，不默认运行代码。用测试宿主传入预留的模式和交互状态，验证分派与回退即可，不因此提前实现子模式产品功能。

### 7.3 持久化与受控扩展

第二期需要调整当前固定的 `view.type` 校验和强制 `source_ref` 约束：由注册描述确定 Renderer 支持的源；只有声明无源的类型可以省略绑定。未知 Renderer、未知数据类型和不支持的 Schema 版本应分别报告，原始内容仍可保留、导出和通过通用只读视图检查。

文档记录实际使用的 Renderer 标识、版本、配置及所需资源引用；打开者缺少版本时不能静默改用效果不同的“最新版本”。本期不建设通用兼容层，但格式/协议有变化时必须显式升级版本并给出迁移或拒绝策略。

无限扩展是架构目标，本期用以下两个样本证明机制：

1. 为同一 TableSource 注册一种新指标或图表 Block，不修改 Shell、选择工具、保存流程和撤销机制。
2. 用一份人工准备、模拟 AI 产出的声明式 Block 定义，绑定已有 Record/TableSource，提供属性与动作描述；通过相同注册、校验和回退路径加载，不为它写专用画布逻辑。

这两个样本验证扩展契约，不等于已支持任意生成代码。可信内置 Renderer 可复用 React；文档携带的定义只解释已支持的声明式能力，不能 `eval` 或注入脚本。未来可执行 Renderer 必须经过隔离宿主与权限命令桥，React 错误边界本身不是代码沙箱。

## 8. 两个 ai-canvas demo 的迁移验证

先完成画布框架，再迁移场景。入口位于 `canvas/fixtures/sample-canvas.ts` 和 `canvas/fixtures/aigc-workflow.ts`；其现有演示路径本期不迁移到可运行 UI。

### 8.1 季度经营分析

将销售表迁移为 TableSource，说明与摘要为 RichText，指标为 Record，图表为引用数据的 Cell，许愿格为可配置的加工入口。一个确定性 Mock 生成指标、区域对比、异常明细与摘要。

验收路径：

1. 创建示例 Workspace，在数据源模式检查并修改销售数据。
2. 在两张画布中创建共享该源的不同视图，确认视图配置互不影响。
3. 从许愿格显式运行 Mock，预检后将结果、Cell 和来源记录一次应用，结果标明“模拟”。
4. 改动相关输入，两个模式均显示结果需要刷新；修改布局不触发重算或误判过期。
5. 人工修改摘要后刷新，验证保留/替换/副本、版本冲突、一次撤销与失败保留旧结果。
6. 保存、重新打开、导出再导入，恢复数据、绑定、布局与可解释的来源状态。

本期以固定 fixture 作为主验收输入；CSV/XLSX 导入可在复用原解析器并接入正式命令后补充，不把完整 Excel 兼容作为画布架构验收的前置条件。

### 8.2 AI 短片工作流

迁移“剧本＋角色表＋风格 → 角色设定图 → 故事板/分镜表 → 成片预览”的多阶段链路。图片和预览帧通过正式 AssetRef 与资产上传路径保存，不能继续依赖旧 CanvasDocument 中的大块 data URL 作为唯一存储。

验收重点：

- 许愿格、视觉框、图片、表格、文本、媒体预览组合为普通 Block，使用同一套选择、移动和属性机制。
- 上一阶段的结果集合成为下一阶段的输入；从任一结果可查看上下游来源并定位相关画布。
- 修改角色表或剧本后，显示直接过期与间接上游过期；按顺序显式刷新，不能因多个客户端收到变化而重复运行。
- 结果结构稳定时保留引用身份；结构变化、人工修改和取消/失败均按正式内核规则处理。
- 使用确定性 Mock 和原有逐帧预览说明架构，不宣称生成了真实模型视频；默认画布保持静态，用户显式打开预览。

迁移后的两个 demo 必须通过 WorkspaceSession、正式 `proc`/候选应用和资产接口运行。现有 `mock.task-summary@1` 不足以覆盖这两个程序，需要补充对应确定性程序；复用原型生成算法时转换为正式候选操作，不保留 `APPLY_AGENT_PATCH` 的第二套写入链。

涉及持久化的自动化断言同时检查 RPC/存储结果，不能只比较 DOM。模式/视口不写共享文档、拖拽提交次数、缺失扩展往返和越权拒绝必须有可重复的证据。

### 10.2 性能探针

采用固定 fixture：3 张画布，共 1,000 个轻量 Block；可见区混合文本、图片与图表，包含引用 10,000 行表格的 Cell。分别记录冷打开、切换画布、平移缩放、多选拖动、激活编辑器、内存与常驻编辑器数量。

以约定的桌面 Chromium 环境作为首个基准，记录硬件、浏览器、构建方式和数据规模。建议首轮目标：首个可操作视图 2 秒内；拖拽/缩放帧耗时 P95 不超过 32 ms；交互期间不出现由全量 Block 渲染导致的连续 200 ms 以上主线程阻塞。M0 探针后冻结正式门槛，不能把这些建议值写成现有性能结论。

无论设备速度如何，必须证明工作量受可见区和已激活编辑器约束：不会为每个 Block 挂载编辑器，不会为展示一个表格下载整表，手势期间不产生连续网络写入，离屏卸载不丢输入。
