# BuckyOS AI Workspace 分层架构

> **文档状态：讨论整理版 v0.1**  
> **定位：** 统一产品定位、文档模型、架构分层与阶段验证目标，为后续详细设计和原型实现提供依据。  
> **边界：** 本文记录当前已明确的方向，同时保留尚未决定的技术问题。示例结构、接口职责和验证路线用于解释设计，不代表已冻结的文件格式、API 或实现方案。

## 一、产品定位与总体目标

### 1.1 一种 AI 时代的可编程在线文档

BuckyOS AI Workspace 首先是一种新的在线文档，而不是一组现有办公功能的简单拼装。

其产品形态可以理解为 **Notion + Miro + AI 数据加工能力**：既能组织流式文档、表格和结构化数据，也能承载自由画布、脑图、图表、交互界面和演示内容。目标是在不以打印排版为中心的场景中，逐步覆盖传统 Excel、PowerPoint 等办公工具的主要用途，并把 AIGC 原生融入文档。

它的另一个重要用途是承载轻量的数据处理应用。例如，用户通过一个表单输入原始数据，通过按钮或许愿格加工数据，再将结果组织成报表、图表或视频制作流程。

从运行形态看，Workspace 最终仍是运行在浏览器中的复杂网页；从用户心智看，它是一份可以打开、编辑、协作、复制和演示的文档；从系统模型看，它是一个**边界明确的“数据 + 算法”空间**。

### 1.2 核心取舍：先定义文档，再扩展功能

优先确定文档格式、对象结构以及程序能操作的边界，而不是先做完整的办公软件界面。

一旦文档内核稳定，后续能力主要通过对象类型、布局、渲染器、编辑器和代码片段扩展。图表、数据加工、交互窗体等功能，不必全部变成内核中写死的功能项。

AI 可以直接生成内容，也可以生成一段代码，由代码批量创建、计算或修改对象。对于大量重复对象，应优先验证“生成程序，再执行程序”的路径，而不是让模型逐个输出所有结果。

### 1.3 文档应掌握自身的表现逻辑

一个重要目标是：**已经生成并保存在文档中的图表、界面和行为，不应仅因为 Workspace 软件升级就自动改变。**

系统可以提供模板，但模板生成的代码应成为文档的一部分。用户需要采用新效果或新实现时，再显式执行升级、迁移或重新生成。

这是设计目标，不意味着“保存代码”就足以解决所有兼容性问题。运行接口、依赖版本、资源引用和对象 schema 的兼容边界，仍需在后续实现中明确。

### 1.4 首轮范围

首先围绕**单张画布**把核心模型想清楚，不急于完整展开多画布组织和跨画布操作体验。

Workspace 可以先被理解成一个文件夹，其中包含多张画布或 Sheet。单张画布是一个对象树入口；多画布只是组织层面的扩展，不应使单画布内核变成另一种模型。

第一阶段不要求完成精致 UI。一个简单的对象树查看器、数据录入界面和 AI 入口，就应能验证：非程序员是否可以维护原始数据、表达加工目标，并构造一个能够持续使用的小型应用。

## 二、总体架构：五组能力，而非五层严格调用栈

### 2.1 分层总览

| 层次 | 核心职责 | 主要内容 |
| --- | --- | --- |
| 第一层：对象与编程内核 | 定义文档是什么，以及 AI 和程序可以做什么 | 对象树、命名与版本、schema、CRUD、事件、数据加工代码、AI 产物落点 |
| 第二层 A：对象视图与编辑框架 | 把对象树变成可查看、可编辑的办公界面 | 布局、Renderer、Editor、对象类型扩展、设备相关视图 |
| 第二层 B：协作与权限框架 | 定义多人如何操作同一对象树 | Yjs/CRDT 适配、并发合并、评论与标注、节点与子树权限 |
| 第三层 A：演示编排层 | 把已有对象组织成演示过程 | Presentation Program、时间轴、视口、显示属性变化器 |
| 第三层 B：工作区交互与状态层 | 定义用户当前如何工作 | 工作区 Profile、输入设备适配、窗口管理、交互状态 |
| 第四层：数据源与发布管理 | 管理“引用别人”和“被别人引用” | 外部查询、本地镜像、同域引用、离线边界、引用感知、素材与生命周期 |
| 第五层：Agent 集成与 AI 工作流 | 区分开放式构建和受约束执行 | Workspace Agent、Skills、对象操作接口、许愿格、逻辑模型、克隆后的复现 |

第二层的两个框架是并列关系：都依赖对象树，但在职责上彼此正交。第三层同样包含两种不同能力，不能把所有 UI 交互都归入 Presentation。

这里将后续讨论的数据源与发布管理、Agent 集成分别整理为第四、第五层，便于组织内容；**这不表示它们只能在前面所有层做完后才开始实现。** AI 操作边界和数据源语义从第一阶段就必须进入内核设计。

### 2.2 依赖关系

```text
                       ┌───────────────────────────────┐
                       │ 第一层：对象与编程内核         │
                       │ 对象树 / 版本 / CRUD / 事件    │
                       │ 代码执行 / AI 产物操作边界     │
                       └───────────────┬───────────────┘
                                       │
                  ┌────────────────────┴──────────────────┐
                  ▼                                       ▼
       第二层 A：对象视图与编辑                 第二层 B：协作与权限
       Layout / Renderer / Editor              合并 / 标注 / 访问控制
                  │                                       │
                  └────────────────────┬──────────────────┘
                                       ▼
                      面向用户的 Workspace 使用体验
                      ├─ 第三层 A：演示编排
                      └─ 第三层 B：工作区交互与状态

       第四层：数据源与发布管理 ── 围绕对象和引用关系贯穿各层
       第五层：Agent 与 AI 工作流 ── 通过受控接口操作对象与代码
```

图中第三层汇合的是使用体验，不表示演示和工作区状态必须等待多人协作完成才能开发。架构分层与实施顺序应分别讨论。

## 三、第一层：对象与编程内核

### 3.1 基本单位：命名对象与对象树

沿用 CYFS 命名对象体系的思路，对象可以先近似理解为带有类型和属性的 JSON 数据。对象具有 Workspace 内的名字，也具有确定版本对应的 Object ID。

每张画布本身也是对象，其内部具有明确的父子层级。按当前设想，画布对象树具有唯一的结构性根节点，根节点不作为普通内容节点直接编辑；素材目录、主要数据源等通常挂在第一层节点上。

以下仅是逻辑组织示例，不规定最终磁盘目录或序列化形式：

```text
Workspace（文件夹式容器）
├─ 画布 A
│  └─ 根对象
│     ├─ 素材目录引用
│     ├─ 原始数据表
│     ├─ 派生数据表
│     ├─ 许愿格
│     ├─ 数据加工代码
│     └─ 内容容器
│        ├─ 图表对象
│        ├─ 文字对象
│        └─ 按钮 / 窗体对象
└─ 画布 B
   └─ 根对象
```

父子关系有实际意义，例如子对象的坐标通常相对于父对象定义。后续流式排版、容器布局也需要利用这些关系。

**结构上的父子关系与数据上的引用关系需要分开解释。** 前者形成画布对象树；后者可以指向树内其他节点、其他画布、外部数据源或特定版本，整体可能形成引用图。不能因为存在跨对象引用，就把结构层级和依赖关系混为一谈。

### 3.2 两种引用：名字与 Object ID

| 引用方式 | 语义 | 典型用途 |
| --- | --- | --- |
| Name / Path | 通过名字解析当前对象或当前数据状态，是可变引用 | 正常编辑、跟随当前数据、工作流连接 |
| Object ID | 指向属性已确定的对象版本，是确定版本引用 | 固定依赖、历史查看、已发布素材、版本回溯 |

Object ID 可以标识当前版本，也可以标识历史版本；关键在于它标识的是**确定版本**，而不是“最新”这一动态含义。

名字的目标不一定是静态数据本体，也可能是一个外部查询入口，或一个配置了远程来源的本地对象。这些不同来源仍应落在统一引用模型中，具体读取和更新语义见第四层。

必须保留一个版本边界问题：如果某个确定版本的对象内部仍保存了可变 Path，那么固定该对象的 Object ID，并不自动等于固定所有下游引用的解析结果。因此，“固定一个对象版本”和“固定一份完整可复现文档及其依赖”是两个需要分别定义的概念。

### 3.3 对象类型、属性与维护来源

对象通过 schema / type 表达结构。内核可以保存基础 UI 属性、程序、代码引用以及渲染描述，但不应依赖具体编辑器才能理解或操作这些内容。

当前已明确的一个方向是：系统需要知道哪些数据由人维护，哪些数据由 AI 或程序派生。可以先区分三种来源：

| 来源 | 含义 | 需要进一步明确的行为 |
| --- | --- | --- |
| 人类维护的原始数据 | 用户手工输入或维护的事实性输入 | 哪些程序允许修改；修改后如何触发加工 |
| AI 直接生成的结果 | AI 输出对象、文字或其他结果数据 | 重新生成是否覆盖；是否保留历史版本 |
| 代码加工得到的数据 | 由保存的算法处理已有对象而来 | 谁触发执行；如何识别结果已过期；是否允许手工覆盖 |

这一分类不宜过早限定为“整张表只有一种来源”。同一表格中可能既有用户填写的原始列，也有程序维护的派生列。来源标记最终落在对象、字段、列还是其他粒度上，需要和表格模型一起验证。

### 3.4 核心编程模型

第一层可以收敛为：

**Object Tree + CRUD + Event + Code Execution**

| 基础能力 | 需要解决的问题 |
| --- | --- |
| 对象读取与解析 | 按名字或 Object ID 获取对象，理解 schema、层级和引用 |
| 对象增删改 | 创建对象、修改属性、组织父子关系、移除引用 |
| 变化事件与订阅 | 感知对象或更细粒度字段的变化，驱动依赖更新 |
| 代码执行与写回 | 运行生成的程序，批量创建或修改对象 |
| AI 操作边界 | 让 AI 通过明确接口生成结果或代码，而不是任意修改未知结构 |

这些是接口职责，不是最终函数列表。具体方法名称、事务形式、批处理接口和序列化格式，仍需单独设计。

### 3.5 派生数据：从逐格公式转向语义化加工

以工资表为例，用户只录入姓名和工资。需要“工资与平均工资的差值”时，可以定义一个许愿格或语义化动作：

> 根据工资字段计算平均工资，并将每个人的工资与平均工资的差值写入差值列。

用户点击按钮后，AI 可以理解字段含义并生成执行代码，由代码计算并写回数据。结果单元格保存的是结果值，不一定保存类似 Excel 的逐格公式。

这里存在两条不同执行路径：

- **每次调用 AI 加工：** 灵活，但每次执行都可能消耗 token，结果也需要校验。
- **AI 生成代码，后续复用代码：** 由保存的脚本重复计算，适合明确、可程序化的加工任务。

语义化目标应尽量依赖字段含义，而不是纯粹依赖当前行列位置。但不能据此假定任意已生成脚本都能自动适应结构变化：代码采用何种字段标识、schema 改变后是继续运行还是重新生成，仍需设计。

是否在原始数据变化后自动重算，也不能与“能够重算”混为一谈。当前例子首先是用户显式触发；事件驱动的自动执行是另一种可支持的方式。

### 3.6 事件传播与循环终止

对象树需要提供细粒度的变化事件，例如对象值变化、某字段变化等，使 AI 生成的代码可以建立依赖关系。

讨论中提出使用“触发代数”避免事件在循环依赖中无限传播。例如：

```text
A 发生变化，开启第 101 代传播
A ──101──> B ──101──> C ──101──> A
                                  │
                                  └─ A 已处理第 101 代，终止重复传播
```

按该例子，一轮传播沿链路携带的是**同一个传播代数**。不能同时解释成“每经过一个节点就产生新代数”，否则无法依靠“已处理本代”阻止回环。

这仍是候选机制，而非已经验证的完整算法。至少需要区分：

1. 传播代数与对象内容版本不是同一件事。
2. 一次传播能够终止，不等于循环依赖已经求得稳定结果。
3. 多个上游在同一轮传播中先后变化时，不能因为下游已经执行过一次就遗漏必要更新。
4. 多人并发和异步 AI 任务下，传播身份、去重范围、执行顺序与过期结果处理仍待定义。

因此第一阶段应验证“不会无限触发”和“不会漏掉应该执行的加工”两种性质，而不是只验证其中一种。

### 3.7 表格粒度是第一阶段的关键未决问题

目前没有决定整张表、行列、每个单元格分别如何映射成对象。

| 候选方向 | 可关注的优势 | 必须验证的代价 |
| --- | --- | --- |
| 整张表作为一个对象 | 对象层级相对简单 | 如何提供字段或单元格级事件、并发修改与权限 |
| 表下建立行或列级对象 | 可以在结构与细粒度之间折中 | 行列重排、稳定身份和引用规则如何定义 |
| 每个单元格独立成为对象 | 单元格可被统一寻址和操作 | 对象数量、版本开销、存储与协作成本是否可接受 |

**事件粒度、协作粒度与存储对象粒度不必预先假定完全相同。** 需要细粒度通知，并不自动要求每个单元格都有独立 Object ID。应通过代表性表格和数据量验证后再收敛。

### 3.8 第一层应证明的价值

即使没有完整 UI，也应该可以完成以下闭环：用户维护原始对象，AI 通过受控接口搭建结构、生成结果或生成代码，程序再稳定地操作这棵对象树。

第一层的核心目标不是“做一个无限开放的编程环境”，而是：

> 让非程序员在一个能够理解、能够检查、操作边界明确的空间中，用原始数据和 AI 生成的算法构造自己的软件。

## 四、第二层：对象视图与协作两个正交框架

### 4.1 第二层 A：对象视图与编辑框架

这一框架解决的是：**如何把裸对象树组织成用户熟悉的办公界面。** 为避免与第三层 Presentation 混淆，本文将它称为“对象视图与编辑框架”，不再泛称为演示层。

#### 布局与单个对象表现分开

对象树的空间关系不仅包含自由画布坐标，也包含流式排版、父子容器和不同的内容组织关系。设计可以借鉴 HTML 的结构与布局分离思路，但不预先把所有画布都定义成绝对坐标系统。

这一层至少有两类职责：

| 职责 | 解决的问题 |
| --- | --- |
| Layout | 一组对象如何排列，父容器如何影响子对象，如何形成流式或自由画布 |
| Renderer / Editor | 一个特定类型的对象如何显示，以及进入编辑状态后如何交互 |

布局是否需要成为开放的扩展接口，目前尚未确定。第一阶段可以保留清晰的布局边界，但没有必要立即承诺任意布局插件能力。

#### 同一个对象，不同的查看与编辑形态

对象类型与对象视图不能绑定为一对一关系。同一对象可能具有 PC 查看、手机查看、PC 编辑、只读审阅以及进入对象内部编辑时的专用形态。

当前首发方向是以 PC 作者编辑为主，手机及非作者以查看为主。后续考虑触控、数位板和屏幕笔等输入方式，是框架需要预留的方向，不应据此把“所有设备完整编辑”变成首轮实现要求。

同样，设备类型不等于权限身份；“当前主要在 PC 编辑”是产品范围，不应成为底层授权模型。

### 4.2 对象扩展：安装来源与文档交付是两个问题

对象类型分为标准对象与扩展对象。系统自带一批标准对象，作者可以通过安装扩展增加新的类型、渲染器或编辑器。

扩展可以来自 BuckyOS 上的系统级应用，也可以形成随画布携带的内嵌代码。这里需要区分两个维度：

| 维度 | 关键问题 |
| --- | --- |
| 扩展的安装与管理 | 谁在 BuckyOS 上安装能力，谁有权限使用或更新它 |
| 文档的交付与打开 | 打开者需要依赖外部扩展，还是文档已携带所需代码与资源 |

按照当前方向，扩展安装发生在 BuckyOS 端，不要求浏览器用户额外安装客户端插件。编辑器可以利用服务器端安装的扩展，将对象所需的 HTML、JavaScript 等片段写入文档。

因此，“扩展装在服务器上”和“文档携带扩展代码”并不矛盾。前者是能力的安装与管理位置，后者是结果文档的交付方式；也不能由前者推导出所有 UI 代码都在服务器执行。

### 4.3 文档自包含、兼容性与安全边界

直接携带所需代码和资源，会增加文档体积，但打开者更容易获得完整效果。其目标是让打开 Workspace 接近打开一个站点，而不是先寻找并安装一组插件。

标准对象和扩展对象仍然需要处理版本兼容问题，包括旧版本无法识别某些属性、扩展缺失、执行接口变化等。

需要验证的方向包括：固定文档实际使用的代码与依赖；对未知属性或缺失扩展给出可解释状态；把用户显式升级与软件自动升级区分开。具体版本清单、兼容声明、迁移方式和降级策略尚未确定。

此外，服务器端安装不能代替代码执行的安全设计。Workspace 写权限、BuckyOS 扩展安装权限、生成代码的对象写权限和外部访问权限是不同边界，不能因常见场景中由同一个人持有就合并。

这里暂不指定沙箱技术，但后续必须回答：一段文档代码可以访问哪些对象、哪些系统能力，能否联网，以及如何避免越过协作权限。

### 4.4 第二层 B：协作与权限框架

协作框架解决的是：**多人通过何种操作模型修改同一对象树，最后应得到什么结构和内容。**

当前考虑以 Yjs/CRDT 作为协作模型的技术方向。尚未决定的是如何将文档对象、表格、属性、代码与引用映射到具体的协作数据结构，而不是只要引入 Yjs 就视为协作完成。

协作设计需要覆盖以下对象树语义：

- 多人同时修改属性、插入节点、删除节点或改变层级时，如何解释最终结果。
- 评论、批注、标注可以继续建模为对象；其锚点在内容变化后如何定位，需要进一步设计。
- 对节点、子节点、子树或对象类型的查看与编辑权限如何表达、继承和冲突处理。

权限描述是否全部存入同一棵树，目前不作决定。评论可以是对象，不等于权限的全部执行机制也必须成为普通可编辑对象。

### 4.5 协作不能绕过对象与执行语义

协作层必须遵守对象内核的规则，而不仅是传递任意字段变化。至少有四组跨层问题：

| 问题 | 必须明确的边界 |
| --- | --- |
| 实时编辑与版本 | 协作中的可变状态何时生成确定的 Object ID，如何形成可引用版本 |
| 授权与合并 | 不被允许的修改如何拒绝，不能只依赖前端隐藏编辑控件 |
| 事件与重复执行 | 同一变化被多个协作者接收时，是否每个客户端都执行派生脚本或 AI 节点 |
| 层级与引用 | 并发调整父子关系、删除被引用节点时，如何维护可解释的结构 |

特别是 AI 节点可能消耗 token，程序也可能产生新文件，不能把“所有客户端都收到 on-change”直接等同于“所有客户端都执行一次”。执行归属、去重与写回校验，需要在协作验证时一起检查。

### 4.6 正交关系的含义

UI 可以在单用户对象树上独立开发；协作可以通过无头程序或简单界面验证。二者都依赖第一层，但不应互相要求对方的完整实现。

这里的正交是职责上的分离，不是说整合时没有接口：协作需要呈现权限和远端变化，UI 的修改也需要进入统一对象操作通道。

## 五、第三层：演示编排与工作区交互状态

### 5.1 第三层 A：Presentation 演示编排

Presentation 解决的是如何让已有对象成为演示素材，而不是重新建立一份 PPT 专用对象树。

用户可以通过一个演示程序组织画布：在时间轴上定义视口切换、缩放、对象出现与消失、移动和其他显示属性变化，从而把无限画布组织成类似幻灯片的观看过程。

其基本抽象是：

```text
演示程序
  ├─ 目标对象或视口
  ├─ 生效的时间区间
  ├─ 目标显示属性
  └─ 属性变化器 / 变化函数
```

详细动画能力当前不是优先事项。框架首先需要把“文档状态”与“演示时的临时变化”分开。

### 5.2 文档属性与演示变化器

例如，文档中“文字位于图表右侧”是一项持久布局属性；演示时“文字上升并淡出”是一项临时的显示变化。

动画记录的不是对文档基础属性的永久改写，而是在某个时间范围内作用于显示结果的变化器。平时它不生效，进入 Presentation 后才依据时间轴计算效果。

因此，Presentation 具有以下边界：

- 演示过程对文档数据是只读的，不因动画而修改原始数据或持久布局。
- 视口、可见性和显示变换等临时变化，不应被当作文档编辑广播或触发数据加工。
- 退出演示时移除临时覆盖，重新按文档当前状态显示。

“恢复”不是把进入演示前的整棵树重新写回。如果演示期间其他协作者修改了文档，退出演示不能覆盖这些修改。演示是固定进入时的快照，还是观察实时文档，也是后续需要明确的模式选择。

### 5.3 第三层 B：工作区交互与状态

工作区状态回答的是“用户当前如何工作”，不属于演示程序本身。

同一文档可以拥有多个工作区 Profile，决定工具布局、窗口组、默认可见状态、输入方式等。系统提供默认配置，同时允许作者针对内容和使用场景做适当调整。

需要考虑的输入方式包括键盘鼠标、手机手指触控、Wacom 一类数位板、Surface / Apple Pencil 一类屏幕触控笔，以及演示遥控器。

设备适配包含两个不同问题：第二层负责对象在设备上如何显示和编辑，第三层负责当前使用哪些工具、输入映射和工作窗口。它们需要配合，但职责不同。

### 5.4 可交互对象与窗口管理

Workspace 中不只有静态文本和图表，也可以有按钮、HTML 窗体、表单和弹出窗口。

需要区分两种情况：

| 实现方式 | 含义 |
| --- | --- |
| 按钮运行私有代码，在自身内部创建 UI | 对象树可能只知道按钮存在，无法统一管理代码内部产生的窗口 |
| 窗口被建模为对象，按钮改变其可见状态 | Workspace 可以理解这个窗口，并将其纳入工作区 Profile 与窗口组管理 |

对于需要统一管理的窗口，应该能够在模型中找到它，而不是完全隐藏在任意脚本内部。但“窗口作为对象存在”，并不意味着当前用户打开窗口这一动作必须修改所有人共享的文档属性。

例如：窗口的定义可以存入文档；某个 Profile 的默认显示规则也可以被保存；用户本次是否打开窗口，则可能只是该用户的工作状态。具体状态归属需要显式区分。

### 5.5 三类状态边界

| 状态类别 | 例子 | 持久化与协作方向 |
| --- | --- | --- |
| 文档状态 | 原始数据、结果对象、基础布局、保存的代码、窗口定义、已保存的 Profile 定义 | 作为文档内容管理；按权限进行协作和版本化 |
| 用户工作状态 | 当前 Profile、选中对象、当前打开的表单窗口、尚未提交的输入 | 不默认写入共享文档；是否保存、是否共享需要明确策略 |
| 演示运行状态 | 当前播放时间、临时透明度、动画变换、当前演示视口 | 不修改文档基础属性；演示结束后解除运行态覆盖 |

这一划分是根据讨论整理的状态边界，不意味着它们必须分别存放在三个数据库。存储实现可以后定，但语义不能混淆。

用“按钮打开表单”举例：按钮和表单定义属于文档；打开窗口通常改变当前工作状态；提交数据时，才通过有权限的对象操作写入文档数据。录入内容与编辑文档结构是否使用不同权限，也需要另行定义。

纯 Presentation 模式保持只读。需要写入数据的交互，应明确属于允许操作的工作模式，而不是以动画或观看行为的名义隐式修改文档。

## 六、第四层：数据源、跨文档引用与发布管理

### 6.1 两个方向：我引用谁，谁引用我

文档可以引用外部对象，Workspace 内的对象也可以被其他文档引用。

这形成两个不同的管理视角：

```text
消费视角：我的对象 ──引用──> 其他对象 / 数据源
发布视角：其他对象 ──引用──> 我的对象
```

消费侧关心读取、同步、版本、缓存和离线；发布侧关心外部依赖感知、权限、稳定引用和删除保护。二者使用同一套命名与版本体系，但产品交互不同。

这一层不是对外公开发布的强制要求。“被引用”可以发生在同一个用户的不同 Workspace 之间，也可以发生在团队或跨用户场景。

### 6.2 外部数据模式一：远程查询与结果缓存

第一种方式中，Name / Path 指向的不是必须整体下载的数据，而是一个可返回数据的查询入口。查询器根据数据源和条件取得结果，再供画布中的对象使用。

其设计方向是：

- 使用时读取或按刷新规则查询，不要求把远程数据集完整导入 Workspace。
- 一次加载得到的结果，在同一画布内作为统一状态提供给依赖对象，避免不同图表各自读取不同批次结果。
- 保留最近一次成功取得的查询结果，断网时仍能展示已有内容，并支持基于这些内容的操作。
- 外部源本身原则上只读；本地消费其结果，可以继续生成派生对象。

适合的例子是千万条记录的数据源：在远端查询所需范围，仅将结果缓存到 Workspace，而不是全量导入。

这里的“一致”首先指**同一数据源某次已加载状态的一致使用**，不自动承诺多个不同远程源在同一时刻形成全局快照。读取频率、刷新触发方式、查询参数如何识别缓存，以及过期状态如何显示，仍需详细设计。

### 6.3 外部数据模式二：手工同步的本地镜像

第二种方式类似 Git 的手工同步心智：Workspace 中真实存在一个本地命名对象，另行配置它的 remote source。下游依赖本地对象，而不是直接依赖远程源。

```text
Remote Source
      │
      │ 用户显式执行 sync
      ▼
Workspace 中的本地命名对象
      │
      ├─ 报表
      ├─ 图表
      └─ 后续数据加工
```

用户不执行 sync，本地数据就保持在已获取的版本。远程数据即使被修正，也不会自动改变当前文档的分析基线。

例如，分析某段股票历史交易数据时，报告基于已拉取的版本制作。后续官方修正数据，只在用户选择同步后才进入本地数据源；至于后续派生报告是否重算，还取决于其手工或自动执行设置。

镜像数据原则上只读，除了同步更新外，不鼓励直接修改。即使允许本地修改，也应明确下次同步可能覆盖这些修改，而不是暗示系统已经支持类似 Git 的双向编辑、冲突合并或回推。

这是当前预期的主要外部数据使用方式。主要代价是完整本地副本的体积，不适合所有大规模数据源。

### 6.4 两种模式的边界

| 维度 | 远程查询型 | 本地镜像型 |
| --- | --- | --- |
| 下游读取目标 | 统一发布的查询结果 | Workspace 内的本地对象 |
| 数据更新来源 | 重新查询或刷新 | 用户显式同步 |
| 本地保存范围 | 已取得的查询结果 | 被镜像的数据整体 |
| 断外网后的能力 | 使用已有结果；未缓存查询可能不可执行 | 已镜像数据继续可用，不能取得远端新版本 |
| 适合的数据体量 | 远程大数据集，按条件取子集 | 适合完整保留在 Workspace 的数据 |
| 稳定分析基线 | 需要明确冻结所用结果 | 不同步就保持本地版本 |

“本地”在这里首先指 **Workspace / BuckyOS 一侧的本地副本**，不等于浏览器已经持有同样的数据。这个区别直接影响离线承诺。

### 6.5 同域与异域：独立于查询和镜像方式的分类

外部对象还可以区分为同域与异域。

同一 BuckyOS 系统内，不同 Workspace 之间的引用，可以视为同域引用。它们可能共享存储、连接条件和安全设施，因此可以在同步效率、可靠性和去重方面做更紧密的设计。

底层 Lambda Object Store 已被设想为共同的对象存储基础。同域引用可以利用共享存储空间进行更积极的物理去重，但不应该因此混淆逻辑上的对象身份、版本和保留责任。

尤其需要区分：

- 物理上共享相同内容，不等于引用语义必须“跟随最新”。本地镜像仍可以保留稳定的逻辑版本。
- 能连上同一 BuckyOS，不等于对其中所有对象都有权限。
- 同域数据通常共享可达条件，是部署假设，不是所有数据源永远在线的保证。

查询/镜像描述“如何取得与更新数据”，同域/异域描述“数据位于什么受控环境”。它们是两个维度，不应合并成一组互斥的数据类型。

### 6.6 两层离线边界

网络边界应明确拆成：

```text
浏览器设备  ← 第一段连接 →  用户自己的 BuckyOS
                              ↑
                              └─ 第二段连接 → Internet / 外域数据源
```

**第一种离线：浏览器连不上自己的 BuckyOS。**

此时只能使用浏览器已经保存的文档、资源和结果。是否支持继续编辑、支持哪些对象、是否需要预先指定离线数据范围，都是待定的产品边界。

**第二种离线：浏览器仍能访问 BuckyOS，但 BuckyOS 不能访问外网。**

封闭网、保密网或间歇连接外网的部署属于这种情况。同域对象、本地镜像和已缓存结果，应在所需运行资源已准备好的前提下继续可用；在线查询、在线模型或其他外网能力则需要分别处理。

| 状态 | 浏览器到 BuckyOS | BuckyOS 到外网 | 应依据的数据与能力 |
| --- | --- | --- | --- |
| 正常联网 | 可连接 | 可连接 | 按权限访问同域数据及可用外域能力 |
| BuckyOS 断外网 | 可连接 | 不可连接 | 同域对象、本地镜像、已缓存结果和本地可执行能力 |
| 客户端离线 | 不可连接 | 不作假设 | 仅依赖浏览器实际持有的内容与本地运行能力 |

数据可访问，不等于所有 AI 步骤都能离线执行。应分别说明“已有结果可看”“确定代码可运行”和“新的模型请求可完成”，不能用一个“离线可用”统一承诺。

### 6.7 浏览器不默认承载全量 Workspace

BuckyOS 与不可控服务器上的传统在线文档不同：用户可以拥有自己的服务端数据节点，因此没有必要先假定浏览器必须复制整个系统的能力和数据。

当前明确的问题意识是：数据量较大时，不能默认浏览器 local storage 或其他本地存储足以容纳整个 Workspace。

后续需要确定浏览器缓存范围、可选离线内容、未缓存数据的降级行为，以及恢复连接后的同步机制。具体使用哪种浏览器存储、容量目标是多少，本文不作选型或承诺。

这里应优先划清责任：BuckyOS 负责受控环境中的对象存储与服务；浏览器承担当前编辑和观看所需的工作数据。究竟向浏览器下沉多少离线能力，应由验证结果决定。

### 6.8 发布管理：感知外部依赖

当 Workspace 中的对象被别人引用，所有者需要尽可能知道哪些对象正在被依赖，以免随意修改或移除造成影响。

讨论提出以“君子协议”登记引用关系：引用方主动声明自己引用了哪个对象，发布方据此建立反向引用信息。未声明、离线复制或绕过体系的使用，不保证能够追踪。

由已知引用关系，可以进一步支持权限控制、删除提醒、保护、隐藏和归档等行为。常见需求并不是删除本体，而是让内容不再出现在自己的工作视图中，同时继续向已有引用方提供服务。

需要明确区分以下操作：

| 操作 | 含义 |
| --- | --- |
| 在当前视图隐藏 | 只是不在本工作区显示，不等于撤销外部访问 |
| 移入隔离区或归档区 | 改变本地组织方式，仍需考虑旧名字是否继续可解析 |
| 删除画布中的引用 | 移除当前文档与目标对象的连接，不直接等于删除本体 |
| 撤销访问权限 | 改变谁可以读取或使用，可能影响外部依赖 |
| 删除底层实体 | 属于存储与保留策略，需要独立处理 |

对 Name / Path 的发布尤其要注意：如果归档操作改变了解析路径，单纯“不删除文件”也可能破坏引用。是维持原名字、提供别名还是提供迁移机制，需要详细设计。

### 6.9 文件、文件夹与 AIGC 素材

非结构化数据也应进入统一引用模型。节点可以引用文件或目录，画布内的命名不必改变底层文件系统中的实际名称。

例如，一个 AIGC 短剧 Workspace 可以在对象树第一层挂载素材目录，再通过画布内的语义化命名让 Agent 理解素材结构：

```text
素材目录引用
      │
      ▼
许愿格 / 工作流节点
      │ 读取画布状态与素材引用
      ▼
调用视频生成能力
      │
      ▼
生成新视频文件
      │
      ▼
更新“成片”等命名对象，使其指向新版本
```

每次生成可以形成同一名字下的新版本。需要跟随当前成片的对象使用名字；需要保留已发布效果的对象使用确定的 Object ID。

### 6.10 Object ID、使用感知与实体保留

对于需要固定版本、跨 Workspace 复用和发布的素材，倾向于鼓励 Object ID 引用，而不是直接传递难以统一管理的裸文件路径。

统一对象身份有利于关联引用登记和访问记录，进而展示“这个视频被哪些已知文档使用”“最近是否有访问”等信息。但 **Object ID 本身不是自动发现所有使用者的机制**，访问次数也不等于引用方数量。

画布内删除素材时，通常只删除对底层分布式文件系统对象的引用。实体是否保留、保留多久、何时回收，应由存储层和发布保护规则决定，不能把“当前画布不再引用”直接当作“系统内无人使用”。

## 七、第五层：Agent 集成与可复制 AI 工作流

### 7.1 两种 AI，不同的工作边界

Workspace 中同时存在两种 AI 使用方式：一种负责搭建和修改整个工作区，另一种是文档中一个确定的数据加工节点。

| 维度 | Workspace Agent / Code Agent | 许愿格 / AI 节点 |
| --- | --- | --- |
| 核心职责 | 理解需求，构建、修改或重构 Workspace | 执行某个明确的数据加工步骤 |
| 典型产物 | 对象树、数据结构、代码、视图、流程骨架 | 指定的结果对象、内容或派生数据 |
| 操作范围 | 在授权范围内进行开放式操作 | 在声明的输入、输出和对象范围内执行 |
| 上下文来源 | Agent 自身上下文、能力以及可能存在的长期 memory | 尽量使用单画布内显式提供的状态与知识 |
| 与个人 Agent 的关系 | 用户可以选择由哪个 Agent 接管 | 不应强依赖作者个人 Agent 的特殊记忆和行为 |
| 主要目标 | 灵活解决构建问题 | 克隆后仍尽量稳定、可理解地执行 |

可以把两者概括为：

**Agent 帮用户搭建和修改工具；许愿格是工具内部可重复运行的一步。**

### 7.2 Workspace 级 AI 入口与 Skills

每个 Workspace 应有一个 AI 入口，后端由用户选择的 Agent 承接。系统向 Agent 提供对象树操作接口，并通过 Skills 说明 Workspace 的结构和使用方式。

用户可以提出“帮我搭一个报表”之类的需求，由 Code Agent 创建原始数据区、派生对象、加工代码和展示结构。此后用户主要维护数据并执行工作流，而不需要持续手工编写程序。

Skills 的内容建议覆盖以下职责边界，而不预先绑定某一个 Agent 实现：

- 对象树、schema、Name / Path 与 Object ID 的含义，以及对象操作接口。
- 数据源的查询、镜像、只读和同步语义，以及文件与目录引用方式。
- 如何生成对象和代码，如何遵守事件、权限及状态分层约束。
- 哪些能力属于文档定义，哪些只是用户工作状态，哪些属于演示临时状态。

Agent 可以直接修改对象属性，也可以绕过某个许愿格重新组织数据。这种“绕过”只表示不必通过既有工作流节点操作，不表示可以绕过权限、版本或数据来源规则。

### 7.3 许愿格是文档内的 AI 执行节点

许愿格本身是对象模型中的节点，而不是打开一个具有无限背景信息的个人 Agent 会话。

它应尽量携带完成任务所需的语义目标、知识、输入范围和输出约束。其可引用状态以当前单画布为主要边界；需要素材、外部数据或其他范围的内容时，应通过显式引用进入上下文，而不是隐式依赖作者环境。

许愿格可以参与如下数据流：

```text
用户填写原始数据
       │
       ▼
第一组加工节点：得到第二阶段数据
       │
       ▼
第二组加工节点：得到第三阶段数据
       │
       ▼
报表 / 图表 / 宣传视频 / 其他结果对象
```

其中某些节点调用 AI，某些节点只运行已生成代码。两者应能够共存，不必把每一步都转化成模型请求。

### 7.4 三种产物与执行方式不要混淆

从 AI 参与方式看，可以区分：

| 方式 | 工作过程 | 后续执行特点 |
| --- | --- | --- |
| 直接生成结果对象 | AI 根据输入输出数据或内容，再写入对象树 | 再次生成通常需要新的 AI 请求 |
| 生成数据加工代码 | AI 先生成算法，执行环境运行算法并写回 | 可以重复执行保存的代码，不必每次重新调用模型 |
| 生成界面与交互代码 | AI 或扩展生成 Renderer、表单、按钮等 UI | UI 事件通过受控接口读取或修改对象 |

AI 节点内是否总是即时生成临时代码，还是允许保存并复用代码，具体选择取决于任务。不能把一个需要生成新视频的节点，与一个计算工资差值的节点都当成相同的可重复执行机制。

### 7.5 逻辑模型与跨用户运行

Workspace 是文档，能够复制、克隆，甚至作为工作流产品被购买后使用。复制者通常接入自己的 AI 能力，不应被要求同时复制作者的完整 Agent 环境。

当前方向是使用逻辑模型，而不是假设所有用户都有同一实际模型。由用户所在系统将逻辑能力映射到可用模型。

这样可以保留部署弹性，但无法保证不同模型得到完全一致的结果。因此，可复现性的目标应表述为：

> 在输入完整、任务边界明确、模型能力满足要求的情况下，尽量保持流程可执行、输出结构可接受、工作效果接近，而非承诺逐字或逐帧一致。

逻辑模型的能力要求如何声明，能力不足时如何提示，能否替换模型或降级，以及输出如何校验，仍需要专项设计和验证。

### 7.6 克隆后应该保留什么

一个优秀的电商宣传视频工作流被克隆后，应尽量依靠文档自身包含的信息运行，而不是依赖作者没有交付的记忆或环境。

建议把以下内容作为克隆验证清单，而不是立即冻结为文件格式字段：

| 检查项 | 要验证的问题 |
| --- | --- |
| 对象结构与 schema | 原始数据和派生数据的位置、含义是否清楚 |
| 节点任务与上下文 | 必要知识、输入输出规则是否已经明确写入或引用 |
| 代码与 UI 依赖 | 是否携带所需版本，还是隐含依赖作者环境 |
| 素材与数据源 | 克隆者是否有权读取，是否需要重新绑定自己的素材 |
| 逻辑模型能力 | 克隆者系统是否能提供该节点要求的能力 |
| 历史结果与新结果 | 是否能区分复制来的既有结果和本次重新生成的结果 |
| 个体化状态 | 是否不依赖作者的长期 memory、个人会话或未声明设置 |

克隆也不应被默认解释为继承作者的身份、授权或模型访问凭据。相关绑定与授权流程，需要独立定义。

### 7.7 第五层与第一层的关系

第五层不是在项目末期才添加一个聊天框。第一阶段就必须让 Agent 能够读懂并操作对象树，也必须能容纳许愿格与生成代码。

这一层单独列出，是为了明确两类 AI 的上下文、可控性和交付边界。复杂 Agent 生态接入、多种逻辑模型适配和跨用户工作流复现，可以在基础闭环之后逐步加强。

## 八、分阶段实施与验证路线

本节将分层模型转化为一条可执行的验证路线。其中，“先确定内核”和“第二层的两条正交路线”已经在讨论中明确；后续里程碑顺序属于整理建议，不代表固定排期或已经完成的实现。

### 8.1 第一阶段：对象内核与 AI 最小闭环

**目标：不依赖完整 UI，先证明数据与算法可以在受控对象空间中工作。**

优先形成对象格式、命名与版本语义、基本 schema、对象操作接口、事件和代码执行边界。数据源至少要能区分本地数据、查询结果与镜像数据；不必在这一阶段实现所有跨域部署能力。

最小原型可以只提供对象树查看、原始数据录入、执行按钮和 Agent 入口。用工资差值或类似简单报表场景完成两条路径：AI 直接产生结果；AI 生成代码，再由代码重复加工数据。

建议验证：

1. 用户能区分原始输入、派生结果和生成代码，并知道哪些数据会被覆盖。
2. Agent 可以通过明确接口搭建或修改对象树，不依赖完整办公界面。
3. 保存的代码可以再次执行；Name 和 Object ID 的引用行为符合定义。
4. 事件循环能够终止，多输入变化不丢失必要加工。
5. 表格粒度在代表性数据规模下可接受，没有被 UI 实现提前锁死。

第一阶段不追求大量内置对象类型、复杂动画或全功能浏览器离线。

### 8.2 第二阶段：对象 UI 与协作分别验证，再合流

**目标：让同一对象内核既能形成办公界面，也能承载多人操作。**

UI 路线验证基础流式布局与自由画布、少量标准对象、查看与编辑状态，以及一种扩展对象的嵌入与打开。

协作路线验证 Yjs 与对象树的适配、并发属性修改、节点增删与层级调整、基础评论标注，以及节点或子树级权限。

随后验证整合后的行为：UI 修改进入同一操作模型；无权修改不能通过其他入口绕过；多人收到同一事件不会产生不受控的重复 AI 执行；实时协作状态能够在明确时机形成确定版本。

这一阶段不必完成所有对象类型，也不必对权限规则的所有组合一次性实现。应先选择能暴露核心问题的场景。

### 8.3 第三阶段：工作区状态、数据源与发布可靠性

**目标：让一个已可编辑、可协作的 Workspace 能稳定依赖真实数据，并被其他文档安全复用。**

建议优先贯通：工作区 Profile 与窗口管理、手工同步镜像、远程查询缓存、同域引用、文件目录素材、已知反向引用，以及隐藏、移除引用和实体删除的区分。

同时分别验证 BuckyOS 断外网和浏览器断开 BuckyOS。浏览器尚不支持的离线能力，应明确显示边界，不以“本地有副本”笼统代替客户端能力。

该阶段的核心验收不是功能数量，而是：原始数据不会被隐式覆盖，别人正在使用的内容不会因本地整理而意外失效，个人窗口状态不会污染共享文档。

### 8.4 第四阶段：可复制工作流与轻量演示

**目标：证明文档能够带着足够的结构和行为交付，而不只在作者环境中可用。**

一条路线验证工作流克隆：由 Agent 搭建较完整的报表或视频制作流程，在另一用户环境中绑定素材和逻辑模型，检查许愿格能否依靠显式上下文运行。

另一条路线验证最小 Presentation：用视口切换、对象出现与隐藏组织演示，不先追求完整动画系统。验证演示不改写文档数据，退出演示不覆盖协作者更新。

这两条路线可以按产品需要调整先后，不构成彼此的硬依赖。复杂时间轴、丰富动画、多设备精细交互和大规模扩展生态应继续分批推进。

### 8.5 代表性验证场景

以下是建议测试，不代表当前已有测试结果。

| 场景 | 操作 | 观察与通过标准 |
| --- | --- | --- |
| 工资差值 | 修改原始工资，手工运行加工；调整字段排列后再次执行 | 输出写入目标字段；结构变化不能静默写错位置 |
| 事件回环与分支汇合 | 构造 A→B→C→A，以及多个上游汇入同一结果节点 | 回环有界；下游最终结果使用了应纳入的输入 |
| 远程修正与镜像 | 远程源更新，本地不 sync；随后显式 sync | 同步前基线不变；同步后按既定策略更新或标记派生结果 |
| 大数据查询 | 对超出全量导入目标的数据源只查询子集 | 不因查询子集而隐式导入整个远程数据集 |
| 两种断网 | 分别切断外网和浏览器到 BuckyOS 的连接 | 各自能力与缓存范围相符；缺失能力能够被解释 |
| 多人编辑与执行 | 两人同时改同一表格，并触发加工节点 | 合并语义可解释；权限有效；执行次数与写回归属可控 |
| 私有窗口状态 | 用户 A 打开录入窗口，用户 B 正常查看 | A 的临时界面动作不无意改变 B 的文档或工作状态 |
| 演示期间协作 | A 演示时 B 修改原始文档，随后 A 退出 | 演示不写回临时属性；B 的合法修改仍然存在 |
| 外部引用保护 | 另一个 Workspace 登记引用，原作者隐藏、归档或移除节点 | 行为与引用模式一致；潜在影响可见，不误删底层素材 |
| 工作流克隆 | 在另一用户的模型与素材环境中运行许愿格 | 输入与能力缺口可定位；不依赖作者未声明的 memory |
| 软件与扩展升级 | 打开保存了旧代码与依赖的文档 | 不静默替换文档逻辑；不兼容之处可诊断并由用户决定迁移 |

## 九、必须保留的未决问题

这些问题已经影响架构，但当前讨论尚未给出最终实现答案，不应在整理文档时被隐式定死。

| 问题 | 待决定的内容 | 优先验证阶段 |
| --- | --- | --- |
| 表格对象粒度 | 整表、行列、单元格与稳定字段身份如何组织 | 第一阶段 |
| 引用闭包与版本 | 固定 Object ID 时如何处理内部可变引用；何时生成版本 | 第一阶段，协作阶段深化 |
| 事件传播模型 | 传播代数、分支汇合、异步完成、循环终止与重算顺序 | 第一阶段 |
| 生成代码的执行边界 | 能访问哪些对象和外部能力，运行位置与隔离方式如何选择 | 第一阶段起 |
| 协作结构与合并 | 对象树如何映射到 Yjs；并发移动和删除如何解释 | 第二阶段 |
| 权限表达与执行 | 节点、子树、类型权限如何组合，授权在何处落实 | 第二阶段 |
| 多人场景的计算归属 | 谁执行脚本或 AI 节点，如何避免重复执行与过期写回 | 第二阶段 |
| 布局与对象扩展协议 | 布局是否开放扩展，Renderer / Editor 依赖如何携带和升级 | 第二阶段 |
| Profile 与运行状态 | 默认配置、个人覆盖、共享演示状态分别如何保存与同步 | 第三阶段 |
| 浏览器离线深度 | 缓存多少数据，允许哪些操作，如何处理未缓存内容 | 第一阶段明确目标，第三阶段验证 |
| 同域共享与保留责任 | 去重后如何保持独立版本、授权与实体保留语义 | 第三阶段 |
| 发布与反向引用协议 | 如何登记、更新和解除引用；名字迁移与删除保护如何处理 | 第三阶段 |
| 许愿格的可复现性 | 完整上下文、逻辑模型能力声明、输出校验和环境差异如何处理 | 第一阶段确定边界，第四阶段深化 |
| 演示读取模式 | 固定快照还是实时文档；视觉覆盖如何与工作状态组合 | 轻量演示阶段 |

## 十、架构结论

BuckyOS AI Workspace 的核心不是先复制 Office 的全部功能，而是先定义一种**可版本化、可编程、可协作、可被 AI 理解和操作的文档对象模型**。

在此基础上，架构逐步展开为：

```text
稳定的对象与编程内核
    ├─ 用布局、Renderer 和 Editor 形成办公界面
    ├─ 用协作与权限框架支持多人操作
    ├─ 用工作区状态组织不同设备、工具和交互窗口
    ├─ 用 Presentation 临时编排现有对象，不改写文档本体
    ├─ 用数据源和发布管理连接其他 Workspace 与外部素材
    └─ 用 Agent 搭建工作流，用许愿格执行受约束的 AI 加工
```

贯穿各层的关键边界是：**名字不等于固定版本，引用不等于本体，界面变化不等于数据修改，收到事件不等于必须再次执行，Agent 的开放式构建不等于许愿格的稳定执行。**

先验证这些边界，再扩展对象类型、表现效果和交互能力，才能使系统在功能增长时仍然保持一个稳定、可理解的内核。
