## 向下兼容与升级契约

**从本次冻结基线开始，新版本必须能够打开并继续使用已受支持的旧版本工作区。** 兼容覆盖在线工作区与导出包，也覆盖标准库、扩展定义和程序所依赖的正式宿主接口。FORMAT 1.0 是内容格式基线；此处的产品兼容承诺进一步约束宿主和扩展运行契约。冻结前实验格式的支持范围应在版本清单中明确，不能混用实验格式与正式支持格式。

### 兼容对象与保证

| 对象 | 新版本的责任 |
| --- | --- |
| 在线存储与 `.bcanvas` | 识别旧版结构，通过旧版读取器或显式转换载入，保留内容、稳定身份、引用与重要关系 |
| 业务 Schema 与富文本 | 按记录的版本解释；迁移结构时给出明确映射，不用新规则猜测旧内容 |
| 内置 Block/control | 旧实例继续显示和编辑；属性、绑定、事件及布局的含义保持兼容 |
| 随文档携带的扩展 | 依赖实现和资源可解析；旧正式 host API 保持可用，或提供经过验证的兼容适配 |
| 宏与后台程序 | 稳定对象 API 的参数、结果、错误和副作用语义保持兼容，不依赖当前 UI 内部结构 |
| 外部数据与服务 | 保留来源和本地有效内容；远端失效、凭据缺失与版本不兼容分别报告 |

可打开、可显示、可编辑、可运行必须分别验收。对已支持的标准内容及完整依赖，不能仅靠“保留原始 JSON”代替正常使用承诺；对依赖缺失或外部服务不可用的内容，应完整保留数据，提供静态或通用回退，并说明不可用能力。

旧文档不会因为升级而自动获得新权限。兼容既有数据与程序接口，不恢复过期凭据、已撤销授权或历史任务；运行仍以当前有效能力为准。

### 版本层次

版本至少分为存储 schema、FORMAT、PROTOCOL、业务 Schema、RichText Schema、扩展 manifest、host API 和宏 API。来源包版本、Workspace 内的 build 修订与宿主 API 版本分别记录，不能共用一个数字代替全部兼容判断。

同一版本的含义不得静默变化。同一 FORMAT 内只能增加旧实现能够安全忽略的内容；不兼容结构变化显式升版，并由新版提供旧正式格式的载入路径。新增 API 可以进行能力协商；已有 API 不得原名改义。旧实现被替换时，应保留兼容适配，或通过可验证迁移维持既有行为。

未知的新业务类型保留为不透明内容；未知必需格式或运行能力明确报告。`UNSUPPORTED_VERSION` 用于超出支持范围的版本，不能成为拒绝已承诺旧正式工作区的通用处理方式。

### 转换与失败恢复

升级流程为“读取版本 → 选择转换路径 → 在候选副本中转换 → 校验数据、引用和资源 → 切换为新版本”。切换前保留可恢复的原始内容，失败不覆盖最后可用工作区；禁止边读边破坏原库。转换应可重复验证，记录起止版本和结果。

在线升级不是 Fork 或恢复导入：保持 Workspace 身份和现有授权归属，不复制到新的安全主体。纯格式升级不默认更换 epoch；确需截断并重建协作历史时，按历史重建协议处理离线意图，不能偷偷接续旧信封。

转换可能改变内容对象的编码及 Content ID，应保留来源与可验证映射；原本已承诺的固定版本仍按保留规则解释，不能把转换后的新对象冒充原固定对象。

应用日志的解释版本必须可判定。存储表结构迁移须保持旧行级日志的可应用语义，必要时使用确定性的版本适配，不重新调用 planner。无法保持协作接续时，按显式历史重建协议处理 epoch 和离线意图，不静默删除或重新解释旧日志。

兼容验收必须包含旧工作区在新版本中打开、编辑、保存、再打开，以及旧宏、旧控件、导出导入和恢复失败的用例。不能只测试新版产生的文件由新版读取。

## 存储、快照与导出文件

### 持久化布局

```text
workspaces/<workspace_id>/
  doc.sqlite       可移植文档、共享状态、提交与协作数据
  local.sqlite     本部署授权、入口、运行、私有状态与控制记录

named store        资产、内容对象、快照、生成版本、导出包的对象本体
对象桶绑定          assets / objects / exports 的保留关系
```

`doc.sqlite` 与逻辑内容包不是同一种交付物。在线库用于当前协作；可分享内容按固定 ContentRoot 物化。`local.sqlite` 不随普通文档导出。

Workspace 不维护另一套自有 `objects/`、`chunks/` 磁盘仓库或服务级 mark-sweep 回收器。资产、快照和导出包接入 named store；资源保留与释放通过对象桶表达。运行工作目录和可重建缓存不构成文档事实。

### 内容快照与协作快照

| 产物 | 用途 | 可以包含的历史 |
| --- | --- | --- |
| ContentRoot 内容快照 | 分享、发布、固定数据引用、内容交换 | 当前导出范围的内容，不包含已删文本的 CRDT 历史或 commits |
| 同 ACL 数据库克隆 | 固定演示基线 | 可带完整协作历史；必须留在受控服务中 |
| 个人备份 | 保存本人有权带出的内容与协作状态 | 可带完整富文本历史，界面必须明确标识 |
| 离线协作 bootstrap | 初始化获准副本 | 按同步协议携带续接所需状态，不作为公开分享物 |

完整数据库克隆不得用作公开内容分享。个人备份带富文本历史也不等于带全套提交、授权和部署状态；恢复能力必须以包的实际承诺为准。

固定快照需要覆盖所承诺范围内的数据、Block 配置、资源，以及影响结果的计算定义和输入。动态依赖可通过显式任务产生的物化结果闭合；无法闭合时拒绝、列出缺失或明确降级，不能仅凭根对象有 Content ID 就声称完整离线可用。

### `.bcanvas` 内容包

包采用以 `content_root` 为根的 NamedObject 闭包，形态为：

```text
example.bcanvas
  manifest.json
  objects/<hex>.<obj_type>
  chunks/<hex>.<chunk_type>
  collab/<entity_id>.loro
  personal/entities.jsonl
```

`objects/` 是包内路径，不是 Workspace 服务自建的对象库。`chunks/` 是否包含资源字节由 `self_contained` 决定；`collab/` 与个人作用域内容仅用于明确选择的 `personal_backup`。manifest 不参与 NamedObject 哈希，声明格式、版本、模式、根、对象清单、缺失项、外部来源和必要的类型信息。

`share` 和 `personal_backup` 区分内容分享与个人备份；`self_contained` 是另一个维度。导出必须列出缺失资源和未物化的外部依赖。自包含不意味着能导出无权读取或无权导出的内容。

导出针对一致版本。导入先按包声明的源格式校验对象、类型、大小、闭包和原 ContentRoot；缺失依赖不得伪装成完整包。无需格式转换时，重新物化的内容根必须一致；需要明确转换时，校验转换后的内容与引用完整性，并记录新旧根映射，不要求不同编码格式的根相等，也不能通过忽略原根校验实现兼容。

`new` 创建 Fork，`restore` 表示受控恢复；恢复建立新 epoch 和新的提交起点。两者均不重新派发历史任务，不导入在线凭据、旧委托或其他用户私有状态。
