## Command、Commit 与共享事务

### 一个变更入口

人、AI、Source、显式计算结果和扩展的共享写入统一通过 Command/Commit。客户端提交有限操作，不向数据内核提交任意代码。

必须区分三个动作：保存私有草稿、提交共享变更、发布下游结果。已接受的共享变更实时分发；尚未提交的输入是否对外同步由编辑模式明确决定。私有中间态不能先广播再靠 UI 隐藏。

一次 Commit 的操作列表具有原子性，覆盖数据、Block、引用、共享派生元数据及其版本变化。数据、历史、接受记录和 head 必须在同一逻辑提交中一致落地；多个 Workspace 或外部系统之间不隐含分布式事务。

### 请求与准入

提交信封包含 `protocol_version`、`workspace_id`、`epoch`、`idempotency_key`、`session_id`、`origin`、`run_id`、`undo_group`、`message`、`preconditions`、`operations` 等协议字段。可选性、长度及操作形状以 Schema 为准。

实际作者、有效 principal、接收时间和 `origin` 由服务端认证上下文与入口推导。客户端声明不能让普通写入冒充 Source、内部系统操作或受托任务。

新提交的逻辑流程为：

1. 认证调用者，检查协议、Workspace、epoch、请求边界与规范摘要。
2. 在对应幂等作用域查找接受记录；命中相同请求则恢复结果，不重新执行。
3. 检查当前授权、放映限制、任务/尝试有效性；规划操作并校验读条件、类型与引用。
4. 在完整候选状态上检查最终约束，确定实际写集和锁目标，再检查写锁。
5. 校验所需资产可靠可用，完成用量核算、容量预留和操作成本准入。
6. 产生完全解析的规范化变更，将数据、版本格、引用、日志、幂等记录、用量和 head 原子持久化。
7. 达到持久化确认边界后返回 accepted，随后发送变更通知或继续已记录的工作。

这定义逻辑依赖，不要求所有校验按一次固定函数调用排列。写锁可在 planner 产出目标后检查；幂等恢复先于新提交的当前权限、锁和配额检查，但仍受协议/epoch 及结果可见性规则约束。

外部资源可以预先暂存和绑定。提交成功时必要资源必须已经可用；失败可留下受控、可回收的暂存物，不能留下已发布却缺失内容的引用。跨数据库或对象桶的步骤必须有失败补偿与恢复衔接，不能假装与 SQLite 天然共用事务。

### 冲突与约束

不同版本格上的修改可以按明确规则合并；同一版本格按操作声明执行合并、覆盖或冲突策略。例如允许省略属性 `expect` 的操作可按服务端顺序覆盖，不能因此声称它保护了基于旧值的编辑。已提供但过期的版本条件必须冲突；目标已删除则按操作协议明确失败，不重新绑定同名对象。

`expect` 是否必填由操作目录规定，服务端、SDK、WASM 和 Schema 必须一致。结构修改、写集与读集的关系不能靠调用方猜测；缺失必要前置条件应拒绝。

约束以事务最终候选状态为准；合法的多步更新不应因中间步骤暂时不满足最终约束而无法表达。各操作自身仍可有必要的前置条件。

确定性要求是：相同初始协作状态、相同操作输入及标准应用顺序产生相同结果；不承诺不同顺序总得到相同结果。

### 幂等、三态结果与 unknown

| 结果 | 语义 |
| --- | --- |
| `accepted` | 本次共享变更已到达约定持久化边界 |
| `conflict` | 操作与当前版本条件或并发变化冲突，需要处理后另行提交 |
| `rejected` | 权限、类型、资源、执行资格或其他准入规则不满足 |
| 客户端 `unknown` | 超时或断线使客户端不知道服务端结果；不是第四种服务端事务结果 |

幂等按 Workspace 历史上下文内的 `(实际写入 principal, idempotency_key)` 隔离。同 key、同规范请求恢复原结果；同 key、不同请求返回 `IDEMPOTENCY_MISMATCH`。任务结果使用确定的运行与计划身份，例如 `run/<run_id>/<plan_digest>`，不因换一个触发 Apply 的用户而重复写入。

已接受事实不因后来锁过期、权限撤销或配额变化而变成“未发生”。查询仍需认证并限制返回内容，恢复接受事实不重新授予读写权限。未能查到接受记录不等于一定没发生；客户端只在协议窗口内用原 key、原请求安全重试。

## 纯应用日志、离线恢复与 epoch

### 纯应用型规范化日志

日志必须是纯应用型：版本格写入、结构变化、版本推进、引用变化及级联删除已经解析完成。重放应用记录，不再次调用 planner 重新决定业务结果。

规范化操作与应用日志分工不同：`commit_ops` 用于审计和生成补偿操作，`commit_deltas.rows_json` 保存已解析的行级变更供副本直接应用。副本可以对尚未接受的本地意图规划临时视图，但不能重新规划已接受的历史。

重放不检查当前 ACL、锁、配额和业务 Schema，不读取当前时间、随机值或最新 Source，不重新计算“还有多少引用”。重放入口仍须授权，原语及日志结构仍须可验证。

重放只恢复数据，不调用模型、不重做同步、不启动历史任务、不重复第三方副作用。需要读取外部存储中的固定对象时，必须按已固定身份校验，不能用源站当前内容替代。

核心验收是：**旧日志在 planner 升级后仍能重放到相同状态**。无需随客户端携带所有历史 planner 版本，也不能只验证同一 planner 的自洽性。

### 历史边界与离线恢复

v1 不主动截断结构化提交历史，保留离线副本续接能力；协议仍提供历史下界 `base_seq`，可以初始为 0。幂等接受窗口与历史下界协调。低于可安全接续边界的请求返回 `BASE_TOO_OLD`，客户端重新 bootstrap，不能把旧请求当新写入。

离线修改保存操作意图和原基准。重连先取得共享变化，再检查版本、权限与目标；本地曾有权限不代表当前仍有权限。不能双向文件同步一个由多用户写入的 SQLite 文件来替代提交协议。

结构化日志保留不等于其全部历史资产永久保留。资源过期后可明确失去旧版本恢复或撤销能力，见[保留根与资源生命周期](11-权限资源与保留.md#保留根与资源生命周期)。

### epoch、lineage 与升级

恢复导入、截断历史后重建会建立新 epoch。旧 epoch 的信封返回 `EPOCH_MISMATCH`；待发操作以冲突处理方式重新定位、重新取得前置条件，再经确认作为新提交准入，不能原样重发旧 `expect`。

恢复替换是 manage 级操作，影响所有离线副本。普通 Schema 迁移不必换 epoch；换 epoch 也不必销毁保留下来的每个富文本 lineage。新 Workspace/Fork 拥有新文档身份和自己的提交历史。

格式、Schema 与宿主 API 的向下兼容遵循[向下兼容与升级契约](01-兼容与文档格式.md#向下兼容与升级契约)；历史恢复规则不能用于绕过旧正式文档的读取与迁移责任。
