## 对外接口与冻结治理

### 服务入口与契约来源

AIWS 的服务名是 `aiworkspace`，服务模式监听 `127.0.0.1:4120`，主入口为 `POST /kapi/aiworkspace`。kRPC 请求为 `{ method, params, sys: [seq, token] }`。网关转发不代替 AIWS 的身份验证；服务将验证后的身份转换为 `Caller`，再按 Workspace、实体范围及 run 委托授权。

| 契约 | 当前源码入口 |
| --- | --- |
| kRPC 方法及稳定级别 | [分类清单](#aiws-对外-api-分类清单)逐项说明功能；源码为 [server/src/lib.rs](../../../src/frame/aiworkspace/server/src/lib.rs) 的 `METHOD_LEVELS`、`krpc`、`dispatch`；字段说明见[服务 README](../../../src/frame/aiworkspace/README.md#protocol) |
| HTTP、WebSocket 与对象访问 | 同文件 `build_router`；schema、healthz 公开，资产代读、媒体 stream、session WebSocket、publication 与 `obj/*` 路由按各自规则检查访问 |
| 身份、受限会话与动态授权主体 | [server/src/auth.rs](../../../src/frame/aiworkspace/server/src/auth.rs)、[store/src/workspace.rs](../../../src/frame/aiworkspace/store/src/workspace.rs) |
| 格式、协议与存储版本 | [core/src/model.rs](../../../src/frame/aiworkspace/core/src/model.rs)、[store/src/schema.rs](../../../src/frame/aiworkspace/store/src/schema.rs) |
| 操作、错误与扩展格式 | [schemas](../../../src/frame/aiworkspace/schemas)、[core/src/error.rs](../../../src/frame/aiworkspace/core/src/error.rs) |

`GET /kapi/aiworkspace/healthz` 只返回进程路由存活状态 `ok`，不检查 system-config、对象桶、AICC 或 Agent 是否可用。不能用一次 healthz 成功替代后端依赖验收。

### API 分级

API 分为稳定、内部、实验三级，由服务方法目录声明，不按前缀笼统分类。

| 级别 | 范围与规则 |
| --- | --- |
| 稳定 | 基础 Workspace 管理与授权、分享入口、解析/读/查、prepare/commit/stage、提交查询、undo、变更拉取与等待、私有状态、lock、资产接入与 stream URL 等；变化遵循协议版本与契约测试 |
| 内部 | outline、诊断、replica、传统 show 等实现接口；随配套客户端演进，不作为外部通用承诺 |
| 实验 | 未完成稳定发布条件的任务、发布、快照或独立会话接口；必须显式标记，不能因本文冻结了语义就宣称方法已稳定 |

截至 2026-11-12，服务声明 FORMAT 1.0、PROTOCOL 1.2、存储 schema 6；这三者独立演进，实体及 RichText Schema、纯文本呈现 `body` 的格式版本（`BODY_FORMAT_VERSION` 1）和 HTML 宿主接口（6）另行版本化。PROTOCOL 1.2 是统一发现、读取与查询：新增 `doc.list`、`doc.find`、`doc.read { as, path }`，`doc.query` 只接受文本或 SQL，URL 表的远端行改由 `doc.source_query` 读取，删除 `doc.list_children`；1.0、1.1 的 Commit 请求仍被接受，`doc.query` 的旧参数明确拒绝。存储 schema 6 让每个实体都有名字，打开 5 的存储时回填。具体方法级别见 [METHOD_LEVELS](../../../src/frame/aiworkspace/server/src/lib.rs)：`proc.*` 随浏览器优先执行与许愿格三阶段升为稳定；托管配置、发布、checkpoint/export 和 `session.*` 等仍应按目录中的实验标记使用，不能写成全部 `ws.*` 稳定。

资源上传复用 NDM 与对象桶，以 `asset.import_object` 接入 Workspace；不恢复历史草案的 `asset.begin_upload/finish_upload` 或本地上传路由。资源代读仍须经过 Workspace 授权，不能要求协作者直接拥有 Owner 对象桶权限。

### 错误与失败行为

错误枚举、`retryable` 和冲突详情属于协议；调用方不能按自然语言错误文本分支。Commit 保持三态结果，其他方法按其 Schema 返回错误信封。

当前 wire 行为需要区分以下层次：

- 普通业务结果位于 kRPC `result`：成功为 `{ ok: true, ... }`，失败为 `{ ok: false, error: { code, retryable, detail, sub_code?, data?, denial? } }`；提交结果使用 `status: accepted | conflict | rejected`。
- 无效 token、未知方法和无法解析的请求使用 kRPC 顶层 `error`。受限会话被拒使用 `{ error, code: "access_denied", data: AccessDenial }`；`ws.join_entry` 的拒绝也走这个共享 SSO 信封，其其他错误走普通 kRPC error。
- kRPC 处理器通常返回 HTTP 200；请求体限额及资产、媒体等 HTTP 路由另有 HTTP 状态语义。调用方必须检查结果内容，不能只检查 HTTP 是否成功。

| 类别 | 代表错误或处理 |
| --- | --- |
| 请求身份不一致 | `IDEMPOTENCY_MISMATCH` |
| 历史无法接续 | `EPOCH_MISMATCH`、`BASE_TOO_OLD` |
| 内容不再保留 | `VERSION_NOT_RETAINED`、`RESOURCE_RECLAIMED` |
| 不可补偿 | `NOT_UNDOABLE` |
| 执行上下文或委托失效 | `EXECUTION_CONTEXT_MISSING`、`DELEGATION_STALE` |
| 运行取消或执行资格失效 | `RUN_CANCELLED`、`RUN_REVOKED` |
| 资源准入失败 | 配额/流量错误及可回收、所需额度等结构化详情 |
| 后端存储或对象不可用 | `STORAGE_FULL`、`STORAGE_IO_ERROR`、`DEPENDENCY_UNAVAILABLE`；桶错误映射见下文，区别于 Workspace 自身的逻辑配额 |
| 版本超出支持范围 | `UNSUPPORTED_VERSION`，不猜测未知语义；已承诺旧正式版本走兼容载入或转换；首批不支持的固定版本读取（`meta`、`body`、发现、查询）也返回它，不退化为当前版本 |
| 查询超出预算或游标失效 | `LIMIT_EXCEEDED`（`data.limit`: `time`、`bytes`）；SQL 行数超出时 `truncated: true`；文本查询没扫完时 `coverage.complete: false` 并给续查游标；游标依赖的版本变化或 `expect_head` 不符时 `SNAPSHOT_EXPIRED`（`HEAD_MISMATCH`）。SQL 被拒绝分 `SQL_NOT_ALLOWED`、`SQL_ERROR`、`NOT_MATERIALIZED`（URL 表），不可读与不存在的表同为 `NOT_FOUND` |

权限不足与内容不存在的对外细节须服从可见性策略。`retryable` 不表示可以改用新 key 盲目执行；结果 unknown 时先恢复接受事实。

### FORMAT 1.0 必须表达的内容

| 契约结构 | 来源决策 |
| --- | --- |
| 实体业务 Schema 标识/版本及 RichText Schema 版本 | D01 |
| 资源目录与确定性 DirObject 物化 | D01、D25 |
| owns、引用目录、live/fixed、strong/weak | D05 |
| 纯应用型日志与规范化操作的分工 | D20 |
| 历史位置/内容寻址两类 fixed 身份 | D03、D10 |
| `$formula` 的显式值形状与类型标记；服务端不求值 | D18 |
| run 能力、任务配置摘要、输出声明与委托记录 | D14–D16、D22、D23 |
| 用量账本及可释放的保留承诺 | D06、D19；保留物由对象桶绑定实现 |
| user_state 修订号与命名空间 | D13 |
| 历史下界与 epoch | D06、D07 |

该表冻结语义，不要求恢复已被对象桶替代的 `retentions` 物理表。新增类型、操作、选择器、引用种类或日志语义时，必须评估协议与格式影响，同步内核、服务、共享类型、SDK、WASM、副本、前端、Schema、文档和相关 Agent 手册。

稳定接口必须有可执行的契约向量。新增业务 Schema 可以不升级 FORMAT；新增或改变数据内核行为不能假装只是业务配置。宿主 API、宏 API、扩展 manifest 和标准库接口也要有版本化契约与旧版本兼容向量。

## AIWS 对外 API 分类清单

本节按调用者要完成的工作分类，逐项列出当前 `METHOD_LEVELS` 的 **126 个 kRPC 方法：stable 53、internal 15、experimental 58**。级别分别对应前文的稳定、内部、实验；分类不改变各方法的授权或稳定性。后面的 HTTP／对象入口、宿主 JavaScript API 属于不同调用层，单独列出。

所有 kRPC 方法均使用同一服务入口。多数文档操作需要 `workspace_id`，但 `ws.list/create/ensure/time/list_subjects`、`entry.describe`、控件目录等有各自参数；会话方法常以 `session_id` 定位，不能统一强加 Workspace 参数。字段、选择器和错误详情见[服务协议](../../../src/frame/aiworkspace/README.md#protocol)与 [schemas](../../../src/frame/aiworkspace/schemas)。`entity.create`、`table.set_values` 等是 `doc.commit.operations` 中的操作，不是额外的顶层 RPC；完整原语见 [operations.json](../../../src/frame/aiworkspace/schemas/operations.json)。

方法目录和分发依据：[lib.rs](../../../src/frame/aiworkspace/server/src/lib.rs) 的 `METHOD_LEVELS`、`krpc`、`dispatch`，以及 [ext.rs](../../../src/frame/aiworkspace/server/src/ext.rs)、[show.rs](../../../src/frame/aiworkspace/server/src/show.rs)、[session.rs](../../../src/frame/aiworkspace/server/src/session.rs) 的子分发。仅扫描同步 `dispatch` 会漏掉异步及专用入口。

### HTTP、WebSocket 与页面入口

这一板块提供字节传输、会话实时通道和公开访问；不经过 `METHOD_LEVELS` 的路由不能套用 kRPC 的稳定级别。下表路径均以 `P = /kapi/aiworkspace` 为前缀。

| 入口 | 功能 | 访问与调用边界 |
| --- | --- | --- |
| `POST P`、`POST P/` | 调用本节列出的全部 kRPC 方法 | 使用 `{ method, params, sys: [seq, token] }`；身份与结果语义见前文 |
| `GET P/healthz` | 检查进程路由存活 | 公开；不代表依赖或业务就绪 |
| `GET P/schemas/richtext.basic.v1.json` | 获取内置 RichText JSON Schema | 公开；Schema 版本独立于协议版本 |
| `GET P/asset/{workspace_id}/{object_id}` | 经 Workspace 授权代读资产文件 | bearer 身份，检查资产可见性；HTML、SVG 等主动内容按下载字节处理 |
| `GET P/stream/{token}` | 音视频等资产的流式读取与 Range 定位 | 先经 `asset.stream_url` 取得临时地址；当前有效期 6 小时，读取时验证 stream token |
| `GET P/session/ws`（WebSocket Upgrade） | 会话事件、在场状态、控制与 RPC 复用通道 | 首条 `hello` 携带 `session_id`、`token`／`link` 等；鉴权后返回 `welcome`，可用 `after` 接续事件 |
| `GET P/pub/{workspace_id}/{name}` | 读取已发布实体的 JSON 信封或 HTML | 按 publication 和 `public` 可读范围；支持 `format=json` 与 `fixed` 查询 |
| `POST P/pub/{workspace_id}/{name}/referrers` | 登记发布内容的引用方 | 无凭据登记弱引用；登记不授予权限，也不阻止撤回发布 |
| `P/obj`、`P/obj/{*rest}` | DID Object Provider，提供对象卡片、属性和索引查询 | 复用原调用者身份转入 kRPC；具体对象面见下表 |
| Workspace 独立域名的 `GET /`、`GET /{workspace_slug}`、`GET /{workspace_slug}/{name}` | 提供 AIWS 页面、Surface 定位或同域发布内容 | 有 `?id=<surface_id>` 时打开页面；无 id 时优先匹配发布名，否则解析 Surface 并重定向；页面入口不授予数据访问权 |
| fallback `GET` 静态文件路径 | 提供 Desktop 构建中的脚本、样式、字体、PDF.js 等文件 | 从已配置 Web 目录读取；这是页面资源入口，不是文档数据 API |

WebSocket 客户端消息为 `hello`（建立会话）、`ping`（保活／校时）、`follow`（切换跟随）、`call`（调用会话方法）。`call` 仅承载当前会话的 `session.*`，不含 `session.create/list/list_mine/join/feed_sample`；服务返回 `result`、`event`、`control`、`pong` 或 `resync` 等消息，不能将该通道当成通用 kRPC 隧道。

源码依据：[build_router](../../../src/frame/aiworkspace/server/src/lib.rs)、[stream.rs](../../../src/frame/aiworkspace/server/src/stream.rs)、[session.rs](../../../src/frame/aiworkspace/server/src/session.rs)、[source.rs](../../../src/frame/aiworkspace/server/src/source.rs)、[pages.rs](../../../src/frame/aiworkspace/server/src/pages.rs)。

### 对象发现与属性访问

这一板块把 Workspace 和实体暴露为 Agent 可发现的对象。`obj://aiworkspace/...` 映射到上述 `P/obj/...`；对象卡片用 `GET <object>`，Profile 用 `GET <object>?type=profile`，属性用 `GET <object>/props/<property>`，有索引的对象通过 `POST <object>/methods/query` 查询。

| 对象 | 属性／能力 | 对应功能与底层方法 |
| --- | --- | --- |
| `obj://aiworkspace` | `workspaces`、`query` | 列出调用者可见的 Workspace，并返回对象链接；对应 `ws.list` |
| `obj://aiworkspace/{ws}` | `info`、`outline`、`query` / `page` | `info` 读取 Workspace 信息（`ws.get_info`）；`outline` 一次取可读实体树（`doc.outline`）；index 按 URL 查询参数（或动作输入的 `query`）执行 `op=ls`（默认）、`op=find&name=`、`op=grep&text=`，`at`、`type`、`not_type`、`schema`、`depth`、`case` 缩小范围，`page_size` / `cursor` 分页（`doc.index` → `doc.list` / `doc.find` / `doc.query { text }`） |
| 同上 | `head`、`locks` 事件声明 | 声明新提交和锁表变更的对象事件；实际通知与回退方式见后端依赖章节 |
| `obj://aiworkspace/{ws}/entities/{entity}` | `meta`（摘要）、`body`、`content` | `meta`：公共属性（`doc.read { as: meta }`）；`body`：纯文本，`?cursor=&max_bytes=&parts=true`、`?selector=`（`doc.read { as: body }`）；`content`：原生内容，可带 `selector`，`?mode=fixed&version=` 读该版本或明确失败（`doc.read`） |
| 同上 | `relations`、`freshness`、`versions` | 分别读取引用关系、依赖新鲜度、可寻址版本；对应 `doc.relations`、`doc.freshness`、`doc.list_versions` |
| 同上 | `reference` | 按 URL 的 `mode`、`selector`、`version` 解析规范引用；对应 `doc.resolve` |
| `obj://aiworkspace/{ws}/path/{path}` | `resolved` | 按可读路径定位实体，返回规范引用和稳定对象 URL；对应 `doc.resolve` |

路径会随重命名和移动改变（名字跟随标题时改标题也会改路径），后续操作应保存返回的实体 ID。当前对象面只提供发现和读取，写入仍走 kRPC。对象入口的 HTTP 状态按错误码给出：`PERMISSION_DENIED` 为 403；`NOT_FOUND`、`TARGET_DELETED`、`VERSION_NOT_RETAINED`、`REFERENCE_BROKEN` 为 404；`INVALID_OPERATION`、`INVALID_SCHEMA`、`UNSUPPORTED_VERSION` 为 400；其余为 500。`content` 把 URL 的固定版本传给 `doc.read`，读到该版本或明确失败，不会退化为当前版本；`meta`、`body` 首批只读当前版本，带固定版本时返回 `UNSUPPORTED_VERSION`。实现见 [obj_provider.rs](../../../src/frame/aiworkspace/server/src/obj_provider.rs)，访问示例见 [objects.rs](../../../src/frame/aiworkspace/server/tests/objects.rs)。

## Agent 操作 AIWS 的接口

Agent 有两种使用方式：作为获授权的协作者直接读写 Workspace，或作为某次 Wish run 的执行器提交候选结果。前者使用普通 Workspace API 和当前身份的权限；后者使用 `proc.*` 执行器协议，结果经预览和 `proc.apply` 才写入文档。配置了 hosted Agent，不等于给该 Agent 任意 Workspace 写权限。

### 调用入口与命令映射

CLI 入口是 `buckyos aiws`，底层仍调用 `POST /kapi/aiworkspace`。TypeScript 使用 `buckyos.getAiWorkspaceClient()`：已有封装包括 `info/read/query/resolve/resolvePath/outline/prepare/commit/getSubmission/getChanges/waitChanges`、`run*` 和 `ext*`；其余接口通过 `client.call(method, params)` 调用。CLI 子命令与 RPC 方法不是一一对应，当前没有为所有 RPC 提供同名命令。

| Agent 要完成的工作 | 当前 CLI / SDK 入口 | 对应 API 与作用 |
| --- | --- | --- |
| 发现、创建和进入 Workspace | SDK `call`；`buckyos aiws info --workspace <ws>` | `ws.list/create/ensure/get_info`：列出可见工作区、创建或按名称确保存在、取得 epoch、能力、用量与页面入口 |
| 查找并读取数据 | CLI `ls/find/grep/stat/cat/resolve/sql/read`；SDK 的对应方法 | `doc.list/find/read { as: meta | body | content }/query { text | sql }/resolve`：按路径或名称发现、读公共属性和纯文本、文本与 SQL 查询、把路径转为稳定引用；`outline` 仍为内部接口 |

### 普通协作者的读写闭环

1. 用 `ws.list/create/ensure` 确定工作区，再用 `ws.get_info` 取得当前 `epoch` 和有效能力。使用 `doc.resolve` 将名称路径转换为实体 ID / Reference，后续操作绑定稳定身份。
2. 用 `doc.read`（含 `as: meta`）、`doc.query { sql }`、`doc.list` 读取要修改的内容、修订号和依赖；根据操作契约填写 `expect`、前置条件或读集合。需要锁的操作先获取锁。字段、树结构、富文本等操作均采用 [operations.json](../../../src/frame/aiworkspace/schemas/operations.json) 的名称与结构。
3. 按需 `doc.prepare` 预检，再以 `protocol_version`、`workspace_id`、`epoch`、固定的 `idempotency_key` 和 `session_id` 调用 `doc.commit`。SDK 的一次 `commit` 会在必要时通过 `doc.stage` 分片传输，仍形成一次原子提交；当前整体上限为 32 MiB / 50,000 个操作。
4. 检查 `accepted/conflict/rejected`。响应丢失时先用原 `epoch + idempotency_key` 调 `doc.get_submission` 恢复接受事实；重发仍使用原请求和原 key。修改了意图或操作内容就不能复用旧 key。冲突时重新读取、合并并构造新提交。
5. 用 `doc.read/query` 核实结果；用 `doc.get_changes/wait_changes` 接续后续变化。仅有 HTTP 200、CLI 退出成功或 `prepare` 成功均不能替代 Commit 接受事实。

### hosted Agent 的执行闭环

托管配置由有 `manage` 能力的调用者通过 `ws.set_hosted_exec` 设置，包含 Agent、允许的 Wish 和触发主体。触发者在 `proc.start` 的参数中指定 `program: "wish.xllm@1"` 和 `params.execution.mode: "hosted"`；服务向配置的 Agent 分发包含 `workspace_id/run_id/claim_token` 的 Goal。Agent 持正常 session 调用以下接口，且使用领取响应中的实际 `attempt`，不能固定写成 `1`。

| 顺序 / 命令 | API 与关键输入 | Agent 得到什么、接下来做什么 |
| --- | --- | --- |
| 读运行状态：`run-get` | `proc.get { workspace_id, run_id }` | 查看状态、执行上下文、错误、候选和预览；已取消的 run 不继续执行 |
| 领取：`run-claim` | `proc.claim { workspace_id, run_id, claim_token, executor? }` | 返回 `attempt/run_token/lease_until/lease_ms` 和 `stage`。stage 包含本阶段的任务、工具说明或待重跑的程序 |
| 续租：`run-heartbeat` | `proc.heartbeat { workspace_id, run_id, attempt, progress? }` | 更新 lease 和进度；按返回的租期提前续租，当前默认租期 90 秒，手册建议至少每分钟一次 |
| 读取执行快照：`run-files` | `proc.files { workspace_id, run_id, attempt }` | 获取 `context/`、`request.json`、`WORKSPACE.md`、`catalog/` 和 `lib/`；程序使用这份上下文和输入，而非自行取最新数据冒充本次输入 |
| 运行阶段工具：`run-tool` | `proc.tool { workspace_id, run_id, attempt, name, args }` | 通过下表工具读取阶段数据、提交分析、补充候选并检查结果；按 `stage.tools` 使用当次提供的工具 |
| 交程序执行产物：`run-program` | `proc.program { workspace_id, run_id, attempt, source, results?, log?, files? }` | Agent 在执行器运行 `lib/run.js` 后交回源码、结果清单、输出文件与日志；服务校验结果。此 API 不替 Agent 运行任意程序 |
| 结束或报告失败：`run-report` | `proc.report { workspace_id, run_id, attempt, finished: true }`，或 `analysis/results/error/progress` | `finished` 提交已收集的阶段候选，转入服务端验证与规划；也支持直接报告结构化分析/结果，不能将两者混为已落库 |
| 查看与应用 | `proc.get` → `proc.apply { workspace_id, run_id, plan_digest, session_id? }` | 执行器交付通常止于候选及预览；有权的确认方选择计划后应用。成功应用才形成文档修改，旧任务配置、冲突或撤销可使应用被拒 |

`analyze` 阶段通过工具检查输入并 `submit_analysis`，不要求生成程序；`execute/repair_program` 通常先交程序结果，再完成检查与 `finish`；`rerun_program` 使用领取的 `stage.source` 重跑。`proc.tool` / `proc.program` 的业务返回还包含 `status: ok | error`，工具校验失败必须处理，不能只看外层 `ok: true`。收到 `RUN_REVOKED` 后停止当前 attempt，先查 `proc.get`；恢复 `interrupted` run 时重新领取并使用新 attempt。申请取消使用 `proc.cancel`，不通过停止心跳冒充取消。

实现依据：[wish/exec.rs](../../../src/frame/aiworkspace/server/src/wish/exec.rs)、[wish/stages.rs](../../../src/frame/aiworkspace/server/src/wish/stages.rs)、[wish/mod.rs](../../../src/frame/aiworkspace/server/src/wish/mod.rs)、[store/src/wish/runs.rs](../../../src/frame/aiworkspace/store/src/wish/runs.rs)。`proc.*` 当前仍是实验接口，以上流程说明现有行为，不构成稳定性升级。

### session、claim token 与 run token 的边界

- 普通 session 使用调用者自己的有效权限；Agent 需要相应访问能力。`claim_token`（`ct_…`）是 `proc.claim` 的参数，用于领取对应 run，不替代普通登录凭据。
- 领取返回的 `run_token`（`rt_…`）可放入 kRPC `sys[1]`，只开放 [RUN_TOKEN_METHODS](../../../src/frame/aiworkspace/server/src/lib.rs) 的 13 个方法：`proc.get`、`proc.heartbeat`、`proc.report`、`proc.tool`、`proc.program`、`proc.files`、`proc.list`、`ws.get_info`、`doc.read`、`doc.query`、`doc.resolve`、`doc.outline`、`doc.list`。CLI 的 `run-*` 当前使用正常 session 调用；并非每次都必须手工切换为 run token。
- run token 不开放 `doc.commit`、`proc.apply`、`proc.cancel`、`acl.*` 等写入或管理入口；它只在所属尝试仍是当前尝试、运行仍在执行时有效，持有者按触发者重建身份。读取仍经 Workspace 可见性检查；阶段候选与普通文档写入不能混用。执行器续租、交工具结果和回报携带 `attempt`，服务在相应路径检查当前 attempt 和运行状态。
- 当前租约到期转为 `interrupted` 的处理发生在 `proc.get` 读取路径；不要把租约描述成独立后台实时撤销器。任务摘要和候选 attempt 在 Apply 时还会复核，调用方应以返回状态和结构化错误决定恢复方式。

## 当前 AIWS 服务依赖的 Backend APIs

这里列的是 **AIWS 服务发起的调用**，包括 runtime/共享库代它发起的调用；`ws.*`、`doc.*`、`proc.*` 等是 AIWS 对外提供的接口，不是下游服务。下表使用 wire 方法名，必要时同时列出 Rust 客户端方法。服务地址由 runtime 解析，不能把开发环境端口当成固定远端地址。

### 启动、身份和授权

| Backend / 入口 | 实际 API 与数据 | AIWS 使用场景及身份 | 当前依赖与失败行为 |
| --- | --- | --- | --- |
| verify-hub，`/kapi/verify-hub` | `login_by_jwt`、`refresh_token` | `KernelService` runtime 将启动 assertion 换成服务 session，随后续期；不是用户交互登录 | 启动登录或首次换票失败则退出；后续跨服务调用使用 runtime 当前 session |
| system-config，`/kapi/system_config` | `sys_config_get`（客户端 `get`）：`boot/config`、`system/rbac/policy` | runtime 加载 Zone 配置、信任材料与 RBAC；使用 runtime 的启动/服务身份 | 属于运行时基础依赖；RBAC 策略缺键允许默认值，其他读取失败不能当成授权成功 |
| 同上 | `sys_config_get`：`services/aiworkspace/settings` | 启动读取限额、历史保留和 Wish 配置 | 当前读取或反序列化失败会使用 `AiWorkspaceSettings::default()`；验收须确认实际生效配置，不能假定失败会阻止启动 |
| 同上 | `sys_config_get`：`services/<service>/info` | runtime 发现 nfs-server、AICC、msg-center、verify-hub 和 Agent 绑定服务的地址 | 使用服务实例信息选本机端口或网关路径；地址发现失败影响对应调用 |
| 同上 | `sys_config_set`（客户端 `set`）：`services/aiworkspace/instances/<node>` | runtime 定期上报本服务实例状态、端口等 | 属于运行时注册/保活依赖，不是 Workspace 文档写入 |
| 同上 | `sys_config_list`（客户端 `list`）：`users`、`system/user_groups`；`sys_config_get`：`system/user_groups/<id>`、`system/user_groups/_projections` | `ws.list_subjects` 获取用户与组目录，使用服务身份；读取 projections 是 `load_user_groups` 的附带行为 | 用户列表或组目录读取失败时，相应候选会被省略；候选列表不构成授权结果 |
| 同上 | `sys_config_get`：`users/<principal>/settings`、`users/<principal>/doc` | 解析 `group:<id>` 的成员关系、账户 DID，或核验 contact 授权条目的拥有者 | 无法确认的主体记为 `unconfirmed`；若现有已确认授权不足以满足请求，则拒绝并带 `authorization_unavailable` |
| 同上 | `sys_config_get`：`system/sso/settings` | `ws.join_entry` 将分享入口方式与 Zone SSO 开关取交集 | 仅缺键使用默认值；其他读取或解析失败返回 `authorization_unavailable` |
| 同上 | `sys_config_get`：`users/<owner>/agents/<agent_id>/spec` | hosted run 分发前读取 Owner 指定 Agent 的 `binding.service_name` | 只在托管分发时需要；失败记录在 run 的 `dispatch` 中 |
| msg-center，`/kapi/msg-center` | `contact.check_membership`，请求 `{ owner, did, tag }`，读取结果 `member` | 解析 `contact:<owner_did>#<tag>` 授权主体；服务 session 调用，以请求中的 DID 核验成员 | 无法确认时不授予该主体的权限；已独立获得所需能力的调用不必因此失败 |

两项容易误读的边界：

- `get_control_panel_client()` 在上述路径返回基于 system-config 的 `ControlPanelClient`。`get_user_list`、`load_user_groups`、`get_user_settings_by_username`、`get_user_did` 和服务发现并不发起 control-panel HTTP RPC。
- `verify_session_token_opened(token, SessionScope::AiWorkspace)` 使用 runtime 本地信任材料验签并检查 session ceiling，不是每个 AIWS 请求都调用 verify-hub `verify_token`。组和 contact 在授权请求中重新解析；system-config 客户端当前只缓存 `services/`、`system/rbac/` 前缀，用户、用户组与 SSO 配置不在该缓存名单中。

### 对象、资产、导入导出和扩展库

| 同上 | `bucket.create_access_token` | 服务 session 为导出包、replica、扩展包生成指定单 key、仅 `read` 的下载 token | 当前导出 token 有效期 1 小时；返回下载描述，由客户端读取数据面 |
| nfs-server NDM，HTTP | `POST /ndm/v1/store/get_object`，body `{ obj_id }` | 转发**原调用者 bearer**，核验其可读裸 FileObject；用于 `asset.import_object`、`ws.import`、`ext.build`、`ext.install` 的相应裸 `obj_id` 路径 | 未配置 NDM gateway 返回 `DEPENDENCY_UNAVAILABLE`；HTTP 非成功当前统一为 `PERMISSION_DENIED`；网络/超时为 `STORAGE_IO_ERROR`，超时 30 秒 |

桶命名为 `user/aiworkspace/<owner>/<name>`，当前声明四类：`assets` 保留资产，`objects` 保留快照/版本的 DirObject 闭包，`exports` 保存临时导出、replica 和 fixed 发布内容（默认 7 天），`library` 保存安装的控件和模板。桶定义见 [aiworkspace_client.rs](../../../src/kernel/buckyos-api/src/aiworkspace_client.rs) 的 `aiworkspace_bucket_decls`。

其中资产、快照、`doc.export` 和 replica 使用 Workspace Owner 的桶；`ext.pack` 使用调用者自己的 `exports`，扩展安装使用目标 library owner 的桶，不能把这些 owner 混为同一身份。

`ext.install mode=installer` 是例外入口：仅接受 control-panel 服务身份，由 Installer 交付其已验证的暂存包，不重复做用户裸对象检查；普通 `mode=dev` 仍须证明对象可读。这是 control-panel 调用 AIWS 的入站流程，不是 AIWS 调用 control-panel 的后端依赖。

桶错误由 [server/src/buckets.rs](../../../src/frame/aiworkspace/server/src/buckets.rs) 映射：`quota_exceeded` / `object_too_large` → `STORAGE_FULL`，`content_not_available` / `content_evicted` / `not_held` → `DEPENDENCY_UNAVAILABLE`，未被 get/delete 特殊分支处理的 `no_such_key` / `bucket_not_found` → `NOT_FOUND`，其他错误 → `STORAGE_IO_ERROR`。调用方不得把这些映射都当成可盲目重试的网络故障。

对象字节本身通过**进程内 NamedDataMgr** 访问：`is_object_exist`、`is_object_stored`、`put_object`、`put_chunk`、`get_object`、`get_chunk_data`、`open_reader`；文件入库还复用 `ndn_toolkit::cacl_file_object`。Zone 模式使用 `runtime.get_local_named_store()`，不是把上述写入改成 NDM HTTP 上传。文档、授权和运行状态使用本地 SQLite，扩展库使用 `library.sqlite`，没有额外的远端数据库或扩展库服务。

### 后端依赖的组合验收

## 验收入口与交付要求

### 查询预算与性能验收

统一读取的成本上限是契约的一部分，超出时返回上面“错误与失败行为”中的结构化结果，不静默缩小范围：

| 入口 | 上限 |
| --- | --- |
| `doc.query { sql }` | SQL 16 KiB；执行 2 秒；`max_rows` 默认 1000、最多 5000；结果 4 MiB |
| `doc.query { text }` | 字面串 1–256 个字符；一次调用扫描 8 MiB 文本或 1 秒；默认 20 个命中、最多 100，每个实体一页最多 5 个 |
| `doc.read { as: body }` | 一页默认 32 KiB，`max_bytes` 64 字节到 256 KiB |
| `doc.list` / `doc.find` | `list` 默认 100、最多 1000；`find` 默认 50、最多 200，一次最多遍历 20 000 个实体，深度最多 16 |

- 逻辑表的列是对 JSON 的表达式，JOIN 用不上索引。两张大表 JOIN 时要把小的一侧写成 `WITH d AS MATERIALIZED (SELECT …)`，SQLite 才会给它建自动索引；读了多张表的查询超时，错误里带这条写法。store 为 `table_records` 维护 `sqlite_stat1`（打开时没有就建，累计写入超过记录数的十分之一、至少 1000 条时重建），并删掉 STAT4 样本：内置 SQLite 开了 STAT4，有样本时规划器会选错 JOIN 顺序。
- 查询执行期间持有该 Workspace，同一 Workspace 的提交要等它结束，最长就是时间预算（SQL 2 秒，文本查询 1 秒）。

性能验收数据固定为 10 万条记录 × 20 个字段的表、1000 条的第二张表、两个保存的表视图和一篇接近文档上限的长文档（4899 块、约 48 万字符）。通过条件取基线机器（i7-13700KF，release 构建）基线的约 2.5–3 倍，用于发现退化，不是弱设备上的延迟承诺：

| 项 | 通过条件（store / 真实 Zone） |
| --- | --- |
| SQL 单次调用（计数、筛选排序取一页、分组求和、全表 LIKE、物化一侧的 JOIN） | ≤ 500 ms / ≤ 1000 ms |
| 不持有副本的 Desktop 渲染一个保存的视图 | ≤ 1000 ms / ≤ 2000 ms |
| `body` 一页 | 32 KiB 页 p95 ≤ 20 ms、256 KiB 页 ≤ 50 ms，与位置无关 / 256 KiB 页 p95 ≤ 200 ms |
| 整表 CSV 逐页读完、长文档每页 | ≤ 5000 ms、≤ 100 ms |
| 文本查询单次调用、读到底 | ≤ 1500 ms、≤ 5000 ms / 单次 ≤ 2000 ms |
| `meta`、按名字 `find` | ≤ 10 ms |

基线数字、2026-11-12 的两组结果和已知限制见 [AIWS 核心 API 设计](../../../notepads/aiws-core-api-design.md) §12.2。入口：store 的 `perf_core_api`（release、`--ignored`）和 Desktop 的 `tests/dv/aiworkspace.perf.spec.ts`（真实 Zone，经网关提交同一份数据）。

# 方法目录和 wire 形状
