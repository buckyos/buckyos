## 1. 本期要交付什么

第一期围绕三件事展开：**Workspace 文档格式与对象模型、Command Engine、内置标准对象**。正式实现采用 **Rust 独立后台 + BuckyOS Desktop 默认应用**，后台代码位于 `buckyos/src/frame/aiworkspace`。最终应能通过 Desktop 打开和编辑文档，也能在显式准备后离线编辑、保存、关闭、重新打开，并通过统一命令协议完成批量修改、冲突处理和撤销。富文本和 Notion 式表格是验证内核的主要样本。

设计依据：

- [《实现的核心设计》](<BuckyOS AI Workspace 实现的核心设计.md>)：约束数据、视图、个人状态、命令、共享与发布的语义。
- [《分层架构》](<BuckyOS AI Workspace 分层架构.md>)：约束对象树、编程模型与后续扩展方向。
- [《CYFS Protocol》](<../../../cyfs-ndn/doc/CYFS Protocol/CYFS Protocol.md>)和[《CYFS 标准对象》](<../../../cyfs-ndn/doc/CYFS Protocol/CYFS 标准对象.md>)：作为 NamedObject、ObjectId、稳定编码、内容寻址与路径解析的依据。这里的相对链接按 `buckyos` 与 `cyfs-ndn` 为同级仓库组织。

本文把前两份文档的讨论收敛为本期边界。**“必须”是验收约束；“建议”是默认实施路线，调整时记录依据；“验证后决定”必须在相应里程碑给出结论，不能一直留成 TODO。** 示例是待实现的 Workspace 协议草案，不表示仓库已有同名 API，也不新增 CYFS 标准。

阅读顺序：§2–3 定义对象和文档，§4 定义修改协议，§5–7 指导类型和技术选型，§8–10 规定验证与交付。相对于分层架构中“第一阶段包含 AI 生成代码”的原路线，本期先用受控程序验证写回协议，将任意生成代码执行延后；核心设计中的权限、草稿和原子性要求不因此延后。

### 1.2 产品 PoC 与正式实现的关系

已归档的 [Canvas 原型](https://github.com/buckyos/buckyos/blob/9ff98e613dd3133b447175726b47e70300a32652/src/frame/desktop/src/app/canvas/README.md)是产品体验 PoC，目的是感受 AI 驱动的 Workspace 如何工作。**新的实现可以完全不参考它的代码。** 原型中的数据结构、reducer、命令、存储格式、UI 组件和技术选择均不构成正式实现的起点或约束。

本期不要求迁移旧 Canvas、兼容 `.aicanvas.json`、复用旧 UI 或为原型保留适配层。CodeAgent 应从本文定义的契约设计正式实现，直接在 `buckyos/src/frame/aiworkspace` 建立 Rust 后台；前端作为 BuckyOS Desktop 的默认应用接入。是否借用原型中的产品体验样例是可选事项，不影响架构验收。

系统基础能力仍优先使用 BuckyOS 已有组件与协议，例如身份认证、服务运行时、网关、存储和 CYFS NamedObject；这与复用产品 PoC 是不同的要求。

### 1.3 系统定位与前后端分工

`aiworkspace` 与 `nfs_server` 同属系统关键的**产物管理服务**：`nfs_server` 管理文件、目录及其访问组织；`aiworkspace` 管理可编辑的结构化 Workspace 产物，包括对象、内容、命令历史和版本快照。Workspace 的业务生命周期由自己的后台管理，文件/资产引用通过明确协议与 NFS/CYFS 能力衔接。

| 部分 | 代码归属与责任 |
| --- | --- |
| Rust 后台 | `src/frame/aiworkspace`；独立进程，包含领域内核、类型适配、Command Engine、授权、权威持久化、快照和服务 API |
| Desktop 默认应用 | 接入 `src/frame/desktop` 的默认应用体系；建议独立 `src/app/aiworkspace` 入口，负责对象编辑、视图、交互和调用后台 |
| 浏览器离线副本 | 前端侧保存显式准备的文档、私有草稿和待提交操作；离线时可编辑，重连后交由 Rust 后台验证和接受 |
| Agent/其他调用方 | 通过后台的公开能力接口读写 Workspace；无需打开 Desktop，也不能直接修改后台数据库 |

后台应提供可独立测试的领域库与进程入口，服务生命周期参考 [nfs_server 的系统服务与独立启动模式](<../../src/frame/nfs_server/README.md>)。系统模式接入 BuckyOS 的服务身份、配置、日志、网关与启停管理；独立测试模式使用隔离数据目录和明确的测试身份。具体端口、路由和服务配置在 M0/M1 定义，不能从 NFS 直接复制业务协议或未完成能力。

后台是在线权威状态与共享提交的执行边界。Desktop 关闭后，产物仍可由后台读取和管理；后台重启后能恢复已接受的提交。浏览器缓存不替代后台持久化，浏览器的本地成功也不等于后台已接受。

前后端共享版本化协议、schema 与一致性测试。离线逻辑可评估复用 Rust/WASM 内核或实现受限的客户端适配器，但不得另建一套拥有不同业务规则的权威引擎。富文本协作选型必须覆盖 Rust 端解码、语义校验、合并与持久化，不能只证明两个浏览器能同步。

## 2. NamedObject、稳定身份与对象树

### 2.1 对齐 CYFS，而不是重建一套内容寻址

必须区分以下标识：

| 标识 | 含义 | 是否随编辑变化 |
| --- | --- | --- |
| `workspace_id` | 一个 Workspace 实例的稳定身份 | 正常编辑不变，Fork 改变 |
| `entity_id` | Workspace 内一个逻辑对象的稳定身份 | 改名、移动、修改内容不变 |
| `ObjectId` / `object_id` | CYFS NamedObject 的不可变内容版本 | 被哈希的内容改变即产生新 ID |
| `name` / `path` | 在指定命名空间内解析对象的可变名字 | 可改变或重新绑定 |
| `revision` | 用于并发校验的工作状态版本令牌 | 对应修改发生时改变 |
| `commit_id` | 一次有效提交的身份 | 每次有效提交产生，重试不产生新提交 |
| `record_id` / `field_id` / `block_id` | 类型内部的稳定寻址身份 | 不因排序、改名或插入其他项改变 |

`entity_id` 是 Workspace 管理可变实体的标识，不是另一种 CYFS ObjectId。内部引用建议使用 `(workspace_id, entity_id)`【回写 §11-1：持久化的内部引用不写 `workspace_id`】；需要固定版本时优先绑定 `object_id`。不能把随机 UUID、整数 revision、CRDT 时钟称为内容 ObjectId。

**ObjectId 是优先采用的能力，不是所有对象和数据源的接入前提。** 普通内置对象、文档元数据和可物化产物应尽力使用它；仅在少数明确的大数据场景，例如持续更新的大表、无法合理全量物化的查询结果，允许使用“数据源 URL + 查询参数”引用。选用该路径需记录规模/成本依据和可用能力，不能因实现方便把全部普通对象退回 URL，也不设置一个未经测量的统一行数阈值。

```text
可变工作状态
  workspace_id + entity_id ──内容定位──> ObjectId（优先）
            ↑                           或数据源 URL + 查询参数（大数据例外）
       name / path 解析

Command 修改工作状态 → 更新工作 revision
  可物化内容：按检查点生成 ObjectId
  URL 查询源：保存查询定义及实际取得的源版本/读取能力，不要求全表哈希
```

复用 [ndn-lib/object.rs](<../../../cyfs-ndn/src/ndn-lib/src/object.rs>) 的 `ObjId`、`NamedObject`、构造与验证语义；资产复用 `FileObject`、`ChunkList`、Chunk。浏览器侧用同规则实现或绑定，不能自创一个仅名字类似的 hash 格式。第一期可用通用 JSON NamedObject（`jobj`）承载带 Workspace `type_id` 的描述；不必先注册一批新的 CYFS ObjType。**Workspace 的 `type_id` 与 CYFS ObjType 前缀是两层分类。**

### 2.2 编码、验证和边界

普通 JSON NamedObject 按 CYFS 的 JCS 稳定编码与 SHA-256 规则计算 ID；`clist` 等特殊类型遵循已有实现，不能统一套用普通 JSON 算法。对象 ID 在被哈希正文之外保存，正文不能包含自己的最终 ID。

实现时必须注意以下已知接缝：

1. Rust 与浏览器共用测试向量：键顺序、UTF-16 键排序、Unicode、转义、浮点表示、大整数、空值与缺省。禁止重复 JSON key、非有限数和无法编码的值；大整数、精确小数用有类型约束的字符串。
2. 《CYFS Protocol》的文字摘要提到 NFC，但 RFC 8785 §3.1 要求保留字符串原样，当前 `ndn-lib` 使用 `serde_jcs`。Workspace 不在哈希前擅自增加 Unicode 归一化；命名规范化若需要，应作为显式输入规则，与内容编码分开。以跨语言向量消除歧义，不能靠手写摘要猜算法。[RFC 8785](https://www.rfc-editor.org/rfc/rfc8785.html#section-3.1)
3. 当前 `build_named_object_by_json` 对序列化错误存在退回 `{}` 的实现。Workspace 的导入与提交适配层必须先进行可失败的严格校验，错误时拒绝，不允许坏输入获得空对象的合法 ID；是否修订底层 API 另行按实际修改范围处理。
4. 对可选元数据，缺省就省略；业务字段的显式 `null` 必须保留。两者不是同一个值，也不具有相同 ID。
5. 校验内容 ID 只证明取得了指定内容；授权和 PathObject 签名验证各有边界。不得把“知道 ObjectId”视为有权读取、修改或发布。

NamedObject 应保持适合结构化读取的大小。适合物化的大富文本二进制、表格数据分片、图片和数据库快照通过已有文件/Chunk 类型引用，不把全部内容塞入一个巨型 JSON 或 base64 字段。对物化成本不合理的大表，可按 §2.5 保留 URL 查询引用，不要求先全量下载、分片或计算 ObjectId 才能使用。

### 2.3 可变树、引用图与不可变快照

建议把对象注册表和结构关系分开：注册表保存逻辑对象；工作页/容器的结构关系组成树；对象之间的数据绑定组成引用图。

- 每个结构节点有一个父节点，根节点除外；禁止循环、悬空父节点和重复成员关系。
- `parent_id` 与兄弟排序只选一份权威表示，不同时维护可独立修改的 `children[]` 和 `parent_id`。
- 名称用于查找，显示标题允许重复；若提供唯一 `path`，需定义同级冲突、转义和规范化规则。持久绑定解析后保存稳定 ID，改名不能把旧绑定指向同名新对象。
- 同一 TableSource 可被多个 Cell/View 引用；不要为了“只能有一个父节点”而复制数据。
- 文本段落、字符与普通表格单元格不要求成为 Workspace 树节点。类型适配器提供内部 selector、版本和细粒度事件。
- 删除默认产生可识别的 tombstone 或等效删除版本；删除容器需显式声明子树策略。被其他对象引用的源可先拒绝删除并返回引用列表，不得静默级联破坏内容。
- 一般引用可形成图；本期自动计算依赖必须是 DAG，拒绝计算环。嵌入视图的递归显示另设深度上限，不能无限渲染。

不可变快照建议采用“根描述 + 对象版本索引 + 内容引用”。父子关系在快照的结构索引中表达；不要让父、子不可变对象互相包含彼此的新 ObjectId，形成无法计算哈希的循环。

固定一个对象版本，不等于固定它内部所有动态引用。生成可复现快照时，必须记录依赖解析清单，将所需的 `live_head` 绑定解析为确定版本，或明确标为未包含/未固定的外部依赖。URL 查询定义本身可以得到 ObjectId，但这只固定定义，不固定远端查询结果。

### 2.4 引用与类型内部寻址

引用至少区分：`live_head`、`fixed_revision`、`published_channel`。本期实现前两种；第三种保留独立结构，不能先映射成 live head 冒充发布。

表格单元格的逻辑定位示例：

```json
{
  "workspace_id": "ws-project",
  "entity_id": "tasks",
  "version_policy": { "mode": "live_head" },
  "selector": {
    "kind": "table_cell",
    "record_id": "task-42",
    "field_id": "status"
  }
}
```

内容寻址的固定引用须携带真实、可验证的 CYFS `object_id`；URL 查询引用可以不带 ObjectId。若源确实支持保留并重新读取指定版本，可用源提供的 revision/snapshot token 表达 `fixed_revision`，并声明保证来自该源；普通 URL、时间戳或仅能检测变化的 ETag 不能自动成为固定版本引用。源不支持固定版本时，保留 `live_head` 并报告该能力缺失，不能伪造 ObjectId。

解析返回实际版本（若可取得）、类型、可用能力和可解释错误。`selector` 是 Workspace 类型语义，不能直接等同于数组下标、数据库 rowid 或 CYFS `inner_path`。只有确定快照中确实存在相应 JSON 字段时，才可由适配器转换为 `inner_path`；大表查询不应伪装成任意 JSON 路径读取。对外 `/@/` 解析复用 CYFS 规则，不自行增加写入不可变对象的语义。

### 2.5 大数据例外：URL 数据源与查询

建议仍将大表注册为有稳定 `entity_id` 的 TableSource，保存 schema、访问能力和查询定义，TableView 继续引用它。底层数据用 URL 定位，不强制进入 Workspace SQLite 或为每行生成 ObjectId。数据源可以来自本机服务、同一 Zone 或远端；URL 表示访问方式，不必等同于公网 HTTP。

URL 查询引用示例（参数语法由 Source Adapter 定义）：

```json
{
  "kind": "url_query",
  "source_url": "https://data.example.com/datasets/events",
  "query": {
    "fields": ["event_id", "created_at", "amount"],
    "filter": { "field_id": "project_id", "operator": "eq", "value": "project-42" },
    "sort": [{ "field_id": "event_id", "direction": "asc" }]
  },
  "version_policy": { "mode": "live_head" },
  "consistency": "best_effort"
}
```

URL 与查询参数共同决定读取目标。可以由适配器编码为完整查询 URL，也可以结构化保存；不得只以基础 URL 作为缓存键、忽略过滤/排序/投影条件。缓存还需隔离授权范围，并绑定源版本（若有）；分页 cursor 是读取会话状态，不混入长期查询定义。凭据不放入可分享 URL 或文档正文。

| 能力 | 使用内容 ObjectId | 仅 URL + 查询参数 |
| --- | --- | --- |
| 内容完整性与相等性 | 可校验取得的指定内容，识别相同内容 | 不能凭 URL/查询摘要证明内容相同，需信任源或另取内容校验信息 |
| 版本固定与复现 | 指定不可变内容；完整依赖仍需另行固定 | 默认随源变化；仅在源提供真实快照/历史读取时获得相应保证 |
| 去重、内容缓存与资产保留 | 可基于内容身份建立这些机制 | 退回源/查询/版本缓存策略；不能保证远端保留历史结果 |
| 离线和自包含导出 | 已取得并纳入包的内容可离线使用 | 默认只保留查询定义；缓存切片或物化所需结果后才能提供对应离线能力 |

不使用 ObjectId 不放宽 schema、授权或提交规则。第一期 URL 查询源默认只读；源不支持可靠的条件写入时不开放编辑。未来接入写操作也必须经过 Command Engine 和源适配器，不能声称远端修改与本地文档天然 ACID。

源支持快照 token 时，分页绑定同一个 token；不支持时标为 `best_effort`，提示结果可能变化。需要严格一致源视图的导出/加工必须取得相应快照能力，否则明确返回能力不支持；普通浏览可继续工作。可按需把一次查询结果、一个分区或已确认产物物化为 ObjectId，固定实际取得的这份内容，无需先物化整个数据集；物化不能反向保证先前跨页读取的一致性。

## 3. 文档格式与持久化

### 3.1 三种表示各司其职

| 表示 | 职责 | 本期建议 |
| --- | --- | --- |
| 逻辑格式 | 说明对象、关系、类型、值、版本和引用意味着什么 | 有版本的 JSON Schema/类型定义；富文本语义 AST；表格 schema + records |
| 运行时存储 | 快速读取、事务写入、查询、恢复 | Rust 后台管理每份 Workspace 的工作数据库，建议 SQLite；资产独立存储，浏览器维护授权离线副本 |
| 交换与版本快照 | 可移交、验证、导入、备份、固定依赖 | Manifest + 优先采用的 CYFS NamedObject/资产集合 + 明确列出的 URL 查询依赖，支持打包为一个文件 |

**SQLite 是本期工作文档存储的建议实现，CYFS NamedObject 是不可变内容与引用的协议基础，两者不是替代关系。** 不把 SQLite 页布局规定成逻辑文档格式，也不要求每次按键重算整库 ObjectId。持久化后的命令批次可改变工作 revision；按提交/检查点策略物化不可变版本。

该建议针对可携带的用户文档。`aiworkspace` 的服务目录、索引、任务等服务级数据需与文档内容分开分类，其持久化遵循 BuckyOS 系统服务规范；账号和凭据使用已有系统能力。

### 3.2 文档数据分类

| 数据 | 是否必须持久化 | 普通分享导出 |
| --- | --- | --- |
| 对象、结构关系、共享视图、内置表记录、已提交富文本 | 是 | 按授权纳入 |
| 已提交版本、恢复所需 CRDT 状态、幂等结果 | 是，依保留策略 | 不默认导出全部历史 |
| 用户私有草稿、未发送操作、离线 outbox | 是，不能当缓存丢弃 | 排除 |
| 有权限的 Overlay 内容 | 是，独立作用域 | 显式按范围纳入 |
| 搜索索引、AST 派生缓存、缩略图 | 可重建 | 按需 |
| 选区、焦点、光标、实时视角、加载动画 | 临时或个人偏好 | 排除 |
| 外部服务凭据、token、AI 密钥 | 由宿主凭据系统管理 | 排除 |

私有草稿至少按用户和 Workspace 隔离，不能挂在会被整量广播的共享 CRDT 文档中。个人存储与共享存储物理分开时，采用“冻结草稿 → 幂等提交共享变更 → 清理草稿标记”的恢复协议，不声称跨两个数据库天然原子。

### 3.3 最小逻辑实体与版本

对象公共信封建议包含 `entity_id`、`type_id`、`schema_version`、可选 `name`、`content_revision`、类型 payload 定位及扩展元数据。位置、选区、执行中的 token 流不得成为所有对象共有的业务字段。

分别定义以下版本，不使用一个 `version` 承担所有责任：

- `format_version`：Workspace 交换格式。
- `storage_schema_version`：SQLite 表结构。
- `schema_version`：具体标准对象的数据结构。
- `content_revision` / 字段版本：OCC 与变化订阅。【回写 §11-2：统一为每个 Workspace 一个 `seq` 加若干“版本格”】
- CRDT 状态向量/前沿：由对应引擎解释的合并状态。
- `renderer_api_version` 与依赖描述：显示和编辑能力的兼容边界。

本期允许预发布格式 breaking change，但必须明确拒绝不支持的版本、保留原文件。不能自动清空旧库，或把未知结构当成空文档保存。正式冻结后再定义后续升级策略。

### 3.4 SQLite 的建议布局

下表是职责划分，不是要求直接复制的 SQL DDL。第一项实现交付必须补齐实际列类型、主外键、唯一约束、索引、删除策略及初始化/升级流程。

| 逻辑表组 | 关键内容与约束 |
| --- | --- |
| `workspace_meta` | Workspace 身份、存储版本、已确认 head、本地工作版本 |
| `objects` / `tree_edges` | 实体类型及版本；结构父子与排序；ID 唯一、关系完整 |
| `table_schemas` / `table_records` | source、field、record 的稳定 ID；类型定义；记录 JSON 与必要字段版本 |
| `richtext_states` | 引擎与编码版本、快照、后续增量、对应内容版本/检查点 |
| `commits` / `commit_ops` | 有效提交、基准、可信作者、操作、受影响 selector、撤销所需数据 |
| `idempotency_results` | 提交作用域、幂等键、请求摘要、结果；相同 key 不允许不同请求内容【回写 §11-3：并入 `commits`，不单独建表】 |
| `asset_refs` / `snapshots` | 已校验资产引用、不可变检查点与保留根 |
| `outbox` | 本地待共享提交、依赖顺序、重试与确认状态；与对应本地变更同事务落盘【回写 §11-3：只存在于客户端副本；后台没有 outbox】 |

第一期表格可采用“一条记录一行，属性值为 JSON”，另建支持目标查询的索引。不要预先给所有单元格创建 Workspace 对象，也不要先设计覆盖任意数据库的 ORM。通过 1 万行数据验证后，再决定是否需要按属性拆表、更多索引或分片。

最小查询路径：按实体读取、列子节点、按记录 ID 读取、按稳定字段过滤/排序/分页、按 selector 查询版本、按提交获取变更、按幂等键查结果。一致模式的分页必须固定快照/读版本，并提供稳定的次级排序；源无法提供时，只能显式采用 `best_effort` 或拒绝一致模式，不能把变化中的 offset 分页称为一致读取。上述本地表布局不要求 URL 查询源复制全部记录入库。

在各自执行边界内，后台的权威数据、有效日志、幂等结果及必要待发送通知，以及浏览器的本地变更与提交 outbox，都必须分别处于可恢复事务边界。网络两端不构成一个跨库事务。浏览器与 Rust 后台需要做同一逻辑内容的读写往返；不以两个 SQLite 文件的字节是否完全一致判断业务相等。

离线副本还必须区分“最后确认的共享基准”和“包含待提交操作的本地工作视图”。可采用基准检查点加 pending 操作重建工作视图，不强制复制两份全库。接收远端变更时先推进确认基准，再重放/合并未确认操作；拒绝的候选留在待处理区。禁止直接用远端快照覆盖本地工作视图，或把本地临时 revision 当成远端已接受的版本。

### 3.5 交换包与不可变快照

建议先采用便于检查的展开目录，打包扩展名沿用候选 `.bcanvas`；在格式冻结前，扩展名本身不构成协议承诺。

```text
example.bcanvas/
  manifest.json
  objects/          # CYFS NamedObject 的 canonical JSON
  assets/           # 本包包含的文件/Chunk 数据
  dependencies/     # 已包含的 schema、renderer 描述或资源
```

Manifest 至少定义：格式版本、Workspace 身份、快照根定位（优先 ObjectId）、导出模式、对象/资产定位清单、类型和渲染依赖、未包含/未固定资源、来源关系。包内物化内容记录大小、编码/媒体类型和可验证 ID；URL 查询依赖记录数据源、查询、实际版本与能力边界，不强制填写 ObjectId 或未知的全量大小。字段本身需要明确 schema。采用 ObjectId 的快照根引用对象版本、结构索引及依赖描述，**不反向包含外层包文件的 hash**；根的不可变性不使 URL 指向的数据自动不可变。

第一期必须支持两种明确的产品操作：

1. **导出当前可分享内容**：构造授权范围内的新内容快照，不携带私有草稿、完整撤销历史、凭据和已删除秘密。CRDT 二进制可能含历史信息，不能直接复制完整协作状态到普通分享包；必要时从可见语义内容建立新 CRDT lineage。重新建立 lineage 时重映射依赖旧相对位置的锚点，无法映射则显式标为失效。
2. **个人恢复备份**：显式纳入恢复所需的原始 CRDT 状态、历史与个人未完成工作，标注敏感内容和恢复语义。它不能作为普通分享包。最小实现可将共享检查点与个人状态分别封装，并记录两者的基准关系。

“引用型/自包含”是另一个维度：外部依赖未包含时列出清单，不能宣称全量离线。第一期可只对内置对象及已取得资产实现自包含导出；遇到不能包含的外部资源必须报告，不能静默丢失。

含 URL 大表的引用型导出应保留查询定义，重新打开后仍可按权限查询；不要求导出整个大表。其快照可固定 Workspace 的本地结构和查询定义，但只有已取得并物化的数据切片，或源真正保留的版本，才能具有相应的数据复现保证。测试须分别断言“文档定义往返一致”与“查询结果固定”，不能混为一项。

导出针对明确检查点执行。若把 SQLite 作为备份 payload，使用一致性备份机制或等价快照 API，不能复制一个仍在写入的 `.db` 后忽略 WAL。导入先在暂存区检查版本、ID、大小、引用和结构约束，完整通过后再使文档可见。[SQLite 备份机制](https://www.sqlite.org/backup.html)

恢复同一 Workspace 与 Fork 必须分开。Fork 产生新 `workspace_id`，可保留其命名空间内的 `entity_id`；内部 Workspace 引用全部重绑定，外部固定引用保持或按复制策略处理。重置作者会话、在线授权、outbox 和运行任务，记录来源快照。打开导入包不会自动获得原 Workspace 的在线写权限。

### 3.6 CYFS 的接入深度

本期必须完成本地 NamedObject 构造/验证、版本快照引用、资产完整性与跨语言向量。网络 PathObject 发布、跨 Zone 获取和发布渠道管理可以后续接入，不要求先部署 CYFS 网络才能编辑文档。

同时用一个按需分页的确定性大表源验证无 ObjectId 路径：支持 URL 查询引用、能力声明、导出保留定义和网络失败状态。不要求本期接入多种生产数据库，也不能为了通过验证先全量拉取数据并偷偷生成 ObjectId。

已有标准对象的递归遍历不自动理解 Workspace 自定义 JSON 中的资产引用；必须由 Workspace 适配器显式枚举依赖与保留根，或组织为已有可遍历容器。不能假设把新对象写入 named store 后，下载器与 GC 就能发现所有子对象。本期可保守保留已提交快照的资产，延后自动 GC；不能提前删掉仍被历史、草稿或 outbox 引用的内容。

## 4. Command Engine：所有有效修改的共同入口

### 4.1 职责与模块边界

```text
Desktop 默认应用 / 离线副本 / Agent / 受控程序
                        │ 版本化服务协议
                        ▼
               aiworkspace Rust 独立后台
                        │ 类型化操作
                        ▼
 Command Engine：授权 → 校验 → 候选状态 → 冲突检查 → 提交协调
             │                         │
       Type Adapter                Document Store
   语义、selector、合并、undo       数据/日志/outbox 原子落盘
             │                         │
             └────────提交后变化事件────┘
                           ▼
                 视图 / 索引 / 依赖失效通知
```

Rust 后台建议包含 `ObjectRegistry/Resolver`、`TypeRegistry`、`CommandEngine`、`DocumentStore`、`AssetStore` 与服务 API/通知模块；这些是同一后台内的逻辑职责，不要求拆成多个服务。Desktop 客户端管理 `SessionStore`、编辑器绑定和 `CommitTransport`，并按需要提供离线执行适配。接口必须明确在哪一侧执行，不把前端本地校验当成后台授权或最终提交。

Type Adapter 至少提供 schema 校验、读取投影、selector 解析、操作校验与应用、引用枚举、快照编解码、冲突/合并、撤销能力声明。Adapter 不能自行提交共享历史、越过权限或直接把变化广播到网络。

UI 不拿裸 SQLite 写连接；Agent 不输出任意 SQL；富文本插件不直接连接一个绕过命令授权的同步 provider。编辑器可在内存中维护未提交的交互状态，但其有效持久修改、共享变更与撤销都必须进入同一协调入口。

对调用方的最小能力面如下，方法名可以调整，语义不得混并：

| 能力 | 必须说明的输入/输出 |
| --- | --- |
| `resolve` / `read` | 引用、selector、读版本、调用者能力 → 已授权内容、实际版本或错误 |
| `query` | source、受控过滤/排序、一致性要求、可选快照 token、cursor、limit → 结果、实际版本与一致性能力 |
| `prepare` | 基准与候选操作 → 校验结果、影响范围、候选标识；不改变共享状态 |
| `commit` / `get_submission_status` | 候选、前置条件、幂等键 → 接受/冲突/拒绝；可查询未知结果 |
| `undo` / `redo` | 历史目标与作用域 → 新的合法操作或补偿提交，不是裸快照替换 |
| `checkpoint` / `export` / `import` / `fork` | 明确版本、内容范围、复制/恢复策略 → 可验证产物或完整错误 |
| `subscribe` | 已授权目标与变化类别 → 可去重的提交后事件 |

`prepare` 成功不保证 `commit` 成功，也不持有跨网络的长期锁【回写 §11-4：`prepare` 是无状态试算，不返回需要后台保存的候选标识】；后台提交必须重查基准和授权。读接口同样执行权限和字段投影，不能先把受限整库下载给客户端再隐藏列。内核方法不必逐个映射为 RPC，但第一期服务 API 必须覆盖 Desktop 和无 UI 调用方所需的读写、查询、提交结果确认、快照与变化通知能力。

### 4.2 LocalCommand、SharedCommit、Publication

| 概念 | 语义 | 本期要求 |
| --- | --- | --- |
| LocalCommand | 当前 Session 的一次本地操作，含私有中间态 | 支持分组、本地撤销、必要持久化 |
| SharedCommit | 经过验证、可进入权威共享状态的有效变更集 | 实现协议、接收端、幂等、冲突与重试 |
| Publication | 将某个确定版本或版本集合暴露给指定下游通道 | 独立接口/对象定义，本期不做完整发布产品 |

即使是单机单用户部署，也由本机的 `aiworkspace` Rust 后台接受有效提交并记录历史。浏览器离线副本的 `saved_locally` 与后台权威的 `accepted` 必须区分；本地已保存不代表已获后台授权。

提交策略至少验证 `immediate` 与 `explicit` 两种：前者允许编辑批次即时进入共享提交；后者私有编辑多次后提交一个有效结果。私有 CRDT 草稿不能把包含全部中间态的增量合并到公共 CRDT；应依据基准生成允许分享的语义变更，在共享分支重新应用，冲突时保留草稿。

### 4.3 最小提交协议

```json
{
  "protocol_version": "0.1",
  "workspace_id": "ws-project",
  "submission_id": "submission-17",
  "session_id": "session-a",
  "idempotency_key": "edit-17",
  "origin": "human",
  "preconditions": [
    {
      "target": { "entity_id": "tasks", "record_id": "task-42", "field_id": "status" },
      "expected_revision": "field-revision-8"
    }
  ],
  "operations": [
    {
      "op": "table.set_value",
      "target": { "entity_id": "tasks", "record_id": "task-42", "field_id": "status" },
      "value": "option-done"
    }
  ]
}
```

【回写 §11-5】上面的信封是 v0.1 的示意：实施后去掉 `submission_id`，增加 `epoch`，`expect` 内联在每个覆盖型操作上，Commit 级 `preconditions` 只表达读集合；操作名与参数以《内置对象详细设计》§2.6、§3 为准。

示例中 `status` 为 select 字段，值是稳定 option ID。可信接收端根据调用上下文补齐实际作者、授权范围、接收时间和 `commit_id`；客户端 `origin` 只用于追踪，不能提升权限。

返回结构至少区分 `accepted`、`conflict`、`rejected`；传输失败导致的 `unknown` 属于调用端观测状态。已接受结果包含 `commit_id`、新版本、变化范围及幂等重放标志；冲突包含授权范围内的 selector、基准与当前版本、可恢复候选。

幂等作用域必须包含 Workspace、可信提交主体及幂等键。同一键同一请求返回原结果；同一键不同请求返回错误。数据库约束保证并发重试不会执行两次。网络超时后查询或重发原请求，不能生成新键赌一次成功。

### 4.4 原子性与执行顺序

一次命令组在一个 Workspace 内必须满足“全部生效或全部不生效”，包括对象/表格/富文本的混合修改。

1. 解析目标并获取允许读取的基准；校验大小、操作数、深度、schema 与能力。
2. 在隔离候选状态中应用全部操作，检查树约束、引用、字段类型和业务约束。大任务在锁外准备，不能长时间占住写事务。
3. 进入存储事务，重查权限、幂等结果与前置版本；若候选准备后数据变化，重新验证或返回冲突。
4. 一次落盘数据、富文本状态/增量、有效历史、幂等结果和必要 outbox；事务失败不产生成功记录。
5. 事务成功后发布内存状态、事件与待发送提交。崩溃恢复从已提交记录重建，订阅者按 `commit_id` 去重；不能在落盘前发送“已提交”事件。

编辑器可以乐观显示输入，但必须区分尚未落盘与已保存。IO 失败保留可恢复候选、明确显示未保存，并提供重试/应急导出；不能仅显示 toast 后丢掉输入。

**Yjs 的事务分组、Loro 的 commit 与 SQL 事务不是同一个概念。** Loro 文档明确说明其事务模型不提供数据库式 ACID 回滚。CRDT Adapter 必须证明：候选校验失败时，权威 CRDT、持久化状态和已广播状态均未被污染。可使用隔离文档/分支、暂存增量或等效写前协议；不能“先改共享 CRDT，再期望 SQL rollback 把它还原”。[Loro transaction model](https://www.loro.dev/docs/concepts/transaction_model)

本地物化资产采用先写入并验证不可变内容、再提交引用的顺序；资产准备失败不得提交悬空引用。URL 查询源允许记录暂时不可达的有效配置，但必须标明不可用，不能伪装成已有数据快照。外部上传、源查询/写入和跨 Workspace 修改不进入本地 ACID 承诺。未引用的暂存资产可后续清理。

### 4.5 冲突和撤销

| 操作 | 默认处理 |
| --- | --- |
| 两人修改独立字段/独立记录 | 在约束允许时均可提交；不因整文档 revision 变化全部拒绝 |
| 两人基于同一旧版本修改同一业务字段 | OCC 显式冲突，不默认后写覆盖 |
| 富文本同一 lineage 的并发文本修改 | 使用已验证的类型级 CRDT 合并，再校验对象仍存在、类型和权限有效 |
| 删除对象与迟到编辑竞争 | 返回目标已删除，保留待处理操作；不得隐式复活对象 |
| 字段改类型与基于旧 schema 写入竞争 | schema 前置条件失败，要求转换或重新提交 |
| 唯一值/跨记录业务约束 | 权威提交边界校验，不能只依靠单字段合并 |

字段版本应能发现“改走又改回”的竞争；仅比较当前值等于旧值不足以代替 revision。树移动第一期可由权威接收端串行化并校验预期父节点，不要求所有结构编辑先做成 CRDT。【回写 §11-6：树的移动与摆放改为自动合并（后到者生效），不校验预期父节点；另增按对象开启的写锁】

未共享操作允许局部逆操作；已共享撤销生成新的补偿提交，不删除公共历史、不恢复整个旧文档覆盖他人变化。补偿的目标已被别人修改时，默认返回冲突；若允许部分撤销，必须先返回可执行部分并形成显式新命令组。

富文本插件的 UndoManager 与 Workspace 历史由一个 coordinator 路由。文本输入合并为可理解的编辑批次；一次 Agent 批量操作为一个撤销单位。不能一次快捷键同时执行编辑器 undo 和全局 undo。跨对象批次撤销仍经 Command Engine。

### 4.6 事件、依赖与受控加工

事件至少携带 `commit_id`、稳定 target/selector、变化类别、新内容版本、`origin`、可选 `run_id`/`causation_id`。区分业务内容变化与布局变化：移动 TableView 不应让基于表数据的结果过期；修改被读取字段应使结果失效。

第一期实现“提交后失效通知 + 显式运行加工”。自动执行如要验证，只支持 DAG 和有上限的任务队列；拒绝计算环，不把“同一传播代只执行一次”当成普适求解算法。异步结果绑定实际输入版本，返回时再次检查。

提供确定性 Mock：读取固定版本的任务表，生成摘要 RichText 和一个派生字段，返回候选命令组。验证 staging、校验、一次应用、人工修改保护、取消后迟到结果拒绝。Mock 与后续真实 Agent 使用同一候选协议；不能为 Mock 开一个跳过校验的入口。

### 4.7 最小错误模型

错误使用稳定 `code`，附带 `retryable`、授权范围内的 target、可恢复候选标识和必要版本信息，不能只返回任意异常文本。至少区分：

- `INVALID_SCHEMA` / `INVALID_OPERATION` / `LIMIT_EXCEEDED`：输入、操作或资源限制不满足。
- `NOT_FOUND` / `TARGET_DELETED` / `REFERENCE_BROKEN`：目标生命周期与引用错误。
- `PERMISSION_DENIED`：能力不足；对无权确认对象存在的调用者，不泄露隐藏对象信息。
- `REVISION_CONFLICT` / `SCHEMA_CONFLICT` / `IDEMPOTENCY_MISMATCH`：需要保留候选并处理的竞争。
- `UNSUPPORTED_VERSION` / `MISSING_EXTENSION` / `DEPENDENCY_UNAVAILABLE`：文档或执行依赖不可用。
- `STORAGE_FULL` / `STORAGE_IO_ERROR` / `WRITER_BUSY`：保存失败或锁冲突，不能标记已保存。

传输断开形成的未知结果不等于业务拒绝；状态查询和幂等重试负责消除不确定性。具体 code 可在 M1 统一命名，但上述区别必须保留。【回写 §11-7：已统一命名并增补 9 个 code】

## 5. 内置标准对象

### 5.1 最小集合

| 标准类型/角色 | 本期内容 | 验证目的 |
| --- | --- | --- |
| WorkspaceRoot / Container | 根、单工作页、简单分组；流式或自由布局配置 | 树、移动、组合与独立视图 |
| RecordObject | 有 schema 的小型 JSON 业务对象 | 通用属性编辑、schema 与命令基本闭环 |
| RichText | 段落、标题、列表、基础 marks、链接、受控对象引用 | 复杂内部结构、协作、快照和细粒度撤销 |
| TableSource | typed fields + records | 细粒度版本、批量操作、稳定引用和查询 |
| Cell / TableView | 绑定数据源，持久显示配置 | 同源多视图，不复制业务数据 |
| AssetRef | 文件/图片引用及基础元数据 | CYFS 资产引用、打包与缺失状态 |

Cell 是展现实例；TableView 是它的一种标准视图配置。实现可把两者放在同一条类型化对象记录中，但不得复制 TableSource 的 records。富文本内容也可以被多个 Cell 引用。

Overlay 可用最小注释对象验证：锚定一个稳定表格字段或富文本块，权限/所有者与正文独立。无需完整评论 UI，但必须证明它不会因排序、改名被附着到另一个对象。【回写 §11-13：锚点分为目标、范围、原文三层并逐级降级；富文本字符范围已实现；应用可自定义范围种类】

### 5.2 富文本：语义 AST 与协作状态

建议采用 [ProseMirror](https://prosemirror.net/) 生态的文档 schema 和 transaction 模型；Tiptap 可作为编辑 UI 封装候选。第一期冻结一小组节点和 marks，避免默认引入全部扩展。源码查阅以项目当前维护地址为准；原 [prosemirror-model GitHub 仓库](https://github.com/ProseMirror/prosemirror-model) 已注明迁移地址，不应把归档仓库状态误解为整个项目停止维护。

语义快照示例：

```json
{
  "type_id": "buckyos.richtext",
  "schema_version": 1,
  "editor_schema": "buckyos.richtext.basic.v1",
  "content": {
    "type": "doc",
    "content": [
      {
        "type": "paragraph",
        "attrs": { "block_id": "paragraph-1" },
        "content": [{ "type": "text", "text": "本周项目进展" }]
      }
    ]
  }
}
```

`block_id` 是需要在自定义节点 schema 中声明和校验的属性，不是假定 ProseMirror 自动提供的 ID。字符选择区/精确批注使用所选协作引擎支持的相对位置或专用 anchor，不保存会随插入漂移的裸 offset。【回写 §11-13】

保存分工必须明确：

- 启用 CRDT 后，**原生快照 + 必要增量是可继续协作的内容权威表示**；SQLite 是其持久载体。AST 是对应检查点的投影，用于预览、检查、普通内容导出与 AI 输入。
- AST 与 CRDT 不得各自成为可独立修改的主数据。AI 改文字也要经适配器生成合法操作；投影不能被反向整段覆盖而丢失协作身份。
- 快照记录引擎名、编码版本、lineage、检查点和对应内容 revision。恢复不能只加载 HTML/Markdown 后假装延续原协作历史。
- 普通内容导入可以从 AST 建立新的协作 lineage；完整恢复需要保留原生状态。压缩/裁剪历史前必须验证旧离线客户端的重连规则。
- HTML、Markdown 是互操作输出，不是富文本的权威格式；不承诺任意扩展节点无损往返。
- 未知节点或缺失扩展不得在打开时被编辑器静默删除；保留原始 payload，显示只读 fallback，显式迁移后才继续编辑。

富文本中的表格嵌入建议引用 TableView，不把整份业务表转换为编辑器内部 table node。普通排版用的小表可以日后扩展，但不能混淆为同一种数据源。

### 5.3 表格：记录与属性，不以坐标为身份

采用接近 Notion 数据库的心智：一行是一条记录，一列是有稳定身份和类型的属性，视图决定如何排列和显示。第一期不实现 A1 公式、合并单元格、打印分页、按视觉行号持久引用。

下述 records/SQLite 设计是普通内置表的默认路径；明确的大数据表允许使用 §2.5 的 URL 查询源，并复用 TableView、schema 和查询接口。源若不提供稳定行键，只支持结果展示，不承诺跨次查询的行级引用、批注或编辑；不能用分页位置冒充 `record_id`。

表定义示例：

```json
{
  "entity_id": "tasks",
  "type_id": "buckyos.table-source",
  "schema_version": 1,
  "fields": [
    { "field_id": "title", "name": "任务", "type": "text", "required": true },
    {
      "field_id": "status",
      "name": "状态",
      "type": "select",
      "options": [
        { "option_id": "option-open", "label": "进行中" },
        { "option_id": "option-done", "label": "完成" }
      ]
    },
    { "field_id": "budget", "name": "预算", "type": "decimal", "scale": 2 },
    { "field_id": "due", "name": "截止日期", "type": "date" }
  ]
}
```

记录示例；交换时可按记录逐行写入 JSONL，运行时不要求加载整表：

```json
{
  "record_id": "task-42",
  "values": {
    "title": "完成第一期架构验证",
    "status": "option-open",
    "budget": "1200.00",
    "due": "2026-10-20"
  },
  "body_ref": {
    "workspace_id": "ws-project",
    "entity_id": "task-42-details",
    "version_policy": { "mode": "live_head" }
  }
}
```

`body_ref` 指向可选的 RichText 详情，正文不是所有记录的必填内容。记录的展示标题来自明确的 title 字段，不额外维护一份会漂移的副本。

第一期值类型建议收敛为 `text`、`boolean`、`number`、`decimal`、`date`、`datetime`、`select`、`multi_select`、`object_ref`；`int64` 若需要则用字符串编码。必须定义：

- `number` 的有限双精度范围；decimal 的精度、scale 与规范化方式，不使用 JS 浮点计算金额后再补字符串。
- date 是日历日期；datetime 表示时间点，采用明确时区/UTC 规则。两者不能自动互换。
- 缺字段表示未设置，`null` 表示显式空值，空字符串是一个文本值；清空与删除值使用明确操作。必填与 nullable 分别约束。
- select/multi_select 保存 option ID；改显示标签不改业务值。multi_select 的去重与确定性序列化顺序必须固定。
- `object_ref` 验证目标类型和引用策略；关联字段可保留接口，但跨表 rollup 等功能延期。
- 字段删除、option 删除与类型变更必须显式处理已有值和引用；改字段类型是有预检报告的迁移命令，不是直接改 schema 字符串。

建议第一期实现命令：新增/删除记录、批量写字段、新增/改名字段、修改选项标签、字段迁移预检及至少一种实际类型迁移。大型迁移采用暂存结果后原子切换，不把部分迁移结果暴露成成功状态。

人工与派生数据可存在于同一张表。字段可声明维护来源，具体派生结果还应保存输入版本和执行来源；手工覆盖产生显式标记。刷新已被人工修改的派生值时，不能仅凭之前的一次确认绕过应用前的版本检查。

### 5.4 TableView 与组合

TableView 保存 `source_ref`、可见 `field_id`、列宽、filter、sort、group 和可选手工顺序；个人临时筛选/选区放在 Session，只有显式保存视图才修改文档。过滤语言使用受控 AST，不执行任意 JS/SQL；操作符按字段类型校验。

同一 source 至少建立两个独立视图：“全部任务”和“未完成任务”。两者共享 records，但各自保存布局。视图排序不改变 record ID；如果用户显式手工排序，应定义独立的排序键与并发规则，不用 records 数组下标充当身份。

本期组合样例：项目说明 RichText 引用“未完成任务”视图；每条任务的详情链接到另一份 RichText。删除某个视图不删除表数据，修改任务状态使两个视图和说明中的嵌入同步更新。

## 6. 开源组件与实现选型

### 6.1 建议基线

| 部分 | 建议 | 不应外包给它的责任 |
| --- | --- | --- |
| 服务形态 | Rust 独立后台 + Desktop 默认应用；复用 BuckyOS 系统服务接入模式 | 不沿用体验 PoC 的前端内核作为后台 |
| NamedObject/资产 | 复用 `cyfs-ndn` 对象模型与适配接口 | Workspace 业务权限、命令事务 |
| 工作数据库 | 后台文档库建议 SQLite；浏览器离线副本建议 SQLite WASM + Worker + OPFS | 对象 schema、同步协议、历史语义 |
| 富文本模型/编辑 | ProseMirror；按新 Desktop 应用需要选择是否加 Tiptap | Workspace 对象生命周期与授权 |
| 富文本协作 | 有界验证 Loro 或 Yjs 路线的编辑器绑定与 Rust 接入，选一条默认路线 | 通用业务冲突、数据库回滚、共享草稿策略 |
| 表格 | 自有 typed records 模型，按需选择表格 UI/虚拟化组件 | 不把 UI 组件的数据结构当持久协议 |
| Command Engine | `aiworkspace` 内的 Rust 领域内核，组合已有 schema/存储库 | 不引入一个无法约束的通用低代码平台替代设计 |

SQLite 作为应用文件的实践可参考 [SQLite application file format](https://www.sqlite.org/appfileformat.html)；结构化表格的物理组织可参考 [Grist 数据库说明](https://github.com/gristlabs/grist-core/blob/main/documentation/database.md)。借鉴其元数据/记录/视图分离，不复制不需要的公式运行时或私有编码。

### 6.2 富文本是否局部使用 Yjs

**可以局部使用；第一期不把“所有对象都上 Yjs”设为前提。** 默认把协作引擎限制在 Type Adapter 之后。对象树和普通业务字段先由稳定 ID、命令与 OCC 管理，仍可在无 CRDT 的情况下正确工作。

若希望同时验证可移动对象树和 Rust/JS 复用，优先做一个小规模 Loro 探针。Loro 有[树结构 API](https://www.loro.dev/docs/tutorial/tree)，也已有 [loro-prosemirror](https://github.com/loro-dev/loro-prosemirror) 的同步、游标和撤销绑定；不能假设使用 ProseMirror 就必然再引入 Yjs。

若主要风险在编辑器生态或 Loro binding 的实际能力，使用 [Yjs/y-prosemirror](https://github.com/yjs/y-prosemirror) 是候选路线。Yjs 原生增量与状态向量可用于富文本同步，但不能把它的共享类型直接视为可任意移动的 Workspace 树节点。[Yjs shared types](https://docs.yjs.dev/getting-started/working-with-shared-types)、[document updates](https://docs.yjs.dev/api/document-updates)

【回写 §11-8：已选定 ProseMirror + Loro；树不使用 CRDT 数据结构。】本期不要求完整实现两套引擎。先选择一条默认候选，用同一组用例验证；只有实际失败或关键能力缺失时再比较另一条。若最后选择“树用 Loro、富文本用 Yjs”，必须额外证明跨引擎命令组的原子性、快照一致性、撤销路由和崩溃恢复；没有这些证据，就保持树由 Command Engine 管理的较小组合。

决策记录至少包括：测试的实际包版本与 license、所用 binding/API、Rust/浏览器边界、增量格式、undo 支持、失败用例、包体和性能、升级/降级影响。必须证明 Rust 后台能解释并校验所选富文本内容与操作，不能只原样转发前端二进制、把语义正确性完全交给客户端。源码主分支和稳定发布包可能不同，按实际引入版本验证。依赖声明遵守仓库 AGENTS；本文的候选清单不是新增所有依赖的指令。

### 6.3 一次探针要回答的问题

- 中文输入法、粘贴、列表和 marks 是否正确；同文档两个编辑实例能否共享内容而保持选区独立？
- 并发修改在交换顺序、重复消息和断线后是否收敛；对象已删除时能否拒绝迟到操作？
- 能否在候选分支校验后再接入权威状态，而非先污染共享文档？
- 富文本修改与表格修改在同一个批次中，后者失败是否导致整批不生效？
- 原生快照恢复后能否继续合并离线增量？普通导出是否清除了不应分享的历史？
- 编辑器内部撤销与 Workspace 批次撤销能否只有一个明确入口？

BlockSuite 可作为块 schema、store、编辑器集成的参考，第一期不默认整体嵌入其应用框架。它的编辑命令机制也不能替代这里定义的授权、持久事务和共享提交。[BlockSuite store](https://blocksuite.io/guide/store)

## 7. 浏览器离线验证

第一期采用**显式准备的一份 Workspace**验证离线能力，不默认浏览器下载用户全部资料。最低闭环为：Desktop 从 Rust 后台取得授权文档 → 准备离线资源 → 断开后台连接 → 修改并保存到本地副本 → 关闭重开 → 导出 → 恢复连接并由后台验证提交。浏览器离线是正式服务架构的一项客户端能力，不能用纯浏览器实现替代后台交付。

SQLite 数据放进 LocalStorage 后不会自动变成可操作数据库；需要 WASM 引擎和存储适配。官方确有基于 localStorage 的 `kvvfs`，但它不作为本期大文档的默认方案。建议选择 SQLite WASM 的 OPFS VFS，运行于 Worker；具体 VFS 的跨源隔离头、锁和多标签页要求必须按目标浏览器验证。[SQLite WASM persistence](https://sqlite.org/wasm/doc/trunk/persistence.md)

必须落实：

1. 选定并公布本期支持的浏览器和 VFS。单写入者是可接受的第一期策略；第二标签页应只读或明确拒绝编辑，不能让两个实例各自整库覆盖。
2. 数据和应用资源分别准备。Service Worker 或宿主等价机制缓存 HTML、JS、CSS、WASM、标准编辑器和必要资产；只存 `.db` 不保证关闭页面后离线还能启动。[Service Worker 使用说明](https://developer.mozilla.org/en-US/docs/Web/API/Service_Worker_API/Using_Service_Workers)
3. HTTPS/安全上下文、配额、持久存储申请、存储被清理和写满都要有明确状态。浏览器存储不能替代用户备份。[OPFS](https://developer.mozilla.org/en-US/docs/Web/API/File_System_API/Origin_private_file_system)
4. 落盘确认必须等待存储事务提交完成；内存对象变化、SQL 已排队或 IndexedDB request success 都不足以代表整个事务已提交。
5. 本地有效修改与 outbox 同事务持久化。重连先取远端 head/变化，再按字段 OCC 或富文本策略验证候选；逐个保留 accepted/conflict/rejected 状态。
6. 同步 Commands/SharedCommits/受校验类型增量，不同步互相覆盖的整份 SQLite 文件。对权限撤回、对象删除、基准太旧均保留可恢复本地输入。
7. 区分“外网不可达但 BuckyOS 可达”和“浏览器连 BuckyOS 也不可达”。真实 AI、外部查询等网络能力不可用时明确说明，不把 Mock 输出冒充真实执行结果。

OPFS 不可用时可以提供明确只读/导出状态；如承诺 IndexedDB 回退，就必须实现并执行同一套持久化验收。纯内存回退不能显示“保存成功”。本期不要求双击 `file://` 下的 HTML 即具备完整离线应用能力。

## 8. 验证方案与通过标准

### 8.1 一个贯穿全程的样例

构造“项目工作区”：一个流式容器、一份项目说明 RichText、一份 typed tasks 表、两个 TableView、一条带 RichText 详情的任务、一张 AssetRef 图片和一个独立注释。提供确定性 Mock，根据选定字段生成摘要与派生字段。

同一样例用于 UI 操作、无 UI 命令调用、序列化往返、离线恢复、冲突和批次撤销。测试不能只验证空文档或把复杂对象替换成字符串。

### 8.2 必须自动化的验收矩阵

| 编号 | 场景 | 通过条件 |
| --- | --- | --- |
| V01 | CYFS 编码与跨语言 ID | Rust/浏览器同输入得到同 canonical JSON 和 ObjectId；非法输入拒绝；篡改内容验证失败 |
| V02 | 身份和移动 | 改名、移动、字段改名后原稳定引用仍指向同一目标；固定 ObjectId 的内容不变 |
| V03 | 树与引用校验 | 环、悬空父节点、非法目标、超限批次整批拒绝；源删除按策略返回引用冲突 |
| V04 | 一致导出/导入 | 编辑期间取得明确检查点；导入后类型、值、关系、资产和视图语义一致；损坏包不覆盖原文档 |
| V05 | Fork | 新 Workspace 与原件独立修改；内部引用已重绑定，外部引用按策略保留，无原会话/outbox/凭据 |
| V06 | 富文本恢复 | 中文/marks/列表/引用正确；保存重开继续编辑；完整恢复后可继续合并原 lineage 增量 |
| V07 | 富文本并发 | 两实例离线编辑后合并，交换顺序与重复增量不改变结果；只撤销自己的相应编辑 |
| V08 | 表格稳定寻址 | 排序/过滤/插行/改列名后选择器和注释仍指向原 record/field；两个视图共享同一数据 |
| V09 | 类型与迁移 | decimal/date/null/缺省等往返保真；迁移失败无半张表生效，旧 schema 写入被识别 |
| V10 | 混合原子批次 | 同批包含树、富文本、表格修改；最后一步故意失败时，数据、历史、广播均未部分提交 |
| V11 | 同字段/异字段冲突 | 不同字段在允许条件下均成功；同字段旧基准竞争显式冲突；删除后迟到写入不复活目标 |
| V12 | 幂等与未知结果 | 接收端提交后断开响应，原键重试只产生一次效果；相同 key 不同 payload 被拒绝 |
| V13 | 撤销重做 | 未共享批次可撤销/重做；共享补偿不覆盖他人后续修改；编辑器和全局不重复撤销 |
| V14 | 草稿与导出隐私 | 私有连续修改四次，对端只能看到提交结果；普通包和消息不含私有中间态或被删历史秘密 |
| V15 | 浏览器完整离线 | 实际断网、编辑、关闭重开，内容可用且 outbox 保留；应用资源缺失有清晰状态 |
| V16 | 多标签与存储故障 | 第二写入者遵循锁策略；注入写满/事务失败/Worker 退出后，无“成功但丢数据” |
| V17 | 重连再授权 | 权限撤回、目标删除或冲突时不接受旧离线权利；本地输入可恢复，重试不重复应用 |
| V18 | Mock/受控加工 | 输入版本固定，错误候选整批拒绝；一次应用可撤销；人工修改与取消后的迟到结果受保护 |
| V19 | 变化事件 | 提交后发出可去重事件；内容变化使相应结果 stale，布局变化不误触发数据加工 |
| V20 | 未知版本/类型 | 原始内容保留，降级只读/拒绝有原因，不经编辑器自动丢弃未知内容 |
| V21 | 权限与读投影 | 直接按 ID 调用不能绕过权限；只读拒写；append-only 可追加但不能读取整表或改旧记录 |
| V22 | 资产与快照保留 | 缺失/损坏资产可解释；提交失败不留下有效悬空引用，历史/待提交仍引用的资产不回收 |
| V23 | Rust 服务与 Desktop 接入 | 后台可独立启动并通过 API 完成读写；Desktop 默认入口操作同一服务；关闭前端后 API 仍可用，重启后台后已接受提交保留；系统服务启停与鉴权路径可验证 |
| V24 | 无 ObjectId 的大表查询 | 只用 URL + 查询参数即可按需查询和展示；查询条件/授权范围不同不串缓存；导出再导入保留定义；无版本能力时不声称固定结果，断网不把未取得内容当作离线可用；可只物化所需结果切片 |

【回写 §11-9】新增 V25（写锁）：两人竞争同一把锁恰好一人成功；非持有者的提交被拒绝且内容可恢复；租约到期后他人接手，原持有者的迟到提交得到 `LOCK_LOST` 且不被应用；强制解除、空闲释放同理；同一用户的第二个会话拿不到锁；被锁容器的直接子节点成员变化被拒绝而子节点内容修改不被拒绝；导出再导入后策略保留、锁不存在；受控加工在未持锁时 `LOCK_REQUIRED`。

协议、持久化和故障恢复必须有真实 Rust 后台的集成测试；UI 测试覆盖 Desktop 到后台的调用、复杂编辑与真实浏览器存储，不只验证按钮存在。崩溃测试至少覆盖事务前、事务中、已落盘但尚未应答三个位置，并验证后台进程重启后的恢复。

这组验证落实核心设计中 D01、D05、D08–D11、D13、D18、D23、D27–D29、D31–D36、D38–D42 的相关内核要求；不表示这些编号涉及的全部后续产品功能已交付。其余场景按 §1.1 延期并保留对应接口归属。

### 8.3 性能与复杂度验证

至少提供三档可重复 fixture：小样例；1 万记录 × 20 字段的表；10 万字符、约 1000 块的富文本。再用 1000 个 Workspace 对象验证层级与引用开销，以及一个按页生成结果、未提供 ObjectId 的大表 URL fixture，断言打开/查询/保存定义均不触发全量拉取。这些是探测规模，不是已验证的产品容量承诺。

记录目标硬件、浏览器、依赖版本、数据库/VFS 配置，测量首次打开、单字段写入、1000 行批量修改、分页查询、富文本输入、undo、快照/导出、内存峰值和磁盘增长。区分编辑反馈延迟、落盘延迟和远端确认延迟。

必须证明普通单字段修改不需要整表重写、每次按键不需要整份 Workspace 导出、渲染不要求一次创建全部行 DOM。具体延迟/内存预算在实现里程碑 M1 中记录，在 M5 按同配置复测；超预算时给出瓶颈和明确可接受边界，不能只写“性能良好”。

## 10. 从验证进入正式实现的门槛

通过验证的内核就是正式内核的起点，不再另写一套生产版。转入正式开发必须同时满足：

1. 文档格式、NamedObject 映射、命令协议、错误码、内置类型 schema 均有版本与可执行校验；示例包可独立打开和解释。
2. V01–V25 在明确支持环境中通过，提供运行命令和结果；性能按已声明预算验收。
3. 没有已知的数据丢失、草稿泄露、权限绕过、部分提交、无提示内容丢弃问题。
4. UI、Agent、类型编辑器与导入路径都使用正式内核；没有仅在演示中成立的第二套写入/保存入口。
5. 恢复、普通分享、Fork 的语义和内容范围有明确区分；保存成功与共享成功可被用户判断。
6. 文档列明实际支持的浏览器、VFS、对象类型、容量探测结果及延期功能；未实现能力返回明确错误，不能假装成功。
7. `src/frame/aiworkspace` 中的 Rust 后台以 BuckyOS 系统产物管理服务交付，Desktop 默认应用使用同一服务协议；不依赖旧 Canvas PoC、打开中的浏览器或前端 Mock 才能管理已保存产物。

第一期应留下的核心资产是：**一份可解释、可验证、可移交的 Workspace 文档；一个统一且可恢复的变更引擎；一套由富文本和结构化表格证明可用的类型扩展机制。** 后续协作服务、AI、发布、演示与行业对象都在这些契约上扩展。
