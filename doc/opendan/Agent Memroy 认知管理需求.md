**项目：OpenDAN**

**目标读者：系统架构负责人、Agent Memory / Self Improvement 开发者、Session SDK 开发者**  
**关联文档：[《Agent Session SDK 化核心需求》](<Agent Session SDK化核心需求.md>)**

## 1. 文档定位与核心问题

本文依据本次讨论，定义 Agent Memory 的认知管理需求。重点不在于选择一个向量库、Hint 表或 Notebook 文件格式，而在于确定：什么值得成为记忆、如何低成本写入、如何形成跨 Session 认知，以及如何在合适的时候让 Agent 想起它。

全文沿用关联文档的确定性标记：**明确方向**来自本次讨论；**派生约束**是使这些方向可靠成立所需的工程要求；**待决设计**表示还没有确定的模型与策略。本文不声称相关能力已经实现。

**v1.1 补充说明。** 保留原有 M-01—M-29 的需求编号与未决边界，新增第 4.1—4.3 节的写入类型与载荷示例、第 5.1—5.5 节的感知到认知变化案例、第 6.1—6.5 节的召回入口和主动查询接口示意，以及第 10.2 节的配套验收场景。所有样例人物、时间、对象、观测结果均为虚构测试数据；字段、状态名和接口名称用于说明需求，不是现有实现、最终 Schema 或已定 SDK API。


### 1.1 为什么应用要使用 Agent，而不只是 LLM Context

用户或应用选择以 Agent 身份执行一次工作，一个重要预期是：此次经历可能被这个 Agent 记住，并影响之后的工作。

调用方不希望逐条管理“记住多少、什么时候记、如何整理”。只要通用 Memory 机制默认开启，不同进程、不同 Runtime 中运行的同一 Agent 的 Session，就应通过共享的持久状态获得跨 Session 连续性。

### 1.2 Memory 的核心问题

> **Agent Memory 不仅要支持“知道要查什么时能够查到”，更要帮助 Agent 发现“自己原本不知道应该去查什么”。**

当 Agent 已经明确意识到需要查询某个对象或事实时，可以使用 DID Object、搜索或其他工具。Memory 更关键的作用是，在当前情境中提供线索，使 Agent 意识到某个既有经验、偏好、边界或判断可能相关。

这里并不是要求 Memory 创造从未获得的信息，而是让已经形成的内部状态，在 Agent 尚未主动想到它时，有机会进入当前推理。

### 1.3 核心处理链

```text
不同 Session 中的任务、对话与观察
                 ↓
       低成本记录感知 Perception
                 ↓
   跨 Session 整理 / Self Improvement
                 ↓
       形成可修正的认知 Cognition
                 ↓
  依据当前情境触发线索、按需读取与使用
                 ↓
        新的经历继续形成新的感知
```

成功整理后的感知应被清理，留下认知。历史消息与工作产物可以是来源，但不因参与这个循环就全部等同于 Memory。

## 2. Memory 与世界状态的边界

### M-01｜继续使用 Agent Memory 作为统一概念

**明确方向。** 所有 Agent 认为值得保存并跨 Session 使用的内部状态，统一称为 Agent Memory。Agent Notebook、Hint 等名称可以继续用于具体组织方式或机制，但不替代这个总体概念。

本文重点是这些内部状态中的认知管理。锁、订阅消费进度、执行租约等运行元数据可以与其共用存储设施，但不因此自动成为需要供模型召回的认知条目。

### M-02｜区分内部认知与独立世界对象

**明确方向。** Agent 的内部状态属于 Memory；独立存在的文件、产品版本、Workspace、业务对象等属于世界状态，由 DID Object / 世界对象协议等机制访问。

Agent Memory 不应重新成为所有外部对象的一套特殊事实库。它可以保存对世界对象的理解、使用偏好、选择依据、经验或访问线索；对象本身仍有独立的身份、状态与有效版本。

例如，在贪吃蛇工作场景中：

| 内容 | 主要归属 |
|---|---|
| 贪吃蛇源码、效果资源、产物版本 | Workspace / 世界对象 |
| 某次修改的输入、工具结果与执行状态 | 对应的 Task Session |
| 用户为何放弃某种方案、在特定范围内采用什么偏好 | 可进入 Agent Memory 的感知或认知 |
| 当前有效版本是哪一个 | 以世界状态为事实依据；Memory 可以保存相关选择线索，但不能无视后续变更 |

**派生约束。** 允许缓存必要的外部事实，但必须能分辨其来源、时间和适用范围。缓存是缓存，认知判断是判断，不能因被写入 Memory 就变成永久有效的世界事实。

### M-03｜统一访问协议，不特殊化访问方式

**明确方向。** Agent 具有 DID。它愿意开放的内部状态，可以通过与其他对象相同的 DID Object 协议被读取，不需要仅因名称叫 Memory 就发明一套完全不同的读取体系。

**派生约束。** 内部 / 外部是语义归属，是否可访问是授权问题。Memory 经授权对外开放，并不会因此失去内部认知属性；使用统一协议也不意味着整个 Memory 默认公开。

## 3. 认知建模要求：先定义记什么，再讨论怎么查

### 3.1 不预设 Hint List 就是最终模型

现有讨论中，Side Topic 与 Hint 主要用于研究如何查找和召回。相对更困难的问题是：Agent 在什么情况下应主动创建一条 Hint，以及 Hint List 是否足以承载所需的认知。

因此，本版不把“新增一个 Hint 表”作为认知管理需求的答案。Hint 可以是触发和索引方式，底层认知也可能围绕人物、偏好、适用边界或经验组织。

### M-04｜模型需要表达的不只是孤立事实

**明确方向。** 认知模型应能够表达对人的印象、对某个人偏好的理解、对某类事情边界的理解等内容，而不只是若干 key-value。

下表是需要覆盖的语义举例，不是已确定的固定类型枚举。

| 语义 | 要表达的内容 | 容易发生的误用 |
|---|---|---|
| 对象相关认知 | 对某人、某项目或某工作对象形成的理解 | 把一次观察变成永久、全面的判断 |
| 偏好 | 谁在什么情况下倾向于怎样处理 | 把某个项目的偏好推广到所有项目 |
| 边界与约束 | 什么条件下适用，什么情况下不应继续 | 只记结论，不记成立条件 |
| 经验与选择依据 | 发生过什么、结果如何、为什么采用或放弃 | 把被否定的试验当作已采纳方案 |
| 关联与提醒线索 | 什么情境应想起某个认知或去查某个对象 | 只有内容，没有能够触发它的入口 |

### M-05｜认知应具有来源、范围与可修正性

**派生约束。** 认知模型无论最终采用何种结构，都需要支持以下语义：认知涉及的对象与适用范围、来源依据、与时间或版本有关的条件，以及当前是否仍然有效。

这些信息不一定全部由模型手工填写，也不要求每条记忆都有复杂元数据；可以由 Session、对象引用和运行环境提供。但系统必须能够回答“为什么形成这个认知”和“在哪些条件下应该重新检查”。

相对稳定不等于永久正确。用户明确纠正、世界对象变化或新证据出现后，应能够修订、缩小范围、撤回或替代既有认知，而不是只追加越来越多互相冲突的文本。

### M-06｜保留观察、推断和已确认信息的区别

**派生约束。** 感知允许随意、初步甚至错误，但进入后续推理时必须保持其证据性质。用户明确表达、工具观测结果与 Agent 自己的推测不能不加区分地混为事实。

例如，“用户这次没有采用某种动画”不能直接整理为“用户始终反对动画”。系统应保留具体对象和情境；证据不足时可以形成暂定认知，也可以继续保留为未整理材料。

不要求模型输出的一个置信度数字自动证明结论可靠。如何表示不确定性可以待定，但使用层必须能区分有依据的结论和待验证假设。

### M-07｜同一底层认知可以有多个召回入口

**派生约束。** 模型应允许同一个认知被不同话题或对象关系触发，而不是为了每个 Hint 复制一整份认知。认知变更时，应能够使相关入口同步修正或失效。

是否采用独立 Hint、主题索引、对象索引、关系结构或组合，属于待决设计。不能把某个召回技术提前当作认知本体。

## 4. 感知层：任务中低成本写入

### M-08｜记录感知不要求当场形成成熟认知

**明确方向。** Session 执行主任务时，只需以很小的思考量记录注意到的事情。感知可以不完整、不确定，甚至后来被证明是误判；“先感知到”比当场完成抽象更重要。

感知写入不应要求当前 LLM 偏离任务，展开完整的归因、长期价值判断或跨 Session 检索。

### M-09｜提供默认的感知入口

**明确方向。** Agent Session 的通用机制应默认允许感知记录。应用开发者无需在每个业务分支手工编写 Memory 管理逻辑；外部 Runner 与常驻 Runtime 应使用兼容的写入机制。

**派生约束。** 默认工作不代表不可控制。Agent 或调用方经授权应能表达本次工作不进入长期记忆、限定记忆范围等要求；具体配置和权限分工待定。

### M-10｜写入契约保持轻量，来源由系统补齐

**派生约束。** 感知写入在概念上应至少具有：一段观察内容、属于哪个 Agent、来自哪个 Session / 交互或动作，以及必要的对象范围。

已由运行环境掌握的 Session 标识、时间和输入来源，应尽量自动附加，不要求模型重复生成。感知应能关联 Task 和产物版本，以便后续区分成功结果、试验过程与被放弃的工作。

具体字段名、序列化格式和存储位置不在本版固定。关键要求是低写入负担与可追溯性同时成立。

### M-11｜写入触发依据需要被设计和评估

**明确方向。** 什么事情值得记录，是本需求的核心难点之一。通用提示词可以引导写入，但不能用一句“记住重要的事情”替代明确的建模与评估。

可用于验证触发机制的情形包括：用户明确表达的后续偏好、对象选择及其原因、任务过程中观察到的限制、结果反馈、与已有认知相矛盾的新信息。这些只是候选场景，不是规定每次出现都必须生成独立 Hint。

**派生约束。** 写入机制应能够控制噪声和重复；既不能因为门槛过高完全漏记，也不能把每条输入都机械改写成长期记忆。

### M-12｜低成本写入不阻塞主任务

**明确方向。** 感知记录与认知整理在运行成本上分层。普通任务不应为写一条感知而同步执行重型 Self Improvement。

**派生约束。** 写入失败或重试应有可观察的处理结果，不应悄悄演变成主任务的无限重试。是否允许任务继续、何时补写、什么场景必须可靠提交，需要按 Session 策略定义。

同一输入因重放或 Runner 恢复而被再次处理时，应避免无意义地重复写入同一感知。低成本目标需在原型中测量，但本版不凭空规定统一的 token 或耗时阈值。

### 4.1 写入的数据类型与实例

**示例性设计，不固定最终类型枚举。** “写入类型”需要区分两个维度：一是记录的**语义**，例如偏好、选择依据和经验；二是承载它的**数据形态**，例如短文本、结构化属性和对象引用。以下样例均为虚构测试数据，不代表真实用户偏好或已经实现的功能。

| 候选语义类型 | Session 中可低成本写下的感知 | 整理后可能得到的认知 | 不能直接得出的结论 |
|---|---|---|---|
| 偏好 `preference` | 用户说：“这个贪吃蛇游戏页面以后用静态背景，不要闪烁。” | 针对该用户、该项目和游戏页面的效果偏好 | 用户在所有产品中都不喜欢动画 |
| 选择及依据 `decision_context` | 用户在 alpha、beta 两个工作区中选了 alpha，理由是操作更稳定 | 当时的选择理由，以及后续应检查哪个项目对象的选择状态 | alpha 永远是当前工作区，或者最近修改的版本必然被采用 |
| 边界与约束 `boundary` | 用户说：“只改游戏页面，演示页面不在这次范围内。” | 本次任务的约束；用户明确要求持续适用时，才形成后续项目边界 | 每次临时任务要求都自动成为永久约束 |
| 结果反馈 `outcome_feedback` | 用户说：“这个版本干扰操作，撤掉；以后也别在游戏背景用这种效果。” | 对该效果的负面反馈及其明确适用范围 | 仅凭工具返回成功，就认为用户认可结果 |
| 工具或环境观察 `environment_observation` | 当前校验工具在资源中缺少 `tick_ms` 字段时返回错误 | 有版本和资源类型条件的检查线索，或暂定限制 | 所有工具版本都要求这个字段 |
| 暂定印象 `tentative_understanding` | Agent 注意到用户连续两次跳过长解释，猜测其可能希望更短的反馈 | 带有依据和限制的暂定交互偏好；也可能暂不形成认知 | 用户已经明确要求以后只给短回答 |
| 方法与经验 `procedure_candidate` | 两次任务都在补齐配置字段后通过同一类校验 | 在特定条件下可复用的检查步骤或经验 | 一次相关结果就证明唯一因果关系，或直接生成无条件自动执行的脚本 |
| 纠正、替代与撤回 `correction` | 用户说：“不是不能动，可以慢慢移动，但不要闪烁。” | 修订已有偏好及其召回入口，而不是并列保留两个冲突结论 | 仅把纠正内容追加到历史里，旧结论仍作为有效默认值 |

实际载荷可以是以下几种形态。无论采用什么形态，都应保持来源和范围。

| 数据形态 | 示例 | 使用边界 |
|---|---|---|
| 短文本 | “用户明确要求当前项目游戏页不使用闪烁背景。” | 最小写入路径，不要求模型先建完整认知对象 |
| 结构化观察属性 | `{"error_code":"ASSET_KEY_MISSING","field":"tick_ms"}` | 字符串、数值、布尔值等承载一次观察；数值需说明单位、观测条件和来源 |
| 对象及版本引用 | 资源对象、Workspace、某次任务产物版本的 ObjectRef | 保存访问线索，不复制整套世界状态 |
| 来源片段或多模态证据引用 | 一条用户消息、工具结果、被评价图片的对象引用 | 大文件、图片和完整日志原则上仍作为外部对象；Memory 保存理解及必要引用 |
| 条件化结构或步骤 | “当资源类型为 X 且工具版本为 Y 时，先检查字段 Z。” | 通常由认知整理阶段形成；观察阶段只需写下发生的事情 |

当前时间、天气、任务进度和当前有效产物版本，首先属于动态世界状态。它们可能触发感知或为认知提供条件，但不能因为容易写入，就全部变成长期认知。密码、访问令牌等秘密也不应进入可召回的通用 Memory。

### 4.2 最小感知写入：模型只记一件事，Runtime 补齐出处

以下 `memory.*`、`objects.read` 均为**拟议的逻辑接口示意**，不是现有 OpenDAN SDK 的真实函数声明。示例中的 `agent:a1`、`user:u1`、`world:workspace:snake-alpha` 等是对象引用别名，不定义 DID / ObjectRef 的实际编码格式。

假设当前用户消息为：“这个贪吃蛇游戏页面以后用静态背景，不要闪烁。”模型可以只提交：

```python
memory.record_perception(
    content="用户要求当前贪吃蛇项目的游戏页面以后使用静态背景，不要闪烁。",
    object_refs=["world:workspace:snake-alpha"],
    suggested_kind="preference"
)
```

概念上，系统保存的记录可以是：

```json
{
  "ref": "memory:p-101",
  "layer": "perception",
  "content": "用户要求当前贪吃蛇项目的游戏页面以后使用静态背景，不要闪烁。",
  "suggested_kind": "preference",
  "agent_ref": "agent:a1",
  "subject_refs": ["user:u1"],
  "object_refs": ["world:workspace:snake-alpha"],
  "source": {
    "session_ref": "session:ui-web-01",
    "event_ref": "session:ui-web-01/event/31",
    "actor_kind": "user"
  },
  "observed_at": "2026-09-01T10:00:00+08:00",
  "state": "pending"
}
```

其中，Agent 身份、真实 Session、来源事件、时间和授权范围由执行环境补齐或核验；对象引用须能够解析且在授权范围内。`suggested_kind` 只是分类建议，允许省略，不等于已经形成 `preference` 认知。

`actor_kind=user` 只能说明来源事件确实来自用户，不能证明感知文本准确转述了原话。整理时仍需判断是否存在误读、范围扩大或从引用内容中误认指令的情况。Agent 自己的推测，应关联自己的观察或推理来源，不能伪装成用户明确表达。

这个调用的成功只表示**感知已被记录**，不表示认知已形成、Hint 已生成，或者其他 Session 已感知更新。同一来源事件重放时，可由 Runtime 提供稳定的去重键；一个事件确有多条不同感知时，不能只按事件 ID 去重而误删有效内容。

### 4.3 明确纠正与普通新观察，写入后的处理可以不同

普通观察可以等待后续整理；明确纠正则可能使正在使用的旧认知立刻失去适用性。例如用户说“不要再按静态背景处理”，系统不能在整理尚未完成的时间窗口里，仍把“必须静态”无提示地召回。

**派生约束与候选实现。** 可以先对能够定位的相关认知设置“待复核”状态，或者在召回前检查相关纠正事件，再由整理过程完成正式修订。采用何种方式待定；不能为了做完整认知分析而阻塞当前主任务，也不能把一次无关观察当作全库失效信号。

这项有效性要求，不等于默认把所有未整理感知都塞进上下文。新近感知快速路径是否开启，仍沿用 M-21 的待决边界。用户明确要求不记忆时，应先执行相应记录策略，不能先持久化再假定以后总能清理。

## 5. 认知层：跨 Session 整理与感知清理

### M-13｜Self Improvement 处理多个 Session 的新鲜感知

**明确方向。** 认知整理是一个独立于主任务的过程，可以由 Agent 的 self-input 机制触发。其输入包括来自多个 Session 的新鲜感知，以及整理时需要参考的既有认知；输出是 Agent 内部认知状态的更新。

Self-input 描述触发方式，Self Improvement 描述整理业务，两者不必被实现成唯一绑定关系，也不意味着所有自触发 Session 都只能做 Memory 整理。

### M-14｜整理可以新增，也必须能够修正

**明确方向与派生约束。** 整理不是简单把若干感知拼成一段摘要。它应能识别它们是否指向同一对象、是否重复或冲突，是否足以形成一种认知，以及是否需要修改既有理解。

至少需要覆盖：合并一致信息、保留必要分歧、限定结论范围、更新已有认知、撤回失效内容，以及认定某些感知不值得转化为长期认知。

原始材料不足以支持一个结论时，不应为了“清空感知池”而编造解释。可以暂缓形成认知，或只形成带有明确限制的认知。

### M-15｜认知提交成功后再清理感知

**明确方向。** 感知被成功整理后，应清理或删除被吸收的感知，留下认知，而不是长期同时积累一套完整感知库和一套完整认知库。

**派生约束。** 必须先使认知更新可靠生效，再清理对应感知。实现可以使用事务或等价机制，但不能出现“感知已删、认知未写”的丢失窗口。

```text
待整理感知
    ↓
选取一批材料并进行整理
    ↓
形成认知更新与本次已处理范围
    ↓
可靠提交认知
    ↓
清理已处理的感知内容
```

仅标记为已消费并无限保留全部感知正文，不应被当作默认完成清理。被吸收、不值得保留和仍需补充证据的材料，可以有不同处理结果，但必须有明确生命周期。

### M-16｜清理原材料与保留来源依据分开

**派生约束。** 删除感知正文，不必同时删除相关 Task 标识、原始事件引用或最小来源元数据。认知仍需具备支撑修正、冲突处理和任务回滚的来源关联。

来源引用应尽量指向真实 Session 事件、对象版本或其他授权材料，而不是只指向即将删除的临时感知记录。引用可追踪不等于永久保留全部原文；保留范围和时长需单独定义。

原始 Session 历史是否保留，由 Session / 数据保留策略决定，不能从“删除已整理感知”直接推导为“删除全部聊天历史”。来源已不可读取时，也不能继续声称结论仍有可复核的原文支持。

### M-17｜支持整理失败与并发恢复

**派生约束。** 多个 Session 可以同时产生感知，整理过程也可能失败或重试。因此需要保证：尚未处理的感知不被误删，同一批材料不会因并行整理产生相互覆盖的认知，重试不会无控制地复制结果。

认知更新应有可辨认的版本或等价的提交边界。采用单整理者、批次领取、版本检查或其他方式，留待实现设计。

整理频率、触发阈值、是否按 topic / 对象分批，以及如何处理长期不足以形成结论的感知，均是待决策略，不预设每次感知写入都会立即启动整理。

### 5.1 完整例子 A：两次感知形成一条有范围的偏好认知

以下例子承接 4.2。时间、标识和对象均为示例。

**输入变化：**

| 阶段 | 新增数据 | 当时的含义 |
|---|---|---|
| 初始 | 尚无相关认知 | 不能假设用户喜欢或不喜欢动画 |
| Session 1 | `p-101`：用户要求当前贪吃蛇游戏页面以后使用静态背景，不要闪烁 | 一条明确表达，仍处于待整理状态 |
| Session 2 | `p-102`：用户确认“静态版操作不受干扰，就保持这样；这是当前项目的要求，演示页另说” | 增补原因与适用边界，不是另一个全局偏好 |
| 整理 | 综合两条感知及其原始事件 | 形成一条认知，保留用户、项目、页面范围及来源 |

认知不是把两段话拼接成摘要，而是抽出可供未来工作使用的条件化理解。例如：

```json
{
  "ref": "memory:c-snake-background",
  "revision": 1,
  "layer": "cognition",
  "kind": "preference",
  "subject_refs": ["user:u1"],
  "scope": {
    "workspace_ref": "world:workspace:snake-alpha",
    "surface": "game_page"
  },
  "statement": "在该项目的游戏页面中，用户希望默认使用静态、不闪烁的背景，以免干扰操作。",
  "exceptions": [
    "不自动推广到演示页面",
    "不自动推广到其他项目"
  ],
  "basis": "user_statement",
  "state": "active",
  "evidence_refs": [
    "session:ui-web-01/event/31",
    "session:ui-telegram-01/event/12"
  ],
  "review_when": [
    "用户明确改变偏好",
    "拟将该认知应用于其他页面或项目"
  ]
}
```

这里没有要求“至少两次才可以形成认知”：一次清楚、有效授权下的明确表达，也可以形成窄范围认知。跨 Session 综合的价值，是补齐条件、发现一致性或冲突，而不是机械凑够样本数。

同一条认知可以有多个召回入口，例如“该用户 + 游戏背景”“该 Workspace + 效果修改”“闪烁 / 干扰操作”。入口只引用 `c-snake-background` 的有效版本，不各自复制一份偏好全文；具体是否存成 Hint 表仍不限定。

**提交后的存储变化：**

```text
整理前：
  p-101、p-102 = pending
  c-snake-background 不存在

可靠提交认知后：
  c-snake-background@1 = active
  本批次记录 p-101、p-102 已被吸收，关联到该认知

清理完成后：
  p-101、p-102 的感知正文被删除
  保留必要的批次 / 来源关联元数据
  认知的 evidence_refs 指向原始 Session 事件，而非已删除的感知正文
```

认知提交失败时，两条感知不能删除。清理失败时可以继续重试清理，但不能重复生成另一条相同认知。原始 Session 事件能否长期读取，仍由数据保留与访问策略决定。

### 5.2 完整例子 B：用户纠正后，认知修订而不是冲突堆叠

随后，用户在新的 UI Session 中说：

> 换一下默认效果：这个项目游戏页可以用缓慢移动的背景，但仍然不能闪烁。其他项目别受这个要求影响。

Session 先低成本写入 `p-103`，其来源是 `session:ui-web-02/event/8`。它可以提示与 `c-snake-background` 有关，但不要求主任务当场完成完整合并。

整理后的**逻辑变更示意**为：

```json
{
  "target_ref": "memory:c-snake-background",
  "expected_revision": 1,
  "new_revision": 2,
  "changes": {
    "statement": "在该项目游戏页面中，背景可缓慢移动，但不应闪烁或干扰操作。",
    "basis": "user_statement",
    "state": "active"
  },
  "unchanged": [
    "subject_refs",
    "scope",
    "exceptions"
  ],
  "added_evidence_refs": [
    "session:ui-web-02/event/8"
  ],
  "previous_revision_state": "superseded"
}
```

这不是规定数据库必须使用这种补丁格式，而是要求变更语义清楚：

| 数据 | 整理前 | 整理后 |
|---|---|---|
| 有效认知 | `c-snake-background@1`：默认静态 | 同一逻辑对象的 `@2`：允许缓慢移动，仍不得闪烁 |
| 旧版本 | 当前有效 | 被替代；只有历史审查明确需要时才读取 |
| `p-103` | 待整理纠正 | 成功吸收后清理正文 |
| 召回入口及摘要缓存 | 可能仍写“静态背景” | 更新或失效，不能继续无条件返回旧摘要 |
| 已运行 Session | 可能已读入 `@1` | 在下一次合适观察机会收到修订线索，不重新注入一遍所有认知 |

旧历史消息不一定能从已经形成的上下文里删除；至少要让 Session 明确知道旧结论已被替代。版本冲突时应重新读取再合并，不能让另一个整理者用旧结论覆盖 `@2`。多条互相矛盾的来源也不能简单按“最新时间戳获胜”；本例能够修订，是因为同一主体明确改变了同一范围内的要求。

### 5.3 完整例子 C：记住选择理由，但不接管“当前工作版本”

用户曾试做多个贪吃蛇项目版本。一次对话中，用户明确选择 alpha，理由是操作更稳定；后续某个试验任务又产生了更新时间更晚的 beta 产物。

| 层次 | 适合保存的数据 |
|---|---|
| 世界对象 | 项目的当前选定 Workspace、有效产物版本，以及各版本文件 |
| 原始感知 | “用户在这次比较中选了 alpha，理由是操作更稳定。” |
| 整理后认知 | 当时选择 alpha 的依据；用户更重视该场景下的操作稳定性；定位项目选择对象的线索 |
| 召回入口 | 用户说“刚刚那个贪吃蛇”时，提示存在历史选择及多个候选工作区 |
| 主动查询 | 读取项目选择对象，确认当前有效 Workspace；必要时再读取候选产物或向用户澄清 |

一条可能的认知是：

```json
{
  "ref": "memory:c-snake-choice",
  "revision": 1,
  "kind": "decision_context",
  "subject_refs": ["user:u1"],
  "scope": {
    "project_ref": "world:project:snake"
  },
  "statement": "用户曾在比较中选择 alpha，主要原因是游戏操作更稳定。",
  "state": "active",
  "basis": "user_statement",
  "evidence_refs": ["session:ui-web-01/event/22"],
  "related_object_refs": [
    "world:workspace:snake-alpha",
    "world:project:snake/selection"
  ],
  "use_condition": "用于理解历史选择；操作前需读取项目选择对象确认当前有效工作区。"
}
```

这里的 `active` 表示“这条历史选择及其理由尚未被撤回”，**不是**“alpha 仍是当前选中版本”。更新时间更晚的产物也不自动代表被采用。

如果世界对象随后显示当前选择已变为 beta，应以最新授权可读的选择状态作为工作基础。Memory 可以帮助理解为什么曾选择 alpha，也可以触发“是否发生了选择变化”的检查，但不能覆盖世界对象。尚无明确选择记录且存在多个候选时，不得仅凭记忆线索猜定目标。

### 5.4 完整例子 D：工具观察转化为有条件的经验

假设有一个测试用的效果资源校验工具。以下错误与处理过程仅为示例，不描述任何现有工具的真实行为。

```text
p-201（Task A 的工具观察）：
  effect-validator v1 对某类效果资源报 ASSET_KEY_MISSING，
  指向 tick_ms 字段。

p-202（Task A 的后续结果）：
  补齐 tick_ms 后，同一版本工具对该资源校验通过。

p-203（Task B 的独立观察）：
  同类型资源在同一工具版本下出现相同现象。
```

整理可以形成：

> 对于已观察到的这类资源及 `effect-validator v1`，遇到相同缺字段错误时，优先检查 `tick_ms`；工具版本或资源类型改变后，应先读取当前规范或重新验证。

这条认知可以建模为带条件的 `procedure_candidate` / 经验条目，来源是工具结果而非用户声明。召回入口包括工具标识、错误码、资源类型和当前任务对象；它只是检查建议，不直接获得自动修改文件的权限。

不应形成“所有效果都必须有 `tick_ms`”或“这个工具永远不兼容新格式”。一次成功还不能排除同时发生的其他修改；若无法隔离原因，应保留“优先检查”的经验表述，而不是宣称已证明唯一因果关系。

相反，“用户这次没有回复”或“一次查询偶然失败”通常不足以形成长期偏好或能力判断。此类感知可以暂缓整理、请求更多依据，或者按生命周期清理而不生成任何认知；不能为了清空感知池硬造结论。

### 5.5 完整例子 E：任务被放弃后，区分产物失效与经验保留

假设 Task `task-effect-11` 产生了闪烁背景，用户随后说：“这个结果不要了，回到之前的版本；但记住以后不要在游戏背景里采用这种效果。”

| 涉及数据 | 应发生的变化 |
|---|---|
| 该 Task 产物 | 由任务 / 世界状态系统处理放弃或回滚；Memory 不宣称自己已经完成产物回滚 |
| “工具成功生成闪烁效果”的感知 | 只能表示曾生成，不能表示结果被用户采纳；可在整理后清理 |
| 用户这次反馈 | 作为新的、可溯源的感知输入 |
| 基于用户明确反馈的边界认知 | 可以保留，因为用户在本例中明确要求记住经验 |
| 依赖该成果“当前有效”才能成立的认知 | 应失效或待复核，不能继续诱导后续任务使用弃用成果 |
| 仅提及“曾尝试过该效果”的历史经验 | 不能因同一 Task 被放弃就一律删除；应检查来源、授权和用户的真实意图 |

本例有“保留经验”的明确表达，不能据此确定所有任务回滚的默认 Memory 策略。用户另行要求“忘记这次经历”时，应转入 M-28 的遗忘语义，不得用“保留经验有价值”抵消其要求。

## 6. 召回与显露：帮助 Agent 意识到需要查询

### M-18｜在显式检索之前提供触发机会

**明确方向。** 召回机制不能只提供一个“模型已经知道要查时才调用”的搜索接口。它应根据当前问题、任务、对象和近期观察，获得发现潜在相关认知的机会。

典型目标是：Agent 在本次任务中尚未想到某个偏好或历史限制时，系统可以提供一条有根据的线索，使其进一步读取或调整行为。

这不是要求无依据地随机插入记忆，也不是要求所有 Memory 每次都完整加入 prompt。

### M-19｜线索与完整认知可以分层显露

**明确方向与派生约束。** 可以先显露小粒度 Hint、topic 或对象线索，再由 Agent 判断是否读取更多信息。线索应足以说明“为什么可能相关”，并能找到对应认知或来源对象。

```text
当前输入 / 任务对象 / 观察结果
                ↓
寻找可能相关的认知及触发入口
                ↓
筛选出有限的提示：内容摘要、适用范围、引用
                ↓
Agent 意识到需要关注
                ↓
按需读取认知或查询世界对象，再继续任务
```

Hint 是否独立持久化、由整理阶段生成还是运行时生成，仍未确定；Side Topic 可继续作为现有探索基础，但不被直接写死为唯一方案。

### M-20｜召回必须考虑范围、有效性与预算

**派生约束。** 相关性不能只看文字相似。对谁有效、针对哪个 Workspace、是否被用户纠正、是否对应被放弃版本，以及是否只是暂定推断，都会影响是否应该显露。

进入 context 的记忆应有明确预算。宁可提供少量可展开的线索，也不应把全部历史认知堆入每次模型输入，抵消 Task Session 短周期、上下文健康的设计目标。

同一条认知在同一阶段不应反复机械注入；进入新任务或新的相关情境后仍可再次召回。Memory 的重复控制不能简单照搬“某事件只通知一次”，否则一次使用后的重要认知可能永远不再出现。

### M-21｜根据 Session 类型选择召回时机

**明确方向与派生约束。** Task Session 应在启动装配时尽量获得必要认知，使任务随后稳定推进。UI Session 长期面对新话题与世界变化，需要在新输入及合适的观察机会持续获得相关线索。

这不禁止 Task 在遇到新对象、新约束或关键变化时重新召回，也不要求 UI 每一步都进行全量 Memory 检索。触发条件与成本预算需要按使用形态设计。

未经整理的感知如果在当前情境中被使用，必须以“新近观察 / 待确认材料”的身份显露，而非冒充成熟认知。是否默认允许这条快速路径，仍需评审。

### M-22｜被召回的内容不自动成为最高优先级指令

**派生约束。** Memory 可以影响理解和决策，但不能因为进入上下文就替代当前明确任务、有效授权或世界对象的真实状态。

外部文本进入感知或认知后，仍需保留其来源属性。不得通过“先写 Memory、再召回”的路径，把不可信内容升级为系统权限或可执行指令。

当 Memory 与用户当前明确表达或最新对象状态冲突时，应识别冲突，必要时查询、澄清或修正，不能静默坚持旧认知。

### 6.1 常见召回入口：先有触发机会，再决定是否检索和注入

“召回入口”不是只有一个关键词搜索框。它首先是 Session 运行中的一个机会点，由 Runtime / SDK 根据已知输入、对象和状态变化决定是否寻找认知线索，不要求 LLM 先意识到具体哪条记忆存在。

| 入口 | 谁发起、何时发生 | 可使用的上下文 | 应产生的线索及边界 |
|---|---|---|---|
| Task 启动装配 | Session Builder 构造 initial context 时 | 任务目标、用户、Workspace、工具和已有明确约束 | 尽量预装与本任务相关的偏好、经验和边界，避免执行中频繁补课 |
| UI 新输入 | Feedback Session 准备处理用户新消息时 | 当前输入、近期话题、已解析对象 | 用户只说“效果再活泼一点”，也有机会想起该项目“不闪烁”的要求 |
| Intent 分析 | 独立意图分析过程确定对象和任务边界时 | 候选项目、历史选择线索、待完成任务 | 提醒存在多个版本及历史选择；当前目标仍需读取世界对象确认 |
| 新对象或新话题 | 输入解析或工具结果首次涉及新对象时 | 新识别的人、项目、文件或工具引用 | 只补充与新增对象相关的认知，不因每个词变化而全库检索 |
| Action Result / Observation | 下一次正常推理前 | 工具标识、错误码、资源类型和结果摘要 | 出现已知错误模式时，显露带适用条件的经验 |
| 半订阅 Context Change | 正常观察机会收到状态增量时 | 任务被放弃、对象换版、认知被修订等 | 优先处理失效或修订，必要时重新召回；事件本身不必唤醒 Session |
| 多信道关联 | 当前信道缺少指代上下文时 | 同一授权主体、其他活动 UI Session 的可见 topic 或对象线索 | 提醒可能存在相关工作，再按权限查询；不复制另一个信道的完整对话 |
| 关键行动前的定向复核 | 即将提交、覆盖或执行具有副作用的操作时 | 当前目标、有效认知版本、已知变更 | 检查相关边界是否被纠正；Memory 不能替代权限检查和当前授权 |

Self Improvement 也会读取既有认知，但其目的主要是合并、冲突处理和修正，不应把这类内部读取混同于“给 UI 插入一条 Hint”。

每个入口可以先执行轻量的相关变化判断，再决定是否运行实际检索。不要将“每次 Observation 都有机会”实现成“每次都进行全量检索”。Side Topic 可以作为候选话题来源，Hint 可以作为输出线索，二者如何实现不在示例中固定。

### 6.2 自动召回的调用与返回示例

以下承接 5.2 中已经修订到 `revision=2` 的偏好。假设 Intent 分析已通过世界对象确定目标是 `snake-alpha`，用户说：“把这个贪吃蛇游戏背景再做得有动感一点。”

Runtime 可以在该机会点调用逻辑接口 `memory.recall(context)`，例如传入：

```json
{
  "trigger": "intent_analysis",
  "input_summary": "用户希望当前贪吃蛇项目的游戏背景更有动感。",
  "subject_refs": ["user:u1"],
  "object_refs": ["world:workspace:snake-alpha"],
  "topic_hints": ["游戏背景", "动效"],
  "phase": "planning",
  "budget": {
    "max_items": 3,
    "max_tokens": 600
  }
}
```

这里 `3` 和 `600` 只是展示预算参数的样例，不是已决定的性能指标或默认值。身份、授权、当前 Session 与去重进度由 Runtime 提供，不应要求模型手工声明访问权限。

一次可能的返回结果：

```json
{
  "status": "ok",
  "memory_snapshot": "memory-snapshot:21",
  "items": [
    {
      "cognition_ref": "memory:c-snake-background",
      "revision": 2,
      "summary": "该项目游戏页允许缓慢移动的背景，但不应闪烁或干扰操作。",
      "scope": {
        "workspace_ref": "world:workspace:snake-alpha",
        "surface": "game_page"
      },
      "why_recalled": [
        "匹配当前工作区",
        "当前意图涉及背景动效"
      ],
      "detail_read_recommended": true
    }
  ]
}
```

这条线索使 Agent 在尚未主动搜索“不闪烁偏好”之前意识到它。`detail_read_recommended` 是展开提示，不是另一条认知，也不要求所有场景无条件再查一次。

相同认知、相同版本、相同任务阶段不应机械重复注入；进入新任务或认知修订到新版本后，可以再次召回。去重进度应按接收 Session / 上下文阶段维护，不能由一个 Session 的使用把其他 Session 的召回机会全局消耗掉。可持久化该进度以支持 Runner 恢复，但它本身不是认知正文。

### 6.3 主动查询接口：检索、对象读取、主体视图和来源追踪

当 Agent 已经知道需要查询什么时，需要直接、可预期的读取能力，而不是只能等待自动召回。以下四种能力可以由少量逻辑接口承载，不要求四套独立存储或四种专用协议。

| 查询目的 | 拟议调用方式 | 返回内容 |
|---|---|---|
| 查相关认知 | `memory.query(query, filters, limit, cursor)` | 满足范围、状态和权限要求的认知引用、摘要、版本及匹配依据 |
| 读一条已知认知 | `objects.read(ref, view="cognition")` | 当前有效认知内容、适用范围、证据性质与版本 |
| 查看对某个主体的认知 | `memory.query(filters, view="by_subject")` | 按人物、项目或对象组织的认知视图；复用相同认知引用 |
| 查“为什么这样记” | `objects.read(ref, view="provenance")` | 当前结论依据、历史修订及可访问的原始来源引用 |

`objects.read` 表示既有 DID Object / 世界对象读取能力的逻辑用法。`view`、`select` 等参数表达所需能力，是否映射为对象字段、子对象或现有协议参数，需后续确定；本文不另外发明 Memory 专用 DID 协议。

#### 6.3.1 按问题和范围检索

例如，Intent 分析已意识到需要检查背景效果要求，可调用 `memory.query(...)`：

```json
{
  "query": "游戏背景效果的偏好和限制",
  "filters": {
    "subject_refs": ["user:u1"],
    "applies_to": {
      "workspace_ref": "world:workspace:snake-alpha",
      "surface": "game_page"
    },
    "kinds": ["preference", "boundary"],
    "states": ["active"]
  },
  "include_recent_perceptions": false,
  "limit": 5
}
```

一种返回示例：

```json
{
  "status": "ok",
  "memory_snapshot": "memory-snapshot:21",
  "items": [
    {
      "ref": "memory:c-snake-background",
      "revision": 2,
      "kind": "preference",
      "summary": "该项目游戏页允许缓慢移动背景，但不应闪烁或干扰操作。",
      "basis": "user_statement",
      "match_reason": "主体、项目与页面范围匹配"
    }
  ],
  "next_cursor": null
}
```

`applies_to` 表达“对这个情境有效”，不只是匹配一段相似文字。如何纳入更广范围且确实适用的认知，需要定义明确的范围匹配策略；不能为提高召回率而自动混入其他项目的偏好。

此例关闭了未整理感知读取，不意味着全系统默认值已确定。若启用快速路径，结果应分开返回 `cognitions` 与 `recent_perceptions`，后者明确标注“未整理 / 待确认”，不能混装成同一批有效认知。

#### 6.3.2 读取已知认知，不再依赖搜索排序

拿到认知引用后，可以使用通用对象读取：

```python
objects.read(
    ref="memory:c-snake-background",
    view="cognition",
    select=["ref", "revision", "statement", "scope", "state", "basis", "evidence_refs"]
)
```

投影后的内容示例：

```json
{
  "ref": "memory:c-snake-background",
  "revision": 2,
  "statement": "在该项目游戏页面中，背景可缓慢移动，但不应闪烁或干扰操作。",
  "scope": {
    "workspace_ref": "world:workspace:snake-alpha",
    "surface": "game_page"
  },
  "state": "active",
  "basis": "user_statement",
  "evidence_refs": [
    "session:ui-web-01/event/31",
    "session:ui-telegram-01/event/12",
    "session:ui-web-02/event/8"
  ]
}
```

不指定历史版本时，示例读取的是当前可用版本；若系统支持快照或固定版本读取，应显式说明。旧 Hint 指向 `@1`、对象已更新为 `@2` 时，返回方应让调用方识别差异，不能把历史内容伪装成当前结果。

历史来源参与形成过程，不代表每条来源都同样支持当前表述。哪些依据已被明确纠正，可以通过下一节的来源视图进一步判断。

#### 6.3.3 对象中心查询：形成视图，而不是复制一份“人物档案”

用户问“你记得我对这个项目有什么要求吗”，可按主体与项目查询，不需要事先知道关键词：

```python
memory.query(
    filters={
        "subject_refs": ["user:u1"],
        "applies_to": {"workspace_ref": "world:workspace:snake-alpha"},
        "states": ["active"]
    },
    view="by_subject",
    limit=20
)
```

视图应将偏好、边界、相关经验分别展示，并带上适用范围及认知引用。例如“游戏页背景不闪烁”仍指向 `c-snake-background@2`，不产生另一个独立维护、容易与原认知不一致的“用户画像文本”。

查询某人时不能仅按同名合并身份；查询某项目时也不能把它的要求提升为用户在所有项目中的偏好。跨信道是否可见，由授权主体和可见范围决定，而不是由视图类型决定。

#### 6.3.4 来源和修订查询：回答“你为什么这样认为”

例如：

```python
objects.read(
    ref="memory:c-snake-background",
    view="provenance"
)
```

返回应能表达当前依据与历史依据的不同角色，例如：

```json
{
  "ref": "memory:c-snake-background",
  "revision": 2,
  "current_basis": [
    {
      "event_ref": "session:ui-web-02/event/8",
      "role": "explicit_correction",
      "source_availability": "available",
      "excerpt": "这个项目游戏页可以用缓慢移动的背景，但仍然不能闪烁。"
    }
  ],
  "historical_basis": [
    {
      "event_ref": "session:ui-web-01/event/31",
      "role": "previous_preference",
      "source_availability": "available"
    },
    {
      "event_ref": "session:ui-telegram-01/event/12",
      "role": "scope_clarification",
      "source_availability": "available"
    }
  ],
  "previous_revision": 1,
  "previous_revision_state": "superseded"
}
```

感知正文已被清理，不影响该示例通过保留的原始 Session 事件追溯。但如果原始历史也已清除，应明确返回来源不可读取，不凭空生成“原话”；若无读取权限，则按访问控制返回受限信息，不通过来源摘要泄露内容。

是否保留完整认知版本历史及其保留期限，仍需制定策略。示例展示的是可解释修订所需的信息，不要求永久保存所有感知或全部历史。

### 6.4 查询契约中的常见边界

**派生约束。** 示例接口至少需要区分以下情况；具体错误码和返回格式未固定。

| 情况 | 应表达的结果 |
|---|---|
| 正常查询但未命中 | 可以返回空列表，但不能声称“这个人没有此类偏好”或“Agent 从未经历过此事” |
| 存储不可用、索引未就绪或仅部分可查 | 明确返回不可用或结果不完整，不能伪装成正常空列表 |
| 返回条数受限 | 表达截断或分页信息；多页读取应有一致的结果边界，不悄悄混用不同状态 |
| 对象不存在或当前调用者不可见 | 遵循既有对象协议的访问语义，不泄露未授权对象是否存在 |
| 旧认知已被明确纠正、整理尚未完成 | 标明待复核，或从有效结果中排除并提示有相关修订待处理；不能返回无提示的旧结论 |
| 读取的认知依赖一个世界事实 | 返回引用和适用条件；当前文件版本、选择状态等仍应通过世界对象读取 |
| 搜索命中来自不可信输入的指令性文本 | 保留证据性质，不把它变成系统指令或授权 |
| 来源已不可读 | 如实表示不能复核原文，不把认知摘要当作原始证据 |

例如，4.3 的纠正正在处理时，对相关认知的查询可以返回“待复核”提示，或者返回带该状态的条目；未经整理感知的普通快速路径是否开启，不影响旧结论必须受到有效性约束。

检索、对象读取、主体视图和来源视图都应先执行授权过滤。仅在读取全文时检查权限是不够的，因为摘要、Hint、主体关联和“存在一条相关认知”的提示也可能泄露信息。

### 6.5 贯穿示例：从“没想到要查”到正确构造新任务

```text
用户在 UI Session 中说：
  “把刚刚的贪吃蛇背景做得更有动感。”

UI / Intent 的机会式召回：
  发现有多个候选工作区，以及一条历史选择线索。
  若相关线索不可见或证据不足，不猜定目标。

Intent 主动读取世界对象：
  读取项目 selection，确认当前工作区是 snake-alpha。
  不是根据“哪个 Session 最新”来决定目标。

针对已确认对象再次匹配认知：
  显露 c-snake-background@2：
  “允许缓慢移动，但不要闪烁或干扰操作。”

按需读取认知：
  确认该要求仅适用于该项目游戏页，
  不把已被替代的“必须静态”当作现行要求。

构造新的 Task Session：
  目标 = 增加背景动感。
  边界 = 不闪烁、不干扰操作。
  工作基础 = 世界对象确认的当前有效产物版本。

Task 执行及后续反馈：
  工具成功不等于用户认可；
  新的观察先写感知，用户反馈再参与后续认知整理。
```

这个流程不要求每一步都调用一次 LLM，也不要求 UI 承担深入调查。SDK 可以复用已经获得的对象状态和有效认知，Intent 过程负责必要探索，Task 则尽量带着充分上下文启动。新消息本身有明确约束时也应直接纳入任务，不能因为尚未进入长期 Memory 就忽略它。

## 7. 共享状态与访问控制

### M-23｜Memory 属于 Agent，不属于某个 Runner

**明确方向。** 同一 Agent 的不同 Session 即使运行在不同进程、不同语言的环境中，也应能够经授权共享持久 Memory。其连续性不依赖某个容器永远在线。

把 Memory 类比为 RDB，是强调共享持久状态及相应访问语义，不是要求所有 Runner 直接拿到数据库账号，更不是假定无协调并发写入天然安全。

### M-24｜跨进程读写遵循兼容约定

**派生约束。** 多个 Runner 的感知写入应可合并而不互相覆盖；认知整理产生的更新应有可识别的提交状态；读取方不应看到被误当成完整认知的半成品。

状态结构和对象接口需要支持必要的版本兼容。旧 Runner 面对无法理解的新结构，应明确报错或通过兼容层读取，不能静默丢弃字段并覆盖原认知。

不同 Session 何时看到新认知、是否采用快照读取以及如何收到失效通知，需要定义一致性规则。本文不预设所有读取都要求强一致，但“已经更新”与“所有 Session 已感知更新”必须可以区分。

### M-25｜共享不突破主体与信道边界

**派生约束。** 不同 Agent 的 Memory 默认不因共用存储而混合；某个 Agent 暴露给另一个 Agent 的对象范围，应受授权控制。

同一 Agent 服务多个用户或群组时，内部认知也可能具有不同可见范围。跨信道共享的线索、摘要和缓存均需遵循相同边界，不能只在读取完整正文时检查权限。

对人的印象、偏好等信息应尽量有明确主体引用；仅凭同名或相似文本，不应把不同人的认知合并。

## 8. 修正、任务放弃与记忆失效

### M-26｜区分任务经历与有效成果

**派生约束。** Memory 写入可能早于 Task 完成，任务之后也可能失败、被放弃或被回滚。感知和认知必须能够关联这些后续状态。

“某任务尝试过方案 A”与“方案 A 是当前采用方案”是不同信息。任务被否定后，后者不能继续作为有效认知使用；前者是否保留为经验，需要由策略决定。

### M-27｜任务结果失效时能定位受影响的 Memory

**派生约束。** Session 与产物版本关联应支持检查哪些感知、认知及召回入口依赖该任务结果。当一个结果被撤销时，应能对这些内容进行失效、重新判断或索引更新。

跨 Session 整理后的认知可能同时依赖多个来源，不能简单删除其中一个来源就断言整个结论必然消失，也不能因为存在其他来源就无条件保留原结论。需要重新评估剩余依据和适用范围。

这要求必要的来源关联，但不预先承诺能够精确计算一切模型推断的因果贡献。

### M-28｜不混同放弃产物、撤销认知与明确遗忘

**明确方向。** UI Session 应知道用户已放弃某次工作，后续不能继续以该成果为基础。

**待决设计。** 以下语义必须分别定义，不能由实现自行视为同一操作：

| 用户意图 | 必须进一步确定的处理范围 |
|---|---|
| 不采用这次任务结果 | 成果失效后，是否仍允许保留尝试过程及失败经验 |
| 把这次工作当作没发生过 | 除受管产物外，是否撤销相关感知、认知和召回入口；哪些最小生命周期信息仍需保留 |
| 忘记这条信息或这段经历 | 原始材料、派生认知、索引、缓存及其他受控副本各自如何处理 |

在默认策略确定前，不宣称 Task rollback 已自动清除了所有相关 Memory。

### M-29｜支持明确纠正与范围调整

**派生约束。** 当用户说明“那只是对这个项目的要求”或明确否定一条已有认知时，系统应能够缩小范围、撤回或替换，而不是保留原认知并新增一条同等有效的反向内容。

修正后，相应召回入口和缓存也应更新。旧消息或旧事件重放，不应无判断地重新恢复已撤销的认知；具体如何记录撤销依据与处理优先级，留待设计。

对明确遗忘的实现，只能承诺系统可控制的数据范围，不应将删除本地索引表述为已经删除所有外部源或外部副本。

## 9. 与 Session SDK、世界对象和半订阅的接合

### 9.1 三种连续性分别承担

| 连续性 | 承载机制 | 典型问题 |
|---|---|---|
| 一次执行的连续性 | Session 持久状态与 Runner 恢复 | 这个任务执行到哪一步了？ |
| 工作产物的连续性 | Workspace / 文件 / 世界对象的有效版本 | 下一次改进应基于哪个成果？ |
| Agent 内部认知的连续性 | Agent Memory | 过去有什么偏好、经验或边界值得想起来？ |

三者相互引用，不应互相替代。使用 Memory 不能免除读取真实产物，使用共享 Workspace 也不能自动替代对用户偏好与经验的理解。

### 9.2 与实时变化感知的互补关系

Memory 主要帮助 Agent 想起过去形成的认知；半订阅主要让 Session 意识到当前世界发生的变化。两者共同帮助发现原本没有意识到需要查询的事项，但不能合并成同一种数据语义。

例如，“某 Task 已被放弃”首先是生命周期变化；它可能使某个认知失效，也可能在后续整理中形成新的经验，但不是事件到达时就已经完成认知更新。

同理，认知完成更新后，也可以经既有的变化机制让相关活动 Session 得到简短提示；是否立即唤醒，应遵循主动 / 半订阅策略，而不是一律启动推理。

### 9.3 双文档共享的逻辑契约

| 契约 | Memory 一侧提供什么 | Session SDK 一侧提供什么 |
|---|---|---|
| 身份与授权 | 按 Agent 和可见范围组织读写 | 当前 Agent、执行主体及授权上下文 |
| 感知来源 | 可追溯的轻量观察记录 | Session / 输入 / 动作及目标对象引用 |
| 认知召回 | 有范围、有效性和来源的有限线索 | 当前任务、topic、观察机会与上下文预算 |
| 整理执行 | 跨 Session 输入、认知提交与感知清理 | 可独立运行的自维护执行环境 |
| 任务失效 | 受影响认知的定位与处理能力 | 完成、放弃、回滚及产物版本状态 |
| 变化通知 | 认知更新 / 失效的简要变化 | 主动 / 半订阅及去重、合并、注入机制 |

上述为逻辑信息要求，不强制某套字段名称，也不要求所有关联都由模型填入。

## 10. 可验收场景

以下为需求验收场景，不表示已完成实现或测试。

| 编号 | 场景 | 通过条件 |
|---|---|---|
| B-01 | 应用没有手工编排记忆步骤 | 默认 Agent Session 仍能产生符合策略的感知；不要求调用方逐条创建 Hint。 |
| B-02 | 同一 Agent 的 Session 跨进程执行 | 共享持久 Memory；Runner 变化不造成内部认知从零开始。 |
| B-03 | 主任务中出现暂定观察 | 能低成本写入；不为写感知强制启动重型整理；暂定观察不立即被包装成事实。 |
| B-04 | 多个 Session 产生相关感知 | 整理能形成或修订认知，并保留适用范围和必要来源；不只是拼接摘要。 |
| B-05 | 两条感知存在冲突 | 能识别冲突或保留不确定性，不静默选一条冒充已确认结论。 |
| B-06 | 整理成功后清理材料 | 认知已可靠提交；已吸收的感知正文按规则清理；必要来源关联仍可用于修正。 |
| B-07 | 整理中途失败、重试或并发运行 | 不丢失尚未处理的材料，不产生无控制的重复认知，也不覆盖其他合法更新。 |
| B-08 | Agent 未主动想到相关偏好 | 当前情境能触发有限提示，再按需读取，而非只有显式搜索后才能使用记忆。 |
| B-09 | 同一认知只适用于特定项目 | 在无关任务中不被机械注入；改变适用范围后，召回行为相应变化。 |
| B-10 | 某个 Task 的结果被用户放弃 | 不能继续把该结果当作当前采用方案；可定位相关感知、认知及触发入口。 |
| B-11 | 世界对象版本发生变化 | Memory 中的缓存或判断不会自动覆盖最新世界事实；必要时查询并修正。 |
| B-12 | 用户明确纠正既有认知 | 原结论被修订、缩小范围或撤回；相关索引和缓存不继续无条件召回旧结论。 |
| B-13 | 多用户 / 多信道共用一个 Agent | 未获授权的 Session 不通过 Hint、摘要或缓存看到其他范围的记忆。 |
| B-14 | 感知包含外部指令性文本 | 内容仍按来源属性处理，不通过记忆召回获得系统权限。 |

### 10.1 原型阶段的评估重点

原型不能只证明“写入成功、搜索命中”。还应使用带有后续任务的样例，评估是否记住了真正影响工作的信息、是否在 Agent 没想到查询时提供了有用提示，以及是否因误召回而污染任务。

建议观察感知写入的额外成本、遗漏与噪声、认知范围是否准确、纠正是否生效、每次注入的上下文占用，以及整理失败后的数据完整性。样例需要包括没有值得记忆的内容、偏好仅限单个项目、任务被否定和多来源互相矛盾的情况。

具体数值门槛应根据原型基线确定，本版不凭空给出统一准确率或延迟指标。

### 10.2 新增示例对应的验收场景

这些场景检验的是行为与数据变化，不要求原型照抄示例字段名。

| 编号 | 对应例子 | 通过条件 |
|---|---|---|
| B-15 | 4.1—4.2：不同写入类型 | 短文本、结构化观察和对象引用可进入轻量写入路径；来源可区分；工具成功不被自动升级为用户认可。 |
| B-16 | 5.1：跨信道形成同一偏好 | 在同一授权主体及允许共享的范围内形成一条有项目边界的认知，不为每个信道复制冲突偏好。 |
| B-17 | 5.1：多入口与清理 | 不同入口能指向同一认知；可靠提交后清理感知正文；来源引用不只指向被删除的临时记录。 |
| B-18 | 5.2：明确纠正 | 旧版本不再作为当前有效结论；修订前的窗口也不静默召回旧结论；新版本可以再次进入相关 Session。 |
| B-19 | 5.3：选择理由与当前版本 | 能想起选择线索，并读取世界对象确认当前目标；不按产物更新时间或最近 Session 猜定当前版本。 |
| B-20 | 5.4：带条件的经验 | 相同工具版本及错误条件可触发线索；范围变化时要求重新检查；弱观察不被强行整理为长期事实。 |
| B-21 | 5.5：放弃结果但明确保留经验 | 不再使用弃用成果；有独立依据且用户要求保留的经验仍可有效；不声称所有回滚默认采用此策略。 |
| B-22 | 6.1—6.2：机会式召回与去重 | LLM 未显式发起查询也能收到相关线索；不因每个 Observation 全库扫描；一个 Session 的消费不影响其他 Session。 |
| B-23 | 6.3：主动查询与可解释性 | 能按条件检索、按引用读取、按主体组织和追踪来源；各入口引用相同有效认知；不存在来源时明确说明。 |
| B-24 | 6.4：空结果、故障与权限 | 空结果和不可用可区分；摘要及来源视图均执行授权；不通过“相关记忆存在”的提示泄露受限信息。 |
| B-25 | 6.5：端到端新任务 | 正确选择工作对象，装配有效认知，创建有边界的新 Task，不依赖继续旧 Task 的消息流。 |

## 11. 待决设计

| 主题 | 已明确的要求 | 尚需确定的内容 |
|---|---|---|
| 认知基本模型 | 能表达人物、偏好、边界、经验及适用范围 | Hint List、对象中心、关系结构或混合模型；最小认知单元是什么 |
| Hint 的地位 | 支持在未显式搜索前提供线索 | 是认知本体、独立索引，还是运行时派生提示 |
| 感知写入触发 | 低成本，不要求主任务深度反思 | 通用提示词、观察机会、去噪方式及漏记 / 误记的评估方法 |
| 整理策略 | 跨 Session 加工，成功后清理材料 | 调度方式、批次范围、暂缓条件和长期未处理材料的生命周期 |
| 认知修正 | 可更新、限定范围、撤回，不能只追加 | 冲突处理规则、证据要求与时效策略 |
| 新近感知快速使用 | 不得冒充已形成的认知 | 是否提供默认快速路径、如何与整理后召回区分 |
| 召回机会与预算 | Task 启动充分装配，UI 持续获得线索 | Side Topic / Hint 的配合方式、注入频率及排序 / 去重策略 |
| 任务放弃与遗忘 | 能关联来源，不能把产物回滚等同认知清除 | 默认保留失败经验与否，显式遗忘覆盖的受控数据范围 |
| 数据承载与授权 | 跨进程共享，支持受控 DID Object 访问 | 存储结构、并发提交、接口粒度、版本兼容与缓存失效 |
| 示例字段与查询接口 | 轻量写入、自动召回、主动查询和通用对象读取应能够衔接 | 最终语义类型、ObjectRef 表达、接口签名、视图映射、分页及一致性策略 |

下一阶段应优先通过具体场景检验认知模型，再确定存储和索引。不能因为 Hint-based recall 已有实现路径，就跳过“何时写入、写成什么、如何修正”的需求。

## 12. 本版非目标

本版不要求模拟完整的人脑机制，不把人物印象固化为不可修正的标签，不要求保存所有对话，不把聊天摘要直接等同于认知，也不强制使用向量数据库、知识图谱或 Notebook 作为唯一结构。

**最终目标是让 Agent 在不显著干扰当前任务的前提下，把值得保留的经历转化为可修正的跨 Session 认知，并在未来尚未想到查询时，获得恰当的提醒。**
