## 1. 文档定位与核心问题

本文定义 Agent Memory 的认知管理需求。核心机制并不复杂：Session 低成本记录感知，Memory 整理 Goal 把感知整理成可修正的认知，召回在合适的时机把线索交给 Agent。难点在于**怎么用**：什么值得成为记忆、如何低成本写入、如何形成跨 Session 认知、如何在合适的时候让 Agent 想起它，以及哪些信息即使方便也不该放进 Memory。使用边界集中在 §2，后续章节都以它为前提。

本文是 Agent Memory 模块重构的依据。`Agent元能力/` 下的旧设计文档（Memory v2、Attention Signal、Notebook、Self-Check、Self-Improve、浮现 Hints）只作参考：其中仍适用的设计和失败教训已经吸收进本文，旧设计当时也只实现了一部分。与本文冲突时以本文为准。

**确定性标记。** 全文沿用关联文档的标记：**明确方向**是已经讨论确定的方向；**派生约束**是使这些方向可靠成立所需的工程要求或判断基线；**待决设计**是尚未确定的模型与策略。标为**示例**的内容是说明用的虚构数据，人物、时间、对象和观测结果都不真实；字段、状态名和接口名也不是现有实现、最终 Schema 或已定 SDK API。本文不声称相关能力已经实现。各需求的实施阶段见 §10.5，版本变化见 §13。组件的接口与数据模型见附录 A（继承旧 Memory Graph v2.10 规格并按本文调整），实现现状与给 code agent 的调整清单见附录 B。

**术语。**

- **半订阅**：记录待感知变化但不单独唤醒 Session，在下一次已有推理前装配。定义见《SDK 化核心需求》S-15、S-16。
- **topic**：Session 当前的工作主题及相关主体、对象范围，用来匹配召回和半订阅变化，对应架构文档中的动态 Topic。形态是一行标题加一组有上限的 tag，维护规则见 §6.6。早期稿中的“Side Topic”在仓库中没有对应设计，本版统一称 topic。
- **Hint**：召回时显露给 Agent 的短线索，指向一条认知或感知，不是另一份认知。
- **Task 修订**：执行期间由授权方追加到 Task 对象上的修改，属于任务数据，不是 Memory，见 §9.4。


### 1.1 为什么应用要使用 Agent，而不只是 LLM Context

用户或应用选择以 Agent 身份执行一次工作，一个重要预期是：此次经历可能被这个 Agent 记住，并影响之后的工作。

调用方不希望逐条管理“记住多少、什么时候记、如何整理”。只要通用 Memory 机制默认开启，不同进程、不同 Runtime 中运行的同一 Agent 的 Session，就应通过共享的持久状态获得跨 Session 连续性。

### 1.2 Memory 的核心问题

> **Agent Memory 不仅要支持“知道要查什么时能够查到”，更要帮助 Agent 发现“自己原本不知道应该去查什么”。**

当 Agent 已经明确意识到需要查询某个对象或事实时，可以使用 DID Object、搜索或其他工具。Memory 更关键的作用是，在当前情境中提供线索，使 Agent 意识到某个既有经验、偏好、边界或判断可能相关。

这里并不是要求 Memory 创造从未获得的信息，而是让已经形成的内部状态，在 Agent 尚未主动想到它时，有机会进入当前推理。

### 1.3 核心处理链

```text
不同 Session 中的任务、对话与观察
                 ↓
       低成本记录感知 Perception
                 ↓
   跨 Session 整理 / Memory 整理 Goal
                 ↓
       形成可修正的认知 Cognition
                 ↓
  依据当前情境触发线索、按需读取与使用
                 ↓
        新的经历继续形成新的感知
```

成功整理后的感知应被清理，留下认知。历史消息与工作产物可以是来源，但不因参与这个循环就全部等同于 Memory。

本文将新架构的 UI、Work、Goal 作为 Memory 的使用方。旧文中的 Task Session 对应执行 Task 的 Work Session；Self Improvement 表示整理等自维护业务用途，不再要求专用 Session 类型。Runtime 提供运行机会，Memory 整理 Goal 在预算内处理材料。

## 2. 使用边界：Memory 存什么、谁来写、怎么用

### M-01｜继续使用 Agent Memory 作为统一概念

**明确方向。** 所有 Agent 认为值得保存并跨 Session 使用的内部状态，统一称为 Agent Memory。新设计取消独立 Agent Notebook；感知和认知由同一组件承载写入、召回及修订，Hint 是显露线索的机制。旧 Notebook 中有用的实现可按需迁入 Memory，不保留独立的用户笔记库或另一条记忆写入路径。

用户说“你记一下”时，同样记录带来源、范围和明确记忆意图的感知，持久化成功后才确认。明确表达一次即可作为形成窄范围认知的依据；无需用户理解跨 Session 管理。要求保存可查看、编辑的原文笔记时，产物属于文档等世界对象，Memory 可保存其相关线索。

本文重点是这些内部状态中的认知管理。锁、订阅消费进度、执行租约等运行元数据可以与其共用存储设施，但不因此自动成为需要供模型召回的认知条目。

### M-02｜区分内部认知与独立世界对象

**明确方向。** Agent 的内部状态属于 Memory；独立存在的文件、产品版本、Workspace、业务对象等属于世界状态，由 DID Object / 世界对象协议等机制访问。

Agent Memory 不应重新成为所有外部对象的一套特殊事实库。它可以保存对世界对象的理解、使用偏好、选择依据、经验或访问线索；对象本身仍有独立的身份、状态与有效版本。

例如，在贪吃蛇工作场景中：

| 内容 | 主要归属 |
|---|---|
| 贪吃蛇源码、效果资源、产物版本 | Workspace / 世界对象 |
| 某次修改的输入、工具结果与执行状态 | 对应的 Work Session |
| 用户为何放弃某种方案、在特定范围内采用什么偏好 | 可进入 Agent Memory 的感知或认知 |
| 当前有效版本是哪一个 | 以世界状态为事实依据；Memory 可以保存相关选择线索，但不能无视后续变更 |

**派生约束。** 允许缓存必要的外部事实，但必须能分辨其来源、时间和适用范围。缓存是缓存，认知判断是判断，不能因被写入 Memory 就变成永久有效的世界事实。

### M-03｜统一访问协议，不特殊化访问方式

**明确方向。** Agent 具有 DID。它愿意开放的内部状态，可以通过与其他对象相同的 DID Object 协议被读取，不需要仅因名称叫 Memory 就发明一套完全不同的读取体系。

**派生约束。** 内部 / 外部是语义归属，是否可访问是授权问题。Memory 经授权对外开放，并不会因此失去内部认知属性；使用统一协议也不意味着整个 Memory 默认公开。

映射到对象协议时，认知的每个 revision 是不可变对象，认知的逻辑 ID 是指向当前 revision 的可变入口：读取逻辑 ID 得到当前有效版本，读取 revision 得到固定内容。感知是待整理的临时材料，正文整理后会被清理，默认不作为 DID Object 对外暴露；需要引用证据时，指向原始 Session 事件或对象版本（M-16）。

### 2.1 Memory 像全局变量：好用，所以容易被滥用

认知对同一 Agent 的所有 Session 可见，任何 Session 都能写入感知，召回又会在没人点名时把内容送进上下文。这和程序里的全局变量很像：哪里都能读、哪里都能写，方便到让人什么都想往里放。全局变量的老问题，在 Memory 里一个不少：

| 全局变量的问题 | 在 Memory 中的表现 |
|---|---|
| 远距作用 | 一个 Session 写下的内容，悄悄改变了另一个不相关 Session 的行为 |
| 隐式耦合 | 某个流程要正确运行，暗中依赖某条记忆恰好被召回 |
| 状态陈旧 | 记下的“当前版本”“当前进度”已经变了，Memory 里还是旧值 |
| 所有权不清 | 一条内容错了，不知道该由谁修正、以什么为准 |
| 越用越宽 | 为了“省得以后再说”，把局部判断写成对所有任务都生效的规则 |

因此本文给 Memory 划定一个窄用途：**Memory 让 Agent 带着过去形成的理解做判断，不负责让系统正确运行。** 下面 M-30—M-34 是使用边界，所有使用方和后续设计都应遵守。

### M-30｜Memory 是尽力而为的线索，不承载正确性

**明确方向。** 召回受范围匹配、预算、排序和整理进度影响，任何一条记忆都可能这次没被想起。因此，凡是“没被召回就会出错”的信息，都不能只放在 Memory 里，必须由正式对象或交付链路承载：任务书和 Task 修订、授权、Goal 定义与状态、Final Report、世界对象的当前版本，以及消息。

判断方法是**可丢失性测试**：假设这条内容这次没被召回，系统是变得**不够聪明**（可以放进 Memory），还是变得**不正确**（不能只靠 Memory）？

### M-31｜Memory 不是 Session 之间的通信通道

**明确方向。** Session 之间传递任务、修改、结果和请求，走 Task 对象、Task 修订、Final Report、Goal 状态和消息等正式路径。运行中 Work 的目标修改写为 Task 修订，由 Work 对自身 Task 对象的半订阅送达（§9.4），不写成感知。

Memory 可以从这些交流中**另外**记录有长期价值的观察，例如用户在修改中顺带说的“以后都……”。这时写的是一条独立感知，与修订本身是否送达无关。

### M-32｜感知谁都能写，认知只有整理者能改

**明确方向。** 授权 Session 只能追加感知，不能直接新增、修改或撤回认知。认知只能由 Memory 整理 Goal 通过可靠提交来变更（M-15、M-17）。

这样，“谁都能写”被限制在只追加、带来源的感知层，每条认知都只有一条修改路径和可追溯的依据。用户纠正等需要尽快生效的情况，由写入方记录纠正感知，召回层据此派生“待复核”显示（§4.3），普通 Session 不需要直接改认知。明确遗忘、授权变更等管理操作由 Memory 组件按授权执行，语义见 M-28，不算认知写入。

### M-33｜只有模型读 Memory 做判断，程序逻辑不以 Memory 为条件

**明确方向。** Runtime、SDK、工具和应用代码读取 Memory，只能是为了服务 Memory 本身：写入、匹配、召回、注入、整理和清理。它们不能以“Memory 里有没有某条内容”作为业务分支、配置来源或权限依据。认知影响的是模型的理解和判断，而模型仍要服从当前任务、授权与世界状态（M-22）。

同理，应用不应把 Memory 当作自己的键值存储。应用的配置、状态和数据放在应用自己的存储或世界对象里。

### M-34｜范围默认最窄，扩大范围要有证据

**明确方向。** 感知和认知的适用范围，默认取证据直接支持的最窄范围：这个用户、这个项目、这个页面、这个工具版本。只有来源明确表达了更宽的范围（例如用户说“所有项目都这样”），才能形成更宽范围的认知；推断出的认知不能扩大到 Agent 全局。范围越宽的认知越像全局变量，越需要明确依据和复核条件（§5.7）。

### 2.2 信息去处对照

下表列出最常被误放进 Memory 的信息。左列内容可以**触发**一条感知（例如从中观察到了偏好），但内容本身由中间列承载。

| 信息 | 由谁承载 | Memory 可以保留什么 |
|---|---|---|
| 任务书、运行中的目标修改 | Task 对象及 Task 修订（§9.4） | 修改中顺带表达的长期偏好 |
| 任务进度、Goal 等待状态、预算余量 | Session 状态、Goal 状态 | 不保留；每轮恢复不重新写感知 |
| 执行结果、交付摘要 | Final Report | 从结果中得到的可复用经验 |
| 当前有效版本、当前选择、文件内容 | 世界对象（Workspace、项目 selection 等） | 当时的选择理由，去查哪个对象的线索 |
| 用户要保存、查看、编辑的笔记或原文 | 文档等世界对象 | 文档的关联线索 |
| 操作手册、Skill、XLLM 配置 | 能力资产，由对应的结晶 Goal 维护 | 作为结晶输入的经验候选 |
| 应用配置与应用状态 | 应用自己的存储 | 不保留（M-33） |
| 执行日志、工具完整输出 | Session 历史与工作记录 | 关键观察、条件和来源引用 |
| 锁、订阅进度、执行租约 | 运行元数据，可共用存储设施 | 不作为可召回内容 |
| 密码、令牌等秘密 | 凭据管理 | 不进入可召回的 Memory |
| 时间、天气、在线状态等实时信息 | 世界状态与半订阅 | 满足 §5.7 的长期观察 |

### 2.3 常见误判

以下误判在写入、整理和使用三个环节都会出现。其他章节用编号引用，不再逐处重复。

| 编号 | 误判 | 正确理解 |
|---|---|---|
| E-01 | 一次观察 → 永久、全面的判断 | “这次没用动画”不等于“始终反对动画”；保留具体对象和情境 |
| E-02 | 局部范围 → 更大范围 | 某项目、某页面、某工具版本的结论不自动推广（M-34） |
| E-03 | 工具或执行成功 → 用户认可 | 成功只说明产物生成了；认可要有用户反馈 |
| E-04 | 沉默、跳过、一次超时 → 偏好或能力判断 | 用户没回复不等于“喜欢短回答”，偶然失败不等于“工具不可用” |
| E-05 | 转述、摘要、继承 → 独立证据 | Report、UI 转述、Goal 摘要、Fork 继承和上下文压缩都不增加证据强度 |
| E-06 | 改完就成功 → 唯一原因 | 一次成功不能排除同时发生的其他修改；无法隔离原因时只写“优先检查” |
| E-07 | 最新 → 当前有效 | 最新时间戳、最新产物、最近的 Session 都不自动代表当前选择或已被采纳 |
| E-08 | 用户说“记住” → 内容已核验 | 记忆意图说明用户要求保留，不说明所述外部事实正确 |
| E-09 | 一次性任务要求 → 长期偏好 | “这次用蓝色”推不出“以后都用蓝色” |
| E-10 | 为清空待整理材料而下结论 | 证据不足就暂缓或丢弃，不硬造解释 |
| E-11 | 写入成功 → 后续阶段已完成 | 写入、可召回、进入上下文、形成认知、落实修改是不同状态 |
| E-12 | `active` → 已被证明 | `active` 只表示当前可按条件使用；证据性质和不确定性另行保留 |
| E-13 | 进入 Memory → 获得指令权威 | 外部文本写进感知再被召回，仍只是有来源的材料（M-22） |
| E-14 | 查询为空 → 不存在 | 空结果不说明用户没有此类偏好，也不说明 Agent 没经历过此事 |
| E-15 | 召回回声 → 新证据 | Session 读到召回的认知后复述成新感知，或 Agent 主动研究的结果被当成用户关注，都是同源；不加强证据，也不提高显著度（§4.2） |
| E-16 | 本次例外、搁置 → 撤回既有认知 | “这次先不用”“以后再说”不是纠正；只有明确否定、替换或缩小范围才算（§4.3） |
| E-17 | 行为推断 → 覆盖明确表达 | 嘴上说重视质量、实际总选快：两者都保留并标明证据性质，召回时显露分歧，必要时询问 |

## 3. 认知建模要求：先定义记什么，再讨论怎么查

### 3.1 不预设 Hint List 就是最终模型

现有讨论中，topic 与 Hint 主要用于研究如何查找和召回。相对更困难的问题是：Agent 在什么情况下应主动创建一条 Hint，以及 Hint List 是否足以承载所需的认知。

因此，本版不把“新增一个 Hint 表”作为认知管理需求的答案。Hint 可以是触发和索引方式，底层认知也可能围绕人物、偏好、适用边界或经验组织。

### M-04｜模型需要表达的不只是孤立事实

**明确方向。** 认知模型应能够表达对人的印象、对某个人偏好的理解、对某类事情边界的理解等内容，而不只是若干 key-value。

下表是需要覆盖的语义举例，不是已确定的固定类型枚举。

| 语义 | 要表达的内容 | 容易发生的误用 |
|---|---|---|
| 对象相关认知 | 对某人、某项目或某工作对象形成的理解 | 把一次观察变成永久、全面的判断 |
| 偏好 | 谁在什么情况下倾向于怎样处理 | 把某个项目的偏好推广到所有项目 |
| 边界与约束 | 什么条件下适用，什么情况下不应继续 | 只记结论，不记成立条件 |
| 经验与选择依据 | 发生过什么、结果如何、为什么采用或放弃 | 把被否定的试验当作已采纳方案 |
| 关联与提醒线索 | 什么情境应想起某个认知或去查某个对象 | 只有内容，没有能够触发它的入口 |
| 事件背景 | 某主体在某时段参与的进行中事务：涉及谁、哪些对象、做过哪些决定及理由 | 把事件阶段当成状态长期保存；阶段属于 Task、Goal 或世界对象，Memory 只记带时间条件的背景 |
| 第三方关系 | 用户提到的人与人、人与组织之间的关系，以及用户对它们的态度 | 为只被顺带提到的人建立印象（M-34） |
| 私有用语与指代 | 用户特有的说法具体指什么，例如“整理照片”指哪几步 | 当成正式流程参数；流程本身属于能力资产或应用配置（§2.2） |

### M-05｜认知应具有来源、范围与可修正性

**派生约束。** 认知模型无论最终采用何种结构，都需要支持以下语义：认知涉及的对象与适用范围、来源依据、与时间或版本有关的条件，以及当前是否仍然有效。

这些信息不一定全部由模型手工填写，也不要求每条记忆都有复杂元数据；可以由 Session、对象引用和运行环境提供。但系统必须能够回答“为什么形成这个认知”和“在哪些条件下应该重新检查”。

相对稳定不等于永久正确。用户明确纠正、世界对象变化或新证据出现后，应能够修订、缩小范围、撤回或替代既有认知，而不是只追加越来越多互相冲突的文本。

认知还应记录有效期（如有）和产生它的整理版本（整理 Goal 使用的提示词与模型版本）。有效期到了，召回层默认不再显露它，这是派生状态，正式撤回仍由整理 Goal 完成（M-32）。发现某一版整理提示词有缺陷时，可以据此定位受影响的认知 revision。

### M-06｜保留观察、推断和已确认信息的区别

**派生约束。** 感知允许随意、初步甚至错误，但进入后续推理时必须保持其证据性质。用户明确表达、工具观测结果与 Agent 自己的推测不能不加区分地混为事实。

例如，“用户这次没有采用某种动画”不能直接整理为“用户始终反对动画”。系统应保留具体对象和情境；证据不足时可以形成暂定认知，也可以继续保留为未整理材料。

不要求模型输出的一个置信度数字自动证明结论可靠。如何表示不确定性可以待定，但使用层必须能区分有依据的结论和待验证假设。

### M-07｜同一底层认知可以有多个召回入口

**派生约束。** 模型应允许同一个认知被不同话题或对象关系触发，而不是为了每个 Hint 复制一整份认知。认知变更时，应能够使相关入口同步修正或失效。

是否采用独立 Hint、主题索引、对象索引、关系结构或组合，属于待决设计。不能把某个召回技术提前当作认知本体。

## 4. 感知层：任务中低成本写入

### M-08｜记录感知不要求当场形成成熟认知

**明确方向。** Session 执行主任务时，只需以很小的思考量记录注意到的事情。感知可以不完整、不确定，甚至后来被证明是误判；“先感知到”比当场完成抽象更重要。

感知写入不应要求当前 LLM 偏离任务，展开完整的归因、长期价值判断或跨 Session 检索。

### M-09｜提供默认的感知入口

**明确方向。** Agent Session 的通用机制应默认允许感知记录。应用开发者无需在每个业务分支手工编写 Memory 管理逻辑；外部 Runner 与常驻 Runtime 应使用兼容的写入机制。

**派生约束。** 默认工作不代表不可控制。Agent 或调用方经授权应能表达本次工作不进入长期记忆、限定记忆范围等要求；具体配置和权限分工待定。这些策略只作用于 Memory，不影响 Task 修订等正式数据的传递（M-31）。

### M-10｜写入契约保持轻量，来源由系统补齐

**派生约束。** 感知写入在概念上应至少具有：一段观察内容、属于哪个 Agent、来自哪个 Session / 交互或动作，以及必要的对象范围。

已由运行环境掌握的 Session 标识、时间和输入来源，应尽量自动附加，不要求模型重复生成。感知应能关联 Task 和产物版本，以便后续区分成功结果、试验过程与被放弃的工作。

具体字段名、序列化格式和存储位置不在本版固定。关键要求是低写入负担与可追溯性同时成立。

### M-11｜写入触发依据需要被设计和评估

**明确方向。** 什么事情值得记录，是本需求的核心难点之一。通用提示词可以引导写入，但不能用一句“记住重要的事情”替代明确的建模与评估。

可用于验证触发机制的情形包括：用户明确表达的后续偏好、对象选择及其原因、任务过程中观察到的限制、结果反馈、与已有认知相矛盾的新信息。§4.4—§4.6 给出写入和排除的判断基线；符合写入条件也不要求每次都立即生成独立 Hint。

**派生约束。** 写入机制应能够控制噪声和重复；既不能因为门槛过高完全漏记，也不能把每条输入都机械改写成长期记忆。

当场写入之外，可以有**事后回扫**作为补充来源，给漏记兜底：在 Session 空闲、一轮表达完整后，由一个 Goal 从 Session 历史（不是从 LLM 上下文快照）回看值得记录的内容，只写感知（M-32 允许）。回扫游标属于运行元数据，写入成功后才推进；回扫要遵守“本次不记忆”策略，与当场写入按来源事件去重，并排除整理 Goal 自身的 Session 和召回回声（E-15）。是否采用、由哪个 Goal 执行属于待决设计（§11）。

### M-12｜低成本写入不阻塞主任务

**明确方向。** 感知记录与认知整理在运行成本上分层。普通任务不应为写一条感知而同步执行重型认知整理或启动专门的 Goal 运行轮次。

**派生约束。** 写入失败或重试应有可观察的处理结果，不应悄悄演变成主任务的无限重试。是否允许任务继续、何时补写、什么场景必须可靠提交，需要按 Session 策略定义。

同一输入因重放或 Runner 恢复而被再次处理时，应避免无意义地重复写入同一感知。低成本目标需在原型中测量，但本版不凭空规定统一的 token 或耗时阈值。

### 4.1 写入的数据类型与实例

**示例。** 不固定最终类型枚举。“写入类型”需要区分两个维度：一是记录的**语义**，例如偏好、选择依据和经验；二是承载它的**数据形态**，例如短文本、结构化属性和对象引用。以下样例均为虚构测试数据，不代表真实用户偏好或已经实现的功能。

| 候选语义类型 | Session 中可低成本写下的感知 | 整理后可能得到的认知 | 不能直接得出的结论 |
|---|---|---|---|
| 偏好 `preference` | 用户说：“这个贪吃蛇游戏页面以后用静态背景，不要闪烁。” | 针对该用户、该项目和游戏页面的效果偏好 | 用户在所有产品中都不喜欢动画 |
| 选择及依据 `decision_context` | 用户在 alpha、beta 两个工作区中选了 alpha，理由是操作更稳定 | 当时的选择理由，以及后续应检查哪个项目对象的选择状态 | alpha 永远是当前工作区，或者最近修改的版本必然被采用 |
| 边界与约束 `boundary` | 用户说：“这个项目以后调整游戏页效果时，不要连带改演示页。” | 用户明确要求持续适用的项目边界 | 每次临时任务要求都自动成为永久约束 |
| 结果反馈 `outcome_feedback` | 用户说：“这个版本干扰操作，撤掉；以后也别在游戏背景用这种效果。” | 对该效果的负面反馈及其明确适用范围 | 仅凭工具返回成功，就认为用户认可结果 |
| 工具或环境观察 `environment_observation` | 当前校验工具在资源中缺少 `tick_ms` 字段时返回错误 | 有版本和资源类型条件的检查线索，或暂定限制 | 所有工具版本都要求这个字段 |
| 暂定印象 `tentative_understanding` | Agent 注意到用户连续两次跳过长解释，猜测其可能希望更短的反馈 | 带有依据和限制的暂定交互偏好；也可能暂不形成认知 | 用户已经明确要求以后只给短回答 |
| 方法与经验 `procedure_candidate` | 两次任务都在补齐配置字段后通过同一类校验 | 在特定条件下可复用的检查步骤或经验 | 一次相关结果就证明唯一因果关系，或直接生成无条件自动执行的脚本 |
| 纠正、替代与撤回 `correction` | 用户说：“不是不能动，可以慢慢移动，但不要闪烁。” | 修订已有偏好及其召回入口，而不是并列保留两个冲突结论 | 仅把纠正内容追加到历史里，旧结论仍作为有效默认值 |

实际载荷可以是以下几种形态。无论采用什么形态，都应保持来源和范围。

| 数据形态 | 示例 | 使用边界 |
|---|---|---|
| 短文本 | “用户明确要求当前项目游戏页不使用闪烁背景。” | 最小写入路径，不要求模型先建完整认知对象 |
| 结构化观察属性 | `{"error_code":"ASSET_KEY_MISSING","field":"tick_ms"}` | 字符串、数值、布尔值等承载一次观察；数值需说明单位、观测条件和来源 |
| 对象及版本引用 | 资源对象、Workspace、某次任务产物版本的 ObjectRef | 保存访问线索，不复制整套世界状态 |
| 来源片段或多模态证据引用 | 一条用户消息、工具结果、被评价图片的对象引用 | 大文件、图片和完整日志原则上仍作为外部对象；Memory 保存理解及必要引用 |
| 条件化结构或步骤 | “当资源类型为 X 且工具版本为 Y 时，先检查字段 Z。” | 通常由认知整理阶段形成；观察阶段只需写下发生的事情 |

当前时间、天气、任务进度和当前有效产物版本，首先属于动态世界状态。它们可能触发感知或为认知提供条件，但不能因为容易写入，就全部变成长期认知。密码、访问令牌等秘密也不应进入可召回的通用 Memory。

### 4.2 最小感知写入：模型只记一件事，Runtime 补齐出处

以下 `memory.*`、`objects.read` 均为**拟议的逻辑接口示意**，不是现有 OpenDAN SDK 的真实函数声明。示例中的 `agent:a1`、`user:u1`、`world:workspace:snake-alpha` 等是对象引用别名，不定义 DID / ObjectRef 的实际编码格式。

假设当前用户消息为：“记一下，这个贪吃蛇游戏页面以后用静态背景，不要闪烁。”模型可以只提交：

```python
memory.record_perception(
    content="用户要求当前贪吃蛇项目的游戏页面以后使用静态背景，不要闪烁。",
    object_refs=["world:workspace:snake-alpha"],
    suggested_kind="preference",
    memory_intent="explicit"
)
```

概念上，系统保存的记录可以是：

```json
{
  "ref": "memory:p-101",
  "layer": "perception",
  "content": "用户要求当前贪吃蛇项目的游戏页面以后使用静态背景，不要闪烁。",
  "suggested_kind": "preference",
  "memory_intent": "explicit",
  "agent_ref": "agent:a1",
  "subject_refs": ["user:u1"],
  "object_refs": ["world:workspace:snake-alpha"],
  "source": {
    "session_ref": "session:ui-web-01",
    "event_ref": "session:ui-web-01/event/31",
    "actor_kind": "user"
  },
  "observed_at": "2026-09-01T10:00:00+08:00",
  "state": "pending"
}
```

其中，Agent 身份、真实 Session、来源事件、时间和授权范围由执行环境补齐或核验；来自 Work 或 Goal 的感知，`source` 还会带上 `task_ref` 或 `goal_ref`。对象引用须能够解析且在授权范围内。`suggested_kind` 只是分类建议，允许省略，不等于已经形成 `preference` 认知。

`memory_intent` 只在用户明确要求记住时由模型填写，供整理时保留处置依据（§4.4）。没有这个字段，不降低用户明确要求的证据性质（§4.5 第一行）；有这个字段，也不说明所述内容已被核验（E-08）。

**情境锚点。** 整理往往在几小时甚至几天后才运行，那时“明天”“周五”“老地方”已经变义。Runtime 因此要补齐解读所需的锚点：时区、语言区域，必要时附位置。模型保留原话里的相对表达，不做时间算术；整理 Goal 按 `observed_at` 当时的锚点解读，有效期存成绝对时间（§5.6 第 2 步）。所述事情的发生时间（`occurred_at`，可以是估算）和得知时间（`observed_at`）分开记录，只有前者需要模型给出。意图自带的锚点优先于环境锚点：用户出差到东京时说“买明天上午飞东京的票”，“明天上午”按起飞地时区理解。

**提及与指代。** 对象只有名字、还没有 DID 时，可以写原始提及（如“Bob”），由组件附上解析候选及依据（联系人、既有认知、上下文）。写入时不合并对象，归属由整理 Goal 决定（M-25、§5.6）。

**召回回声。** 感知如果由召回内容引出（Agent 读到一条认知后据此推出新判断），写入时须引用该认知；Runtime 附加的 Memory 观察不能作为新感知的来源事件。否则，A 写下的感知显露给 B，B 复述一遍，整理 Goal 就会看到两条“独立证据”（E-15）。

**写入回执。** 回执可以附带同主体、同对象范围下已有认知的引用，供写入方在纠正时补上关联（§4.3），也供整理 Goal 预分组。写入方不必处理这些引用，写入时也不做去重裁决；范围索引不可用时省略，不报错。

`actor_kind=user` 只能说明来源事件确实来自用户，不能证明感知文本准确转述了原话。整理时仍需判断是否存在误读、范围扩大或从引用内容中误认指令的情况。Agent 自己的推测，应关联自己的观察或推理来源，不能伪装成用户明确表达。

这个调用的成功只表示**感知已被记录**，不表示认知已形成、Hint 已生成，或者其他 Session 已感知更新。同一来源事件重放时，可由 Runtime 提供稳定的去重键；一个事件确有多条不同感知时，不能只按事件 ID 去重而误删有效内容。

### 4.3 明确纠正与普通新观察，写入后的处理可以不同

普通观察可以等待后续整理；明确纠正则可能使正在使用的旧认知立刻失去适用性。例如用户说“不要再按静态背景处理”，系统不能在整理尚未完成的时间窗口里，仍把“必须静态”无提示地召回。

**派生约束。** 按 M-32，写入方不直接修改认知；纠正在整理完成前的效果由召回层派生。纠正类感知指写入时标为 `correction`、或附带了被纠正认知引用的感知。分两层：

1. **兜底（必须）**：召回或查询任何认知时，无论是否请求近期感知，都同时返回同一主体、同一范围下尚未整理的纠正类感知，并标注“可能已被纠正”。这只依赖感知自带的主体和对象范围，不需要从自然语言定位受影响的认知。
2. **精确标记（增强）**：写入方的上下文里已经有被纠正认知的引用时（它刚被召回过，这是最常见的纠正场景），写入纠正时附带该引用，几乎没有额外成本。组件据此把该认知显示为“待复核”，直到整理 Goal 完成修订。待复核是召回层的派生状态，不是对认知的写入。

只有明确否定、替换或缩小范围才标 `correction`。“这次先不用”“以后再说”按普通观察记录，范围限于本次（E-16）；否则兜底会到处显示“可能已被纠正”，变成误报。

从自然语言自动定位受影响的认知是后续能力，不作为 B-18 的前提。纠正写入不能为了完整分析而阻塞当前主任务，也不能把一次无关观察当作全库失效信号。

这项有效性要求，不等于把所有未整理感知都塞进上下文。组件须支持按情境召回待整理感知；按 M-21，相关新增感知默认可通过已建立的半订阅观察，显式关闭除外，不必等待整理完成。这些都是尽力而为的线索（M-30）。用户明确要求不记忆时，应先执行相应记录策略，不能先持久化再假定以后总能清理。

### 4.4 什么值得进入感知层：未来有用、出现变化、出处明确

**派生约束。** 感知保存的是值得后续理解或复用的观察。当前 Session 不需要先证明它是长期规律，也不需要为了决定是否写入而检索全部历史。可用当前已有信息快速判断：

| 判断 | 记录时需要知道什么 | 不要求当场完成什么 |
|---|---|---|
| 未来用途 | 在可描述的后续情境中，可能改变选择、检查步骤、交互方式，或提醒去查某个对象 | 证明一定会长期复用，或预测精确收益 |
| 本次变化 | 新要求、新条件、结果反馈、例外、纠正或可复用的失败线索；没有新变化的进度重复通常不写 | 全库查重；相同事件重放由组件幂等处理 |
| 可追溯性 | 谁表达或观察了什么，涉及哪个对象，在什么条件下发生；推测明确标为推测 | 构造完整认知、证明因果或填写大段元数据 |
| 信息归属 | 值得保留的是理解、经验或访问线索；任务状态和世界对象仍由原系统管理 | 把任务书、Goal 状态、文档、工具日志再复制成一个事实库 |

在允许记忆的范围内，明确的记忆请求、后续偏好和对既有认知的纠正应优先记录；其他内容满足“有可描述的后续用途、这次有新观察、来源和范围可追踪”时进入感知。无法指出任何后续用途的普通流水，留在原事件或工作记录中即可。复用可以只限于一个项目，不要求对所有任务都有价值。

“后续用途”指 Agent 以后的理解和判断，不包括“让另一个 Session 收到这条信息”。UI 收到对正在执行的工作目标的修改时，这条修改必须送达运行中的 Work，属于 Task 修订（§9.4、M-31），不写成感知；只有修改中带出的长期信号（如“以后都……”）另写感知。是否值得进入感知层，与是否值得升级为认知，是两个判断。

不确定性本身不是拒绝写入的理由。例如一次代价很高的异常，即使原因未明，也值得留下“在什么条件下发生了什么、下次应检查什么”的候选线索。相反，不能为每个小错误都猜一个长期规律（E-01）。写入策略要同时评估漏记有用信息和制造噪声，不能用单一数量目标代替。

用户明确要求记住后，整理应保留可追溯的处置：由哪条认知承接、为何被纠正或替代，或仍缺什么信息。不能以“只是一次表达”为由静默丢弃，也不因此把所述外部事实视为永久正确或永久置顶。

### 4.5 Session 使用方的正例、反例和信息归属

| 场景与原始内容 | 感知层的处理 | 后续可能的用途 / 原信息归属 |
|---|---|---|
| UI：“这个项目游戏页以后不要闪烁。” | 写“u1 要求该项目游戏页以后不闪烁”，关联用户事件；有无“你记一下”都可成立 | 以后讨论背景或视觉改动时显露项目边界 |
| UI：“这次先选 alpha，因为操作更稳定。” | 记录本次选择及理由，保留比较对象和时间 | 提示历史选择与判断依据；当前选定版本仍读项目对象 |
| UI 在创建 Work 前：“这一次先用蓝色，做完给我看。” | 纳入本次 Task 约束；无其他后续用途时无需重复写成感知 | 创建时的任务书由正式对象传递；单次要求不自动变成长期偏好 |
| UI 在 Work 执行中：“背景改成蓝色；字号也大一点。” | 不写感知；作为两条 Task 修订追加到 Task 对象，附原始用户消息；Work 及相关子 Session 经 Task 对象半订阅观察 | 下一次推理据此调整当前实现；修订随 Task 保留，不进入整理 Goal，也推不出“以后都用蓝色”（E-09） |
| UI 在 Work 执行中：“这次改深灰；以后这个项目都别用亮色背景。” | 前半句是 Task 修订；后半句另写一条项目范围的偏好感知 | 修订保证本次送达，感知供以后的任务召回，两者互不依赖 |
| Work：工具 v1 在当前环境省略输出目录时失败，补目录后通过 | 记录环境、失败、变更及验证结果的关联，区分观察和原因猜测 | 下一次使用同工具和环境时检查输出目录；不是全量命令日志 |
| Work：一次拼写错误被立即修正；常规构建通过 | 通常留在执行日志 / Final Report；反复出现或暴露真实限制时再提取线索 | 当前执行成功与否由 Report 表达，不推断用户已认可产物 |
| Goal：本轮还在等 PR 审核、预算剩余 20% | 留在 Goal 状态；不因每轮恢复而重新生成感知 | 下一轮进度恢复以 Goal/Task 对象为准 |
| Goal：对照多个 Work 发现某环境下远程校验多次缺一个参数，本轮又取得直接验证 | 记录新增证据与条件，引用原始工具结果；已记录材料只补关联 | 可供后续同环境的其他任务复用，不自动扩展为全局规则 |
| 意图分析的 Context Fork：推测用户也许希望所有页面统一，但尚未询问 | 通常留在意图分析的待澄清项；若确有后续价值，可记为有依据的待验证假设 | 不写成用户确认；创建 Task/Goal 前仍按就绪条件澄清 |
| UI/Goal：转述一个 Work Report 中已经记录的错误 | 保留原始事件关联；没有新反馈时不增加独立观察 | 转述、摘要和 Fork 继承不能把一份证据变成三份（E-05） |
| 用户没有回复一次；一次查询偶然超时 | 默认不据此记录偏好或长期能力判断；有重要后果时仅记具体异常 | 不推出“喜欢短回答”或“这个工具不可用”（E-04） |
| 用户要求保存会议原文，或明天下午提醒一次 | 由文档、Task/Goal 或相应业务对象承接；有复用价值时另留 Memory 线索 | Memory 写入不等于创建文档、完成提醒安排或获得执行授权 |
| UI：“我去 Costco 买了点东西。”与“我更喜欢 Costco，不喜欢 World Market。” | 前一句通常不写；后一句写偏好 | 对象应是可区分的个体或明确的品牌、地点；“超市”这类泛指类型词不作对象 |

UI、Work、Goal 都可产生感知。初始任务书、执行期的 Task 修订、授权、Final Report 与 Goal 当前状态通过正式对象传递，不能靠 Hint 查询重建（M-30、M-31）。这些信息的去处汇总见 §2.2。

### 4.6 一条合格感知如何写得轻

推荐表达为“在条件 X 下，来源 Y 表达 / 观察到 Z；需要保留的边界或未知是 W”。已知的身份、时间、Session、Task/Goal 和原事件引用由 Runtime 附加；对象或环境条件只写本次确有意义的部分。类型标签和未来用途说明可用于评估，不要求每次模型调用都填完整表单。

```text
不充分：输出目录很重要。
合格感知：tool-x v1 / linux / Task A 中，未指定输出目录时报错 E_OUTPUT；
          加入 --out 后同一输入通过。来源 call8、call9；是否适用于其它环境未知。

不充分：用户不喜欢动画。
合格感知：u1 要求 snake-alpha 的游戏页以后不闪烁，演示页另说。
          来源 user-event-31；尚未讨论其它项目。
```

需要保留的是关键观察、条件、结果和来源，完整工具输出继续由原日志承载。组件负责持久化、幂等、范围和来源契约；使用方的写入策略判断内容价值，整理 Goal 判断能否形成认知。接口校验成功只证明记录被接受，不证明内容值得长期保留或结论正确。

## 5. 认知层：跨 Session 整理与感知清理

### M-13｜Memory 整理 Goal 处理多个 Session 的新鲜感知

**明确方向。** 认知整理是一个独立于主任务的过程，在新架构中由持续维护型 Memory 整理 Goal 承担。其输入包括多个 UI、Work、Goal Session 的新鲜感知、必要原始来源及既有认知；输出是 Agent 内部认知状态的更新和逐条材料处置。

Runtime 决定何时提供运行机会及预算；self-input 可以是承载输入的机制，Self Improvement 可以描述业务用途，二者都不要求新设一级 Session 类型。每轮积压归零只表示当轮无待办，不表示长期 Goal 永久完成；有缺证材料时可以暂缓并结束当轮。

### M-14｜整理可以新增，也必须能够修正

**明确方向与派生约束。** 整理不是简单把若干感知拼成一段摘要。它应能识别它们是否指向同一对象、是否重复或冲突，是否足以形成一种认知，以及是否需要修改既有理解。

至少需要覆盖：合并一致信息、保留必要分歧、限定结论范围、更新已有认知、撤回失效内容，以及认定某些感知不值得转化为长期认知。

原始材料不足以支持一个结论时，不应为了“清空感知池”而编造解释（E-10）。可以暂缓形成认知，或只形成带有明确限制的认知。

### M-15｜认知变更与材料处置提交成功后再清理感知

**明确方向。** 感知被成功整理后，应清理或删除被吸收的感知，留下认知，而不是长期同时积累一套完整感知库和一套完整认知库。

**派生约束。** 必须先使认知变更（如有）与逐条材料处置可靠生效，再清理对应感知。整批仅包含重复或应丢弃材料时，可以只提交处置，不强制生成认知。实现可以使用事务或等价机制，但不能出现“感知已删、认知未写”的丢失窗口。

```text
待整理感知
    ↓
选取一批材料并进行整理
    ↓
形成认知变更（如有）与逐条材料处置
    ↓
可靠提交认知变更及处置记录
    ↓
清理已吸收/丢弃的感知内容，保留暂缓材料
```

仅标记为已消费并无限保留全部感知正文，不应被当作默认完成清理。被吸收、不值得保留和仍需补充证据的材料，可以有不同处理结果，但必须有明确生命周期。

清理不等待所有订阅方都观察到这条感知。尚未观察的订阅方之后看到的是吸收或丢弃的结果，而不是已删除的旧正文。感知本来就是尽力而为的线索（M-30），必须送达的内容不放在这里。

### M-16｜清理原材料与保留来源依据分开

**派生约束。** 删除感知正文，不必同时删除相关 Task 标识、原始事件引用或最小来源元数据。认知仍需具备支撑修正、冲突处理和任务回滚的来源关联。

来源引用应尽量指向真实 Session 事件、对象版本或其他授权材料，而不是只指向即将删除的临时感知记录。引用可追踪不等于永久保留全部原文；保留范围和时长需单独定义。

原始 Session 历史是否保留，由 Session / 数据保留策略决定，不能从“删除已整理感知”直接推导为“删除全部聊天历史”。来源已不可读取时，也不能继续声称结论仍有可复核的原文支持。

### M-17｜支持整理失败与并发恢复

**派生约束。** 多个 Session 可以同时产生感知，整理过程也可能失败或重试。因此需要保证：尚未处理的感知不被误删，同一批材料不会因并行整理产生相互覆盖的认知，重试不会无控制地复制结果。

认知更新应有可辨认的版本或等价的提交边界。采用单整理者、批次领取、版本检查或其他方式，留待实现设计。

整理频率、触发阈值、是否按 topic / 对象分批，以及如何处理长期不足以形成结论的感知，均是待决策略，不预设每次感知写入都会立即启动整理。

### 5.1 完整例子 A：两次感知形成一条有范围的偏好认知

以下例子承接 4.2。时间、标识和对象均为示例。

**输入变化：**

| 阶段 | 新增数据 | 当时的含义 |
|---|---|---|
| 初始 | 尚无相关认知 | 不能假设用户喜欢或不喜欢动画 |
| Session 1 | `p-101`：用户要求当前贪吃蛇游戏页面以后使用静态背景，不要闪烁 | 一条明确表达，仍处于待整理状态 |
| Session 2 | `p-102`：用户确认“静态版操作不受干扰，就保持这样；这是当前项目的要求，演示页另说” | 增补原因与适用边界，不是另一个全局偏好 |
| 整理 | 综合两条感知及其原始事件 | 形成一条认知，保留用户、项目、页面范围及来源 |

认知不是把两段话拼接成摘要，而是抽出可供未来工作使用的条件化理解。例如：

```json
{
  "ref": "memory:c-snake-background",
  "revision": 1,
  "layer": "cognition",
  "kind": "preference",
  "subject_refs": ["user:u1"],
  "scope": {
    "workspace_ref": "world:workspace:snake-alpha",
    "surface": "game_page"
  },
  "statement": "在该项目的游戏页面中，用户希望默认使用静态、不闪烁的背景，以免干扰操作。",
  "exceptions": [
    "不自动推广到演示页面",
    "不自动推广到其他项目"
  ],
  "basis": "user_statement",
  "state": "active",
  "evidence_refs": [
    "session:ui-web-01/event/31",
    "session:ui-telegram-01/event/12"
  ],
  "review_when": [
    "用户明确改变偏好",
    "拟将该认知应用于其他页面或项目"
  ]
}
```

这里没有要求“至少两次才可以形成认知”：一次清楚、有效授权下的明确表达，也可以形成窄范围认知。跨 Session 综合的价值，是补齐条件、发现一致性或冲突，而不是机械凑够样本数。

同一条认知可以有多个召回入口，例如“该用户 + 游戏背景”“该 Workspace + 效果修改”“闪烁 / 干扰操作”。入口只引用 `c-snake-background` 的有效版本，不各自复制一份偏好全文；具体是否存成 Hint 表仍不限定。

**提交后的存储变化：**

```text
整理前：
  p-101、p-102 = pending
  c-snake-background 不存在

可靠提交认知后：
  c-snake-background@1 = active
  本批次记录 p-101、p-102 已被吸收，关联到该认知

清理完成后：
  p-101、p-102 的感知正文被删除
  保留必要的批次 / 来源关联元数据
  认知的 evidence_refs 指向原始 Session 事件，而非已删除的感知正文
```

认知提交失败时，两条感知不能删除。清理失败时可以继续重试清理，但不能重复生成另一条相同认知。原始 Session 事件能否长期读取，仍由数据保留与访问策略决定。

### 5.2 完整例子 B：用户纠正后，认知修订而不是冲突堆叠

随后，用户在新的 UI Session 中说：

> 换一下默认效果：这个项目游戏页可以用缓慢移动的背景，但仍然不能闪烁。其他项目别受这个要求影响。

Session 先低成本写入 `p-103`，其来源是 `session:ui-web-02/event/8`。它可以提示与 `c-snake-background` 有关，但不要求主任务当场完成完整合并。

整理后的**逻辑变更示意**为：

```json
{
  "target_ref": "memory:c-snake-background",
  "expected_revision": 1,
  "new_revision": 2,
  "changes": {
    "statement": "在该项目游戏页面中，背景可缓慢移动，但不应闪烁或干扰操作。",
    "basis": "user_statement",
    "state": "active"
  },
  "unchanged": [
    "subject_refs",
    "scope",
    "exceptions"
  ],
  "added_evidence_refs": [
    "session:ui-web-02/event/8"
  ],
  "previous_revision_state": "superseded"
}
```

这不是规定数据库必须使用这种补丁格式，而是要求变更语义清楚：

| 数据 | 整理前 | 整理后 |
|---|---|---|
| 有效认知 | `c-snake-background@1`：默认静态 | 同一逻辑对象的 `@2`：允许缓慢移动，仍不得闪烁 |
| 旧版本 | 当前有效 | 被替代；只有历史审查明确需要时才读取 |
| `p-103` | 待整理纠正 | 成功吸收后清理正文 |
| 召回入口及摘要缓存 | 可能仍写“静态背景” | 更新或失效，不能继续无条件返回旧摘要 |
| 已运行 Session | 可能已读入 `@1` | 在下一次合适观察机会收到修订线索，不重新注入一遍所有认知 |

旧历史消息不一定能从已经形成的上下文里删除；至少要让 Session 明确知道旧结论已被替代。版本冲突时应重新读取再合并，不能让另一个整理者用旧结论覆盖 `@2`。多条互相矛盾的来源也不能简单按“最新时间戳获胜”（E-07）；本例能够修订，是因为同一主体明确改变了同一范围内的要求。

### 5.3 完整例子 C：记住选择理由，但不接管“当前工作版本”

用户曾试做多个贪吃蛇项目版本。一次对话中，用户明确选择 alpha，理由是操作更稳定；后续某个试验任务又产生了更新时间更晚的 beta 产物。

| 层次 | 适合保存的数据 |
|---|---|
| 世界对象 | 项目的当前选定 Workspace、有效产物版本，以及各版本文件 |
| 原始感知 | “用户在这次比较中选了 alpha，理由是操作更稳定。” |
| 整理后认知 | 当时选择 alpha 的依据；用户更重视该场景下的操作稳定性；定位项目选择对象的线索 |
| 召回入口 | 用户说“刚刚那个贪吃蛇”时，提示存在历史选择及多个候选工作区 |
| 主动查询 | 读取项目选择对象，确认当前有效 Workspace；必要时再读取候选产物或向用户澄清 |

一条可能的认知是：

```json
{
  "ref": "memory:c-snake-choice",
  "revision": 1,
  "kind": "decision_context",
  "subject_refs": ["user:u1"],
  "scope": {
    "project_ref": "world:project:snake"
  },
  "statement": "用户曾在比较中选择 alpha，主要原因是游戏操作更稳定。",
  "state": "active",
  "basis": "user_statement",
  "evidence_refs": ["session:ui-web-01/event/22"],
  "related_object_refs": [
    "world:workspace:snake-alpha",
    "world:project:snake/selection"
  ],
  "use_condition": "用于理解历史选择；操作前需读取项目选择对象确认当前有效工作区。"
}
```

这里的 `active` 表示“这条历史选择及其理由尚未被撤回”，**不是**“alpha 仍是当前选中版本”。更新时间更晚的产物也不自动代表被采用（E-07）。

如果世界对象随后显示当前选择已变为 beta，应以最新授权可读的选择状态作为工作基础。Memory 可以帮助理解为什么曾选择 alpha，也可以触发“是否发生了选择变化”的检查，但不能覆盖世界对象。尚无明确选择记录且存在多个候选时，不得仅凭记忆线索猜定目标。

### 5.4 完整例子 D：工具观察转化为有条件的经验

假设有一个测试用的效果资源校验工具。以下错误与处理过程仅为示例，不描述任何现有工具的真实行为。

```text
p-201（Task A 的工具观察）：
  effect-validator v1 对某类效果资源报 ASSET_KEY_MISSING，
  指向 tick_ms 字段。

p-202（Task A 的后续结果）：
  补齐 tick_ms 后，同一版本工具对该资源校验通过。

p-203（Task B 的独立观察）：
  同类型资源在同一工具版本下出现相同现象。
```

整理可以形成：

> 对于已观察到的这类资源及 `effect-validator v1`，遇到相同缺字段错误时，优先检查 `tick_ms`；工具版本或资源类型改变后，应先读取当前规范或重新验证。

这条认知可以建模为带条件的 `procedure_candidate` / 经验条目，来源是工具结果而非用户声明。召回入口包括工具标识、错误码、资源类型和当前任务对象；它只是检查建议，不直接获得自动修改文件的权限。

不应形成“所有效果都必须有 `tick_ms`”或“这个工具永远不兼容新格式”（E-02）。无法隔离原因时，保留“优先检查”的经验表述，不宣称已证明唯一因果（E-06）。

相反，“用户这次没有回复”“一次查询偶然失败”这类弱观察（E-04），可以暂缓整理、请求更多依据，或按生命周期清理而不生成认知（E-10）。

### 5.5 完整例子 E：任务被放弃后，区分产物失效与经验保留

假设 Task `task-effect-11` 产生了闪烁背景，用户随后说：“这个结果不要了，回到之前的版本；但记住以后不要在游戏背景里采用这种效果。”

| 涉及数据 | 应发生的变化 |
|---|---|
| 该 Task 产物 | 由任务 / 世界状态系统处理放弃或回滚；Memory 不宣称自己已经完成产物回滚 |
| “工具成功生成闪烁效果”的感知 | 只能表示曾生成，不能表示结果被用户采纳（E-03）；可在整理后清理 |
| 用户这次反馈 | 作为新的、可溯源的感知输入 |
| 基于用户明确反馈的边界认知 | 可以保留，因为用户在本例中明确要求记住经验 |
| 依赖该成果“当前有效”才能成立的认知 | 应失效或待复核，不能继续诱导后续任务使用弃用成果 |
| 仅提及“曾尝试过该效果”的历史经验 | 不能因同一 Task 被放弃就一律删除；应检查来源、授权和用户的真实意图 |

本例有“保留经验”的明确表达，不能据此确定所有任务回滚的默认 Memory 策略。用户另行要求“忘记这次经历”时，应转入 M-28 的遗忘语义，不得用“保留经验有价值”抵消其要求。

### 5.6 综合的具体步骤：按问题组织材料，逐条给出处置

**派生约束。** 以下是整理 Goal 的工作方法，不要求普通 Session 在写感知时执行，也不要求每一步新增公开接口。

| 步骤 | 整理时做什么 | 必须避免的错误 |
|---|---|---|
| 1. 收敛问题与范围 | 从有限批次中按主体、对象、环境、时间及待回答问题分组，也可按进行中事务分组；借助写入回执或建议分组键找到相关既有认知 | 只因出现同一关键词，就混合不同用户、项目或工具版本 |
| 2. 还原来源与关系 | 核对原事件；按 `observed_at` 当时的锚点解读相对时间和指代；标出同一观察的转述、召回回声、补充、独立复现、纠正和反例 | 把 UI 转述、Work Report、Goal 摘要当作三次独立验证 |
| 3. 比较支持和限制 | 区分明确要求、外部事实自述、工具结果和推测；寻找适用条件、例外及尚未排除的解释 | 多数票、只取最新文本，或把“改完成功”直接视为唯一因果证明 |
| 4. 提炼最小可复用结论 | 写清“在什么条件下，应考虑什么、为什么、何时复核”，范围以证据能支持的部分为限 | 把一组流水压缩后直接命名为认知，或为了通用而扩大范围 |
| 5. 选择变更与材料处置 | 新增、补充既有认知、修订/缩小范围、撤回；证据不足则暂缓，无保留价值则丢弃 | 每批都必须产出新认知，或已处理游标跳过暂缓材料 |
| 6. 形成召回入口并可靠提交 | 为同一认知建立当前任务可触发的对象/主题入口；提交版本、依据、材料处置后再清理 | 只有一句结论却无法召回，或清理后无法解释认知从何而来 |

分组用于发现联系，不要求一组只能输出一条认知。一条感知也可能支持不同但相关的判断。补充来源、发现适用范围应拆开、明确撤回旧结论，都是有效整理结果；重复材料可以关联已有认知后清理，无需制造新版本正文或重复 Hint；新材料已被更宽的既有认知覆盖时，也只补充依据。

确认两个提及指向同一对象后，由整理 Goal 提交合并，保留修订链，旧入口重定向到合并后的对象；没有把握时保留歧义，不按同名合并（M-25）。

“暂缓”需保存缺失依据和重新评估条件，例如需要某次 Work 的直接结果、用户确认或新版本验证；“丢弃”需给出简短理由，例如仅是进度副本、已被记录的重复内容或无后续用途。若有必要把能力缺口交给 Self Correct Goal、把经验交给操作经验结晶 Goal，只提供候选及来源引用；相关任务是否创建、工具是否安装、资产是否发布，仍由对应职责判断。

### 5.7 什么条件下可以称为认知

**派生约束。** 认知至少应让后续使用方回答以下问题；这些是评审维度，不规定新增五个必填字段。

1. **会影响什么理解或行动？** 能在特定情境下提示偏好、边界、检查步骤、历史依据或应查询的对象；纯流水转述不足以满足。
2. **结论由什么支持？** 每个关键结论能对应有效来源，区分直接表达、直接观测与推断，指出不能确定的部分。
3. **能推广到哪里？** 主体、项目、版本、时间和例外与证据一致；没有证据支持的范围保持未知。
4. **怎样处理冲突与变化？** 明确是新认知、既有认知的修订还是并存的不同条件；遇到新要求、反例或对象换版时可复核。
5. **未来怎样被想起和核查？** 普通任务情境能触发线索，线索指向同一认知及必要来源，不依赖使用者事先知道结论关键词。

不同结论需要不同依据，不设统一的“出现 N 次就升级”或置信度阈值：

| 结论性质 | 足以支持的范围 | 不足以支持的范围 |
|---|---|---|
| 用户明确的持续要求 | 一次清楚表达即可形成该主体、该范围内的偏好或边界 | 自动推为所有项目、所有用户的规则 |
| 用户对运行中任务的一次性调整 | 属于 Task 修订，不进入 Memory，整理 Goal 不处理（§9.4） | 因为已执行就升级为持续偏好（E-09）；只有调整中明确的长期表达才另写感知 |
| 用户自述的外部事实 | 可以形成“用户在某时报告 X”的有来源认知 | 仅因说了“记住”就声称已独立核验 X |
| 第三方文档、推荐或其他 Agent 的主张 | 形成“来源 X 认为 Y”的有来源认知 | 未经自身经验验证就当成已采纳的经验 |
| 工具/环境经验 | 一次可追溯观察可支持窄范围检查线索；独立复现、规范核对或对照验证可加强结论 | 同一事件的多次摘要不能加强证据；局部成功不能证明普遍规律或唯一原因 |
| 行为模式或人物印象 | 需要相关的实际观察、情境及反例检查；有用途但未充分确认时可形成显式暂定判断；与用户明确表达冲突时两者都保留（E-17） | 沉默、一次跳过或没有报错不等于确认偏好、认可产物或授予权限 |

`active` 等状态只表示当前可按条件使用或参与召回，不能代表结论已经被证明（E-12）。证据性质和不确定性独立保留；一次明确表达形成的认知也可能后来改变，暂定认知进入上下文时仍必须显露其限制。

### 5.8 对照例子：同一批感知不应全部升级成规则

承接新 Session 架构 §9.2 的“输出目录”例子，以下工具、事件和结果均为虚构 fixture。已有 `c-output@1` 错误地泛化为“tool-x 所有版本都必须显式指定输出目录”。整理 Goal 本轮读取：

| 材料 | 原始内容及关系 | 整理判断 |
|---|---|---|
| `p-301`，Work A | tool-x v1 / linux 省略输出目录时报 E_OUTPUT，加入 `--out` 后同一输入通过；来源 `A/call8`、`A/call9` | 保留一次失败与后续验证的条件；尚不能断言唯一原因 |
| `p-302`，UI | 转述 Work A 的 Final Report：“不写输出目录就失败” | 追溯到同一来源，不增加独立证据，也不当作用户偏好 |
| `p-303`，Work B | 同工具版本和环境下，另一个输入独立出现相同现象；来源 `B/call4`、`B/call5` | 支持同条件检查经验，不能据此扩展到所有版本 |
| `p-304`，Work C | tool-x v2 按当前规范省略目录，实际成功；来源 `C/call6` 及规范对象版本 | 是“所有版本都必须”的反例；v1/v2 分开处理 |
| `p-305`，UI | 用户：“记一下，本项目以后把产物统一放 workspace/build。”来源 `U/e7` | 一次明确表达足以形成项目约定；与工具是否强制 `--out` 是两件事 |
| `p-306`，旧写入路径 | “Goal 当前在等 Work D 返回”，无新增经验 | 仅为 Goal 状态副本，不形成认知；原状态仍由 Goal 保存 |
| `p-307`，Work D | 一次重要的远程输出异常，来源 `D/call3`；猜测可能为权限问题，尚无权限检查结果 | 保留具体异常，暂缓“由权限造成”的结论；等待可定位的检查结果 |

本轮拟议整理计划至少包含：

```text
修订 c-output@1 → @2：
  结论：tool-x v1 / linux 的上述使用条件下，生成产物前可优先检查显式输出目录。
  支持：A/call8、A/call9、B/call4、B/call5；A 的 Report 和 UI 转述不重复计数。
  反证依据：C/call6 及 v2 规范对象版本，保留在修订依据中。
  限制：v2 已有省略目录成功的反例；未证明输出目录是所有失败的唯一原因。
  复核：工具版本、环境或规范改变，或相同条件出现反例。
  召回入口：tool-x v1 + 生成产物；不要求新 Session 先知道 E_OUTPUT。

新增 c-project-output@1：
  结论：u1 要求本项目后续产物统一放 workspace/build。
  依据：U/e7 的明确要求；限定本项目，后续可由该用户修订。
  召回入口：本项目 + 生成/保存产物；不推广到其它项目。

材料处置：
  p-301/p-303/p-304 由修订后的经验及其依据承接；p-302 关联同源记录。
  p-305 由项目约定承接，保留明确记忆意图。
  p-306 丢弃，理由为仅重复 Goal 运行状态。
  p-307 暂缓，缺少权限/路径验证；对应新结果到达后再评估。
  先提交认知与逐条处置，再清理已吸收/丢弃正文；p-307 继续待处理。
```

这次整理同时完成了经验修订、项目约定提取、重复识别、噪声清理和缺证暂缓。后续模型输入应能看出 `c-output@2` 是带条件的经验建议，`c-project-output@1` 是用户明确要求；不能因为它们共享“输出目录”主题就混为一种事实。

### 5.9 Memory 整理 Goal 的运行与效果判断

该 Goal 的目标是维持可复用认知的质量和待处理材料的可控性。每次运行观察新增/到期材料、待复核认知、提交或清理失败项，按纠正的重要性、后续用途、积压与预算选择有限工作。

暂缓材料记录缺证原因及重评条件。下一轮既无新证据、也未到达既定复核条件时，避免重新消耗推理。记录复核条件不等于 Goal 自行唤醒，运行机会仍由 Runtime 提供。

暂缓不能无限期。每条暂缓材料有观察窗口上限（初值可取 72 小时，由原型校准）。窗口内出现用户独立再次提起、补充了上下文、相关世界对象出现时，可以提前重评；转述不算新信息（E-05）。到期必须实际处置，三选一：证据已够就形成认知；把握低就丢弃并写明理由；有价值但缺条件就只保留来源线索。到期处理要真正执行，查询时惰性过滤，再加后台兜底清扫：旧实现只落了状态词汇、没落状态跃迁，结果所有材料永远停在待处理。

缺的是用户确认时，暂缓材料可以附一个可澄清的问题，作为低优先级 Hint。UI 进入相关 topic 时显露它，由 UI 决定是否顺带问；用户的回答形成新感知。整理 Goal 本身默认静默，不主动打扰用户。这类问题受 M-20 的重复控制约束，不能反复追问；不问就会出错的事项归 Task 或 Goal（M-30）。

运行机会的成本也要控制。Runtime 给机会前，先用不调用 LLM 的廉价查询判断有没有新增、到期或待重试的材料。整理 Goal 自己的提交（认知、处置记录、运行记录）不算新材料，否则会自我唤醒；旧实现就出过“写处置备注推高更新时间、触发下一轮”的问题。选材料按处置状态，不只按时间窗口。可以先粗筛重复、噪声和纠正，只对需要的材料做深度综合。一轮完整表达应整体进入同一批次，优先于 token 上限；读取被截断时，只处置实际读到的部分。

本轮可报告“新增 1、修订 1、重复/噪声已处理、缺证暂缓 1、清理待重试 0”等结果；这是运行记录，不把报告再次写成待整理感知。预算不足、暂无材料或缺证时可以无动作结束本轮。不能把待处理数下降、认知数增加或本轮归零单独视为认知质量提高，更不能为归零删除暂缓材料。

经验认知可成为 Manual、Skill 或 XLLM 结晶的输入，能力缺口可成为 Self Correct 的候选输入；这些资产的验证、发布和具体行动仍归对应 Goal，Memory 整理完成不等于那些工作完成。结晶产物应记录所依据的认知 revision；认知被撤回或缩小范围时，Memory 提供变化通知或反向查询，由对应 Goal 自己重评，Memory 不修改这些资产。

## 6. 召回与显露：帮助 Agent 意识到需要查询

### M-18｜在显式检索之前提供触发机会

**明确方向。** 召回机制不能只提供一个“模型已经知道要查时才调用”的搜索接口。它应根据当前问题、任务、对象和近期观察，获得发现潜在相关认知的机会。

典型目标是：Agent 在本次任务中尚未想到某个偏好或历史限制时，系统可以提供一条有根据的线索，使其进一步读取或调整行为。

这不是要求无依据地随机插入记忆，也不是要求所有 Memory 每次都完整加入 prompt。

### M-19｜线索与完整认知可以分层显露

**明确方向与派生约束。** 可以先显露小粒度 Hint、topic 或对象线索，再由 Agent 判断是否读取更多信息。线索应足以说明“为什么可能相关”，并能找到对应认知或来源对象。

```text
当前输入 / 任务对象 / 观察结果
                ↓
寻找可能相关的认知及触发入口
                ↓
筛选出有限的提示：内容摘要、适用范围、引用
                ↓
Agent 意识到需要关注
                ↓
按需读取认知或查询世界对象，再继续任务
```

Hint 是否独立持久化、由整理阶段生成还是运行时生成，仍未确定；topic 可继续作为现有探索基础，但不被直接写死为唯一方案。

### M-20｜召回必须考虑范围、有效性与预算

**派生约束。** 相关性不能只看文字相似。对谁有效、针对哪个 Workspace、是否被用户纠正、是否对应被放弃版本，以及是否只是暂定推断，都会影响是否应该显露。

进入 context 的记忆应有明确预算。宁可提供少量可展开的线索，也不应把全部历史认知堆入每次模型输入，抵消 Work Session 短周期、上下文健康的设计目标。

同一条认知在同一阶段不应反复机械注入；进入新任务或新的相关情境后仍可再次召回。Memory 的重复控制不能简单照搬“某事件只通知一次”，否则一次使用后的重要认知可能永远不再出现。

排序可以使用**召回强度**：近期被提及、被实际用到、用户明确说过重要。它回答“值不值得想起”，和回答“可不可信”的证据性质分开表示，两者都随线索显露；重要但证据弱的认知，可以排得靠前，同时标明证据弱。召回强度只用于 Memory 内部排序（M-33）；计数先按来源去重，召回回声不计入（E-15）；它由召回层派生统计或由整理 Goal 提交，普通 Session 不在线修改认知（M-32）。

长期没被想起的认知可以逐渐降低排序，称为**淡出**。淡出不是删除，也不是 M-28 的遗忘。用户明确提出的偏好和边界不随时间淡出，只随修订改变；否则一条一年前的明确边界，会输给新近的噪声。

预算按类别分池。有效性变化（修订、失效、待复核）优先于普通线索；新近感知和已有认知各有保留额度，避免一批新感知挤掉关键认知。具体类别不固定（M-04）。

### M-21｜根据 Session 类型选择召回时机

**明确方向与派生约束。** Work Session 应在 Task 启动装配时尽量获得必要认知。UI Session 长期面对新话题与世界变化，需要持续获得相关线索。Goal Session 在恢复当前目标与状态、获得新观察或 Work Report 时，可按当前对象和问题更新关注范围。

Work 的基础关注范围由创建方或 Runtime 在创建时，按任务书中的 Task 引用和对象引用确定性建立；子 Session 的范围由创建它的父 Session 一并确定。模型可以追加关注，但不负责建立这份基础订阅，正确性不依赖模型是否设置了 topic。

除非显式关闭，Session 每次进入推理前都应有一次半订阅观察机会，包括同一次运行中工具返回后继续推理的时刻，不以收到新 Message 或开始新 Turn 为前提。Work 没有 Message input，也通过这条路径观察两类内容：自身 Task 对象的修订（必达，§9.4），以及已订阅 topic 的相关新感知和认知变化（尽力而为，M-30）。相关子 Session 按各自订阅范围和进度观察。通知本身不额外唤醒 Session，也不要求每次全库检索。

未经整理的感知必须以“新近观察 / 待整理材料”的身份显露。符合已订阅范围的感知新增也进入默认观察路径，使显式记忆请求在整理前即可使用。可随 function call result 一起装配到下一次模型输入，但须区分实际工具返回与 Runtime 附加的 Memory 观察，保留来源。具体承载格式、预算和排序留待实现收敛；预算外内容不得被当作已交付，Task 修订不受 Memory 召回预算截断。写入、可召回、进入上下文与被落实是不同状态（E-11）。

读过或被注入过某条认知的 Session，自动关注它之后的修订和失效，不依赖 topic 是否仍然命中；§5.2 要求“已读入 @1 的 Session 收到修订线索”，靠的就是这份记录。修订提示只带引用、版本和摘要，只由整理 Goal 的提交触发（M-32），推送前先过授权（M-25）。整理前的纠正只在召回和查询视图中派生“待复核”（§4.3），不经这份记录提示：topic 仍命中的 Session 通过范围匹配看到纠正感知，话题已转走的 Session 在再次召回该认知时由兜底获得。

观察进度只在材料成功装配后推进，并且只覆盖实际送出的条目；被预算压掉的条目不能一起跳过，旧 Notebook 实现就因此永久丢过提示。Session 自己刚写的感知不推回给它自己。模型追加的关注要有生命周期，规则见 §6.6。

### M-22｜被召回的内容不自动成为最高优先级指令

**派生约束。** Memory 可以影响理解和决策，但不能因为进入上下文就替代当前明确任务、有效授权或世界对象的真实状态。

外部文本进入感知或认知后，仍需保留其来源属性。不得通过“先写 Memory、再召回”的路径，把不可信内容升级为系统权限或可执行指令。

当 Memory 与用户当前明确表达或最新对象状态冲突时，应识别冲突，必要时查询、澄清或修正，不能静默坚持旧认知。

运行中任务的修改走 Task 修订，不经过 Memory（M-31）。Memory 里出现的用户要求转述只是有来源的材料：与任务书、Task 修订或用户当前表达冲突时，以正式对象和当前表达为准，必要时澄清。感知不会扩大权限，也不会让已结束的 Work 恢复运行。

### 6.1 常见召回入口：先有触发机会，再决定是否检索和注入

“召回入口”不是只有一个关键词搜索框。它首先是 Session 运行中的一个机会点，由 Runtime / SDK 根据已知输入、对象和状态变化决定是否寻找认知线索，不要求 LLM 先意识到具体哪条记忆存在。

| 入口 | 谁发起、何时发生 | 可使用的上下文 | 应产生的线索及边界 |
|---|---|---|---|
| Task 启动装配 | 创建 Work、装配初始上下文时，由创建方或 Runtime 执行 | 任务目标、用户、Workspace、工具和已有明确约束 | 尽量预装与本任务相关的偏好、经验和边界，避免执行中频繁补课 |
| UI 新输入 | UI Session 准备处理用户新消息时 | 当前输入、近期话题、已解析对象 | 用户只说“效果再活泼一点”，也有机会想起该项目“不闪烁”的要求 |
| Goal 恢复与新反馈 | Goal Session 获得一次运行机会，读取当前定义、状态和新 Report 后 | Goal 范围、关联任务、环境及待决问题 | 召回可复用经验；Goal 进度、授权和 Report 交付不依赖 Memory |
| Intent 分析 | 独立意图分析过程确定对象和任务边界时 | 候选项目、历史选择线索、待完成任务 | 提醒存在多个版本及历史选择；当前目标仍需读取世界对象确认 |
| 新对象或新话题 | 输入解析或工具结果首次涉及新对象时 | 新识别的人、项目、文件或工具引用 | 只补充与新增对象相关的认知，不因每个词变化而全库检索 |
| Action Result / Observation | 下一次正常推理前 | 工具标识、错误码、资源类型和结果摘要 | 出现已知错误模式时，显露带适用条件的经验 |
| 半订阅 Context Change | 除非显式关闭，每次推理前检查相关增量，包括工具返回后的继续推理 | 相关感知新增、认知被修订或失效、任务被放弃、对象换版等 | 带来源地显露新观察及失效/修订；Task 修订走 Task 对象订阅，不在此列；无需 Message input，事件本身不额外唤醒 Session |
| 多信道关联 | 当前信道缺少指代上下文时 | 同一授权主体、其他活动 UI Session 的可见 topic 或对象线索 | 提醒可能存在相关工作，再按权限查询；不复制另一个信道的完整对话 |
| 关键行动前的定向复核 | 即将提交、覆盖或执行具有副作用的操作时 | 当前目标、有效认知版本、已知变更 | 检查相关边界是否被纠正；Memory 不能替代权限检查和当前授权 |

Memory 整理 Goal 也会读取既有认知，但其目的主要是合并、冲突处理和修正，不应把这类内部读取混同于“给 UI 插入一条 Hint”。

每个入口可以先执行轻量的相关变化判断，再决定是否运行实际检索。不要将“每次 Observation 都有机会”实现成“每次都进行全量检索”。topic 的变化是这一判断的主要依据（§6.6），Hint 是输出线索，二者如何实现不在示例中固定。

### 6.2 自动召回的调用与返回示例

以下承接 5.2 中已经修订到 `revision=2` 的偏好。假设 Intent 分析已通过世界对象确定目标是 `snake-alpha`，用户说：“把这个贪吃蛇游戏背景再做得有动感一点。”

Runtime 可以在该机会点调用逻辑接口 `memory.recall(context)`，例如传入：

```json
{
  "trigger": "intent_analysis",
  "input_summary": "用户希望当前贪吃蛇项目的游戏背景更有动感。",
  "subject_refs": ["user:u1"],
  "object_refs": ["world:workspace:snake-alpha"],
  "topic_hints": ["游戏背景", "动效"],
  "phase": "planning",
  "budget": {
    "max_items": 3,
    "max_tokens": 600
  }
}
```

这里 `3` 和 `600` 只是展示预算参数的样例，不是已决定的性能指标或默认值。身份、授权、当前 Session 与去重进度由 Runtime 提供，不应要求模型手工声明访问权限。

自动召回要区分三种结果：未触发、已召回、失败。召回失败不影响主操作，也不推进去重进度。每条线索宜短，参考量级 20—50 token，只说明存在什么、为何相关、指向哪里，详情按需读取。

一次可能的返回结果：

```json
{
  "status": "ok",
  "memory_snapshot": "memory-snapshot:21",
  "items": [
    {
      "cognition_ref": "memory:c-snake-background",
      "revision": 2,
      "summary": "该项目游戏页允许缓慢移动的背景，但不应闪烁或干扰操作。",
      "scope": {
        "workspace_ref": "world:workspace:snake-alpha",
        "surface": "game_page"
      },
      "why_recalled": [
        "匹配当前工作区",
        "当前意图涉及背景动效"
      ],
      "detail_read_recommended": true
    }
  ]
}
```

这条线索使 Agent 在尚未主动搜索“不闪烁偏好”之前意识到它。`detail_read_recommended` 是展开提示，不是另一条认知，也不要求所有场景无条件再查一次。

相同认知、相同版本、相同任务阶段不应机械重复注入；进入新任务或认知修订到新版本后，可以再次召回。去重进度应按接收 Session / 上下文阶段维护，不能由一个 Session 的使用把其他 Session 的召回机会全局消耗掉。可持久化该进度以支持 Runner 恢复，但它本身不是认知正文。

### 6.3 主动查询接口：检索、对象读取、主体视图和来源追踪

当 Agent 已经知道需要查询什么时，需要直接、可预期的读取能力，而不是只能等待自动召回。以下四种能力可以由少量逻辑接口承载，不要求四套独立存储或四种专用协议。

| 查询目的 | 拟议调用方式 | 返回内容 |
|---|---|---|
| 查相关认知 | `memory.query(query, filters, limit, cursor)` | 满足范围、状态和权限要求的认知引用、摘要、版本及匹配依据 |
| 读一条已知认知 | `objects.read(ref, view="cognition")` | 当前有效认知内容、适用范围、证据性质与版本 |
| 查看对某个主体的认知 | `memory.query(filters, view="by_subject")` | 按人物、项目或对象组织的认知视图；复用相同认知引用 |
| 查“为什么这样记” | `objects.read(ref, view="provenance")` | 当前结论依据、历史修订及可访问的原始来源引用 |

`objects.read` 表示既有 DID Object / 世界对象读取能力的逻辑用法。`view`、`select` 等参数表达所需能力，是否映射为对象字段、子对象或现有协议参数，需后续确定；本文不另外发明 Memory 专用 DID 协议。

#### 6.3.1 按问题和范围检索

例如，Intent 分析已意识到需要检查背景效果要求，可调用 `memory.query(...)`：

```json
{
  "query": "游戏背景效果的偏好和限制",
  "filters": {
    "subject_refs": ["user:u1"],
    "applies_to": {
      "workspace_ref": "world:workspace:snake-alpha",
      "surface": "game_page"
    },
    "kinds": ["preference", "boundary"],
    "states": ["active"]
  },
  "include_recent_perceptions": false,
  "limit": 5
}
```

一种返回示例：

```json
{
  "status": "ok",
  "memory_snapshot": "memory-snapshot:21",
  "items": [
    {
      "ref": "memory:c-snake-background",
      "revision": 2,
      "kind": "preference",
      "summary": "该项目游戏页允许缓慢移动背景，但不应闪烁或干扰操作。",
      "basis": "user_statement",
      "match_reason": "主体、项目与页面范围匹配"
    }
  ],
  "next_cursor": null
}
```

`applies_to` 表达“对这个情境有效”，不只是匹配一段相似文字。如何纳入更广范围且确实适用的认知，需要定义明确的范围匹配策略；不能为提高召回率而自动混入其他项目的偏好。

此例对本次主动查询显式关闭了未整理感知读取，不改变 M-21 的默认半订阅观察策略。`include_recent_perceptions` 只控制普通近期感知；按 §4.3，同一范围内未整理的纠正类感知总会随认知返回。查询包含近期感知时，结果应分开返回 `cognitions` 与 `recent_perceptions`，后者明确标注“未整理 / 待确认”，不能混装成同一批有效认知。

#### 6.3.2 读取已知认知，不再依赖搜索排序

拿到认知引用后，可以使用通用对象读取：

```python
objects.read(
    ref="memory:c-snake-background",
    view="cognition",
    select=["ref", "revision", "statement", "scope", "state", "basis", "evidence_refs"]
)
```

投影后的内容示例：

```json
{
  "ref": "memory:c-snake-background",
  "revision": 2,
  "statement": "在该项目游戏页面中，背景可缓慢移动，但不应闪烁或干扰操作。",
  "scope": {
    "workspace_ref": "world:workspace:snake-alpha",
    "surface": "game_page"
  },
  "state": "active",
  "basis": "user_statement",
  "evidence_refs": [
    "session:ui-web-01/event/31",
    "session:ui-telegram-01/event/12",
    "session:ui-web-02/event/8"
  ]
}
```

不指定历史版本时，示例读取的是当前可用版本；若系统支持快照或固定版本读取，应显式说明。旧 Hint 指向 `@1`、对象已更新为 `@2` 时，返回方应让调用方识别差异，不能把历史内容伪装成当前结果。

历史来源参与形成过程，不代表每条来源都同样支持当前表述。哪些依据已被明确纠正，可以通过下一节的来源视图进一步判断。

#### 6.3.3 对象中心查询：形成视图，而不是复制一份“人物档案”

用户问“你记得我对这个项目有什么要求吗”，可按主体与项目查询，不需要事先知道关键词：

```python
memory.query(
    filters={
        "subject_refs": ["user:u1"],
        "applies_to": {"workspace_ref": "world:workspace:snake-alpha"},
        "states": ["active"]
    },
    view="by_subject",
    limit=20
)
```

视图应将偏好、边界、相关经验分别展示，并带上适用范围及认知引用。例如“游戏页背景不闪烁”仍指向 `c-snake-background@2`，不产生另一个独立维护、容易与原认知不一致的“用户画像文本”。

查询某人时不能仅按同名合并身份；查询某项目时也不能把它的要求提升为用户在所有项目中的偏好。跨信道是否可见，由授权主体和可见范围决定，而不是由视图类型决定。

#### 6.3.4 来源和修订查询：回答“你为什么这样认为”

例如：

```python
objects.read(
    ref="memory:c-snake-background",
    view="provenance"
)
```

返回应能表达当前依据与历史依据的不同角色，例如：

```json
{
  "ref": "memory:c-snake-background",
  "revision": 2,
  "current_basis": [
    {
      "event_ref": "session:ui-web-02/event/8",
      "role": "explicit_correction",
      "source_availability": "available",
      "excerpt": "这个项目游戏页可以用缓慢移动的背景，但仍然不能闪烁。"
    }
  ],
  "historical_basis": [
    {
      "event_ref": "session:ui-web-01/event/31",
      "role": "previous_preference",
      "source_availability": "available"
    },
    {
      "event_ref": "session:ui-telegram-01/event/12",
      "role": "scope_clarification",
      "source_availability": "available"
    }
  ],
  "previous_revision": 1,
  "previous_revision_state": "superseded"
}
```

感知正文已被清理，不影响该示例通过保留的原始 Session 事件追溯。但如果原始历史也已清除，应明确返回来源不可读取，不凭空生成“原话”；若无读取权限，则按访问控制返回受限信息，不通过来源摘要泄露内容。

是否保留完整认知版本历史及其保留期限，仍需制定策略。示例展示的是可解释修订所需的信息，不要求永久保存所有感知或全部历史。

### 6.4 查询契约中的常见边界

**派生约束。** 示例接口至少需要区分以下情况；具体错误码和返回格式未固定。

| 情况 | 应表达的结果 |
|---|---|
| 正常查询但未命中 | 可以返回空列表，但不能声称“这个人没有此类偏好”或“Agent 从未经历过此事”（E-14） |
| 存储不可用、索引未就绪或仅部分可查 | 明确返回不可用或结果不完整，不能伪装成正常空列表；按引用读取和来源视图不应依赖检索索引 |
| 名字匹配到多个对象 | 返回歧义候选及依据，不静默择一；未匹配时不自动新建对象 |
| 同一上下文重复读取同一范围，且版本未变 | 可以只回“未变化”短提示；范围不同不能判为未变化；上下文压缩、Fork 或重建后失效；同范围有未整理纠正时不算未变化 |
| 本范围还有待整理材料 | 可附待整理条数和最近一次整理时间（先过授权），让模型能如实说“记下了，还没整理完” |
| 返回条数受限 | 表达截断或分页信息；多页读取应有一致的结果边界，不悄悄混用不同状态 |
| 对象不存在或当前调用者不可见 | 遵循既有对象协议的访问语义，不泄露未授权对象是否存在 |
| 旧认知已被明确纠正、整理尚未完成 | 返回旧认知时附带同范围的纠正感知；写入方给出了认知引用时标为待复核（§4.3）；不能返回无提示的旧结论 |
| 读取的认知依赖一个世界事实 | 返回引用和适用条件；当前文件版本、选择状态等仍应通过世界对象读取 |
| 搜索命中来自不可信输入的指令性文本 | 保留证据性质，不把它变成系统指令或授权 |
| 来源已不可读 | 如实表示不能复核原文，不把认知摘要当作原始证据 |

例如，4.3 的纠正尚未整理时，即使显式关闭近期感知读取，对相关认知的查询也必须带回该纠正或待复核状态。

检索、对象读取、主体视图和来源视图都应先执行授权过滤。仅在读取全文时检查权限是不够的，因为摘要、Hint、主体关联和“存在一条相关认知”的提示也可能泄露信息。

### 6.5 贯穿示例：从“没想到要查”到正确构造新任务

```text
用户在 UI Session 中说：
  “把刚刚的贪吃蛇背景做得更有动感。”

UI / Intent 的机会式召回：
  发现有多个候选工作区，以及一条历史选择线索。
  若相关线索不可见或证据不足，不猜定目标。

Intent 主动读取世界对象：
  读取项目 selection，确认当前工作区是 snake-alpha。
  不是根据“哪个 Session 最新”来决定目标。

针对已确认对象再次匹配认知：
  显露 c-snake-background@2：
  “允许缓慢移动，但不要闪烁或干扰操作。”

按需读取认知：
  确认该要求仅适用于该项目游戏页，
  不把已被替代的“必须静态”当作现行要求。

创建新的 Task 与 Work Session：
  目标 = 增加背景动感。
  边界 = 不闪烁、不干扰操作。
  工作基础 = 世界对象确认的当前有效产物版本。

Task 执行及后续反馈：
  工具成功不等于用户认可；
  新的观察先写感知，用户反馈再参与后续认知整理。
```

这个流程不要求每一步都调用一次 LLM，也不要求 UI 承担深入调查。SDK 可以复用已经获得的对象状态和有效认知，Intent 过程负责必要探索，Task 则尽量带着充分上下文启动。新消息本身有明确约束时也应直接纳入任务，不能因为尚未进入长期 Memory 就忽略它。

### 6.6 topic 的维护：有上限的工作记忆

**派生约束。** topic 决定召回和半订阅匹配什么，它自己也会犯全局变量的毛病：只增不减，范围越来越宽，召回随之发散。因此 topic 应当是有上限的工作记忆。

| 规则 | 说明 |
|---|---|
| 组成 | 一行标题，写给未来的自己看，不是 Session 总结；加一组有上限的 tag |
| 分层 | Runtime 按 Task 和对象引用确定性建立的基础范围固定保留（M-21）；模型追加的 tag 参与衰减和淘汰 |
| 增强与淘汰 | tag 再次被提及时增强，随时间衰减，满了就机械淘汰分数最低的；被淘汰不等于信息丢失 |
| 何时更新 | 主题首次明确、显著漂移或进入长尾时更新；边角问答、内部中间步骤、细微展开不更新 |
| 追加关注的生命周期 | 模型追加的关注绑定到具体 tag，tag 被淘汰时关注失效，同类关注合并，Session 结束时清理；基础订阅与 Task 修订订阅不受影响 |
| 变化阀门 | §6.1 的“轻量相关变化判断”看 topic 的变化：新增和淘汰的 tag 比例、标题语义偏移、距上次召回的轮次或时间。变化大走深检索，只是到了间隔走轻检索，否则不检索 |

默认走机械召回：先做授权、范围、有效性和纠正状态的硬过滤，再排序。变化阀门打开时，才可以让模型做语义筛选，给出更准的线索、追加关注或决定暂不召回；超时按失败处理。

旧原型的参考初值：容量 8 个 tag，衰减时间常数 30 分钟，tag 变化比例达到 0.5 走深检索，距上次召回 5 轮走轻检索。这些是可配置项和评估起点，不是指标。衰减太快会丢掉刚讨论的方向，太慢会让旧话题残留；冷却太短打扰多，太长则话题迁移时反应迟钝。不同入口可以取不同策略：关键路径保守，空闲时积极。

## 7. 共享状态与访问控制

### M-23｜Memory 属于 Agent，不属于某个 Runner

**明确方向。** 同一 Agent 的不同 Session 即使运行在不同进程、不同语言的环境中，也应能够经授权共享持久 Memory。其连续性不依赖某个容器永远在线。

把 Memory 类比为 RDB，是强调共享持久状态及相应访问语义，不是要求所有 Runner 直接拿到数据库账号，更不是假定无协调并发写入天然安全。

### M-24｜跨进程读写遵循兼容约定

**派生约束。** 多个 Runner 的感知写入应可合并而不互相覆盖；认知整理产生的更新应有可识别的提交状态；读取方不应看到被误当成完整认知的半成品。

状态结构和对象接口需要支持必要的版本兼容。旧 Runner 面对无法理解的新结构，应明确报错或通过兼容层读取，不能静默丢弃字段并覆盖原认知。

不同 Session 何时看到新认知、是否采用快照读取以及如何收到失效通知，需要定义一致性规则。本文不预设所有读取都要求强一致，但“已经更新”与“所有 Session 已感知更新”必须可以区分。

§6.2 示例里的 `memory_snapshot`，定义为 Agent 级的单调版本或按范围的视图版本（组件实现为提交序号与各 Session 感知序号组成的版本向量，见 A.9）：每次提交都会改变它，包括状态变化、感知新增与吸收；读取不改变它；对调用方不透明。重复读取判断、缓存失效，以及恢复时“读取某快照之后的变化”，都以它为依据。

已提交的记录是真相源，检索索引是派生物，可以删除重建；修复工具不能静默改写真相或合并冲突。

### M-25｜共享不突破主体与信道边界

**派生约束。** 不同 Agent 的 Memory 默认不因共用存储而混合；某个 Agent 暴露给另一个 Agent 的对象范围，应受授权控制。

同一 Agent 服务多个用户或群组时，内部认知也可能具有不同可见范围。跨信道共享的线索、摘要和缓存均需遵循相同边界，不能只在读取完整正文时检查权限。

对人的印象、偏好等信息应尽量有明确主体引用；仅凭同名或相似文本，不应把不同人的认知合并。

## 8. 修正、任务放弃与记忆失效

### M-26｜区分任务经历与有效成果

**派生约束。** Memory 写入可能早于 Task 完成，任务之后也可能失败、被放弃或被回滚。感知和认知必须能够关联这些后续状态。

“某任务尝试过方案 A”与“方案 A 是当前采用方案”是不同信息。任务被否定后，后者不能继续作为有效认知使用；前者是否保留为经验，需要由策略决定。

### M-27｜任务结果失效时能定位受影响的 Memory

**派生约束。** Session 与产物版本关联应支持检查哪些感知、认知及召回入口依赖该任务结果。当一个结果被撤销时，应能对这些内容进行失效、重新判断或索引更新。

跨 Session 整理后的认知可能同时依赖多个来源，不能简单删除其中一个来源就断言整个结论必然消失，也不能因为存在其他来源就无条件保留原结论。需要重新评估剩余依据和适用范围。

这要求必要的来源关联，但不预先承诺能够精确计算一切模型推断的因果贡献。

### M-28｜不混同放弃产物、撤销认知与明确遗忘

**明确方向。** UI Session 应知道用户已放弃某次工作，后续不能继续以该成果为基础。

**待决设计。** 以下语义必须分别定义，不能由实现自行视为同一操作：

| 用户意图 | 必须进一步确定的处理范围 |
|---|---|
| 不采用这次任务结果 | 成果失效后，是否仍允许保留尝试过程及失败经验 |
| 把这次工作当作没发生过 | 除受管产物外，是否撤销相关感知、认知和召回入口；哪些最小生命周期信息仍需保留 |
| 忘记这条信息或这段经历 | 原始材料、派生认知、索引、缓存及其他受控副本各自如何处理 |

在默认策略确定前，不宣称 Task rollback 已自动清除了所有相关 Memory。

### M-29｜支持明确纠正与范围调整

**派生约束。** 当用户说明“那只是对这个项目的要求”或明确否定一条已有认知时，系统应能够缩小范围、撤回或替换，而不是保留原认知并新增一条同等有效的反向内容。

修正后，相应召回入口和缓存也应更新。旧消息或旧事件重放，不应无判断地重新恢复已撤销的认知；具体如何记录撤销依据与处理优先级，留待设计。

对明确遗忘的实现，只能承诺系统可控制的数据范围，不应将删除本地索引表述为已经删除所有外部源或外部副本。

认知状态至少区分：有效、已替代、有分歧、待复核或过期、已撤回。“有分歧”用来表示 M-14 要求保留的必要分歧。状态变更本身也是可回放的提交，由整理 Goal 完成；非法跃迁（如已撤回直接回到有效）要拒绝，或显式写明依据。重放旧事件不能让已撤回的认知复活。

## 9. 与 Session SDK、世界对象和半订阅的接合

### 9.1 四种连续性分别承担

| 连续性 | 承载机制 | 典型问题 |
|---|---|---|
| 一次执行的连续性 | Session 持久状态与 Runner 恢复 | 这个任务执行到哪一步了？ |
| 长期目标的连续性 | Goal 定义、当前状态、工作记录与关联 Work | 当前目标是什么，哪些事项在等待，下轮从哪里继续？ |
| 工作产物的连续性 | Workspace / 文件 / 世界对象的有效版本 | 下一次改进应基于哪个成果？ |
| Agent 内部认知的连续性 | Agent Memory | 过去有什么偏好、经验或边界值得想起来？ |

四者相互引用，不应互相替代。使用 Memory 不能免除读取真实产物，使用共享 Workspace 也不能自动替代对用户偏好与经验的理解。Goal Context 中的“目标级认知摘要”可以是该目标自己的恢复材料；只有符合 §4.4 的新观察才进入共享 Memory，压缩本身不构成新证据。

### 9.2 与实时变化感知的互补关系

Memory 提供过去形成的认知和新近感知；半订阅让相关 Session 在推理前意识到关注范围内的新变化。感知、认知与变化通知保持不同语义，通知不等于已形成认知。

例如，“某 Task 已被放弃”首先是生命周期变化；它可能使某个认知失效，也可能在后续整理中形成新的经验，但不是事件到达时就已经完成认知更新。

相关感知新增时就可进入半订阅增量，不等待认知整理；认知更新后再提供吸收、修订或失效提示。半订阅默认在下一次推理前观察，不额外启动推理。若另有主动订阅，其唤醒策略单独定义。

### 9.3 Memory 与 Session 架构共享的逻辑契约

| 契约 | Memory 一侧提供什么 | Session SDK 一侧提供什么 |
|---|---|---|
| 身份与授权 | 按 Agent 和可见范围组织读写 | 当前 Agent、执行主体及授权上下文 |
| 感知来源 | 可追溯的轻量观察记录，以及 §4.4 的内容筛选准则 | UI/Work/Goal 的观察机会、来源事件、Task/Goal 及目标对象引用 |
| 来源事件 | 以原始事件作为感知来源和认知证据（M-16） | 事件引用稳定，不随上下文压缩或 Runner 恢复改变；引用它的感知处理完之前不清除该事件 |
| 认知召回 | 有范围、有效性和来源的有限线索 | 当前任务、topic、观察机会与上下文预算 |
| 整理执行 | 跨 Session 材料、综合规则、认知提交、逐条处置与清理 | 维护型 Memory 整理 Goal 的上下文与预算；Runtime 的运行机会 |
| 任务失效 | 受影响认知的定位与处理能力 | 完成、放弃、回滚及产物版本状态 |
| 变化通知 | 感知新增、吸收，以及认知更新 / 失效的相关变化 | 默认每次推理前的半订阅观察及显式关闭；独立进度、去重、合并和注入机制 |
| Task 修订 | 不承载修订，只接收修订中另行写出的长期感知 | Task 对象的修订、确定性订阅与必达送达（§9.4） |

上述为逻辑信息要求，不强制某套字段名称，也不要求所有关联都由模型填入。

意图分析的 Context Fork 使用与所属 Session 一致的授权范围；复制的上下文沿用原始证据身份。放弃 Fork 不会撤销已写入共享 Memory 的内容，发现误写需走修订或撤回。Task/Goal 定义、Final Report 和当前世界状态继续走原有交付与读取接口；执行期的目标修改按 §9.4 写为 Task 修订，经 Task 对象半订阅送达，不转换成 Work 的 Message input，也不经过 Memory。

### 9.4 运行中修改与结束后修改：走 Task 修订，不走 Memory

**明确方向。** UI 收到对运行中 Work 的目标修改时，把它作为 **Task 修订**追加到该 Task 对象上，不写成感知（M-31）。这条修改必须送达，Memory 的尽力而为语义（M-30）承担不了。

| 要求 | 说明 |
|---|---|
| 内容 | 每条修订附原始用户事件的引用和原文，标明适用的子对象范围（如游戏页、计分数据），以及它与之前修订的关系：新增，或纠正第几条 |
| 写入者 | 只有持有该 Task 修订授权的主体能追加，通常是创建它的 UI 或 Goal |
| 订阅 | Work 创建时，由 Runtime 确定性建立对自身 Task 对象的半订阅；子 Session 由父 Session 在创建时按子对象范围建立。不依赖模型自行设置 topic |
| 送达 | 每次推理前随半订阅观察装配，包括同一次运行中工具返回后继续推理；不受 Memory 召回预算截断。无法装配时观察失败可见，不推进观察进度 |
| 次序与纠正 | 多条独立修订都保留，不按 topic 只留最后一条；纠正关系可见，其他仍有效的修订继续有效 |
| 边界 | 修订只能在已有授权和任务边界内调整；超出边界时按架构文档的执行边界让 Work 失败，不扩大任务 |
| 交付 | Final Report 写明已观察到的最后一条修订编号，以及每条修订的落实情况 |
| 生命周期 | 修订随 Task 对象保留，不进入 Memory 整理 Goal；“本次不记忆”等 Memory 策略不影响修订送达 |

及时生效指下一次已有的推理机会，不中断正在执行的工具，也不改写已发出的模型请求。Work 不因此成为可交互主体，也不为等待下一条意见而延长生命周期。观察到修订只说明它进入了上下文，是否落实由执行结果和 Report 说明。

Work 结束后，用户再提修改，由 UI 基于有效产物形成新 Task、创建新 Work，不唤醒已结束的 Work。编号大于 Final Report 所记“最后观察修订”的修订，就是旧 Work 没有处理的修改，由 UI 确定性地交给后续 Work，不需要靠模型对照反馈和 Report 来判断。

用户在修改里顺带表达长期偏好时（“这次改深灰，以后这个项目都别用亮色背景”），UI 除了追加修订，再写一条项目范围的感知。修订保证这次送达，感知供以后的任务召回，两者互不依赖。一次性调整不自动成为新任务的长期偏好（E-09）。

Memory 一侧的边界场景见 [组件模拟 TODO §3.11](../../notepads/agent-memory-multi-session-simulation-todo.md#311-场景六-运行中-work-的修改不经过-memory)。

## 10. 可验收场景

以下为需求验收场景，不表示已完成实现或测试。

| 编号 | 场景 | 通过条件 |
|---|---|---|
| B-01 | 应用没有手工编排记忆步骤 | 默认 Agent Session 仍能产生符合策略的感知；不要求调用方逐条创建 Hint。 |
| B-02 | 同一 Agent 的 Session 跨进程执行 | 共享持久 Memory；Runner 变化不造成内部认知从零开始。 |
| B-03 | 主任务中出现暂定观察 | 能低成本写入；不为写感知强制启动重型整理；暂定观察不立即被包装成事实。 |
| B-04 | 多个 Session 产生相关感知 | 整理能形成或修订认知，并保留适用范围和必要来源；不只是拼接摘要。 |
| B-05 | 两条感知存在冲突 | 能识别冲突或保留不确定性，不静默选一条冒充已确认结论。 |
| B-06 | 整理成功后清理材料 | 认知已可靠提交；已吸收的感知正文按规则清理；必要来源关联仍可用于修正。 |
| B-07 | 整理中途失败、重试或并发运行 | 不丢失尚未处理的材料，不产生无控制的重复认知，也不覆盖其他合法更新。 |
| B-08 | Agent 未主动想到相关偏好 | 当前情境能触发有限提示，再按需读取，而非只有显式搜索后才能使用记忆。 |
| B-09 | 同一认知只适用于特定项目 | 在无关任务中不被机械注入；改变适用范围后，召回行为相应变化。 |
| B-10 | 某个 Task 的结果被用户放弃 | 不能继续把该结果当作当前采用方案；可定位相关感知、认知及触发入口。 |
| B-11 | 世界对象版本发生变化 | Memory 中的缓存或判断不会自动覆盖最新世界事实；必要时查询并修正。 |
| B-12 | 用户明确纠正既有认知 | 原结论被修订、缩小范围或撤回；相关索引和缓存不继续无条件召回旧结论。 |
| B-13 | 多用户 / 多信道共用一个 Agent | 未获授权的 Session 不通过 Hint、摘要或缓存看到其他范围的记忆。 |
| B-14 | 感知包含外部指令性文本 | 内容仍按来源属性处理，不通过记忆召回获得系统权限。 |

### 10.1 原型阶段的评估重点

原型不能只证明“写入成功、搜索命中”。还应使用带有后续任务的样例，评估是否记住了真正影响工作的信息、是否在 Agent 没想到查询时提供了有用提示，以及是否因误召回而污染任务。

建议观察感知写入的额外成本、遗漏与噪声、认知范围是否准确、纠正是否生效、每次注入的上下文占用，以及整理失败后的数据完整性。样例需要包括没有值得记忆的内容、偏好仅限单个项目、任务被否定和多来源互相矛盾的情况。

具体数值门槛应根据原型基线确定，本版不凭空给出统一准确率或延迟指标。

### 10.2 新增示例对应的验收场景

这些场景检验的是行为与数据变化，不要求原型照抄示例字段名。

| 编号 | 对应例子 | 通过条件 |
|---|---|---|
| B-15 | 4.1—4.2：不同写入类型 | 短文本、结构化观察和对象引用可进入轻量写入路径；来源可区分；工具成功不被自动升级为用户认可。 |
| B-16 | 5.1：跨信道形成同一偏好 | 在同一授权主体及允许共享的范围内形成一条有项目边界的认知，不为每个信道复制冲突偏好。 |
| B-17 | 5.1：多入口与清理 | 不同入口能指向同一认知；可靠提交后清理感知正文；来源引用不只指向被删除的临时记录。 |
| B-18 | 5.2：明确纠正 | 旧版本不再作为当前有效结论；修订前的窗口内，召回旧结论时总会带回同范围的纠正（§4.3 兜底），写入方给出认知引用时显示待复核；新版本可以再次进入相关 Session。 |
| B-19 | 5.3：选择理由与当前版本 | 能想起选择线索，并读取世界对象确认当前目标；不按产物更新时间或最近 Session 猜定当前版本。 |
| B-20 | 5.4：带条件的经验 | 相同工具版本及错误条件可触发线索；范围变化时要求重新检查；弱观察不被强行整理为长期事实。 |
| B-21 | 5.5：放弃结果但明确保留经验 | 不再使用弃用成果；有独立依据且用户要求保留的经验仍可有效；不声称所有回滚默认采用此策略。 |
| B-22 | 6.1—6.2：机会式召回与去重 | LLM 未显式发起查询也能收到相关线索；不因每个 Observation 全库扫描；一个 Session 的消费不影响其他 Session。 |
| B-23 | 6.3：主动查询与可解释性 | 能按条件检索、按引用读取、按主体组织和追踪来源；各入口引用相同有效认知；不存在来源时明确说明。 |
| B-24 | 6.4：空结果、故障与权限 | 空结果和不可用可区分；摘要及来源视图均执行授权；不通过“相关记忆存在”的提示泄露受限信息。 |
| B-25 | 6.5：端到端新任务 | 正确选择工作对象，装配有效认知，创建有边界的新 Task，不依赖继续旧 Task 的消息流。 |

### 10.3 内容筛选与综合判断的验收

以 §4.5 和 §5.8 为基础建立评审样例。每条标注原始事件、Session 角色、已知范围及既有认知，给出预期的“记录 / 留在原对象 / 暂定观察”及理由；每组给出允许形成的结论、不能推广的范围、材料处置，以及未来任务应收到的具体线索。应保留可接受的多个整理结果，不用措辞完全一致作为正确性条件。

| 编号 | 场景 | 通过条件 |
|---|---|---|
| B-26 | 同时输入未来偏好、一次性指令、普通进度和异常 | 创建前的任务约束进入任务书；运行中的一次性修改写为 Task 修订，不进入感知；普通进度留在 Task/Goal，不要求每次交互都有感知 |
| B-27 | 用户只说一次“记一下，本项目以后……” | 与普通明确后续要求共用 Memory 路径；成功持久化才确认，整理前可有范围地召回；一次表达可形成窄范围认知，无独立 Notebook |
| B-28 | 同一工具事件被 Report、UI 和 Goal 摘要转述 | 保留原始来源关系，不按消息数量增加独立证据，不因压缩或跨 Session 转述提高结论强度 |
| B-29 | 同版本独立复现与新版本反例同时存在 | 缩小工具经验的范围、修订旧泛化结论；不把新版本行为平均掉，也不否定旧版本实际观察 |
| B-30 | 一批材料含偏好、经验、重复和缺证异常 | 产生可解释的不同处置；用户约定与工具经验分开；逐条交代已吸收、重复、丢弃与暂缓，不以生成认知数量为目标 |
| B-31 | 暂缓后又获得一次运行机会，但没有新证据 | 保留材料与缺证/重评条件，不重复深度分析、不强行归零；预算不足允许当轮不行动，长期 Goal 不因本轮无待办而完成 |
| B-32 | Task 失败、Goal 等待或世界对象换版 | 当前状态和 Final Report 由原对象及正式交付提供；Memory 只补充有用经验和线索，不用 Hint 代替执行状态与授权 |
| B-33 | Fork 产生假设后被放弃 | 不将假设写成用户确认，不把继承事件算独立观察；已发生的 Memory 写入不会因 Fork 结束自动回滚 |
| B-34 | 有效认知包含用户自述或暂定推断 | 注入内容保留证据性质、适用条件及不确定性；`active` 不被解释为已核验的客观事实；普通任务主题能触发线索 |
| B-35 | 工具缺失或操作经验值得进一步处理 | 形成带来源的候选并交对应 Goal 判断；整理本身不自动安装工具、发布 Manual/XLLM 或扩大任务授权 |
| B-36 | UI 修改运行中 Work 的目标细节 | 无 Message input 的 Work 在下一次推理前收到 Task 修订，包括同一次运行中工具返回后；不经过 Memory 和整理 Goal，不受召回预算截断，材料标明原始来源 |
| B-37 | UI 连续追加修订并纠正其中一项，存在相关子 Session 与无关 Work | 独立修订不丢失，纠正关系可见；子 Session 按创建时确定的子对象范围接收，各自进度独立；无关 Work 收不到 |
| B-38 | 关闭 Memory 半订阅，或用户要求本次不记忆 | 不注入 Memory 增量，不冒充已观察；Task 修订照常送达；不为半订阅另起推理，也不增加 Work Message queue |
| B-39 | Work 已结束，或修订在最后一次观察后才到达 | 按 Final Report 记录的最后观察修订编号，确定性识别未处理修订；不复活旧 Work，不虚报已完成；由 UI 创建新 Work，一次性修改不扩展为长期偏好 |

组件模拟验证写入、来源关系、查询、提交、通知和清理是否遵守预设计划；它不能证明模型会正确筛选和综合。接入真实模型后，使用同一组带标签样例分别评估写入遗漏/噪声、结论依据、范围扩大、同源重复、纠正效果，以及后续任务收到线索后的行为。故意加入“没有内容值得记”和“暂不形成认知”的样例，不能仅测试写入成功的正例。具体质量门槛由基线评估确定。

### 10.4 使用边界的验收

| 编号 | 场景 | 通过条件 |
|---|---|---|
| B-40 | 关闭召回，或召回预算为零 | 系统仍能正确运行：任务书、Task 修订、授权、Report 与世界状态都不依赖 Memory；Agent 只是缺少历史线索（M-30） |
| B-41 | 普通 Session 试图直接新增、修改或撤回认知 | 被拒绝；只能追加感知，认知变更只来自整理 Goal 的可靠提交（M-32） |

| 对象归一与去重 | 同名不合并（M-25）；原始提及可带解析候选（§4.2）；确认同一后由整理 Goal 合并并保留修订链（§5.6） | 别名线索的存储；建议分组键（merge key）由谁给出、如何索引 |
| 示例字段与查询接口 | 轻量写入、自动召回、主动查询和通用对象读取应能够衔接 | 最终语义类型、ObjectRef 表达、接口签名、视图映射、分页及一致性策略 |

下一阶段应优先通过具体场景检验认知模型，再确定存储和索引。不能因为 Hint-based recall 已有实现路径，就跳过“何时写入、写成什么、如何修正”的需求。

### 11.1 已知风险

按“先给能力”的取向，以下风险先记录在案，本版不增加隔离或审批机制。

| 风险 | 来源 | 当前缓解 |
|---|---|---|
| 整理前广播 | 半订阅默认开启，写一条感知就在整理之前推给所有 topic 匹配的 Session | 显露时标注“待整理”和来源（M-21）；不获得指令权威（M-22、E-13） |
| 误判扩散 | 一个 Session 的误读或推测，经感知进入其他 Session 的上下文 | 证据性质随材料保留（M-06）；整理时按来源核对（§5.6） |
| 外部内容注入 | Work 读取网页等外部材料后写下的感知，可能夹带指令性文本 | 保留来源属性，召回不升级为系统权限（M-22） |
| 宽范围认知的影响面 | 范围越宽的认知越像全局变量，一旦有误会影响所有任务 | 范围默认最窄（M-34）；复核条件随认知保存（M-05） |
| Memory 内容进入日志 | 调试日志、公共日志可能带出感知和认知正文 | 先记录在案；遗忘范围要覆盖日志中的副本（M-28） |

## 12. 本版非目标

本版不要求模拟完整的人脑机制，不把人物印象固化为不可修正的标签，不要求保存所有对话，不把聊天摘要直接等同于认知，也不强制使用向量数据库或知识图谱。新抽象不保留独立 Agent Notebook；Task/Goal 状态、用户文档及能力资产仍由对应对象和组件管理。Memory 也不用作 Session 之间的通信通道、运行状态存储或应用数据库（§2）。

**最终目标是让 Agent 在不显著干扰当前任务的前提下，把值得保留的经历转化为可修正的跨 Session 认知，并在未来尚未想到查询时，获得恰当的提醒。**

### A.2 继承的核心契约

- 每个 Agent 有且只有一个 Memory（单例 `memory_root`）；不同 Agent 不共享 `memory_root`（M-25）。
- 认知层的基础结构是 `key → item`。Graph 语义约束如何生成 canonical key 和索引 key，不是独立的图数据库，也不做开放式 N 跳遍历。
- `.meta/occasions.jsonl` 是追加写的提交日志和真相源。canonical item 与日志共同承载语义；state 快照、path 索引、`memory.sqlite` 都是派生物，可以删除重建（M-24）。
- 所有认知条目都是可修正的推断，不用 fact、truth 命名（M-05、E-12）。
- 淡出是不再召回，不是删除；`deleted` 是逻辑删除（tombstone）；显式遗忘的语义见 M-28。
- 同一 `memory_root` 同时只允许一个写者（`.meta/lock`）；只读端允许并发，容忍瞬时不一致。
- 跨语言互操作的边界是统一 CLI：digest、规范化和 replay 都在 CLI 内部完成，调用方不复现 canonical JSON。
- CLI 不构造对象、别名和 tag，不翻译，不做语言检测；这些由整理 Goal 和召回层提供。

相对 v2.10 的调整：写入者从“任意 Agent / curator”收窄为整理 Goal（M-32）；整理提交改为多操作原子提交（A.4.1，推翻 v2.10 B.9“不提供 commit”）；删除 Notebook 相关条款；增加 revision、适用范围、证据性质等字段（A.3.4）。这些调整对应 schema 3.0；2.10 根目录不再直接挂载，须经显式迁移（A.8）。

### A.3 数据模型

字段名与代码一致。kind、status、alias_type、`SourceRef.type`、`basis`、处置结果都是封闭枚举，非法取值在反序列化或提交校验时拒绝（TD-08）。下文标“新增”的字段均已实现（schema 3.0）。

#### A.3.1 来源引用与时间

```ts
interface SourceRef {
  type: "session_event" | "tool_result" | "file" | "url" | "manual" | "system";
  session_id?: string;
  event_ref?: string;        // 新增：原始 Session 事件引用（M-16、SDK S-31）
  message_id?: string;
  tool_call_id?: string;
  task_ref?: string;         // 新增
  goal_ref?: string;         // 新增
  uri?: string;
  digest?: string;
  actor_kind?: "user" | "agent" | "tool" | "runtime" | "system" | "third_party";  // 新增：由宿主核验；runtime 不能作为观察的来源（E-15）
  // 删除：notebook_id、item_id（Notebook 已取消；2.10 迁移时转写进 uri 并在迁移报告中列出）
}
```

时间规则：

1. `noticed_at`：条目被记录或再次被整理触及的时间，所有条目通用，只驱动淡出排序，不参与覆盖顺序；覆盖顺序以 occasion 的 `seq` 为准（继承）。
2. `occurred_at`：所述事情的发生时间，可以是估算（继承 v2.10 的双时间）。v2.10 把它限定为 occasion 专属；整理模式下一次提交会吸收多个时间点的材料，因此改为随证据观察保存，取自感知的 `occurred_at`（§4.2）。occasion 自身的 `occurred_at` 只表示提交时间。
3. 感知的 `observed_at` 对应原始事件时间，通过证据观察的 `source_ref.event_ref` 追溯，不另存一份。
4. 召回时刷新 `noticed_at` 属于召回层的派生状态，不写进提交日志（继承 v2.10 §3.2 第 3 条；同时满足 M-32）。

#### A.3.4 认知条目

```ts
interface MemoryItem {
  item_id: string;            // item_…；调整：作为认知的逻辑 ID，修订时保持不变
  revision: number;           // 新增：每次修订加一，历史内容可由提交日志 replay 得到（M-03）
  kind: "object" | "attribute" | "relation" | "event_effect" | "salience"
      | "observation_inference" | "free";
  semantic_kind?: string;     // 新增：§4.1 的语义类型，如 preference、boundary
  entities: string[];         // 对象 id；free 可为空
  claim: MemoryClaim;
  scope?: Scope;              // 新增：适用范围，默认取证据支持的最窄范围（M-34）
  basis?: "user_statement" | "tool_observation" | "third_party_claim" | "inference";  // 新增：证据性质（M-06）
  explicit?: boolean;         // 新增：用户明确提出，不随时间淡出（M-20）
  weight: number;             // 召回强度
  confidence: number;         // 置信度，只参与排序
  evidence: string[];         // 证据观察 id
  source_occasion: string;
  noticed_at: string;
  valid_until?: string;       // 新增：有效期，到期后召回层默认不显露（M-05）
  review_when?: string[];     // 新增：复核条件（M-05）
  produced_by?: { goal_run?: string; prompt_version?: string; model?: string };  // 新增：整理版本（M-05）
  write_reason: string;       // 为何值得记，必填
  status: "active" | "superseded" | "disputed" | "stale" | "deleted";
  replaces: string[];         // 合并或替代其他条目时使用
  replaced_by?: string;       // 新增：被哪条认知替代
  first_occasion: string;     // 新增：创建逻辑条目的 occasion（source_occasion 是当前 revision 的）
  free_key?: string;          // 自由条目的 key
  tags: string[];
}

type MemoryClaim =
  | { type: "object"; object_id: string; statement: string }
  | { type: "attribute"; subject: string; attribute: string; value: string }
  | { type: "relation"; subject: string; predicate: string; object: string }
  | { type: "event_effect"; occasion_id: string; affected_objects: string[]; effect: string }
  | { type: "salience"; object_id: string; reason: string; delta: number }
  | { type: "free"; key?: string; statement: string };
```

`Scope` 的组件阶段最小定义及匹配、可见性规则见 A.3.7；更多字段随 §11“示例字段与查询接口”收敛，参照 §5.1 示例的 `scope` 与 `exceptions`。

§4.1 语义类型的建议表达：

| 语义 | 建议的 kind / claim |
|---|---|
| 对象相关认知 | `object`，statement 描述对该对象的理解 |
| 偏好、边界 | `relation`（如 `prefers`、`avoids`）或 `attribute`，配合 `scope` 与 `semantic_kind` |
| 选择依据、经验、方法候选 | `observation_inference` 或 `free`，配合 `semantic_kind` 与 `review_when` |
| 事件背景 | `event_effect`，只记带时间条件的背景，不记阶段状态（M-04） |
| 第三方关系 | `relation`，谓词用稳定的 snake_case，方向有意义时保留方向 |
| 私有用语 | `attribute`（subject 为用户，attribute 为用语，value 为所指） |

继承的条目规则：每条都有 `kind`，缺省 `free`；自由条目可以没有对象锚点，但必须有内容、`write_reason`、weight 和 confidence；weight 与 confidence 分开，召回输出两者都要显露；关系变化不静默覆盖旧条目。调整：同一三元组且同一范围的关系再次写入时修订原条目，不再每次新建；范围不同则是另一条认知（TD-12）。

实现约定（schema 3.0）：任何内容或状态变化都让 `revision` 加一，每个 revision 的完整内容保存在 replay 出的历史里，按 `item_id@N` 读取且内容固定；自由条目按 key 原地修订，删除后同 key 再写是新的逻辑条目，不复活旧条目；任意 claim 可带可读的 `statement`，召回摘要优先用它；整理提交（`consolidation`）中的新认知或修订必须带证据观察、`scope` 与 `basis`。

#### A.3.5 状态与迁移

| 状态 | 对应 M-29 | 是否参与普通召回 |
|---|---|---|
| `active` | 有效 | 是 |
| `superseded` | 已替代 | 否，历史审查时可读 |
| `disputed` | 有分歧 | 是，显露分歧 |
| `stale` | 待复核或过期 | 否；纠正尚未整理时的“待复核”是召回层派生状态，不写这个值（§4.3） |
| `deleted` | 已撤回（逻辑删除） | 否 |
| `merged`、`deprecated` | 仅对象与别名 | 否；`merged` 跳转到 `merged_into` |

状态变更经 `set_status` 写入提交日志，可 replay；非法跃迁拒绝（TD-08）。已实现的规则：同状态不算变更；`deleted` 为终态；`superseded`、`stale` 恢复为 `active`（或 `superseded → disputed`）必须附证据观察；对象与别名的 `merged`、`deleted` 为终态，对象合并或删除时别名级联为 `merged` / `deleted` 并保留跳转。

#### A.3.6 salience 审计条目（继承）

每次增强对象权重派生一条 `kind = "salience"` 的条目，记录为什么调整权重。它只用于审计：不进全文索引，不建召回索引，不进 `load`，只能经 `get item` 或调试模式读取。

#### A.3.7 范围与可见性（新增）

组件阶段先用最小形式；§11 收敛后可以加字段，但匹配和过滤的判定点不变。

```ts
interface Scope {
  subjects: string[];     // 主体引用：用户、群组或 Agent 自身，至少一个
  objects?: string[];     // 对象路径，按 "/" 分段，如 "project:snake-alpha/game_page"；省略表示不限对象
  exceptions?: string[];  // 明确不适用的对象路径
}
```

| 规则 | 说明 |
|---|---|
| 对象重叠 | 两个对象路径中，一个是另一个的分段前缀（含相等）即重叠：项目级偏好适用于其页面，查询项目时也能看到页面级认知。按分段而不是按字符比较，`snake-alpha` 与 `snake-alpha2` 不重叠 |
| 范围匹配 | 主体有交集；双方对象至少有一对重叠（省略对象的一方与任意对象重叠）；查询对象不落在条目的 `exceptions` 之下。召回、半订阅变化（A.9）和 §4.3 “同主体、同范围”的纠正兜底都用这条规则 |
| 可见性 | 宿主为每个 Session 绑定授权主体集合（自身用户、所属群组，以及 Agent 自身）；条目、感知或证据观察的每个主体都在集合内才可见。可见性先于范围匹配执行，覆盖 Hint、变化提示、摘要、来源读取和“存在相关记忆”的提示（M-25、B-13、B-24） |
| 对象与别名 | 对象和别名本身不带范围，只经引用它们的可见条目或证据观察显露；别名歧义候选只列可见对象 |
| 写入 | 感知的 `subjects` 由宿主按写入 Session 的绑定补齐，模型只能在授权主体集合内收窄；认知范围由整理 Goal 按证据取最窄（M-34） |

相关性和可见性是两道过滤：对象重叠只说明相关，不代表有权看到。S 阶段接入真实授权时，可以把“授权主体集合”换成 ACL 查询，过滤位置不变。

实现补充（组件阶段）：

- `objects` 是并集：任一对象重叠即匹配。需要“工具 v1 且资源类型为 X”这类组合条件时，范围取能表达它的最窄对象路径（如 `tool:x/v1`），其余条件写进认知正文和 `review_when`，不要把多个条件对象并列在 `objects` 里，否则任一条件命中都会召回。
- 召回入口：双方都有对象且重叠时，范围本身就是一个结构入口（`scope:<path>`）；只有主体的认知需要 tag、全文或对象实体命中才进入候选。
- 主体为空的记录（旧 2.10 数据、Runtime 记录）对该 Agent 的所有 Session 可见，但不参与带范围的话题匹配。

### A.4 写入

#### A.4.1 整理提交（调整）

一次整理提交写成**一条** occasion：所有图操作加上逐条材料处置放在同一个 envelope 里，单行追加即原子提交，满足 M-15“认知变更与处置一起可靠生效”。实现为 `AgentMemory::commit_consolidation`，组件经 `Consolidator::commit` 调用；CLI 的 `commit --plan` 仍待 S 阶段（TD-03）。

```ts
interface ConsolidationCommit {
  occasion_type: "consolidation";
  idempotency_key: string;            // 同一批次重试返回已有结果（M-17）
  summary: string;
  produced_by: { goal_run: string; prompt_version?: string; model?: string };
  operations: GraphOperation[];       // 见 A.4.2，可以为空（纯重复/丢弃批次）
  dispositions: Array<{
    perception_ref: string;           // <sid>:<seq>
    outcome: "absorbed" | "duplicate" | "discarded" | "deferred";
    cognition_refs?: string[];        // 承接它的认知
    reason?: string;                  // discarded、deferred 必填
    reevaluate_when?: string[];       // deferred 的重评条件（§5.9）
    deadline?: string;                // deferred 的观察窗口上限
    clarify?: string;                 // 新增：缺用户确认时的低优先级澄清问题（§5.9）
  }>;
}
// envelope 另记：actor_session_id（真实整理 Session）、lease_epoch（整理 lease 的 epoch，
// 旧 epoch 的提交被拒绝）、plan_digest（同键不同计划报冲突）、produced_by
```

提交成功后，感知层清理 `absorbed`、`duplicate`、`discarded` 的正文，保留最小处置记录与来源引用；`deferred` 继续留在待处理集合（M-15、M-16、§5.9）。整理 Goal 自己的提交不算新材料（E-15）。

提交校验（新增，TD-03）：

- 每条 `perception_ref` 必须存在、对整理 Goal 可见，且尚未被终局处置。已是 `absorbed`、`duplicate`、`discarded` 的材料再次出现时，整条提交按冲突拒绝；同一 `idempotency_key` 的重试除外，它返回原结果。`deferred` 可以在后续提交中改为终局处置。
- 修订已有认知的操作带 `expected_revision`（A.4.2）；与当前 revision 不同则整条提交拒绝，整理 Goal 重新读取、合并后再提交，不用旧版覆盖新版（M-17）。
- 批次不落盘、不预留：同一时间只有一个整理 lease 持有者，lease 被接管后，重叠的处置由前两条拒绝。计划未提到的批次材料保持原状态，下次仍可选到。
- 实现补充：只能处置本批次实际读到的材料（含作为上下文读到的未到期暂缓材料）；`deferred` 必须有理由、重评条件和不超过配置窗口（初值 72 小时）的截止时间，再次暂缓不能晚于第一次的截止时间；`absorbed` 必须指出承接的认知，`discarded` 必须有理由；被引用的认知必须存在。
- 提交结果：`Committed`；`AlreadyCommitted`（同键同计划的重试）；`CommitUnknown`（追加或 fsync 中途失败，调用方用同一幂等键重试，写者先截掉未完成的尾行再按键查询，不会重复追加）；派生物重建失败时仍是 `Committed`，`derived = PendingRepair`，由下一次写入或 `verify --repair` 修复。

#### A.4.2 图操作（继承）

| 操作 | 字段 | 规则 |
|---|---|---|
| `upsert_object` | `object_id?, kind, canonical_name, aliases[{alias, alias_type, confidence}], evidence, weight?, confidence, merge_into?` | 没有匹配对象时新建；命中时可加别名或提升身份置信度；别名必须有证据，冲突不覆盖 |
| `add_observation` | `observation_id?, kind, entities, content, source_excerpt?, source_ref?, confidence` | 至少绑定一个对象，除非用来引入新对象；内容是可复用观察 |
| `reinforce_object_weight` | `object_id, delta(-1..1), reason, evidence` | 表示更值得想起，不是更可信；结果 clamp 到 0..1；派生 salience 审计条目 |
| `upsert_relation` | `subject, predicate, object, weight, confidence, evidence, write_reason, replaces` | 两端必须是已存在的有效对象；predicate 为 `[a-z0-9_]`；建 by_entity、by_pair、by_relation、by_predicate 索引 |
| `set_status` | `target_kind(item/object/observation/alias), target_id, status, reason, replaced_by?` | 状态变更经日志，可 replay；不直接改派生文件或 SQLite |
| `set_free` / `remove_free` | `key, content, reason, entities?, tags?, weight?, confidence?` / `key, reason?` | 写或逻辑删除自由条目；同 key 按 `seq` 覆盖 |
| `put_item` | `item_id?, kind, entities, claim, weight, confidence, evidence, write_reason, replaces` | 写入 object、attribute、event_effect、observation_inference 等显式条目，只经 `commit` |

`put_item`、`upsert_relation`、`set_status` 修订或改变已有条目时带 `expected_revision`（新增，A.4.1），新建条目不带。实现补充：`upsert_relation` 可带 `item_id` 与条目元数据（`scope`、`basis` 等）；`set_status` 可带 `evidence`（恢复被替代条目时必需）；`upsert_object` 不带 `object_id` 时按别名匹配：命中一个有效对象则更新它，命中多个返回 `Ambiguous`，未命中才新建；带 `object_id` 时允许与其他对象共享别名，提交结果列出共享情况（不覆盖对方）；每个操作的真实生成 id 由提交结果返回（TD-17）。

v2.10 §5“什么值得写入”与 §5.3 最小问题清单已由本文 §4.4、§5.7 取代。

#### A.4.3 管理操作

`init`、`verify`、`compact`、`migrate` 与逐条图操作保留给开发、迁移和人工修复使用，不给普通 Session（TD-02）。逐条操作为每次调用新建一条包装 occasion，被引用的 occasion 记在 `parent_occasion` 字段里，`actor_session_id` 为管理身份（TD-05）。组件门面经 `Memory::admin()` 提供这些操作。

### A.5 感知层

现有记录（`lib_opendan/src/protocol/agent_state.rs` 的 `PerceptionRecord`）：

```ts
interface PerceptionRecord {
  seq: number;                // 每个 Session 内严格递增，重复 seq 视为重放并丢弃
  at_ms: number;
  session_id: string;
  kind: "run_digest" | "observation" | "task_outcome" | "task_discarded";
  source: "session" | "self";
  tags?: string[];
  objects?: string[];
  summary?: string;
  payload?: unknown;
  refs?: unknown;
}
```

为满足 §4.2 新增的字段（已实现，TD-16）：`idempotency_key`、`content_digest`（清理后仍保留，用来识别同键不同内容）、`scope`（`subjects` 即主体引用，加对象与例外）、`suggested_kind`（含 `correction`）、`memory_intent`、`cites`（召回回声与纠正引用的认知，E-15、§4.3）、`anchors`（时区、语言区域、位置、意图锚点）、`occurred_at`、`source_ref`（事件引用、`task_ref`/`goal_ref`、`actor_kind`）、`mentions`（原始提及与组件附上的可见候选）、`backfilled`（补写标记）、`cleared`（清理后的处置标记）。

写入入口：Runtime 在运行结束时自动写 `run_digest`、`task_outcome`，任务放弃时写 `task_discarded`；模型经 `agent-session ctl perceive <text> [--kind] [--tag]` 写观察，“你记一下”也走这里（M-01）。追加要求持有 Session lease。组件库入口 `Memory::record_perception(caller, session_lease, input)` 由宿主绑定身份、授权主体、来源事件和记录策略：“不记忆”策略直接跳过、不写入；来源事件经宿主核验，Runtime 附加的 Memory 块不能作为来源；`cites` 必须指向可见的认知；回执返回 `<sid>:<seq>`、同范围已有认知引用（读不到 Graph 时省略）和提及候选。仍待 S 阶段：`ctl perceive` 的参数接线，`catch_up` 合成的运行摘要设置 `backfilled`（TD-16）。

整理读取：组件按逐条处置状态计算待处理集合（未处置、到期暂缓、已终局待清理），排除整理自身的 Session，同一来源事件的一轮表达整体进入同一批次；runner 的 self_improve 旧路径仍用字节偏移游标，S 阶段改接（§5.6 第 5 步、TD-03）。

写入幂等（新增，TD-16）：`idempotency_key` 由写入方给出，Runtime 默认取 `<event_ref>/<序号>`，同一来源事件的多条观察用不同序号；在同一 `<sid>` 内唯一。相同键、相同内容视为重放，返回原 `<sid>:<seq>`；相同键、不同内容返回冲突。正文清理后仍保留键和处置记录，重放不会让已清理材料复活。没有键的 Runtime 记录沿用现有的 `seq` 幂等。

一个感知文件只有一个 seq 分配者（Session 的驱动者，或组件阶段的模拟 Session；库入口可传显式 `seq`）：`seq` 已在文件中的记录只有与已存内容相同时才算重放，否则报错，不静默丢弃。追加前在短锁内修复上次中断的追加：未以换行结束的尾部是完整记录就补换行，否则截掉；最后一行损坏时读取末尾 seq 退回为扫描，单个文件损坏不影响其它 Session 的快照。

文件锁与清理（新增，TD-04）：现状每个感知文件只有一个写者，即持 Session lease 的 driver。整理要清理其他 Session 文件中的正文，而 UI Session 可能持续数天，不能等它结束。因此增加文件级短锁 `<sid>.jsonl.lock`：driver 追加时仍要 Session lease，并在追加期间持有短锁；清理持整理 lease 和该短锁，以“写新文件 → fsync → rename”替换原文件，只把已终局处置记录的正文换成处置标记，保留 `seq`、幂等键、来源引用和 `<sid>:<seq>` 身份。待处理集合由处置状态计算，不再按文件大小或字节偏移推导。

### A.6 召回与查询

#### A.6.1 召回管线

| 步骤 | 目标 | 现状 |
|---|---|---|
| 1. 入口 | topic 的标题与 tag、已识别的对象与别名、当前 Task 的对象引用（§6.6） | 组件：标题全文、tag、对象路径（经路径/DID 别名解析为 Graph 对象）、别名；全部为空时“未触发”。runner 仍只传 `state.topic.tags`（恒为空，S 阶段改接，TD-15） |
| 2. 硬过滤 | 授权、适用范围（A.3.7）、状态、有效期、纠正状态（M-20、§4.3） | 已实现：可见性、范围与例外、状态、`valid_until`、证据观察未删除；纠正以叠加方式标注（待复核 / 可能已被纠正），不隐藏认知 |
| 3. 候选 | 对象单点、对象对、有向关系的一到两跳展开；tag；全文（含证据观察与自由条目）；范围内未整理的感知与纠正 | 已实现：实体、对象对、有向一到两跳展开（上限 32）、范围对象、tag、全文（CJK 二元组 + 词，SQLite FTS5 与日志一致时用索引，否则内存扫描并在结果中说明）；感知层由组件按范围与入口另行召回 |
| 4. 打分 | `结构命中 + tag 位置加分 + weight×Wd + confidence×Cd − 淡出(noticed_at)`；明确提出的认知不淡出 | 已实现：实体 +12、对象对 +18、范围对象 +12、一跳 +6、两跳 +3、tag 8/4/2/1、全文每个命中词 +2（上限 5 个）、weight×10、confidence×6，淡出 `min(age_days/30, 20)` 可配置，`explicit` 不淡出；完整分项（`score_parts`）随结果返回 |
| 5. 预算 | 按类别分池，有效性变化优先（M-20） | 组件：有效性变化（待复核、可能已被纠正、替代、撤回及其纠正感知）优先，其后认知与新感知各有保留额度，剩余按序填充；预算外的引用进 `omitted` / `pending` |
| 6. 输出 | 摘要、适用范围、证据性质、revision、命中原因、是否建议展开（§6.2） | 组件 Hint 已带 layer、ref/revision、scope、basis、weight、confidence、状态、命中原因、来源事件、纠正引用、有效期、是否建议展开；runner 的 `<hints>` 仍只有 id、时间和一句话（S 阶段，TD-13） |

排序键继承 v2.10：`score DESC, weight DESC, confidence DESC, item_id ASC`。tag、对象、别名和全文都没给时视为“未触发”，不再按全局显著性返回全库前若干条（M-34，TD-10）。一次查询最多 32 个 tag、对象、别名，全文不超过 4096 字节；非空 tag 全部非法时报参数错误，部分非法时忽略并在结果中列出。

#### A.6.2 tag 规则（以代码为准）

trim 后 UTF-8 长度 2—32 字节；允许 Unicode 字母、数字、空格和连字符，至少含一个字母或数字；不允许引号、冒号、括号、星号和控制字符；连续空格归并为一个；大小写不敏感。允许短语 tag。v2.10 原定只允许 ASCII，代码已放宽为 Unicode，本文继承代码的做法，以适应中文为主的场景。

#### A.6.3 别名解析（继承）

trim、大小写归一、空白归并后匹配：命中一个有效对象就加入对象集合；命中多个时返回歧义候选（`ambiguous_aliases`，各候选附名称与别名证据，只列调用者可见的对象），不静默选择；命中已合并对象时跳转到 `merged_into`；未命中时不自动新建对象。写感知时的原始提及也按这条规则附候选，但不在写入时择一。

#### A.6.4 输出格式（继承并扩展）

`load` 的默认文本格式，每条记录以长度前缀给出正文，以 `END` 结束：

```text
ITEM <item_id>
KIND <kind>
ENTITIES <comma-separated-object-ids>
WEIGHT <0..1>
CONFIDENCE <0..1>
SOURCE_OCCASION <occasion_id>
NOTICED_AT <iso8601>
EVIDENCE <comma-separated-observation-ids>
MATCHED <comma-separated-tags-or-index-handles>
SIZE <n>
TRUNCATED <0|1>
---
<exactly n bytes of UTF-8 claim summary>
END
```

`MATCHED` 可以是 tag 或索引句柄，如 `entity:obj_a`、`pair:obj_a:obj_b`、`scope:<path>`、`hop2:<obj>:via:<item>`、`fts:observation`。`REVISION`、`BASIS`、`SCOPE`、`STATE` 四行已加入文本输出；`--json` 输出与其中的 `ambiguous_aliases` 仍待 S 阶段（TD-06、TD-13）。默认 `--max-records 50`、`--max-bytes 65536`；第一条即使超过字节上限也保留。CLI 的 `load` 是管理读取：不按授权过滤，未触发时输出为空。

召回结果区分未触发、已召回、失败与存储不可用；失败不能返回空列表（§6.2、§6.4，TD-01）。组件已按此实现（`NotTriggered` / `Recalled` / `Unchanged`，错误分为锁超时、损坏、不可用、参数错误）；runner 召回处的 `.unwrap_or_default()` 仍在，S 阶段移除。

```text
│   └── by_kind/  by_alias/  by_entity/<obj>/{obs,item}/  by_pair/  by_predicate/  by_relation/<s>/<p>/<o>/
├── graph/{objects,observations,items}.jsonl   # replay 后的快照，可重建
├── memory.sqlite                              # 派生查询缓存（含 FTS5 表与 graph_seq），可重建
└── .meta/
    ├── meta.json        # schema_version 3.0、primary_language mul、tokenizer、time_model 等
    ├── occasions.jsonl  # 唯一的追加写真相源
    ├── lock
    ├── archive/occasions_<首个 seq>.jsonl + archive/manifest.json   # compact 归档及清单
    └── legacy-2.10/     # 显式迁移时移走的旧日志、旧 meta 与旧快照（不删除）
```

提交日志每行是完整 envelope，含 `schema_version, occasion_id, seq, occurred_at, noticed_at, occasion_type, actor_session_id, lease_epoch, idempotency_key, plan_digest, produced_by, parent_occasion, source_ref, summary, tags, operations, dispositions, digest`；digest 由组件计算（blake3），覆盖除 digest 外的内容。`actor_session_id` 是真实的整理 Session 或管理身份（TD-05）。

写入顺序：取锁 → 截掉上次中断留下的未完成尾行 → 按幂等键查已提交结果 → 校验 lease epoch → 分配 `seq` 与缺省 id → 在内存副本上按提交规则应用（失败则不写任何东西）→ 以 `O_APPEND` + `fsync` 追加 envelope → 重建派生物（canonical 文件、graph 快照、path 索引、SQLite，各自写到旁边再换入）→ 释放锁。追加成功即视为已提交；之后的步骤失败不影响真相源，结果标 `PendingRepair`，由下一次写入、`repair_derived` 或 `verify --repair` 重建；追加之前失败不得留下可见状态。

replay 顺序：清单中的归档 → 当前日志，按 `seq` 确定，冲突时报错，不静默修复；清单列出的归档缺失或内容与清单不符视为损坏；条目状态按最后一次 `set_status` 或 `replaces` 生效；引用的 `source_occasion` 不存在时 `verify` 必须报错。读者忽略当前日志末尾未以换行结束、也无法解析的内容（正在追加或中断的写入）；中间行损坏则报损坏，召回与观察返回错误，不返回空结果。

`verify` 检查日志行完整性（含未完成尾行）、`seq` 单调、digest、操作 schema、归档清单、别名共享、证据与来源引用完整性，以及 SQLite 的 `graph_seq`、path 索引与 canonical 文件；不带 `--repair` 只报告；`--repair` 只重建派生物，不改写提交日志，不合并共享别名。`compact` 归档当前日志、写清单、新建空日志并重建派生物，不生成状态快照（TD-23 取“去掉快照”），不删除已淡出的条目；归档后 `memory_snapshot` 的 `graph_seq` 取清单中的最大 seq。归档按“硬链接当前日志为归档文件 → 写清单 → 以空文件原子替换当前日志”的顺序进行，读者在任何时刻都看到完整的图；replay 跳过归档与当前日志中 digest 相同的重复 envelope，同一 seq 内容不同仍是损坏。`migrate` 先把原文件复制到 `legacy-2.10/` 并写完成标记，总是从这份副本转换，最后才写新 meta，中途崩溃后重跑结果相同。

写者锁使用 `flock`，默认等待 5 秒，超时退出 `2`；只读端不持写锁，按日志的长度与 inode 缓存 replay 结果（TD-21）。兼容规则：`schema_version` 主版本不一致拒绝读写（返回需要迁移），次版本、`primary_language` 或分词器不一致只读挂载（TD-24）。2.10 → 3.0 只能显式迁移（`AgentMemory::migrate`）：按旧序列化逐行校验 digest，逐字段转换，无法一一对应的取值（未知枚举、Notebook 来源等）映射到兜底值并逐条列入迁移报告，旧文件移到 `.meta/legacy-2.10/`。

### A.9 topic、半订阅与观察进度（新增）

本节是组件阶段的接口约定，已在 `lib_opendan/src/memory/` 实现（TD-15、TD-18 的组件部分）；真实 Session 的保存位置与每次推理前的调用留给 S 阶段。

**分工：订阅状态归 Session，Memory 只回答“某个快照之后有什么变化”。** Memory 不保存订阅注册表，不知道有哪些 Session 在关注，也不主动推送。每个 Session 在自己的运行状态里保存观察状态（与《OpenDAN Agent Session 架构设计》§11.6 中的订阅和观察进度一致），每次推理前凭它向 Memory 拉取变化。因此不需要另建变化日志：提交日志和感知文件就是变化的来源；Session 结束时，它的关注随之消失。

```ts
// 对调用方不透明（M-24）；组件内部是版本向量
interface MemorySnapshot {
  graph_seq: number;                    // occasions.jsonl 的最大 seq
  perception: Record<string, number>;   // <sid> → 该 Session 感知文件的最大 seq
}

// 保存在 Session 运行状态中；组件阶段由模拟 Session 持久化到自己的目录
interface ObservationState {
  enabled: boolean;                     // 显式关闭 Memory 观察时为 false
  topic: {
    revision: number;                   // 标题或 tag 变化时加一
    title: string;
    base_scope: Scope;                  // 创建方或宿主确定性建立，不参与淘汰（M-21、§6.6）
    tags: Array<{ tag: string; score: number; touched_at: string }>;  // 模型追加，有上限
  };
  snapshot: MemorySnapshot;             // 已成功装配到的位置
  pending: string[];                    // 已检出但因预算或装配失败未送出的引用，有上限，下次优先
  read_set: Record<string, number>;     // item_id → 已装配过的 revision（读过即关注）
  last_query?: { at: string; topic_revision: number };  // 变化阀门使用
}
```

感知分量按 Session 独立推进，写感知不需要 Agent 级计数器或锁（M-12）；清理不改变 `seq`，处置写在提交日志里，会推进 `graph_seq`。

Memory 提供的调用（逻辑名，不是最终签名）：

| 调用 | 输入 | 返回与规则 |
|---|---|---|
| `query_topic` | 可见性绑定、范围（基础范围加当前 tag）、层次、预算 | 先取当前快照再读内容：结果覆盖快照之前的全部提交，快照之后的写入一定出现在后续增量里；两边可能重叠，调用方按引用加 revision 去重。返回两层 Hint、快照、截断与续读信息 |
| `changes_since` | 快照、范围、`read_set`、可见性绑定、上限 | 返回快照之后对该 Session 可见的变化引用：范围内的新感知、处置标记、认知新增、修订与状态变化，以及纠正感知派生的待复核；`read_set` 中的认知只要有整理提交的修订或状态变化就返回，不看范围是否命中。快照后新增、但已被清理的感知只返回处置和承接认知。附带新快照；变化数超过上限时返回 `resync_required`，调用方改用 `query_topic` 重建 |
| `read(ref, view)` | 引用、视图 | 读当前版本或固定 revision；已清理的感知返回处置标记和承接认知，不返回旧正文 |

Session 侧的库函数（组件提供实现，状态由 Session 保存）：

- `set_topic`：更新 `topic`，参数相同则幂等，标题或 tag 变化时 `revision` 加一。按 §6.6 的变化阀门选择深检索、轻检索或不检索，需要检索时调用 `query_topic`。被淘汰的 tag 不再进入之后的查询范围，绑定在它上面的关注随之失效，不需要通知 Memory。
- `observe`：每次推理前（显式关闭除外）先取 `pending`，再调用 `changes_since`；排除自己写的感知（`<sid>` 等于自身）；按 M-20 的分池预算装配。
- 确认：只有成功装配后，才把 `snapshot` 推进到返回的新快照，把预算外的引用放入 `pending`，把实际装配的认知记入 `read_set`；装配失败时什么都不推进。确认只写 Session 状态，不调用 Memory，也不表示要求已被理解或落实（E-11）。`pending` 溢出时改用 `query_topic` 重建。

其他规则：

- **快速路径**：快照与当前版本相同就直接返回空变化。判断只看 `occasions.jsonl` 和各感知文件的末行 `seq`，不打开 Graph、不取写锁、不 replay（TD-21）。每次推理前都会调用，这条路径必须便宜。
- **已读修订提示只由整理提交触发**（M-21）。整理前的纠正只在召回和查询视图里派生“待复核”（§4.3）：topic 仍命中的 Session 经范围匹配看到纠正感知；话题已转走的 Session 在再次召回该认知时由兜底获得，`read_set` 不为它产生提示。
- **运行摘要不做变化提示**：Runtime 自动写的 `run_digest`、`task_outcome`、`task_discarded` 只进入整理批次，可按引用读取，不出现在其他 Session 的 `changes_since` 里；Session 进度留在 Task/Goal（M-31、B-26）。
- **时效**：快照不随时间变化；返回缓存或判定“未变化”时，仍检查 `valid_until`、暂缓 `deadline` 等时效条件。
- **重启**：Session 重开后从保存的 `ObservationState` 继续；Memory 一侧没有需要恢复的订阅状态。

实现补充（组件阶段）：

- `ObservationState` 另存 `shown`（本 topic 阶段已显露的引用与状态，用于去重；有效性状态变化不被它压掉）、`context_generation`（Fork、压缩、重建后加一，使“未变化”失效）、`resync_required`；`last_query` 另记缓存键（身份、范围、上下文代次）、快照、是否显露过纠正和最早到期时间。`pending` 的引用编码为 `c:<item>`、`p:<sid>:<seq>`、`r:<item>`（待复核）、`q:<sid>:<seq>`（澄清），送出前按当前状态重新推导并重新校验可见性。
- `set_topic`：标题漂移达到阈值（标题全文词的 Jaccard 距离 ≥ 0.5）视为切换话题，未再次提及的 tag 随之退出，`shown` 清空开始新阶段；只追加 tag 是细化，不清空 `shown`。tag 衰减到 0.05 以下时移除。`resync_required` 时阀门直接走深检索。轻检索在缓存键、快照、话题 revision 都相同、没有显露过纠正、也没有到期项时返回“未变化”。
- `accept_recall`：首次召回或需要重建时采用召回结果的快照；之后的召回不前移快照，让两次之间的已读修订仍经 `observe` 送达，重叠由 `shown` 去重。`observe` 返回 `resync_required` 时，确认只把 Session 标为需要重建，下一次 `set_topic` 走深检索并采用新快照。
- 已显露过的感知也算“读过即关注”：`observe` 把 `shown` 中的感知引用并入传给 `changes_since` 的 `read_set`（值为 0），这些感知被处置时，即使清理后已不再匹配 topic，也会收到处置标记；清理保留 `tags`。
- Hint 的来源事件、关系展开与来源视图中的已吸收感知只列调用者可见的部分。
- `changes_since` 的变化类型：新感知、感知处置（含已清理的只给标记）、新认知、修订、状态变化、待复核（新的带引用纠正）、已读修订（`read_set`）。同一 Session 自己写的感知不回推；Runtime 记录不出现；超过上限返回 `resync_required`。
