> 版本：v1.0  
> 日期：2026-10-10  
> 面向：OpenDAN / BuckyOS 架构、Runtime、Agent SDK 与产品实现团队  
> 文档性质：新的架构设计目标；根据本次连续讨论收敛，不作为现有代码已经全部实现的声明。原《Agent Session》与事件订阅设计已合入本文；现有实现的可复用基础与迁移差距见 §15.5—§15.6，不以实现现状收缩设计目标。

Memory 内容规则见[《Agent Memory 认知管理需求》](<Agent Memory 认知管理需求.md>)：§2 定义使用边界（Memory 不承载正确性、不作 Session 间通信通道、认知只由整理 Goal 写入），§4.4—§4.6 定义什么值得记录为感知，§5.6—§5.9 定义综合与认知形成条件。本文定义使用方职责与运行方式，两者共同约束 Memory 整理 Goal。

## 设计摘要

OpenDAN 将 Agent 的主要 Session 工作模式划分为 **UI Session、Work Session 和 Goal Session**。分类依据不是简单的“有没有用户输入”，也不是单纯的运行时长，而是每一种 Session 承担的责任、持有的上下文以及任务边界。

**UI Session 是交互入口。** 它长期响应用户输入，不以完成某一个固定任务为存在目的。复杂意图分析通过 LLM Context Fork 隔离，执行工作下沉到 Work Session，主会话主要保留用户决策、关键线索和结果。

**Work Session 是有界执行单元。** 它在任务目标、关键依赖、运行环境、Workspace 和结束条件已经明确后创建，在既定边界内执行，允许成功，也必须能够明确失败，最终输出 Final Report。它不能通过持续等待需求确认、Issue 关闭或外部反馈，把一次执行变成长职责。

**Goal Session 是长期目标的推进单元。** Goal 首先是持久化目标对象，而不只是一种会话名称。围绕同一个 Goal，Goal Session 在多次唤醒之间积累上下文，每次观察现状、评估与目标的距离，在资源预算内决定不行动、直接行动，或者创建具体的 Work Session。它不负责决定自己何时被唤醒。

原有 Self Check、Memory 整理、结晶和 Self Correct 中适合目标驱动的部分，可以用不同 Goal 统一承载。“Self Improve”更多描述目标的用途，不再适合作为所有无新用户输入行为的统一分类。

能力资产同时分层：**Goal 使用偏方法论、判断与工作流组织的 Skills；Work 使用偏具体操作与 SOP 的 Manuals；XLLM 是配置化的单次 LLM 推理工具，不属于 Agent Session。**

事件处理区分三种语义：**PendingTool 恢复当前执行，主动订阅触发新的运行机会，半订阅为已有推理补充相关环境。** 半订阅默认在每次推理前提供观察机会，不依赖用户新消息，也不自行唤醒 Session；三种机制共同遵守同一 Session 串行推进、输入有来源、观察与执行结果分开的约束。

## 1. 背景、范围与设计原则

### 1.1 当前分类暴露的问题

原有分类大致区分 UI Session、Work Session 与 Self Improve Session。前两者通常有明确输入，后者则承接没有新用户输入、由 Agent 自主运行的工作。

随着实际使用，这种分类产生了两个主要问题。

其一，**Self Improve 变成了过于宽泛的集合**。例如，从 Notebook 取出 Item、结合当前情况判断是否提醒用户，与整理 Memory、总结 Skills、补齐工具，并不是同一种业务目的，却都因为“没有新用户输入”被放在一起。无新消息不等于无目标、无状态或无信息来源。

其二，**Work Session 的边界不断被放宽**。部分实现利用等待 Task 的能力，让 Work Session 持续等待外部确认、Issue 关闭、新评论或新的条件。这使得一次任务执行变成长期跟踪，既增加上下文负担，也模糊了任务是否成功、何时失败以及何时应重新决策。

本次改造不是增加一个新的名称来覆盖旧问题，而是重新明确：哪些工作属于一次有界执行，哪些工作需要长期承担责任。

### 1.2 本文范围

本文定义三类 Session 的职责，明确 Task、Goal、运行轮次、上下文、工具与能力资产之间的关系，并给出迁移和实现建议。

本文不重新设计 BuckyOS 的基础消息网络、权限体系、进程调度或全套 Agent Memory 数据模型；这些能力继续通过现有系统接入。本文也不将每一种业务 Goal 都固化成新的 Runtime Session 类型。

本次分类不要求穷尽所有未来 Agent 行为。允许存在其他模式，正是严格定义 Work Session 的前提。

### 1.3 核心设计原则

| 原则 | 含义 |
|---|---|
| 交互、执行、目标分离 | UI 面向用户，Work 面向确定任务，Goal 面向持续目标状态。 |
| 复杂过程隔离，必要结果返回 | 深度探索与执行不默认进入 UI 主上下文；通过 Report 和产物引用传递。 |
| 明确任务才创建 Work | 关键需求和依赖在创建前收敛，而不是在执行中反复要求用户补充任务书。 |
| 失败是合法结果 | 不通过偷偷改目标、长期等待或无限重试伪装成功。 |
| 长期变化交给 Goal | 环境变化、持续跟踪、优先级调整和新的任务决策由长期目标层承担。 |
| 唤醒与目标推进解耦 | Runtime 决定什么时候给执行机会；Goal Session 决定机会内做什么。 |
| 目标运行受预算约束 | Agent 在预算内选择行动，不因 Goal 长期存在就获得无限推理或执行额度。 |
| 上下文隔离不等于世界隔离 | 文件、代码、消息和共享 Memory 仍可能产生真实副作用，不能把 Fork 当作事务回滚。 |

## 2. 术语与核心对象

### 2.1 术语统一

本文统一使用 **OpenDAN**。口述中的 OpenAI，以及 Go / go session、Worker Session、future 等转写，在本次设计语境中分别归一为 OpenDAN、Goal / Goal Session、Work Session、Feature Request。

`try_create_work_session` 是此前的功能名称；`try_analyze_user_intent` 是本次倾向采用的更广泛语义。最终接口名称仍待实现阶段确定。

Memory 整理的方向统一为 **感知 → 认知**。口述中曾出现的反向表述，不作为数据流定义。

### 2.2 核心对象

| 对象 | 定义 | 不应混淆的概念 |
|---|---|---|
| Agent | 具有身份、授权、共享认知及一组运行职责的主体。 | 不等于一个进程，也不等于一个聊天窗口。 |
| Session | 持有连续上下文与运行状态的逻辑工作容器。 | 不必长期占用计算进程；也不天然隔离外部状态。 |
| UI Session | 以持续响应用户为职责的交互 Session。 | 不是一个不断追加所有工具输出的万能执行会话。 |
| Task | 已收敛、可执行、具有结束条件的具体任务定义。执行期可由授权方追加 Task 修订，原任务书保持不变。 | 不是尚待条件逐渐成熟的长期愿望；Task 修订是任务数据，不是 Memory。 |
| Work Session | 执行一个确定 Task 的有界 Session。 | 不是等待开放条件的长期观察器。 |
| Goal | 可持久化、可调整、具有边界及状态评估方法的目标对象。 | 创建 Goal 不等于立即启动一个常驻进程。 |
| Goal Session | 围绕 Goal 积累认知并持续决定行动的 Session。 | 不等于 Goal 对象本身，也不要求每次运行完成整个 Goal。 |
| Activation | Goal Session 被唤醒后的一次有限运行机会。 | 可以包含多次推理及工具调用；不等于新的 Goal，也不强制与一个 Turn 一一对应。 |
| Turn | 从输入到结果或明确结局的一次逻辑工作轮次，可包含多次模型推理、工具调用与上下文切换。 | 不等于一次模型调用、一次 run/resume 调用或一个目标的生命周期。 |
| Run | 某个 LLMContext 的一次可持久化执行，包含快照与调用状态，可挂起后恢复。 | 一次恢复不自动开启新 Turn；Session 可以保留多个上下文，但同一时刻串行推进。 |
| Context Fork | 在独立上下文分支中展开分析，仅将选定结果返回父上下文。 | 不代表另建 Agent 身份，或自动获得文件和世界状态隔离。 |
| Workspace | 执行工作所使用的项目、目录或产物空间。 | 可以跨 Session 复用，但不意味着应共享完整聊天上下文。 |
| Final Report | Work 的终局结果及可供其他 Session 使用的交付摘要。 | 不是完整执行日志的简单拼接。 |

### 2.3 三类 Session 对比

| 维度 | UI Session | Work Session | Goal Session |
|---|---|---|---|
| 存在目的 | 持续响应用户 | 完成一个确定 Task | 接近或维持一个 Goal |
| 目标来源 | 用户持续输入 | 创建时确认的任务书，加上执行期的 Task 修订 | 持久化 Goal 及其后续授权调整 |
| 生命周期 | 长期 | 有界，倾向相对短期 | 长期；可达成结束，也可持续维护 |
| 主要上下文 | 用户对话、决策、关键结果 | 当前任务与执行过程 | 目标状态、历史观察、策略与效果 |
| 条件变化 | 与用户交互，必要时重新分析 | 无 Message input，经半订阅观察 Task 修订及相关变化并调整；超出任务边界时允许失败 | 重新观察、判断、调整下一步行动 |
| 创建 Work | 可以 | 不作为本次讨论的主要编排层 | 可以，承担上级目标职责 |
| 完成/暂停方式 | 保持交互，必要时归档 | 成功或失败，输出 Final Report | 本轮可结束而 Goal 继续存在 |
| 能力重点 | 少量交互与任务/目标管理入口 | Manuals、CLI、执行工具 | Skills、评估工具、轻量执行器与 Work 创建 |

“有输入/无输入”仍可描述一次运行的触发形态，但不再充当这三类 Session 的核心分类依据。

## 3. 总体架构与责任关系

### 3.1 主结构

```text
用户 / 外部沟通对象
         │
         ▼
    UI Session ─────────── 直接响应简单问题
         │
         │ Context Fork
         ▼
   Intent Analysis
         │
         ├── 需要澄清 ────────────────► UI Session 与用户补充确认
         │
         ├── 明确 Task ──────────────► Work Session
         │                                 │
         │                                 └── Final Report + 产物引用
         │
         └── 持久 Goal ──────────────► Goal Object
                                           │
Runtime / 调度机制 ── 唤醒 ──────────► Goal Session
                                           │
                                           ├── 不行动 / 本轮结束
                                           ├── 直接行动 / Tool / XLLM
                                           └── 创建 Task → Work Session
                                                               │
                                           ◄── Final Report ───┘
```

UI Session 和 Goal Session 都可以提出创建 Work Session 的请求；创建时必须经过同一类 Task 就绪性检查。不能因为调用者是后台 Goal，就绕过任务边界与依赖确认。

### 3.2 三层责任

从管理视角看，UI Session 负责理解用户正在交代什么；Goal Session 负责持续承担什么目标、目前进展如何以及下一步应做什么；Work Session 负责执行已经确定的一次具体工作。

这不是要求每个用户指令都依次经过三层。简单问题可以由 UI 直接响应；明确任务可直接创建 Work；只有需要跨时间持续观察、调整和推进的意图，才需要建立 Goal。

### 3.3 结果回流

Work 的 Final Report 返回创建方。创建方可以是 UI Session，也可以是 Goal Session。必要时，由上层决定是否将结果告知用户。

Goal 运行所产生的观察、决策与 Work 引用形成目标工作记录。UI Session 可以读取与当前用户交互直接相关的摘要，但不默认接收 Goal 的全部历史推理。

Work 失败意味着本次执行没有按任务书完成，不等于 Agent 整体失败，也不等于上级 Goal 永久失败。

### 3.4 执行基础设施的分层

UI / Work / Goal 描述业务职责，宿主、Session Runtime 和 LLMContext 描述执行分工，两套分类不能混在一起：

| 层次 | 职责 |
|---|---|
| Agent 宿主 / Loader | 装配身份、配置与运行环境，接入消息和事件，维护路由及调度入口，按资源策略装载或卸载 Session 执行者。 |
| Session Runtime / SDK | 持有 Session 的执行所有权，选择并提交输入，装配上下文，处理 run 的结果、调用依赖、订阅、状态转移与结果投递。 |
| LLMContext 与执行组件 | 推进模型和工具调用循环，记录步骤、调用结果及快照，提供挂起、恢复、预算和中断机制。 |
| Agent State 与外部服务 | 提供 Session 登记、Task / Goal / Workspace 等正式对象及共享状态；Memory 按自己的边界提供辅助线索。 |

宿主不再复制一套推理循环，也不直接拼接模型历史来绕过 Session 的提交与恢复规则。Session 根据配置构造推理请求和依赖、消费执行结果；其可恢复状态不能只留在宿主协程里。

Session class 可以提供生命周期、输入、观察、能力和预算的默认策略，behavior 提供具体处理方式。同一 behavior 可用于不同 class，但 class 不能通过开放输入或等待策略绕过 Work 的就绪性要求。新架构中的 UI / Work / Goal 不要求直接等同于当前代码的类型枚举。

## 4. UI Session：长期交互与上下文控制

### 4.1 定位

UI Session 的特定职责就是持续响应用户需求。它不预先绑定“写完某个程序”“修好某个 Bug”等固定目的。

用户通常不希望为了内部执行机制频繁切换聊天 Session。因此，设计目标是让用户尽可能在同一个 UI Session 中持续交互，由系统内部完成分析、分流和任务执行。

UI Session 可以直接回答对当前用户有直接价值的问题，但不承担大量工程扫描、反复读取文件和深入工具探索。其复杂程度不能随着 Agent 的所有后台工作一起增长。

### 4.2 Context Window 管理目标

UI Session 采用以下目标性运行区间：

```text
约 30% ── 追加用户交互与关键结果 ──► 约 80%
  ▲                                      │
  └──────── 一次较充分压缩 ◄───────────────┘
```

从约 30% 增长至约 80% 的区间，尽量保持已有上下文前缀稳定，避免频繁重写整个 Context。达到上阈值后，一次压缩回约 30%，而不是持续做小幅压缩。

这里的增长空间约为 50 个百分点，**不是将上限另定为 50%**。上述数值是当前设计目标，不是所有模型和部署都必须使用的硬编码参数。

维持稳定前缀有利于争取缓存复用，但缓存命中仍取决于实际 Provider、模型和请求组织方式。本设计不将“未压缩”等同于“必然全部命中缓存”。

更重要的是，单靠压缩算法不能达成长期轻量运行。必须首先把大量分析与执行过程移出 UI Context。

### 4.3 UI 主上下文保留与排除内容

| 保留 | 不默认进入或长期留在 UI Context |
|---|---|
| 用户输入与关键澄清 | `read file`、`grep`、`rg` 的大量中间输出 |
| 用户确认过的目标和约束 | 工程扫描、命令帮助、反复试错过程 |
| 意图分析结果 | Fork 中的多轮探索推理 |
| Task / Goal / Work 的标识和必要状态 | Work 内的完整执行轨迹 |
| Final Report 摘要和产物引用 | 已被结果吸收的重复细节 |
| 与用户后续交互直接相关的承诺或待决项 | 与当前交互无关的后台 Goal 全部历史 |

“从 UI Context 删除”是上下文组织策略，不等于删除审计日志、项目产物或用户已经确认的约束。

### 4.4 工具注入原则

UI Session 注入少量直接服务于交互、意图分析、创建与查询 Task/Goal 的工具。复杂操作尽量发生在 Intent Analysis Fork 或 Work Session 内。

UI 不需要为了理解“用户正在让 Agent 做什么”，同时学习所有底层工具的完整使用方式。

## 5. 意图分析：从用户需求到 Task 或 Goal

### 5.1 从任务创建入口升级为意图收敛入口

此前 `try_create_work_session` 隐含“分析成功就是创建 Work”的假设。本次改造将其语义扩展为 `try_analyze_user_intent`：识别用户真正需要的是一次具体任务，还是持续目标。

当前至少明确两类有效产物：

- **Task**：已收敛的有界工作，可以据此创建 Work Session。
- **Goal**：需要跨时间持续观察、判断和推进的目标，可以据此创建 Goal 对象。

需要补充信息、目标过于宽泛或当前无法形成可执行安排，是分析状态，不必因此发明新的 Session 类型。

### 5.2 Context Fork 机制

意图分析看起来是一次函数调用，内部却可以包含多轮 LLM 推理和工具调用。分析需要同时利用聊天上下文与现实世界的现状，后者通常不能只靠对话推测。

```text
UI 发起分析
  → 创建 Context Fork
  → 理解当前请求与必要聊天上下文
  → 探索 Workspace / 项目 / 依赖 / 外部状态
  → 收敛任务或目标，标记缺口
  → 返回结构化结果与简明 Report
  → UI 仅接收结果，不接收完整探索过程
```

分析中的必要事实、来源、假设和用户待决事项，应进入结果；没有必要把所有发现过程带回主会话。

Fork 内的上下文隔离不赋予额外写权限。以探索为目的的分析，不应因为能够调用工具就擅自部署、安装或修改外部状态。

### 5.3 Task 就绪性

创建 Work 前，应确认以下内容足够清楚：任务目标、范围与非目标、可验证结束条件、必要输入、关键依赖、执行环境或 Runtime 配置、Workspace，以及允许执行的动作。

还需判断这是新项目，还是在已有项目和既有产物上继续修改。任务条件不足时，分析结果应把缺口交给 UI，让用户补充或作出选择，而不是先创建 Work 再长期等待。

“条件足够”是基于当前探索的合理判断，不是要求在开始执行前证明世界不会变化。

### 5.4 Goal 就绪性

创建 Goal 前，至少需要把以下内容说明白：追求什么状态、作用于什么对象、服务谁、如何判断进展，以及有哪些重要边界。

例如“让我保持健康”过于宽泛，不能仅因是长期意图就直接放入后台无限运行。可以继续澄清为具有范围、策略和评估方式的目标。

Goal 的明确性不等于一次性完成所有未来行动的规划。它需要明确的是长期职责及判断方式，而不是穷举未来环境中的每一步。

### 5.5 创建与确认模式

本次保留两种流程，不强行确定唯一交互模式。

| 模式 | 流程 |
|---|---|
| 自动创建 | 分析已经足够明确，且处于既有授权内，直接创建 Work 或 Goal，并向 UI 返回结果。 |
| 分析后确认 | 先返回方案、差异与选择，由 UI 与用户确认后再创建。 |

分析结果不能悄悄把原始需求扩展为更大的目标。在关键条件或授权未明确时，应停留在待澄清/待确认，而不是用默认假设启动高成本执行。

## 6. Work Session：有界执行、明确失败与结果交付

### 6.1 定义

Work Session 是由已经收敛的 Task 创建、在明确边界内执行、最终产生成功或失败结果的工作单元。

它可以有一定规模，例如完成一个网站的第一个版本，而不必被限制成一次命令调用。决定其是否属于 Work 的，不是代码行数或步骤数量，而是能否定义任务书、准备条件和结束条件。

从管理角度看，它相当于战略意图已经转化为一次战术任务或明确的阶段 Todo。执行者应解决任务内的问题，而不是不断重新讨论上级战略、修改 KPI 或扩充任务范围。

创建通过后，先持久化任务、创建来源、Runtime / Workspace 绑定及必要订阅，再从任务书构造首批输入。这个 bootstrap 是初始化动作，不是给 Work 伪造一条聊天 Message。创建与初始化提交要有稳定身份，重复创建请求或进程重启不能重复创建同一工作、再次执行已提交的首批输入。

Work 与业务 Task 的绑定需要能追溯任务版本及修订；执行期 TaskMgr 的状态映射另见 §12.13。任务服务中的“运行中”不能代替 Task 就绪检查，状态同步也不能代替 Final Report。

### 6.2 适用与不适用的任务

| 请求 | 判断 |
|---|---|
| 按明确功能范围写一个贪吃蛇游戏 | 可形成 Work。 |
| 完成某个网站第一版，并通过已约定验收 | 可形成 Work，规模不妨碍其有界性。 |
| 输出一份满足给定条件的饮食计划 | 交付计划是有界任务；不代表保证长期健康结果。 |
| 持续让我保持健康 | 不直接形成 Work，需要澄清 Goal。 |
| 根据已确认结论修复 Bug、完成测试并提交 PR | 可形成 Work。 |
| 盯住一个 Issue，直到关闭，并持续处理所有新评论 | 不属于 Work，应由 Goal 承担。 |
| 等待需求确认之后再开始开发 | 确认未到位时不应先创建开发 Work。 |

### 6.3 执行边界

Work 在开始时接受确定的目标与必要条件。运行过程中，允许为完成同一任务进行正常探索、技术选择、错误修正和有限重试；不允许把任务成功的定义改成更容易达到的另一件事。

这里需要区分两种变化：

**任务内的执行问题与调整**，例如编译错误、测试未通过、参数需要调整，以及用户对当前工作目标提出明确的新修改，可以在已有授权和有界任务内继续处理。**任务前提失效**，例如必要权限缺失、关键依赖无法满足、需求已变成另一项无法在当前边界内完成的工作，不能无限吸收到当前 Work 中。

重要前提失效，且无法在既定边界内解决时，Work 应快速失败并说明原因。不要不断向用户索取新的核心需求，也不要通过长时间等待掩盖任务尚未准备好。

#### 6.3.1 无 Message 输入，每次推理前观察相关变化

Work 没有普通 Message input，这是有意的设计：它不是可交互主体，UI 不通过重定向用户消息把它改造成聊天会话。运行期间，UI 把针对当前工作目标的新意见作为 **Task 修订**追加到 Task 对象上：每条修订附原始用户事件的引用和原文，标明适用的子对象范围，以及它是新增还是纠正之前的哪条修订。只有持有该 Task 修订授权的主体（通常是创建它的 UI 或 Goal）能追加。

修订不写成 Memory 感知。它必须送达，而 Memory 召回是尽力而为的：会被预算截断，会被整理清理，也会被“本次不记忆”策略关闭（Memory 需求 M-30、M-31、§9.4）。Memory 只接收修订中另行表达的长期信号，例如“以后这个项目都别用亮色背景”，那是 UI 另写的一条感知，与修订互不依赖。

Work 创建时，由 Runtime 确定性建立对自身 Task 对象的半订阅；子 Session 由父 Session 在创建时按子对象范围建立订阅，各自维护观察进度。这份基础订阅不依赖模型自行设置 topic；仅有父子关系也不保证收到全部更新，无关 Work 不应因属于同一 Agent 就收到这些修订。

除非显式关闭，**每次进入推理前都有一次半订阅观察机会**，包括同一次运行内 function call 返回后继续推理的时刻。观察可随 function call result 一起装配，但实际工具返回、Task 修订与 Runtime 附加的 Memory 材料应明确区分来源；具体消息格式待实现收敛。观察机会不依赖新 Message、新 Turn 或上下文切换，也不要求每次全量查询 Memory。Task 修订不受 Memory 召回预算截断；无法装配时观察失败可见，不推进观察进度。关闭 Memory 半订阅不影响修订送达。

连续多条修订要保留独立要求及明确的纠正关系，不能按 topic 只留最后一条。这条路径在下一次已有推理前生效，不中断正在运行的工具，也不因半订阅通知单独增加推理。Work 仍按完成条件结束，不为了等用户未来意见而保持开放。观察到修订与完成修改应分别记录；修订只能在已有授权和任务边界内调整，超出边界按 §6.3 失败，权限和预算不会因修订进入上下文而扩大。

这里规定的是新架构的观察时机与语义；事件承载、Topic 和成本控制见 §12.7—§12.10，当前 Runtime 尚需补齐的部分见 §15.5。

Work 结束后，用户再提出修改，由 UI 基于有效产物创建新 Task 和新 Work，不恢复旧 Work。Final Report 写明已观察到的最后一条修订编号；编号更大的修订就是旧 Work 没有处理的修改，由 UI 确定性地交给后续工作，不靠模型对照反馈和 Report 判断。Memory 一侧的边界场景见 [Memory 模拟 TODO §3.11](../../notepads/agent-memory-multi-session-simulation-todo.md#311-场景六-运行中-work-的修改不经过-memory)。

### 6.4 有界等待与开放等待

本设计拒绝的是把 **开放性业务等待** 塞进 Work，并不删除执行所需的所有等待能力。

| 等待 | 处理原则 |
|---|---|
| 等待本次已发出的工具调用、构建或测试返回 | 可以作为任务内的有界等待，受超时与预算控制。 |
| 等待本次明确子任务执行结束 | 可以，但子任务不能只是对外部无限等待的包装。 |
| 等待用户未来确认需求 | 应由 UI / Goal 接续，不长期保持开发 Work。 |
| 等待 Issue 某一天关闭、评审人未来留言或审批人未来批准 | 由 Goal 跟踪，条件成熟后再创建新的 Work。 |

判断不能停留在“技术上它在等一个 Task”。如果被等待的 Task 本质上没有可控结束条件，仍然是在绕过 Work 的有界约束。

PendingTool 适用于保留当前调用依赖的有界等待；跨人、跨 Agent 的长期协作由 UI / Goal 显式订阅相关变化，并结束本次执行后等待新的运行机会。两者的恢复语义见 §12.7。把等待改成事件订阅也不能让一个原本不符合就绪条件的 Work 变得合理。

Work 倾向相对短的生命周期，以减少分析时的环境与实际执行环境之间的变化。具体时长需要按任务类型设置，本文不规定统一的分钟数或小时数。

### 6.5 成功、失败与重新执行

Work 必须依据任务书的完成条件及执行期已观察到的 Task 修订报告结果，说明哪些已落实、哪些未完成，并写明最后观察的修订编号。创建时判断“有条件完成”，不构成成功承诺；仅观察到修订也不构成修改完成。

```text
Task 已就绪
    ↓
Work 开始执行
    ├── 达到约定完成条件 → Succeeded → Final Report
    └── 关键前提失效 / 无法在边界内完成 → Failed → Final Report
                                                        ↓
                                                上层重新分析
                                                        ↓
                                          调整条件，创建新的 Work
```

失败后的重新分析可以发生在 UI 与用户之间，也可以由具有相应授权的上级 Goal 完成。涉及用户必须决定的范围或权限时，仍应回到用户，而不是由 Goal 擅自改写。

新的 Work 不默认继承旧 Work 的全部执行 Context。可以继承有效产物、已验证事实、必要状态和失败 Report，并按需检查来源。失败 Session 中的旧假设、无效尝试和未经验证的结论不能自动成为新任务的事实。

### 6.6 Final Report

Final Report 是 Work 最重要的跨 Session 交付接口，尤其在失败时，可能是其他 Session 了解本次工作最主要的材料。但它不替代真正的文件、代码、测试结果和其他产物。

以下为建议的内容规范，而非已冻结的字段协议：

| 内容 | 要求 |
|---|---|
| 标识 | Work、Task、创建方及关联 Goal；必要时带任务版本。 |
| 终局状态 | 成功或失败，不用模糊措辞隐藏未完成。 |
| 任务摘要 | 本次实际接受的目标和完成条件。 |
| 已完成与未完成 | 区分实际交付、部分成果和仍缺失内容。 |
| 验证依据 | 测试结果、观察记录和可访问的证据引用。 |
| 产物引用 | Workspace、文件、提交、PR 或其他对象的位置。 |
| 失败原因 | 区分发现的事实、原先假设、两者差异及影响。 |
| 副作用 | 已修改的文件、已发送的消息、已产生的外部状态。 |
| 后续条件 | 下一次尝试需要补齐什么，由上层重新决策。 |
| 经验候选 | 值得结晶的操作经验，可选；不直接升级为全局 Manual。 |

Report 应是可理解、可追溯的结果压缩，而不是一段无证据的自我评价。

进度报告与 Final Report 分开。创建方可以选择仅接收终局、接收顶层进度，或接收相关子工作的进度，但不能把 checkpoint 当作工作已完成。报告应先持久保存，再按创建关系交付给 UI / Goal；稳定报告身份、阶段、版本与接收方用于投递去重，具体链路见 §14.8。

### 6.7 失败不自动撤销真实世界

Work 失败不代表已经产生的外部影响消失。Context Fork、Session 结束与清空提示词都不能撤回已提交的代码、已发送的消息或已修改的共享 Memory。

实现上应保留副作用记录。是否回滚、如何回滚、是否需要人工决定，由任务授权和具体工具能力决定，不能默认承诺原子回滚。

取消、超时和预算终止可作为工程层扩展状态，但都需要留下明确原因和结果材料。状态枚举以及它们与 Failed 的映射，留待接口设计确定。

## 7. Goal Session：目标模型、运行循环与持续认知

### 7.1 Goal 首先是对象

意图分析得到长期目标时，首先创建的是 **Goal 对象**：它描述持续职责，并具有独立于当前 UI 对话和当前计算进程的身份与状态。

Goal Session 是围绕该目标工作的认知与执行上下文。长期存在的是目标和连续状态，而不是要求模型进程永不停机。

本次实现方向是让同一 Goal 的多次努力保持上下文连续性。建议首版为一个 Goal 绑定一个主要的逻辑 Goal Session；是否允许多 Session 协同同一 Goal，以及 Session 重建时的绑定关系，仍属于实现待决项。无论怎样绑定，不能丢失目标身份与历史连续性。

### 7.2 Goal 的基本构成

一个可运行的 Goal 至少需要回答三个问题：**目标边界是什么，怎样判断当前状态与目标的距离，依靠什么方法推进。**

| 构成 | 说明 |
|---|---|
| 目标与作用范围 | 希望达到或维持的状态，涉及的项目、事项或人。 |
| 创建者与受益者 | 谁交付目标、谁有权调整、为谁服务；三者不一定是同一个人。 |
| 生命周期类型 | 达成型或持续维护型。 |
| 达成/健康状态判定 | 怎样确认目标已达到，或当前维护状态符合要求。 |
| 距离评估方法 | 以自然语言明确观察哪些证据、如何判断差距与进展。 |
| 边界与约束 | 不做什么，什么变化需要重新授权，哪些输入只能作为参考。 |
| 当前 Skills | 为目标服务的方法论、工作流和能力入口。 |
| 预算 | 每次运行可以使用的轮次、Token 或其他资源约束。 |
| 当前状态与记录 | 最近观察、历史行动、有效经验、关联 Work 和反馈。 |

### 7.3 达成型与持续维护型

**达成型 Goal** 有可以到达的结束边界。例如在指定期间完成朋友接待，或完成一个经过定义的长期事项。确认达成后，可以进入完成状态。

**持续维护型 Goal** 追求反复维持某种状态。例如消化新增感知、维护软件、持续修正可复用操作经验。即使某次检查发现积压为零，未来仍可能出现新工作，因此一次“当前满足”不等于整个 Goal 永久结束。

口述中的 `forever run` 应理解为长期可持续维护，而不是持续占用 CPU、无预算限制或每次检查都必须找到事情做。

### 7.4 距离评估

目标距离不必是一个数学分数。自然语言也可以清楚表达“离目标还差什么”。

| Goal | 距离或状态判断示例 |
|---|---|
| 处理待整理感知 | 还有多少未处理项目、哪些已经积压、哪些尚缺足够上下文。 |
| 软件维护 | 哪些问题未分类、哪些需求未确认、哪些修复未验证、哪些 PR 待处理。 |
| 工具补齐 | 哪些高价值能力缺口仍未解决，哪些已有工具可以覆盖。 |
| 朋友接待 | 当前行程是否合适、已有反馈是否被吸收、下一段安排是否明确。 |

评估必须允许“信息不足、当前未知”。没有观察到某件事，不等于它没有发生；没有新反馈，也不等于目标已经达成。状态来源及其时效应在结果中可追溯。

距离用于决定行动，而不是鼓励制造漂亮分数。投入更多 Token 不必然产生更大进展，最终仍需观察真实效果。

### 7.5 每次唤醒的执行循环

```text
收到一次运行机会及预算
    ↓
恢复 Goal 定义、当前 Skills、状态与必要历史
    ↓
观察现实状态及自上次运行后的变化
    ↓
判断目标是否达到 / 当前维护状态是否满足
    ↓
评估剩余差距、不确定性和可行动事项
    ↓
按价值、依赖与预算决定优先级
    ├── 暂不行动
    ├── 请求必要信息或提示相关人员
    ├── 直接执行轻量操作 / 调用工具或 XLLM
    └── 条件就绪，创建一个或多个 Work Session
    ↓
记录观察、决策、行动、预算消耗及关联 Work
    ↓
保存状态，本次运行结束
```

本次运行可以只做几个 Turn，也可以在预算允许时安排多个 Work。它不要求在一次 Activation 中完成整个 Goal，也不需要一直阻塞等待子 Work 全部返回后才交还执行资源。

子 Work 结果进入目标记录，并由后续获得的运行机会吸收。具体回调或事件投递方式由 Runtime 确定。

### 7.6 Goal 作为 Work 的上级

Goal 负责判断“现在应该做什么”，Work 负责“把已经明确的事情做完”。

例如，工具补齐 Goal 可以直接安装一个已经确认适用的软件包；如果需要开发一组 CLI，则应先明确输入输出、环境、测试和完成条件，再创建 Work。

Goal 不能将“继续推进整个目标”原封不动作为 Work 任务书。否则只是把长期目标重新包装成一个无边界 Work，分类改造没有实际发生。

### 7.7 Goal 的调整与连续性

人可以通过 UI 或 Web 管理界面细化 Goal、调整目标范围内的重点、改变评估标准或推进方法。这种演进是 Goal 的正常能力。Work 则保留创建时的任务依据，并按 §6.3.1 观察同任务的新反馈，不承担无限扩展的目标演进。

目标可调整不等于后台可以任意替主人修改目标。Goal Session 可以在授权范围内调整策略、选择 Skills；改变用户追求的目标或扩大权限仍需用户决定。

建议记录 Goal 版本以及每次调整内容。新版本影响后续运行；已经创建的 Work 仍保留自己的任务书，不因 Goal 更新而静默改变。发现旧 Work 已不合适时，应显式决定继续、取消或重新创建。

保留任务书用于追踪工作来源，不意味着 Work 必须忽略执行期间有来源的明确修改。后者作为 Task 修订追加到 Task 对象并进入观察（§6.3.1），由 Work 理解并在当前任务和授权边界内调整，与后台静默覆盖任务定义不同。

### 7.8 不负责自我唤醒

Goal Session 接受运行机会，但不承担自我调度器的职责。每次唤醒后，统一执行“观察—评估—按预算行动”。

需要特别区分：**为用户设置今天的活动提醒**是 Goal 决定的一项业务动作；**决定这个 Goal Session 明天几点再次运行**是 Runtime/调度职责。二者不是同一种定时。

Goal 可以表达需要关注的对象、事件与业务超时条件，由 Runtime 绑定订阅、安排检查并提供运行机会（§12.8）。表达等待意图不等于在 Goal 内部运行一个自我唤醒循环。

## 8. 典型业务场景

### 8.1 从机械提醒到目标驱动提醒

用户提出“每个工作日下午四点提醒我活动十五分钟”。传统实现可以直接创建重复日程，但本次 Goal 范式关注的是：在用户实际处境下，怎样持续落实这个意图。

当用户请假、出差或跨时区旅行时，下午四点的含义、提醒是否仍有必要、当日是否已有活动，都可能需要结合上下文判断。Goal 不应擅自假定“请假就不需要活动”或“出差就一定无法活动”，而应依据已确认偏好和实际信息决策。

一种执行方式是由系统每天提供一次检查机会：Goal 观察当天情况，决定是否设置当天的具体提醒、是否调整安排或是否需要澄清。它也可以在一次运行中判断无需任何外部动作。

进一步的目标可以带有结束条件，例如在用户设定的体重目标达成之前持续提醒。本次口述中的“130 斤”仅是目标建模例子，不构成健康建议，也不能仅凭体重值判定 BMI 是否适合。架构应保存用户确认的目标和判断依据，而不是写死医学结论。

需要区分：输出一份活动计划可以是 Work；持续判断提醒策略和目标状态才是 Goal。

### 8.2 为他人提供持续服务

主人出差，朋友来到主人所在地旅行，主人要求 Agent 帮朋友安排接待与行程。

Goal 的创建者是主人，受益者是朋友。朋友与 Agent 的 UI Session 提供当天体验和偏好信息；Goal Session 将这些信息用于后续安排，而不必绑定在主人的某一个聊天窗口里。

当天可以直接回答的具体问题，由 UI 响应；需要综合当日反馈、调整第二天行程的工作，由 Goal 组织。例如在约定的晚间检查机会中生成次日安排，复杂计划可转成一次 Work。

跨用户协作不代表所有 UI Session 的信息默认互通。Goal 只能使用被授权用于该接待目标的信息。

### 8.3 软件维护：拒绝“等待 Issue 关闭”的 Work

原有反例是：一个 Work 以修复 Bug 为目标，之后持续等待 Issue 关闭；每次新增评论，就继续修改。这个 Work 的真实职责已经变成长期跟踪，而不再是一次确定执行。

正确的拆分是：

```text
Goal：推进某个 Issue 的解决，或持续维护一个软件项目
    │
    ├── 获取 Issues / 评论 / PR 的最新状态
    ├── 分类：Bug、Feature Request，以及需要澄清的事项
    ├── 调用工具或轻量执行器，辅助判断与收集信息
    ├── 提示、建议、追问，引导相关人员确认需求
    │
    └── 当具体变更已确认
          ↓
       Work A：按确认结论实现、验证并提交 PR
          ↓
       Final Report 返回 Goal
          ↓
       Goal 继续跟踪评审与新反馈
          ├── 需要明确修改 → Work B
          ├── 合并条件就绪 → 执行获授权的合并动作或创建有界 Work
          └── 尚缺条件 → 保持目标状态，本轮结束
```

Work A 的完成条件可以是“实现约定变更、通过指定测试并提交 PR”，而不是“无论未来发生什么，一直等到有人关闭 Issue”。

PR 的评审、合并与最终验收可以由维护 Goal 继续管理；有需要时，也可以定义专门的 PR 推进 Goal。但不是每一个 Issue 或 PR 都必须机械地生成一个新 Goal，应由责任范围和上下文规模决定粒度。

### 8.4 从单个问题扩展到持续职责

“修复这个 Bug”可以是较小的 Goal；“维护这个软件项目”可以是更大的持续维护 Goal。关键不是名称大小，而是后者要有足够明确的范围、分类方法、优先级规则、完成/健康状态判断以及资源限制。

软件维护 Goal 的 Skills 应描述怎样分类问题、何时要求确认、如何评估现状以及哪些事情应交给 Work。具体执行 Bug 修复、构建、测试和提交的步骤，则进入相应 Work Manuals。

## 9. Agent 自身目标：Memory、结晶与 Self Correct

### 9.1 从专用 Session 迁移为不同 Goal

Goal 不一定来自用户临时交代，也可以是 Agent 被配置的长期自我维护职责。

这使得过去为 Memory 整理、经验结晶、工具补齐分别考虑“应该放在哪个 Session 运行”的问题，可以统一为：定义相应 Goal，配置评估方法和 Skills，并复用 Goal Session 的运行机制。

这些是不同业务目标，不需要各自增加一个一级 Session 类型。

### 9.2 Memory 整理 Goal：感知转为认知

某个 UI 或 Work Session 中记录的一句话，可能只是一条局部感知。它不一定已经与其他信息关联，也不一定足够稳定，不能仅因被写入 Memory 就当作成熟认知。

Memory 整理 Goal 的职责是持续处理尚未消化的感知，将能够确认和综合的信息转为可复用认知。

UI、Work、Goal 都可记录有后续用途、包含新观察且有来源和范围的感知。普通进度、任务书、Goal 等待状态和完整 Report 继续由原对象保存；Context 压缩或转述已有材料本身不形成新证据。具体正反例按 Memory 需求 §4.4—§4.6 判断。

```text
各 Session 写入低成本感知 / 来源线索
    ↓
形成待处理集合
    ↓
Memory 整理 Goal 检查新增与积压
    ↓
按需取得来源，关联、比较、综合分析
    ↓
形成认知变更（如有）与逐条处置，保留依据与不确定性
    ↓
可靠提交后，清理已吸收/丢弃的感知正文，保留暂缓材料
```

示例：一次工作记录“工具在当前项目中需要显式指定输出目录”，另一次工作记录了省略输出目录导致失败的过程。整理后可以形成带有工具/环境适用范围的认知，而不是两条脱离来源的零散句子。

整理要核对两条记录是否来自同一次调用，区分转述与独立验证，并比较反例和工具版本。一次明确用户要求也可形成窄范围认知；不能设统一次数门槛。Memory 需求 §5.8 给出了同一批材料分别修订经验、提取项目约定、合并重复和暂缓缺证结论的完整例子。

“清空感知”在此指完成当前可处理材料的处置，不是删除已经形成的认知或无条件删除原始依据。按 Memory 需求 M-15/M-16，先可靠提交再清理已吸收/丢弃的感知正文；原始日志和事件引用受各自保留策略约束。暂缓材料保留缺证与重评条件，既无新证据、也未到达复核条件时不反复推理，不能为了归零强行产生结论。

由于新感知持续到来，这是典型的维护型 Goal。某一轮待处理数归零后，可以不行动并结束该轮，而不是销毁整个长期目标。

### 9.3 操作经验结晶 Goal

Work 创建时，依据任务方向选择适用的 Manuals 和 CLI。没有已安装的合适能力时，可以在任务与权限边界内自由探索。

探索结束后，Work 可以在 Final Report 中留下本次经验候选。此时的经验仍可能过于局部、依赖特定环境，不能直接把它当作未来所有 Work 都应遵循的全局操作规范。

结晶 Goal 负责跨 Work 汇总：检查授权范围内的工作目录、工作日志与结果，识别可复用经验，再维护可供未来 Work 选择的 Manual 集合。

主要工作包括三类：

| 工作 | 含义 |
|---|---|
| 修正 | 发现已有 Manual/操作型 Skill 存在错误、过时假设或环境不匹配，进行修订。 |
| 清理 | 判断长期不用或不再适用的资产；按策略停用、归档或自动删除。 |
| 提炼 | 从多个 Work 中反复出现且效果较好的经验中形成可复用操作手册。 |

以 AI 短视频创作为例，早期 Work 需要不断查 CLI 帮助、试参数、调整流程。经历多次有效实践后，可以结晶出适用场景、操作步骤、参数说明与验证方法，供下一次 Work 创建时选择，减少重复探索。

结晶的目标不是让资产数量不断增加，而是提高当前任务所需操作知识的准确性与复用价值。

实现上建议保留资产来源、适用环境和修订记录；自动清理也应有明确策略，避免把当前 Goal 或 Work 正在引用的内容无记录地删除。这些是落地约束，不改变“允许自动维护资产”的方向。

### 9.4 XLLM 结晶 Goal

另一条结晶路径面向标准化、短任务能力。企业可以把某类任务定义为一个 XLLM 配置，由 Decision Model 根据输入和能力描述选择配置，再调用一次 XLLM 获取结果。

在客服场景中：

```text
客户问题
    ↓
Decision Model 按 XLLM 任务描述分类
    ├── 已覆盖 → 加载相应配置 → 一次 XLLM 调用 → 返回结果
    └── 未覆盖 / 无法处理 → 人工处理 → 形成处理记录
                                                ↓
                                      XLLM 结晶 Goal
                                                ↓
                              总结可复用任务，形成候选配置
                                                ↓
                                 检查后加入可路由能力集合
```

这条路径不要求企业为每次客服问题开放完整 Agent 的广泛自主能力。成熟的处理模式可以变成边界清楚的 LLM 工具，而不是每次都创建 Work。

从人工记录结晶新能力，不意味着每条人工答复都自动变成正确规则。候选能力的适用范围、代表性样例、失败边界和加入路由的条件，建议由结晶策略定义。

### 9.5 Self Correct / Intent Engine Goal

工具调用失败，尤其是不存在的 Function 或 Shell 命令，可能包含一条有价值的信号：Agent 试图使用某种尚未具备的能力。

本次设计沿用“工具幻觉可能是一种意图”的观察，但不把每次 `command not found` 都当成必须开发新工具的需求。命令拼写错误、PATH 配置、未安装依赖、使用错误命令和真实能力缺口，需要结合当时上下文判断。

#### 9.5.1 从现场打造改为离线处理

过去的 Self Correct 倾向在调用失败时立即打造缺失工具。但这样可能把一个简单用户任务扩展成工具研发；打造工具又需要更多 Shell 调用，可能触发新的缺失与新的打造链。

现在倾向采用离线检查：原任务保留失败信号，当前能在边界内换用已有能力则继续，否则按 Work 规则失败；工具补齐需求进入后续检查周期，不强制当场修复。

这里“离线”表示脱离原调用的同步关键路径，不等于不联网，也不等于不受授权和预算约束。

#### 9.5.2 信号记录与处理

建议为一次缺失工具调用保留：调用位置、原始命令或 Function、错误结果、关联任务目的、必要上下文以及是否已有替代方案。

Self Correct Goal 从全局视角对这些记录进行去重、归并、价值判断和优先级排序。所谓“清空不存在命令记录”，应理解为让待处理意图得到解决、归类或明确不处理，而不是抹去错误历史。

补齐能力的优先顺序为：

1. 优先寻找已有能力，适合时通过包管理器下载安装，例如当前讨论中的 `apt install` 路径。
2. 其次寻找可使用的开源实现，在当前环境中构建。
3. 最后自行编码；足够简单、直接实现更合适的情况可以例外。

按本次讨论，Agent Infra 提供编码工具链，以 TypeScript 为默认实现方向，也可使用配置中的 GCC、Rust 等环境。本文不规定所有节点必须安装完全相同的工具链，实际能力仍需在执行节点确认。

轻量补齐可以由 Goal 当轮处理；复杂工具开发应形成明确 Task，交给 Work 实现和验证，再由 Goal 判断是否纳入可用能力。

#### 9.5.3 与用户意图分析的关系

UI 中的 Intent Analysis 处理显式用户需求；Self Correct 处理执行记录中暴露的潜在能力需求。二者都在做意图收敛，但来源和运行位置不同。

“Intent Engine”可以保留为能力或子系统名称，不必因此定义第四类 Session，也不能把工具缺失信号直接等同于用户已经授权安装或开发。

## 10. Skills、Manuals 与 XLLM 能力分层

### 10.1 为什么需要区分

过去很多内容都被称为 Skill，但其中既有“如何组织一类工作”的方法论，也有“既然决定做这件事，按哪些命令执行”的操作步骤。

随着 Goal 和 Work 分层，继续把两类内容混在一起，会使能力选择、上下文注入和结晶目标不清楚。

本次方向是：**Goal 的方法论继续称为 Skill，Work 的操作规范倾向称为 Manual。** 这主要是语义与使用方式的分层，不先行要求全面修改外部生态的文件格式。

### 10.2 Goal Skill

Goal Skill 应帮助 Agent 回答：如何取得现状、如何评价目标状态、出现不同差距时有哪些推进方式、哪些条件足以创建 Work，以及怎样判断此前行动是否有效。

例如软件维护 Skill 可以定义 Bug 与 Feature Request 的处理范式、需求确认要求、何时发评论、何时转成开发任务、如何处理评审反馈。

它偏方法论和工作流组织，不只是命令步骤清单。它可以调用工具、轻量执行器或 XLLM 获取局部判断，也可以指定适合交给 Work 的工作类型。

### 10.3 Work Manual

Work Manual 服务于已经明确的任务，重点是执行约定和操作方法。例如项目构建、测试、代码修改、产物检查与 PR 提交流程。

它应有适用条件和失败边界，而不是承诺在任何环境下都能成功。操作手册不能替代 Task 目标，也不能授权 Work 在发现需求变化时自行改任务。

口述前半段的“Work Session 级别 Skill”在此归入候选 Manual 或局部经验；经过结晶后，才进入面向未来 Work 的候选能力集合。

### 10.4 三类资产比较

| 维度 | Goal Skill | Work Manual | XLLM 配置 |
|---|---|---|---|
| 核心作用 | 指导判断、组织与推进 | 指导具体任务操作 | 定义一种单次 LLM 工具能力 |
| 典型问题 | 下一步应做什么 | 已决定做，具体怎样做 | 给定输入，按约束生成一次输出 |
| 主要消费者 | Goal Session | Work Session | 路由器、业务程序或其他获授权调用者 |
| 典型来源 | 外部方法论、目标执行经验 | Work 的探索与操作经验 | 业务任务定义、人工处理经验 |
| 运行形态 | 注入/读取的知识与方法 | 注入/读取的操作知识 | 独立工具调用 |
| 是否是 Session | 否 | 否 | 否 |

### 10.5 Goal Skills 的自我升级

Goal Session 可以在运行中为自身目标添加、选择、修订适用 Skills，使其逐渐适合当前 Agent、环境与长期工作方式。

需要区分两种变化：**当前 Goal 的方法调整**，与**发布供其他 Goal 或 Work 选择的共享资产**。前者不应自动等同于后者；跨目标复用仍需要明确的结晶与资产管理规则。

方法升级也不能静默扩大权限、替换用户目标或提高预算。能力知识如何做得更好，与获准做什么，是两件事。

### 10.6 XLLM 的执行边界

XLLM 是一个有预定义任务和配置上下文的 One-shot LLM 工具：

```text
任务配置 + 一次 user message
                ↓
           一次 LLM 推理
                ↓
         一次 assistant message
```

它不是具有长期身份和累计上下文的 Agent Session，也不是缩小名称后的 Work Session。调用结束即返回结果，不把它扩展成自主规划、持续观察的 Agent Loop。

业务可以用 Decision Model 在多个 XLLM 描述之间选择；该路由过程与被选中的一次推理是分开的能力。

企业希望的“确定性执行”主要指入口、配置、上下文和调用边界更可控，不能据此宣称生成输出在数学意义上必然确定。调用是否允许外部副作用，应在工具合同中明确，不能只因不叫 Session 就假定没有风险。

## 11. 上下文、持久状态与跨 Session 信息传递

### 11.1 区分四类信息

| 信息层 | 典型内容 | 保存目的 |
|---|---|---|
| 定义与授权 | Task 任务书、Goal 定义、版本、预算与权限 | 确认接受了什么工作，不能依赖模型记忆随意漂移。 |
| 当前工作 Context | 最近对话、当前观察、正在分析的问题 | 支持当前推理，可选择、压缩和重建。 |
| 持久工作状态与产物 | Goal 状态、Workspace、Work Report、工作日志 | 跨次恢复、追踪执行及复用有效成果。 |
| Agent 共享 Memory | 跨 Session 的感知、认知与来源线索 | 积累可复用认知，并以尽力而为的线索提示相关 Session；不承载必须送达的内容，不替代任务书、Task 修订或 Goal 状态。 |

同一信息不应在多个地方被当作互不关联的“最新真相”。例如 Goal 版本属于持久定义，Context 中的副本应注明它对应哪个版本。

目标判断可以读取共享 Memory 中有范围的感知与认知。按 Memory 新抽象，独立 Agent Notebook 退役；旧实现中的可复用机制按需迁入 Memory，调用方切到统一入口。用户要求保存可编辑的笔记时，产物属于文档等世界对象。

Goal 的目标级摘要用于本目标的恢复，不自动成为共享认知。Task/Goal 定义、Task 修订、授权和 Final Report 通过正式对象与交付链路传递；执行期的目标修改写为 Task 修订，经 Task 对象半订阅送达，不进入 Memory，也不能把观察回执等同于执行结果。Memory 只承载“没被召回会让 Agent 不够聪明、但不会让系统出错”的内容（Memory 需求 M-30）。

### 11.2 UI、Work、Goal 的压缩策略不同

**UI Session** 强调长期沟通与轻量上下文，使用约 30%→80%→30% 的目标区间，尽量只保留关键决策、结果和最近交互。

**Work Session** 的 Context 服务于一个明确任务，可以围绕任务保留较多执行信息；需要压缩时，也应保留任务约束、已验证结论、当前执行状态与产物引用。其重点是完成并结束，不是把它长期养成另一个 Goal。

**Goal Session** 的 Context 服务于同一目标的多次努力，要保留此前的观察、策略、有效经验与反馈关联。不能每次醒来只读取一句 Goal 描述，从头探索；也不能不加筛选地保留所有历史。

Goal 的压缩倾向比 UI 更重视目标相关认知的连续性，本次不规定固定比例，也不直接照搬 UI 的阈值。

### 11.3 Goal 压缩后的恢复结构

建议在系统约束之后，使用以下顺序重建 Goal 的核心上下文：

```text
[Goal 定义、版本、边界与距离评估方法]
[Current Skills：当前可用 Skills 列表、版本和读取入口]
[目标级认知摘要：验证过的经验、有效策略与重要失败]
[最近状态：观察时间、来源、不确定性]
[正在执行及已完成的 Work / 待吸收 Report]
[本次运行机会、可用预算与新增信息]
```

其中 **Current Skills 应进入压缩后靠前、稳定的恢复区域**，不能因为丢弃了历史对话，就丢失此前已经为这个 Goal 配置或整理出来的方法。

保留可用 Skills 列表，不等于把全部 Skill 全文一次性塞入系统提示词。详细内容可按需要读取；列表应指向实际存在、当前授权且版本明确的能力。

### 11.4 跨 Session 传递最小必要结果

| 来源 → 目标 | 应传递 | 不默认传递 |
|---|---|---|
| Intent Fork → UI | 分析结论、缺口、用户选项、Task/Goal 草案或创建结果 | 探索过程全文 |
| UI / Goal → Work | 明确任务书、相关事实、来源、Workspace、授权与能力选择 | 创建方的全部历史上下文 |
| UI → 运行中 Work 及相关子 Session | Task 修订（附原始用户事件），经 Runtime 建立的 Task 对象半订阅在下一次推理前观察 | 重定向的聊天 Message、写成 Memory 感知的修改、无关任务修改及 UI 全部对话 |
| Work → UI / Goal | Final Report、产物引用、验证与副作用说明 | 执行过程全量拼接 |
| 一个 Work → 新 Work | 经过上层筛选的有效结果、失败原因及必要产物 | 默认继承失败推理全部历史 |
| 多个 UI → 同一 Goal | 被授权、与该目标相关的事实与反馈 | 不相关聊天及其他用户的私密上下文 |
| Goal / Work → 结晶 Goal | 授权范围内的工作记录、经验与结果 | 任意跨域读取所有日志 |

日志可以为诊断和复盘保留，但“日志存在”不意味着每次模型调用必须携带日志全文。

### 11.5 世界状态与认知状态的边界

Session 拥有连续 Context，不代表外部世界冻结。共享项目可能被人或其他 Session 修改，Goal 和 Work 都需要按其职责重新观察真实状态。

Goal 根据新的状态重新判断策略；Work 判断变化是否仍在当前任务范围内。前者可以继续组织后续工作，后者不能把严重前提变化无限吸收进旧任务。

共享 Workspace 的并行写入、工具副作用和权限管理属于执行安全问题，不能靠 Context 隔离解决。

### 11.6 持久状态与恢复依据

Session 的权威运行状态必须可持久恢复；worker 是可替换的执行者与缓存。文件实现以已提交的磁盘状态为准，其他存储实现也必须提供同等的提交、版本和所有权合同。这里不要求把全部数据放进一个 `SessionMeta`，也不把模型历史当作正式状态的唯一副本。

| 状态类别 | 至少需要保留的信息 |
|---|---|
| 身份与绑定 | Session / Agent 身份、创建方、Task 或 Goal 引用及版本、Runtime、Workspace、交互和结果回送路由。 |
| 配置与能力 | 当前配置版本、上下文入口、使用的 behavior / 模板 / 能力版本，以及运行时应执行的权限与预算策略。 |
| 输入与观察 | 输入来源和稳定身份、接收与提交进度、订阅、待观察版本、Task 修订的独立观察进度。 |
| 执行与调用 | 当前逻辑 Turn、run 引用、上下文栈、快照、待回填调用、外部 Task 标识、等待原因与期限。 |
| 审计与恢复 | 工作日志的已提交边界、输入 receipt、配置变更、工具执行与结果证据、恢复阻塞原因。 |
| 输出与交付 | 最终状态、Report 与产物引用、待发回复、投递进度、预算和未完成事项。 |

登记表、活动视图、最近状态和 Workspace 占用提示可以服务查询与调度，但它们是有版本的投影；不能用过期缓存覆盖权威运行状态。用户消息的正文、附件和来源关系应有可恢复的结构化记录或可靠引用，不能只保留一次临时渲染结果。

日志与快照需要协同：只读取已提交的日志范围，压缩后仍保留调用、输入与结果的对应关系。长期 Goal 的未完成事项不能只存在于某次压缩摘要中；Task 修订的送达和观察进度也不能依赖 Memory 是否被召回。

### 11.7 输入提交与崩溃恢复

输入链路使用“可靠接收 → 上下文提交 → 执行与结果提交”的顺序，延续 §12.9.3 对三种进度的区分。不能同时采用“整轮成功后才消费”和“进入内存上下文就删除”两套相互冲突的规则。

1. **接收**：验证目标、权限与输入策略，按稳定输入身份写入可靠存储，成功后才确认上游投递。此时仅证明 Session 已接收，不证明模型已经看到。唤醒只是提示，有效载荷不能只存在于唤醒信号中。
2. **选择与渲染**：在允许的边界选择输入，冻结本次环境并渲染。失败时不提交本批输入，未选中的输入继续保留。
3. **提交上下文**：将模型可见材料、输入身份、观察版本及相应 receipt 与可恢复快照关联，完成 Session 消费进度的持久提交。跨文件或跨组件提交需要可恢复的提交标记，在提交完成前不能启动依赖该批输入的工具副作用。
4. **推进与记录**：继续推理或回填调用，持久保存执行结果。已提交输入不因后续推理失败重新变成一条新输入；失败仍须有可查询的状态和证据，不能描述为输入无痕丢失。
5. **完成与交付**：按 Session 语义关闭 Turn、结束 Work 或结束本次 Activation，将结果与待投递记录提交，再执行对外发送与必要重试。

上游消息服务的接收确认与 Session 输入总线的消费确认属于不同边界。落盘失败不能提前确认；确认失败导致重投时，应识别同一输入，避免重复追加上下文。输入提交不需要等待整轮推理成功，但必须留下足以核对它去向的证据。

恢复时先获得执行所有权，校验格式版本、Runtime / Workspace 绑定、配置和快照引用，再核对未完成提交。已写入快照的输入 receipt 可以用于补齐 Session 进度，不能再次追加同一消息；已经完成的 run 若尚未提交 Session 结果，应补交结果而非重跑任务。

| 中断现场 | 恢复原则 |
|---|---|
| 输入尚未提交到上下文 | 仍按待处理输入推进；重投按稳定身份去重。 |
| 上下文已提交，模型或工具步骤尚未结束 | 从合法检查点恢复，保留同一逻辑工作的身份，不重新从头执行输入。 |
| PendingTool 已登记外部 Task | 按既有 Task 与调用标识查询、回填；不因为通知丢失重新创建外部任务。 |
| 工具可能已产生副作用，但没有可靠结果 | 保留现场，查询可验证状态或标记未知 / 阻塞；不能把“无结果”当作“没执行”而自动重试。 |
| 版本、绑定、快照或依赖无法核验 | 明确阻止推进并报告原因，不能靠丢弃快照或猜测字段修复。 |

允许恢复确定可继续的推理与调用，不等于允许重放未知副作用。是否重试失败业务由任务边界、工具幂等合同及上层决策共同决定；终止后的 Work 仍遵守不 reopen 的规则。

### 11.8 Behavior、上下文切换与模板合同

Session 决定什么时候取输入、观察和推进；behavior 决定当前上下文如何处理任务。输入策略、上下文入口与提示词模板应分别配置，不能让模板读取队列、推进游标或隐式获得新的执行权限。

Runtime 向模板提供有明确 schema 的环境视图，包括已选输入、时钟、Session / Workspace 身份、相关观察和调用结果。外部读取先完成并冻结；同一版本模板与同一视图应产生相同输出，渲染不能读取实时时钟、随机取值或产生外部副作用。模板可按合同选择可选字段，但 Task 修订等必须送达材料由 Runtime 保证装配，不能因模板漏写而被确认已观察。

初始化、外部输入和上下文交接是受控输入的典型边界；推理前半订阅是独立的观察职责，不能限缩为这几个边界。应避免在没有有效输入、必要初始化、待恢复工作或到期运行机会时调用 LLM；空模板也不能把必须处理的输入静默消费掉。

上下文切换需要明确三类合同，具体模式名称由 SDK 定义：

| 方式 | 历史与配置 | 完成后的流向 |
|---|---|---|
| 切换到持有自身状态的上下文 | 目标使用自己的身份约束、模板、能力配置与历史；首次构造，后续恢复其已有状态。 | 按工作流交接，不能假定复制调用者的完整历史。 |
| 创建独立子上下文 | 按目标入口配置构造，仅继承显式选定的材料；记录父调用与子上下文身份。 | 子结果返回原调用方，不把子上下文结束当作整个 Session 结束。 |
| Context Fork | 保留分叉点的有效系统配置与历史，分支拥有独立执行状态。 | 仅回传选定结果，符合 §5 的意图分析隔离要求。 |

创建子上下文与创建 Work Session 是不同操作：后者还要经过 Task 就绪检查、登记、绑定和资源分配。旧式在同一历史上替换 system 的“normal switch”不能被默认当作独立上下文隔离。

切换或恢复时要核对目标入口、历史继承、调用栈深度、工具策略及有效配置；需要调整工具执行视图时，应在进入目标上下文前落实，不能只换提示词而沿用不相符的能力。配置与模板版本应可追溯，压缩或重启不能静默换成另一份配置。`END`、等待或预算 outcome 的含义由调用层级和 Session 策略解释，不能把任何上下文的完成都映射为 Session 终态。

## 12. 调度、事件订阅、预算与分布式运行

### 12.1 调度与执行职责

Runtime 或既有调度机制负责提供运行机会，可以根据系统策略安排周期、事件或其他触发方式。Goal Session 本身只实现被唤醒后的目标判断与行动。

```text
调度侧：什么时候允许哪个 Goal 获得多少执行资源
目标侧：在这次资源内，当前最值得做什么
执行侧：怎样完成一个已经确定的 Task
```

本设计不要求新增一个独立部署的 Goal Scheduler 服务；它是一项明确职责，可以由现有 Runtime 承担。

Goal 对每一次唤醒都应重新观察必要现状。被唤醒不证明事件内容仍然最新，也不证明现在一定需要行动。

定时唤醒应携带原因、目标对象与版本、预期触发时间和触发来源，供 Goal 定向检查。可以同时有精确时间触发和低成本兜底核对，但兜底频率不直接等于 LLM 调用频率，也不在本架构中固定为 60 秒。提醒与持续改进的预算耗尽时，保存未完成事项并结束本次运行机会；下一次先读取最新状态再判断，不能机械重放上一轮计划。

### 12.2 预算模型

Goal 长期存在，但单次执行必须有限。当前讨论至少要求支持推理轮次或 Token 消耗方面的约束；具体单位和配置协议待定。

建议把预算区分为以下层次，避免只限制表面上的 Goal 推理：

| 层次 | 控制对象 |
|---|---|
| 单次 Activation | 本次判断、工具调用和直接行动的资源使用。 |
| Goal 周期总预算 | 该目标在一个统计周期内可投入的总体资源；属于建议的管理能力。 |
| 派生 Work 预算 | 创建子 Work 所需的资源，应计入明确的归属，不允许成为绕过父级约束的出口。 |
| Agent 总体预算 | 多个 Goal 及直接任务共享的总体资源边界；与现有资源体系衔接。 |

预算可以表现为轮次、Token 或费用等维度，但不能把不同模型的一个 Turn 当成天然等价成本。采用何种组合和如何计费，应由产品与 Runtime 确定。

Goal 根据差距、价值与成本选择优先级。没有预算可行动时，可以记录未处理原因并结束本轮；不能把“暂停投入”写成“目标已经达成”。

### 12.3 子 Work 的成本归属

Goal 在创建 Work 前，应知道这次委派是否处于授权和资源范围内。对于并行创建多个 Work 的情况，需要记录关联与资源分配，避免所有子任务都认为自己拥有完整总预算。

具体是预留额度、硬上限还是其他计量方式，属于实现待决。必须保持的原则是：**子任务的成本可追踪，委派不构成无限放大预算的通道。**

预算耗尽或进程中断时，Runtime 应能够保存可恢复状态和可报告结果，而不是依赖模型在最后一轮恰好主动总结。

### 12.4 同一 Agent 的多个 Goal

一个 Agent 可以挂载多个 Goal，每个 Goal 保有自己的定义、状态和上下文。它们可以运行在不同节点，不要求共享一个常驻进程或同时装载进同一个 Context。

这与 Agent Session SDK 化方向一致：Session 的状态构造、Prompt 组装和 Runner 推进应能与长期 Agent 进程解耦，持久状态不能只存在于某个进程的内存中。具体 API 与既有 SDK 对齐，不在本文凭空替换。

跨节点执行需要同时考虑所选节点的工具链、Workspace 可访问性和授权。逻辑上属于同一 Agent，并不表示每个节点天然具备同样的执行条件。

### 12.5 并发与恢复建议

同一逻辑 Session 在任意时刻只能有一个正在推进的执行者，不能让两个事件分别启动并发推理、写入同一份 Context 和状态。挂起的调用者上下文与可恢复快照不代表它们同时执行。不同 Goal 和派生 Work 可以并行，但共同写同一 Workspace 时仍需解决冲突。

运行记录和 Work Report 应能够关联到 Goal、Activation 和任务版本。重复的唤醒或重复投递的报告，不应无条件导致再次创建同一工作或重复发送通知。

这些约束服务于“目标可恢复、结果不重复、上下文不串写”，不要求把所有 Goal 强制串行化。

事件排队、批处理与恢复需要遵守 §12.9 的合同。跨节点如何实现所有权、接管与写入协调仍需确定，不能把单进程或本地文件锁直接当作分布式保证。

### 12.6 企业组织映射

企业可以用一个 Agent 承担多个部门的 Goals，也可以按产品、开发、测试、销售等职责配置不同 Agent。架构上不强制一部门一 Agent。

Agent 划分涉及身份、权限与责任边界；Goal 划分涉及持续目标与上下文边界；节点划分涉及执行资源。三者不能直接画等号。

### 12.7 事件订阅与三种等待模式

Agent 委派工作后，当前推理可以已经结束，而业务目标尚未完成。例如下游 Task 经过 25 分钟仍未交付，上层需要根据最新状态决定继续等、催办、取消或换方案。新的运行机会主要来自目标对象变化和业务超时检查；每次重新决策都应读取必要的最新状态，不能把旧上下文当作世界快照。

这类情况需要区分三种机制。它们与 UI / Work / Goal 的职责分类正交，可以在同一个 Session 中配合使用，但不能绕过各类 Session 的生命周期边界。

| 维度 | 模式一：PendingTool / 调用内等待 | 模式二：显式等待与主动订阅 | 模式三：环境弱订阅 / 半订阅 |
|---|---|---|---|
| 当前执行 | 挂起在尚未得到结果的调用处 | 本次执行可结束，等待新的运行机会 | 不负责挂起或延长执行 |
| 依赖如何表达 | 工具调用记录精确的 Task / call 依赖 | Agent 明确表达要关注的外部变化，由系统绑定订阅 | Topic、任务范围或显式配置决定相关背景 |
| 推进来源 | 依赖结果可回填，或调用的等待期限到达 | 匹配事件或业务超时事件，经 Runtime 调度 | 已有推理机会到来前检查，不自行唤醒 |
| 模型可见载体 | 对应调用的 ToolResult / Resume | 带来源的事件消息，可批量进入一次输入 | 与本次输入关联的环境块或可区分的观察材料 |
| 主要用途 | 本次工具、构建、测试或明确子任务的有界等待 | 等人确认、跨 Agent 协作、Goal 持续跟踪 | 位置、时区、对象状态、相关感知与认知 |

**模式一保留的是调用依赖。** Runtime 必须知道恢复哪个调用、回填哪个结果；事件通知只提示检查依赖，不能直接充当可信结果。等待期限到达时，可以返回“仍在运行”或未知状态，但不能伪造完成，也不意味着底层 Task 已取消。多个挂起调用应按恢复协议完整、准确地回填。

这是一种由工具执行机制承接的等待，适合有界执行。它的主要风险是上下文陈旧：等待前读过的文件、对象或权限可能已经变化，恢复同一次执行不会自动刷新这些已成功的读取。选择模式时要考虑信息有效期，不能只用固定的秒数或分钟数划线。

**模式二表达的是下一次需要响应什么。** Agent 可以说“等审批结果再继续”，但必须由工具或 Runtime 把该意图落实成可检查的订阅与超时条件；一句自然语言本身不构成订阅成功。完成委派与订阅后，本次执行可以结束，事件到达后由调度侧启动下一次处理。

事件应渲染成 Agent 能理解的消息，例如“审批对象已有结果，请检查后决定下一步”，而不是将任意事件 JSON 直接塞入主上下文。Agent 编写者可以按业务定义自然语言模板，同时保留来源、对象、版本与数据引用。这里的 `user message` 是模型输入角色：它不代表真人说过这句话，也不要求把事件的存储类型改成人类聊天消息。

**模式三提供的是决策背景。** 它模拟相关环境信息在需要决策时浮现：订机票时看到用户从硅谷到了上海，或者运行中的 Work 在下一次推理前看到针对当前任务的新要求。变化本身不值得增加一次推理，但已有推理不应继续依赖过期背景。

原事件订阅稿将半订阅限定为“用户发新消息时附带”。本设计将其扩展为 §6.3.1 的统一要求：除非显式关闭，每次推理前都有观察机会，包括没有 Message input 的 Work，以及工具返回后继续推理的时刻。观察材料可以为空，不能因为存在订阅就强制追加无变化的上下文。

“主动 / 半订阅”描述是否产生运行机会，“显式 / 自动注册”描述订阅如何建立，两者不是同一维度。半订阅也可以显式配置，不要求所有订阅都依赖旁路 LLM 才能成立。

### 12.8 订阅、唤醒与输入装配

订阅以可定位的对象、路径或资源引用为基础，同时明确关注的事件或状态范围、投递目标、主动或半订阅模式，以及取消和失效条件。具体通道由 Runtime 与事件桥接组件绑定，不要求 Agent 在自然语言意图中指定网络传输方式。

输入链路按职责分开：

```text
外部对象 / Task / Session / Timer
                 │
          事件桥接与订阅匹配
                 │
                 ├── 当前 PendingTool 依赖 → 查询实际结果 → 精确回填调用
                 │
                 ├── 主动订阅 → 待处理输入 → Runtime 调度 → 事件批次
                 │
                 └── 半订阅 → 待观察变化 → 下一次已有推理前装配
```

主动事件与普通 Message 可以共享输入调度、去重和批次提交机制，但必须保留各自身份。Work 的“无普通 Message input”不能被事件渲染后的模型角色绕过；针对执行中同一任务的用户反馈仍按 §6.3.1 写为 Task 修订，经半订阅送达。开放性的业务事件等待由 UI / Goal 承担。

**超时需要区分三个层次。** PendingTool 的等待期限决定何时回填当前调用；Runtime 的轮询或重新拉取用于检查是否已有状态变化；业务超时事件用于触发 Agent 的下一次判断。轮询一次不等于调用一次 LLM，等待状态也不会自动建立 Timer。业务需要防止漏通知时，应显式安排状态核对与超时兜底。

Session / behavior 的配置需要分别表达以下职责，具体字段不在本架构中冻结：

| 配置职责 | 需要回答的问题 |
|---|---|
| 订阅与匹配 | 关注哪个对象、哪类变化；谁负责建立、取消和恢复订阅？ |
| 激活策略 | 哪些变化需要主动运行，哪些只积累为观察；哪些超时需要重新决策？ |
| 消费策略 | 在哪些输入边界消费主动事件；一次批次的数量与上下文预算是多少？ |
| 观察策略 | 默认每次推理前检查哪些范围，如何显式关闭、控制成本和保存进度？ |
| 渲染模板 | 如何把事件表达为任务相关消息，把环境材料与用户原话、工具原始结果区分？ |

半订阅在语义上附属于本次决策。目标是让上下文构造层和 UI 能识别环境块的特殊身份，而不是把位置变化展示成用户新指令。它可以随本次输入或工具结果一起装配，但必须保留独立来源；消息的具体 block 格式由 Runtime / SDK 收敛。

### 12.9 串行推进、事件合并与可靠消费

#### 12.9.1 单 Active Run 与待处理输入

同一 Session 遵守 §12.5 的单执行者约束。推理或工具执行期间到达的普通事件先保存，不直接调用 LLM，也不抢占当前执行。主动事件等待下一次允许消费外部输入的边界，半订阅等待下一次推理前观察；明确的 stop / cancel 控制走独立的中断语义。

“待处理事件”是逻辑职责，不要求主动输入、半订阅快照和 PendingTool 依赖共用一个物理队列。三者分别保存待处理输入、尚未展示的状态变化和待回填依赖，不能把主动事件的出队等同于工具完成。

Session 已结束后不因迟到事件自动恢复。Work 的迟到反馈由 UI / Goal 判断是否创建新 Work；订阅解除、终止与队列中已有输入的处置应可追踪。

#### 12.9.2 Coalesce 与 Override

为了限制高频变化对上下文的消耗，需要两类不同的合并语义：

| 机制 | 语义 | 适用例子与边界 |
|---|---|---|
| Coalesce：状态合并 | 同一对象、同一状态维度的中间快照可以省略，只保留较新的有效状态。 | 多次位置上报通常只需最新位置；不同属性、独立要求不能仅因路径或 Topic 相同而互相覆盖。 |
| Override：语义覆盖 | 新事件按明确的业务关系使旧事件不再有效。 | 同一审批的取消可以否定此前确认；同一次任务的完成可以取代进度提示，但不能覆盖另一版本任务的事件。 |

Coalesce 的分组键至少能区分订阅、来源与状态维度；版本应优先于到达顺序，不能让迟到旧状态覆盖新状态。Override 需要事件类型声明终态或纠正关系，不能靠 Runtime 猜测两段自然语言谁“更重要”。被省略或覆盖的来源与关系应可审计。

这些优化只适用于允许丢弃中间态的材料。用户连续提出的多个独立修改、具有独立副作用的业务事件和未完成要求需要分别保留；仅有明确纠正关系时才能消除被纠正项。尤其不能把 Task 修订或 Memory 感知按 Topic 压成“最后一句话”。

#### 12.9.3 Event Batch 与消费确认

对已积累的相关主动事件，应在预算内构造一个事件批次再推理，让 Agent 一次看到相关变化。例如同时收到“任务已完成”和“用户已取消”，需要先检查它们所属的任务版本与有效条件，再决定是否交付。批处理不改变各条事件的身份与顺序，也不强制把不同 Session 的事件混在一起。

需要逐条处理的事件可以声明相应消费策略。批次容量和上下文预算之外的输入应继续保留；队列满时应提供明确的拒绝、重试或允许合并的策略，不能静默丢失必须处理的事件。

可靠消费至少区分三个事实：**通知已持久接收、材料已进入模型上下文、要求已实际处理。** 总线 ack、观察游标与执行结果分别表示不同进度，前两者不能证明修改已落实。

半订阅仅在对应版本随输入提交后确认已展示；提交期间到达的新版本必须保留，渲染失败或恢复过程不能提前推进展示进度。主动输入也应有稳定身份和提交记录，防止重投后重复进入上下文。事件只提供检查线索，真正的 Task / Goal 状态和 Final Report 仍从正式对象读取。

### 12.10 Topic、环境浮现与上下文成本

Session 的动态 Topic 表示当前工作主题及相关对象范围，帮助决定哪些环境变化值得进入上下文。目标是由低成本的旁路处理维护它：根据对话和任务变化更新 Topic，在必要时调整环境订阅、召回相关感知与认知。无需每次主推理都重新遍历所有环境对象。

这与历史压缩形成两条互补路径：历史压缩整理已经进入上下文的旧信息，环境感知筛选即将进入上下文的新信息。二者都为主推理控制信息量，但不能因为采用旁路就忽略观察时效。

Topic 更新可以由新输入、任务范围变化或积累的环境变更触发，旁路结果用于更新订阅与召回范围。旁路 LLM 不是基础订阅成立的先决条件；稳定且明确的背景可以直接配置。新输入改变主题时，要在相关决策前补齐必要观察，不能等下一条用户消息才发现本次订票已经需要当前位置。

环境注入至少需要以下成本控制维度：

| 维度 | 目的 |
|---|---|
| 相关性与可见范围 | 只观察当前 Topic / Task 相关且有权限访问的对象；各 Session 独立维护进度。 |
| 变化幅度阈值 | 区分有意义变化与状态噪声，例如位置移动距离或时间跨度。 |
| 最小注入间隔 | 抑制高频抖动；不能因此吞掉必须处理的终态、取消或明确用户修改。 |
| 单次条数与 Token 预算 | 控制新增上下文，优先重要变化；未展示且仍有效的内容继续保留。 |

“每次推理前有观察机会”不要求每次调用旁路 LLM 或全量查询。可用游标、版本、缓存与变化探测降低成本；阈值与间隔按变量类型配置，默认值和优先级策略待实现验证。

Memory 也可以通过 Topic 发现相关变化，但不必把它和外部对象强行统一成同一种存储或事件协议。Memory 继续按 §11 与认知管理需求保存来源、范围和纠正关系；相关的新感知无需等整理成长期认知即可被观察，但只是尽力而为的线索，运行中 Work 的修改走 Task 修订（§6.3.1）。Topic 改变只是召回或订阅的线索，不会自动扩大读取权限，也不能代替正式任务和结果交付。

### 12.11 模式选择与误用反例

| 误用 | 后果 | 合适的处理 |
|---|---|---|
| 用 PendingTool 等待数小时或数天后的用户审批 | 长期保留执行依赖，审批前的文件读取等结果可能已经失效。 | UI / Goal 发出审批请求并建立主动订阅与必要超时检查，本次执行结束；恢复业务时重读必要状态，条件成熟后创建 Work。 |
| 每次位置变化都主动唤醒 Agent | 高频推理成本增加，主上下文堆积大量低价值消息。 | 位置走半订阅，在订票等已有推理前按相关性、变化阈值和预算提供环境。 |
| 委派任务后只靠半订阅获知完成 | 没有新的推理机会就不会处理结果，无法保证通知、催办或继续执行。 | 需要主动后续动作时建立主动完成事件或业务超时订阅；当前有界调用的返回依赖也可以由 PendingTool 承接。 |

选择顺序是：先判断这是当前调用必须返回的结果，还是跨运行的业务变化；再判断是否需要主动响应；最后按等待期间的信息有效性、事件频率和上下文成本设置消费策略。三种模式应并存，不能用“所有变化都转主动消息”或“所有等待都变长 Tool”统一替代。

### 12.12 宿主装载、运行状态与中断

#### 12.12.1 执行者的装载与卸载

宿主维护消息路由、有效订阅和调度依据；Session worker / runner 可以按需装载、空闲卸载。投递输入不应假设目标协程已经存在：先可靠接收，再请求调度；即使唤醒提示丢失，也能通过持久输入或依赖检查继续推进。

有效运行机会包括首次 bootstrap、主动输入、Goal Activation、挂起调用的结果以及未完成提交的恢复，不能限定为“只有新 Message 到达才能装载”。启动时核对登记和持久状态，按这些条件与资源策略恢复执行，不要求所有长期 Session 常驻内存，也不能让待恢复工作无限等待新消息。

空闲卸载只释放执行资源，不删除 Session、订阅、待处理输入、调用依赖或结果；`keep_alive` 一类策略即使保留，也只表达资源驻留偏好，不决定逻辑生命周期。卸载前需确保提交完成且已发出的任务仍可查询或接管，不能把丢失工具句柄当作成功休眠。

消息入口按交互身份和会话范围绑定 UI Session；对话方、群组与路由的具体表示由宿主确定。路由层可以提前拒绝终态 Session 的新工作输入，接收与消费层仍须校验持久状态，覆盖路由缓存滞后或投递竞态。终态的结果查询和允许的验收操作与重新启动执行分开。

#### 12.12.2 逻辑状态与等待原因

状态模型需要分开记录 **Session 是否仍有效、当前执行到哪里、正在等待什么**。下表是语义要求，不冻结状态枚举：

| 状态或原因 | 允许的推进方式与边界 |
|---|---|
| 就绪 / 空闲 | 有已提交任务或有效运行机会时推进；没有实际工作时不空转推理。 |
| 正在运行 | 一个执行者推进模型、工具与上下文切换，遵守检查点和提交规则。 |
| 等待调用依赖 | 保存调用身份与期限，以结果或到期状态回填当前执行，不能转成普通聊天等待。 |
| 等待新运行机会 | UI 等交互，Goal 等调度或订阅事件；不为 Work 保留开放的需求确认等待。 |
| 暂停 / 预算不足 | 保存原因及未完成事项；是否恢复由授权控制和预算策略决定，不伪报完成。 |
| 错误 / 恢复阻塞 | 保留证据，区分可恢复执行错误、未知副作用和不可满足的任务前提，再选择恢复或失败。 |
| 已结束 | 保存终局结果和交付进度，不因新工作输入 reopen；必要时建立新的工作。 |

一个 run 的完成、一个 Turn 的关闭、一次 Goal Activation 的结束和 Session 的终止分别判断。`WAIT_USER_MSG` 一类执行信号由 Session 策略解释：UI 可以进入等待，Work 缺少必要条件时应报告无法继续；子上下文需要将情况返回调用方，不能直接把父 Session 变成交互会话。

归档与 GC 是终态数据的保留策略，不是暂停或空闲卸载的别名。清理前应考虑产物和 Report 引用、未交付结果、审计与保留要求；具体保留期和清理协议另行确定。

#### 12.12.3 中断与外部副作用

普通事件不抢占执行；stop / cancel 等控制请求走独立通道，并持久记录请求、执行结果与原因。系统应区分停止模型生成、阻止下一步调用、请求取消已发出的外部 Task，以及终止 Session，不能把一个停止信号当作这些动作都已完成。

在可提交的边界停止时，保存检查点、已完成工具结果与待处理输入。需要立即中断时，也应保留进行中调用的证据；对无法确认已经取消的调用记录未知或仍在执行，不能批量填成“已取消”来凑齐工具结果。两种方式都不会撤销已经发生的副作用。

父 Session 暂停或停止时，子 Session 与外部 Task 是否级联处理，需要按创建关系、任务归属和授权声明策略并记录结果；不能默认所有子工作都已停，也不能让父级消失后无人承担剩余工作。暂停恢复不得重置预算或丢失调用身份。

### 12.13 Task 服务映射与状态同步

业务 Task 是 Work 接受的任务书与修订载体，TaskMgr 等服务中的执行记录用于跟踪运行、依赖和成本，两者需要显式绑定。一个 Session 可以产生多个 Turn 或子工作，不能仅凭相同的 Task 名称推断一对一关系。

建立映射时保留 Work / Turn / run、父任务、创建来源及幂等键，运行、等待和终局状态由有权推进该工作的执行方更新。任务服务的状态投影不反向改写任务书；最终交付仍由 Report 与产物说明。

外部暂停或取消如果需要控制 Session，应转成经过授权的控制请求，由 Session 处理并报告实际结果；不能仅修改 TaskMgr 的显示状态就宣称执行已停止。没有接入任务服务的运行形态也应保留必要的本地执行记录与依赖，不影响 Session 的持久恢复合同。

## 13. Agent Homepage 与目标管理

### 13.1 产品定位

Agent Homepage 不只是聊天历史入口，应让使用者看见这个 Agent 的工作边界：它与谁交流、接受了哪些直接任务、承担哪些长期目标，以及目标如何驱动具体工作。

主页应明确区分三组对象，而不是把所有活动都压成同一种消息流。

| 区域 | 展示重点 |
|---|---|
| UI Sessions | 与外界的沟通对象、最近交互、关键待决事项。 |
| Work Sessions | 直接指令或 Goal 派生的任务、当前状态、结果与失败原因。 |
| Goals | 持续职责、当前状态与差距、最近检查、关联 Work、方法与成本。 |

Work 列表应保留创建来源，区分“由某个 UI 指令直接创建”与“由某个 Goal 判断后创建”，方便用户理解 Agent 为什么在做这件事。

### 13.2 Goal 详情

建议 Goal 页面提供目标说明与作用范围、创建者/受益者、达成或维护条件、距离评估方法、当前 Skills、预算、最近观察、运行记录和关联 Work。

人可以直接细化目标、调整实现方法。暂停、恢复、结束目标及修改预算可作为对应管理操作，与授权体系衔接。

Goal 的某次运行可能只有几个 Turn，也可能创建多个 Work。页面应呈现“本次观察—决策—行动—结果”的工作记录，而不是要求用户翻阅完整模型推理才能理解进度。

### 13.3 目标调整与审阅

修改 Goal 时，建议展示修改前后差异及其影响范围，并记录哪一版本驱动了哪次 Activation 和哪个 Work。

用户审阅的重点是：目标是否更近、采用的方法是否有效、哪些事情在等待条件、哪些失败需要决定，以及投入是否合理。不能用“调用很多工具”“消耗很多 Token”代替绩效。

这与传统组织中的目标管理相似：先交付职责，再按日、按周查看推进效果，而不是要求执行者用一个永不结束的任务承接全部未来变化。

### 13.4 Goal 数量与成本提示

口述中提出“超过 16 个 Goal 时提示用户成本可能较高”。本文将 **16 保留为候选提醒阈值**，不定义为硬限制，也不宣称少于 16 就一定低成本。

实际成本还取决于运行频率、单轮预算、工具开销和派生 Work。主页应逐步展示实际资源使用；资源充足且授权明确的企业部署，可以运行更多目标并分布到多个节点。

## 14. 数据结构、目录与 Runtime 接口建议

> 本章为根据前述原则提出的实现建议，用于开发对齐。字段名、文件名、状态枚举和接口形式均未冻结，不能视为现有仓库已经提供的协议。

### 14.1 最小数据对象

| 对象 | 建议包含的核心信息 |
|---|---|
| Session Record | `session_id`、`agent_id`、类型、状态、Context 引用，以及对应 Task 或 Goal 的关联。 |
| Session Execution Record | 配置版本、当前 Turn / run、上下文栈、快照与日志提交边界、初始化进度、待回填调用、等待与中断原因。 |
| Input / Observation Commit | 输入稳定身份、接收与消费进度、提交 receipt、订阅版本，以及 Task 修订和辅助观察各自的进度。 |
| Runtime / Workspace Binding | 运行身份、实际执行目标、工作目录、工具环境与持久配置的对应关系。 |
| Delivery Record | 回复或 Report 身份、阶段与版本、接收方、原消息引用、发送结果与重试进度。 |
| Activation Reason | 目标对象与版本、触发来源、业务原因、预期与实际触发时间；不等同于新的用户指令。 |
| Intent Analysis Result | 分析结果类型、必要事实与依据、缺口、用户选项、Task/Goal 草案或创建引用。 |
| Task Definition | 目标、范围、验收条件、输入、依赖、关键假设、Runtime、Workspace、授权、Manuals、创建来源。 |
| Goal Definition | 身份、目标、作用范围、生命周期、创建者/受益者、达成与距离判断、基础 Skills、预算与权限引用、版本。 |
| Goal State | 最近观察与来源、距离评估、不确定性、活动 Work、最近决策，以及当前有效 Skills 的引用。 |
| Goal Activation Record | 本轮标识、使用的 Goal 版本、观察、决策、直接行动、派生 Work、实际成本及结束原因。 |
| Work Final Report | 终局状态、交付、验证、失败原因、副作用、产物引用、后续条件和可选经验候选。 |
| Tool Intent Record | 不存在的工具调用、发生上下文、关联任务、归类与处理状态。 |
| 能力资产记录 | Skill / Manual / XLLM 各自的定义、适用范围、版本、来源及验证材料；不要求三者使用完全相同的 Schema。 |

Task Definition 保留创建时的任务依据；执行期的明确修改作为 Task 修订另行追加，保留来源、纠正关系与处理结果，不能把“稳定任务书”解释为忽略用户新要求。Goal Definition 可以修订，但历史执行必须能找到当时使用的版本。

Goal State 中的“距离”可以是结构化指标，也可以是有依据的自然语言评价。不要为了统一字段，强制所有目标都输出一个 0—100 分。

### 14.2 Goal 定义示例

以下 YAML 仅示意软件维护 Goal 的定义方式，不是可直接交给现有系统运行的配置，也不包含真实仓库数据。

```yaml
goal_id: goal_software_maintenance_example
revision: 1
owner: agent_owner
beneficiaries:
  - project_team
lifecycle: maintenance

objective: >-
  在已授权的软件项目范围内，持续分类和推进问题，
  将已确认、条件齐备的变更转化为有界开发任务。

scope:
  project_ref: project_example
  workspace_ref: workspace_example

healthy_state: >-
  当前已知问题有明确分类与处理状态；
  已确认且可执行的事项得到推进；没有被重复创建的开发工作。

distance_evaluation: >-
  检查未分类问题、待澄清事项、已确认未实施的变更，
  以及待吸收的测试和评审反馈。
  对缺少依据的状态标记未知，不假设问题已经解决。

initial_skills:
  - software_maintenance_methodology
  - issue_triage_methodology

constraints:
  - 需求未确认时不创建开发 Work。
  - Work 的结束条件不得是无限等待 Issue 被关闭。
  - 未取得合并授权时不合并 PR。
  - 不静默修改已经运行的 Work 任务书。

budget_policy_ref: goal_budget_policy_example
permission_policy_ref: project_permission_policy_example
```

当前有效 Skills 可以在运行中演进，建议单独维护其版本或引用；初始声明与当前有效集合不应混为一个无法追踪的历史字符串。

Goal 的唤醒频率与节点分配属于 Runtime 调度配置。它们可以在产品界面与 Goal 一起管理，但执行逻辑不因此承担自我唤醒职责。

### 14.3 Final Report 示例

以下同样为虚构的结构示例，展示关键前提失效后如何提供可用于重新分析的结果。

```yaml
work_id: work_fix_example
task_id: task_fix_example
parent_goal_id: goal_software_maintenance_example
goal_revision: 1
status: failed

task_summary: >-
  按已确认方案修改指定模块，运行约定测试并提交 PR。

completed:
  - 已检查当前工作区与任务所引用的环境。
uncompleted:
  - 未实施修复。
  - 未完成验收测试，未创建 PR。

failure:
  category: assumption_invalid
  original_assumption: 任务所需接口存在于指定版本的项目中。
  observed_state: 执行时发现该接口已被移除，原方案无法直接实施。
  impact: 继续开发需要重新确认替代接口和变更范围。

evidence_refs:
  - observation_record_example
artifact_refs: []

side_effects:
  workspace_changes: 无
  external_actions: 无

required_for_next_attempt:
  - 确认新接口及对应的任务范围。
  - 根据当前版本重新形成任务书。

experience_candidates: []
```

新的 Work 可以使用此 Report 及其证据，而不必把旧 Work 的全部 Context 装载进来。Report 中的“建议下一步”也不等于已经获得执行授权。

### 14.4 目录组织建议

目录应体现 Goal 比 Work 更丰富的长期状态，但不要复制多份不一致的目标定义或强制把共享 Workspace 放进 Session 目录。

```text
agents/<agent_id>/
├── goals/
│   └── <goal_id>/
│       ├── goal.yaml                 # 目标定义与策略引用
│       ├── state.json                # 最近状态、距离、关联工作
│       ├── current_skills.json       # 当前有效 Skills 及版本引用
│       ├── revisions/                # 目标/方法的变更记录
│       └── activations/              # 每次运行的观察、决策与成本
│
├── sessions/
│   ├── ui/<session_id>/
│   │   ├── context.json
│   │   └── history.jsonl
│   ├── goal/<session_id>/
│   │   ├── binding.json              # 关联 Goal，不重复定义目标
│   │   ├── context.json
│   │   └── checkpoints/              # 长期上下文的恢复信息
│   └── work/<session_id>/
│       ├── task.yaml                 # 稳定任务书，含 Workspace 引用
│       ├── context.json
│       ├── worklog.jsonl
│       └── final_report.json
│
├── capabilities/
│   ├── skills/                       # 方法论资产
│   ├── manuals/                      # 操作手册资产
│   └── xllm/                         # 单次推理工具配置
│
└── tool_intents/                      # 未满足工具意图及处理结果
```

以上是逻辑组织示意，不要求将现有数据库或对象存储改成这些物理文件。Agent 共享 Memory、消息与 Workspace 继续引用其既有存储，不在这里另造一套副本。

Runtime 私有的配置、状态、run 快照、输入 receipt、日志与锁应有清晰边界；可重建的工具执行视图与长期产物分开管理。旧稿的 `.meta/session.json`、`state.snap` 和“禁止在 Session 目录放 bin”不作为新布局约束，当前磁盘协议与迁移差异见 §15.6。

### 14.5 Runtime / SDK 职责接口

不先冻结函数签名，但需要明确以下调用合同：

| 接口职责 | 输入重点 | 输出/约束 |
|---|---|---|
| 分析用户意图 | 请求、必要上下文、授权及可用环境 | Task、Goal、澄清需求或明确不能收敛的结果；隔离分析过程。 |
| 创建 Work | 完整 Task、创建来源、Workspace、运行环境与资源 | 创建结果或明确拒绝理由；不接受开放等待作为任务核心。 |
| 推理前半订阅观察 | 当前 topic、可见范围、独立观察进度、预算与显式关闭设置 | 默认每次推理前装配 Task 修订（必达）与相关感知/认知增量（尽力而为）；无需 Message input，不额外唤醒，也不将观察确认当作修改已落实。 |
| 登记/取消事件订阅 | 对象或路径、关注范围、主动/半订阅模式、业务超时与生命周期 | 返回明确的订阅结果；Runtime 绑定通道与唤醒条件，保留取消及失效记录。 |
| 构造主动事件批次 | 已匹配的输入、来源与版本、合并规则、消费预算 | 在允许的输入边界串行消费，按模板表达事件，保留独立要求和覆盖关系。 |
| 确认观察进度 | 本次实际展示的事件版本及输入提交结果 | 只确认已提交版本，新到或未展示材料继续保留；与实际执行结果分开记录。 |
| 装载与恢复 Session | 持久配置、执行所有权、Runtime / Workspace 绑定、提交和调用记录 | 校验后补齐提交或恢复执行；未知副作用和不支持版本明确阻塞，不重复启动已提交工作。 |
| 暂停/停止执行 | 授权主体、目标范围、控制原因与子工作策略 | 分别报告模型、工具、子工作和 Session 的实际状态，不默认承诺外部副作用回滚。 |
| 投递回复与报告 | 稳定输出身份、内容、阶段、接收方与原路由 | 先保存待投递记录再发送；重试沿用原身份和内容，不重复生成业务结果。 |
| 创建/调整 Goal | 目标定义、修改权限、目标版本 | 持久化目标及变更记录；不静默改写已有 Work。 |
| 推进 Goal Session | Goal 引用、当前运行机会、预算、相关新信息 | 运行记录、状态更新、直接动作或 Work 创建请求。 |
| 结束 Work | 执行状态、验证和副作用 | 可供上层消费的 Final Report。 |
| 获取工作结果 | Work/Report 引用及读取权限 | 结果与产物引用，不强制导入完整历史。 |
| 选择/更新能力 | 目标或任务方向、可见能力、版本与授权 | 当前适用 Skills / Manuals / XLLM 配置。 |
| 记录工具意图 | 失败调用与必要上下文 | 可后续归并和处理的意图记录，不同步强制打造。 |

UI 和 Goal 创建 Work，应共享就绪性与授权检查。SDK 不应让某一种调用入口可以创建无限生命周期的 Work，而另一种入口才执行边界检查。

### 14.6 需要明确的事件关系

Work 结束要能使创建方获得结果；Goal 调整要能使后续运行使用新版本；外部状态变化要能成为新的观察线索。这些关系可以通过现有消息、事件或状态查询机制实现，不在本文规定独立消息总线。

结果处理至少要能识别“哪个 Work、为哪个版本目标、在什么任务条件下产生”。旧 Work 的成功或失败不能不加判断地覆盖已经调整过的 Goal 状态。

三种机制应按调用关系选择：父 Session 挂起在本次子调用上时，结果回填对应调用；需要在本轮结束后主动处理结果时，建立主动订阅；只需为后续已有推理补充背景时，使用半订阅。通知可以共用事件基础设施，但不能同时被无条件当成新指令、工具结果和已处理回执。

事件摘要不替代 Final Report。创建方收到完成或超时提示后，仍需核对正式状态与产物，再决定是否通知用户、继续等待或创建新 Work。

### 14.7 Runtime 与 Workspace 绑定

Session 的持久绑定说明实际使用的运行身份、执行目标和工作目录；Workspace 可以位于 Agent 内部、用户项目或另一个可访问的存储位置。恢复时重新解析并核对绑定，不能因当前宿主目录或环境变量改变，就让旧调用在另一个项目里继续运行。

工具声明、能力策略和实际进入执行环境的命令视图需要一致。视图可以重建，但相关版本与依赖应可验证；权限、凭据和当前可用环境需在继续执行前核验，不能把旧快照中的配置视为永久授权。

Workspace 的 `current_session` 一类占用提示不构成写锁。多个 Session 共享 Workspace 时，需要按实际写入范围进行调度、锁定或隔离，并处理外部人员的修改；Session 自身的 lease 只防止同一 Session 被重复推进。绑定不符或写入冲突应作为可见的等待、阻塞或失败原因，不能靠上下文压缩掩盖。

### 14.8 回复、报告与可靠投递

UI 的回复关联到原交互路由、触发输入与当前 Turn；Work 的结果关联到创建方和 Task / Goal 版本。内部报告是否再转成面向用户的消息由 UI / Goal 决定，不能仅因 Work 结束就向任意对话渠道广播。

输出先与执行结果或报告一起持久登记，再交给消息通道发送。发送失败可按策略重试，但必须复用同一输出身份、内容与目标，不能重新调用模型生成“同一结果”后当作重试；重启后继续处理未完成投递。外部通道能否保证幂等仍依赖其合同，不能仅有本地去重就宣称端到端恰好一次。

进度与终局报告按 §6.6 的交付策略区分，投递记录至少标识报告、阶段、版本和接收方。对外“已发出”、创建方“已收到”和“已吸收结果”分别记录；同一报告被再次投递不能无条件重复通知用户或再次创建 Work。验收、接受或丢弃产物也是独立动作，不会把已经结束的 Work 重新变成运行态。

## 15. 迁移路径与实施顺序

### 15.1 保留已经有效的机制

据本次讨论，UI 的复杂分析分流与长期上下文控制已基本形成实践。改造应先明确语义和边界，而不是把已有运行方式整体推翻。

Context Fork、Work 执行、Final Report、已有 Task 等待和 Agent Memory 都可以继续复用。需要改变的是它们被用于什么职责，而不是仅仅换名称。

### 15.2 分阶段实施

| 阶段 | 主要工作 | 退出条件 |
|---|---|---|
| 一：定义与盘点 | 固定 UI/Work/Goal 术语；盘点长期等待的 Work 和已有 Self Improve 行为。 | 知道哪些保留为 Work，哪些迁为 Goal，哪些仍需另行分析。 |
| 二：收紧 Work | 明确任务书、就绪检查、失败规则和 Final Report；识别等待 Task 中的开放业务等待。 | 不再新建“等待需求成熟/Issue 关闭”的伪有界 Work。 |
| 三：引入 Goal | 建立 Goal 对象、持久状态、单次运行、预算和派生 Work 回流。 | 一个 Goal 能跨多次唤醒推进，并正确吸收 Work 结果。 |
| 四：扩展意图分析 | 在原分析流程中支持 Task / Goal 两种主要结果，保持 Fork 隔离。 | 用户可以经澄清创建合适类型，不再强制所有意图进入 Work。 |
| 五：迁移内部目标 | 接入 Memory 整理、经验结晶、XLLM 结晶、离线 Self Correct。 | 同一职责不会被旧循环与新 Goal 重复执行。 |
| 六：管理与治理 | 上线 Goals 视图、目标编辑、成本追踪及需要的跨节点能力。 | 用户能够理解目标、工作来源、进度和资源使用。 |

这是建议的交付拆分，不是不可调整的工程排期。实际顺序可依已有实现基础并行推进，但不能跳过 Work 边界和目标状态的语义确认。

### 15.3 旧机制映射

| 原机制/用法 | 迁移方向 |
|---|---|
| `try_create_work_session` | 复用分析能力，扩展为多结果意图分析；更名与兼容接口待定。 |
| UI 中的深度工程探索 | 保持或迁入 Intent Analysis Fork，不继续扩大 UI Context。 |
| Work 长期等待 Issue、评论与确认 | 迁入相关 Goal，具体实现工作拆成独立 Work。 |
| Self Check 扫描 Notebook 并判断提醒 | 将有明确目标的部分建立为 Goal，从相应业务对象及统一 Memory 获取线索；不为该用途保留独立 Notebook。 |
| 感知到认知整理 | 维护型 Memory 整理 Goal。 |
| Work 经验与操作型 Skills 维护 | Manual 结晶 Goal；保留旧资产引用和格式兼容。 |
| 人工处理经验自动化 | XLLM 结晶 Goal。 |
| 调用失败现场造工具 | 记录意图，迁为离线 Self Correct Goal；复杂开发下沉 Work。 |

不应该在没有检查用途的情况下，把所有旧 Self Improve 内容自动改名为 Goal。缺少目标边界、评估方式或授权条件的行为，需要先收敛定义。

### 15.4 兼容与防止重复执行

现有长期 Work 迁移时，应提取已确认的事实、有效产物、待跟踪状态和必要历史，建立 Goal，而不是直接把全部旧 Context 无限继承。

原 Work 是否终止、是否仍有正在运行的工具，以及哪些外部动作已经发生，要显式记录。旧周期任务和新 Goal 不应同时给用户发送相同提醒、同时生成重复 PR 或重复消化同一批记录。

历史 Skills 不必一次性全部重写。可以先标记用途与消费方，对操作型内容建立 Manual 映射；随后通过结晶和验证逐步整理。

### 15.5 事件订阅的实现基础与迁移差距

以下是对当前仓库源码的核对，用于安排迁移，不是对前文目标的替代定义。尤其不能因为当前只在受控输入前注入半订阅，就把 §6.3.1 的“每次推理前观察”降级为等待用户消息。

| 能力 | 现有实现基础 | 面向新设计的迁移要求 |
|---|---|---|
| Session 分类与输入策略 | 内建模板仍为 `work / ui / self_improve / self_check`；默认 Work 单 Turn、无输入队列。 | 引入 Goal 职责与生命周期；保留 Work 无普通 Message input 的边界，补齐执行中观察。 |
| PendingTool | 按 Task ID 查询；所有挂起调用可回答后以 `ResumeFill::ToolResults` 恢复同一 run / Turn。Task Finished、Unknown 或各调用 `until_ms` 到期均可能使等待可回答。 | 复用精确依赖与恢复机制；限制开放业务等待，明确到期仍运行和旧读取失效的处理。 |
| 订阅与事件身份 | `subscriptions` 支持 `active / semi`，来源为 `session / object_event / task / timer / system`；`subscribe / unsubscribe` 控制修改配置。总线区分 `msg / event / control`。 | 复用结构化事件与订阅；完善业务意图到订阅、失效、超时及恢复的合同，不把自然语言意图当作已登记。 |

| Task 修订 | 尚无修订概念；订阅已支持 `task:<task_id>` 来源（`SubscriptionSource::Task`），可承载任务事件。 | 新增 Task 修订的数据与授权；Work 创建时由 Runtime 订阅自身 Task，子 Session 由父 Session 按子对象范围订阅；修订必达，不受 Memory 预算截断；Final Report 记录最后观察的修订编号。 |
| 半订阅时机 | checkpoint 路由并保存 Observe，但不注入；目前在 `on_init / on_input / on_context_switch` 受控输入前展示。 | 扩展为默认每次推理前观察，包括工具返回后的继续推理；明确不同推理模式中的挂接位置与显式关闭方式。 |
| 半订阅载体 | `prompt.semi_subscription_snapshot` 渲染独立的 snapshot user message，与其后的受控输入同批提交。主动事件通过 `input.events / input.items` 等视图渲染。 | 保留来源可辨性与原子提交，收敛与当前输入关联的环境 block / 观察材料格式；当前独立消息不等于目标 UI 语义已完成。 |
| 合并与观察进度 | semi 按 `(subscription_id, source)` 分组；`latest / terminal` 分槽，槽内比较版本，终态不被非终态覆盖。仅按 receipt 清理实际展示版本。active 没有同等状态合并，当前也没有通用语义 Override。 | 复用版本与精确确认机制；区分状态维度、独立要求及显式纠正关系，再实现适用事件的 Coalesce / Override。 |
| Topic 与成本控制 | 有 Topic 字段、显式/隐式订阅和每批变化预算，已有默认用户时区半订阅；未形成旁路 LLM 维护 Topic、自动重订阅与统一相关 Memory 观察链路。 | 实现 §12.10 的范围选择、增量观察、变化幅度与间隔控制，保证相关新感知及时可见。 |
| 事件桥接与超时 | 已有 Timer / KEvent bridge；Timer 按 `every_secs` 生成事件，再由订阅决定路由。Session 状态拉取目前进入半订阅；PendingTool 也支持无通知时轮询查询。 | 补齐需要主动响应的状态来源与超时核对；不能将定时轮询或所有 Session 订阅描述成已经保证主动唤醒。 |

## 16. 验收场景与观测指标

### 16.1 核心验收场景

以下是新架构的目标验收要求，不表示当前代码已经全部满足；事件订阅相关的实现差距见 §15.5。

| 场景 | 预期行为 |
|---|---|
| 用户要求一个功能范围明确的小游戏 | 形成 Task，创建 Work，按验收条件完成并输出 Report。 |
| 用户提出“长期保持健康”等过宽意图 | 先澄清，不直接创建无限执行的 Work 或无边界 Goal。 |
| 意图分析读取大量文件并调用检索工具 | UI 只保留必要分析结果，不携带全部探索过程。 |
| UI 长期交互达到压缩阈值 | 按配置压缩并保留关键决策；检查前后 Token 使用，而非声称必然命中缓存。 |
| 创建开发任务时仍缺需求确认 | 不创建一个等待确认的长期 Work。 |
| Work 遇到普通构建错误 | 在既定任务与资源边界内修正，不因任何小错误立即失败。 |
| UI 在 Work 执行中连续提出同目标修改 | UI 追加 Task 修订，不写 Memory 感知；无 Message input 的 Work 及相关子 Session 在下一次推理前看到修订并调整，独立要求和纠正关系不丢失，无关 Work 不接收；Final Report 记录最后观察的修订编号。 |
| Work 在同一次运行中工具返回，且没有新 Message | 默认检查半订阅并将相关观察随本次输入装配；显式关闭才跳过，不把 Runtime 观察伪装成工具原始返回。 |
| Work 结束后用户再修改，或修改未赶上最后一次观察 | 由 UI 基于有效产物与未处理要求创建新 Work，不恢复旧 Work，不把仅写入或已观察当作已落实。 |
| Work 发现关键接口/权限条件不成立 | 明确失败，报告差异、已做工作和下一次需要的条件。 |
| 修复 Work 已提交 PR，但 Issue 仍未关闭 | Work 按自身约定结束；Goal 继续跟踪，不强制延长 Work。 |
| 原 Work 已结束后，Issue 出现新的有效修改意见 | Goal 重新收敛具体变更，条件成熟后创建新的 Work；仍在执行的同任务反馈按 §6.3.1 处理。 |
| 用“等待子 Task”包装无限业务等待 | 能识别其真实边界问题，不能据此绕过 Work 约束。 |
| PendingTool 等待通知丢失或达到等待期限 | 查询正式 Task 状态，按调用身份恢复；到期仍运行不伪造完成，不因一次轮询调用 LLM。 |
| Goal 委派任务后结束本轮，之后收到完成或业务超时事件 | 经主动订阅与 Runtime 调度重新判断，不依赖用户再发消息，必要时重读状态和 Report。 |
| Session 推理中连续收到主动事件 | 普通事件排队，不启动并发推理；在允许的消费边界按预算批量处理，控制中断另行处理。 |
| 高频环境变化且没有新的运行机会 | 合并适用的状态变化，不由半订阅自行唤醒；下次已有推理前按相关性和预算观察。 |
| 同一对象出现旧版本重投、终态和明确取消 | 旧状态不覆盖新状态；按声明的覆盖关系处理，保留审计来源，不丢弃独立用户要求。 |
| 半订阅输入提交期间又到达新版本，或渲染失败后恢复 | 仅确认实际提交展示的版本，新版本及未展示材料继续保留，不把接收确认当作已处理。 |
| 新输入改变 Topic，例如订票需要当前位置 | 在本次相关决策前补齐必要背景，不等下一条用户消息；旁路与召回受权限、预算约束。 |
| 重复创建请求或 bootstrap 提交后重启 | 识别已有 Work 与初始化提交，不再创建同一工作或重复执行首批输入。 |
| 输入已持久接收但上游确认失败 | 重投去重；模型上下文只按提交身份追加一次，未选中输入不受影响。 |
| 输入快照已写但 Session 消费进度尚未提交时崩溃 | 从 receipt 补齐提交，不重复追加消息，也不越过未完成提交启动工具副作用。 |
| 工具可能已执行但结果未持久化 | 查询实际状态或显式标记未知 / 阻塞，不从头重跑调用。 |
| 宿主重启时没有新用户消息，但有待恢复 run 或 Task 结果 | 依据持久状态与资源策略恢复；空闲卸载不会丢弃有效工作。 |
| 切换、子上下文返回或 Fork 后重启 | 恢复正确入口、版本与调用关系，子上下文结束不错误终止父 Session，权限与预算不被重置。 |
| 停止模型时外部工具仍未确认取消 | 报告工具的实际状态与副作用，按策略处理子工作，不宣称全部已撤销。 |
| Runtime / Workspace 绑定变化或多个 Session 争用写入范围 | 核验并显式阻塞、调度或隔离，不在错误目录继续执行，不把占用提示当写锁。 |
| 最终结果已保存，但消息发送失败后重启 | 从持久待发记录使用同一输出身份、内容与目标重试；不重新推理生成结果，不 reopen Work。 |
| 维护型 Goal 本轮无待处理项 | 记录无需行动，本轮结束；Goal 保持存在。 |
| Goal Context 压缩并恢复 | 当前 Skills、目标版本、关键经验和关联 Work 可恢复。 |
| Goal 预算不足以推进所有事项 | 按优先级处理或不行动；保留未处理原因，不伪报达成。 |
| Goal 创建多个 Work | 资源归属和关联可追踪，不借子任务无限放大预算。 |
| 用户修改 Goal 时已有 Work 在运行 | 保留旧任务书，明确处理旧 Work，不静默改变其目标。 |
| 工具不存在 | 留下带上下文的意图信号；不必在原调用中递归打造工具。 |
| 一次 Work 产生了经验候选 | 可进入结晶流程，但不直接成为全局有效 Manual。 |
| 同一观察被 Work Report、UI 和 Goal 摘要转述 | 追溯到同一原始事件，不算多份独立证据；进度与 Report 仍由原对象交付。 |
| Memory 整理存在缺证材料但本轮无新增依据 | 保存暂缓原因与重评条件，不强造认知或反复推理；未处理材料不因当轮结束被清理。 |
| 用户明确说“以后这个项目……” | 一次表达可形成有来源和范围的偏好；普通感知与显式“记一下”共用 Memory 路径。 |
| 企业输入匹配 XLLM | 按配置调用一次推理工具，不自动创建完整 Agent Session。 |
| 多个 UI 提供同一 Goal 的相关信息 | 在授权范围内融合，不串入无关或私密会话内容。 |
| 多节点恢复同一逻辑目标 | 保持目标身份与状态连续，避免同一上下文并发冲突及重复动作。 |

### 16.2 建议观测指标

**UI 层**关注主 Context 的规模、压缩前后变化、分析过程是否泄漏到主会话、关键用户约束是否保留，以及真实缓存与成本表现。

**Work 层**关注生命周期、开放等待占比、成功与失败是否有证据、失败原因是否可用于重新决策、完整 Report 比例，以及失败后重复携带无效历史的情况。

**Goal 层**关注目标状态的实际变化、单次运行成本、无动作检查、有效派生 Work、重复行动、策略调整及用户介入情况。不要仅用执行次数或 Token 消耗排名。

**结晶层**关注被复用且有效的 Manuals/XLLM、错误资产修正、重复探索是否减少，以及工具补齐需求是否得到合理处置，而不是只统计新增资产数量。

**事件与观察链路**关注主动事件到处理的延迟、半订阅到实际展示的延迟、每次观察的上下文成本、重复输入与遗漏、合并和覆盖的依据，以及已观察却尚未落实的要求。单纯统计事件接收量或 ack 数量不能证明目标已被推进。

本文不提供虚构性能结果，也不预设必须达到的成功率。具体阈值需要结合实际任务与运行数据确定。

## 17. 已明确的设计方向与待决事项

### 17.1 本次采用的设计方向

本节描述本次文档选择的架构方向，不意味着团队对每一个参数和实现细节已经达成一致。

**分类上**，UI 面向持续交互，Work 面向确定任务，Goal 面向持续目标；不能再只按有无新用户输入分类。Goal 是对象，Goal Session 是承担该目标的上下文与运行机制。

**UI 上**，复杂意图分析通过 Context Fork 完成，只回传必要结果。约 30%→80%→30% 是当前上下文目标区间，依靠任务分流和压缩共同实现。

**Work 上**，明确目标、前置条件和结束条件，允许失败并以 Final Report 交付结果。Work 无 Message input；每次推理前通过对自身 Task 对象的半订阅观察 Task 修订，在执行中理解同目标修改，结束后的修改创建新 Work。不通过开放等待把它做成长会话，也不默认将失败的全过程传给下一个 Work。

**Goal 上**，每次唤醒观察现状、评估距离、按预算决定行动和优先级；允许不行动，也允许创建 Work。目标可以长期维护，可以由人调整；Session 不负责自我唤醒。

**能力上**，方法论 Skills、操作 Manuals 和单次推理 XLLM 需要区分。Memory 整理、结晶与离线 Self Correct 可以成为 Agent 自身的 Goal。

**管理上**，Agent Homepage 同时呈现交互、执行与长期职责。多个 Goal 可以分布式运行，工作结果和成本需要可追踪。

### 17.3 架构收敛

本次设计的核心不是让 Work Session 变得更能“坚持”，而是承认一次确定执行与长期承担目标属于不同的工作模式。

**UI Session 接受安排，Goal Session 承担职责，Work Session 交付结果。**

用有界 Task 控制执行，用持久 Goal 承接变化，用 Report 连接各个上下文，用 Skills 与 Manuals 积累能力，才是本次 OpenDAN Agent Session 架构调整的主线。
