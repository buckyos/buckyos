# 企业知识库建设：OpenDAN 的两种使用范式

企业建设 AI 知识库时，常见的起点是把文档切分成文本块，生成向量，存入向量数据库，再根据用户的问题召回相关内容交给模型回答。这是一条有价值的技术路线，尤其适合从大量资料中快速发现语义相关的内容。

在 BuckyOS / OpenDAN 的设计中，我们更关注知识如何参与 Agent 的工作。企业应先明确 Agent 的职责、资料的组织方式和查询需求，再决定是否建立向量索引。已经建设的向量数据库可以继续作为查询工具接入。

我们把知识库的使用分为两种范式：**查询型 Agent 围绕一个明确问题查找、理解并合并资料；通用 Agent 在持续工作中，需要先意识到某些知识与当前任务有关，再决定是否查询。** 前者重点解决查询与理解，后者还要解决知识介入的时机。

## 第一种范式：由 LLM 驱动查询、理解和结果合并

类似 Mia 的资料查询 Agent，以及企业面向消费者提供的产品问答、售前咨询和技术支持 Agent，都可以按这一范式建设。这里借用的是 Mia 的查询职责；对外能够交付的数据仍受当前用户权限约束，具体可以采用下文介绍的两种授权方式。

这类 Agent 的任务本身已经提供了查询时机。用户询问某个产品能否满足需求，Agent 就应当查阅相关资料。系统需要让 LLM 能够拆解问题、选择数据源、调用查询工具、阅读结果，并在证据不足时继续查询。

一个典型过程是：

1. **理解问题。** 确定产品型号、使用环境、时间范围等条件；缺少关键条件时向用户补充询问。
2. **定位资料。** 根据目录、元数据、关键词、业务字段或语义相似度，缩小候选范围。
3. **按问题理解内容。** 阅读相关章节、表格或图片，提取支持当前判断的事实及其适用条件。
4. **合并与核对。** 比较多个来源，检查版本、前提和冲突；必要时改写查询、补充阅读。
5. **返回有依据的回答。** 给出结论、适用范围和来源；资料没有覆盖的部分保留为未知。

在这个过程中，查询工具可以有多种选择：

| 企业资料的形态 | 可采用的查询方式 |
|---|---|
| 订单、库存、产品参数等结构化数据 | 业务 API、受控 SQL、字段过滤 |
| 按产品、项目和版本整理的文档 | 目录浏览、元数据过滤、文档目录与章节定位 |
| 有明确型号、错误码、术语的资料 | 关键词、全文索引、`rg` 等文本搜索工具 |
| 已定位的图片、扫描件或其他媒体 | OCR、专用解析工具、按目标调用多模态模型理解 |
| 值得预处理、需要反复查询的非结构化资料 | 多模态 LLM 生成文本摘要，与提取文本一起纳入全文检索 |
| 大量缺乏明确定位线索的非结构化资料 | 向量检索、全文与向量混合检索、重排序 |

**LLM 负责组织查询和判断证据，底层系统负责实际搜索与读取。** 让 LLM 驱动查询，不意味着每次把整个知识库交给模型通读。

业界也在采用类似的按需读取思路：通过文件路径、查询入口和链接等轻量引用，让 Agent 在工作时逐步获取上下文。同时，运行时探索往往比读取预计算结果更慢，需要根据任务组合使用。参见 Anthropic 的 [Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)。

### 借鉴 `llm_understand_media`：按需理解，也可以先生成文本摘要

OpenDAN 的 `llm_understand_media` 设计提供了一种值得用于知识库建设的思路：保留原始媒体及其引用，在需要时带着明确目标启动一次专门的理解过程，再把与目标有关的观察和结论返回给主 Agent。

将这种思路用于企业资料，可以组织成以下流程：

> 定位原始资料 → 指定本次需要理解的问题 → 解析或预处理 → 模型理解 → 返回精简结果与原始资料引用 → 由主 Agent 合并答案。

例如，用户上传一张设备接口照片，并询问某个配件能否使用。Agent 可以先识别图片中的接口特征，再查询配件的规格和兼容条件，最后合并判断。如果照片无法区分两个外观相近的型号，就继续核对铭牌，而不根据相似的产品描述直接给出确定答案。

在这一流程中，媒体理解承担的是具体问题下的阅读工作。主 Agent 可以保留“识别到了哪些特征、结论基于什么、原图在哪里”，后续追问需要新细节时再打开原始资料。原始图片无需在每一轮对话中重复进入模型上下文。相关设计见 [LLM Understand Media](<LLM Understand Media.md>)。

**如果预处理成本可以接受，还可以通过多模态 LLM 为非结构化内容生成文本 summary（摘要），再归并到统一的全文检索中。** 这是把按需理解思路扩展到知识库预处理：让图片、扫描件等资料先获得一份可搜索的文字描述；音视频也可以在接入相应解析和模型能力后采用同一路径。

> 非结构化资料 → 解析、OCR 或多模态 LLM 理解 → 文本摘要及提取文本 → 全文索引 → Agent 查询命中 → 按需回看原始资料。

用于检索的 summary 应包含有助于查找的实体、场景、主题、关键关系和限制条件。原始资料中能够准确提取的型号、错误码、数字和表格文字，应与摘要一起保留；长资料可以按页、章节或时间段组织，避免只留下一个过于笼统的总摘要。例如，一张产品接线图可以同时保存图中可读的接口名称，以及模型生成的连接关系描述，随后通过普通文本查询找到它。

这条路线把一部分模型成本前置，让后续查询可以复用全文索引。summary 属于有损的派生资料，可能遗漏细节或出现理解错误，因此必须关联原始内容、版本和来源权限。资料更新时同步更新摘要和索引；当问题涉及摘要未覆盖的条件时，再读取原文或重新理解媒体。企业可以先处理高频使用的资料，逐步评估这一投入是否值得。

**对于资料能够被定位、单次候选范围有限、答案依赖完整上下文或图文关系的场景，我们建议优先采用这种按需理解范式。** 相比只把预先切好的相似文本块交给模型，它更有利于保留章节条件、表格关系和视觉细节，并针对问题补充读取。这里的“效果更好”主要指回答的完整性、证据解释和复杂条件处理，不代表所有场景下都更快、更便宜，或已有统一的准确率优势。

这种方式仍然需要做好资料组织：稳定的文件引用、清楚的目录、版本和权限，以及可用的搜索入口。原始资料、模型生成的摘要和索引应能对应起来；摘要帮助定位，最终结论仍要能回到原始证据。

**面对文本内容和结构化内容，对于大部分以明确事实、条件筛选和原文核对为目标的企业查询，我们建议优先采用全文索引、数据库查询和 `rg`。** 在这些任务中，它们通常比纯向量相似度召回更准确、可控，也更便于 LLM 根据结果逐步逼近答案。这里比较的是适合各类数据的查询工具组合与单纯向量召回，具体优势来自已有文本和结构能够被直接利用：

- **全文索引**适合定位型号、专业术语和错误码，并结合字段、目录或版本过滤。语义相似的产品描述不等于同一个型号，召回相近错误也不能代替命中实际错误码。
- **数据库查询**适合精确条件、数值范围、关联、排序和聚合。例如“某型号最近一个月有哪些未完成订单”，应直接查询业务记录；相似文本的前若干条结果不能保证记录完整，也不能代替准确统计。
- **`rg`（ripgrep）**适合在可访问的文本文件、配置、日志和代码中搜索字符串或模式，再打开命中位置附近的原文。它直接查询当前文件，无需先生成向量；大规模文本服务则可以使用持久化全文索引。

**LLM 的优势还在于能够利用上一次结果改写下一次查询。** 例如，先从用户描述中提取产品名，再从目录确认型号，用全文检索找到限制条件，用数据库核对适用记录，最后读取相关章节验证结论。第一次没有找到时，还可以扩展同义词、调整过滤条件或改查其他数据源；不同来源冲突时，也可以继续核对版本。这种“提出查询 → 阅读证据 → 缩小或修正范围 → 再查询”的循环，比把一次相似度召回直接当作最终证据，更能发挥 LLM 的推理能力。

因此，已有文本可以直接进入全文检索，结构化内容可以保留在数据库中，非结构化内容则可以按成本选择即时理解或先生成可检索摘要。向量检索仍可作为这个循环中的一个工具，在缺乏明确词汇或需要语义联想时补充候选；LLM 驱动查询本身并不排斥它。

### 向量数据库适合解决大规模候选发现

当企业拥有大量非结构化资料，而用户又很难提供型号、路径、项目等定位条件时，逐份理解资料的成本就会变得很高。例如，需要从多年积累的素材中快速找出符合某种场景描述的图片。此时，预先生成语义表示并建立向量索引，具有明确价值。

向量检索可以先筛选候选，Agent 再对命中的原始资料进行定向阅读，并结合其他来源形成答案。精确型号、错误码和业务字段仍可使用全文检索或结构化查询；语义与关键词检索可以组合使用。Anthropic 的 [Contextual Retrieval](https://www.anthropic.com/engineering/contextual-retrieval) 也讨论了精确匹配、向量检索和重排序的组合，以及切分资料时丢失上下文的问题。

大规模非结构化数据是向量索引的重要适用场景。高查询频率、严格响应时间和较高的重复读取成本，也可能让较小的知识库值得预先生成摘要或建立索引。因此，企业可以把“LLM 驱动查询 + 按需理解”作为方案起点，按数据特点增加全文索引或向量索引，并通过实际问题验证候选发现、延迟和成本是否改善。

## 第二种范式：让通用 Agent 在合适的时机意识到相关知识

通用 Agent 可能同时处理沟通、规划和任务执行。用户只给它一个目标，并不会列出所有需要查询的资料。此时，知识库使用的难点是：**Agent 不知道自己不知道什么。**

例如，用户要求准备某产品的演示方案。知识库里恰好有一份最近的通知，说明某个演示功能暂不可用。如果 Agent 没有意识到这份通知可能存在，它可能根本不会发起查询。即使查询工具和向量索引都很好，也没有机会返回这条信息。

OpenDAN 的 Hints 设计尝试补上这一环：根据当前会话的话题、对象和任务背景，先让一条简短线索浮现出来，例如“该产品最近有一份功能状态通知，可能影响演示，来源在这里”。Agent 再判断是否读取详情，并核对它是否适用于当前任务。

这一范式可以概括为：

> 当前任务与话题 → 召回相关线索 → 告知某份资料或某个变化的存在 → Agent 主动查询 → 核实后用于任务。

Hints 只需提供存在性、关联理由和来源引用，避免每轮都注入大量资料。对于持续变化的对象，还可以结合订阅，在相关状态更新时提示 Agent。线索本身不能直接充当事实结论，原始资料仍需要被读取和验证。相关思路见 [Agent 浮现 Hints](<../../notepads/Agent元能力/Agent 浮现Hints.md>)。

需要严格执行的业务规则，例如“每次演示前必须检查最新功能状态”，应明确写入工作流程。这类必查项可以确定性触发，不应只依靠可能命中的 Hints。

### 很多企业问答场景暂时不需要这一层

企业面向消费者的产品咨询、FAQ、售后说明和支持问答，即使以 Agent 的形式提供，核心职责通常仍是围绕用户的问题组织回答。产品或问题本身已经限定了知识范围，查询时机也比较明确。

对这类项目，先把第一种范式做好通常就足够了：能够理解问题、查询正确的数据源、阅读相关内容、合并证据，并给出可追溯的答案。多轮追问、调用多个工具，或者同时查询多个知识源，都可以在第一种范式内完成，无需为此引入完整的通用 Agent 浮现机制。

当 Agent 开始承担跨任务、跨会话、长时间持续的工作，需要主动察觉未被用户提及的信息或外部变化时，第二种范式才更值得投入。两者也可以组合：通用 Agent 发现线索后，把明确的查询任务交给查询型 Agent。

## 权限与数据安全：把授权落实到系统边界

企业经常遇到的访问链路是：

> 用户 → Agent → 查询知识库。

如果 Agent 可以读取全部资料，而系统只在提示词中要求它“不要把内部数据告诉普通用户”，就必须按这道限制可能被攻击绕过来设计。用户的提问和被读取的文档都可能影响模型输出。**提示词可以指导行为，但不能承担用户之间的数据隔离。** 授权应由模型之外的程序执行，不能由 LLM 自行判断是否放行。OWASP 对 [Excessive Agency](https://genai.owasp.org/llmrisk/llm062025-excessive-agency/) 的建议也强调按用户身份执行下游操作，并由下游系统校验权限。

这一问题可以采用两种授权方式。它们分别控制“Agent 能读到什么”和“用户能拿到什么”，适用于前文的两种知识使用范式。

### 方式一：Agent 按当前用户的权限查询

Agent 代表谁工作，就以谁的有效权限读取资料。系统把可信的登录身份传递给查询服务，由知识库或查询网关在返回内容前完成授权过滤。用户所属的部门、项目组或角色决定其可访问范围；Agent 自身的工具权限还可以进一步收窄这一范围。

> 用户身份与分组 → 查询服务鉴权 → 返回该用户可读的资料 → Agent 理解并回答。

这要求整个知识库能够按用户或用户组做权限分离。可以采用独立知识库、逻辑分区、文档 ACL 或查询时的权限过滤，不一定要为每组用户部署一套物理数据库。权限应覆盖全文检索、向量召回、原文读取及派生摘要，确保无权内容不会先进入模型上下文，再等待模型自行隐藏。

这种方式的优点是边界直接：Agent 的回答建立在当前用户有权读取的材料之上。它适合已有用户权限体系，或可以统一改造查询入口的企业。BuckyOS 的 [RBAC 权限设计](<../arch/verify-hub/BuckyOS RBAC权限设计.md>) 采用用户权限与应用权限的交集思路，可以作为这一方式的基础。

### 方式二：Agent 读取全部资料，结果按数据来源独立鉴权

另一类企业已经接入多套知识库和数据库，逐一改造它们的终端用户鉴权成本较高。此时可以把拥有完整读取权限的 Agent 放在受控后台，让它查询和处理资料，再把用户授权统一放到结果交付层。

每项结果使用带来源的 Hint 结构表达，一次查询可以返回多条：

> 数据来源 → 数据内容（保存在需要独立鉴权的 URL 中）。

这里的 Hint 是结果引用结构，用来连接来源与受控内容；采用这种结构不要求启用前文的通用 Agent 浮现机制。

后台将原文摘录、分析和答案写入受控结果存储，用户侧先收到结果服务生成的链接。用户打开链接时，结果服务验证**当前访问者**的身份，查询“用户／用户组 → 数据源”的权限配置，通过后才返回内容。转发链接不会自动授予接收者权限。

> 用户提出问题 → 后台 Agent 查询 → 保存内容及来源关系 → 返回 Hint 链接 → 用户打开链接 → 结果服务鉴权 → 展示允许访问的内容。

例如，一次查询分别得到产品手册中的公开规格和内部项目库中的测试结论，可以保存成两个独立结果，各自关联自己的数据源。用户能否打开其中任何一项，由对应数据源的权限决定。示意结构如下，来源名称也须是允许向该用户展示的信息：

| Hint | 数据来源 | 数据内容 |
|---|---|---|
| 1 | 产品资料库 | 需要鉴权的结果 URL A |
| 2 | 项目资料库 | 需要鉴权的结果 URL B |

**这一方式成立的前提是，高权限 Agent 的可见输出受到程序约束。** 未鉴权的 Hint、聊天回复和链接预览不能包含受限正文、摘要或由受限内容推导出的结论。如果来源名称或资料的存在性本身也保密，就应隐藏该条 Hint，或仅展示不泄露这些信息的通用入口。

因此，高权限 Agent 应只把内容写入受控结果存储；面向用户的入口由结果服务生成，只能返回通过可见性检查的字段和不透明结果标识。原文不能通过聊天流、共享记忆、用户可见日志或其他外发工具绕过这一出口。仅要求模型“只返回链接”，仍然属于提示词限制，不能构成这种架构的安全边界。

来源关系也必须由查询连接器和结果服务记录并传播，不能由模型任意声明或删除。一份答案合并了多个来源，默认需要用户同时拥有这些来源的读取权限；若要展示权限较少的版本，应只使用该用户可读的材料重新生成。无法可靠区分来源影响时，应保守继承全部相关来源的限制。

结果 URL 每次被打开时都要按当前身份和权限判断，包括预览、下载及缓存访问。URL 是受控入口，不能变成“拿到地址就能读取”的公开文件或免鉴权凭证。权限撤销后，后续访问也应被拒绝。这与 OWASP [Authorization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html) 中逐次请求校验权限的原则一致。

在数据源内部访问级别一致的前提下，企业主要维护“用户／用户组 → 数据源”的授权关系，并新增统一的结果鉴权层；现有知识库和数据库可以继续使用原来的后台访问方式，无需逐个改造其终端用户鉴权。如果同一数据源内还存在文档或记录级权限，就需要把来源粒度细化到对应权限单元，或继续执行原有细粒度授权，不能直接按整个数据库放行。

第一种方式更适合让 Agent 直接向用户组织答案；第二种方式更适合统一接入现有数据系统，并通过受控结果页交付内容。两者可以组合使用，但每条数据路径都需要明确授权在哪里执行。
