# Agent 主动给用户发"消息"的方法总结

> 适用范围：OpenDAN Agent / BuckyOS 的会话、任务执行、系统通知与外部通信设计。
>
> 本文中的“消息”带引号，是因为用户看到的“Agent 给我发了一条消息”，在系统内部可能对应几种完全不同的机制。本文整理这些机制的语义、边界和组合方式；接口名称、状态名与流程示例用于表达设计意图，不构成最终协议规格。

## 一、核心判断：不要把所有“发消息”都做成 Assistant Message

用户看到的表现可以很相似：Agent 问了一个问题、弹出了一个授权请求、发来了一个提醒，或者向别人发出求助。但这些行为的触发者、接收者、等待方式和结果归属并不相同。

本设计首先区分以下机制：

| 机制 | 解决的问题 | 输出与返回方式 | 核心边界 |
| --- | --- | --- | --- |
| Session Inbox / Outbox | 用户与 Agent 的持续对话 | 消费输入，生成 Assistant Message | 正常会话与 Turn 语义 |
| System Notify | 系统告知、授权、提醒以及需要用户处理的事件 | 独立通知通道；必要时等待通知处理结果 | 不进入 Session Outbox |
| `ask_user` | Agent 需要获得结构化的用户补充信息 | Tool Call 返回用户答案 | 可复用 System Notify，但不等于安全审批 |
| `post_message` | 主动联系外部的人或 Agent | 投递后返回收据，回复另行关联和查询 | 不等待外部收件人回复后才返回 |
| Input Task / Final Report | 内部 Work Session 的任务协作 | 创建时输入任务，执行后输出报告 | 不靠持续收发聊天消息推进任务 |

智能提醒不是必须另建的一套消息协议。它可以由 Goal Session 管理长期意图，由定时唤醒的 Work Session 判断是否需要提醒，最终通过 System Notify 触达用户。

**整体方向是：会话消息、系统通知、外部投递保持语义分离；需要关联时，通过执行来源、任务状态、消息收据和环境上下文重新建立联系，而不是把所有东西塞进同一个 Inbox / Outbox。**

## 二、最简单的基线模型：Session Inbox → Agent → Session Outbox

### 2.1 Agent 只负责处理输入并产生输出

理想情况下，Agent 的工作非常简单：从输入队列取消息，完成推理和执行，再把 Assistant Message 放入输出队列。

```text
外部消息系统
    → Session Inbox
    → Agent 在该 Session 的上下文中处理
    → Session Outbox
    → 外部消息系统向用户展示回复
```

Agent 不需要知道谁向 Inbox 投递，也不需要负责消费 Outbox。输入从哪里来、回复最终在哪个客户端展示，由外围消息系统处理。

这里的 Inbox / Outbox 首先是 **Session 级** 概念，而不是整个 Agent 只有一组队列。一个 Agent 可以拥有多个连续上下文，用户可以在不同会话中讨论不同话题。

### 2.2 Agent Session 与外部 Conversation 不是同一个对象

在自有 Message Hub 中，用户可以手工创建不同的会话，并分别绑定 Agent 的 UI Session。Email 等外部通信渠道也可以承载这样的交互。

典型绑定关系是：用户在某个 Conversation 发消息，外围程序将消息送入对应 Session 的 Inbox；Agent 产生回复后，外围程序消费该 Session 的 Outbox，再把回复放回原 Conversation。

需要区分三个对象：

- **Agent**：具有身份、共享状态和执行能力的主体。
- **Agent Session**：组织连续上下文与执行过程的单元。
- **外部 Conversation**：用户实际看到、参与的消息会话。

一个普通 UI Conversation 与一个 UI Session 的绑定，是本次讨论的常规交互基线，不代表三者可以在实现中混成同一个对象。

### 2.3 Work Session 是这个基线的有意收缩

通用 Session 架构在抽象上可以容纳 Inbox / Outbox，但 Work Session 默认**不实际创建**这两个消息队列。

这是资源与职责两方面的选择：分布式消息队列有成本；有界任务也不应天然成为一个持续聊天入口。Work Session 主要通过 Input Task 和 Final Report 工作，后文将展开这一边界。

因此，“每个 Session 都可以理解为一个上下文”，并不意味着“每个 Session 都必须分配两条持续通信队列”。

## 三、Turn、处理中补充输入与用户看到的消息顺序

### 3.1 一个 Turn 不必只对应一条用户消息

在本文的会话模型中，一个 Turn 通常以最终的 Assistant Message 结束。但在这之前，Agent 可能合并消费多条 User Message。

例如，用户连续发出 A、B、C 三条补充信息，系统可以把它们作为同一轮输入，最终生成一条回复。工具调用和中间处理并不因此变成三个独立 Turn。

真正需要明确的是：**每条消息在哪个处理机会进入上下文，以及最终回复覆盖了哪些输入。**

### 3.2 处理中是否读取新消息，是产品与架构共同决定的

本次讨论提到的当前实现是：Agent 在每一次推理前，都有机会从 Inbox 获取新消息。因此，用户在处理过程中补充的信息，有可能被当前 Turn 吸收。

也可以采用更简单的实现：当前 Turn 埋头处理既有输入，后续消息全部等本轮结束后再处理。

从产品角度，可以形成两类体验，其中第二类又包含两种明确的控制方式：

| 交互选择 | 新消息如何处理 | 用户预期 |
| --- | --- | --- |
| 自由消息 | 用户随时发送，系统按当前执行状态决定是否纳入本轮 | 能自然聊天，但无法预先确定处理边界 |
| 明确排队 | 等当前 Assistant Message 返回后，作为后续输入处理 | 明确知道这条消息没有进入当前处理 |
| 明确要求本轮吸收 | 在当前处理过程的下一次可用推理入口纳入补充信息 | 明确要求尽快影响尚未完成的处理 |

“下一次推理前读取”不是任意时刻中断模型、改写已经生成的结果。尤其当最后一次推理已经完成，后续新消息就可能来不及参与当前结果。产品必须使这种情况可理解，不能让用户误以为它已经被考虑。

### 3.3 使用“处理中”占位消息时，排列要反映处理关系

如果消息流中先出现一条“处理中”的 Assistant 占位消息，结束后再将其替换为最终回复，就需要处理补充消息与占位消息的位置关系。

当 B 被当前 Turn 纳入时，应表达为：

```text
用户消息 A
用户补充 B
Assistant 占位消息：处理中
    ↓ 完成后替换
Assistant 回复：基于 A、B 的结果
```

当 B 只是排队等待下一轮时，应表达为：

```text
用户消息 A
Assistant 占位消息：处理中
    ↓ 完成后替换
Assistant 回复：本轮结果，未纳入 B
用户补充 B：等待后续处理
```

这意味着展示顺序不能只机械采用客户端发送时间，而应尽量表达真实的输入归属和结果关系。

### 3.4 也可以把“处理中”放在 Session 状态区

另一种方式是不创建占位消息，而是在会话侧边或状态区显示 Idle / Processing。这样可以避免占位消息引起的动态插入与排序问题。

但它只是减少了展示层的复杂度，并没有消除输入归属问题。用户仍然可能需要通过消息详情或处理状态，了解某条补充信息是否进入了当前处理。

**无论选择哪种 UI，目标都是让用户知道：当前结果基于哪些输入，哪些消息还没有被处理。**

## 四、两种容易混淆的询问：LLM 澄清与机械授权

### 4.1 LLM 主动澄清，可以直接结束当前 Turn

例如，用户说“把项目的字体改大”，但当前上下文同时涉及项目 A 和项目 B。LLM 判断操作重要、目标不明确，于是问：“要修改项目 A，还是项目 B？”

最简单的做法是将问题作为标准 Assistant Message 写入 Outbox，并结束本轮处理。用户下一次回复“项目 A”，作为普通输入进入 Inbox，由新的 Turn 根据上下文判断并继续。

用户也可能下一句完全换了话题。是否在回答前一个问题、应继续哪件事，仍由 LLM 结合上下文处理，不要求系统强制锁住输入。

这种做法完全保持原有 Inbox / Outbox 语义：**事情暂时无法推进，就把需要澄清的内容作为本轮正常回复。任务未完成，不等于 Turn 必须保持运行。**

Email 很适合用来检验这个边界：Agent 可以发一封询问邮件，但不能锁住用户邮箱，要求下一封邮件只能选择 A 或 B。自由消息模型不需要这样的 UI 控制能力。

### 4.2 阻塞式询问是另一种执行语义

在可控 UI 中，也可以要求用户先完成一个结构化问题，再继续当前执行。例如显示选项、限制当前输入，直到用户作出明确选择。

这需要 UI 和执行层配合，不能与“已经发出 Assistant Message、Turn 正常结束”的方式混为一谈。后文的 `ask_user` 提供了这一类工具化交互的统一入口。

### 4.3 机械授权不是 LLM 主动澄清

另一种“询问”来自工具执行层：Agent 调用了某个函数，独立检测层发现该操作需要用户授权，于是暂停该调用，等待批准、拒绝或超时。

```text
Agent 发起 Tool Call
    → 执行层检查
    → 需要用户授权
    → 发出 System Notify
    → 用户决策，或发生超时
    → Tool Call 返回对应结果
    → Agent 根据 Tool Result 继续推理
```

这时不需要由 LLM 再组织一条 Assistant Message。Agent 可能只知道工具尚未返回；友好的实现可以显示 `wait_user_approve` 一类状态，但通知如何触达用户不应成为执行任务的 LLM 的职责。

### 4.4 为什么机械授权不宜全部转为普通对话

首先是成本。工具先返回“需要确认”，再让模型推理并提出问题，随后再经另一轮恢复处理，会增加本可由执行层完成的交互开销。

其次是安全边界。是否必须授权、是否已经满足授权条件，应由独立执行层约束，而不能只依赖正在执行任务的 LLM 自行判断，以免授权要求受到提示词或上下文操纵。

需要准确理解这里的区别：**安全性来自执行层强制执行授权规则，而不是来自“用了通知弹窗，没有用聊天文字”这个表面形式。** 即使某种界面使用自然语言，底层授权约束仍然必须成立。

## 五、System Notify：独立系统通道，底层复用 Task

### 5.1 System Notify 明确不进入 Session Outbox

Session Outbox 承载正常会话输出。系统通知不是该 Session 的 Assistant Message，即使它由这个 Session 的工具调用触发，也不应混入同一条输出通道。

同时，Agent 在系统里也是一个 App。System Notify 应是系统级能力，而不是只为 Agent 临时增加的特殊通道。其他应用也可以使用它。

通知至少需要保留足够的来源语义，例如来自哪个 App / Agent、哪个 Session、哪一次具体 Tool Call，以及通知涉及的操作。这里强调的是关联能力，尚未确定最终字段结构。

### 5.2 分为无需回复与需要回复两类

**无需回复的通知**用于告知、警告和提醒。用户不必作出决定，发送方也不需要等待一个答案。

**需要回复的通知**用于授权、确认或信息收集。用户操作会影响等待中的调用，必须能够返回处理结果，并考虑超时。

通知发出、到达某个渠道、被用户看到、用户完成处理，是不同的事情。特别是“成功发出”不能被直接解释为“已经批准”。

### 5.3 发送与等待应支持异步、离线和恢复

对 Agent Core，概念上的调用方式可以是：

```text
notify_ref = send_system_notify(...)

# 仅对需要回复的通知：
result = wait_system_notify(notify_ref)
```

这里的 `wait` 是逻辑等待，不要求某个进程、线程或网络连接始终存活。

如果发送通知的进程崩溃，通知及其结果不能因此丢失。恢复时，只要 Checkpoint 保留了足够的信息，就应该能够重新关联原通知：尚未处理则继续等待，已处理则取得结果，已超时则得到对应结果。

恢复的目标是继续同一件事，不是因为重启而向用户发起一份无关的新审批。具体如何保证重复调用不重复创建通知，需要在实现阶段明确。

### 5.4 不重新建设一套分布式等待系统

本设计选择复用底层通用 Task：通知需要等待时，本质上是等待某个持久化 Task 的状态和结果改变。

但面向调用者，仍然应该包装为 System Notify API，而不是只暴露通用 Task API。

```text
System Notify API
    ├─ 描述通知内容、来源、目标用户与触达要求
    ├─ 根据配置选择通知方式
    ├─ 引导用户查看上下文并操作
    └─ 复用通用 Task 保存状态、结果及等待关系
```

Task 解决“如何持久化等待一个结果”；System Notify 解决“为什么找用户、通过哪里找到用户、让用户做什么”。二者不能互相替代。

## 六、通知如何触达：统一页面、通知中心与强度匹配

### 6.1 每个 Notify 都有统一的 URL 处理入口

BuckyOS 的设计可以利用系统组件可通过 URL 访问这一基础条件，为每个 Notify 提供独立页面。用户从不同渠道收到同一通知后，可以进入同一处理入口。

页面应提供足够上下文，让用户知道谁发起了请求、正在做什么、具体要决定什么。尤其对于没有对话界面的 Work Session，只有一句“是否允许”通常不足以支持判断。

不同渠道不应各自维护一份互不关联的处理状态。用户已经在一个入口完成操作后，再从另一个链接进入，应该看到同一个最终结果。

**准确地说，唯一真相源是 Notify / Task 的持久化状态；统一页面与 API 是访问、修改这一状态的入口，而不是网页自身成为另一份状态。**

### 6.2 默认引导进入统一页面，不默认在消息里放 Yes / No

通知本身应包含基本说明和链接，鼓励用户进入详情页处理。对于内容简单、上下文完整且策略允许的场景，可以优化为原地操作。

这是一种默认交互倾向，不是禁止自有 UI 提供便捷按钮。无论采用哪种表现，最终都应操作同一个 Notify 对象。

### 6.3 来源与触达渠道不必相同

系统应根据通知来源、用户配置以及当前可用渠道选择合适的触达方式。例如：

- 来自 Email 交互的请求，可以通过邮件发送通知链接。
- 来自自有 Web UI 当前执行的授权，可以在相关会话内呈现完整操作界面。
- 来自后台 Work Session 的通知，可以在关联会话显示提示，也可以投递到更容易触达用户的渠道。

通知不是必须沿创建它的会话原路返回。来源信息帮助系统理解上下文，但不是绝对的渠道绑定。

### 6.4 API 还需要表达通知强度

仅有来源和内容不够。普通告知、时间敏感的提醒、等待用户决定的请求，对“多快被注意到、需要多强的提醒”有不同要求。

因此 System Notify 应增加**通知强度或期望触达等级**这一维度。它与“是否需要回复”是两个维度：一条很需要及时被看到的提醒，可以不要求用户回答；一个需要回答的问题，也不一定都必须以最强方式打断用户。

系统结合通知要求与实际渠道能力选择触达方式，例如 Web UI、BuckyOS App、Telegram、Email，或已配置的短信网关。

这里不预设固定的“短信一定高于 IM、IM 一定高于邮件”排序。选择依据应是该用户当前可用的渠道、通知设置及实际触达条件。强度等级、回退和升级规则尚待定义。

### 6.5 阻塞的是哪个执行主体，决定如何展示

如果当前 UI Session 的工具调用正在等待审批，且原执行确实不能继续，自有界面可以使用毛玻璃遮罩加模态对话框，把上下文和操作集中呈现。

但如果被阻塞的是后台 Work Session，就不应因此锁住创建它的主 UI Session。主会话还可能在处理其他任务。更合适的方式是气泡、待处理通知入口或局部提示。

**Work Session 被阻塞，不等于主 UI Session 被阻塞；强度高，也不自动等于必须锁住整个聊天界面。**

### 6.6 每个用户都需要统一通知中心

通知中心提供完整的通知清单和处理入口，使用户不必依赖某一次弹窗、某一封邮件或某个聊天窗口才能找到待办事项。

应能按来源、类型及处理状态筛选，查看当前状态，并进入相应 Notify 页面。不同渠道负责触达，通知中心负责统一查看与追踪；不能把“用户没在某个渠道点开”当成通知不存在。

通知中心并不能保证人一定注意到所有通知，但可以避免因入口分散而失去统一可查的记录。

## 七、无 UI 的 Work Session 与 `ask_user` 兜底

### 7.1 Work Session 的默认契约：Input Task → Final Report

在本设计中，Work Session 的输入应在创建时尽量准备充分。调用者知道 Session ID，提交任务，然后取得最终报告；必要时也可以收到少量关键报告。

```text
UI Session 分析用户意图
    → 创建 Work Session，提供 Input Task
    → Work Session 在独立上下文中执行
    → 输出 Final Report
    → UI Session 根据报告继续与用户交互
```

UI Session 不需要继承全部执行过程，其上下文主要保留创建意图、结果以及必要的关键报告。这既保持上下文干净，也减少通信资源开销。

父 Session 消费报告后，可以决定是否向用户回复，或通过明确的控制接口调整任务状态。报告机制并不等于允许所有 Session 互相往 Inbox 塞任意聊天消息。

### 7.2 默认偏好：关键输入不足时快速失败

如果 Work Session 执行中发现“项目到底是 A 还是 B”这样的关键前提尚未明确，优先判断为创建准备不足。

推荐处理方式是：收束当前 Work，输出失败报告，说明缺少什么信息；由上层 UI Session 与用户澄清，再决定是否创建新的 Work Session。

这不是断言所有中途问题都能在创建前预测，而是有意保持职责清晰：**Work Session 负责执行有界任务，不应轻易演化为长时间等待用户补充的对话会话。**

### 7.3 通用框架仍需要为高成本任务保留例外

有些重型任务已经消耗大量 Token、完成了大量工作，最后才遇到一个补充问题。强制全部放弃会让使用者难以接受，而且 LLM 何时需要反问用户也不能总被预判。

折中方式不是给所有 Work Session 增加持续 Inbox / Outbox，而是提供一个标准工具：`ask_user`。

它为必要的信息补充提供兜底，但不改变 Work Session 默认轻量、任务有界和倾向快速失败的定位。

### 7.4 `ask_user` 返回的是答案，不是普通会话回复

对 LLM，`ask_user` 是一个普通 Agent Tool：填写问题和选项，等待工具返回用户答案，再继续处理。

概念示例：

```json
{
  "question": "请选择要修改字体的项目",
  "options": [
    {"value": "project_a", "label": "项目 A"},
    {"value": "project_b", "label": "项目 B"}
  ],
  "allow_free_text": true
}
```

这里仅展示工具参数的结构化意图，不确定最终 Schema。自由文本、选项数组等参数使问题表达更稳定，不需要每次由 LLM 临时拼装交互格式。

### 7.5 相同 Tool，按交互环境选择实现

在有原地结构化交互能力的 UI Session 中，`ask_user` 可以直接使用当前界面，不必经过 System Notify。即使已有普通聊天能力，开发者也可能因为结构化体验更好而选择它。

在没有直接 UI 的 Work Session 中，则通过 System Notify 找到用户，底层等待结果，再把用户答案作为 `ask_user` 的 Tool Result 返回。

```text
ask_user
    ├─ 当前界面支持原地交互
    │      → 展示结构化问题 → 用户回答 → Tool Result
    └─ 无直接 UI，或当前渠道不足以承载所需交互
           → System Notify → 用户处理 → Tool Result
```

“UI Session 可以原地交互”不能被理解为任意外部渠道都有可锁定、可嵌入表单的界面。Email 等渠道需要按实际交互能力处理。

### 7.6 `ask_user` 与机械审批共享机制，不共享安全语义

`ask_user` 是 LLM 主动要求补充信息；机械审批是独立执行层强制要求授权。两者都可能通过 System Notify 等待，但不能把用户对一个普通问题的回答自动视为对危险操作的授权。

同样，`ask_user` 是尚未返回的工具调用，不是已经结束 Turn 的 Assistant Message。这与“正常回复一个澄清问题，下轮再继续”是两种不同选择。

## 八、内部 Session 协作与外部 Agent 通信必须分开

### 8.1 内部多角色任务不必包装成多个 Agent

在本文采用的架构视角中，同一本地环境里的多角色分工，可以通过具有不同 System Prompt 的 Work Session 组合完成。Agent 的边界更多涉及身份与共享状态，而不是每换一个提示词就必须新建一个独立 Agent。

因此，内部推荐采用树状协作：父 Session 创建子 Session，子 Session 执行后交回 Report。

```text
父 Session
    ├─ Work Session A → Report A
    ├─ Work Session B → Report B
    └─ 汇总结果，决定下一步
```

可以并行执行多个子任务，但当前体系不提供“所有 Session 持续活跃、彼此任意发聊天消息”的自由通信网络。

### 8.2 不能悄悄把 Session A 的输出伪装成 B 的用户输入

如果 Session B 是与用户的一对一会话，Session A 向它的 Inbox 写入一条消息，就首先遇到身份问题：这是谁说的，凭什么作为用户输入？

技术上把内容标成 `user` 并不等于真实用户提出了请求。内部协作应优先使用任务、报告和明确控制接口，不靠冒充用户来触发另一段上下文。

因此，“Session 之间是否能互发消息”不是单纯的队列写入能力问题，而是身份与执行语义问题。

### 8.3 跨独立 DID 实体时，是另一类通信边界

两个不同用户的 Agent 之间，可以通过外部消息网络异步通信。此时双方已是独立实体，不能假设对方使用同一个内核，也不能仅根据消息文字声称“我是人”或“我是 Agent”就确定对方的实现。

对被动接收方，只要消息通过正常协议与既有接收机制进入 Inbox，就可以按普通输入处理，不需要因为对方可能也是 Agent，就新建一套特殊会话协议。

对主动发送方，问题变成：如何依据 DID、通讯簿、渠道配置和通信偏好，联系外部实体。这与内部创建一个子 Work Session 是两回事。

## 九、`post_message`：投递后返回收据，外部回复另行处理

### 9.1 这是一个浅封装，不是新的 Agent 网络

系统可以提供类似以下语义的工具：

```text
receipt = post_message(recipient, content, ...)
```

Agent 负责描述收件人和消息内容；系统结合通讯簿、DID 关联信息、渠道配置和偏好，选择合适的通信方式。

这个封装的重点是减少重复研究邮件发送、短信网关等细节对上下文的占用，复用公共配置，降低 Token 开销。它不是要求对方使用 OpenDAN，也不是为了重建现有通信网络。

### 9.2 名字倾向 `post`，因为不应等待对方回答

`post_message` 不能被理解成“发送问题，等对方回复之后函数才返回”。外部收件人可能很久不回复，也可能根本不回复，不能将这种不确定性封装进当前工具调用的同步返回。

它可以返回发送或投递相关状态与收据，但不能以取得外部答复为返回条件。

```text
不采用：发消息 → 一直卡在 Tool Call → 对方回复 → Tool 返回

采用：  发消息 → 返回 Receipt
                     ↓
              后续根据 Receipt 检查回复
```

这与 `ask_user` 的差异不是名字，而是等待模型。

### 9.3 收据需要支持后续找到回复

Receipt 不应只是一个“成功”布尔值。它应提供或关联足够信息，让调用方知道通过哪个渠道、哪个账号发出了什么请求，以及后续如何查询与这次发送有关的回复。

具体字段未定，但必须能支撑这样的行为：“我通过这个邮箱发出了求助，现在检查与这次求助相关的回复是否已经到达。”

收据的发送状态也不能自动等同于对方已读，更不等同于对方会回答。

### 9.4 Work Session 可以拉取回复，而不必拥有 Inbox

Work Session 缺少关键数据时，可以主动向外部联系人求助，并记录一项等待依赖。之后在允许的时间范围内，通过收据查询回复，获得信息后继续执行。

它等待的是外部条件，而不是让 `post_message` 一直不返回。回复可以保存在可查询的位置，供 Work Session 拉取，不要求为它创建完整的对话队列。

这一模型仍需有界。长期等待由 Goal Session 处理，不能因为“工具已经返回了”就允许 Work Session 无限期悬挂。

### 9.5 共享邮箱会引入全局回复路由问题

现实中，用户可能只给 Agent 配置了一个邮箱：用户与 Agent 的普通对话走这个邮箱，Work Session 联系外部人员也复用这个邮箱。

外部联系人回信后，若按默认规则全部投递到 Email UI Session 的 Inbox，真正等待回复的 Work Session 就可能拿不到正确关联的信息。

因此需要系统级关联与路由，而不是让每个 Session 各自猜测：

```text
共享渠道收到消息
    → 判断是否关联某次外部求助
        ├─ 是：保存为相关回复，供目标任务查询
        └─ 否：按普通会话路由规则处理
```

本次讨论提出的轻量做法，是在邮件标题中加入关联标识。对方正常回复并保留标识时，系统可以识别其归属，使它不再误入普通 UI Session 的 Inbox。

这带有“君子协定”性质，不能视为无条件可靠的保证。标识被删改、关联不明及多重匹配时如何处理，仍需定义。

**全局路由与 Work Session 拉取是配合关系：前者把回复放在正确的关联位置，后者在合适时机读取结果；并不等于把消息直接推入 Work Session 的 Inbox。**

## 十、Work Session 有界等待，Goal Session 管长期目标

### 10.1 Work Session 的等待必须能结束

Work Session 可以因为审批、`ask_user` 或外部回复暂时等待，但必须有合理超时。超过等待边界后，应收束当前执行并报告仍未满足的条件，而不是无限保持“正在工作”。

机械授权、信息补充和外部回信可以采用不同的等待规则，具体时限尚未确定；共同点是不能把一个明确任务拖成无边界的长期会话。

### 10.2 Goal Session 追求的是持续接近目标

已知要长期推进的事项，适合交给 Goal Session。它不是一次性执行到结束，也不是让进程永远运行，而是反复获得观察与决策的机会。

```text
唤醒
    → 观察当前状态与等待事项
    → 判断现在是否需要行动
        ├─ 小事：当前直接处理
        ├─ 明确任务：创建 Work Session
        └─ 暂无行动条件：不执行
    → 记录本次结果与目标状态
    → 休眠，等待后续唤醒
```

等待邮件也可以成为 Goal Session 的一项观察条件。关键不是持续卡在函数里，而是在后续被拉起时重新判断：对方回复了吗，现在应该继续做什么？

这与 Work Session 的有界等待形成清晰分工：**Work 负责完成一段明确工作，Goal 负责长期观察、决策和渐进推进。**

## 十一、智能提醒：定时触发的是判断，不一定是通知

### 11.1 用户的真实需求是意图，不只是重复规则

例如：

> 工作日下午三点，提醒我站起来活动十五分钟。

这句话背后的意图，是避免工作时久坐，不是要求在每一个日历上的工作日下午三点无条件打扰用户。

如果 Agent 已经知道用户正在休年假、外出度假，那么本次提醒可能没有必要。重要的是根据实际掌握的环境信息判断，而不是只机械执行一个重复规则，也不能凭空假定用户的状态。

### 11.2 本次展开的实现路线：长期管理 + 一次性唤醒

长期的日程管理 Session 可以定期运行，维护用户意图，并为适当时间创建一次性的定时任务；这一长期管理职责可以由 Goal Session 承担。

定时任务不是直接向用户弹提醒，而是启动一个输入明确、目标有界的 Work Session，判断当前是否值得提醒。

```text
日程管理 Goal Session 定期运行
    → 根据意图安排一次性触发
    → 接近目标时间时启动 Work Session
    → Work Session 检查当前条件
        ├─ 不该提醒：结束并记录结果
        └─ 应当提醒：调用 System Notify，再结束
```

例如目标时间是 15:00，可以适当提前唤醒，为模型推理预留时间。提前一分钟只是讨论中的例子，不是固定时限，也不意味着推理完成时间已被保证。

本次口述具体展开的是这一条路线，没有将其他调度实现补写为已定方案。

### 11.3 通知内容由 Agent 判断，触达方式由系统选择

Work Session 判断应该提醒后，调用 System Notify，说明内容、来源与所需强度。

用户可能在 Web UI 的健康管理会话中创建提醒，但到了提醒时刻，系统发现 Telegram 或 BuckyOS App 更适合及时触达，于是选择相应渠道。

这时三个角色可以分离：

```text
Web UI Session：形成提醒意图
Work Session：判断本次是否提醒
Telegram / App：实际向用户呈现通知
```

所以，System Notify 的渠道选择不能只看创建时在哪个界面聊天，还要匹配通知强度和当前触达条件。

## 十二、最难的一步：Agent 必须看到用户实际看到的上下文

### 12.1 通知绕过 Outbox，不意味着它可以对 Agent 不可见

考虑以下过程：用户在 Web UI 创建了健康提醒，后台 Work Session 判断需要执行，System Notify 把提醒投递到 Telegram。用户随后直接回复：

> 我今天在外面度假，不要打扰我。

这条回复会进入 Telegram 对应 UI Session 的 Inbox，但原提醒并不是这个 Session 产生的 Assistant Message。

如果 Agent 只看到新收到的这句话，就可能不知道用户在说哪个提醒，也不知道应该调整哪项安排。即使同一个 Agent 有 Global Memory，也不等于它天然知道系统刚刚在另一个通道展示了什么。

### 12.2 环境观察应补足真实交互上下文

在 UI Session 处理输入、构建每次推理上下文时，应尽可能让 Agent 观察到用户实际所在 Conversation 的相关状态，尤其是与当前输入有关的系统通知。

必要信息可以包括通知的基本内容、来源、关联链接、当前处理状态，以及可获得的回复关联关系。这里不要求把整个界面转成截图，也不要求无差别注入全部通知历史，而是要提供理解本次输入所必需的环境信息。

这些信息进入的是**观察上下文**，不是伪造成新的 User Message，也不是补造一条 Session Outbox 中的 Assistant Message。

通知在界面中已被呈现，也不应无条件等同于用户实际已读；Agent 应依据系统真正掌握的信息作判断。

**架构上分离输出通道，认知上补全用户交互环境，两者并不矛盾。**

### 12.3 标准引导仍然是点击通知链接

System Notify 中应包含基本上下文和统一链接，鼓励用户点击后查看详情并操作。这是关联最明确、状态最清楚的标准路径。

对于被配置为只负责单向触达的短信通道，用户可能只是收到通知，再通过链接处理。对于 Telegram 等可继续聊天的界面，用户也可能完全不点击链接，直接在下面说“好的”“可以”或“今天不要”。

系统不能把“用户不按推荐路径操作”当成异常情况而完全失去理解能力。

### 12.4 UI Session 可以理解回复，并代用户操作同一个 Notify

理想情况下，UI Session 能够看到通知及其链接，明确用户在回答哪个问题，并通过 API 操作对应的 System Notify。

```text
后台执行发出 Notify
    → 系统通过 Telegram 向用户展示通知与链接
    → 用户直接在 Telegram 回复
    → 回复进入 Telegram UI Session Inbox
    → Agent 结合环境信息定位原 Notify、理解意图
    → 调用 System Notify 操作 API
    → 原 Notify / Task 的状态与结果更新
    → 对应等待者取得结果，继续原执行
```

例如，对一个确实需要用户回答、尚处于等待状态的问题，Agent 可以把用户明确的答案提交到原 Notify，将其从概念上的 `wait` 更新为 `finish`，并填写结果。这里仍未确定正式状态枚举。

这样不必把用户回复硬路由到发起通知的 Work Session，也不必为 Work Session 创建 Inbox。当前 UI Session 只是代理操作通知；原执行通过既有 Task / Tool 等待关系取得结果。

### 12.5 保持三个边界，避免“理想代理”反而破坏模型

**第一，通知关联要明确。** 有足够上下文和链接，才有机会知道用户在回应哪个对象；有多个待处理请求时，不能把一句“好的”随意归给某一条。

**第二，告知、确认和真实完成不能混为一谈。** 一条不要求回复的活动提醒，不需要因为用户回复了“好”就凭空产生一个等待中的审批 Task；用户说“好的”也不等于已经实际活动了十五分钟。是否需要提交结果、提交什么结果，取决于原通知定义和用户意图。

**第三，代理操作必须服从独立授权策略。** 通知链接可以帮助定位对象，不等于自动取得处理权限。哪些信息补充可以由 Agent 代理提交，哪些敏感审批必须由用户通过可信入口明确完成，需要执行层约束，不能让 Agent 借自然语言解释自行批准自己的危险调用。

因此，自然语言代理路径的定位是：在明确上下文和允许的权限内，为用户省去不必要的点击，而不是取消系统的授权边界。

### 12.6 全局记忆不替代局部观察，局部观察也不直接决定长期修改

当用户说“今天在度假，不要打扰我”，当前 UI Session 首先需要理解这句话与通知的关系。之后是否只跳过本次、暂停当天提醒，或修改长期目标，仍需根据明确意图处理。

Global Memory 可以帮助跨 Session 保持认知，但不能因为存在全局记忆，就省略这次通知的现场上下文；也不能把一个临时反馈自动扩大为长期规则变更。

这一部分归结为整个讨论中最重要的实践判断：

> **Agent 能否作出正确决策，首先取决于它能否观察到正确的东西。模型知道得再多，如果不知道用户刚刚看到了什么，也可能误解一句非常简单的回复。**

## 十三、落地边界与待明确事项

### 13.1 已明确的设计取舍

正常对话采用 Session Inbox / Outbox；LLM 的普通澄清可以作为 Assistant Message 结束 Turn。System Notify 与会话输出分离，底层复用 Task，支持异步等待与恢复，并通过统一 URL、API 和通知中心收敛到同一个状态源。

UI Session 面向持续交互；Work Session 默认不创建 Inbox / Outbox，以 Input Task / Final Report 为主，优先快速失败，必要时通过有界的 `ask_user` 兜底。长期事项由 Goal Session 周期性观察和推进，而不是把 Work Session 无限挂起。

内部任务协作采用树状 Session 组织，不提供任意 Session 互相聊天的团队网络。跨独立实体则使用外部通信网络，`post_message` 返回收据，不等待对方答复；回复通过关联路由与查询接回任务。

系统根据来源、用户配置、通知强度和实际可达渠道选择触达方式。通知可能出现在另一个 UI Session 的界面中，因此该 Session 的观察上下文必须能够感知相关通知，并在权限允许时代理用户操作原通知对象。

### 13.2 仍需在接口与实现阶段确定

以下问题已经显露，但本次讨论尚未确定具体协议或默认值：

| 待定项 | 需要明确的内容 |
| --- | --- |
| Notify 与 Task 的关系 | 标识如何关联、如何查询结果；不预设一对一映射 |
| 可恢复等待 | Checkpoint 保存哪些信息；重启后如何关联原通知而不重复发起 |
| 状态与时限 | 等待、完成、拒绝、超时等如何表达；迟到回复如何处理 |
| 多入口一致性 | 重复提交、同时操作、已经结束后的操作如何处理 |
| 通知策略 | 强度如何分级；渠道如何匹配、回退及是否升级触达 |
| `ask_user` 约束 | 哪些 Work Session 允许使用；等待上限、问题 Schema 与失败策略 |
| 自然语言代理 | 哪类 Notify 可代用户操作；哪些审批必须走独立确认路径 |
| Reply Receipt 与路由 | 跨渠道关联字段、关联标识失效、重复或无法匹配的回复如何处置 |
| 环境观察接口 | UI Session 如何获得相关通知及交互状态，而不污染会话消息流 |

这些事项不应被实现中的临时选择悄悄固定为协议承诺，也不应为了解决一个局部问题而模糊已经明确的几条通道边界。

## 结语

Agent 主动给用户发“消息”，难点不只是如何把一段文字送出去，而是：这段信息属于什么语义、由谁触发、应触达谁、是否需要等待、结果归哪次执行，以及用户反馈时 Agent 能否看到正确上下文。

本设计选择保留几种足够简单、职责明确的机制：**用 Inbox / Outbox 处理会话，用 System Notify 处理系统触达与交互，用 `ask_user` 提供受控的信息补充，用 `post_message` 处理跨实体异步投递，用 Input Task / Final Report 组织内部工作，再用 Goal Session 管理长期目标。**

它们可以共同服务于同一段用户体验，但不应因此丢失各自的身份、生命周期、等待和安全语义。
