# Agent Session SDK 化核心需求

**项目：OpenDAN**  
**版本：1.0｜日期：2026-09-27**  
**目标读者：系统架构负责人、Agent Runtime / SDK 开发者、应用集成开发者**  
**关联文档：[《Agent Memory 认知管理需求》](<Agent Memroy 认知管理需求.md>)**

## 1. 文档定位

本文将本次讨论整理为 Agent Session SDK 化的需求基线，重点回答：应用怎样在自己的执行环境中，以某个 Agent 的身份完成一次工作，同时获得该 Agent 的跨 Session 连续性。

全文区分三种确定性：

- **明确方向**：讨论中已经提出的目标与边界，构成本版需求的主体。
- **派生约束**：为了使上述目标在多进程、状态共享和任务回滚条件下成立，必须补充的工程约束；不表示已有实现。
- **待决设计**：尚未确定的结构、策略和接口，不在本文中提前固定。

本文不选定具体数据库、编程语言、文件布局或函数签名，也不把需求文档等同于现有能力说明。

## 2. 背景与核心目标

### 2.1 当前耦合

按本次讨论描述，大量路由相关能力已经进入 LM Context，但 Session 的触发、输入分发和执行仍与 Agent 的长期运行服务紧密绑定。

当前基本路径为：一个 Agent 对应一个长期运行的服务进程 / 容器；多个 Session 在其中运行；外部输入触发该服务，由 Runtime dispatch 输入并唤醒对应 Session。Agent 内部还维护类似网关路由表的配置，用于决定输入对应的处理逻辑、提示词和 Session。

这种组织方式适合统一托管，但使应用为了运行一次有明确结束条件的 Agent 任务，也必须依赖该 Agent 的固定长期进程。身份、状态、提示词装配、路由和执行位置因此混在一起。

### 2.2 SDK 化的核心目标

> **保留长期 Agent 服务，同时允许其他进程、其他语言的应用，通过共享的 Agent / Session 状态，创建或恢复一个 Session，并将其推进到明确的结束条件。**

SDK 化不是简单地给现有长期服务增加一个远程调用包装。长期服务应成为 Session 的一种执行宿主，而不是唯一拥有 Session 执行权的进程。

Agent 服务可以继续承担状态管理、默认触发、路由和托管执行；这些职责不应阻止外部 Runner 运行经授权的 Session。

### 2.3 两个主要使用层次

| 层次 | 应用意图 | 本次需求边界 |
|---|---|---|
| 裸模型推理 | 获取一次模型输出 | 可满足简单文本需求，但不承担完整的 Agent 身份、工具执行与跨 Session 连续性。 |
| LM Context | 使用上下文、模型调用及相关路由能力 | 不要求绑定具体 Agent。讨论中的 LLM Context 在本文统一写为 LM Context。 |
| Agent Session | 让某个 Agent 完成一次工作 | 使用 Agent 的身份、工具环境与默认 Memory 机制，并拥有可恢复的执行状态。是本次 SDK 化的重点。 |

选择 Agent Session，不只是选择一段 system prompt；还意味着选择了一个具有持续内部状态的 Agent。

## 3. 核心概念与状态边界

以下是概念边界，不要求一一实现为独立服务或数据库表。

| 概念 | 含义 | 不应混同于 |
|---|---|---|
| Agent | 具有身份与持久内部状态的主体；在本体系中可由 DID 标识 | 某一个常驻进程或某一个容器 |
| Session | 一段可标识、可读取、可恢复的交互或执行过程 | 永久存在的产品、项目或 Workspace |
| Runner / Runtime | 装配上下文、执行推理循环、调用工具并提交状态的执行宿主 | Agent 本身或持久状态的唯一所有者 |
| Session 状态 | 消息流、执行进度、待处理输入、工具结果、生命周期及必要的恢复信息 | 已经形成的全部 Agent Memory |
| Agent Memory | Agent 认为值得跨 Session 保存和使用的内部状态；认知管理见关联文档 | 工作产物的唯一事实来源 |
| 世界状态 | 独立存在的文件、Workspace、版本、业务对象等 | 某个 Session 的聊天历史 |
| Intent | 对用户希望达成什么的候选理解，需要进一步明确对象、范围和工作边界 | 已经可以直接执行的任务说明 |

**Session 可以作为 DID Object 暴露状态。** 内部仍然如何持久化，由实现决定。统一的对象访问协议不意味着所有对象都公开可读。

## 4. Session 的三种主要使用形态

三种形态反映目的和生命周期差异，不必先实现为三套不兼容的执行引擎。

| 形态 | 来源与目标 | 生命周期 | 上下文特征 |
|---|---|---|---|
| Task Session | 应用通过代码创建，或由意图分析后创建，完成特定工作 | 尽量短周期，有明确结束条件 | 启动时尽量准备充分，运行中以稳定目标推进 |
| Self-input Session | Agent 自触发，读取自身状态，再更新自身状态 | 自维护机制可以长期存在；单次处理的边界需能识别 | 例如将跨 Session 感知整理成认知 |
| UI / Feedback Session | 用户通过某个信道持续与 Agent 交流 | 长期存在，不以完成一个任务为终点 | 必须持续感知世界变化，并保持 context window 健康 |

### S-01｜Task Session：充分准备后执行到底

**明确方向。** Task Session 应在创建与初始上下文装配阶段取得完成任务所需的大部分环境信息。它的设计目标是尽量在健康的上下文空间中完成一次有边界的工作：要么高质量成功，要么尽早给出明确失败。

“短周期”是一种任务拆分与上下文设计目标，不是强制规定所有工作必须在固定时长内结束。它也不表示任务完全不读取外部状态，而是减少与目标无关、反复发生的环境探查。

**派生约束。** 目标对象失效、权限撤销、关键前置条件改变等影响执行正确性的变化，仍须被识别；“埋头执行”不能成为使用已失效前提的理由。

### S-02｜UI Session：持续反馈，不承载全部重任务

**明确方向。** 普通用户不应为了维持对话质量而学习如何拆分或删除 Session。用户可以在一个信道中长期与同一个 Agent 交流，系统负责压缩、摘要及上下文管理。

UI Session 的主要职责是及时反馈、发现意图、接收澄清、展示工作状态以及处理接受或放弃结果等决定。重任务应交给边界明确的 Task Session，而不是不断堆进 UI Session。

## 5. SDK 的执行与装配能力

### S-03｜执行位置与持久身份解耦

**明确方向。** 同一个 Agent 的不同 Session 可以由不同进程、不同语言的 Runner 执行。经授权的 Runner 应能够访问同一 Agent 的持久状态，不以“运行在原 Agent 容器里”为必要条件。

这不要求所有语言都复刻完整 Agent 逻辑，也不预先选定跨语言方式；共享协议、语言绑定、公共执行内核等均属于后续设计选择。

### S-04｜Session 可独立创建、恢复与推进

**明确方向。** SDK 应支持创建新的 Session，也应支持从已保存的消息流和执行状态恢复一个尚未完成的 Session，并持续推进到结束条件满足。

持久化不能只保存一份聊天文本；须足以分辨当前工作目标、已完成的动作、待处理结果和下一步可执行条件。

**派生约束。** 恢复时，不应因为切换 Runner 而无条件重做已经成功产生副作用的动作。无法确认某个动作是否完成时，应暴露不确定状态，而非默认为可安全重试。

### S-05｜允许应用自行装配 Session

**明确方向。** 应用可以提供本次任务专用的提示词、初始输入和上下文，不必先把这些材料安装进 Agent 的常驻容器。

Session 的初始装配至少需要表达：使用哪个 Agent、做什么、处理哪个对象或 Workspace、已有上下文在哪里，以及什么情况算完成。不同应用可以在 system prompt 和 input rendering 上保留差异。

应用提供的任务材料与 Agent 自身配置如何合成，需要形成稳定的装配约定，但本版不规定模板语法。

### S-06｜装配差异与通用循环分离

**明确方向。** 完成初始 system prompt / context 装配后，大部分 Session 可以共享相近的执行循环：读取上下文、推理、调用工具、观察结果、记录状态并判断是否结束。

SDK 应暴露必要的装配和输入渲染扩展点，而不是要求每个应用复制整套循环。通用循环仍需识别所用模型、工具能力和结束条件，不能把“后续逻辑相近”理解为完全没有运行差异。

### S-07｜执行环境必须明确

**明确方向。** 讨论中的扩展执行主要通过 CLI 命令完成，包括 Agent 的跨 Session 操作。因此，一个 Session 能在哪个 Runtime 运行，取决于那里能否提供所需命令及其语义。

**派生约束。** SDK 在运行前应能识别所需工具是否可用、工作目录 / Workspace 是否正确、状态访问是否授权。不能仅因为能读到 Session 文件，就认为任意宿主均可无差别执行。

具体如何描述 CLI 能力、连接远程能力或发现依赖，属于待决设计。

### S-08｜身份和权限不由提示词授予

**派生约束。** “以 Agent 身份执行”应由可验证的授权与资源访问机制成立，而不是由 system prompt 中的一句身份声明成立。

应用提供自定义提示词，不等于获得该 Agent 的全部权限。Runner 的权限、工具可用范围及状态读取范围应受到调用授权和 Agent 自身策略的约束。敏感凭据不应因为 Session 可共享或可恢复而被当作普通消息历史传播。

## 6. 从 UI 意图到 Task Session

### S-09｜增加独立的意图分析阶段

**明确方向。** UI Session 发现潜在工作意图后，不应总是在一次浅层判断中直接创建任务。系统应允许基于当前上下文派生一个独立的意图分析过程，用于探索目标对象、补充信息并界定工作范围。

这里的 fork 指逻辑上的上下文分支，不要求操作系统级进程 fork；意图分析也不必先被定义成第四种持久 Session。

```text
用户输入
   ↓
UI / Feedback Session：识别候选意图、及时反馈
   ↓
独立意图分析：继承相关上下文，探索对象与边界
   ├─ 信息不足 → 请求用户补充，再继续分析
   ├─ 对应尚未完成且允许接收补充的任务 → 路由必要信息
   └─ 信息足够、工作边界明确 → 创建新的 Task Session
```

“不污染 UI Session”是指不把全部探索过程和中间试探塞回用户对话；必要的澄清问题、分析结论和任务状态仍应反馈给 UI。

### S-10｜任务开始前确定正确的工作对象

**明确方向。** 意图分析应处理用户表达中的省略和指代，而不假定最近提到的名称只有一个对象。

以贪吃蛇为例：历史上可能存在多个实验 Workspace，用户最终选择其中一个继续发展。“改一下刚刚那个效果”应定位到用户实际采用的产物，而不是任意同名对象，也不只是按创建时间选择最后一个 Session。

系统不能要求用户通过删除旧 Session 来消除歧义。必要时应读取 Workspace、任务结果或相关 Session 状态；仍不能确定时，再向用户澄清。

### S-11｜一次任务对应一次可结束的工作

**明确方向。** 不应把“一个贪吃蛇产品”定义成永久 Session；应把“实现第一版”“修改某种效果”“修复某个问题”分别作为有结束条件的工作。

这类似一次意图尽量形成一项可提交的改动，而不是整个项目始终使用同一条无限延长的执行线程。该类比约束的是工作边界，不要求所有产物都采用 Git 或 PR。

### S-12｜通过产物继承，而非依赖旧 Session 继续运行

**明确方向。** 已完成任务之后的新改进，优先创建新 Task Session，通过同一 Workspace、产物文件夹或世界对象的有效版本继承成果。

旧 Session 可以作为解释历史决策的材料被读取，但不应成为“只有重开它才能修改该产物”的强制前提。

### S-13｜默认稳定执行，避免中途重写目标

**明确方向。** 当意图已明确且准备充分，Task Session 应以稳定目标推进到结束。用户越来越倾向于评估完整结果，再决定接受、放弃或回滚，而不是持续在执行中改写计划。

这是一种默认工作方式，不是禁止停止任务。系统仍应提供可理解的停止 / 放弃入口。

**待决设计。** 对尚未完成任务的补充如何区分“补齐缺失信息”和“修改工作目标”，何时允许投递给原任务、何时必须创建新任务，需要进一步定义。对已完成任务追加新的实质工作，不应作为默认路径。

### S-14｜用户主要管理尚未完成的工作

**明确方向。** UI 应突出进行中、等待补充、失败待处理等未完成工作，并能查看结果；不要求用户理解或管理所有历史 Task Session。

放弃、停止和结果无效化等决定可以在 UI Session 中作出。UI 必须据此知道哪些成果不再有效，后续分析不能继续把已放弃结果当成当前工作基础。是否继续尝试，由新的用户意图决定，不自动反复重做。

## 7. 持续上下文感知与事件订阅

### S-15｜主动订阅与半订阅分离

**明确方向。** Session 应支持两种具有不同唤醒语义的订阅。

| 方式 | 事件发生时 | 何时进入推理上下文 | 主要用途 |
|---|---|---|---|
| 主动订阅 | 为 Session 增加 input，触发或排队一次处理 | 本次事件对应的处理机会 | 需要主动反应的事件 |
| 半订阅 | 记录待感知变化，不单独唤醒 Session | 下次已有 input 或执行循环中的观察机会 | 低打扰的世界状态感知 |

半订阅不是轮询的另一种名字，也不是一种延迟后必然启动模型的定时任务。它的核心是：变化可先到达，但不因此制造一次独立推理。

### S-16｜在每次合适的观察机会检查变化

**明确方向。** 半订阅检查不应只发生在用户 input 到来时。Session 运行中的 action result / tool result / observation 等准备继续推理的位置，也应允许检查并注入新的 context change。

```text
外部事件 → 记录待感知变化（半订阅不唤醒）
                         ↓
已有 input 或执行中的观察机会
                         ↓
检查变化 → 去重 / 合并 / 筛选 → 写入 context change
                         ↓
继续推理；需要详情时读取相关 DID Object
```

注入应发生在可定义的上下文装配边界，不需要在一次模型生成中途改写输入，也不要求每个内部函数调用都触发查询。

### S-17｜先提供变化摘要，再按需读取详情

**明确方向。** UI Session 可以默认半订阅相关活动任务。例如：某任务已完成、失败或被放弃，并附一句话 report。

该摘要应帮助模型决定是否需要进一步查询，而不是复制完整任务日志。需要详情时，通过 Session 的 DID Object 读取状态、结果引用及相关报告。

目标是减少反馈循环中的反复主动查询，同时让模型意识到原本不知道应该查询的变化。

### S-18｜同一变化不重复占用上下文

**明确方向。** 一个变化通常只需通知一次。订阅接收和 context 注入之间需要精细区分，并允许考虑通知间隔、强度和权重。

**派生约束。** 至少要区分“已经收到”“等待注入”“已经写入 Session 上下文”，不能把收到事件直接当作模型已感知。Runner 重启后仍应保有必要的去重 / 消费进度。

去重与消费进度应以接收的 Session 为边界：某个 UI Session 已经收到变化，不能导致另一个尚未感知的 UI Session 漏收。

具体可用事件标识、对象版本或其他等价方式实现，不在本版固定。这里要求的是同一语义变化不被反复追加成新消息，不承诺模型调用或外部副作用的全局 exactly-once。

### S-19｜事件到达不等于必须注入

**明确方向。** 通知系统可以接收变化，但是否进入 context change，应独立判断。判断应能考虑相关性、强度、权重及时间间隔。

**派生约束。** 对高频状态变化，应能合并为有意义的最新摘要，避免上下文和待处理队列无界增长。对已关注任务的终态、用户明确放弃等关键变化，不应被普通进度更新永久挤掉。

因合并、过期或不再相关而丢弃的待注入变化，需要可说明的处理规则；“尚未注入”不能被误标为“已感知”。具体算法与阈值待定。

### S-20｜长期 UI 对实时状态保持新鲜度意识

**明确方向。** UI Session 应持续适应用户位置 / 时区、当前时间、天气、活动任务等可能变化的上下文，而不能把启动时的环境信息视为永久有效。

半订阅负责让模型意识到变化，但不能独自保证所有实时回答都足够新。时间、天气等状态如何在使用时刷新，应作为上下文源的策略明确；不要求为每秒钟的流逝生成一个事件。

### S-21｜多信道共享状态，不机械复制全部聊天

**明确方向。** 同一用户可能通过 Email、Telegram 和 Web UI 等不同信道与一个 Agent 交流。各 UI Session 应保留其信道内的连续上下文，同时能够感知相关的活动任务与其他 UI Session 的主题摘要。

某信道缺少完整对话背景时，可以先通过活动状态或 topic 线索意识到相关事项，再主动读取必要信息。目标是共享“有哪些相关事情”，而不是把所有信道的消息流直接拼接。

**派生约束。** 主题可见范围、跨信道读取权限和用户身份映射必须明确。共享同一 Agent 状态不应自动突破不同参与者、群组或信道的访问边界。

## 8. 多进程状态共享与执行一致性

### S-22｜状态共享具有明确的一致性边界

**派生约束。** 把 Agent 状态类比为 RDB，意味着多个 Runner 可以共享持久状态，不意味着可以无协调地同时覆盖同一 Session。

系统至少需要保证：不同 Session 的合法状态更新不会互相丢失；同一 Session 的消息、工具结果与生命周期更新能够形成可恢复的顺序；多个 Runner 竞争推进同一 Session 时，不会静默执行出相互冲突的副作用。

是否采用单推进者、租约、版本条件更新或其他协调方式，留待设计。默认最小方案可以是一个 Session 同时只有一个推进者，但本文不把该实现方式作为既定架构。

### S-23｜状态提交、通知和恢复可以对齐

**派生约束。** 不能先通知“任务成功”，再发现最终状态或产物尚未持久化。任务状态、结果引用及其变化通知应建立明确的提交关系。

Runner 崩溃、重复输入或重复事件不能直接导致重复创建同一任务、重复提交认知或无判断地重复执行外部动作。具体重试、去重和幂等边界须在接口设计中定义。

Session 的持久状态也不必等同于完全无状态的 Runner；宿主可以拥有临时缓存和执行现场，只是恢复不能依赖一个永远不会消失的私有进程。

## 9. 产物版本、放弃与回滚

### S-24｜每次 Task 的变更边界可辨认

**明确方向。** 用户应能理解一次 Task 改了哪些产物，并在不满意时放弃其成果。理想目标是在受管工作范围内，让这次工作如同没有发生过。

**派生约束。** Task 应能够关联其输入基线、目标 Workspace / 对象、输出结果及实际变更范围。完成执行与用户接受结果是两种不同含义，不应只用一个“完成”标记代替。

### S-25｜为受管产物提供版本化与无效化能力

**明确方向。** 文件系统 / 状态系统需要支持类似版本管理的能力，使一次任务的改动能够独立保留、接受或撤销。Session 之间继承的应是有效产物版本，而不是最后完成但已被用户否定的结果。

不强制采用 Git；大文件和复杂数据对象可以使用快照、对象版本或其他等价机制。具体隔离、提交与回滚实现待定。

**派生约束。** 并发任务修改同一对象时，撤销其中一个任务不能悄悄删除另一个任务的有效改动。回滚前应检查基线和依赖关系，冲突必须显式处理。

### S-26｜不把所有副作用都声称为可完全回滚

**派生约束。** “完全回滚”必须说明覆盖范围。受控文件、版本化对象与外部系统动作的撤销能力不同；对无法撤销的动作，应在执行前识别其限制，并采用相应授权、延迟提交或可用的补偿机制。

用户请求放弃任务时，系统应反馈哪些变更已撤销、哪些尚未撤销、哪些不支持撤销。不能仅把 Session 标记为 discarded，就声称世界状态已恢复。

### S-27｜任务回滚与 Memory 回滚分别定义

**明确方向。** UI Session 必须知道某次结果已被用户放弃，不能继续将其作为有效成果使用。

**派生约束。** Task 可能已写入感知，甚至已参与跨 Session 认知整理。因此产物回滚不自动等于认知回滚。Session、产物版本与 Memory 来源之间应保留必要关联，以支持失效处理。

**待决设计。** 放弃任务后，是只撤销产物、还要撤销相关感知，还是允许保留失败经验，尚未确定。默认策略及显式“忘记这次工作”的语义，见关联文档的待决事项；不得自行宣称所有痕迹均已消失。

## 10. SDK 与 Memory 的接合要求

### S-28｜Memory 是 Agent Session 的默认机制

**明确方向。** 应用选择 Agent Session，一个重要预期就是此次工作可能被 Agent 记住。应用无需手工决定每条记忆写什么、记多少，也不应为了获得 Memory 而退回原长期 Runtime 中运行。

经授权的不同 Runner 应能使用同一 Agent 的 Memory，运行时以低成本写入感知，并在相关上下文中获得认知召回线索。

### S-29｜认知整理不阻塞普通任务

**明确方向。** Session 正在执行任务时，应尽量轻量记录感知；跨 Session 感知向认知的整理，由 Self Improvement 等独立过程完成。

SDK 不应要求每个应用自带一套重型 Memory 整理逻辑，也不应让每次感知写入都同步触发深度反思。

### S-30｜历史认知与实时变化使用兼容的上下文入口

**派生约束。** Memory 召回与半订阅事件都可以成为额外上下文，但语义必须区分：前者提示过去形成的认知，后者提示当前世界变化。

它们应能共享上下文预算、来源标识和注入边界；不能把一条未验证感知包装成已确认事实，也不能把事件到达当成稳定认知已经更新。

## 11. 逻辑能力清单

下表描述 SDK 需要覆盖的能力，不是已经确定的 API 命名或函数签名。

| 能力 | 必须表达的信息 | 预期结果 |
|---|---|---|
| 创建 / 装配 Session | Agent 身份、任务输入、上下文、目标对象、结束条件、运行能力 | 可识别的 Session 及其初始持久状态 |
| 恢复 / 推进 Session | Session 引用、授权、待处理输入、执行环境 | 进展、等待、成功或失败及已提交状态 |
| 读取 Session | Session DID / 对象引用与读取范围 | 生命周期、简要报告、结果引用；按需读取详情 |
| 投递输入 | 目标 Session、输入来源和必要的关联标识 | 可追踪的投递结果；是否允许改变目标遵循任务策略 |
| 订阅变化 | 对象范围、主动 / 半订阅方式及必要筛选条件 | 唤醒输入或待注入变化 |
| 写入感知 / 获取记忆线索 | Agent 范围、当前任务上下文和来源引用 | 低成本感知记录或有限的相关提示 |
| 停止 / 放弃 / 撤销成果 | 任务引用、请求范围、变更基线 | 明确区分执行是否停止、成果是否失效、变更是否撤销 |

## 12. 核心验收场景

以下为待实现能力的验收要求，不表示测试已经执行。

| 编号 | 场景 | 通过条件 |
|---|---|---|
| A-01 | 应用在独立进程中使用 Agent | 无需将本次 Prompt 安装进常驻容器，即可创建并完成 Task；身份、工具和 Memory 访问仍受授权约束。 |
| A-02 | 同一 Agent 由不同 Runner 使用 | 两个 Runner 的不同 Session 共享同一持久 Agent 状态；不要求共享进程内存。 |
| A-03 | Runner 退出后恢复 | 新 Runner 能恢复尚未完成 Session；已完成动作不会被无判断地重复执行。 |
| A-04 | 从长期聊天发起重任务 | UI 保持反馈能力，意图分析独立探索后再启动 Task，不把全部探索过程堆入 UI 上下文。 |
| A-05 | 多个贪吃蛇实验版本 | 用户要求修改时能定位已选择的 Workspace；歧义未解决时不擅自修改任意版本。 |
| A-06 | 已完成任务后继续改进 | 新建 Task 并继承有效产物；不依赖重新运行旧 Session。 |
| A-07 | 半订阅收到任务完成事件 | 事件自身不新增一次推理；下一次 input 或 action observation 能获得简要变化。 |
| A-08 | 正在执行时外部状态变化 | 不必等待下一条用户消息；合适的观察边界可以注入该变化。 |
| A-09 | 同一事件重放 / Runner 重启 | 同一变化不会反复追加为新上下文；未注入变化不会因仅被接收就丢失。 |
| A-10 | 高频通知与重要终态并存 | 进度可合并，已关注任务的完成 / 失败 / 放弃状态不会永久被淹没。 |
| A-11 | 多信道出现相关话题 | 在权限允许范围内看到活动状态 / topic 线索，再按需读取，不复制全部聊天记录。 |
| A-12 | 用户放弃一次任务 | UI 知道成果已失效；受管变更可按声明范围撤销；不支持撤销的部分被明确反馈。 |
| A-13 | 回滚与并发修改冲突 | 不静默覆盖其他任务成果；能识别冲突，并关联需重新处理的 Memory 来源。 |
| A-14 | 外部 Runner 与长期 Runtime 并存 | 两者遵循相同 Session 状态与 Memory 约定；对同一 Session 的竞争推进受到控制。 |

## 13. 待决设计与下一阶段输出

| 问题 | 已确定的边界 | 下一阶段需要决定 |
|---|---|---|
| 状态承载 | 允许持久共享，不能锁死在单进程内 | 文件、RDB、状态服务或组合；版本兼容与存储格式 |
| 跨语言 SDK | 其他语言能够运行或驱动经授权 Session | 协议绑定、公共执行内核或多语言实现的范围 |
| Session 装配 | 应用可注入本次任务材料，不必安装到 Agent 容器 | Agent 配置、应用 Prompt、Memory 与动态 context 的合成边界 |
| Runner 协调 | 不允许无协调地并发推进同一状态 | 执行权、恢复点、版本检查和重试协议 |
| 意图分析 | 与 UI 快速反馈分离，先探索再落任务 | 是否持久化；澄清回路；追加信息与变更目标的区别 |
| 订阅注入 | 主动与半订阅分离，变化避免重复注入 | 去重单位、时间间隔、权重、合并和过期策略 |
| 多信道感知 | 局部上下文保留，相关活动状态可共享 | topic 摘要粒度、权限和跨信道身份映射 |
| 产物回滚 | Task 变更范围可识别，受管成果可无效化 | 隔离、提交、冲突、外部副作用与 Memory 的联合处理 |
| 生命周期 | 完成、停止、放弃、回滚不是同一件事 | 精确状态机与操作合法性，避免用单一状态字段混淆 |

下一阶段设计应据此给出状态模型、逻辑接口、执行循环扩展点、授权模型和验收测试设计，而不是重新把全部能力装回唯一的常驻 Agent 进程。

## 14. 本版不预设的事项

本版不要求 UI Session 被统一拆成固定长度，不要求所有工作都异步执行，不禁止读取历史 Session，不把 Task Session 直接等同于具备全局 ACID 保证的事务，也不承诺任意外部副作用均可抹除。

本版的核心分离是：**Agent 的身份与内部连续性、Session 的执行生命周期、工作产物的有效版本，分别由明确的机制承担。** SDK 化应让这三者协作，而不是再次绑定到同一个进程。
