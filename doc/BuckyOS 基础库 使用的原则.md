# BuckyOS 基础库使用原则

> 状态：Draft  
> 适用范围：BuckyOS Rust workspace、相关 repository，以及所有新增或调整基础库依赖的贡献者和 Reviewer。  
> 本文中的“基础库”既包括通过 Cargo 引入的第三方 crate，也包括 BuckyOS 内部沉淀的可复用基础代码。

## 1. 文档目的

Rust 和 Cargo 让第三方库的引入非常方便。这种便利提高了开发效率，但也容易让依赖选择逐渐变成个人偏好：开发者可能基于过去的经验、熟悉的 API、教程示例或临时需求，引入一个新的 crate，而该 crate 又继续引入一组传递依赖。

当这种行为缺少统一约束时，整个系统会逐渐出现以下问题：

1. **编译成本持续增加。** 依赖树膨胀会增加首次编译、增量编译和 CI 构建时间，也会增大最终产物。
2. **同一 crate 的多个版本并存。** 在 BuckyOS 的常见构建方式中，Rust crate 通常会静态链接进最终产物。不同版本可能同时存在，并拥有各自独立的全局变量、注册表、缓存或初始化状态，进而造成重复初始化、状态不一致或难以诊断的运行时问题。
3. **供应链安全风险增加。** 精确锁死旧版本、传递依赖过多或上游版本策略混乱，都可能阻碍安全补丁及时进入系统。
4. **系统工程品位被个人选择稀释。** 同一功能由多个库重复实现，会增加理解、维护、替换和 Review 成本。

本规范的目标不是消灭第三方依赖，也不是为每个依赖设置繁重审批，而是让 BuckyOS 的基础库保持：

- 统一；
- 明确；
- 稳定；
- 可审查；
- 可复现；
- 可升级；
- 可持续演进。

## 2. 规范用语

本文使用以下约束级别：

- **必须**：除非经过明确的例外流程，否则不得违反。
- **应当**：默认做法；偏离时需要在 PR 中说明理由。
- **可以**：根据具体情况选择。

## 3. 核心原则

### 3.1 先统一，再选择更好

对于系统层面的同一项基础能力，BuckyOS 原则上只保留一个公共选择。

例如，当系统已经统一选定异步运行时、序列化框架、HTTP 实现、数据库访问库、日志体系或密码学基础库后，新代码应继续使用已有选择，不得因为个人习惯再次引入功能重叠的库。

这一原则可以概括为：

> **先统一，再优化。更好的库应替换现有选择，而不是与现有选择静默共存。**

统一的目的不是证明当前选择是理论上的绝对最优，而是先建立全局一致的工程基线。团队可以继续讨论更好的方案，但讨论结果应表现为一次有计划的全局迁移，而不是不同模块长期各用一套。

因此：

- 某一功能域已有公共选择时，新的 PR 必须使用该选择；
- 引入功能重叠的库，除非已有明确例外，否则 PR 应被拒绝；
- 不得通过局部 PR 先引入替代库，再用既成事实推动全局接受；
- 修改公共选择必须先发起 Issue 或 Discussion，再制定迁移计划。

### 3.2 第三方库的准入以稳定性为先

当某项能力只有一个可用实现，选择可能是“零和一”的问题：系统必须使用它，否则功能无法完成。即使如此，也应限制使用范围、记录风险，并考虑未来替换条件。

当同一领域存在多个候选库时，应优先选择工程品位更好、长期风险更低的实现。重点考察以下方面。

#### 3.2.1 愿景和边界明确

库应清楚说明自己解决什么问题，也清楚说明自己不解决什么问题。其定位不应随着社区热点频繁变化。

#### 3.2.2 发布节奏可预期

维护者应谨慎发布版本，避免无意义的高频发布或在兼容版本中随意引入破坏性变化。版本更新应主要服务于 Bug 修复、安全修复、性能优化、兼容性改进和边界内的必要完善。

#### 3.2.3 向后兼容有可信记录

成熟库应认真对待公开 API。需要不兼容调整时，应通过明确的主版本、迁移说明和合理过渡进行管理。

#### 3.2.4 有足够的真实使用和质量口碑

用户数量不是唯一标准，但长期、广泛的真实使用有助于暴露边界条件、平台差异和隐藏缺陷。应关注维护响应、历史严重缺陷、安全事件处理能力和版本质量稳定性。

#### 3.2.5 测试覆盖真实边界

候选库应具有可靠测试，尤其是错误路径、极端输入、并发行为、跨平台差异、兼容性和历史回归问题。测试质量通常能反映维护者是否真正理解库的边界。

#### 3.2.6 提供明确的稳定版本信号

上游应能够明确告诉使用者，哪个版本系列适合稳定使用，以及该系列会获得怎样的兼容性和安全维护。这个信号可以是 LTS、stable channel、长期维护分支、官方推荐主版本或其他等价机制。

如果一个库只有在使用者精确锁死到某个具体版本时才能保证工作，通常意味着它没有提供可信的兼容承诺和发布规则。除非没有替代方案，否则不应将这类库作为 BuckyOS 的长期公共依赖。

### 3.3 边界清晰，不等于越小越好

BuckyOS 认可“小而美”，但反对将“小而美”推向极端。

一个库有清晰边界，不代表每一个函数、算法或小工具都应独立成为一个 crate。传统 NPM 生态已经证明，过度碎片化会导致依赖数量、供应链风险、编译成本和维护成本快速增长。

对于网络、密码学、序列化、文件系统、时间处理、数据库访问、压缩、并发等已经成熟的基础领域，应优先选择具有合理完整性的领域库，而不是为每个细小功能分别引入 crate。

判断 scope 时，可以参考 Java、C# 等成熟平台中 System 类库经过大型工程验证的领域划分。这里不是要求复制其 API，而是借鉴其对基础能力边界的长期工程判断。

引入一个小型 crate 前，必须先判断：

> 这个功能是否真的构成一个独立领域，还是只是某个成熟领域中的普通组成部分？

如果只是简单字符串处理、字节转换、重试循环、格式校验、小型数据结构或少量通用逻辑，应优先考虑：

1. Rust 标准库是否已经提供；
2. 当前公共领域库是否已经提供；
3. BuckyOS 内部基础库是否已有实现；
4. 是否值得在本地直接实现；
5. 引入一个新供应链节点是否真的合理。

### 3.4 依赖声明跟随上游，正式构建通过锁文件复现

BuckyOS 自己声明直接依赖时，应使用合理的兼容版本范围，通常采用 Cargo 的 caret 或部分版本约束；原则上不使用精确版本锁定。

推荐：

```toml
some-crate = "1.4"
```

原则上避免：

```toml
some-crate = "=1.4.7"
```

精确锁定只有在存在明确兼容性问题且已登记例外时才可以使用，并必须说明解除锁定的条件。

这一策略的目标是尽早跟随上游兼容变化，让安全补丁、兼容性变化和潜在破坏尽可能早地在 CI 阶段暴露，而不是长期隐藏在旧版本中。

`Cargo.toml` 和 `Cargo.lock` 承担不同职责：

- `Cargo.toml` 表达项目接受的版本兼容范围；
- `Cargo.lock` 记录某次构建实际解析出的完整依赖图。

因此，不在 `Cargo.toml` 中锁死版本，并不等于放弃可复现构建。对于正式 CI 结果，必须保存并关联：

- 源码提交；
- `Cargo.lock`；
- Rust 工具链版本；
- 关键构建配置；
- 最终构建产物。

CI 应同时具备两类能力：

1. 使用既定 `Cargo.lock` 的可复现构建；
2. 定期刷新兼容版本范围，尽早发现上游变化。

### 3.5 可复用代码采用三层模型

可复用代码不应全部通过外部依赖解决。BuckyOS 将其分为三层。

#### 第一层：外部领域通用库

通过 Cargo 引入的第三方库，应主要用于与 BuckyOS 产品无关、具有成熟领域边界、可被广泛项目复用的基础能力。

#### 第二层：Wrapper 或子系统内部公共库

如果一段代码只在某个 wrapper、子系统或相邻模块中复用，应优先放入该范围内的公共库。这样可以限制变更影响面，避免过早设计系统级抽象。

#### 第三层：BuckyOS Base

当一项能力已经被证明会被多个 wrapper、多个 repository 或整个系统共同使用时，可以讨论将其上移到 BuckyOS Base。

BuckyOS Base 用于有意识地沉淀：

- 跨 wrapper 的公共代码；
- 跨 repository 的公共能力；
- BuckyOS 特有的系统抽象；
- 与 BuckyOS 运行环境密切相关的基础设施；
- 未来 System Framework 的基础组成。

当前 BuckyOS Base 主要服务于内部体系，不承诺对外的严格 API 兼容性。但它仍必须保持清晰边界，不得成为随意堆放 helper 的杂物库。

公共代码应按实际复用需求逐级上移：

> 当前模块 → wrapper/子系统公共库 → BuckyOS Base → 必要时再独立为真正的领域通用库。

### 3.6 Wrapper 只隔离真实的不稳定性

不得仅仅为了“以后可能替换 Provider”就默认给第三方库增加一层 Wrapper。

以下理由不足以支持新增 Wrapper：

- 团队暂时不知道该选哪个库；
- 需要照顾不同开发者的个人偏好；
- 理论上担心成熟库未来可能修改接口；
- 认为所有第三方 API 都必须隔离；
- 只是希望代码看起来更有架构感。

对于 SQLite 这类成熟领域，如果已经选定一个质量可靠的 Rust 库，应统一直接使用。没有独立系统语义的薄封装通常只会复制 API、丢失底层能力并增加维护风险。

Wrapper 可以被接受的典型场景是：

- 上游领域非常新；
- 多个候选库都处于快速变化的 `0.x` 阶段；
- API、数据模型或平台支持频繁变化；
- 没有候选库表现出足够成熟度；
- 该能力对 BuckyOS 又十分重要，并会在多个位置使用。

这时，Wrapper 的意义是隔离现实存在的不稳定性，而不是逃避技术选择。它必须围绕 BuckyOS 真正需要的稳定语义设计，并明确：

- 需要隔离的具体风险；
- 支持的最小能力边界；
- Provider 替换是否真的可行；
- 测试策略；
- 长期保留还是临时过渡；
- 什么条件满足后可以删除 Wrapper 或固定实现。

由此形成两种基本范式：

1. **成熟、稳定、领域边界清晰的能力：统一选择并直接使用优秀第三方库。**
2. **系统高度依赖、但上游生态尚不成熟的能力：通过内部 Wrapper 隔离真实不稳定性。**

### 3.7 允许例外，但例外必须明确、可见、可追踪

原则一定会有例外。当系统需要某项特殊能力，而现有统一选择确实无法满足，并且没有其他合理方案时，可以引入例外依赖。

合理例外通常是明确的“零和一”需求，而不是 API 偏好、教程习惯或未经验证的性能想象。

每个例外必须同时满足以下要求：

1. 在对应 `Cargo.toml` 中用注释说明原因；
2. 说明现有公共选择为什么无法满足；
3. 限定使用范围；
4. 标记实验性、临时性或已知风险；
5. 给出移除或重新评估条件；
6. 在集中例外清单中登记；
7. 在后续定期 Review 中持续跟踪。

示例：

```toml
# Exception:
# Used only for resumable hashing of very large files.
# The workspace-standard hashing library does not expose serializable
# intermediate state. Remove this dependency when resumable hashing is
# no longer required by the chunking strategy.
resumable-hash = "0.x"
```

曾经为了超大文件的 checkpoint 式流式哈希，引入实验性库可能是合理的；当系统限制 chunk 大小、不再需要断点恢复后，该例外也应自然删除。

> **例外不是永久授权。例外默认是临时的，并应随其需求条件消失而被清理。**

## 4. 依赖清单与持续治理

### 4.1 维护系统已知依赖表

BuckyOS 应按功能领域维护公开的系统已知依赖表。建议至少包含：

| 字段 | 说明 |
|---|---|
| 功能领域 | 异步运行时、序列化、数据库、日志、密码学等 |
| 当前公共选择 | 统一使用的 crate 或内部基础库 |
| 使用范围 | 全系统、特定 wrapper、特定 repository |
| 状态 | Standard、Experimental、Deprecated 等 |
| 版本策略 | 推荐主版本、稳定分支或其他约束 |
| 上游状态 | 维护活跃度、稳定信号、重要风险 |
| 多版本情况 | 是否存在多个版本及原因 |
| 迁移状态 | 是否计划升级、替换或移除 |
| 备注 | 设计背景和重要限制 |

该表不仅回答“系统正在使用什么”，也应逐步回答“为什么这样选择”。

### 4.2 维护例外依赖表

例外依赖应集中登记，建议至少包含：

| 字段 | 说明 |
|---|---|
| crate | 例外依赖名称 |
| 使用位置 | repository、wrapper 或 crate |
| 引入 PR | 便于追溯背景 |
| 例外原因 | 不可替代的具体能力 |
| 使用范围 | 限制影响面 |
| 风险 | 实验性、维护状态、安全或兼容风险 |
| 移除条件 | 何时可以删除 |
| 负责人 | 当前跟进者 |
| 最近 Review | 最近一次重新确认时间 |

`Cargo.toml` 注释解决“为什么这里用了它”，集中清单解决“整个系统还有多少例外”。

### 4.3 普通新增通过 PR

当前阶段不需要为每一个第三方库建立复杂的前置审批。

如果新依赖符合本文原则，可以通过正常 PR 引入。PR 必须同时完成：

- 说明新增能力和使用范围；
- 确认不存在已有公共选择或说明例外；
- 检查直接和传递依赖影响；
- 采用正确版本策略；
- 更新系统已知依赖表；
- 必要时更新例外依赖表。

### 4.4 公共选择变更必须先讨论

从库 A 迁移到库 B、替换全系统异步运行时、序列化框架、数据库访问库、密码学实现或其他公共基础能力，会影响多个 crate、已有代码和发布结果，因此必须先通过 Issue 或 Discussion 讨论。

讨论至少应说明：

- 当前选择存在的真实问题；
- 替换的必要性和紧迫性；
- 候选方案的优势和风险；
- 迁移影响面；
- 兼容性、性能和安全变化；
- 如何避免新旧方案长期共存；
- 完整迁移和验证计划。

形成结论后，再通过一个或多个 PR 完成全局迁移。

### 4.5 定期 Review

依赖治理是一项持续工作，而不是一次性整理。

原则上：

- **每周进行一次自动扫描。** 可由固定脚本和 AI 辅助检查新增依赖、多版本、精确锁定、安全公告、上游维护状态、传递依赖增长、编译时间和产物体积变化。
- **每月进行一次人工 Review。** 重点确认功能重叠、失效例外、长期旧版本、停止维护的上游、异常依赖增长，以及是否需要发起替换讨论。

AI 可以辅助归纳和发现风险，但最终结论仍应由正常工程 Review 流程决定。

## 5. PR Review 的基本判断

Reviewer 在看到新增或修改依赖的 PR 时，应重点判断：

1. 该能力是否已经存在公共选择；
2. 新依赖是否真的属于独立、通用的领域能力；
3. 是否只是为了一个很小的函数引入 crate；
4. 上游是否具备清晰边界、稳定节奏、测试和兼容承诺；
5. 是否引入大量不必要的默认 feature 或传递依赖；
6. 是否导致同一 crate 多版本共存；
7. 多版本是否涉及全局状态、注册表、运行时或初始化风险；
8. 版本约束是否过度锁死；
9. 是否错误地用 Wrapper 回避统一选择；
10. 例外是否有明确语义、限制范围和移除条件；
11. 系统依赖表是否已同步更新。

## 6. 快速 Check 清单（贡献者提交 PR 前）

下面的清单用于快速判断一个基础库应如何使用。提交涉及依赖的 PR 前，请逐项确认。

### A. 先确认是否真的需要新依赖

- [ ] Rust 标准库不能直接完成该功能。
- [ ] workspace 已有依赖或 BuckyOS Base 不能完成该功能。
- [ ] 这不是仅包含少量简单代码的“小函数 crate”；本地实现不会明显更简单、更安全。
- [ ] 该功能具有合理、完整的领域边界，而不是成熟领域中的一个过度碎片化组件。

### B. 检查是否已有统一选择

- [ ] 已查阅系统已知依赖表。
- [ ] 该功能领域尚无公共选择；或者本 PR 正在使用已有公共选择。
- [ ] 没有因为个人习惯、教程示例或 API 偏好引入功能重叠的库。
- [ ] 若要替换公共选择，已经先发起 Issue/Discussion，并有全局迁移方案。

### C. 检查候选库质量

- [ ] 库的愿景和 scope 清晰。
- [ ] 发布节奏可预期，没有频繁、随意的破坏性变化。
- [ ] API 向后兼容记录可信，或有明确稳定/LTS 信号。
- [ ] 测试、文档和错误处理足够可靠。
- [ ] 上游仍在维护，安全问题响应方式可接受。
- [ ] 依赖树规模与该功能价值相匹配。

### D. 检查 Cargo 使用方式

- [ ] 优先通过 workspace dependency 统一声明和复用。
- [ ] 只启用实际需要的 features，避免无意义的默认能力。
- [ ] 使用合理兼容版本范围，没有无理由写成 `=x.y.z`。
- [ ] 已检查 `cargo tree`，确认没有意外的重复版本和异常传递依赖。
- [ ] 若出现多个版本，已评估全局变量、注册表、运行时、缓存和初始化风险。
- [ ] 正式 CI 结果能够关联对应的 `Cargo.lock`、工具链和构建配置。

### E. 检查代码应放在哪一层

- [ ] 完全产品无关、属于成熟通用领域的能力，才通过 Cargo 引入第三方库。
- [ ] 只在一个 wrapper/子系统中复用的代码，优先放在该范围的公共库。
- [ ] 跨 wrapper、跨 repository 的系统公共能力，经过讨论后上移到 BuckyOS Base。
- [ ] 没有把 BuckyOS Base 当作无边界的 helper 集合。

### F. 检查是否真的需要 Wrapper

- [ ] Wrapper 不是为了回避库选择，也不是为了照顾个人偏好。
- [ ] Wrapper 隔离的是现实存在的上游不稳定性，而不是理论上的“以后可能替换”。
- [ ] Wrapper 定义了 BuckyOS 自己需要的稳定语义，而不是简单转发第三方 API。
- [ ] 已写明 Provider 替换策略、测试方式和退出条件。

### G. 检查例外

- [ ] 若违反统一选择或版本原则，确实存在明确、不可替代的“零和一”需求。
- [ ] 已在 `Cargo.toml` 中用注释写明例外原因。
- [ ] 已说明使用范围、风险和移除条件。
- [ ] 已更新例外依赖表，并指定后续 Review 责任。

### H. 提交前最后确认

- [ ] 本 PR 已同步更新系统已知依赖表。
- [ ] 新依赖带来的编译时间、产物体积和供应链成本是可接受的。
- [ ] Reviewer 不依赖口头背景，仅从代码、注释和清单就能理解这次选择。
- [ ] 当未来需求消失或上游成熟后，该依赖、例外或 Wrapper 可以被明确清理。

如果以上任一关键项无法确认，应先使用已有公共选择、缩小实现范围，或发起 Issue/Discussion，而不是直接把新的依赖加入系统。

---

**一句话原则：**

> **统一优先于局部最优；稳定优先于新奇；选择完整领域库而不是碎片化依赖；用 `Cargo.lock` 保证构建复现，用持续 CI 跟随上游变化；Wrapper 只隔离真实不稳定性；所有例外都必须明确、可见并可清理。**
