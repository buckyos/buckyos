# Session Only Member 设计

- 版本：草案，2026-10-04；修订为标准 BuckyOS guest 身份、App access token 登录和统一授权模型。
- 状态：**设计结论，尚未实现**。本文确定认证与授权边界；协议细节和上线前置见 §10、§12。
- 核心流程：**App 页面取得外部用户的 access token，调用 verify-hub 的 `login_by_app_access_token`，换取标准 BuckyOS guest session token。** 后续调用沿用系统认证、RBAC 和资源授权。
- 实施原则：**先完整设计并验证权限模型，再开放 guest 登录。** 可以逐项开放业务能力，不能先签发全系统认可的 token，再逐个服务补权限检查。

## 1. 背景与结论

### 1.1 场景

客服是群成员，客户没有自己的 Zone，也没有本 Zone 的普通账号，但在 CRM 等应用里有稳定账号。客户打开应用发来的链接，在浏览器里进入自己的工单 Session；换设备、重新登录后仍是同一个人，历史保持连续。

这类客户从第一次接入起就是系统认可的 guest user。App 负责验证外部账号，verify-hub 负责建立 BuckyOS 登录态，系统和资源方共同决定访问权限。

### 1.2 设计结论

1. **身份标准化**：应用账号映射到稳定的 BuckyOS guest DID；已有经过验证的身份绑定时优先复用，不能每换一种联系方式就新建身份（§3）。
2. **登录标准化**：App 页面调用 `verify-hub.login_by_app_access_token`，得到标准 session token；其主体是 guest 本人，并绑定明确的 AuthTarget（§5）。
3. **权限默认拒绝**：guest 创建时没有业务权限，不继承普通用户、App owner 或 App service 的权限。具体能力由有权授权的主体显式授予（§4）。
4. **创建与使用分开**：`app owner + app instance` 决定 App 能管理哪些 guest、能授予什么权限；请求执行时使用 `guest + 当前 AuthTarget`。
5. **复用群模型**：Session Only Member 在群里仍是 v2 的 Session Guest；邀请、加入、封禁、Hook 和历史可见区间保持原有语义（§6）。
6. **完整授权是上线前提**：统一 RBAC、服务内部授权和全部入口必须共同满足 guest 的默认拒绝规则（§9、§10）。

本文不再引入身份型 tunnel、msg-center 专用访客凭据、`mhg_` token 或绕过标准认证的访客分支。Telegram 等已有消息 tunnel 继续处理外部平台消息，与本设计的浏览器登录无关。

### 1.3 与 SSO 的关系

`login_by_app_access_token` 是系统统一提供的一种登录方式。对下游服务而言，用户通过密码、钱包或 App 凭证登录，不改变标准 token 的校验方式。

SSO 负责应用身份域登记、外部账号绑定、稳定 DID 映射、App 凭证验证、标准会话签发及生命周期。RBAC 和资源方负责授权；登录成功不产生隐含的资源访问权。Message Hub 只负责访客页面与 Session 交互，不承担身份提供方或 token 签发中心的职责。

## 2. 术语与身份层次

| 术语 | 含义 |
| --- | --- |
| 匿名访问者 | 尚未认证、没有当前用户登录态的请求方；只可访问明确公开的入口 |
| BuckyOS guest user | 有稳定 DID、可持有标准登录态、默认无业务权限的受限用户 |
| Session Guest | 某个 DID 在指定 Session 内的参与角色；与系统用户类型是两个维度 |
| Session Only Member | 本文场景中的 guest user，仅被授予参与指定 Session 所需的能力 |
| 身份源 App | 验证外部账号、为其提供 App access token 的应用，例如 CRM |
| 应用身份域 | 系统登记的身份管理范围，绑定获准管理它的 App 实例及其 owner |
| App access token | App 为某个外部用户提供、获准用于向 verify-hub 换取登录态的凭证；不是 App service 自己调用系统的 token |
| 标准 guest session token | verify-hub 签发的标准用户 session token；用户类型为 guest，不是另一种 token 格式 |
| AuthTarget | 当前登录对应的精确 App 实例或系统服务；不同于证明用户身份的身份源 App |

token 的 `principal_kind` 沿用 `user`。guest 是用户类型与授权策略，不新增一个能落入“非 User 默认放行”分支的主体类型。后端必须从可信用户状态识别 guest，不能由页面自报用户类型。

## 3. 稳定 guest 身份

### 3.1 映射与复用

SSO 维护以下稳定绑定；具体 DID 命名由系统身份规范确定，首次实施前定案：

```text
(应用身份域, 外部账号稳定 ID) → BuckyOS guest DID
```

- 第一次接入可以预先创建 guest，也可以在登录兑换时按已批准的创建策略创建；并发或重试必须得到同一个身份。
- **已有通过其它联系方式建立的稳定身份时，优先复用经过验证的绑定。** 新手机号、邮箱或第三方登录是给该身份增加凭据，不自动生成新 DID。
- 复用必须验证身份控制权和绑定授权。App 不能提交任意 DID、相同昵称或相同手机号就接管已有用户，也不能通过此接口登录普通用户或管理员。
- 外部账号已经绑定普通 BuckyOS 用户时，走该用户的标准 SSO / 已授权的联合登录流程；不能把 guest 登录入口变成普通账号的认证旁路。
- 尚无可信跨域绑定时，不同身份域的相同账号字符串视为不同用户。

### 3.2 标识与凭据分离

账号主键必须稳定、不含隐私原文且不可复用。手机号、邮箱等只作为可更换的绑定，不能直接成为 DID 的一部分。手机号回收后，新持有人应建立新账号，不能继承旧客户历史。

消息、成员记录和审计引用 DID；access token、session token 的轮换或过期不改变 DID。应用身份域 ID 同样不可复用，App 升级、改名或重装不能隐式改变身份归属。

guest 不需要自己拥有 Zone 或私钥。标准登录态由本 Zone 的 verify-hub 背书；群消息继续遵循 host 的信任模型。这不自动赋予 guest 跨 Zone 登录或访问远端资源的权利。

### 3.3 联系人与生命周期

- DID 映射属于系统身份设施，不依赖 `contact.resolve_did` 创建。业务需要备注、屏蔽或对账时，可在获准的 owner 通讯录里建立 contact。
- Contact 按 owner 分库；访客页面和客服界面上的显示名取 Session 成员资料，不能要求访客读取客服通讯录。
- 身份域保留来源 App、owner、账号绑定和签发审计。App 卸载或身份源停用时冻结其代登录权，并按 §9 撤销相关会话；身份和历史不得随之删除或转交给同名新实例。
- Zone owner 可通过受审计的管理流程接管身份域；日常管理、恢复与未来迁移都必须有明确的授权链。

## 4. 完整的授权模型

### 4.1 创建、授权与调用分别检查

| 操作 | 授权主体 | 必须检查 |
| --- | --- | --- |
| 注册身份域、获得 guest 管理能力 | Zone 授权的管理主体 | 哪个 App 实例可管理哪个域、允许哪些登录目标和授权范围 |
| 创建 / 管理 guest | `app owner + app instance` | 域归属、guest 管理权限、账号状态与配额；创建本身不授予业务权限 |
| 给 guest 增加资源权限 | 资源 owner 或获准转授的主体 | 具体资源、动作、接收者、期限及可转授范围 |
| 用 App access token 登录 | 已登记身份源及目标登录策略 | 凭证真实有效、用户绑定、代登录权、guest 状态、AuthTarget 和会话范围 |
| guest 调用系统服务 | `guest DID + 当前 AuthTarget` | 用户授权、App 能力、会话限制、资源当前规则及撤销状态 |

owner 必须来自可信安装记录和调用上下文，不能由请求参数指定。App 实例需要精确区分，不能仅凭相同 `appid` 就允许不同 owner 下的实例互相创建、登录或管理 guest。

### 4.2 “可使用”不等于“可转授”

App 有权读取资源，不表示有权把读取权限授予别人。它给 guest 新增的授权必须满足：

```text
App 本次授予 guest 的权限
    ⊆ 系统允许该类 guest 获得的权限
    ∩ 该 app owner + app instance 获得的可转授范围
    ∩ 资源方允许授予该接收者的范围
```

可转授范围必须显式定义资源、动作及接收者约束，不能从 owner 的 admin 身份或 App 的已有读取权限自动推导。App 默认没有继续转授的能力，guest 也不因获得资源访问权而得到再次授权的能力。

例如客服 App 可以读取全部工单，但只获准把某张工单的参与权授予对应客户。给客户甲开放工单 A，不得顺带开放其它工单、客服邮箱或系统配置。

这个上限限制的是 **App 发起的授权**。其他资源 owner 仍可独立给 guest 授权；每条授权都要保留来源、范围、有效期和撤销关系，不能把所有来源混成一个不可追溯的权限集合。

### 4.3 请求执行时取交集

```text
实际访问权限 = guest 当前已获授权
             ∩ 当前 AuthTarget 允许使用的能力
             ∩ 本次登录会话的范围与来源限制
             ∩ 资源当前的 ACL / 成员资格 / 业务规则
```

- guest 的默认授权集合为空。不自动加入普通 `users` 权限组，不自动获得个人邮箱、通讯录、存储、任务、系统配置或 sudo 权限；“这是自己的资源”也不能替代显式授权。
- App 需要使用某项系统能力时，须开放该 App 的对应能力，同时给 guest 授予具体资源权限。不能把请求主体替换成 App owner 来解决权限不足。
- 身份源 App 与承载页面的 AuthTarget 可以不同，但跨目标登录必须经过明确批准。App access token 不能让调用者自行选择一个高权限系统 target。
- 即使 guest 页面由 Message Hub / control-panel 承载，其更宽的系统 App 权限也不能消除 guest 和来源会话的限制。登录来源、目标、允许的范围都必须保留并参与检查。
- 后续资源方给 guest 新增的权限，不能隐式扩大已签发的 App 代登录会话。该会话仍受签发时批准的范围上限约束；扩大范围需重新授权。
- API 入口允许调用，只是第一层检查；具体 Session、对象、路径和动作仍由资源方判断。任何一层拒绝即拒绝。

统一 RBAC 与服务内部授权应表达一致的规则，明确每类授权的权威来源。群成员表仍是 Session 成员资格的真相源，不能另建一份访客专用成员表或凭据表，导致撤销不同步。

### 4.4 App 代登录的信任边界

信任 App 证明域内用户身份，就意味着 App 可以取得这些用户的代登录会话。用户打开链接只能证明有人持有该凭证，不能证明身份源绝无冒用可能。

因此，资源方授权时必须能看到身份来源及其认证强度；需要更强身份保证的权限可以拒绝 App 代登录，或要求独立的认证。不能一边允许 App 签发用户凭证，一边宣称 App 无法代表该用户操作。

系统保证 App 只能认证自己获准管理的账号，且最终操作受 §4.3 的交集约束。只有群邀请权的客服不因此获得客户的代登录权；认证和邀请是两项不同的能力。

## 5. `login_by_app_access_token` 登录流程

### 5.1 主流程

```text
1. 用户打开 App 的特定页面或登录链接。
2. 页面取得 App 为该外部账号提供的 access token。
3. 页面调用 verify-hub.login_by_app_access_token。
4. verify-hub 校验身份源、凭证、账号绑定、登录目标和权限边界。
5. 查找稳定 guest DID；需要首次创建时，执行已批准的创建策略。
6. verify-hub 签发标准 session token，以及标准刷新机制需要的 refresh token。
7. 页面以 guest 身份调用 msg-center 或其他已获授权的系统服务。
```

这是“App 代登录”。登录成功只建立用户会话，不代表已接受邀请，也不代表已经加入任何 Session。

### 5.2 输入与校验契约

接口逻辑输入是 App access token 和明确的登录目标；具体字段和响应结构按 SSO 协议落定。输入中用于定位身份源的 App 实例标识只作查找线索，必须与验证后的凭证和登记信息一致。

verify-hub 必须校验：

1. 身份源是获准代登录的有效 App 实例，身份域、owner 和信任配置匹配。
2. access token 的真实性、有效期、兑换用途及接收方；不能接受仅为其它服务签发的第三方 token，或 App service 的系统访问 token。
3. token 中的稳定账号标识属于该身份域；DID、用户类型和权限来自系统可信绑定及策略，不能照抄未经授权的 claims。
4. 目标 AuthTarget 与凭证绑定及系统批准的目标一致；App target 精确到实例，System target 需有单独授权。
5. guest、身份域和 App 的当前状态允许此次登录，会话 scope 不超过已批准范围；登录接口不能顺带接受任意提权请求。
6. 兑换的重放与重试规则。用于链接登录的凭证只能兑换一次；用绑定该次兑换的随机 nonce 区分合法重试，只为同一兑换返回仍有效的原结果。更换 nonce 的重复兑换应拒绝，不能重复建号或无限产生会话。

App 凭证可用已登记公钥验签，也可经系统登记的服务端校验接口验证；具体方式见 §12。校验地址和信任根不能由页面或 token 任意指定。

### 5.3 标准 token 与会话上下文

| 信息 | 语义 |
| --- | --- |
| `sub` / 用户标识 | 映射后的 guest 本人；服务解析为稳定 guest DID |
| `principal_kind` | `user` |
| 用户类型与状态 | 系统可信用户记录中的 guest 及当前状态 |
| `AuthTarget` 相关 claims | 标准 `target_kind`、`appid`；App target 带匹配的实例与 owner 信息 |
| `iss`、`token_use`、有效期与会话标识 | 沿用 verify-hub 的标准会话契约 |
| 认证来源与会话范围 | 可追溯身份源、身份域、登录方式及批准的 scope；供授权、撤销和审计使用 |

最后一项的具体 claims 或服务端会话记录形式由 SSO 统一定义，并由所有相关入口强制执行。不能在尚无 scope 检查能力时，仅把字段写进 token 就认为已经限制了权限。

页面和 App 后端继续传递 guest 的标准 token，不能换成 App service token。会话保存、刷新、退出复用系统 SSO；刷新不得扩大 target、权限范围或认证强度，并重新检查 guest、来源 App 和会话状态。

### 5.4 链接与浏览器入口

- App 可以先验证手机号、第三方账号，再给页面 access token；也可以发送携带短时、一次性登录凭证的链接。
- 链接凭证只承担登录兑换用途，不携带 App 后端的通用服务权限。原始凭证不进入日志；采用 URL fragment 等方式交给页面后，应立即从地址栏清除。
- 若链接还指定工单或咨询入口，该信息只是导航上下文，访问与加入仍须按 guest 身份重新鉴权；可以使用服务端保存的不透明入口 ID，避免公开 Session 标识。
- verify-hub 登录兑换入口允许未持 BuckyOS token 的请求，但必须验证 App 凭证并限流；无效凭证的响应不泄露账号是否存在。兑换失败不得回退成 App owner 或内部调用。
- 换设备或凭据丢失时由 App 重新认证、签发新凭证，映射到原 DID。没有可恢复绑定的匿名账号不能凭空找回。

## 6. Session Guest 接入

### 6.1 加入与双方同意

| 入口 | 群侧准备 | guest 登录后 |
| --- | --- | --- |
| 指定工单 | 有 `session.invite_guest` 能力的成员邀请 guest DID，状态为 `Invited` | 用户确认进入后调用 `accept_session_invitation`，变为 `Included` |
| 公开咨询 | 群配置开启 `membership.guest_entry`，授权相应的咨询申请入口 | 用户确认后调用 `submit_guest_request(request_id)`，host 按模板创建 Session |

访客只能加入具名、`allow_guests = true` 且成员策略不是 `inherit` 的 Session。执行加入时照常检查邀请有效性、封禁、Guest 上限、频率限制和 `join` Hook。

邀请或公开入口策略应提供完成加入所需的最小授权：允许本人看到规定的邀请信息并接受邀请，或向指定群申请咨询；不能要求先成为 `Included` 才允许接受邀请，也不能提前开放历史消息。登录兑换与入群是两个操作，重试分别幂等；登录成功、加入失败时保留登录态，不自动扩大权限。

页面的“进入会话”动作可以依次完成登录兑换和加入确认。审计分别记录 App 代登录来源与 guest 的加入请求，不能把持有 access token 等同于群已同意接纳。

### 6.2 方法与资源授权

msg-center 从标准用户 token 解析 guest DID，构造正常的 `GroupActor`，保留当前客户端上下文。下面是本场景应授予的能力范围，**不是另一套访客 token 的方法白名单**：

| 能力 | 限制 |
| --- | --- |
| 群资料、邀请信息、会话列表 | 仅公开资料或本人获准看到的内容；不泄露其它 Session 的存在 |
| 接受邀请、申请咨询 | 仅本人及对应的邀请 / 公开入口；走 §6.1 的状态转换 |
| Session 成员、共享状态、消息与变更流 | 仅获准参与的 Session，遵守 Guest 可见范围和历史区间 |
| 发消息、修改昵称、已读回执、退出 | 操作者为 guest 本人；消息 `from` 等于认证 DID；遵守 Session 规则 |
| 群消息与附件对象读取 | 同时验证 Session 可读、消息可读及对象确被该消息引用，不能只凭对象 ID 读取 |

个人邮箱、通讯录、群管理、创建群和其它系统资源在本场景中不授予。以后开放新能力时，使用同一授权模型添加明确权限；不能因为接收方能验证标准 token 就直接放行。

`allowed_clients` 等群策略继续生效；客户端来自已验证的登录上下文，不能固定伪装成一个总被允许的“访客客户端”。RPC、群 HTTP、对象读取和事件订阅必须执行一致的授权条件。

### 6.3 存储与更新

访客直接读取 host 上的群存储；不为了登录自动创建个人邮箱或远端消息投递通道，也不注册身份型 tunnel。通知与投递按实际配置的接收能力决定，无个人收件箱的访客通过会话状态获取变化。

页面可以轮询 `group.changes`。标准 token 使复用 kevent 成为可能，但事件订阅也必须取得对应资源权限并正确处理撤销，不能因为已登录就订阅全局事件。

## 7. App 页面与 Message Hub

访客入口只加载登录兑换与会话视图，可复用 `ConversationView`，由面向群存储的数据层承载。登录后它面对的是标准 guest user，有当前 DID 和标准 token；不能继续把该用户当作无身份的匿名请求。

| 位置 | 处理方式 |
| --- | --- |
| 页面初始化 | 取得 App access token，调用统一登录接口，建立标准 guest 会话上下文 |
| 当前用户 DID | 取可信登录结果及用户身份解析；不再依赖 msg-center 私有兑换结果 |
| 会话数据 | 使用 host 的 `group.list_sessions`、`group.list_messages`、`group.changes` 等；不依赖个人邮箱投影 |
| 名字与头像 | 取允许读取的群成员资料和 Session 昵称；不要求 `contact.*` 权限 |
| 身份比较与展示 | 统一经过规范身份解析，客服端与访客端一致（§8） |
| 消息附件 | 按群对象授权读取；上传需要单独的写入权限和配额，本次首发不开放 |
| 删除、归档、置顶等个人邮箱操作 | 本场景不提供 |
| 登录态保存 | 复用标准 SSO / SDK，并隔离 guest 会话与浏览器已有的普通用户或管理员会话，不能静默混用 |

登录 bootstrap 页面必须在尚无 BuckyOS token 时可达。Message Hub 可保留 `/messagehub/guest` 一类公开前端入口；App 子域上的对应入口则由安装和网关策略明确开放。页面公开不等于数据公开，后端仍验证标准 token 和资源权限。兑换 endpoint 的可达性、跨 origin 调用及 cookie 路径需与实际部署一起验证，不能笼统假设所有场景都不需要调整网关。

## 8. 迁移就绪与长期数据

从第一天起满足以下约束，迁移产品流程可以后续建设：

1. 使用稳定且不可复用的账号 ID；手机号、邮箱和外部登录方式只作绑定。
2. 数据引用 DID，不引用登录凭证；换设备、换号码、刷新 token 不改变身份。
3. 保留身份域、签发方及其上级管理关系，应用停用后仍有合法的恢复或迁移主体。
4. 身份归属展示与“是否同一个人”的判断经过规范身份解析；权限仍按当前认证主体和资源授权检查，不能借显示层合并转移权限。
5. 记录绑定、登录、授权、加入同意、撤销和管理接管的审计。

旧消息的 `from` 已被 ObjectId 和签名固定，迁移不改写历史。更换身份域或用户取得自主控制的 DID 时，应由有资格的双方确认身份承接；资源方独立决定是否转移权限。Contact Mgr 的 `resolve_canonical_did` 可供展示层复用，但 owner 私有的联系人合并不是全系统认可的登录或授权证明。

本场景的会话数据以 host 为真相源，访客没有自己的 Zone 副本。被移出或 Session 被删除后，不能再依靠旧 token 访问；需要留存记录时，应在有权限期间提供导出。身份域、账号绑定、授权来源、会话状态与审计需纳入系统备份；恢复备份不能复活已撤销的登录或权限。

## 9. 撤销与全系统安全要求

### 9.1 生命周期必须闭合

| 变化 | 必须产生的效果 |
| --- | --- |
| guest 被停用、删除或系统封禁 | 拒绝新登录、刷新及已有会话的后续受保护请求 |
| 身份绑定被接管、迁移或 guest 升级为普通用户 | 重新确认登录授权；旧 guest 会话不能自动获得新身份或普通用户的权限 |
| App / 身份域被停用，或代登录权被撤销 | 拒绝该来源的新兑换与刷新，撤销依赖该来源的已有会话；其它独立来源按各自策略处理 |
| 某条资源授权或其转授依据被撤销 / 到期 | 依赖该授权的访问失效；不能借已签发 token 固化旧权限；独立有效授权按其范围继续判断 |
| guest 被移出某 Session、群内封禁或 Session 被删除 | 该资源的访问立即按最新成员状态拒绝，不因此注销其它无关资源的会话 |
| 用户退出或单设备会话被撤销 | 对应 session / refresh 链失效，其他设备按明确策略处理 |

撤销完成后，下一次受保护请求必须生效；流式连接和事件订阅也要停止无权读取的后续数据。JWT 验签成功和 `exp` 未过期不能代替状态检查。缓存、策略更新、刷新链和已有连接如何失效，必须在开放 guest 登录前实现；不能只承诺等 token 自然过期。

### 9.2 全入口默认拒绝

- 所有系统服务均须检查用户类型、当前授权与资源范围；“非 User”“内部调用”“本地请求”“对象属于本人”等既有快捷分支必须显式限定适用条件。
- guest 使用 `principal_kind=user`，也不能因此获得现有普通用户分支中隐含的邮箱、Agent 观察或个人数据权限。
- RPC、HTTP、对象下载、上传、事件订阅、代理转发和批量接口不得存在绕过；未声明支持 guest 的受保护操作默认拒绝。
- 系统授权设施不可用或状态无法确认时，受保护的 guest 请求拒绝，不能回退到旧权限或更高权限身份。
- App 凭证、session / refresh token 和密码不得写入日志；链接兑换、绑定与授权变更需要审计，但不保存凭证明文。
- 身份创建、兑换、加入和发消息按身份源、账号及来源等适当维度限制频率和配额，避免用批量 guest 绕过资源限制。

## 10. 当前差距与实施门槛

以下入口按本次工作区核对，仅描述需要改造的位置，不表示本文方案已经落地：

- `buckyos-api/src/app_availability.rs` 的 `user_is_active` 明确排除 `UserType::Guest`；verify-hub 尚无 `login_by_app_access_token`。需区分“guest 可通过获准方式登录”与“匿名入口公开”，同时覆盖刷新和 App availability。
- 标准 token 已有 `principal_kind=user` 与结构化 AuthTarget；应扩展这套会话体系。`runtime.enforce` 使用 target 的 `authorization_key`，其中 App 授权键按 AppId 构造；身份域管理、代登录和实例范围的授权不能因此丢失 AppInstance / owner 隔离。
- msg-center 的 `caller_identity` 会为 User 解析 DID，当前依赖用户 profile；标准 guest 必须可由同一可信身份层解析。无 token 且无来源 IP 的内部调用分支不能被网络请求触发。
- `owner_session.rs` 的邮箱授权存在非 User 放行和 User 可观察本 Zone Agent 的逻辑；必须连同 RBAC 检查 guest 的实际权限，不能仅改变 token 类型。
- 群 RPC、群 HTTP 与对象读取已有资源判定，但不能假定每条路径都执行了完整的 RBAC / 会话范围检查；`contact.*`、task-manager、control-panel、system-config、文件服务和事件入口同样需要检查。

实施按以下依赖组织，**第 1、2 项完成并验证前不得开放第 3 项签发可用的 guest 会话**：

1. **定完整模型**：确定身份域与 DID、guest 用户语义、创建与转授规则、实例隔离、token 来源与 scope、权限真相源、撤销及缓存一致性。先明确所有信任边界，再实现接口。
2. **建立默认拒绝并检查全系统**：列出全部受保护入口，记录每项的认证、RBAC、资源判定与撤销机制；不支持的操作明确拒绝 guest，消除隐含放行和旁路。
3. **实现统一登录与生命周期**：身份绑定、App 凭证验证、`login_by_app_access_token`、标准 session / refresh、退出、停用和恢复流程。
4. **开放 Session 最小能力**：资源方显式授予邀请接受、咨询申请与会话访问；Message Hub 接入统一登录及群存储；贯通 §11 的验证。
5. **后续增加业务能力**：上传、导出、更多系统服务和身份迁移界面，均在已建立的模型内增加授权，不再增设临时凭据或放行例外。

未完成全面检查的系统不能因“暂时只给 msg-center 使用”而提前签发标准 guest token。权限模型必须先闭合，功能范围才可以逐项扩大。

## 11. 验收与文档联动

### 11.1 必须覆盖的验证

| 范围 | 验证要点 |
| --- | --- |
| 身份与兑换 | 重试 / 并发映射到同一 DID；合法绑定复用；跨域冒认、普通用户 / 管理员冒认、凭证篡改、过期、错误用途与重放均失败 |
| 实例与目标隔离 | 同 AppId 不同 owner 不能互管；App service token 不能兑换成客户；未授权 target、伪造 owner 和切换高权限系统 target 均失败 |
| 零权限基线 | 新 guest 即使登录成功也不能访问邮箱、通讯录、系统配置、任务、文件或任意群；不能依靠普通 User 分支、sudo 或 owner 替换提权 |
| 授权交集 | App 无权、guest 无权、scope 不含资源或资源方拒绝时都失败；已有读取权不能冒充转授权；后加权限不能越过旧会话 scope |
| Session | 加入前只能看获准邀请信息；加入后只能读写对应 Session；历史区间、`from`、对象引用、Hook、封禁和咨询上限均生效 |
| 全入口一致 | 同一资源经 RPC、HTTP、对象、事件、代理或批量访问结论一致；不存在身份解析失败后放行 |
| 撤销与刷新 | 持有旧 token、命中缓存或保留事件连接时，停用、移除、授权撤销与退出仍生效；刷新不恢复已失效权限；绑定迁移或用户升级不使旧会话提权 |
| 页面 | bootstrap 可达；目标及 origin 校验正确；不混用已有管理员登录态；换设备后身份和历史连续 |

### 11.2 文档联动

实现时应同步 SSO 使用者指南、UserType、RBAC 设计、verify-hub / SDK 协议，以及 Message Hub 和群应用接入说明。SSO 与 UserType 现有“guest 即匿名且不可登录”的表述需要调整；普通用户与匿名访问的行为也要回归验证。

v2 的 Session Guest 角色、成员状态机和双方同意规则保持不变，补充标准 guest 登录的入口说明即可。Message Tunnel 无需为此增加身份型实例。本次修订只更新本设计，相关文档当前仍描述各自的现有实现。

## 12. 实施前需落定的细节

以下是统一模型内的协议与产品参数，不能用于重新引入 msg-center 私有认证方案：

| 问题 | 约束 / 方向 |
| --- | --- |
| guest DID 命名和身份域存储 | 纳入系统身份规范；稳定、不可复用、不含隐私原文；首次写入消息前确定 |
| App access token 验证协议 | 统一选择登记公钥验签或受信服务端校验；明确兑换用途、受众、失效、一次性链接及幂等规则 |
| 登录接口与会话 scope 表达 | 沿用标准 AuthTarget、TokenPair / 用户信息契约；来源和范围可验证、可撤销，全部消费者都执行 |
| guest 创建、绑定与转授权 API | 系统统一提供；分离管理、认证、资源使用和转授能力，明确实例与资源路径粒度 |
| 默认有效期和多设备策略 | 登录链接短时且一次性；session / refresh 沿用系统生命周期，刷新受来源、状态和范围约束 |
| 单 Session 或多个历史工单 | 默认只授予业务实际需要的范围；查看本人其它工单需对应授权，不能因登录同一 App 就自动获得 |
| 没有外部账号的访客 | 可由获准 App 建立随机稳定账号，再走同一 guest 登录流程；后续验证联系方式追加绑定，不改 DID；恢复绑定前丢失凭据可能无法找回 |
| 迁移格式和产品入口 | 系统 SSO 统一设计，身份承接与权限转移分别确认；§8 的基础约束首发落实 |

前四项及 §9 的撤销机制属于开放登录前必须完成的协议工作。后续可以增加业务授权与产品入口，不能推迟默认拒绝、完整鉴权和撤销语义。
