# BuckyOS Self-host Group 的应用扩展架构设计

**文档状态：** 架构设计稿  
**整理日期：** 2026-10-01  
**设计依据：** 本轮关于 Message Center、Self-host Group 及应用扩展的语音讨论  
**目标读者：** BuckyOS 系统架构与内核开发者、Message Hub 开发者、群聊应用开发者

> 本文确立架构边界与扩展模型，不定义最终 API、配置字段或线协议。语音中描述的现有基础能力按设计背景记录，不代表已经逐项验证实现；Hook 机制、多副本及相关可靠性能力仍包含规划内容。文中的“实现建议”和“待明确事项”用于后续设计，不应视为已经实现的平台承诺。

## 一、设计目标与核心结论

BuckyOS 希望提供一个去中心化、可自行部署的消息基础设施，使应用可以在稳定的消息内核之上构建自己的业务群，而不必为了增加业务逻辑重新实现消息存储、会话、成员管理和可靠性机制。

群聊功能本身容易发展成复杂的独立产品。因此，Message Center 的重点不是在内核中覆盖所有业务场景，而是设计**最小协议集及支持该协议的最小默认实现**，再通过不同深度的扩展能力承接应用需求。

本架构的核心结论是：

1. **Group 是一个独立的 DID 对象。** 标准群不是成员之间的简单群发，而是由群服务管理会话、消息、成员和访问规则。
2. **消息服务与默认聊天界面分离。** Message Center 提供消息与群服务；Message Hub 是系统默认聊天界面，应用不必使用它。
3. **扩展分为四种深度，并且可以组合。** 从配置生成、应用侧面板，到 Hook 逻辑和完全自定义应用；第四层进一步包含复用消息内核与独立实现协议两种形态。
4. **扩展越深入，应用承担的运行责任越大。** 侧面板故障不应影响基础聊天；Hook 故障则可能影响群的关键操作；独立协议实现自行承担服务可靠性。
5. **稳定服务接口与开源 UI 代码采用不同兼容承诺。** Message Center 的对外接口和群配置强调长期向下兼容；Message Hub 组件提供源码复用，不承担同等级别的跨版本兼容负担。

### 1.1 范围

本文覆盖标准 Self-host Group 的基础模型、四层扩展方式、扩展组合、故障隔离、安全边界、兼容责任及后续实现需要明确的问题。

本文不展开完整 IM 产品功能清单，不选择前端框架、存储引擎或复制算法，也不把具体 Hook 名称、配置语法和授权凭据形式提前固化。

### 1.2 开放原则

应用可以使用默认界面、复用 UI 源码、自行编写界面，甚至替换整个消息服务实现。平台不以维护商业入口或强制使用 Message Hub 为设计目标。

开放源码不等于所有内部实现都成为稳定接口。哪些能力属于平台契约，哪些只是可复制和修改的实现代码，必须明确区分。

## 二、基础架构与群消息模型

### 2.1 术语与职责

| 术语 | 本文含义 |
| --- | --- |
| BuckyOS | 承载 Message Center、Message Hub 及相关应用的系统环境。 |
| Message Center | 消息服务侧，提供消息、会话及默认群服务等能力，不等同于聊天 UI。 |
| Message Hub | 系统默认聊天界面，使用 Message Center 的服务能力展示和操作消息。 |
| Self-host Group Service | Message Center 自带的群服务默认实现；负责标准群的配置、成员、会话、消息和相关状态处理。 |
| Group DID | 群本身的标识，也是群消息的目标地址；不同于群主个人 DID。 |
| Group Owner / 管理员 | 群的所有者及被授予管理权限的角色。群主控制群的部署与配置，管理员的能力由授权决定。 |
| Session / Inbox | 群按 Session 组织消息；每个 Session 对应可按权限访问的 Inbox。 |
| Group Configuration | 默认群服务可识别的配置，描述群行为和界面内容，并承载相关扩展声明。 |
| Application Service | 提供业务数据、侧面板功能或 Hook 响应的应用服务。 |
| Owner OOD | 群主控制的部署环境，是本轮设计中群服务和同源应用面板的默认承载位置。 |

本文统一使用 Message Center 和 Message Hub，不沿用语音转写中混用的 Message Sender 等称呼。底层对象协议的正式名称及版本不在本文重新定义。

### 2.2 去中心化 IM 与标准群的区别

整体消息模型借鉴 Email 的 Inbox / Outbox 思路，实现去中心化的点对点消息传递。

协议可以支持一种地位平等、没有群主的多人群发会话。语音中将其称为 `mutual user session`，本质上是点对点消息协议的群发应用，正式术语待统一。

本文讨论的标准群不是这种群发会话。标准群需要有明确的创建者、群主和管理员，需要管理成员，并由群配置决定加入流程、可见会话、消息读取范围与发言权限。

因此，标准群被抽象为一个独立 Group DID，其背后有负责执行群规则的 Group Service。

### 2.3 Session 与 Inbox

从用户的消息视图看，订阅群后会出现以 Group DID 组织的群消息入口。群内再按 Session 组织 Inbox。

概念关系如下，具体存储布局不在本稿限定：

```text
Group DID
  ├─ 群配置与成员状态
  └─ Session 集合
       ├─ Session A → Inbox A
       ├─ Session B → Inbox B
       └─ Session C → Inbox C

成员 → 查询自己有权访问的 Session List
成员 → 从指定 Session 的 Inbox 拉取有权读取的消息
成员 → 向指定 Session 的 Inbox 提交消息，由群服务判断是否接受
```

用户自己的收件视图不等于群的完整数据副本。成员能看到哪些 Session、读到哪些消息，由群配置和相应授权逻辑决定。

消息写入成功后，其他订阅该 Session Inbox 且具备相应读取权限的成员可以拉取该消息。订阅关系本身不表示拥有对全部消息的读取权限。

### 2.4 消息地址语义

点对点消息和群消息复用底层寻址与消息机制，但接收者语义不同。

| 场景 | 发送者字段：`from` / `sender` | 接收者字段：`to` |
| --- | --- | --- |
| 用户 A 向用户 B 发送点对点消息 | 用户 A | 用户 B |
| 用户 A 读取用户 B 发给自己的点对点消息 | 用户 B | 用户 A |
| 用户 A 向群 G 发送消息 | 用户 A | 群 G 的 DID |
| 用户 B 从群 G 拉取用户 A 的消息 | 用户 A | 仍为群 G 的 DID |

**群消息的 `to` 始终是群，不因读取者不同而改写成读取者本人；消息发送者仍是实际发送成员。** 上表用于说明语义，不确定最终字段命名。

群服务是消息承载与规则执行方，不因此自动变成每一条成员消息的作者。

### 2.5 网络去中心化与群内集中管理

对于某一个群的成员，Group Service 是该群的逻辑中心。去中心化并不要求群内所有成员完全平等地共同控制群，而是将这一中心的控制权放在群主所管理的 Group 上，而不是放在全局消息平台上。

在当前设计中，群主掌握群消息和配置的完整视图；普通成员只获得授权范围内的视图。管理员是否拥有完整数据访问能力取决于管理授权，不应仅凭管理员称谓自动推定。

这一模型同时支持明确的责任归属：群主决定使用默认服务还是自定义实现，以及将多少群行为交给应用逻辑。

## 三、四层扩展总览

四层表示扩展深度与责任边界，不是必须依次完成的开发阶段，也不是只能选择一项的互斥模式。

| 层级 | 扩展方式 | 默认群服务 | 应用的主要工作 | 应用故障的主要影响 |
| --- | --- | --- | --- | --- |
| L1 | 配置型扩展 | 使用 | 创建群并生成、写入配置 | 初始化完成后，配置生成器退出不影响群运行。 |
| L2 | 嵌入式应用侧面板 | 使用 | 提供 HTML 面板和必要业务功能 | 面板及其业务功能不可用，基础聊天不受影响。 |
| L3 | Hook / Process Chain 逻辑扩展 | 使用，且深度绑定其扩展机制 | 在群关键操作中参与业务决策 | 由 Hook 故障策略决定，可能影响加入、收发消息等。 |
| L4A | 完整自定义 UI | 使用 | 在独立应用界面中整合群聊，可复用 UI 源码 | 自定义界面可能不可用；群服务及其他入口是否可用取决于附加的 Hook 和访问策略。 |
| L4B | 独立协议实现 | 不要求使用 | 自行实现兼容服务和客户端 | 可靠性与恢复由该实现负责，不继承默认服务保障。 |

其中，L4A 和 L4B 是第四层的两种形态：前者替换表现层，后者可以替换整个实现。

典型组合如下：

- **L1 + L2：** 业务群模板加应用侧面板，消息内核不依赖业务服务。
- **L1 + L2 + L3：** 同时定制群配置、业务界面和运行逻辑，是深度嵌入 Message Hub 的常见形态。
- **L1 + L4A，按需叠加 L3：** 自定义应用界面使用消息内核；不再需要通过 Message Hub 的侧面板承载主界面。

L3 并不强制依赖 L2；L4A 也不强制要求 L3。只有需要改变群运行规则时，才需要引入对应逻辑扩展。

## 四、第一层：配置型扩展

### 4.1 机制

应用使用 Message Center 自带的 Self-host Group Service 创建群，然后生成并写入符合业务场景的 Group Configuration。

默认群服务承担标准行为的执行，包括成员加入相关状态处理、权限控制、会话组织及配置驱动的界面内容。应用不编写独立的群运行内核。

```text
配置脚本 / 初始化程序
        │
        ├─ 创建标准 Group
        ├─ 生成业务配置
        └─ 写入配置并完成初始化
                    │
                    ▼
          默认 Group Service 持续运行
                    │
          配置生成器可以退出
```

因此，最轻量的“群应用”可以只是一段配置脚本，而不必是常驻服务。

### 4.2 配置内容与配置界面分离

Group Configuration 不只是简单开关，也可以描述具有关联关系的群行为和展示内容，例如加入规则、成员相关设置、群或 Session 公告，以及侧面板中的固定链接、常用文件和特定成员展示。

这些配置不要求全部出现在通用设置 UI 中。默认设置面板可以只覆盖常用项目；复杂或低频组合可以通过配置接口由应用完成。

默认情况下，管理员可以看到群控制面板，普通成员侧则以标准成员信息、公告等基础内容为主。更丰富的内容由配置拼装。

应区分两种能力：

| 能力 | L1 的处理方式 |
| --- | --- |
| 在标准侧面板展示链接、文件、指定成员等 | 使用内置支持的配置项，由默认界面渲染。 |
| 提供任意业务交互和自定义页面 | 不依靠配置无限扩展标准控件，而交给 L2 或 L4A。 |

这种边界可以避免把“配置能力丰富”演变成“在内核内实现所有业务 UI”。

### 4.3 示例：一键创建客服群

企业应用可以提供固定的客服群模板：侧面板包含两个固定链接、两份常用文件，并展示两位具有官方身份的群成员；同时配置相应的公告与加入规则。

应用根据业务参数生成配置并完成群初始化，管理员不需要在多级菜单中逐项设置所有关联项目。

此例中的应用是配置生成器，不是群运行时必需的服务。若配置中引用外部链接或文件，资源本身的可用性另行承担，不因此把基础聊天变成对配置生成器的运行时依赖。

### 4.4 兼容承诺

这一层成立的关键前提是：**Group Configuration 是需要认真维护的对外平台契约。**

Message Center 升级时，应支持既有应用生成的有效配置继续工作。配置可增加能力，但不能随意改变原有语义，使旧业务群在升级后出现非预期变化。

具体的版本声明、废弃流程、默认值变化规则及迁移策略需要在配置规范中细化。本文不预设最终字段名称或版本窗口。

## 五、第二层：嵌入式应用侧面板

### 5.1 机制与职责

L2 仍以系统默认群为基础，但允许配置一个应用提供的 HTML 页面链接，由 Message Hub 在群运行过程中加载为应用侧面板。

职责分配是：Message Center 提供群配置和消息服务，Message Hub 承担默认界面及面板加载，应用提供面板内容与业务逻辑。不能把界面嵌入能力与消息内核混为一体。

```text
Message Hub
  ├─ 标准群聊界面 ───────────────→ Message Center
  └─ 应用侧面板 ─→ 应用页面 / 业务服务 ─→ Message Center

基础聊天不以“应用页面或业务服务成功运行”为前提。
```

面板页面和必要业务接口需要在运行期可访问；本稿不规定每个面板都必须拥有一个独立常驻后端进程，也不预先固定具体嵌入技术。

### 5.2 上下文传递

Message Hub 按标准调用约定向面板传递上下文。当前已经明确的核心内容是 **Group ID / DID 与 Session ID**。

面板根据上下文访问 Message Center，读取或操作被授权的信息。上下文参数只是识别当前群和会话，不等于自动授予权限。

嵌入协议及配套配置描述需要进一步约定页面入口、参数传递、上下文变化和加载失败行为。语音中提到的 YAML 要求属于待细化的配置描述范围，不代表已有确定的 manifest 格式。

当前用户身份、服务入口等是否作为参数传递，以及采用何种可信机制，应在接口设计阶段另行明确，不能把它们写成已经确定的字段。

### 5.3 示例：游戏公会群

公会应用维护“群成员身份与游戏账号 ID 的映射”，并在侧面板中按业务需要展示成员在游戏中的职务、积分和排行榜。

这些内容由应用掌握，不必塞入 Message Center 的通用成员模型。用户仍在 Message Hub 中聊天，但可以通过侧面板查看公会业务信息。

### 5.4 单向依赖与故障隔离

L2 的关键约束是：**业务能力可以依赖消息服务，消息服务的基础聊天不能依赖该业务能力。**

面板服务崩溃时，面板可以不显示或显示不可用状态；群、会话及基础消息沟通仍应保留。公会成员应当能够继续在原群中讨论“如何修复公会面板”，而不是连讨论渠道一起失去。

这里的“不影响聊天”是相对于应用侧面板自身故障而言，并不意味着群服务所在机器、网络或 Message Center 自身故障也不会影响聊天。

若同一个应用还启用了 L3，Hook 故障仍可能影响群操作。不能仅因为一个应用有侧面板，就将整个应用的故障边界都归为 L2。

### 5.5 默认部署与访问边界

应用侧面板默认部署在群主 OOD 上，并满足与该群可信服务来源一致的同源要求。不同来源的面板默认不加载；用户显式接受相应安全策略后，才允许例外。

这是平台需要实施的面板加载策略，不应假定只要使用网页嵌入，所有策略就会自动成立。详细边界见第九章。

## 六、第三层：Hook / Process Chain 逻辑扩展

### 6.1 定位与规划状态

L3 是在默认 Self-host Group Service 中提供 Hook 的规划方向。应用业务逻辑开始参与群的实际运行，而不只是改变配置和页面。

这一层与 BuckyOS 自己的 Message Center 默认群服务深度绑定，不是仅实现通用消息协议即可获得的能力。开发者需要理解群的处理流程、状态和扩展契约。

继续复用默认群内核的原因是：稳定的消息服务不仅需要收发消息，还涉及数据可靠性，以及后续考虑的多副本、群核心数据导入导出和完整备份等能力。应用可以复用这套基础设施，将精力放在业务判断上，而不必重新实现全部内核。

这些可靠性能力包含后续规划，不应据此宣称当前内核已经完整实现所有机制。

### 6.2 业务介入点

典型需求包括：加入群之前先完成应用注册或验证；达到某个游戏等级后才可以发言；读取消息时按业务规则检查是否具备访问条件。

这些需求要求应用在运行时参与决策，仅生成静态配置不足以覆盖。

处理方式类似此前 Gateway 的 Process Chain：配置和受控脚本决定处理路径，流程可以路由到应用服务，再根据应用返回继续处理。

```text
加入 / Post / Pull 等请求
          │
          ▼
默认 Group Service 的处理流程
          │
          ├─ 内置检查与状态处理
          ├─ 已配置的 Process Chain / Hook
          │       └─ 调用 Application Service
          │              └─ 返回业务判断或处理结果
          └─ 按正常结果或故障策略继续执行
```

上图仅表示依赖关系，不规定 Hook 与各项内置检查的确切顺序。具体扩展点、返回值、数据修改权限及执行顺序需要单独设计。

与 L2 不同，L3 会形成真实的关键路径依赖：**Group Runtime 可能需要等待 Application Service 的返回，才能决定是否继续操作。**

### 6.3 与 L1 的组合方式

典型部署方式是：先启动应用服务，由应用提供创建脚本，再通过该脚本创建标准群并配置相应 Hook 点。

L1 负责群的声明与初始化，L3 负责运行时业务逻辑。因此，L3 通常与 L1 配合使用，而不是让用户逐项手工安装 Hook。

需要业务界面时，可以继续组合 L2；使用自定义完整界面时，可以组合 L4A。这些能力不是互斥选项。

### 6.4 故障策略决定群的可用性

应用服务不可用后，群是否能够继续工作，取决于所配置的 Hook 和默认行为。

平台开发指南应鼓励：**应用故障时尽量保留现有群的基础沟通能力，但不以放宽访问控制为代价。** 这是一项推荐，而不是要求所有业务场景采用相同的放行规则。

| Hook 场景 | 建议的故障行为 | 预期边界 |
| --- | --- | --- |
| 新成员加入需要应用验证 | 无法验证时暂停或拒绝新成员加入。 | 不把加入失败扩散成现有成员无法聊天。 |
| 发言需要应用动态放行 | 动态授权无法确认时不继续放行；按已配置的原生权限处理。 | 原本独立具备发言权限的人能否继续发言，仍取决于其余处理链是否允许。 |
| 读取需要业务权限判断 | 未能确认的额外读取权限不应自动开放。 | 不以维持可用性为由扩大消息可见范围。 |
| 所有 Post / Pull 都强依赖应用 | 无可用替代处理时相应操作失败。 | 可能导致整个群无法沟通，开发者须明确接受这一风险。 |

“每个 Hook 有默认行为”不自动等于“群一定能正常聊天”。默认拒绝虽然是明确行为，也可能阻止关键操作；需要按群的完整处理链评估结果。

### 6.5 原生权限与动态许可的区别

语音中的发言场景是：部分成员在原生配置中没有发言权限，应用依据业务规则为其放行。当应用失效时，无法继续确认这些动态许可，只有不依赖该动态许可、且满足其他规则的成员可以继续发言。

这不应被写成“应用崩溃会自动撤销所有已经持久化的权限”。如果应用此前修改并保存了原生权限，是否回收以及何时回收，需要另一套明确规则。

因此，后续实现必须区分**单次请求的动态许可**与**持久化权限变更**。本文不将二者合并，也不预设系统已经实现动态许可机制。

### 6.6 实现建议：区分业务拒绝与服务故障

Hook 的正常拒绝、超时和服务不可用应有可区分的语义。应用明确拒绝一个请求，不应仅因为配置了故障回退就被当作“服务故障”而放行。

超时边界、重试与幂等、默认行为、错误提示和可观测性需要在 Hook 规范中明确。这些是后续接口设计事项，不是本文新增的一组已存在配置字段。

平台可以鼓励故障降级，但不强制消除业务服务的所有关键路径依赖。选择 L3 的开发者和群主应能够理解并判断这种依赖。

## 七、第四层 A：自定义完整 UI，复用 Message Center

### 7.1 应用接管产品界面

L4A 应用在自己的页面内嵌入群聊功能，不使用 Message Hub 的完整默认界面。消息、会话及群服务仍由 Message Center 提供。

```text
自定义业务应用 UI ───────→ Message Center / 默认 Group Service
         │                            │
         └─ 应用业务服务 ←─ 可选 Hook ─┘

Message Hub：不是该应用必须采用的入口。
```

这种应用通常仍会利用 L1 完成群初始化，需要改变运行逻辑时再使用 L3。由于主界面已经完全自定义，通常不需要 L2 的 Message Hub 侧面板承载模式。

产品方向上，这是一类重要的业务应用形态：应用拥有自己的完整产品体验，同时复用消息内核。语音中对其可能成为多数应用选择的判断属于产品预期，不是本稿已经验证的使用比例。

### 7.2 限定应用访问入口

部分应用不希望用户从通用 Message Hub 直接进入业务群，而希望用户通过自己的界面和业务流程读取消息。架构上，可以结合群配置及 L3 在消息访问路径上实施相应限制。

这里需要明确一个安全语义：**“只有本应用 UI 可读”应落实为受认可的应用访问路径、业务会话及授权条件，而不能只理解为识别一个页面外观或隐藏 Message Hub 的入口。**

具体采用何种身份绑定、凭据或业务校验尚待设计。仅携带 Group ID、Session ID 或页面地址不应自动构成授权依据；也不应把“使用了自定义 UI”直接等同于已经实现安全隔离。

如果群明确限制通用客户端访问，那么 Message Hub 能否读取它由群策略决定。自定义 UI 服务失效时，不能保证用户仍可从 Message Hub 进入，除非预先提供并授权了这样的备用路径。

### 7.3 Message Hub UI 组件开放

应用不必从零编写全部交互界面。BuckyOS 将开放 Message Hub 自身可复用的 UI 组件源码，允许应用选取某个版本使用、复制或修改。具体组件清单与封装方式另行确定。

这种开放属于**源码级复用**，而不是把所有 UI 组件承诺为长期稳定的平台控件接口。

| 复用对象 | 兼容性定位 | 应用开发者责任 |
| --- | --- | --- |
| Message Center 对外服务接口 | 强调长期向下兼容的平台接口。 | 遵守公开契约及后续明确的版本策略。 |
| Message Hub 某一版本的组件源码 | 开源实现代码，不提供同等级别兼容承诺。 | 自行集成、修改、测试，并决定何时同步新版本。 |
| 系统当前运行版本的共享 UI 组件 | 不是本架构保证的跨应用稳定依赖。 | 若主动采用，需自行承担系统更新带来的适配责任。 |

当应用复制了某一版组件后，系统 Message Hub 的升级不会自动将这些源码更新到应用中。反过来，应用保持旧源码也不要求系统长期保留对应的内部 UI 行为。

不排斥开发者探索运行时组件复用，但当前不把它纳入平台兼容保证。平台需要保留默认 UI 的演进空间，不因第三方深度依赖内部控件而背负无限扩大的兼容负担。

**边界总结：服务接口稳定，UI 源码开放，UI 升级由使用方主动同步。**

## 八、第四层 B：独立实现底层协议

### 8.1 可以替换整个实现

L4B 不要求应用使用 Message Center，也不要求服务运行在 BuckyOS 上。开发者可以独立实现群服务、数据存储、权限、消息处理和客户端，只保留与底层 DID / 对象消息协议的兼容关系。

此时，扩展已经超出“在默认群内核上开发应用”的范畴，转为协议级互操作。协议是共同边界，而不是某个服务进程、前端组件或部署环境。

底层 CYFS 对象体系以及 DID Post Object Protocol 等名称、版本和具体关系，应与对应正式协议文档统一。本文不沿用语音转写中不确定的对象术语来新增协议定义。

### 8.2 互操作示例

以一家现有聊天产品为假设：如果它实现兼容的群消息协议，提供一个 Group DID，并允许标准协议客户端访问，则其自有客户端和 BuckyOS Message Hub 可以访问同一群服务。

```text
第三方自有客户端 ──────┐
                      ├──→ 第三方自行实现的兼容 Group Service
BuckyOS Message Hub ──┘                 │
                                      └─ 同一个 Group DID
```

语音中使用 Discord 作为这种可能性的示例，**不表示 Discord 当前已经支持、集成或计划采用该协议**。

双方不需要共享 UI 或后端实现。能否互通取决于实际支持的协议能力、寻址和连接条件，以及群的访问授权。

协议兼容也不等于所有客户端都能渲染任意业务 UI。通用 Message Hub 对业务扩展内容能展示到什么程度，需要相应消息类型与扩展规则支持；不能只凭基本消息兼容就承诺完整产品体验等价。

### 8.3 自由度与责任

独立实现可以自行定义内部数据模型、运行架构和客户端体验，但不继承默认 Self-host Group Service 的存储、备份、多副本及 Hook 实现。

实现者需要自行保证其声明支持的协议行为，并承担数据可靠性、成员权限、服务可用性及升级维护责任。

这是自由度最大的扩展形态，也是默认实现提供的便利最少的一层。协议开放不意味着独立实现仍会自动获得 Message Center 内核服务。

## 九、安全与信任边界

### 9.1 区分身份、部署来源与访问权限

架构中需要分开处理三类信息：Group DID 标识群；Owner DID 标识群主；面板与服务的来源表示内容实际由哪里提供。这三者有关联，但不能混为同一个标识。

与此同时，知道 Group DID 或知道群主是谁，并不等于具有读取群消息、修改群配置或执行管理操作的权限。

本文只确认这些边界，具体身份验证、可信解析及授权机制沿用或衔接系统安全体系，另行明确接口。

### 9.2 侧面板默认同源策略

本轮确定的默认规则是：应用侧面板应位于群主 OOD，并满足与群可信服务来源一致的同源要求。

判断基准是**该群对应的可信来源**，而不是任意读取者自己部署 Message Hub 的来源。一个用户可以从自己的 Message Hub 访问由另一群主托管的群，面板的信任基准仍应随群确定。

后续实现需要同时回答两个问题：页面是否位于预期群主控制的部署环境，以及页面是否满足具体的 origin 策略。同一 OOD 的部署归属与浏览器 origin 的匹配不能仅靠名称关联代替校验。

具体 origin 定义、OOD 与域名的绑定、代理与跳转的处理，以及嵌入技术配套的浏览器限制，需要在安全规范中细化。本稿不把“配置了 URL”当作完成了安全验证。

### 9.3 跨来源例外必须显式接受

当面板来自另一来源时，默认禁止加载。用户可以通过显式接受相应安全策略开启例外。

策略应让用户能够判断将加载哪一方提供的内容，以及会向其提供哪些群上下文。授权范围、有效期、撤销方式和来源变更后的重新确认属于后续设计事项。

群主配置了外部面板，不等于用户已经接受向该外部应用暴露自己的群上下文。

### 9.4 加载许可不等于消息授权

允许面板加载，与允许它读取或修改群数据是两件事。同源面板也不应因此获得群主权限；跨来源面板即使获得加载许可，也仍需满足数据接口的访问控制。

Group ID、Session ID 等上下文用于定位资源。实际操作必须由相应用户或被授权主体发起，并受其权限约束。

**实现建议：** 在扩展协议中明确哪些上下文可公开传递、哪些属于受保护的身份或凭据，不把配置字符串或 URL 参数直接当作权限来源。

### 9.5 Hook 与权限的安全语义

L3 允许业务逻辑参与授权，因此必须明确原生权限、动态许可和持久化权限变更之间的关系。权限优先级、哪些限制不可被 Hook 覆盖、Hook 运行主体及其可访问数据，仍需专门定义。

故障策略可以选择拒绝、降级或退回已有规则，但不应把“未知”默认变成不受约束的放行。对于有意采用强依赖业务规则的群，拒绝服务可能是其选择的安全边界，即使这会降低可用性。

侧面板中展示“官方成员”等身份信息，与授予管理员或消息读取权限也应分开。展示配置本身不是隐含的授权指令，除非配置规范明确包含对应权限操作。

## 十、兼容性、升级与数据可靠性

### 10.1 不同边界采用不同兼容责任

| 边界 | 本文的兼容定位 | 不应误解为 |
| --- | --- | --- |
| 底层 DID / 对象消息协议 | 独立实现互操作的共同契约，具体规则由正式协议规范确定。 | 只要能发送普通消息，就一定实现了全部群与业务语义。 |
| Message Center 公开服务 API | 为应用提供长期向下兼容的服务基础。 | 所有内部接口、实现细节都保持不变。 |
| Group Configuration | 认真维护旧配置的有效性与既有语义。 | 可以不定义版本、默认值变化及迁移规则。 |
| Group Hook / Process Chain | 默认群实现的深度扩展契约，尚需专门明确版本与行为。 | 与协议一样无实现耦合，或已经具备无限期不变的接口。 |
| 面板嵌入约定 | 需要明确参数、生命周期与安全规则的对外扩展边界。 | 任意 HTML 页面和参数组合天然兼容。 |
| Message Hub UI 组件 | 开源源码级复用，升级由应用选择和集成。 | 系统提供跨应用、跨版本的稳定共享控件运行时。 |

兼容性必须覆盖行为语义，而不只是“配置文件仍可解析”或“接口仍能调用”。例如旧群的消息可见范围和 Hook 故障行为，不能在升级后悄然发生变化。

具体兼容期限、版本协商和废弃机制未在本轮确定，需要后续形成接口级规范。

### 10.2 同一 Group 的多副本方向

后续的重要升级方向是让一个逻辑 Group 由多个 Self-host Group Service 实例承载，通过主从或其他小规模多副本方式实现完整数据备份及相应可靠性目标。

本文将语音中“多个群组、例如不超过五个”的讨论按**同一 Group 的多个服务副本**理解，不是创建若干无关群后拼接消息。该数量是讨论中的规模示例，尚不是协议或部署层面的硬性上限。

语音中提到类似 etcd 的多副本模式作为参考方向，但未选择具体复制或一致性算法。当前原则是保留明确群主与管理关系，不为了形式上的平等而引入无主的成员共识；这不意味着复制、冲突或故障切换可以不定义规则。

### 10.3 完整备份不能依赖普通成员视图拼接

普通成员可能只能看到部分 Session 或部分消息，因此各成员的本地消息记录不能自动视为群的完整备份，尤其不能替代群配置和权限状态的保存。

完整备份与恢复应面向获得相应权限的群服务数据，而不是假定任意成员都掌握全貌。

**实现建议：** 后续明确核心恢复数据的范围，至少讨论群配置、成员与权限状态、Session 及消息数据；同时明确快照一致性、恢复授权与凭据处理。多成员参与自动备份的方案还需独立定义备份授权，不等于默认给成员开放所有消息。

### 10.4 群内核数据与业务数据分别负责

默认群服务负责哪些数据，应用负责哪些数据，应在扩展设计时划清边界。

| 数据或资源 | 默认责任归属 |
| --- | --- |
| 标准群配置、群会话和群消息等内核数据 | 默认 Group Service 及其备份恢复机制。 |
| 游戏账号映射、积分、排行榜等业务数据 | 对应 Application Service。 |
| 自定义页面及被复制的 UI 组件源码 | 应用自身的代码与部署管理。 |
| 独立协议实现的全部群服务数据 | 该实现自行负责。 |

群服务的多副本不自动覆盖应用数据库。恢复了群消息，也不等于恢复了所有应用业务状态。Hook 配置被恢复后，对应应用服务是否存在、入口是否有效，仍需要恢复流程检查。

## 十一、典型选择与实现分工

### 11.1 按实际需求选择扩展边界

| 需求 | 适合的组合 | 选择原因 |
| --- | --- | --- |
| 一键生成固定结构的客服群、项目群 | L1 | 用配置表达即可，不引入无必要的运行时依赖。 |
| 在标准聊天旁展示公会积分、业务资料 | L1 + L2 | 业务展示增强群聊，但不改变消息关键路径。 |
| 用业务注册决定加入资格，并提供业务面板 | L1 + L2 + L3 | 需要运行时业务决策，也需要嵌入式交互。 |
| 在自己的完整业务产品内提供群聊 | L1 + L4A，按需增加 L3 | 保留产品界面控制权，同时复用消息服务。 |
| 使用独立后端、让不同产品通过协议互通 | L4B | 共同依赖协议，而不是 BuckyOS 默认实现。 |

选择原则是使用能够满足需求的最浅扩展边界，而不是为了“能力完整”给每个应用同时加入所有机制。是否需要 L3，应由业务是否必须影响群操作决定，而不是由页面复杂度决定。

### 11.2 开发责任分配

**Message Center / Group Service 侧**负责最小消息与群能力、公开服务接口和配置契约，并规划 Hook 执行语义及内核数据可靠性。不在核心路径中无条件依赖所有应用服务。

**Message Hub 侧**负责默认聊天 UI、配置驱动的标准内容、应用侧面板加载、上下文传递与加载策略呈现，同时提供可复用的 UI 源码。侧面板异常应局限在面板及业务能力范围内。

**应用侧**负责生成业务配置、提供业务页面或服务、管理业务数据、声明和实现所依赖的 Hook 行为，并承担对应的可用性与源码集成责任。选择 L4B 时，同时承担独立消息服务的协议与可靠性责任。

### 11.3 实施组织建议

先稳定基础消息模型、服务与界面的职责划分，以及 L1 配置边界；在此基础上实现 L2，并验证面板失效不会破坏基础聊天。

L4A 可以随着公开服务接口和组件源码开放并行推进，不必等待 L3 完成。L3 应在处理链、权限语义及故障策略明确后实施，避免先开放任意回调，再倒推安全与兼容规则。

L4B 的互操作依赖协议规范，不应以复用默认实现或等待全部 UI 能力完成为前提。

以上是实施顺序建议，不是已经承诺的版本范围或交付时间表。

## 十二、架构验证与待明确事项

### 12.1 关键验证场景

以下场景用于检查实现是否符合本架构；涉及规划能力的条目，在对应能力落地时验证。

| 场景 | 应验证的结果 |
| --- | --- |
| L1 配置生成器完成创建后退出 | 群持续工作；不再调用生成器完成日常收发。 |
| 不同成员读取同一群消息 | `to` 保持 Group DID，发送者保持原成员；消息可见性仍受权限约束。 |
| 成员只能访问部分 Session | Session List 与消息拉取不泄露未授权内容。 |
| L2 应用页面或业务服务不可用 | 标准群聊继续工作，失败集中在面板及业务能力。 |
| 同一个应用同时启用 L2 和 L3 | 分别验证面板故障与 Hook 故障，不能只测试前者。 |
| L3 加入验证服务不可用 | 按配置处理新成员加入；在采用所建议隔离策略时，已有成员仍可沟通。 |
| L3 动态发言许可服务不可用 | 正确区分动态许可和原生权限，按声明的回退规则执行。 |
| Hook 正常拒绝与超时分别发生 | 正常拒绝不会被错误地当成故障回退而放行。 |
| 自定义 UI 限制通用客户端访问 | 限制落实在服务授权路径，不只是隐藏默认界面入口。 |
| 外部来源侧面板被配置到群 | 默认阻止；显式策略接受后的加载与数据访问仍分别受控。 |
| Message Center 升级并加载旧配置 | 已有配置和公开接口保持所承诺的兼容语义。 |
| Message Hub 升级，而应用仍使用旧组件源码 | 平台不要求应用自动同步 UI；应用按自己的依赖与测试维护。 |
| 两种独立兼容客户端访问 L4B 服务 | 在支持的协议范围及授权条件下互通，不要求共享 UI 或后端代码。 |
| 群服务备份恢复或多副本切换 | 验证完整群数据和配置；不将成员局部记录或应用数据库误当作已被完整覆盖。 |

### 12.2 待明确的接口与机制

| 事项 | 需要明确的内容 |
| --- | --- |
| 术语与规范关系 | 平等群发会话、底层对象协议、DID Post Object Protocol 的正式名称及版本边界。 |
| Group Configuration | Schema、默认值、可配置行为、版本与迁移；哪些内容由 UI 暴露，哪些仅通过配置接口提供。 |
| 面板嵌入协议 | HTML 入口、Group / Session 上下文传递、会话切换、加载生命周期、配置描述格式。 |
| 同源与跨来源策略 | 群的可信来源如何确定，OOD 与 origin 的绑定，用户接受策略的范围和撤销方式。 |
| 应用身份与授权 | 面板及自定义 UI 如何以用户或应用主体访问 Message Center，如何限制指定业务路径。 |
| Hook / Process Chain | 实际 Hook 点、执行顺序、返回语义、可操作范围、超时、重试、默认行为和版本边界。 |
| 权限语义 | 原生权限与动态许可的优先级、持久化变更、不可覆盖的限制，以及服务故障时的处理。 |
| 数据可靠性 | 多副本规模、主从关系、复制与切换、导入导出、完整备份的授权及恢复数据范围。 |
| UI 源码开放 | 可复用组件清单、源码获取与集成方式；不扩大为稳定共享控件契约。 |
| 协议互操作 | 独立实现需要支持的最小能力，以及通用客户端对扩展消息内容的处理方式。 |

这些事项需要后续专项设计，不能通过在本稿中添加示意字段或假设接口来代替。

## 十三、结论

BuckyOS Self-host Group 的应用扩展，不是把所有业务功能塞进群服务，而是围绕一个可自部署、职责清晰的消息内核开放多层边界：用配置构造业务群，用侧面板增强标准聊天，用 Hook 参与业务决策，用自定义 UI 构建完整产品，最终允许独立实现通过协议互操作。

其中最重要的约束是：**Message Center 与 Message Hub 分离，协议与默认实现分离；配置和服务接口承担稳定性，UI 源码复用保留演进自由；展示增强与关键路径扩展分别承担故障责任。**

应用可以按需要逐步深入，但每增加一层控制能力，都应同时明确其授权、可用性、数据和升级责任。这样既能保持内核精简，也能让复杂应用复用可靠基础，而不被默认聊天产品的界面和业务模型束缚。
