> **文档定位**：面向系统架构师与实现团队的架构基线。

> **v0.7 变更**：纠正“每个 Zone 只有一个 HomeStation、只服务 Zone owner”的设定。HomeStation 和 Message Center 一样服务 Zone 的所有用户：每个用户都有自己的发表流与投递入口（`cyfs://<Zone>/home/<用户名>/...`），状态互相隔离；同 Zone 用户之间的关注、投递与读取和跨 Zone 完全相同（§4.4）。新增 Zone 汇总列表（Zone feedlist）、默认发表流与访问地址（§4.6）。

## 1. 架构摘要

HomeStation 是 BuckyOS 预装的 Self-hosted 个人门户与内容消费应用。对外，它承载用户自己的动态、评论和内容发表；对内，它综合社交投递、主动订阅与内容抓取，为用户生成可以持续浏览的个人 Feed。

一个 Zone 的 HomeStation 服务该 Zone 的**所有用户**，与 Message Center 一样：每个用户都有自己的发表流、投递入口、候选与待读、设置和评价记录，彼此隔离；Zone 另外维护一个汇总列表（Zone feedlist），并配置短域名默认打开哪个发表流（§4.6）。

其核心不是建设一个由平台统一控制的推荐系统，而是建立一套开放的内容流通协议，将复杂的内容采集、筛选、准备和推荐反馈放在用户自己的 HomeStation 中执行。

因此节点之间的社交网络协议可以很薄：**它的核心只约定，给定一个以 DID 标识的用户，如何找到其发表流（Home Feed List）与投递入口，以及读取和投递时需要的访问参数**（§4.4）。关注就是持续读取对方的发表流；评论、互动和关注声明写入自己的发表流，并投递到相关方的投递入口；收录者读取发表流并对外提供查询。发表流按读者身份只返回其受众允许的条目（§4.5），条目是发表者签名的入口状态，内容按 ObjId 获取。

HomeStation 同时提供**通用标签评价服务**：用户、其他应用与 Agent 可以按需请求对身份或内容进行标签化评价，形成由各用户掌握规则、模型与采用方式的去中心化、AI Native 自审核能力。评价服务独立于 Feed 阅读流程，待读过滤、社交准入、联系人提示、内容检索和发表前检查均可复用，详见 §6。

整体架构可以概括为：

```text
其他用户 / 好友 / 间接社交关系                    公开内容源
              │                                  │
              │ Push                             │ Pull
              ▼                                  ▼
       Social Inbox                      Spider / Agent Cache
       轻量对象与资源引用                  原生对象 / 外部内容封装
              └────────────────┬─────────────────┘
                               ▼
                   同构化候选集合：Feed Object
                               │
                               ├─ 关注但未入列 ─> 私有补看入口 ─> 按需准备与阅读
                               │
              本地标签修正与过滤 + 推荐 + 内容资源准备
                               ▼
                      统一、有限的待读列表
                               │
                    分类视图 + 对应浏览游标
                               ▼
                           Feed UI
                               │
              ┌────────────────┼─────────────────┐
              ▼                ▼                 ▼
        本地消费行为      主动反馈 / 评论     可选消费证明
              │                │                 │
       改进抓取与推荐     对象发表与传播      授权后的网络回执
```

评论不另建一套传播系统。**评论本身就是 Feed Object**，引用被评论内容的具体版本，可以出现在评论者自己的主页中，并向原作者、好友、已发现的讨论参与者和收录节点传播。

同一内容的评论可以有作者视图、收录者视图和用户本地默认视图。作者可以管理自己的列表，但不能垄断其他节点保存、传播和展示评论的能力。

**点赞、收藏等也是特殊评论。** 公开互动由互动者签名，按同样的列表模式收集、验证和统计；内容作者提供的数字只是一个来源，不能代替可查询的记录依据。收藏仍默认私有，采用统一对象模型不等于默认公开。

关注采用让对方知情的君子协议。Message Center 中的好友默认互相关注，用户可以配置“不看某人／某分组的朋友圈”。关注驱动服务主动 Pull 到候选集合，不保证进入待读列表；应用提供“来自我关注的人，但未进入我的 Feed”的补看入口。转发也是特殊评论，在转发者自己的发表流中形成可撤回、包裹原文的 Feed Object。

**Feed Object 本身不可变。** 它的内容要么自包含（内联正文加不可变部件的 ObjId），要么包裹另一个对象的 ObjId；对象的 ObjId 因此固定了它的全部内容。需要后续编辑、撤回或取消的对象，在发表时声明一个可变入口（URL 或 DID），说明“这条发表可能变化，当前状态在此查询”；未声明入口的对象是终态对象。

Feed Object 的更新与删除采用君子协议：发表者通过入口发布单调递增、可验证的入口状态，接收者据此更新默认展示和有效统计。不可变版本仍可被引用，历史副本不保证消失，原文作者也无权撤回他人的评论或互动。

架构需要优先稳定四类跨节点语义：

1. 以 DID 定位发表流与投递入口，发表流的读取方式、访问参数及发表受众。
2. Feed Object 的发表、内容形态、版本身份、引用以及 Push/Pull 流通。
3. 普通评论及特殊评论的传播、列表发现、多维护者视图与可复算统计。
4. 可变入口与入口状态的君子协议，以及自愿消费证明。

推荐算法、候选管理、待读列表、分类游标、行为分析和资源缓存属于应用实现，不应因此被固定成统一的网络协议。

## 2. 产品定位与设计目标

### 2.1 两个界面，一套内容对象

HomeStation 同时具有个人门户和个人阅读中心两种使用方式，必须区分个人发表流与个人待读列表，并明确评论和候选补看视图的边界。

| 名称 | 面向谁 | 主要内容 | 边界 |
| --- | --- | --- | --- |
| 个人发表流（Personal Published Feed / Home Feed List） | 访问该用户主页的人、订阅者、抓取者 | 用户主动发表的动态、评论、转发及公开互动 | 在标准路径上按每条的受众对外提供（§4.4、§4.5）；不含私人抓取、待读与阅读记录 |
| 个人待读列表（Reading List） | HomeStation 所有者 | 从多种来源筛选并准备好的内容 | 默认属于本地应用状态，不因进入列表而自动公开 |
| 关注未入 Feed 集合 | HomeStation 所有者 | 已获取、来自有效关注对象、尚未进入待读列表的候选 | 私有候选查询视图，不保证资源已就绪，不是第二套待读列表 |
| 评论列表（Comment List） | 查看某条内容讨论与互动的人 | 针对某个具体 Feed Object 版本的普通评论及获准披露的特殊评论引用 | 可以由不同主体维护，按类型形成讨论或互动视图，不存在天然唯一的权威列表 |

用户在自己的主页发表内容，不等于向自己投递私人消息；用户把内容加入待读列表，也不等于在自己的主页再次发表该内容。

### 2.2 Feed 的构成

HomeStation 将三种机制组合起来：

- **订阅与抓取**：主动 Pull 原生 HomeStation 动态及传统互联网公开内容。
- **社交投递**：接收好友、订阅者关系、符合规则的间接关系或其他允许来源的 Push。
- **用户侧筛选**：由本地程序或 LLM 根据用户状态组织最终可阅读内容。

用户定义的话题决定内容方向，但具体内容组合不必仅仅迎合已有偏好。默认推荐方向应服务用户，而不是将平台商业利益或无限延长停留时间作为首要目标。

“对用户更好”是推荐层的产品目标，不是协议可以自动保证的事实，也不能假定只要使用 LLM 就必然消除偏见或信息茧房。用户必须保留替换算法、调整规则和选择信息来源的能力。

### 2.3 注意力经济的定位

此前讨论的 Hot Pot 方向，将用户有限的消费时间视为可自主分配的资源，允许用户通过透明约定，将部分注意力交换给广告商或其他商业参与者。

当前架构为这一方向保留消费证明和自愿回执机制，但不预设完整 Token 系统，不确定发行、定价、清结算或反作弊方案，也不把经济模型变成正常阅读和社交互动的前置条件。

### 2.4 首版目标与非目标

首版应交付一个能实际使用的完整应用：用户可以发表、更新和撤回内容，获得候选信息，浏览已准备的 Feed，留下本地反馈，发表普通评论或特殊评论，并通过不同来源查看评论及有效互动统计。

首版不承担以下目标：构建全网完整索引、保证看见全部评论、统一所有人的推荐算法、实现完整注意力市场、证明用户真实的心理注意力，或者保证已传播内容可以被全网撤回。

## 3. 术语与既有系统边界

### 3.1 术语统一

本文统一使用 **BuckyOS** 与 **HomeStation**，并区分内容对象、投递入口、阅读状态与对外发表状态。

| 术语 | 本文含义 |
| --- | --- |
| Feed Object | 面向内容发表与传播的统一不可变对象，内容自包含或包裹另一个 ObjId |
| 自包含 / 包裹 | Feed Object 的两种内容形态：内联正文并以 ObjId 引用部件；或以 ObjId 包裹一个可独立存在的对象，自身只提供发表语境 |
| Message Object | 更强调发送者、接收者及送达关系的消息对象 |
| 发表流（Home Feed List） | 用户对外发表的全部入口及其变化序列，位于由 DID 可定位的标准路径；按读者身份返回其受众允许的条目 |
| 受众（Audience） | 一条对外发表允许谁读取与接收，由发表者服务按入口执行；不写入对象 |
| Social Inbox / 投递入口 | HomeStation 自有的投递入口，以 CYFS dispatch 接收他人 Push 的对象与 Head，执行准入后形成候选 |
| Spider | 主动采集内容的执行者，可以是普通程序，也可以是 LLM/Agent |
| Spider Cache | 抓取产生的候选对象和必要资源缓存 |
| 候选集合 | Push 与 Pull 输入在 Feed Object 层形成的逻辑集合 |
| 标签评价服务（Evaluation Service） | HomeStation 提供的公共系统服务能力，按需评价 DID 身份或具体内容，并返回可追溯的结构化标签判断 |
| 评价记录（Evaluation Record） | 某评价主体在指定时间、证据范围与评价配置下对目标作出的判断；独立于目标对象和采用该判断的业务动作 |
| 待读列表 | 已完成筛选和必要内容准备、可供用户开始消费的有限有序集合 |
| Source / Subscription | 可采集来源及用户的持续订阅关系；关注人的发表流是其中一种订阅 |
| 关注声明 | 向被关注方说明关注关系的可验证记录，有效与取消由其可变入口的 Head 表达；不等于好友权限或公开全部关注名单 |
| 特殊评论 | 表达点赞、点踩、收藏、转发等互动的 Feed Object；可私有保存或经授权对外发表 |
| 可变入口 | Feed Object 在发表时自声明的 URL 或 DID，代表一条逻辑发表或一个互动状态，必须位于发表者控制的命名空间 |
| 入口状态（Head） | 解析可变入口得到的独立签名对象，以单调序号表达当前有效版本或已撤回；更新、撤回、取消都是新的 Head，不改写旧对象 |
| 终态对象 | 未声明可变入口的 Feed Object，协议上不存在后续版本或撤回 |
| 消费证明 | 用户授权对外发送的、带签名的消费行为声明 |
| 收录者 | 提供对象接收、索引、查询和发现服务的独立参与者 |

### 3.2 复用消息与命名对象基础设施

本次讨论所称“Message Hub 协议”“Message Hub 的 Inbox”，指向已经形成的消息收发、对象投递与 Inbox 基础能力。

实现对接时，需要区分共享消息服务与消息 UI：按此前的系统分层，Message Center 承载消息服务，Message Hub 是相关消息界面。HomeStation 应复用底层服务与对象协议，而不是依赖某个聊天 UI 的内部实现。具体服务名、地址格式及 SDK 接口以现有工程为准，本文不假设已核实任何代码接口。

HomeStation 主要增加内容语义、通用标签评价、社交投递规则、发表与收录能力，以及本地阅读管线，不重新建立一套身份系统、消息传输网络或好友关系数据库。

当前工程的 `src/kernel/buckyos-api/src/msg_center_client.rs` 已用 `Contact.access_level` 表达好友等级，并提供 `Contact.groups` 联系人分组。HomeStation 从 Message Center 读取这些关系，派生默认关注、分组展示策略及受众判定；不另建一份权威好友关系。这里的分组指联系人分组，不等同于群聊或 Group Inbox。

HomeStation 不经由 Message Center 的消息投递接收 Feed。Message Center 的 `dispatch` 只接收 `MsgObject`，准入按聊天关系执行（`AccessGroupLevel`，陌生来源进入 `RequestBox`），与 Feed 的宽准入（§7.3）不是同一套规则。HomeStation 在自己的语义路径上以 CYFS dispatch 接收 Feed Object、Head、关注声明等小型命名对象（§4.4、§7.4），复用网关的接收侧缓存；只从 Message Center 读取关系数据。CYFS 的 No-Push 约定本来就把评论、通知、索引更新列为跨 Zone 语义事件的典型例子，附件与正文仍由接收方按需 Pull。

### 3.3 网络协议与应用实现

| 应优先形成跨节点约定的部分 | 保持本地可演化的部分 |
| --- | --- |
| 由 DID 定位发表流与投递入口，读取方式、访问参数与受众 | 发表流的存储方式与分页大小 |
| Feed Object 内容形态、版本身份与引用语义 | Spider 使用脚本还是 AI |
| 投递入口的传输结果及准入披露语义 | 候选评分、排序与淘汰策略 |
| 关注及取消关注的可验证通知 | 订阅任务、联系人／分组“不看”规则及候选补看入口 |
| 发表流和评论列表的发现与读取能力 | 待读列表的更新节奏与容量 |
| 普通/特殊评论的目标、身份、状态归并及统计依据 | 分类、游标、展示过滤及阅读起点策略 |
| 自愿公开互动与消费证明的语义 | 原始行为事件、兴趣推断及保留周期 |
| 可变入口、入口状态及列表移除的区别 | 资源预取、播放器与内容查看体验 |
| 对外共享评价时的目标绑定、评价者身份与签名 | 评价维度、模型、证据采集范围、人工修正、采用与处置策略 |

特别需要避免把“统一待读列表”理解为整个网络必须实现相同的列表协议。它首先是 HomeStation 应用内部的阅读模型。网络上需要统一读取约定的列表是发表流（§4.4）；作者和收录者的评论视图（§15）可以沿用其展示读取与变化读取两种方式。

## 4. 参与者、对外入口与模块划分

### 4.1 三种网络角色

HomeStation 的生态包含生产者、消费者和收录者。一台节点或一个用户可以同时承担多种角色。

**生产者**发表原创内容、评论或主动分享的内容对象。**消费者**获取、阅读并参与互动。**收录者**接收对象、建立索引并提供发现能力，不因此获得内容所有权或全网评论控制权。

原作者在某条内容的早期讨论中通常也是参与者发现入口，相当于该讨论的一个初始 Tracker，但不应成为无法替换的唯一入口。

### 4.2 用户端侧的含义

本文所说“把复杂度放在用户端侧”，主要指放在**用户控制的 Self-hosted HomeStation 环境**，通常是用户的 BuckyOS 服务器，而不要求所有任务都在浏览器内运行。

浏览器负责展示、交互和必要行为采集；持续抓取、推荐、资源准备、评论同步等任务可以在用户关闭浏览器后继续由服务器服务执行。

“资源已下载到 HomeStation”只表示其已存在于用户的托管节点，不等于已经缓存到每一台访问设备，也不自动意味着手机断网后仍可观看。

### 4.3 建议的逻辑模块

以下是便于实现的职责划分，不要求拆成独立微服务。首版可以由一个后端应用承载多个模块与后台任务。

| 模块 | 核心职责 |
| --- | --- |
| Publish Service | 创建正文、普通/特殊评论 Feed Object，串行签发可变入口的 Head，维护发表流及其变化序列，按受众提供展示读取与变化读取 |
| Subscription / Source Manager | 管理来源、订阅意图及关注通知，读取好友与分组关系，驱动持续 Pull |
| Publishing Assets | 复用文件／对象存储接收图片、视频、语音等素材，管理上传、引用与保留 |
| Social Ingress / Delivery | 在投递入口以 CYFS dispatch 接收对象并执行准入；向他人投递入口发送对象与 Head，保留重试责任直至 `accepted` |
| Spider Runtime | 读取原生来源或传统公开来源，封装对象并缓存必要资源 |
| Candidate Store | 管理候选引用、来源与关注关联、处理和入列记录，提供关注未入 Feed 的查询 |
| Evaluation Service | 向应用与 Agent 提供身份／内容的按需标签评价、结果查询、人工修正及变化通知，管理证据、缓存与可见范围 |
| Selection Service | 调用 Evaluation Service，结合用户策略形成有效标签，根据分类目标及反馈筛选内容，应用过滤与“不看”规则并输出理由 |
| Resource Preparation | 按 ObjId 获取正文、图片、视频等对象并校验，形成可消费状态 |
| Reading List Service | 维护统一待读列表、分类视图与游标 |
| Comment Sync / Index | 同步普通/特殊评论及其入口状态，验证与归并状态，维护多来源视图及可复算统计 |
| Local Feedback | 临时记录行为并为抓取、推荐提供本地反馈 |
| Receipt Sender | 在授权下发送消费证明；快速互动沿用评论发表与投递能力 |
| Profile / Topic Views | 复用用户资料，组织作品、商品、精选栏目及 Topic 分类与汇总 |
| Web UI | 个人主页、Feed 阅读、内容详情、评论视图、发表及配置 |

收录节点可以复用 Publish、Ingress 和 Comment Index 等能力，但其部署角色不等于每个普通用户必须承担公共收录服务。

### 4.4 发表流与投递入口：社交网络协议的核心

HomeStation 之间的社交网络协议，核心只约定一件事：**给定一个以 DID 标识的用户，如何找到其发表流与投递入口，以及读取和投递时需要的访问参数。** 其他跨节点行为都建立在这两个入口上：

| 行为 | 使用的入口 |
| --- | --- |
| 关注、访问主页、收录 | 读取对方的发表流 |
| 评论、互动、转发 | 写入自己的发表流，并投递到原作者及相关方的投递入口 |
| 关注声明 | 写入自己的发表流（受众为被关注者），并投递到对方的投递入口 |
| 编辑、撤回、取消 | 在自己的发表流签发新 Head，并沿已知路径投递 |

**发现。** 一个 Zone 的 HomeStation 服务该 Zone 的所有用户，每个用户在 Zone 内有自己的主页路径 `cyfs://<Zone>/home/<用户名>`。默认按约定定位：由 DID 解析到用户的 Zone，再向该 Zone 查询这个 DID 的用户名（`GET https://<Zone>/home/?did=<DID>`，Zone 不托管该 DID 时明确回答“没有”）；发表流位于 `cyfs://<Zone>/home/<用户名>/feed`，投递入口位于 `cyfs://<Zone>/home/<用户名>/inbox`。用户将 HomeStation 托管在其他位置时，在公开资料中以发表者能力信息（§5.3）声明这两个地址，声明优先于约定。发表流覆盖该用户的全部对外入口：正文与评论位于 `home/<用户名>/feed/@/<入口键>`，公开互动位于 `home/<用户名>/reactions/@/<互动键摘要>`，关注声明位于 `home/<用户名>/follows/@/<键>`；它们共用一个变化序列，读者用一个游标即可同步全部变化。

**同 Zone 用户没有特例。** 同一 Zone 的两个用户之间的关注、投递、读取与跨 Zone 完全相同：各自的发表流、投递入口、受众规则和准入都独立；实现可以不经公网而在本机转发这些请求，但语义不变。没有 HomeStation 的身份（例如 Zone 内的 Agent）没有发表流，不派生关注，也不向其投递。

**条目是签名 Head，列表响应不签名。** 发表流的每个条目是一个入口的当前 Head（§16.5），由入口控制者签名、可以独立验证；读取单个入口 `<入口路径>` 直接返回该 Head。内容按 Head 指向的 ObjId 获取，响应可以按 §5.5 的随附规则附带读者有权读取的对象 JSON，省去逐条获取。列表响应本身只是查询结果，不是签名对象：中间节点可以漏掉条目，但不能伪造条目。读者不能把某次响应缺少某个条目解释为撤回，撤回只由已撤回的 Head 表达。

**两种读取方式。**

| 读取方式 | 访问参数 | 返回 | 典型读者 |
| --- | --- | --- | --- |
| 展示读取 | 读者身份、分页位置、可选的类别／类型筛选（如作品、商品） | 当前有效条目，按发表者声明的 `iat` 倒序 | 访客、个人门户、首次关注时的回填 |
| 变化读取 | 读者身份、上次的变化游标 | 该游标之后的 Head 变化：新入口、新版本、撤回，以及对该读者新变为可见的条目 | 关注者、评论追踪者、收录者 |

变化游标对应发表流级别的单调变化序号，由发表流服务分配，与每个入口自身的 Head `seq` 不是同一个序号。读者为每个关注对象保存一个游标，即 §7.7 的采集进度。发表流可以压缩旧的变化；游标早于压缩点时返回需要重新完整同步的明确结果，不能静默跳过其间的撤回。

**读者身份。** 匿名读者只得到公开条目；经认证的读者得到其受众允许的条目（§4.5）。同一路径对不同读者返回不同结果是发表流的正常语义，不是不一致。读者身份的认证复用 CYFS 跨 Zone 请求的既有身份机制，具体方式待对齐（§21）。

**Pull 是事实来源，Push 只为及时。** 发表时，Publish Service 把对象及其 Head 投递到受众内相关方的投递入口，使对方尽快收敛；对方离线、投递丢失或未被准入，都通过变化读取补齐。投递入口只接收小型命名对象，正文与媒体仍由接收方按 ObjId 获取（§7.2）。

**发表流里没有的内容。** 私有收藏、候选与待读、私人抓取（§5.6）、阅读记录和推荐理由都不进入发表流，也没有对外读取路径。发表流只包含用户主动对外发表的内容，个人门户（§9.6）是它面向访客的展示。

### 4.5 发表受众

每条对外发表在发表时选定受众。受众同时决定两件事：Push 投递给谁，以及谁能通过 Pull 读取该条目、它的 Head 和它引用的对象。

| 受众 | 可读取者 | 用途 |
| --- | --- | --- |
| 公开 | 任何人，包括匿名访客与收录者 | 点赞的默认受众；正文、评论与转发的默认受众由用户设置 |
| 关注者 | 发表者已收到其有效关注声明的人 | 由用户选择 |
| 好友 | Message Center 中的好友 | 由用户选择，对应“朋友圈” |
| 联系人分组 | 指定联系人分组的成员 | 由用户选择 |
| 指定 DID | 列出的身份 | 关注声明（受众为被关注者）、对受限内容的评论与互动（受众为原作者） |

规则：

- **受众是入口的访问策略，不写入对象。** 发表者服务在读取和投递时按读者身份执行受众规则；对象内容和签名不包含成员名单，既不向所有读者泄露受众，也使调整受众不必产生新版本。好友与分组按读取时的 Message Center 关系判定，关系变化后自动生效。发表界面始终显示当前受众。
- **知道 ObjId 不等于有读取权。** 受限条目的 Head 与对象只向受众提供。投递和读取响应以不签名的附带信息标明条目受限，供接收方的界面与转发规则使用。
- **调整受众。** 扩大受众后，新获得权限的读者在变化读取中看到该条目；缩小受众不能收回已经取得的副本，需要他人停止展示时应撤回（§16.4）。
- **受限内容不能转发。** HomeStation 不为受限对象提供普通转发和引用转发，推送任何包裹对象时也不随附受限对象的 JSON。即使有人包裹了受限对象的 ObjId，受众以外的读者也取不到原文，界面显示“原文不可见”。
- **对受限内容的评论与互动只给原作者。** 评论、点赞等仍写入评论者的发表流，但受众固定为原作者：只投递和提供给原作者，不出现在评论者的公开主页，也不提交给收录者；其他人只能通过作者视图在原受众范围内看到。这类讨论因此依赖作者，失去 §15 多视图带来的开放性，这是受限可见本身的代价。
- **包裹他人的非公开对象需要授权。** 从 MessageHub 等处一键发表时，只能直接包裹自己发表的对象或公开对象；别人发给我的消息、文件等非公开对象，需要原发表者授权才能包裹发表。
- **点赞默认公开。** 点赞默认以公开受众发表，界面在首次点赞时告知用户；收藏仍默认私有（§11.1）。

### 4.6 一个 Zone 的 HomeStation：用户主页、Zone 汇总列表与访问地址

**访问地址。** HomeStation 的页面与协议路径分开：协议路径在 `/home/` 下（§4.4），页面在 `/homestation/` 下。

| 地址 | 内容 |
| --- | --- |
| `https://<Zone>/homestation` | 登录用户自己的 HomeStation（待读、发表、设置），需要登录 |
| `https://<Zone>/homestation/<用户名>` | 该用户的发表流（个人门户），登录可选：访客按自己的身份读取，匿名只看公开条目 |
| `https://<Zone>/homestation/<用户名>/<入口键>` | 该用户的一条发表（`home/<用户名>/feed/@/<入口键>` 的当前版本），用于分享链接 |
| `https://<Zone>/homestation/~zone` | Zone 汇总列表 |
| `https://homestation.<Zone>/`、`https://www.<Zone>/` | Zone 配置的默认发表流 |

`homestation.<Zone>` 总是可用，一般同时启用 `www.<Zone>` 短域名并默认使用它。只有这两个主机上路径为 `/` 时才特殊处理：打开默认发表流；页面里的链接一律指向 `https://<Zone>/homestation/...`。用户名不允许包含 `~`，所以 `~zone` 不会与任何用户的主页冲突。

**默认发表流。** 由 Zone 配置，常见两种：指定某个用户的发表流（例如测试环境的 `devtest`），或者 Zone 汇总列表。未配置时为 Zone owner 的发表流。

**Zone 汇总列表（Zone feedlist）。** 有写权限的用户发表时，可以选择同时把这条发表放进 Zone 汇总列表，之后也可以单独加入或移出。规则：

- **条目仍是发表者自己签名的 Head。** 汇总列表不产生新的对象或签名，只记录哪些入口被列入，并维护自己的变化序列。读者对每个条目按其发表者验证（§5.4），与读取个人发表流完全相同；列表响应同样不签名。
- **只收公开发表。** 列入时条目必须是公开受众的正文或引用转发；之后发表者缩小受众、编辑或撤回，汇总列表按发表者入口的当前状态返回：受众以外的读者看不到，撤回的不再展示。
- **变化读取。** 列入、移出，以及已列入条目的新 Head 与受众变化都进入汇总列表的变化序列，关注汇总列表的读者用一个游标同步。移出只是不再列入，不是撤回；撤回仍只由发表者的 Head 表达（A68）。
- **写权限由 Zone 决定。** 默认为 Zone 的普通用户（admin、root、user 类型），可由服务设置改为指定的用户名单。
- **汇总列表不是个人。** 它没有私人状态，不发表关注声明，也不接收投递。

**签名。** 服务模式下 Zone 的 HomeStation 用 OOD 设备密钥替该 Zone 的所有用户签名（Zone 托管）：验证方接受“签名设备所属的 Zone 正是发表者所在的 Zone”。这意味着 Zone 可以替其用户签名，属于已知风险，与用户把账号托管在 Zone 的信任关系一致；用户需要独立密钥时，可在其 DID Document 列出自己的密钥（§5.4）。

## 5. Feed Object：统一的发表与传播单元

### 5.1 Envelope 同构化

无论内容是好友投递、原生订阅、传统网页抓取，还是用户自己发表，进入 HomeStation 候选集合后都使用 Feed Object 表达。

对原生内容，保留其对象身份和来源信息。对外部内容，Spider 或 Agent 包裹抓取快照，或者发表链接卡片（§5.6），使其成为可被 HomeStation 处理的对象。

同构化发生在对象层，不要求所有正文都变成同一种内容格式，也不要求进入候选集合前必须下载全部附件。

### 5.2 与 Message Object 的关系

Message Object 更强调“谁向谁发送了什么，以及送达结果如何”；Feed Object 更强调“谁发表了什么内容，以及该内容可以如何被引用和传播”。

同一个 Feed Object 可以通过多个投递通道送达，也可以被多次 Pull。传输路径的变化不应被误认为内容本身发生了变化。

Feed Object 与 Message Object 可以复用底层命名对象、签名和投递能力，但变更模型不同。MsgObject 以 `relates_to` 关系消息表达编辑和撤回，多条编辑的先后由托管会话的接收方分配；Feed 没有这样的托管方，发表者自己的入口才是天然的定序者，因此 Feed 的更新与撤回走可变入口（§5.4），不复用 `relates_to`。是否共用其他字段与 SDK 类型，见 §21。

### 5.3 最小语义集合

以下是需要在协议设计中覆盖的概念，不是已冻结的字段名或线格式。

| 概念 | 要表达的问题 |
| --- | --- |
| 协议/对象类型与兼容信息 | 这是何种对象，接收者能否理解 |
| 对象身份 | 当前具体内容版本是什么，即由内容计算的 ObjId |
| 发表主体 | 谁发表或封装了该对象，如何验证其声明 |
| 时间信息 | 发表者声明的创建时间，只用于展示，不作为版本先后的依据 |
| 内容 | 自包含时的内联正文与部件 ObjId，或被包裹对象的 ObjId 及发表语境（§5.5） |
| 可变入口 | 这条发表之后能否更新或撤回，当前状态去哪里查询（§5.4）；缺省即终态对象 |
| 对象关系 | 该对象在评论、回复或引用哪个具体对象；特殊评论表达何种互动 |
| 来源信息 | 原生发表还是外部抓取，原始出处在哪里；只是数据，不是内容引用或可变入口 |
| 可选的发表者能力信息 | 去哪里查询其发表流、评论视图或投递相关对象 |

实际签名范围、对象 ID 计算方式和序列化规则应与 BuckyOS 既有对象体系对齐：ObjId 由 canonical JSON 计算；需要签名时以 JWT 形式承载，ObjId 只由 claims 计算，与是否签名无关。Feed Object 宜定义为新的 CYFS 标准对象类型，直接定义 `publisher`、`iat`、`entry`、`references` 等字段，不整体沿用 `BaseContentObject`：后者的 `did` 字段类型是 DID，只能承载 DID 形式的入口（E08），承载不了 Zone 路径入口；`references` 目前是空结构，表达不了关系与目标；`create_time`／`last_update_time` 两个时间字段放在不可变对象里会造成歧义。可复用的字段（如 `tags`、`base_on`、`copyright`）在 §21 逐项确定。本文不另行选择哈希算法、DID 方法或传输协议。

### 5.4 不可变对象与可变入口

Feed Object 一经发表就不可变，修改内容会产生新的 ObjId。可变性不靠改写对象，而由对象在发表时自声明的**可变入口**表达：

- 入口是一个 cyfs URL 或 DID，写在对象内容中并参与 ObjId 计算，是发表时作出的承诺：“这条发表之后可能更新或撤回，当前状态在此查询”。
- 未声明入口的对象是**终态对象**：协议上不存在它的后续版本或撤回，接收方无需查询其状态。发表者希望保留编辑、撤回或取消的能力，就必须在发表时声明入口。HomeStation 默认为用户发表的正文、评论、公开互动和转发声明入口。
- 入口代表一条**逻辑发表**，或一个互动状态（§12.4）；各版本的 ObjId 是入口在不同时刻指向的内容。

```text
可变入口 cyfs://<Alice Zone>/home/alice/feed/@/garden-0001
    ├─ Head seq=1：active，current = P1
    ├─ Head seq=2：active，current = P2
    └─ Head seq=3：withdrawn

针对 P1 的评论 ──引用──> P1 的 ObjId
针对 P2 的评论 ──引用──> P2 的 ObjId
```

解析入口得到**入口状态（Head）**：由入口控制者签名、带单调递增序号的小记录，说明入口当前指向哪个版本，或已经撤回。URL 入口使用发表者签发的 Head 对象，入口路径位于发表流之下（§4.4），读取该路径直接返回当前 Head；DID 入口（例如拥有独立内容名字的作品、商品）使用名字系统解析出的内容文档，其版本序号同样单调（CYFS ContentDocument 的“撤销即发布新文档”）。Head 是独立的小型命名对象，不复用 CYFS `PathObject`：后者的 `target` 必填、没有撤回状态、先后按 `iat` 判断，表达不了 Head 的单调序号与撤回。Head 的最低语义与传播见 §16.5。

对象自报的入口只说明“去哪里查”，本身不授予任何权限。接收方按以下约束认定版本归属：

1. **入口键由发表者选择。** 入口写在对象里，而 ObjId 由对象内容计算，所以入口不能包含对象自身的 ObjId，否则形成哈希循环。
2. **入口必须位于发表者控制的命名空间**：发表者主页 `cyfs://<Zone>/home/<用户名>/` 下的语义路径（同一 Zone 的其他用户的路径不算），或发表者拥有的内容 DID。入口不在 `publisher` 的命名空间内、也没有可验证授权的，视为无效入口，对象按终态对象处理。
3. **Head 指向的版本必须声明同一入口，且发表者相同。** 入口不能指向他人发表的对象，也不能把无关对象认领为自己发表的新版本。

**普通评论、点赞、收藏等都绑定具体版本的 ObjId，而不是入口。** 持有旧版本的节点可以经由入口发现新版本并提示“该发表已更新”，但旧版本上的讨论和互动不能被解释为对新版本的评论或认可。新版本可以用 `base_on` 指向前一版本，供历史展示使用；版本归属只由 Head 认定，`base_on` 不授予任何权限。

可变入口不改变历史可见性：旧版本一旦被其他节点获取，就不能假定通过更新 Head 可以消除旧版本及其评论。不过，这并不意味着协议承诺全网永久保存所有历史。

### 5.5 内容形态：自包含或包裹

既然 Feed Object 不可变，它的 ObjId 就必须固定它的全部内容，否则“不可变”只固定了一个外壳。因此对外 Feed Object 的内容只有两种形态：

| 形态 | 结构 | 适用 |
| --- | --- | --- |
| 自包含 | `content` 内联正文，媒体等部件以 ObjId 引用 | 文字、多图、语音动态，正文评论，点赞等无正文的特殊评论，链接卡片 |
| 包裹 | `wraps` 以 ObjId 指向一个可独立存在的对象；`content` 只提供标题、摘要、说明、封面等发表语境 | 转发与引用转发、长文、视频、外部抓取快照、分享存储中的文件或目录 |

规则：

- **内容引用只能是 ObjId 或 ChunkId。** 图片、视频、音频、长文正文等先存入命名对象存储（通常是 FileObject `cyfile`），再以 ObjId 引用；mime、尺寸、时长等描述放在 FileObject 的 meta 中。URL 不能作为内容引用。
- **URL 只能作为数据出现**：来源信息中的原始出处（`source.original_url`），或卡片上的跳转链接（`link`）。它们说明出处或可前往的页面，不属于对象固定的内容，也不是可变入口；链接目标的变化与对象身份无关。
- **被包裹对象保持自身身份。** 包裹不复制、不改写被包裹对象；多次包裹同一对象得到不同的 Feed Object，内层 ObjId 不变。这与 §7.5 禁止的“重新封装并丢失原对象身份”不同。相同字节的抓取快照会得到相同的内层 ObjId，可作为聚合与去重的线索。
- **内联有大小上限。** Social Inbox 只接收轻量对象（§7.2），超过上限的正文必须存为独立对象再包裹；具体上限待定。
- **随附只是传输优化。** 推送包裹对象或含部件的对象时，可以随附被引用对象的 JSON（如 FileObject、被转发的 Feed Object），沿用 CYFS SimpleObjectMap 内嵌子对象的规则：随附内容不参与哈希，接收方按 ObjId 校验后使用。这样包裹不必为取得被包裹对象再多一次往返。只随附接收方有权读取的对象，受限对象不随附给其受众以外的接收方（§4.5）。

候选转为待读时，“让 Feed Object 变完整”指按 ObjId 取得它引用的对象和数据并用哈希校验，而不是改写已签名对象。下载的数据进入本地命名对象存储的缓存，下载位置、缓存时间和可用性检查结果属于本地状态。内容完整性由 ObjId 保证，可用性取决于来源是否可达，两者分开处理。

### 5.6 外部抓取的来源边界

Spider 对外部内容的封装不等于获得原作者的签名。应能区分原始内容作者、来源地址，以及负责抓取和封装的用户或 Agent。

Spider 把外部内容带入 Feed 只有两种形态：保存抓取快照（正文及必要媒体存为命名对象）后包裹该快照；或者不保存快照，只形成链接卡片，卡片的标题、摘要、封面固定在对象里，原文只是跳转目标。不能把一个远程 URL 当作正文引用。来源页面后来变化，不构成封装对象的新版本。

**私人抓取默认不进入发表流。** Spider 为用户阅读而抓取得到的快照与封装对象只是本地候选对象：不声明对外入口，不进入发表流，也不对外提供快照；重新抓取时直接以新的本地对象替换候选，无需签发 Head。用户主动分享时，才以自己的入口发表包裹该快照的对象（E06）或链接卡片，此后的重新抓取才在该入口下发表新版本。这样用户的主页不会被阅读用的抓取内容填满，也不会默认向他人再分发第三方快照。

为抓取所使用的 Cookie、会话令牌等访问材料不应进入对外传播的 Feed Object。能在一次抓取会话中访问，也不自动意味着相关访问凭据可以转交给其他节点。

### 5.7 实例阅读约定与对象分层

以下实例是指导实现的语义样本，覆盖原型中的主要内容和操作；字段名用于把设计讲清楚，尚不是已发布 SDK 的线格式。实现协议时应保留这些语义，并映射到既有命名对象、签名、媒体存储和投递机制。

`P1`、`C1` 等是示例对象的别名，`<P1>` 表示对应的真实 ObjId，`<Alice DID>`、`<Alice Zone>` 等表示实际身份，`<… 的 cyfile>` 表示已存入命名对象存储的 FileObject 的 ObjId。示例 JSON 展示参与对象身份计算的内容，不把自身 ObjId 放进被哈希内容中；签名通过既有命名对象机制以 JWT 形式承载，未在样本中伪造签名值。所有对外 Feed Object 均需验证其 `publisher`；业务关系中的原作者与对象签署者不能混淆。

对象的创建／签发时间使用 `iat`（u64，Unix 秒，遵循 JWT NumericDate），不作为版本先后的依据；Head 的先后仍以 `seq` 为准。`captured_at_ms`、`updated_at_ms` 等独立事件时间仍使用毫秒。同一时刻的不同字符串写法会算出不同 ObjId，因此不使用带时区的时间字符串。正文、评论等发表类对象还应带随机 `nonce`，避免内容相同的两次发表得到同一 ObjId，示例中省略。`entry` 是可变入口，`garden-0001` 这类入口键由发表者选择。

| 层次 | 内容举例 | 边界 |
| --- | --- | --- |
| 不可变 Feed Object | 发表者、创建时间、可变入口、内联正文、部件或被包裹对象的 ObjId、原始标签、评论类型 | 修改这些事实会产生新 ObjId |
| 对象身份与签名载体 | 根据内容计算的 ObjId、发表者签名 | 验证身份与完整性，不用 UI 布尔值代替 |
| 入口状态与控制记录 | 入口 Head、关注声明、收件人与投递结果 | 复用命名对象设施，但不混入原正文，也不计为新增评论 |
| 私有应用投影 | 来源路径、本地标签修正及有效标签、Topic、推荐理由、准备状态、游标、按钮状态与统计缓存 | 可变、按用户保存，不传播为原作者签名的内容 |

### 5.8 原生发表与外部内容实例

#### E01：文字动态 P1

Alice 的原创动态，自包含，可以直接在 Feed 卡片和个人主页展示。`tags` 是 Alice 发表的标签，不是阅读者本地分类的唯一依据。发表时 Alice 同时签发该入口 seq=1 的 Head，见 E14。

```json
{
  "kind": "post",
  "publisher": "<Alice DID>",
  "iat": 1791424800,
  "entry": "cyfs://<Alice Zone>/home/alice/feed/@/garden-0001",
  "content": { "type": "text", "text": "今天开始搭建阳台菜园。" },
  "tags": ["园艺", "生活"]
}
```

#### E02：多图动态 PIC1

自包含。图片顺序和说明固定在对象中，图片本身以 FileObject 的 ObjId 引用，mime 和尺寸在 FileObject 的 meta 中；推送时可随附这两个 FileObject 的 JSON，供卡片布局直接使用。UI 将 ObjId 解析成当前有权访问的图片地址，不将本机缓存路径写回对象。

```json
{
  "kind": "post",
  "publisher": "<Alice DID>",
  "iat": 1791425100,
  "entry": "cyfs://<Alice Zone>/home/alice/feed/@/garden-0002",
  "content": {
    "type": "image",
    "text": "搭建前后的对比。",
    "media": [
      { "object": "<photo-before 的 cyfile>", "alt": "搭建前" },
      { "object": "<photo-after 的 cyfile>", "alt": "搭建后" }
    ]
  }
}
```

#### E03：视频动态 VID1

包裹。视频文件是一个独立对象，VID1 为它提供标题和封面，时长等描述在视频 FileObject 的 meta 中。封面可用不等于视频已准备完成，播放资源的就绪状态由 Resource Preparation 单独返回。

```json
{
  "kind": "post",
  "publisher": "<Alice DID>",
  "iat": 1791425400,
  "entry": "cyfs://<Alice Zone>/home/alice/feed/@/garden-0003",
  "wraps": "<garden-video 的 cyfile>",
  "content": {
    "type": "video",
    "title": "花箱安装过程",
    "cover": "<video-cover 的 cyfile>"
  }
}
```

#### E04：语音动态 AUD1

自包含。录音保存后成为 FileObject，以 ObjId 引用。未来生成的转写可以作为本地派生结果或另行发表的新内容，不能默默改写此对象。

```json
{
  "kind": "post",
  "publisher": "<Alice DID>",
  "iat": 1791425700,
  "entry": "cyfs://<Alice Zone>/home/alice/feed/@/garden-0004",
  "content": {
    "type": "audio",
    "text": "记录一下今天的种植计划。",
    "media": [{ "object": "<garden-voice 的 cyfile>" }]
  }
}
```

#### E05：长文 ART1

包裹。摘要用于 Feed，正文用于 Reader；正文是 `text/markdown` 的 FileObject，评论因此能够绑定所读的具体内容。修改正文时产生新的正文 FileObject 和新的 ART1 版本，再更新入口。

```json
{
  "kind": "post",
  "publisher": "<Alice DID>",
  "iat": 1791426000,
  "entry": "cyfs://<Alice Zone>/home/alice/feed/@/garden-0005",
  "wraps": "<garden-article-body 的 cyfile>",
  "content": {
    "type": "article",
    "title": "阳台菜园第一周",
    "summary": "从光照、容器到浇水的实践记录。"
  },
  "tags": ["园艺"]
}
```

#### E06：抓取封装 EXT1

包裹。Bob 的 Spider 把网页快照保存为 `text/html` 的 FileObject，起初它只是 Bob 本地的候选对象（§5.6）；Bob 读后选择分享，才发表包裹该快照的 EXT1。对象由 Bob 签署，只证明 Bob 发表了此封装，不表示网站作者参与签名；`source` 只记录出处，不是内容引用，也不是可变入口。

```json
{
  "kind": "post",
  "publisher": "<Bob DID>",
  "iat": 1791426300,
  "entry": "cyfs://<Bob Zone>/home/bob/feed/@/clip-0001",
  "wraps": "<external-article-snapshot 的 cyfile>",
  "content": {
    "type": "article",
    "title": "家庭种植指南",
    "summary": "一篇公开园艺文章的摘要。"
  },
  "source": {
    "kind": "web",
    "original_url": "https://example.org/garden-guide",
    "original_author": "示例网站作者",
    "captured_at_ms": 1791426240000
  }
}
```

网页之后变化，不构成 EXT1 的新版本；Bob 重新抓取并希望更新这条分享时，在同一入口下发表包裹新快照的版本。不同人独立抓取同一网页，各自得到不同的 Feed Object；若快照字节相同，内层 ObjId 也相同，可以据此提示它们是同一内容，但首版不合并它们的评论统计。不保存快照时只能发表链接卡片（参照 E07），不能把原始 URL 当作正文。

#### E07：作品入口 WORK1

自包含的链接卡片。作品栏目按发表者声明的分类组织；Feed 分发入口，作品页面承担实际展示。卡片的标题、摘要和封面固定在对象中，`link` 只是跳转目标，页面后续变化不影响 WORK1 的身份；Alice 调整卡片时通过入口发表新版本。

```json
{
  "kind": "post",
  "publisher": "<Alice DID>",
  "iat": 1791426600,
  "entry": "cyfs://<Alice Zone>/home/alice/feed/@/work-garden-photos",
  "publication_category": "work",
  "content": {
    "type": "link",
    "title": "我的花园摄影集",
    "summary": "这一季的阳台照片。",
    "cover": "<garden-photos-cover 的 cyfile>"
  },
  "link": "https://alice.example/works/garden"
}
```

#### E08：商品入口 PROD1

商品对象可以被评论、收藏和转发；购买操作由 `link` 指向的页面承接。这里演示 DID 形式的可变入口：花架拥有由 Alice 持有的独立内容名字，解析该 DID 得到其内容文档，文档的当前版本就是商品卡片当前的 Feed Object。库存等页面实时状态不进入对象；Alice 改价或改描述时发表新的卡片版本并更新内容文档。没有独立内容名字的商品，使用 Zone 路径入口即可。

```json
{
  "kind": "post",
  "publisher": "<Alice DID>",
  "iat": 1791426900,
  "entry": "<闲置花架的内容 DID>",
  "publication_category": "product",
  "content": {
    "type": "product",
    "title": "闲置花架",
    "summary": "一个可折叠的阳台花架，详情见原始页面。",
    "media": [{ "object": "<plant-stand-photo 的 cyfile>" }]
  },
  "link": "https://alice.example/products/plant-stand"
}
```

### 5.9 评论与互动实例

以下对象都由 Bob 创建，针对 E01 的 P1。它们共享评论索引，通过 `comment_type` 形成正文、点赞、收藏和转发视图；没有正文的特殊评论可以省略 `content`。评论目标是 `references` 中的 `comment_on`；转发类评论包裹原文，目标就是被包裹对象，不再重复写 `comment_on`。

#### E09：正文评论 C1

```json
{
  "kind": "comment",
  "comment_type": "text",
  "publisher": "<Bob DID>",
  "iat": 1791428400,
  "entry": "cyfs://<Bob Zone>/home/bob/feed/@/c-0001",
  "content": { "type": "text", "text": "可以先试试耐阴的叶菜。" },
  "references": [{ "relation": "comment_on", "object_id": "<P1>" }]
}
```

C1 是 Bob 的独立发表，可以进入 Bob 的主页及 P1 的不同评论视图；它的入口位于 Bob 自己的发表流，编辑或撤回只能由 Bob 通过该入口进行。对同一原文再次发表不同观点应创建另一条独立评论，不按“同人同目标”去掉正文评论。

#### E10：点赞 L1

```json
{
  "kind": "comment",
  "comment_type": "like",
  "publisher": "<Bob DID>",
  "iat": 1791428460,
  "entry": "cyfs://<Bob Zone>/home/bob/reactions/@/<由 P1 与 like 派生的互动键>",
  "references": [{ "relation": "comment_on", "object_id": "<P1>" }]
}
```

点赞是自包含、没有正文的特殊评论，默认以公开受众发表（§4.5）。它的入口由互动键确定性派生（§12.4），Bob 对 P1 的点赞只有这一个入口，入口的 Head 就是该互动的当前状态。三个收录来源提供 L1 仍只是一条点赞；同一个 Bob 对 P1 的多个点赞对象也不能直接相加，按 §12.4 的互动键求当前有效状态。

#### E11：私有收藏 B1

```json
{
  "kind": "comment",
  "comment_type": "bookmark",
  "publisher": "<Bob DID>",
  "iat": 1791428520,
  "references": [{ "relation": "comment_on", "object_id": "<P1>" }]
}
```

B1 的存储及查询权限为 Bob 私有，不进入公开发表流，也不投递给 Alice；这由服务端权限和发表策略执行，不能只靠 UI 隐藏。私有记录不对外发表，也不声明入口，它的添加与移除只是 Bob 的本地状态；`iat` 表示该私有对象的创建时间，不代表网络发表。Bob 选择公开收藏时，发表一个带互动键入口的公开收藏对象并签发其 Head，同时在本地记录两者关联，不能顺带公开其他私有收藏历史。查询一个从未公开过的收藏入口，与查询不存在的入口返回相同结果，不泄露私有状态。

#### E12：普通转发 R1

```json
{
  "kind": "comment",
  "comment_type": "repost",
  "publisher": "<Bob DID>",
  "iat": 1791428580,
  "entry": "cyfs://<Bob Zone>/home/bob/reactions/@/<由 P1 与 repost 派生的互动键>",
  "wraps": "<P1>"
}
```

普通转发是包裹 P1 的特殊评论。Bob 的主页展示“Bob 转发了 Alice 的 P1”；Bob 的订阅者收到的是这个可验证转发，推送时可随附 P1 的 JSON；这以 P1 公开为前提，受限对象不能转发（§4.5）。普通转发按互动键维护开关状态，取消转发把 R1 的入口置为已撤回，P1 保持不变。

#### E13：引用转发 Q1

```json
{
  "kind": "comment",
  "comment_type": "quote",
  "publisher": "<Bob DID>",
  "iat": 1791428640,
  "entry": "cyfs://<Bob Zone>/home/bob/feed/@/q-0001",
  "wraps": "<P1>",
  "content": { "type": "text", "text": "准备照这个方案试一次，先从小花箱开始。" }
}
```

Q1 包裹 P1 并附带 Bob 的正文，同时是 Bob 的一条发表和 P1 的特殊评论。引用转发可以有多条，各自使用普通发表入口。普通正文评论、点赞和转发数量分别从类型视图派生，不能因为它进入了多个列表就重复计数。

### 5.10 更新、撤回与再次互动实例

以下 `feed_head` 是入口状态的示意，不是额外的一条正文评论。Head 以 JWT 形式由入口控制者签名；接收方对每个入口只保留已验证的最高序号 Head（§16.6）。

#### E14：P1 更新为 P2

Alice 发表 P1 时已签发入口的第一个 Head H1：

```json
{
  "kind": "feed_head",
  "entry": "cyfs://<Alice Zone>/home/alice/feed/@/garden-0001",
  "seq": 1,
  "state": "active",
  "current": "<P1>",
  "updated_at_ms": 1791424800000
}
```

修改时，P2 是新的 Feed Object，声明同一入口，并用 `base_on` 提示前一版本：

```json
{
  "kind": "post",
  "publisher": "<Alice DID>",
  "iat": 1791432000,
  "entry": "cyfs://<Alice Zone>/home/alice/feed/@/garden-0001",
  "base_on": "<P1>",
  "content": { "type": "text", "text": "调整计划：先搭建两个小花箱。" },
  "tags": ["园艺", "生活"]
}
```

Alice 随后签发 seq=2 的 Head H2：

```json
{
  "kind": "feed_head",
  "entry": "cyfs://<Alice Zone>/home/alice/feed/@/garden-0001",
  "seq": 2,
  "state": "active",
  "current": "<P2>",
  "updated_at_ms": 1791432001000
}
```

接收者验证 H2 的签名属于入口控制者，P2 声明了同一入口且发表者相同，再更新当前发表投影。C1、L1、B1、R1 和 Q1 仍引用 P1，不能因为主页默认展示 P2 就把它们解释为针对 P2 的互动。

#### E15：撤回整条发表

Alice 签发 seq=3 的 Head H3：

```json
{
  "kind": "feed_head",
  "entry": "cyfs://<Alice Zone>/home/alice/feed/@/garden-0001",
  "seq": 3,
  "state": "withdrawn",
  "updated_at_ms": 1791433800000
}
```

P1/P2 不再作为这条发表的有效当前内容推荐；他人评论、转发和私有收藏仍保留各自身份，引用区显示目标发表已撤回。首版只支持撤回整条逻辑发表，只撤回某个历史版本的需求见 §21。

#### E16：取消点赞，再次点赞

Bob 点赞时签发 L1 入口 seq=1 的有效 Head；取消点赞时签发 seq=2、`withdrawn` 的 Head；再次点赞时签发 seq=3 的有效 Head，可以重新指向 L1，也可以指向新建的点赞对象：

```json
{
  "kind": "feed_head",
  "entry": "cyfs://<Bob Zone>/home/bob/reactions/@/<由 P1 与 like 派生的互动键>",
  "seq": 3,
  "state": "active",
  "current": "<L1>",
  "updated_at_ms": 1791429600000
}
```

该互动键的状态依次是有效、撤回、有效，贡献计数依次为 1、0、1。迟到的 seq=1 或 seq=2 Head 不覆盖已知的 seq=3；无法验证的 Head 按 §16.6 处理。取消普通转发同样由 Bob 将 R1 的入口置为已撤回，不改写 P1，也不要求 Alice 代为减数。

### 5.11 关注通知与本地候选投影实例

这一节是辅助记录示例，不把它们伪装成 Feed Object。关注声明复用同一可变入口机制；本地候选投影只是应用状态。

#### E17：关注声明 FOLLOW1

```json
{
  "kind": "follow",
  "publisher": "<Bob DID>",
  "iat": 1791421200,
  "entry": "cyfs://<Bob Zone>/home/bob/follows/@/<由 Alice DID 派生的键>",
  "target": { "publisher": "<Alice DID>", "stream": "<Alice 的发表流入口>" }
}
```

Bob 签署 FOLLOW1，把它写入自己的发表流（受众只有 Alice，§4.5），并向 Alice 的投递入口投递 FOLLOW1 及其 seq=1 的有效 Head，同时启动对 Alice 发表流的 Pull。Alice 据此知道 Bob 关注了自己，但不能推断 Bob 已阅读 P1。若关注由好友关系派生，本地保留好友依据，另一方向由 Alice 的服务独立处理。取消有效关注时，Bob 签发 `withdrawn` 的 Head 并投递给 Alice；再次关注时签发更高序号的有效 Head。“不看 Alice 的朋友圈”只修改 Bob 本地设置，不改变该入口。

#### E18：P1 已进入 Bob 的候选但尚未进入待读

```json
{
  "owner": "<Bob DID>",
  "object_id": "<P1>",
  "source_paths": [
    { "transport": "pull", "subscription_id": "<Bob 的 Alice 订阅>" },
    { "transport": "push", "sender": "<Alice DID>" }
  ],
  "local_topics": ["园艺"],
  "selection": { "state": "not_selected", "reason_code": "reading_window_full" },
  "resources": { "state": "not_prepared" },
  "first_admitted_at": null,
  "opened_from_followed_candidates_at": null
}
```

在 Bob 有效关注 Alice、没有“不看”规则且 P1 所在入口未撤回的前提下，这条候选可以出现在“关注未入 Feed”集合。后来选中并准备完成时，应用写入 Reading Entry、首次入列时间及诸如“来自已关注的 Alice”的推荐理由；P1 的字节和 ObjId 不变。个人点赞状态、评论计数和统计视图也由本地索引组合提供，不附加到 Alice 的签名对象中。

#### E19：构造待读时补充标签并过滤

以下假设 Bob 的评价服务对 P1 作出了“疑似完全由 AI 生成”的判断，仅用于展示本地投影，不代表 E01 的内容实际由 AI 生成。Bob 配置了隐藏此类模型推断结果的规则；待读服务引用 §6 中的通用评价结果形成自己的分类投影：

```json
{
  "owner": "<Bob DID>",
  "object_id": "<P1>",
  "classification": {
    "state": "complete",
    "revision": 1,
    "evaluation_refs": ["<P1 的生成方式评价记录>"],
    "tag_assertions": [
      {
        "tag": "AI生成",
        "action": "add",
        "scope": "whole_content",
        "source": "model",
        "status": "inferred",
        "confidence": 0.86,
        "basis": "<此次推断的依据及已检查的正文／部件范围>",
        "classifier_revision": "<模型与分类策略版本>"
      }
    ],
    "user_overrides": [],
    "effective_tags": ["园艺", "生活", "AI生成"]
  },
  "selection": {
    "state": "filtered",
    "reason_code": "tag_filter",
    "rule_id": "<Bob 的隐藏疑似完全 AI 生成内容规则>",
    "classification_revision": 1
  }
}
```

P1 原始 `tags` 仍是 `["园艺", "生活"]`，它的 ObjId、签名及评论引用均不变。`effective_tags` 是本地分类视图使用的派生结果，过滤还应检查对应判断的来源、状态和作用范围，不能只匹配一个字符串。这里的置信度是模型输出的示意评分，不表示已验证的检测准确率。

Bob 可以移除此标签或将其改为“AI辅助”，通过评价服务保存作用于该内容版本的用户修正；待读服务随即重算有效标签及过滤结果，重新评估候选，资源就绪后才可入列。自动重算不能覆盖这项修正。候选和待读条目共享评价记录；示例中的判断字段可随查询展开返回，无需另存一套独立事实源。待读侧的采用规则见 §8.5。

## 6. 通用标签评价服务：去中心化的 AI Native 自审核

### 6.1 服务定位与调用边界

HomeStation 系统服务提供统一的标签评价能力，支持两类独立请求：**对一个 DID 身份作评价**，以及**对一个 ObjId 或对象路径指向的内容作评价**。它不以存在 Feed Object、候选条目或待读条目为前提，也不要求先关注目标。文件、消息、作品等可寻址内容都可以成为评价目标。

这里的“公共能力”指向当前用户授权的应用、系统组件和 Agent 提供可复用接口；评价结果和所用证据仍按授权范围访问，不因为服务可调用而自动向全网公开。服务可以复用同一进程内的模块、既有模型调用设施与任务机制，不要求另建独立模型平台。具体 API 与 SDK 名称尚待实现对齐，以下为应提供的能力契约。

AI Native 表示模型能参与理解身份上下文、内容及证据，输出结构化标签判断；规则、可信来源声明与人工评价同样是可用输入。去中心化表示各用户自己的 HomeStation 选择评价配置、模型、证据来源及采用策略，允许不同节点对同一目标有不同评价。

**评价与业务处置分开。** 服务回答“在什么范围内、基于什么依据，对该目标作出了哪些判断”；调用方决定提示、排序、过滤、要求进一步确认或拒收。调用评价本身不会修改权限、拉黑联系人、撤回内容或发表公开评论。某个调用方的“放行”也不能替代原有权限检查。

### 6.2 两类目标及对象路径的版本绑定

| 目标 | 输入语义 | 结果必须绑定的范围 |
| --- | --- | --- |
| 身份 | `target.kind = identity`，给出主体 DID | 该 DID、评价维度、观察时点／时间窗口及实际采用的资料、行为或内容证据 |
| 具体内容 | `target.kind = content`，给出 ObjId | 该不可变版本及实际检查的正文／部件范围；不限定对象类型为 Feed Object |
| 路径内容 | `target.kind = content`，给出对象路径，或根 ObjId 与 InnerPath | 请求路径、解析时点、已解析的根／目标 ObjId、内部路径及必要的入口状态依据 |

身份评价可用于识别主题领域、账号性质、已观察到的投递行为等。DID Document 验签只能证明身份或授权声明，不直接证明该身份的能力或信誉。评价某人“频繁投递广告”，必须说明基于哪个观察窗口与哪些可访问记录，不能把一个节点的局部观察表述为全网历史。身份评价中的证据可以引用内容，但某条内容的标签不会自动变成作者的永久标签；对作者的评价也不会自动写入其每条内容。

对象路径沿用既有语义路径和 InnerPath 规则，可由 HTTPS／CYFS 语义地址、已支持解析的 DID URL，或 ObjId 加 InnerPath 表达。裸 DID 指向身份还是命名内容，由请求的 `target.kind` 明确区分，不仅根据字符串外观猜测。路径输入只是定位手段，不能把可变 URL 当作被评价内容的版本身份。

评价开始前，在调用者有权读取的范围内解析路径并固定此次评价目标。路径若指向 Feed 入口，先取得并验证 Head，再确定具体内容 ObjId；若指向容器内成员，记录根 ObjId、InnerPath 及最终成员 ObjId。InnerPath 的结果如果只是普通 JSON 值，没有独立 ObjId，则以“不可变根 ObjId + InnerPath”固定目标，不能虚构一个内容 ID。针对局部字段或媒体部件的评价必须保留局部范围。

任务执行过程中路径发生变化，不应悄悄替换正在评价的对象。结果只描述已固定的版本；调用方按“路径当前内容”使用它时，需要重新核对路径／Head 是否仍绑定该版本。路径已改指新对象时，旧结果可以作为历史读取，新对象需重新评价。目标不可获取、已撤回或解析失败时返回明确状态，不把失败解释为负面评价，也不据此创建候选。

### 6.3 评价请求与结果的最低语义

请求指定目标、需要的评价维度、评价配置及必要上下文；还可设置可接受的结果年龄、是否刷新、证据获取范围、时间／资源预算。评价主体及可访问范围来自调用身份和授权上下文，调用者不能通过填写另一个用户 DID 获得其私有评价视角。

| 结果概念 | 最低要求 |
| --- | --- |
| 评价身份 | 结果标识、承担评价的主体／授权执行者及可见范围，区分评价者与被评价目标 |
| 目标绑定 | 原始请求目标、实际评价的身份或内容版本；路径目标包含解析记录 |
| 标签判断 | 维度与标签标识、取值／支持或否定状态、整体或局部作用范围；使用维度命名空间和词表／配置版本区分含义，显示文字相同不代表同一标签 |
| 来源与依据 | 规则、模型、作者声明、第三方评价或人工判断；记录可追溯的依据摘要及证据引用 |
| 评价上下文 | 评价配置／规则／模型版本、观察窗口和证据快照；本地模型上下文不等于可公开的内容 |
| 时间与适用性 | 使用 `iat` 表示本次评价产生时间，单位为 Unix 秒；另记有效期或需刷新的条件 |
| 结果状态 | 完成、部分完成、未知／证据不足，以及各维度的覆盖范围；任务状态与标签判断分开 |
| 不确定性 | 模型推断、声明或人工确认分别标明；可附来源相关的置信度，不把不同模型分数当作统一事实概率 |

可以同时评价多个维度，例如主题、生成方式、内容质量和广告特征；维度及词表可扩展，不以一组 Feed 分类枚举限制公共服务。未请求、未检查和判断为否是不同状态。任务完成只说明本次处理结束，仍可能有未知维度或未检查的部件。

评价记录保持独立。它既不改写目标对象的 `tags` 或 DID Document，也不强制成为公开 Feed Object。人工纠正通过保存针对目标、维度和适用范围的覆盖记录实现；自动重算保留原始评价及覆盖关系。调用方使用获准读取的记录和自己的采用策略，构造“有效标签”视图。用户全局修正与仅对某应用／配置生效的修正应明确区分，避免一个应用的操作改变所有场景。

### 6.4 公共调用能力与执行过程

| 能力 | 输入与操作 | 返回或效果 |
| --- | --- | --- |
| `evaluate` | 身份／内容目标、维度、配置、证据范围与预算，可批量请求 | 可复用的评价结果，或可查询的任务标识及当前状态 |
| `get_evaluation` | 结果／任务标识，或带目标与配置条件的查询 | 有权查看的结果、覆盖范围、时效、证据摘要及失败原因 |
| `refresh_evaluation` | 目标或已有结果、刷新原因和预算 | 在当前证据／版本下重新评价，保留新旧结果关系 |
| `set_tag_override` | 明确目标、维度、添加／否定／替换操作及作用范围 | 持久人工修正，或撤销已有修正；更新相关有效标签视图 |
| 评价变化通知 | 获准关注的目标／结果范围及继续读取位置 | 新结果、过期／失效及人工修正的通知；可先用轮询实现 |

这些名称表达接口职责，不宣称当前仓库已有同名服务方法。评价流程为：鉴权与预算检查 → 解析并固定目标 → 查找符合条件的可见结果 → 必要时收集证据并执行规则／模型 → 保存评价记录 → 返回或通知调用方。任务排队、执行中、超时、取消及失败需要可查询，不能让调用方无限等待，也不能把任务失败返回为“正常／通过”。

服务按需执行，也可由用户规则触发刷新，不要求预先评价所有 DID 或下载所有内容。依赖正文、图像、语音等的维度明确资源预算与覆盖范围；仅有封面时可返回局部评价或未知。调用不会隐式创建订阅、遍历目标全部社交关系或无限扩展证据采集。外部模型调用继续遵守 §10.3 的授权与数据外发约束；被评价内容作为数据处理，不能把其中的指令变成服务权限。

### 6.5 复用、时效与多来源评价

结果复用至少区分评价主体及可见范围、实际目标版本、维度、评价配置／模型版本、证据快照和影响判断的上下文。授权和这些条件相容时，待读、联系人提示及其他应用可以复用结果；不能仅凭目标 DID 或 ObjId 相同就跨用户、跨权限、跨配置复用。必要时只向调用方返回获准披露的结果字段，私有证据不随摘要泄露。

内容字节由 ObjId 固定，但评价可能随证据、模型或用户修正而变化。身份评价还需考虑观察窗口和新行为，不能作为永久信誉标签。路径结果按 §6.2 校验当前绑定，模型／配置或证据变化触发失效或重算；原始评价记录、人工修正和可重算视图分别保存，旧任务较晚完成不能覆盖较新的视图修订。

结果默认在本用户授权范围内使用。用户选择对外共享时，由评价主体签发独立命名对象并明确目标、依据范围与时效；可以通过既有对象读取／投递机制流通，也可以被 Feed 包裹引用，不因产生评价而自动群发。接收方验证签名、目标版本及来源，并按自己的策略采用。签名证明评价出自谁，不证明评价必然正确；多个来源的不同判断分别保留，重复转发和同一来源的多份副本不能变成多票共识。

#### E22：评价对象路径中的一个成员

Agent 请求评价 Alice 作品容器中的 `garden-001`。解析时将容器和成员版本固定下来：

```json
  "result": {
    "result_id": "<作品成员主题评价记录>",
    "evaluator": "<Bob DID>",
    "target": { "kind": "content", "object_id": "<WORK1>" },
    "resolution": {
      "requested_path": "https://<Alice Zone>/alice/home/works/@/garden-001",
      "resolved_at": 1791435600,
      "root_object_id": "<作品容器本次版本的 ObjId>",
      "inner_path": "/garden-001",
      "resolved_object_id": "<WORK1>"
    },
    "iat": 1791435600,
    "visibility": "private",
    "state": "complete",
    "profile_revision": "<配置与模型版本>",
    "evidence_refs": ["<WORK1>"],
    "assertions": [
      {
        "dimension": "topic",
        "tag": "园艺",
        "value": true,
        "scope": "link_card",
        "source": "model",

      }

  }

```

这里评价的是 WORK1 链接卡片中已固定的内容，未自动评价 `link` 指向的外部页面。该路径以后指向另一个作品时，不能沿用这个结果描述新作品。若调用者本来就持有容器 ObjId，可直接用根 ObjId 与相同 InnerPath 定位，省去可变路径查找；最终仍需记录真实评价范围。

### 6.7 业务接入方式

| 调用场景 | 使用的评价 | 由调用方决定的动作 |
| --- | --- | --- |
| 待读构建、分类与检索 | 内容主题、生成方式、质量等 | 按用户规则生成有效标签、分类、排序或过滤，见 §8.5 |
| 联系人／身份详情与 Agent 判断 | DID 的领域、账号性质及有依据的行为标签 | 展示提示、选择来源或请求进一步确认，不自动授予身份权限 |
| Social Inbox 准入 | 发送者 DID 与本次投递内容的独立评价 | 在既有授权基础上决定接收、暂存或拒收；资源不足时按本地策略处理 |
| 文件、作品或消息检查 | 无需先封装 Feed 的具体 ObjId／对象路径评价 | 提示用户、归类、发表前检查或决定后续任务 |
| 收录者索引 | 内容评价及获准采用的第三方记录 | 按收录策略组织视图，保留评价来源，不改写原对象 |

首版需由至少一个其他应用或 Agent 验证两类非 Feed 调用：直接评价 DID，以及直接评价未进入候选集合的内容／路径。仅把待读管线内部的分类函数改名，不算完成公共评价能力。

## 7. 候选输入：Social Inbox 与 Spider Cache

### 7.1 两个入口，一个逻辑候选集合

Social Inbox 接收别人 Push 的内容；Spider Cache 保存主动 Pull 的内容。二者不必共享同一物理存储，但上层应以统一的 Feed Object 候选视图处理它们。

候选只是“可能值得后续考虑的素材”。进入候选集合不代表已经进入待读列表，更不代表用户已经看到。

### 7.2 轻量候选原则

Social Inbox 原则上只接收 JSON 级对象、必要的小型内容和资源的 ObjId 引用（可随附被引用对象的 JSON，见 §5.5），尽量不在接收阶段下载图片、视频等重型资源。

Push 和 Pull 都有容量限制。准入较宽不等于存储无限，也不等于任何发送者可以要求接收方承担无限流量或抓取成本。

Spider 有一个必要例外：某些资源只能在当前抓取 Session 中获取，若不同时保存，之后可能失效。因此 Spider Cache 可以在候选阶段预先缓存这部分资源。

### 7.3 社交准入

HomeStation 的社交 Inbox 应允许比私人聊天更广泛的内容触达，包括直接好友、主动订阅的发布者、符合用户规则的间接关系，以及用户允许的商业内容来源。

准入在 HomeStation 的投递入口执行。所依据的好友等级与联系人分组读自 Message Center（§3.2），但不套用聊天的陌生来源请求箱规则。

例如用户关注 A 并在 A 的内容下评论，B 通过 A 或讨论参与关系发现该用户，有机会向其投递内容。但这种可发现性不是绕过接收方权限的通行证：是否允许 B 进入候选，仍由接收方准入规则决定。

宽准入表示允许更广泛的关系和内容来源，不表示取消权限校验，也不表示让陌生来源无条件进入。

准入与推荐分离：准入解决是否接收，推荐解决是否值得展示。广告或间接关系内容即使已入候选，也不能由发送者自行提升为待读内容。

### 7.4 投递结果与准入披露

投递入口基于 CYFS dispatch，发送方得到的结果分两层：传输结果说明对象是否已被接收方可靠接收，准入披露说明接收后的处理档位。两层不能混用。

**传输结果**直接采用 CYFS dispatch 的定义：

| 结果 | 语义 | 发送方的处理 |
| --- | --- | --- |
| 无响应 `no_response` | 未取得可确认的结果，接收方可能已经收到 | 保留重试，不解释为拒绝 |
| 拒绝 `rejected` | 投递入口或准入规则明确拒绝，带原因及是否可重试 | 按 `retryable` 处理；原因可以只是笼统的“未准入”，不需要公开内部规则 |
| 已缓存 `cached` | 网关在 HomeStation 不可达时尽力暂存并稍后转投，对象仍可能丢失 | 继续保留重试责任，不当作已投递 |
| 已接收 `accepted` | HomeStation 已完成持久接收与准入，或确认此前已接收同一投递 | 投递完成 |

`cached` 只是传输层的暂存，与对象是否进入候选无关，网关此时也还没有执行准入。

**准入披露**只随 `accepted` 给出，作为 dispatch 状态体中的附加字段，也可以省略：

| 披露 | 语义 | 不代表什么 |
| --- | --- | --- |
| 已入候选（candidate） | 已作为候选接收，等待后续处理 | 不承诺进入用户 Feed |
| 优先处理（preferred） | 根据关系和接收策略给出更高一档的接收预期，内容大概率进入后续阅读处理 | 不等于已展示、已读或保证最终入列 |

准入拒绝通过传输结果 `rejected` 表达，不另设披露值。披露是语义标签，字段编码见 §21。

接收方可以隐藏内部处理粒度：即使内部已采用较高接收级别，也可以只返回 `accepted` 而不附披露。**信息披露策略与接收结果是两个维度**，不能把隐藏状态变成额外的“已读”承诺。

幂等与重试沿用 dispatch 的语义：以对象 ObjId 和投递目标去重，同一对象重复投递不产生重复候选；未得到 `accepted` 时发送方保留重试责任，`no_response` 不能解释为接收方拒绝。

### 7.5 Spider 的实现自由

Spider 可以由规则程序、常规爬虫、LLM Agent 或其组合实现。协议只关心它能否产出合法 Feed Object 并写入候选缓存。

首版主要处理两类公开来源：原生 HomeStation 的发表内容，以及传统互联网内容。如何选源、多久抓一次、如何摘要和分类，是可替换的应用策略。

对于已是原生 Feed Object 的内容，不应仅因从另一个 URL 抓到就重新封装并丢失原对象身份；需要附加自己的语境时，应包裹原对象的 ObjId（§5.5）。对于同一对象的多次到达，应保留不同来源路径，同时避免重复存储同一对象。

### 7.6 关注、好友与“不看朋友圈”

用户主动关注某人后，HomeStation 应向对方发送由关注者签署的关注声明，并启动对其发表流的持续 Pull。取消有效关注时，在该声明的入口上签发已撤回的 Head 并通知对方（E17）；通知失败保留重试状态，不阻止已经具备读取权限的采集，也不向用户假称对方已经收到。被关注者知情不代表该关系必须向所有人公开，关注名单的公开展示仍按用户权限处理。

**好友关系比关注关系更强，Message Center 中的好友默认互相关注。** 双方各自的 HomeStation 根据本方已有好友关系派生关注并维护自己的声明，不能由一方伪造另一方的签名。关注本身不反向提升为好友，也不授予私聊权限。

实现中保留关注的来源依据，例如用户主动关注、好友关系派生。相同对象由多个依据产生关注时只维护一个有效关系和一套采集进度；好友关系解除后移除好友派生依据，仍有主动关注依据时继续关注。好友仍存在时，仅移除主动关注依据不会取消好友默认关注；只想停止看到对方动态，应使用“不看朋友圈”。对方主页的关注者数量按已收到的有效声明去重统计，不能把本方联系人数量当作对方已确认的关注者数量。

| 用户行为或关系 | 关注与采集 | 展示效果 |
| --- | --- | --- |
| 主动关注某人 | 建立关注、通知对方、持续 Pull 入候选 | 候选经过筛选与准备后才进入待读 |
| 成为 Message Center 好友 | 双方默认派生关注并各自采集 | 默认按关注内容处理，不保证每条都入列 |
| 不看某人的朋友圈 | 保留好友和关注关系，按采集策略继续维护候选 | 默认 Feed 与关注补看入口隐藏该人的直接动态 |
| 不看某个联系人分组的朋友圈 | 复用 Message Center 分组成员，动态应用本地规则 | 对该组成员执行相同隐藏规则，分组变化后重新计算 |
| 恢复看朋友圈 | 不重复创建关注，也不重复采集已有对象 | 对仍在保留范围内的内容恢复正常筛选与补看资格 |

“不看”是私有展示设置，不作为取消关注或拉黑通知发给对方，不改变聊天权限，也不改变他人查看我的权限。明确的个人或分组“不看”规则优先于默认关注规则；多个隐藏规则同时命中时，解除其中一条不会绕过其他规则。规则变更应作用于已有待读条目，生效时遵循浏览位置稳定原则。

首版“不看”作用于该人发表的条目，包括其原创、评论和转发；其他未被隐藏用户对这些内容的独立引用仍属于引用者的发表，不推导为全网内容封锁。UI 保留原作者与引用者的区别。

### 7.7 来源、订阅意图与 Topic

Source 表达可采集入口，Subscription 表达用户为什么持续采集它。Follow、粘贴 URL 和自然语言输入最终都进入这套管理模型：保存原始意图、解析得到的一个或多个来源、所属用户、有效状态、采集进度、最近成功时间与失败原因。自然语言订阅由 Agent 持续维护来源映射，不能退化为一次搜索后丢弃用户意图。

对具备 HomeStation 关注入口的主体执行知情通知。普通网页或 RSS 没有该能力时，记录“来源不支持关注通知”，按公开读取能力采集，不捏造送达确认，也不通过无关渠道发送通知。暂停采集是运行设置，取消订阅是关系变更；只有所有有效采集依据都消失后，才停止相应共享任务，历史对象按保留策略处理。

Topic 的内容标签、用户订阅和聚合视图应分别保存。用户可订阅某个主题意图，系统将抓取结果映射到本地 Topic；作者原始标签保留在内容中，本地分类按 §8.5 形成有效标签，不会改写已签名对象。Topic 分类与本地汇总使用同一份有效标签及展示规则；数量和热度按本地有效内容及明确时间窗口计算，并标明范围，不把本地排行称为全网热榜。

## 8. 推荐与内容准备：生成统一待读列表

### 8.1 持续运行的用户侧服务

推荐服务根据用户当前状态，从候选集合中挑选有限数量的内容。其输入可以包括用户配置的话题、分类目标、当前状态、经允许使用的位置线索，以及本地阅读反馈。

实现可以从简单程序开始，也可以使用复杂 LLM 或 Agent。HomeStation 不要求所有节点运行同一模型，也不要求 LLM 参与每一次排序。

位置和状态只是可使用的输入，不应被设计成所有用户必须提供的信息。

筛选结果需要附带可展示的推荐理由，例如关注来源、命中的主题或用户规则，并保存在本地 Reading Entry 中。理由可以由规则或模型产生，至少能关联实际采用的来源或条件；不要求公开完整算法，也不能让来源作者替阅读者声明“为什么推荐”。

### 8.2 筛选与准备是两个不同职责

```text
候选对象
   │
   ▼
本地标签分析／修正 → 应用用户过滤规则
   ├─ 被过滤：记录命中规则，按候选保留策略处理
   │
   ▼
推荐筛选
   ├─ 未选中：保留为候选或按策略淘汰
   │
   └─ 被选中
        │
        ▼
     内容准备
        ├─ 成功：补全标签判断，复查过滤规则，通过后入列
        └─ 未完成：保持准备状态、重试或按策略放弃
```

推荐回答“值得看什么”，资源准备回答“现在能否顺畅地看”。不能把一个推荐分数较高、但正文或必要媒体尚不可用的对象直接等同于已经准备好的条目。

两者可以由同一个服务执行，也可以拆成不同模块。标签判断可以先利用已有内容；依赖正文或媒体的判断在资源准备后补全，入列前复查用户过滤规则，不能因为先前的推荐分数而跳过过滤。

### 8.3 入列时的内容准备

进入待读列表之前，尽可能下载正文、图片、视频等必要资源，使用户开始浏览时无需再从头发现和抓取内容。

资源都以 ObjId 引用，可以从发表者 Zone、收录者或其他持有者获取，取回后按 ObjId 校验，来源本身不必可信。是否预先完整下载、可用存储与流量预算，由用户配置；不预取的资源在准备阶段检查是否有可达来源。

一次可达性检查不能保证来源永远在线。因此，首版应区分“资源已在本地”和“依赖可达来源”，记录必要的检查状态，并在阅读时支持重新获取、重试或清楚提示不可用。

对于只准备了封面而视频不可用的条目，不应向用户暗示视频已完整就绪。采用流式播放或其他降级策略时，应与用户配置一致。

### 8.4 统一而有限的列表

HomeStation 维护一个统一的待读列表，具有顺序、时间信息和分类相关状态。AI 在整体筛选时已经考虑分类，不需要为每个分类独立生产一套候选与资源副本。

“统一列表”不意味着无限保存所有历史。“有限”也不意味着用户只能看到一屏；它表示准备窗口与保存范围受容量策略控制，可以持续补充、更新和淘汰。

看过内容不会自动触发删除。保存历史、移出待读窗口和清理资源是不同的本地策略。

### 8.5 本地标签修正与内容过滤

待读构建是 §6 通用标签评价服务的一个调用方。Selection Service 对候选 ObjId 请求需要的内容评价维度，按用户策略采用结果，补充分类、纠正误标，并添加作者没有提供的标签，例如“AI生成”；调用不依赖作者主动标注。其他应用可以独立评价同一内容，也可以直接评价 DID 身份，无需经过候选或待读流程。

原始 `FeedObject.tags` 属于不可变签名内容。待读服务引用获准使用的评价记录、用户修正及采用策略，合并产生 `effective_tags`，不把评价记录复制为另一套分类事实源。修正包含添加、屏蔽和替换；替换在本地表现为屏蔽旧标签并添加新标签，不生成新的 Feed Object。人工修正在其声明的作用范围内优先，自动结果与作者标签冲突时按用户策略取舍并保留依据；重复 Push／Pull 复用相同目标与评价配置的结果。

“AI生成”的使用约定：

- 区分作者声明、模型推断、用户确认及其他来源；模型推断展示为“疑似 AI 生成”，作者声明也只证明作者作出过该声明。
- 区分完全生成、辅助创作和局部部件生成；仅封面或某个部件使用 AI，不能据此把全文标为完全生成。资源不足、分类失败或没有标签时，状态为未判断／未知，不能反向认定为人工创作。
- 生成方式与内容质量分别标注。“AI生成”和“低质量”可独立或组合过滤，用户可以选择隐藏完全生成的内容，也可以只隐藏同时被判断为低质量的内容。
- 过滤规则明确接受哪些来源、是否接受模型推断、推断阈值及未知状态如何处理。模型分数不作为事实证明；用户可查看过滤原因、纠正标签或显式查看被过滤的内容。

候选筛选、待读分类、Topic 和关注补看共享有效标签及适用的过滤规则。默认主 Feed 即使不选择某个分类，也继续应用用户的排除规则。被过滤不等于撤回、已读或资源准备失败，不删除原对象、个人收藏或评论；过滤不阻止入口 Head 的同步。用户主动解除过滤或查看单条内容仍需通过访问权限、撤回状态与资源就绪检查。

分类结果变化、用户修正或规则调整后，重新计算已有候选和待读视图，保留稳定游标；不需要重新抓取或改写原对象。人工修正与筛选偏好属于持久私有状态，不随临时行为日志清理。新版本有新的 ObjId，应重新分类，不能直接继承旧版本的判断或单对象人工修正。需要长期作用于某个作者或入口的偏好应另存为用户规则。

## 9. 分类、游标与 Feed UI

### 9.1 无分类视图是主入口

默认主 Feed 是统一待读列表的无分类视图，即不应用类别限制的阅读入口。这里的“无分类”不是“没有被打标签的内容”这一单独类别。

其他分类是在同一列表上形成的视图，例如某个话题、来源或用户配置的分类条件。标签分类使用 §8.5 的本地有效标签，同时应用用户排除规则。同一个对象可以匹配多个视图，但不因此变成多个独立内容对象。

### 9.2 每个分类独立维护游标

每个分类视图，包括默认主视图，都有自己的浏览位置。

```text
统一待读列表
   ├─ 默认视图：游标 A
   ├─ 技术视图：游标 B
   └─ 其他分类：游标 C
```

待读列表不是必须严格出队的生产者—消费者队列。用户可以从最新内容开始，也可以回到上次位置，由用户配置决定，不应强制补看全部“尚未消费”的旧条目。

### 9.3 动态更新时保持浏览稳定

以下是实现建议，而非网络协议：

- 游标优先引用稳定条目身份或顺序锚点，不仅保存容易随重排变化的数组下标。
- 用户正在浏览时，后台补充和重排不应导致当前内容突然跳走。
- 返回某个分类时，处理好游标对应条目已被淘汰的情况。
- 区分内容发表时间、加入待读时间和实际消费时间，不用一个时间字段混淆所有语义。

首版可以采用统一排序、分类过滤的简单模型，再演进到更复杂的阅读体验。

### 9.4 UI 的职责边界

主 Feed UI 从待读服务获得当前分类的可阅读内容，负责展示、展开、播放、发表互动、切换评论视图和保存浏览位置。关注补看入口按 §9.5 查询候选并按需准备资源，不能伪装成已准备好的待读视图。

UI 不负责在每次打开页面时重新运行完整抓取与推荐流程，也不应直接把外部内容页面当成有权操作用户系统的代码。

阅读列表、个人发表主页和评论列表需要在数据接口与页面语义上明确区分，避免将私人推荐结果意外展示给访客。

### 9.5 来自关注对象但未进入 Feed 的内容

原型中的“已关注”筛选继续表示待读列表中来自有效关注对象的内容。另提供一个私有补看入口，查询已经获取、来自有效关注对象、仍在保留范围内且尚未进入过待读列表的候选。该入口同样尊重撤回、访问权限、“不看某人／分组”及适用的标签过滤规则，不把用户已排除的内容自动换一个入口展示。

它可以包含尚未筛选、未被选中或资源仍在准备的对象，应显示对应状态。关注提高采集的确定性，不构成全部内容入列的承诺；未抓取到或已淘汰的对象不在此集合中，界面应说明保留范围与同步状态，不宣称它是来源完整历史。

该集合是 Candidate Store 上的查询，不创建第二套对象副本，也不要求预先下载全部资源。用户主动打开某条内容时，可以绕过推荐评分请求资源准备，成功后阅读或按用户选择加入待读；资源不可用时保留清楚提示，不能绕过访问权限。

为区分“从未进入 Feed”和“曾进入但已移出”，保留对象首次入列记录，而不能只用当前两个列表做差集。直接从补看入口阅读也保存独立状态，默认补看视图排除已经这样读过的内容；它们不是临时曝光日志，不能随日志清理立即再次出现。此最小历史至少覆盖对应候选的保留期。

### 9.6 阅读模式、搜索与个人门户

标准、读图、长文和沉浸式模式复用同一对象和资源解析，阅读模式是展示方式，不改变对象身份。类别、Topic 与当前搜索条件共同定义查询视图，切换模式不能暗中丢弃这些限制。不同视图的游标使用稳定对象锚点；图片组序号、播放位置等属于本地阅读状态。

首版搜索覆盖当前查询范围内的标题、正文和作者，明确与全网搜索、来源全部历史区分。已完整加载的小列表可以在 UI 过滤；分页时由应用查询层对同一范围搜索，不能把“当前页无结果”当作整个视图无结果。

个人门户复用既有用户身份与资料能力，地址为 `https://<Zone>/homestation/<用户名>`（§4.6），任何人都可以打开，登录用户按自己的身份读取。门户内容就是该用户发表流的展示读取（§4.4），按访客身份只返回其受众允许的条目，包括用户的正文、评论与转发；私人待读与候选接口只向所有者开放。作品、商品通过发表者提供的内容分类组织；精选由用户维护对象引用与顺序，改变精选不修改原对象。作品和商品可以是链接卡片（E07、E08），详情操作进入 `link` 指向的作者页面，首版不要求 HomeStation 实现交易或网页创作引擎。

### 9.7 图片、视频、语音与素材发布

媒体发布复用既有文件／命名对象存储，流程为“上传或录制 → 素材存入命名对象存储 → 取得 FileObject 的 ObjId → 创建 Feed Object 并签发入口 Head → 写入发表流并投递”。图片顺序、说明和封面属于 Feed Object 的内容，媒体类型、尺寸、时长属于 FileObject 的描述；临时上传地址和访问令牌不能进入对外对象。

上传失败不显示为发布成功。客户端以一次发布意图的幂等标识重试，避免生成多条相同动态。未发表素材可按草稿保留期清理；已经发表、收藏保留或仍被其他有效对象引用的资源不能随普通缓存一起淘汰。撤回发表后再按引用、保留与访问策略清理资源，不承诺回收其他节点的副本。

## 10. 本地行为反馈与隐私边界

### 10.1 形成两个反馈回路

UI 需要采集必要的消费信号，例如实际展示、停留、点击、展开、播放及主动操作结果。它们反馈到两个层面：

```text
本地消费行为 ──> Spider：以后去哪里、找什么
本地消费行为 ──> 推荐层：已有候选中选什么、如何组织
```

这些数据用于帮助个人应用改进，不是默认向原作者或广告商发送的网络回执。

### 10.2 本地、临时、由用户控制

原始行为数据默认只在用户控制的本地环境中临时保留，不对外发送。其格式、抽样、统计和淘汰属于应用实现，不纳入 Feed 网络协议。

用户主动保存的收藏、点赞状态及其入口状态不属于这里的临时行为日志，应独立持久保存。清理浏览事件或待读窗口不能顺带清除收藏，也不能使已知取消的互动恢复有效。

如需从原始事件形成较长期的偏好状态，也应明确保存目的、用户控制方式和清理策略，不能把“临时本地记录”偷偷变成默认永久行为档案。

停留时间、点击或播放记录不直接等同于真实兴趣。如何解释这些信号，属于可演化算法，不在协议中写死判断阈值。

### 10.3 云模型调用是需要显式控制的外发路径

Self-hosted 部署本身不能替代数据外发控制。若 Spider 或推荐模块调用外部模型，将原始行为、个人位置或可识别用户偏好写入请求，同样构成向第三方发送数据。

因此建议将这些数据的外发权限与普通公开内容处理分开管理。默认本地反馈闭环不得以“调用 AI”为由自动越过隐私边界；外发必须符合用户明确授权的范围。

公开 Feed 内容也应被视为待分析资料，而不是允许 Agent 修改权限、泄露行为数据或发起任意投递的操作指令。

## 11. 自愿反馈与消费证明

### 11.1 快速反馈就是特殊评论

**点赞、点踩、收藏等主动互动都是特殊类型的评论，因此也是 Feed Object。** 它们由互动者创建，引用目标内容的具体 ObjId，并表达互动类型。普通评论用正文表达观点，特殊评论用结构化动作表达观点或个人标记，不再另建一套独立的 Feedback Object 传播与统计系统。转发同样属于特殊评论，其发表和取消规则见 §12.5。

特殊评论对外发表时由互动者签名，沿用评论的投递、收录、Pull、来源合并及视图机制。内容作者可以提供自己的互动列表和统计，但不能成为点赞数、收藏数等数据的唯一事实来源。接收方根据实际获得的有效记录计算结果，统计规则见 §15.5。

统一对象模型不改变可见性：收藏默认保存为私有的特殊评论，不进入公开发表流，不向原作者、好友、讨论参与者或公共收录者投递，也不计入公开收藏数。用户明确选择公开收藏时，才发表带互动键入口的公开收藏对象。公开改回私有时，将该入口置为已撤回并保留本地收藏状态，不能承诺删除已传播副本。

点赞默认以公开受众发表，界面在首次点赞时告知用户点赞是公开的；被点赞对象受限时，受众固定为原作者（§4.5）。其他互动是否对外发表，应由清晰的操作语义和用户授权决定。本地状态、公开入口状态和投递状态分别保存。取消已公开的点赞或收藏，需要由互动者在该入口上签发撤回 Head 并传播，不能仅在本地减一或删除记录；再次操作签发更高序号的有效 Head，规则见 §16.4—§16.6。

这些持久的个人操作状态与 §10 的临时消费事件不同。快速反馈也不等同于消费证明，不因采用统一评论模型而自动参与经济约定。

### 11.2 消费证明的目的

部分商业内容可能希望用户提供消费回执。HomeStation 将这种对外声明称为**消费证明（Proof of Consumption）**，用来承载未来注意力经济中的约定履行信息。

例如双方约定用户完整观看一段视频后获得某项权益，用户完成消费后，自愿发送描述该行为的签名声明。

正常阅读不以发送消费证明为前提，内容对象提出回执请求也不等于用户已经同意发送。

### 11.3 消费证明的最小语义

| 概念 | 含义 |
| --- | --- |
| 消费目标 | 对应哪个具体 Feed Object 版本 |
| 消费行为 | 声明进行了什么行为，例如完成视频播放 |
| 行为结果与必要时间信息 | 表达约定要求的最小事实范围 |
| 签署主体 | 与用户 DID 或被允许的身份机制有关的签署身份 |
| 验证材料 | 验证声明来源和完整性的签名信息 |
| 接收方/约定关联 | 如未来经济协议需要，关联相应接收方和约定 |

后两类关联的具体编码、重放防护及结算使用方式，留给后续协议细化。首版只需要明确对象机制和用户授权边界，不需要完整商业闭环。

签名证明某个身份签署了声明，不能仅凭签名证明自然人确实注意到内容。当前“君子协议”模型不应被包装成强反作弊的注意力证明。

### 11.4 匿名性与最小披露

未来可以考虑 Tracker ID、场景身份或其他方式降低主 DID 暴露，但仅更换标识不自动等于不可关联匿名。其与签名身份、跨内容跟踪和跨服务关联的关系仍需单独设计。

首版不应宣称已经实现完整匿名方案，也不应把全量停留、点击日志附在消费证明中。只发送用户同意、且对应约定真正需要的内容。

## 12. 评论即 Feed Object

### 12.1 评论是独立发表

用户 B 评论 A 的内容时，B 创建一个新的 Feed Object，正文是自己的评论，并引用 A 内容的具体 ObjId。

评论可以默认出现在 B 的个人发表流。别人打开 B 的主页时，可以看到“我评价了某个内容”，被评价的原文位于引用区。被评论的对象受限时，评论的受众固定为原作者，不出现在 B 的公开主页（§4.5）。

这使得经常评论、但很少发表长篇原创的用户同样拥有自己的内容流。评论的发表、保存与传播不依附于原作者的服务器。

### 12.2 引用语义示意

以下仅是帮助理解的语义草图，不是最终 JSON Schema；对象 ID 和签名由既有对象体系生成或承载。

```json
{
  "kind": "comment",
  "comment_type": "text",
  "publisher": "<评论者 DID>",
  "iat": "<创建／签发时间，u64 Unix 秒>",
  "entry": "<评论者发表流中的可变入口>",
  "content": {
    "type": "text",
    "text": "这是我对该版本内容的评论。"
  },
  "references": [
    {
      "relation": "comment_on",
      "object_id": "<被评论 Feed Object 的具体版本 ID>"
    }
  ]
}
```

不应将这里的 `comment` 再实现成一套与 Feed Object 平行、不参与普通发表和传播的独立内容体系。

若将来支持多级回复，可增加“回复哪个评论”与“属于哪个根内容讨论”的关系，但回复目标同样需要版本明确；具体关系字段尚未冻结。

### 12.3 内容与评论同等重要

本设计将内容与其评论视为同样重要的信息组成部分。评论可以影响阅读者的理解，因此发布权的开放不能以作者独占评论呈现权为代价。

作者可以表达自己希望保留和排序哪些评论，但阅读者必须能够选择其他评论来源和组织方式。

### 12.4 普通评论与特殊评论共享底层能力

评论对象至少区分普通正文评论、点赞、点踩、收藏、普通转发和引用转发等语义类型；这里的名称是语义分类，不是已冻结的字段值。所有类型都具有独立对象身份和明确的目标版本，对外发表的记录必须能验证发表主体。

普通评论允许同一用户对同一内容发表多条独立观点。对于点赞或收藏这类开关操作，以“互动者 DID + 目标版本 ObjId + 互动类型”标识一个逻辑互动状态，同一键至多贡献一个有效计数。互动对象的可变入口由互动键确定性派生，位于互动者自己的命名空间（例如 `cyfs://<Bob Zone>/home/bob/reactions/@/<互动键摘要>`），因此一个互动键在正常情况下只有一个入口，入口的 Head 就是该互动的当前状态，取消和再次点赞都是该入口的状态更新。多个新 ObjId、重复点击、多路径投递或重试都不能让同一个点赞被计为多次；即使互动者为同一键制造了多个入口，统计仍按互动键至多计一次。

UI 可以把普通评论展示为讨论列表，把特殊评论展示为按钮状态、数量及可查看的参与者列表。类型筛选只改变展示，不建立互不相通的收集系统；显示“评论数”时应说明是否包含特殊评论，默认可只统计普通正文评论。

私有特殊评论使用同一对象与索引模型，但始终受所属用户的访问权限约束。只有允许对外发表的部分参与 §13 的传播；收到点赞也不意味着必须将其作为普通正文卡片插入主 Feed。

### 12.5 转发也是特殊评论

普通转发创建一个由转发者签署、包裹原文具体版本的新 Feed Object，正文可以为空；引用转发同样包裹原文，并附带转发者的正文。两者都进入转发者自己的发表流，按转发的受众通知相关方，受限对象不能转发（§4.5），并沿用评论列表的收集与统计能力。

UI 同时展示转发者与原作者，不能把转发者伪装成原作者，也不能把转发行为仅实现为增加原文计数或传输一次原对象。取消转发是把自己转发对象的入口置为已撤回，不撤回原文，不删除其他人的评论，也不承诺抹除已传播副本；用户修改引用转发正文时产生新版本，并通过同一入口更新。

首版普通转发按钮按“转发者 + 目标版本 + 普通转发类型”维护开关状态，入口由该互动键派生，重复点击和重试不增加独立转发数；引用转发允许形成多条独立发表，按各自入口归并其修改版本。统计可以分别列出普通转发和引用转发数量；原文换版不自动继承两类转发的背书。

## 13. 评论发表、传播与持续同步

### 13.1 默认发表流程

以下流程适用于针对公开对象的评论，也适用于对外发表的特殊评论。私有收藏不进入这条对外传播链路；针对受限对象的评论只写入发表流并投递原作者（§4.5）。所有 Push 都投递到对方的投递入口（§4.4），对方也可以通过读取评论者的发表流补齐。

```text
评论者创建评论 Feed Object
             │
             ├─ 写入自己的个人发表流（按评论的受众提供读取）
             ├─ Push 给原内容作者
             ├─ 按评论的受众 Push 给好友或关注者
             ├─ Push 给已发现的该讨论参与者
             └─ 可选提交给一个或多个收录节点
```

“已发现的参与者”包括评论者查看评论列表时发现的既有评论者。它不是要求每个用户先得到全网完整参与者集合。

对于好友传播，评论沿用普通 Feed 的受众规则。对讨论参与者的投递也必须通过接收方准入，不因为双方评论过同一内容就获得任意发送其他内容的权限。

### 13.2 作者接收与 Owner Comment List

评论投递到原作者后，应用判断其引用对象是否与自己发表的内容有关。原作者开放评论时，默认应接收相关对象，并将其加入自己维护的评论列表展示区域。

君子协议鼓励作者明确确认接收，并展示相关评论。但需要区分“收到对象”和“已经加入某个可查询评论视图”：投递得到 `accepted` 本身不是已展示证明。

作者可以维护自己的保留和排序规则，不能以此控制其他节点是否保存该评论。

### 13.3 评论列表的持续追踪

用户参与过某个 Feed Object 的评论之后，HomeStation 默认持续追踪该对象的讨论，而不是只在发表评论时读取一次评论列表。

追踪可以综合 Push 更新与周期性 Pull：读取作者的评论列表，也读取已发现参与者或收录节点提供的相关评论。

持续任务的调度周期、历史保留、活跃讨论优先级，以及用户暂停追踪的方式，属于本地策略。逻辑上的持续追踪不要求无间隔轮询或无限存储。

作者后来从自己列表中移除评论，不会使已经到达其他节点的对象和索引自动消失。

### 13.4 从作者 Tracker 到参与者网络

在讨论开始时，新用户通常先找到原作者，因此原作者提供初始评论列表和参与者线索。

当 B、C 等参与者通过列表发现彼此后，它们就可以直接投递和持续获取相关评论。原作者由唯一入口变成多个发现节点之一。

这里形成的是围绕一个具体对象讨论的发现关系，不必自动创建聊天群，也不必把所有参与者变成私人好友。

### 13.5 传播的实现约束

为使上述模型可落地，建议采用以下限制：

- 以对象身份和目标接收方对投递去重，重试不重复创建评论。
- 由主动发表评论或明确转发触发扩散，不能把每次收到评论都当作再次全量群发的指令。
- 对大量参与者使用批次、速率和资源预算；未覆盖的节点仍可以通过 Pull 发现。
- 接收评论后分别更新评论索引和候选状态，不把“进入讨论索引”强制等同于“进入个人主 Feed”。
- 新的入口 Head 沿已知传播路径通知，并可通过发表流的变化读取（§4.4）补齐；已验证的 Head 必须更新已有索引和统计，不因未被推荐而忽略，也不触发无条件再次群发。

这些是可靠性与资源管理建议，不改变评论向原作者、好友和已发现参与者主动传播的设计方向。

## 14. 收录者与冷启动

### 14.1 公共评论收录

独立收录者允许用户将针对某个 Feed Object 的评论提交给它，并允许其他用户查询该对象相关的已收录评论。

收录者可以绕开作者作为唯一查询入口的问题，但“独立于作者”不意味着某个收录者天然完整或绝对公平。用户应能选择多个收录者，并在本地合并结果。

### 14.2 不限于评论

评论本身也是 Feed Object，因此收录能力可以自然扩展到全部 Feed 内容：接收对象、提供索引、支持内容发现及后续 Pull。

收录者是内容传播生态中的第三类角色，不只是作者服务器的备份，也不是所有用户必须注册的中心平台。

### 14.3 系统冷启动

新用户可能既没有可投递对象的人，也没有明确订阅来源。系统可以预置若干收录节点，使其立即具备可 Push 和可 Pull 的入口。

预置节点应可配置、替换和移除，不应成为协议不可替换的根。本文不指定实际运营方或节点地址。

预置收录服务提供的是内容入口，不自动获得用户的私人待读列表、位置、停留记录或兴趣画像。

## 15. 评论的三种视图

### 15.1 作者视图

作者视图由原内容作者维护，可按其意愿保留、移除评论引用和调整展示顺序。

它表达的是“作者提供的评论组织结果”，不是协议宣布的全网全部评论。

### 15.2 收录者视图

收录者视图表达某个独立节点已经收集到的评论集合。可以存在多个收录者视图，各自具有不同覆盖范围和维护策略。

查看者可以绕开作者，直接向收录者提交评论或查询讨论。

### 15.3 用户本地默认视图

本地默认视图根据用户已经获取的作者、收录者、好友及讨论参与者数据，尽量合并更多评论，并应用本地排序和过滤规则。

```text
作者评论列表 ───────────┐
多个收录者列表 ─────────┤
好友/参与者投递 ─────────┼─> 合并与去重 ─> 本地默认评论视图
历史抓取与本地保存 ───────┘
```

“默认视图”只是该用户当前的本地结果，不声称覆盖所有评论。用户可以根据需要切换视图，作者无权强制每个阅读者采用作者视图。

### 15.4 合并时需要保留来源

建议索引至少能回答：评论针对哪个版本、从哪些路径获得、在哪个维护者列表中出现过、目前在哪些视图可见。

同一个评论从三个来源到达，应合并为一个对象并保留来源关系，而不是显示三次。对于不同 ObjId、但文字相同的评论，不应仅凭文本相同就认定它们是同一条已签名发表。

本地用户仍然可以过滤垃圾内容、屏蔽来源和调整顺序。反对作者垄断评论，不等于强制阅读者显示所有收到的内容。

### 15.5 从可验证的评论记录派生互动统计

点赞、公开收藏等统计应沿用作者视图、收录者视图和本地合并视图。**计数是指定视图中有效互动记录的派生结果，不是内容作者可以自行填写并要求其他节点采信的事实。** 作者或收录者可以返回统计缓存，但应同时提供可查询的记录依据、视图范围和统计时点；未取得依据的数字只能标明为该来源的声明。

接收方按以下步骤构建自己的统计：

1. 验证互动者签名、目标版本和互动类型，并按 §5.4 验证入口归属与 Head 签名；无法验证的记录不进入有效统计。
2. 按 ObjId 合并重复到达的对象，保留来源；再按入口归并同一发表的版本，按互动键归并互动状态，不能直接把多个来源的计数相加。
3. 普通评论及引用转发按独立逻辑发表统计，修改版本不额外增加数量；点赞、收藏和普通转发按 §12.4—§12.5 的互动键统计，在当前已知有效状态下每键至多计一次。
4. 收到更高序号的已验证 Head 后使相应统计失效并重算。旧对象或旧 Head 重放不能覆盖已知的更高序号状态；同一序号出现矛盾 Head 时单独标记冲突，暂不计入有效互动数。
5. 按当前视图、类型、可见性和本地过滤规则输出数量，并保留继续同步的状态。私有收藏不能进入公共统计；旧版本的互动不能自动累加到新版本。

“本地已验证的点赞数”仍只表示当前已获取记录中的结果，可能尚未收到新的点赞或取消对应的 Head，不等于全网实时总数。不同视图的结果可以不同，差异不自动证明某方造假；已有记录和 Head 的历史才是进一步判断的依据。

这套机制使作者无法仅靠修改计数字段冒充其他用户的互动，也使第三方能复算已收集记录。它不证明一个 DID 就对应一个自然人，不能单独解决批量身份刷赞、合谋或来源隐瞒记录；来源选择、身份信任和反滥用策略仍由阅读者控制。

## 16. 发表、修改、删除与排序的语义

### 16.1 必须区分的操作

| 操作 | 影响对象 | 不能被误解为 |
| --- | --- | --- |
| 发表 Feed Object | 产生一个可传播内容版本，加入发表或相关索引；声明入口时签发第一个 Head | 已经全网送达 |
| 发表终态对象 | 不声明入口，协议上不再有后续版本或撤回 | 之后还能通过协议编辑或撤回 |
| 修改内容 | 产生新 ObjId，入口签发指向新版本的更高序号 Head | 用原 ID 原地改写已发表内容 |
| 作者撤回自己的内容 | 入口签发已撤回的 Head，并通知已知接收方 | 能删除所有节点已有副本 |
| 取消点赞或公开收藏 | 互动者将自己特殊评论的入口置为已撤回，接收方据此更新状态和统计 | 内容作者代替互动者修改意愿，或只修改一个计数 |
| 取消转发 | 转发者将自己普通／引用转发的入口置为已撤回 | 撤回原文、删除他人评论或保证消除已传播副本 |
| 列表维护者移除引用 | 改变自己维护的某个视图 | 删除他人发表的评论对象 |
| 调整列表顺序 | 改变某个列表的组织结果 | 改变评论正文或原始版本绑定 |
| 本地缓存淘汰 | 释放本节点资源 | 作者撤回内容或否认曾经收到 |

删除、修改和顺序变更的编码需要利用既有对象与列表能力继续细化，但首版必须遵循本节的权限、传播和状态处理约定，不能把这些操作压缩成一个含义不明的 `delete`。

### 16.2 控评的可发现性

目标不是保证百分之百发现所有评论，而是让作者知道：自己对评论列表的筛选或移除可能被其他节点对比发现，并留下可观察的痕迹。

可以依赖的线索包括：曾抓取到的列表版本、作者给出的接收确认、其他节点保存的评论、收录者索引，以及后续列表变化。

“公开评论原则上应通知原作者”构成君子协议的基线，私有收藏等不在此范围内。发起投递不等于作者已经成功接收，只有保留了相应确认或列表历史，才能支持更强的判断。

### 16.3 区分差异与证据

| 观察到的情况 | 可以表达的结论 |
| --- | --- |
| 本地有评论，作者当前列表没有 | 作者视图当前未列出该评论；原因未必已知 |
| 已确认作者收到，但尚未见于作者列表 | 已收到，当前未在该视图发现；可能仍在处理或被筛选 |
| 历史列表包含，后来完整版本或明确变更中移除 | 该维护者列表发生了可观察的移除 |
| 只有部分分页、查询失败或同步不完整 | 信息不足，不能据此断言主动删除 |

因此，对外列表应能表明查询范围、分页或读取进度，并为维护者与版本识别留下空间；具体采用快照、增量还是变更记录仍待确定。

若首版要展示“曾被作者移除”，必须有足够历史或变更依据。仅仅比较两份不完整列表，只能展示差异，不能伪装成已证明的恶意控评。

### 16.4 更新与删除的君子协议

不可变对象不提供原地修改和全网物理删除，但应用仍需支持用户理解的“编辑”和“删除”。双方通过可变入口协作：发表者在入口上签发新的 Head，说明当前有效版本或已经撤回；接收者验证后更新自己的默认展示、索引与统计。这套约定同样适用于正文、普通评论以及点赞、收藏、转发等特殊评论。没有声明入口的终态对象不参与这套约定。

| 操作 | 发表者应提供 | 遵循协议的接收者应执行 |
| --- | --- | --- |
| 编辑内容或评论 | 声明同一入口的新版本对象，以及指向它的更高序号 Head | 记录版本关系，默认展示已知的有效新版本，并提供版本区别；旧版本引用保持原目标 |
| 删除已发表内容或评论 | 已撤回的 Head，作用于整条逻辑发表 | 默认不再作为有效内容展示和推荐；引用处可显示已撤回占位，保留该 Head 以处理后续同步 |
| 取消公开点赞或收藏 | 互动者在互动键入口上签发的已撤回 Head | 将该互动从当前有效统计中移除；不因此删除其他人的评论或互动 |
| 再次点赞或重新公开收藏 | 同一入口上更高序号的有效 Head | 验证后恢复该互动键的有效状态，仍至多计一次 |
| 取消普通或引用转发 | 转发者在自己转发入口上签发的已撤回 Head | 更新转发者发表视图与有效转发统计，不改写或撤回原文 |

更新或撤回只能由入口的控制者发起，也就是该对象的原发表者，或可验证地获得相应授权的主体。原文作者不能撤回别人发表的评论或点赞，因为那些入口不在原文作者的命名空间内；列表维护者也不能用移除引用代替互动者的撤回。对外部抓取内容，封装者只能变更自己发表的封装对象；来源页面变化、失联或返回 404，不自动构成原作者的签名撤回。

正文换版后，原版本上的评论、点赞和公开收藏仍指向原版本；可以展示历史互动入口，不能把原来的认可冒充为对新内容的认可。撤回原文也不会级联撤回其他人发表的评论，相关 UI 应保留“所引用版本已撤回”的上下文。

### 16.5 入口状态的最低语义与传播

Head 本身是可寻址、可签名验证的独立命名对象，复用既有对象传输与发现能力，但不复用 `PathObject`（§5.4）。它属于生命周期控制记录，不作为新增正文评论或点赞参与统计。以下是最低语义，具体字段与编码仍需对齐既有对象体系：

- 所属入口，以及入口控制者的签名：发表者本人，或其 DID Document 授权的 Zone、设备密钥。
- 单调递增的序号。序号由入口控制者的发表服务串行分配，是同一入口状态先后的唯一依据；Head 中的时间只用于展示。
- 当前状态：有效时给出当前版本的 ObjId；撤回时不再指向任何版本。

Head 以 JWT 形式即可独立验证，因此不依赖发表者在线：发表者把新 Head 推送给原投递路径中的已知接收方、相关作者和收录节点，任何持有者都可以转发或缓存它。逐个对象轮询入口不可扩展，关注者与评论追踪者通过发表流的变化读取批量增量同步（§4.4）；入口 URL 是发表流路径加入口键（`.../home/<用户名>/feed/@/<入口键>`），读取它直接返回当前 Head。接收者同步评论列表时也应同步相应的 Head，不能只拉当前仍展示的引用。

Head 的读取权限与其入口的受众一致（§4.5）。私有收藏不产生对外 Head，它的创建、修改和删除都不向公共节点广播；公开收藏改回私有后再次公开时，在同一入口上签发更高序号的有效 Head，本地私有状态仍独立保存。

已验证 Head 的应用不经过内容推荐筛选，也不以是否值得进入主 Feed 为条件。发布与通知需要可恢复的任务状态；节点离线只能延迟收敛，不能让已取消的点赞因为从未发出撤回 Head 而永久有效。

### 16.6 乱序、重放与保留边界

接收者对每个入口只保留已验证的最高序号 Head。序号更低的 Head 无论何时到达都不覆盖已知状态，因此旧对象或旧 Head 的重放不会使内容或点赞“复活”。先收到 Head、后收到对象时，保存该 Head，对象到达后再验证它是否声明了同一入口。发表者推送对象时应随附当前 Head；只收到对象、尚无 Head 时，可以暂按有效对象处理，进入待读列表前解析入口确认，之后获知的 Head 始终优先。

已经验证的撤回状态不能因正文、媒体或候选缓存被淘汰而一并丢失：对象内容可以淘汰，入口的最新 Head 必须保留，保留期至少覆盖对应对象可能再次到达的时间范围。

未核验或签名不符的 Head 不能使已有有效记录失效，也不能仅凭制造“冲突”压低统计。同一入口同一序号出现两个内容不同、且都通过验证的 Head，说明入口控制者自身出了问题（例如多台设备没有串行分配序号），应标记冲突：冲突未消解时，不把有争议的肯定状态计入有效互动数，正文版本也不冒充已确认的唯一最新版本；控制者签发更高序号的 Head 即可消解冲突。不能凭到达顺序、作者自报时间或原文作者的计数裁决。

君子协议约定接收者如何更新默认展示和统计，不强迫所有节点抹除历史字节。对已撤回内容，正文与资源是否继续保留、是否提供明确标记的历史查看入口，仍由保存方按其策略处理；这种历史保存不能被展示成仍然有效的发表或互动。作者和收录者可以不遵守约定，系统只能通过保留依据、比较视图和替换来源降低对单方的依赖。

## 17. 协议能力与本地数据模型建议

本节是为实现落地补充的结构建议，概念与前述原则一致，但不把示意名称当作现有 SDK 或已发布接口。

### 17.1 跨节点最小能力集合

| 能力 | 请求/输入的概念 | 结果/输出的概念 |
| --- | --- | --- |
| 定位发表流与投递入口 | 用户 DID | 发表流与投递入口的地址，按约定或用户声明（§4.4） |
| 投递 Feed Object | 目标投递入口、对象及其 Head、必要投递上下文 | dispatch 传输结果，`accepted` 时可附准入披露（§7.4） |
| 读取具体对象 | ObjId、读者身份 | 该版本对象，或明确的不可获取／无权读取结果 |
| 读取个人发表流 | 读者身份；展示读取的分页位置与筛选，或变化读取的游标 | 受众允许的条目（签名 Head），可随附对象；继续读取信息，或需重新完整同步的结果 |
| 读取评论视图 | 目标版本 ID、视图维护者、评论/互动类型、读取范围 | 该维护者获准提供的记录引用、顺序和继续读取信息 |
| 向收录者提交对象 | Feed Object 或可获取引用 | 收录接收结果，不承诺全网传播 |
| 查询相关内容/评论 | 对象目标或收录查询条件 | 该收录者范围内的结果 |
| 发表或取消公开互动 | 互动者签署的特殊评论对象及其入口 Head | 复用评论投递的接收结果，不直接接受外部设置计数 |
| 解析入口与同步 Head | 入口，或发表流的继续读取位置及读取权限 | 入口当前的签名 Head，或按变化顺序的 Head 更新与继续读取信息；保留撤回的发现能力 |
| 查询互动统计与依据 | 目标版本、视图、互动类型及读取范围 | 派生数量、依据记录入口、统计时点与同步状态 |
| 通知关注关系 | 关注者签署的关注声明及其入口 Head | 对方接收结果；不授予好友权限，也不表示已读 |
| 发送消费证明 | 已授权的签名消费声明 | 接收结果；不等同于已经完成经济结算 |

上述能力应尽量映射到已有 Post/Send Object、对象获取和列表查询机制。是否使用 HTTP、WebSocket 或其他传输，不是本次讨论要重新规定的重点。

### 17.2 本地逻辑数据集合

| 集合 | 建议保存的内容 | 归属 |
| --- | --- | --- |
| Object Store | 不可变正文、普通/特殊评论 Feed Object、被包裹对象与部件等已获取的关联对象 | 本地对象存储，私有对象不得通过公开读取接口提供 |
| Sources / Subscriptions | 来源入口、原始订阅意图、来源映射、主动／好友派生依据、采集启停与进度 | 私有应用状态；好友及分组真相来自 Message Center |
| Follow Records | 本方签署及收到的关注声明、对应 Head、验证与通知状态 | 按关系披露范围提供；双方各自声明自己的关注 |
| Feed Preferences | 不看某人／联系人分组的规则，标签过滤规则及未知状态策略，阅读起点与其他用户筛选配置 | 私有设置，不等于修改好友关系或取消关注 |
| Candidate Entries | 对象引用、多条来源路径、关注关联、到达时间、筛选原因与准备状态 | 私有应用状态；支持关注未入 Feed 查询 |
| Evaluation Records | 评价主体、DID／内容目标、路径解析版本、标签判断、证据范围、配置／模型版本、iat 与时效、结果状态及可见范围 | 通用评价事实源；默认私有，独立于候选和待读条目 |
| Evaluation Tasks / Cache | 任务进度、目标与授权范围、证据／配置对应的缓存键、预算、失效原因及结果引用 | 可恢复的系统服务状态；不同权限或评价上下文不可直接混用 |
| Tag Overrides / Views | 目标及维度、人工修正与作用范围、结果引用、调用方采用策略、有效标签与视图修订号 | 人工修正持久保存；业务标签视图可重算，不改写评价原始记录 |
| Admission / Reading History | 对象首次入列及从补看入口阅读的最小记录 | 私有状态；保留期至少覆盖候选，不与临时行为日志一并清理 |
| Resource Cache | 按 ObjId 缓存的数据（命名对象存储）、资源状态、来源检查时间 | 私有缓存 |
| Publishing Assets | 上传／草稿状态、FileObject 的 ObjId、发表关联及资源保留依据 | 用户素材，复用既有存储；不等同于可随时淘汰的缓存 |
| Reading Entries | 对象引用、排序、时间、评价记录及标签视图引用、准备状态及推荐／过滤依据 | 私有应用状态，不修改原始 Feed Object |
| View Cursors | 分类/视图与浏览位置、阅读起点配置 | 私有应用状态 |
| Published Lists | 用户对外发表的入口、变化序列、每个入口的受众，以及精选等用户维护的顺序 | 按受众提供（§4.4、§4.5） |
| Comment Index | 目标版本到普通/特殊评论的关系、类型、逻辑发表、来源和视图归属 | 本地索引；对外部分须有明确维护者及访问范围 |
| Entry Heads | 每个入口已验证的最高序号 Head、入口归属验证结果、已知版本及冲突标记 | 按入口受众保存和同步；不随正文缓存淘汰 |
| Personal Interaction State | 私有收藏、当前点赞／转发等持久状态，以及关联的公开入口状态与投递状态 | 私有应用状态；公开部分通过特殊评论表达 |
| Saved Collections | 收藏、稍后再看等用户主动维护的引用集合及顺序 | 私有持久数据；收藏关联对应特殊评论，不随待读窗口淘汰 |
| Interaction Stats | 按目标版本、视图、类型和有效记录计算的统计缓存及依据 | 可重算的派生数据；更新或撤回触发失效，不作为作者独占的事实源 |
| Topics / Profile Collections | 本地主题映射、用户订阅、范围明确的汇总，以及作品／商品索引和精选引用顺序 | 分类与聚合索引；用户身份和资料复用既有服务 |
| View History | 为列表差异判断保留的快照或变更依据 | 本地观察记录，保留策略可配置 |
| Local Behavior | 临时消费事件、必要统计或偏好状态 | 默认不对外 |
| Outgoing Tasks | 待投递对象、目标、重试与确认状态 | 本地任务状态 |

候选对象、待读条目、评论索引可以引用同一个 ObjId。一个对象被移出主 Feed，不代表它必须从个人发表流或评论索引中删除。

### 17.3 处理幂等与任务恢复

建议以现有对象身份作为内容级去重基础，对“对象—接收目标”建立投递级去重，特殊评论另按互动键归并有效状态。对重启后需要继续的发表与 Head 投递、资源准备和评论追踪任务，保留可恢复状态。入口 Head 与当前状态应先可靠保存，再更新可重算的统计；不能只更新显示数字而丢失记录依据。

首版不必引入复杂分布式调度器，但应避免浏览器关闭或服务重启后，已发表评论只写入本地而永远不再尝试通知原作者。

### 17.4 支撑产品原型的应用能力

跨节点能力之外，HomeStation 还需向自己的 UI 提供以下应用能力。表中名称表达职责，不要求各自独立部署；除按权限公开的门户读取外，均以当前用户身份鉴权。

| 能力 | 输入与操作 | 应返回或维护的结果 |
| --- | --- | --- |
| 来源与订阅管理 | Follow、URL、自然语言意图，暂停／恢复，移除主动订阅依据 | 解析来源、有效关注依据、通知结果、抓取状态与失败原因 |
| 好友与分组联动 | 读取 Message Center 的好友、分组及变化 | 幂等更新好友派生关注和有效展示规则，不复制权威好友库 |
| 朋友圈展示设置 | 配置不看某人／分组、恢复展示 | 当前有效规则及对已有候选／待读的过滤结果 |
| 通用标签评价 | 按需评价 DID 或 ObjId／对象路径，指定维度与评价配置，查询／刷新结果 | 独立评价记录或任务状态、实际评价目标与证据范围；不要求创建 Feed 条目 |
| 标签与内容过滤 | 查看分类依据、人工修正、配置标签组合与判断来源／阈值、显式查看过滤内容 | 有效标签、推断／确认状态、命中规则及候选／待读视图重算结果 |
| 待读查询 | 分类、Topic、标签过滤、当前搜索条件、稳定游标及分页范围 | 已准备条目，有效标签及来源，推荐理由，资源解析，个人操作状态与统计范围 |
| 关注补看查询 | 有效关注关系、未入列条件、直接阅读状态、分页位置 | 保留范围内的候选、准备／未选中原因及同步状态 |
| 候选主动阅读 | 选定对象，准备或加入待读的意图 | 可用内容或明确准备状态，不绕过权限与有效性检查 |
| 发布与素材管理 | 文字／媒体、受众、上传结果、发布幂等标识 | 草稿、FileObject 的 ObjId、发表对象、入口 Head、当前受众及待投递状态 |
| 评论及互动 | 正文、点赞、收藏、转发，取消或更新 | 新对象／入口 Head、当前个人状态及可重算统计 |
| 持久收藏与稍后再看 | 添加、移除、按用户主动保存的集合查询 | 与自动待读窗口分离的持久引用；目标撤回时显示状态 |
| Topic 与个人门户 | 用户资料引用、主题订阅、作品／商品分类、精选顺序 | 公开发表投影或私有主题视图，范围明确的数量与热度 |

UI 原型中的 `FeedObject` 实际承担卡片数据模型。实施时由不可变 Feed Object 与上述私有投影组合成 UI 数据，`effective_tags`、`isLiked`、`isBookmarked`、`isReposted`、`recommendReason` 及各种计数不能成为原作者签名内容的一部分。UI 分类使用 `effective_tags`，需要查看作者原始标签时读取对象的 `tags`，不能把本地新增标签展示为作者声明；原型中的 `FeedMedia.url` 与 `originalUrl` 也要分别改为 ObjId 引用与 `link`／`source`。

## 18. 端到端场景

### 18.1 传统公开内容进入个人 Feed

1. Spider 按用户话题发现一篇含视频的公开内容。
2. 若视频只能在当前 Session 中获取，Spider 此时就保存为命名对象并包裹；否则可以先形成链接卡片。两者都只是本地候选对象，不进入用户的发表流（§5.6）。
3. 对象进入候选集合，服务补充本地标签、应用用户过滤规则，推荐服务决定是否选中。
4. 资源准备模块按 ObjId 获取必要内容；对链接卡片则抓取快照，以包裹快照的本地对象替换原候选。
5. 准备完成后补全依赖正文／媒体的标签判断，通过过滤复查后加入统一待读列表；用户通过默认或分类视图看到它。
6. UI 记录临时消费反馈，用于后续抓取与推荐，不自动把行为发送给来源站点或模型服务。

### 18.2 间接社交关系触达

用户 B 经由 A 的讨论发现用户 C，向 C 的投递入口投递内容。C 的准入规则允许这一类关系，于是返回 `accepted`，并只披露“已入候选”；内容随后是否进入待读列表，由 C 自己的推荐与准备服务决定。若 C 的 OOD 当时离线，网关返回 `cached`，B 仍保留重试责任。

B 不能把 `accepted` 或“已入候选”解释为 C 已观看，也不能凭同一讨论参与关系获得 C 的私聊权限或行为记录。

### 18.3 评论传播与作者移除

A 发表 P1，B 评论得到 C1。C1 引用 P1 的 ObjId，进入 B 的主页，并投递给 A、B 的好友、已发现参与者及选定收录者。

A 开放评论并将 C1 加入作者视图。参与者 D 抓取该视图后，也保存 C1 并持续跟踪讨论。

之后 A 从作者视图移除 C1。D 和收录者仍可能提供 C1，阅读者的本地默认视图仍可显示它。若保存了作者列表的前后状态，可以表明作者视图移除了该引用；否则仅显示不同视图的覆盖差异。

### 18.4 原文换版不能继承旧评论背书

A 把 P1 修改为意思不同的 P2，P2 声明同一入口，A 在入口上签发指向 P2 的新 Head。C1 仍然针对 P1。查看 P2 时可以提供旧版本及其讨论入口，但不能把 C1 混入 P2 的评论区而隐藏版本区别。

### 18.5 自愿消费证明

某内容提出消费回执需求，但用户未参加对应约定时，正常播放只产生本地反馈。

用户明确参加相关约定后，应用可在符合条件时构造消费证明，引用具体对象并签名，发送给约定接收方。该证明不包含未经授权的全部浏览日志；首版不因发送成功而宣称已完成支付或强反作弊验证。

### 18.6 点赞、取消与第三方统计

B 对 A 的 P1 发表点赞 L1，作者和独立收录者都收到该特殊评论。D 合并两个来源后只计一个点赞；A 自报更多点赞时，D 不把没有记录依据的部分当作已验证结果。

B 随后在点赞入口上签发已撤回的 Head。D 从收录者获知并验证该 Head 后，移除该有效点赞；即使 A 仍返回 L1 和旧 Head，也不能覆盖已知的更高序号撤回状态。B 再次点赞时签发序号更高的有效 Head，恢复一次计数。P1 更新为 P2 后，这些记录仍只属于 P1。

### 18.7 私有收藏与内容撤回

B 收藏 P1 时创建私有特殊评论，只维护自己的收藏状态。作者和公共收录者既收不到该记录，也不能据此增加公开收藏数。B 若主动公开收藏，则发表带互动键入口的公开收藏对象；改回私有时将该入口置为已撤回，本地收藏仍保留。

A 撤回 P1 后，遵循协议的节点停止把它作为有效发表推荐，B 的收藏可显示“目标内容已撤回”，不自动删除 B 的收藏或其他用户的评论。已保存历史可按本地策略保留，但不冒充当前有效内容。

### 18.8 好友默认关注与未入 Feed 的补看

A 与 B 是 Message Center 中的好友，双方 HomeStation 默认派生关注并各自维护通知与 Pull。B 抓取到 A 的 P1、PIC1 和 VID1，三者均进入候选，但当前只选中并准备了 P1。B 的主 Feed 和“已关注”筛选中出现 P1，补看入口列出仍在保留范围内的 PIC1 和 VID1，并提示资源准备状态。

B 主动打开 VID1 后按需准备并阅读，保存补看阅读状态；默认补看列表不再反复显示它。B 配置“不看 A 所在分组的朋友圈”后，A 的直接动态在主 Feed 与补看入口均按规则隐藏，关注与好友关系保持不变，也不向 A 发取消关注通知。

### 18.9 转发与取消转发

B 对 A 的 P1 创建 R1，R1 出现在 B 的主页并由 B 的订阅者采集；附带个人观点时创建 Q1。两者都包裹 P1 的具体版本，保留 A 的原作者身份。

B 取消 R1 时将其入口置为已撤回，其他节点验证后更新 B 的发表投影和 P1 的有效普通转发数。P1、Q1 以及其他人的评论不随之删除；A 把 P1 更新为 P2，也不会让 R1 或 Q1 自动成为针对 P2 的转发。

## 19. 首版实现范围与推进顺序

### 19.1 必须形成的完整功能闭环

| 范围 | 首版最小实现 |
| --- | --- |
| 发表流与投递入口 | 由 DID 按约定或声明定位；发表流提供展示读取与变化读取，条目为签名 Head，按读者身份过滤；投递入口以 CYFS dispatch 接收 |
| 发表受众 | 公开／关注者／好友／联系人分组／指定 DID；读取鉴权；受限内容不可转发，评论与互动只给原作者 |
| 原生发表 | 创建自包含或包裹形态的 Feed Object 并声明可变入口，写入个人发表流，支持版本明确的引用 |
| 媒体发表 | 图片、视频、语音上传为 FileObject 并以 ObjId 引用，发布重试幂等，区分用户素材和资源缓存 |
| 更新与撤回 | 可变入口与单调 Head、入口归属验证、已知路径推送与发表流增量同步，正确处理乱序和旧状态重放 |
| Push | 投递入口、基本准入，dispatch 传输结果与 candidate／preferred 准入披露分层 |
| Pull | 原生发表流抓取，加至少一种可工作的传统公开内容采集实现（包裹快照或链接卡片） |
| 订阅与好友联动 | Follow 知情通知，好友默认互相关注，URL／自然语言意图持久化并驱动持续采集 |
| 朋友圈偏好 | 按 Message Center 联系人或分组配置“不看”，不改变好友权限和关注关系 |
| 候选统一 | 两类来源进入同构候选视图，具有容量与对象去重 |
| 关注补看 | 查询已获取但从未入列的关注候选，展示准备状态，支持按需阅读及最小历史记录 |
| 推荐 | 可替换的筛选接口，先使用简单规则或基础 LLM，向 UI 返回推荐理由 |
| 通用标签评价 | 独立提供 DID 身份与 ObjId／对象路径内容评价、结果查询、刷新及人工修正；支持非 Feed 场景调用 |
| 本地标签与过滤 | 复用评价服务，支持有效标签、来源与范围、未知状态及 AI 生成内容过滤；原对象不变 |
| 内容准备 | 必要资源下载/检查，区分准备中与可消费 |
| 阅读 UI | 一个统一待读列表、默认视图、基础分类、每视图游标 |
| 本地反馈 | 必要消费行为临时记录，并能影响后续采集或筛选 |
| 快速反馈 | 点赞、收藏等作为特殊评论，持久个人状态与自愿对外发表分离，支持取消与再次操作 |
| 转发 | 普通／引用转发作为特殊评论进入个人发表流，取消只撤回自己的发表 |
| 评论 | 普通/特殊评论均为 Feed Object，公开部分进入发表流并按授权范围传播 |
| 评论同步 | 作者列表、持续追踪、参与者发现和去重 |
| 多视图 | 作者视图、至少一个独立收录来源、本地合并默认视图 |
| 互动统计 | 按有效普通/特殊评论记录归并和计数，提供范围与依据，不依赖作者自报数字 |
| 冷启动 | 可配置预置收录入口，不依赖先建立好友关系 |
| 个人门户与 Topic | 复用用户资料，支持作品／商品分类、精选引用、本地主题与范围明确的汇总 |
| 消费证明机制 | 明确对象语义与授权入口，可验证最小签名声明；无需商业结算 |

首版不能只有漂亮 Feed 页面而缺少评论传播，也不能把所有评论强制留在原作者服务器上。后两点会失去本架构最重要的开放性。

### 19.2 建议的推进顺序

**第一阶段：稳定对象语义并验证互通。** 先对齐既有命名对象、签名和投递基础设施，先定下由 DID 定位发表流与投递入口、发表流的两种读取方式及受众，再明确 Feed 的内容形态、普通/特殊评论、可变入口与 Head、投递结果以及列表维护者等最低语义，用小规模多节点验证互通。

**第二阶段：建立公共评价能力并贯通阅读链路。** 实现可独立调用的身份／内容标签评价服务，先用规则或基础模型验证非 Feed 调用；再实现来源订阅、好友关注派生与知情通知、持续采集、候选管理、采用评价结果的筛选与推荐理由、资源准备和分类游标，并支持“不看”设置与关注补看，使用户可以连续浏览真实内容。

**第三阶段：贯通发表与评论网络。** 实现文字／媒体、普通／特殊评论及转发的发表，作者／好友／参与者投递和变更持续同步，以及个人门户、独立收录节点、三种评论视图和基于记录的统计。

**第四阶段：接入反馈并加固。** 接入本地行为闭环、自愿快速反馈与消费证明机制，验证隐私、重试、资源限制、版本变更和视图差异的正确性。

这只是交付顺序，不改变首版需要覆盖的完整范围；复杂推荐、完整经济模型和强匿名方案继续留在后续演进。

| A30 | 同一入口同一序号出现矛盾 Head，或同步尚未完成 | 暴露冲突或同步范围；不把有争议状态计入有效互动数，不宣称全网实时总数 |
| A31 | 已撤回对象仍被保留在明确标记的历史视图 | 可按本地策略查看历史，不作为当前有效发表或互动统计 |

| A35 | 用户设置不看某人／某联系人分组 | 主 Feed 与关注补看入口均按直接发表者过滤；不取消关注，不改变聊天权限，不发送隐藏设置 |
| A36 | 分组成员变化，或好友关系解除 | 重算展示规则及好友派生关注；保留仍有主动依据的关注，继续遵守其他命中的隐藏规则 |
| A37 | 关注来源的内容进入候选但未被选中 | 不强制加入待读；在权限、保留范围和展示规则允许时进入关注补看集合 |
| A38 | 补看条目未准备资源，用户主动打开 | 按需准备并返回就绪／失败状态，保存直接阅读记录，默认不反复补看同一条 |
| A39 | 已入列条目后来被移出待读，或临时行为日志被清理 | 不因简单差集或日志清理重新冒充从未入列的关注候选 |
| A40 | 普通转发、引用转发及取消 | 形成转发者自己的签名发表，保留原文版本与作者；取消不撤回原文，统计按对应规则归并 |
| A41 | 媒体上传失败、发布重试或清理缓存 | 失败不显示发表成功，重试不重复创建动态，已发表或需保留的素材不被普通缓存淘汰 |
| A42 | 自然语言订阅建立后关闭浏览器再恢复服务 | 保留意图、来源映射及采集进度，后台可继续执行并显示状态 |
| A43 | 读取个人门户、作品／商品／精选 | 只返回获准公开的数据；精选调整不改写原文，私人候选、收藏和推荐理由不随门户泄露 |
| A44 | 同一内容在不同模式、Topic 和搜索条件下查看 | 保持对象身份与查询约束，推荐理由可追溯，分页搜索不局限于当前加载页 |
| A45 | 关注普通 RSS 或网页，对方没有关注通知入口 | 继续按公开能力采集并标明不支持通知，不伪造知情确认 |
| A46 | 对象声明的入口不在发表者命名空间，或 Head 指向他人发表的对象 | 入口无效，不据此认定版本或撤回 |
| A47 | 对象未声明可变入口 | 作为终态对象处理，不查询状态，也不接受针对它的更新或撤回 |
| A48 | Feed Object 以远程 URL 作为正文或媒体引用 | 不作为合法对外对象接受；外部内容只能包裹快照或形成链接卡片 |
| A49 | 同一对象被多人转发或包裹 | 被包裹对象的 ObjId 不变，各包裹对象独立计数，评论目标不混淆 |
| A50 | 发表者离线时，其他节点转发了新的撤回 Head | 验证签名后生效，不要求发表者在线 |
| A51 | 作者未标注 AI 生成，本地分类器补充标签 | 原 tags、ObjId 和签名不变；有效标签可用于分类与过滤，UI 明确为本地推断并能查看依据 |
| A52 | 用户配置隐藏完全 AI 生成内容，或只隐藏同时低质量的内容 | 按生成范围、来源及质量条件过滤；默认 Feed、分类与关注补看一致执行，Head 同步不受影响 |
| A53 | 用户删除误标标签，之后模型重算或服务重启 | 保留人工修正的优先级，更新过滤结果并重新评估候选；原对象和引用不变 |
| A54 | 只检查了封面、分类失败或尚未取得正文 | 不把局部 AI 使用标成全量生成，不把未知当作人工；按未知策略处理，资源准备后补判并复查过滤 |
| A55 | 原对象换版，或同一版本经不同路径重复到达 | 新版本重新分类；同版本共享本地记录，不重复添加标签，不自动把旧版本人工修正迁移到新版本 |
| A56 | 用户调整过滤规则，或显式查看被过滤条目 | 已有候选与待读视图重算且游标稳定；仍校验权限、撤回和资源状态，不自动删除收藏或记为已读 |
| A57 | 其他应用或 Agent 请求评价一个 DID，或未进入任何 Feed 的内容 ObjId | 通过公共服务得到评价结果／任务状态，无需创建候选、待读或公开评论 |
| A58 | 同一 DID 在不同时间窗口或评价配置下得到不同标签 | 保留评价主体、证据范围、配置与时效；不把局部观察合并成永久或全网结论 |
| A59 | 按对象路径评价后，路径改指新 ObjId | 原结果只适用于记录的旧版本；使用当前路径结果前重新核对绑定，不命中旧版缓存 |
| A60 | 评价 ObjId 的 InnerPath 或语义路径中的局部内容 | 记录根 ObjId、内部路径和实际解析目标；局部结论不自动升级为整对象或作者身份结论 |
| A61 | 两个调用方请求同一目标，但权限、证据或评价配置不同 | 只在授权与缓存条件相容时复用，不泄露私有证据或误用其他上下文结论 |
| A62 | 评价任务超时、目标不可取或证据不完整 | 返回明确任务／覆盖状态及未知项，不返回默认正常或自动执行屏蔽 |
| A63 | 外部节点提供互相矛盾的身份／内容评价 | 验证评价者与目标版本，分别保存；本地按可信来源与用户策略采用，不按重复记录投票定论 |
| A64 | 同一评价分别用于联系人提示、Inbox 准入与待读过滤 | 各调用方独立决定动作，评价本身不改权限、不发表评论、不修改目标 tags |
| A65 | 用户在某应用内纠正标签，之后其他应用调用或服务重启 | 保留修正及声明的作用范围；限定于应用的修正不扩散，全局修正在同一用户范围生效 |
| A66 | 只知道对方 DID | 按约定或对方声明找到发表流与投递入口，完成首次展示读取并开始变化同步 |
| A67 | 关注者离线一段时间后恢复 | 用游标的变化读取得到期间的新发表、编辑与撤回；游标早于压缩点时得到需要重新完整同步的明确结果 |
| A68 | 某次发表流响应缺少一个已知条目 | 不解释为撤回；只有已验证的撤回 Head 才使条目失效 |
| A69 | 匿名访客、关注者与好友读取同一发表流 | 各自只得到受众允许的条目；知道 ObjId 也读不到受限对象及其 Head |
| A70 | 有人尝试转发好友可见的动态 | HomeStation 不提供转发；即使他人包裹其 ObjId，受众以外的读者取不到原文，显示“原文不可见”，推送时不随附受限对象 |
| A71 | 用户评论或点赞受限对象 | 评论与点赞只投递和提供给原作者，不出现在评论者的公开主页，不提交给收录者 |
| A72 | Spider 为私人阅读抓取网页 | 快照与封装对象不出现在发表流，不对外提供；用户分享后才以自己的入口发表 |
| A73 | 接收方 OOD 离线，网关返回 `cached` | 发送方继续保留重试责任，不当作已投递；`cached` 不附带任何准入披露 |
| A74 | 用户首次点赞 | 以公开受众发表并告知用户点赞公开；收藏仍保持私有 |
| A75 | 同一 Zone 的两个用户互为好友 | 各自有自己的发表流与投递入口；互相关注、投递与读取和跨 Zone 相同，都能完成；一方的设置、待读和私有收藏对另一方不可见 |
| A76 | 只知道同 Zone 某用户的 DID，或另一个 Zone 的用户要关注他 | 通过 Zone 的 DID 查询得到 `home/<用户名>`，按该路径读取与投递；Zone 托管签名的 Head 能被验证，入口不在该用户主页下的被拒绝 |
| A77 | 有写权限的用户发表时选择同步到 Zone 汇总列表，之后编辑、撤回或移出 | 汇总列表展示其签名 Head，读者可逐条验证；编辑与撤回进入汇总列表的变化读取，撤回后不再展示，移出不被解释为撤回；无写权限或非公开发表不能列入 |
| A78 | 打开 `www.<Zone>/` 或 `homestation.<Zone>/` | 匿名也可访问，显示 Zone 配置的默认发表流；页面链接指向 `https://<Zone>/homestation/...` |

多视图验证至少需要作者、评论者/阅读者和一个独立收录角色。不能只在单个数据库里模拟三个标签，就宣称已验证作者无法独占评论传播。

| 本地标签与过滤 | 复用公共评价服务，原始 tags 不变，分类采用有效标签，用户修正在其作用范围内优先 | 各场景的推断阈值、可信来源、未知状态默认策略与视图重算预算 |
| 转发 | 普通／引用转发是特殊评论，取消仅撤回自己的发表 | UI 展示细节及普通／引用转发统计的呈现 |
| 传播规模 | 原作者、好友及已发现参与者共同传播 | 批次、限流、追踪生命周期与关系证明 |
| 可变入口与 Head | 对象自声明入口、入口须在发表者命名空间、单调序号、整条发表撤回、Head 是独立对象且可独立转发，不复用 `PathObject` | Head 的 ObjType 与编码、互动键摘要算法、是否需要按版本撤回 |
| 互动统计 | 多来源记录验证、按互动键归并、撤回失效、范围可见 | 查询字段、分页与统计快照的一致性、反滥用策略 |
| 本地保留 | 候选、待读、资源、行为与持久互动状态具有不同生命周期 | 默认预算、淘汰及保留入口 Head 的方式 |
| 消费证明 | 自愿、签名、面向未来经济约定 | Tracker 身份、关联隐私、防重放及结算接口 |
| 收录节点 | 可替换、多来源、可用于冷启动 | 初始部署、运营政策与能力发现 |

这些待定事项不应阻止先完成端到端原型，但在宣布网络格式稳定之前，需要明确哪些决定影响跨节点兼容，哪些仅影响本地行为。

## 22. 架构结论

HomeStation 将内容消费拆成“获取候选—本地筛选—资源准备—用户阅读—本地反馈”的闭环，把算法复杂度和用户行为数据尽可能留在用户控制的环境中。

节点之间的社交网络协议因此保持很薄：以 DID 定位每个用户的发表流与投递入口，约定读取与投递的访问参数。发表流按读者身份返回受众允许的签名条目，Pull 是事实来源，Push 只为及时；发表流之外的一切都是各节点自己的应用实现。

通用标签评价服务构成这一闭环可复用的基础能力：按需对 DID 身份和内容对象作出带来源、依据及作用范围的判断，供各应用与 Agent 自主采用。评价与业务处置分开，各用户掌握自己的规则与结果可见范围，形成去中心化的 AI Native 自审核；待读分类与过滤只是其中一个场景。

它通过不可变的 Feed Object 统一 Push 与 Pull：对象内容自包含或包裹另一个 ObjId，可变性只存在于对象自声明的入口上；通过不可变版本引用维护内容与评论的对应关系，通过评论的独立发表和多路径传播，避免把讨论完全附着在原作者的服务器上。

关注、好友及分组关系驱动持续采集，用户的“不看”规则控制默认展示；未入待读的关注内容仍可在保留范围内主动补看。转发以自己的引用型发表参与同一条传播和变更链路，具体对象与应用状态的边界由本文实例及功能映射共同说明。

点赞和收藏作为特殊评论复用同一套能力，公开统计从可验证记录中派生；更新与删除通过入口上单调递增的签名 Head 及接收方遵循的君子协议生效。内容作者既不能替别人声明互动，也不能独占其统计依据；私有互动和历史保存仍保持各自明确的边界。

作者视图、收录者视图与本地默认视图共同提供选择权：**作者可以组织自己的评论列表，但不能把这种组织权变成控制所有人所见评论的权力。** 系统追求的是可发现、可对比、可替换，而不是承诺全网绝对完整。

首版需要先把这个完整闭环做出来，再持续演进推荐、资源管理、隐私机制和注意力经济。稳定的协议负责对象流通、版本关系及自愿的跨节点声明；用户自己的应用负责决定去哪里找、接下来读什么，以及如何理解阅读后的反馈。

## 23. 实施回写（2026-10-09）

首版实现（`src/frame/homestation`，Desktop 前端 `src/frame/desktop/src/app/homestation`）对 §21 的待定项采用以下选择；完整的线格式、接口、数据与验证见《HomeStation 协议与实现》。这些选择在宣布网络格式稳定前都可以修改。

| §21 议题 | 实现选择 |
| --- | --- |
| 发表流与投递入口 | 约定路径 `cyfs://<Zone>/home/<用户名>/feed`、`.../inbox`；DID → 用户名由 Zone 回答 `GET /home/?did=`；Zone → `https://<Zone>`，可在服务设置声明其他源站，本 Zone 指向本机监听；读者证明为自签 JWT（`Authorization: DID …`，`aud = cyfs://<Zone>/home`，有效期 ≤ 10 分钟），同 Zone 用户用会话令牌；变化游标为发表流自增序号，压缩后早于压缩点的游标得到 `resync`；展示读取游标为 `iat|入口` |
| Zone 汇总列表 | `cyfs://<Zone>/home/~zone/feed`，读取方式与个人发表流相同；列入随发表（`zoneFeed`）或单独操作；Zone 级数据库记录列入与变化序列 |
| 发表受众 | 枚举 `public` / `followers` / `friends` / `group` / `dids`；“关注者”在读取时判定，好友视同关注者；受众调整追加 `audience` 变化，并向新增受众补一次 Push；包裹他人非公开对象的授权尚未实现 |
| Feed/Message 关系 | ObjType：Feed Object `cyfeed`、Head `cyfhead`、关注声明 `cyfollow`、消费证明 `cyfproof`、共享评价 `cyfeval`；字段自定义，不复用 `BaseContentObject` |
| 对象身份与签名 | ObjId = type + sha256(JCS claims)；JWT（EdDSA），`kid = <签名者 DID>#<key id>`；签名者须为发表者本人、其 DID Document 列出的密钥、其拥有的设备，或发表者所在 Zone 的设备（Zone 托管）；服务模式用 OOD 设备密钥替 Zone 的所有用户签名 |
| 内容形态 | 内联正文 ≤ 8000 字符、对象 ≤ 64 KiB、部件 ≤ 9；`wraps` 与部件均为 ObjId 字符串 |
| 投递结果 | 准入披露为 `accepted` 状态体中的附加字段 `admission`；拒绝原因 `not-admitted`、`not-addressed`、`rate-limited`、`invalid-signature`、`signature-required`、`signing-key-unavailable` 等 |
| 列表发现与变更 | 作者视图与收录者视图均为 `GET /home/<用户名>/comments?target=<ObjId>` 的完整列表（`complete: true`）；接收方保存视图快照，只有两次完整快照之间消失的记录才标为“可观察的移除” |
| 可变入口与 Head | Head 增加 `publisher` 字段；互动键摘要为 `<type>-` 加 `sha256("homestation/reaction/v1\n<互动者>\n<目标>\n<type>")` 前 16 字节的十六进制；只支持整条撤回 |
| 评论关系 | 关系字段为 `references[{relation: "comment_on"}]`；转发类以 `wraps` 为目标；多级回复未实现 |
| 通用标签评价 | 维度：内容 `topic` / `generation_method` / `quality` / `ad`，身份 `topic_affinity` / `delivery_behavior`；档案 `rules`（规则，默认）与 `model`（AICC，需配置）；修正作用域 `global` / `app:<id>` |
| 本地保留 | 候选 14 天、待读窗口 300 条、行为事件 7 天；入口 Head 不随内容淘汰 |

尚未覆盖或未经真实环境验证的部分：设备签名（含 Zone 托管）的跨 Zone 验证没有第二个可达 Zone 可测；跨 Zone 关注 Zone 汇总列表未实现；chunk list 大文件不预取、不校验；自然语言订阅的来源映射由规则完成，尚无 Agent 持续维护；收录者没有检索接口。
