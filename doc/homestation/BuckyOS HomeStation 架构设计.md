# BuckyOS HomeStation 架构设计

> **版本**：v0.3  
> **日期**：2026-10-08  
> **文档定位**：面向系统架构师与实现团队的架构基线。  
> **设计依据**：本次关于 HomeStation 的连续口述与讨论。文中明确区分已形成的设计原则、为首版落地补充的实现建议，以及尚未冻结的协议细节。

## 1. 架构摘要

HomeStation 是 BuckyOS 预装的 Self-hosted 个人门户与内容消费应用。对外，它承载用户自己的动态、评论和内容发表；对内，它综合社交投递、主动订阅与内容抓取，为用户生成可以持续浏览的个人 Feed。

其核心不是建设一个由平台统一控制的推荐系统，而是建立一套开放的内容流通协议，将复杂的内容采集、筛选、准备和推荐反馈放在用户自己的 HomeStation 中执行。

整体架构可以概括为：

```text
其他用户 / 好友 / 间接社交关系                    公开内容源
              │                                  │
              │ Push                             │ Pull
              ▼                                  ▼
       Social Inbox                      Spider / Agent Cache
       轻量对象与资源引用                  原生对象 / 外部内容封装
              └────────────────┬─────────────────┘
                               ▼
                   同构化候选集合：Feed Object
                               │
                               ├─ 关注但未入列 ─> 私有补看入口 ─> 按需准备与阅读
                               │
                 本地推荐算法 + 内容资源准备
                               ▼
                      统一、有限的待读列表
                               │
                    分类视图 + 对应浏览游标
                               ▼
                           Feed UI
                               │
              ┌────────────────┼─────────────────┐
              ▼                ▼                 ▼
        本地消费行为      主动反馈 / 评论     可选消费证明
              │                │                 │
       改进抓取与推荐     对象发表与传播      授权后的网络回执
```

评论不另建一套传播系统。**评论本身就是 Feed Object**，引用被评论内容的具体版本，可以出现在评论者自己的主页中，并向原作者、好友、已发现的讨论参与者和收录节点传播。

同一内容的评论可以有作者视图、收录者视图和用户本地默认视图。作者可以管理自己的列表，但不能垄断其他节点保存、传播和展示评论的能力。

**点赞、收藏等也是特殊评论。** 公开互动由互动者签名，按同样的列表模式收集、验证和统计；内容作者提供的数字只是一个来源，不能代替可查询的记录依据。收藏仍默认私有，采用统一对象模型不等于默认公开。

关注采用让对方知情的君子协议。Message Center 中的好友默认互相关注，用户可以配置“不看某人／某分组的朋友圈”。关注驱动服务主动 Pull 到候选集合，不保证进入待读列表；应用提供“来自我关注的人，但未进入我的 Feed”的补看入口。转发也是特殊评论，在转发者自己的发表流中形成可撤回的引用型 Feed Object。

Feed Object 的更新与删除采用君子协议：发表者传播可验证的更新、撤回声明，接收者据此更新默认展示和有效统计。不可变版本仍可被引用，历史副本不保证消失，原文作者也无权撤回他人的评论或互动。

架构需要优先稳定三类跨节点语义：

1. Feed Object 的发表、版本身份、引用以及 Push/Pull 流通。
2. 普通评论及特殊评论的传播、列表发现、多维护者视图与可复算统计。
3. 对象更新、撤回的君子协议，以及自愿消费证明。

推荐算法、候选管理、待读列表、分类游标、行为分析和资源缓存属于应用实现，不应因此被固定成统一的网络协议。

## 2. 产品定位与设计目标

### 2.1 两个界面，一套内容对象

HomeStation 同时具有个人门户和个人阅读中心两种使用方式，必须区分个人发表流与个人待读列表，并明确评论和候选补看视图的边界。

| 名称 | 面向谁 | 主要内容 | 边界 |
| --- | --- | --- | --- |
| 个人发表流（Personal Published Feed） | 访问该用户主页的人、订阅者、抓取者 | 用户发表的动态、评论及主动分享 | 按发表权限对外提供，不等于用户的私人阅读记录 |
| 个人待读列表（Reading List） | HomeStation 所有者 | 从多种来源筛选并准备好的内容 | 默认属于本地应用状态，不因进入列表而自动公开 |
| 关注未入 Feed 集合 | HomeStation 所有者 | 已获取、来自有效关注对象、尚未进入待读列表的候选 | 私有候选查询视图，不保证资源已就绪，不是第二套待读列表 |
| 评论列表（Comment List） | 查看某条内容讨论与互动的人 | 针对某个具体 Feed Object 版本的普通评论及获准披露的特殊评论引用 | 可以由不同主体维护，按类型形成讨论或互动视图，不存在天然唯一的权威列表 |

用户在自己的主页发表内容，不等于向自己投递私人消息；用户把内容加入待读列表，也不等于在自己的主页再次发表该内容。

### 2.2 Feed 的构成

HomeStation 将三种机制组合起来：

- **订阅与抓取**：主动 Pull 原生 HomeStation 动态及传统互联网公开内容。
- **社交投递**：接收好友、订阅者关系、符合规则的间接关系或其他允许来源的 Push。
- **用户侧筛选**：由本地程序或 LLM 根据用户状态组织最终可阅读内容。

用户定义的话题决定内容方向，但具体内容组合不必仅仅迎合已有偏好。默认推荐方向应服务用户，而不是将平台商业利益或无限延长停留时间作为首要目标。

“对用户更好”是推荐层的产品目标，不是协议可以自动保证的事实，也不能假定只要使用 LLM 就必然消除偏见或信息茧房。用户必须保留替换算法、调整规则和选择信息来源的能力。

### 2.3 注意力经济的定位

此前讨论的 Hot Pot 方向，将用户有限的消费时间视为可自主分配的资源，允许用户通过透明约定，将部分注意力交换给广告商或其他商业参与者。

当前架构为这一方向保留消费证明和自愿回执机制，但不预设完整 Token 系统，不确定发行、定价、清结算或反作弊方案，也不把经济模型变成正常阅读和社交互动的前置条件。

### 2.4 首版目标与非目标

首版应交付一个能实际使用的完整应用：用户可以发表、更新和撤回内容，获得候选信息，浏览已准备的 Feed，留下本地反馈，发表普通评论或特殊评论，并通过不同来源查看评论及有效互动统计。

首版不承担以下目标：构建全网完整索引、保证看见全部评论、统一所有人的推荐算法、实现完整注意力市场、证明用户真实的心理注意力，或者保证已传播内容可以被全网撤回。

## 3. 术语与既有系统边界

### 3.1 术语统一

本文统一使用 **BuckyOS** 与 **HomeStation**，并区分内容对象、投递入口、阅读状态与对外发表状态。

| 术语 | 本文含义 |
| --- | --- |
| Feed Object | 面向内容发表与传播的统一对象信封，包含内容描述及必要引用 |
| Message Object | 更强调发送者、接收者及送达关系的消息对象 |
| Social Inbox | HomeStation 的逻辑社交投递入口，接收他人 Push 的候选内容 |
| Spider | 主动采集内容的执行者，可以是普通程序，也可以是 LLM/Agent |
| Spider Cache | 抓取产生的候选对象和必要资源缓存 |
| 候选集合 | Push 与 Pull 输入在 Feed Object 层形成的逻辑集合 |
| 待读列表 | 已完成筛选和必要内容准备、可供用户开始消费的有限有序集合 |
| Source / Subscription | 可采集来源及用户的持续订阅关系；关注人的发表流是其中一种订阅 |
| 关注声明 | 向被关注方说明关注关系的可验证记录；不等于好友权限或公开全部关注名单 |
| 特殊评论 | 表达点赞、点踩、收藏、转发等互动的 Feed Object；可私有保存或经授权对外发表 |
| 变更声明 | 发表者签署的更新、撤回等生命周期记录，用于改变对象的当前展示与有效状态，不改写旧对象 |
| 消费证明 | 用户授权对外发送的、带签名的消费行为声明 |
| 收录者 | 提供对象接收、索引、查询和发现服务的独立参与者 |

### 3.2 复用消息与命名对象基础设施

本次讨论所称“Message Hub 协议”“Message Hub 的 Inbox”，指向已经形成的消息收发、对象投递与 Inbox 基础能力。

实现对接时，需要区分共享消息服务与消息 UI：按此前的系统分层，Message Center 承载消息服务，Message Hub 是相关消息界面。HomeStation 应复用底层服务与对象协议，而不是依赖某个聊天 UI 的内部实现。具体服务名、地址格式及 SDK 接口以现有工程为准，本文不假设已核实任何代码接口。

HomeStation 主要增加内容语义、社交投递规则、发表与收录能力，以及本地阅读管线，不重新建立一套身份系统、消息传输网络或好友关系数据库。

当前工程的 `src/kernel/buckyos-api/src/msg_center_client.rs` 已用 `Contact.access_level` 表达好友等级，并提供 `Contact.groups` 联系人分组。HomeStation 从 Message Center 读取这些关系，派生默认关注和分组展示策略；不另建一份权威好友关系。这里的分组指联系人分组，不等同于群聊或 Group Inbox。

### 3.3 网络协议与应用实现

| 应优先形成跨节点约定的部分 | 保持本地可演化的部分 |
| --- | --- |
| Feed Object 信封、版本身份与引用语义 | Spider 使用脚本还是 AI |
| Social Inbox 的投递及响应语义 | 候选评分、排序与淘汰策略 |
| 关注及取消关注的可验证通知 | 订阅任务、联系人／分组“不看”规则及候选补看入口 |
| 发表流和评论列表的发现与读取能力 | 待读列表的更新节奏与容量 |
| 普通/特殊评论的目标、身份、状态归并及统计依据 | 分类、游标、展示过滤及阅读起点策略 |
| 自愿公开互动与消费证明的语义 | 原始行为事件、兴趣推断及保留周期 |
| 对象版本更新、撤回声明及列表移除的区别 | 资源预取、播放器与内容查看体验 |

特别需要避免把“统一待读列表”理解为整个网络必须实现相同的列表协议。它首先是 HomeStation 应用内部的阅读模型。

## 4. 参与者、部署与模块划分

### 4.1 三种网络角色

HomeStation 的生态包含生产者、消费者和收录者。一台节点或一个用户可以同时承担多种角色。

**生产者**发表原创内容、评论或主动分享的内容对象。**消费者**获取、阅读并参与互动。**收录者**接收对象、建立索引并提供发现能力，不因此获得内容所有权或全网评论控制权。

原作者在某条内容的早期讨论中通常也是参与者发现入口，相当于该讨论的一个初始 Tracker，但不应成为无法替换的唯一入口。

### 4.2 用户端侧的含义

本文所说“把复杂度放在用户端侧”，主要指放在**用户控制的 Self-hosted HomeStation 环境**，通常是用户的 BuckyOS 服务器，而不要求所有任务都在浏览器内运行。

浏览器负责展示、交互和必要行为采集；持续抓取、推荐、资源准备、评论同步等任务可以在用户关闭浏览器后继续由服务器服务执行。

“资源已下载到 HomeStation”只表示其已存在于用户的托管节点，不等于已经缓存到每一台访问设备，也不自动意味着手机断网后仍可观看。

### 4.3 建议的逻辑模块

以下是便于实现的职责划分，不要求拆成独立微服务。首版可以由一个后端应用承载多个模块与后台任务。

| 模块 | 核心职责 |
| --- | --- |
| Publish Service | 创建正文、普通/特殊评论 Feed Object，维护发表流及可验证的更新、撤回记录 |
| Subscription / Source Manager | 管理来源、订阅意图及关注通知，读取好友与分组关系，驱动持续 Pull |
| Publishing Assets | 复用文件／对象存储接收图片、视频、语音等素材，管理上传、引用与保留 |
| Social Ingress / Delivery | 复用消息基础设施，执行准入、接收、投递确认与重试 |
| Spider Runtime | 读取原生来源或传统公开来源，封装对象并缓存必要资源 |
| Candidate Store | 管理候选引用、来源与关注关联、处理和入列记录，提供关注未入 Feed 的查询 |
| Selection Service | 根据用户状态、分类目标及本地反馈筛选内容，应用“不看”规则并输出推荐理由 |
| Resource Preparation | 下载或检查正文、图片、视频等资源，形成可消费状态 |
| Reading List Service | 维护统一待读列表、分类视图与游标 |
| Comment Sync / Index | 同步普通/特殊评论及变更声明，验证与归并状态，维护多来源视图及可复算统计 |
| Local Feedback | 临时记录行为并为抓取、推荐提供本地反馈 |
| Receipt Sender | 在授权下发送消费证明；快速互动沿用评论发表与投递能力 |
| Profile / Topic Views | 复用用户资料，组织作品、商品、精选栏目及 Topic 分类与汇总 |
| Web UI | 个人主页、Feed 阅读、内容详情、评论视图、发表及配置 |

收录节点可以复用 Publish、Ingress 和 Comment Index 等能力，但其部署角色不等于每个普通用户必须承担公共收录服务。

## 5. Feed Object：统一的发表与传播单元

### 5.1 Envelope 同构化

无论内容是好友投递、原生订阅、传统网页抓取，还是用户自己发表，进入 HomeStation 候选集合后都使用 Feed Object 表达。

对原生内容，保留其对象身份和来源信息。对外部内容，Spider 或 Agent 增加信封，将原始出处、内容摘要或正文引用、媒体引用等组织成可被 HomeStation 处理的对象。

同构化发生在信封层，不要求所有正文都变成同一种内容格式，也不要求进入候选集合前必须下载全部附件。

### 5.2 与 Message Object 的关系

Message Object 更强调“谁向谁发送了什么，以及送达结果如何”；Feed Object 更强调“谁发表了什么内容，以及该内容可以如何被引用和传播”。

同一个 Feed Object 可以通过多个投递通道送达，也可以被多次 Pull。传输路径的变化不应被误认为内容本身发生了变化。

Feed Object 与 Message Object 可以复用底层命名对象、签名和信封能力，但不在本文中决定它们必须完全共用 Schema，或必须定义两套独立格式。

### 5.3 最小语义集合

以下是需要在协议设计中覆盖的概念，不是已冻结的字段名或线格式。

| 概念 | 要表达的问题 |
| --- | --- |
| 协议/对象类型与兼容信息 | 这是何种对象，接收者能否理解 |
| 对象身份 | 当前具体内容版本是什么 |
| 发表主体 | 谁发表或封装了该对象，如何验证其声明 |
| 时间信息 | 发表时间及相关时间语义是什么 |
| 内容描述与资源引用 | 正文、图片、视频及其他内容在哪里 |
| 对象关系 | 该对象在评论、回复或引用哪个具体对象；特殊评论表达何种互动 |
| 来源信息 | 原生发表还是外部抓取，原始出处在哪里 |
| 可选的发表者能力信息 | 去哪里查询其发表流、评论视图或投递相关对象 |

实际签名范围、对象 ID 计算方式和序列化规则应与 BuckyOS 既有对象体系对齐。本文不另行选择哈希算法、DID 方法或传输协议。

### 5.4 不可变版本与可变名称

Feed Object 是命名对象体系中的内容对象。修改内容会产生新的 Object ID；可变名称可以解析到新的对象版本。

```text
一个可变名称
    ├─ 曾指向：Feed Object V1 / Object ID 1
    └─ 当前指向：Feed Object V2 / Object ID 2

针对 V1 的评论 ──引用──> Object ID 1
针对 V2 的评论 ──引用──> Object ID 2
```

**普通评论、点赞、收藏等都绑定具体 Object ID，而不是可变名称。** 作为同一发表的更新，新版本必须通过可验证关系关联旧版本；旧版本讨论和互动可以单独查看，但不能直接伪装成新版本的评论或认可。版本变更与撤回的传播约定见 §15。

发布者要传播可变内容，需要承担名称更新、版本传播和历史可见性等复杂度。旧版本一旦被其他节点获取，就不能假定仅通过更新名称可以消除旧版本及其评论。不过，这并不意味着协议承诺全网永久保存所有历史。

### 5.5 资源完整化不得暗中改变对象身份

候选转为待读时，“让 Feed Object 变完整”主要指准备它引用的资源，而不是悄悄改写已签名对象。

建议将不可变对象与本地资源解析表分开保存。例如对象仍引用原始媒体标识，本地解析表将该引用映射到已下载的文件。下载位置、缓存时间和可用性检查结果属于本地状态。

若确实修改了参与对象身份计算的正文或引用内容，就应按对象体系产生新版本，而不是继续冒用旧 Object ID。

仅封装一个可能变化的远程 URL，并不自动固定该 URL 背后的字节内容。对于需要可靠版本绑定的正文和媒体，后续应明确内容摘要、不可变资源引用或抓取快照的使用规则；未固定的外部资源需要保留这一限制。

### 5.6 外部抓取的来源边界

Spider 对外部内容的封装不等于获得原作者的签名。应能区分原始内容作者、来源地址，以及负责抓取和封装的用户或 Agent。

为抓取所使用的 Cookie、会话令牌等访问材料不应进入对外传播的 Feed Object。能在一次抓取会话中访问，也不自动意味着相关访问凭据可以转交给其他节点。

### 5.7 实例阅读约定与对象分层

以下实例是指导实现的语义样本，覆盖原型中的主要内容和操作；字段名用于把设计讲清楚，尚不是已发布 SDK 的线格式。实现协议时应保留这些语义，并映射到既有命名对象、签名、媒体存储和投递机制。

`P1`、`C1` 等是示例对象的别名，`<P1>` 表示对应的真实 Object ID，`<Alice DID>` 等表示实际身份，媒体引用也都是占位符。示例 JSON 展示参与对象身份计算的内容，不把自身 Object ID 放进被哈希内容中；签名通过既有命名对象机制承载，未在样本中伪造签名值。所有对外 Feed Object 均需验证其 `publisher`；业务关系中的原作者与对象签署者不能混淆。

| 层次 | 内容举例 | 边界 |
| --- | --- | --- |
| 不可变 Feed Object | 发表者、创建时间、正文、媒体引用、原始标签、评论类型和版本引用 | 修改这些事实会产生新 Object ID |
| 对象身份与签名载体 | 根据内容计算的 Object ID、发表者签名 | 验证身份与完整性，不用 UI 布尔值代替 |
| 投递与控制记录 | 收件人、投递结果、关注声明、更新或撤回声明 | 复用命名对象设施，但不混入原正文，也不计为新增评论 |
| 私有应用投影 | 来源路径、本地 Topic、推荐理由、准备状态、游标、按钮状态与统计缓存 | 可变、按用户保存，不传播为原作者签名的内容 |

首个发表对象以自身 ID 作为逻辑发表的起点，不需要自引用字段。后续版本可以通过 `publication_root` 及可验证变更关联到该起点；互动再次生效可用 `previous_state` 承接已公开撤回。这里提出的是关系语义，不能仅凭对象自报这些字段就接受更新权限。

### 5.8 原生发表与外部内容实例

#### E01：文字动态 P1

Alice 的原创动态可以直接在 Feed 卡片和个人主页展示。`tags` 是 Alice 发表的标签，不是阅读者本地分类的唯一依据。

```json
{
  "kind": "post",
  "publisher": "<Alice DID>",
  "created_at": "2026-10-08T10:00:00+08:00",
  "content": { "type": "text", "text": "今天开始搭建阳台菜园。" },
  "tags": ["园艺", "生活"]
}
```

#### E02：多图动态 PIC1

图片顺序、说明及资源引用固定在发表对象中；UI 将资源引用解析成当前有权访问的图片地址，不将本机缓存路径写回对象。

```json
{
  "kind": "post",
  "publisher": "<Alice DID>",
  "created_at": "2026-10-08T10:05:00+08:00",
  "content": {
    "type": "image",
    "text": "搭建前后的对比。",
    "media": [
      { "type": "image", "resource_ref": "<photo-before>", "mime": "image/jpeg", "width": 1600, "height": 1200, "alt": "搭建前" },
      { "type": "image", "resource_ref": "<photo-after>", "mime": "image/jpeg", "width": 1600, "height": 1200, "alt": "搭建后" }
    ]
  }
}
```

#### E03：视频动态 VID1

封面可用不等于视频已准备完成。播放资源的就绪状态由 Resource Preparation 单独返回。

```json
{
  "kind": "post",
  "publisher": "<Alice DID>",
  "created_at": "2026-10-08T10:10:00+08:00",
  "content": {
    "type": "video",
    "title": "花箱安装过程",
    "media": [
      { "type": "video", "resource_ref": "<garden-video>", "mime": "video/mp4", "thumbnail_ref": "<video-cover>", "duration_ms": 90000 }
    ]
  }
}
```

#### E04：语音动态 AUD1

录音保存后成为稳定音频引用。未来生成的转写可以作为本地派生结果或另行发表的新内容，不能默默改写此对象。

```json
{
  "kind": "post",
  "publisher": "<Alice DID>",
  "created_at": "2026-10-08T10:15:00+08:00",
  "content": {
    "type": "audio",
    "text": "记录一下今天的种植计划。",
    "media": [
      { "type": "audio", "resource_ref": "<garden-voice>", "mime": "audio/ogg", "duration_ms": 45000 }
    ]
  }
}
```

#### E05：长文 ART1

摘要用于 Feed，正文用于 Reader；正文引用指向不可变资源，使评论能够绑定所读的具体内容。

```json
{
  "kind": "post",
  "publisher": "<Alice DID>",
  "created_at": "2026-10-08T10:20:00+08:00",
  "content": {
    "type": "article",
    "title": "阳台菜园第一周",
    "summary": "从光照、容器到浇水的实践记录。",
    "body": { "format": "text/markdown", "resource_ref": "<garden-article-body>" }
  },
  "tags": ["园艺"]
}
```

#### E06：抓取封装 EXT1

Bob 的 Spider 封装传统网页。对象由 Bob 签署，只证明 Bob 发表了此封装，不表示网站作者参与签名；正文快照与原始 URL 分开记录。

```json
{
  "kind": "post",
  "publisher": "<Bob DID>",
  "created_at": "2026-10-08T10:25:00+08:00",
  "content": {
    "type": "article",
    "title": "家庭种植指南",
    "summary": "一篇公开园艺文章的摘要。",
    "body": { "format": "text/html", "resource_ref": "<external-article-snapshot>" }
  },
  "source": {
    "kind": "web",
    "original_url": "https://example.org/garden-guide",
    "original_author": "示例网站作者",
    "captured_at": "2026-10-08T10:24:00+08:00"
  }
}
```

只有远程 URL 而没有快照或内容哈希的封装，不能声称固定了远程字节版本。同一网页被不同人独立封装可能形成不同 Object ID；首版保留来源关联，不仅凭 URL 相同就合并为同一个已签名对象或混合其评论统计。

#### E07：作品入口 WORK1

作品栏目按发表者声明的分类组织；Feed 分发入口，作品页面承担实际展示。

```json
}
```

商品对象可以被评论、收藏和转发；购买操作由原始页面承接。动态库存等页面状态不自动成为这个对象的已固定内容。

```json
  "created_at": "2026-10-08T10:35:00+08:00",
```

### 5.9 评论与互动实例

以下对象都由 Bob 创建，针对 E01 的 P1。它们共享评论索引，通过 `comment_type` 形成正文、点赞、收藏和转发视图；没有正文的特殊评论可以省略 `content`。

#### E09：正文评论 C1

```json
{
  "kind": "comment",
  "comment_type": "text",
  "publisher": "<Bob DID>",
  "created_at": "2026-10-08T11:00:00+08:00",
  "content": { "type": "text", "text": "可以先试试耐阴的叶菜。" },
  "references": [{ "relation": "comment_on", "object_id": "<P1>" }]
}
```

C1 是 Bob 的独立发表，可以进入 Bob 的主页及 P1 的不同评论视图。对同一原文再次发表不同观点应创建另一条独立评论，不按“同人同目标”去掉正文评论。

#### E10：点赞 L1

```json
{
  "kind": "comment",
  "comment_type": "like",
  "publisher": "<Bob DID>",
  "created_at": "2026-10-08T11:01:00+08:00",
  "references": [{ "relation": "comment_on", "object_id": "<P1>" }]
}
```

三个收录来源提供 L1 仍只是一条点赞。同一个 Bob 对 P1 的多个有效点赞对象也不能直接相加，按 §11.4 的互动键及变更关系求当前有效状态。

#### E11：私有收藏 B1

```json
{
  "kind": "comment",
  "comment_type": "bookmark",
  "publisher": "<Bob DID>",
  "created_at": "2026-10-08T11:02:00+08:00",
  "references": [{ "relation": "comment_on", "object_id": "<P1>" }]
}
```

B1 的存储及查询权限为 Bob 私有，不进入公开发表流，也不投递给 Alice；这由服务端权限和发表策略执行，不能只靠 UI 隐藏。私有记录的 `created_at` 是创建时间，不代表网络发表。Bob 选择公开收藏时，创建对应的公开签名声明并记录两者关联，不能顺带公开其他私有收藏历史。

#### E12：普通转发 R1

```json
{
  "kind": "comment",
  "comment_type": "repost",
  "publisher": "<Bob DID>",
  "created_at": "2026-10-08T11:03:00+08:00",
  "references": [{ "relation": "comment_on", "object_id": "<P1>" }]
}
```

Bob 的主页展示“Bob 转发了 Alice 的 P1”。Bob 的订阅者收到的是这个可验证转发及原文引用；取消转发撤回 R1，P1 保持不变。

#### E13：引用转发 Q1

```json
{
  "kind": "comment",
  "comment_type": "quote",
  "publisher": "<Bob DID>",
  "created_at": "2026-10-08T11:04:00+08:00",
  "content": { "type": "text", "text": "准备照这个方案试一次，先从小花箱开始。" },
  "references": [{ "relation": "comment_on", "object_id": "<P1>" }]
}
```

Q1 同时是 Bob 的一条发表和 P1 的特殊评论。普通正文评论、点赞和转发数量分别从类型视图派生，不能因为它进入了多个列表就重复计数。

### 5.10 更新、撤回与再次互动实例

以下 Feed Object 的新版本与生命周期声明共同说明状态变化。`feed_change` 是控制记录的示意类型，不是额外的一条正文评论。

#### E14：P1 更新为 P2，附更新声明 U1

P2 是新的 Feed Object：

```json
{
  "kind": "post",
  "publisher": "<Alice DID>",
  "created_at": "2026-10-08T12:00:00+08:00",
  "publication_root": "<P1>",
  "content": { "type": "text", "text": "调整计划：先搭建两个小花箱。" },
  "tags": ["园艺", "生活"]
}
```

Alice 同时签署 U1，说明这两个版本属于同一发表：

```json
{
  "kind": "feed_change",
  "publisher": "<Alice DID>",
  "created_at": "2026-10-08T12:00:01+08:00",
  "operation": "update",
  "publication_root": "<P1>",
  "previous_state": "<P1>",
  "target_object_id": "<P1>",
  "replacement_object_id": "<P2>",
  "scope": "publication"
}
```

接收者验证两份对象的发表主体与版本关系，再更新当前发表投影。C1、L1、B1、R1 和 Q1 仍引用 P1，不能因为主页默认展示 P2 就把它们解释为针对 P2 的互动。

#### E15：撤回正文 D1

Alice 撤回整条逻辑发表，承接已知更新 U1：

```json
{
  "kind": "feed_change",
  "publisher": "<Alice DID>",
  "created_at": "2026-10-08T12:30:00+08:00",
  "operation": "withdraw",
  "publication_root": "<P1>",
  "previous_state": "<U1>",
  "target_object_id": "<P2>",
  "scope": "publication"
}
```

P1/P2 不再作为这条发表的有效当前内容推荐；他人评论、转发和私有收藏仍保留各自身份，引用区显示目标发表已撤回。若只撤回某个历史版本，需要明确使用版本范围并指定该版本，不能把两种作用范围混为一谈。

#### E16：取消点赞 CL1，再次点赞 L2

Bob 对 L1 发出撤回声明 CL1：

```json
{
  "kind": "feed_change",
  "publisher": "<Bob DID>",
  "created_at": "2026-10-08T11:10:00+08:00",
  "operation": "withdraw",
  "publication_root": "<L1>",
  "previous_state": "<L1>",
  "target_object_id": "<L1>",
  "scope": "publication"
}
```

再次点赞产生新的 Feed Object L2，并明确承接取消状态：

```json
{
  "kind": "comment",
  "comment_type": "like",
  "publisher": "<Bob DID>",
  "created_at": "2026-10-08T11:20:00+08:00",
  "publication_root": "<L1>",
  "previous_state": "<CL1>",
  "references": [{ "relation": "comment_on", "object_id": "<P1>" }]
}
```

已知有效状态依次是 L1、CL1、L2，贡献计数依次为 1、0、1。迟到的 L1 或 CL1 不覆盖已知 L2；无法验证前序关系时按 §15.6 处理。取消普通转发同样由 Bob 撤回 R1，不改写 P1，也不要求 Alice 代为减数。

### 5.11 关注通知与本地候选投影实例

这一节是辅助记录示例，不把它们伪装成 Feed Object。它们与前面的内容对象共同支撑产品操作。

#### E17：关注声明 FOLLOW1

```json
{
  "kind": "follow",
  "publisher": "<Bob DID>",
  "created_at": "2026-10-08T09:00:00+08:00",
  "target": { "publisher": "<Alice DID>", "stream": "<Alice 的发表流入口>" },
  "state": "active"
}
```

Bob 签署并向 Alice 投递 FOLLOW1，同时启动 Pull。Alice 据此知道 Bob 关注了自己，但不能推断 Bob 已阅读 P1。若关注由好友关系派生，本地保留好友依据，另一方向由 Alice 的服务独立处理。取消有效关注时发表明确承接前序的 inactive 声明；“不看 Alice 的朋友圈”只修改 Bob 本地设置，不发送该取消声明。

#### E18：P1 已进入 Bob 的候选但尚未进入待读

```json
{
  "owner": "<Bob DID>",
  "object_id": "<P1>",
  "source_paths": [
    { "transport": "pull", "subscription_id": "<Bob 的 Alice 订阅>" },
    { "transport": "push", "sender": "<Alice DID>" }
  ],
  "local_topics": ["园艺"],
  "selection": { "state": "not_selected", "reason_code": "reading_window_full" },
  "resources": { "state": "not_prepared" },
  "first_admitted_at": null,
  "opened_from_followed_candidates_at": null
}
```

在 Bob 有效关注 Alice、没有“不看”规则且 P1 仍有效的前提下，这条候选可以出现在“关注未入 Feed”集合。后来选中并准备完成时，应用写入 Reading Entry、首次入列时间及诸如“来自已关注的 Alice”的推荐理由；P1 的字节和 Object ID 不变。个人点赞状态、评论计数和统计视图也由本地索引组合提供，不附加到 Alice 的签名对象中。

## 6. 候选输入：Social Inbox 与 Spider Cache

### 6.1 两个入口，一个逻辑候选集合

Social Inbox 接收别人 Push 的内容；Spider Cache 保存主动 Pull 的内容。二者不必共享同一物理存储，但上层应以统一的 Feed Object 候选视图处理它们。

候选只是“可能值得后续考虑的素材”。进入候选集合不代表已经进入待读列表，更不代表用户已经看到。

### 6.2 轻量候选原则

Social Inbox 原则上只接收 JSON 级信封、必要的小型内容和资源引用，尽量不在接收阶段下载图片、视频等重型资源。

Push 和 Pull 都有容量限制。准入较宽不等于存储无限，也不等于任何发送者可以要求接收方承担无限流量或抓取成本。

Spider 有一个必要例外：某些资源只能在当前抓取 Session 中获取，若不同时保存，之后可能失效。因此 Spider Cache 可以在候选阶段预先缓存这部分资源。

### 6.3 社交准入

HomeStation 的社交 Inbox 应允许比私人聊天更广泛的内容触达，包括直接好友、主动订阅的发布者、符合用户规则的间接关系，以及用户允许的商业内容来源。

例如用户关注 A 并在 A 的内容下评论，B 通过 A 或讨论参与关系发现该用户，有机会向其投递内容。但这种可发现性不是绕过接收方权限的通行证：是否允许 B 进入候选，仍由接收方准入规则决定。

宽准入表示允许更广泛的关系和内容来源，不表示取消权限校验，也不表示让陌生来源无条件进入。

准入与推荐分离：准入解决是否接收，推荐解决是否值得展示。广告或间接关系内容即使被缓存，也不能由发送者自行提升为待读内容。

### 6.4 Push 响应语义

| 结果 | 语义 | 不代表什么 |
| --- | --- | --- |
| 已缓存（Cached） | 已作为候选接收，等待后续处理 | 不承诺进入用户 Feed |
| 已收到（Received） | 根据关系和接收策略给出更高一档的接收预期，内容大概率进入后续阅读处理 | 不等于已展示、已读或保证最终入列 |
| 拒绝（Rejected） | 当前权限、关系或准入策略不允许接收 | 不需要向发送方公开内部推荐规则 |

这些是语义标签，不是已确定的网络状态码。

接收方还可以隐藏内部处理粒度：即使内部已采用较高接收级别，也可以只披露通用确认，不告诉发送者更多状态。**信息披露策略与接收结果是两个维度**，不能把隐藏状态变成额外的“已读”承诺。

失败、超时与重复请求的处理属于可靠投递实现。建议使用现有消息设施的幂等和重试能力，避免同一对象重复投递导致重复候选；未得到确认不能直接解释为接收方拒绝。

### 6.5 Spider 的实现自由

Spider 可以由规则程序、常规爬虫、LLM Agent 或其组合实现。协议只关心它能否产出合法 Feed Object 并写入候选缓存。

首版主要处理两类公开来源：原生 HomeStation 的发表内容，以及传统互联网内容。如何选源、多久抓一次、如何摘要和分类，是可替换的应用策略。

对于已是原生 Feed Object 的内容，不应仅因从另一个 URL 抓到就随意重新包装并丢失原对象身份。对于同一对象的多次到达，应保留不同来源路径，同时避免重复存储同一对象。

### 6.6 关注、好友与“不看朋友圈”

用户主动关注某人后，HomeStation 应向对方发送由关注者签署的关注声明，并启动对其发表流的持续 Pull。取消有效关注时同样通知对方；通知失败保留重试状态，不阻止已经具备读取权限的采集，也不向用户假称对方已经收到。被关注者知情不代表该关系必须向所有人公开，关注名单的公开展示仍按用户权限处理。

**好友关系比关注关系更强，Message Center 中的好友默认互相关注。** 双方各自的 HomeStation 根据本方已有好友关系派生关注并维护自己的声明，不能由一方伪造另一方的签名。关注本身不反向提升为好友，也不授予私聊权限。

实现中保留关注的来源依据，例如用户主动关注、好友关系派生。相同对象由多个依据产生关注时只维护一个有效关系和一套采集进度；好友关系解除后移除好友派生依据，仍有主动关注依据时继续关注。好友仍存在时，仅移除主动关注依据不会取消好友默认关注；只想停止看到对方动态，应使用“不看朋友圈”。对方主页的关注者数量按已收到的有效声明去重统计，不能把本方联系人数量当作对方已确认的关注者数量。

| 用户行为或关系 | 关注与采集 | 展示效果 |
| --- | --- | --- |
| 主动关注某人 | 建立关注、通知对方、持续 Pull 入候选 | 候选经过筛选与准备后才进入待读 |
| 成为 Message Center 好友 | 双方默认派生关注并各自采集 | 默认按关注内容处理，不保证每条都入列 |
| 不看某人的朋友圈 | 保留好友和关注关系，按采集策略继续维护候选 | 默认 Feed 与关注补看入口隐藏该人的直接动态 |
| 不看某个联系人分组的朋友圈 | 复用 Message Center 分组成员，动态应用本地规则 | 对该组成员执行相同隐藏规则，分组变化后重新计算 |
| 恢复看朋友圈 | 不重复创建关注，也不重复采集已有对象 | 对仍在保留范围内的内容恢复正常筛选与补看资格 |

“不看”是私有展示设置，不作为取消关注或拉黑通知发给对方，不改变聊天权限，也不改变他人查看我的权限。明确的个人或分组“不看”规则优先于默认关注规则；多个隐藏规则同时命中时，解除其中一条不会绕过其他规则。规则变更应作用于已有待读条目，生效时遵循浏览位置稳定原则。

首版“不看”作用于该人发表的条目，包括其原创、评论和转发；其他未被隐藏用户对这些内容的独立引用仍属于引用者的发表，不推导为全网内容封锁。UI 保留原作者与引用者的区别。

### 6.7 来源、订阅意图与 Topic

Source 表达可采集入口，Subscription 表达用户为什么持续采集它。Follow、粘贴 URL 和自然语言输入最终都进入这套管理模型：保存原始意图、解析得到的一个或多个来源、所属用户、有效状态、采集进度、最近成功时间与失败原因。自然语言订阅由 Agent 持续维护来源映射，不能退化为一次搜索后丢弃用户意图。

对具备 HomeStation 关注入口的主体执行知情通知。普通网页或 RSS 没有该能力时，记录“来源不支持关注通知”，按公开读取能力采集，不捏造送达确认，也不通过无关渠道发送通知。暂停采集是运行设置，取消订阅是关系变更；只有所有有效采集依据都消失后，才停止相应共享任务，历史对象按保留策略处理。

Topic 的内容标签、用户订阅和聚合视图应分别保存。用户可订阅某个主题意图，系统将抓取结果映射到本地 Topic；作者原始标签保留在内容中，本地分类不会改写已签名对象。Topic 数量和热度先按本地有效内容及明确时间窗口计算，并标明范围，不把本地排行称为全网热榜。

## 7. 推荐与内容准备：生成统一待读列表

### 7.1 持续运行的用户侧服务

推荐服务根据用户当前状态，从候选集合中挑选有限数量的内容。其输入可以包括用户配置的话题、分类目标、当前状态、经允许使用的位置线索，以及本地阅读反馈。

实现可以从简单程序开始，也可以使用复杂 LLM 或 Agent。HomeStation 不要求所有节点运行同一模型，也不要求 LLM 参与每一次排序。

位置和状态只是可使用的输入，不应被设计成所有用户必须提供的信息。

筛选结果需要附带可展示的推荐理由，例如关注来源、命中的主题或用户规则，并保存在本地 Reading Entry 中。理由可以由规则或模型产生，至少能关联实际采用的来源或条件；不要求公开完整算法，也不能让来源作者替阅读者声明“为什么推荐”。

### 7.2 筛选与准备是两个不同职责

```text
候选对象
   │
   ├─ 未选中：保留为候选或按策略淘汰
   │
   └─ 被选中
        │
        ▼
     内容准备
        ├─ 成功：进入可消费的待读列表
        └─ 未完成：保持准备状态、重试或按策略放弃
```

推荐回答“值得看什么”，资源准备回答“现在能否顺畅地看”。不能把一个推荐分数较高、但正文或必要媒体尚不可用的对象直接等同于已经准备好的条目。

两者可以由同一个服务执行，也可以拆成不同模块。

### 7.3 入列时的内容准备

进入待读列表之前，尽可能下载正文、图片、视频等必要资源，使用户开始浏览时无需再从头发现和抓取内容。

是否完整下载、是否允许远程媒体、可用存储与流量预算，由用户配置。允许远程引用时，准备阶段需要检查其访问条件和可用性，并处理明显过期或不可访问的链接。

一次链接检查不能保证远端资源永不失效。因此，首版应区分“资源已在本地”和“依赖可访问远端”，记录必要的检查状态，并在阅读时支持重新验证、重试或清楚提示不可用。

对于只准备了封面而视频不可用的条目，不应向用户暗示视频已完整就绪。采用流式播放或其他降级策略时，应与用户配置一致。

### 7.4 统一而有限的列表

HomeStation 维护一个统一的待读列表，具有顺序、时间信息和分类相关状态。AI 在整体筛选时已经考虑分类，不需要为每个分类独立生产一套候选与资源副本。

“统一列表”不意味着无限保存所有历史。“有限”也不意味着用户只能看到一屏；它表示准备窗口与保存范围受容量策略控制，可以持续补充、更新和淘汰。

看过内容不会自动触发删除。保存历史、移出待读窗口和清理资源是不同的本地策略。

## 8. 分类、游标与 Feed UI

### 8.1 无分类视图是主入口

默认主 Feed 是统一待读列表的无分类视图，即不应用类别限制的阅读入口。这里的“无分类”不是“没有被打标签的内容”这一单独类别。

其他分类是在同一列表上形成的视图，例如某个话题、来源或用户配置的分类条件。同一个对象可以匹配多个视图，但不因此变成多个独立内容对象。

### 8.2 每个分类独立维护游标

每个分类视图，包括默认主视图，都有自己的浏览位置。

```text
统一待读列表
   ├─ 默认视图：游标 A
   ├─ 技术视图：游标 B
   └─ 其他分类：游标 C
```

待读列表不是必须严格出队的生产者—消费者队列。用户可以从最新内容开始，也可以回到上次位置，由用户配置决定，不应强制补看全部“尚未消费”的旧条目。

### 8.3 动态更新时保持浏览稳定

以下是实现建议，而非网络协议：

- 游标优先引用稳定条目身份或顺序锚点，不仅保存容易随重排变化的数组下标。
- 用户正在浏览时，后台补充和重排不应导致当前内容突然跳走。
- 返回某个分类时，处理好游标对应条目已被淘汰的情况。
- 区分内容发表时间、加入待读时间和实际消费时间，不用一个时间字段混淆所有语义。

首版可以采用统一排序、分类过滤的简单模型，再演进到更复杂的阅读体验。

### 8.4 UI 的职责边界

主 Feed UI 从待读服务获得当前分类的可阅读内容，负责展示、展开、播放、发表互动、切换评论视图和保存浏览位置。关注补看入口按 §8.5 查询候选并按需准备资源，不能伪装成已准备好的待读视图。

UI 不负责在每次打开页面时重新运行完整抓取与推荐流程，也不应直接把外部内容页面当成有权操作用户系统的代码。

阅读列表、个人发表主页和评论列表需要在数据接口与页面语义上明确区分，避免将私人推荐结果意外展示给访客。

### 8.5 来自关注对象但未进入 Feed 的内容

原型中的“已关注”筛选继续表示待读列表中来自有效关注对象的内容。另提供一个私有补看入口，查询已经获取、来自有效关注对象、仍在保留范围内且尚未进入过待读列表的候选。该入口同样尊重撤回、访问权限及“不看某人／分组”的规则。

它可以包含尚未筛选、未被选中或资源仍在准备的对象，应显示对应状态。关注提高采集的确定性，不构成全部内容入列的承诺；未抓取到或已淘汰的对象不在此集合中，界面应说明保留范围与同步状态，不宣称它是来源完整历史。

该集合是 Candidate Store 上的查询，不创建第二套对象副本，也不要求预先下载全部资源。用户主动打开某条内容时，可以绕过推荐评分请求资源准备，成功后阅读或按用户选择加入待读；资源不可用时保留清楚提示，不能绕过访问权限。

为区分“从未进入 Feed”和“曾进入但已移出”，保留对象首次入列记录，而不能只用当前两个列表做差集。直接从补看入口阅读也保存独立状态，默认补看视图排除已经这样读过的内容；它们不是临时曝光日志，不能随日志清理立即再次出现。此最小历史至少覆盖对应候选的保留期。

### 8.6 阅读模式、搜索与个人门户

标准、读图、长文和沉浸式模式复用同一对象和资源解析，阅读模式是展示方式，不改变对象身份。类别、Topic 与当前搜索条件共同定义查询视图，切换模式不能暗中丢弃这些限制。不同视图的游标使用稳定对象锚点；图片组序号、播放位置等属于本地阅读状态。

首版搜索覆盖当前查询范围内的标题、正文和作者，明确与全网搜索、来源全部历史区分。已完整加载的小列表可以在 UI 过滤；分页时由应用查询层对同一范围搜索，不能把“当前页无结果”当作整个视图无结果。

个人门户复用既有用户身份与资料能力。公开入口按主页所属用户返回有权展示的发表对象，私人待读与候选接口只向所有者开放。作品、商品通过发表者提供的内容分类组织；精选由用户维护对象引用与顺序，改变精选不修改原对象。作品和商品可以是元数据加原始页面 URL，详情操作进入作者页面，首版不要求 HomeStation 实现交易或网页创作引擎。

### 8.7 图片、视频、语音与素材发布

媒体发布复用既有文件／命名对象存储，流程为“上传或录制 → 素材保存成功 → 取得稳定资源引用 → 创建 Feed Object → 写入发表流并投递”。封面、媒体类型、尺寸、时长及图片顺序属于内容描述；临时上传地址和访问令牌不能进入对外对象。

上传失败不显示为发布成功。客户端以一次发布意图的幂等标识重试，避免生成多条相同动态。未发表素材可按草稿保留期清理；已经发表、收藏保留或仍被其他有效对象引用的资源不能随普通缓存一起淘汰。撤回发表后再按引用、保留与访问策略清理资源，不承诺回收其他节点的副本。

## 9. 本地行为反馈与隐私边界

### 9.1 形成两个反馈回路

UI 需要采集必要的消费信号，例如实际展示、停留、点击、展开、播放及主动操作结果。它们反馈到两个层面：

```text
本地消费行为 ──> Spider：以后去哪里、找什么
本地消费行为 ──> 推荐层：已有候选中选什么、如何组织
```

这些数据用于帮助个人应用改进，不是默认向原作者或广告商发送的网络回执。

### 9.2 本地、临时、由用户控制

原始行为数据默认只在用户控制的本地环境中临时保留，不对外发送。其格式、抽样、统计和淘汰属于应用实现，不纳入 Feed 网络协议。

用户主动保存的收藏、点赞状态及其更新和撤回依据不属于这里的临时行为日志，应独立持久保存。清理浏览事件或待读窗口不能顺带清除收藏，也不能使已知取消的互动恢复有效。

如需从原始事件形成较长期的偏好状态，也应明确保存目的、用户控制方式和清理策略，不能把“临时本地记录”偷偷变成默认永久行为档案。

停留时间、点击或播放记录不直接等同于真实兴趣。如何解释这些信号，属于可演化算法，不在协议中写死判断阈值。

### 9.3 云模型调用是需要显式控制的外发路径

Self-hosted 部署本身不能替代数据外发控制。若 Spider 或推荐模块调用外部模型，将原始行为、个人位置或可识别用户偏好写入请求，同样构成向第三方发送数据。

因此建议将这些数据的外发权限与普通公开内容处理分开管理。默认本地反馈闭环不得以“调用 AI”为由自动越过隐私边界；外发必须符合用户明确授权的范围。

公开 Feed 内容也应被视为待分析资料，而不是允许 Agent 修改权限、泄露行为数据或发起任意投递的操作指令。

## 10. 自愿反馈与消费证明

### 10.1 快速反馈就是特殊评论

**点赞、点踩、收藏等主动互动都是特殊类型的评论，因此也是 Feed Object。** 它们由互动者创建，引用目标内容的具体 Object ID，并表达互动类型。普通评论用正文表达观点，特殊评论用结构化动作表达观点或个人标记，不再另建一套独立的 Feedback Object 传播与统计系统。转发同样属于特殊评论，其发表和取消规则见 §11.5。

特殊评论对外发表时由互动者签名，沿用评论的投递、收录、Pull、来源合并及视图机制。内容作者可以提供自己的互动列表和统计，但不能成为点赞数、收藏数等数据的唯一事实来源。接收方根据实际获得的有效记录计算结果，统计规则见 §14.5。

统一对象模型不改变可见性：收藏默认保存为私有的特殊评论，不进入公开发表流，不向原作者、好友、讨论参与者或公共收录者投递，也不计入公开收藏数。用户明确选择公开收藏时，才将对应声明签名发表。公开改回私有时，应撤回先前公开的声明并保留本地收藏状态，不能承诺删除已传播副本。

点赞等操作是否对外发表，应由清晰的操作语义和用户授权决定；本地状态、公开声明状态和投递状态分别保存。取消已公开的点赞或收藏，需要传播由互动者签署的撤回声明，不能仅在本地减一或删除记录。再次操作需要有可验证的后继关系，规则见 §15.4—§15.6。

这些持久的个人操作状态与 §9 的临时消费事件不同。快速反馈也不等同于消费证明，不因采用统一评论模型而自动参与经济约定。

### 10.2 消费证明的目的

部分商业内容可能希望用户提供消费回执。HomeStation 将这种对外声明称为**消费证明（Proof of Consumption）**，用来承载未来注意力经济中的约定履行信息。

例如双方约定用户完整观看一段视频后获得某项权益，用户完成消费后，自愿发送描述该行为的签名声明。

正常阅读不以发送消费证明为前提，内容对象提出回执请求也不等于用户已经同意发送。

### 10.3 消费证明的最小语义

| 概念 | 含义 |
| --- | --- |
| 消费目标 | 对应哪个具体 Feed Object 版本 |
| 消费行为 | 声明进行了什么行为，例如完成视频播放 |
| 行为结果与必要时间信息 | 表达约定要求的最小事实范围 |
| 签署主体 | 与用户 DID 或被允许的身份机制有关的签署身份 |
| 验证材料 | 验证声明来源和完整性的签名信息 |
| 接收方/约定关联 | 如未来经济协议需要，关联相应接收方和约定 |

后两类关联的具体编码、重放防护及结算使用方式，留给后续协议细化。首版只需要明确对象机制和用户授权边界，不需要完整商业闭环。

签名证明某个身份签署了声明，不能仅凭签名证明自然人确实注意到内容。当前“君子协议”模型不应被包装成强反作弊的注意力证明。

### 10.4 匿名性与最小披露

未来可以考虑 Tracker ID、场景身份或其他方式降低主 DID 暴露，但仅更换标识不自动等于不可关联匿名。其与签名身份、跨内容跟踪和跨服务关联的关系仍需单独设计。

首版不应宣称已经实现完整匿名方案，也不应把全量停留、点击日志附在消费证明中。只发送用户同意、且对应约定真正需要的内容。

## 11. 评论即 Feed Object

### 11.1 评论是独立发表

用户 B 评论 A 的内容时，B 创建一个新的 Feed Object，正文是自己的评论，并引用 A 内容的具体 Object ID。

评论可以默认出现在 B 的个人发表流。别人打开 B 的主页时，可以看到“我评价了某个内容”，被评价的原文位于引用区。

这使得经常评论、但很少发表长篇原创的用户同样拥有自己的内容流。评论的发表、保存与传播不依附于原作者的服务器。

### 11.2 引用语义示意

以下仅是帮助理解的语义草图，不是最终 JSON Schema；对象 ID 和签名由既有对象体系生成或承载。

```json
{
  "kind": "comment",
  "comment_type": "text",
  "publisher": "<评论者 DID>",
  "created_at": "<创建时间>",
  "content": {
    "type": "text",
    "text": "这是我对该版本内容的评论。"
  },
  "references": [
    {
      "relation": "comment_on",
      "object_id": "<被评论 Feed Object 的具体版本 ID>"
    }
  ]
}
```

不应将这里的 `comment` 再实现成一套与 Feed Object 平行、不参与普通发表和传播的独立内容体系。

若将来支持多级回复，可增加“回复哪个评论”与“属于哪个根内容讨论”的关系，但回复目标同样需要版本明确；具体关系字段尚未冻结。

### 11.3 内容与评论同等重要

本设计将内容与其评论视为同样重要的信息组成部分。评论可以影响阅读者的理解，因此发布权的开放不能以作者独占评论呈现权为代价。

作者可以表达自己希望保留和排序哪些评论，但阅读者必须能够选择其他评论来源和组织方式。

### 11.4 普通评论与特殊评论共享底层能力

评论对象至少区分普通正文评论、点赞、点踩、收藏、普通转发和引用转发等语义类型；这里的名称是语义分类，不是已冻结的字段值。所有类型都具有独立对象身份和明确的目标版本，对外发表的记录必须能验证发表主体。

普通评论允许同一用户对同一内容发表多条独立观点。对于点赞或收藏这类开关操作，建议以“互动者 DID + 目标版本 Object ID + 互动类型”标识一个逻辑互动状态，同一键至多贡献一个有效计数。多个新 Object ID、重复点击、多路径投递或重试都不能让同一个点赞被计为多次；取消和再次点赞是该状态的后续变更。

UI 可以把普通评论展示为讨论列表，把特殊评论展示为按钮状态、数量及可查看的参与者列表。类型筛选只改变展示，不建立互不相通的收集系统；显示“评论数”时应说明是否包含特殊评论，默认可只统计普通正文评论。

私有特殊评论使用同一对象与索引模型，但始终受所属用户的访问权限约束。只有允许对外发表的部分参与 §12 的传播；收到点赞也不意味着必须将其作为普通正文卡片插入主 Feed。

### 11.5 转发也是特殊评论

普通转发创建一个由转发者签署、引用原文具体版本的新 Feed Object，正文可以为空；引用转发使用相同关系并附带转发者的正文。两者都进入转发者自己的发表流，按普通发表权限通知相关方，并沿用评论列表的收集与统计能力。

UI 同时展示转发者与原作者，不能把转发者伪装成原作者，也不能把转发行为仅实现为增加原文计数或传输一次原对象。取消转发撤回自己的转发对象，不撤回原文，不删除其他人的评论，也不承诺抹除已传播副本；用户修改引用转发正文时产生新版本并沿用更新协议。

首版普通转发按钮按“转发者 + 目标版本 + 普通转发类型”维护开关状态，重复点击和重试不增加独立转发数；引用转发允许形成多条独立发表，按逻辑发表归并其修改版本。统计可以分别列出普通转发和引用转发数量；原文换版不自动继承两类转发的背书。

## 12. 评论发表、传播与持续同步

### 12.1 默认发表流程

以下流程适用于公开或已获准向相应对象传播的评论，也适用于对外发表的特殊评论。私有收藏不进入这条对外传播链路。

```text
评论者创建评论 Feed Object
             │
             ├─ 写入自己的个人发表流
             ├─ Push 给原内容作者
             ├─ 按普通 Feed 传播规则 Push 给好友
             ├─ Push 给已发现的该讨论参与者
             └─ 可选提交给一个或多个收录节点
```

“已发现的参与者”包括评论者查看评论列表时发现的既有评论者。它不是要求每个用户先得到全网完整参与者集合。

对于好友传播，评论沿用普通 Feed 的权限和传播范围。对讨论参与者的投递也必须通过接收方准入，不因为双方评论过同一内容就获得任意发送其他内容的权限。

### 12.2 作者接收与 Owner Comment List

评论投递到原作者后，应用判断其引用对象是否与自己发表的内容有关。原作者开放评论时，默认应接收相关对象，并将其加入自己维护的评论列表展示区域。

君子协议鼓励作者明确确认接收，并展示相关评论。但需要区分“收到对象”和“已经加入某个可查询评论视图”：通用 Received 本身不是已展示证明。

作者可以维护自己的保留和排序规则，不能以此控制其他节点是否保存该评论。

### 12.3 评论列表的持续追踪

用户参与过某个 Feed Object 的评论之后，HomeStation 默认持续追踪该对象的讨论，而不是只在发表评论时读取一次评论列表。

追踪可以综合 Push 更新与周期性 Pull：读取作者的评论列表，也读取已发现参与者或收录节点提供的相关评论。

持续任务的调度周期、历史保留、活跃讨论优先级，以及用户暂停追踪的方式，属于本地策略。逻辑上的持续追踪不要求无间隔轮询或无限存储。

作者后来从自己列表中移除评论，不会使已经到达其他节点的对象和索引自动消失。

### 12.4 从作者 Tracker 到参与者网络

在讨论开始时，新用户通常先找到原作者，因此原作者提供初始评论列表和参与者线索。

当 B、C 等参与者通过列表发现彼此后，它们就可以直接投递和持续获取相关评论。原作者由唯一入口变成多个发现节点之一。

这里形成的是围绕一个具体对象讨论的发现关系，不必自动创建聊天群，也不必把所有参与者变成私人好友。

### 12.5 传播的实现约束

为使上述模型可落地，建议采用以下限制：

- 以对象身份和目标接收方对投递去重，重试不重复创建评论。
- 由主动发表评论或明确转发触发扩散，不能把每次收到评论都当作再次全量群发的指令。
- 对大量参与者使用批次、速率和资源预算；未覆盖的节点仍可以通过 Pull 发现。
- 接收评论后分别更新评论索引和候选状态，不把“进入讨论索引”强制等同于“进入个人主 Feed”。
- 更新和撤回沿已知传播路径通知，并可通过 Pull 补齐；已验证变更必须更新已有索引和统计，不因未被推荐而忽略，也不触发无条件再次群发。

这些是可靠性与资源管理建议，不改变评论向原作者、好友和已发现参与者主动传播的设计方向。

## 13. 收录者与冷启动

### 13.1 公共评论收录

独立收录者允许用户将针对某个 Feed Object 的评论提交给它，并允许其他用户查询该对象相关的已收录评论。

收录者可以绕开作者作为唯一查询入口的问题，但“独立于作者”不意味着某个收录者天然完整或绝对公平。用户应能选择多个收录者，并在本地合并结果。

### 13.2 不限于评论

评论本身也是 Feed Object，因此收录能力可以自然扩展到全部 Feed 内容：接收对象、提供索引、支持内容发现及后续 Pull。

收录者是内容传播生态中的第三类角色，不只是作者服务器的备份，也不是所有用户必须注册的中心平台。

### 13.3 系统冷启动

新用户可能既没有可投递对象的人，也没有明确订阅来源。系统可以预置若干收录节点，使其立即具备可 Push 和可 Pull 的入口。

预置节点应可配置、替换和移除，不应成为协议不可替换的根。本文不指定实际运营方或节点地址。

预置收录服务提供的是内容入口，不自动获得用户的私人待读列表、位置、停留记录或兴趣画像。

## 14. 评论的三种视图

### 14.1 作者视图

作者视图由原内容作者维护，可按其意愿保留、移除评论引用和调整展示顺序。

它表达的是“作者提供的评论组织结果”，不是协议宣布的全网全部评论。

### 14.2 收录者视图

收录者视图表达某个独立节点已经收集到的评论集合。可以存在多个收录者视图，各自具有不同覆盖范围和维护策略。

查看者可以绕开作者，直接向收录者提交评论或查询讨论。

### 14.3 用户本地默认视图

本地默认视图根据用户已经获取的作者、收录者、好友及讨论参与者数据，尽量合并更多评论，并应用本地排序和过滤规则。

```text
作者评论列表 ───────────┐
多个收录者列表 ─────────┤
好友/参与者投递 ─────────┼─> 合并与去重 ─> 本地默认评论视图
历史抓取与本地保存 ───────┘
```

“默认视图”只是该用户当前的本地结果，不声称覆盖所有评论。用户可以根据需要切换视图，作者无权强制每个阅读者采用作者视图。

### 14.4 合并时需要保留来源

建议索引至少能回答：评论针对哪个版本、从哪些路径获得、在哪个维护者列表中出现过、目前在哪些视图可见。

同一个评论从三个来源到达，应合并为一个对象并保留来源关系，而不是显示三次。对于不同 Object ID、但文字相同的评论，不应仅凭文本相同就认定它们是同一条已签名发表。

本地用户仍然可以过滤垃圾内容、屏蔽来源和调整顺序。反对作者垄断评论，不等于强制阅读者显示所有收到的内容。

### 14.5 从可验证的评论记录派生互动统计

点赞、公开收藏等统计应沿用作者视图、收录者视图和本地合并视图。**计数是指定视图中有效互动记录的派生结果，不是内容作者可以自行填写并要求其他节点采信的事实。** 作者或收录者可以返回统计缓存，但应同时提供可查询的记录依据、视图范围和统计时点；未取得依据的数字只能标明为该来源的声明。

接收方按以下步骤构建自己的统计：

1. 验证互动者签名、目标版本和互动类型，并验证相关更新、撤回声明的权限及关系；无法验证的记录不进入有效统计。
2. 按 Object ID 合并重复到达的对象，保留来源；再按逻辑评论或互动状态归并版本与后继变更，不能直接把多个来源的计数相加。
3. 普通评论及引用转发按独立逻辑发表统计，修改版本不额外增加数量；点赞、收藏和普通转发按 §11.4—§11.5 的互动键统计，在当前已知有效状态下每键至多计一次。
4. 收到有效撤回后使相应统计失效并重算。旧对象重放不能覆盖已知的新状态；不能确定先后的冲突状态单独标记，暂不计入有效互动数。
5. 按当前视图、类型、可见性和本地过滤规则输出数量，并保留继续同步的状态。私有收藏不能进入公共统计；旧版本的互动不能自动累加到新版本。

“本地已验证的点赞数”仍只表示当前已获取记录中的结果，可能尚未收到新的点赞或取消声明，不等于全网实时总数。不同视图的结果可以不同，差异不自动证明某方造假；已有记录和声明的历史才是进一步判断的依据。

这套机制使作者无法仅靠修改计数字段冒充其他用户的互动，也使第三方能复算已收集记录。它不证明一个 DID 就对应一个自然人，不能单独解决批量身份刷赞、合谋或来源隐瞒记录；来源选择、身份信任和反滥用策略仍由阅读者控制。

## 15. 发表、修改、删除与排序的语义

### 15.1 必须区分的操作

| 操作 | 影响对象 | 不能被误解为 |
| --- | --- | --- |
| 发表 Feed Object | 产生一个可传播内容版本，加入发表或相关索引 | 已经全网送达 |
| 修改内容 | 产生新 Object ID，可更新名称指向 | 用原 ID 原地改写已发表内容 |
| 作者撤回自己的内容 | 发布可验证撤回声明，更新自己的入口并通知已知接收方 | 能删除所有节点已有副本 |
| 取消点赞或公开收藏 | 互动者撤回自己发表的特殊评论，接收方据此更新状态和统计 | 内容作者代替互动者修改意愿，或只修改一个计数 |
| 取消转发 | 转发者撤回自己的普通／引用转发对象 | 撤回原文、删除他人评论或保证消除已传播副本 |
| 列表维护者移除引用 | 改变自己维护的某个视图 | 删除他人发表的评论对象 |
| 调整列表顺序 | 改变某个列表的组织结果 | 改变评论正文或原始版本绑定 |
| 本地缓存淘汰 | 释放本节点资源 | 作者撤回内容或否认曾经收到 |

删除、修改和顺序变更的编码需要利用既有对象与列表能力继续细化，但首版必须遵循本节的权限、传播和状态处理约定，不能把这些操作压缩成一个含义不明的 `delete`。

### 15.2 控评的可发现性

目标不是保证百分之百发现所有评论，而是让作者知道：自己对评论列表的筛选或移除可能被其他节点对比发现，并留下可观察的痕迹。

可以依赖的线索包括：曾抓取到的列表版本、作者给出的接收确认、其他节点保存的评论、收录者索引，以及后续列表变化。

“公开评论原则上应通知原作者”构成君子协议的基线，私有收藏等不在此范围内。发起投递不等于作者已经成功接收，只有保留了相应确认或列表历史，才能支持更强的判断。

### 15.3 区分差异与证据

| 观察到的情况 | 可以表达的结论 |
| --- | --- |
| 本地有评论，作者当前列表没有 | 作者视图当前未列出该评论；原因未必已知 |
| 已确认作者收到，但尚未见于作者列表 | 已收到，当前未在该视图发现；可能仍在处理或被筛选 |
| 历史列表包含，后来完整版本或明确变更中移除 | 该维护者列表发生了可观察的移除 |
| 只有部分分页、查询失败或同步不完整 | 信息不足，不能据此断言主动删除 |

因此，对外列表应能表明查询范围、分页或读取进度，并为维护者与版本识别留下空间；具体采用快照、增量还是变更记录仍待确定。

若首版要展示“曾被作者移除”，必须有足够历史或变更依据。仅仅比较两份不完整列表，只能展示差异，不能伪装成已证明的恶意控评。

### 15.4 更新与删除的君子协议

不可变对象不提供原地修改和全网物理删除，但应用仍需支持用户理解的“编辑”和“删除”。双方通过可验证的变更声明协作：发表者说明自己修改或撤回了什么，接收者验证后更新自己的默认展示、索引与统计。这套约定同样适用于正文、普通评论以及点赞、收藏等特殊评论。

| 操作 | 发表者应提供 | 遵循协议的接收者应执行 |
| --- | --- | --- |
| 编辑内容或评论 | 新版本对象，以及将原版本与新版本关联起来的签名更新声明 | 记录版本关系，默认展示已知的有效新版本，并提供版本区别；旧版本引用保持原目标 |
| 删除已发表内容或评论 | 指向被撤回发表的签名撤回声明，明确撤回的是某个版本还是整条逻辑发表 | 默认不再作为有效内容展示和推荐；引用处可显示已撤回占位，保留必要状态以处理后续同步 |
| 取消公开点赞或收藏 | 由互动者签署、关联原互动及前序状态的撤回声明 | 将该互动从当前有效统计中移除；不因此删除其他人的评论或互动 |
| 再次点赞或重新公开收藏 | 明确承接已知取消状态的新声明 | 验证后恢复该互动键的有效状态，仍至多计一次 |
| 取消普通或引用转发 | 转发者签署针对自己转发发表的撤回声明 | 更新转发者发表视图与有效转发统计，不改写或撤回原文 |

更新或撤回只能由该对象的原发表者，或可验证地获得相应授权的主体发起。原文作者不能撤回别人发表的评论或点赞，列表维护者也不能用移除引用代替互动者的撤回。对外部抓取内容，封装者只能变更自己发表的封装对象；来源页面变化、失联或返回 404，不自动构成原作者的签名撤回。

正文换版后，原版本上的评论、点赞和公开收藏仍指向原版本；可以展示历史互动入口，不能把原来的认可冒充为对新内容的认可。撤回原文也不会级联撤回其他人发表的评论，相关 UI 应保留“所引用版本已撤回”的上下文。

### 15.5 变更声明的最低语义与传播

更新、撤回声明本身应是可寻址、可签名验证的命名对象，复用既有对象传输与发现能力。它们属于生命周期控制记录，不作为新增正文评论或点赞参与统计。以下是最低语义，具体字段与编码仍需对齐既有对象体系：

- 声明主体及签名，和它有权变更目标发表的验证依据。
- 被变更的逻辑发表或互动键、明确的目标对象版本，以及变更范围；不能用一个后来改变指向的名称代替目标身份。
- 操作含义、更新后的对象引用，以及前序对象或声明关系，使接收者能够判断已知状态之间的先后，而不是只比较发送者填写的时间。

发表者应向原投递路径中的已知接收方、相关作者和收录节点传播变更，并在自己的可查询入口提供变更记录，供离线节点后续 Pull。接收者同步评论列表时也应同步相应的更新与撤回状态，不能只拉当前仍展示的引用。变更披露沿用原对象的权限范围；私有收藏的创建、修改和删除都不向公共节点广播。

对外声明的前序关系只引用已获准披露的记录，不能为验证公开互动而要求用户公布私有收藏历史。公开收藏改回私有后再次公开时，应承接上次公开撤回状态，本地私有状态仍独立保存。

已验证变更的应用不经过内容推荐筛选，也不以是否值得进入主 Feed 为条件。发布与通知需要可恢复的任务状态；节点离线只能延迟收敛，不能让已取消的点赞因为从未发出撤回而永久有效。

### 15.6 乱序、重放与保留边界

接收者先收到撤回、后收到原对象时，应保存待核验的声明；确认目标身份与变更权限后，不能再把旧对象当作有效新发表展示或计数。已经验证的撤回状态不能因正文、媒体或候选缓存被淘汰而一并丢失，否则旧副本重放会使内容或点赞“复活”。首版需保留必要的变更依据和当前状态；压缩历史时必须保留足以继续验证并拒绝旧状态覆盖的依据。

未核验或权限不符的变更不能使已有有效记录失效，也不能仅凭制造“冲突”压低统计；只有通过相应身份与权限校验的声明才能进入状态归并。

首版建议由用户自己的发表服务串行生成同一逻辑发表或互动键的后继变更。对并发、断链或相互矛盾的声明，应明确标记待同步或冲突；不能凭到达顺序、作者自报时间或原文作者的计数裁决。冲突未消解时，不把有争议的肯定状态计入有效互动数，正文版本也不冒充已确认的唯一最新版本。有效后继声明应能明确承接并消解已知分支。

君子协议约定接收者如何更新默认展示和统计，不强迫所有节点抹除历史字节。对已撤回内容，正文与资源是否继续保留、是否提供明确标记的历史查看入口，仍由保存方按其策略处理；这种历史保存不能被展示成仍然有效的发表或互动。作者和收录者可以不遵守约定，系统只能通过保留依据、比较视图和替换来源降低对单方的依赖。

## 16. 协议能力与本地数据模型建议

本节是为实现落地补充的结构建议，概念与前述原则一致，但不把示意名称当作现有 SDK 或已发布接口。

### 16.1 跨节点最小能力集合

| 能力 | 请求/输入的概念 | 结果/输出的概念 |
| --- | --- | --- |
| 投递 Feed Object | 目标 Social Inbox、对象或对象引用、必要投递上下文 | 接收结果及允许披露的信息 |
| 读取具体对象 | Object ID | 该版本对象或明确的不可获取结果 |
| 读取个人发表流 | 发表者、读取范围或继续读取位置 | 对象引用及继续读取信息 |
| 读取评论视图 | 目标版本 ID、视图维护者、评论/互动类型、读取范围 | 该维护者获准提供的记录引用、顺序和继续读取信息 |
| 向收录者提交对象 | Feed Object 或可获取引用 | 收录接收结果，不承诺全网传播 |
| 查询相关内容/评论 | 对象目标或收录查询条件 | 该收录者范围内的结果 |
| 发表或取消公开互动 | 目标版本及互动者签署的特殊评论或撤回声明 | 复用评论投递的接收结果，不直接接受外部设置计数 |
| 同步更新与撤回 | 目标发表/互动、已知变更位置及读取权限 | 可验证的变更记录、覆盖范围与继续读取信息；保留撤回的发现能力 |
| 查询互动统计与依据 | 目标版本、视图、互动类型及读取范围 | 派生数量、依据记录入口、统计时点与同步状态 |
| 通知关注关系 | 关注者签署的目标发表者／来源、有效状态及前序关系 | 对方接收结果；不授予好友权限，也不表示已读 |
| 发送消费证明 | 已授权的签名消费声明 | 接收结果；不等同于已经完成经济结算 |

上述能力应尽量映射到已有 Post/Send Object、对象获取和列表查询机制。是否使用 HTTP、WebSocket 或其他传输，不是本次讨论要重新规定的重点。

### 16.2 本地逻辑数据集合

| 集合 | 建议保存的内容 | 归属 |
| --- | --- | --- |
| Object Store | 不可变正文、普通/特殊评论 Feed Object、已获取的关联对象 | 本地对象存储，私有对象不得通过公开读取接口提供 |
| Sources / Subscriptions | 来源入口、原始订阅意图、来源映射、主动／好友派生依据、采集启停与进度 | 私有应用状态；好友及分组真相来自 Message Center |
| Follow Records | 本方签署及收到的关注／取消声明、前序关系、验证与通知状态 | 按关系披露范围提供；双方各自声明自己的关注 |
| Feed Preferences | 不看某人／联系人分组的规则，阅读起点与其他用户筛选配置 | 私有设置，不等于修改好友关系或取消关注 |
| Candidate Entries | 对象引用、多条来源路径、关注关联、到达时间、筛选原因与准备状态 | 私有应用状态；支持关注未入 Feed 查询 |
| Admission / Reading History | 对象首次入列及从补看入口阅读的最小记录 | 私有状态；保留期至少覆盖候选，不与临时行为日志一并清理 |
| Resource Cache | 媒体引用到缓存文件的映射、资源状态、检查时间 | 私有缓存 |
| Publishing Assets | 上传／草稿状态、稳定资源引用、发表关联及资源保留依据 | 用户素材，复用既有存储；不等同于可随时淘汰的缓存 |
| Reading Entries | 对象引用、排序、时间、分类、准备状态及推荐理由 | 私有应用状态，不修改原始 Feed Object |
| View Cursors | 分类/视图与浏览位置、阅读起点配置 | 私有应用状态 |
| Published Lists | 用户主动发表内容的引用及顺序 | 按发表权限提供 |
| Comment Index | 目标版本到普通/特殊评论的关系、类型、逻辑发表、来源和视图归属 | 本地索引；对外部分须有明确维护者及访问范围 |
| Lifecycle Records | 签名更新/撤回声明、版本与前序关系、验证结果、已知有效状态及冲突 | 按原发表权限保存和同步；不随正文缓存淘汰 |
| Personal Interaction State | 私有收藏、当前点赞／转发等持久状态，以及关联的公开声明与投递状态 | 私有应用状态；公开部分通过特殊评论表达 |
| Saved Collections | 收藏、稍后再看等用户主动维护的引用集合及顺序 | 私有持久数据；收藏关联对应特殊评论，不随待读窗口淘汰 |
| Interaction Stats | 按目标版本、视图、类型和有效记录计算的统计缓存及依据 | 可重算的派生数据；更新或撤回触发失效，不作为作者独占的事实源 |
| Topics / Profile Collections | 本地主题映射、用户订阅、范围明确的汇总，以及作品／商品索引和精选引用顺序 | 分类与聚合索引；用户身份和资料复用既有服务 |
| View History | 为列表差异判断保留的快照或变更依据 | 本地观察记录，保留策略可配置 |
| Local Behavior | 临时消费事件、必要统计或偏好状态 | 默认不对外 |
| Outgoing Tasks | 待投递对象、目标、重试与确认状态 | 本地任务状态 |

候选对象、待读条目、评论索引可以引用同一个 Object ID。一个对象被移出主 Feed，不代表它必须从个人发表流或评论索引中删除。

### 16.3 处理幂等与任务恢复

建议以现有对象身份作为内容级去重基础，对“对象—接收目标”建立投递级去重，特殊评论另按互动键归并有效状态。对重启后需要继续的发表、更新、撤回投递，资源准备和评论追踪任务，保留可恢复状态。变更记录与当前状态应先可靠保存，再更新可重算的统计；不能只更新显示数字而丢失记录依据。

首版不必引入复杂分布式调度器，但应避免浏览器关闭或服务重启后，已发表评论只写入本地而永远不再尝试通知原作者。

### 16.4 支撑产品原型的应用能力

跨节点能力之外，HomeStation 还需向自己的 UI 提供以下应用能力。表中名称表达职责，不要求各自独立部署；除按权限公开的门户读取外，均以当前用户身份鉴权。

| 能力 | 输入与操作 | 应返回或维护的结果 |
| --- | --- | --- |
| 来源与订阅管理 | Follow、URL、自然语言意图，暂停／恢复，移除主动订阅依据 | 解析来源、有效关注依据、通知结果、抓取状态与失败原因 |
| 好友与分组联动 | 读取 Message Center 的好友、分组及变化 | 幂等更新好友派生关注和有效展示规则，不复制权威好友库 |
| 朋友圈展示设置 | 配置不看某人／分组、恢复展示 | 当前有效规则及对已有候选／待读的过滤结果 |

| 关注补看查询 | 有效关注关系、未入列条件、直接阅读状态、分页位置 | 保留范围内的候选、准备／未选中原因及同步状态 |

| 发布与素材管理 | 文字／媒体、上传结果、发布幂等标识 | 草稿、稳定资源引用、发表对象及待投递状态 |
| 评论及互动 | 正文、点赞、收藏、转发，取消或更新 | 新对象／变更声明、当前个人状态及可重算统计 |

UI 原型中的 `FeedObject` 实际承担卡片数据模型。实施时由不可变 Feed Object 与上述私有投影组合成 UI 数据，`isLiked`、`isBookmarked`、`isReposted`、`recommendReason` 及各种计数不能成为原作者签名内容的一部分。

## 17. 端到端场景

### 17.1 传统公开内容进入个人 Feed

1. Spider 按用户话题发现一篇含视频的公开内容，并封装为 Feed Object。
2. 若视频只能在当前 Session 中获取，Spider 同步保存必要资源；否则先保存引用。
3. 对象进入候选集合，推荐服务决定是否选中。
4. 资源准备模块下载必要内容，或根据用户配置检查可用远端。
5. 准备完成后加入统一待读列表；用户通过默认或分类视图看到它。
6. UI 记录临时消费反馈，用于后续抓取与推荐，不自动把行为发送给来源站点或模型服务。

### 17.2 间接社交关系触达

用户 B 经由 A 的讨论发现用户 C，向 C 的 Social Inbox 投递内容。C 的准入规则允许这一类关系，于是返回 Cached；内容随后是否进入待读列表，由 C 自己的推荐与准备服务决定。

B 不能把 Cached 解释为 C 已观看，也不能凭同一讨论参与关系获得 C 的私聊权限或行为记录。

### 17.3 评论传播与作者移除

A 发表 P1，B 评论得到 C1。C1 引用 P1 的 Object ID，进入 B 的主页，并投递给 A、B 的好友、已发现参与者及选定收录者。

A 开放评论并将 C1 加入作者视图。参与者 D 抓取该视图后，也保存 C1 并持续跟踪讨论。

之后 A 从作者视图移除 C1。D 和收录者仍可能提供 C1，阅读者的本地默认视图仍可显示它。若保存了作者列表的前后状态，可以表明作者视图移除了该引用；否则仅显示不同视图的覆盖差异。

### 17.4 原文换版不能继承旧评论背书

A 把 P1 修改为意思不同的 P2，签署关联两者的更新声明，并更新同一个名称指向 P2。C1 仍然针对 P1。查看 P2 时可以提供旧版本及其讨论入口，但不能把 C1 混入 P2 的评论区而隐藏版本区别。

### 17.5 自愿消费证明

某内容提出消费回执需求，但用户未参加对应约定时，正常播放只产生本地反馈。

用户明确参加相关约定后，应用可在符合条件时构造消费证明，引用具体对象并签名，发送给约定接收方。该证明不包含未经授权的全部浏览日志；首版不因发送成功而宣称已完成支付或强反作弊验证。

### 17.6 点赞、取消与第三方统计

B 对 A 的 P1 发表点赞 L1，作者和独立收录者都收到该特殊评论。D 合并两个来源后只计一个点赞；A 自报更多点赞时，D 不把没有记录依据的部分当作已验证结果。

B 随后签署取消声明 CL1。D 从收录者获知并验证 CL1 后，移除该有效点赞；即使 A 仍返回 L1，也不能覆盖已知撤回状态。B 再次点赞时发表明确承接 CL1 的新声明 L2，恢复一次计数。P1 更新为 P2 后，这些记录仍只属于 P1。

### 17.7 私有收藏与内容撤回

B 收藏 P1 时创建私有特殊评论，只维护自己的收藏状态。作者和公共收录者既收不到该记录，也不能据此增加公开收藏数。B 若主动公开收藏，则传播对应签名声明；改回私有时撤回该公开声明，本地收藏仍保留。

A 撤回 P1 后，遵循协议的节点停止把它作为有效发表推荐，B 的收藏可显示“目标内容已撤回”，不自动删除 B 的收藏或其他用户的评论。已保存历史可按本地策略保留，但不冒充当前有效内容。

### 17.8 好友默认关注与未入 Feed 的补看

A 与 B 是 Message Center 中的好友，双方 HomeStation 默认派生关注并各自维护通知与 Pull。B 抓取到 A 的 P1、PIC1 和 VID1，三者均进入候选，但当前只选中并准备了 P1。B 的主 Feed 和“已关注”筛选中出现 P1，补看入口列出仍在保留范围内的 PIC1 和 VID1，并提示资源准备状态。

B 主动打开 VID1 后按需准备并阅读，保存补看阅读状态；默认补看列表不再反复显示它。B 配置“不看 A 所在分组的朋友圈”后，A 的直接动态在主 Feed 与补看入口均按规则隐藏，关注与好友关系保持不变，也不向 A 发取消关注通知。

### 17.9 转发与取消转发

B 对 A 的 P1 创建 R1，R1 出现在 B 的主页并由 B 的订阅者采集；附带个人观点时创建 Q1。两者都保留 P1 的具体版本引用与 A 的原作者身份。

B 取消 R1 时签署撤回，其他节点验证后更新 B 的发表投影和 P1 的有效普通转发数。P1、Q1 以及其他人的评论不随之删除；A 把 P1 更新为 P2，也不会让 R1 或 Q1 自动成为针对 P2 的转发。

## 18. 首版实现范围与推进顺序

### 18.1 必须形成的完整功能闭环

| 范围 | 首版最小实现 |
| --- | --- |
| 原生发表 | 创建 Feed Object，维护个人发表流，支持版本明确的引用 |
| 媒体发表 | 图片、视频、语音上传与稳定引用，发布重试幂等，区分用户素材和资源缓存 |
| 更新与撤回 | 签名变更声明、权限验证、已知路径通知与 Pull 补齐，正确处理乱序和旧状态重放 |
| Push | Social Inbox、基本准入和 Cached/Received/Rejected 语义 |
| Pull | 原生发表流抓取，加至少一种可工作的传统公开内容采集实现 |
| 订阅与好友联动 | Follow 知情通知，好友默认互相关注，URL／自然语言意图持久化并驱动持续采集 |
| 朋友圈偏好 | 按 Message Center 联系人或分组配置“不看”，不改变好友权限和关注关系 |
| 候选统一 | 两类来源进入同构候选视图，具有容量与对象去重 |
| 关注补看 | 查询已获取但从未入列的关注候选，展示准备状态，支持按需阅读及最小历史记录 |
| 推荐 | 可替换的筛选接口，先使用简单规则或基础 LLM，向 UI 返回推荐理由 |
| 内容准备 | 必要资源下载/检查，区分准备中与可消费 |
| 阅读 UI | 一个统一待读列表、默认视图、基础分类、每视图游标 |
| 本地反馈 | 必要消费行为临时记录，并能影响后续采集或筛选 |
| 快速反馈 | 点赞、收藏等作为特殊评论，持久个人状态与自愿对外发表分离，支持取消与再次操作 |
| 转发 | 普通／引用转发作为特殊评论进入个人发表流，取消只撤回自己的发表 |
| 评论 | 普通/特殊评论均为 Feed Object，公开部分进入发表流并按授权范围传播 |
| 评论同步 | 作者列表、持续追踪、参与者发现和去重 |
| 多视图 | 作者视图、至少一个独立收录来源、本地合并默认视图 |
| 互动统计 | 按有效普通/特殊评论记录归并和计数，提供范围与依据，不依赖作者自报数字 |
| 冷启动 | 可配置预置收录入口，不依赖先建立好友关系 |
| 个人门户与 Topic | 复用用户资料，支持作品／商品分类、精选引用、本地主题与范围明确的汇总 |
| 消费证明机制 | 明确对象语义与授权入口，可验证最小签名声明；无需商业结算 |

首版不能只有漂亮 Feed 页面而缺少评论传播，也不能把所有评论强制留在原作者服务器上。后两点会失去本架构最重要的开放性。

### 18.2 建议的推进顺序

**第一阶段：稳定对象语义并验证互通。** 先对齐既有命名对象、签名和投递基础设施，明确 Feed、普通/特殊评论、更新/撤回声明、Push 响应以及列表维护者等最低语义，用小规模多节点验证互通。

**第二阶段：贯通阅读链路。** 实现来源订阅、好友关注派生与知情通知、持续采集、候选管理、基础筛选与推荐理由、资源准备和分类游标，并支持“不看”设置与关注补看，使用户可以连续浏览真实内容。

**第三阶段：贯通发表与评论网络。** 实现文字／媒体、普通／特殊评论及转发的发表，作者／好友／参与者投递和变更持续同步，以及个人门户、独立收录节点、三种评论视图和基于记录的统计。

**第四阶段：接入反馈并加固。** 接入本地行为闭环、自愿快速反馈与消费证明机制，验证隐私、重试、资源限制、版本变更和视图差异的正确性。

这只是交付顺序，不改变首版需要覆盖的完整范围；复杂推荐、完整经济模型和强匿名方案继续留在后续演进。

## 19. 首版验收场景

以下用可观察结果检验架构，而不是用某种具体技术栈作为验收条件。

| 编号 | 场景 | 预期结果 |
| --- | --- | --- |
| A01 | Push 与 Spider 得到同一个原生对象 | 统一按 Feed Object 处理；去重并保留来源路径 |
| A02 | 候选包含大量图片/视频引用 | 接收阶段不被迫全量下载；资源成本有边界 |
| A03 | 某抓取资源只在当前 Session 有效 | Spider 能保存必要资源，不把会话凭据传播出去 |
| A04 | 陌生来源不满足准入 | 可以拒绝；宽准入不绕过用户规则 |
| A05 | 内容获得 Cached 或 Received | 发送方不能据此得知已读或完整行为 |
| A06 | 推荐选中但必要资源不可用 | 不伪装成完整就绪条目；有准备、重试或清晰降级 |
| A07 | 在默认与两个分类间切换 | 基于统一列表，各视图保持独立游标 |
| A08 | 从最新内容打开后返回旧位置 | 不强制队列式补读，也不因后台重排突然跳动 |
| A09 | 用户正常阅读、点击、播放 | 产生本地反馈；默认无第三方行为上报 |
| A10 | 模型模块尝试带出私人行为数据 | 未授权时不能越过外发边界 |
| A11 | 用户收藏但未授权公开 | 创建私有特殊评论并持久保留，不发送、不公开查询，也不计入公共收藏数 |
| A12 | 用户发表公开正文评论 | 评论有独立 Feed Object 身份，出现在个人发表流并通知相关方 |
| A13 | 原作者节点暂时不可用 | 评论仍可本地发表并走其他传播路径；作者通知可重试 |
| A14 | 同一评论通过多个节点重复到达 | 一条评论、多个来源，不重复展示或无限再广播 |
| A15 | 原作者移除其列表中的评论 | 其他节点仍可保留；默认视图可从其他来源发现 |
| A16 | 对比的是不完整评论列表 | 不把缺失直接标注为已证实删除 |
| A17 | 原文由 V1 更新为 V2 | V1 评论不冒充 V2 评论，引用仍指向具体版本 |
| A18 | 新用户没有好友和订阅 | 通过预置但可替换的收录入口获得初始内容 |
| A19 | 用户未参加回执约定 | 消费后不自动发送证明 |
| A20 | 用户同意发送消费证明 | 只发送约定范围内的签名声明，不捆绑全量行为日志 |
| A21 | 同一点赞由作者、收录者及好友重复提供 | 验证互动者签名并合并来源，同一互动键最多计一次 |
| A22 | 作者自报大量点赞却未提供记录依据 | 只能显示为来源声明，不能并入本地已验证统计 |
| A23 | 用户取消点赞后，旧点赞再次到达或服务重启 | 已验证撤回继续生效，不因重放或缓存淘汰恢复计数 |
| A24 | 先收到撤回声明，后收到原对象 | 先保留待核验记录；验证目标与权限后，不将旧对象作为有效新发表 |
| A25 | 原文作者试图撤回别人的评论或点赞 | 因缺少对应发表者授权而拒绝；作者只能调整自己的列表 |
| A26 | 普通评论编辑，或原文由 V1 更新为 V2 | 评论编辑不增加独立评论数；V1 点赞和收藏不自动成为对 V2 的认可 |
| A27 | 取消点赞后再次点赞 | 通过有效后继关系恢复一次计数，不用到达时间覆盖状态 |
| A28 | 用户将公开收藏改回私有 | 传播公开声明的撤回，保留本地收藏；不承诺抹除远端历史副本 |
| A29 | 作者撤回原文，其他节点保存有评论和收藏 | 默认显示目标已撤回；不级联撤回他人的发表或清除个人收藏 |
| A30 | 收到并发矛盾变更，或同步尚未完成 | 暴露冲突或同步范围；不把有争议状态计入有效互动数，不宣称全网实时总数 |
| A31 | 已撤回对象仍被保留在明确标记的历史视图 | 可按本地策略查看历史，不作为当前有效发表或互动统计 |
| A32 | 私有收藏的对象 ID 被提交给公开读取接口 | 权限校验拒绝披露，知道对象 ID 不等于获得读取权 |
| A33 | 用户关注原生发表者，对方暂时离线 | 保存签名关注声明并重试通知；在具备读取权限时仍持续 Pull，不把关注或确认解释为已读 |
| A34 | Message Center 已有好友关系，或好友关系新建立 | 默认派生互相关注，双方各自处理自己的声明；主动与好友依据重叠时不重复关注或采集 |
| A35 | 用户设置不看某人／某联系人分组 | 主 Feed 与关注补看入口均按直接发表者过滤；不取消关注，不改变聊天权限，不发送隐藏设置 |
| A36 | 分组成员变化，或好友关系解除 | 重算展示规则及好友派生关注；保留仍有主动依据的关注，继续遵守其他命中的隐藏规则 |
| A37 | 关注来源的内容进入候选但未被选中 | 不强制加入待读；在权限、保留范围和展示规则允许时进入关注补看集合 |
| A38 | 补看条目未准备资源，用户主动打开 | 按需准备并返回就绪／失败状态，保存直接阅读记录，默认不反复补看同一条 |
| A39 | 已入列条目后来被移出待读，或临时行为日志被清理 | 不因简单差集或日志清理重新冒充从未入列的关注候选 |
| A40 | 普通转发、引用转发及取消 | 形成转发者自己的签名发表，保留原文版本与作者；取消不撤回原文，统计按对应规则归并 |
| A41 | 媒体上传失败、发布重试或清理缓存 | 失败不显示发表成功，重试不重复创建动态，已发表或需保留的素材不被普通缓存淘汰 |
| A42 | 自然语言订阅建立后关闭浏览器再恢复服务 | 保留意图、来源映射及采集进度，后台可继续执行并显示状态 |
| A43 | 读取个人门户、作品／商品／精选 | 只返回获准公开的数据；精选调整不改写原文，私人候选、收藏和推荐理由不随门户泄露 |
| A44 | 同一内容在不同模式、Topic 和搜索条件下查看 | 保持对象身份与查询约束，推荐理由可追溯，分页搜索不局限于当前加载页 |
| A45 | 关注普通 RSS 或网页，对方没有关注通知入口 | 继续按公开能力采集并标明不支持通知，不伪造知情确认 |

多视图验证至少需要作者、评论者/阅读者和一个独立收录角色。不能只在单个数据库里模拟三个标签，就宣称已验证作者无法独占评论传播。

## 20. 待进一步确定的设计点

| 议题 | 已明确的边界 | 待决定内容 |
| --- | --- | --- |
| Feed/Message 关系 | 语义不同，复用既有基础设施 | 共用哪些字段、信封与 SDK 类型 |
| 实例与线格式 | §5.7—§5.11 的实例覆盖内容、互动和状态关系 | 与命名对象／SDK 对齐字段及签名编码，不能把示例别名当真实 ID |
| 对象身份与签名 | 版本不可混淆 | 具体序列化、签名范围及既有对象接口映射 |
| 外部资源版本 | 仅固定 URL 不足以固定资源内容 | 快照、摘要和不可变引用的最低要求 |
| Push 回应 | Cached、Received、Rejected 与披露粒度分开 | 具体状态码、错误与兼容机制 |
| 列表发现与变更 | 多维护者、可分页、不宣称天然完整 | 维护者发现、快照/增量、删除标记和排序表达 |
| 评论关系 | 普通/特殊评论均为 Feed Object，目标绑定版本 | 类型与关系字段、多级回复及跨版本历史入口 |
| 关注与好友 | 君子协议通知对方，好友默认互相关注，“不看”是独立本地设置 | 关系通知编码、既有联系人变更接入及通知去重 |
| 关注补看 | 关注驱动候选采集，不保证入列，提供候选查询与按需阅读 | 默认保留窗口、查询排序及界面命名 |
| 转发 | 普通／引用转发是特殊评论，取消仅撤回自己的发表 | UI 展示细节及普通／引用转发统计的呈现 |
| 传播规模 | 原作者、好友及已发现参与者共同传播 | 批次、限流、追踪生命周期与关系证明 |
| 对象更新与撤回 | 发表者签名授权、后继关系、明确作用范围、传播及默认展示规则 | 声明编码、逻辑发表标识、冲突消解表达及可验证历史压缩 |
| 互动统计 | 多来源记录验证、按互动键归并、撤回失效、范围可见 | 查询字段、分页与统计快照的一致性、反滥用策略 |
| 本地保留 | 候选、待读、资源、行为与持久互动状态具有不同生命周期 | 默认预算、淘汰及保留必要变更依据的方式 |
| 消费证明 | 自愿、签名、面向未来经济约定 | Tracker 身份、关联隐私、防重放及结算接口 |
| 收录节点 | 可替换、多来源、可用于冷启动 | 初始部署、运营政策与能力发现 |

这些待定事项不应阻止先完成端到端原型，但在宣布网络格式稳定之前，需要明确哪些决定影响跨节点兼容，哪些仅影响本地行为。

## 21. 架构结论

HomeStation 将内容消费拆成“获取候选—本地筛选—资源准备—用户阅读—本地反馈”的闭环，把算法复杂度和用户行为数据尽可能留在用户控制的环境中。

它通过 Feed Object 统一 Push 与 Pull，通过不可变版本引用维护内容与评论的对应关系，通过评论的独立发表和多路径传播，避免把讨论完全附着在原作者的服务器上。

关注、好友及分组关系驱动持续采集，用户的“不看”规则控制默认展示；未入待读的关注内容仍可在保留范围内主动补看。转发以自己的引用型发表参与同一条传播和变更链路，具体对象与应用状态的边界由本文实例及功能映射共同说明。

点赞和收藏作为特殊评论复用同一套能力，公开统计从可验证记录中派生；更新与删除通过签名变更声明及接收方遵循的君子协议生效。内容作者既不能替别人声明互动，也不能独占其统计依据；私有互动和历史保存仍保持各自明确的边界。

作者视图、收录者视图与本地默认视图共同提供选择权：**作者可以组织自己的评论列表，但不能把这种组织权变成控制所有人所见评论的权力。** 系统追求的是可发现、可对比、可替换，而不是承诺全网绝对完整。

首版需要先把这个完整闭环做出来，再持续演进推荐、资源管理、隐私机制和注意力经济。稳定的协议负责对象流通、版本关系及自愿的跨节点声明；用户自己的应用负责决定去哪里找、接下来读什么，以及如何理解阅读后的反馈。
