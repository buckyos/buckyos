# BuckyOS 内容分享、发布、上线功能讨论记录

> **文档性质：** 产品与架构讨论记录，尚非定稿 PRD 或协议规范。  
> **记录依据：** 本次连续语音讨论及后续术语更正。文中涉及的当前实现、合约规则和原型状态，均按口述记录，未另行核验代码或线上服务。  
> **术语统一：** 系统名称使用 BuckyOS，个人运行域使用 Zone，内容网络使用 NDN；此前误记的 PaaSKG / passskg 统一为 **PIKG**，Nemesis 统一为 **namedstore**。

## 一、讨论背景与核心问题

BuckyOS 早期主要围绕 File Browser 提供类似网盘的文件分享功能。随着系统逐步支持更多 App，并形成基于 NDN、命名对象、BNS 和应用运行环境的能力，原有的“选择文件—生成分享链接”已经不能涵盖全部使用场景。

本轮讨论涉及三个经常被用户用同一个“发布”或“分享”称呼、但实际过程并不相同的行为：

| 行为 | 本轮讨论中的核心含义 | 典型结果 |
| --- | --- | --- |
| 分享 | 将文件或内容交给某个目标 App，由目标 App 决定后续处理 | 消息、Feed、互动页面、访问链接等 |
| 内容发布 | 确定内容对象及其身份，使其进入 NDN 内容网络，并按需要命名、投递收录或配置付费消费 | Object ID、对象链接、逻辑名称、收录状态等 |
| 上线 | 将页面、网站或应用服务放到自己的 Zone 中，使其可被访问和使用 | 已上线页面或服务的稳定 URL |

三者都可能输出一个链接，但不能仅凭“最后都有链接”认定它们是同一种系统操作。另一方面，系统能力上的区分也不自动决定界面必须提供三个按钮。

**本轮最主要的未决问题是：现有的“分享”“发布”双入口是否合并，以及普通用户界面的名称与底层系统语义如何对应。** 讨论先梳理各类流程，再决定入口设计；目前尚未形成最终答案。

## 二、分享：从 File Browser 功能升级为系统公共能力

### 2.1 早期分享沿用传统网盘模式

早期 File Browser 的分享流程比较直接：用户找到一个文件，点击分享，选择公开分享或需要密码、访问码的分享，再设置永久有效或指定失效时间。

生成的链接通常并不直接返回原始文件，而是打开一个由网盘服务提供的包装页面。例如，图片位于页面中间，旁边提供下载、评论等交互功能。这种分享的结果不仅是“文件可访问”，还包括围绕文件建立的互动入口。

过去系统中主要只有这一类文件浏览应用，由 File Browser 独立提供整套分享功能没有明显问题。现在系统可以扩展更多 App，分享能力需要从单个应用提升到操作系统层面。

### 2.2 保留用户熟悉的“分享到某个应用”的心智模型

移动互联网时代，用户理解的分享通常包含一个中间步骤：先把内容交给某个服务，再由该服务决定最后发生什么。

```text
原始文件或内容
    → 选择分享目标 App / 服务
    → 目标应用接收并处理
    → 形成符合该服务要求的结果
```

同一个文件交给不同目标，结果可以完全不同：分享到朋友圈或微博，可能形成一条 Feed；分享到 Telegram，可能是发给某个人的一条消息；分享到网盘，可能生成一个带访问控制和互动功能的页面。

因此，分享不应被收窄为“生成一个文件 URL”。过去 File Browser 的网盘分享，可以理解为“把文件分享给网盘服务”，只是当时这一个目标与发起入口合在了同一个应用里。

**设计方向是保留这个用户心智模型，不要求用户改成先理解对象存储、内容协议，再进行日常分享。**

### 2.3 分享目标注册与系统对话框

App 可以在注册时声明自己是否接受成为分享目标。成为分享目标的应用，应能够出现在系统提供的分享选择界面中。

分享选择界面属于系统对话框，任何需要该能力的应用都可以调用，不应让每个 App 各自重复实现一套目标选择和分享入口。

调用范围还存在一些交互细节。例如，某个 App 可能只希望将内容交给自己处理，也可能希望打开系统分享对话框，让用户在所有可用目标中选择。这些范围控制需要保留，但具体调用参数、过滤规则和界面细节本轮没有展开。

目标 App 负责决定最终动作。系统不预设每次分享都必须产生网页或 URL；但无论结果是链接、消息还是其他形态，都需要向系统交代流程结果。

### 2.4 系统统一跟踪分享流程及结果

与早期只提供一次性分享操作不同，系统需要跟踪已经发生的分享。

系统级“已分享列表”至少应能回答：某个文件曾经分享给谁、交给了哪个应用或服务、分享流程是否完成，以及目标应用是否产生了最终链接或其他结果。

这里的“分享给谁”既涉及用户可理解的分享去向，也涉及处理该内容的目标应用；本轮尚未规定两者在记录结构中的具体字段。

记录分享流程不只是为了查看历史，也为了在目标服务支持的情况下继续管理结果。例如，原先设置十天过期，用户可能希望中途取消，或调整失效时间。

这不意味着系统已经能够统一撤销所有外部应用中的内容。不同目标能提供哪些管理能力，仍取决于对应服务；第三方目标的管理接口和结果回传协议尚待进一步明确。

### 2.5 File Browser 与系统级已分享列表

File Browser 作为系统应用，可以继续保留自己的“已分享”入口，用户可在其中查找网盘分享记录，并修改有效期、取消相关分享。

系统层面同时需要一个统一的已分享列表。由于内置系统服务数量有限，对几个已知系统服务提供的分享结果，可以直接在系统列表中显示对应管理操作，不必要求用户先进入 App。

对这些内置能力，界面也不必刻意显示所属 App 名称。例如，能直接在该条记录上修改过期时间，就不必先强调“这条记录来自 File Browser”。这里讨论的是已知系统服务的直接整合，不是要求所有第三方分享目标都隐藏名称。

应用自己的分享列表与系统列表如何共用记录、第三方结果如何管理，本轮没有确定最终结构。

## 三、“分享”与“发布”的入口争议

### 3.1 当前界面与讨论状态

当前界面保留“分享”和“发布”两个入口。团队正在讨论是否合并，尚未作出最终决定。

### 3.2 一种观点：发布是分享的长期稳定形态

支持合并入口的观点主要从普通用户的理解出发：发布可以视为一种长期有效、使用稳定链接的分享。

在这一理解下，用户已经熟悉“分享”按钮，再增加一个“发布”入口可能增加选择上的困惑。因此，可以考虑将发布放到分享流程内部，作为一种类型或目标。

该观点还认为，开发者发布 App 通常通过开发工具或 CI/CD 完成，不会把 File Browser 当作主要开发者发布入口，所以普通用户界面中的“发布”不必承担完整的开发者工作流。

以上是团队中的一种产品判断，不在本记录中将其写成所有开发者必然如此操作的事实。

### 3.3 另一层语义：SDK 中已经存在的产物发布

BuckyOS 的底层和 SDK 已经使用“发布”描述另一类行为：将开发完成的 PIKG 等产物通过自己的 Zone、后端或对象服务发布，使其进入 BuckyOS 相关的应用分发体系。

这里的发布关注产物在操作系统生态中的发行，而不仅是某个 URL 的有效期。底层已有的 Publish 概念，与普通用户眼里的“分享一个文件”未必具有完全相同的边界。

因此，争议不仅是按钮叫“分享”还是“发布”，还包括上层入口到底映射到哪一种流程，以及是否应直接沿用底层术语。

### 3.4 当前保留的判断边界

“开发者不会从文件浏览器发布 App”并不能单独解决系统语义的关系；底层已经叫 Publish，也不自动要求普通用户入口必须同名。

本轮采取的讨论顺序是先讲清楚产物形态和实际流程，再讨论入口合并。后续章节中的分类用于辨认能力，不代表已经决定增加相同数量的一级按钮。

## 四、发布的共同基础：命名对象、Metadata 与地址

### 4.1 内容发行网络以命名对象为基础

BuckyOS 希望建立的内容发行网络，根本上以命名对象为基础。后续涉及图片、视频、音乐、软件包等内容形态的发布，都从 NDN 和 Object ID 的角度讨论。

Public 目录虽然提供最直观的文件系统入口，也不应被理解为一套与命名对象无关的内容发行机制。后续口述进一步明确：相关内容仍然要形成 Object ID，才能进入这套内容网络。

用户操作的入口可以是复制文件，底层的对象基础仍然一致。对象生成的具体触发时机及自动处理过程，本轮没有细化为实现规范。

### 4.2 先确定发布形态，再确定对象身份

分享通过选择目标 App 决定结果形态，发布也可以借鉴这一思路：先决定发布成什么，再填写对应的 Metadata，形成对象身份。

文件不只是一串原始数据。它可以按普通文件发布，也可以被明确标注为视频、音乐或软件包等内容商店支持的类型。类型和 Metadata 的不同，会影响最终生成的 Object ID。

因此，Metadata 不是在固定链接之外随意补充的一组说明。对于包含元数据的对象，它本身就是对象构成的一部分。

### 4.3 文件数据的几种表示

本轮讨论了三种基础表示：

| 表示 | 本轮讨论的用途 | 元数据要求 |
| --- | --- | --- |
| Chunk | 能被一个 Chunk 容纳的数据 | 不需要用户填写 File Object 的额外 Metadata |
| File Object | 以文件对象表达内容及相关描述 | 需要相应的文件元数据 |
| Chunk List | 超过单 Chunk 容量、需要组合多个 Chunk 的内容 | 以 Chunk 的组合表达数据；具体格式未展开 |

Chunk 就称为 Chunk，不额外改称 Chunk Object。

单 Chunk 上限口述中出现了 32 MB 和 64 MB 两种可能，尚未确认。本记录不把其中任一个数值固化为协议规定。关于较大文件必须使用 File Object 或 Chunk List 的讨论，应理解为以最终确认的单 Chunk 上限为界。

这些对象类型对普通用户可能难以理解。界面究竟让用户选择类型，还是提供默认策略、仅在必要时暴露选项，仍待明确。主动发布向导中的 Metadata 输入，与直接发布 Chunk 无需额外元数据的情况，也需要在具体交互中衔接。

### 4.4 目录对象

文件夹可以整体作为发布对象。除通过目录路径访问其中内容外，还可以为整个目录生成 Dir Object，得到对应的 Object ID。

目录的文件系统位置与 Dir Object 的身份是两个层次：前者便于直接操作，后者用于进入命名对象网络。

### 4.5 地址所表达的含义需要区分

| 地址或名称 | 表达的主要含义 | 与磁盘路径的关系 |
| --- | --- | --- |
| Public 路径 URL | 通过 Zone 网关访问某个公开路径 | 对应 Public 目录中的文件系统入口 |
| Object ID URL | 指向一个确定内容对象或版本 | 不要求存在同名磁盘路径 |
| 长期逻辑路径 URL | 以稳定逻辑入口跟踪对象及其后续版本 | 可以完全是逻辑映射 |
| BNS 名称 | 在 BNS 命名体系中给作品命名，按需接入交易机制 | 不依赖某台本地系统的文件路径 |

Object ID 确定后，用它引用的是该确定对象。内容或参与标识生成的 Metadata 改变时，不能再把新内容当作原对象本身没有变化。

“链接标识稳定”和“内容始终能够取到”也不是同一件事。后者仍依赖数据提供和访问权限。这里保留这一区分，不将讨论中的“长期有效”解释为不受运行、存储或授权状态影响的绝对保证。

## 五、发布形态一：Public 目录公开发布

### 5.1 最简单的发布入口是文件操作

系统网关允许匿名访问 Public 目录中的内容。用户将文件复制到该目录，或把文件的软链接放入该目录，即可建立公开访问入口。文件夹也可以整体复制进去。

例如：

```text
/public/readme.txt
```

按本轮口述中的子域名组织方式，路径链接示意为：

```text
https://public.<zone-host>/readme.txt
```

这里使用占位符说明“Public 子域名 + 相对路径”的组织方式，不将此前整理中出现的其他 URL 写法视为已经确定的网关协议。

### 5.2 同时提供路径访问与 NDN 访问

Public 目录发布不只是提供按文件名构成的 HTTP 链接。按本轮设计方向，放入该目录的内容原则上也同时进入 NDN 发布体系，形成相应的 Chunk 或对象标识，并提供 NDN 访问方式。

对于文件，具体采用 Chunk、File Object 还是 Chunk List，取决于表示方式和文件规模；对于目录，可以生成 Dir Object。

NDN 地址的正式 URL 结构本轮没有确认，不在此固定路由字符串。其核心是通过对应对象标识访问内容，而不是依靠 Public 中的文件名。

### 5.3 对用户与 Agent 都足够直接

这个入口不要求用户经过一个专门的系统分享或发布对话框。复制操作本身就是触发公开发布的方式。

这对 Agent 尤其友好：Agent 已经能够进行文件系统操作，就能利用这条路径快速使产物可访问。它也兼容开发者已有的工作习惯：创建一个子目录，把文件放进去，便可通过 HTTP 访问。

### 5.4 公开状态直接来自目录位置

该形态不提供传统网盘分享中按链接配置密码、接收对象或到期时间的同一套过程。将内容放到 Public 目录，意味着允许匿名公开访问。

这里的“没有权限”指缺少逐条分享的访问限制，并不意味着任何人都应拥有向 Public 目录写文件的权限；写入权限不是本轮讨论的重点。

这种公开状态不要求先建立传统分享流程中的一条独立备案记录。系统查看 Public 目录，就能知道其中哪些路径处于公开状态，并据此构造链接。

### 5.5 管理方式与用户理解

用户会自然地认为：要从已发布文件中移除某个内容，就到 Public 目录删除对应入口。它的管理心智与文件操作一致。

“永久”在这里主要指没有设置一个自动到期的分享期限。它不意味着文件可以被任意删除、移动而路径链接仍然继续提供原内容。

删除 Public 入口后，对应 NDN 对象、其他引用或已经取得内容的副本如何处理，本轮没有展开。不能仅根据“删除目录中的文件”推导出已经完成全网撤回。

## 六、发布形态二：主动发布到 NDN

### 6.1 用户明确选择发布到内容网络

第二种形态是用户主动要求将文件或其他对象发布到 NDN，而不是通过复制到 Public 目录间接触发。

这个流程应出现系统对话框，让用户确定对象形态并填写相应 Metadata。对象构成确定后，系统生成 Object ID，使对象身份在界面中显现出来。

### 6.2 链接先行，再实际发布

这一流程的重要特征是“链接先行”：可以先得到对象身份和链接，再执行后面的实际存储与登记。

```text
选择内容与发布形态
    → 确定 Metadata
    → 生成 Object ID，展示对应链接
    → 可检查系统中是否已有相同的公开对象
    → 用户继续发布
    → 将对象实际放入 namedstore 并登记
    → 完成对应的 NDN 发布
```

根据 Object ID，系统可以提供去重检查，提示该对象是否已经在系统中公开可访问。这是本轮提出的一项可提供能力，尚未规定每次发布必须采用怎样的阻止、复用或提示交互。

“生成对象”和“完成网络中的实际可访问发布”是相关但不同的阶段。先得到链接，不要求把数据复制到 Public 目录。

### 6.3 管理入口不再是 Public 目录

主动 NDN 发布将对象交给 namedstore 和发布登记机制管理，而不是在 Public 下留一个同名文件。

因此，需要一个“我已发布的 NDN 对象”管理入口。用户不能通过在 Public 目录中执行一次文件列表查看，就完整看到这些对象。

其产品目标是让链接不再受 Public 目录中某个文件是否被误删影响。要查找和管理这些发布，应通过系统的对应管理界面，而不是寻找不存在的磁盘映射。

该管理列表与前面的系统“已分享列表”是统一列表的分类、不同视图还是独立入口，本轮尚未决定。

### 6.4 对象版本地址与长期逻辑地址

得到 Object ID 后，还可以继续给它赋予一个逻辑路径，让该路径指向对象。

```text
确定版本：Object ID URL → 指定版本对象

长期入口：逻辑路径 URL → 对应 Object ID → 对象内容
```

这样可以同时获得两个有意义的 URL：一个用于引用确定版本，另一个用于长期跟踪该内容对象的更新。

两者都可以是纯逻辑表达，不要求本地磁盘存在同名文件或目录。这个逻辑路径也不自动等同于后续的 BNS 名称；二者在本轮讨论中承担不同层面的作用。

### 6.5 NDN 访问控制仍存在方案分歧

按口述，当前 NDN 的访问机制比较开放：只要相关内容存在、请求者知道 Object ID，系统通常就允许访问。多个 App 共享同一内容也使用了这种方式。

正在考虑的另一种方案是：NDN 默认检查登录态；未登录请求不能仅凭 Object ID 直接访问，而需要带上 Reference Path，由系统查询其指向的记录，再判断内容能否公开提供。

Reference Path 在这个方案中相当于把访问判断与一个逻辑路径及其登记信息关联起来。它不是“只要带一个路径字符串就自动获得权限”。

该方案尚未最终确定。Reference Path 与长期逻辑路径是否采用同一套记录、以及其与公开发布状态如何联动，本轮也没有作出实现层面的规定。

## 七、按内容形态发布：从普通文件进入内容商店

### 7.1 内容商店是通用机制，不限于应用商店

同样是一个文件，可能是图片、视频、音乐，也可能是已经打包好的 PIKG。BuckyOS 后续希望提供通用的内容商店机制，使这些不同类型的产物可以被发现、上架和消费。

当用户明确选择了内容商店支持的类型，发布对象就不再只是普通 File Object，而可能是 Video Object、Music Object 等具有更明确消费含义的对象。这里的类型名称按讨论示意记录，不替代正式的类型规范。

对应界面应提供该内容类型所需的 Metadata。用户确定内容类型和元数据，本质上就在确定内容网络应如何理解该产物，同时影响最终 Object ID。

这里的核心不是只标注“文件”或“文件夹”，而是标注它作为内容是什么。

### 7.2 本地生成对象身份，是“一键发布”的基础

以音乐为例，创作者可以在本地确定音乐对象及其 Metadata，生成 Object ID 和相应链接，不必等内容商店在线返回一个平台分配的链接。

链接生成后，可以立即复制并交给别人，即使发布者当时处于离线状态。此时别人暂时取不到内容，并不影响链接和对象身份已经确定。

口述中将这种在确定 Metadata 和 Object ID 时完成内容身份建立的能力称为“一键发布”的有趣之处。这里应区分：本地可以完成身份与链接生成，但把数据放到可访问的对象存储、向收录者投递和满足上架条件，仍有各自的后续过程。

### 7.3 收录者接收的是对象标识

发布流程除了将对象放入本地 namedstore，还可以把 Object ID 投递给一个或多个收录者。

收录者只需先获得 Object ID，就具备开展收录工作的入口；随后可以从发布者的对象服务读取对应 Metadata，了解该对象及其类型。

对发布者而言，这不要求把自己完全绑定到某一家商店的上传页面。对象身份可以先存在，再被不同收录者获取和处理。

### 7.4 “知道了”与“已收录”必须分开

收到一个 Object ID，不等于已经完成上架或正式收录。本轮明确区分两个阶段：

| 阶段 | 收录者能够表达的事实 | 尚不能直接推导的结果 |
| --- | --- | --- |
| 已知晓、进入处理 | 已获得 Object ID；取得 Metadata 后，知道相应对象描述 JSON 是什么 | 不代表完整数据已取得，也不代表满足上架条件 |
| 已收录 | 已完成该收录者要求的处理，并给出收录结论 | 不代表其他收录者也会接受 |

例如，有些视频收录者至少需要将整部视频下载到自己的对象存储，才会承认完成收录。能读到 Metadata，只能说明已识别对象，不能替代完整内容的取得。

不同收录者可以有不同条件。本轮没有要求所有收录者采用同一套缓存或上架规则。

发布者应能够用 Object ID 向对应收录者反查处理结果。界面不能把“已经投递”直接显示为“已经上架”。

### 7.5 免费传播场景保持简单

对于不启用付费消费、主要希望内容被看到的作品，基础路径可以很简单：建立内容对象，提供对象数据，把 Object ID 投递给相应收录者。

口述中以免费内容和 copyleft 内容举例。这里按“不启用商业化、以开放传播为主要目标”的讨论场景记录，并未选定某个具体许可证，也不把“免费”写成“没有版权”。

这类内容不必先取得一个单独的付费作品名称，才能让收录者开始处理；但是否正式上架，依然取决于收录者自己的条件。

## 八、作品命名：NDN 与 BNS 的结合

### 8.1 为什么在 Object ID 之后引入名字

当创作者把产物作为一个需要持续经营的作品，希望使用 NDN 网络中的付费使用机制，或进一步支持未来的版权转让，就需要给作品赋予名称。

按本轮设想，这类机制目前只支持 BNS 名称。这里的“严肃作品”是创作者对作品经营方式的表述，不是系统对内容质量作出的等级判断。

Object ID 标识确定对象，BNS 名称则为作品提供命名和后续交易关联。顺序是先有对象身份，再选择并绑定名称。

### 8.2 自己命名空间下的二级名称

用户可以在自己已有的 DID / BNS 命名空间内为作品建立子名称，不必为每个作品另外取得一个独立一级名称。

讨论以 Bob 和作品 X-Man 为例，说明可以使用类似以下关系：

```text
Bob 控制的命名空间
    └── X-Man.Bob → 作品 Object ID
```

这只是命名关系示意，完整 DID / BNS 字符串格式以协议为准。

口述也提到以 Object ID 为局部名称的默认命名方式。默认自动名称究竟按 Object ID 生成，还是由用户填写作品名，尚未细化；目前明确的是“在自己控制的命名空间内命名”这一原则。

这类名称不需要先购买一个新的独立一级名，创作者可以在自己已有的控制范围内完成命名。但这不等于后续启用链上交易时也完全无需登记或费用。

### 8.3 独立一级名称

用户也可以为作品选择独立一级 BNS 名称，例如希望作品直接以 X-Man 被识别。

此时必须先取得名称的控制权，才能将它绑定到对象。取得名称可能涉及链上合约、竞价或相应费用，不能只在本地填写一个字符串就完成独立一级名的占用。

按本轮口述，当前设想中的长度与费用关系如下：

| 名称情况 | 口述中的规则 | 记录边界 |
| --- | --- | --- |
| 长度超过 8、尚未被注册 | 原则上支付一次手续费即可取得 | 尚未核验合约 |
| 长度少于 8 | 原则上需要支付维护费用 | 具体费用和取得过程未展开 |
| 恰好为 8 | 本轮没有明确边界 | 待核对 |

名称长度的实际计量方式也没有在本轮明确。以上不作为最终收费表或当前线上合约规则。

### 8.4 免费命名与链上销售登记不是同一步

二级名字可以在已有命名空间内建立，不代表它天然已经具备通过 BNS 合约购买的状态。

如果希望消费者在链上购买，即使使用二级名称，也需要完成相应上架或登记，使名称、对象和交易信息能够被找到。

这一点在后续消费者流程中尤其重要：用户可能只拿到 Object ID；若作品未进入相应链上交易登记和可查询关联，仅凭 Object ID 不一定能反查到可调用的购买入口。

BNS 体系的名称权属及链上交易关联不依赖用户当前磁盘上的文件路径。已有命名空间内的子名称建立，与链上交易所需登记应分别描述，不能笼统合并成“所有名称都免费”或“所有二级名称都要单独竞价”。

### 8.5 命名步骤中的用户选择

完成对象身份创建之后，用户需要按用途选择名称策略：使用自己命名空间内的二级名称，或取得独立一级名称。

相应交互可能涉及无需单独购买名称、现场完成名称取得和付费等不同分支。名称绑定是 Object ID 生成后的环节，不应倒过来把平台注册或付款作为所有对象生成的前提。

## 九、消费者视角：统一访问内容

### 9.1 不依赖最初发现内容的渠道

BuckyOS 既是内容发布端，也是消费端。消费者无论通过哪个收录者、哪个商店或朋友分享发现内容，最后都应能进入同一套内容访问机制。

对一个基于 BuckyOS 的视频播放器，最直接的入口就是输入 Object ID，或粘贴包含 Object ID 的 URL。名称入口可以先定位到对应对象，但消费者不必先了解原来的发行渠道。

应用通过 HTTP 请求读取内容。有权限且内容可用时，就直接读取或播放；打不开时，根据返回结果决定如何提示或继续处理。

### 9.2 访问失败不只有一种原因

需要区分访问权限、资源状态和付费要求。口述中的例子包括：内容未公开、请求者不是作者好友、作者的对象服务中没有找到内容，以及该对象需要购买后才能访问。

客户端不能把所有打不开的情况都当成“需要付款”，也不能把所有失败都解释成“文件已删除”。具体错误结构本轮尚未定义。

### 9.3 可以隐藏对象的存在

系统应允许发布者选择隐私策略：好友访问时可以打开，非好友访问时表现为资源不存在，而不是必须明确提示“你不是好友”。

因此，请求者是否有资格知道对象存在，也属于访问策略的一部分。应用不能要求服务端在每次拒绝访问时都泄露对象的真实存在状态。

### 9.4 付费内容由实际提供方返回购买要求

消费者可能从原作者取得内容，也可能从已经存储该对象的收录者取得内容。实际提供方应能根据相关记录判断该请求是否需要购买凭证。

若需要购买，则在 HTTP 响应中告诉应用：这是付费内容，需要先完成购买，并在后续请求中提供相应凭证。

这种路径不以所有内容都已经上链为前提。链下网关购买和链上购买都可以成为后续分支。

## 十、付费消费保持简单：完整版与试看内容分成两个对象

### 10.1 基础协议不承担无限扩展的营销规则

本轮明确希望保持公共协议简单，不把限时免费、复杂试用期等运营规则不断加入底层。

基础能力集中于对象访问和购买凭证。怎样组织试看、如何呈现购买按钮、如何说明内容组合，交给 Metadata 与应用层处理。

### 10.2 免费小样与付费完整版使用不同 Object ID

一个作品需要“免费试看 + 付费完整版”时，可以制作两个独立对象：

```text
作品相关 Metadata / 内容描述
    ├── 试看 Object ID：公开可访问
    └── 完整版 Object ID：需要购买凭证
```

两个对象之间的关系由 Metadata 描述。一个面向用户的分享入口可以携带或通过元数据找到这两个对象，不要求基础协议理解“同一个文件的前几分钟免费”。

### 10.3 播放器的典型消费流程

播放器先尝试打开完整版。遇到付费访问限制时，读取相关 Metadata，查找是否有公开的试看对象。

若有可访问的小样，就播放小样，同时提示当前播放的是试看内容，完整版需要购买。用户看完或播放过程中，可自行决定是否进入购买流程。

这是应用如何解释多个对象组合的例子，而不是要求 NDN 对所有视频实现统一试看策略。

### 10.4 用 HTTP 402 衔接购买流程

本轮拟采用 HTTP 402 表达“需要付费”。响应中提供后续购买所需的信息，由应用决定是否帮助用户跳转到发布者定义的支付网关，或进入合约购买流程。

402 在这里是本轮设想的付费流程入口。具体响应体、购买信息字段、凭证携带方式尚未确定，不把本轮讨论直接视为完整的 HTTP 付费协议规范。

应用可以选择引导，但不意味着一收到付费响应就替用户自动付款。

## 十一、购买凭证与两条支付路径

### 11.1 路径一：支付网关与签名收据

第一条路径允许使用传统货币，通过内容发布者或授权销售者提供的支付网关完成购买。

本轮描述的典型方式是作者自行搭建支付网关：用户付款成功后，网关使用与内容作者公钥对应的私钥，签发购买收据。后续访问请求携带该收据，内容提供方验证后允许访问。

```text
请求付费对象
    → 返回付费要求及支付入口
    → 用户进入支付网关并付款
    → 获得签名购买收据
    → 携带收据重新请求内容
    → 提供方验证并返回内容
```

实际销售方不一定只有作者一家，收录者也可能被授权销售。但本轮没有确定被授权销售者如何获得授权、使用什么签名身份，或如何与作者的验证规则对接，不应假定只要某个网关签了收据就必然有效。

### 11.2 路径二：BNS 合约购买

第二条路径通过 BNS 合约支持的购买功能完成。价格等交易信息由对应的合约记录确定，用户调用合约接口购买。

按本轮当前设计，合约购买使用 USDT。这里记录的是项目当前设想，并非所有内容支付都必须使用该方式；前述传统支付网关仍是独立分支。

购买成功后，相应购买标识进入合约维护的已购记录，后续访问可据此确认购买资格。

链上购买所依赖的是合约中的购买事实，不能简单写成“也由作者支付网关再签一次相同的收据”。客户端具体如何携带或证明链上购买资格，本轮尚未展开。

### 11.3 只有 Object ID 时，如何找到合约购买入口

消费者可能不知道作品的 BNS 名称，只拿到了 Object ID。但调用购买接口时，需要知道相应的名字或交易定位信息。

本轮提出两种找到入口的方式。

**第一种，通过 BNS 友好查询服务反查。** 客户端根据 Object ID 查询对应的 BNS 名称或交易关联，再调用合约。这个友好查询功能可以由本地或 Zone 内的 BNS RPC 相关服务提供，不应直接假定反向查询本身就是合约提供的服务接口。

**第二种，通过内容请求的 402 响应获得。** 用户直接请求作者 Zone 上的内容，服务端在付费响应中说明应使用哪个名称、进入哪个合约购买入口。这样即使客户端事先只有 Object ID，也能继续购买。

上述路径都依赖相关对象与可销售作品之间存在可查询或可返回的关联。二级名称若要用于合约购买，也需要相应登记，不能省略这一步。

### 11.4 合约方式的优势是购买结果可验证

按照本轮设想，合约路径的一个重要优势是：用户可以知道执行成功后，购买标识将进入合约的已购记录，不必完全依赖一个网关在收款之后继续履行“再给你凭证”的承诺。

这种确定性针对的是合约中记录的购买结果，不是对内容可交付性的保证。即使购买记录存在，也仍可能遇到内容下不回来、提供者不可用或入口不可信等问题。

### 11.5 当前原型状态与后续信任问题

按口述，相关原型能够跑通演示流程，可以利用测试环境和水龙头领取测试资产，展示名称取得、上架、购买及后续访问。正式的链和合约尚未上线。

当前重点是跑通流程，整个信用体系还没有建立。正式系统需要进一步提示或判断购买链接是否可信、支付入口与内容发布者是否匹配，以及付款后能否取得内容。

本轮明确保留的风险是：不能让用户仅因看见一个可付款链接，就误以为发布者可信、对象真实且必然可以下载。后续需要处理这些问题，但本轮没有提出完整的信用、担保或退款方案。

## 十二、另一种“发布”：将页面或应用上线到自己的 Zone

### 12.1 内容发行与应用上线目的不同

用户说“发布一个视频”或“发布一首音乐”，可能是在建立内容链接、进入内容网络；用户说“发布一个网站”或“发布一个小游戏”，很多时候只是想把它放到自己的 Zone 中运行，让朋友能访问。

后一种行为在本轮讨论中更准确地称为“上线”。它并不要求把产物拿去销售，也未必有进入内容商店的意图。

例如，用户制作了一个贪吃蛇小游戏，希望得到一个稳定 URL，发给朋友后即可开始玩。这个目标是让页面或服务在自己的 Zone 可用，而不是发行一个供别人安装或购买的软件作品。

同一个 PIKG 也可以分别进入两条不同路径：作为软件产物对外发布，或只在自己的 Zone 安装上线。不能仅凭产物是 PIKG，就认定用户正在进行内容发行。

### 12.2 上线输入不局限于 Agent 新写的代码

用户要上线的内容，可以是单个 HTML、包含静态网站的目录、Node.js 编写的 HTTP API 后端、已有 PIKG，也可以是从其他渠道找到的 Docker 镜像或其引用。

这些输入的共同目标是“让它在自己的系统中被用起来”，而不是要求每一种输入都先经过应用商店。

### 12.3 三种主要上线方式

| 上线形态 | 典型输入 | 处理方式 | 面向用户的结果 |
| --- | --- | --- | --- |
| Public 目录直接上线 | 单个 HTML、轻量静态页面及资源目录 | 复制到 Public，由现有网关提供访问 | 路径型 URL |
| Static Web 类型上线 | 作为独立静态站点组织的页面或目录 | 按 Static Web 应用形态进行上线 | 对应的站点访问入口 |
| 标准应用服务上线 | 有后端的应用、Docker 或 Script Host 服务 | 以 PIKG 进入安装与调度机制 | 应用服务 URL |

第二种 Static Web 类型在口述中作为独立方式提出，但具体打包格式、是否统一使用 PIKG、域名分配及管理界面尚未展开。不将这些细节直接补成已确定方案。

第三种标准应用服务不是“静态服务”。其运行方式至少包括 Docker-based 和 Script Host 两类；按口述，Script Host 支持 TypeScript、Python。

### 12.4 最轻方式：复制静态页面到 Public

例如，将单页面小游戏放入：

```text
/public/snack/snack.html
```

按本轮的地址组织示意，可得到：

```text
https://public.<zone-host>/snack/snack.html
```

用户把链接发给朋友，对方就可以通过页面使用这个小游戏。

这种方式有一个前提：页面及其资源引用不能错误地假设自己一定部署在网站根路径。页面若能适应子路径，就能利用 Public 目录实现很轻的上线过程。

这也是早期系统尚未形成完整发布体系时仍能提供实际能力的原因之一。熟悉 HTTP 的开发者只需创建子目录、复制产物，就能快速让它可访问。

### 12.5 有后端的应用需要正式接入系统

当应用包含后端服务，就不能只把文件放到 Public 目录。按本轮设计，有后端的应用需要走 PIKG 对应的上线机制，以进入系统的权限、隔离、安装和调度管理。

口述提到的内部 PaaS 式机制，是对运行与上线能力的描述；相关包统一称为 PIKG，不另设一个 PaaSKG 包类型。

### 12.6 子域名属于上线实例的选择

对于需要通过 Web 访问的应用，上线时需要处理是否需要子域名、选择什么子域名，以及如何接入系统权限体系。

同一个 PIKG 被不同用户安装到各自 Zone 时，可以选择不同的子域名。因此，包身份与某个具体部署实例的域名应区分：不是在制作包时，就必须把所有用户将来的访问域名固定进去。

本轮将子域名接入视为应用获得稳定访问入口、纳入系统正确权限体系的关键环节之一，但没有展开详细的域名、证书或网关配置协议。

## 十三、无需先上应用商店：临时 PIKG 与本地上线

### 13.1 自用部署可以独立成立

用户从网上找到一个 Docker 应用，仅希望在自己的 BuckyOS 中使用，不应该因为该应用没有进入 BuckyOS 应用商店，就无法部署。

从系统流程看，关键是让安装服务和调度器能够识别它，并按系统规则运行；不是要求所有自用应用都先包装成正式对外发行的商品。

因此，应允许为了完成一次本地上线而生成 PIKG。这个 PIKG 可以不进入内容商店，也不作为公开发行产物发布。

### 13.2 已有简单 Metadata 的 Docker

若 Docker 应用已经带有足够简单、明确的 Metadata，就可以据此包装成 PIKG，由安装服务和调度器识别，再在本地完成上线。

其流程可以表示为：

```text
已有 Docker 应用及必要 Metadata
    → 形成 PIKG
    → 安装服务与调度器识别
    → 在目标 Zone 上线
    → 获得相应访问入口
```

### 13.3 缺少 Metadata 时由 Jarvis 辅助包装

若 Docker 缺少必要描述，可以让 Agent 分析它的特点，补充包装所需信息。

本轮提出可以给 Jarvis 提供相应 Skill，使其完成这类分析与 PIKG 生成。现代 Agent 可以把原本需要手工适配的工作简化，从而让现有 Docker 更容易被系统使用。

```text
Docker 镜像或已有项目
    → Jarvis 依据 Skill 分析
    → 补充上线所需 Metadata
    → 生成包装用 PIKG
    → 在本地安装和上线
```

Skill 的具体检查项、自动处理范围，以及哪些权限需由用户确认，本轮没有进一步定义。

### 13.4 临时 PIKG 的目的不是公开发行

这类包装产物的目的可以仅是让调度器、安装服务识别应用，并完成一次本地上线。它不必进入公开发布链路，也没有必须对外发行的要求。

因此，“产生了 PIKG”“把对象存进 namedstore”“向内容网络公开发布”和“在自己的 Zone 上线”，应分别理解，不能视为同一件事自动连带发生。

## 十四、namedstore 的存储占用与 GC 风险

### 14.1 反复包装可能造成空间消耗

BuckyOS 大量使用命名对象。在口述描述的打包方式中，某些 PIKG 会包含完整的 Docker 打包内容。如果用户反复分析、修改和重新包装大型 Docker，可能产生多个临时产物，造成较明显的存储占用。

这个问题在磁盘空间不大的设备上尤其容易被用户感知：看起来只是试着上线几次，空间却迅速减少。

### 14.2 当前管理方式

按口述，namedstore 的 GC 管理界面还没有完成，目前主要通过命令行操作 GC。

这对熟悉系统的开发者比较容易处理，但普通用户未必理解临时 PIKG、命名对象和旧内容之间的关系，也未必知道应该如何清理。

### 14.3 本轮记录的问题，不预设解决方案

本轮已经指出空间占用和清理体验风险，但尚未确定自动 GC、缓存复用、手工清理界面或其他方案。

也不能直接推断每次包装都会完整重复占用同样大小的空间，或所有旧版本都可安全删除。实际引用、复用及回收策略仍需结合 namedstore 的实现确认。

后续产品设计需要让用户理解存储消耗及可管理范围；本记录不把某种具体回收机制写成已经作出的决策。

## 十五、与 Code Agent 结合的产品价值

### 15.1 从代码交付推进到可访问服务交付

本轮最后提出一个对外解释 BuckyOS 价值的重要问题：在桌面上使用 Code Agent，与在 BuckyOS 中使用 Jarvis，有什么实质区别？

这里希望体现的差异，不只是两个 Agent 都能写代码，而是 Jarvis 可以接上操作系统已有的安装、调度、权限、网关和 Zone 运行能力，把代码产物进一步变成可访问服务。

最终用户拿到的不必只是源代码目录，还可以是已经在自己 Zone 上线的访问链接。

### 15.2 多人使用是典型目标场景

例如，用户让 Jarvis 写一个基于社交的小游戏，希望朋友能一起参加。BuckyOS 应尽量简化从生成应用到上线的过程，使用户在得到链接后，就能邀请朋友访问和使用。

```text
用户提出想法
    → Jarvis 生成页面或服务代码
    → 选择合适的上线形态
    → 必要时生成 PIKG
    → 在用户的 Zone 中上线
    → 输出访问链接
    → 朋友打开链接并参与使用
```

这不是对其他 Code Agent 当前部署能力作比较测试，而是本轮为 BuckyOS 确定的产品价值方向：**让 Agent 的产物更容易在用户自己的系统里成为可用、可访问、可协作的服务。**

## 十六、流程关系与管理入口汇总

### 16.1 三类主流程

```text
分享
内容 → 系统分享入口 → 目标 App → 应用产生结果 → 系统记录与后续管理

内容发布
内容 → 选择类型及 Metadata → Object ID
    → 提供对象数据与登记公开状态
    → 按需绑定逻辑路径 / BNS 名称
    → 按需投递收录者、完成对应上架或交易登记
    → 消费者访问、授权或购买

应用上线
页面 / 项目 / Docker / PIKG
    → Public、Static Web 或标准应用服务路径
    → 在目标 Zone 提供页面或运行服务
    → 形成可访问入口
```

上述是概念关系，不是已经确定的统一向导步骤。尤其是内容存储、名称绑定和向不同收录者投递，可以有不同先后安排；当前明确的关键依赖是先有确定对象，才能基于其 Object ID 进行后续关联。

### 16.2 不同方式对应不同的管理依据

| 方式 | 管理依据或入口 | 本轮明确的区别 |
| --- | --- | --- |
| 通过目标 App 分享 | 系统已分享记录及目标应用能力 | 需要知道流程结果，但不要求结果都是链接 |
| Public 目录发布 | Public 中的文件系统入口 | 可以直接通过复制、查看、删除入口管理 |
| 主动 NDN 发布 | 已发布 NDN 对象记录与 namedstore | 不依赖 Public 中存在对应文件 |
| 内容商店收录 | 以 Object ID 查询对应收录者的状态 | 已投递、已知晓、已收录不能混同 |
| BNS 命名与销售 | 名称控制、绑定及交易登记 | 自有命名空间内命名与链上销售登记不同 |
| 页面或应用上线 | Zone 中的上线实例及对应系统机制 | 关注页面可访问或服务可运行，不要求公开发行包 |

### 16.3 四个容易混淆、必须区分的结果

**生成链接，不等于内容已经能从网络取到。** Object ID 及链接可以离线确定。

**让内容可访问，不等于内容商店已经收录。** 收录者有自己的条件与处理过程。

**完成购买记录，不等于内容交付一定成功。** 凭证可验证与数据可取得是不同问题。

**把应用上线，不等于将应用包对外发行。** 自用服务可以只在自己的 Zone 完成安装和运行。

这些区别是本轮讨论自然形成的边界，不要求普通用户先学习全部概念，但系统记录和流程设计需要能够表达它们。

## 十七、当前明确的方向与待定事项

### 17.1 已明确的产品方向

分享应成为系统公共能力，保留“交给目标 App 处理”的用户心智，并由系统跟踪流程及结果。对已知系统服务，统一列表可以直接提供对应管理操作。

内容网络以命名对象为基础。内容类型和 Metadata 参与对象身份形成；身份与链接可以先在本地确定，实际存储、公开访问、收录与商业化分别完成。

Public 是轻量的文件操作入口；主动 NDN 发布则以对象存储和发布管理为中心，两者不能只因为都能生成链接就混为同一种生命周期。

付费消费保持简单，通过购买凭证控制访问；试看与完整内容采用独立对象，由 Metadata 和应用组合。支付既可以走签名收据，也可以走 BNS 合约购买。

应用上线与内容发行应在系统语义上区分。用户可以通过 Public、Static Web 或标准应用服务路径在自己的 Zone 使用产物；临时 PIKG 不必先进入应用商店。

Jarvis 与系统能力结合的重点，是让生成的代码和服务更容易真正上线、被自己和朋友使用。

### 17.2 尚未确定的事项

| 议题 | 当前保留的问题 |
| --- | --- |
| 一级入口 | 分享与发布是否合并；上线在 UI 中使用什么名称；是否保留现有双入口 |
| 分享调用 | App 只分享到自己或展示全部目标的接口与交互细节 |
| 分享结果管理 | 第三方回传哪些结果、支持哪些后续操作；与应用自身列表如何对应 |
| 统一管理中心 | 已分享列表、已发布 NDN 对象列表与各类上线入口之间的关系 |
| NDN 权限 | 继续按 Object ID 开放访问，还是默认登录态检查并引入 Reference Path |
| 对象表示 | 单 Chunk 上限是 32 MB 还是 64 MB；File Object、Chunk、Chunk List 的自动选择与界面呈现 |
| 地址格式 | NDN URL、逻辑路径及完整 DID / BNS 名称的正式语法 |
| BNS 默认命名 | 默认子名称按 Object ID 生成还是使用作品名；相关用户选择如何呈现 |
| BNS 名称费用 | 恰好 8 的长度边界、计量单位、实际竞价及维护规则 |
| 付费协议 | 402 响应字段、收据格式、凭证携带与验证、授权销售者如何接入 |
| 链上购买定位 | Object ID 反查名称的索引及服务边界、二级名称销售登记的具体流程 |
| 交易信任 | 如何提示可信发布者、真实支付入口和付款后的内容可取得性 |
| Static Web 上线 | 第二类上线方式的包装、域名及管理流程 |
| 临时 PIKG | Agent 自动包装的具体 Skill、权限边界与安装处理细节 |
| namedstore GC | 临时产物及大型 Docker 包装的占用、引用保留、回收与用户界面 |

### 17.3 原型与正式能力的状态边界

按本轮口述，Public 目录访问机制已有基础，系统已在使用命名对象与相关应用上线能力；BNS 相关发布和购买流程可用于测试演示，但正式的链和合约尚未上线；完整信用体系未建立；namedstore 的 GC 主要通过命令行管理，图形界面尚未完成。

以上状态不能互相替代：某段流程可以跑通 Demo，并不代表相应的正式网络、合约、信用或管理界面已经完成。

## 十八、记录结论

本轮讨论没有将“分享”“发布”“上线”统一定为一个概念，而是先把三个方向的行为和结果辨认清楚：

**分享解决把内容交给谁处理；内容发布解决对象以什么身份、形态和条件进入内容网络；上线解决页面或服务怎样在自己的 Zone 被实际使用。**

下一阶段的入口设计，应建立在这些真实流程及其管理差异之上。是否合并按钮仍然开放，不因本记录按能力分章就预设界面必须按同样方式拆分。
