## 1. 方案结论与核心决策

### 1.1 总体方案

**采用“一个通用分享入口、三个明确的系统动作、按场景提供快捷入口、一个统一管理中心”。**

普通用户不需要先回答“我到底是在 Share、Publish 还是 Deploy”。他只需要表达目的：把东西发给别人、得到一个可转发链接、发布一份可以长期引用的内容，或者把网站和服务用起来。

系统内部继续严格区分分享、内容发布与应用上线。统一的是入口组件、任务反馈、结果表达与管理入口，不是把几种生命周期强行合并。

三个系统动作是：

| 用户看到的动作 | 一句话说明 | 系统内部语义 |
| --- | --- | --- |
| **创建分享链接** | 发给别人查看，可以设置密码和到期时间 | 创建由系统管理的分享访问入口 |
| **发布内容** | 保存独立版本，供长期引用；可进一步作为作品发行 | 创建并托管命名对象，按需关联名称及收录者 |
| **上线网站或服务** | 让网站、小游戏或服务在自己的 BuckyOS 中可用 | 在目标 Zone 中部署一个可访问实例 |

“通过应用分享”保留为分享面板里的应用目标区，不要求它产生链接，也不强行套入上述三个系统动作。

### 1.2 对原有入口争议的明确回答

**建议合并文件类界面中含义不清的“分享／发布”双入口，保留通用“分享”按钮；但不取消“发布内容”和“上线”的独立动作，也不把它们定义成普通分享链接的某个有效期。**

在音乐创作器、视频编辑器中，可以直接出现“发布作品”；在网站编辑器、Jarvis 生成的项目卡片中，可以直接出现“上线”。这些都是同一系统流程的快捷入口，不是另一套实现。

因此，本方案既不是“所有界面都摆三个按钮”，也不是“只剩分享，所有底层动作都隐去”。

### 1.3 关键决策表

| 编号 | 本方案建议 | 对用户的意义 |
| --- | --- | --- |
| D01 | 通用入口用“分享”，专业动作保留精确名称与直达入口 | 普通用户有熟悉入口，高级用户不必反复走选择页 |
| D02 | 根据内容及所在场景推荐操作，但不自动执行发布或上线 | 系统帮助判断，不替用户改变公开范围或启动服务 |
| D03 | 普通分享默认固定本次内容；内容发布默认手动发布新版本 | 修改源文件不会悄悄改变别人看到的内容 |
| D04 | “不自动到期”只是期限，不等于永久可访问，也不等于内容发布 | 避免以期限混淆操作语义 |
| D05 | 发布内容显示“长期入口”和“此版本链接”，默认只突出一个推荐链接 | 普通用户容易复制，高级用户能够精确引用 |
| D06 | 源文件、已发布版本、名称、上线实例分别管理 | 删除源文件、撤回发布、下线服务不再互相误伤 |
| D07 | Public 是高级捷径，不作为所有分享的后台实现 | 不为了生成一个私密链接而把内容放进公开目录 |
| D08 | 自用上线不要求内容发行、BNS 注册或应用商店上架 | Docker 和 Agent 产物可以直接用起来 |
| D09 | 系统维护统一管理视图，各服务保留自己的权威状态 | 用户在一个地方管理，系统不制造互相矛盾的两本账 |
| D10 | 付费、第三方投递、公开范围扩大、敏感权限提升必须显式确认 | 一键操作不能变成隐蔽上传、收费或授权 |
| D11 | 密码、好友及付费限制必须覆盖对象和数据访问路径 | 页面上看起来私密，底层也必须真正受控 |
| D12 | 先交付分享与上线的完整基础体验，再启用真实交易 | 不把测试链 Demo 包装成正式可购买能力 |

## 2. 用户目标与设计原则

### 2.1 三类用户，共用一套产品

| 用户 | 典型表达 | 应交付的结果 | 不应强迫理解的内容 |
| --- | --- | --- | --- |
| 普通使用者 | “把这张图给朋友”“这个页面怎么让别人打开” | 明确的接收方、可用入口、停止访问的方法 | Chunk 类型、对象图、PIKG、网关路由 |
| 创作者与进阶用户 | “这份报告以后还会更新”“我要发布一首歌” | 稳定入口、版本管理、作品信息、发行状态 | 与当前任务无关的合约、部署细节 |
| 开发者与高级用户 | “部署这个镜像”“只要固定 Object ID”“直接放 Public” | 可预测语义、少步骤、可脚本化、可诊断 | 每次重复的基础解释和不必要的向导 |

不设置一个会改变全系统行为的“新手模式／专家模式”开关。采用渐进展开：默认简洁，按对象展示相关选项；高级设置、快捷入口和自动化参数随时可用。

### 2.2 四个必须始终说清楚的问题

每条流程的确认页和结果页都必须回答：**将交付什么、谁能访问、以后修改会怎样、到哪里停止或管理。**

对于上线，还必须回答：在哪里运行、会占用哪些资源、申请哪些权限。对于收费，还必须回答：向谁付钱、买到哪个版本或哪种授权、凭证由谁验证。

### 2.3 不通过“少一个按钮”牺牲结果的确定性

允许系统自动填名称、识别类型、推荐部署方式，甚至在明确授权范围内自动执行。但以下行为不能依靠不明显的默认值：把私有内容变为匿名公开、把数据发送到新的外部服务、执行不可信代码、购买名称、支付内容费用、删除受引用对象。

### 2.4 本期不做的事情

本方案不把协同编辑权限、复杂会员订阅、限时营销、全网撤回、版权真实性认证、任意 Docker 零适配保证纳入基础能力。分享“可查看”不等于授予源文件编辑权限；协作编辑仍由相应应用提供独立的“邀请协作”动作。

## 3. 概念、链接与权限的统一表达

### 3.1 三个动作不是文件类型的分类

同一首音乐可以通过聊天应用发送，可以生成七天有效的分享页面，也可以发布为 Music 类型内容对象。一个 PIKG 可以作为文件发送、作为软件产物发行，或者只在自己的 Zone 安装上线。

**输入类型用于判断哪些动作可用，用户意图决定执行哪个动作。** 系统不能看到 PIKG 就自动发行，也不能看到 HTML 就自动执行。

### 3.2 面向用户的链接名称

| 名称 | 用户应理解的含义 | 关键边界 |
| --- | --- | --- |
| **分享链接** | 打开一个可管理的分享页面 | 可以有密码、接收范围及到期时间；不必是文件直链 |
| **此版本链接** | 始终指向这一个确定版本 | 不跟随源文件修改；标识不变不代表数据永不下线 |
| **长期入口** | 指向这份内容当前正式发布的版本 | 只有执行“发布新版本”后才切换，不随编辑自动变化 |
| **网站／服务地址** | 访问已经上线的站点或服务实例 | 依赖实例、网关、访问策略和运行状态 |
| **Public 路径地址** | 访问公开目录中这个位置的内容 | 跟随目录入口；改名、移动、删除会影响路径 |
| **作品名称（BNS）** | 用名字找到作品，按需关联销售 | 名称控制、内容版本和购买授权是不同关系 |

高级区域另列 Object ID、对象描述地址、原始数据地址、Reference Path 等。**对象描述 JSON 的 URL 不能被无标注地当作视频数据流直链。** 客户端通过系统解析能力取得可消费的数据入口及必要授权上下文。

### 3.3 四个独立维度

内部模型分别表达：

| 维度 | 例子 | 不允许的混同 |
| --- | --- | --- |
| 访问范围 | 仅自己、指定用户、好友、持链接者、任何人 | 只在自己的 Zone 运行，不等于只有自己能访问 |
| 内容更新 | 固定此次快照、手动发布新版、跟随 Public 路径 | 使用同一 URL，不等于内容永远不变 |
| 可发现性 | 不主动投递、投递指定内容商店 | 匿名可访问，不等于已被所有商店发现 |
| 可用性 | 仅本地准备好、本 Zone 可提供、外部访问已验证、收录者副本可提供 | Object ID 已生成，不等于任意设备都能下载 |

“不主动投递”不承诺不被第三方发现或索引。“只有链接的人能看”不承诺链接绝不被转发。界面用完整的权限说明，不用这些名称暗示额外的保密保证。

### 3.4 默认值一览

以下是本方案的产品默认值，需经可用性测试验证，不是来自已有实现的事实。

| 场景 | 默认访问范围 | 默认期限 | 默认内容语义 |
| --- | --- | --- | --- |
| 新建普通分享链接 | 持链接者可访问，创建前明确显示 | 7 天；可改为不自动到期 | 固定此次快照 |
| 已知接收方的分享 | 优先采用对应接收方授权；缺少该能力时明确说明 | 使用对应服务规则 | 由目标应用声明，不能默认为同步源文件 |
| 发布普通内容 | 默认不投递商店；公开发布前确认访问范围 | 不自动到期 | 托管独立版本，默认创建长期入口 |
| 发布作品 | 先完成版本；免费传播或启用收费由用户选择 | 不自动到期 | 类型化内容对象，手动更新 |
| 首次上线网站或服务 | 仅自己 | 不自动停止 | 在自己的 Zone 运行 |
| 明确“发朋友一起玩”的上线 | 根据意图预选访问方案，在执行前展示 | 不自动停止 | 不自动发行源码或 PIKG |
| Public 快速公开 | 匿名公开，不提供密码或到期选项 | 随目录入口存在 | 跟随公开路径，生成对应版本标识 |

源对象有组织策略或禁止外发限制时，所有默认值服从这些约束；“推荐选项”不得绕过系统授权。

## 4. 入口设计：统一分享，按场景直达

### 4.1 通用分享面板

文件管理器、图片查看器、播放器、Workspace 与其他应用调用同一个系统面板。首屏展示内容摘要、已有结果和相关目标，不先弹出术语选择题。

```text
分享「项目介绍.pdf」
2.4 MB · 当前文件                         查看已有分享

创建分享链接
发给别人查看，可设密码和到期时间                   >

通过应用分享
[消息中心]  [已安装目标应用]  [更多应用]

更多方式
  发布内容          保存独立版本，供长期引用         >
  ……仅显示与当前内容有关的其他动作……
```

上面是信息布局示意，不是最终视觉稿。没有生成链接时，不出现一个会在幕后公开文件的“复制链接”按钮。已经有结果时，顶部可以显示“复制已有链接”，同时展示该链接的权限和期限。

### 4.2 情境推荐规则

| 当前内容或上下文 | 优先显示 | 保留的其他动作 |
| --- | --- | --- |
| 普通图片、PDF、文件 | 创建分享链接、通过应用分享 | 更多方式中的发布内容 |
| 正在创作的音乐、视频 | 分享预览、发布作品 | 创建普通分享链接 |
| 单个 HTML、静态站点目录 | 上线网站，与创建分享链接并列且说明差异 | 分享源文件；高级快速公开 |
| 带后端项目、Docker 引用 | 上线服务 | 分享项目文件；发布软件产物 |
| 已打包 PIKG | “在我的 BuckyOS 上线”与“发布这个软件包”两个明确选项 | 作为普通文件分享 |
| 已上线服务 | 分享访问地址、管理访问权限 | 更新上线版本；另行发行应用包 |
| 已发布内容 | 复制长期入口、分享当前版本、发布新版本 | 管理收录者与作品设置 |
| Public 中的文件 | 复制公开路径地址、查看公开状态 | 保存为独立内容发布 |

推荐仅基于明确的文件类型、应用提供的内容角色及用户意图。存在歧义时同时显示两个有区别的选项，不依靠推测执行副作用。

### 4.3 快捷入口

网站编辑器可以保留“预览｜上线”；创作应用可以保留“发布作品”；高级用户可以把“发布内容”“上线”“复制 Object ID”固定到工具栏或右键菜单。

这些入口直接进入相应配置页，跳过通用面板。高级参数、最近一次选择可以复用，但不记忆跨任务的付款同意、敏感权限授权或公开范围扩大同意。

### 4.4 批量与混合选择

多张图片可以作为一个分享集合，结果说明“固定包含这 12 项”。发布时提供“分别发布”或“作为一个合集”，默认不悄悄产生多个链接。批量文件权限不一致时先列出例外项，不按最宽权限处理全部内容。

同时选中视频、网站项目和 PIKG 时，不自动决定上线。面板优先提供兼容的普通分享；进入发布或上线后要求选择一个明确的产物范围。

## 5. 流程一：通过应用分享

### 5.1 标准流程

用户选择目标应用后，系统将本次选择的内容及有限读取授权交给目标应用。目标应用完成自己的接收方选择、消息编辑、Feed 发布或其他处理，并把结果回传系统。

不要求系统先生成一个公开链接，也不要求先把文件复制到 Public。目标应用需要上传到外部服务时，应在其确认页说明内容去向，不能把“选择一个应用”解释为授权它读取整个目录或账户。

### 5.2 系统负责到什么程度

| 项目 | 责任 |
| --- | --- |
| 目标筛选、内容摘要、目标身份展示 | 系统 |
| 接收方、文字说明及应用内特定选项 | 目标应用 |
| 本次数据的受限交付 | 系统与目标应用按契约完成 |
| 最终消息、Feed、分享网页等结果 | 目标应用 |
| 全局记录、任务状态与支持的管理操作 | 系统聚合，目标应用提供事实与能力 |

### 5.3 结果等级，不伪造“已发送”

系统区分“已交给应用”“应用已完成”“失败”“结果未确认”。只有目标应用确认发送完成，才能显示“已发送”；只有获得相应回执，才能展示“已送达”或“已读”。

通过浏览器原生分享能力交接时，不能把 API 成功当作接收方已完成处理。W3C Web Share 规范的成功可以止于向目标或操作系统交付数据，并不等待目标认可最终业务结果。此类路径在 BuckyOS 中应显示“已交给外部应用，后续结果未确认”。[^web-share]

### 5.4 分享已发布内容与已上线服务

分享已上线游戏时，目标应用默认收到**访问地址**，不是源码、PIKG 或安装包。分享已经发布的音乐时，默认收到当前选定的作品入口或版本引用，不重新上传完整音乐。

确需发送原文件时，用户切换“发送文件副本”，系统重新检查外发权限。不能把“复制链接”偷偷变成“上传文件”，也不能反向把接收者打不开的私有本地路径当作可用链接交付。

## 6. 流程二：创建分享链接

### 6.1 普通流程只要求确认一张卡片

```text
创建分享链接

内容       项目介绍.pdf · 固定此次内容
谁能查看   持有链接的人                         [修改]
有效期     7 天，到期时刻按当前时区显示           [修改]

更多设置   访问密码 / 指定接收方 / 页面选项

修改或删除原文件，不会自动改变本次分享。
                                           [创建链接]
```

用户可直接接受这组明确展示的设置，也可以修改。打开对话框、选择期限、复制尚未生效的预览地址，都不产生公开访问权限；点击“创建链接”才提交。

系统内置分享服务默认生成只读预览与下载页面。评论等互动能力由已有服务能力决定，不把评论系统作为所有分享的必要前提。

### 6.2 快照与存储

建议普通分享持有独立内容快照，并在分享有效期内保留相应 namedstore 引用。这样用户移动或删除源文件后，已发出去的链接不会突然失效。

创建页只需一句话解释，结果详情提供源文件位置及“使用的是分享时的副本”。文件变化后，再次分享显示“源文件已有变化：复制旧分享／为当前内容创建新链接”。默认不覆盖旧分享内容。

长时间维护同一入口的需求导向“发布内容”。第一期不在普通分享页加入复杂的实时跟随规则，以免把快照、别名和源文件同步混在一起。

### 6.3 密码、到期与接收方

密码保护仅保护当前分享入口；密码与链接可以分别复制。指定用户需要真实的身份授权能力，不用一个看似私密的短 URL 代替。过期由服务端判断，界面显示具体时刻及所用时区。

默认七天允许快捷改为一天、三十天或“不自动到期”，也允许自定义时刻。不自动到期的分享仍然是分享，不自动转为 NDN 作品发布或 BNS 命名。

不提供“禁止下载所以不能保存”的承诺。页面可以不显示下载按钮，但文案不能把这一点说成防复制或版权保护。

### 6.4 复用与重复创建

同一内容、同一版本、同一访问策略存在有效分享时，优先提供“复制已有链接”。用户更换密码、接收方或期限时，明确选择“修改这个分享”还是“另外创建一个”，不能自动修改过去发给其他人的入口。

对固定内容的重复分享可以复用底层数据，不复用不相容的访问授权。共享对象存储与共享一个密码不是同一件事。

### 6.5 停止分享

操作名称为“停止此分享”。确认文案：

> 此链接将不能继续提供内容。原文件不会被删除；其他分享入口及对方已经保存的副本不受影响。

系统取消本分享的访问授权和保留引用，是否释放数据由其他有效引用及清理规则决定。不能用“删除记录”假装完成撤销。

<a id="s07"></a>
## 7. 流程三：发布内容

### 7.1 普通发布与作品发行共用起点

入口统称“发布内容”。图片、音乐、视频创作场景可显示“发布作品”，但第一步仍是确定内容类型及其必要描述。系统根据来源应用与文件特征预填信息，不要求用户手选 Chunk、File Object 或 Chunk List。

普通文件不必填写封面、简介、分类等作品字段。音乐或视频只显示对应内容类型必须的信息，更多描述可展开。字段不足以形成有效对象时才阻止继续，不能为了统一表单让所有人填写所有 Metadata。

### 7.2 基础向导：确认内容，确认发布

**第一步：确定这一版是什么。**

展示标题、类型、内容范围、作者身份及必要元数据。标题默认来自文件名；作者只有在该类型需要作者身份时使用当前已选身份，并明确该身份是否对外显示。来源路径、个人备注、设备名、非必要 EXIF 信息不自动进入公开 Metadata。

填写完成后生成对象及 Object ID。大文件的计算展示进度，可以保存草稿。高级用户可提前展开“查看此版本标识”，但普通用户无需等待一串标识出现后再重新理解流程。

**第二步：确定如何提供访问。**

```text
发布「项目介绍」

访问范围     任何人可访问                       [修改]
对外更新     只在我点击“发布新版本”后更新
长期入口     项目介绍                           [修改]
内容发现     不主动投递到内容商店               [修改]

本次内容会作为独立版本保存，源文件修改不会自动发布。
没有自动到期时间；停止提供内容后，链接可能无法访问。

高级设置：此版本标识 / 对象类型 / 提供位置
                                      [公开发布]
```

公开只是默认可见方案，最终提交前必须清楚展示。需要只对指定用户发布的进阶场景，可以使用受控策略；系统必须具备第 14 节规定的实际保护能力。受限内容不能默认投递给公开商店。

### 7.3 链接先行，但不把草稿显示成发布成功

得到 Object ID 后可以复制“此版本引用”，包括离线状态。按钮旁始终说明：

> 标识已生成，内容尚未对外提供。现在发给别人，对方可能暂时无法打开。

这时的状态是“版本已准备”，不是“已发布”。对象提交到 namedstore、建立所需保留引用和访问策略后，才进入“本 Zone 已提供”。网络可达性、外部验证和商店收录分别显示。

普通用户默认在内容已经提供后看到主复制按钮；高级用户可以在准备阶段提前复制。允许先拿到链接，不允许把未完成过程伪装成已完成。

### 7.4 默认提供两种引用，但只突出一个

基础发布默认创建一个 Zone 内的**长期入口**，指向正式发布版本，不要求用户购买 BNS 名称。入口名称建议由标题生成；冲突时提供可编辑候选，不静默抢占或覆盖。

结果页主按钮为“复制长期入口”；旁边的次级菜单提供“复制此版本链接”“复制 Object ID”。一次性固定发布的高级用户可以关闭长期入口，主按钮自动改为“复制此版本链接”。

纯文件的发布入口可以直接提供数据，不强制产生网盘互动页。音乐、视频等可以由系统预览器或兼容应用展示，**预览方式不应改变对象身份，也不额外制造另一份发布状态**。

### 7.5 更新规则

编辑源文件不自动触发对外更新。用户在已有发布条目中选择“发布新版本”，系统显示变更摘要，形成新 Object ID，完成保存及可访问性检查后，再切换长期入口。

| 修改内容 | 是否产生新对象版本 | 是否需要重新发布 |
| --- | --- | --- |
| 文件数据或参与对象身份的 Metadata | 是 | 是 |
| 视频改为另一种内容类型 | 是 | 是 |
| 系统中的私有备注、管理标签 | 否 | 否 |
| 不进入对象身份的访问策略或发行渠道 | 否 | 修改对应策略；涉及放宽权限须确认 |
| 作品展示文字已属于对象 Metadata | 是 | 不能偷偷当作管理标签修改 |

已经复制过的此版本链接保持指向原版本。长期入口指向最后一次成功发布的版本。不得在后台生成新 ID 后，把先前显示给用户的旧 ID 当作同一版本的别名。

### 7.6 元数据冻结与去重

在版本准备阶段，系统对数据和 Metadata 形成一致快照。准备完成后再次修改元数据，应明确使先前的预览 ID 失效，并重新生成。发布时发现源内容已变，允许选择“继续发布已准备版本”或“重新准备”，不静默替换。

去重检查区分“相同 Object ID 已存在”和“底层文件数据可复用”。相同视频以 File Object 和 Video 类型对象表达时，不能只因数据相同就合并其语义。

检查范围限于用户有权查看的记录或明确公开的信息，不能借去重接口探测他人的私有内容是否存在。建议把管理备注、投递时间等不必参与身份的字段放在发布记录中，避免无意义地生成重复版本。

### 7.7 目录、合集与依赖

发布目录时，先展示将纳入的文件列表、总规模、排除项与外部依赖。推荐发布可重复访问的一致目录快照，而不是边读取边让内容变化。

默认排除或阻止意外纳入密钥、凭证文件、版本控制内部目录和不相关构建缓存，并允许用户查看具体规则。依赖于外部 URL 或私有对象时，分别提示“访客可能无法读取”“需要授权后生成副本”或“仅保留外部引用”。不能为了让链接看起来完整，擅自抓取并公开原本受限的数据。

<a id="s08"></a>
## 8. Public 目录：保留捷径，补齐可见性

### 8.1 定位：文件系统级的快速公开通道

保留将文件、目录或允许的软链接放入 Public 后提供匿名访问的能力。高级用户和 Agent 可以继续通过文件操作完成，不被强制带回图形向导。

示意：

```text
/public/snake/index.html
    → https://public.<zone-host>/snake/index.html
```

该形式来自讨论中的地址组织方式，仅作路由示意；实际域名与路径由 Gateway 配置提供，前端不自行拼接。

### 8.2 界面名称与提示

File Browser 中显示“Public · 公开目录”，持续保留“这里的内容允许匿名访问”的说明。高级操作菜单名称为**“快速公开到 Public”**，不叫“安全分享”“永久分享”或“一键私密发布”。

通过系统界面首次复制或创建软链接时，显示精简确认；用户已经明确使用 Public 的脚本或命令行流程不额外弹出交互阻塞，但必须拥有相应写入和公开能力。Agent 的普通工作目录写权限不应隐含 Public 发布权限。

### 8.3 Public 内容也出现在统一管理中心

本方案建议增加目录观察与周期性校准，把 Public 现状投影为管理中心条目，标记为“Public 目录公开”。这不是要求文件操作之前先完成一次传统分享登记。

系统应展示路径、当前版本标识、公开状态、来源为复制还是软链接，以及可执行操作。对于历史文件，只能标记“系统发现时间”；没有真实操作记录时，不编造“由某人在某时分享”。

直接用命令行新增、修改、删除 Public 文件，也应通过观察和校准更新视图。管理中心不能因为没有经过 UI，就把这些公开入口漏掉。

### 8.4 完整内容提交与对象化

UI 发起的快速公开建议先在非公开暂存区准备完整内容和 Object ID，再原子地提交到公开路径。直接文件操作也需要进入一致的对象化处理。

为避免访问到半写入文件，新实现建议让 Gateway 只暴露已完成一致快照及对象登记的版本。大文件仍在准备时，文件系统中可以看到文件，外部状态显示“正在准备公开”；覆盖时尽量保持上一个完整版本可用，准备成功后切换。

这项完整性控制是新增实现要求，不是假定现有文件监听天然能够知道写入何时完成。需要结合写入提交、原子改名或可验证快照机制落地。若尚不能保证，必须保留“准备中／完整性未确认”的状态，不能显示 NDN 发布已完成。

### 8.5 软链接的处理

软链接仅在系统允许的可导出范围内工作。确认时必须提示“目标更新会改变公开内容”，并说明删除该公开入口不会删除源文件。

系统必须检查真实目标及后续变更，阻止跨越禁止公开的系统目录、密钥目录或其他权限边界。不能只在创建时检查一次，再允许通过替换目标绕过限制。无法可靠执行此检查的版本，应暂时禁止该类软链接公开，而不是假装安全支持。

### 8.6 Public 与独立发布的生命周期区别

Public 的默认管理承诺是“跟随目录入口”，不是“永远保留每个历史版本”。删除或移动入口会影响对应路径及该入口所授予的本地公开访问；历史对象是否仍可访问，取决于是否还存在其他合法发布或保留关系。

管理中心提供“保存为独立内容发布”。执行后为选定版本建立独立保留与发布关系；以后删除 Public 入口，不再影响这份独立发布。界面明确表示这是增加另一种提供方式，而不是悄悄把原路径改成另一种生命周期。

### 8.7 Public 不能承担受控分享的底座

用户要求加密码、指定好友或付费时，系统引导创建受控入口，不在 Public 上画一个权限开关。

如果同一内容仍可通过 Public 或其他匿名入口直接取得，应提示：

> 这份内容还存在公开入口。给新链接加密码，只能保护这个入口，不能让已经公开的内容重新变成私密内容。

移除本机公开入口也不能承诺追回外部缓存或他人保存的副本。

## 9. 流程四：上线网站或服务

### 9.1 对普通用户只问“怎么用”，不先问“怎么部署”

进入上线流程后，系统先识别产物并准备上线方案。默认表单集中于网站名称、访问地址、谁能访问以及必要的运行权限。

```text
上线「朋友一起玩」

运行位置     我的 BuckyOS
访问地址     friends-game.<zone-host>           [修改]
谁能访问     仅自己                             [修改]
运行方式     应用服务 · 系统已选择合适方式

预计资源     显示可用的估算与存储预检结果
权限         创建本应用的数据目录；访问网络      [详情]

这会在你的 BuckyOS 上运行服务，不会发行源码或安装包。
                                          [确认上线]
```

如果用户已经明确说“让朋友打开就能玩”，可以预选适合的方案，但执行前必须说明是“指定好友登录后使用”还是“知道地址的任何人均可使用”。“朋友”这个自然语言词不能直接等同于匿名公开。

### 9.2 三种上线方式及默认路由

| 方式 | 推荐使用场景 | 系统处理 | 对用户的主要差异 |
| --- | --- | --- | --- |
| **快速公开页面** | 用户明确选择 Public；轻量且可信的临时静态内容 | Public 路径与对象化处理 | 无独立应用隔离；路径依赖目录；匿名公开 |
| **独立静态网站** | 普通用户上线 HTML、静态小游戏或站点 | 按 Static Web 类型管理；建议用轻量 PIKG 描述站点，不引入容器 | 独立站点入口、版本切换及统一管理 |
| **应用服务** | 有 HTTP 后端、多人状态、Docker 或 Script Host 项目 | 生成或使用 PIKG，进入安装、权限、隔离与调度 | 需要运行资源、数据目录及服务健康检查 |

这里把 Static Web 的产品方向明确为“独立、受管理的静态站点”，建议采用轻量 PIKG 与既有安装体系衔接。该包装与安装契约是新建议，需与现有 Static Web 实现核对，不能在兼容性未确认时强制改包。

包含后端的项目不能降级为“复制进 Public”来冒充成功。系统不能确定类型时，显示“静态网站／有后端服务”两项并给出依据，或让 Jarvis 继续分析。

### 9.3 为什么普通网站不默认都放 Public

Public 下的不同路径不构成浏览器同源隔离边界。同源判定主要取决于 scheme、host 和 port，而不是 URL 的文件夹路径。[^origin] 因此，独立静态站点应使用合适的独立来源和最小权限，不能把 Public 的子目录当作各应用间的安全隔离。

本方案保留 Public 的效率，但把它放在明确的高级捷径中。普通用户点击“上线网站”时，优先获得可管理的独立站点，避免以后才发现登录状态、脚本权限或根路径假设不匹配。

### 9.4 静态网站预检

系统检查入口页、资源相对路径、是否依赖网站根路径、前端路由回退需求以及缺失资源。对于当前无法自动处理的构建步骤或外部后端，明确展示依赖，不能把“有 index.html”当作完全可用的证据。

单个 HTML 可以自动包装为站点。含未构建源码的目录先构建或让 Agent 补齐，不能把密钥文件、开发配置和完整项目目录直接公开。

### 9.5 Docker 与 Script Host 应用

已有有效 PIKG 时直接检查并进入安装。Docker 或项目具有必要 Metadata 时可自动包装；不足时由 Jarvis 分析端口、启动方式、资源、持久化路径及依赖，再形成可检查的方案。

首次分析不自动给应用特权容器、宿主机根目录、Docker 控制接口或整个用户目录。Agent 推断出的权限进入确认摘要；不支持的运行方式显示明确原因，而不是不断更换参数直到高权限启动。

Script Host 按讨论中的 TypeScript、Python 方向接入。运行时和版本由系统能力返回，不能只凭文件扩展名保证可以执行。镜像引用尽量固定到可验证版本或摘要，防止一次更新引入未确认的不同产物。

### 9.6 子域名属于实例，不属于所有安装者共用的包

系统建议可用子域名，并验证保留名称、冲突、证书与 Gateway 路由。用户可修改。同一个 PIKG 在不同 Zone 或同一 Zone 的不同实例中，可有不同地址。

显示“地址已保留”不等于上线成功。最终至少需要完成安装或站点配置、服务健康检查及入口路由检查。对 API 服务提供接口基地址和适当的健康信息，不强迫它伪装成有首页的网站。

### 9.7 上线完成必须区分运行与外部可达

结果分别显示：应用是否运行、Gateway 是否能访问、当前访问范围是什么、外部可达性是否验证。

系统只能在有对应证据时显示“外部访问已验证”。若仅完成本机检测，则显示“已上线，外部访问尚未验证”，提供测试入口或经授权的远端检测。仅用管理员登录态打开成功，不能证明匿名访客也能访问。

从上线结果点击“发给朋友”时，先检查当前范围。仅自己可访问的服务不能直接给出“朋友已可使用”的成功提示；用户可以明确选择调整访问权限，或继续复制一个注明受限的地址。

### 9.8 更新、回退与下线

升级尽量先准备新版本，检查通过后切换同一服务地址；失败时保留旧版本。回退必须说明是否只是代码版本回退，不能承诺自动恢复数据库、外部状态或不可逆迁移。

“下线”停止对应站点或服务入口，默认保留应用数据及可恢复配置；“卸载”另行确认是否删除数据。下线一个实例不撤销 PIKG 的公开发行，撤回包发行也不自动停止已安装实例。

## 10. 统一结果页与链接复制规则

### 10.1 所有流程使用同一类结果卡片

结果卡片包含内容名称、实际动作、主状态、主入口、访问范围、内容更新方式、最后检查时间与管理按钮。无需用户先进入应用日志，才能理解是否完成。

```text
「项目介绍」已发布

长期入口     [可读地址]                        [复制]
谁能访问     任何人
更新方式     只跟随正式发布的新版本
可用状态     本 Zone 已提供 · 外部访问未验证

其他链接     此版本链接 / Object ID
后续操作     发给朋友 / 发布新版本 / 管理
```

不同结果使用不同主文案：“分享链接已创建”“内容已提供”“网站已上线”“已交给消息应用”。不用一个统一的“发布成功”覆盖全部动作。

### 10.2 主复制按钮的选择

| 当前结果 | 主按钮复制什么 | 次级选项 |
| --- | --- | --- |
| 普通分享 | 当前分享页面链接 | 复制链接与密码说明；不默认合并密码 |
| 有长期入口的内容发布 | 当前正式发布入口 | 此版本链接、Object ID、数据直链 |
| 仅固定版本发布 | 此版本链接 | Object ID、适用的数据直链 |
| 已上线站点／服务 | 站点地址或 API 基地址 | 技术入口、实例信息 |
| Public 快速公开 | 公开路径地址 | 当前对象版本标识、独立发布 |
| 应用发送且没有 URL | 不显示复制 URL | 查看目标结果或消息 |

每种复制结果保留类型标签。高级用户可在同类场景记住“总是复制固定版本”，但界面继续显示当前复制的是哪一种，不能让一个看不见的历史偏好导致复制错地址。

### 10.3 三种特别容易误报的状态

**离线准备：** 允许复制版本引用，显示“内容尚未对外提供”。

**商店投递：** 内容在本 Zone 已可访问，但收录者尚在处理，显示“已发布 · 1 个商店处理中”，不显示“已上架全部商店”。

**服务就绪：** 程序启动但路由失败，显示“服务运行中 · 访问入口未就绪”，不能把容器启动成功等同于上线成功。

<a id="s11"></a>
## 11. 统一管理中心与生命周期操作

### 11.1 一个入口，不把不同对象塞进同一套按钮

系统侧栏提供 **“分享与发布”**。内部以以下视图组织：

| 视图 | 内容 | 常用操作 |
| --- | --- | --- |
| 全部 | 当前用户有权管理的各类结果 | 搜索、筛选、查看待处理事项 |
| 分享链接 | 系统创建的受控分享入口 | 复制、改权限、改期限、停止此分享 |
| 已发布内容 | NDN 发布及 Public 投影视图 | 版本、长期入口、收录、撤回；Public 条目管理路径 |
| 网站与服务 | 各种已上线或准备中的实例 | 打开、权限、更新、下线、卸载 |
| 通过应用发出 | 消息、Feed 及第三方结果 | 查看结果；按能力撤销或到应用管理 |

不再要求用户先记住“这个链接由 File Browser 还是别的系统组件生成”，才能找到管理入口。

### 11.2 列表字段与详情

列表默认显示名称、结果类型、谁能访问、当前状态及更新时间。高级筛选支持源文件、Object ID、名称、目标应用、接收方、Zone、任务来源、到期时间。

详情页再展开链接、版本、提供位置、收录者、存储占用、源文件关系及操作历史。同一文件有多个分享结果时可以分组，但每个结果保留独立身份与独立控制，不能按文件名合并。

### 11.3 与各应用列表的关系

File Browser 的“已分享”保留为统一记录的过滤视图，使用相同的结果标识、授权数据与操作接口。它不维护另一套不同的到期时间。

已知系统服务的操作直接整合，列表不必反复显示内部 App 名。第三方目标保留应用名称和管理边界，只展示它实际支持的操作。

第三方状态暂时无法刷新时，显示“最后确认于……”，保留历史而不假定内容还有效。系统聚合视图不是所有服务状态的替代权威。

### 11.4 动作名称必须准确

| 用户动作 | 实际影响 | 不能承诺或顺带执行的事情 |
| --- | --- | --- |
| 停止此分享 | 停止该分享入口的授权 | 不撤销其他入口，不删除源文件，不追回已下载副本 |
| 停止本机提供此版本 | 移除本机对应发布授权／提供关系 | 不使 Object ID 消失，不保证外部副本停止服务 |
| 请求商店下架 | 向所选收录者提交下架请求 | 不等于所有收录者已经执行，不等于删除作者内容 |
| 删除 Public 入口 | 删除对应文件位置或软链接入口 | 软链接不删源文件；不移除独立发布关系 |
| 解除长期入口 | 取消该名称或逻辑路径映射 | 不自动删除历史对象，不转让 BNS 所有权 |
| 下线 | 停止此实例的站点或服务访问 | 不默认删除持久化数据，不撤回软件包发行 |
| 卸载 | 移除安装；是否删数据另行确认 | 不自动释放所有仍受引用的对象 |
| 清理空间 | 回收无保留需求的实际存储 | 不以隐藏列表项冒充释放空间 |
| 隐藏记录 | 只影响当前管理视图 | 不改变任何访问权限或运行状态 |

### 11.5 “停止对外提供”可以是组合操作，但必须展示范围

对普通用户提供一个任务型入口“停止对外提供”。展开后列出：本机分享链接、Public 路径、NDN 提供关系、网站实例和已知商店。

默认只操作用户有权控制的本机入口；外部收录者显示“请求停止”，结果分别跟踪。付费作品还要提示可能影响已购用户的访问，不能以单个无说明开关完成。

任何组合撤回都不能显示“已从互联网删除”。若仍有其他公开入口，应明确指出，而不是因为当前条目停止就给出完全私密的暗示。

<a id="s12"></a>
## 12. 发布作品、BNS 命名与内容商店

### 12.1 作品发行是发布内容后的扩展，不是所有人的必经流程

当内容类型支持商店消费时，发布向导提供“作为作品发行”。创作者确认作品类型、必要 Metadata 与访问方式后，可以选择内容商店及是否启用收费。

普通用户发布一个 PDF，不会被要求选择销售模式或注册名字。免费作品也不必先购买一个独立 BNS 一级名，才能生成对象或向收录者投递。

### 12.2 用创作者语言表达 BNS

| 普通界面 | 高级说明 | 交互要求 |
| --- | --- | --- |
| 使用我的作品名称 | 自有 DID／BNS 命名空间内的子名称 | 优先推荐；提示不需要另购独立一级名称 |
| 使用独立名称 | 独立一级 BNS 名称 | 检查控制权或进入取得名称流程 |
| 仅使用内容链接 | Object ID 与可选 Zone 逻辑入口 | 免费普通内容可选；需 BNS 的收费功能不能借此跳过 |

名称输入显示可读示意，如 `作品名.我的名字`，正式序列化由 BNS 能力负责。前端不自行推导 `did:` 字符串，也不把 BNS 名称伪装成已经能被任意浏览器直接打开的传统域名。

默认以标题生成可编辑的子名称；冲突时给出候选。高级用户可以使用 Object ID 派生局部名称，但不能让普通用户面对一长串标识作为必填命名题。

### 12.3 名称取得、绑定、销售登记三步分开

“我控制这个名称”“名称指向这个版本”“消费者可以通过它购买”，分别展示。

使用自己命名空间下的子名称，不等于链上销售登记无需交易或费用。独立一级名需要先确认已有控制权，或完成相应取得过程。名称竞价、手续费、维护费用均由实际服务或合约能力返回，UI 不写死讨论中尚未核实的八字符规则。

离线时可以生成版本标识和保存候选名称；需要权威确认的名称占用、费用与交易状态显示“待联网确认”。不能离线宣布一个新的一级名已被占用。

### 12.4 内容商店是可选发行渠道

界面使用“投递到内容商店”，高级详情显示“收录者”。默认不向所有渠道广播，只向用户本次选择或明确设置为默认的渠道投递。

对于每个收录者分别保存状态：

| 状态 | 用户文案 | 不能推导的结论 |
| --- | --- | --- |
| 未投递 | 尚未发送到该商店 | 不说明本地内容是否可访问 |
| 已投递／已接收标识 | 已通知商店 | 不等于完整数据已取得 |
| 已读到描述 | 商店已识别作品，正在处理 | 不等于审核通过或副本完整 |
| 已收录 | 已完成该商店的收录要求 | 不自动等于该商店已公开上架 |
| 已上架 | 已在该商店展示；需有明确回报 | 不代表其他商店也上架 |
| 拒绝／需补充 | 显示该商店的原因与可执行操作 | 不撤销本地对象和其他渠道 |

同一收录者可以在其契约中把收录与上架合并；系统只有在获得明确语义时才合并显示。投递失败允许单独重试，不重新生成内容 Object ID。

### 12.5 免费、授权说明与付费不是同一字段

界面分别表达“访问是否收费”和“允许怎样使用作品”。免费不能自动填成“无版权”，也不能自动选择 copyleft 或其他授权方式。用户没有提供许可说明时，系统不代替作者作出授权承诺。

第一期收费授权建议以**本次明确发布的内容版本**为范围，购买页写明是否包含后续版本。长期入口换到新版本不自动扩大旧购买权利，也不能悄悄改变既有订单对应的内容。

名称控制和链上登记只展示系统能够验证的事实，不加盖“版权已认证”标签。版权转让及复杂许可交易留作后续独立方案。

<a id="s13"></a>
## 13. 消费者访问、试看与购买

### 13.1 普通消费者只需要打开链接

浏览器用户打开可用的 HTTP 入口；BuckyOS 内的应用支持粘贴 Object ID、对象 URL 或可解析名称。系统负责把标识解析为内容类型、可用提供方及访问方式。

免费且有权限时直接展示。需要登录、申请权限或购买时，提供明确动作。外部用户不应为了查看匿名公开图片而被强制安装 BuckyOS；需要身份或付费能力时，才进入对应网页流程或兼容应用。

### 13.2 错误结果的用户表达

| 实际结果 | 默认文案 | 行动 |
| --- | --- | --- |
| 需要身份 | 请登录后继续 | 登录 |
| 权限不足且允许说明 | 当前账号没有访问权限 | 切换账号；按作者配置申请访问 |
| 不愿透露存在 | 无法找到或访问此内容 | 检查链接；不泄露“作者有这个私密文件” |
| 需要购买且信息有效 | 完整内容需要购买 | 显示报价与销售者，用户主动进入购买 |
| 提供方暂不可用 | 内容提供方暂时无法连接 | 重试；查找其他已知提供方 |
| 对象不完整或校验失败 | 内容未能通过完整性检查 | 停止消费，不提示再次付款 |
| 已购买但取不到内容 | 已有购买记录，内容暂不可用 | 恢复授权或诊断交付，不重复购买 |

HTTP 允许服务端以 404 隐藏被拒绝资源的存在，客户端不能强行把这类结果解释成明确的对象删除事实。[^http]

### 13.3 试看与完整版

作品 Metadata 关联独立的试看对象和完整版对象。客户端先检查完整版是否有权访问；需要购买时，在能够取得试看对象的前提下播放，并明确标注“正在播放试看，完整版尚未解锁”。

没有试看内容就直接显示作品说明及购买入口，不在底层临时截取完整版前几分钟公开。试看结束不自动购买。完整版打不开且错误原因不是需要购买时，也不能擅自把它解释成付费门槛。

### 13.4 HTTP 402 的产品边界

本方案沿用讨论中的 HTTP 402 方向，但 **RFC 9110 将 402 保留供未来使用，并未定义 BuckyOS 所需的支付字段、自动跳转或收据协议**。因此，需要定义带版本号的 BuckyOS 扩展契约，不能宣传为浏览器天然支持的统一支付能力。[^http]

兼容应用只在识别有效的扩展响应并核对其与所请求对象的关系后，展示购买操作。普通 402、无效响应、未知扩展版本只能显示受限提示或经过核实的外部入口，不能据此自动支付。

### 13.5 两条支付路径的界面

| 方式 | 用户看到的内容 | 成功依据 |
| --- | --- | --- |
| 发布者／授权销售者支付网关 | 作品、版本、收款方、金额、支付方式与授权范围 | 获得可验证、被内容提供方认可的签名收据 |
| BNS 合约购买 | 网络、作品名称、对应版本、价格、交易费用及授权范围 | 合约购买状态获得所需确认，并能验证购买者资格 |

使用传统支付的网关可以支持传统货币。合约购买按本轮设想使用 USDT；实际网络、代币标识和合约地址均由环境配置提供，不能只显示一个“USDT”字样就让用户无法辨别资产或网络。

网关路径的默认接入可先限于作者本人签发收据。允许授权销售者接入时，必须具备可验证的授权链与明确权限范围，不能只因为收据上有签名就认定有效。

### 13.6 购买凭证管理

建议由系统的“已购买内容”能力保存订单关联与凭证，内容应用请求使用授权，不各自保管一份无法恢复的收据。签名收据至少绑定作品或版本、购买者身份、签发主体及授权范围；不把可随意复制的收据当作任意人都能使用的永久通行证。

链上方式记录网络、合约、作品定位、交易及购买者身份，按验证需要构造授权证明。两种方式共用消费体验，但不伪装成同一种底层证明。

凭证不进入公开 Metadata、普通 URL、日志或第三方分享内容。用户换设备或重新打开播放器时应能够恢复合法购买，不被误导再次付费。

### 13.7 购买定位与恢复

仅有 Object ID 时，可通过 BNS 友好查询服务查找交易关联，或从可信的付费响应中取得购买入口。返回的名称、版本和交易条款必须与原请求核对，不能从长期名称重定向到另一部作品后仍沿用原报价。

支付流程分为“待支付”“确认中”“已有购买资格”“内容已取得”。网关已付款但收据未返回时进入恢复流程；链上提交但确认未知时查询原交易，不重新发起购买。任何超时都不能直接等价于“未付款”。

### 13.8 正式交易门槛

按讨论记录，当前只有可演示的相关原型，正式链与合约未上线，信用体系尚未建立。[^discussion] 因此，第一阶段展示测试购买时必须有持续的“测试网络／测试资产”标识，不收真实款项，不让测试报价看起来可以正式交易。

启用真实交易前，至少完成销售者身份与支付入口校验、凭证恢复、失败诊断和内容提供状态展示。链上记录可验证不等于内容一定交付；购买页需要清楚说明谁负责提供内容及故障时如何处理，不能仅靠一个“可信”图标代替这些信息。

## 14. 权限与安全边界

### 14.1 本方案建议的 NDN 权限方向

**建议私有 namedstore 内容默认需要授权；知道 Object ID 只表明知道标识，不自动获得读取权限。** 公开访问必须存在明确的公开提供关系。已经合法公开的内容仍可按其公开策略通过对象标识访问，不要求每次先经过包装页。

这是对原讨论中两种权限方向的产品选择建议，而不是声称当前系统已经完成切换。跨 App 共享私有对象可以通过主体授权或限定能力实现，不继续依赖“所有人知道 ID 就能取到”来替代授权。

### 14.2 访问控制必须覆盖整条数据链

分享页面、对象描述、File Object、Dir Object、Chunk List、Chunk、下载接口、媒体 Range 请求、缓存及收录者提供接口，都需要与对应授权语义保持一致。

例如，付费 Video 对象的描述可公开，完整版数据不能因为底层 Chunk ID 已知而匿名下载。把 PIKG 放进 namedstore 用于本地安装，也不得因此自动公开它包含的源文件或镜像。

**如果当前版本做不到这一点，受限分享和付费内容必须经过真正能保护数据的路径，或关闭相应能力；不能只在 UI 上增加密码框。** 这是发布门槛，不是后续美化项。

### 14.3 Reference Path 的用户表达

普通用户不填写 Reference Path。系统生成能携带必要访问上下文的链接，高级详情可以查看并用于 SDK 调用。

Reference Path 是查找访问策略的线索，不是任意写一个路径就获得授权，也不是 HTTP 的 `Referer` 请求头。底层读取依赖对象时，要保持授权链的适用范围，防止用一个允许访问的根对象去读取不相关的私有对象。

### 14.4 同一内容多入口的权限不能靠单个开关收紧

系统尽量检测当前用户可管理范围内的其他公开路径和匿名授权。已有公开数据再创建带密码入口，只能保护新入口；不能把新对象包装或改个 Metadata 当作已经收回旧数据的证明。

同样，多个分享引用同一对象时，撤销其中一个只能移除该入口的授权。全局把对象一刀切成不可读，会误伤其他合法分享；仅删入口却保留一个绕过授权的裸数据 URL，也是假撤销。

### 14.5 浏览器与服务隔离

用户发布的 HTML、公共预览和应用服务不能获得系统控制台的身份凭证。独立子域名只是部署隔离的一部分，还要限制凭证作用域、跨来源访问、嵌入关系及应用访问系统 API 的权限。不能把同站点关系当作同源关系。[^origin]

系统保留认证、控制台、管理接口等名称，不允许普通部署抢占。上线实例使用自己的权限与数据边界，不能因用户选择“公开访问”就顺便公开管理端、调试端口或后台密钥。

### 14.6 分享对象与外部 URL 的安全检查

系统只向被用户选中的目标交付数据，不为了推荐目标就预先把内容传给全部注册应用。外部目标抓取 URL 时，必须防止它借本机网络位置或登录凭证读取并转发受限资源；重定向后的目标也需检查。W3C Web Share 的安全说明明确讨论了这类机密信息泄露风险。[^web-share]

预览封面、远程图片、购买网关等外部资源同样不能成为探测内网或转发账户凭证的通道。

### 14.7 发布前检查的范围与限度

系统或 Jarvis 可以发现常见密钥文件、环境变量、可疑目录和缺失依赖。检查结果称为“发现的问题与建议”，不称为“已保证无任何敏感信息”。

用户必须能查看将公开或交付给应用的实际范围。权限限制来自系统可执行策略，而不是只要求 Agent 在提示词里“不要泄露”。

<a id="s15"></a>
## 15. 高级用户、Jarvis 与自动化

### 15.1 快速，但不省略真正改变结果的决策

高级用户可固定常用动作、保存发布预设、记住默认收录者、使用快捷键或命令面板直接进入指定流程。预设明确包含快照方式、访问范围、入口类型和运行目标，并在执行前显示摘要。

允许取消重复解释，不取消关键事实显示。用户即使跳过向导，也应能从结果知道本次到底是文件分享、内容发行还是部署实例。

### 15.2 人和 Agent 共用同一套系统能力

Jarvis 不通过模拟点击才能发布。GUI、CLI、SDK 与 Agent 使用相同的准备、授权、执行、结果及管理语义，产生可追踪的结果标识。

建议的调用阶段为：

```text
分析输入与意图
    → 准备操作计划与预检结果
    → 检查已有授权；必要时请求用户确认
    → 执行具体动作
    → 返回可查询任务与结构化结果
    → 在统一管理中心继续管理
```

这里描述的是拟议契约，不是已经存在的命令名称。

### 15.3 Jarvis 的确认摘要

当用户说“把这个小游戏上线，发链接给朋友”时，确认摘要应接近：

> 将它作为应用服务运行在你的 BuckyOS，地址为建议的站点名称。任何拿到链接的人都可以打开；需要一个应用数据目录和网络访问权限。不会公开源码或 PIKG。是否按这个方案上线？

若用户已经在当前任务明确批准这些范围，或配置了匹配的持续授权，可直接执行并回报，不重复询问相同决定。公开范围更大、运行位置改变、权限增加或产生费用时必须重新获得授权。

### 15.4 明确区分四种自动化意图

| 意图 | Agent 可以做的事 | 不得自动连带做的事 |
| --- | --- | --- |
| 发给某人 | 调用指定目标，提交明确内容 | 公开到 Public、发到其他平台 |
| 创建分享链接 | 按批准的访问策略创建入口 | 注册 BNS、投递商店 |
| 发布内容 | 准备版本、提供内容、执行已选渠道 | 自动收费或购买一级名称 |
| 上线服务 | 包装 PIKG、安装与调度、生成地址 | 对外发行源码、镜像或应用包 |

Agent 不确定用户的“发布”究竟意味着什么时，应利用当前项目和目标结果解释选择：“是让别人直接打开使用，还是提供安装包给别人安装？”这是产品内的意图确认规则，不要求用户学习 Share／Publish／Deploy 英文术语。

### 15.5 自动化授权与持久任务

建议把公开能力、应用外发能力、安装运行能力、敏感权限与付款能力分别授权。授权应限定对象或工作区、目标 Zone、接收目标、资源上限和适用期限，不采用一个永久有效的“Agent 可以做所有事情”。

大文件对象化、镜像下载、安装、收录等使用可持久查询的系统任务。用户关闭页面、Agent Session 结束或进程重启后，任务状态仍可恢复；系统任务继续运行是产品能力，不依赖对话持续存活。

需要人工处理时，在任务上保留明确待办和上下文。最终交付既包括链接，也包括访问范围、可用性证据、管理入口及尚未完成事项，不能只说“搞定了”。

<a id="s16"></a>
## 16. namedstore 空间管理与清理

### 16.1 把“存储为什么增长”翻译成用户能理解的类别

“存储空间”页面区分已发布内容、分享保留副本、正在运行的应用、可回退版本、下载缓存、失败任务临时文件及其他数据。用户无需先知道 GC 是什么。

发布或安装前尽可能展示新增占用和执行期间的峰值需求；无法精确计算时给出范围和依据，不把包文件大小当作全部运行占用。Docker 拉取、解包、构建暂存与应用数据应分别考虑。

### 16.2 明确哪些对象不能自动清理

| 引用来源 | 保留规则建议 |
| --- | --- |
| 正在生效的分享链接 | 保留其依赖内容，停止或到期后解除该条保留 |
| 独立发布的版本 | 保留所有仍承诺提供的版本，不因长期入口升级就自动删旧版本 |
| 上线实例与持久化数据 | 运行所需内容保留；应用数据另按数据生命周期管理 |
| 明确保留的回退版本 | 按用户设置保留，删除前解释将失去回退能力 |
| 尚未完成的任务 | 任务有效期间保留，取消后的清理由引用检查决定 |
| 付费内容提供承诺 | 单独检查交付义务和用户设置，不能按普通缓存自动删除 |
| 其他应用或系统引用 | 由实际引用关系决定，不能仅看当前管理列表是否可见 |

namedstore 中的逻辑引用与真实文件占用要区分。多个 PIKG 复用相同数据时，不把包的标称大小简单相加为可释放空间。

### 16.3 临时 PIKG 的产品规则

用于本地上线的包装 PIKG 标记为“本地部署产物”，默认不公开、不投递。失败重试尽量复用已确认的对象和镜像，避免每次只修改部署参数就无意义地重新嵌入全部大文件。

能否分离运行配置、镜像引用与包身份，需要核对当前 PIKG 格式。即使暂时无法优化格式，也必须提供占用说明与安全清理入口，而不是把空间问题完全交给命令行。

### 16.4 最小可用清理界面

第一期至少提供“查看占用”“检查可清理内容”“清理失败任务临时数据”，并展示会影响哪些分享、发布、实例和回退能力。

默认安全清理只处理没有有效保留或依赖的对象。候选列表可先试算，执行前再次检查引用，防止预览之后新增引用却仍被删除。真实释放空间以 GC 结果为准，不以条目从列表消失为准。

取消任务后可回收的空间、解除引用后待回收的空间、已经释放的空间分别显示。没有可靠依赖检查的对象宁可暂不自动清理，也不误删仍在提供服务的数据。

<a id="s17"></a>
## 17. 系统能力与应用接入契约

### 17.1 复用现有系统，不再建设一套孤立发布平台

| 能力 | 建议责任 |
| --- | --- |
| 系统分享面板 | 统一入口、目标筛选、上下文推荐及授权展示 |
| 分享结果与管理聚合 | 稳定结果标识、分类视图、状态同步、能力化操作 |
| namedstore | 对象、数据、依赖与保留关系；不以“存在”代替“公开” |
| NDN 提供与 Gateway | 解析访问入口、执行数据访问策略、提供内容或路由服务 |
| 命名能力 | Zone 逻辑入口与 BNS 的各自绑定、解析及状态 |
| 内容收录接口 | 投递、查询、收录与下架请求的结果契约 |
| 安装与调度 | PIKG、Static Web、Docker／Script Host 实例生命周期 |
| 通用任务与通知 | 长任务、恢复、待确认事项及结果提醒 |
| 凭证与购买能力 | 订单恢复、收据保存、链上购买验证及授权使用 |

以上是责任划分，不要求新增同等数量的独立进程。优先扩展已有服务，避免 File Browser、系统面板和 Jarvis 各写一套。

### 17.2 分享目标注册

注册描述至少提供：目标身份、可接收的内容类型、单项或多项能力、输入上限、交互入口、是否会把内容发送到外部服务、结果回传能力及后续管理能力。

调用方可指定“仅本应用”“指定目标”或“系统选择”。可见目标必须满足用户权限与内容兼容性。推荐或置顶不能越过系统筛选，也不能让应用伪装成内置系统操作。

与本次内容不兼容的应用不占用默认列表；高级“查看所有目标”可以展示不可用原因。未安装目标不作为可直接执行的分享选项，更不能点击后自动安装并上传数据。

### 17.3 内容交付与操作计划

以下字段名称用于说明拟议的接口语义，不是现有 SDK 定义：

```text
OperationPlan
  intent                  share_to_app / create_share_link /
                          publish_content / deploy_instance
  input_ref               文件、目录、对象、项目、镜像或实例引用
  input_revision          本次确认的内容修订或快照
  target                  目标应用、发布位置或目标 Zone
  access_policy           访问范围与限制
  update_policy           固定版本、手动发布新版或 Public 路径行为
  required_permissions    本次需要的能力
  expected_results        预期输出及其含义
  resource_estimate       存储与运行需求，允许标记未知项
  warnings                阻止项与需确认风险
  idempotency_key         重试去重依据
```

计划不是授权本身。提交时需确认输入版本、目标和权限仍与计划一致；需要变更时生成新计划或明确提示差异。

### 17.4 结果回传契约

```text
OperationResult
  operation_id            本次流程的稳定标识
  task_state              进行中、待确认、已完成、失败、结果未知等
  result_refs[]           一次流程可以形成多个持久结果
  delivery_state          是否仅交接、目标是否确认业务完成
  availability            提供状态及检测范围、时间、证据
  links[]                 每个链接包含用途、访问策略与当前状态
  management_actions[]    当前主体可以执行的管理操作
  remaining_steps[]       收录、名称确认等尚未完成事项
```

`links` 允许为空。应用发出一条消息可以有结果引用而没有公共 URL。即使同一个 URL 用于多个客户端，也应保留它属于预览、固定版本、长期入口、数据流还是服务地址的明确类型。

### 17.5 流程记录与持久结果不是同一条对象

一个操作可以产生多个结果；同一结果又会经历修改权限、发布新版本、下线等多次操作。建议分别保留：

| 对象 | 作用 |
| --- | --- |
| 操作记录 | 谁以什么意图发起了什么任务，当前执行到哪一步 |
| 结果记录 | 一个可持续管理的分享入口、发布关系或上线实例 |
| 内容版本 | 由 Object ID 标识的不可变对象及依赖 |
| 名称／入口绑定 | 长期名称当前引用哪个版本或实例 |
| 授权与保留关系 | 谁能读取，以及为何不能被 GC |
| 外部结果投影 | 外部应用或收录者最后确认的事实与时间 |

统一管理中心读取这些关系的聚合视图，具体执行仍调用对应权威服务。Public 条目可以通过现状观察重建；历史动作没有证据时只能标为未知。

### 17.6 管理能力按实际支持展示

目标应用声明并实际提供 `查看结果、查询状态、修改期限、撤销、删除、打开管理页` 等能力中的哪些，系统才展示对应操作。第三方自定义页面只能在授权范围内处理自己的结果，不能改写整个系统的分享记录。

回调必须可验证来源、关联原操作，并防重复、过期和越权。仅返回“成功”而没有业务结果语义的应用，不能获得最高级别的“已完成且可管理”状态。

<a id="s18"></a>
## 18. 状态、失败恢复与一致性

### 18.1 不用一个状态同时表达所有事实

每个结果至少有执行状态、可用状态及访问策略；涉及外部渠道时另有渠道状态，涉及支付时另有交易状态。前端可以简化展示，但后台不能把它们压成一个布尔值 `published=true`。

| 维度 | 典型状态 | 由谁确认 |
| --- | --- | --- |
| 执行 | 草稿、准备中、待确认、执行中、完成、失败、取消、结果未知 | 通用任务与具体执行服务 |
| 内容可用性 | 未提供、本 Zone 已提供、提供方暂不可用、对象不完整 | namedstore／NDN 提供方 |
| 入口可用性 | 已保留、路由就绪、外部已验证、外部未验证 | 命名与 Gateway 检查 |
| 分享交付 | 已交给目标、目标确认完成、结果未确认 | 目标应用回传 |
| 商店 | 已投递、已识别、已收录、已上架、拒绝、下架处理中 | 对应收录者 |
| 交易 | 待支付、确认中、已有资格、凭证恢复中 | 支付网关或合约验证能力 |

状态附带更新时间及必要的证据来源。不能把昨天成功的外部探测一直显示成“此刻已确认任何人可访问”。

### 18.2 标准提交顺序

普通内容发布建议采用以下提交逻辑：

```text
固定输入快照与对象身份
    → 准备数据和依赖
    → 建立保留关系及访问策略
    → 验证当前提供方能读取
    → 提交可用的发布关系
    → 切换长期入口（有该入口时）
    → 更新结果状态
    → 分别执行后续渠道投递
```

不先把长期入口切到一个尚不存在的对象。任何关键步骤失败，已有正式版本继续工作。渠道投递和外部收录不能被当成本地原子事务的一部分。

### 18.3 失败恢复矩阵

| 情况 | 用户看到什么 | 恢复方式 |
| --- | --- | --- |
| Metadata 不完整 | 指出缺少哪些必需项 | 保留已填内容，原位补齐 |
| 计算期间源文件变化 | 源内容已变，当前版本尚未确定 | 使用已形成的一致快照或重新准备 |
| namedstore 空间不足 | 显示缺口、可清理类别和原版本状态 | 清理后续传；不先创建假可用链接 |
| 名称冲突 | 内容版本已准备，名称尚不可用 | 改名或选择已有受控名称，不重复对象化 |
| 链上名称交易待确认 | 对象可保留，名称状态待确认 | 查询原交易；不重复付费 |
| 部分商店失败 | 本地已发布，具体渠道失败 | 仅重试失败渠道 |
| 应用安装成功但路由失败 | 应用已安装，入口未就绪 | 修复路由，不重复安装或申请更高权限 |
| 服务更新失败 | 新版本失败，旧版本仍在运行 | 查看原因，重试或放弃新版本 |
| 外部分享回调超时 | 已交给应用，最终结果未确认 | 先查询目标；用户明确选择后才重新发送 |
| 支付成功但凭证缺失 | 已发现付款，正在恢复授权 | 查原订单并补领，不再次收款 |
| 用户关闭界面 | 在管理中心保留进行中的任务 | 重新打开续接，而不是重复提交 |
| 用户取消 | 已停止的步骤与不可撤销步骤分别显示 | 清理本机临时产物；外部已发送结果另行处理 |

### 18.4 幂等与重复点击

同一次提交、网络重试、页面恢复必须复用操作标识。生成两个独立分享或向同一个人有意发送两次，则是两个明确的新操作，不能只用 Object ID 作为全部操作的去重键。

外部发送或付款结果未知时，不盲目自动重试。对已经发生的名称交易、付费、消息发送，只能查询、恢复或按外部规则发起后续处理，不能显示“本地取消，所以全都撤销”。

### 18.5 多人或多端更新

长期入口和上线实例的版本切换需检查当前修订，避免两个客户端同时发布时后到的旧状态覆盖新状态。冲突提示“已有其他更新”，展示当前版本并允许重新选择，不静默覆盖。

GUI、CLI 和 Agent 更新同一结果时，操作历史分别记录真实操作者、发起方式与时间。管理中心定期校准权威状态，不能依赖某次 UI 回调永远正确。

### 19.1 页面清单

| 页面标识 | 页面 | 必须展示 | 主要行为 |

| UI-01 | 通用分享面板 | 内容摘要、已有结果、兼容目标、推荐动作 | 选择明确的后续动作，不产生公开副作用 |
| UI-02 | 分享链接配置 | 快照语义、访问范围、期限、可选密码 | 提交创建，或管理已存在链接 |

| UI-05 | 上线配置 | 目标 Zone、地址、权限、资源和运行方式 | 提交部署，不混入软件发行 |
| UI-06 | 通用进度／结果 | 实际阶段、主入口、未完成项及管理入口 | 复制、继续、诊断、进入管理 |
| UI-07 | 分享与发布中心 | 类型化列表、筛选、范围与状态 | 进行与结果类型相符的管理 |
| UI-08 | 发布或实例详情 | 版本、入口、授权、依赖、操作历史 | 更新、撤销、下线或查看引用 |
| UI-09 | 作品发行与购买 | 名称、商店、销售者、版本及授权条款 | 独立执行投递、命名或用户确认的购买 |
| UI-10 | 存储空间 | 占用类别、引用原因、可清理结果 | 试算与安全清理 |

桌面端可以使用侧栏或对话框，窄屏采用完整页面或底部面板。布局可以不同，但字段含义、确认边界与主动作保持一致。

### 19.2 文案对照

| 不采用的文案 | 推荐文案 | 原因 |
| --- | --- | --- |
| 永久分享 | 不自动到期 | 不承诺设备、数据和权限永远不变 |
| 发布成功（仅生成 ID） | 版本标识已生成，内容尚未对外提供 | 分清身份与可用性 |
| 已分享（仅交接给 App） | 已交给该应用，后续结果未确认 | 不虚构发送结果 |
| 已上架（仅投递成功） | 已通知商店，正在等待处理 | 不虚构收录或审核完成 |
| 发布应用 | 在我的 BuckyOS 上线／发布软件包 | 区分运行实例与对外发行 |
| 删除 | 停止此分享／下线／卸载／清理空间 | 说明实际影响 |
| 链接永久不变 | 此版本标识固定；访问依赖内容提供状态 | 分清标识与持续交付 |
| 复制链接（未准备好） | 复制版本引用 · 尚不可访问 | 保留高级能力但不误导普通用户 |
| 受密码保护（存在匿名直达入口） | 此入口需要密码；内容另有公开入口 | 不把入口保护冒充内容保密 |
| 已获版权认证 | 已确认名称控制／已登记链上交易 | 只表达系统真正验证的事实 |

### 19.3 无障碍与操作一致性

所有操作支持键盘导航，焦点进入对话框后位于标题或首个可操作字段，关闭后回到原入口。错误提示与对应字段关联，进度变化有可读取的文字，不只依赖颜色、图标或动画。

复制按钮提供明确反馈，长 Object ID 不截断复制内容。风险说明必须在执行前可见，不能只放进悬浮提示。链接性质用文本标记，不能要求用户凭链条图标判断是版本地址还是服务地址。

### 19.4 新手帮助与高级信息

默认只解释当前决定的后果，例如“修改原文件不会影响这次分享”。不在每次分享时讲解 NDN、BNS 或对象哈希。

高级详情使用精确术语，并支持查看 Object ID、实际对象类型、数据提供方、作用中的授权关系和引用来源。可读说明与技术字段一一对应，不维护两套含义不同的界面。

### 19.5 未启用能力的呈现

未支持的内容类型、无法执行的权限策略、尚未上线的交易网络不展示一个可以点到最后才失败的完整流程。普通入口隐藏无关能力；用户有明确需求或进入高级页面时，显示未开放原因、现有替代路径及其限制。

例如，受控 NDN 访问尚未完成时，不能自动改为匿名公开作为替代；链上交易未上线时，不能把测试网当作正式购买入口。

## 20. 典型场景端到端验收

### 20.1 普通用户场景

**场景 A：把 PDF 发给朋友，七天后失效。** 用户在 File Browser 点分享，创建默认分享链接并复制。朋友能在允许范围内打开；原文件移动不影响快照；到期后该入口不能继续提供。用户在统一管理中心能提前停止，也能看到其他有效分享不受影响。

**场景 B：报告不断更新，但朋友只保存一个入口。** 用户选择发布内容，获得长期入口。改动源文件后旧发布不变；点击发布新版并确认后，长期入口切换，新旧版本引用各自明确。

**场景 C：让 Jarvis 写一个朋友可以一起玩的小游戏。** 系统识别有后端，准备本地 PIKG，解释运行位置、资源和访问范围。上线后提供实例地址，不发行源码；朋友访问范围经确认，匿名或登录访问的实际结果与配置一致。

**场景 D：只想运行网上找到的 Docker。** 用户选择上线服务，不需要应用商店或 BNS。Jarvis 补齐必要描述，系统预检权限和空间。失败后可以重试或清理临时产物，不让普通用户只能去命令行执行 GC。

### 20.2 高级与创作者场景

**场景 E：离线准备一个固定对象引用。** 用户选择精确内容类型与 Metadata，本地生成对象标识，提前复制。系统标记未对外提供。联网继续后使用相同对象，除非用户明确修改了参与对象身份的数据。

**场景 F：命令行把 HTML 放进 Public。** 无需图形向导；经过相应权限及完整性处理后提供路径和对象信息；统一管理中心自动发现并标记来源，不编造历史操作。删除软链接不删源文件。

**场景 G：发布一首收费音乐，并提供免费小样。** 小样和完整版使用独立对象。免费描述可读取，完整版与底层数据均受控。消费者进入明确的购买流程，成功后恢复凭证；支付完成但数据不可用时不要求重复购买。

**场景 H：同一个 PIKG 同时用于自用和发行。** 自用实例和对外发行是两个独立结果。撤回发行不自动下线实例，下线实例不导致商店条目被撤销。

### 20.4 体验与效率目标

建议以如下目标开展原型验证，不把目标数值写成已经实现的性能：

| 维度 | 建议目标／验证方法 |
| --- | --- |
| 普通分享路径 | 打开分享面板后，接受默认设置至复制链接不超过三次主要操作；不计数据准备等待 |
| 高级直达 | 固定动作可跳过通用选择页；不重新填写已明确且仍有效的 Metadata |
| 模态阻塞 | 大文件准备、安装与投递不要求用户一直留在对话框 |
| 行为理解 | 测试者能正确说明谁可访问、源文件修改影响、链接是否跟随版本以及如何停止 |
| 结果诚实 | 离线、交接未确认、收录处理中与外网未验证场景不出现虚假完整成功 |
| 默认路由 | 以真实用户任务测试是否选错“分享文件”与“上线使用”；记录误选及返回原因 |
| 数据安全 | 受控内容的旁路读取和授权扩大用例必须全部通过，不能用体验评分抵消 |
| 生命周期安全 | 清理、撤销及升级不能误伤其他有效结果，失败后可恢复到可说明的状态 |

核心评估不是按钮数量，而是用户能否一次得到想要的结果，并且之后不会因为误解链接或生命周期而出错。

## 21. 实施顺序与上线门槛

### 21.1 第一阶段：日常分享与可用上线

交付通用分享面板、内置分享目标、分享链接配置与结果跟踪、统一管理中心基础视图、Public 现状可见性、现有上线能力的统一入口，以及最小存储预检和安全清理。

普通用户应能完成“发一个文件”和“让一个网站／服务用起来”，并且能够找到、停止和管理结果。针对实际已支持的对象类型提供能力，不为凑齐界面而暴露尚无实现的选项。

**第一阶段硬门槛：** 新建受控分享的所有读取路径确实受控；上线不隐含发行；服务状态与访问范围不误报；任务可查询；取消与清理不破坏其他结果。对应重点用例为 A01—A11、A20—A31、A39—A42，以及适用的旁路访问检查。

### 21.2 第二阶段：完整内容发布与版本管理

交付对象类型自动选择、Metadata 表单、离线版本准备、独立发布保留关系、长期入口与固定版本双链接、版本更新、收录者投递与状态，以及与 Public、File Browser 和已上线实例的关系管理。

优先把免费内容发布闭环做完整，再增加丰富的内容类型与收录者。Static Web 轻量 PIKG 方案若尚需适配，在这一阶段统一契约，过渡期通过适配层保持用户动作一致。

**第二阶段硬门槛：** Metadata 与 ID 一致；新版本失败不切坏原入口；去重不泄露隐私；收录状态可核验；命名与存储不会产生管理孤岛。重点覆盖 A12—A24。

### 21.3 第三阶段：作品命名与可验证交易

接入 BNS 名称、销售登记、试看关联、402 扩展、签名收据或合约购买、凭证恢复及交易风险提示。测试环境与正式环境明确隔离。

不要求等待完整信用体系才能继续做免费分享和上线；但真实收费必须达到支付入口校验、购买证明、失败恢复、数据授权与交付诊断的最低要求。正式链或合约不可用时，只开放明确标识的测试演示。重点覆盖 A32—A38。

已有网盘分享链接尽量保持可用，不改变用户已经发出去的地址和既有期限。新旧记录通过适配进入同一管理视图；无法撤销或同步的旧条目明确标注其管理方式。

## 22. 待核实参数与决策边界

本方案已经给出产品方向，不把所有关键决定退回“待讨论”。以下内容属于仍需代码、协议或运行环境确认的实现参数；不能凭口述猜测后固化进界面。

| 待核实项 | 本方案已经确定的产品行为 | 未确认时的处理 |
| --- | --- | --- |
| 单 Chunk 上限、Chunk List 条件 | 普通用户自动选型，高级用户可查看真实类型 | 由底层能力返回；不写死 32 MB 或 64 MB |
| NDN URL 与对象描述／数据流路由 | 每个链接标明用途，前端不把 Object ID 当任意可播放 URL | 通过解析能力生成，不在 UI 自行拼协议路径 |
| Reference Path 与对象授权实现 | 私有对象不能只凭 ID 读取，授权应覆盖依赖 | 未达成时不开放会被绕过的权限或付费选项 |
| Public 写入完成及快照机制 | 不把半成品当完整发布，保留文件操作入口 | 根据 Gateway 与文件系统能力确定安全提交方式 |
| Static Web 的现有安装契约 | 普通用户得到受管理的独立站点 | 优先适配，轻量 PIKG 作为建议统一方向 |
| PIKG 与 Docker 数据复用能力 | 本地包装不发行，空间可解释且可清理 | 以实际占用显示，不能承诺未实现的零重复存储 |
| BNS 字符规则、费用、一级名取得方式 | 默认用自己的名称；付费前显示权威报价 | 离线不确认占用，不用未核实的八字符边界收费 |
| BNS 二级名称销售登记及反查 | 名称绑定与可购买状态分开 | 查询能力不足时显示未就绪，不显示已经上架 |
| 402 扩展与收据格式 | 必须绑定内容、销售者、购买者和授权范围 | 未实现端到端验证前不启用真实购买 |
| 合约网络、资产、确认与恢复 | 显示明确环境和交易状态，不重复购买 | 正式条件未具备时仅开放显著标识的测试流程 |
| namedstore 依赖与 GC | 活跃分享、发布和实例不能被误清理 | 不具备可靠证明的候选不进入自动清理 |
| 旧 NDN 公开范围 | 新内容授权明确，旧入口迁移透明 | 有影响的变更须明确告知，不伪造完整历史 |

本方案暂不规定 CLI 的具体命令名、SDK 的正式函数名、合约地址或最终 Object Schema。这些应在产品动作与状态语义通过评审后，对照现有实现确定，避免本文另造一套冲突 API。

## 23. 评审摘要与参考依据

### 23.1 普通用户最终看到什么

他在需要把东西给别人时点击“分享”。分享文件就创建链接或选一个应用；要持续维护内容就选择“发布内容”；要让一个网站或小游戏可以打开使用，就选择“上线”。系统说明结果，不要求他先学习协议。

完成后，他知道哪个链接应该复制、朋友是否能打开、以后修改会不会生效、到哪里停止。失败时也知道完成了哪一部分，不被一个笼统的“成功”误导。

### 23.2 高级用户最终得到什么

他可以直接选 Object ID、固定版本、长期入口、Public 路径或上线实例，能够看到真正的对象类型、运行目标、权限、引用与状态。CLI、SDK、Jarvis 和 UI 语义一致，可以复用预设、跳过无关步骤，但不会偷偷改变对象身份或授权范围。

### 23.3 本方案的取舍

**入口可以合并，动作必须明确；界面可以简化，结果不能含糊；流程可以自动化，公开、运行、付款与删除的权限不能合并。**

本方案优先实现三条独立但衔接顺畅的闭环：

| 闭环 | 完成标准 |
| --- | --- |
| 分享闭环 | 内容交付给明确目标，结果有交代，能执行支持的后续管理 |
| 发布闭环 | 对象版本确定，数据实际提供，长期入口与渠道状态可分别管理 |
| 上线闭环 | 产物在指定 Zone 以合适方式运行或提供，访问范围明确，能更新与下线 |

三条闭环可以连续发生，但不自动捆绑。例如“写代码→上线→分享地址”是一次组合任务；“生成 PIKG→保存到 namedstore”本身并不等于已经发行或公开。

### 23.4 参考依据与使用边界

本方案的业务背景和内部术语来自讨论记录；入口、默认值、权限方向、记录模型与分期为本方案建议。仅对涉及外部标准的少量边界作公开来源核对，没有核验 BuckyOS 代码、BNS 合约或线上服务，也没有开展真实用户可用性测试。
