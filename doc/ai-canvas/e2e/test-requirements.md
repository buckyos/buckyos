# AI Canvas E2E：把一份分析交给团队继续工作

## 1. 验收目标

团队用 Canvas 收集资料、借助 AI 形成分析、人工修订、交给别人复核并继续工作。E2E 要回答：
参与者能否完成这些目标，是否理解结果的依据，自己的内容会不会丢失，以及失败后能否安全继续。

本文以协作问题和可观察结果组织场景。发起者、协作者、审阅者是任务角色，同一个人可以在不同
时刻承担这些角色；它们不预设账号类型或权限模型。测试 Agent 是操作浏览器的执行者，产品
Agent 是 Canvas 调用的生成服务，两者在记录中分开命名。

[产品 PRD](../BuckyOS%20AI%20Canvas%20PRD.md) 决定产品承诺，
[原型 README](https://github.com/buckyos/buckyos/blob/9ff98e613dd3133b447175726b47e70300a32652/src/frame/desktop/src/app/canvas/README.md) 说明原型删除前的能力；本文场景作为历史需求保留，归档状态见 [入口说明](README.md)。已有判据完整保留在
[细粒度验收附录](assertions.md)，新增风险保留在 [覆盖缺口附录](coverage-gaps.md)。
场景提供组织方式，不放宽旧断言，也不把未来协作目标变成已冻结的内核设计。

## 2. 今天可以验证到哪里

| 层 | 可执行范围 | 不能由此推断的结论 |
|---|---|---|
| T-A 原型级 | 单人 UI、本地保存、Mock / 受控 HTTP、文件交接、同一存储中的双窗口竞争 | 真实模型质量、跨账号权限、在线共享、实时协作、服务端持久性 |
| T-B 内核契约级 | 待相关接口和语义冻结后，验证真实服务的文档、提交、权限等契约 | 当前不启动；本地拒绝冲突不等于分布式合并正确 |
| T-C 应用业务闭环级 | 待服务、真实身份和多节点就绪；行业角色和业务流程由应用仓库维护 | 当前不启动；通用 Canvas 测试不能代替业务授权验收 |

当前原型没有分享、实时协作、后台任务和交互块沙箱。T-A 可以让两个隔离浏览器先后扮演作者和
接收者，通过文件交接检查成果是否可用；这只证明文件交接。未来多人场景保留完整意图，缺失
的部分明确记为 NOT_RUN。组件位置、文案和布局变化不应改变下列目标与判据。

## 3. 七条协作场景

| 编号与名称 | 团队面对的问题 | 当前验证范围 |
|---|---|---|
| S01 · 从资料形成可信初稿 | 原始数据到分析结论之间容易失去依据 | T-A 可跑整理、显式选源、生成和数值核对 |
| S02 · 来源更新后保住人工修订 | 新数据与人工判断会互相覆盖或混淆 | T-A 可跑刷新、保护、分叉与撤销 |
| S03 · 把成果交给下一位参与者 | 作者能看到的内容，接收者未必能打开或复核 | T-A 可跑保存、重开、文件交接；在线共享待后续 |
| S04 · 共同编辑时分清改动归属 | 旧副本、异步结果或他人的操作可能覆盖当前工作 | T-A 可跑本地竞争；真正多人提交与合并待后续 |
| S05 · 只把必要信息交给合适对象 | AI 输入、导出和共享容易扩大信息范围 | T-A 可跑上下文和导出边界；真实访问控制待后续 |
| S06 · 中断后知道发生了什么并能继续 | 失败、取消、离线和迟到结果让人误以为工作已完成 | T-A 可跑故障恢复及保存状态真实性 |
| S07 · 让别人能看懂并完成复核 | 内容存在，不代表不同参与者能找到、理解和操作 | T-A 可跑讲述、导航、键盘、焦点和性能；远程跟随待后续 |

### S01 · 从资料形成可信初稿

**问题与思路。** 发起者整理团队资料，并请产品 Agent 生成初稿。系统应让来源选择可见、处理过程
可理解，结果与依据能对上。把不相关资料放在同一工作区，不应让它们自动变成输入。

**用户旅程。** 创建工作空间，导入或粘贴资料，检查数据含义；选择用于本次分析的范围并表达目标；
运行后查看进度、结果和来源，再用预先独立计算的事实核对关键指标。换一种导入入口属于变体，
不是换一套业务需求。

**完成证据。** 导入值与原始资料一致；实际请求只含明确选择的来源；结果结构满足所选 PRD 流程，
指标和图表读数符合独立预期，运行状态与实际写入一致。Mock 通过只说明原型链路与展示行为，
不能证明真实模型的分析质量。输入追溯仍按既有补充判据验收。

### S02 · 来源更新后保住人工修订

**问题与思路。** 协作者在初稿上加入判断，随后原始资料更新。系统需要区分数据过期与人工修改，
让用户明确选择替换、保留副本或取消，并能撤销已经完成的修改。

**用户旅程。** 编辑生成内容，更新一处来源，查看哪些结果需要刷新；尝试取消刷新，再选择保留
人工版本并生成新结果；对新结果继续分析，核对依赖关系，撤销并重做一次生成。

**完成证据。** 只有相关结果过期；取消不改业务内容；人工版本按选择保留，失败不留下半份替换；
新旧结果和下游来源不串线；撤销范围对应用户操作。结果块、表格 AI 单元格、复制和快照恢复
仍按附录分入口验证，不能用一条顺利路径代表全部通过。

### S03 · 把成果交给下一位参与者

**问题与思路。** 审阅者需要接着作者的工作复核。系统应交付可以打开和解释的成果，说明内嵌数据、
外部依赖与保存边界；未知内容或不支持的格式应可理解地保留或拒绝。

**用户旅程。** 作者保存并重新打开成果，导出文件；接收者在独立浏览器导入，核对资料、人工内容、
生成结果和媒体，再编辑、保存并导出。补跑已载入页面断网、未知块、高版本及损坏文件变体。

**完成证据。** 双方业务内容和来源关系可核对，往返无静默丢失；接收者不需要作者浏览器的私有
状态或凭据才能使用承诺自包含的内容；不支持的部分有明确说明，失败不破坏已有文档。
在线分享、共同文档及访问撤销留到对应能力就绪，不能用文件交换替代验收。

### S04 · 共同编辑时分清改动归属

**问题与思路。** 两人或两个窗口从旧状态开始工作，AI 也可能稍后返回。系统必须避免静默覆盖，
让用户了解哪些修改生效、哪些冲突需要处理，以及自己的撤销会影响什么。

**用户旅程。** 从同一份内容分头编辑；在生成期间继续修改、切换文档或恢复快照；随后处理冲突，
核对双方修改和撤销结果。不同人编辑同一内容与无关内容都应纳入未来协作验收。

**完成证据。** T-A 检查迟到补丁不会写错文档、过期修订被拒绝、双窗口不会无声丢数据、撤销不
夹带独立操作。真正多用户的合并策略、改动归属和补偿规则待产品及内核契约明确后细化；没有
规则时记为规格待定，不让执行 Agent 自选一种策略并判通过。

### S05 · 只把必要信息交给合适对象

**问题与思路。** 发起者同时持有公共资料和未打算披露的内容。系统应使输入与交付范围符合明确
选择，并在未来权限发生变化时提供可理解的拒绝和恢复路径。

**用户旅程。** 用可识别的合成内容区分选中资料、范围外资料和模拟凭据；运行分析、查看诊断、
导出并交接，核对信息去了哪里。未来再由独立账号验证查看、编辑、分享及访问变化的效果。

**完成证据。** T-A 的请求、导出和诊断满足各自的数据边界；非可信内容不执行宿主代码。导出
完整文档与只发送选中上下文是不同契约，不能把前者误判为泄漏。真实权限、草稿与发布可见性、
撤销访问对在途操作及既有副本的影响均需另定策略，不宣称本地过滤已经实现这些能力。

### S06 · 中断后知道发生了什么并能继续

**问题与思路。** 参与者面对慢响应、取消、服务故障、断网或保存失败，需要知道什么已经完成，
还能安全重试什么。系统的状态应与数据事实一致，重试不应引入重复结果或丢失输入。

**用户旅程。** 先建立正常对照，再在明确时点引入一种故障；观察反馈，取消或重试，必要时切换
服务、离开再回来；检查旧任务迟到与新任务交错时的最终内容。

**完成证据。** 已有内容和 Prompt 保留，没有半成品、误写或重复提交；错误反馈对应真正失败的
阶段，保存成功必须有持久化事实支撑。受控 HTTP / 存储故障是 T-A 夹具，不冒充真实服务验收。
未命中故障注入点时不能把结果算成失败路径通过。

### S07 · 让别人能看懂并完成复核

**问题与思路。** 审阅者需要理解结论、定位依据并提出修改，不应依赖作者记住的按钮位置。系统
应支持清晰的讲述顺序、自由浏览、回到当前内容及可辨识的操作反馈。

**用户旅程。** 作者组织讲述顺序；审阅者播放、离开当前步骤查看来源、再返回；调整窗口和缩放，
通过键盘完成主要操作，并在大表、多块内容、弹窗及编辑状态间切换。

**完成证据。** 内容与目标对应，导航不改变业务数据；焦点、快捷键和手势不会误操作另一窗口或
编辑目标；非视觉状态可辨识，大数据下仍可操作。浏览器自动输入不能代表真实中文输入法，
自动扫描也不能代表全部辅助技术。当前讲述播放不证明未来远程跟随通过。

## 4. Agent 怎样执行这些场景

执行 Agent 读取任务目标、前置资料和验收标准，使用 Playwright 等浏览器工具，重复“观察当前
页面 → 选择能推进目标的操作 → 点击、输入或上传 → 观察结果 → 留证”。具体入口由当前 UI
决定；一次运行的点击轨迹记录在执行报告，固定坐标、CSS 类和按钮旧文案不写进场景合同。

可调整的是操作路径，不可调整的是数据、权限和结果判据。缺少入口要记录当时页面和寻找过程，
区分能力未实现、入口难发现与自动化定位失败；不得直接调用内部命令完成用户目标。
详见 [浏览器执行约定](execution-guide.md)。

## 5. 推进顺序与完成口径

先执行 **S01 可信初稿 → S02 人工修订 → S03 文件交接** 的 T-A 连续旅程，验证这种执行方法能
留下可复核证据。接着补 S04～S06 的本地冲突、隐私及故障分支，再展开 S07 和附录中的高风险
变体。每阶段结束先报告结果和限制，再继续；T-B / T-C 本轮不启动。

场景是组织单位，附录断言是判定单位。报告同时列出场景目标和实际覆盖的“编号 + 名称”；
一次顺利旅程不能替代 PRD 四组验收、15 条 TC 或全部边界。一个场景存在未执行的必要分支时，
只报告已经完成的子范围，不把整个场景记为 PASS。失败的旧记录继续保留，新版本复跑另建记录。

文档整理本身不产生测试结果；首条旅程的执行包保存在 Git 忽略的本地 `runs/`。
风险补充中的销售额核对只完成部分变体，当前范围见覆盖缺口附录；后续只按真实运行更新相应变体。
所有结果按 [附录 §8 八字段记录](assertions.md#8-结果记录与问题归属) 写入本地执行包，
问题先在本地记录，不自动创建 GitHub issue。追溯映射见 [附录 §9](assertions.md#9-协作场景与既有断言的映射)。
