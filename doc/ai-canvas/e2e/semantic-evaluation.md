# Canvas E2E：语义复核与新增协作场景

我们希望评估“同事拿到这个成果能否放心继续工作”，而不只检查按钮点完、页面没有报错。
Agent 仍通过 Playwright 等工具观察和操作当前界面；在初稿、修订和交接后，可把已有证据交给
Jev 做补充判断。测试设计描述人的目标和可观察结果，UI 改版只需调整当次操作路径。

## 分工与接入顺序

执行 Agent 负责观察、操作和留证；独立检查负责数值、数量、请求边界、持久化、撤销与原子性；
评估器判断文字和结构证据是否支持任务目标。Jev 不生成 CanvasPatch、不执行浏览器动作，
也不能从成功文案推断后台已保存。现有 FAIL 或证据不足不会被它的积极判断覆盖。

先用已有证据和正反对照校准评估器，再在浏览器流程的检查点进行旁路复核，最后才考虑把它的
建议用于选择后续动作。前两步始终由执行 Agent 或人工复核分歧；还未接入浏览器自动检查点。
当前 [测试工具](../../../test/canvas_e2e/README.md) 已能离线准备、调用与重放；真实准确性待验证。
这是 T-A 证据的辅助评估，不把原型提升为 T-B/T-C，也不代替真实多人权限和同步验收。

一次评估包含任务目标、冻结判据、独立检查的事实、最少必要的产物与用户可见状态、缺失证据。
保留出处和哈希用于复核；参考答案与构造标签留在本地评估表，不发给模型。截图仍由执行 Agent
复核，Jev 当前只处理文本或结构化输入，不能声称它检查了布局、遮挡或图片视觉质量。
接口类型与限制依据 [TypeSafe API](https://docs.typesafe.ai/api) 和
[OpenRouter Jev 文档](https://openrouter.ai/blog/tutorials/how-to-use-jev/)（2026-09-28 核对）。

## 值得补充的用户任务

以下是现有七条旅程的补充要求，不新增一套绑定按钮的用例编号。当前样本只校准“评估器能否
识别相反情况”，合成样本不代表对应 Canvas 流程已跑通。未来每个任务都应有正常、反例与
证据不足变体；UI 支持后仍需真正通过浏览器完成。

| 编号与名称 | 协作中要解决的问题 | 系统解决思路与成功证据 | 当前准备 |
|---|---|---|---|
| J01 完整兑现交付目标（S01） | 生成了很多内容，却少了同事明确要求的产物 | 将结果与原始目标对应；缺项明确说明。结构由程序检查，语义复核是否答非所问 | c01/c02 对比缺图表与结构齐全 |
| J02 缺少资料时诚实表达（S01/S07） | 接收者把默认值或猜测当事实，带入决策 | 区分已知、假设和无法计算；指出需补充的资料。假设与指标不能互相矛盾 | c03/c04/c09 比较确定百分数、未知值与等价措辞 |
| J03 保留分歧和人工判断（S02/S03） | 刷新后数字更新了，但作者的疑问、限制条件丢了 | 交接保留意见并区分新旧版本；接收者能复述未决项并继续修改 | c05/c06 仅覆盖意见与版本信息是否保留；接收者理解待跑 |
| J04 能证明的信息边界（S05） | “看起来只选了一份资料”被误当成没有泄露 | 真实请求与选择范围独立比对；缺失请求明确无法判定，资料里的指令不能改变评估规则 | c07/c08 边界证据；c10 仅评估器抗诱导对照 |
| J05 中断后的可靠交接（S06） | 同事看到“已保存”，实际上最新修改不可恢复 | 清楚标明未保存范围、可恢复版本和下一步；另用读回/重开证明持久化 | c11/c12 合成成功提示与存储事实的对照 |
| J06 多方意见不被悄悄合并（S04/S07） | 不同角色意见冲突，却被总结为所有人同意 | 保留各方归属、冲突和待确认决定；摘要不能把提议写成批准 | 待设计观察样本；真正共享编辑仍受 T-B 前置约束 |
| J07 结论可追溯且不过度推断（S01/S07） | 数值正确但趋势、因果或行动建议没有资料支持 | 区分观察和推断；无时间对照不声称增长，无因果证据不下因果结论；给出资料依据 | 待补时间范围、单位、缺失基期与相关性反例 |
| J08 接收者能独立完成下一步（S03/S07） | 成果可导入，但必须反复问作者才知道如何继续 | 隔离角色仅凭交付内容定位来源、解释限制、完成指定修改；保留其实际操作与复述 | 已有文件交接证据；“不依赖作者提示”盲交接待跑 |

J06 不因为能合成两段意见就算真实多人协作已实现。J04 的评估器抗诱导不能替代 Canvas 对生成
模型提示注入的验证。J02/J07 是本轮提出的结果可信度要求，应与产品约定后纳入正式判定；
现有风险可以记录，但不能据新标准追溯改写历史 PRD 验收。

## 判定与校准

每个问题只返回 `supported`（证据支持）、`contradicted`（证据反驳）或 `insufficient`（证据不足），
附原始概率分布。它们是语义判断，不直接等同于产品 PASS/FAIL。置信度不表示实际正确率，也
不能弥补缺少的证据；当前不设置通行阈值，所有结果旁路记录。

第一批 12 个样本包括四个真实观察摘要和八个合成/修改对照，参考标签由 Agent 起草，待人工
复核。请求不含参考标签；对照结果需分别报告漏检、误报、证据不足被误判为支持、配对一致性，
并回看证据。小样本共享上下文，既不是独立准确率基准，也不覆盖中文长文、截图和真正多人场景。
校准请求、响应和逐条结果写入 Git 忽略的本地 `runs/`；没有真实调用时记 NOT_RUN。

后续引入新的独立留出样本，覆盖中英文改写、资料顺序变化、长历史、多份矛盾资料、局部成功与
失败，以及模型版本变化。任何准备用作门禁的阈值都必须由这些数据评估误放代价后决定。
版本、判据、摘要方式变化需重新校准；禁止根据一次错误不断修改措辞直到“跑绿”。

## 流程接点与留证

初稿完成后检查 J01/J02/J07；刷新后检查 J03/J06；导出、导入与继续工作后检查 J03/J08；
取消、保存失败或恢复后检查 J05。J04 需要实际请求记录，只有 UI 引用时留下证据缺口。
这描述的是检查目标；入口位置、菜单名称和组件结构只存在于该次 Playwright 操作轨迹中。

每个检查点沿用八字段执行记录，附评估输入摘要、出处、判据版本、请求哈希、真实返回模型、
概率、时延、用量/费用及人工复核意见。网络/凭据/限流/响应格式问题属于评估器故障，Canvas
结果保持原状；没有真实调用记 NOT_RUN。历史结果与新一轮评估并存，不互相覆盖。

只发送经审核的最小测试证据。本轮资料为合成销售数据，不发送凭据、整个项目或真实业务文档。
凭据和临时结果在 `.work`；发布报告只取已脱敏证据。真实调用限定供应商、输入、次数和时间；
具体运行与费用边界见测试工具 README。接入 AICC 的网关、身份、计费等验证另行按 AICC 流程执行。
