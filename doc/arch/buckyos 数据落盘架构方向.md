# BuckyOS 数据落盘架构方向

> 整理日期：2026-10-25  
> 文档性质：架构方向讨论稿  
> 整理依据：本次关于系统数据、RDB、namedstore、非结构化存储、应用级 Bucket 和原生工具访问方式的五段口述。

## 一、背景与总体判断

BuckyOS 即将发布需要长期维护兼容性的正式版本。自这一版本起，后续覆盖安装和升级都必须认真处理旧版本的数据；系统的备份、恢复以及未来不同部署形态之间的数据迁移，也需要有稳定的架构基础。

当前 BuckyOS 主要运行在单节点 Desktop 环境中。应用数据通常位于本机的数据目录，结构化数据大量使用 SQLite。这使得开发和运维容易把“数据落盘”理解成“哪些文件放在哪些目录”。

但物理目录和 SQLite 文件只是当前实现的结果，不应成为长期的数据资源模型。需要先明确系统向应用提供哪些存储资源、应用通过什么接口使用这些资源、谁负责数据可靠性与生命周期，再决定这些资源在某个版本和部署环境中如何落盘。

**总体方向是：以操作系统管理的存储资源作为应用持久化的基础，而不是以应用自行维护的一组本地文件作为基础。**

具体而言：

- 系统引导和身份相关数据，主要分为 **System Config** 与 **Security** 两类，分别处理配置恢复与身份恢复问题。
- 系统服务和普通应用采用统一的数据资源抽象。结构化业务数据优先使用系统提供的 **RDB Instance**；对象本体保存在 **namedstore**，应用通过 ID 引用。
- 对从零开发的原生应用，非结构化数据优先直接进入 **Named Data** 体系，并考虑通过应用级 **S3-like Bucket** 归集和管理。
- **规划中的分布式文件系统 DCFS（下文统称 DFS）仍然保留**，主要承接传统应用兼容，以及用户明确依赖文件、文件夹的工作方式。
- 系统内置应用与原生工具的资源访问应当 **URL 化**，不能把本机文件路径作为唯一入口。

本文区分三种状态：已有实现与使用方式属于“现状”；口述中明确提出的原则属于“架构方向”；Bucket 的具体接口、引用管理、GC、兼容边界等尚未定案的内容属于“待设计事项”。

## 二、从物理目录转向资源抽象

### 2.1 当前落盘方式不等于长期接口

在当前 Desktop 版本中，应用通常使用一个普通的 Linux 数据目录。SQLite 数据库文件和其他应用文件可能都位于该目录下。某些单机硬件的目录背后也可能挂载存储池；未来集群环境中，同类目录则可能挂载到 DFS。

这些实现可以继续存在，但应用所依赖的长期能力不应全部等同于“这个目录可以写文件”。尤其是原生应用，应尽可能明确区分自己申请的数据库资源、保留的对象数据，以及确实需要文件系统语义的用户文件。

本文统一使用“应用数据目录”指代上述目录，不将口述转写中的具体路径拼写作为最终目录规范。

### 2.2 数据资源的总体划分

| 数据类别 | 逻辑形态 | 主要管理职责 |
| --- | --- | --- |
| 系统配置 | System Config，结构化 KV | 系统负责引导、配置读取及配置数据管理 |
| 安全与身份数据 | Security，当前主要为密钥等小文件 | 系统按身份、密钥类型及恢复场景处理 |
| 应用结构化业务数据 | RDB Instance | 系统管理实例与存储引擎，应用管理业务表结构和业务逻辑 |
| 命名对象本体 | Named Object / Object Body | namedstore 保存；应用及其他对象通过 Object ID 引用 |
| 非结构化内容 | Chunk；文件通过 File Object 组织 Chunk | 系统提供 Named Data 存储能力；拟以应用级 Bucket 表达保留范围 |
| 需要文件系统语义的数据 | 本地目录或 DFS 目录 | 系统提供文件访问与持久化能力，支持兼容应用和用户文件工作流 |

这里既有物理内容类型，也有对应用暴露的逻辑资源。Bucket、File Object 与 Chunk 不是三份互相独立的数据副本，而是不同层次的管理或引用概念；它们之间的具体映射仍需设计。

### 2.3 系统服务与普通应用采用相同模型

系统中的用户态服务与普通应用都通过 SDK 开发。它们的运行位置和部署方式可以不同，但从数据资源的申请和使用来看，没有必要建立两套互不相同的存储体系。

内核主要依赖 System Config 与 Security；进入系统服务和应用服务层后，应统一使用系统提供的存储资源。

存储引擎属于操作系统基础能力，与文件系统处于同一层级的架构位置。系统引导时首先建立配置基础，再依据配置拉起逻辑网关、存储引擎等设施。应用不应各自承担这些基础设施的启动和运维。

## 三、系统自身的数据：System Config 与 Security

### 3.1 System Config：系统配置不是文件目录抽象

System Config 是结构化 KV，数据模型类似于 etcd，而不是以目录和文件名为核心的普通文件结构。

系统的大部分核心配置位于这里。引导过程中，系统先建立 System Config 的访问能力，再根据其中的配置启动后续基础设施，包括逻辑网关和相应存储引擎。

因此，System Config 的持久化和恢复应围绕其逻辑配置数据展开。它底层是否使用某个文件或数据库，不应改变其对系统暴露的 KV 抽象。

### 3.2 Security：需要恢复判断，而不只是文件复制

Security 主要包含密钥等小型数据。单看数据形态，这些内容也可以放进 KV；当前出于兼容性等考虑，仍采用文件形式保存。

这部分不能简单当作普通应用用户数据处理。按照本次讨论，一部分重要密钥应当能够从用户持有的相应身份或密钥基础推导；另一些身份及其密钥，可能在重装时重新生成。

所以 Security 的核心问题并不是“有没有把文件备份下来”，而是：

**在当前恢复场景中，旧身份是否仍然成立，旧密钥是否应当继续使用，以及这些安全数据能否重新放回这个系统。**

由此，Security 既不能被默认排除在恢复考虑之外，也不能被默认整体复制回去。需要根据密钥类别和身份恢复语义单独确定策略。这部分尚未形成完整规则。

## 四、结构化业务数据：系统管理的 RDB Instance

### 4.1 坚持使用 RDB 作为主要结构化存储能力

BuckyOS 面向个人或企业内部集群，而不是以大型互联网平台的极端规模为默认前提。在这一规模判断下，常规 RDB 及其分布式实现应当能够满足可预见的大部分需求。

应用通过 Schema 申请自己的 RDB Instance，并原则上通过 BuckyOS SDK 的 RDB 接口操作数据。实际后端可以是当前 Desktop 使用的 SQLite，也可以是 PostgreSQL，或者未来更大规模部署中的其他 RDB，例如 TiDB。

具体选择由系统控制，而不是由应用把后端产品固化为自身的数据访问前提。SDK 的统一接口范围以及不同后端差异的处理方式，仍需进一步定义。

### 4.2 可靠性责任落在系统管理的实例上

应用负责业务数据的含义、表结构和业务操作；数据库底层的可靠性保障，由系统管理的 RDB Instance 及其存储引擎承担，不要求每个应用重复实现。

这里明确的是责任归属，不是认为使用某一种数据库就天然完成了所有可靠性工作。系统仍需掌握实例的实际后端和运行形态。

例如，系统应能够列出某个应用申请了哪些 RDB Instance，以及这些实例对应什么后端。在当前 SQLite 实现中，这通常体现为识别相应的数据库文件；这些文件目前一般位于应用数据目录中。使用 PostgreSQL 等后端时，则应在系统数据库管理或运维视图中识别对应的逻辑数据库资源。

**数据库实例不能仅因其落盘文件位于应用目录，就在系统管理层面变成一个不可识别的普通文件。**

### 4.3 提供权限受控、后端无关的 Dump / Restore

系统应提供统一的 RDB Dump / Restore 接口。拥有相应权限的主体，可以导出指定实例，并通过系统接口恢复。

导出结果的目标是与具体后端无关，而不只是提供某个数据库产品的原生文件副本。口述中的 CSV 是通用数据表示的例子，并不是已经确定的唯一格式。

最终导出包需要包含哪些信息、如何表达 Schema 与数据类型、如何处理不同后端之间的差异，属于后续格式设计。不能把“数据可以导出为 CSV”直接等同于“已经具备完整的跨后端恢复能力”。

从应用视角，长期依赖的是系统的实例和导入导出接口，而不是自行复制 SQLite 文件或调用某个后端专用的运维命令。

## 五、namedstore 中的结构化对象与引用完整性

### 5.1 RDB 保存引用，namedstore 保存对象本体

除 RDB 业务数据外，BuckyOS 还有自己的命名对象存储 namedstore。

它与 MongoDB 一类带查询和索引能力的文档数据库不是同一项能力，也不应与后文的 S3-like 数据接口混为一谈。当前并未原生引入 MongoDB 一类引擎；未来是否需要提供这类独立存储资源，可以根据应用需求另行讨论。

当前鼓励的应用模式是：RDB 保存业务关系和 Object ID，namedstore 保存对应的 Object Body。

以 Message Hub 的 Inbox 为例，应用保存 Message ID，再根据该 ID 从 namedstore 取回消息对象的结构化内容。

```text
应用的业务记录 / Inbox
        │
        ▼
RDB 中的 Message ID / Object ID
        │
        ▼
namedstore 中的 Object Body
        │
        └── 对象内部还可能引用其他 Object ID
```

### 5.2 只导出 RDB 不等于完整导出应用数据

当表中保存的是对象 ID 时，RDB 的 Dump 只保存了引用，不一定保存被引用的对象本体。对象内部又可能包含其他引用，因此完整备份不能止步于第一层对象。

严格的应用级导出，需要知道哪些字段是 Object ID，并追踪这些 ID 所指向的对象，以及对象内部进一步引用的内容。应用清楚自己的表结构，是识别这些业务引用的重要参与者。

本次讨论并未确定这一遍历最终由应用、SDK 还是系统统一执行；目前也尚未形成完整的应用级扫描和导出机制。

### 5.3 当前策略：整体备份结构化对象部分

当前采用的方式，是整体备份 namedstore 中的结构化对象部分，而不是为每个应用单独计算其全部引用范围。

这一做法基于结构化对象通常较小的判断。现阶段结构化对象的保留方式接近持续增长、很少删除；系统 GC 的主要精力放在非结构化数据上。

这是一项现状，不应被直接固化为底层设施长期“只增不减”的承诺。异常增长、失去引用的对象、对象归属不清等问题，都需要重新审视。

已有部分 GC 基础设施，但过去实际运行和验证不足。结构化对象的生命周期管理、应用级导出和跨对象引用完整性，仍然是本轮落盘架构需要继续解决的问题。

## 六、非结构化数据：原生应用优先使用 Named Data

### 6.1 重新定位 DFS，而不是取消 DFS

过去的默认共识是：系统给每个应用提供一个持久化数据目录，当前写入本地磁盘，未来把同一类目录挂到 DFS。应用只需把它当作普通 Linux 目录使用，不必关心背后是本地磁盘、存储池还是分布式文件系统。

这一模式有明确价值，尤其适合迁移已有 Docker 应用和兼容传统软件。

但本次讨论观察到，BuckyOS 当前不少应用已不是移植而来，而是在 AI 辅助开发下从零构建。数据上传、后续 API 处理、Agent 操作和最终消费，都有机会建立在系统自己的协议和 SDK 之上。

因此需要重新判断：对于这样的原生应用，传统文件系统是否仍然必须成为非结构化数据的中间层。

**本次明确提出的方向是：既然应用从头开发，能够不依赖文件系统保存非结构化数据，就尽量不依赖文件系统，直接使用 Named Data。**

这是一项原生开发的优先选择，不是禁止文件系统，也不是要求所有现有应用立即重写。

### 6.2 真正承载非结构化内容的是 Chunk

在 BuckyOS 的 Named Data 模型中，非结构化内容最终由 Chunk 承载。

File ID 指向一个 File Object。File Object 本身是 Named Object，其中通过 Chunk List 引用具体的 Chunk。应用可以在 RDB 中保存 File ID，也可以在合适的场景直接保存 Chunk ID。

```text
应用 RDB
   ├── File ID
   │      └── File Object（Named Object）
   │              └── Chunk List
   │                     ├── Chunk ID → Chunk 内容
   │                     └── Chunk ID → Chunk 内容
   │
   └── Chunk ID → Chunk 内容
```

因此，“文件”在这一模型中并不要求先成为某个本地目录中的文件。应用可以通过对象和内容 ID 直接引用、获取和处理数据。

同时必须保持区分：File Object 是结构化描述，Chunk 是实际非结构化内容。文件可恢复，需要相关描述和内容都满足恢复要求，不能只保存其中一部分。

### 6.3 在 namedstore 之上引入应用级 Bucket

> 2026-10-25 补注：本节及 §6.4–§6.6、§10.4 中 Bucket 相关的待设计事项，已在 [应用对象桶 Bucket 设计](./应用对象桶%20Bucket%20设计.md) 中收敛为设计稿（v0.4，设计定稿）。

只有底层 Object ID 和 Chunk ID，还不足以让应用方便地管理自己需要保留的全部非结构化数据。

本次提出的方案方向，是在 namedstore 之上提供类似 S3 的应用级数据接口，并考虑 S3 兼容性。应用在管理自己的 RDB 数据时，也拥有类似 Bucket 的逻辑资源，用来归集它认为应该保留的非结构化内容。

```text
应用
   ├── RDB Instance：业务结构、业务关系和数据引用
   └── 应用级 Bucket：该应用希望保留的非结构化数据集合
                              │
                              ▼
                       Named Data / namedstore
```

这里应同时区分两个侧面：数据面负责数据的上传和访问；控制面负责应用归集、用量统计以及与缓存管理的关联。

Bucket 是应用表达数据保留范围的拟议管理边界，不意味着相同内容必须为每个应用复制一份，也尚未确定它与底层对象、Chunk 的具体对应方式。一个应用可以申请多少个 Bucket、是否完整兼容 S3、如何命名和授权，均未定案。

### 6.4 应用数据量应当容易计算和展示

应用级 Bucket 最直接的用户体验价值，是系统可以更容易回答：某个应用希望保留多少非结构化数据，以及最近新增了多少。

初始统计口径可以按“这些数据都由该应用独占”来理解，计算它所声明保留的数据规模。这样，用户不必理解底层对象关系，就能看到应用的数据使用情况。

这一数值首先表达的是应用的逻辑数据规模。它不能直接等同于整个系统的实际物理占用；共享内容、去重和本地缓存等因素，应在需要时另设口径。新增量的统计周期，以及新增与净增长的区别，也需要在具体界面设计时明确。

### 6.5 与缓存控制建立关联

应用不再原生依赖文件路径后，系统可以在数据接口和控制面上更早地接入缓存管理：哪些数据应在关键时刻准备好、哪些数据需要保留在本地、哪些缓存可以轮换，都可以围绕应用及对象进行组织。

这也是引入 Bucket 的重要动机，而不仅是替换读写接口。

这里必须区分“应用仍然需要这份数据”和“某台设备当前缓存了这份数据”。前者属于保留范围，后者属于缓存状态。缓存轮换与数据永久删除不能混成同一个操作；具体策略和权限尚待设计。

### 6.6 上传流程直接指定目标 Bucket

当前上传链路不够顺畅，存在较多重复代码。新的方向是让上传流程直接接收目标应用的 Bucket ID，使系统从入口就知道这份数据属于哪个应用的保留范围。

```text
网页 / 客户端上传
        │
        ├── 指定目标应用 Bucket ID
        ▼
系统统一上传接口
        ▼
Named Data 存储与 Bucket 归集
        ▼
应用取得数据引用并完成业务处理
```

这有机会减少各应用重复实现临时落盘、路径转换和数据归集的工作，使上传接口与 SDK 更一致。

该图表达的是目标链路，不代表接口已实现。上传结果的具体类型、写入 Bucket 与更新业务 RDB 的先后和失败处理，仍需定义。

## 七、保留文件系统语义的必要场景

### 7.1 传统应用兼容

已有软件，特别是迁移到 BuckyOS 的 Docker 应用，可能从设计上就依赖文件系统路径。这类应用仍然需要系统提供可持久化的目录。

当前 Desktop 无需仅为这一抽象而运行完整 DFS，可以继续使用本地目录；未来集群再采用相应的 DFS 实现。应用不必直接处理两者的部署差异。

对于系统提供的持久化 DFS 数据空间，应由系统统一承担备份管理，而不是要求每个应用自行备份整个底层文件系统。

### 7.2 用户明确采用文件夹管理数据

文件系统的价值不只在于兼容旧应用。用户也可能明确以目录和文件组织自己的工作。

例如，用户通过 FileBrowser 浏览 Home Directory，上传文件与文件夹，整理文档和视频；或者要求 Agent 把某个文件夹中的视频处理后，保存到另一个文件夹。

在这些场景中，文件夹就是产品向用户承诺的操作对象。系统应当支持这种工作方式，而不是要求用户先理解 Object ID、Chunk 或 Bucket。

**应用内部的数据持久化可以优先采用 Named Data；面向用户的文件与目录体验仍然需要保留。两者并不冲突。**

### 7.3 两条路线的适用边界

| 维度 | 文件系统路线 | 原生 Named Data 路线 |
| --- | --- | --- |
| 主要场景 | 传统软件兼容、用户目录工作流 | 从零开发的原生应用内部数据 |
| 调用入口 | 文件路径或对应资源 URL | 对象/内容 ID、原生接口或拟议的 S3-like 接口 |
| 数据组织方式 | 文件和目录 | 业务引用、File Object、Chunk，以及应用级 Bucket |
| 系统管理重点 | 持久化目录和文件系统资源 | 应用保留范围、对象引用、内容与缓存 |
| 架构态度 | 必须支持 | 原生开发优先采用 |

## 八、内置应用与 Agent 工具的资源访问 URL 化

### 8.1 统一资源入口，不等于强制统一为本地路径

BuckyOS 内置应用在打开资源时，应当使用 URL 化的资源入口，原则上支持本地文件、DFS 文件、File Object 和 Chunk 等来源。

这个要求不是把所有资源都先转换为本机临时文件，而是让应用能识别系统支持的资源定位方式，再通过相应能力取得内容。

如果一个原生工具只能接受某个本机绝对路径，就说明其访问层仍需适配。系统不应长期把“先落成临时文件，再调用工具”作为所有处理任务的固定前置条件。

具体 URL Scheme、授权信息传递以及各资源的访问语义，尚未在本次讨论中定稿。

### 8.2 对随系统提供的开源工具做必要适配

打包给 Agent 的媒体处理等开源工具，也应纳入这一方向。可以考虑对其数据访问层进行必要调整，让它们尽可能直接打开 File Object 或 Chunk，而不是只接受传统本地文件。

这一要求强调“尽可能”，不否定必要的文件系统兼容。工具的业务处理功能与底层资源获取方式应尽量分离，使 Agent 可以围绕系统资源 URL 完成任务，减少调用方反复导出、复制和转换路径。

## 九、对备份、恢复和升级的直接约束

本节归纳前述架构对完整性和版本演进的要求，不将尚未讨论的实现机制写成既定方案。

### 9.1 备份对象不能只有目录

当应用同时使用 RDB 和 namedstore 时，仅备份应用数据目录可能不足以覆盖全部业务数据；仅导出数据库，也可能遗漏对象本体和内容。

从逻辑完整性看，应用备份需要覆盖其恢复所必需的资源：

```text
应用恢复所需数据
   = RDB 业务数据及必要结构信息
   + 被业务引用的 Named Object
   + 对象及业务所需的 Chunk 内容
   + 该应用确实使用的持久化文件数据
```

这是一种完整性检查视角，不是要求对同一份内容重复打包，也不是已经确定的备份文件格式。

### 9.2 不同类别的数据需要不同恢复语义

| 数据类别 | 当前状态或方向 | 尚需明确的恢复问题 |
| --- | --- | --- |
| System Config | 系统级 KV 配置 | 版本变化后哪些配置可以直接恢复，哪些需要转换 |
| Security | 当前主要为密钥等小文件 | 旧身份是否继续有效，哪些密钥可恢复、可推导或需重建 |
| RDB | 统一、权限受控的 Dump / Restore 方向 | 导出格式、Schema 表达及后端差异 |
| namedstore 结构化对象 | 当前整体备份该部分 | 应用级引用遍历、对象归属及恢复完整性 |
| Chunk / 应用级 Bucket | Named Data 与 Bucket 管理方向 | 备份范围、共享内容、保留意图与缓存状态的关系 |
| 文件系统数据 | 系统统一管理持久化目录或 DFS 备份 | 与其他资源之间的应用恢复边界 |

### 9.3 RDB、Bucket 与对象引用需要一起考虑

引入 Bucket 有助于表达非结构化数据的保留范围，但不会自动解决所有 namedstore 问题。

例如，RDB 中引用的结构化对象可能不属于某个非结构化数据 Bucket 的管理范围；对象内部还可能继续引用其他对象或 Chunk。因此，Bucket 并不能直接替代结构化对象的引用追踪和 GC 设计。

至少需要明确以下关系：RDB 的业务引用、Bucket 的保留集合、对象内部引用，以及跨应用共享。谁负责声明、谁负责验证，以及这些状态不一致时如何处理，目前仍然开放。

### 9.4 跨资源恢复必须形成可用的业务状态

RDB、对象本体和 Chunk 即使都分别具有备份，也不代表组合后一定对应同一份可恢复业务状态。这是上述跨资源引用模型带来的后续完整性问题。

需要进一步明确备份范围与一致性要求，避免出现“数据库已经恢复，但其引用内容缺失”的情况。本次没有确定跨资源快照、事务或协调协议。

### 9.5 正式版本应明确兼容契约

后续覆盖安装和升级需要面对的是逻辑数据资源，而不仅是覆盖程序文件。至少需要分别明确：系统配置如何演进、应用 RDB 的 Schema 如何迁移、Named Object 的读取兼容边界，以及旧的文件系统存储方式如何与新的原生存储方式并存。

前向与后向兼容的具体含义也需要落实到场景：新版本读取旧数据、旧版本读取新数据、降级恢复、跨后端迁移，并不应未经区分就被当成同一项承诺。

本次明确的是必须认真处理这些问题，尚未确定全部版本兼容矩阵、迁移流程和可降级范围。

## 十、后续落地的收敛重点

以下按讨论中的问题依赖关系整理，不代表已承诺的版本排期。

### 10.1 先识别当前已有的数据资源

先建立对现状的准确理解：系统有哪些配置和身份数据，各应用使用哪些 RDB Instance，哪些表保存对象 ID，哪些数据进入 namedstore，哪些仍依赖文件目录。

特别是 SQLite 实例，不能继续只表现为应用目录中一批无人统一识别的文件。这个资源清单是后续管理、备份和升级处理的基础。

### 10.2 再收敛对应用提供的稳定接口

优先明确 RDB 的申请和访问接口，以及 Dump / Restore 的逻辑契约；同步细化应用级 Bucket 的作用、上传入口和统计口径。

同时明确原生应用的资源 URL 接口，使新增应用和工具适配有统一方向，而不是继续增加各自的上传、下载和临时文件转换代码。

### 10.3 完整性与 GC 不能留在物理实现之外

需要把对象归属、引用关系、保留集合和缓存状态分开表达，再决定删除和回收行为。结构化对象不应因体积通常较小，就永久采用未经约束的只增不减策略。

已有 GC 基础设施需要实际验证；新增 Bucket 机制也需要和既有 namedstore 模型衔接，不能只增加一层接口而不解决数据生命周期问题。

### 10.4 待定事项清单

| 议题 | 需要收敛的问题 |
| --- | --- |
| RDB 资源管理 | 实例登记、Schema 声明、后端映射以及 SDK 的兼容边界 |
| RDB 导出格式 | 如何表达可恢复的数据及结构，如何处理跨后端差异 |
| Bucket 模型 | 每应用的资源组织方式、接口兼容范围、命名与权限 |
| 上传链路 | Bucket ID 的使用方式、返回引用、失败与业务写入的衔接 |
| 应用容量统计 | 逻辑保留量、新增量、物理占用与缓存量分别采用什么口径 |
| 对象归属 | 对象被多个应用引用时，谁有保留和删除权限 |
| 引用完整性 | 如何发现 RDB 和 Object Body 中的引用，谁负责遍历 |
| 数据生命周期 | RDB 引用与 Bucket 保留范围不一致时如何处理 |
| GC 与缓存 | 永久删除、解除保留和本地缓存淘汰如何区分与协调 |
| URL 与工具适配 | 资源 URL 规范、权限传递及内置工具的支持范围 |
| 备份与恢复 | 系统级与应用级范围、跨资源一致性、恢复校验 |
| 版本兼容 | 覆盖安装、数据迁移、降级边界与身份恢复规则 |

## 十一、方向总结

BuckyOS 的数据落盘架构，应当从“给应用一个目录，应用自行把数据写进去”，演进为“系统提供可识别、可管理的存储资源，应用通过稳定接口表达自己的数据与保留意图”。

System Config 与 Security 构成系统引导和身份基础；RDB 承担结构化业务数据；namedstore 保存对象本体及 Named Data；应用级 Bucket 的拟议作用，是让非结构化数据的归集、统计、上传和缓存控制有明确入口。

DFS 保留为重要的文件系统能力，服务传统应用兼容和用户文件夹工作流，但不再被视为所有原生应用保存非结构化数据的必经路径。系统内置应用和 Agent 工具应当通过 URL 化的资源接口，尽可能直接处理 File Object 和 Chunk。

**最终需要稳定下来的，不只是数据放在哪个目录，而是数据由谁声明、通过什么资源访问、由谁保障可靠性、在什么条件下保留或回收，以及升级和恢复后如何重新形成完整可用的状态。**
