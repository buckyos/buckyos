## 1. 产品概述

### 1.1 一句话定义

BuckyOS 混合 SSO 是面向分享与外部协作的系统级身份接入能力：用户从邀请链接或分享链接进入 Message Hub、AI Workspace 等应用时，可以根据资源所有者允许的方式，以访客、指定本地账号、自建本地账号或已有 DID 身份参与协作，并在合理范围内延续身份和登录状态。

这里的“混合”不是要求用户理解多套认证技术，而是让不同背景的用户都能顺利进入同一协作空间，同时清楚知道自己正在以谁的身份、访问谁的资源。

### 1.2 为什么必须做

BuckyOS 的分享不只发生在已注册用户之间，也会面向客户、朋友和社交网络中的陌生访问者。分享出去的对象也不只是一份静态文档，还可能是一个持续运行、具有角色与操作权限的 AI-native 应用。

如果每个应用分别建立身份体系，或者每访问一个 Zone 都要求重新注册，分享就会不断被账号问题打断。尤其是不同 Zone 的 AI Workspace 外观高度相似，用户很容易认为自己反复打开的是“同一个应用”，却被要求反复创建不同账号。

混合 SSO 的产品价值是降低这种分享和协作门槛，而不仅是增加一种登录按钮。

当前已实现的基础是**登录本 Zone，并记录、维持本 Zone 的登录状态**。本文讨论的是在此基础上扩展外部邀请、公开分享和跨 Zone 身份复用，不能把这些规划能力与现有登录能力混为一谈。

### 1.3 已明确的方向

| 编号 | 已明确的产品决定 |
| --- | --- |
| D-01 | 采用 **BuckyOS 系统级 SSO 扩展**，不由 Message Hub、AI Workspace 分别建立互不相通的外部身份系统。 |
| D-02 | 账号相关入口分为 **专属邀请：指定 Local User、自助注册：自建 Local User、DID 登录：已有身份联合登录**。匿名 Guest 是独立的访问方式，不是第四种账号注册路线。 |
| D-03 | 已有 DID 的用户不应为了访问其他 Zone 的分享内容而反复创建本地账号。 |
| D-04 | 首次使用某身份进入目标 Zone 时，要保留用户选择；确认后，应尽量长期复用有效登录状态。 |
| D-05 | 邀请链接作为访问入口的可用性，与链接所附带的临时免密登录资格，必须分开理解。 |
| D-06 | 用户只有一个 **canonical zone**，也使用 **current zone** 表达同一概念。访问其他 Zone 不会改变这一归属。 |
| D-07 | 认证组件统一命名为 **`verify-hub`**。不能把任意目标 Zone 的 `verify-hub` 当成用户对外联合登录的身份来源。 |
| D-08 | 本轮所有扩展能力仍属规划中的需求，不能在产品说明中表述为已经实现。 |

### 1.4 需求状态说明

本文将内容区分为三类：

- **已明确：** 来自本轮口述，或口述中的明确更正，应作为后续设计依据。
- **补充建议：** 为使主要流程能够安全、完整地落地而补充的异常处理、管理能力或验收要求，需评审确认。
- **待确定：** 讨论尚未作出选择，不能由技术实现或本文描述默认代替产品决策。

后文的交付优先级是规划建议，不是既有版本承诺。

## 2. 目标、范围与非目标

### 2.1 产品目标

**G-01：让分享真正成为可用的入口。** 客户或朋友拿到链接后，能够理解下一步并进入目标内容，不必先学习 BuckyOS、Zone、DID 等概念。

**G-02：让已有身份被复用。** 同一目标 Zone 中，从 Message Hub 打开 AI Workspace 不应重新注册；已有 DID 的用户跨 Zone 访问时，不应被迫为每个 Zone 建立一套新的本地账号和密码。

**G-03：让登录状态具有连续性。** 首次选择身份并成功登录后，在登录状态仍有效、访问资格未改变的情况下，后续访问应尽量直接继续。

**G-04：让身份选择可理解、可控制。** 用户应知道将以哪个身份进入哪个 Zone。不能因为用户曾经登录过自己的 Zone，就在首次访问其他 Zone 时未经选择地暴露或使用该身份。

**G-05：保护用户的身份归属。** 在别人的 Zone 注册、被邀请或留下本地档案，不应让该 Zone 获得代表用户向第三方登录的资格。

### 2.2 本 PRD 覆盖范围

| 范围 | 需要解决的问题 |
| --- | --- |
| Message Hub 企业邀请 | 为指定外部客户生成专属加入链接，允许其以预设身份进入会话，并逐步转为可持续使用的本地账号。 |
| AI Workspace 公开分享 | 允许访问者根据分享者设置，以 Guest、自助注册的本地账号或已有 DID 进入文档或应用。 |
| 同 Zone 跨应用访问 | 用户从群聊打开该 Zone 中的共享文档或应用时，复用适用的已登录身份。 |
| 跨 Zone 联合登录 | 已有 DID 用户完成首次身份选择后，减少重复注册和重复登录。 |
| 身份与权限边界 | 区分登录身份、资源访问资格、应用内角色，以及 canonical zone 的归属。 |
| 主要异常和恢复体验 | 链接过期、密码已设置、身份冲突、权限失效、身份来源不可用等情况。 |

### 2.3 非目标

本轮不设计底层认证协议、签名格式、接口、登录状态存储方式、账号数据模型或网络跳转机制；不决定是否必须由目标 Zone 的 `verify-hub` 集中承接全部应用登录状态。

本轮也不建设浏览器钱包插件，不实现一个浏览器中的复杂多身份工作台，不提供跨 Zone 的本地账号自动合并、密码同步或资源权限自动同步。DJ 电台中的播放、音频同步和内容编排属于示例应用本身，不属于 SSO 的交付范围。

## 3. 概念与身份边界

### 3.1 术语

| 术语 | 本文含义 | 必须避免的误解 |
| --- | --- | --- |
| Zone | 承载某组 BuckyOS 应用、账号和资源的系统空间。 | 不同 Zone 中界面相同的应用，并不因此共享所有账号与权限。 |
| 目标 Zone | 本次分享资源或邀请会话所在的 Zone。 | 不是用户的 canonical zone 的另一种说法。 |
| canonical zone / current zone | 用户唯一指定的身份归属 Zone；两种称呼在本讨论中同义。 | **current zone 不是用户当前浏览的网页所在 Zone。** |
| `verify-hub` | BuckyOS 身份认证相关组件。本 PRD 关注其代表谁提供身份证明的边界，不规定内部实现。 | 不能把任意 Zone 的 `verify-hub` 都视为某 DID 的合法对外认证来源。 |
| DID | 用户可在不同目标 Zone 中复用的稳定身份标识。 | 有 DID 不等于自动获得任何目标资源的权限。 |
| Local User | 在某个 Zone 中建立、由该 Zone 管理的本地账号。 | 创建本地账号，不会自动为某个 DID 指定或变更 canonical zone。 |
| Guest | 在资源所有者允许时，无须创建正式账号即可使用的访客身份。 | Guest 不是已有 DID，也不保证更换浏览器后仍是同一人。 |
| 本地 Profile | 目标 Zone 为参与者保留的展示资料、协作记录及相关权限信息。 | 保存 Profile 不等于获得该用户的全局身份控制权。 |
| 专属邀请 | 身份预先指定的 Local User 邀请模式；早期讨论稿称 EA。 | 用户不需要自行选择一个新的账号身份。 |
| 自助注册 | 允许访问者自行创建 Local User 的注册模式；早期讨论稿称 EB。 | 创建的是目标 Zone 的本地账号，不是自动建立全局 DID 身份。 |
| 免密登录资格 | 在限定条件下，凭邀请链接直接以指定身份进入的资格。 | 与链接作为入口的长期存在不是同一件事。 |

Local User 与 DID 不能仅凭名称作简单互斥判断。例如，一个没有自有 OOD 的用户，也可能在家人承载的系统环境中建立自己的正式 DID 归属。关键在于本人是否明确建立了相应身份关系，而不是账号在本地如何保存。

### 3.2 三层必须分开

| 层次 | 回答的问题 | 示例 |
| --- | --- | --- |
| 身份 | 你是谁，以谁的身份参与？ | Guest、企业预设的 Alice、某个已有 DID。 |
| 访问资格 | 你能否进入这个会话、文档或应用？ | 被邀请进入客服会话，或获得某份 Workspace 的访问权。 |
| 操作权限 | 进入后可以做什么？ | 添加歌曲、切歌、编辑公告、查看文档。 |

登录成功不应自动扩大访问范围；加入一个会话也不等于成为该 Zone 的管理员。跨应用复用身份，同样不意味着跨应用自动获得全部资源权限。

## 4. 用户与核心场景

### 4.1 参与者

| 参与者 | 主要诉求 |
| --- | --- |
| 企业管理员或业务管理方 | 通过后台操作或现有脚本创建会话、预设客户身份、生成并发送邀请链接。 |
| 外部客户 | 点击短信或邮件中的链接即可进入正确会话；不被复杂注册流程阻挡。 |
| Workspace 所有者／DJ | 将应用分享给朋友或公众，并控制允许的身份入口和参与权限。 |
| 普通访问者 | 无须理解系统架构，能以游客或常见的注册方式参与。 |
| 已有 DID 的 BuckyOS 用户 | 复用自己的稳定身份，在不同用户的分享空间之间顺畅切换。 |
| Zone 管理者 | 保持本 Zone 的账号、访问和管理边界，不因开放分享而失去控制。 |

### 4.2 场景一：企业 AI 客服的定向邀请

企业使用 BuckyOS 承载 AI 客服业务。一个 Message Hub 会话中可以包含内部经理、员工、AI 客服，以及一个或多个外部客户。

企业先建立会话和客户身份，再为每位客户生成专属的加入链接。若同一会话有 Alice 和 Bob，两人收到不同链接。Alice 点击自己的短信或邮件链接后，应以预设的 Alice 身份加入该会话；Bob 同理。

**期望体验：**

1. 管理方能够明确将“某个客户身份”和“某个会话”关联起来，再把对应邀请发给该客户。
2. 客户在链接有效时直接进入，不必先自行起用户名、重新填写身份资料或注册另一套账号。
3. 客户在使用过程中能看到设置密码的明确入口，但不必为了第一次参与而先设密码。
4. 设置密码后，客户可继续使用这一既有账号；后续需要登录时使用账号密码，而不是继续依赖原邀请的免密能力。
5. 同一 Zone 内，企业员工向群里发送 AI Workspace 文档，客户不应再次注册另一套身份；能否打开文档仍由文档权限决定。

**场景的关键：** 链接关联的是已经指定的参与者身份，而不只是一个大家共用的会话地址。

### 4.3 场景二：AI Workspace 作为公开分享的 DJ 电台

DJ 用 AI Workspace 制作一个小型音乐电台应用，并把链接发布到朋友圈或社交网络。

| 行为 | DJ | 普通参与者 |
| --- | --- | --- |
| 向歌曲表格添加自己的歌曲 | 按应用设置允许 | 允许插入记录 |
| 选择或切换当前播放歌曲 | 允许 | 不允许 |
| 编辑广播公告文本框 | 允许 | 不允许 |
| 收听音乐、查看公告 | 允许 | 允许 |

普通参与者可以将网页放在旁边，一边工作，一边听歌和看 DJ 发布的文字。这个应用体现了 AI Workspace 不只是共享文档，还可以承载具有不同角色的协作应用。

**期望体验：**

1. DJ 决定是否允许 Guest、目标 Zone 本地注册和 DID 联合登录，并据此开放相应入口。
2. 只想轻度参与的人，可以在允许匿名访问时直接以 Guest 进入。
3. 希望保留稳定身份、但不了解 BuckyOS 的人，可以完成普通网站式的账号注册，在 DJ 的 Zone 创建 Local User。
4. 已有 DID 的人，可以选择使用既有身份，无须再为这个 DJ 建立新账号和密码。
5. 无论使用哪种入口，参与者的应用权限仍由 DJ 或应用规则决定。登录不能使普通参与者自动获得切歌或编辑广播的权限。

**场景的关键：** 公开分享链接面对未知访问者，不能预先为每个人指定身份；需要在进入过程中容纳不同身份基础。

### 4.4 场景二的延伸：重度用户连续访问多个 Zone

一个 Message Hub 群里的成员都已拥有 DID。用户 A 连续打开 B、C、D 分享的 AI Workspace。这些页面的界面几乎相同，只是域名和资源所有者不同。

**不可接受的体验：** A 被要求分别在 B、C、D 的 Zone 注册，并自行管理三套新账号密码；或者每次打开之前访问过的 Workspace 都要完整重走登录流程。

**期望体验：** A 可以在首次访问每个目标 Zone 时选择是否使用已有 DID，完成一次必要操作后，在较长时间内复用有效状态。访问同一目标 Zone 中另一份获准访问的文档，不应因为文档换了就重新注册。

不要求首次登录 B 自动代表 A 同意向 C、D 使用该身份；首次选择应以目标 Zone 为边界，而不是对所有陌生站点一揽子授权。

### 4.5 无自有 OOD 不应成为 DID 使用障碍

Alice 没有购买自己的 OOD，但家人 Bob 提供了可承载其身份归属的环境。Alice 可以将 Bob 承载的 Zone 明确指定为自己的 canonical zone。

这与 Alice 临时在 DJ 的 Zone 注册本地账号不同。前者是本人明确建立的身份归属；后者只是使用一个外部应用。产品必须保持这种差异，不能根据“这里也有 Alice 的账号”就自动推断 canonical zone。

## 5. 身份入口需求

### 5.1 入口总览

| 入口 | 身份由谁决定 | 用户最小操作 | 后续延续方式 | 适用场景 |
| --- | --- | --- | --- | --- |
| Guest | 系统提供访客身份，资源所有者允许使用 | 打开并以游客参与 | 在同一浏览器的访客状态有效时延续 | 公开应用、轻度协作。 |
| 专属邀请 | 管理方已指定本地账号及相关身份字段 | 点击有效的专属邀请链接 | 后续可设置密码，使用原账号登录 | 客服、定向客户邀请。 |
| 自助注册 | 访问者自己选择账号并填写资料 | 完成目标 Zone 的本地注册 | 使用所建本地账号密码登录 | 不具备既有 DID 的普通访问者。 |
| DID 登录 | 用户选择自己的既有稳定身份 | 首次确认向目标 Zone 使用该身份，完成必要登录 | 复用有效的联合登录状态 | BuckyOS 用户之间的跨 Zone 协作。 |

三类账号入口是专属邀请、自助注册和 DID 登录。Guest 不应被包装成必须补齐注册的账号；是否允许 Guest 完成某项操作，由资源权限决定。

### 5.2 Guest：低门槛参与

**已明确需求：**

- 资源所有者允许匿名访问时，用户可以不注册、不登录正式账号进入。
- 在同一浏览器的访客状态有效期间，再次打开链接应识别为同一访客，保留适用的参与连续性。
- 鼓励用户拥有稳定身份，但不应因这种鼓励取消已经允许的游客体验。

**已明确（2026-10-21 确认）：** Guest 是资源级的匿名访客，只在资源所有者开放给游客的资源中有效；它不形成系统登录状态，也不能使用目标 Zone 的其它功能。

**边界：** 浏览器状态清除、失效或更换浏览器后，不承诺自动恢复原 Guest 身份。不把 Guest 自动升级成 DID，也不把本地暂存的访客状态解释为跨设备的稳定账号。

Guest 后续注册或使用 DID 时，历史歌曲、评论和其他记录是否归并，尚未讨论确定，见第 13 节。

### 5.3 专属邀请：预创建、指定身份的 Local User

**已明确需求：**

- 管理方预先建立客户账号；user ID 等已指定字段不能在加入过程中被访问者任意替换。
- 同一会话中不同客户拥有各自的专属邀请，不能使用一个无差别公共链接来选择 Alice 或 Bob。
- 邀请的免密资格有效时，客户可直接以指定身份进入关联会话，不要求重复注册。
- 客户可设置该既有账号的密码；这不是创建第二个账号，也不应丢失原会话关系。
- 设置密码后，原邀请凭据不再提供直接登录资格；没有有效登录状态时，应使用账号密码完成登录。
- 每次通过邀请入口进入时，都应有显著但不强迫的设置密码引导。
- 同一客户在同一 Zone 参与多个会话时，共用同一个客户账号和身份，不为每个会话另建账号。每个会话各自有邀请和访问资格：打开某个会话的链接，不会因此进入该客户的其它会话。（Q-10，2026-10-21 确认）
- 账号复用由管理方在发出邀请时明确指定已有客户账号；系统不按手机号、邮箱等联系方式自动判断是否同一人。客户已设置密码时，新会话的链接只作为入口，使用账号密码登录。
- 首次设置密码始终可用，不受管理员“是否允许修改密码”设置的限制；设置之后再修改密码，按管理员对该账号的设置执行，默认不允许。（P-1，2026-10-21 确认）

邀请有效期内是否多次使用，应遵循本轮讨论中的限时可用体验；**不能未经产品确认将其改为默认“点击一次立即作废”**。

### 5.4 自助注册：用户自建 Local User

**已明确需求：**

- 资源所有者允许时，访问者可从分享入口创建目标 Zone 的本地账号。
- 用户自己填写用户名、密码及所需 Profile 信息，体验应接近常见网站注册，不以理解 DID 或拥有 OOD 为前提。
- 注册完成后返回原分享内容，而不是让用户重新寻找链接。
- 后续使用该账号密码登录；同一目标 Zone 内已有账号的人应可以直接登录，而不是再次注册。
- 页面应让用户知道账号属于谁的 Zone，不能暗示这个账号天然适用于所有 BuckyOS 站点。

自助注册账号建立不会自动将目标 Zone 设为用户的 canonical zone，也不会自动建立与已有 DID 的关联。

**已明确（2026-10-21 确认）：** 自助注册只在资源所有者允许、且 Zone 未关闭自助注册时提供（见 §9.1）。注册得到的是受限本地账号，权限规则见 §9.2。

### 5.5 DID 登录：使用已有稳定身份联合登录

**已明确需求：**

- 用户可以使用已有 DID 进入目标 Zone，无须额外设一套目标 Zone 本地账号密码。
- 首次向某个目标 Zone 使用该身份时，应清楚显示身份和目标，并允许用户选择，不默认无提示进入。
- 用户在自己的 canonical zone 已登录时，应尽量减少重复输入凭据；尚未登录时，引导其完成必要认证，再回到原分享内容。
- 联合登录成功后，不得要求用户因此再注册一个独立身份。该 DID 已在目标 Zone 有账号时，使用原账号；尚未入驻时，目标 Zone 不为其建账号或密码，显示名和头像取自 DID 的公开资料，只保留协作记录和授予该 DID 的资源权限。（2026-10-21 确认）
- 后续访问同一目标 Zone 中有权访问的资源时，在状态有效的情况下复用身份。
- 目标 Zone 的本地 Profile、访问记录和应用角色，不产生代表该 DID 向其他 Zone 登录的资格。
- 首次确认时展示并共享：所用 DID、来源 Zone 与目标 Zone、公开显示名和头像；不共享手机号、邮箱等私密联系方式。同意以 DID + 目标 Zone 为单位记录，向 B 的同意不代替向 C 的同意；以后申请更多资料、用户撤回同意或更换 canonical zone 时，重新确认。（Q-05，2026-10-21 确认）
- 首期尚未入驻目标 Zone 的 DID 登录者，可使用 Message Hub 群会话、AI Workspace 和 HomeStation 中授权给他的内容，不能使用目标 Zone 的其它系统功能。（2026-10-21 确认）

### 5.6 钱包路径的范围

此前讨论提出了未来通过浏览器钱包证明 DID 身份的方向。当前浏览器钱包插件尚未实现，本 PRD 不将其列为首期依赖，也不在现有界面中展示无法完成的可用登录入口。

钱包用户尚未建立 Zone 归属时的完整产品形态，留作远期需求澄清；它不改变本轮已确定的 canonical zone 唯一性原则。

## 6. 统一进入与身份连续性

### 6.1 分享入口首先需要让用户明白什么

无论来自短信、邮件、群聊还是社交网络，入口应尽可能清楚地呈现：访问的是哪个人的或哪个企业的空间、目标是什么、即将使用什么身份，以及需要完成什么操作。

具体展示多少资源信息必须受分享权限约束，不能为了展示登录页就向无权访问者公开私密内容。

### 6.2 首次选择与后续访问

| 情况 | 期望行为 |
| --- | --- |
| Guest 被允许，用户选择游客 | 不要求先注册正式账号。 |
| 有效的专属邀请，当前没有冲突身份 | 按链接指定身份进入，不要求再选一个账号。 |
| 访问者选择自助注册 | 完成目标 Zone 本地注册或登录后，返回原资源。 |
| 已有 DID 首次进入某目标 Zone | 明确选择是否使用该 DID；确认后完成必要认证。 |
| 目标 Zone 中已有有效且适用的登录状态 | 尽量直接进入有权访问的资源，不重复展示首次流程。 |
| 当前身份不具有资源权限 | 明确告知权限问题；不能把“无权限”伪装成“必须再注册”。 |

### 6.3 同 Zone 跨应用复用

**已明确需求：** 用户经专属邀请、自助注册或 DID 登录在目标 Zone 获得适用的登录状态后，从该 Zone 的 Message Hub 打开其 AI Workspace，不应被迫建立新的应用专属账号或再次填写相同身份资料。

复用的是适用身份和登录体验，而不是资源权限。企业客户在群里收到一份没有对其授权的文档，仍然应当被拒绝访问，或被引导走该文档允许的访问申请流程。

只读文档是否需要申请入口不在本轮确定；最基本要求是正确区分“还未登录”和“已登录但没有权限”。

### 6.4 跨 Zone 复用

**已明确需求：** 稳定 DID 应可用于多个目标 Zone，但不同目标 Zone 的资源资格和首次身份选择仍各自独立。联合登录不能变成“所有 Zone 都是一个账号管理后台”。

登录状态保持多久、canonical zone 退出或改密后的影响，见 §6.6。

### 6.5 身份冲突与多身份使用

**补充建议：** 当浏览器已以 Bob 登录，却打开指定 Alice 的专属邀请链接时，不应在用户不知情的情况下替换身份，也不能以 Bob 身份错误加入 Alice 的会话。应说明当前身份和邀请身份不同，由用户明确处理后继续。

**已明确的范围取舍：** 在 B 的 Workspace 使用身份 X、在 C 的 Workspace 使用身份 Y，属于低频高级需求。初期不建设复杂的并行多身份管理功能，可引导有此需求的用户使用不同浏览器分别登录。

不建设高级多身份功能，不等于可以混用账号或隐式改变用户正在操作的身份。

### 6.6 登录状态保持与撤销

**已明确（Q-03、Q-04，2026-10-21 确认）：**

| 情况 | 产品行为 |
| --- | --- |
| 本地账号（密码登录、专属邀请免密进入） | 7 天内使用过就持续保持登录；连续 7 天未使用需重新登录；不设总时长上限。 |
| DID 登录 | 同样按 7 天滑动保持；另外最长 30 天须重新经 canonical zone 确认一次。已同意过的目标 Zone 通常只需一次跳转，不再重复确认资料。 |
| 敏感管理操作 | 仍需再次输入密码，确认后只维持约 3 分钟。 |
| 权限被提高（改账号类型、加入用户组） | 重新登录后生效；已有登录状态不自动获得新权限。 |
| 被移出会话或授权用户组、分享授权被取消、资源被删除 | 下一次访问即被拒绝，已打开页面的后续更新也停止。 |
| 账号停用、邀请被撤销、用户退出登录 | 新登录与续期立即被拒绝；其它已登录页面最长 15 分钟内失效。 |
| canonical zone 退出或修改密码 | 不传播到已访问的目标 Zone；目标 Zone 的 DID 登录状态最晚在 30 天重新确认时结束。 |
| canonical zone 暂不可用 | 已有登录状态在有效期内继续；新的 DID 登录和到期的重新确认无法完成。 |

登录页不再提供“记住我”选项，所有登录统一按上表处理。

**已知限制：**

- 首期不提供全局退出：在一个 Zone 退出，不会同时退出其它 Zone。
- canonical zone 修改密码后，目标 Zone 中已有的 DID 登录状态最长仍可保持 30 天。
- 有多台 OOD 的 Zone 中，认证服务迁到另一台设备后，已登录用户需要重新登录。

## 7. 专属邀请链接的生命周期

### 7.1 两件事必须分开

**链接作为入口：** 帮助用户找到原来的业务、会话或登录入口。

**链接作为临时登录凭据：** 在规定条件下，允许持有者不输入密码就以指定身份进入。

“链接失效”不能笼统地表示所有功能都消失。临时登录资格失效后，原地址仍可保留为入口，展示密码登录或重新获取邀请的操作；但业务已关闭、资源已删除或访问已撤销时，不承诺继续进入原资源。

### 7.2 状态与用户体验

| 状态 | 链接入口应呈现的行为 | 不应发生的行为 |
| --- | --- | --- |
| 邀请免密资格有效，尚未设置密码 | 以预设身份进入；提供设置密码入口。 | 强制重新注册，或把预设身份改成其他人。 |
| 免密资格已过期，尚未设置密码 | 说明已过期；按允许的流程申请向原绑定渠道重发新链接。 | 仅因为知道旧链接就直接恢复免密登录。 |
| 已成功设置密码，当前没有有效登录状态 | 原链接可以继续作为入口；要求账号密码登录。 | 继续使用设密码前的旧邀请凭据直接登录。 |
| 已成功设置密码，当前已有适用的有效登录状态 | 可按现有登录状态继续访问有权访问的资源。 | 把正常复用既有状态误解为旧邀请仍有免密资格。 |
| 管理方已撤销邀请或资源访问资格 | 说明无法继续访问，提供适当的联系提示。 | 通过重发邀请自动恢复已撤销的权限。 |
| 链接无法识别或已经不对应可用入口 | 给出可理解的错误说明。 | 展示不相关客户的信息，或进入错误会话。 |

最后两项属于为完整体验补充的建议要求，具体管理操作范围需评审确认。

### 7.3 有效期

**已明确（Q-01，2026-10-21 确认）：** 邀请的免密资格默认有效期为 **48 小时**。首期不提供按企业、按业务或按单个邀请调整；是否开放调整、由谁调整，以后另行确定。

48 小时只约束免密登录资格，不代表会话、客户账号或历史记录在 48 小时后删除，也不会让已有的有效登录状态因此退出。邀请失效和业务 case 关闭是不同的状态，不能相互替代。

### 7.4 过期后的重新发送

**已明确的体验：** 用户从历史短信或邮件打开过期链接后，页面告诉用户已过期；用户可以申请重新发送。新链接仍通过该身份原绑定的短信或邮箱送达，用户打开新链接后继续进入。

**已明确（Q-02 及发送责任，2026-10-21 确认）：**

- 新链接由发出邀请的管理方经原绑定渠道发送，系统本身不发送短信或邮件。用户申请重发后，系统提醒管理方；提醒中不含新链接，管理方在管理界面取得新链接后发出。
- 页面只告诉用户申请已提交、受限或失败，不向当前打开页面的人显示新链接或授予新登录资格，也不允许改发到其它地址。
- 重新发送只替换这个入口的免密资格，该客户其它会话的邀请不受影响；已被密码或撤销替代的资格不会因重发恢复。

**补充安全要求建议：**

- 不通过页面暴露完整的敏感联系方式；发送失败、重复请求或暂不可发送时，应给出可理解的提示。
- 已设置密码后的正常入口应为密码登录，不能默认允许旧邀请重新发送一条可绕过密码的免密链接。
- 密码遗忘后的恢复流程应单独定义，不与未激活邀请的重发混为一谈。

### 7.5 设置密码后的变化

设置密码的产品含义是：**为已经存在的指定账号建立一种后续可持续使用的登录方式，并终止原邀请凭据的直接登录能力。**

该操作不应另建身份，不应丢失原会话成员关系，也不应自动切换为 DID 联合登录。**已明确（Q-03，2026-10-21 确认）：** 设置密码的这台设备保持登录；此前凭该邀请免密登录的其它设备最长 15 分钟内退出，之后需用密码登录。

## 8. canonical zone 与身份控制权

### 8.1 唯一性与术语

**已明确：用户只有一个 canonical zone，也称 current zone。** 用户可以拥有、使用或访问多个 Zone，但不能把多个普通 Zone 同时视为该用户的 canonical zone。

用户在不同网页之间切换，不改变 current zone；目标 Zone 变化也不意味着身份归属随之变化。

### 8.2 对外联合登录的来源

在通过 Zone 进行 DID 联合登录的路径中，目标 Zone 必须确认身份证明来自该用户唯一指定的 canonical zone 的 `verify-hub`，不能仅因为某个 Zone 中存在同名账号或相同展示资料，就认可其代表该 DID。

本要求定义“谁有资格代表用户证明登录身份”，不规定如何查找 Zone、获取公钥或验证证明。

**已明确（2026-10-21 确认）：** 能从某个 Zone 出发、以 DID 登录其他 Zone 的，只有该 Zone 的管理员和普通用户，且本人已把该 Zone 建立为自己的 canonical zone。专属邀请、自助注册建立的本地账号不能用来登录第三方 Zone；仅修改账号类型也不会产生这种资格。

### 8.3 普通注册和访问不能改变归属

以下行为均不应自动改变用户的 canonical zone：

- 在 DJ 的 Zone 自助注册本地账号。
- 通过专属邀请链接加入企业客服会话并设置密码。
- 使用 DID 登录某个目标 Zone，并在其中形成本地 Profile。
- 在其他 Zone 中打开文档、加入群聊或使用应用。

canonical zone 的变更必须是由用户明确控制的严肃身份操作，不能夹带在普通注册、登录或分享流程中。其本人授权强度需要单独设计，不能由目标 Zone 管理员仅凭本地账号管理权完成。

### 8.4 Alice、Bob 与 DJ 的边界示例

Alice 可以在 Bob 承载的环境中明确建立自己的 canonical zone 归属；她不需要先拥有自己的物理 OOD。

Alice 随后在 DJ 的 Zone 使用应用，即使 DJ 为她建立了本地账号或 Profile，也不会改变 Alice 的 canonical zone。DJ 不能因为控制这个目标 Zone，就代表 Alice 的 DID 向第三个 Zone 联合登录。

这条边界是本轮需求的核心验收条件，不是可有可无的高级选项。

## 9. 角色权限、分享控制与界面要求

### 9.1 分享者的控制

**已明确需求：** Workspace 所有者能够决定是否允许 Guest、是否允许自助注册本地账号，并让已有 DID 用户在允许时使用联合登录。企业定向邀请采用专属邀请，不将指定身份邀请变成任意选身份的公开注册入口。

**补充建议：** 各分享入口只展示当前实际可用的方式。某种方式被关闭后，需要说明原因或给出其他被允许的进入方式，不能将用户带入无法完成的流程。

**已明确（Q-06，2026-10-21 确认）：**

- 分享设置以分享入口为单位，入口属于具体资源（Workspace 或会话）。资源所有者决定该入口允许 Guest、自助注册、DID 登录中的哪些方式。
- Zone 管理者有两个全 Zone 开关：允许自助注册、允许 DID 登录，默认开启。关闭后，所有分享入口的对应方式都不可用，资源所有者不能绕过；分享设置中显示该方式“已被 Zone 设置关闭”。
- Zone 不提供全局关闭 Guest 的开关，Guest 只由资源所有者在入口上开放。已知风险：管理者无法一键关闭全 Zone 的匿名访问；游客只能进入各所有者自行开放的资源。
- 只有对资源有分享权限的人才能创建分享入口；能读取资源或能创建客户账号都不够。应用代为创建入口时同样受此限制。
- 分享入口的公开说明不包含私密内容或客户名单。

### 9.2 权限不随入口方式自动扩大

同一人可以通过不同入口形成不同的身份状态，但每次访问都必须遵守相应资源权限。在 DJ 电台中，“成功登录”不应自动获得 DJ 权限；在企业客服中，“创建了本地账号”不应自动看到其他客户的会话。

**已明确（2026-10-21 确认）：** 专属邀请和自助注册建立的都是受限本地账号：默认没有业务权限，只能访问为其指定或分享给它的资源；需要更多权限时，由管理员把账号加入相应用户组。自助注册不会自动加入任何用户组。

是否允许 Guest 插入歌曲、是否要求评论使用稳定身份等，由应用或分享规则决定。本 PRD 不统一规定所有应用必须给 Guest 相同权限。

### 9.3 身份和归属应清楚可见

**已明确需求：** 用户在选择登录时，应能分辨自己进入的是谁的空间、使用的是哪种身份。对于普通访问者，优先使用“游客访问”“在此创建账号”“使用已有身份”等可理解表达，不把专属邀请、自助注册、canonical zone 等文档术语当作必须学习的用户操作术语。

**补充建议：** 在进入后的适当位置，持续展示当前身份和资源归属；从本地账号切换到 DID 或反向切换时，不用同样的头像、昵称掩盖身份实际发生了变化。

### 9.4 AI Workspace 的轻量个性化

**已提出的辅助需求：** Workspace 可提供背景花纹、纹理等轻量个性化元素，让用户对不同所有者的空间有一定视觉感知，同时保持生产力应用的简洁。

个性化不是 SSO 的前置条件，也不能单独承担身份识别功能。文档或空间的所有者信息仍应能够清楚辨认。

### 9.5 过程连续性

**补充建议：** 注册、登录、身份确认或链接续发完成后，应尽可能回到原来要访问的会话、文档或应用，而不是只停在系统首页。用户取消认证时，也不应被当成已同意使用某个身份。

## 10. 异常处理与质量要求

本节主要是为主流程补齐的需求建议，需评审后纳入交付范围；不规定具体技术处理方式。

| 情况 | 用户应得到的反馈与行为 |
| --- | --- |
| 未登录且资源要求登录 | 说明需要身份，并提供当前允许的入口。 |
| 已登录但无权限 | 明确提示无权限，不循环要求登录或重新注册。 |
| canonical zone 暂不可用 | 说明当前无法完成已有 DID 登录；已有登录状态在有效期内继续（见 §6.6）；不自动将目标 Zone 改为 canonical zone，也不偷偷换成另一个身份。 |
| 目标 Zone 暂不可用 | 说明暂时无法访问，保留用户理解原目标所需的信息。 |
| 注册用户名不可用或资料不符合要求 | 就地提示可纠正的问题，不丢失已填写的非敏感信息。 |
| 邀请重发受限或发送失败 | 给出清楚反馈，避免用户误以为已成功收到新链接。 |
| 分享关闭、会话结束或权限被撤销 | 分别说明原因；不把资源不可用统称为密码错误。 |
| 浏览器访客状态丢失 | 不承诺恢复为原 Guest；允许按资源设置重新进入。 |
| 现有身份与定向邀请身份冲突 | 不静默替换身份，不把一个客户的操作记到另一个客户名下。 |
| 原分享目标已经不存在 | 说明目标不可用，不在登录成功后把用户带到无关内容。 |

**已明确（2026-10-21 确认）：** 拒绝时说明属于哪一类原因，并指出能调整的设置以及由谁调整（管理员、资源所有者或分享者），例如“该分享未允许 DID 登录”“Zone 已关闭自助注册”“缺少该文档的访问授权”。属于产品边界的限制（此类账号不支持该功能）直接说明，不引导管理员寻找不存在的开关。对访客，未向其开放的资源与不存在的资源显示相同结果，不暴露资源是否存在或其他人的信息。

**质量目标：**

- 主要流程应适合用户从短信、邮件、聊天消息或社交平台中打开，不依赖用户记住系统域名或手动寻找后台。
- 不因同一目标 Zone 中的应用切换而产生不必要的账号分裂。
- 不要求将身份根控制信息交给目标 Workspace 或目标 Zone 的管理员；用户的身份控制权不能成为访问分享内容的代价。
- 不把“用户大概率不会转发邀请”当成唯一安全前提；限时邀请及设置密码后的免密失效规则必须可验证。
- 移动端和桌面端的身份选择与错误提示应含义一致。具体性能指标和兼容范围需另行确定。

## 11. 需求验收场景

以下为用户视角验收草案。标注“建议”的项目，须先确认相应补充需求；其余对应本轮已明确要求。验收不限定底层实现。

| 编号 | 场景／前提 | 预期结果 |
| --- | --- | --- |
| AC-01 | 企业在一个会话中邀请 Alice、Bob，分别发送有效专属链接。 | 两人各自以预设身份进入同一会话，不需要自行选择客户身份或重复注册。 |
| AC-02 | Alice 首次打开有效的专属邀请，尚未设置密码。 | 可以直接参与会话；可看到设置密码入口，但不会因未设密码而被强制阻挡。 |
| AC-03 | 专属邀请的免密资格仍有效，未设置密码，用户再次打开链接。 | 按限时可用规则处理，不因首次点击过就默认判定为一次性失效。 |
| AC-04 | Alice 为既有专属邀请账号设置密码，再在无登录状态的浏览器打开旧邀请。 | 旧入口仍可指向相关业务，但不再凭原邀请直接登录；要求使用账号密码。 |
| AC-05 | 专属邀请免密资格过期，账号尚未设密码。 | 显示过期提示并可申请向原绑定渠道重发；打开新链接后继续原业务。 |
| AC-06 | 仅持有过期链接的人申请重发。 | 新链接不直接出现在当前页面，也不能被改发到任意新地址。 |
| AC-07 | 专属邀请用户已进入企业 Message Hub，打开同一 Zone 内已对其授权的 Workspace 文档。 | 不重复注册，不建立新的应用专属账号，能够复用适用登录状态。 |
| AC-08 | 同一客户打开尚未对其授权的另一份文档。 | 登录成功不等于自动有权访问，不能看到未授权内容。 |
| AC-09 | DJ 允许 Guest；访客添加歌曲后，在同一浏览器有效状态下再次打开。 | 延续同一访客身份及适用参与状态，不要求先注册。 |
| AC-10 | DJ 允许自助注册；普通访问者创建账号。 | 完成常见账号注册流程并回到原应用，无须先理解 DID 或拥有 OOD。 |
| AC-11 | 已有目标 Zone 本地账号的用户再次访问。 | 能直接登录原账号，而不是被要求重新注册。 |
| AC-12 | 已登录自己 canonical zone 的 DID 用户首次进入 B 的 Zone。 | 可以明确选择是否使用该 DID；不能未经选择就以该身份进入。 |
| AC-13 | 用户取消使用当前 DID。 | 不以该 DID 自动完成目标 Zone 登录；其他入口是否可用取决于分享设置。 |
| AC-14 | 已成功联合登录 B，登录状态仍有效，再打开 B 的其他获准访问的 Workspace。 | 不要求重复创建本地账号，不重复完整首次登录流程。 |
| AC-15 | 同一 DID 用户随后首次打开 C、D 的分享。 | 可复用 DID，无须各建一套密码；仍保留分别向 C、D 使用身份的首次选择。 |
| AC-16 | 普通参与者通过 Guest、自助注册或 DID 登录进入 DJ 电台。 | 权限依应用规则执行；不能因登录而获得切歌或编辑 DJ 公告的权限。 |
| AC-17 | DID 用户在目标 Zone 形成了本地 Profile。 | Profile 不等于新注册全局身份，也不自动授予该 Zone 代表此 DID 对外登录的资格。 |
| AC-18 | Alice 在 DJ 的 Zone 注册或被邀请。 | Alice 的 canonical zone 不发生变化，current zone 不被解释为当前访问站点。 |
| AC-19 | Alice 没有自有 OOD，但已明确使用 Bob 承载的 canonical zone。 | 不能仅因她没有自有 OOD 就拒绝其正常 DID 联合登录。 |
| AC-20 | DJ 试图凭本 Zone 的本地账号／Profile 或本 Zone 的认证来源，代表 Alice 的 DID 登录第三方 Zone。 | 不能被当作来自 Alice canonical zone 的合法联合登录身份。 |
| AC-21〔建议〕 | Bob 已登录，打开指定 Alice 的邀请。 | 明确处理身份冲突，不静默覆盖、不串用身份。 |
| AC-22〔建议〕 | 邀请已撤销，或相关访问权限已取消。 | 重发或重新登录不能自动恢复被撤销的访问资格。 |
| AC-23〔建议〕 | 用户完成登录后返回原分享目标。 | 能继续原会话、文档或应用；目标已失效时给出准确提示。 |
| AC-24 | 查看首期产品中的可用登录方式。 | 不将尚未实现的浏览器钱包路径展示成可以完成的正式功能。 |

验收时应特别区分：**认证未完成、认证成功但无权限、链接免密资格过期、资源本身失效**。这四种结果不能用同一个“请重新登录”替代。

## 12. 规划优先级与效果观察

### 12.1 优先级建议

以下用于后续 Roadmap 评审，不指定研发排期或承诺版本。

| 建议级别 | 内容 | 理由 |
| --- | --- | --- |
| P0：核心闭环 | 系统级身份接入；专属邀请、自助注册、DID 登录三类入口；允许时的 Guest 访问；同 Zone 跨应用复用；首次 DID 身份选择；后续状态延续；专属邀请限时与设密码后的免密失效；canonical zone 唯一性与对外认证边界。 | 缺少其中关键部分，就无法完整覆盖两类主要场景，或会出现不可接受的身份混淆。 |
| P0：必要流程补齐，需评审 | 明确身份冲突处理、资源权限错误、过期重发限制与撤销后的行为。 | 主流程会直接遇到这些情况，不能留给用户猜测。 |
| P1：体验完善 | 轻量个性化、更完整的身份与空间提示、分享入口管理体验，以及经确认的恢复流程。 | 降低不同 Zone 界面相似造成的困惑，提高持续使用质量。 |
| 后续独立规划 | 钱包直接登录、同一浏览器复杂多身份使用、Guest／Local User／DID 的历史记录归并与账号升级。 | 本轮未形成完整需求，且不应阻塞当前主要使用路径。 |

同 Zone 跨应用和跨 Zone 联合登录都应在核心验证中出现，不能只演示单个应用的登录页，就宣布“混合 SSO 已完成”。

### 12.2 效果观察建议

| 观察项 | 关注的问题 |
| --- | --- |
| 邀请进入完成率 | 客户点击有效邀请后，是否能成功到达原会话，而非停留在账号流程。 |
| 分享进入完成率 | 普通访问者是否能根据允许的入口完成进入，失败主要发生在哪个环节。 |
| 非必要重复注册 | 同一 Zone 跨应用、已有 DID 跨 Zone 时，是否仍出现必须另建账号的情况。 |
| 重复登录干扰 | 在应复用有效状态的再次访问中，是否仍被要求完整重走流程。 |
| 专属邀请生命周期通过率 | 过期重发、设置密码、旧凭据失效等行为是否一致且可验证。 |
| 身份与权限错误 | 是否出现串号、未经选择使用 DID、越权操作或 canonical zone 被意外改变。 |

本轮不设虚构的转化率或耗时目标；登录保持时长是 §6.6 的规则，不作为效果目标。具体数值应在流程方案和测试条件明确后确定。

## 13. 待确定事项

Q-01～Q-06、Q-10 已于 2026-10-21 确定，结论写入各节；Q-13 已移交技术设计。保留编号便于追溯。仍待确定的是 Q-07～Q-09、Q-11、Q-12，不应被当作已经批准的需求或默认实现：

| 编号 | 待确定问题 | 当前边界 |
| --- | --- | --- |
| Q-01 | 专属邀请默认有效期是多少，谁可调整？ | **已确定：** 默认 48 小时，首期不可调整；见 §7.3。 |
| Q-02 | 重发新邀请后，其他仍有效的同账号邀请如何处理？ | **已确定：** 只替换同一入口的免密资格，其它会话的邀请不受影响；见 §7.4。 |
| Q-03 | 后续登录状态应保持多久，哪些事件需要重新认证？ | **已确定：** 7 天滑动保持，本地账号不设总上限，DID 登录最长 30 天重新确认；见 §6.6、§7.5。 |
| Q-04 | 在 canonical zone 退出或修改凭据后，已访问目标 Zone 的状态如何变化？ | **已确定：** 首期不传播，DID 登录状态最晚在 30 天重新确认时结束；见 §6.6。 |
| Q-05 | 首次向某目标 Zone 使用 DID 的确认具体涵盖哪些资料？ | **已确定：** DID、来源与目标 Zone、公开显示名和头像；见 §5.5。 |
| Q-06 | 哪些分享设置属于 Workspace Owner，哪些由 Zone 管理者限制？ | **已确定：** 所有者按入口选择方式，Zone 只有自助注册、DID 登录两个总开关；见 §9.1。 |
| Q-07 | Guest 转为自助注册账号或 DID 登录后，已有记录是否、如何归属？ | 本轮不自动承诺合并。 |
| Q-08 | 专属邀请／自助注册的本地账号能否绑定 DID，以及绑定后原账号如何保留？ | 本轮只要求各路径可用，不自动建立账号升级关系。 |
| Q-09 | 专属邀请用户忘记已设置的密码后如何恢复？ | 不默认用旧邀请重新获得免密登录，需独立定义恢复需求。 |
| Q-10 | 一个客户参与同一企业多个会话时，账号与邀请的复用粒度是什么？ | **已确定：** 同 Zone 同客户共用一个账号；每个会话各自有邀请和访问资格，复用由管理方明确指定；见 §5.3。 |
| Q-11 | 用户如何正式变更 canonical zone，变更后既有访问状态如何处理？ | 唯一性、本人控制与普通登录不改变归属是硬边界；流程待专门设计。 |
| Q-12 | 尚未建立 Zone 归属的钱包用户如何进入完整身份体系？ | 属远期需求；不推出同时多个 canonical zone，也不作为首期依赖。 |
| Q-13 | 目标 Zone 的系统认证组件与应用如何划分登录处理责任？ | **已移交技术设计：** 产品要求统一、可复用的系统级体验；分工见实施 TODO §4.3。 |

## 14. 评审结论应围绕的问题

本 PRD 的评审重点不是选定某种认证协议，而是确认以下产品结果能够同时成立：

**外部客户能靠专属链接顺利加入；普通访问者能在允许时匿名或本地注册；已有 DID 的用户不会被迫到处重建账号；同一 Zone 的多个应用不会反复索要身份；用户在任何普通访问中都不会失去对自己 canonical zone 的控制。**

最终交付应同时通过“企业客服邀请”和“AI Workspace 公开分享／跨 Zone 协作”两组端到端场景，而不是分别为两个应用做出外观相似、实际互不相通的登录功能。
