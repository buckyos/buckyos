# MessageHub 双用户 E2E 用例（devtest × bob）

状态：设计稿，2026-09-30 编写，尚无执行结果。

DV Test 环境默认有两名真实用户：zone 主人 `devtest` 和本地普通用户 `bob`。本文件让 Test Agent 用
Playwright 启动两个独立浏览器（其中一个模拟手机），分别以这两个身份登录，通过真实 zone 的 msg-center
互发消息。每条用例产出两类结论：

- **功能结论**：流程是否走通，数据是否正确。
- **体验结论**：以目标用户的视角，判断现在的版本好不好用，并给出证据。

用例只描述用户意图、判据和观察点。具体按钮和定位由执行时观察当前 UI 决定，UI 改版不改变判据。
通用的“观察 → 行动 → 核对”方法和证据纪律沿用
[Canvas 浏览器执行约定](../../doc/ai-canvas/e2e/execution-guide.md)，本文只写 MessageHub 的补充。

## 1. 范围

在范围内：同一 zone 内两名用户的私聊，包括文本、附件、未读、会话管理、多设备、手机布局、断网和权限边界。

不在范围内：

- Agent 对话。已由 [messagehub.real.spec.ts](../../src/frame/desktop/tests/e2e/real/messagehub.real.spec.ts) 和 `messagehub-agent.real.spec.ts` 覆盖。
- Telegram 等 tunnel、群组（真实 zone 没有建群入口）、性能压测。

现有真实后端测试只用了 devtest 一个账号。zone 内用户互发只有 msg_center 的 Rust 单测覆盖，本文件是第一批双用户浏览器用例。

| 编号 | 名称 | 主要风险 | 设备（A / B） | 类别 |
|---|---|---|---|---|
| MH-P0 | 环境预检 | 账号或联系人前置不成立 | 桌面 / 手机 | 必跑 |

| MH-E04 | 离线留言与上线补收 | 离线期间丢消息 | 桌面 / 手机 | 核心 |
| MH-E05 | 消息内容保真 | 换行、表情丢失，注入，排版溢出 | 桌面 ⇄ 手机 | 核心 |

## 2. 环境

### 2.1 账号与角色

| 角色 | 账号 | 密码 | DID | 身份 | 默认设备 |
|---|---|---|---|---|---|
| A | `devtest` | `bucky2025`，或取 `BUCKYOS_TEST_ADMIN_PASSWORD` | `did:bns:devtest` | zone 主人、管理员 | 桌面 Chrome，1440×900 |
| B | `bob` | `buckyos2026` | `did:web:bob.test.buckyos.io` | 本地普通用户（`users` 组） | 手机，Pixel 7 模拟，412×839 |

- bob 由 `src/make_config.ts` 的 `applyDevBootTemplate` 写入 dev 组的启动模板。
- devtest 的显示名来自 profile，不一定是 “devtest”（有的机器上是真实姓名）。确认身份时看实体详情里的 DID，不要硬编码显示名。

### 2.2 入口与浏览器

- **入口**：默认 `https://test.buckyos.io`，MessageHub 的独立路由是 `/messagehub`。
  - 被测版本是部署在 `/opt/buckyos/bin/control-panel/web` 的构建。
  - Vite 开发服务器只用于排查问题，不作为体验结论的依据，因为用户拿到的不是它。
  - 本机 `/etc/hosts` 把 `test.buckyos.io` 指向 `::1`，所以要用 `--host-resolver-rules` 把 zone 域名钉到 `127.0.0.1`（见 §7）。
- **两个独立浏览器**：每个用户各一次 `chromium.launch()`，进程和存储都独立。不能用同一个浏览器的两个页面代替。
- **手机端**：
  - 用 Playwright 的 `devices['Pixel 7']`（isMobile、hasTouch），在手机上用 `tap`。
  - 宽度必须小于 768 px。桌面布局从 769 px 起，而对话页的返回按钮在 768 px 及以上会被隐藏，所以正好 768 px 时手机布局没有返回按钮。
- **语言**：建议 A 用 `en-US`、B 用 `zh-CN`，顺带检查中文界面是否完整。若界面语言由桌面设置决定，以设置为准并记录。
- **登录**：
  - MH-E01、MH-E13 必须走真实登录表单。
  - 其他用例可以复用 UI 登录后保存的 `storageState`，里面是真实的 SSO cookie。
  - 用 API 注入 token（`messagehub.real.spec.ts` 的 `login()`）只作为兜底，用了要记为偏离。

### 2.3 MH-P0 · 环境预检

预检不过时，后续用例一律标 `NOT_RUN`，写明原因。

1. 两个账号都能通过 UI 登录，桌面上出现 MessageHub 图标。
2. A 的实体列表里，bob 显示为“人”，不在 Requests（请求）筛选里。反过来，B 的列表里 devtest 也一样。
   - msg-center 只在**启动时和设置重载时**把 zone 用户互相加为好友。
   - 如果 bob 是在 msg-center 启动之后才创建的，消息会进 Requests，此时标 `ENV`。
   - 由操作者决定是否重启 msg-center。重启要记入执行包。这个现象本身也是 MH-X01 要评估的产品问题。
3. 记录以下信息：
   - 仓库 commit 和未提交的改动；
   - web 构建时间、`msg_center` 二进制的修改时间；
   - 浏览器版本、视口、locale；
   - 本次运行标签 `RUN`。
4. 记录 devtest 和 bob 之间是否已有会话和历史。已有时，MH-E01 按“再次联系”变体执行。

### 2.4 测试数据

- **运行标签**：`RUN=mh2u-<yyyyMMdd-HHmm>`。每条测试消息结尾带 `[RUN#序号]`，这样在不断累积的历史里也能精确定位、计数，并反查顺序。
- **附件夹具**：执行前记录每个文件的 sha256 和大小。夹具放在执行目录里，不提交到仓库。

| 文件 | 规格 | 用途 |
|---|---|---|
| `photo.jpg` | 4000×3000，约 3 MB | 相册照片、缩略图、预览 |
| `anim.gif` | 多帧，1 MB 以内 | GIF 自动播放设置 |
| `clip.mp4` | H.264，10 秒，约 5 MB | 视频封面、播放、首帧耗时 |
| `doc.pdf` | 3 页，约 1 MB | 文件卡片、下载、哈希比对 |
| `notes.txt` | UTF-8，含中文 | 文本文件下载 |
| `big.bin` | 70 MB | 超过对象路由 64 MB 上限，只用于 MH-E06/b |

- **状态卫生**：
  - zone 是长期共享的，历史会不断累积。不要用 RPC 删除消息或改数据库。
  - 需要“双方没有会话”的前置时，只用 UI 里的“永久删除”（见 MH-E07）。
  - 执行顺序：P0 → E01…E13 → E14 → X01。MH-E14 会改联系人准入级别，必须最后跑并恢复。MH-X01 要删除新建的用户。

## 3. 执行约定

- **产品动作只走 UI**。
  - RPC 只做只读旁证，例如 `msg.list_sessions`、`msg.list_session`、`msg.get_session_state`，在记录里标“旁证”。
  - 部署构建里没有 `window.__messageHubStore`，不要依赖它。
  - 不通过 store 或 IndexedDB 直接写入结果。
- **等待上限**：
  - 跨用户消息最长等 30 秒。界面每 20 秒轮询一次，kevent 推送是尽力而为，失败时会静默退回轮询。
  - 超时后 reload 一次，用来区分“没送到”和“送到了但界面没刷新”。两种情况分开记录。
- **计时**：每条跨用户消息记 4 个时间点，在报告里给出 A→B、B→A 各自的 p50 和最大值。
  - t0：点击发送；
  - t1：自己的气泡出现；
  - t2：自己的气泡显示已送达；
  - t3：对方界面可见。
- **定位**：
  - 优先用角色、标签和可见文字。
  - 当前有几类控件没有可访问名称：发送按钮、手机返回箭头、回形针、附件卡片上的移除按钮、送达状态图标。这些只能用结构或图标类名定位。
  - 每类控件记一条可访问性问题，只记一次，不在每条用例里重复扣分。
- **留证**：
  - 每个检查点双方各截一张图，命名为 `<用例>-<步骤>-A|B.png`；
  - 两个浏览器都录 trace；
  - 收集 console error 和 `/kapi/` 的错误响应；
  - 附上时延表；MH-E06 还要保存下载的文件和哈希。
- **输出目录**：`test/message_hub/runs/<日期>/<批次>/`。
  - 这个目录**还没加入 `.gitignore`**，首次执行前要先加上，或者改放到仓库外。
  - 不要写到 `src/frame/desktop/test-results/`，那里的 `.last-run.json` 受 git 跟踪。
- **预算**：同一个阻塞最多尝试三条有证据的路径，然后停止该子项，写明原因。

### 3.1 已知未实现与已知无效控件

**已知未实现**（据 2026-09-30 代码与 [UI_DATAMODEL](../../src/frame/desktop/src/app/messagehub/UI_DATAMODEL.md) §9.4）：

- 已读回执和“对方已读”状态；
- 对方正在输入的提示；
- 系统通知和桌面级未读角标（状态栏上的数字是打开的窗口数）；
- 回复引用、表情回应、编辑、撤回、转发；
- 共享会话标题（对端只看到“私聊 / Direct Message”）；
- 草稿跨设备同步；
- 建群；
- 服务端消息搜索（搜索框只过滤名字和最后一条预览）；
- 旧记录变更游标（只对最新一页对账）。

遇到这些时，功能结论标 `N/A`。但如果缺失导致目标用户完不成任务或产生误解，要在体验意见里明确说出来，并标为“已知缺口”。

**已知无效控件**：实体详情里的 Mute、Pin、备注编辑按钮当前点了没有效果。会话详情里的个人偏好（标题、Pin、Mute）是有效的。用户看得见、点了却没反应的按钮按**体验缺陷**记录，不算“未实现”。

## 4. 体验评估方法

### 4.1 以角色视角评判

- **A（devtest）**：zone 主人，懂技术，主要用电脑，关心“消息到了没有”“对方看了没有”。
- **B（bob）**：家庭成员，不懂技术，主要用手机，只知道对方叫什么。bob 看到 DID 字符串，或看到 native、owner、Source information 这类技术词，都算负担。

### 4.2 逐步走查四问

每个子目标执行前后，Test Agent 用一行记录这四个问题的答案，并写出“预期 vs 实际”的落差：

1. 这个角色会想到要做这一步吗？
2. 入口看得见吗？
3. 他能把这个入口和自己的目的联系起来吗？
4. 做完之后，界面能让他看出成功了没有？

### 4.3 评分维度

每个维度按 1–5 分打分，下表给出 5、3、1 分的锚点。

| 维度 | 5 | 3 | 1 |
|---|---|---|---|
| D1 可发现性 | 首次使用无需猜测，3 步以内 | 需要试探一两处才找到 | 不看源码或提示就找不到 |
| D2 即时性（跨用户到达） | 2 秒以内 | 20 秒以内（靠轮询） | 超过 30 秒，或必须刷新 |
| D3 状态可信 | 发送中、已送达、失败、未读都一眼能辨，且与事实一致 | 状态存在，但含义要猜或有滞后 | 状态缺失或与事实矛盾 |
| D4 双方一致 | 两边看到同一段对话、同样的顺序和内容 | 内容一致，但标题或分组要靠猜 | 有消息只在一边看得到，或顺序不同 |
| D5 容错与恢复 | 出错说人话，一键恢复，不丢不重 | 能恢复，但要重新输入或自己摸索 | 丢消息、重复发送或卡死 |
| D6 手机适配 | 触控目标够大，返回路径清晰，没有溢出 | 能用，但偶有误触或死路 | 关键操作在手机上做不了 |
| D7 表达力 | 多行、表情、图片、文件都能自然表达 | 能表达，但有降级 | 常见内容发不出或变形 |

**评分纪律**：

- 每个分数都要引用证据：截图、时延、步数或 DOM 测量值。
- 如果某个入口是靠源码、testid 或本文的提示才找到的，该步 D1 最高只能给 2 分。
- 不因为“内部实现合理”而加分。
- 可以把微信、Telegram、iMessage 的通行做法当作用户预期的来源，但要写明这是参考，不是需求。
- 功能结论和体验结论分开写：功能 PASS 不代表好用，体验差也不能把功能改判成 FAIL。

### 4.4 问题记录

问题编号为 `MH2U-<n>`，字段如下：

- 所属用例；
- 严重度：阻断 / 严重 / 一般 / 建议；
- 类型：缺陷 / 已知缺口 / 体验 / 可访问性 / 环境 / 规格待定；
- 现象；
- 证据路径；
- 对目标用户的影响；
- 改进建议。

归属要依据证据，不能只凭现象猜。

## 5. 用例

判据编号为 `<用例>-F<n>`。检查手机横向溢出的方法：`document.documentElement.scrollWidth <= clientWidth`。

### MH-E01 · 首次联系：主人在电脑上给家人发第一条消息

**角色**：A devtest 用桌面；B bob 用手机，开始时未登录。

**用户故事**：devtest 想告诉 bob，家里的 BuckyOS 也能用来聊天，于是发出第一条消息。bob 在手机上登录后看到消息并回复。

**步骤**：

1. [A] 通过 UI 登录，从桌面打开 MessageHub。
2. [A] 先不用搜索，看能否在实体列表里一眼找到 bob；再用搜索框输入 `bob` 找到他，点开。
3. [A] 发送 `你好 bob，这是第一条消息 [RUN#1]`，观察状态从发送中变为已送达。
4. [B] 在手机上通过 UI 登录，点 MessageHub 图标。记录落地在哪一屏、默认选中了谁。
5. [B] 不刷新页面，找到 devtest 的消息。
6. [B] 回复 `收到 [RUN#2]`。
7. [A] 保持会话打开、不刷新，等回复出现。
8. [A][B] 各自打开会话详情里的来源信息，记录 sessionId；各自 reload，确认两条消息都在。

**功能判据**：

- **E01-F1**：bob 在 A 的列表里显示为“人”，不在 Requests；devtest 在 B 的列表里也一样。
- **E01-F2**：[RUN#1] 在 B 端恰好出现一次，文字一致；通过实体详情里的 DID 能确认发送者是 devtest。
- **E01-F3**：[RUN#2] 在 30 秒内出现在 A 当前打开的会话里，无需刷新。
- **E01-F4**：双方记录的 sessionId 相同；刷新后历史完整、顺序一致。
- **E01-F5**：A 的 [RUN#1] 最终显示已送达；全程没有 console error 或 kapi 错误。

**体验观察**：

- A 从登录到发出第一条消息用了几步、多长时间。
- B 打开 MessageHub 后的第一屏：
  - 当前版本会自动打开最近的实体。如果该实体还没有会话，会自动新建一个空会话。
  - 如果落在别的实体上（例如 Jarvis），bob 能否看出新消息在别处？
  - 事后看 B 的会话列表里有没有因此多出来的空会话。
- bob 看到的发送者名字和头像，能否让他认出这是谁。
- 会话标题“私聊 / Direct Message”对 bob 有没有意义。
- 送达图标（时钟、双勾）没有文字说明，A 能否读懂。
- 记录 t2 和 t3。

**变体 E01/b · 再次联系**：环境里已有两人的历史时，步骤相同，重点核对 F2–F5。

### MH-E02 · 实时往返对话

**角色**：A 用桌面，B 用手机，双方都停在同一会话里（用 E01 的 sessionId 核对）。

**用户故事**：两人商量周末安排，你一句我一句，中间有人连着发了好几条。

**步骤**：

1. 双方交替发送 10 条消息 `[RUN#10]`…`[RUN#19]`，A 发奇数号，B 发偶数号。每条等对方看到后再发下一条，记录 t0–t3。
2. [A] 快速连发 5 条 `[RUN#20]`…`[RUN#24]`，每条按 Enter 发出，间隔不到 1 秒。
3. [B] 在 A 连发期间开始输入回复，先不发送。观察输入框和滚动有没有被打断，然后发出 `[RUN#25]`。
4. 双方 reload，对比完整顺序。

**功能判据**：

- **E02-F1**：16 条消息在双方各出现恰好一次，没有缺漏，没有重复（按序号计数）。
- **E02-F2**：双方的显示顺序一致，并且符合发送的先后因果；连发的 5 条保持发送顺序。
- **E02-F3**：每条都在 30 秒内到达对方；刷新前后内容一致。
- **E02-F4**：连发时没有出现发送失败，也没有卡在发送中超过 30 秒。
- **E02-F5**：B 正在输入时收到新消息，输入内容不被清空，焦点不被抢走。

**体验观察**：

- 看时延分布：消息是秒级推送过来的，还是在 20 秒轮询时一批批冒出来（“一阵一阵到”）？后者 D2 最高 3 分。
- 停在底部时，新消息会不会自动滚进视野。
- 发送后，桌面端输入框是否保持焦点，手机端键盘怎么表现。
- 手机上按回车是发送还是换行？手机 IM 通常回车换行、按钮发送，记录是否符合这个习惯。

- **E13-F1**：切换账号后没有数据串号，包括实体列表、会话、草稿和媒体。
- **E13-F2**：退出后，`buckyos_session_token` 和 `buckyos_refresh_token` 两个 cookie 都被清除。
- **E13-F3**：越权查看被服务端拒绝，UI 给出明确的无权限提示，不显示 devtest 的任何会话。
- **E13-F4**：bob 重新登录后，自己的数据完整。

**体验观察**：

- 在手机上，退出入口好不好找。
- 用户切换后，bob 的草稿是否还以明文留在 IndexedDB 里。只读取检查，不做修改，结果记为隐私观察。

### MH-E14 · 屏蔽与恢复（破坏性，最后跑）

**角色**：A 用桌面，B 用手机。

**步骤**：

1. [B] 打开 devtest 的实体详情，在准入区点“屏蔽”。记录有没有二次确认。
2. [A] 发送 `[RUN#b1]`，观察状态 30 秒：应该变为失败，并能展开看到原因。
3. [B] 在这 30 秒内，收件箱和请求箱里都不应出现 [RUN#b1]。
4. [B] 在实体详情里点“接受联系人”，恢复关系。
5. [A] 发送 `[RUN#b2]`。如果界面有重试入口，也对 b1 重试一次并记录结果。B 应收到。
6. **清理核对**：B 端对 devtest 的准入状态恢复为好友；A→B、B→A 各发一条，确认一切正常。

**功能判据**：

- **E14-F1**：屏蔽期间，消息不会进入 B 的任何信箱。
- **E14-F2**：A 端得到失败状态（红色图标和失败详情），不会一直停在发送中。
- **E14-F3**：恢复后，新消息正常进入收件箱，而不是请求箱。
- **E14-F4**：清理完成。如果没能恢复，把整批环境标为“脏”并停止执行。

**体验观察**：

- A 看到的失败原因是什么文案：是暴露了“被屏蔽”（隐私问题），还是让人无从判断（可理解性问题）？记录原文，交给评审定性。
- bob 找到屏蔽和解除入口各用了几步。
- 屏蔽前有没有确认。

### MH-X01 · 新家庭成员加入后直接聊天（扩展，需要建用户）

**角色**：A devtest 用桌面（管理员）；C 是新用户 `carol-<RUN>`，用手机。

**背景**：msg-center 只在启动和设置重载时同步 zone 用户之间的联系人。运行中新建的用户，发来的消息很可能进请求箱。本用例从用户视角确认这件事的影响。

**步骤**：

1. [A] 在“用户与智能体”里创建本地用户，沿用 [local-user.spec.ts](../../src/frame/desktop/tests/dv/local-user.spec.ts) 的 UI 路径。
2. [C] 在手机上登录并打开 MessageHub，看 devtest 和 bob 在不在列表里。
3. [C] 给 devtest 发消息。[A] 观察这条消息出现在普通会话里，还是出现在“请求”里。
4. [A] 如果在“请求”里，点“接受联系人”，然后双方互发消息。
5. **清理**：以管理员身份（sudo）删除 carol。

**功能判据**：

- **X01-F1**：新用户无需任何额外操作，就能看到并联系 zone 内的成员（这是期望，不是当前已承诺的行为）。
- **X01-F2**：如果消息进了请求箱，接受之后，新消息进入普通会话。当前旧消息不会从请求箱迁移出来，这是已知缺口。
- **X01-F3**：清理完成。

**体验观察**：

- devtest 能否理解“请求”是什么，以及为什么家人的消息被当成了陌生人的消息。

## 7. 自动化骨架与定位参考

下面的骨架只示意“两个独立浏览器 + 其中一个是手机”的组织方式，未经执行验证。执行时以当次观察到的 UI 为准。

```ts
import { chromium, devices, type Page } from '@playwright/test'

const BASE = process.env.MH2U_BASE_URL ?? 'https://test.buckyos.io'
const ZONE_IP = process.env.MH2U_ZONE_IP
const host = new URL(BASE).hostname
const args = ZONE_IP ? [`--host-resolver-rules=MAP ${host} ${ZONE_IP}, MAP *.${host} ${ZONE_IP}`] : []

async function openUser(kind: 'desktop' | 'mobile', locale: string) {
  const browser = await chromium.launch({ args })
  const context = await browser.newContext({
    ...(kind === 'mobile' ? devices['Pixel 7'] : { viewport: { width: 1440, height: 900 } }),
    baseURL: BASE,
    ignoreHTTPSErrors: true,
    locale,
  })
  await context.tracing.start({ screenshots: true, snapshots: true })
  return { browser, context, page: await context.newPage() }
}

async function arrival(receiver: Page, text: string, sentAt: number, limitMs = 30_000) {
  await receiver.getByTestId('conversation-history').getByText(text, { exact: true })
    .waitFor({ timeout: limitMs })
  return Date.now() - sentAt
}
```

**定位参考**（2026-09-30 版本的观察，UI 改版以后以实际观察为准）：

- **实体列表**：
  - 搜索框只有占位文字 “Search...”，没有 label；
  - 筛选按钮：All、Unread、People、Agents、Groups、Requests；
  - 实体行是按钮，可访问名称以实体名开头；
  - `entity-load-more`。
- **对话**：
  - `conversation-history`，带 `data-raw-count` 属性；历史列表是虚拟化的，只有渲染出来的消息才能定位到；
  - `message-composer`，发送中带 `aria-busy`；
  - 输入框只有占位文字 “Message...”；
  - “Scroll to bottom”；
  - `request-banner`、`request-chip`、`delivery-details`、`action-message`。
- **附件**：
  - `attachment-ready`，带 `data-kind` 属性；
