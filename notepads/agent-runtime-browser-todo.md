## 0. 结论

- PRD 把这件事定成了一个产品：「Agent 浏览器」。浏览器运行在 Personal Server 上，Personal Agent 主用，Owner 可以直接用。首要场景是只有手机、没有桌面浏览器可借的用户。
- 浏览器的用途仍建议分开处理：
  - **开发测试用的浏览器**：Playwright 自己启动的无头浏览器，数量多、寿命短、没有状态。它缺的是运行环境：浏览器依赖的系统库和字体。对应 PRD 的“BuckyOS 应用开发”。
  - **Agent 的常驻浏览器**：就是 PRD 的「Agent 浏览器」。每个 Agent 一个，长期运行，带登录状态，Owner 和 Agent 轮流操作。对应 PRD 的“Kiosk 与手机用户”。
  - PRD 的第三个需求“AIWS 导出 PDF”由系统服务从自己的入口触发，建议另列（Q8）。
- 两种用途共用同一份浏览器和运行库，建议做成一个默认安装的扩展包。
- 常驻浏览器要的不只是一块屏幕。PRD 的三种模式里，只有原始页面模式是“把画面传给用户”。重排和对话模式要 Agent 读懂页面、按元素操作。所以 Agent 对浏览器的语义访问（页面结构、元素级动作、标签页）从后续项变成首期前提，建议作为 ComputerUse 的浏览器驱动接入（§3.6）。
- **画面传输的建议改了。** 浏览器这一种屏幕建议先用浏览器自己的调试协议（CDP 截屏流加输入注入），不引入虚拟显示和 VNC。理由是手机优先：App 本来就要有自己的地址栏、标签和模式切换；视口能按手机模拟；中文可以整段插入；文件对话框和下载能截下来接到 Zone。RFB（VNC）留给以后的虚拟机。与传输无关的“屏幕”接口不变，有两种实现（§3.3）。
- **控制权的建议改了。** PRD 里用户本来就是这个浏览器的使用者：原始页面模式下用户直接操作，交给 Agent 后网页只读。所以不是初稿的“默认只看”，而是“同一时刻一方操作，双向显式交接”（§3.4）。接手规则仍沿用 ComputerUse：不检测人工输入，靠显式交接，恢复后重新观察。
- PRD 里的“Work Session”是讨论时的口头说法，指用户在浏览器里办一件事，不是 OpenDAN 的 Work Session（D1）。建议一件事对应 MessageHub 里的一个会话（一个 UI Session）加它名下的一组标签页（§3.8、Q12）。
- 重排是一个选择器：页面有匹配好的重排代码就用代码，没有就用 LLM 兜底重排（D2，§3.7）。
- 安全是有时必须把浏览器控制权交回用户的原因。第一期原型只管密码：遇到密码框交回用户填写，其余的能 Agent 填就 Agent 填（D3，§3.5）。网页内容按不可信输入对待；提交前要不要确认仍待定（Q16）。
- 以后 Agent 的私有 Win11、macOS 共用屏幕接口、查看组件和交接规则，但不放进「Agent 浏览器」App，另给入口（§3.11）。
- 打印、网页快照这类由系统服务调用的浏览器，和 Agent 自己的浏览器不是一回事，建议另列（Q8）。

相对初稿的改动：Q4、Q5 的建议改了；Q7 由 PRD 给出了方向；Q8、Q9、Q11 补了 PRD 的内容；新增 §1.2、§3.6–§3.8 和 Q12–Q17；§4 的任务按三种模式重排；§6、§7 相应更新。

## 1. 需求

### 1.1 owner 的要求

原话要点：

1. 现在 Agent 做前端开发经常需要 Playwright。
2. 希望 Agent 的私有 runtime 里默认有浏览器可用。
3. 引入浏览器后还需要接线。
4. 用户有需要时，可以通过类似远程桌面的方法观察和操作 Agent 的浏览器。
5. 这个“Jarvis's browser”可以成为一个 App，用户可以直接使用。
6. 技术类似虚拟机。以后 Agent 有私有的 Win11、macOS，也可以用这个技术栈让用户用到。

### 1.2 PRD 方向的要点

| # | 要点 | PRD 位置 |
| --- | --- | --- |
| R1 | 浏览器运行在 Personal Server 上，网页资源由服务器加载。Personal Agent 主用，Owner 可以直接用。只有手机的用户也能从 BuckyOS 打开它 | 一、三 |
| R2 | Desktop 版已经能经 Computer Use 借用 Owner 宿主上的浏览器和登录状态。Kiosk（类似 NAS 的无显示器盒子）上、只用手机的用户没有浏览器可借，这是要补的场景 | 二 |
| R3 | 需求来源有三个：Kiosk 与手机用户、BuckyOS 应用开发（Agent 打开实际页面检查和调试）、AIWS 导出 PDF。前端调试和 PDF 导出由各自的工作入口触发，普通用户从「Agent 浏览器」App 进入三种模式 | 二 |
| R4 | 原始页面模式：原网页，保留原布局和交互。用户直接操作，需要时交给 Agent，Agent 从当前页面接着做。手机网络弱时降低帧率，先保证看清和能操作 | 三 |
| R5 | 重排模式：按用户为这个网站设定的偏好重新呈现，经常浏览的网站沿用设定。可以带着当前页面进对话调整。重排页直接在手机上显示，传输量少。依赖原网页交互的动作由 Agent 在原网页执行，结果带回重排页；也可以切回原始页面，沿用浏览进度 | 三 |
| R6 | 对话模式：对话和网页共用一个 Work Session（口头说法，指用户在浏览器里办的这件事，D1）。Agent 找入口、操作网页，期间网页对用户只读。Agent 先用已有信息预填，缺项在聊天框里问（类似 Ask User），或只展示需要补填的几项 | 三 |
| R7 | 按事情组织：一件事可以跨页面、跨网站。用户可以在几件事之间切换，回来接着办。改变显示方式、从用户交给 Agent，都要延续当前的页面和任务进度 | 四 |
| R8 | 待定的产品选择：默认入口、首批场景、协作控制（谁在操作、Agent 在等什么、用户怎么接手） | 五 |

## 3. 设计问题

### 3.1 两种用途

| | 开发测试用 | 常驻浏览器（Agent 浏览器） |
| --- | --- | --- |
| PRD 的需求来源 | BuckyOS 应用开发 | Kiosk 与手机用户 |
| 谁启动 | 项目里的 Playwright | Agent Service，按需启动 |
| 数量和寿命 | 多个并行，跑完就退出 | 每个 Agent 一个，长期保留 |
| 状态 | 没有 | 有登录状态、历史、下载 |
| 画面 | 无头，不需要 | 用户要看、要操作 |
| 谁操作 | 项目的测试脚本 | Owner 和 Agent 轮流 |
| 浏览器版本 | 由项目的 Playwright 版本决定，各项目不同 | 系统统一的一个版本 |
| 系统要提供的 | 运行库、字体，以及一份预装的浏览器省去下载 | 浏览器、远程画面、交接、Agent 的语义访问、重排、对话办理 |

Playwright 每个版本绑定特定的浏览器构建。所以开发测试这一侧，系统能稳定提供的是运行环境，不是“唯一的那个浏览器”。项目可以继续用自己版本对应的构建，只要依赖齐全就能跑。

PRD 说开发者委派前端任务后，“Agent 能打开实际页面、检查效果并完成调试”。自动化测试走开发测试用的浏览器；要给用户看效果时，Agent 可以在常驻浏览器里打开同一个页面。两者都能访问 Agent 在容器里起的开发服务（§3.2）。

### 3.2 浏览器跑在哪里

| 选项 | 做法 | 好处 | 问题 |
| --- | --- | --- | --- |
| A | 在 Agent 自己的容器里，浏览器和运行库来自扩展包 | Playwright 按默认方式启动就能用。浏览器能直接访问 Agent 在 `localhost` 起的开发服务，文件上传下载也在同一个文件系统。不需要新的容器生命周期。原生运行的 Agent 也能照此办理 | 浏览器和 Agent 的 shell 同权。Chromium 自己的沙箱在容器里多半要关 |
| B | 每个 Agent 一个伴随容器，和 Agent 容器共用网络 | 崩溃和资源互相隔离。可以单独配置安全参数。形态上最接近虚拟机 | node_daemon 要管一种新容器。Playwright 要改成连接远端，而远端连接要求两边版本一致，开发测试用起来不顺 |
| C | Zone 级共享的浏览器服务 | 给系统服务用正合适 | 不是“Agent 的浏览器”，访问不到 Agent 的 `localhost` 和文件 |

建议：首期用 A。它符合 PRD 的“浏览器运行在 Personal Server 上”：Agent 的容器跑在 Zone 的节点上。常驻浏览器由 Agent Service 在同一个容器里启动和管理。“屏幕”接口（§3.3）不依赖它跑在哪里，以后换成伴随容器或虚拟机不影响上层。系统服务的需要走 C，另列（Q8）。

### 3.3 屏幕：画面和输入怎么传

PRD 带来的约束：

- 主要在手机上看和操作（R1、R4）。
- 弱网时降低帧率，先保证看清和能操作（R4）。
- 用户要输入中文。
- 上传从 Zone 选文件，下载存到 Zone（产品原则：Zone 是主文件系统）。
- App 要有自己的地址栏、标签或事情列表、三种模式的切换和对话面板（R4–R6）。浏览器自带的界面在手机上反而碍事。

| 选项 | 做法 | 好处 | 问题 |
| --- | --- | --- | --- |
| A | 浏览器自己的调试协议（CDP）：页面截屏流加输入注入 | 不需要虚拟显示和 VNC，浏览器无头运行即可，扩展包小。截屏流每帧要回确认才发下一帧，弱网时帧率自然降下来，还能调画质和尺寸。视口和触屏能按手机模拟，网站会给手机版布局。文字可以整段插入，不经按键映射。文件对话框、下载、弹框、新窗口都有事件，可以交给 App 用自己的界面接住。Agent 读页面用的也是这个协议 | 只有页面内容。浏览器之外的界面要 App 自己做：地址栏、标签、下拉框、权限请求、右键菜单。不能用于虚拟机 |
| B | 浏览器以有界面模式跑在虚拟显示上，用 RFB（VNC）传画面和输入，Desktop 里用网页客户端显示 | 看到的是完整的浏览器。与内容无关：QEMU 虚拟机本身就提供 VNC，Win11、macOS 客体可以直接接入 | 要引入虚拟显示、VNC 服务端和网页端的 VNC 客户端。手机上看到的是缩小的桌面浏览器。按键位送字符，中文输入法组字要实测。改远端分辨率要靠扩展协议。文件对话框是容器里的，接 Zone 要另想办法 |
| C | WebRTC 视频流加数据通道 | 跨公网体验最好 | 最重：编码器、穿透，还要和网关、SN 配合 |
| D | 复用 ComputerUse 的截图和动作 | 不引入新协议 | 帧率很低，只能算“定时看一眼” |

初稿建议第一种实现用 B，理由是一种实现同时覆盖浏览器和以后的虚拟机。PRD 把手机定为主要入口后，A 在手机上的几处优势比这份复用更重要。建议改为：

- 屏幕接口不变：画面、输入、尺寸、剪贴板、谁在控制。再加一类“页面之外的请求”事件（选文件、下载、弹框、新窗口），没有这类事件的实现（虚拟机）不报。
- 浏览器这一种屏幕用 A。首期不引入虚拟显示和 VNC。
- 以后的虚拟机用 B（QEMU 的 VNC）。查看组件按屏幕的实现选解码方式，交接和权限共用。
- 调试连接等于对浏览器的完全控制，只在容器内由 Agent Service 持有，不经网关暴露。用户端只连 Agent Service：经网关的 WebSocket 到 Desktop，沿用现有的会话令牌和权限，不另开端口。
- 视口跟随正在看的设备：手机上按手机尺寸和触屏模拟，App 里可以切“桌面版”；Agent 操作时不改视口，免得页面在用户眼前变样（Q17）。
- C 留作以后跨公网体验不够时的升级，接口不变。

A 的几处要实测（B1）：无头模式下下拉框、弹框、文件对话框、新窗口能不能都接住；手机上的帧率、延迟和流量；输入法组字。

### 3.4 Agent 和用户谁在操作

PRD：原始页面模式下用户直接操作，需要时交给 Agent；对话模式下 Agent 操作，网页对用户只读；待定的“协作控制”要让用户一眼看懂当前谁在操作、Agent 在等什么、怎么接手（R4、R6、R8）。

建议：

- 每块屏幕同一时刻只有一个操作方：用户或 Agent。另一方只看，输入不送达。
- 交接都是显式的，两个方向：
  - **用户交给 Agent**：在原始页面里点“交给 Agent”，或在对话里交代一件事。Agent 收到交接时的页面（网址、标题、语义快照），从这里接着做（R4）。
  - **用户接手**：用户点“接手”，控制租约收回，Agent 对这块屏幕的后续动作被拒，在飞的那一步结束后 Agent 停住。用户交还后，Agent 重新观察再继续。
  - **Agent 请用户接手**：遇到密码框（§3.5），或者 Agent 自己过不了的验证（图形、滑块验证码等），Agent 把控制交给用户，状态是“等你接手”。
- Agent 办完或停下后，控制回到用户。
- 接手不等于暂停 Session：Agent 对这块屏幕的命令返回“用户在操作”，它可以等交还，也可以先做别的。
- 沿用 ComputerUse 的规则：不检测人工输入，谁在操作由显式交接决定；租约用 fencing 拒绝迟到的旧动作；恢复后必须重新观察（ComputerUse 技术草案 §8.1）。
- 界面上始终显示操作方和 Agent 的状态：操作中、等你回答、等你接手、已完成、卡住（附原因）。这是 PRD 待定的“协作控制”的技术底座，文案和样式归产品。
- 交接、接手、交还都记进会话，Agent 才知道页面为什么变了。

与初稿的差别：初稿是“默认只看，接管后才能输入”，出发点是“观察 Agent 的浏览器”。PRD 里用户本来就是使用者之一，原始页面模式下默认是用户在操作。

### 3.5 登录状态、身份和安全

- **用户数据目录。** 常驻浏览器的登录状态、历史、下载放在 Agent 的实例卷里，属于这个 Agent。
- **替 Agent 登录。** 用户接手时输入的账号会留在 Agent 的浏览器里，之后 Agent 能以这个登录状态行动。这是主要用途之一（帮 Agent 登录网站、过验证码），也是风险。界面上要明示，并提供清除登录状态的入口。
- **谁能看。** 画面里可能有敏感内容。默认只有 Agent 的 owner 能看和操作。
- **Zone 内的身份。** Agent 的浏览器访问 Zone 里的应用时用 Agent 自己的身份，不自动带上用户的会话。
- **密码交回用户（D3）。** 有些时候必须把浏览器的控制权交回用户，安全是主要原因。第一期原型只管密码：Agent 遇到密码框就请用户接手，用户直接在页面上填。密码不经对话，不进会话记录和模型上下文。浏览器驱动的观察要保证不返回密码框的值。登录状态留在浏览器里，之后通常不用再输。
- **其余的能 Agent 填就 Agent 填（D3）。** 其他缺项，包括短信验证码、证件号，都在对话里问，用户回答后由 Agent 填进页面（owner：老网站的很多交互太灾难了）。PRD 说的“只展示需要补填的几项”是提问的一种呈现，回答照样交给 Agent 去填。第一期不做绕过对话、直接写进页面的补填框。
- **网页内容是不可信输入。** 重排和代办时 Agent 读的是第三方网站的内容，而它此时带着 Owner 的登录状态。网页里的文字可能诱导 Agent 做交代之外的事。建议：代办的动作限在用户交代的目标内。提交前要不要确认见 Q16。
- **重排页的显示。** 重排页由 Agent 生成，内容来自第三方网站，却在 Zone 的域名下显示。它不能带网站的脚本。建议放进没有同源权限的沙箱 iframe，配 CSP 禁止脚本和外部请求；图片由服务器取回后提供；页面上的链接和按钮由 App 截下来转给 Agent Service。
- **做不了的验证。** 网站看到的是 Personal Server 的出口地址和服务器上的浏览器，有的网站会因此要求额外验证。短信验证码发到用户手机，用户在对话里告诉 Agent，由 Agent 填（D3）；U 盾、客户端控件、人脸识别在远程浏览器里做不了。选首批场景时要避开（R8）。
- **沙箱。** 容器是隔离边界。Chromium 自身的沙箱在容器里能不能开，要实测。本机 PVE 宿主上 Docker 的 AppArmor 配置曾经让容器里的 unix socket 全部被拒，Chromium 的多进程依赖它，要一并验证。

### 3.6 Agent 怎么读和操作页面

重排和对话模式都要 Agent 读懂页面、按元素操作（R5、R6）。原始页面模式里“从当前页面接着做”也要 Agent 能读当前页面（R4）。

ComputerUse 草案把浏览器语义驱动列为后续可选扩展：通用动作（聚焦、激活、设值、勾选、选择、展开、滚动到可见）到浏览器 DOM 的映射已经写了；导航、标签页、弹框要另行声明能力；daemon 不执行任意浏览器代码（草案 §7）。

建议：

- 常驻浏览器作为 ComputerUse 的一个浏览器驱动接入，驱动跑在浏览器所在的容器里，登记成这个 Agent 的一块屏幕。观察返回页面的语义大纲（可访问性树，带元素引用）和截图，动作按元素引用执行，导航、标签页、弹框按能力扩展声明。复用 ComputerUse 的观察有效性、去重、租约和图片结果，不加新的 tool。
- Agent 对常驻浏览器的所有动作都经 Agent Service。不让 Agent 直接用 Playwright 连上常驻浏览器，否则会绕过控制租约和交接记录（Q13）。开发测试用 Playwright 自己启动的浏览器，不受影响。
- 这是首期前提：没有它，重排和对话模式都做不了。草案把它定为桌面交付的可选扩展，这里要把它提前，在 [ComputerUse TODO](computer-use-uia-semantic-todo.md) 里立项（B8）。

### 3.7 重排

PRD 的要求见 R5。拆开是四件事：

| 环节 | 建议 |
| --- | --- |
| 站点偏好 | 用户说的“这个网站我只看更新日期、标题和正文，按手机单栏显示”，按站点（域名，必要时加路径）保存。它是用户的偏好，在 App 里能查看和删除。存在哪里待定（Q14） |
| 生成 | 一个选择器（D2）：页面有匹配好的重排代码（提取用的选择器或一小段脚本，加模板）就用代码重排，不经过模型；没有匹配，或者代码套用失败（网站改版、页面类型不同），就用 LLM 按偏好兜底重排。偏好是两者共同的输入。常用站点靠代码，其余靠兜底，PRD 说的“经常浏览的网站可以沿用设定”由此承担。代码从哪里来、存在哪里见 Q14 |
| 显示 | 重排页是一份文档，直接发到手机，不走画面流。图片由服务器取回、压缩后提供，弱网时传输量小。按 §3.5 放进沙箱显示 |
| 交互 | 普通链接：在原标签页打开，再走一遍选择器。依赖原网页的按钮：重排页要记下它对应原网页的哪个元素（代码重排时由代码记下，兜底重排时用语义大纲里的元素引用），点击后在原网页执行，页面变化后重新走一遍选择器；处理不了的交给 Agent。切回原始页面：原标签页一直在，切换只是换视图，浏览进度自然保留 |

由此带来的要求：重排模式下原标签页要一直活着。空闲回收（B5）回收的是整个浏览器，要能恢复各标签页的网址和位置。

用户“带着当前页面进入对话”调整偏好时，Agent 拿到的是当前标签页、当前偏好，以及这个站的重排代码（如果有），改完重新生成。这走 §3.8 的对话办理。

### 3.8 对话办理与“一件事”

PRD 的要求见 R6、R7。

PRD 里的“Work Session”是口头说法，指用户在浏览器里办的一件事（D1）。落到 OpenDAN 上，用户能对着说话的是 UI Session；OpenDAN 的 Work Session 是 UI Session 名下执行一个 Task 的有界会话，没有消息输入（§2）。

建议的对应：

- **一件事 = MessageHub 里的一个会话（一个 UI Session）加它名下的一组标签页。** MessageHub 已经是多会话的，“新建会话”就是开始一件新事。
- **办理。** 短的由 UI Session 自己做；过程长的，UI Session 照常建 Work，Work 操作同一组标签页。用户看进度看的是这组标签页，在对话里看说明。
- **切换。** 在几件事之间切换就是切换会话，浏览器视图跟着切到那组标签页。回来时页面和进度都在（R7）。
- **跨网站。** 同一件事里新开的标签页（包括网站自己弹出的窗口）归到这件事。
- **登录状态整个 Agent 共用。** 一个浏览器用户数据目录，各件事只是标签页分组。不用 Playwright 那种互相隔离的浏览器上下文，否则每件事都要重新登录。
- **还没交代事情时。** 用户在原始页面里自己浏览、还没交代任何事，这些标签页先归哪个会话要定（Q12）。
- **提问。** 缺项用现有的 `ask_user`，问题在 App 的对话面板里显示和回答，回答由 Agent 填进页面。密码按 §3.5 交回用户。
- **预填和提交。** 预填的信息来自 Agent 的 Memory 和用户资料。提交前是否确认见 Q16。
- **结果。** 办完或卡住，Agent 在对话里说明结果，或说清卡在哪一步（PRD §四 第 3 步）。

### 3.10 成为一个 App

- 名称按 PRD 叫「Agent 浏览器」。
- 结构：先选一个 Agent（PRD：“使用某个 Agent 在 Personal Server 上运行的浏览器”），然后是地址栏、事情列表（每件事的标签页）、三种模式的切换和对话面板。按手机设计，桌面上用同一套。
- 默认入口是 PRD 待定的产品选择（R8）。技术上两种都行：从原始页面进入要先开一个标签页，从对话进入要先有一个会话。
- “用户可以直接使用”：PRD 给了方向，Owner 用的就是某个 Agent 的浏览器，Agent 随时可以协助。没有不属于任何 Agent 的浏览器（Q7）。
- 文件：
  - 上传：截下文件对话框，用系统文件选择器从 Zone 选，文件复制进 Agent 的工作目录再交给页面。
  - 下载：落在 Agent 的工作目录，一步存到 Zone；手机上默认就存到 Zone。
- 以后的私有 Win11、macOS 不放进这个 App：它们没有重排和对话模式。另给入口，共用屏幕查看组件和交接规则（§3.11）。

### 3.11 泛化到私有 Win11、macOS

- 屏幕接口与客体是什么无关。浏览器的画面来自 CDP；虚拟机的画面可以来自虚拟机管理程序（QEMU 的 VNC），也可以来自客体里的代理。查看组件按实现选解码方式，交接规则和权限共用。
- 客体里的代理已经有了：Agent Daemon 在 Windows、macOS 上能截图、输入、读语义树，并且能登记成 Agent 的一台 runtime。所以“Agent 的私有 Win11”在 Agent 这一侧，可以就是一台跑着 Agent Daemon 的虚拟机。
- 缺的是虚拟机本身：创建、镜像、资源、系统授权。这些不在本文范围，本文只保证屏幕接口将来接得上。

### 3.12 平台

- **Linux 容器。** 首期目标，也是 PRD 的主要场景（Kiosk、只用手机的用户）。
- **原生运行的 Agent**（Desktop Lite、宿主 runtime，Windows 或 macOS）。私有 runtime 是宿主上的进程。扩展包本来就有五个平台，开发测试用的浏览器可以照样提供。PRD 说 Desktop 版已经能经 ComputerUse 借用宿主浏览器，所以常驻浏览器和远程屏幕建议首期不做（Q9）。

| Q2 | 常驻浏览器跑在哪里 | 首期在 Agent 自己的容器里（§3.2 的 A），符合 PRD 的“运行在 Personal Server 上”。接口上不绑定，以后可以换成伴随容器或虚拟机 |
| Q3 | 怎么分发 | 一个独立的扩展包，默认安装，依赖 ext-core。不并入 ext-core，体积大的话低配设备可以不装。不装进工作镜像。选 CDP 时包里不需要虚拟显示和 VNC，体积主要是浏览器和运行库 |
| Q4 | 远程画面用什么（PRD 后改） | 屏幕接口不变。浏览器先用 CDP 截屏流加输入注入，不引入虚拟显示和 VNC；RFB 留给以后的虚拟机。初稿的建议是先用 RFB |
| Q5 | 谁在操作（PRD 后改） | 同一时刻一方操作，双向显式交接，Agent 也能请用户接手。用户接手时 Agent 的动作被拒，交还后重新观察。界面始终显示操作方和 Agent 的状态。初稿的建议是默认只看 |
| Q6 | 登录状态和可见范围 | 登录状态属于 Agent，放在它的实例卷里，有清除入口。默认只有 owner 能看和操作。密码见 D3 |
| Q7 | “用户可以直接使用”的范围（PRD 已给方向） | Owner 直接用的就是某个 Agent 的浏览器，Agent 随时可以协助。不做不属于任何 Agent 的浏览器 |
| Q8 | 系统服务用的浏览器（AIWS 导出 PDF、网页快照）是否纳入本文 | PRD 把导出 PDF 列为三个需求之一，由它自己的入口触发。建议仍不纳入：它以用户的身份读画布，实例和权限都和 Agent 的浏览器分开。共用同一个扩展包，另立一份 TODO。用不用浏览器渲染还取决于打印 TODO 的 Q1（渲染路线） |
| Q9 | 原生运行的 Agent | 首期只保证开发测试用的浏览器可用，不做常驻浏览器和远程屏幕。PRD：Desktop 版已经能经 ComputerUse 借用宿主浏览器 |
| Q10 | 浏览器种类 | 先只做 Chromium。Playwright 的 Firefox、WebKit 等有需要再补运行库 |
| Q11 | 名称 | App 按 PRD 叫「Agent 浏览器」。扩展包暂名 `ext-browser`，接口暂名“屏幕” |
| Q12 | “一件事”（D1）怎么落到 OpenDAN 上 | 一件事 = MessageHub 里的一个会话（UI Session）加它名下的一组标签页；办理过程长的在它名下建 Work。还没交代事情时浏览的标签页归哪个会话要定，倾向归 App 为这个 Agent 留的一个默认会话，交代事情时转到那件事 |
| Q13 | Agent 怎么操作常驻浏览器 | 经 ComputerUse 的浏览器驱动，连接由 Agent Service 持有。不让 Agent 直接用 Playwright 连常驻浏览器 |
| Q14 | 重排代码从哪里来、存在哪里（选择器本身已由 D2 定下） | 来源：常访问的站点在兜底重排之后由 Agent 写出重排代码，下次就走代码；用户在对话里调整偏好时一并改代码；代码失效时回到兜底，再由 Agent 修。存放：首期放在 Agent 的实例卷里，因为代码由 Agent 写、Agent 修；要让同一用户的几个 Agent 共用时再放到用户名下。偏好和代码都能在 App 里查看和删除。B2 的结果可能改变这条建议 |
| Q16 | 网页内容和提交前确认 | 网页内容按不可信输入对待，代办限在用户交代的目标内。D3 定的是“填”：除密码外能填就填。“提交”我建议另算：付款、对外发送、删除这类动作提交前在对话里确认一次，确认时列出 Agent 填进去的个人信息。第一期做不做由你定 |
| Q17 | 视口 | 跟随正在看的设备，手机上按手机模拟，可切桌面版。Agent 操作时不改视口 |

PRD 待定的产品选择（R8），不在本文裁决，列出技术上的关系：

- **默认入口。** 技术上两种都行（§3.10）。
- **首批场景。** 和 B2 一起选。建议避开要 U 盾、客户端控件、人脸识别的网站；短信验证码由用户在对话里告诉 Agent（D3）。
- **协作控制。** §3.4 给出了操作方和 Agent 状态的集合，文案和样式归产品。

## 6. 验收

开发测试：

- 新装的系统上，Agent 在私有 runtime 里新建一个前端项目并跑通 Playwright 测试，不需要自己安装浏览器或系统库。

原始页面模式与交接：

- 在手机上打开「Agent 浏览器」，选一个 Agent，打开一个网站：能看清、能点、能输入中文；限速的弱网下仍能用。
- 在页面上从 Zone 选一个文件上传；下载一个文件并存到 Zone。
- 用户浏览到某一页后交给 Agent，Agent 从这一页接着做。
- Agent 操作时页面对用户只读；用户接手后 Agent 停住；交还后 Agent 重新观察再继续，并且知道中间发生过接手。
- 用户接手，登录一个网站，交还；Agent 之后能以登录状态继续操作。

重排：

- 给一个旧网站设定“只看标题、日期和正文，手机单栏”，手机上按此阅读。这个站有重排代码时不调用模型；没有代码的站由 LLM 兜底重排，同样按偏好显示。
- 网站改版、重排代码套用失败时，页面仍能由兜底重排显示出来。
- 在重排页点一个依赖原网页的按钮，结果回到重排页；切回原始页面，停在同一页同一位置。

对话办理：

- 交代一件跨两个网站的事，Agent 预填已有信息，缺项（包括短信验证码）在对话里问，由 Agent 填进页面。
- 需要密码时 Agent 请用户接手，用户在页面上填；密码不出现在对话记录里，也不出现在 Agent 的观察里。
- 按 Q16 的结论：提交前 Agent 在对话里确认，并列出填进去的个人信息。
- 在两件事之间切换，回来时页面和进度都在。

通用：

- 不是 owner 的人看不到这块屏幕。
- 清除登录状态后，网站回到未登录。
- 常驻浏览器空闲后被回收，再用时能恢复各标签页和登录状态。
- 不装这个扩展包时，系统其他部分照常工作，Agent 能得到“浏览器不可用”的明确答复。

## 7. 不在本期

- 虚拟机本身：创建、镜像、资源和系统授权。
- WebRTC 画面传输。
- 不属于任何 Agent 的浏览器。
- Firefox、WebKit。
- 系统服务用的浏览器（Q8）。
- 浏览器扩展、书签同步、从用户别的浏览器导入登录状态。
- 同一块屏幕给 owner 以外的人看或操作。
- 第一期：密码以外的敏感字段交回用户填写；绕过对话、直接写进页面的补填框（D3）。
- PRD“长期判断”里超出重排模式的部分：所有网页内容先由 Agent 阅读再呈现。
