# BuckyOS Node Executor 设计思路

> 整理日期：2026-10-18  
> 文档性质：架构设计思路与协议方向稿  
> 依据：本次关于最终恢复通道、分级执行、Agent 可控设备及轻量客户端的连续讨论。  
> 状态说明：已明确的设计方向按正文记录；尚未定稿的消息字段、状态细节、加入交互和实现选择，均单独标明，不视为现有系统已经实现的能力。

## 1. 设计出发点

### 1.1 不为 Agent 远程访问再造一套安全体系

当前的直接需求是：用户将一台没有安装完整 BuckyOS 的电脑或其他终端，授权给运行在 BuckyOS 上的 Agent 使用。Agent 能够读取设备信息、操作文件、调整配置以及执行必要的任务。

这一需求不应被处理成一个孤立的“远程控制电脑”功能。BuckyOS 已有设备身份、公私钥、Zone、可信连接、RTCP、调度器、System Config 和 Node Config 等基础设施。新的设备执行能力，应尽可能建立在这些设施之上，而不是另建一套账户、认证、授权、配置分发和命令传输系统。

Node Executor 的定位是：**在设备本地承接经过授权的操作请求，按照当前安全等级、执行模式和权限配置完成执行，并返回结果。**

它不是新的调度器，不是新的身份中心，也不等同于一个默认拥有全设备权限的远程 Shell。

### 1.2 从最极端的恢复需求反推通用能力

本次讨论从一种少见但必须考虑的情况开始：设备没有显示器、键盘和鼠标，仍然能够访问外部网络，却无法连接所属 Zone，正常管理设施已经不可用。

这种情况可能发生在 OOD、普通 Node、临时托管给 Agent 的电脑，以及只允许 Agent 访问的终端上。因此，“最终恢复”首先是受管设备的通用问题，而不是某一类集群节点的专属功能。

由这一极端需求反推，可以形成统一的设计链条：

```text
Headless 设备的最终恢复需求
        ↓
正常 Zone 之外的恢复发现与最终授权
        ↓
按安全等级选择执行模式
        ↓
统一的 Node Executor
        ↓
复用于日常管理、Agent 远程使用设备和轻量客户端
```

设计目标不是让日常访问都经过急救流程，而是让日常管理与极端恢复共享执行基础，同时使用不同的授权入口和安全约束。

### 1.3 本文的范围

本文讨论协议层的身份、信道、执行授权、恢复状态和组件组合方式。不讨论 Node Executor 本身遭到入侵后如何保持可信，也不规定厂商必须采用哪种硬件、固件或可信计算实现。

协议仍然需要明确自身依赖什么可信状态，例如安全等级对应的公钥、命令执行进度和恢复等待状态。如何保护这些状态，是厂商或具体运行环境的实现责任；不能因为不规定保护手段，就省略协议所依赖的安全条件。

本文以“Agent 远程使用设备”指代口述中的 Agent Long Time 场景；Runtime 仅指可被 Agent 使用的执行环境，不据此定义另一套长期任务机制。

客户端协议网关统一使用既有工程名称 **CYFS Gateway（`cyfs-gateway`）**。口述中的 CFOS Gateway 按这一术语整理；涉及 Service Gateway 的表述，保留其“本机协议与服务访问入口”的职责含义。

## 2. 设备角色与受控能力

### 2.1 保留原来的三类基本设备角色

原有设备模型的基本角色是 Client、Node 和 Sensor。OOD 是承担关键系统服务的 Node 角色，不需要因为本次讨论而将其重定义成与 Node 完全无关的基础类别。

| 角色 | 在系统中的主要职责 | 与集群资源的关系 |
| --- | --- | --- |
| Client | 使用系统服务，作为请求发起方访问 Zone | 不向集群提供通用计算、存储和服务容器承载能力 |
| Node | 承载计算、存储以及系统或应用服务 | 是集群资源和服务承载的一部分 |
| Sensor | 获取身份后采集数据并向系统推送 | 以数据上报为主，不以访问通用服务为主要职责 |
| OOD，作为 Node 的关键服务角色 | 按本次讨论，承担 Gateway、System Config 等关键服务 | 仍属于服务节点体系 |

这里的“不提供资源”，不是说 Client 的本地操作不消耗 CPU 或存储，而是说它不把这些资源交给集群作通用调度。

### 2.2 Agent 可控 Client 不等于 Node

传统 Client 主要是单向使用服务：Client 请求服务，服务返回结果。

Agent 出现以后，Client 可以增加另一种能力：在用户授权和设备在线时，接受 Agent 发来的操作请求。设备因此成为 Agent 的受控对象，但并没有自动成为集群资源节点。

**是否提供集群资源，与是否允许 Agent 操作，是两个不同维度。**

例如，一台电脑可以允许 Agent 编辑本地文件，一台电视盒子可以允许 Agent 调整配置，但二者都不需要因此接受集群容器部署，也不需要被要求全天候在线。

本阶段将这一方向称为“Agent 可控 Client”。是否在设备模型中新增正式类型，还是为 Client 增加能力声明，尚未确定。

### 2.3 典型需求：把设备配置交给 Jarvis

用户购买或更换影音设备后，需要重新处理音频、视频、网络及其他播放配置。即使用户具备相关知识，也不愿每次重新完成全部手动设置。

目标产品体验是：设备安装或启用轻量受控组件后，用户向 Jarvis 描述配置需求，由 Agent 在设备授权范围内读取当前状态并完成调整，用户主要负责表达需求和使用设备。

这一目标不预设普通 App 能修改所有系统设置。设备实际开放哪些能力，取决于宿主权限、厂商提供的接口，以及设备端执行组件实现了什么。

## 3. 组件划分与部署形态

### 3.1 组件职责

| 组件 | 本次设计中的职责 | 不应承担的职责 |
| --- | --- | --- |
| CYFS Gateway | 复用现有协议栈、设备连接与 RTCP 能力，提供本机访问入口或相应网关能力 | 不能仅因连接可信就替所有 Agent 获得执行授权 |
| Node Executor | 校验执行条件、处理登录与操作权限、执行命令、返回结果 | 不重新建立身份中心或独立的全局授权决策体系 |
| Node Daemon | 维持现有服务节点的管理与运行职责；本次不重新定义其完整内部结构 | 不应成为所有轻量受控终端必须安装的前提 |
| Agent Daemon，暂名 | 在非完整 BuckyOS 设备上组织通信、受控执行和在线展示能力 | 不意味着本机必须运行 Agent 推理，也不意味着设备加入集群资源池 |
| Scheduler | 在正常 Zone 运行体系内形成并下发权威配置 | 不必逐条代理 Command Stream 中的执行数据 |

“Daemon”在这里是暂定组件或产品名称，不保证它在每个平台上都以常驻系统守护进程运行。

### 3.2 标准客户端：共享本机 Gateway

原有客户端的典型构成是客户端 App 加本机 CYFS Gateway。

例如，一个支持相关协议的原生播放器，通过 SDK 使用本机 Gateway。应用不应各自重新构建完整协议栈，而应复用设备已有的协议入口。部分 Zone 服务处于不能直接连接的网络环境时，继续使用既有 RTCP 连接与中转能力。

```text
本地 App / 原生播放器
          │ SDK
          ▼
本机 CYFS Gateway
          │ 既有协议、RTCP 与必要中转
          ▼
Zone 内服务
```

本次设计不改变这一复用方向。

### 3.3 轻量 Agent Daemon：进程内嵌入组件

对于不能方便部署独立后台服务的设备，可以将 CYFS Gateway 和 Node Executor 以 Library 方式嵌入普通应用。

```text
Agent Daemon App，单进程形态
┌──────────────────────────────────────────┐
│ 用户界面：设备状态、受控开关、权限说明       │
│                                          │
│ CYFS Gateway Library                     │
│   身份连接、协议栈、RTCP 与命令流承载        │
│                                          │
│ Node Executor Library                    │
│   登录、权限检查、命令处理、结果流           │
│                                          │
│ 平台适配层                                │
│   使用宿主 App 已获授权的本地能力           │
└──────────────────────────────────────────┘
```

产品可以是 Android APK、iOS App 或其他平台应用，而不必安装完整 BuckyOS。具体平台能开放哪些 API、允许怎样的后台运行，需要在实现时另行确认，本文不作平台能力保证。

独立服务与嵌入式 Library 应尽量共享协议和核心逻辑，而不是形成两套互不兼容的 Executor。

### 3.4 网关组件不等于 OOD 角色

Client 运行一个供本机使用的 Gateway，或者 App 嵌入 Gateway Library，不等于它承担 Zone 的核心网关服务，也不因此成为 OOD。

需要区分“使用网关组件”和“承担集群关键服务角色”。否则，轻量客户端一旦嵌入协议栈，就会在概念上被错误升级为服务节点。

对于已经存在独立 Gateway 的设备，Agent Daemon 应如何复用既有实例；对于多个相互隔离的 App，协议栈实例和设备身份如何协调，属于待明确的部署规则。

## 4. 统一安全模型

### 4.1 两种授权环境

**正常 Zone 环境**依赖现有身份体系、可信设备连接和 Scheduler 下发的有效 Node Config。日常运行不应依赖 Owner 私钥。

**最终恢复环境**用于 Zone 不可达的极端情况，依赖 Zone 外部公共基础设施发现恢复状态，并通过 Owner 最终授权进入受约束的恢复流程。

Scheduler 是正常运行体系中的最高信任配置来源；Owner 则承担正常体系之外的最终授权根。二者处于不同层次，不应混淆为两个并行争夺日常控制权的管理者。

### 4.2 Owner 私钥不进入日常运行依赖

系统正常工作应使用已有的低一级权限凭据，不要求 Owner 私钥常驻 Agent、设备端执行进程或日常系统服务。

Owner 私钥在最终恢复场景中用于授权恢复状态变化，但不因此变成一个可以随时对所有设备立即执行任意命令的凭据。

具体脚本签名使用 Owner 密钥还是符合当前等级的另一把授权密钥，不能一概而论，应由对应安全等级规则确定。

### 4.3 安全等级决定允许的执行机制

Node Executor 根据当前安全等级，选择可接受的执行模式和可信公钥。

本次不预设 L0、L1 等固定等级编号，也不假定所有设备都支持相同等级。已经明确的是：不同等级可以对应不同的签名信任关系、连接准入和执行机制。

安全等级、公钥及其更新规则需要受到相应保护。厂商可以选择使普通程序乃至已取得操作系统高权限的程序，仍不能随意改写这些信任依据。是否依赖重启、固件操作或其他保护手段，不在本协议中固定。

### 4.4 将连接、登录与操作权限分开

日常命令流中的安全判断分成三个层次：

```text
设备级：这个对端能否与本设备建立命令信道？
        ↓
身份级：这个 User / Agent 能否登录此 Command Stream？
        ↓
操作级：已登录主体被允许执行哪些操作？
```

可信设备可能只是中转者，不能把中转设备的可信身份直接替换成真实 Agent 的身份。

Stream 完成一次身份认证以后，不需要逐命令重新登录；但每个操作仍受会话已取得的权限约束。**免去重复认证，不等于免去操作授权检查。**

### 4.5 Node Config 统一承载正常授权

Node Executor 使用经现有配置体系取得的有效 Node Config，不再创建另一套分散的授权事实来源。

从职责上看，配置需要能表达允许的连接设备、允许登录的 User/Agent，以及相应操作权限。具体字段名称和结构尚未确定。

这里的“信任 Node Config”，是信任由既有可信分发机制交付的调度器配置，不是信任任意同名文件，也不是通过普通网络下载到一份 JSON 后就接受它。

对于 Client，复用这一配置体系不应自动让它成为集群资源 Node。设备执行配置与资源调度资格需要分开表达。

## 5. 执行模式一：签名命令拉取与顺序执行

### 5.1 模式定位

第一种模式具有较强的单次操作授权约束，适合最终恢复等高安全要求场景。

设备主动查询待执行命令，取得完整签名的脚本，按照当前安全等级对应的可信公钥验签。执行完成后，按命令 ID 回报状态和结果，再继续查询新的命令。

这里的“完整签名”指脚本的完整内容及必要执行上下文受到签名保护；不要求逐字节分别签名，也不能只签一个与脚本内容没有可靠绑定的下载地址。

恢复服务负责分发命令和收集结果。**控制恢复服务器或 HTTPS 端点，不等于自动具有命令授权权力。**

### 5.2 基本交互

```text
Node Executor                         恢复端
      │                                  │
      ├── 查询当前命令 ID / SEQ ─────────→│
      │←─ 当前序号、命令内容、签名 ────────┤
      │                                  │
      │  根据安全等级验签、检查 SEQ        │
      │  执行脚本                         │
      │                                  │
      ├── 按 ID 上报状态与执行结果 ───────→│
      │                                  │ 按需要发布更大 SEQ
      ├── 再次查询 ──────────────────────→│
      │←─ 新命令或暂无新命令 ─────────────┤
```

命令 ID 可以直接使用单调递增序号，也可以与 SEQ 建立明确绑定。本次不要求一定存在两个独立字段。

### 5.3 SEQ 负责防止旧命令重放

恢复端后续发布的命令使用更大的 SEQ。Node Executor 维护本地已认可的序列进度，随着进度推进，旧序号的签名命令不再具有执行资格。

例如，本地进度已经推进到 104，则攻击者重新提交签名仍然有效的 101、102 或 103，也不能使设备再次执行这些旧命令。已经消费的 104，同样不能仅因再次被查询到就自动重新执行。

本次思路要求的是严格递增，不要求每个数值连续出现；也不应默认把服务器上的所有旧命令当成待补跑的历史队列。

必须明确：**本地进度只能因经过认证的有效命令而推进，不能因为服务器声称存在一个更大的数字就直接更新。** 否则，未授权的序号仍然可以破坏后续执行。

签名与 SEQ 各自承担不同职责：签名证明操作获得授权，SEQ 约束旧授权能否再次触发执行。

### 5.4 顺序执行不等于自动获得“恰好一次”语义

本模式按顺序处理命令，但执行、记录状态和上报结果之间仍可能发生中断。

例如脚本已产生效果，但结果尚未上报时设备断电。设备重启后，不能仅因恢复端“没有收到结果”，就无条件再次执行同一脚本。

协议定稿时，应明确至少三种不同事实：命令已经接受、命令执行状态、结果是否成功送达。重发结果与重跑脚本必须分开。

SEQ 用于拒绝旧请求，不会自动使脚本本身变成幂等操作，也不自动解决断电后的执行状态判断。

### 5.5 本模式待补全的协议细节

| 项目 | 需要明确的语义 |
| --- | --- |
| 签名覆盖范围 | 除脚本内容外，如何绑定 SEQ、目标设备或目标范围、当前授权上下文，避免跨设备或跨恢复轮次挪用 |
| 进度推进时点 | 验证通过、接受执行、开始执行或完成执行分别更新什么状态 |
| 进度持久化 | 重启后如何维持反重放保证，不因进度丢失重新接受旧命令 |
| 失败与重试 | 失败命令是否消耗序号、如何以新授权恢复、结果丢失如何重报 |
| 序列作用域 | 全设备、安全等级、授权主体或恢复轮次是否共用序列 |
| 结果真实性 | 恢复端如何确认结果来自目标设备，并与对应命令绑定 |

这些项目是对当前协议方向的完善要求，不代表消息格式或存储方案已经定稿。

## 6. 执行模式二：可信 Tunnel 上的 Command Stream

### 6.1 模式定位

第二种模式面向日常使用：建立可信信道，在命令流上完成一次登录，然后持续执行操作并双向传输数据。

它在交互体验上类似一个使用 BuckyOS 身份体系的远程执行会话，但不要求采用完整 SSH，也不意味着必须提供全部 SSH 功能。

与第一种模式相比，本模式不要求每条命令都独立签名。其授权依据是经过认证的信道、流上登录的真实主体，以及 Node Config 中的操作权限。

### 6.2 第一步：可信设备建立连接

Node Executor 根据当前安全等级和配置，判断对端设备的公钥身份是否在允许范围内。

连接可以主动发起，也可以被动接受，不需要把建立方向规定为唯一形式。重要的是对端设备符合准入要求，并且连接按既有机制完成认证。

底层优先复用已有 RTCP 能力。是否支持 SSH 或其他实现，是传输与平台实现选择，不改变上层的身份和权限模型。

### 6.3 第二步：每个 Command Stream 完成一次 Login

Tunnel 建立以后，在其上打开 Command Stream。真实操作主体在此 Stream 上登录。

登录应使用既有 User ID 与 Agent ID 模型，识别是谁、由哪个 Agent 发起操作，以及其被配置允许做什么。仅提交一个 Agent ID 字符串不是身份认证；如何提供身份凭据，复用系统已有体系，不在这里再发明一套。

即使同一可信 Tunnel 上已经有一个登录成功的 Stream，新 Stream 的授权也不能仅凭“共享一条 Tunnel”就自动获得。每个流应取得与自身一致的登录和权限上下文；具体是否复用既有认证材料，由协议实现明确。

登录通过后，流上不需要逐命令重复身份认证，但操作不能超出该登录上下文的授权范围。

### 6.4 第三步：双向流式执行

Command Stream 是双向流，允许操作开始后持续返回输出，而不是必须等完整脚本结束才报告。

```text
建立可信 Tunnel
      ↓
打开 Command Stream
      ↓
Login：识别 User / Agent，取得权限上下文
      ↓
命令输入  ←────────────→  持续结果 / 字节流输出
      ↓
流结束，当前登录上下文随之结束
```

消息分帧、多个命令如何区分、是否允许同一流并发、取消和断线后的任务语义，都属于后续协议细节。当前已明确的是流式交互方向，不预设某种终端或 RPC 格式。

### 6.5 点对点优先，允许一次可信中转

系统的协调角色主要处理身份、配置和连接建立。进入执行阶段后，命令和输出不应被设计成每一条都必须往返调度器。

可直接建立连接时使用点对点信道；需要中转时，典型结构如下：

```text
受控设备 / Node Executor ── Tunnel A ──┐
                                       │
                                可信 OOD / Gateway
                                       │
Agent 所在设备 ──────────── Tunnel B ──┘

中转设备对两条连接中的相关流进行关联与复制：
Agent  ═══════ Command Stream，经一次中转 ═══════  Node Executor
```

Agent 可以请求可信中转设备接通两侧的流。Node Executor 接受中转设备的连接，不代表它忽略最终 Agent 的身份；真实操作者仍须在 Command Stream 上登录。

“一次中转”描述的是预期拓扑和数据路径，不自动承诺端到端加密，也不自动规定中转端能否读取命令内容。相关保密性边界应在传输方案中明确。

### 6.6 本机回环监听只是部署选择

独立系统服务形态下，Node Executor 可以监听 `127.0.0.1`，由已建立的可信信道接入，而不是直接暴露公网执行端口。

嵌入式 Library 形态下，可以在进程内交付 Command Stream，不必为了形式一致再增加一个本地监听端口。

回环监听解决的是入口暴露问题，不代替登录与操作授权。不能因为请求最终来自本机接口，就自动认为它来自合法 Agent。

## 7. 命令能力与权限边界

### 7.1 初期只开放四类能力

Agent 远程使用设备的初期需求，先围绕 Read、Write、Edit 和 Execute 四类操作展开，不直接开放一整套远程系统管理功能。

| 能力 | 基本目的 | 应由权限规则约束的内容 |
| --- | --- | --- |
| Read | 读取授权资源或状态 | 可读范围与敏感信息边界 |
| Write | 写入授权目标 | 可写范围及写入条件 |
| Edit | 修改已有内容 | 可修改对象与修改范围 |
| Execute | 执行设备提供的命令或操作 | 允许的执行能力及实际影响范围 |

这是能力方向，不是已经确定的函数签名。文件、配置和平台能力怎样映射到具体接口，还需要平台适配层定义。

### 7.2 少量接口不等于天然低权限

只提供四个接口，并不自动意味着能力很弱。若 Execute 可以任意运行高权限程序，它仍可能绕过 Read、Write、Edit 的表面限制。

因此，“只读 Agent”不仅是隐藏 Write 和 Edit；还需要保证其允许的 Execute 不产生与只读授权矛盾的效果。此处应在操作授权和设备适配层处理，不能仅凭接口数量宣称安全。

这一点是当前最小能力方向必须保持的边界，并不要求现在就引入某一种新的沙盒实现。

### 7.3 BuckyOS 授权与宿主权限取交集

对一个已经通过信道和登录检查的主体，其最终能够使用的操作范围受到以下共同限制：

```text
最终可执行范围
    ⊆ Node Config 授权范围
       ∩ 宿主操作系统实际授予的权限
       ∩ Node Executor / 平台适配层已实现的能力
```

Node Executor 是系统服务时，可以具有其被授予的系统级能力；嵌入普通 App 时，其操作不能自然超出 App 的权限范围。

厂商预装、更高权限版本与普通安装版本，可以使用相同协议，但不能对外宣称拥有相同的设备管理能力。

### 7.4 SSH 不是本阶段的主要决策

是否采用 SSH，需要结合跨平台实现、维护成本与实际能力需求判断；不能简单把 SSH 等同于 Linux 专属能力，也不应认为需要远程命令就必须启用完整 SSH 功能集合。

当前明确的取舍是先保留较小的能力边界，不默认加入动态代理、额外端口转发、完整文件传输子系统等并非当前必需的能力。

后续即使使用 SSH 作为某种实现，也应继续保持既有设备身份、User/Agent 登录和操作权限约束，而不是让传输协议反过来定义产品的全部授权范围。

## 8. 最终恢复通道

### 8.1 启用条件：Zone 不可达

当前设计的最终恢复入口只在设备无法连接所属 Zone 时启用。

设备必须仍能运行恢复所需的最小逻辑，并具备访问相关公共基础设施的网络条件。DNS、BNS 等名字系统在这里是 Zone 外部依赖，而不是“任何联网情况下都必然可达”的保证。

Zone 正常可达时，设备使用已有常规管理体系，不依赖这一恢复入口。本文不把它扩展成一个常年并行的远程执行通道。

### 8.2 通过公共名字设施发现恢复状态

设备属于一个 Zone，能够通过公共名字系统取得相关 Zone Config 或恢复信息，并已具有可据以验证 Owner 授权的信任依据。

设备查到的恢复声明可以作用于整个 Zone，也可以仅针对指定设备。设备需要判断声明是否有效，以及自身是否被纳入范围。

```text
无法连接 Zone
      ↓
查询 DNS / BNS 等 Zone 外部公共设施
      ↓
验证恢复声明的 Owner 授权
      ↓
判断目标范围：整个 Zone / 指定设备
      ↓
本设备被纳入时，进入 Frozen
```

公共设施承担发现和分发职责。即使其内容可被读取，或者其发布账户具有写权限，也不应取代设备对恢复授权的验证。

本设计所说的“只有 Owner 私钥才能改变状态”，应落实为：**设备只承认满足 Owner 授权规则的恢复状态变化**，而不是仅依赖 DNS 后台的账号权限。

Owner 公钥的初始可信来源，以及后续轮换规则，应与已有设备身份体系衔接；不能仅因为某次查询同时返回了一把公钥和一份声明，就自证两者可信。

### 8.3 第一阶段：确认声明后立即 Frozen

设备确认有效恢复声明且自身在范围内后，立即进入高安全待恢复状态。

Frozen 的目标是阻断原有常规指令路径，防止已泄露的日常管理权限继续被使用。它并不意味着所有进程和网络都停止：用于查询恢复状态、验证授权、维持等待期以及接收纠正状态的最小逻辑仍需能够工作。

“立即”指设备确认声明后的本地状态切换，不指 Owner 发布时刻所有设备同时生效。离线或尚未完成查询的设备，不能被认为已经冻结。

已经开始的命令如何停止、普通业务服务是否继续运行，以及具体冻结范围，尚未定稿。对普通 App 而言，冻结首先只能约束其自身暴露的执行能力，不能把 App 级冻结等同于整个操作系统冻结。

### 8.4 第二阶段：强制等待后才允许恢复执行

设备进入 Frozen 后，恢复执行权不立即开放。必须经历一个强制等待期，之后才具备建立恢复命令通道的资格。

24 小时只是本次讨论的示例值，不是最终常量。按当前口述，等待发生在设备进入 Frozen 之后；协议仍需明确计时、持久化和重启处理。

```text
Owner 发布恢复声明
        ↓ 设备后续查询并确认，存在传播与发现时间
设备进入 Frozen
        ↓ 强制等待期，例如 24 小时，数值待定
具备恢复通道启用资格
        ↓ 当前恢复授权仍有效，配置符合规则
建立恢复通道并执行恢复
```

这一设计把两种权力在时间上分开：合法 Owner 可以先阻断失控的常规执行路径，但新获得 Owner 私钥的人不能立即取得全部设备的完整远控能力。

等待期间应允许用户发现异常，并通过后续规定的公共纠错或撤销流程阻止非法恢复。

必须保留一个未解决的条件：**等待期只提供干预时间，并不自动提供纠错权。** 若合法用户和攻击者都能使用同一把已泄露私钥，设备不能仅凭同一种签名区分二者。私钥泄露后的撤销、替换或争议处理机制仍需单独明确。

### 8.5 动态指定恢复端点

恢复通道不能预设 Zone 内仍有另一台健康设备，也不能写死必须连接某个既定恢复主机。

Owner 应能在故障发生后，通过已授权的公共恢复信息指定 HTTPS 或其他合适的 URL。设备主动连接该入口，获取更完整的恢复执行配置。

获取配置以后，可以进入两条路径：

| 路径 | 行为 |
| --- | --- |
| 一次性或连续的签名恢复命令 | 下载符合当前安全等级的签名脚本，按模式一执行并回报；需要继续修复时发布更大 SEQ |
| 建立持续恢复信道 | 按配置使用 RTCP 等机制连接指定端点并保持 Tunnel，再按允许的模式接入 Node Executor |

恢复配置可在急救时调整，但配置变化不能成为绕过签名、等待期或真实身份授权的捷径。

具体需要区分哪些修改只是端点迁移，哪些修改改变授权范围并需要重新等待。此规则尚未确定。

### 8.6 恢复状态不是普通 Command Stream 权限

恢复声明版本、撤销状态、等待期和脚本 SEQ 具有不同职责，不能假定一个递增命令序号就解决全部恢复控制问题。

同样，建立恢复 Tunnel 也不意味着此前设定的安全等级自动降低。恢复阶段允许哪种执行模式、使用哪个等级的密钥、是否需要重新建立流上登录，应由恢复授权和设备当前状态共同决定。

### 8.7 恢复完成与退出条件待明确

目前已经明确了入口、冻结、等待和恢复连接方向，但尚未规定何时恢复普通运行。

协议需确定：恢复成功由谁确认；重新连接 Zone 是否足以退出 Frozen；旧恢复声明怎样结束；执行中的修复任务怎样收尾；恢复期间信道中断后是否继续保持冻结。

另外，当前入口只在 Zone 不可达时使用。因此，对“常规权限被盗但设备仍正常连接 Zone”的情况，本文不直接声称 Owner 能通过同一入口完成全局冻结；是否允许在线设备也响应某类最终止损声明，需要另作决策。

## 9. 设备加入、上线与使用生命周期

### 9.1 复用已有加入体系，不新增孤立账号体系

本次讨论尚未把首次配对和设备加入的交互完整定稿。已经明确的是，新受控设备需要复用既有 Zone、设备身份和配置体系，而不是只输入一个远控地址就自动获得全部信任。

从运行条件反推，加入完成后至少应能回答：设备属于哪个 Zone，信任什么身份依据，允许连接哪些设备，接受哪些 Agent 登录，以及实际提供哪些操作能力。

这些是加入后的必要结果，不代表已经确定采用扫码、邀请码或某种新的证书流程。

### 9.2 建议的逻辑阶段

以下流程是对已讨论条件的组织，不是已定稿的入网消息协议：

```text
安装、预装或启用 Agent Daemon
        ↓
沿既有机制建立设备身份、Zone 归属与初始信任
        ↓
取得适用于该设备的有效执行配置
        ↓
在宿主允许范围内启动 Gateway / Executor
        ↓
连接允许的设备或可信 OOD / Gateway
        ↓
向 Agent 体系呈现可用 Runtime 与当前能力
        ↓
Agent 建立 Command Stream 并登录
        ↓
在已授权范围内使用设备
```

向 Agent 呈现 Runtime，不等于调度器可以向这台设备部署任意服务。Runtime 可访问性与集群资源可调度性继续分离。

### 9.3 上线状态与长期身份分开

设备可能保留长期登记和授权关系，但只在用户主动启用时提供执行能力。

例如用户打开 Agent Daemon App，界面说明当前设备允许已授权 Agent 操作；App 建立连接后，Agent 发现该设备在线。用户退出或明确关闭受控功能后，应撤销当前访问路径，并让 Agent 侧不再把它视为可用 Runtime。

“退出即下线”是本次提出的产品行为目标。它需要通过连接和执行生命周期实现，而不是假定任何平台上的关闭窗口行为都会自动终止后台服务。

正常退出、进程异常终止、系统挂起和网络中断的可观测时间不同。具体探测和通知机制尚未决定，不能把设备过去上线过当成现在仍可执行。

### 9.4 退出后的在途任务

App 退出时，后续命令应不再通过该访问入口被接受。但已经开始的操作是立即取消、尽力中止，还是允许在已授权范围内收尾，需要按操作性质定义。

尤其不能把“Agent 已无法连接”直接等同于“设备上的一切已开始操作都停止”。命令断线语义应与模式二的执行状态规则共同制定。

### 9.5 普通 App 不自动具备无人值守急救能力

最终恢复和轻量客户端可以共享协议，但它们的运行保障并不相同。

普通 App 未运行或已被宿主停止时，不能依靠它持续查询公共恢复声明。厂商预装或具有适当后台保障的版本，才可能承担更强的无人值守恢复职责。

因此，应把“支持某种恢复协议”与“在指定故障状态下保证恢复组件仍运行”分别说明，不对所有 Agent Daemon 安装形态作同等保证。

## 10. 两种执行模式的统一关系

| 维度 | 模式一：签名命令顺序执行 | 模式二：认证命令流 |
| --- | --- | --- |
| 主要方向 | 高安全要求下的受控执行，尤其是恢复 | 日常设备操作、远程管理与 Agent 使用 |
| 命令来源 | 主动拉取签名脚本 | 已建立 Command Stream 上的输入 |
| 核心授权 | 当前安全等级对应的命令签名 | 设备信道准入、User/Agent Login、操作权限 |
| 身份校验单位 | 每条命令的授权校验 | 每个 Stream 的登录认证 |
| 旧请求处理 | 单调 SEQ 排除旧命令重放 | 流的认证、会话与执行状态规则，细节待定 |
| 结果形式 | 执行后按命令 ID 上报 | 双向流式输出 |
| 传输依赖 | 公共恢复入口等分发路径 | RTCP 等可信连接，允许中转 |
| 本地执行主体 | Node Executor | Node Executor |

安全等级决定某一时刻允许哪些模式。不能机械地认为第一种只可能用于恢复，或第二种永远不能用于恢复；恢复阶段能够建立哪类通道，仍由当时的授权规则控制。

Node Executor 统一的是本地执行与权限实施能力，而不是把所有场景强行压成同一种连接或认证过程。

## 11. 协议定稿前的主要决策项

| 决策项 | 当前已明确 | 尚需确定 |
| --- | --- | --- |
| 安全等级 | 等级与可信公钥、执行模式有关 | 等级列表、转换条件及各模式允许范围 |
| 配置分发 | 正常运行信任 Scheduler 经既有体系提供的 Node Config | 轻量 Client 对应的配置结构、更新时机与失效语义 |
| 首次加入 | 复用既有身份与 Zone 体系 | 具体配对交互、初始信任取得及配置授权流程 |
| 签名命令 | 完整内容受保护，按 SEQ 单调推进 | 签名字段、作用域、持久状态与失败恢复规则 |
| Stream 登录 | 每个命令流一次登录，识别真实 User/Agent | 凭据如何绑定流、中转链身份保证、会话有效期 |
| 操作授权 | 由本地 Executor 执行配置，允许只读等差异 | Execute 与只读/写入权限的一致性、能力粒度 |
| 配置更新 | 权威来源不另建 | 已登录 Stream 遇到撤权、身份或安全等级变化时如何处理 |
| Frozen | 确认恢复后立即限制常规控制 | 在途任务、业务服务、设备级与 App 级冻结范围 |
| 等待期 | 冻结后有强制延迟，24 小时仅为示例 | 起算与可信计时、重启规则、敏感修改是否重新等待 |
| 私钥泄露纠错 | 需要为合法用户留下干预窗口 | 不依赖同一泄露私钥的有效纠错或撤销依据 |
| 恢复退出 | 恢复目标是重新取得正常管理能力 | 退出确认者、与 Zone 重连的关系、旧声明失效规则 |
| 部署一致性 | 独立服务与嵌入式 Library 共享协议方向 | 已有 Gateway 复用、多 App 实例与身份协调 |

这些问题应在统一协议内逐步补全，不应通过给每种设备单独添加一套认证路径来解决。

## 12. 后续验证场景

以下是根据本次设计整理的验证目标，不表示已有实现已经通过测试。

| 场景 | 应验证的行为 |
| --- | --- |
| 对端设备不在信道准入范围 | 不因其能到达端口或中转节点就建立可用执行通道 |
| 中转 OOD 可信，但 Agent 不允许登录 | Tunnel 可以存在，Agent 的 Command Stream 仍被拒绝 |
| 同一 Tunnel 上由另一 Agent 打开新 Stream | 不继承前一 Agent 的登录身份和操作权限 |
| Agent 仅具有只读授权 | 不允许直接写入，也不能通过已开放 Execute 绕过只读约束 |
| 合法旧脚本被再次提供 | 依据本地 SEQ 拒绝重新执行 |
| 服务器提供未授权的大 SEQ | 不推进本地有效执行进度 |
| 脚本已执行但结果上报中断 | 区分结果重报和脚本重跑，不因未收到回报就无条件重执 |
| 设备发现有效恢复声明 | 本地及时进入 Frozen，但等待期内不开放完整恢复执行 |
| Owner 已发布声明但设备尚未查询到 | 不把该设备标为已冻结 |
| 恢复端点在故障后调整 | 能按有效配置迁移，同时不能绕过既有授权和等待规则 |
| Zone 正常可达 | 日常访问无需 Owner 私钥，也不依赖急救入口 |
| 轻量 App 停止提供受控服务 | 关闭相关访问路径，更新可用状态，并按既定规则处理在途任务 |
| App 版本权限较低 | 同一协议下只能开放其宿主权限支持的实际能力 |

## 13. 总结

BuckyOS Node Executor 应成为一个可以独立运行、也可以嵌入应用的本地执行组件，为不同设备复用统一的身份、连接和权限基础。

日常场景采用“可信设备连接 → Command Stream 登录 → 按 Node Config 执行操作”的路径；高安全场景可以采用“签名脚本 → 单调 SEQ → 执行并回报”的路径。两种模式通过当前安全等级连接起来，而不是各自形成独立的远控体系。

最终恢复以 Zone 外部公共基础设施为发现入口，以 Owner 为最终授权根，通过“先冻结、再等待、后恢复执行”限制最终凭据的即时滥用；它不依赖某台预先指定且必须健康的 Zone 内恢复主机。

面向普通用户的 Agent 可控设备仍可属于 Client。通过轻量 Agent Daemon，在应用内组合 CYFS Gateway、Node Executor 和平台适配能力，便可按需向 Agent 提供执行环境，而无需把设备升级成全天候集群节点。

**整体方向是：设备角色与受控能力分离，连接身份与操作身份分离，日常授权与最终恢复分层，配置统一来源，权限在设备本地执行；先提供当前确实需要的能力，再逐步扩展。**
