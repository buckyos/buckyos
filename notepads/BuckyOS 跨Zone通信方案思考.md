# BuckyOS 跨Zone通信方案思考

> 整理日期：2026 年 10 月 29 日  
> 文档性质：方向性架构讨论稿  
> 整理依据：本轮七段口述，以最后提出的“RTCP / HTTPS 统一登录换取 Token”方向为准；术语及用户唯一 canonical zone 的约束沿用此前确认的定义。

## 一、方案概述

BuckyOS 跨 Zone 通信以 **DID 作为身份入口，以 RTCP 作为首选传输，以 HTTPS 作为不可达时的降级传输，以目标 Zone 的 `verify-hub` 作为统一身份认证入口**。

无论底层最终采用 RTCP 还是 HTTPS，跨 Zone 调用方都先向 Target Zone 的 `verify-hub` 登录，取得由 Target Zone 签发的 Session Token，再携带该 Token 访问目标业务服务。业务服务继续采用现有的 Token 验证与业务授权机制，不再分别维护“Zone 内认证”和“Zone 外认证”两套实现。

RTCP 提供的可信设备身份仍然重要，但它主要服务于网关准入和跨 Zone 登录，不直接替代用户、应用的业务身份。Device、Zone、User 等身份之间的关系验证，统一收敛到 `verify-hub`，而不是分散到每个业务服务。

连接发现、RTCP 探测、HTTPS 降级、反向建连、RTCP 恢复后的切换，以及集群内连接可用性的共享，应尽量由 SDK 与 Gateway 封装。应用面对的是“访问某个 Target Zone 的某个服务”，而不是自己选择和维护一套跨 Zone 传输协议。

**整体分工：传输层解决如何连通，身份层解决谁在调用，业务层解决允许做什么。**

## 二、问题范围：跨 Zone 要解决什么

讨论的共同前提是：调用方已经知道 **Target Zone 的 DID**。

跨 Zone 的核心需求分为两类。

### 2.1 向目标 Zone 投递信息

调用方需要向 Target Zone 投递一条信息，例如向目标用户的 Inbox 投递消息。这是本轮讨论中最重要、最基础的一类需求。

这里不仅需要解决网络可达性，还需要让接收方判断消息的来源身份是否成立，以及是否允许该身份执行投递。

### 2.2 读取目标 Zone 的内容

调用方需要通过 BuckyOS 自身的系统服务接口，读取另一个 Zone 中的内容或资源。

已经公开、可以直接通过普通 HTTP / HTTPS 访问的内容，不属于本次重点。讨论聚焦于需要使用 BuckyOS 身份、服务接口或权限体系的跨 Zone 访问。

### 2.3 本文的边界

本文覆盖连接发现、传输路径、身份建立、Token 使用和基础设施分工，不定义消息格式、Inbox 投递规则、具体内容服务的数据模型，也不冻结 RTCP 线协议、SSO 请求字段或 Token Claims 格式。

消息投递与内容读取可以共用基础设施，但是否接受消息、是否允许读取或写入，仍由具体业务服务决定。

## 三、术语与身份边界

| 术语 | 本文含义 |
| --- | --- |
| Source Zone | 发起此次跨 Zone 请求的一方。口述中的“当前 Zone”在描述连接时通常指这一方。 |
| Target Zone | 接收此次跨 Zone 请求、提供目标服务的一方。 |
| canonical zone | 某个 User DID 唯一指定的身份所属 Zone。此前讨论也使用 `current zone` 表达这一概念。它不等于“当前正在访问的 Zone”。 |
| Zone DID | Zone 的身份标识，不以 Hostname 替代其根身份地位。 |
| Device DID | 设备身份。RTCP 对端认证直接建立的是这一层身份。 |
| User DID | 用户的全局身份。用户是否由某个 Zone 代表，需要独立验证。 |
| App ID | 调用应用的身份标识。Zone 内短名称如何扩展为跨 Zone 无歧义标识，尚需明确。 |
| `verify-hub` | Zone 内负责身份验证和 Session Token 签发的系统组件。语音中的 World Hub、Waterhub 等统一为此名称。 |
| `cyfs-gateway` | 本轮讨论中承载用户态协议栈及相关代理、网关能力的组件。Service Gateway、Node Gateway 在下文描述逻辑职责，不预设必须拆成独立进程。 |
| RTCP Tunnel | 按本轮设计设想，由设备身份参与建立、可保持一段时间并复用的双向通信通道。 |
| Session Token | 业务服务采用的会话身份凭据。跨 Zone 常规调用最终使用 Target Zone 自己签发的 Token。 |

### 3.1 来源 Zone 与 canonical zone 不能混为一谈

Source Zone 描述请求从哪里发出；canonical zone 描述谁有资格为某个用户身份提供跨 Zone 认证来源。两者在常规场景中可以是同一个 Zone，但概念上不能合并。

沿用此前已确认的约束：同一用户在同一时刻只有一个 canonical zone。用户可以在其他 Zone 拥有 Local User、Profile 或访问会话，但这些记录不会自动赋予其他 Zone 代表该 User DID 向第三方认证的资格。

因此，对用户身份的跨 Zone SSO，应回到该用户唯一 canonical zone 的 `verify-hub` 所提供的认证依据。不能仅因为某个设备属于 Source Zone，或者 Source Zone 保存了一个同名用户，就接受其代表该 User DID 的声明。

Target Zone 为外部用户签发本地 Session Token，也不会因此成为该用户的 canonical zone。

### 3.2 设备身份不等于业务身份

一个经过 RTCP 验证的 Device DID，可以证明通信对端的设备身份；它并不直接证明 HTTP 请求中填写的 User ID、App ID 或业务角色。

口述中“用 service 身份登录”的方向，落到这里应理解为：**使用已经建立的可信设备／服务来源上下文，加上本次调用所需的业务身份材料，向 `verify-hub` 登录。** 不把它理解为 RTCP 自动证明了任意服务、用户或应用身份。

## 四、基础协议选择：RTCP 优先，HTTPS 兼容

### 4.1 为什么不把 HTTPS 作为原生通信首选

BuckyOS 的 Zone 需要支持浏览器访问，HTTPS 因此是现实中必须保留的入口。但浏览器兼容性不应反过来决定 BuckyOS 原生跨 Zone 通信的根身份体系。

本轮明确的长期方向是：使用 DID 标识 Zone，使用 DID Document 等身份资料建立验证依据，逐步形成不以传统 CA 证书体系为根本依赖的原生通信能力。

DID 可以被映射为 Hostname，也可以通过某种外部设施发现访问地址，但 Hostname 是定位或兼容手段，不应取代 DID 成为根身份。

当通信双方都使用 BuckyOS 原生能力时，应优先使用基于 DID / DID Document 的 RTCP，而不是为了复用浏览器入口，把原生身份认证重新绑定到域名和 CA 证书上。

### 4.2 HTTPS 的定位

HTTPS 有两个明确用途：一是兼容既有浏览器；二是在 RTCP 无法建立时，为跨 Zone 通信提供降级路径。

这不是放弃 DID，而是在同一套身份目标下保留不同的传输方式。使用 HTTPS 连接某个地址，仍然需要把该入口与目标 Zone 身份建立可靠对应。

“去 CA”是长期架构目标，不意味着使用 DID 这一名称就已经消除了所有依赖。若某一阶段仍使用 HTTPS 获取身份资料或承载 SSO，该路径仍需考虑相应的发现与信任依赖。

## 五、RTCP 连接发现、端口与 Relay

### 5.1 复用已有连接流程

本轮口述认为，现有节点连接 SN 等基础设施时，已经具备标准的 RTCP 连接流程。跨 Zone 通信应优先复用这些机制，而不是另造一套建连协议。

真正需要补齐的是：从 Target Zone DID 出发，找到合适的目标设备、验证其身份，并获得可以连接的 Endpoint。

RTCP 协议栈是设备级的。因此，“连接某个 Zone”最终会落实为连接该 Zone 中有资格代表它的某个设备，而不是把 Zone DID 与 Device DID 当成同一个对象。

### 5.2 直连要求可达的 TCP Endpoint

按本轮方案，RTCP 基于 TCP。直接建立连接需要目标具备互联网可达的 TCP Endpoint，例如公网 IPv4、IPv4 端口映射，或具有可达性的 IPv6 地址与端口。

能够取得一个地址，不等于这个地址一定能够连接；最终仍需由连接过程判断可达性。

### 5.3 默认端口与自定义端口

本轮口述使用的 RTCP 默认端口为 **`2980`**，并明确指出可配置端口从 RTCP 初始设计阶段就已存在，应把已有机制用起来。

典型场景是同一家庭内的多台设备共享一个公网 IPv4。各设备内部都可以监听 `2980`，但对外映射需要使用不同的端口。例如：

| 对外入口示例 | 内部目标示例 |
| --- | --- |
| 公网地址的 TCP 2980 | 设备 A 的 TCP 2980 |
| 同一公网地址的 TCP 2981 | 设备 B 的 TCP 2980 |
| 同一公网地址的 TCP 2982 | 设备 C 的 TCP 2980 |

以上端口映射仅作说明，不是新增配置规范。对外发现信息必须表达客户端实际应连接的入口，不能把设备内部监听端口与公网映射端口混淆。

这里的关键不是“浏览器是否允许非默认端口”，而是 **原生客户端能够依据 Zone 的公开发现信息，选择 RTCP 的实际连接入口**。

### 5.4 连接配置必须能在 Zone 外发现

调用方不能先连进 Target Zone，才能知道该如何连接 Target Zone。相应信息应能通过 DID 解析、DNS 或其他 Zone 外部设施发现。

公开信息至少需要能够表达以下几类语义：

| 语义 | 预期用途 |
| --- | --- |
| 直接访问入口 | 告诉调用方可尝试的设备、地址及 RTCP 端口。 |
| 非默认端口 | 支持端口修改和 IPv4 NAT 映射等部署。 |
| Relay 入口 | 没有直连入口时，告知调用方可通过哪个 Relay 接入。 |
| 未配置时的默认规则 | 决定是否尝试候选地址的 TCP 2980。 |

这些语义究竟存放在 DID Document、Zone Document、Zone Config 的什么位置，以及如何通过外部设施发布，尚未冻结。发现结果还需要与目标身份形成可验证的对应关系，不能只凭请求方自报的地址或公钥建立信任。

### 5.5 未配置时的默认行为：当前倾向保留给未来

讨论过两种选择：未填写连接信息即认为不可连接；或者未填写时默认尝试已发现候选地址的 TCP `2980`。

**当前倾向第二种，但尚未定为最终协议规则。**

理由是面向长期 IPv6 可达环境，让默认端口直连成为简单路径；非默认端口和 Relay 通过显式配置表达，而不完全按当前 IPv4 NAT 环境设计默认值。

这里的“默认直连”只表示尝试规则，不构成可达性保证，也不意味着对任意地址进行扫描。如何显式表示“本 Zone 禁用 RTCP”，以及多地址如何选择，仍需明确。

### 5.6 Relay 应是隧道级中转

原则上优先直接连接。没有公网可达入口时，Zone 可以配置 Relay。

本轮所说的“可信中转”，要求中转发生在隧道层，而不是由中间节点终止明文应用请求，再用自己的身份重建另一条连接。以下方式不是本轮期望的模型：

```text
来源端 --应用层 HTTP 请求--> 中转节点 --另一条 RTCP 请求--> 目标端
                         中转节点解释、重建应用请求
```

期望的方向是：Relay 帮助传送隧道流量，通信两端仍保有可验证的设备身份与受保护的通信关系。不能因为经过 Relay，就把 Relay 的身份当成原始发送设备身份，也不能把“可转发”当成“已认证”。

具体 Relay 接入、目标绑定和端到端保护细节，后续由协议设计明确。

### 5.7 SN 不默认承担通用 RTCP Relay

根据口述中的现状回忆，SN 当前最重要的职责是为已注册节点提供可靠的 HTTP / HTTPS 访问相关能力，其 RTCP 权限控制较收敛。

已注册 Zone 能与 SN 建立 RTCP 连接，并不等于 SN 允许它借道连接任意其他 Zone。当前是否存在例外或已实现部分转发能力，需要检查代码与配置，本文不把回忆当作核验结论。

本轮的职责划分方向是：**通用 RTCP Relay 应考虑独立的节点类型或能力，而不是默认扩展 SN 的现有职责。**

## 六、用户态协议栈下的服务接入链路

### 6.1 普通服务继续使用 HTTP

按本轮描述，BuckyOS 的 RTCP 协议栈运行在用户态；普通系统服务主要生活在 HTTP 世界中，浏览器入口的 TLS 通常由网关处理。

普通业务服务不天然持有设备身份，也不应被要求各自实现 RTCP 握手、密钥管理和连接发现。它应通过具有明确设备身份的 Gateway，使用该设备上的 RTCP 协议栈访问对端。

设计分工如下：

```text
业务服务：构造 HTTP / kRPC 调用，提供本次调用的业务身份
    ↓
客户端 SDK / 本地代理：鉴权、选择路径、管理登录结果
    ↓
设备 Gateway / RTCP 协议栈：建立并使用跨 Zone 传输
    ↓
目标 Gateway：设备准入、解密、可信来源传递、HTTP 路由
    ↓
目标 verify-hub 或目标业务服务
```

这是逻辑链路，不要求各层独立部署，也不预先确定 SDK 与 Gateway 的精确分工。

### 6.2 本地 SOCKS5 作为接入入口

当前已有思路是：设备上的 `cyfs-gateway` 为本地进程提供 SOCKS5 接口，绑定 `127.0.0.1` 等回环地址，不向外部网络公开。

本地调用方配置 SOCKS5 代理，并把对端 DID 对应的 Hostname 作为目标交给代理；Gateway 再完成身份解析、Endpoint 发现和 RTCP 连接。

这里的 Hostname 是对现有 HTTP 客户端接口的适配方式，不改变 DID 的身份地位。DID 与代理目标地址之间的具体编码方式、服务寻址方式，本文不新增约定。

### 6.3 发送端必须约束本地调用者

BuckyOS 允许第三方应用运行任意代码。应用能够自行构造 HTTP 请求，因此“来自本机”不能直接等于“有权使用这个设备的可信身份对外声明任意用户或应用”。

Zone 内需要身份的服务调用已有 Session Token 机制，常见业务身份包含 User ID 与 App ID。跨 Zone 出口同样需要判断本地调用者是否有权以相应身份发起请求。

本轮倾向尽可能把这一鉴权边界放在 SOCKS5／代理接入侧，但具体机制尚未展开：它可能涉及本地会话、进程身份或其他可信调用上下文。

这里不能直接假定“标准 SOCKS5 天然能验证 HTTP Session Token”。若选择在代理侧执行相关校验，需要明确凭据如何交付、进程如何绑定、HTTP 语义由谁处理。这些是实现选择，而不是已经确定的协议能力。

### 6.4 目标端先做设备准入，再路由服务

Target Zone 的 RTCP 协议栈取得经过验证的来源 Device DID 后，可以在握手或 Incoming 准入阶段执行系统安全策略，例如允许名单、拒绝名单或其他设备级约束。

未通过系统准入的连接不进入业务服务。通过准入后，Gateway 恢复 HTTP 请求，并依据现有 Node Gateway 路由规则，把请求送到相应服务。

在 RTCP 已提供所需加密保护的设计前提下，通道内可以承载 HTTP，不要求每个业务服务自行提供 HTTPS。内部转发路径仍需遵守系统自身的信任与隔离边界。

### 6.5 可信来源 Header：先清理，再注入

RTCP 验证得到的来源设备身份，需要由接收端 Gateway 传给后续组件，尤其是 `verify-hub`。

本轮明确采用 HTTP Header 承载这类来源上下文，但尚未指定字段名称。必须遵守的处理顺序是：

```text
验证 RTCP 对端设备身份
    → 恢复 HTTP 请求
    → 清除请求中已有的受保护来源身份字段
    → 写入本地协议栈验证得到的身份信息
    → 路由到 verify-hub 或目标服务
```

不能只追加一个 Header，而保留发送方自行填写的同名或冲突字段。否则请求方可以借重复字段、不同解析方式等制造来源身份歧义。

作为这一边界的实现要求，受保护字段的范围、重复字段处理，以及非 RTCP 入口的清理规则，都需要统一定义。后端也不能允许普通客户端绕过可信转发路径，直接提交可被当作网关认证结果的 Header。

来源 Header 证明的是设备／连接上下文，不取代业务服务所需的 Session Token。

## 七、统一认证：两条传输路径都先向目标换取 Token

### 7.1 方案演进：不让每个服务验证整条跨 Zone 信任关系

早期设想是：RTCP 验证设备身份，Gateway 将其传入 HTTP 请求，再由目标业务服务判断 Device、Zone、User 的代表关系。

后续讨论修正了这一方向。业务服务既支持 Zone 内 Token，又直接验证 Zone 外身份关系，会增加复杂度和出错机会；这些工作本质上属于登录认证。

因此，当前收敛为：

**RTCP 路径也先登录 Target Zone 的 `verify-hub`，换取 Target Zone 的 Session Token，再调用目标业务服务。**

早期的身份关系验证逻辑没有消失，而是集中到了 `verify-hub`。它不再作为普通业务服务的另一套常规认证入口。

### 7.2 “第一跳换 Token”的含义

这里的“第一跳”，指建立跨 Zone 业务会话时，先完成目标侧登录。它不是要求每一个业务请求都额外登录一次，也不是要求每新建一条 TCP 连接就一定重新取得 Token。

调用方应维护有效登录结果，在会话可复用时继续使用，按最终确定的有效期与刷新规则更新。

本文的“换 Token”是架构语义，不预设采用某个现成 Token Exchange 标准，也不预先指定接口名称。

### 7.3 `verify-hub` 负责验证哪些关系

目标 `verify-hub` 需要把来源声明转换为自己能够签发的身份结果。至少涉及以下判断：

| 判断层次 | 核心问题 |
| --- | --- |
| 设备身份 | 这个 Device DID 是否能够被可靠验证？ |
| 设备与 Zone | 该设备是否有资格代表所声明的 Source Zone？ |
| Zone 与用户 | 该 Zone 是否是所声明 User DID 的合法认证来源，是否符合唯一 canonical zone 约束？ |
| 应用或服务身份 | 本次声明的 App／服务身份，是否具有足够的来源和授权依据？ |
| 本次登录 | 当前请求是否真实持有相应认证能力，而不只是复制了公开身份资料？ |
| 本地会话 | 验证通过后，Target Zone 应签发怎样的身份与会话权限？ |

RTCP 可以提供已验证的 Device DID；HTTPS 路径需要另外完成来源证明。二者都不能仅根据 HTTP 请求中自报的身份直接签发 Token。

设备身份中即使包含 Zone 信息，也不能只凭字符串中的归属声明授予代表资格；还需要与可验证的身份资料和授权关系一致。

### 7.4 不能假设对端运行着完整、正确的 BuckyOS

跨 Zone 协议应该允许最小实现。一个对端可以不运行完整的 BuckyOS，只要它具备相关身份凭据并实现必要的通信协议，就可能发起合规请求。

Target Zone 因此不能依赖“发送端肯定执行过本地 Session Token 验证”。本地出口鉴权解决的是 Source Zone 内部的安全问题；目标侧独立验证解决的是跨 Zone 信任问题，两者不能相互替代。

同样，不是 Source Zone 内所有设备都自然具备跨 Zone 代表资格。若目标侧无法可靠获得某设备的验证资料，或无法证明其对 Zone 的代表关系，就可能在建连或登录阶段拒绝。

### 7.5 本地 Token 可以表达外部身份

登录成功后，Token 的签发者是 **Target Zone 的 `verify-hub`**；Token 所表达的用户或应用身份可以来自其他 Zone。

目标业务服务继续验证本 Zone 信任的 Token，并据此执行业务授权。它不必再次完成跨 Zone 登录，但也不能因为签发者是本 Zone，就把外部用户自动当成本 Zone 管理员或内部系统应用。

外部 Token 身份在本地被认可，只表示该身份经过了本次登录认证，不等于自动获得某项业务权限，更不等于 Target Zone 取得了替该用户向第三个 Zone 认证的资格。

## 八、两条传输路径的完整调用流程

### 8.1 RTCP 首选路径

```text
Source Zone 调用方
    │ 通过 SDK / 代理提供目标信息与业务身份
    ▼
Source Zone 本地接入与鉴权
    │ 选择有资格对外通信的设备 Gateway
    ▼
RTCP Tunnel 建立或复用
    │ 验证通信设备身份
    ▼
Target Zone Gateway
    │ 设备级准入；清理并注入可信来源上下文
    ▼
Target Zone verify-hub
    │ 验证 Device / Zone / User / App 等必要身份关系
    │ 签发 Target Zone Session Token
    ▼
Source Zone 保存本次身份面向 Target Zone 的登录结果
    │ 后续请求携带该 Token，经可用传输访问
    ▼
Target Zone 业务服务
      验证本 Zone Token，再执行业务授权
```

RTCP 的价值在于提供首选的原生可信通道，并为登录提供可靠的设备来源上下文。它不要求目标业务服务直接接管整条身份关系的验证。

### 8.2 HTTPS 降级路径

当 RTCP 无法使用，例如没有公网可达端口、没有可用 Relay，或者连接探测失败时，调用方使用 Target Zone 已有的 HTTPS 入口。

本轮方案把 HTTPS 入口可用作为降级路径的部署前提。这不是对所有故障状态的保证；如果 HTTPS 也不可用，应向调用方返回明确失败，而不是假设系统总能连通。

```text
Source Zone 调用方
    │ RTCP 暂不可用
    ▼
Target Zone HTTPS 入口
    │ 向目标 verify-hub 发起跨 Zone SSO
    ▼
Target Zone verify-hub
    │ 发现并反查来源身份与 Zone 配置
    │ 验证本次登录的身份证明和代表关系
    ▼
签发 Target Zone Session Token
    │ Source Zone 保存登录结果
    ▼
通过 HTTPS 携带 Token 调用目标业务服务
      目标服务采用同一套 Token 验证与业务授权
```

与 RTCP 相比，HTTPS 路径缺少 RTCP 直接提供的设备认证上下文，因此需要在 SSO 登录中补足来源证明，而不是信任客户端自行填写的设备 Header。

### 8.3 HTTPS 反查的作用与边界

目标 `verify-hub` 可以根据 Source Zone 的身份信息，通过 HTTPS 等发现路径反查 Zone 配置、公钥及 SSO 验证资料。

这里必须区分两件事：**取得验证资料**，以及**验证当前请求确实具有该身份的认证能力**。公开 DID、公开公钥和公开配置本身可被任何人读取，不能单独作为登录成功的证据。

具体采用怎样的签名、挑战应答或其他来源证明，本轮尚未确定。实现时需要同时明确反查入口与所声明 DID 的绑定、请求证明的有效性，以及用户与 canonical zone 的关系验证。

这项工作集中在 `verify-hub`，不要求每个业务服务分别实现。

### 8.4 HTTPS 登录可以触发反向 RTCP 建连

本轮提出了一个重要的连接恢复机会：RTCP Tunnel 建立后可以双向使用，建立连接的方向不必与后续业务调用的方向一致。

可能出现以下情况：

```text
Source Zone → Target Zone：RTCP 主动连接失败
Source Zone → Target Zone：通过 HTTPS 发起 SSO 登录
Target Zone → Source Zone：反查期间尝试反向建立 RTCP
连接成功：双方得到可复用的双向 Tunnel
后续通信：优先利用已有 RTCP 通道
```

因此，“当前发起方无法连到目标 RTCP 入口”不一定意味着“两端永远无法建立 RTCP”。目标侧反查可以成为发起反向连接的触发点。

反向建连仍必须完成正常的身份验证和准入检查。若两端都没有可达入口、也没有可用 Relay，就继续使用 HTTPS 完成 SSO 和后续调用；不能把反向 RTCP 成功设为 HTTPS 登录的前置条件。

### 8.5 RTCP 与 HTTPS 的共性及差异

| 项目 | RTCP 路径 | HTTPS 路径 |
| --- | --- | --- |
| 选择优先级 | 首选 | RTCP 不可用时降级 |
| 建连入口 | 经发现获得的 RTCP Endpoint 或 Relay | Target Zone 的 HTTPS 入口 |
| 来源证明基础 | 已认证的 Device DID，加上登录所需的业务身份材料 | 在跨 Zone SSO 中完成来源证明与反查 |
| 目标认证组件 | Target Zone `verify-hub` | Target Zone `verify-hub` |
| 业务凭据 | Target Zone Session Token | Target Zone Session Token |
| 目标服务认证 | 现有 Token 验证机制 | 同一套 Token 验证机制 |
| 最终业务授权 | 目标业务服务决定 | 目标业务服务决定 |

HTTPS 与 RTCP 的区别，不应简单表述为“HTTP 完全不能复用连接”。本方案关心的是 RTCP 自身的设备认证、双向 Tunnel 和系统级复用能力；HTTPS 路径不以这些能力为成立前提。

## 九、Session Token、登录结果与身份表示

### 9.1 本地会话与远端会话分开

Source Zone 的本地 Session Token，用于证明调用者在本地的业务身份与权限；Target Zone 签发的 Session Token，用于调用 Target Zone 的服务。

不能简单把本地 Token 透传过去，就假定它自动成为目标服务认可的会话。跨 Zone 登录的作用，正是把经过验证的外部身份转换为目标自己的会话凭据。

同样，目标 A 的会话不能无条件拿去访问目标 B。具体 Token 结构虽未冻结，但使用范围必须有明确边界。

### 9.2 按目标与身份维护登录结果

口述提出由调用侧为每个身份维护登录成功的结果。整理为实现要求时，至少要同时区分 **Target Zone 与业务身份**，避免不同目标、用户或应用之间串用会话。

可以按以下逻辑维度理解，但不将其作为冻结的缓存键格式：

```text
目标 Zone
    + 用户／服务主体
    + 应用身份（当协议要求区分时）
    + 会话权限或其他必要约束
    → 登录状态、Session Token、有效期、可用的刷新凭据
```

同一个用户通过不同应用发起请求时，是否可以共用登录结果，应由最终的身份与权限模型决定，不能因为 User DID 一样就直接合并。

Token 保存于 SDK、进程、本机受控组件还是其他系统位置，也需结合隔离要求确定。

### 9.3 有效期与刷新

Session Token 应有有效期。可以考虑复用已有体系中的双 Token／刷新机制，避免反复完整登录，但本轮没有确定有效时长、刷新接口或具体实现状态。

会话过期、来源授权变化、设备失去资格、用户 canonical zone 变更等情况，如何影响已签发 Token，需要后续明确。不能把建立过一次登录会话理解为永久授权。

### 9.4 外部身份不再只是 Zone 内短名称

当前很多服务以 Zone 内短名称表示用户和应用，甚至不保存完整 DID。接纳跨 Zone 会话后，身份字段可能变长，也可能携带外部命名空间。

这要求业务服务正确处理以下区别：

| 情形 | 需要保持的区别 |
| --- | --- |
| 本地用户短名称与外部 User DID | 展示名称相同，不代表同一身份。 |
| 不同来源 Zone 的同名应用 | 相同 App ID 短名称，不代表同一个应用主体。 |
| 身份与角色 | 验证了外部身份，不等于接受来源端自称的本地高权限角色。 |
| 外部用户与本地映射记录 | 本地 Profile／别名不改变该用户的 canonical zone。 |

具体采用完整 DID、带来源的复合标识，还是目标侧内部规范化标识，尚未确定。无论采用哪一种，都应保持可区分的主体身份，不能简单截短为末尾名称后进行权限判断。

在口述预期中，业务服务最主要的适配就是支持这些外部身份，而不是重做登录认证。落地时需要检查的不仅是字符串长度，也包括身份比较、存储字段、ACL 匹配和展示逻辑。

## 十、跨 Zone 客户端能力应高度封装

### 10.1 面向业务暴露统一访问语义

业务调用方只需要表达：访问哪个 Target Zone、哪个服务，以什么业务身份执行什么操作。

底层负责发现入口、选择传输、管理登录与会话、探测和复用连接。业务不应自己编写一套“先 RTCP，失败后 HTTPS，再反向建连，再切回来”的流程。

本文用“跨 Zone 客户端运行时／连接管理能力”描述这组职责，它是逻辑能力，不代表已经决定新增一个同名系统服务。

### 10.2 SDK 与 SOCKS5 的具体分工未定

本轮提出了两种可能的实现位置：在 SDK 中高度封装；或者让调用方尽量统一通过 SOCKS5，由 Gateway 内部处理 RTCP 与 HTTPS 的选择，并配合共享状态。

最终也可能是二者协作。核心要求是上层统一、信息可共享，而不是先固定所有逻辑必须塞进哪一个组件。

尤其是把 HTTPS 降级和自动登录放入 SOCKS5 接入侧时，需要明确它是否只负责连接转发，还是同时理解应用层请求、执行 TLS 连接和管理 Token。不能仅凭“总是走 SOCKS5”就省略这些职责设计。

### 10.3 传输可用性与登录状态分别管理

跨 Zone 运行时至少面对两组独立状态。

**传输状态：** 未发现、探测中、RTCP 可用、HTTPS 降级可用、完全不可达等。

**认证状态：** 未登录、已登录、需刷新、登录失败、授权失效等。

这两组状态应协作，但不能合并。连接建立成功不等于用户已登录；已有有效 Token 也不等于网络一定可达。

### 10.4 自动降级与恢复

方向性流程是：优先使用已有 RTCP 通道；没有可用通道时尝试发现和建立；不可用时使用 HTTPS；后续一旦 RTCP 可用，优先把后续通信切回原生通道。

这里的“切换”首先应理解为后续请求选择新的传输路径，不预设已经发出一半的请求可以无损迁移，也不预设写操作可以被自动重放。

统一 Token 机制为切换提供了基础，但 Token 是否绑定某个设备、通道或登录上下文尚未确定。如果存在绑定，切换时需要满足或更新该约束，不能假定任意通道都能直接复用同一凭据。

## 十一、连接可用性应尽量扩散到整个 Cluster

### 11.1 不把跨 Zone 通道局限于单个业务进程

当 Source Zone 中某个设备已经与 Target Zone 建立 RTCP Tunnel，该结果应尽可能让本 Zone 的整个集群受益，而不是只有最初发起连接的进程知道它存在。

例如，HTTPS 登录触发了目标侧反向 RTCP 建连，其他仍在使用 HTTPS 的调用方应有机会获知这条更合适的路径。

### 11.2 区分“知道路径”与“能够使用路径”

集群共享包含两个层次：

| 层次 | 含义 |
| --- | --- |
| 共享可用性信息 | 知道哪台本地设备能够到达 Target Zone、当前使用哪种传输、状态是否仍有效。 |
| 共享实际连接能力 | 本地其他节点可以经由合适的内部转发路径，使用已有 RTCP 通道完成访问。 |

第二层需要额外的内部路由、接入权限和失效处理。传播一条“已连接”状态，并不会自动让其他机器获得可用的数据通路。

具体使用 Gateway 间协作、共享状态还是其他机制，本轮尚未决定。

### 11.3 连接共享不等于身份共享

**共享的是受控连接能力，不是无条件共享 Session Token、用户权限或设备私钥。**

经由某台设备的 RTCP Tunnel 出口时，目标看到的 RTCP 对端身份仍然是那台实际建立通道的设备。原始调用者的用户／应用身份，应通过已验证的登录和会话机制表达，不能由内部调用者随意改写来源设备 Header。

跨节点转发需要重新检查本地接入边界，不能为了复用通道，就把原本只绑定回环地址的 SOCKS5 直接暴露给整个集群或互联网。

同样，某设备成功建连不表示其对外代表资格可被其他节点无限继承；使用路径的调用者仍需满足各自的身份和授权要求。

## 十二、不同业务可以采用不同认证要求

### 12.1 普通业务采用统一登录与 Token

对于常规消息投递、内容读取以及其他系统服务调用，默认使用本方案统一的登录和 Session Token 流程。

这避免每次请求都要求用户直接使用身份主私钥签名，也避免每个服务自行实现跨 Zone 信任链。

### 12.2 业务本身可以要求独立签名

某些业务具有明确的公钥验证规则，能够独立验证请求或对象的业务身份签名。这类业务可以在自己的协议中规定额外签名，或在明确允许的场景下，以独立签名作为相应身份认证依据。

这属于业务特定的认证要求，不把普通服务重新引向两套跨 Zone 登录逻辑。是否可以免除额外 Session Token，应由该接口的安全规则明确，不能由客户端自行决定。

### 12.3 签名、保密与授权是不同问题

口述中“业务签名完整时，甚至可以通过 HTTP 投递”的重点，是业务身份证明可以独立于传输层认证存在，而不是普通 HTTP 能提供防窃听能力。

整理为安全边界时，应明确：签名可以用于验证签名者及其覆盖内容，**不提供内容保密**；是否防重放取决于具体协议；证明谁签了名，也不等于该身份有权执行操作。

因此，独立签名不能替代全部传输保护和业务授权。对于需要保密的内容，仍需依赖 RTCP、HTTPS 或明确设计的内容加密机制。

## 十三、组件职责与分层收敛

| 组件／逻辑层 | 主要职责 | 不应默认承担的职责 |
| --- | --- | --- |
| 本地业务服务／第三方 App | 表达业务请求、目标与调用身份。 | 自行维护完整跨 Zone 网络探测和身份信任链。 |
| SDK／跨 Zone 客户端能力 | 封装登录、会话使用、路径选择及相关错误语义；与 Gateway 协作。 | 自动绕过业务授权或把所有身份共用一个 Token。 |
| 本地代理接入层 | 约束谁可以使用设备出口能力，绑定可信本地调用上下文。 | 因为请求来自本机就接受任意身份声明。 |
| RTCP 协议栈／Gateway | 设备认证、通道维护、系统级准入、可信来源传递与服务路由。 | 把 Device DID 直接当作 User DID 或应用权限。 |
| Target Zone `verify-hub` | 验证跨 Zone 身份及代表关系，签发目标侧 Session Token。 | 把公开身份资料直接当成当前请求的身份证明。 |
| Target Zone 业务服务 | 验证本 Zone Token，识别外部主体，执行业务授权。 | 重复实现一整套跨 Zone SSO。 |
| RTCP Relay | 在选定模型下提供隧道级连接中继。 | 默认终止应用明文、伪装为原始发送方。 |
| SN | 保持既有访问保障职责；实际能力按代码核实。 | 默认成为任意 Zone 间的通用 RTCP Relay。 |

| 发现数据 | Endpoint、外部端口、Relay、设备验证资料放在哪里，如何发布并可信解析。 |
| 缺省行为 | 默认 2980、多候选地址、显式禁用 RTCP 的表示与优先级。 |
| 本地接入鉴权 | Session Token、进程身份与代理请求如何可靠绑定。 |
| RTCP 来源上下文 | 受保护 Header 集合、来源验证、重复字段处理、非可信入口清理。 |
| 跨 Zone SSO | 登录证明、反查、用户 canonical zone 验证，以及 App／服务身份如何参与。 |
| 会话 | 外部身份表示、Token 使用范围、有效期、刷新、撤销及登录结果的保存位置。 |
| 传输切换 | 是否绑定通道或设备；何时复用会话，何时重新登录。 |
| 集群协作 | 连接状态传播、实际内部转发、访问权限和失效清理。 |
| Relay | 接入授权、目标设备绑定、端到端保护和连接生命周期。 |

## 十五、由上述方向推导的实现检查项

以下是整理时归纳的检查项，用于防止实现偏离口述目标，不作为本轮已经冻结的新增协议规则。

### 15.1 区分网络失败与认证拒绝

RTCP 端口不可达可以触发 HTTPS 降级；设备身份验证失败或被系统策略明确拒绝，不应简单作为“换个协议继续试”的理由。

需要防止同一不被允许的主体通过降级路径绕过共同的身份或授权策略。具体失败分类与返回方式由实现定义。

### 15.2 不把外部反查变成任意地址访问能力

`verify-hub` 的反查和反向建连会根据外部输入触发网络访问。实现时应验证目标与所声明身份的关系，并限制可访问的地址、端口与资源，避免被任意登录请求利用。

### 15.3 防止身份字段混淆

外部同名用户、同名应用、来源端角色声明，以及未经清理的来源 Header，都可能造成身份混淆。身份规范化应在受信任边界完成，业务授权使用规范化结果，而不是展示名称。

### 15.4 对重试和切换定义业务语义

网络超时不一定意味着远端未执行操作。消息投递和写操作在重试或切换传输前，应有明确的重复请求处理规则。幂等标识、结果查询或其他方案尚未选定，不能默认无限重发。

### 15.5 连接状态与权限状态分别失效

Tunnel 仍然在线，不表示用户授权或应用权限仍然有效；反过来，会话有效也不能使已失效的网络路径继续可用。共享连接状态时，应保留各自的更新、过期和撤销机制。

## 十六、收敛结论

本轮讨论从“RTCP 如何直接承载跨 Zone 身份”出发，最终收敛到一个更统一的分层方案：

```text
业务请求：投递消息 / 读取内容 / 调用系统服务
                         │
                         ▼
       SDK / Gateway 封装跨 Zone 连接与会话
                         │
             ┌───────────┴───────────┐
             ▼                       ▼
        RTCP 首选传输           HTTPS 降级传输
             │                       │
             └───────────┬───────────┘
                         ▼
             Target Zone verify-hub
          验证来源与业务身份，签发本地 Token
                         │
                         ▼
                Target Zone 业务服务
              统一验证 Token，按业务授权
```

**RTCP 与 HTTPS 是两条传输道路，不是两套普通业务认证体系。**

RTCP 保留 DID 身份、去 CA 方向、设备级可信通信和 Tunnel 复用的优势；HTTPS 提供现实网络环境中的兼容与可用性。两者在目标 `verify-hub` 处汇合，业务服务继续面对一套熟悉的 Session Token 机制。

设备身份验证、Zone 代表关系、用户 canonical zone 约束与本地应用权限，并没有因为“统一换 Token”而省略，而是放到了能够集中正确实现的边界。连接可用性则尽可能提升为集群共享能力，同时不扩大任何调用者原本拥有的身份与权限。

这就是本方案希望达到的状态：**底层连接有弹性，身份验证有统一入口，业务服务保持简单。**
