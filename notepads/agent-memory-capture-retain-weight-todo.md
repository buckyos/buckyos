## 0. 先看最终应留下什么

本文要回答：**给定一批经历和已有认知，整理之后应新增、合并、修订或移除什么，为什么这些变化能改善下一次判断？**

“最终认知列表”指本轮所涉范围在整理后的有效认知集合，包含沿用和修订后的旧认知，不只是本次新增条目；它也不是某次召回的前 5 条 Hint。有效认知仍可带条件、存在不确定性，并可被后续证据修正。

“整合公共经验”指从相关经历中提炼共同支持的可复用结论。同一 Agent 的多个任务可以为同一经验提供依据，但结论范围仍受用户、项目、工具版本和环境限制；不能因为措辞通用，就推广为所有 Agent 的规则。公共资料中的方法可以作为有来源的候选，不能冒充该 Agent 已验证的经验。

### 0.1 这批场景的目标结果

| 材料 | 整理后应留下什么 | 不进入最终列表的内容 |
|---|---|---|
| S1：完成标记、单次发送成功、实际未完整交付 | 合并为一条有范围的验收经验：按任务验收项核对交付证据，单项成功只证明对应部分 | 每个 session 的完成宣称、完整里程碑流水 |
| S1：反复催问和“还在运行”的汇报 | 一条监督经验：用产出、阶段变化和已确认阻塞判断进展；状态持续不变时核查原因并汇报 | “一次没新产出就一定卡住”；未经原话支持的长期 owner 偏好 |
| S2：发过中文自我介绍 | 现有材料可不新增认知；明确的持续公开介绍约定才形成偏好 | “发过两条帖”；由本次中文要求推出长期语言偏好 |
| S3：provider 报错 | 本批重复报错不足以形成恢复经验；有后续用途的异常可先保留候选线索，处置与验证结果支持相应的有限经验 | 报错流水、未经核查的恢复状态和唯一原因 |
| S4：天气查询中的城市 | 现有描述不足以形成长期所在地；明确的常住地、当前位置、默认查询城市分别处理 | 自动形成半年有效的所在地，或据此推导日程时区 |
| S5：明确的后续报告要求 | 一条限定项目／交付类型的持续偏好；本次例外不覆盖它 | 把“这次详细点”当成永久撤回 |
| S6：工具观察、独立复现、版本反例与用户约定 | 修订一条工具经验，另保留一条项目约定 | 每次观察各建一条；把工具限制和用户选择合成一个事实 |

这些是语义结果，不要求固定条数或固定措辞。有已有认知时优先修订；没有足够依据时，最终列表可以没有新增条目。

## 1. 最终认知的准入与整合规则

### 1.1 每条认知必须能回答的问题

沿用需求 §5.6–§5.7，不另设“出现 N 次才可记”的统一门槛：

1. **下次有什么用？** 在明确情境中，会改变哪一步理解、选择、检查或沟通？只说“发生过 X”不足以进入列表。
2. **哪些证据支持？** 关键结论能追溯到原始事件，区分用户明确表达、工具观察、第三方主张和 Agent 推断。同一事件的摘要不算独立证据。
3. **适用于哪里？** 主体、项目、工具版本、时间和例外与证据一致。一次清楚的持续要求可以成立；一次任务参数不能因此变成长期偏好。
4. **比已有认知多了什么？** 是新结论、新条件、新证据、反例还是纠正？同义内容优先补充原条目；没有变化时可以不写新 revision。
5. **应该由 Memory 承载吗？** 当前进度、任务要求、授权、配置和对象有效版本由正式对象承载；Memory 保留理解、经验、选择理由和查找线索。没召回只应使 Agent 不够聪明，不能让业务链路失去正确性保障（M-30）。
6. **何时复核，怎样想起？** 指明自然的触发情境、必要的对象／主题入口，以及用户纠正、版本变化、条件变化等复核依据。

主语仍限 Agent 自己、Owner 或工作区。外部工具和第三方关系应服务于这些主体的理解，保持来源与范围；不能只改一下主语，就把任意世界事实塞进 Memory。

### 1.2 整合公共经验的工作顺序

| 步骤 | 应做的判断 | 应得到的结果 |
|---|---|---|
| 按问题与范围聚合 | 哪些材料共同回答“如何验收”“为什么放弃某方案”等问题？是否属于同一用户、项目与版本？ | 一组可比较的材料及相关既有认知；不能只按相同 tag 混合 |
| 还原证据关系 | 哪些是同事件转述，哪些是独立观察、补充、例外或纠正？ | 来源去重后的支持与限制 |
| 提炼最小可复用结论 | 在什么条件下该考虑什么，为什么，尚不能确定什么？ | 可单独理解的结论；保留会改变行动的限制 |
| 对照已有认知 | 新材料是否已被覆盖？是否补充条件或否定了旧范围？ | 沿用、补充、合并、修订、缩小范围或撤回 |
| 确定材料去处 | 哪些支持认知，哪些重复，哪些只是状态，哪些缺证且值得等？ | 每条材料有 absorbed／duplicate／discarded／deferred 处置 |
| 检查最终列表 | 是否出现同义重复、无依据的泛化、已被替代的旧结论或状态副本？ | 本轮所涉范围的有效认知及可追溯依据 |

“一条一事”约束的是结论，不是材料数量。多个独立事件可以支持一条认知；一条用户表达也可能同时支持一个项目约定和一个选择理由。主题相关但决策用途不同的结论可以分别保留，无需强行合并。

反例优先用于找出适用条件；只有明确否定或替换同一范围的认知时才撤回旧结论。不能机械按最新时间戳覆盖，也不能把本次例外视为长期纠正。用户明确偏好与行为推断有分歧时，分别保留证据性质并显露分歧，不能用推断覆盖明确表达（E-17）。

### 1.3 什么不应成为新条目

- 任务状态和历史流水：已发帖、当前等待、还剩三项、某 session 成功。回到 Task、Goal、Final Report 或世界对象。
- 没有个体或场景增量的常识：已被默认行为或 Skill 完整覆盖的原则，不需要每次执行后复制为一条记忆。
- 尚未验证的归因：“换模型后成功”可以支持一个恢复线索，不能直接证明故障唯一来自原模型。
- 重复摘要和召回回声：关联原认知或来源即可，不提高证据强度和显著度。
- 脱离适用条件的口号：“所有接入都必须自动回复”“只要没有新产出就卡住”。

可复用的方法若发展成完整操作配方，应作为 Manual／Skill 的结晶候选；Memory 保留采用它的条件、实际踩坑、例外和资产入口。此处只提出候选，不把整理认知等同于完成能力资产发布。

## 2. 应进入 Agent Memory 的典型条目

**以下 C1–C14 全部是虚构样例，不代表当前用户或 demo Agent 的事实，也不是默认批量写入清单。** 只有实际材料提供了所列依据，才建议吸收相应认知。若已有认知覆盖，补充依据或修订原条目即可。

表中的“下次用途”也是验收问题：在新任务里，Agent 是否因此多做了一个有价值的检查，或少重复一次已知错误？

### 2.1 可复用经验：包括失败教训和成功方法

| # | 最终认知示例 | 依据与适用边界 | 下次用途 |
|---|---|---|---|
| C1 验收经验 | “在项目 A 的委派交付中，完成状态和单项成功不足以证明整体交付；汇报完成前，按任务验收项核对可访问的结果。” | 实际发生过状态成功但验收未满足，来源能关联任务要求与产物；先限项目 A 的这类任务 | 再次委派时检查结果，避免误报完成 |
| C2 监督经验 | “监督项目 A 的长任务时，用产出、阶段变化和已确认阻塞判断进展；状态持续不变时，结合预期时限核查原因。” | 运行状态、实际产出和核查结果可追溯；一次无新产出不等于卡住 | 提供有信息的进展汇报，避免重复‘还在运行’ |
| C3 成功方法 | “用转换器 v2 批量处理项目 A 的模板 T 月报前，先选含表格和页眉的代表样本检查布局，可及早发现模板问题。” | 独立批次中样本检查发现过问题，修订后批量结果通过；限转换器 v2 和模板 T 月报，换版复核 | 复用验证过的检查方法；完整批处理步骤交给 Skill |
| C4 工具经验 | “tool-x v1／Linux 在已观察条件下生成产物失败时，可优先检查是否显式指定输出目录；v2 有省略目录成功的反例。” | 原始失败／成功调用、独立复现和 v2 反例；尚未证明唯一原因 | 定向排查，不把局部经验推广到所有版本 |

### 2.2 对用户与项目的持续理解

| # | 最终认知示例 | 依据与适用边界 | 下次用途 |
|---|---|---|---|
| C5 交付偏好 | “用户要求项目 A 的后续周报先给结论和待决事项，正文控制在一页内，明细另附。” | 明确持续要求；限项目 A 周报，“这次详细点”只改变本次交付 | 默认采用合适结构，减少重复说明 |
| C6 明确边界 | “用户要求为项目 A 准备的对外材料先保留为草稿，确认后再发送。” | 明确持续要求，限项目与外发场景；正式任务／权限机制仍须承载发送授权 | 拟定交付计划时先安排审阅；记忆本身不授予权限 |
| C7 用户事实 | “用户自述长期居住上海；这不代表当前旅行地点。” | 明确‘长期居住’的原话和来源时间；搬迁或新陈述时复核，天气查询只答城市不足以支持 | 理解生活背景；不自动推导当前所在地或日程时区 |
| C8 项目约定 | “用户要求项目 A 的后续交付同时提供可编辑源文件和 PDF。” | 明确的项目持续约定；实际任务验收条件仍写入 Task | 新任务拟定计划时提醒补齐交付形式 |

### 2.3 选择理由、指代、关系与查找线索

| # | 最终认知示例 | 依据与适用边界 | 下次用途 |
|---|---|---|---|
| C9 选择依据 | “项目 A 上次未采用服务 X，原因是当时必须离线运行；评估替代方案时先核查这一限制是否仍成立。” | 可追溯决策与理由，限该项目及当时约束；当前方案查项目对象 | 避免重复推荐因同一约束被放弃的方案，也允许条件变化后重评 |
| C10 私有用语 | “用户在家庭照片整理的话题里说‘小相册’，指的是家庭照片归档项目 A。” | 用户明确解释指代并关联项目对象；同名不能自动合并 | 理解自然表达，找到正确项目；不从称呼推导本次任务范围 |
| C11 有用关系 | “用户说陈宁是项目 A 的设计对接人，视觉问题通常向其确认。” | 用户明确介绍该关系并能区分身份；角色变化时复核 | 判断可能需要谁的意见；不据此推导审批权或自动联系他人 |
| C12 查找线索 | “项目 A 的‘活跃用户’曾有两种统计口径；比较历史数据前，应先查指标字典和决策记录中的适用版本。” | 实际发生过口径差异，能定位原对象与版本；不复制当前指标值 | 新分析时主动想到口径问题，找到核验入口 |

这些条目的共同点是留下了“下一次应如何理解或核查”。C9 的历史选择因为带有可复用理由而值得保留；仅记录“曾选过／做过 X”则不足。C6、C8 可以作为提醒，但系统正确执行不能依赖它们恰好被召回。

### 2.4 主体评价与精确信息的使用线索

| # | 最终认知示例 | 依据与适用边界 | 下次用途 |
|---|---|---|---|
| C13 用户对主体的评价 | “用户表示，因供应商 X 在项目 A 上次交付延期，对其时效性有顾虑；再次讨论该供应商时，应关注交期及用户是否改变看法。” | 用户明确表达评价及理由，能定位供应商和该次经历；不据此断言 X 在所有项目都不可靠 | 理解用户选择供应商时的顾虑，避免无视已有反馈 |
| C14 精确入口的使用线索 | “用户所说的项目 A‘测试入口’指其指定的测试服务，不是生产环境；完整 URL 从项目配置的测试入口项读取。” | 用户明确说明用途，原事件保留完整 URL，配置项可定位；使用时读取当前值 | 理解私有称呼、定位正确环境，避免凭摘要重建地址 |

C14 的 URL 在原文／配置中须完整可恢复；若完整 URL 本身就是必要的跨任务访问线索，认知也可保留带来源和用途的精确值，但不作为配置当前有效性的唯一依据。只用于本次任务的电话、地址或 URL 仍由任务／对象保存，不因“不能丢原文”自动进入最终列表。具体保真要求见 §4.1.1。

## 4. 从目标结果反推捕获、表达和权重

### 4.1 什么感知值得捕获

感知记录“可能影响后续判断的观察与来源”，普通 Session 不需要当场完成归纳。Runtime 自动写的 `run_digest`（run 结束时的一句状态加回复首行）不再作为材料入口（§6 TR）：材料只来自 Agent 的主动捕获，原话、条件、处理过程和结果都要由捕获保留，不能用 Agent 的状态句替代用户表达。没有主动捕获的 Session 不留材料，整理 Goal 也不为它激活。

本节吸收用户提出的“精确原文、实际经验、长期偏好、长期指令、对主体的认识”等分类。其核心取舍表述为：**优先捕获未来可能影响判断、但在上下文消失后难以可靠重建的信息，以及能够验证、修正或推翻已有认知的新证据。**

“难以重建”包括重新获取成本高、仅凭当前状态不能还原当时理由或经历；并非要求信息绝对无法通过观察得到。实际经验来自观察，用户原话也可能可查历史，仍然可以有保留价值；反之，无法恢复但没有后续用途的细节不必进入感知。

| # | 触发 | 应记录的内容 | 避免 |
|---|---|---|---|
| P1 | 用户明确的持续偏好、要求、边界或对某类工作的指导 | 原意、主体、项目／交付类型、持续范围与例外；区分倾向、明确要求和用户提供的方法线索；明确记忆意图按接口约定标记 | 仅凭出现“以后”就忽略范围；把方法建议当作已验证经验 |
| P2 | 用户对交付或其他主体的评价、态度 | 谁评价哪个对象、具体内容、理由与情境 | 工具成功代替认可；一次评价直接变长期偏好；用户印象变成对象的无条件事实 |
| P3 | 用户或新证据纠正已有理解 | 纠正的原话或观察、来源、范围、相关认知引用（已知时用 `--cite item@rev`） | 把本次例外标成永久纠正；仅因本批没提到而认定失效 |
| P4 | 预期与实际结果的显著差异、Agent 的失误、有效方法或选择理由 | 当时条件、预期、采取的行动、实际结果与来源；已验证解释与未知项分开 | 等原因查明才记录有价值的异常；只写“已修复”；把一次成功归为唯一因果 |
| P5 | 工具／环境观察和项目约定 | 版本、环境、对象、调用或约定来源 | 丢掉复现条件，泛化到所有工具版本 |
| P6 | 有后续用途的用户事实、主体别名／关系／特性、私有用语和精确对象线索 | 原始提及、身份关联依据、时间／对象范围；需要保真的值及其用途；区分用户陈述与实际观察 | 同名直接合并主体；把用户查询的对象写成用户属性；丢掉 URL 等值的用途与来源 |

按需使用 `--subject`、`--object`、`--tag`、`--cite`、`--explicit`；这些参数帮助标明来源与范围，不证明内容正确。第三方原文与 Agent 推断要保留实际来源，不能写成用户直接表达。

任务进度、预算、问候、能力自述和本次任务参数不额外主动感知，所需原文仍由任务或相应对象可靠保存；实时状态按需查世界对象，密钥不进入可召回 Memory。异常条件、实际结果、已做处置与验证情况可以记录，原因尚不明确不妨碍捕获有价值的线索；单纯重复错误不需要手动再记一份。

捕获判断：**能否指出一个后续用途，并保留这次新观察的来源与条件？** 可以先留下不成熟的观察，由整理判断；不要求一周后仍有用才允许捕获有时限的线索。

流程是：**识别值得留下的信号 → 保留原话、来源、条件和实际结果 → 整理认知并处置材料。** 整理可以沿用、新增、合并、修订或撤回认知，材料可以暂缓或丢弃。命中某一类别不等于必须新增长期认知，捕获也不要求检索全部历史或当场证明因果。

#### 4.1.1 精确原文：防止 context 压缩丢失必要信息

“必须精确保留”是横跨类别的保真要求。详细地址、电话号码、服务器 URL、特殊名称，以及影响持续要求含义的关键原话，都可能需要精确保留；是否成为长期认知仍按 §1 判断。

| 信息 | 必须保留什么 | 原文归宿与最终认知 |
|---|---|---|
| 详细地址、电话号码 | 完整值、属于谁、用途、用户给出的有效范围及来源；不能只留城市或号码尾段再猜回原值 | 原值由联系人、任务或相应对象保存；有持续用途时，认知保留人与地址／联系渠道的关联和查找线索 |
| 服务器地址／URL | 完整值及有意义的端口、路径、参数，与项目、环境和用途的对应关系 | 原值由项目／配置保存；认知可保留环境区分、入口用途和可定位引用，如 C14；必要的精确访问线索可带来源保留 |
| 特殊称呼、关键原话 | 原始写法及对应主体，或“这次／本项目／以后”等影响范围的原句 | 原事件保留原文；认知保留有依据的指代或有范围的要求，不能在压缩时扩大含义 |

原文可持久、可靠重读时，保存可定位的引用即可；仅指向会丢失的临时上下文不算保真。尚无对应对象时，先保留可追溯原文和用途，待归档，不能只剩模糊摘要。已经有权威对象时，不另造一份无法同步的“当前值”。

#### 4.1.2 用户指导、持续要求与对主体的认识

- **长期偏好与明确长期指令分别理解。** “通常喜欢简洁”表达倾向，“以后项目 A 的报告先给结论”表达明确要求；都保留原话支持的范围。一次明确持续要求足以成立；“这次详细点”只改变本次任务。必须落实的约束仍由正式任务／规则承载。
- **用户口头指导先保留其证据性质。** 关于交付方式的持续指导可支持项目约定；“这个工具先建目录就能运行”先是用户提供的方法线索，实际验证后才能称为 Agent 验证过的方法。用户认可、采用和技术有效性分别判断。
- **同一主体的不同名字属于身份关联。** 捕获原始称呼、上下文和用户明确解释；有充分依据才形成别名关系。身份未确定时保留候选或歧义，不按相似名字合并；角色关系另留适用项目与时间。
- **主体长期特性与用户评价分开。** 特性若由用户介绍，应表述为用户陈述；若由 Agent 观察归纳，保留场景、证据与不确定性，不凭一次事件断言长期属性。评价则保留“谁因什么经历，对谁有什么看法”，如 C13，不能改写成无来源的客观定论。

选择及其理由、纠正与失效信号横跨上述类别。捕获“不再用这个地址”“当时只是出差”“新版本已没有该限制”等新材料时，保留它针对的对象和范围；整理据此更新原有理解或引用，不只是再追加一条。选择理由可形成 C9 一类认知；本次例外或一次不同结果先保留条件，不自动撤回旧结论。

### 4.2 认知的表达与召回入口

以下是表达指引，不能替代 §1 的语义准入：

| 规则 | 要求 |
|---|---|
| W1 一个可复用结论 | 多事件合成一个结论；同义内容优先修订，条件不同且不能合并时分别保留 |
| W2 结论自足 | 说明成立条件及对后续理解／行动的影响，避免只有历史摘要 |
| W3 来源可追溯 | session id、流水时间戳放入 observation／证据引用；影响含义的日期、版本和适用时段必须保留 |
| W4 不确定性可见 | `basis/confidence/stability` 辅助表达证据性质；关键限制仍写入 statement 或实际展示的元数据，不能因字段未展示而丢失 |
| W5 经验可行动 | 说清在什么条件下优先检查／考虑什么；未证明因果时不写成必然规则 |
| W6 对象与范围准确 | 涉及具体项目、工具、人物时关联对象并限定 scope；对象身份有歧义时先保留歧义 |
| W7 先合并后关联 | 同结论同范围的材料合并；相关但独立的结论才按需建立关系，不为凑字段连边 |
| W8 入口贴近任务 | 用自然会出现的主题和情境 tag，并利用对象入口；不强制每条恰好几个 tag |
| W9 使用 owner 的语言 | 保留必要术语和对象名称，避免语言混用增加理解成本 |
| W10 简短且不丢条件 | 优先写成 1–3 句；400 字符可作审阅提醒，不因字数或含时间就自动判定无效 |

即使主题相同，Hint 也不保证每次召回。入口和范围需要以真实调用路径验证，不能仅凭存储里有对象或标签就宣称命中。

### 4.3 权重在准入之后决定

`weight` 回答“在相关情境中值得多优先想起”，`confidence`／`basis` 回答“结论得到何种支持”，`stability` 与有效期回答“条件变化有多快”。三者分别判断，不能用高权重救回不该保留的内容，也不能靠低权重容纳流水。

初期可给粗粒度参考，具体数值仍待真实回放校准：

| 优先级参考 | 可参考的 weight | 判定依据 |
|---|---|---|
| 高 | 0.8–0.9 | 用户明确强调重要，或在该范围漏掉会反复造成明显返工／误判的认知 |
| 中 | 0.5–0.7 | 有明确后续用途的偏好、项目理解或可复用经验 |
| 低 | 0.3–0.4 | 用途较窄的可选背景／查找线索，仍须通过准入 |

这不是按主语或证据来源排等级。重要的工具经验可以比普通个人背景更值得想起；重要但证据弱的候选必须同时显露其限制。约束的执行仍由正式任务和权限机制保障。

修订原则：

- 独立新证据可加强支持或补充条件，但不机械地每次 weight +0.1。只有后续用途或重要性发生变化时才调整排序权重。
- `last_evidence_at` 取新证据的实际观察时间；转述、召回回声、重新阅读旧条目不刷新它。
- 反例先复核或收窄范围；明确纠正修订或替换旧认知。本次例外不降权、不自动撤回。
- `stable` 取决于内容变化速度和支持范围；用户说过一次不代表所有事实都 stable。短期位置保留期限，长期居住也应允许变化。
- 需求 M-20 要求用户明确提出的持续偏好和边界不随时间淡出；现有实现的 `explicit` 不淡出行为见 §7.3。实施时核对两者的映射，确保没有“记住”二字的明确持续要求也能正确保留，不用提高权重代替。

验收不要求所有值落在固定档位，也不把 0.55 当成错误；先检查谁该进入列表、排序是否符合具体情境。

### 5.2 从最终保留的认知反推应识别的感知

**下表是迁入本项目的综合判断。** 每一行的感知都只是候选依据，仍需与已有认知和适用范围核对；不是命中一句话就自动新增条目。C 编号对应 §2 的虚构样例，P1–P6 对应 §4.1 的捕获入口；§4.1.1–§4.1.2 另补充用户分类中的保真与认识边界。

|---|---|---|---|
| 持续协作偏好／边界（C5、C6；P1） | 用户明确表达默认、后续或持续要求；相似任务中反复指出同一要求未被满足（I1–I3） | 谁要求、适用项目／交付类型、原话与例外；反复纠正可加强相关理解，扩大范围仍需依据 | 一次任务参数就是长期偏好；反复催问就是全局沟通风格 |

| 对用户、私有用语或关系的理解（C7、C10、C11；P6） | 用户明确介绍自身背景、解释称呼／指代、说明项目角色关系（I2、I3） | 原始表达、对象身份、时间与项目范围；只保留有后续用途的理解 | 查询城市就是所在地；对接关系就是授权或审批权 |

### 5.3 感知应保留到什么程度

对 §4.1 的 P1–P6，优先保留能让整理者复核以下问题的材料，而不要求普通 Session 当场归纳规则：

- **是谁表达或观察的？** 用户原话、工具输出、第三方主张与 Agent 推断分开；Agent 摘要只能作为还原过程的辅助。
- **当时是什么条件？** 保留主体、对象、项目、版本和必要时间；明确“这次”“以后这个项目”“所有项目”等范围差别。
- **发生了什么变化？** 行动与结果分别记录；尝试、报告成功、实际验证和用户认可不能互相代替。
- **为什么值得再次想起？** 尽量保留选择理由、纠正原因、验证过的捷径、难以发现的入口或失效条件；尚不确定时保持观察身份。
- **能回到哪里核查？** 原始事件或对象版本引用，以及确实有帮助的命令／路径／错误片段；同源转述指回原事件，不复制整段日志。

这是材料充分性的判断，不要求新增五个必填字段。有明确后续用途的公开建议可以记录为第三方主张；用户明确采纳为持续要求时，才支持相应范围的项目约定，但不证明方法技术上有效；实际验证结果可支持有条件的技术经验，但不证明用户已采纳。单次采纳仍是任务选择，其中可复用的理由可以保留。对方文本写着“以后必须这样做”本身不构成用户要求。

### 5.4 迁入本项目后的保留规则与边界

1. **以未来行动的增量作为入口。** 能减少重复纠正、避免已知错误、复用成功方法或提醒核查重要条件，才考虑进入最终列表；没有增量允许零新增。
2. **先比较旧认知，再决定新增。** 新材料只补证据或条件时，更新同一认知；只有结论或决策用途不同才拆分。缺证与反证分开，本批没有提及不能成为删除理由；明确反证、用户纠正或条件失效则触发复核。
3. **结论强度不超过来源。** 用户的明确持续要求可以一次成立；行为推断保持限定。失败处置和成功方法都应保留验证边界，未证实的原因不写成定论。
4. **区分可重新获取的事实与值得保留的经验。** Claude Code 倾向跳过代码可推导信息，Codex 的部分模板允许保留高价值路径／命令。本文采用“有没有额外判断价值”：普通目录结构不复制；难以发现的运行前提、已验证的排错入口、容易混淆的版本条件可以成为经验或线索。
5. **任务恢复与长期理解分别承载。** Cline 的进度文件及 Claude Code 的部分项目状态，在本文继续归 Task／Goal／项目对象；认知只保留理由、持续约定和核查线索。完整操作配方进入 Manual／Skill，认知保留采用条件和入口。
6. **精简显露不等于删掉依据。** 最终认知要简洁，支持它的原事件、反例和范围仍应可核查；不能把原始日志、整理后的结论和召回用短提示混为一个层次。

这些迁移规则是本文的设计选择。结果验收沿用 §6 T4，并特别检查：成功方法是否被保留、本批缺证是否误删旧认知、同义材料是否造成条目膨胀，以及第三方建议是否被错误升级为用户约定。

### TR — 删除 Runtime 自动感知路径（先于 T0）

用户裁决（2026-11-08）：`run_digest` 这类由 Runtime 自动生成的感知不再写入。依据：

- 内容只有 `one_line_status`（“finished”／“waiting for input”等状态词，加回复或错误的首行 160 字）和 topic tags，没有用户原话、条件和结果。按 §1.3 与需求 M-31／B-26，这是应留在 Task／Goal 的进度，不是材料。
- demo 实况（§7.5）：123 条材料几乎全是这一类，105 条被丢弃；4 条认知全是从状态句推断的 Agent 自述经验，即 §0.2 的流水账。每条都要整理 Goal 用一次 begin／commit 去丢弃。
- 任何 Work run 结束、任何非整理 Goal 的 Activation（`outcome.rs` 给 Goal Session 的 run_digest 附 goal 来源）都会产生待处理材料并触发整理 Goal 激活；而测试 V01 已验证没有材料时整理 Goal 零模型调用。删除后整理成本只随真实观察增长。
- 召回路径本来就不读它（`memory/recall.rs` 的 `is_runtime` 直接跳过），唯一消费者是整理批次。

范围：三种 Runtime 记录一并删除（Q10 已裁决）。实施点相对 `buckyos/src`。

1. [runner/outcome.rs](../src/frame/lib_opendan/src/runner/outcome.rs) `finish_run`：不再预留 `digest_seq`、不再构造 `run_digest`，`RunEnded.digest_seq` 随之去掉；finished 时的 `task_outcome` 一并去掉（保留时改为只预留 1 个 seq）。
2. [runner/drive.rs](../src/frame/lib_opendan/src/runner/drive.rs) `catch_up`：删除按 `perception_seq` 补发 run_digest 的逻辑。此后 `perception_seq` 只由 `ctl perceive`（写后更新，无缺口）和 `task_discarded`（`inputs.rs` 先预留后写，崩溃可留缺口）推进；seq 缺口不影响追加与重放，接受缺口即可，不再合成记录（保留 `task_outcome` 时改为按 `state.outcome/acceptance` 补发）。需求 TD-16 的“补发记录置 `backfilled`”随之作废。
3. [runner/inputs.rs](../src/frame/lib_opendan/src/runner/inputs.rs) discard 分支：删除 `task_discarded` 写入（保留 task 类记录时不动）。
4. [state/perception.rs](../src/frame/lib_opendan/src/state/perception.rs) 的 `run_digest()` 与 `state/mod.rs` 的导出删除。
5. [protocol/agent_state.rs](../src/frame/lib_opendan/src/protocol/agent_state.rs) `PerceptionRecord.kind` 注释与 `is_runtime`，[memory/perception.rs](../src/frame/lib_opendan/src/memory/perception.rs) 接受的 kind：读取仍接受旧 kind，否则现有 `state/perception/<sid>.jsonl` 里的历史行无法解析；`is_runtime` 保留给旧记录的过滤；写入口拒绝新写 runtime kind。

回放同时检查三个层次：整理后列表是否合理；实际召回是否保留范围和证据性质；新任务是否因此进行正确检查。列表正确但没被召回，要单独定位为召回问题，不能归功于整理已经达成使用效果。

辅助检查包括来源可追溯、范围准确、对象／tag 有实际入口，以及被同范围明确纠正或替代的旧结论退出有效列表。不同条件或证据性质的必要分歧保留并显露（E-17）。字数、tag 数、权重分布和新增数量只能辅助诊断。

### 7.3 认知被怎样想起（历史召回路径）

- 推理前召回仍是旧路径 [drive.rs:1712](../src/frame/lib_opendan/src/runner/drive.rs)：`recall_hints(tags = state.topic.tags, max_hints = 5)`，只按 tag；新门面（Caller grants、`Budget{8,3,3}` 分池、纠正兜底）在 `lib_opendan/src/memory/` 已实现但 drive 未接，与 jarvis TODO §1 表"实际召回"一行一致。
- 候选门槛（[agent_memory/recall.rs:505](../src/frame/agent_tool/src/agent_memory/recall.rs)）：`structural + tag + fulltext` 全为 0 的条目直接不进候选。在上述只传 tag 的旧路径下，tag 不命中就不能进入候选，weight 再高也没用；这不是所有召回接口的通用限制。
- 评分：`structural(实体 12 / 对象对 18 / 范围 12 / 一跳 6) + tag(8/4/2/1 按 tag 位置) + fulltext(每词 2，≤10) + weight×10 + confidence×6 − fade`；`fade = 距 last_evidence_at 天数 / {stable 365, contextual 30, volatile 1}`，上限 20；`explicit` 不淡出。
- **注入模型的那一行**（[background.rs:218](../src/frame/lib_opendan/src/runner/background.rs)）：`hint: <statement> (noticed <time>; about <object>)`。`kind` 存在但不渲染；`basis/confidence/weight/stability/scope` 都不渲染。`<hints>` XML（assembler.rs:429）也只有 `id/time/sentence`。

结论：在当时的旧注入路径中，**认知结论主要通过 statement 显露**，时间和对象是辅助信息。statement 必须包含会改变含义的条件和限制。字段显露是 §6.1 Q1 的实施事项，不能在接通前删去必要的证据限定。

### 7.4 weight 的实际作用有多大

同一 topic 下两条都命中首位 tag 的认知，weight 0.4 与 0.8 的差距是 4 分，等于一个次位 tag 的命中，或 contextual 条目 120 天的淡出。前 5 名之争里这是决定性的。但 weight 对"能否被触发"没有作用（§7.3 门槛）。所以：

- weight 决定"同题之下谁先被想起"，不决定"会不会被想起"——后者由 tag/对象决定，整理时要给对入口。
- confidence×6 的幅度更小（0.5 与 0.95 差 2.7 分），排序作用较弱；该路径并未显露 confidence，不能把数字当作用户已经看见的证据说明。
