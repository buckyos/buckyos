2026-11-18 · 后端已实现，本地 PVE 双 Zone 验收通过 · 代码核对基线 `97669eb28`

群宿主提交变更后，主动通知有成员的远端 Zone。通常只新增一条消息时，宿主随通知发送最新版本和消息，成员 OOD 一次收齐并入库。落后多个变更的成员立即增量拉取。宿主繁忙、推送丢失或节点重启时，成员 OOD 依靠独立运行的低频查询追平，建议默认间隔 **15 分钟**并错峰。推送面向已加入群的远端成员，关闭聊天窗口也应生效。

现场 7 条消息的两端入库间隔为 10.171～30.113 秒。典型样本共 14.417 秒，其中 13.438 秒过去后宿主才收到下一次 `/changes` 请求。修复前，后台每轮维护和同步全部结束后再等 30 秒。原设计 §5.4 已约定按目标 Zone 合并提示，并为校验读权限后携带正文留出了扩展点。[现场记录](https://github.com/buckyos/buckyos/issues/737) · [Self-Host Group v2 §5.3–5.4.1](../doc/message_hub/Self-Host-Groupv2.md#L671-L709) · [后台循环](../src/frame/msg_center/src/group_sync.rs#L1075)

## 实施清单

- [x] **宿主在提交后异步推送。** 从普通消息和群状态变更的提交路径安排推送，复用已有 `group_changed` 触发点，核对成员、Session 变更及删除的通知对象。成员 Zone 从群已有的成员和 Guest 关系确定。按 `(group_did, 目标 Zone)` 合并短时连续更新，限制队列、单次请求大小和发送并发。队列满或目标离线时允许合并到最新状态或放弃本次提示，由成员兜底。慢 Zone 的网络请求在群事务和发送者的 `accepted` 响应之外执行。[消息提交](../src/frame/msg_center/src/group_service.rs#L3397) · [群状态提交](../src/frame/msg_center/src/group_service.rs#L603)
- [x] **定义可验证的“只差一条”。** “版本”指该成员可见的整条群变更流的位置。建议每个读者条目携带其成员周期、前一版本、最新版本，以及从前一版本到最新版本之间唯一可见的消息变更。两个版本均使用绑定群和读者的不透明游标，最新版本可直接用于下次 `/changes?since=…`。当前实现每次查询都会签发新 token，即使位置相同。宿主可复用上次拉取返回或推送成功入库时确认的 token 作为前驱；首次无已知前驱或缓存丢失时先发轻量提示，让一次正常拉取建立基线。例如成员已提交 A，收到 A→B 和消息 m1 后落库并在本次响应确认 B；下一条携带 B→C 和 m2，成员可继续直接入库。单个 `session_seq + 1` 无法排除另一 Session 或成员资格发生变化，原始 `group_seq` 会泄露隐藏 Session 活动量。[变更流](../src/frame/msg_center/src/group_service.rs#L3143-L3202) · [游标读写](../src/frame/msg_center/src/group_store.rs#L131-L175)
- [x] **在发送正文前逐读者授权。** 同一 Zone 可合并为一个请求，携带正文的条目须指明获准的读者。按实际发送时的成员周期、Session/Guest 权限、历史可见区间、客户端策略、`read` Hook 和撤回状态，执行与拉取相同的裁决。排队或重试后重新判定。正文使用原 MsgObject 编码，保留已有 JWT 原文，附件只带对象引用。积压多项、权限上下文不足或变更不适合直接投影时，退回原设计的无正文提示，成员再以自己的身份读取。[读取与投影规则](../doc/message_hub/Self-Host-Groupv2.md#L671-L709)
- [x] **成员 OOD 收到更新后按下表处理。** 用现有 `CrossZoneClient` 和跨 Zone 身份机制投递到成员 Zone 的 msg-center。接收入口按本地 Joined Group 绑定核验群宿主和目标读者。现有群 HTTP 路由先查本地托管群，成员侧须有能找到 Joined Group 的入口。快路径与补拉复用对象校验和投影逻辑，按 `(owner_did, group_did)` 协调提交。对象、副本、成员 INBOX 和新水位在同一事务写入，提交后再发 `box_changed`。保留 host 排序、撤回以及本人发言只记 SENT 的语义。[HTTP 入口](../src/frame/msg_center/src/group_http.rs#L139) · [对象校验](../src/frame/msg_center/src/group_sync.rs#L219) · [投影事务](../src/frame/msg_center/src/group_sync.rs#L587)

| 成员 OOD 收到的更新 | 动作 |
| --- | --- |
| 合法宿主，读者及成员周期匹配，本地已提交游标等于前一版本，唯一变更和正文完整可验证 | 直接投影并推进到最新版本。该条消息从接收到入库，对宿主的回查次数为 **0**。 |

- [x] **独立调度 15 分钟补偿。** 覆盖自动登记和显式配置的 Joined Group，让每个绑定即使一直收不到推送也会轮到。将补偿与邀请过期、入群恢复、DID 发布、对象清理和待上报已读水位分开安排。收窄当前跨网络请求持有的全局 `join_lock`、`sync_lock`，让慢群独立退避，同时保留同一成员同一群的游标和已读更新互斥。补拉满页要继续翻页并给其他群调度机会。客户端当前每次只取 100 项，`/changes.limited` 表示游标失效，不能用来判断还有没有下一页。[动态绑定](../src/frame/msg_center/src/group_remote.rs#L484) · [拉取与锁](../src/frame/msg_center/src/group_sync.rs#L339) · [已读水位](../src/frame/msg_center/src/group_sync.rs#L1212)

## 验收与交付

- [x] **常态。** 用两个 Zone 的正常发消息入口，成员完成初次同步后连续发两条普通消息，每条到达后再发下一条。接收端自动入库，两条各自命中快路径，对应的 `/changes`、`/sessions`、`/objects` 回查均为零。关闭聊天窗口仍入库。真实双节点重复测量宿主提交到成员入库的 P50/P95，健康网络以 P95 ≤ 3 秒为目标，标明实际 RTCP/HTTPS 路径；浏览器展示耗时单列。
- [x] **积压与故障。** 有效游标下积压至少 101 条可见变更，只投一次提示并停止发消息，一次唤醒能补完。覆盖丢失、重复、乱序、断线、双方重启和游标过期。模拟宿主队列满并丢掉最后一次推送，用可控时钟验证即使再无新消息，下一个约 15 分钟的补偿周期仍会补齐。验证无重复投影、水位倒退或额外未读。
- [x] **权限与隔离。** 同一 Zone 两个成员对一条私有 Session 消息的权限不同，只有获准读者能收到正文。覆盖排队期间撤回、移除后重新入群、两条消息之间插入另一 Session 或成员变更，以及异常来源或对象。让一个目标 Zone 超时，验证宿主仍及时接受新消息，其他群仍能收消息、更新已读。
- [x] **成本与回归。** 多群、多成员下记录每个目标 Zone 的推送数、合并和丢弃数、快路径命中数、补拉次数、空闲请求量和峰值并发。以双 Zone 测试夹具验证自动路径，测试中避免手动调用 `group.sync_joined` 掩盖调度问题。在仓库根运行 `cargo test --manifest-path src/Cargo.toml -p msg_center -- --test-threads=1`。随实现更新群设计 §5.4、§11、§14 和后端协议文档，写清线格式、读者版本语义与兜底间隔。[双 Zone 夹具](../src/frame/msg_center/src/test_group_remote.rs) · [投影回归](../src/frame/msg_center/src/test_group_service.rs) · [群后端文档](../src/frame/msg_center/doc/group-v2-backend.md)

## 本次验证记录

指定的 msg_center 全量回归为 256 项通过，0 项失败，1 项因需要真实 Telegram 凭据而忽略。生产入口构建通过，buckyos-api 的 4 项 CrossZoneClient 测试全部通过。

- 两个独立 msg-center、SQLite 库及签名设备通过本机 HTTP 连接。成员完成初始同步后，连续两条普通消息各自直接入库；三类宿主回查均为 0。签名原文、同 Zone 多读者的私有 Session 可见性和重复投递后的已读状态均有断言。超过 32 个近期游标后，成员按持久的逐读者投影记录识别已提交的消息，不触发宿主回查。
- 101 条可见变更分布在六个 Session。断线后一次提示唤醒翻页并追平。另一次测试塞满 256 个发现队列键、丢弃最后一次提示并重启两端，自动绑定和显式绑定在注入时钟的 891900 ms 和 886500 ms 触发补偿，其中失效游标按 Session 补历史。
- 两群、三个 loopback Zone 的故障样本中，B 收到 1 次推送，C 收到 2 次；合并 2 次、队列丢弃 0 次、快投 1 次、提示补拉 1 次，发送峰值并发 2，250 ms 空闲观测窗内请求数为 0。C 的请求延迟并返回 504 期间，另一群的发送、入库和本地已读更新完成。
- 本地 PVE 的反向实测发现，Bob 在 Alice 上已有的联邦登录别名会导致漏推。现按读者 DID 的公开托管关系和 Zone 文档寻址，并在实际发送前重新核对。部署修复后，成员在同一群自动补回了先前漏掉的消息。含本地别名与错误联系人路由的回归已覆盖该场景。

### 本地 PVE 双 Zone 实测

2026-11-18 使用本地 `ssotest` 的 SN（VM 300）、Alice OOD（301）和 Bob OOD（302）验证。两台 OOD 运行同一份 msg-center，SHA-256 为 `46ae4908b58c493e334049d5eadb6912d652ad6ce41735826acc017a93ad4a54`。两端和浏览器运行机均已同步系统时钟。测试复用真实网关、设备签名、verify-hub 和成员 INBOX。

关闭聊天窗口，在初次同步和重启后的基线恢复完成后，通过普通 `msg.post_send` 逐条发送。在成员侧查到上一条后再发下一条，全程由后台推送或自动补拉。时延取 INBOX 的成员投影时间减去宿主接受时间，百分位使用 nearest-rank。下面的传输取自宿主实际成功的 `POST /updates`，回查计数来自成员 OOD 日志。

| 群宿主 → 成员 | 实际传输 | 样本 / 快路径 | 入库 P50 | 入库 P95 | 最大值 | 回查 /changes、/sessions、/objects |
| --- | --- | ---: | ---: | ---: | ---: | --- |
| Alice → Bob | RTCP | 40 / 40 | 119 ms | 135 ms | 166 ms | 0、0、0 |
| Bob → Alice | HTTPS（经 SN） | 40 / 40 | 132 ms | 139 ms | 217 ms | 0、0、0 |
