# BuckyOS AI Workspace 表格数据导入需求

> 整理日期：2026 年 10 月 29 日  
> 主要面向：已有 Excel 等表格工具使用习惯的用户。  
> 本文依据本轮两段口述整理，区分已明确的产品需求、期望支持的能力与待细化事项；不预设解析库、底层存储实现及尚未评估的兼容性承诺。

## 一、背景与目标

BuckyOS AI Workspace 需要让用户方便地使用已有表格数据，而不是要求用户进入 Workspace 后重新建表、重新录入。

用户的数据可能已经存在于 Excel、Mac 上的 Numbers、网页表格，或其他支持表格内容的应用中，也可能以 CSV、Excel、SQLite 文件的形式保存。导入功能应顺应这些现有工作习惯，优先解决“复制后粘贴进来”和“选择已有文件导入”两类需求。

需要注意的是，按照当前产品设定，AI Workspace 的 Table 是具有字段和类型约束的严格二维结构化数据表，而 Excel 更接近自由组织的单元格网格。因此，导入并不只是搬运单元格内容，还需要把原始表头、数据区域和数据类型对齐到 Workspace 的 Table 结构。

整体目标是：**让普通用户接受默认选项即可完成导入，同时为需要控制导入结果的用户保留必要的调整空间。**

## 二、需求范围与定位

| 导入方式或相关能力 | 当前定位 | 主要入口或作用 |
| --- | --- | --- |
| 剪贴板导入 | 已明确；最基础、最常用的导入方式 | 用户复制表格内容后，在 Workspace 中粘贴 |
| CSV 文件导入 | 已明确；基础文件导入能力 | 插入文件、插入表格两个入口均可使用 |
| Excel 文件直接导入 | 明确期望支持；实现难度和兼容范围待调研 | 直接选择已有 Excel 文件导入 |
| 其他常见表格文件格式导入 | 希望评估；具体格式清单待确定 | 根据调研结果扩展文件导入能力 |
| SQLite 文件导入 | 已明确需要支持；具体导入机制待细化 | 从已有 SQLite 文件导入表格数据 |
| Currency（货币）类型 | 本轮提出的新增字段类型需求 | 保留财务类表格中金额与币种的语义 |

其中，剪贴板导入与文件导入是两类主要路径。Currency 是支撑表格数据表达和导入的类型能力，不是独立的导入入口。

## 三、总体交互原则

### 3.1 默认智能，优先完成导入

系统默认应尽可能识别表头、推断字段类型，并将数据整理为合法的目标表格结构。用户不应为了完成一次常见导入，被迫逐列配置所有字段。

### 3.2 简单操作与可控选项兼顾

普通用户接受默认设置即可完成操作；需要调整的用户可以控制表头、字段名称、字段类型等必要选项。

剪贴板导入向导应保持轻量，理想情况下在一屏内完成。即便采用“下一步”的交互，也应让用户沿默认路径顺畅完成导入，而不是把普通导入变成复杂的配置过程。

### 3.3 以结构化数据为导入结果

导入结果应能作为 AI Workspace 的 Table 使用，而不只是保留一个原始文件附件或表格外观。数据需要对齐到 Workspace 的行、列、字段名和字段类型。

### 3.4 不以全部转为字符串代替类型识别

默认策略应尽可能保留数据原有的类型和含义，同时保障目标类型的合法性。对无法可靠识别或与目标类型不兼容的值，具体提示、修正与回退策略需要后续细化。

## 四、剪贴板导入

### 4.1 使用场景与来源

用户在其他工具中复制一块表格内容，然后直接粘贴到 AI Workspace。

需要面向的来源包括：

| 来源类别 | 本轮提到的具体来源 |
| --- | --- |
| 桌面表格工具 | Microsoft Excel、Apple Numbers |
| 网页及在线协作工具 | 网页中的 HTML Table，以及 Notion、Miro 等应用中复制出的表格内容 |
| Workspace 内部 | 从另一个 AI Workspace Table 复制出的表格内容 |

这里的目标是接收这些来源中的表格数据，不等于已经承诺兼容各应用所有专有剪贴板格式。

### 4.2 基本流程

```text
在来源工具中复制表格内容
          ↓
在 AI Workspace 中粘贴
          ↓
出现轻量导入向导
          ↓
接受默认识别结果，或调整必要选项
          ↓
完成导入，得到 Workspace Table
```

粘贴时的向导用于处理自由表格与结构化 Table 之间的差异，而不是要求用户重新录入数据。

### 4.3 表头与字段映射

系统应尽可能识别原始表格中的表头，并将其转换为 Workspace Table 的字段名。常见情况是将首行作为表头，但是否采用该行作为字段名，应允许用户确认或调整。

没有可用表头时，应有自动生成字段名的方式，避免因此阻断导入。具体采用怎样的默认命名规则，留待后续统一确定。

导入后的对应关系为：

| 原始表格内容 | Workspace Table 中的含义 |
| --- | --- |
| 表头 | 字段名称 |
| 一列数据 | 一个字段下的数据 |
| 一行数据 | 一条数据记录 |
| 单元格内容 | 对应字段的值 |

对于合并表头、多层表头、空行、标题区等更复杂的组织方式，本轮尚未确定处理规则，需要在后续兼容性设计中明确。

### 4.4 字段类型识别

默认情况下，系统根据各列的数据内容推断字段类型，而不是将所有数据无差别地转为字符串。

类型识别应同时满足两个目标：一是尽可能保留来源数据的含义；二是导入后的值满足目标字段类型的约束。用户应能够对自动识别的类型作必要调整。

混合类型、缺失值以及不合法值的处理策略，属于后续需要细化的规则。

### 4.5 交互参考

整体操作体验可以向 Miro 的 Copy & Paste 交互靠近：用户先完成自然的复制、粘贴动作，再通过少量必要选项完成导入。

此处记录的是交互参考方向，具体参考哪些界面和行为，需要后续体验与确认，并不要求机械复制其界面。

## 五、Currency（货币）字段类型

### 5.1 引入原因

面向 Excel 用户，特别是财务类工作场景，仅有普通数字类型不足以完整表达金额的含义。货币值需要同时表达金额与币种。

因此，本轮提出为 Table 增加 Currency 类型。

### 5.2 核心语义

每个 Currency 字段具有默认币种。单元格中未显式指定币种的数字，使用该字段的默认币种；单元格中明确给出币种的值，则保留其显式币种。

以字段默认币种为 USD 为例：

| 输入内容 | 预期含义 |
| --- | --- |
| `200` | 200 美元，使用字段默认币种 |
| `RMB500` | 500 人民币，使用输入中明确给出的币种 |
| 带有 `¥` 等货币符号的金额 | 应进入货币识别流程；具体符号的解释和确认规则待细化 |

这一语义意味着：**字段默认币种不应覆盖单元格中已经明确指定的币种。** 同一字段中，使用默认币种的金额和显式指定其他币种的金额，应能够被正确表达。

### 5.3 本轮确定与待细化的边界

本轮确定的是“金额加币种”的表达需求，以及字段默认币种和单元格显式币种之间的关系。

尚需细化的内容包括默认币种如何设置、币种标记如何识别、无法唯一判定时如何确认，以及金额和币种在内部如何存储。

本轮未提出汇率换算、自动统一币种或跨币种汇总规则。这些能力不应被当作货币导入已经包含的功能。

## 六、文件导入

### 6.1 CSV 文件导入

CSV 是本轮明确要求支持的基础文件导入格式，并且需要提供两个并行入口。

#### 入口一：插入文件

用户插入文件时，如果所选文件是 CSV，应能够直接进入表格数据导入流程，将其内容导入为 Workspace Table。

```text
插入文件 → 选择 CSV 文件 → 导入为 Workspace Table
```

这里需要提供的是将 CSV 内容转成可用表格的能力，而不只是把 CSV 作为一个文件放入 Workspace。

#### 入口二：插入表格

用户添加或插入表格时，应能看到“从 CSV 文件导入”选项。点击后打开文件选择器，由用户选择已有 CSV 文件并完成导入。

```text
插入表格 → 从 CSV 文件导入 → 选择文件 → 创建 Workspace Table
```

两个入口应指向一致的 CSV 导入能力，不应因为入口不同而形成两套不同的数据解释规则。

### 6.2 Excel 文件直接导入

直接导入 Excel 是明确的产品期望。用户已有 Excel 文件时，理想体验是直接选中并导入，而不必先手动转换成 CSV。

不过，本轮尚未评估 Excel 及其他常见表格文件格式的实现难度，因此不能将其记录为已经具备或已经承诺完整兼容的能力。

后续需要调研的内容主要包括：具体文件格式的支持范围、解析实现的复杂度，以及工作簿内多个工作表、公式与结果值、格式信息等内容的导入边界。

调研应服务于“尽可能直接导入 Excel”的目标；具体版本范围与实施安排，根据调研结果确定。

### 6.3 其他常见表格文件格式

除 CSV 和 Excel 外，希望评估其他常见表格文件格式的支持可行性。具体格式清单尚未确定。

剪贴板导入中提到 Numbers、Notion、Miro，并不自动意味着本轮已经要求支持这些应用各自的原生文件格式。

### 6.4 SQLite 文件导入

支持从已有 SQLite 数据库文件中导入表格数据。

按照当前口述，Workspace 自身的表格数据结构属于 SQLite 类体系，因此预期这一方向具有较好的实现基础。

此处确定的是 SQLite 文件导入这一产品能力，并不等于已经确定“直接挂载原文件”“复制原文件”或“解析后转换”为具体实现方式。

后续需要明确数据库文件内的表选择、字段与类型映射，以及导入数据如何进入 Workspace 既有的数据结构。

## 七、导入能力之间的关系

剪贴板、CSV、Excel 和 SQLite 的数据来源不同，但最终都需要让数据进入 Workspace 的结构化 Table。

表头识别、字段映射和类型处理存在共通部分，可作为后续实现复用的候选。是否共用同一个导入向导、哪些来源需要额外选项，尚未确定。

当前明确的交互要求是：**剪贴板导入应有轻量向导；CSV 应提供插入文件与插入表格两个入口。** Excel 和 SQLite 的入口呈现及专属配置，应在后续设计中补齐，不在本轮提前锁定。

## 八、后续待调研与待细化事项

| 类别 | 需要确认的问题 |
| --- | --- |
| 剪贴板兼容性 | 各目标来源实际提供的表格数据格式，以及可以保留的信息范围 |
| 表头和字段映射 | 无表头时的字段命名规则，以及复杂表头、非数据区域的处理方式 |
| 类型合法性 | 混合类型、缺失值、不合法值的提示、修正与回退策略 |
| Currency | 默认币种设置、显式币种识别、符号不明确时的确认方式和内部表示 |
| CSV | 编码、分隔符及其他解析差异的处理方式；是否提供额外选项 |
| Excel 及其他格式 | 支持格式、实现难度、多工作表处理，以及公式和格式信息的兼容边界 |
| SQLite | 数据库内多表选择、字段映射和具体导入机制 |
| 统一体验 | 哪些映射与识别能力可以复用，哪些导入来源需要独立配置 |

这些事项用于后续设计和调研，不改变本轮已经明确的基础导入目标。

## 九、基础验收关注点

依据本轮口述，后续实现至少应围绕以下场景验证：

| 场景 | 预期结果 |
| --- | --- |
| 复制常见表格内容并粘贴 | 进入轻量导入向导，接受默认选项即可完成常见表格导入 |
| 导入带表头的数据 | 表头能够映射为字段名，并允许必要调整 |
| 导入不同类型的数据 | 系统尽可能推断字段类型，导入结果符合类型约束 |
| 导入货币数据 | 裸数字采用字段默认币种，显式币种得到保留 |
| 通过“插入文件”选择 CSV | 能将 CSV 内容导入为 Workspace Table |
| 通过“插入表格”选择 CSV 导入 | 能打开文件选择器，并由所选 CSV 创建 Table |
| 选择 SQLite 文件导入 | 能在后续确定的支持范围内，将文件中的表格数据导入 Workspace |

Excel 和其他表格文件格式的验收范围，应在技术调研和支持范围确认后补充。

## 十、需求总结

**以剪贴板导入覆盖最自然、最常用的数据迁移操作，以 CSV 双入口导入提供基础文件能力，以 SQLite 导入衔接现有表格体系，并以直接导入 Excel 为明确扩展目标。**

所有路径都围绕同一个体验目标：用户尽可能少做配置，系统尽可能智能地完成结构映射和类型识别；对于需要控制结果的用户，再提供必要选项。
