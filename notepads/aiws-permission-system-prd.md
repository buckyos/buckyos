**owner 确认的产品需求（2026-11-13）：**

1. 这个版本不调整 UI，先把内核机制做完整。核心 API 已经给 Agent 提供了统一的实体路径，它就是 ACL 里的资源路径。

## 0. 结论

现有模型保留的部分：一套 ACL、9 项能力，授权绑定实体 ID 和子树，沿祖先继承，没有行列级授权（[access.rs](../src/frame/aiworkspace/core/src/access.rs)）。

要改的一条原则：原来“只做加法、没有 deny”，按 owner 的裁决改为引入显式拒绝，拒绝优先（§4.6）。

本版本的主线是六件内核工作：

1. **资源路径（§4.1）。** 授权、查询、审计的接口都用核心 API 的实体路径寻址，存储仍绑定实体 ID。
2. **主体与逻辑组（§4.2、§4.3）。**
   - 授权的主体只有单个调用者和组。组分两类：工作区自己定义的逻辑组；固定组 `@owner`、`@all`、`@guest`、`@creator`。
   - Agent 用自己的身份操作；工作区没有对它单独配置时，按它的 owner 判定权限（R16）。
   - BuckyOS 用户组、联系人组、Zone 全体账号、分享入口，都作为逻辑组成员的来源。
   - 组定义、授给组的条目和宏的组绑定构成“权限设计”，随模板传播；组成员不随模板传播。
3. **允许与拒绝（§4.6）。** 每条授权有允许的能力和拒绝的能力。同一层上拒绝优先，近的层先于远的层（Q21）。
4. **查询与解释（§4.4）。** 按实体看各主体的权限，按主体看资源，解释某项权限由哪一条决定。这是后续 UI 的接口基础，Agent 现在就能用。
5. **宏身份（§4.5）。** 宏默认用运行者的权限；可以绑定组，取并集或交集。本期只做这层抽象，不支持以 owner 身份执行宏，所以并集在本期不会超出运行者自己的能力。
6. **两种发布（R26）。**
   - 不可变发布：把某个版本导出成不可变对象，脱离工作区，交给 ShareContentMgr 按标准流程提供并统计访问；AIWS 读回信息做关联展示。
   - inner-path 发布：把工作区里的一个路径公开出去，内容随工作区更新，仍受工作区权限管理。
   - 两种都登记到 MyContent。

读代码还发现了一批问题（§3），在本版本一起处理：

- **六处可以直接利用的缺陷（§3.1）。** 其中四处不依赖新模型，先修。另外两处由新模型解决：owner 不再是一条授权行（S4）；访客入口改为加入组（S2）。S1 在发布改造（R26）后不复存在，改造前先修。
- **服务内部重建身份时，权限会变宽或变窄（§3.2）。**
- **执行授权与内核文档 08 不一致（§3.3）。**
- **写入可执行代码没有单独的门槛，编辑者可以借管理者打开画布的机会提权（§3.4）。** 要 owner 裁决（Q11）。

## 1. 范围

本版本包括：

- 服务端内核：身份、主体与组、授权与拒绝、可见范围、方法级检查、审计。
- kRPC 协议，以及 SDK / CLI（Agent 使用的接口）。
- 模板格式里的权限设计。
- 分享入口、公开发布、演示会话的内核语义。
- 执行授权（运行、宏、托管、AI 归属）、可执行内容的写入门槛、数据源的授权。

本版本不包括：

- Desktop 界面的调整。§6 列出后续 UI 的需求，以及它依赖的、本版本要先备好的接口。
- 以 owner 身份执行宏，也就是并集提权（Q12）。
- Fork 改名为 Clone 的实施，另见 [工作区 Clone TODO](aiws-workspace-clone-todo.md)。本文只定 Clone 带不带权限设计（R12）。
- verify-hub、SSO、Zone RBAC 本身。AIWS 只使用它们给出的身份、会话上限和用户组。
- Agent 的 appid 统一授权（[Agent＝特殊 App](agent-appid-authorization-implementation-todo.md)）。本文只定 AIWS 一侧怎样认 Agent。
- 资源计量与额度（内核文档 11 第二节）。本文只涉及“由谁承担”。
- 同步程序的执行环境、凭据保管（PRD 第二期）。本文只定它的授权在 ACL 里怎样表达。

原则（内核文档 11）：

- 只有一套 ACL；授权绑定稳定的实体 ID 与子树。组只是主体的组织方式，不是第二个权限引擎。
- 引入显式拒绝，拒绝优先（§4.6）。这修改了内核文档 11 “本版本沿用允许授权的合并模型”一句。
- 不提供行列级授权，用受控提交（提交者字段）代替行级写。
- 由服务端执行，客户端的检查不算数。

### 2.2 调用者

| 调用者 | principal | 能匹配的主体 | 限制 |
| --- | --- | --- | --- |
| 账号（不受限） | 用户 ID | 精确、`public`、`*`、`group:`、`contact:` | 无 |
| 账号（受限，Limited） | 用户 ID | 同上，但不匹配 `*` | 不能拥有（创建、导入、Fork、扩展库、`ws.list_subjects`）；`ws.list` 只列直接授予的工作区；拒绝时只给固定文字 |
| External | DID | 精确、`public`、`contact:` | 同受限账号 |
| 访客 | `guest:<26 字符>`，由浏览器自造的 `gt_` 令牌派生；服务端不发放，令牌不过期 | 精确、`public`，加上所有开放给访客的入口 | 不能拥有，不能加入入口，不能本地运行，不能建会话 |
| Agent | Agent 令牌的 `sub` | 精确、`public` | 可以拥有；不匹配 `*` 和 `group:`；可以本地运行（用自己的 AICC）；能加入演示会话，不能加入分享入口 |
| 其他服务 | 令牌的 `sub`，`app_id` 记应用 | 精确、`public` | 可以拥有；control-panel 可以往别人的扩展库安装 |
| run token（`rt_`） | 运行的触发者，类别是服务 | 精确、`public` | 只能调 13 个方法（`RUN_TOKEN_METHODS`）；不检查运行状态，不过期 |
| 会话链接（`dt_` / `pt_`） | `link:<invite_id>`；`pt_` 在会话里代表演示者 | 精确 | 放在 `sys[1]` 时可以调用任何方法，能做什么由授权决定 |

每个调用者的有效授权都包含 `public` 授权和所有开放给访客的入口模板（`access()` 总是传 `public = true`）。

成员关系：

- `group:` 向 control-panel 查用户设置里的组，`contact:` 问 msg-center。
- 每个请求重新查，不缓存。
- 查不到时拒绝（`authorization_unavailable`），除非调用者已经拥有全部能力。
- 代码：lib.rs `prepare_caller`、auth.rs `resolve_subjects`。

### 2.3 能力

| 能力 | 用在哪里 |
| --- | --- |
| `read` | 所有 `doc.*` 读取、发现、SQL。读不到的实体，父实体可读时报 `PERMISSION_DENIED`，否则报 `NOT_FOUND` |
| `append` | `table.insert_records`；只有 `append` 时只能改、删自己提交的那条记录 |
| `update` | 15 个内容操作；本地运行许愿格；URL 数据源的手动刷新 |
| `delete` | 4 个删除与恢复操作 |
| `structure` | 18 个结构操作（创建、移动、改名、字段） |
| `comment` | 标注；自己的标注和便签 Block 可以改、删、移动 |
| `export` | `doc.export`、`doc.checkpoint`、Fork；导出模板（只检查所选画布） |
| `manage` | 授权、分享入口、公开发布、托管执行配置、删除工作区、维护操作、`entity.set_write_policy`、`entity.purge` |
| `run` | 托管运行许愿格。`may_run` = `run` 或任何写能力 |

### 2.4 方法级检查

没有方法到能力的统一表。`METHOD_LEVELS` 只标 stable / experimental / internal，检查散在各 handler。归纳如下：

| 检查 | 方法 |
| --- | --- |
| 可以拥有（不受限账号或服务） | `ws.create` / `ensure` / `import` / `fork`、`ws.list_subjects`、`ext.*` 扩展库、`create_from_template` |
| 工作区级 `manage` | `ws.delete`、`ws.grant` / `revoke`、`ws.publish` / `unpublish`、`ws.set_hosted_exec`、保留与暂存的清理、`diag.*`、覆盖式恢复 |
| 子树 `manage` | 分享入口、`lock.break` |
| 工作区级 `export` | `doc.export`、`doc.checkpoint` |
| 工作区级 `update` 或 `structure` | 上传资产，包括运行阶段为结果暂存文件 |
| 工作区级 `may_run` | 创建运行记录；看到、预览、应用、取消别人的运行 |
| 有任何授权，再逐实体过滤 | `doc.*` 读取、`ws.get_info`、用户状态、`doc.commit` |

Owner 没有特殊路径：

- 建工作区时，写一条带全部能力的工作区级授权，并在 `local_meta` 里记 owner。
- `ws.revoke` 拒绝删除 owner 的工作区级授权。`ws.grant` 是 `INSERT OR REPLACE`，不检查 owner。
- 没有 Zone 管理员越权的路径。

`tree.move` 只要求被移动实体和新父实体上的 `structure`，不检查移动会不会扩大数据的可见范围。

### 2.5 分享与公开

| 入口 | 谁能建 | 带什么 | 怎样收回 |
| --- | --- | --- | --- |
| 授权行 | 工作区级 `manage` | 任意能力（`public` 不能带 `manage`，`*` 可以） | `ws.revoke`；没有审计记录 |
| 分享入口 | 范围上的 `manage` | 能力模板（不能带 `manage`）；进入方式（访客、密码、自注册、DID 登录）；范围；过期时间 | `ws.close_entry` 让访客失去访问；已加入者的授权写进了各自的授权行，要另行 `ws.revoke` |
| 公开发布 | 工作区级 `manage` | `public` 对一个实体的 `read`，外加 `/pub/<ws>/<name>` 免登录路由 | `ws.unpublish` |
| 演示会话链接 | 会话 owner 或演示者 | `at` 观众、`dt` 显示屏、`pt` 提词器（代表演示者）；没有过期 | `session.revoke_invite` 删除它给的授权行 |
| 放映提词令牌 | 放映开始时生成，只在内存 | `show.command` / `watch` / `notes` | 放映结束 |

### 2.6 执行

| 环节 | 现在的实现 |
| --- | --- |
| 启动 | 许愿格上要有 `update`（本地）或 `run`（托管），并且要有工作区级 `may_run`（`require_run`） |
| 执行身份 | 本地：发起者的浏览器，AI 用发起者的会话；托管：owner 的 Agent，AI 记在 owner 名下。External 和访客不能本地运行 |
| 阶段快照与工具 | 以 `Caller { principal: 触发者, ..Caller::user("") }` 打开 |
| run token | 领取时发放；读取按触发者 principal 的精确授权；不检查运行状态 |
| 应用 | 按应用者的授权检查，写入身份记为触发者。`DELEGATION_STALE` 比较许愿格的 `basis_digest`；`OUTPUT_NOT_DECLARED` 校验落点 |
| 宏 | 浏览器：`sandbox="allow-scripts"` 的 iframe，加 CSP 禁网，再进 Worker，令牌不进沙箱。托管：受限的 Deno 子进程。桥上四种操作：`sql`、`ai.complete`、`llm.map`、`zone.fetch` |
| `zone.fetch` | 浏览器带查看者的 cookie（`credentials: 'include'`），托管带 Agent 的 Bearer；不限方法；`declare.zone` 不强制 |
| 托管配置 | `ws.set_hosted_exec`（`manage`）：Agent、触发者、允许的许愿格、`limits`。Agent 必须是 owner 名下的 |

### 2.7 模板

- 模板是一份快照：所选画布及其子树、Block 引用的数据、扩展定义（服务 README“Workspace templates”）。
- `ext.create_from_template` 装入为新工作区，**不重新映射实体 ID**；创建者是 owner。
- `local.sqlite` 不导出，所以授权、入口、发布都不进模板，也不进 Fork 和普通导出。只有覆盖式恢复会带上原来的授权。

### 2.8 客户端与 SDK

- **授权面板：**
  - 范围只能选“整个工作区”或“某张画布”。画布授权写两行：画布本身和它的内容文件夹。
  - 主体是文本框加下拉，下拉里有 `public`、`*`、Zone 用户和 `group:<id>`（只显示 ID），没有联系人组和 Agent。
  - 能力有四个预设（只读、评论、编辑、管理），也可以逐项勾选。
- **分享对话框：** “公开”开关只作用于整个工作区，固定为 `read` + `comment`。分享入口界面不能设范围和过期时间。
- **能力来源：**
  - 工作区级能力在打开时取一次，在线会话之后不刷新。
  - 实体能力随 envelope 更新。
  - 离线副本把实体能力与工作区级能力取交集。
- **模式：** 没有存过模式时，没有 `update` 的访客默认查看模式，其他人默认编辑模式。查看模式下 HTML 控件自动运行，访客也一样（2026-11-12 起）。
- **HTML 控件：** 在同源 iframe 里运行，不设 `sandbox`；`window.aiws` 的所有调用都走查看者的会话。
- **SDK / CLI：** `buckyos aiws` 没有授权、分享、发布、入口的命令。Agent 只能用 `info` / `stat` 看自己的能力。
- **DID 对象入口：** 经服务自己的 kRPC 入口转调，带调用者的凭据，只读。

### 3.1 可以直接利用的缺陷

**S1 固定版本的公开读取不检查归属（推断）。**

- 问题：`GET /pub/<ws>/<name>?fixed=<content_root>` 只检查对象在不在 named store 里，不检查它属于这个工作区的某个发布，`name` 也被忽略。对象库是整个服务共用的。这条路由免登录。
- 依据：[server source.rs](../src/frame/aiworkspace/server/src/source.rs) `published`、store source.rs `public_fixed_content`。
- 后果：知道一个内容根，就能读到任何工作区的那个版本。内核文档 11 规定“ObjId、名称、URL 都不是凭据”。
- 新模型的解决：R26 的两种发布；改造前按 §8 第 0 步先修。

**S2 开放给访客的入口不要求出示入口 ID。**

- 问题：入口的能力模板加给每一个调用者，不需要出示入口 ID。
- 依据：workspace.rs `access_with`、entries.rs `guest_entry_grants`。
- 后果：
  - 工作区 ID 是 `ws_` + 年月 + 4 位 base36，每月 36⁴ 个，可以枚举。[id.rs](../src/frame/aiworkspace/core/src/id.rs) 的注释说“需要保密的链接另带长参数”，入口 ID 就是这个长参数，但它没有起作用。
  - 不受限账号的 `ws.list` 会列出所有带公开授权或开放入口的工作区。
- 新模型的解决：R8。

**S3 URL 数据源不限抓取地址。**

- 问题：只校验 http(s)、不带用户名口令，不限主机。
- 依据：core [types.rs](../src/frame/aiworkspace/core/src/types.rs) `check_absolute_url`、server source.rs `http_get`。
- 后果：有 `update` 的人可以让服务 GET 回环、内网或 Zone 内的地址，把响应写进工作区。D24 定的是“只做无凭据的公开 URL 抓取”。

**S4 管理者能覆盖 owner 的授权。**

- 问题：`ws.grant` 不检查 owner，可以把 owner 的工作区级授权覆盖成更少的能力；`*` 也可以带 `manage`。
- 依据：workspace.rs `grant_with`。
- 后果：管理者能架空 owner。`ws.revoke` 有保护，`ws.grant` 没有。
- 新模型的解决：`@owner`（§4.2）。

**S5 run token 不过期。**

- 问题：读取时不检查运行状态和尝试编号。
- 依据：lib.rs `run_token_caller`、runs.rs `wish_run_by_token`。
- 后果：运行结束、取消或被新尝试替代以后，旧令牌仍能按触发者的授权读工作区。

**S6 领取令牌外泄，领取不检查领取者。**

- 问题：托管派发失败时，`claim_token` 写进运行详情，能看到这次运行的人都读得到；`proc.claim` 也不检查领取者是不是配置的 Agent。
- 依据：wish/mod.rs `start`、exec.rs `claim`。
- 后果：拿到令牌的人可以领取运行、交回候选，而候选是按执行者的报告被信任的。

### 3.2 服务内部重建身份

| 编号 | 位置 | 现在 | 问题 |
| --- | --- | --- | --- |
| I1 | 运行阶段的快照、阶段工具、宏的 SQL、预检 | `Caller { principal: 触发者, ..Caller::user("") }` | 重建成不受限账号、没有组：受限账号或 External 触发的托管运行多拿到 `*` 的授权；靠 `group:` / `contact:` 授权的协作者在快照里读不到输入 |
| I2 | run token | 类别是服务 | 不匹配 `*` 和 `group:`，与 I1 又是另一套规则 |
| I3 | 数据源定时刷新 | `Caller::user(owner)` | 以 owner 名义写入可以接受，但没有声明这是代行身份 |
| I4 | 数据源手动刷新的写入、会话操作的写入 | `Caller::user(触发者 / 会话 owner)` | 同 I1 |

内核文档 08 要求“缺失所需身份……不回退到系统服务、设备或其他用户的权限”。重建出来的身份既不是原调用者，也不是明确的系统身份。引入逻辑组和拒绝以后，成员关系少算一个组，结果可能从“拒绝”变成“允许”，这个问题会更严重。

## 4. 目标模型

### 4.1 资源路径

- 授权、查询、审计的接口都接受核心 API 的统一路径或实体 ID 作为资源：`/data/销售`、`/surfaces/看板/text-3`、`~<entity_id>/…`。`/` 表示整个工作区，即现在的工作区级授权。
- 写入时把路径解析成实体 ID，并按 ID 保存。改名、移动都不改变授权目标（内核文档 11“稳定目标与继承”）。
- 继承按当前树结构计算，所以移动会改变继承结果。可见范围因移动而扩大时，只在操作记录里写一条（R23）。
- 返回时同时给 `entity_id` 和调用者看到的当前路径。打印规则与核心 API 相同：调用者读不到的祖先不出现，路径从 `~<id>` 开始。
- 解析规则与读取相同，每一步都要可读且未删除。所以管理者只能对自己读得到的实体授权。
- 个人范围和会话范围的实体（`user:<p>`、`participant:<p>`、`presenter`）不能作为授权目标，它们的可见性由范围决定，不由 ACL。
- 审计记录同时记实体 ID 和当时的路径。

### 4.2 主体与组

授权条目的主体（Q1，已定）：

| 主体 | 写法（暂定） | 用途 |
| --- | --- | --- |
| 单个调用者 | principal 原样：用户 ID、External DID、Agent DID、`guest:<id>`。给 Agent 写了条目，就是对它单独配置（R16） | 直接授权，例如“把这张表共享给 Alice” |
| 逻辑组 | `@<组 ID>` | 工作区自己定义的组，按角色授权，例如“老师能改作业表” |
| 固定组 | `@owner`、`@all`、`@guest`、`@creator` | 见下 |

`public`、`*`、`group:<id>`、`contact:<did>#<tag>` 不再直接出现在授权条目里：`public` 由 `@guest` 代替，其余三种成为逻辑组成员的来源。允许 breaking change，不迁移旧的授权行。

**逻辑组。**

- 每个工作区自己定义：稳定 ID（模板作者可以取有意义的 ID，如 `teacher`）、标题、说明。改标题不改身份。
- 成员的来源：

  | 成员 | 匹配谁 |
  | --- | --- |
  | 单个调用者 | 精确 principal，包括 Agent DID。把 Agent 加进组，也算对它单独配置（R16） |
  | BuckyOS 用户组 `group:<id>` | 该系统用户组里的账号；每次请求向 control-panel 现查，与现在相同 |
  | 联系人组 `contact:<did>#<tag>` | 该 owner 联系人组里的 DID；只有该 owner 能加，与现在相同 |
  | Zone 全体账号 `*` | 不受限的账号，不含受限账号、External、访客和服务 |
  | 分享入口 | 经该入口加入的调用者，成员记录带 `via_entry`（R8） |

- 不支持组套组：把组加为另一个组的成员时显式拒绝（内核文档 11）。
- 一个调用者可以同时属于多个逻辑组；冲突时拒绝优先（§4.6）。
- 管理者能看到全部组和成员；其他人能看到自己属于哪些组，不能列出组成员（Q6）。

**固定组。** `@owner`、`@guest` 对应 Linux 的属主和 other；Linux 的“文件属主”在 AIWS 里对应 `@creator`；`@all` 是所有人。不做每个 Block 自己的 `@samegroup`（Q23，已定）。

| 固定组 | 成员 | 规则 |
| --- | --- | --- |
| `@owner` | 工作区的 owner，只有一个人 | 永远拥有全部能力，不能被授权、不能被拒绝、不能被任何操作改变（解决 S4）。由 `local_meta.owner` 决定，不是授权行。查询结果里作为一行出现。不支持转让 owner，与现状相同 |
| `@all` | 能进入这个工作区的所有人：匿名访问打开时 `@guest` 的成员、所有逻辑组的成员、有直接条目的人（Q22，已定；定义待确认，见 Q28） | 不能带 `manage`、`run`。不能删除、不能改 ID，模板可以为它设计授权 |
| `@guest` | 匿名用户，以及已经登录、但不属于任何逻辑组的用户（Q2，已定），包括只有直接条目、不在任何组里的人 | 只在公共匿名访问打开时生效，关闭时整体不生效（Q22，已定）；要给 Zone 内所有账号看，建一个以 `*` 为成员的组。不能带 `manage`、`run`（Q15，已定）。不能删除、不能改 ID，模板可以为它设计授权 |
| `@creator` | 对每个实体，是创建它的那个人 | 授给 `@creator` 的条目，对子树里每个实体分别作用于该实体的创建者，类似 Windows ACL 的 CREATOR OWNER。不能带 `manage` |

`@guest` 按 Linux “other” 的语义，有两个后果：

- 授给 `@guest` 的权限不自动给逻辑组成员。想让所有人都能读，授给 `@all`。
- 组成员退出登录、匿名访问时，仍能拿到 `@guest` 的权限。所以 `@guest` 的权限实际上是所有人的下限；对组成员拒绝 `@guest` 已经有的能力，挡不住他匿名来读。

`@creator` 的用法举例（作业墙）：

- `@学生` 在 `/surfaces/作业墙` 上有 `read` 和 `structure`，可以在墙上新建 Block。
- `@creator` 在 `/surfaces/作业墙` 上有 `update` 和 `delete`。
- 每个学生只能改、删自己建的 Block，看得到别人的，改不了。

`@creator` 需要实体记录创建者（R6）：

- 创建它的那次 Commit 的权限主体；运行的结果记触发者。Agent 按 owner 判定时记 owner，对它单独配置时记 Agent 自己（R16）。
- 从模板、Clone、导入得到的实体，创建者是建立这个工作区的人；覆盖式恢复保留原值。
- 移动、改名不改变创建者。

现有的几处“自己的东西”特例（自己的标注、自己的便签 Block、提交者字段对应的记录）先保留；以后可以改用 `@creator` 表达，不在本版本。

**公开发布与权限配置分开（Q7、Q27，已定）。** 发布有两种：

| | 不可变发布 | inner-path 发布 |
| --- | --- | --- |
| 发布的是什么 | 实体的某个版本，导出成不可变对象 | 工作区里的一个路径，内容随工作区更新 |
| 与工作区的关系 | 脱离工作区体系：之后工作区里的修改、权限变化、删除都不影响它 | 仍受工作区权限管理：发布本身是一条条目，删除、移动、撤销照常影响它 |
| 谁提供内容 | ShareContentMgr，按它的标准流程（Q30，已定） | AIWS，经发布路由；读者不进入工作区 |
| 访问统计 | MyContent | AIWS 记录并报告给 MyContent |

- 两种发布都登记到 MyContent，在那里列出并统计访问。
- 只靠权限配置实现的公共访问（给 `@guest` 写条目）不是发布：不登记到 MyContent，MyContent 也统计不到。
- 发布与公共匿名访问开关无关：发布一个路径，不会打开工作区的匿名访问。
- inner-path 发布的条目，主体是这次发布自己（暂写作 `@pub:<发布 ID>`），只能有 `read`。经发布路由来的读者只带这一个主体，所以它出现在按实体的查询里，管理者能看到、能撤销。

### 4.3 权限设计与模板

权限分成两部分：

| 部分 | 内容 | 随什么传播 |
| --- | --- | --- |
| 权限设计 | 逻辑组的定义；授给逻辑组和固定组（`@guest`、`@creator`）的条目，包括允许和拒绝；宏的组绑定（§4.5） | 模板、Clone、新建导入（`ws.import new`）、覆盖式恢复 |
| 成员与直接授权 | 组的成员；授给单个调用者的条目；公共匿名访问开关；分享入口 | 只随覆盖式恢复；模板、Clone、新建导入都不带 |

理由：组成员和直接授权都是具体部署里的人，换一个 Zone 就没有意义；“老师能改作业表、学生只能提交作业”这样的设计属于工作区本身。

两部分都放在服务控制状态（`local.sqlite`），不进文档的 Commit 历史，不会被内容的撤销撤回；每次变更都写操作记录（Q3，已定；R19）。传播由模板、Clone、导入各自明确地带上。

**模板。**

- `ext.export_template` 导出权限设计。资源按实体 ID 保存（模板实例化不重新映射 ID），同时附路径便于阅读。
- 条目的资源不在快照里的，导出时报告并丢弃。
- 模板里不能有授给单个调用者的条目。
- 导出权限设计要 `manage`；没有 `manage` 的人导出的模板不带权限设计。
- `ext.create_from_template` 原样装入权限设计。所有逻辑组的成员为空；即使模板为 `@guest` 设计了授权，公共匿名访问也默认关闭（Q5）。创建者是 owner。
- 模板清单的 schema（[template.schema.json](../src/frame/aiworkspace/schemas/template.schema.json)）加入权限设计；`aiworkspace_template_dev` 手册同步更新。
- 模板作者可能是 Agent：它为 owner 新建工作区、建组、写条目，再导出模板，全程用路径（R42 的例外）。

### 4.4 有效权限的查询与解释

内核提供三种查询，都按路径寻址：

| 查询 | 回答 | 用途 |
| --- | --- | --- |
| 按实体 | 对这个实体有条目的每个主体（单个调用者、逻辑组、固定组），各自的有效能力和来源：直接在这个实体上、继承自哪个祖先路径、工作区级；拒绝条目也列出，并标明它压过了哪条允许 | 后续 UI“选定实体后查看 / 设置各用户 / 组的权限”；Agent 回答“谁能看这张表” |
| 按主体 | 一个调用者或组的全部条目（路径、允许、拒绝）。对单个调用者，还给出他所属的组及来源：直接加入、经 BuckyOS 用户组、经入口、因不属于任何组而在 `@guest` | 后续 UI“按用户 / 组编辑资源” |
| 解释 | 某个调用者对某个路径的每项能力是允许还是拒绝，由哪一条条目决定 | 排查“为什么他能 / 不能”；验收 |

- 按实体的查询默认按主体列出，不展开组成员。可以选择展开成具体账号：BuckyOS 用户组向 control-panel 查成员；联系人组只列组本身。
- 管理者可以查任何主体、任何实体；其他人只能解释自己，相当于现在 `doc.resolve` 返回的 `capabilities` 再加上来源。
- 写入用一个批量接口：一次提交多条“主体 × 资源 × 允许 × 拒绝”的变更（两者都为空即删除条目），原子生效，写一条审计记录。按主体编辑和按实体编辑都用它。
- 绑定了组的宏（§4.5）在按实体的查询里作为一种来源出现：“经宏 X（组 G，并集）”，同时列出谁能修改宏 X（Q10 的风险提示）。

### 4.5 宏的权限

宏是许愿格的可运行产物（PRD §3.1）。一次运行读写工作区时使用的权限叫“宏身份”：

| 设置 | 宏身份的能力 |
| --- | --- |
| 默认（不绑定组） | 与运行宏的用户（触发者）相同 |
| 绑定逻辑组 G，并集（绑定时的默认） | 触发者的有效能力 ∪ G 的有效能力 |
| 绑定逻辑组 G，交集 | 触发者的有效能力 ∩ G 的有效能力，用来给宏设上限 |

- 并集、交集按能力计算：分别算出触发者和 G 的有效能力（各自按 §4.6 处理拒绝），再取并集或交集。所以触发者被拒绝的能力，只要 G 允许，并集时宏仍然有。
- 不论哪种设置，写入都还要落在宏声明的输出之内（`OUTPUT_NOT_DECLARED`），读取都限于声明的输入（PRD §6.6）。

例子：

- 用户对一个许愿格只有 `run`，没有 `update`。
- 这个许愿格的宏绑定了组 `@报名写入`（并集），该组对“报名表”有 `append`。
- 用户不能直接改报名表；点“运行”后，宏可以往报名表里加一条记录。这个例子要到支持可信执行者以后才能走通（见下）。

**执行权限。** 运行宏要许愿格上的 `run`，或任何写能力（与现在的 `may_run` 相同）。分析和编码会改变宏，要 `update`（R29）。

**绑定（Q10，已定）。**

- 绑定到宏（许愿格）的 ID，不跟宏的版本。宏改了，绑定照常有效。
- 风险：有权修改这个宏的人，等于持有 G 的权限，可以改写宏、借 G 做事。为此：
  - 宏的每次修改进入审计；
  - 按实体查询时，经宏获得的能力旁边列出谁能修改这个宏；
  - 绑定接口的说明里写明这一风险。
- 设置、修改、解除绑定要 `manage`，进审计。
- 绑定的组不能带 `manage`：宏不做管理操作（PRD §6.2）。

**可信的执行者（Q12，已定，本期不做）。**

- 并集给出的、超出触发者自己能力的部分，只在可信执行者上运行时生效。可信执行者是 owner 的 Agent（托管执行），以后也可以是 owner 计算空间里的运行器（PRD §11.3）。
- 原因：本地运行时，宏在触发者自己的浏览器里执行，服务看到的候选结果是浏览器交上来的，无法确认确实出自宏。如果按并集应用，触发者就能借宏的名义直接写入。
- 本期有宏身份的抽象：绑定、并集 / 交集、应用时按宏身份检查。但不支持以 owner 身份执行宏，所以并集在本期不会超出触发者自己的能力；交集照常生效。托管执行仍按现在的方式运行，宏身份同样是触发者。

**读取也按宏身份。** 并集时，宏可能读到触发者自己读不到的输入，结果又会被触发者看到。声明清单列出了全部输入，绑定的人据此判断这是否可以接受。

**应用时检查。**

- 应用按“宏身份 ∩ 输出声明”检查，不按点击应用的人。
- 宏身份在应用时按当前的条目、成员关系和绑定重新计算。
- 只有 `run` 的人可以预览并应用自己触发的运行。

**执行者不是权限来源。** 托管执行的 Agent 只负责执行，它自己的授权不进入宏身份。这修订了内核文档 08 的“托管执行的写权限上限 = 该 Agent 当前权限 ∩ 已确认输出声明”。

**记录。** 运行记录和 Commit 上记触发者、执行者、应用者，以及所用的绑定（组、并集 / 交集）。

**存放与传播。** 绑定属于权限设计（§4.3），按许愿格的实体 ID 保存，随模板、Clone、新建导入传播。

### 4.6 允许与拒绝

按 owner 的裁决（Q1）引入拒绝。条目的形式：

| 字段 | 内容 |
| --- | --- |
| 主体 | 单个调用者、逻辑组或固定组（`@owner` 除外） |
| 资源 | 实体 ID（接口上用路径） |
| 允许 | 能力集合 |
| 拒绝 | 能力集合 |

调用者对实体 E 的能力 c，按下面的顺序判断：

1. 调用者是 owner：允许。
2. 实体的可见范围（`user:` / `presenter` / `participant:`）不让他看：拒绝，与现在相同。
3. 确定调用者的主体集合：自己的 principal、所属的逻辑组、`@all`、不属于任何组时的 `@guest`、E 的创建者是他时的 `@creator`。Agent 没有单独配置时，用它的 owner 的主体集合（R16）。
4. 从 E 开始，沿祖先一层层往上，直到工作区（`/`）。第一层有条目提到 c 的，由这一层决定（Q21，已定）。
5. 在这一层里，按主体的具体程度分三档：单个调用者；逻辑组和 `@creator`；`@guest` 和 `@all`。从最具体的一档看起，第一档有条目提到 c 的，由这一档决定：档内只要有一条拒绝 c，就拒绝；否则允许（Q25，已定）。
6. 一直到工作区都没有条目提到 c：拒绝。

层与层之间的顺序与 Windows / NFSv4 ACL 一致：直接写在实体上的先于继承来的，近的先于远的。同一层里的分档与 POSIX ACL 一致：具名用户先于组，组先于 other。owner 说的“用户属于多个组时明确拒绝优先”是第 5 步的档内规则，因为多个组在同一档。

例子：

- `@老师` 在 `/data/成绩` 上允许 `update`，`@代课` 在同一处拒绝 `update`。一个人同时在两个组里，不能改。
- `@学生` 在 `/data` 上拒绝 `read`，同时在 `/data/公告` 上允许 `@学生` `read`。学生能读公告，读不到 `/data` 下的其他内容，因为近的一层先决定。
- Q21 没有采用的另一种选项（任何一层的拒绝都压过所有允许）做不到第二个例子。

其他规则：

- 成员关系查不到时：如果查不到的组在这个工作区有任何条目（允许或拒绝），就拒绝请求（`authorization_unavailable`）。因为少算一个带拒绝的组，结果可能从拒绝变成允许。owner 不受影响。
- `@guest` 可以被拒绝。
- `@creator` 的条目同样可以是拒绝，例如“创建者不能删除自己提交的作业”。
- 宏身份的并集、交集按 §4.5 的能力计算，在各自应用拒绝之后进行。
- `may_run` 仍然是“`run` 或任何写能力”，在拒绝之后计算。
- 查询与解释（§4.4）要给出每项能力是被哪条条目决定的。

拒绝也覆盖了“私有子树”的需要（M5、PRD §7.4；Q19，已定，不另加“不继承”开关）：

- 只给 owner 看：在子树根上对 `@all` 拒绝 `read`。
- 还要让 Alice 看：在子树根上再允许 Alice 的 `read`。单人条目先于 `@all`（第 5 步），所以她能看。

### 4.7 公式与引用（Q15 的衍生问题）

owner 的问题：用户能读 Block A，A 的值是一个公式，指向用户读不到的 Block B，该怎么办。

现状：公式语言 v1 只能引用同一行的字段，不能引用其他行、其他表或其他 Block（内核文档 07）。没有列级授权，能读这一行就能读到它的所有字段，所以这个问题现在还不会出现。它要在加入跨实体引用之前定下来。

规则（Q24，已定）：

1. **显示求值按查看者自己的权限。**
   - 引用读不到时，结果是明确的“无法读取引用”，不显示成空值、零或旧值。
   - 不显示被引用实体的名字：按路径规则只给 `~<id>`。读不到和不存在看起来一样，与 `NOT_FOUND` 的规则一致。
2. **物化是把 B 的结果放进 A 的唯一方式。**
   - 物化按物化者的权限求值，所以物化者必须能读 B。
   - 写入后成为 A 的普通值，A 的读者都能看到。
   - 物化已经记录物化者和公式（内核文档 07），这相当于一次有记录的复制，与手工复制相同，不需要额外的能力。
3. **需要“读者读不到 B，但能看到由 B 算出的、随 B 更新的结果”时，用绑定了组的宏（§4.5），不用公式。** 公式不是提权的通道。
4. **以后服务端求值时，同样按调用者的权限求值。**

同一原则已经适用于其他引用：Block 显示读不到的数据时显示“不可用”（内核文档 11 “访问者只收到其有权读取的投影”）；视图 SQL 和 HTML 控件的绑定按调用者的权限读取（B-5）。

## 5. 需求（本版本）

### 5.1 资源路径与授权接口

**R1 路径寻址。** 按 §4.1 实现。

**R2 批量授权接口。**

- 每条变更是“主体 × 资源 × 允许 × 拒绝”，结果是替换。

### 5.2 主体与组

**R5 逻辑组的定义与成员。**

- 接口：建组、改标题和说明、删组、加成员、删成员、列组、列成员。
- 都要 `manage`，都进审计；涉及带 `manage` 的组时是 owner 专属（R17）。
- 删组时一并删除它的条目和成员记录。
- 成员的来源与校验按 §4.2；组套组显式拒绝。

**R6 固定组与创建者。**

- 按 §4.2 实现 `@owner`、`@all`、`@guest`、`@creator`。
- 实体记录创建者（`created_by`），规则按 §4.2。允许 breaking change：存储格式升级，旧的工作区按现有做法拒绝打开或由创建 Commit 补出。
- 公共匿名访问的开关要 `manage`，进审计。

**R7 主体收敛与拒绝（Q1，已定）。** 授权条目的主体只有单个调用者、逻辑组和固定组。`group:`、`contact:`、`*` 只作为逻辑组成员出现。条目分允许和拒绝，按 §4.6 计算。

**R8 分享入口改为加入组（解决 S2）。**

- 入口指向一个目标逻辑组，不再带自己的能力模板。范围和能力都由目标组的条目决定。
- 已登录的人经入口加入时，成为目标组的成员，成员记录带 `via_entry`。
- 访客经入口进入时，服务把他的 `guest:<id>` 加为目标组的成员，同样带 `via_entry`。只凭工作区 ID、不出示入口 ID 的人得不到任何东西。
- 经入口加入后，他属于一个组，因此不再在 `@guest` 里（Q2）。
- 入口可以设过期时间和人数上限（匿名入口的限流，内核文档 11）。
- 关闭入口时，可以选择同时移除经它加入的成员。
- 目标组带 `manage` 的入口不允许建立。
- 不受限账号的 `ws.list` 只列自己有条目或是成员的工作区，不列仅因匿名访问才能进入的。

**R9 owner（解决 S4）。** 按 §4.2 的 `@owner` 实现：owner 由 `local_meta.owner` 决定，不是授权行。

### 5.4 身份

**R13 调用者表。**

- 把 §2.2 的调用者种类、能匹配的主体和限制，按新模型改写后写进内核文档 11，作为正式契约。
- 新增调用者种类时，同时更新这张表和 R24 的调用者矩阵。

**R14 代行身份。** 服务代替某人做事时（运行阶段、数据源刷新、会话写入），使用代行身份：

- 带原调用者的类别、是否受限，以及成员关系的来源。
- 成员关系（包括逻辑组和 `@guest`）在使用时重新结算；结算不了按 §4.6 的规则处理。
- 不再用 `Caller::user(x)` 重建身份。
- 确实以服务自己名义做的事（如会话时间线、维护清理），使用明确的内部身份，并在 R13 的表里列出它能做什么。

**R15 run token 的有效期。**

- 只在所属尝试仍是当前尝试、运行未结束时有效；按 R14 的代行身份读取。
- 白名单按 owner 2026-11-12 的裁决保持不变（PRD §6.5、权限优化 TODO B-2）。

**R16 Agent（Q18、Q26，已定）。**

- Agent 仍用自己的身份调用 AIWS，principal 是它的 DID。
- AIWS 经 BuckyOS 确认调用者是 Agent，并取得它的 owner。owner 来自可信来源：AgentSpec，或 [Agent＝特殊 App](agent-appid-authorization-implementation-todo.md) 落地后的令牌声明；不信任请求参数。
- 工作区的权限里对这个 Agent 做了单独配置（有条目提到它的 DID，或把它加进了逻辑组）时，在整个工作区里都按 Agent 自己判定：只要有一次配置，它在这个工作区就立刻成为一个独立的主体（Q29，已定）。
- 想“只限制某个目录”：在 `/` 上允许它需要的能力，再在那个目录上拒绝。
- 删除对它的全部配置后，回到按 owner 判定。
- 否则按它的 owner 判定：主体集合、组成员关系、`@owner` 都按 owner 计算。
- Commit、操作记录、运行记录上记 Agent，同时记按谁判定（owner 或 Agent 自己）。
- 按 owner 判定时，Agent 新建的实体，创建者记 owner，这样 owner 自己也能按 `@creator` 修改；单独配置时记 Agent。
- Agent 新建的工作区归它的 owner（Q26 的建议，owner 没有另行说明）。
- 现在 Agent 是独立的服务类调用者，只按自己的条目判定，还可以自己拥有工作区。这些都要改。

### 5.5 管理与审计

**R17 owner 专属操作（Q9，已定）。** 只有 owner 能做：

- 把 `manage` 授给单个调用者或组；把成员加入带 `manage` 的组；
- 删除工作区；
- 配置托管执行（用的是 owner 的 Agent 和 AI 额度）；
- 覆盖式恢复。

其余 `manage` 操作，管理者可以做：建组、加减不带 `manage` 的组的成员、写不带 `manage` 的条目（包括拒绝）、分享入口、公共匿名访问开关、公开发布、宏的组绑定、维护操作。

**R18 能力上限。** `@all`、`@guest`、`@creator`、入口的目标组、宏绑定的组都不能带 `manage`；`@all`、`@guest` 和入口的目标组不能带 `run`（Q15，已定）。inner-path 发布的主体只能有 `read`。

**R19 操作记录（A-3，Q3）。**

- 以下变更都写一条只追加的记录，内容是谁、何时、对象（实体 ID 和当时的路径）、改前、改后：
  - 条目变更（允许和拒绝）；
  - 组的建立、修改、删除，成员变更；
  - 公共匿名访问开关；
  - 入口的建立、关闭、加入；
  - 发布与撤销；
  - 宏的组绑定，以及已绑定的宏的修改；
  - 托管配置；
  - owner 专属操作；
  - 因移动而扩大的可见范围（R23）。
- 管理者可读。
- 不随导出传播。

**R20 条目的维护。** 资源实体被永久删除（purge）时，一并删除它上面的条目；普通删除时保留，以便恢复。

### 5.6 授权检查

**R21 方法表。**

- 为全部 kRPC 方法建一张声明式的表，写明：
  - 所需能力；
  - 判断位置（工作区、目标实体、owner、可以拥有）；
  - 允许的调用者类别。
- dispatch 按表检查，README 的方法表由它生成。
- 这与 operations.json 对 Commit 操作的做法一致。

**R22 按实体判断。**

- 下列检查从工作区级改为目标实体：
  - 启动运行：运行阶段要许愿格上的 `run`（或写能力）；分析和编码要 `update`（R29）。
  - 看到和应用运行：许愿格上的 `update` 或 `manage`，或者是自己发起的运行。
  - 为结果暂存文件：输出位置的写权限。
- 放映加锁：只有工作区级写权限才加全局锁，只有子树写权限的人按只读放映处理。
- 仍需要工作区级检查的，在 R21 的表里写明理由。

**R23 移动与复制（Q8，已定）。**

- 移动照常执行，不增加门槛。
- 如果移动后有主体新获得了对被移动实体的能力（新位置继承到的条目不是原位置的子集），在这次 Commit 的记录里写一条“可见范围扩大”：哪些主体、新得到哪些能力。同一条也进入操作记录（R19）。
- `tree.clone` / `entity.clone` 复制出的新实体按新位置继承，不带针对旧实体的条目，创建者是复制的人（内核文档 11、§4.2）。

**R24 调用者矩阵（B-1）。**

- 对 R13 的每种调用者，测试它能看到什么。覆盖的读取入口：
  - 发现（`ls` / `find`）、文本查询、SQL、路径解析、`body`；
  - 对象入口；
  - 资产路由、发布路由。
- 状态要覆盖：经逻辑组获得权限、经 BuckyOS 用户组、被拒绝条目压过、`@guest`（匿名与已登录的非成员）、`@all`、`@creator`、Agent（没有单独配置时按 owner 判定，单独配置时按自己）、inner-path 发布的读者、撤权之后、成员关系查不到时、入口关闭之后、匿名访问关闭之后。

**R25 泄露（B-3、B-4、B-5）。**

- 修 §3.5 的 V1–V4。
- V5：幂等重放之前，先确认调用者仍能访问这个工作区。
- 搜索索引不存可见性，查询时过滤（B-4）。
- SQL 的逻辑表范围等于可读的表（B-5）。

### 5.7 公开发布与演示会话

**R26 两种发布（Q7、Q27，已定）。** 按 §4.2 的表实现：

- **不可变发布：**
  - 把实体的某个版本导出成不可变对象，交给 ShareContentMgr，由它完成标准流程：快照保留、分享链接或公开、到期、停止、访问统计（Q30，已定）。这需要 `share.create` 接受对象作为来源，现在它只接受文件系统路径。
  - AIWS 读回分享信息，在实体上做关联展示：哪些版本发布过、链接、状态、访问量。
  - 之后工作区里的修改、权限变化、删除都不影响它；停止、到期在 MyContent 里管理。
  - 格式按 Q27 的建议 A：表导出为 CSV 或 JSON，富文本导出为 Markdown 或 HTML，资产用原文件。
- **inner-path 发布：**
  - 由现在的 `ws.publish` 演变而来：发布记录，加一条主体为 `@pub:<发布 ID>`、只有 `read` 的条目。
  - 读者经发布路由（`/<workspace>/<name>`、`/kapi/aiworkspace/pub/...`）读到当前内容，不进入工作区，不需要打开匿名访问。
  - 撤销发布、删除实体、对该主体拒绝，都会让它读不到。
  - 现在 `ws.publish` 写的是 `public` 主体的授权，访客因此也能在工作区里打开这个实体；改造后发布的读者只能走发布路由。
- **登记与统计：**
  - 两种发布都登记到 MyContent。
  - inner-path 发布的访问由 AIWS 记录，报告给 MyContent。
  - 这需要 MyContent（ShareContentMgr）一侧提供登记和统计上报的接口，与 MessageHub、HomeStation 回传分享结果的做法类似。
  - 只靠 `@guest` 条目的公共访问不登记，也不统计。
- **数据源：** 工作区之间、Zone 之间的数据源，读 inner-path 发布（实时）或不可变发布（固定版本）。
- **固定版本（S1）：** 只来自不可变发布（按 ObjId），或 inner-path 发布实体的历史版本；`?fixed=<root>` 的其他取值一律 404。改造完成前，先按 §8 第 0 步修。

**R27 演示会话。**

- 链接可以设过期时间。
- 撤销观众链接时，经它加入的参与者失去会话访问（Q17，已定）。
- `presenter` 必须是 Zone 内的 principal。
- `session.save` 的说明与代码对齐。

### 5.8 执行

**R28 宏身份（§4.5，Q10、Q12 已定）。**

- 实现默认、并集、交集三种宏身份。应用按“宏身份 ∩ 输出声明”检查，不按应用者。
- 绑定接口：设置、修改、解除；要 `manage`，进审计。绑定到宏 ID，不跟版本。
- 已绑定的宏被修改时进入审计；按实体查询时列出谁能修改这个宏。
- 本期不支持以 owner 身份执行宏：并集不超出触发者自己的能力，交集照常生效。
- 托管执行的 Agent 不需要工作区的写授权：它凭领取令牌和 run token 执行，领取者由 R30 限定。
- E2（只有 `run` 的协作者通过宏完成受限写入）要等可信执行者，本期之后做。

**R29 只有 `run` 的人只能触发“运行”阶段（Q13，已定）。**

- 分析和编码会把触发者的文字交给模型，并产生新的宏版本，所以只开放给许愿格上有 `update` 的人。
- 这同时解决 E8。

**R30 委托与托管配置（Q16，已定）。**

- 删除授权上没有用到的 `task_digest` / `outputs`，以运行上下文为准。
- 应用时复核托管配置摘要（配置变了按 `DELEGATION_STALE` 处理）和上下文有效期。
- 执行 `limits`：每日次数、工具轮数。
- `proc.claim` 只接受配置的 Agent（托管）或发起者本人（本地）。
- 领取令牌不出现在运行详情里。

**R31 记录应用者。** Commit 和运行记录同时记触发者、执行者、应用者。

**R32 `run_id` 的使用。** 只有 `proc.apply` 能写带 `run_id` 的 Commit；`doc.commit` 带 `run_id` 时拒绝。

**R33 落点。**

- 落点的根只来自许愿格的输出声明和它自己的结果。
- `location` 只决定放在哪张画布，并且必须在声明的画布内。
- 输入实体不是可写的根，除非同时被声明为输出。

**R34 宏访问 Zone 的身份与方法（Q14，已定）。**

- `zone.fetch` 只允许 GET / HEAD。
- 目标必须写在 `declare.zone` 里，由宿主强制。
- 带执行者的凭据，维持现状。

**R35 AI 缓存按归属隔离。** `llm_cache` 的键加上 AI 归属的用户，一个人的执行者不能写入别人的运行会命中的条目。

**R36 `run` 的上限（Q15，已定）。** `@all`、`@guest` 和入口的目标组都不能带 `run`。匿名提交（例如公开报名表）用已有的受控提交（提交者字段 + `append`）满足。

**Q5 的答复：工作区、画布能否匿名访问，不需要在网关登记。**

- 所有 `aiws-<id>.<zone>` 主机名，在网关里折叠到同一个 `aiws` 条目，按服务转发（[boot_gateway.yaml](../src/rootfs/etc/boot_gateway.yaml) `get_app_info_from_req`）。scheduler 也只登记这一个条目（[system_config_agent.rs](../src/kernel/scheduler/src/system_config_agent.rs)）。
- 按服务转发时，网关不做鉴权：`permit_check` 只检查 App 访问服务的黑名单，请求不来自 App 时直接放行。身份全部在 AIWS 服务里判断。
- 所以匿名能否访问，只由 AIWS 的匿名访问开关和 `@guest` 的条目决定，不会出现“权限上有、网关里没有”的情况。
- App 的 `access_mode: public` 是另一回事：它只用于 App（网关的 `check_oauth`）。AIWS 是服务，不经过它。
- 另外需要满足的是 Zone 级的条件：Zone 能否从外网到达（SN、公网地址），以及 `aiws-<id>` 子域名的证书。这些对所有工作区都一样，不是逐个登记。
- 两种发布（R26）同样不需要在网关登记：inner-path 发布走 AIWS 自己的发布路由，不可变发布由 ShareContentMgr 提供（Q30）。

## 9. 验收

| 场景 | 通过条件 |
| --- | --- |
| 路径 | 用路径写条目后，改名、移动实体，条目仍跟着实体；查询结果给出新路径 |
| 逻辑组 | 建组“老师”，把一个 BuckyOS 用户组加为成员，在一张表上允许 `update`；该用户组里的账号能改这张表，从用户组移除后立即不能 |
| 拒绝 | 一个人同时在允许 `update` 的组和拒绝 `update` 的组里（同一层），不能改；`@学生` 在 `/data` 上被拒绝 `read`、在 `/data/公告` 上被允许时，学生能读公告，读不到 `/data` 下的其他内容 |
| `@guest` | 匿名访问打开时，匿名访客和不属于任何组的已登录用户得到 `@guest` 的权限；他加入一个组后不再得到；匿名访问关闭时 `@guest` 的条目对谁都不生效，再打开后恢复 |
| `@all` | 授给 `@all` 的 `read`，组成员和有直接条目的人都能读；匿名访问打开时，匿名访客也能读 |
| `@creator` | 作业墙：学生能新建 Block，能改、删自己建的，不能改、删别人建的 |
| `@owner` | 任何条目都改变不了 owner 的能力；管理者不能授予 `manage`、不能删除工作区、不能配置托管执行 |
| Agent | 工作区没有对 Agent 单独配置时，它拥有 owner 的能力；给它的 DID 写了条目后，按这些条目判定；Commit 上记 Agent，同时记按谁判定；Agent 修改权限要经审批门 |
| 私有子树 | 子树根上拒绝 `@all` 的 `read`、允许 Alice 的 `read`：owner 和 Alice 能读，其他人不能 |
| 入口 | 只凭工作区 ID、不出示入口 ID，进不去；经入口进入的访客成为目标组成员；关闭入口并选择移除后，他失去访问 |
| 模板 | 带组、条目（含拒绝）和宏绑定的工作区导出为模板，再创建新工作区：设计都在、成员为空、匿名访问关闭；模板里没有任何单人条目 |
| Clone | 有 `manage` 的人 Clone 出的工作区带组和条目、不带成员；只有 `export` 的人 Clone 出的不带权限设计 |
| 查询与解释 | 对一张表按实体查询，能列出直接条目、继承自画布的条目、工作区级条目、拒绝条目，来源正确；解释某个账号的某项能力时，指出决定它的那条条目，以及他经哪个组、哪个 BuckyOS 用户组进入这个组 |
| 移动 | 把一张表从只有老师能看的文件夹移到全员可见的画布：移动成功，操作记录里有一条“可见范围扩大” |
| 操作记录 | 每次条目、组、成员、匿名访问开关、入口、发布、宏绑定、托管配置的变化，都能查到谁、何时、对象路径、改前、改后 |
| 变更流 | 条目变化后，打开着的会话收到事件 |
| 宏身份 | 交集：管理者运行绑定了交集的宏，写入不超出组的条目。并集：本期本地运行和托管运行都不超出触发者自己的能力。修改已绑定的宏进入操作记录，按实体查询时列出谁能改它 |
| 只有 `run` | 不能发起分析和编码；看不到别人的运行 |
| 不可变发布 | 发布后修改或删除工作区里的实体，已发布的内容不变；MyContent 列出它并统计访问；工作区里能看到这个实体发布过的版本、链接、状态和访问量 |
| inner-path 发布 | 读者经发布路由读到当前内容，不进入工作区，也打不开工作区里的其他实体；撤销发布后读不到；MyContent 列出它并有访问统计 |
| 权限配置的公开 | 只靠 `@guest` 条目公开的内容，不出现在 MyContent |
| 固定版本 | 改造前：未登录请求 `/pub/<ws>/<name>?fixed=<另一个工作区的内容根>`，得到 404 |
| 抓取地址 | URL 数据源指向 `127.0.0.1`、私网地址、Zone 主机，或重定向到这些地址时，刷新失败，原因可读 |
| 代行身份 | 受限账号触发的运行读不到只授给 `*` 成员组的内容；经逻辑组获得权限的协作者触发的运行能读到输入；被某个组拒绝的输入，在运行里同样被拒绝 |
| run token | 运行结束、取消或被新尝试替代后，旧令牌的读取被拒绝 |
| 子树授权 | 只在一张画布上有编辑权的协作者，能启动、预览、应用画布内许愿格的本地运行 |
| 可执行内容 | 没有 `manage` 的人写入或修改 HTML / JS 代码被拒绝；未信任的定义不在查看模式里自动运行 |
| 宏 | `zone.fetch` 的 POST、或访问未声明的 Zone 路径，被拒绝 |
| 调用者矩阵 | R24 的矩阵全部有用例，并进入 CI |
| CLI | Agent 用路径查看一张表的权限、解释自己的权限；在自己新建的工作区里建组并写条目；在 owner 的其他工作区里改权限要经审批门 |
