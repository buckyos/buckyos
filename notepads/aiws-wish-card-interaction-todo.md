## 0. 结论

- 许愿格的全部操作都在卡片上完成，不再打开右侧面板。卡片从上到下是标题、一行状态描述、当前 tab 的内容；左下是四个 tab（愿望、需求、宏、结果），右下是下一步按钮，右上是运行按钮。
- 四个 tab 对应内核已有的三个阶段和它们的产物：愿望是用户写的原文，需求是分析的产物，宏是编码的产物，结果是运行的产物。
- **没有“应用”这一步。** 每个阶段跑完就直接写入，下一个 tab 里马上能看到内容；没有错误就可以继续下一步。用户看过觉得有问题，切回上一个 tab 重跑。
- 写入不再事先问用户，改成事后能退回：**每个 tab 当前生效的那条记录上有“回滚”**，回到上一个版本。结果被人工改过也照样覆盖，靠回滚找回。
- 验收检查没通过算警告还是错误，**由模型判断**：分析时给每条检查定级别。
- 除了愿望，每个 tab 显示这个阶段的摘要记录，最新的在上。**历史存在许愿格自己的数据里**，随工作区走；历史记录里的链接打开的是当时的内容。
- 分析会自己找输入。**找不到输入算运行失败**，用户到许愿格的属性面板里手工绑定后重跑。
- 画布上自动画两种虚线箭头：输入 Block 到许愿格（浅蓝），许愿格到结果 Block（浅橙）。它们是画布按数据算出来的装饰，不是连接线实体；在许愿格的属性里可以关掉。
- 删除许愿格的模拟执行器和开发者工具里的受控处理 Mock。旧数据不兼容、不迁移，三个内置模板跟着升级。之后另立项增加 Agent 执行器，本文保留 `executor` 字段和 `agent-work-session` 这个取值。
- 内核的改动有七处：阶段结束时由服务直接写入（去掉候选确认和 `proc.apply`）、编码只保存宏、缺输入的分析记为失败、验收检查带级别、许愿格数据里加历史、按运行记录回滚、执行器上报 token 用量和模型名。其余是 Desktop 的改动。

## 3. 设计

### 3.1 卡片

- **标题**：Block 的标题，沿用现在的取法。
- **状态描述**：一行文字，取内核的主状态和它的第一条原因，例如“需要分析：愿望在上次分析后改过”“结果已过期：销售明细有更新”“上次分析失败：找不到输入”。运行中显示阶段和正在做的事。现在卡片上的执行器标签、新鲜度徽标、“正在右侧面板中编辑”都去掉。
- **内容区**：当前 tab 的内容，超出时在卡片内滚动。
- **左下**四个 tab，**右下**下一步按钮，**右上**运行按钮。
- 卡片不再分“静态卡片”和“打开后的面板”两套内容，画布、流式页、数据源详情、数据模式用同一个组件。
- tab、下一步按钮、运行按钮在设计模式下也能直接点，不受 `interactive` 限制。它们是 Block 自己的操作，不是内容。在卡片空白处按下拖动仍然是移动 Block。未选中时第一次点击是直接生效还是先选中，M0 按[标准对象的交互改进](<../doc/workspace/标准对象的交互改进.md>)的状态规范定。
- 画布缩得很小时只画标题、状态和运行按钮。
- 默认尺寸沿用 420×300，最小尺寸要放得下四个 tab 和按钮。

### 3.2 四个 tab 与下一步按钮

| tab | 内容 | 什么时候可点 | 这个 tab 上的按钮 |
| --- | --- | --- | --- |
| 愿望 | 愿望原文，有权限时直接编辑 | 总是 | 分析需求（已有当前的需求时是“重新分析”） |
| 需求 | 分析的摘要记录 | 有过分析（含失败的） | 编写宏代码（已有可用的宏时是“重新编写”，上次运行因宏出错时是“修复宏”） |
| 宏 | 编码的摘要记录 | 有宏，或者有过编码（含失败的） | 执行宏 |
| 结果(N) | 运行的摘要记录。N 是累计构造出结果的次数 | N 大于 0，或者有过失败的运行 | 执行宏 |

- 不可点的 tab 标题是灰色。失败的记录也算“有内容”，否则用户看不到为什么失败。
- 后面的阶段因为前面的修改而失效时（§3.5），tab 仍然可点，标题上带过期标记，记录保留。
- 每个 tab 里当前生效的那条记录上有“回滚”，回到上一个版本（§3.4）。
- 按钮只在它是内核给出的下一步时是主按钮样式；其余时候是普通样式，前置条件不满足时置灰并写明原因（例如在“需求”tab 上：“愿望已修改，先重新分析”）。
- 阶段进行中，按钮变成“取消”。运行被中断且本浏览器能恢复时，按钮是“继续”。
- 重跑就是切回前一个 tab 再点它的按钮：对需求不满意，回“愿望”点“重新分析”；对宏不满意，回“需求”点“重新编写”；对结果不满意，回“宏”或留在“结果”点“执行宏”。
- 没有 `update` 能力的人看不到下一步按钮。只有 `run` 的人本期不能运行（权限 Q31），不变。
- 默认停在哪个 tab，跟着内核的下一步走：

| 下一步（`next_action`） | 默认 tab |
| --- | --- |
| 分析 | 愿望 |
| 编码 | 需求 |
| 运行，从未有过结果 | 宏 |
| 运行，有过结果；或者没有下一步 | 结果 |
| 进行中 | 正在跑的那个阶段的产物所在的 tab |

  一个阶段结束时跳到它的产物所在的 tab（分析结束跳“需求”，编码结束跳“宏”，运行结束跳“结果”），失败时也跳，让用户看到失败记录。其他时候用户切到哪就停在哪。

### 3.3 阶段跑完直接写入

owner 的裁决（Q1）：“应用”这个按钮是今天交互复杂的原因之一，没有应用了。跑完后下一步的 tab 里可以看到内容，结果没有错误就可以继续下一步；用户看过觉得有问题，或者警告比较关键，手工切回上一个 tab 重跑。

| 阶段 | 跑完后写入什么 | 接着 |
| --- | --- | --- |
| 分析需求 | 需求（任务契约和找到的输入），加一条历史 | 跳到“需求”，按钮是“编写宏代码” |
| 编写宏代码 | 宏（源码和声明清单），加一条历史。试运行的结果不写进文档，试运行的情况（产出几项、检查通过几项）写在这条记录里 | 跳到“宏”，按钮是“执行宏” |
| 执行宏 | 结果和 `last_run`，加一条历史，累计次数加一 | 跳到“结果” |

- 写入由服务在阶段结束时完成，一个阶段一次提交。发起运行的那个窗口把这次提交记进自己的撤销栈，做法同现在应用之后。
- 运行是谁发起的、以什么身份写入、用谁的 AI 额度，规则都不变。
- 原来要用户在候选里做决定的事，改成固定的处理：

| 情况 | 现在 | 改为 |
| --- | --- | --- |
| 计划有硬问题（输出位置不存在、结果类型不能原地转换、超出单次提交上限等） | 不能应用 | 运行失败，什么都不写，记录里写原因 |
| 运行期间许愿格或它的输出被别人改动 | 应用时冲突 | 运行失败，提示重跑 |
| 验收检查没通过 | 勾“接受”才能应用 | 看这条检查的级别（D2，见下）：错误级的没通过，运行失败，什么都不写；警告级的没通过，照常写入，写在记录最前面 |
| 结果被人工改过 | 选保留、覆盖或另存 | 直接覆盖，作为警告写明覆盖了哪几项人工修改。想找回就用这条记录的“回滚”（D3，§3.4） |
| 会删行或删字段的结构变化 | 勾确认才能应用 | 直接执行，作为警告写明删了什么。这种情况少见，运行通常只是新建或更新 Block（D4） |
| 对编码候选“按反馈修改” | 在候选里输入反馈 | 入口去掉（D5）。要改就回“愿望”改原文，或者在属性里加补充要求，再重跑 |

- **检查的级别由模型判断**（D2）。执行宏时没有模型在场，所以级别要在这之前定下来：
  - 分析阶段，模型写验收检查时给每条标上级别，错误或警告，随任务契约保存。
  - 编码阶段，模型看到试运行的检查结果后继续修；交付时仍有错误级的检查没通过，编码失败，不保存宏。
  - 执行宏时，服务按检查的级别机械处理，如上表。
  - 人工复核类的检查不参与判定，原样列在记录里。
- 失败的运行也写一条历史（一次只含这条记录的提交，不进撤销栈）。取消的运行不记（D7）。
- 分析的结论是“缺输入”时记为失败：不写回需求，失败记录里写明哪个输入找不到（Q4、D6）。主状态里的“缺输入”和下一步“补充后重新分析”去掉，用户到属性里绑定输入后点“重新分析”。
- 随之去掉的东西：
  - 运行状态 `waiting_confirmation`、`conflict`、`rejected`；主状态“待确认”和下一步“应用”。
  - 接口 `proc.apply`，以及 `proc.get` 带选择重新预览的用法、每个运行保留的几份计划。删掉受控处理 Mock（§3.10）之后，`proc.apply` 没有别的调用方。
  - Desktop 的 `WishCandidate.tsx`、`WishPreviews.tsx`，`WishService` 的 `preview`、`apply`、`discard`。
- 内核保留 `feedback`、`parent_run_id` 这两个运行参数（“修复宏”还要用 `parent_run_id`），只是界面不再提供反馈入口。

### 3.4 摘要记录与历史

一条记录对应一次运行。示例：

> **11-14 15:02**　根据 `愿望` 执行“分析需求”（48 秒 · 输入 12,340 / 输出 1,205 token · gpt-6-astra）成功：要生成 3 项结果。**没有找到成本列，利润率无法计算。**
> 输入：`销售明细` `区域目标`　产出：`任务契约`

> **11-14 15:10**　根据 `需求` 执行“编写宏”（6 分 12 秒 · 输入 88,410 / 输出 9,330 token · gpt-6.1-sol）成功：试运行产出 3 项，4 项检查通过。
> 输入：`销售明细` `区域目标`　产出：`宏 a3f9c2`

> **11-14 15:12**　根据 `宏 a3f9c2` 执行“运行”（3 秒）成功：新建 2 项，更新 1 项。
> 输入：`销售明细` `区域目标`　结果：`季度汇总` `区域排名` `异常清单`

规则：

- 警告、未通过的警告级检查、被覆盖的人工修改写在摘要最前面并加重。失败的记录写失败原因，缺输入时写明是哪个输入。
- 运行阶段只有宏用了 AI 才显示 token 和模型。
- 最新一条展开，更早的折叠成一行，点开看全文。

**历史存在哪**（Q2）：许愿格自己的数据里。许愿格载荷新增 `history` 键，随工作区克隆、导出、备份一起走，能读许愿格的人都能看到。

- 每条记录直接存小字段：`run_id`、阶段和动作（分析、编码、修复、运行、回滚）、开始时刻、耗时、发起人、用的是谁的 AI 额度、用量（模型名、输入和输出 token、调用次数）、成败、错误码和原因、警告列表、各条检查的级别和结果、摘要文本的素材、输入列表（各自读到的版本）、产出（宏的摘要值；各结果的名字、实体、Block、生成的版本号、是新建还是更新）、这次写入的提交号。
- 大块内容存成工作区里的对象，记录里只放引用：当时的愿望原文、当时的需求（任务契约全文）、当时的宏源码和声明清单、宏的输出日志。
- 宏的输出日志读取时要求对许愿格有 `update`，因为它可能打印出读者无权读的输入里的内容；摘要文本里也不写输入的内容（D9）。
- 每个阶段保留最近 20 条，超出时丢最旧的。累计次数单独记，不受上限影响。存为模板时不带历史（D8）。
- 部署本地的运行记录表照旧，只当运行期间的工作记录（进度、领取、租约），不再是历史的来源。数据模式的“运行记录”页改读 `history`。

**链接打开的是当时的内容**（Q2）：

| 点的是 | 最新一条记录 | 更早的记录 |
| --- | --- | --- |
| 愿望 | 弹窗：这次分析依据的原文 | 同左，是那一次的 |
| 需求、任务契约 | 弹窗：任务说明、产出约定表、验收检查 | 同左，是那一次的 |
| 宏 | 弹窗：代码，等宽字体带行号（复用 `ProgramView` 的页面形态）；有权限时可以编辑 | 那一版的代码，只读 |
| 日志 | 弹窗：这次运行的输出日志 | 同左，是那一次的 |
| 结果名 | 画布移到它的 Block 并选中；不在本画布就按现有的 `openEntity` 打开 | 只读打开那次运行生成的版本；它就是现行版本时同左 |
| 输入名 | 同结果名 | 当时读到的版本还取得到就只读打开那个版本；取不到就跳到 Block，并注明“这次运行之后有改动” |

- 手机上弹窗都是整屏。已删除或无权读的对象置灰并说明。
- 只读打开某个历史版本，现在的界面只有列出版本和恢复，没有查看，要补一个版本查看的弹窗。

**回滚**（D3）：owner 的要求是能通过运行记录回滚上一个版本，这样结果被人工改过也可以直接覆盖。

- 每个 tab 里当前生效的那条成功记录上有“回滚”，需要 `update`。更早的记录没有；回滚之后上一条成为当前，可以接着回滚。

| 回滚的是 | 效果 |
| --- | --- |
| 结果 | 这次运行写入的内容退回运行之前：更新过的结果回到上一个版本（包括被覆盖的人工修改），这次新建的结果和它的 Block 删除，`last_run` 回到上一次 |
| 宏 | 宏回到上一版（源码和声明清单取自上一条成功的编码记录）。已有的结果因此显示为过期 |
| 需求 | 需求回到上一版（取自上一条成功的分析记录）。之后愿望一侧若已改动，需求仍然是失效的 |

- 回滚是一次普通提交，进发起窗口的撤销栈。历史里加一条“回滚”记录，被回滚的那条保留并标为“已回滚”。结果的累计次数不减。
- 运行之后那些内容又被改过时（别人编辑了结果，或者做过版本恢复），回滚先说明会丢掉哪些后来的改动，确认后执行。
- 托管给 Agent 的运行没有人替它撤销，回滚是这种情况下的退路：对许愿格有 `update` 的人都能回滚。
- “宏”和“需求”的回滚是我顺着同一条规则加的：没有了候选，重新编写或重新分析的产物直接生效，原来“放弃候选”的退路要靠它补上。

字段从哪来：

| 字段 | 现有来源 | 缺口 |
| --- | --- | --- |
| 时间、动作、成败 | 运行的 `created_at`、`stage`、`parent_run_id`、`state`、`error` | 无 |
| 根据 | 分析：`analysis.prompt`。编码：证据里的 `basis`。运行：宏的摘要值 | 编码和运行要明确记下依据的是哪一次分析、哪一版宏 |
| 耗时 | `executed_at − created_at` | 失败的运行没有 `executed_at`，要记结束时刻 |
| token、模型 | 无 | 执行器上报（M2）。宏运行的 AI 调用只有输出 token |
| 摘要文本 | 分析：`summary`、`warnings`。编码和运行：`summary`、`warnings`、`assumptions`、检查结果、计划里各结果的动作 | 现在由面板各处分别拼，要统一成一条生成规则；素材存在记录里，文字按读者的语言生成 |
| 输入列表 | 证据里的 `read_set`、`inputs`、`appended_inputs` | 无 |
| 产出 | 分析：任务契约。编码：`candidate.program`。运行：`result_bindings` | 结果要带上生成的版本号 |

### 3.5 修改前一步时的失效提示

内核已经有失效的判定，界面要做的是在写入之前告诉用户后果。用户能改的只有愿望一侧的内容和宏代码；需求不能手工改（Q3）。

| 修改的是 | 后面已经有 | 提示 | 内核里的实际后果 |
| --- | --- | --- | --- |
| 愿望原文；属性里的长期知识、补充要求、输入 | 当前有效的需求 | “该修改会让需求失效”；还有宏时是“需求和宏”；还有结果时再加一句“已有的结果会标为过期” | `needs_analysis` 为真，重新分析之前不能编码也不能运行宏 |
| 手工改宏代码 | 结果 | “该修改会让结果过期” | 结果记录的配置摘要与现在不同，显示为过期 |

- 后面没有结果时不提示。
- 提示有“继续修改”和“取消”，取消时恢复原文。一次编辑只问一次。
- 修改本身是普通提交，撤销后内核重新判定，失效标记随之消失。

### 3.8 运行日志进状态栏

- **收起的状态栏**：本窗口只有一个运行时显示一行，例如“销售分析 · 编写宏 · 正在试运行 · 42 秒”；多个时沿用现在的“N 个运行中”。

- 运行结束后，“运行中”那一块消失，工作日志里已有开始和结束两条，不变。

### 3.9 连接线

这两种线是画布根据许愿格的数据算出来的，不是实体：不保存，不能选中、编辑或删除，不进大纲，不随 draw.io 导出，不参与打印。

| 线 | 从哪到哪 | 样式 | 数据 |
| --- | --- | --- | --- |
| 输入线 | 输入的 Block → 许愿格 | 浅蓝虚线，箭头在许愿格一端 | `payload.inputs`；Block 是本画布上 `source_id` 等于输入实体的那个，表格视图输入用它的 `selector.cell_id` |
| 结果线 | 许愿格 → 结果的 Block | 浅橙虚线，箭头在结果一端 | `last_run.result_bindings` 里各结果的 `cells`，取在本画布上的 |

- **虚格**：输入在本画布上没有 Block 时（在别的画布、只在数据树里、是文件夹），在许愿格左侧画一个固定大小的半透明正方形，里面是类型图标和名字，输入线从它出发。多个时竖排，超过 4 个收成“+N”。点它按 `openEntity` 打开那个对象。输入已删除或无权读时带警告标记。虚格也是装饰，不能移动。
- 同一个输入在本画布上有多个 Block 时，只连离许愿格最近的一个。
- 每个结果 Block 一条线；同一个分组里超过 6 条时合成一条，指向分组。结果不在本画布上时不画，也不用虚格，“结果”tab 里能点过去（Q5）。
- 派生列（结果写回输入表）时，同一对 Block 之间有一蓝一橙两条线，错开画。
- 走线和箭头的计算复用 `ui/canvas/connectors/` 的 `layout.ts` 和 `paint.ts`，随 Block 的移动和缩放实时更新；线画在 Block 下面，不挡点击。
- 编辑和查看模式都画，流式页和放映舞台不画。用户在许愿格的属性里关掉“显示连线”后，这个许愿格的线和虚格都不画（Q6）。
- 看不到的东西不泄露：调用者读不到的输入只画成带警告的虚格，不显示名字。

## 7. 风险与未核对

- AICC 的返回里有没有输入 token 和实际命中的模型名，没有核对。现在浏览器只读了输出 token（`executor/infer.ts`）。取不到实际模型名时只能显示逻辑名（如 `llm.code`）。
- 历史记录引用的对象（当时的宏源码、需求、日志）怎么登记才不会被回收，没有核对。现行宏的源码也是对象引用，可以照它的做法。
- 输入“当时读到的版本”能不能再取出来，没有核对。结果实体每次生成都留版本；表格这类输入不一定有可读的旧版本，取不到时只能跳到现在的 Block。
- 没有了“应用之前什么都不写”的约定：覆盖模式下，一次运行直接改已有的结果，包括覆盖人工修改（D3）和删行删字段（D4）。退路是运行记录上的回滚，所以回滚要可靠：它依赖运行之前的版本还在。派生列写回输入表、结果是控件实例这两类写入，能不能按版本退回没有核对，退不回的要在 M0 找出来并另想办法。
- 回滚时运行之后的改动会被一起退掉（别人后来对结果的编辑）。设计是先说明再确认，说明要列得出具体丢什么，不能只给一句笼统的提醒。
- 检查的级别由分析阶段的模型定（D2），定错了有两种后果：该拦的没拦住，或者不该拦的让运行一直失败。后一种用户只能改愿望重新分析，没有手工改级别的入口（需求不能手工改，Q3）。
- 服务在阶段结束时自己提交，发起的浏览器关掉也会写入。原来关掉浏览器的后果是候选一直等着，现在是结果已经写了而用户没看到，要靠工作日志和记录让他知道。
- 失败记录也是提交（D7），反复失败会给工作区的提交历史添噪声。
- 卡片在设计模式下直接响应点击，与“内容在设计模式下不响应”的通用规则不同，要确认不影响拖动、框选和连接线吸附。
- e2e 迁到脚本模型后，用模板许愿格的用例会变慢，脚本模型要能应付三个模板的愿望。
- 删掉 `proc.apply` 是对已标为 stable 的接口做破坏性改动，契约 fixture、README、手册要一起改。
- 连线多的画布（许愿格多、每个输入输出也多）的绘制开销没有估。
- 跨仓库：用量上报要改 `buckyos-websdk` 的 CLI；Zone 里的 CLI 发行版要重新打包，托管执行才有用量。

### 8.1 契约（M0 T0-1、T0-2）

- 运行状态：`queued → snapshotting → running → validating → applying → succeeded | failed`，另有 `cancelled`、`interrupted`；去掉 `waiting_confirmation`、`conflict`、`rejected`。阶段结束由服务规划并提交，一次提交写入阶段产物和一条运行记录，幂等键 `run/<run_id>`；重启后 `applying` 的运行按幂等记录对账（已提交 → 成功并补记录，未提交 → 中断）。
- `proc.apply` 删除；新增 `proc.rollback { run_id, confirm? }`（stable，需要对许愿格有 `update`）：只回滚该阶段当前生效的成功记录（否则 `NOT_CURRENT_RECORD`）；运行之后又有别人改过时答 `{ status: needs_confirm, lost: [{ entity_id, type_id, title?, what }], hidden_lost }`，确认后提交并答 `{ status: accepted, commit, record }`。运行视图去掉 `candidate`、`preview`、`simulated`，加 `record`；`proc.report` 收 `usage { model, input_tokens, output_tokens, calls }`。
- 许愿格载荷 `history { analyze[], code[], run[], results_count }`：每阶段 20 条、最新在前、整体不超过 1 MiB，只许服务写（人手写入 `PERMISSION_DENIED`）。记录字段见 README “Run records”。大内容存成工作区资产：`objects.prompt`（当时的愿望原文）、`analysis`（`{ analysis, inputs }`）、`program`（写进载荷的 `program` 值）、`source`（宏源码资产本身）、`log`（宏的输出日志，最多 256 KiB）。
- **历史对象怎么不被回收**（T0-2）：`core/src/types.rs` 的 `asset_object_ids` 列出 `history` 引用的对象，保留、导出、物化都走它；`log` 的引用种类是 `log` 而不是 `asset`，`can_read_asset` 对它要求对许愿格有 `update`（D9）。
- **检查的级别**（T0-2 字段名）：`WishCheckDef.level: error | warning`，程序检查必须给，复核检查可省。
- **回滚各类写入用什么退回**（T0-2）：结果用该次提交存下的逆操作（`commit_ops.inverse_json`，去掉对 `history` 的部分），确认后或没有后来改动时把 `expect` 换成 `"any"` 做内部提交——新建的结果、Block、分组、派生列的字段、控件实例都有逆操作；“后来的改动”按 `commit_ops.touched_json` 找，排除已回滚的运行提交和回滚提交本身。宏和需求按上一条成功记录存下的对象设回，当前值与记录不同算后来的改动。§7 里“派生列、控件实例能否按版本退回”的疑问由此解决。
- **记录的警告**（T0-2 摘要文本规则）：模型给的是原文字符串；服务自己给的是 `{ code, …参数 }`（`check_failed check_not_run uncited_numbers overwrote_manual overwrote_manual_cells deleted_rows deleted_field changed_type changed_structure not_produced recreated_column discarded_edits`），Desktop 的 `ui/wish/records.ts`（`describeRecord`、`warningText`）按读者语言生成整条记录的文字。
- **用量**：§7 第一条核对过，AICC 返回 `usage.input_tokens / output_tokens` 和 `route_trace.final_model`。模型阶段由执行器累加每轮、随 `proc.report` 上报（浏览器 `executor/chat.ts`、`localExecutor.ts`；托管时 Agent 用 `run-report --model --input-tokens --output-tokens --calls`）；宏的 AI 调用由 `aiws.js` 的 `aiStats` 计数（新增 `input_tokens`、`map.tokens`、`models`），服务写运行记录时汇总，宏没用 AI 时不写。运行中的进度里带阶段模型名（`progress.model`）和 `waiting_model`。
- **未选中时的点击规则**（T0-2）：卡片上的 tab、下一步按钮、运行按钮、记录里的链接与回滚、愿望输入框第一次点击就生效，不改变选择（与标准对象的交互改进 §4.2 的悬停按钮一致）；卡片其余地方按普通对象，按下选中、拖动移动。许愿格没有编辑态。

### 8.3 偏差（实施中定的，待 owner 过目）

1. 编码记录的 `usage` 只算编码模型循环，不含试运行里宏的 AI 调用。
2. 编码阶段仍暂存试运行的结果文件（用来当场拒绝工作区里没有的文件），但不写入文档。编码不再写结果之后，HTML 结果的代码由编码后的第一次执行宏写入，只写摘要与声明清单 `code_digest` 一致的代码。
3. 失败记录的提交是以工作区 owner 身份的内部提交（记在运行的发起人名下），幂等键 `run/<id>/record`；回滚提交是按调用者授权的内部提交，幂等键 `rollback/<rb_id>`。克隆或导入的工作区里，旧记录的提交不在，回滚答 `NOT_UNDOABLE`。
4. 内部写入 `analysis`（撤销、回滚）时保留它带的 basis，不重算；否则愿望改过之后回滚需求会被误判为“当前”。
5. 回滚判断“后来的改动”时不算许愿格自身；编码追加补充要求后重述了分析，此时回滚需求算有改动、要确认。
6. `proc.start` 的 `session_id` 作为阶段提交的会话（写锁按它判断），Desktop 已传。
7. 连线：“+N”点开在原地展开全部虚格；读不到的输入即使画布上有 Block 也只画警告虚格；端点按矩形算；多选拖动时线在松手后更新。
8. 单选许愿格时工具栏不再显示 AI 入口（原来是“打开许愿格”）。
9. 卡片的最小尺寸没有强制（registry 没有按类型的最小尺寸），窄卡片（≤400px）tab 一行、按钮另起一行。
10. 宏只生成图片 / 视频时，记录里有调用次数，没有模型名和 token（`ai.image` / `ai.video` 的答复不带）。
